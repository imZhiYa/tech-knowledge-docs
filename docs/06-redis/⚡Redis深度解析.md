<a id="level-1"></a>
## Level 1：Redis 的"快"不是品牌，是跨介质墙的物理账

🧵 进度：`Level 1/9 · C 尚未出发，先看它为什么要出发`

### Why —— 只留 MySQL 硬顶，延迟地板被焊死

**徒弟**：不要 Redis 行不行？MySQL 加几个只读实例，连接池调大，顶不住再加机器，反正能水平扩。

**老陈**：扩，可以用钱解决；**延迟，不行**。先算一笔物理账（全部为数量级教学参考，以你的硬件实测为准）：

- 主存读一次：约 **百纳秒** 级；
- 企业级 NVMe SSD 随机读一次：约 **百微秒** 级——中间隔着 **10³**；
- MySQL 即便全命中 buffer pool，一条 SQL 还要过协议解析、SQL 解析、优化器、事务与 MVCC 快照、锁管理，纯 CPU 开销在微秒~毫秒级。

这不是 MySQL 差——它是一个**通用 ACID 数据库**，这些开销是它的责任。而库存计数、会话、排行榜这类热点小数据只需要一本字典。大促零点，库存计数 QPS 冲到几十万（教学场景），线程全堵在 InnoDB 行锁与页闩上排队，连接池打满，雪崩。钱烧了，延迟纹丝不动。

| 朴素方案 | 它本来想解决什么 | 它留下的致命账 |
|---|---|---|
| 只留 MySQL，靠只读实例 + 连接池硬顶 | 数据只有一份真相，永远没有一致性问题 | 延迟地板被"介质 + 通用数据库执行栈"焊死在微秒~毫秒级；加实例只能买吞吐，买不到延迟 |

### What —— Remote Dictionary：服务进程内存里的那本字典

```text
一次读的时间成本（数量级教学参考，以实测为准）
 L1/L2 cache   ~ 1–10 ns    ┃ ← 纳秒墙
 DRAM 主存     ~ 100 ns     ┃    Redis 住在这里：数据就在服务进程的 DRAM 里
 NVMe SSD      ~ 100 µs     ┃ ← 微秒墙
 机械盘寻道    ~ 10 ms      ┃ ← 毫秒墙
 跨机房网络    ~ 若干 ms     ┃    MySQL 的下限在这里：介质墙 + SQL 执行栈

Redis = Remote Dictionary Service：
把热点小数据从通用数据库里抽出来，放进一个专用进程的 DRAM，
用 O(1) ~ O(log N) 的字典操作提供读写。
```

> 📌 最容易被误解的一点：缓存**不是免费加速**，它是**用一致性换延迟**。数据从此有两份，"以谁为准、多久收敛"这笔账在这一层就欠下了——到决策卡 1（cache-aside + 失效路径）才偿还。

### How —— 主线 C 的一生（Level 1 段：出发前）

```text
① 应用线程：SET sku:1001:stock 42
② 客户端库把 C 序列化为 RESP3 字节流
③ write() → 本机内核 → 网卡 → 对端 6379

本层关键点：数据的位置，从"另一台机器磁盘上的 B+ 树页"，
            变成"目标机器服务进程内存里的一个桶"。
            这一步只负责"换介质"，不解决"并发怎么处理"——那是 Level 2。
            （本层无并发语义，线性化点从 Level 2 才开始定义。）
```

**徒弟**：为什么非要多一个进程？直接在 MySQL 里开一块内存做字典不行吗？

**老陈**：MySQL 的内存被通用性绑架：buffer pool 换页策略、MVCC 版本链、行锁表锁，全是它的职责。一个专用字典进程才能把职责收窄到一件事——用最快路径读写小对象，并且把持久化、复制这些"剩余能力"设计成**可开关的取舍**，而不是默认全开的包袱。

### Transfer —— 这一层能带走什么

1. **评估任何加速方案，先问"跨过了哪面介质墙，跨了几个数量级"**——跨不了墙的优化都是小数点游戏。
2. **凡是把同一份数据放两个地方的方案，一致性问题与它同时出生**。设计时必须同时给出失效路径，不允许"先上线再说"。
3. **DRAM 单位成本显著高于 SSD**（具体倍数随采购价浮动，以你的报价单实测）→ 容量必然受限 → 逼出 Level 4 的"过期与淘汰"。

**本层新账**：内存易失（Level 5）＋ 数据两份的一致性（决策卡 1）。

> 🔴 **口诀：内存是主存，磁盘只是备份**

<a id="production-cache"></a>
### 生产入口补充：一次业务读请求的分层路径

> 这不是新增 Level，而是把 Level 1 的"用一致性换延迟"落到线上。这里不另立主线角色，只画业务请求经过的层；主线 C 仍负责展示一条命令在 Redis 内部如何生效。

**为什么不能把所有请求都直接打 Redis：**

- 全打 DB：真相只有一份，但读放大先把数据库的 IO、连接池和锁竞争打满。
- 全打 Redis：延迟低，但内存成本、一致性窗口、Redis 故障时的全站回源都变成新的账。
- 全放本地缓存：命中最快，却无法跨实例全局失效；十个实例就是十份可能不一致的副本。

```text
读路径：
业务请求
  └─▶ 本地缓存（进程内，零网络）
        ├─ 命中 → 返回
        └─ 未命中 → Redis（共享层，一次网络往返）
                       ├─ 命中 → 回填本地 → 返回
                       └─ 未命中 → DB（最终数据源）
                                      └─ 回写 Redis；允许时再回填本地

写路径（Cache-Aside）：
DB 事务成功 → 删除 Redis key → 本地缓存短 TTL 自愈
                         └─ 删除失败 → 重试队列 / 延迟双删 / CDC 补偿
```

| 一致性档位 | 适合的层 | 典型策略 | 必须承认的账 |
|---|---|---|---|
| 零容忍 | DB 直读或 DB 原子能力 | 不把库存、余额、扣款状态放进本地缓存 | 延迟与数据库容量 |
| 可忍短窗口 | Redis 共享缓存 | 中等 TTL + DB 变更主动删除 | 删除失败与回源重建 |
| 可忍更长窗口、极热且变化少 | 本地缓存 | 短 TTL（如 1–5 分钟，仅为示例，须按业务签字） | 无法全局失效，只能自愈 |

**写后为什么删除而不是直接更新缓存：**并发更新可能乱序——后写 DB 的请求先写缓存，先写 DB 的旧值反而后到，旧值覆盖新值。删除把下一次读变成一次受控回源；如果删除动作本身失败，必须有补偿，不能吞掉异常。

**本段留下的新账**：缓存失效并不只有"命中/未命中"两种平静状态；不存在的 key、成批同时过期、单热点瞬间过期，会分别长成穿透、雪崩、击穿——见 [Level 4 补充](#production-resilience)。

- [ ] 知道一个线程的栈内存与一次上下文切换的大致量级（教学量级：MB 级 / 微秒级）？
- [ ] 能解释为什么"多个线程对同一计数器 INCR"必须串行化临界区？

### Why —— "一连接一线程 + 共享哈希表加锁"死在哪

**徒弟**：来一个连接开一个线程，大家共享一张哈希表，读写加锁，多核全用上，不比单线程强？

**老陈**：思路不坏，我们算账。第一笔，**内存**：一个线程栈默认 MB 级（教学量级），一万条长连接就是 GB 级栈内存，还没干活先吃饱。第二笔，**CPU**：一次上下文切换是微秒级成本（教学量级），一万个线程在几十核上每秒百万次级切换，cache 还互相污染，CPU 大半时间在搬家而不是干活。第三笔，**锁**：热点 key（比如那个库存计数）上，全局锁把所有核串成一颗；细到 per-key 锁，锁元数据又随 key 数膨胀。三笔账合起来：连接数一上五位数（C10K），系统不是"变慢"，是**延迟虚高且抖动不可预测**——这对收银台是政治性死亡。

| 朴素方案 | 它本来想解决什么 | 它留下的致命账 |
|---|---|---|
| 每连接一线程 + 共享表加锁 | 用满所有核；编程模型直观 | 线程栈内存爆炸；切换风暴；热点 key 上锁竞争把多核退化成单核，还附赠不可预测的毛刺 |

### What —— 单 Reactor：一个店长 + 一只感应门铃

```text
      ┌──────────────────────── Redis 主线程 ────────────────────────┐
      │                                                              │
      │  epoll_wait（门铃） ──醒──> 读事件：readQueryFromClient 读/解析 │
      │       ▲                                  │                   │
      │       │                                  ▼                   │
      │  serverCron              lookupCommand → call() 执行 ──dirty++──┐
      │  （每班抽查，L4/L5）              │                          │
      │       │                          ▼                          │
      │  beforeSleep/flush：AOF 写出  ←  回包进输出缓冲，注册可写事件   │
      │                              复制 propagate → 分店（Level 6） │
      └──────────────────────────────────────────────────────────────┘
      命令执行永远只有一个线程 → 每条命令的执行天然原子，INCR 不需要锁。
```

> 📌 最容易被误解的一点："Redis 单线程"的精确含义是**命令执行单线程**。后台一直存在 bio 线程（文件关闭/fsync 等）、fork 出的落盘子进程，以及 6.0 起可选的 io-threads（并行做读、解析、写回）。但**执行阶段始终串行**——io-threads 及 8.0 的 IO 重写属于「代码组织变化」，不改变这一语义（对照勘误表 #1）。

### How —— C 的一生（Level 2 段：进店到出店）

```text
① epoll_wait 返回：6379 上那个 fd 可读（门铃响）
② readQueryFromClient：字节读入查询缓冲，按 RESP3 切出完整命令
   （一次读不完就存着，下次接着拼——半包/粘包在这里被吸收）
③ lookupCommand：在命令表里找到 "set" → setCommand
④ call()：通用前置检查 → setCommand：
      校验参数 → tryObjectEncoding → dbAdd/dbOverwrite 写全局 dict（Level 3）
      → dirty++（账本计数，Level 5 用）→ signalModifiedKey
⑤ "+OK" 追加进该 client 的输出缓冲，注册可写事件
⑥ epoll 报可写 → writeToClient 发出去

★ 线性化点：第 ④ 步改 dict 的那一瞬间。
  因为同一时刻不存在第二个正在执行的命令，
  全系统所有命令构成一个全序，序 = 主线程的执行顺序。
```

**徒弟**（针对最反直觉的一步）：第 ②③ 步读包解析，不也可以并行吗？为什么只准 IO 并行、执行不许？

**老陈**：可以，6.0 起确实这么干了（`io-threads-do-reads` 🔒 默认关，开之前压测）。但注意收益边界：大多数命令本身就是纳秒~微秒级的内存操作（教学量级），并行执行它，唯一的新增物是锁——**没有任何加锁方案能在 O(1) 操作上比"不加锁"更快**。胖 value 的字节搬运才是真正贵的那部分，所以并行被精确地安放在 IO 上。

### Transfer —— 这一层能带走什么

1. **IO 与计算分离**：可并行的只有无状态的字节搬运；有机状态（共享内存）的部分串行——Netty、Node、Nginx 是同一个思想。
2. **串行带来的免费原子性是资产**。评估"上多线程"之前，先列出你会失去什么：原子性、可预测性、无锁。
3. **事件循环公理：循环之内不许慢**。任何 O(N) 命令都是全体连接的延迟——[坑「盘库」](#pit-keys)就是它的第一个标本。
4. **打包三条路——都在这条流水线上做文章**（五维总表与三类错案见[坑「打包混用」](#pit-batching)）：
   - **Pipeline**：纯网络打包，省 RTT（N 次往返 → 1 次收发）；批内每条命令仍各自走上面的六步、**各有自己的线性化点，中途允许他客命令插队**——它不是原子方案；
   - **MULTI/EXEC**：EXEC 起连续吃完一整批，中途无人插队（同一条流水线，只是这单客人点的是"套餐"）；但 QUEUED 阶段命令互看不见执行结果，写不出条件分支；
   - **Lua/Function**：同样不可插队，且脚本内能读了 A 再决定怎么写 B（服务端分支）。
   能力边界不互通：拿 Pipeline 求原子、拿 MULTI 求分支，都是张冠李戴。

**本层新账**：单线程吞吐有天花板（Level 7）；单命令过慢堵死所有人（[坑「盘库」](#pit-keys)/[坑「Lua 大脚本」](#pit-lua)）；dict 具体怎么组织、小对象会不会把内存吃成渣（Level 3）。

> 🔴 **口诀：IO 可以并行，命令必须串行**

## Level 3：type 是语义，encoding 是成本——同一个 list 有两张脸

🧵 进度：`Level 3/9 · C 要落进货架了，问题是：落进哪一种货架`

### 👶 前置知识关卡

- [ ] 能画出事件循环的六步，并指出线性化点（Level 2）？
- [ ] 知道"全局 dict"是字符串 key → 值的哈希表，平均查找 O(1)？
- [ ] 会算"元数据放大"：100 字节的货物若带 60 字节的管理头，内存放大是多少？

### Why —— "一张大哈希表，值全用通用容器装"死在哪

**徒弟**：一张哈希表，value 统一用带头节点的链表/动态数组/小字典，一份代码管所有类型，逻辑清晰，为什么还要搞那么多编码？

**老陈**：清晰，但烧钱。堆上一个小对象要付三次钱：**分配器元数据、robj 对象头（16 字节 🔒 私有实现，以源码为准）、指针跳转带来的缓存不友好**。你一亿个"key 几十字节 + value 几十字节"的小 KV（教学场景），通用容器路线内存放大数倍（以你的数据结构实测为准）：同样的数据量，别人一台 64 G 扛住，你四台还发抖。更要命的是：哈希表会生长，**一次全量 rehash 搬迁一亿个桶需要秒级**，在单线程事件循环里等于全店停业装修——所有连接一起超时。

| 朴素方案 | 它本来想解决什么 | 它留下的致命账 |
|---|---|---|
| 全局哈希表 + 通用链表/数组字典装所有类型 | 一份代码管所有类型，实现简单 | 小对象内存放大数倍；全量 rehash 秒级卡顿；容器 O(N) 遍历暴露在事件循环里 |

### What —— 语义（type）× 实现（encoding）双维矩阵

```text
        ┌── redisObject (robj)：type + encoding + lru(24bit) + refcount + *ptr ──┐
        │                                                                        │
 type   string       list          hash        set             zset              │
 (语义)   │            │              │           │                │               │
        ├───────────┼──────────────┼───────────┼────────────────┤               │
 encod- int /        quicklist：    listpack    intset /         listpack         │
 ing    raw /        多段 listpack  或          listpack(7.2 起)  或              │
 (成本) embstr 🔒     项链           哈希表 ht    或 ht            skiplist+dict   │
        (≤44B 阈值)              (大时)                         (大时)           │
        └─────────────────────────────────────────────────────────┘               │
                                                                                 
  小 → 连续紧凑内存：listpack，一块连续字节，无指针，一次分配，缓存友好
  大 → 跳转结构：哈希表 / 跳表，拿空间换 O(1) ~ O(log N) 查找
  切换由阈值驱动 🔒（默认值见下表，已经实机三源核对，均可 CONFIG SET 调整）
```

**编码阈值默认值 🔒（2026-08-02 经 Redis 7.2.15 实机 `CONFIG GET` 核对；官方仓库 7.2 / 8.10.0 的 `redis.conf` 与 `config.c` 交叉一致；仍以你的版本实测为准）：**

| 类型 | 配置项 | 默认值 | 语义（超过任一阈值就升级编码） |
|---|---|---|---|
| hash | `hash-max-listpack-entries` | **512** | 字段数 ≤ 512 才住 listpack ⚠️ 是 512，不是 128 |
| hash | `hash-max-listpack-value` | 64 B | 任一字段/值超过即升级哈希表 |
| zset | `zset-max-listpack-entries` | 128 | 128 的户口在 zset（别迁去 hash） |
| zset | `zset-max-listpack-value` | 64 B | 任一成员超过即升级 skiplist+dict |
| set | `set-max-listpack-entries`（7.2+） | 128 | 非整数小集合的 listpack 上限 |
| set | `set-max-listpack-value`（7.2+） | 64 B | 任一成员超过即升级 |
| set | `set-max-intset-entries` | 512 | 全整数小集合走 intset 的上限 |
| list | `list-max-listpack-size` | **-2** | 每个 quicklist 节点的填充目标；负数 = 字节档位（-1≈4KB 节点，-2≈8KB 节点，以 redis.conf 注释为准），正数 = 条数上限 |
| stream | `stream-node-max-entries` | 100 | 每个宏节点的消息数上限 |

> 旁注：7.x 里 `CONFIG GET hash-max-ziplist-entries` 仍查得到（512），但旧名是**别名不是第二套配置**——`config.c` 里 `createSizeTConfig("hash-max-listpack-entries", "hash-max-ziplist-entries", …)` 的第二个参数就是别名 🔒（V1.1 已核对两版本源码）。

> 📌 最容易被误解的一点：`TYPE` 报的是**语义**，`OBJECT ENCODING` 报的才是**存储形态**。同样 `SADD` 出来的 set：装整数是 intset，小字符串集合是 listpack 🔒（7.2 起），装多了变哈希表。**阈值是配置不是协议承诺**——跨版本、跨实例迁移，同样数据的内存可能差出数倍，容量评审必须按 encoding 核查（`MEMORY USAGE` / `OBJECT ENCODING` 抽查），不能按 key 数拍脑袋。

### How —— C 的一生（Level 3 段：落进哪个桶）

```text
① dictSdsHash("sku:1001:stock") → 哈希值 & (size-1) 定位桶
② 桶里已有该 key？→ dbOverwrite：释放旧值，挂新值
   没有？        → dictAddRaw 占桶 + dbAdd：新造 robj 挂进桶
③ value 走 tryObjectEncoding：能表成整数 → int；短 → embstr；长 → raw
   （embstr ≤44 字节 🔒：robj 16B + sdshdr8 头 3B + 串 + '\0' 恰好 ≤64B，
     一次 jemalloc 分配搞定——为什么是 44，是 jemalloc 账不是协议账）
④ 若 rehash 进行中：本次增删查**顺手搬一个非空桶**（渐进式 rehash 的一步）

★ 线性化点：第 ② 步完成的那一行。
  对外而言 SET 没有"进行中"：这一行之后任何 GET 看到的就是新值——
  单线程保证了不存在被观察到的中间态。
```

**徒弟**（针对最反直觉的一步）：哈希表扩容要翻倍搬桶，单线程怎么敢在运行时扩？

**老陈**：分两次搬家。扩容时新旧两张桌（`ht[0]`/`ht[1]`）同时在岗，`rehashidx` 记进度；此后**每一次增删查顺手搬一个非空桶**，后台 serverCron 也限时帮忙（`activerehashing` 🔒 默认开）。查找先查旧桌再查新桌。代价：查找多做一步；收益：把秒级搬迁摊成亿次常数小搬运，**店长永不停业**。🔒 私有实现，以 `dict.c` 为准。

### Transfer —— 这一层能带走什么

1. **语义与存储双维解耦**：接口按"类型"稳定，实现按"规模"自适应切换。你自己做集合/列表存储时，同款"小连续、大索引"双实现。
2. **渐进式搬迁**：一切"必须在运行时完成的扩容/迁移"都该问一句——能不能摊到每次操作上？（Level 7 的 slot 迁移是它的集群版。）
3. **连续内存即性能**：listpack 的快本质不是算法，是"没有指针跳转 + 一次分配"。堆对象满天飞的结构，都该被怀疑。

<a id="command-map"></a>
### 命令入口补充：命令 → 结构 → 编码

> 命令不是孤立的 API 名单：它先进入某个语义类型，再落到当前编码。编码是数据规模与内容共同决定的状态，不能把 `OBJECT ENCODING` 当成可永久指定的配置。

| 命令族 | 典型入口 | 语义结构 | 常见编码/实现 | 生产判断 |
|---|---|---|---|---|
| String | `SET` / `GET` / `INCR` | 字节串/计数器 | `int` / `embstr` / `raw` | 缓存、计数、锁；`INCR` 是命令级原子 |
| Hash | `HSET` / `HGET` / `HSCAN` / `HEXPIRE` / `HTTL` | field → value | `listpack` / `hashtable` | 字段级读写；7.4+ 可字段级 TTL；大 hash 禁止全量 `HGETALL` |
| List | `LPUSH` / `BRPOP` / `LRANGE` | 顺序队列/栈 | `listpack` / `quicklist` | 简单可丢队列；可靠消费转 Stream |
| Set | `SADD` / `SISMEMBER` / `SINTER` | 无重复集合 | `intset` / `listpack` / `hashtable` | 去重与集合运算；大集合用游标或拆分 |
| ZSet | `ZADD` / `ZRANGE` / `ZRANGEBYSCORE` | member + score | `listpack` / `skiplist + dict` | 排行榜、滑动窗口、延迟任务 |
| Bitmap | `SETBIT` / `GETBIT` / `BITCOUNT` | 位数组 | **String 的位寻址** | 签到、状态位；不是独立底层类型 |
| GEO | `GEOADD` / `GEOSEARCH` / `GEODIST` | 地理成员与距离 | **ZSet + geohash** | 附近的人/围栏；复用 ZSet |
| Stream | `XADD` / `XREADGROUP` / `XACK` / `XAUTOCLAIM` | 追加流 + 消费组 | `rax + listpack`，另有 PEL | 至少一次；写入端修剪、消费端认票 |
| HyperLogLog | `PFADD` / `PFCOUNT` / `PFMERGE` | 基数估计 | 16384 个寄存器，约 12KB | 趋势 UV；不能做精确对账或相减 |
| Vector Set | `VADD` / `VSIM` / `VINFO` | 向量相似度 | HNSW + int8 量化（8.0+，beta） | 先验证发行版与召回率，不直接压核心链路 |

```text
命令层      SET       HGETALL     LRANGE     SMEMBERS     ZRANGE      XREADGROUP     PFCOUNT
              │          │           │           │           │             │             │
结构层      string      hash       list         set         zset        stream          hll
              │          │           │           │           │             │             │
编码层      embstr    listpack   quicklist   intset/ht   listpack/     rax+listpack   registers
              /raw      /dict                 /listpack   skiplist+dict
```

**命令编排的边界也要一并记住：**

- 纯批量、只想省往返 → Pipeline；它没有原子性，批内每条命令各有线性化点。
- 要执行期间不插队、但不需要条件分支 → `MULTI/EXEC`；它没有回滚，执行期单条报错不等于整组回滚。
- 要在 Redis 内读结果再决定写什么 → Lua / `FUNCTION`；脚本是事件循环内的原子长段，循环上界必须可声明、可压测。
- 要"没人动过才提交" → `WATCH + MULTI`，冲突后重试整段；它不是跨出 Redis 的 fencing token。
- Cluster 下多 key 的原子边界是**槽**；事务、脚本、需要同槽的多 key 操作都必须在 schema 阶段处理 hash tag 或拆分。

**诊断三件套：**`TYPE` 看语义，`OBJECT ENCODING` 看当前形态，`MEMORY USAGE` + 实测延迟看真实成本。官方复杂度是算法量级的契约，不是你的数据量、编码、网络与尾延迟的性能承诺。客户端序列化方案则是缓存数据的外部契约：跨语言前先定编码，切换时要清洗；命令超时也不等于命令未执行，重试必须幂等。

**本层新账**：key 会过期、内存会满——谁扫地？→ Level 4。

> 🔴 **口诀：小用连续大用表，超过阈值自动换**

<a id="level-4"></a>
## Level 4：过期与淘汰——删除必须是设计，不是运气

🧵 进度：`Level 4/9 · C 落了户，紧跟着的问题：它和邻居们什么时候死、被谁埋`

### 👶 前置知识关卡

- [ ] 能说出全局 dict 与 expires 字典"同 key 双挂"的结构（Level 3 货架图）？
- [ ] 知道事件循环内任何固定开销都会挤占全体连接（Level 2 公理）？
- [ ] 记得 DRAM 单位成本显著高于磁盘（Level 1）——所以内存水位本身就是钱？

### Why —— "每 key 一个定时器"与"访问到才删"各死一头

**徒弟**：给每个 key 挂一个定时器，到点准删——既不让用户读到过期数据，又不浪费内存，两全。

**老陈**：两全其美，可惜账本不认。一百万个带 TTL 的 key 就是一百万个定时器：最小堆维护每次 O(log N)（教学量级），到期集中触发是**定时风暴**——成本全在跟事件循环抢时间。反过来走另一头——"只在访问时删"（纯惰性）——你以为省事，结果是**永远没人访问的僵尸 key 永驻内存**，水位只涨不降，直到 OOM。准时要花钱，省钱就要漏。这就是本层的墙。

| 朴素方案 | 它本来想解决什么 | 它留下的致命账 |
|---|---|---|
| 每 key 一个定时器准点删 | 准时、内存零浪费 | 定时器结构随 key 数膨胀；集中触发风暴，成本与事件循环抢同一个核 |
| 纯惰性删除（访问才删） | 零维护成本 | 僵尸 key 永不释放，内存缓慢泄漏到 OOM |

### What —— 双字典 + 两班倒 + 保险丝

```text
键空间 dict   key ────────────────> robj（value）
expires dict  key（同一指针，不双份存）──> 过期时间戳（ms）

扫地两班倒：
 ① 惰性班：任何读写命令碰这个 key 之前 → expireIfNeeded
            → 已过期：当场删除（并传播 DEL），回复"不存在"
 ② 抽查班：serverCron 每秒 hz 次（默认 10Hz 🔒）跑 activeExpireCycle：
            每轮从 expires 里随机抽 ~20 个带 TTL 的 key 🔒；
            若其中超过 1/4 已过期，就继续抽，直到 CPU 时间预算耗尽
            → 用概率把"过期垃圾占比"压在可控水位（教学说法，以源码为准）

内存撞线（maxmemory）的保险丝：8 种 policy 🔒
 noeviction｜allkeys-lru｜volatile-lru｜allkeys-lfu｜volatile-lfu（4.0+）
 ｜allkeys-random｜volatile-random｜volatile-ttl
 其中 LRU/LFU 是**抽样近似**：从 maxmemory-samples 5 🔒 个候选里挑最差的扔
```

> 📌 最容易被误解的一点："Redis 的 LRU"不是教科书精确 LRU——没有全局有序链表，只在采样池里挑最冷；samples 调大更准但更费 CPU。同理，**"过期"在被删除之前仍占内存**：TTL 到点 ≠ 立即释放。

> 🔖 **钩子（预留给 Level 6 的问题）**：那从库呢？——本层只回答主库的过期：两班倒删掉、删除即传播。从库不会自己删、只等主库的通知；而"等通知"期间你从从库读到什么、读不到什么，是一套独立判定——这要等 Level 6 讲完主从复制才有词汇回答，本层不预支，到 Level 6 的「推论」小节兑现。

### How —— C 的一生（Level 4 段：进店先过安检）

```text
主线（C=SET）：
 ① call() 执行前的服务器状态检查含内存水位：
    used_memory > maxmemory 且 policy ≠ noeviction
      → performEvictions 循环：采样 → 淘汰 → 释放，直到水位安全
      （policy = noeviction → 直接回 OOM 错误，写失败——这是特性不是故障）
 ② 落桶（Level 3）→ dirty++

支线（⚠️ 他和主线不是同一条因果链，借他演示 expireIfNeeded）：
 另一客户端 GET 一个"刚过期的 key"：
 ③ 命令真正执行前，expireIfNeeded 先查 expires dict：
    已过期 → 当场删除，删除动作记进 AOF、并传播给副本
            （副本侧怎么处理：Level 6 的「推论」小节——本层不预支）
 ④ 回复 nil ——从用户视角，"过期"这一事件此刻才发生

★ 线性化点：对单个 key，"可见 → 不可见"的切换全部发生在主线程的
   expireIfNeeded 或淘汰释放那一行——不存在"半个过期"的观察态。
```

**徒弟**：既然不准时删，那我用 TTL 管库存/发券，会不会出事？

**老陈**：你把两件事混了。TTL 是**内存契约**（数据何时允许被清理），不是**业务定时器**（到点必有副作用）。读到过期的数据？主库上不会发生（有 ③？不——③ 保证访问前必查）；但"到点一定触发某个动作"从不被承诺。连 `keyspace notification` 的 expired 事件都是**删除时才发**，不是 TTL 到点就发（🔒 语义细节，以你版本实测为准）。需要"到点必执行"的东西（关单、发券），用业务延迟队列 + 幂等，别拿键过期当闹钟。

### Transfer —— 这一层能带走什么

1. **惰性 + 抽样 + 时间预算**的均摊哲学：昂贵且非紧急的工作，摊到触点上，再配一个后台预算化抽检（操作系统的内存回收、文件系统的延迟删，同构）。
2. **淘汰策略是业务语义题，不是配置题**：纯缓存 → allkeys-lru/lfu 且允许 evicted；有持久语义 → noeviction，让写失败报警，而不是偷偷丢数据（决策卡 2）。
3. **"近似"要先证明误差不伤业务再上线**：抽样 LRU 省的是全局有序的成本，买的时候要知道买的是什么。

**本层新账**：扫地再勤，进程一死全没——店里的货怎么备份？→ Level 5。

> 🔴 **口诀：过期不追时，访问才扫地**

<a id="production-resilience"></a>
### 生产横切补充：过期机制如何长成缓存三兄弟

缓存三兄弟不是三条可以互换的配置，而是同一条读链路在不同根因下的三种故障形态。先判根因，再选机制：

| 故障形态 | 根因 | 直接后果 | 对症机制 |
|---|---|---|---|
| 穿透 | 请求的 key 本来不存在，缓存永远不会命中 | 错误/攻击请求反复打 DB | 空值短 TTL、业务侧布隆过滤器、参数校验 |
| 雪崩 | 大量 key 使用齐整 TTL，在同一时间失效 | 大批回源同时压向 DB | TTL 加随机抖动、多级缓存、分批预热 |
| 击穿 | 单个热点 key 在高并发瞬间失效 | 同一个 DB 查询被并发复制 N 次 | `SET lock NX PX` 互斥重建、逻辑过期、旧值/短重试兜底 |

```text
热点 key 失效时：
读 Redis → miss
  ├─ 抢到重建锁 → 只有一个请求查 DB → 写回缓存 → 释放锁（Lua 校验 token）
  └─ 未抢到锁   → 读仍可用的旧值，或短暂等待后重读
```

**不变量：**不存在的结果也要有短暂占位；TTL 分布不能人为齐整；同一热点的回源重建同一时刻最多一个。拿不到重建锁不是"19 个用户失败"，而是它们被挡在 DB 外，等待旧值或新值。

### 爆炸半径：大 key、热 key、内存满是三笔不同的账

| 问题 | 放大路径 | 处理方式 | 观测信号 |
|---|---|---|---|
| 大 key | 一个 O(N) 的 `HGETALL` / `LRANGE` / 同步 `DEL` 占住主线程，拖慢全实例 | hash 拆桶、list 按时间分片、分页读取、`UNLINK` 异步释放 | `SLOWLOG`、p99 毛刺、`blocked_clients` |
| 热 key | 单 key 的 QPS/带宽集中到一个节点；分片只能改变它落在哪 | 本地缓存、读扩散多副本、拆业务粒度；写入补齐要幂等 | 单节点 CPU/带宽显著高于均值 |
| 内存打满 | `maxmemory` 触发淘汰或 `noeviction` 拒写 | 纯缓存按可重建性选 `allkeys-lru/lfu`；持久语义数据隔离并保守拒写 | `used_memory/maxmemory`、`evicted_keys`、写入错误 |

**关键判断：**大 key 的罪通常不是"占了多少字节"，而是一次操作要释放/遍历多少个分配对象；Cluster 也不会把热点 key 自动摊开。缓存被淘汰若伴随 `evicted_keys` 上涨，先按预期淘汰排查，不要直接当作 Redis 丢数据；前提是缓存确实可从 DB 重建。

<a id="level-5"></a>
## Level 5：RDB 与 AOF——持久化是"丢多少"与"停多久"的选型题

🧵 进度：`Level 5/9 · C 已生效，现在给它上账——上哪本账，是本层的仗`

### 👶 前置知识关卡

- [ ] 记得一次 fsync 与一次内存读之间的数量级差（Level 1 的墙）？
- [ ] 能复述 C 从收包到落 dict 的六步，并指出 dirty++ 发生在哪一步（Level 2）？
- [ ] 知道"page cache ≠ 磁盘"：write() 返回时，数据此刻在哪？

### Why —— "每条命令先落盘"与"每小时拍一张"各死一头

**徒弟**：要持久就别怂：每条命令 fsync 落盘之后才回 OK，天塌不丢。

**老陈**：不丢是真的，慢也是真的。一次 fsync 在 NVMe 上是微秒~毫秒级（教学量级，以 `fio` 实测为准）——等于把 Level 1 翻过去的微秒墙再翻回来，QPS 从十万级教学量级掉回千级。**你为了"不丢"，把"为什么用 Redis"赔了进去。**

**徒弟**（换一头）：那不拦营业，每小时 fork 一次拍全量快照。

**老陈**：宕机丢最近一小时（最坏情况）。订单流水、计数器业务当场去世。两个朴素方案各占一头：A 丢不起，B 慢不起。所以真实方案是两张拼起来的账。

| 朴素方案 | 它本来想解决什么 | 它留下的致命账 |
|---|---|---|
| 每命令同步 fsync（appendfsync always 的极端形态） | 写确认 = 已落盘 | 延迟地板回到微秒~毫秒级，吞吐退回磁盘量级，Level 1 白忙 |
| 只按时全量快照（裸 RDB） | 平时零成本，恢复简单 | RPO = 快照间隔，宕机丢一长段；大实例 fork 本身也是毛刺源 |

### What —— 盘点拍照 + 流水小票，两本账互补

```text
RDB｜盘点拍照
  触发：save 规则（如 900s 内 ≥1 次变更 🔒 默认可调）或手动 BGSAVE
  做法：fork() → 子进程把"fork 时刻的内存视图"序列化成紧凑二进制
  原理：COW 写时复制——父子共享物理页，谁写谁单独复制那一页
  优点：文件小、加载快；缺点：RPO = 拍摄间隔

AOF｜收银流水小票
  记录：每条写命令按协议格式追加进 server.aof_buf → 循环尾部 write()
  刷盘：appendfsync = always（每条都刷）/ everysec 🔒默认（每秒）/ no（交给内核）
  瘦身：写长了会"重写"——fork 一份，按当前数据生成最小命令集
        4.0+ aof-use-rdb-preamble yes 🔒：重写的基础段用 RDB 格式，加载提速
        7.0 起 MP-AOF 🔒：目录化（base 文件 + incr 文件 + manifest）
        ——这是「代码组织变化」：崩溃恢复的语义不变（以 release notes 为准）
```

> 📌 最容易被误解的一点：`everysec` 的诚实语义是"**目标最多丢约一秒**"，不是"严格每秒刷"。若上一次 fsync 卡在磁盘上还没回来，下一次 write 会被拖延（上限秒级 🔒，见 `flushAppendOnlyFile` 源码），并计入 `aof_delayed_fsync`。磁盘是上下游：磁盘抖，Redis 只能陪着抖。

### How —— C 的一生（Level 5 段：上账本）

```text
① （Level 2 第④步里）dirty++：账本"待记"计数 +1
② propagate：把 C 按协议格式追加进 server.aof_buf（Level 6 还会再加一路）
③ 事件循环尾部 flushAppendOnlyFile：write(aof_buf → 内核 page cache)
    ← 此刻掉电仍可能丢：数据还在内核，没上磁盘
④ everysec：后台 bio 线程执行 fsync()
    ← 这一下完成后，C 才算"进了保险柜"
⑤ 若恰逢 BGSAVE 进行中：子进程的世界是 fork 点的冻结视图——
    C 若发生在 fork 之后 → 不在这次 RDB 里，但会在 AOF / 下一次 RDB 里

★ 线性化点（持久化层的"已保存"边界）：
   AOF → 已 fsync 的字节偏移；之前=可能丢，之后=已落盘。
   RDB → fork() 系统调用返回那一刻：子进程看到的是冻结的全店照片。
```

**徒弟**（针对最反直觉的一步）：fork 不是把整个内存复制一遍吗？32 G 实例 fork 一下不就变 64 G？

**老陈**：这正是 COW 的本事：fork 只复制**页表（映射关系）**，物理页父子共享，谁写谁复制那一页。所以真实成本 = fork 系统调用本身的耗时（随页表大小涨，`INFO persistence` 里 `latest_fork_usec` 直接看）＋ 快照期间父进程的**写放大**。两个开关能把账恶化：其一，开着 THP（透明大页）时 COW 粒度从 4K 变 2M，改一个字节复制一大片——生产建议关闭 THP 或设 madvise（以你的内核版本为准）；其二，快照期写流量越猛，额外内存占用越高——**BGSAVE 要和业务高峰错峰**（决策卡 3）。还有一条**前置条件**不在 COW 账上，却是运维踩得最多的 fork 失败：Linux 的 `vm.overcommit_memory`。= 0（默认，启发式）时，内核按进程占用估算可提交内存，物理内存 + swap 吃紧时 **fork() 直接失败**——Redis 日志里那句 `Can't save in background: fork: Cannot allocate memory` 就是它，BGSAVE / AOF 重写静默流产。Redis 启动时自带预警（原文见下 🔒），官方建议设 = 1（总是允许超卖：fork 必然放行，COW 物理页仍按需分配）；= 2（严格比例）等于不许超卖，Redis 基本不可用，别碰。

> 🔒 启动 WARNING 原话（server.c，多年未变）：`WARNING overcommit_memory is set to 0! Background save may fail under low memory condition. To fix this issue add 'vm.overcommit_memory = 1' to /etc/sysctl.conf and then reboot or run the command 'sysctl vm.overcommit_memory=1' for this to take effect.`

### Transfer —— 这一层能带走什么

1. **WAL 日志先行**：顺序追加 + 周期性 fsync，是"性能 × 持久"的最优平衡点——MySQL redo、Kafka 的 pagecache+flush，全是同一招。
2. **用 COW 冻结时间**：想拿到"某一瞬间的世界"，fork/快照并让写路径复制页，而不是让全世界停工（ZFS/LVM/Docker overlay 同构）。
3. **评审先写两个数字再选方案**：最多丢几秒数据（RPO）、最多停几分钟机（RTO）。没有这两个数字的"我们要持久化"都是空话（决策卡 3）。

**本层新账**：磁盘再可靠也是单机——机器烧了、机房断了，谁接盘？→ Level 6。

> 🔴 **口诀：快照看 fork，日志看 fsync**

## Level 6：复制与哨兵——控制面要投票，数据面认异步

🧵 进度：`Level 6/9 · C 的复印件顺风吹向分店；然后某个深夜，主店着火了`

### 👶 前置知识关卡

- [ ] 一句话说清 C 在哪一毫秒算"上账本"（Level 5 的 fsync 边界）？
- [ ] 知道同城内网一次 RTT 的教学量级（亚毫秒~毫秒级，以实测为准）？
- [ ] 能解释"写放大"在 COW 快照期间意味着什么（Level 5）？
- [ ] 记得 Level 4 的两班倒：谁删过期 key、删除动作传向哪里（Level 4 钩子）？

### Why —— "写完等全员 ACK"与"单机裸奔"各死一头

**徒弟**：高可用就做到极致：主库每写一条，等全部从库确认收到再回 OK。

**老陈**：极致的是不丢，也极致地慢。每条写 +1 次网络 RTT，写延迟地板抬到毫秒级——Level 1 的墙又白翻一次。更阴的是：**任何一个从库网络一抖，主库写就阻塞**——你为"更可用"买来的，反而是"更不可用"。

**徒弟**（换一头）：那就主从异步复制、不管确认，但半夜主死靠人肉顶上。

**老陈**：RTO 以小时计，值班表以 ICU 计。总结：同步等 ACK 死于延迟与耦合；人肉 failover 死于 RTO。所以要"异步流水 + 机器切换"的组合。

| 朴素方案 | 它本来想解决什么 | 它留下的致命账 |
|---|---|---|
| 全同步复制（写完等所有副本 ACK） | 一条不丢 | 写延迟挂到网络 RTT；任一副本抖动 = 主库写阻塞，可用性反降 |
| 异步复制 + 人肉 failover | 写入快 | 主死切换靠人，RTO 不可控；且没人回答"最后几条丢没丢" |

### What —— 数据面异步流水，控制面投票团

```text
数据面（求快）：
  主 ──写命令流（propagate）──> 从1、从2 …（异步，不等 ACK 才回执）
  主内另有 replication backlog：字节环形缓冲 🔒 默认 1MB，可配
  从库掉线归来：PSYNC <runid> <offset>
     offset 还在 backlog 窗口内 → 只补缺口（部分重同步）
     已不在 → 全量：主 fork 一份 RDB 流过去（可无盘传输 🔒 repl-diskless-sync）

控制面（求稳）：
  Sentinel（奇数个，通常 3，分机房部署）：
   ① 主观下线：单个 sentinel 看 master 心跳超时
      （down-after-milliseconds 🔒 默认 30s，以你网络实况调）
   ② 客观下线：≥ quorum 个 sentinel 同判
   ③ 选 sentinel leader（多数派，Raft 风格）
   ④ 在从库里挑"复制进度最大 + replica-priority 高"的 → SLAVEOF NO ONE 升主
   ⑤ 其余从指向新主，广播拓扑，客户端重连

收窄窗口的旋钮（不是开关）：
  WAIT n 🔒     等 n 个副本确认收到（不等落盘）
  WAITAOF 🔒（7.2+）等本地/副本 AOF 已 fsync
  ——它们缩小丢失窗口，但不把 Redis 变成强一致系统。
```

> 📌 最容易被误解的一点："主从复制" ≠ "数据安全"。Redis 复制是**最终一致（AP 语义）**：客户端那声 `+OK` 只代表"主库内存里有了"。已确认的写仍可能丢（切换窗口）——这不是 bug，是章程。要"确认即不丢"：要么 WAIT/WAITAOF 并咽下毛刺，要么换强一致存储。这是架构评审要签的字。

### How —— C 的一生（Level 6 段：过账到分店 & 主店着火）

```text
平时：
 ① 主执行 C，dirty++ → propagate：写进每个 replica 的输出缓冲 + backlog
 ② 各从库异步读到 C → 在**自己的主线程**重放（顺序 = 主库顺序）
    → 周期性 REPLCONF ACK <offset> 回传主库
 ③ 主库由此知道"每个分店抄到了第几页"（INFO replication 可查）

出事（某个深夜）：
 ④ 主失联 → 主观下线 → 客观下线 → 选 sentinel leader
    → 挑 offset 最大的从 → 升主 → 重配置其余从 → 客户端切过去
 ⑤ 那笔"坏账"：C 已被主确认（+OK 已给客户端），
    但还没 propagate 到被升主的那个从 ——这张小票被新主"赖掉"了。
    若拓扑收敛前旧主仍被分区内的旧客户端写入 → 双主脑裂，数据分叉
   （min-replicas-to-write 1 + min-replicas-max-lag N 🔒 可把窗口再收窄）

★ 线性化点（诚实版）：复制层不存在全局单点。
   每个副本的"已应用到 offset x"是它自己的线性边界；
   "已确认写"与"切换"之间存在一个无法消除的竞态窗口——
   全部 HA 工程都是在压缩这个窗口，而不是消灭它。
```

**徒弟**（针对最反直觉的一步）：选主时像模像样地多数派投票，数据为什么不索性也上 Raft？那样一条都不丢啊。

**老陈**：这一问正暴露了 Redis 的身份：它的取舍是**数据面低延迟优先**。Raft 接管数据面意味着每写必过 quorum RTT，毛刺跟着放大；于是 Redis 把投票只用在"谁是主"这种低频大事上（控制面），数据面保持异步流水。这套"**控制面投票、数据面异步**"的组合，在 Kafka（KRaft + ISR）等系统里是熟面孔。取舍没有对错，只有配不配你的 SLO。（设计动机以官方文档/FAQ 为准，本文不复述二手转述。）

### 推论 —— 过期语义在复制场景下（从库不删 key，墙钟判"逻辑过期"）

Level 4 的钩子在此兑现：复制机制讲完了，"过期"就有了第二套行为——

```text
 主库：惰性班 + 抽查班删过期 key（Level 4 两班倒），删除即传播 DEL（进复制流）
 从库：不主动删、不抽查——物理删除只发生在收到主库 DEL 的那一刻：
  ① 读路径只判"逻辑过期"：判据是从库**自己的墙钟**（`keyIsExpired`
     用本地 mstime，🔒 5.0/6.2/7.2 代码一致）——判定过期就回 nil，
     但**不删、不传播**（`expireIfNeeded` 从库分支直接返回，🔒 源码注释
     原话："the replica key expiration is controlled by the master"；
     7.2 起对主库连接一律判"未过期"，复制流里的命令不受过期判定干扰 🔒）
  ② 官方承认这套判定的精度不完美（原话：replicates expires with an
     accuracy that is not ideal）→ 主从时钟偏差 = 读到"已过期值"的窗口
  ③ 断链期间：DEL 传不过来 → 主库侧已删/已淘汰的 key 在从库继续可读
     （replica-serve-stale-data 🔒 默认 yes，7.2 redis.conf L567 生效行），
     且过期未删的 key 一直占着从库内存
     （从库默认不参与淘汰：replica-ignore-maxmemory 🔒 默认 yes）
  ④ 从库升主那一刻起：独立开始过期/淘汰，不再等旧主
     （官方 replication 页原话："start to expire keys independently"）

 为什么"逻辑可见性"不按主库的 DEL 算、偏要从库自己判？
 ——主从时钟不可能同步（官方 replication 页原话：cannot rely on the
 ability of the master and replica to have synced clocks）；若等 DEL 到达
 才算"已过期"，读从库的流量会在 TTL 后继续读到旧值，直到 DEL 姗姗来迟。
 墙钟判定是"宁可保守报不存在"——官方举的场景正是 HTML 片段缓存：
 用从库扩读的页面缓存，不该返回超过 TTL 的旧内容。代价就是上面 ② 的
 时钟偏差窗口：没有免费午餐，官方原话把账记得很清楚。

 事故形态见坑「从库读过期」；"读不到刚写的"见坑「读写分离」——一对镜像，包住"从库读"的全部语义。
```

> 📌 一句话记忆：**从库的"已过期"是墙钟判定，物理删除永远等 DEL；升主即独立。**

### Transfer —— 这一层能带走什么

1. **控制面 / 数据面分离**：低频大事用一致性协议，高频数据走异步流水——设计任何分布式系统，先问这句话。
2. **断点续传三件套**：runid + offset + 环形 backlog，与 Kafka offset、MySQL GTID + binlog 位点同构。
3. **脑裂不是协议漏洞，是配额没配**。任何"靠超时判死"的系统都必须回答"判错时怎么止血"（min-replicas / fencing token）。
4. **WAIT / WAITAOF 是旋钮，不是开关**：想清楚拧在哪些接口、拧到几档（决策卡 4），别全局限速。
5. **读从库的 TTL 语义 = 时钟偏差窗口 + 断链窗口**：从库判"逻辑过期"用自己的墙钟（🔒），物理删除等主库 DEL，升主即独立。任何"读从库"方案，把这条边界签进 SLO（[坑「从库读过期」](#pit-replica-expire)）。

**本层新账**：一主多从解决了"死得起"，没解决"装不下、写不动"：数据量 > 单机内存、写 QPS > 单机天花板 → Level 7。

> 🔴 **口诀：控制面要投票，数据面认异步**

<a id="level-7"></a>
## Level 7：Cluster 分片——槽位的本质是"以后能搬家"

🧵 进度：`Level 7/9 · C 要决定进哪家店——以及这家店以后怎么搬家`

### 👶 前置知识关卡

- [ ] 能画出 C 在单机内的线性化点，并说明"全序 = 主线程顺序"（Level 2）？
- [ ] 知道复制组内部如何做 HA（Level 6 的整套机制可在分片内复用）？
- [ ] 记得渐进式 rehash "摊到每次操作"的思想（Level 3）——它马上要有集群版？

### Why —— 取模与一致性哈希各有死法

**徒弟**：多台机器还不简单：`hash(key) mod N`。

**老陈**：N=3 变 N=4 那一刻，绝大多数 key 的余数全变了——缓存**大面积失效**，回源流量直接压死数据库。这叫扩容风暴。

**徒弟**（换一头）：一致性哈希环，扩缩容只动相邻弧段。

**老陈**：风暴是没了，换来两个新病：其一，环上节点少时**负载偏斜**严重，要虚拟节点补救，实现与认知成本都上来；其二，环只管"在哪"，**不管"怎么搬"**——数据迁移、再均衡、路由发现，全靠你自己再打一套。你要的是一个把"放哪"和"怎么搬"打包在一起的方案。

| 朴素方案 | 它本来想解决什么 | 它留下的致命账 |
|---|---|---|
| hash(key) mod N | 分片 | 节点数一变全量重 hash，缓存风暴回源压死后端 |
| 一致性哈希环 | 平滑扩缩容 | 偏斜要虚拟节点补救；迁移/再均衡/路由发现另起炉灶，半成品工程 |

### What —— 16384 个槽：预分片，以"片"为最小迁移单位

```text
slot = CRC16(key) & 16383        ← key → 0..16383 号槽位，与节点数无关
节点只认领若干槽位段：            node A: 0-5460，node B: 5461-10922，…
每个槽位段内部仍是一组主从        ← Level 6 整套机制复用为"槽内 HA"

路由（客户端本地缓存 slot→node 表，错了由服务器纠正）：
  -MOVED slot ip:port   永久：这槽以后归那家店——请更新路由表
  -ASK   slot ip:port   临时：槽正在搬，先去那边办这一笔（先发 ASKING）

搬家三件套：
  CLUSTER SETSLOT … MIGRATING / IMPORTING  +  MIGRATE（原子搬走若干 key）
拓扑传播：节点间 gossip；槽内主死 → 该槽从库按多数派升主

为什么 16384：
  ⚠️ 此段是社区广为流传的经典解释（源自 antirez 的设计问答），
  🔒 属设计轶闻而非规范条文——本文只做理解辅助，一手措辞以原始出处为准：
  心跳包内嵌全槽位 bitmap = 16384 bit = 2KB，gossip 包里不痛不痒；
  官方建议集群规模控制在千节点以内，16384 对均衡粒度已足够；
  再大 4 倍槽数， gossip 带宽 ×4，换不到实际收益。
  ——这是"网络开销 × 均衡粒度"的工程甜点，不是魔法常数。
```

> 📌 最容易被误解的一点：**多 key 命令 / 事务 / Lua 的原子边界是"槽"，不是集群**。两个 key 分属两槽 → `CROSSSLOT` 直接报错。要批量原子，用 hashtag：`cart:{u42}:a`、`cart:{u42}:b` 同槽（CRC 只算 `{}` 里那一段）。这是语义约束，任何框架都救不了你——schema 评审阶段就要定（决策卡 5）。

### How —— C 的一生（Level 7 段：找对门牌）

```text
① 客户端：CRC16("sku:1001:stock") & 16383 = 槽 s；查本地路由表 → 节点 X
② 发给 X；X 自查：槽 s 归我？
     归我  → 回到 Level 2 的主线六步，店内的全序照常成立
     不归  → 回 -MOVED s Y（顺便附赠最新答案）
③ 客户端更新路由表，重发 C 到 Y → 正常执行
   ——若槽 s 正在从 X 搬往 Y：
④ X 对"还没搬走的 key"正常服务；对"已搬走的 key"回 -ASK
⑤ 客户端先向 Y 发 ASKING（仅这一笔的临时授权）再发 C → Y 受理
⑥ 收尾：SETSLOT NODE 广播，全拓扑收敛，路由表永久指向 Y

★ 线性化点：槽归属的切换，以拓扑收敛（各节点一致认可 s 归 Y）为界；
   迁移窗口内，-ASK + ASKING 保证单笔请求串到正确的一侧。
```

**徒弟**（针对最反直觉的一步）：为什么搬家时能"边营业边搬"，不怕两边同时写乱吗？

**老陈**：因为搬家的原子单位是 **key**：`MIGRATE` 是把 key 从源店**原子地**搬走并删除源侧（同版本语义下，行为细节以你版本源码为准 🔒）。每一时刻，一个 key 有且只有一个"合法的店主"：没搬走的在源店正常受理；已搬走的，源店用 `-ASK` 把你指去新店。客户端那一声 `ASKING` 相当于出示"迁移期间的临时通行证"。乱不了的原因和 Level 2 一样：**每个 key 的写，永远只在一个主线程里被串行受理**——只是那个主线程可能在搬家前后换了台机器。

### Transfer —— 这一层能带走什么

1. **分片单元数 ≫ 节点数，搬迁按片走**：一致性哈希的虚拟节点、Kafka 的 partition、ES 的 shard，全是"筹码要小到能移动"。
2. **路由发现 = 客户端缓存 + 服务器纠错（MOVED/ASK）**：比"每笔都问中心路由"省一跳，可照搬到自研分片中间件。
3. **扩容是计划，不是开关**：逐槽迁移 + 观测毛刺 + 回滚预案（决策卡 5 的演练清单）。
4. **热点不归拓扑管**：单 key 几百万 QPS，迁到哪个槽都是那一台着火——本地缓存 / 读扩散 / 拆 key（[坑「胖 value」](#pit-fat-value)+ 决策卡 1）。

**本层新账**：槽位会搬家，但槽主死了谁宣判、谁继任？每分片组外挂一套哨兵行不行？→ Level 8。坑/卡/表在 L8/L9 之后统一清算。

> 🔴 **口诀：槽位一万六，搬迁按片走**

## Level 8：没有居委会的老街——Cluster 的 gossip 八卦、两阶段确诊与"偷来的半部 Raft"

🧵 进度：`Level 8/9 · C 的槽主死了，但这条街没有居委会——谁宣判、谁继任？`

### 👶 前置知识关卡

- [ ] 能复述 Sentinel 的"主观下线 → 客观下线 → 选 leader 主持 failover"剧本（Level 6）？
- [ ] 知道槽位路由与 MOVED/ASK（Level 7）？
- [ ] 记得"异步复制存在已确认写丢失窗口"（Level 6 的诚实账本）？

### Why —— "每个分片组配一套 Sentinel"死在哪

**徒弟**：分片就分片，每组主从各挂一套 Level 6 的 Sentinel，方案现成，不重新发明轮子。

**老陈**：三组账压死它。第一组，**运维账**：30 组分片 = 90 个哨兵进程，部署、升级、监控、跨机房摆放全部 ×N——裁判团的规模跟着分片数线性膨胀。第二组，**能力账（真正的死因）**：Sentinel 是**外挂视角**，它的世界只到"谁是主"为止；Cluster 还必须让**全街成员**对另一套元数据收敛——"哪个槽在谁手上、配置版本谁更新"。这套元数据要多对多传播、按版本仲裁，外挂裁判团干不了，只能靠成员间的大喇叭。第三组，**递归账**：那换个思路指定一个"街长"节点总管？街长挂了谁选街长的街长？无限递归。结论：**去中心化，节点自治**——每个店老板自己张罗。

| 朴素方案 | 它本来想解决什么 | 它留下的致命账 |
|---|---|---|
| 每分片组外挂一套 Sentinel | 复用 Level 6 的现成剧本 | 裁判团数量随片数爆炸；且外挂视角管不了槽位元数据的多对多收敛 |
| 指定中心节点当"街长" | 决策集中、逻辑简单 | 街长的高可用问题无限递归；全街元数据与请求路径都压到单点 |

### What —— 两张总线、两阶段确诊、一个逻辑时钟

```text
平面分离（先记住端口，防火墙评审要用）：
  数据总线：客户端 ↔ 6379（C 走的路，Level 7 已讲）
  集群总线（cluster bus）：节点 ↔ 节点，二进制协议，全互连
    端口 = 数据端口 + 10000 🔒（6379 → 16379）
    每对节点间两根连接 🔒（来一根去一根）

失败检测两阶段（官方 cluster-spec 核实）：
  PFAIL（Possible failure，私房怀疑）：
    A 超过 cluster-node-timeout 🔒（默认 15000ms）联系不上 B
    → 只记进自己小本本，夹在 gossip 包里当"八卦"捎给别人
    ——未经公认，不构成任何行动依据
  FAIL（确证讣告）：
    当 A 收集到【多数 master】都在
    NODE_TIMEOUT × FAIL_REPORT_VALIDITY_MULT 🔒（当前实现 = 2，即约 30s 窗口）
    内报告 B 为 PFAIL → A 把 B 升级为 FAIL，
    并立刻广播 FAIL 消息：收到者无条件标记，不等自己的观察
    ★ FAIL 标志基本单向：B 若无槽（非 master）或以副本身份复活才可能清除

选主与逻辑时钟（官方 cluster-spec 核实）：
  currentEpoch：64 位逻辑时钟，随 gossip 包流动，见更大的就跟进
  configEpoch：每个 master 的"配置版本印"，同一槽位冲突时大者赢
 
  B 的分店员 M 想继位（剧本逐行）：
   ① 等一段延迟：DELAY = 500ms + rand(0,500) + RANK×1000ms 🔒
      （RANK 按复制 offset 排位：抄账最新者 rank 0，最先起跑——
        没人指定"你最合适"，是让最合适的人先到，一种被动择优）
   ② 自增 currentEpoch，向全街 master 发 FAILOVER_AUTH_REQUEST 拉票
   ③ 每个 master 每纪元只投一票（凭 lastVoteEpoch 判决，且落盘进 nodes.conf 🔒），
      拒绝旧纪元的请求；也不会投给 configEpoch 比自己已知还旧的候选 🔒
   ④ 拿到多数票 → 自领一个比现存所有 configEpoch 都大的新印，
      广播认领 B 的全部槽位；收到者按"印大者赢"更新世界观
```

> 📌 最容易被误解的一点：**Cluster 选主不是 Raft**。antirez 2013 年的原话（antirez.com/news/62，如实照录）："In short Redis Cluster does not require a full agreement protocol so I stolen just what I needed from Raft, and tried to figure out the rest."——为什么只需要半部？Raft 的日志是为"确定状态机按相同操作序列同步"准备的；而槽位的全部状态只是"这一个槽归谁管"**一个事实，单 packet 就能全量表达**，不需要日志、不需要追赶进度。但有一样东西非借不可：分叉合并时"纪元递增、大者赢"的仲裁规则。偷的是这一件——**它买了"谁是主"的互斥，没买"数据最新"**，数据面的丢失窗口（Level 6）原样保留。

### How —— 槽主 B 之死的完整时序（官方规格口径）

```text
 t0  掌管若干个槽的 master B 断气（宕机 / 被分区）
 t1  街坊 A1,A2… 各自超 15s 🔒 叫不应 B → 小本本记 PFAIL，八卦随包外流
 t2  某节点集齐【多数 master】在 ~30s 🔒 窗口内都举了 B 的 PFAIL
     → 把 B 升级 FAIL，广播 FAIL 消息（收者无条件标记）
     ★ 线性化点：这是全街对"B 之死"的共识时刻——此前一切只是八卦
 t3  B 的分店员 M（抄账最勤，rank 0）延迟最短，第一个醒来
 t4  M 自增纪元、拉票；多数 master 各投一届一票（留档 nodes.conf）
     ★ 线性化点：多数票达成 = 新主合法继位——一届一票 + 纪元递增
        保证同一纪元不可能产生两个胜出者（两个多数派必有交集）
 t5  M 用更大的 configEpoch 广播认槽；旧 B 若复活，见印即认臣
 t6  客户端旧路由撞上 M（或复活后已降级的 B）→ -MOVED 指路，C 的旅途继续

 t0–t4 期间落在槽上的写：B 死前已应答客户端、未及 propagate 给 M 的部分
       随 B 而去——Level 6 的窗口在集群尺度原样存在，莫忘
```

**徒弟**（针对最反直觉的一步）：为什么要等 15 秒+n 秒才换主？这一刀砍到 1 秒，RTO 不就好了？

**老陈**：这不是"检测慢"，是**故意的钝感**。你算代价的两端：误判一次死缓 = 无谓 failover → 链式全量重同步、客户端重连风暴、新窗口丢写；晚判 10 秒 = 该槽 10 秒不可写（而且 minority 分区侧超时还会主动拒写，这是 cluster-spec 里的设计：宁可短暂不可用，不可双主）。PFAIL→FAIL 两阶段、多数制附议、rank 延迟起步——三处设计都在说同一句话：**宁可为观察付钱，不可为错杀付命**。砍 timeout 不是不行，但你必须先在评审里回答"我的网络抖动分布什么样、一次误判 failover 值多少钱"（[坑「node-timeout」](#pit-node-timeout)就是手痒的下场）。

### Transfer —— 这一层能带走什么

1. **症状与确诊分层**：本地观察（PFAIL）永远不要直接驱动全局动作，多数交叉后才升级（FAIL）。SWIM 协议、Cassandra 的 accrual failure detector 是同族思想——怀疑是私事，判决是公务。
2. **逻辑时钟替代物理时钟**：机房之间 NTP 不可信、时钟回拨常见，"谁更新"交给 epoch 而不是时间戳。你设计多副本系统时同理：版本号是裁判，表上的钟只是参考。
3. **配置走 gossip+版本仲裁，数据走异步复制**——控制面/数据面分离（Level 6）在集群尺度的重演，一层心法吃两次。
4. **被动择优**：不指定"谁最合适"，而是让最合适的人先到（rank → 延迟）。排队系统、选举算法都可用这一招省掉一节中心化比较逻辑。

**与 Sentinel 的体制对照表**（读者最容易混的两套协议，一张看穿）：

| 维度 | Sentinel（Level 6） | Cluster 自治（本层） |
|---|---|---|
| 裁判是谁 | 外挂哨兵进程组（奇数，跨机房） | 集群成员自己（gossip 大喇叭） |
| 疑似态 | 主观下线 SDOWN | PFAIL（本地小本本） |
| 确诊态 | 客观下线 ODOWN（≥quorum 哨兵） | FAIL（多数 master 附议 + 广播） |
| 时间参数 🔒 | down-after-milliseconds（默认 30s） | cluster-node-timeout（默认 15s）×2 窗口 |
| 换主方式 | leader 哨兵**主动挑** offset 最大的从 | 各副本按 **rank 延迟**自己起跑拉票（被动择优） |
| 一轮几票 | 哨兵间选 leader | 每 master 每纪元一票，lastVoteEpoch **落盘**进 nodes.conf 🔒 |
| 冲突仲裁 | 哨兵权威通告 | configEpoch 大者赢（简化版 last-write-wins） |
| 泳道 | sentinel 26379 | 数据 6379 + 总线 16379 🔒 |

**本层新账**：货架全会了，但"业务来了选哪张"还没有一张决策表——把每层 Transfer 编成索引 → Level 9。

## Level 9：场景总装——Stream 的小票箱与 HyperLogLog 的水波纹

🧵 进度：`Level 9/9 · 总装：全篇货架排成一张决策表；表 A 两行的机制（Stream/HLL）在此兑现`

### 👶 前置知识关卡

### Why —— "每种结构都会用"解决不了选型

**徒弟**：String/Hash/List/Set/ZSet 我全会了，业务来了照手册拼就是，能有什么坑？

**老陈**：给你两张真实病危单。**病案一**：队列用 `LPUSH + BRPOP`——消费者 BRPOP 拿到消息的一瞬间宕机，这条消息**从宇宙里消失**（弹出即焚，没有副本、没有回执）；老板还想"加第二个消费组各消费一份"，List 没这个器官。**病案二**：日活一亿的 App 用 Set 存当日 UV——一个 key 一天就奔着 GB 级去（教学量级，以你的 ID 长度实测），月末内存病危。**结构全会的人照样开出这两张单子**，缺的不是结构知识，是"这个场景的失败语义和误差容忍是多少"的追问。

| 朴素方案 | 它本来想解决什么 | 它留下的致命账 |
|---|---|---|
| List（LPUSH+BRPOP）当消息队列 | 阻塞消费、先入先出，简单 | 弹出即焚：消费端崩溃 = 消息丢失；无消费组、无重放、无"已取未认"清单 |
| Set 记亿级 UV / 去重 | 精确去重，语义直白 | 内存随基数线性膨胀；亿级场景一台实例都不够用 |

### What —— 场景总表 + 两张新货架

> 🔖 **总装是什么**：Level 1–8 把 C 的旅程走完，也把店里的货架一件件讲透（String/Hash/List/Set/ZSet/Bitmap/GEO）；两张此前只露过名字的货架（Stream/HLL）进入主线，Vector Set 则作为 8.x 的版本边界能力单列，不成为核心依赖。本层做最后一件事：把"业务来了选哪张货架"排成一张决策表（表 A），把与结构正交的能力单独排一张（表 B）。**表是索引，How 是表 A 两行的展开**——Stream/HLL 的机制此前缺席，本层把"机制 + 纪律"一次补齐。

**📑 表 A：业务场景 → 数据结构选型**（每行只回答一个问题：“这个场景该用哪个类型，为什么不是次优”——索引页，理由回指具体 Level 的因果链）：

| 业务场景 | 选型 | 为什么是它（而不是次优选项） | 依赖机制 |
|---|---|---|---|
| 热点缓存 | String | O(1)；别用 Hash 存整对象序列化（字段级失效拗手） | L1 介质账 / L4 / 卡 1 |
| 计数器 | String（INCR） | 命令原子免费；"GET+1 再 SET"两步有竞态 | L2 线性化点 |
| 排行榜 | ZSet（skiplist） | O(log N) 插入 + 范围查询同体，唯一能同时给两者的结构 | L3 编码阈值 |
| 分布式锁 | String（SET NX PX） | 单命令原子；续约与误删用 token+Lua | L2 原子 / L6 / 卡 6 |
| 限流（滑动窗口） | ZSet：ZADD+ZREMRANGEBYSCORE+ZCARD | 窗口内精确计数；固定窗可用 INCR+EXPIRE 换省内存（精度降级） | L2 原子 |
| 消息队列 / 事件流 | **Stream**（本层） | 消费组 + PEL 小票 + 重放；List 弹出即焚、Pub/Sub 不落地 | 本层 |
| 社交关系 / 共同好友 | Set（SINTERSTORE） | 集合运算原生；intset→ht 随规模自适应 | L3 编码族 |
| 亿级 UV / 去重 | **HyperLogLog**（本层） | 固定 ~12KB 🔒 换可证误差；Set 线性内存撑死实例 | L4 近似心法 |
| 向量相似度召回（RAG/推荐） | **Vector Set**（8.0+，beta） | HNSW + int8 量化；先验收发行版、召回率与内存成本 | 本节补充 |
| 签到 / 画像位图 | Bitmap（SETBIT/BITCOUNT） | string 底层逐位寻址；1 亿人签到 ≈ 十几 MB/天（教学量级，以实测为准） | L3 string |
| 地理围栏 | GEO | 复用 ZSet + geohash，不引入新结构 | L3 |
| 延迟任务 | ZSet（score=到期时间戳）轮询 | TTL 是内存契约不是闹钟（L4 的 📌）——正主答案在此 | L4 |
| 配置 / 会话档案 | Hash 或 String(JSON) | 字段级读写用 Hash，整体读写用 String——别混用失效 | L3 / L4 |

> 卡 6：已交付（V1.4）——完整选型（fencing token、效率锁/正确性锁、RedLock 延迟分析）见决策卡 6。

**📐 表 B：横切能力 → 何时启用**（与数据结构选型**正交**的能力——在任何数据类型上都成立，不占“选哪个结构”的决策位，故单独成表、不与表 A 并列）：

| 横切能力 | 何时启用 | 决策卡 |
|---|---|---|
| 客户端读缓存（RESP3 tracking） | 读多写少、热点集中、进程内命中收益 > 失效推送成本；写多/计数器类 key 禁入 | 卡 10 |

| 集群分片与扩容 | 容量或写 QPS 超单机上限 | 卡 5 / 卡 8 |

### How —— 表 A 两行的展开：平行世界的 C（一条订单消息 / 一次 UV 打卡）

C 的旅程在 Level 8 画上句号——但叙事的设备还在：如果当年走进店里的不是 `SET sku:1001:stock 42`，而是一条订单消息、或一次 UV 访问，它的"一生"会怎么走？同一间便利店、同一位店长，把表 A 里缺席机制的两行（Stream / HLL）跑完。⚠️ 两行都不是 C 本人——是它的平行世界。

**支线 A：一条 Stream 消息的一生（小票箱的规矩）**

```text
① XADD orders * item sku:1001 qty 2
     → 追加一条，领到小票号 "1722…-0"（毫秒-序号 🔒，同毫秒自增）
② XGROUP CREATE orders g1 0   → 建消费组 g1，记住"本组读到哪"
③ XREADGROUP GROUP g1 riderA COUNT 1 STREAMS orders >
     → 骑手 A 取餐；消息没有删除，而是进**小票箱 PEL**
       （pending entries list：已取未认清单）
④ riderA 干完 → XACK orders g1 1722…-0 → 小票销毁
     ★ 线性化点：XACK 把条目从 PEL 摘除的那一行——
        "这笔交付成立"从这一瞬才成立
⑤ riderA 连人带餐消失 → 小票留在箱里：
     XPENDING 巡检（谁压着几张票、压了多久）
     XAUTOCLAIM 🔒（6.2+）按超时时长把票过户给 riderB → 消息复活
     → 交付语义：**至少一次（at-least-once）**。
       重复投递由消费端幂等兜底（呼应 T0"超时≠失败"）
⑥ 库存卫生：XADD orders MAXLEN ~ 100000 * …
     "~"近似修剪 🔒：按内部宏节点整块释放——摘走一整块而非逐条搬运，
        代价是可能多留一整个节点（官方 XTRIM 示例：300 条的流
        配 MAXLEN ~ 50 可能留下约 100 条 🔒，属预期的效率取舍；
        该数字以官方当前文档为准，不承诺跨版本稳定，勿当协议承诺抄进注释）
     不写"~"是精确修剪，逐条裁（更贵）。不修剪=只进不出（纪律块见下）
```

> 📌 最容易被误解的一点：Stream 不是"小号 Kafka"。它活在内存里，没有磁盘多副本留存层；它的不变量是 **PEL 小票箱**（消费语义），不是磁盘 offset（留存语义）。教学量级/削峰填谷用它是绝配；要长期回放、事件溯源、海量堆积，回 Level 5 想想介质账，去选真正的日志系统。



**支线 A 的纪律——内存卫生是两份责任**（写入方修剪 + 消费方认票；教训随结构在此，坑清单不再重复开号）：

- **错误 A**：`XADD` 从不带 `MAXLEN`——队列无限长，内存只涨不落
- **错误 B**：消费组只 `XREADGROUP` 不 `XACK` 不 `XAUTOCLAIM`——PEL 小票箱无限积压，内存同样涨
- **错因**：Stream 的内存卫生是**写入方（修剪）+ 消费方（认票）**两份责任，少一份都漏
- **便利店**：外卖单只进不出，取餐小票压满一箱没人销毁——最后连店门都推不开
- **线上现象**：used_memory 爬坡；`XPENDING` 显示百万级未认；记不住它也会触发 maxmemory 淘汰
- **修正**：`XADD … MAXLEN ~ N`（"~"的整块释放语义与官方示例数字见本支线 ⑥，以官方当前文档为准，不承诺跨版本稳定，勿当协议承诺抄进注释）；消费端 XACK 闭环 + XAUTOCLAIM 🔒（6.2+）兜底；监控三件套：`XLEN`、PEL 大小（`XPENDING` summary）、`used_memory`

**支线 B：HyperLogLog——不数人头，看水波**

```text
① PFADD uv:0802 "user:42"
     → 把元素哈希成均匀随机位形：低位选缸，高位看"最长前导零"（水波）
② 16384 🔒 个寄存器（缸），每缸只记见过的**最大纹高**——
     均匀随机下"见过 x 个零"的概率随基数指数衰减，
     全缸纹高合在一起反推基数（调和平均修正，教学描述，
     数学细节以 HLL 原始论文为准 🔒）
③ PFCOUNT → 估计值，标准误差 ≈ 0.81%（官方文档常数）
     代价：固定 ~12KB 🔒 装下亿级基数的估计
④ PFMERGE 周UV = 日1..日7：逐缸取 max 即可合并——
     但代价必须说清楚：O(N) 合并 N 个 HLL，
     官方复杂度标注"常数因子较高"（high constant）🔒：
     每个来源都要过一遍 16384 🔒 个寄存器；
     省的是"成本随基数增长"，不是"成本为零"

★ 不变量（近似结构没有线性化点，只有三条铁律）：
   ① 寄存器只记历史最大纹高 → PFADD 天然幂等（重复加同一元素无副作用）
   ② 只能并、不能减：没有 PFDEL，"今天减昨天"在数学上无解（纪律块见下）
   ③ 误差可证伪、不可对齐：你测得出"误差在 0.81% 内"，
      但永远不知道它此刻偏正还是偏负——两数相减得不到"净增"
```



**支线 B 的纪律——近似结构的账本纪律**（教训随结构在此，坑清单不再重复开号）：

- **错误**：`PFCOUNT uv:0802 - PFCOUNT uv:0801` 算"净增 UV"；或用 HLL 做计费口径
- **错因**：≈0.81%（官方文档常数）的误差**方向不可知**——两个估计值的差没有数学意义；且只有并、没有减（铁律②）
- **便利店**：用水波估计进店人数，还想减去昨天的得到"今天新客"——水波只记得最高纹，不记得昨天
- **线上现象**：报表对不上账被业务方追杀；换精确 Set 后内存爆炸才发现两头不是人
- **修正**：趋势/看板用 HLL（误差知情并公示）；精确口径用 Bitmap/Set 或离线数仓；评审时对每个"近似"指标写下误差上界

<a id="vector-set"></a>
### Level 9 补充：Vector Set 与发行版边界

Vector Set 不能因为命令名看起来像普通数据类型，就直接被塞进主链路。它是一个**版本与构建共同决定的能力**：

```text
VADD  → 写入向量元素
VSIM  → 按相似度召回
VINFO → 查看维度、量化与索引元数据
```

所附生产实践材料在本机 Redis 8.6.1 brew 构建中实测：Vector Set 命令可用，`VINFO` 可观察到 `int8` 量化与 HNSW 相关参数；同一构建中 JSON、TimeSeries、Bloom 等命令并不能据宣传语直接推定存在。**结论不是"某个发行版永远没有"，而是架构评审必须对实际部署构建做 `redis-server --version`、`COMMAND INFO`/冒烟命令核验。**

| 评审问题 | 决策边界 |
|---|---|
| 是否适合 PoC/小规模、延迟敏感的向量召回？ | 可以试，但把 beta 语义变化与召回率损失写进验收 |
| 是否适合生产级大规模向量库？ | 先比较成熟向量引擎；Redis 内存账、量化损失、重建与升级路径必须先算 |
| 是否能把 JSON/时序/概率结构当作"8.0 一定内置"？ | 不能；发行版/构建验证先于代码依赖 |

**因果落点：**Vector Set 的正确位置是"可选能力 + 发行版验收"，不是九层主线的基础依赖。把 beta 功能放进核心链路，等于把版本不确定性升级成业务可用性风险。

**徒弟**（两张货架合问）： Stream 的 at-least-once 和 HLL 的 0.81%，都算"不完美"，凭什么上生产？

**老陈**：因为它们的不完美**都写在名字里，且都能折算成钱**。at-least-once 的代价是消费端写幂等（一行唯一键/去重表的事），换来的是弹出即焚的根治；0.81% 的代价是"大屏看板做趋势、不做对账"这一条纪律，换来的是内存从 GB 级压到 12KB 固定（数量级教学参考）。真正危险的不是不完美，是**把不完美当完美用**——拿 List 当"可靠队列"、拿 HLL 当"精确账本"，才是事故之源（两支线的纪律块）。工程上所有"近似"，买之前先签误差知情同意书。

### Transfer —— 这一层能带走什么

1. **选型先问两个问题**：失败语义（丢一条会怎样）、误差容忍（错 1% 会怎样）。答完，表自己长出来。
2. **"近似家族"是一套通用心法**：抽样 LRU（L4）、HLL（基数）、MAXLEN ~（容量）——都是"可量化误差换数量级资源"。评判任何近似方案的统一句式：误差上界多少、业务能不能签字。
3. **复用即智慧**：GEO 复用 ZSet、Bitmap 复用 String、Stream 复用"追加+游标"这组最老的原语——Redis 自己的扩展方式就是编码复用，你的中间件设计也该先想复用。
4. **交付语义决定消费端设计**：at-least-once 的队列必须配幂等消费；把这个当成队列选型评审的必答题。


**本层新账**：无——货架全集盘点完毕。把九句口诀连起来背一遍，电梯版就在文末等你。

## 生产闭环补充：监控、事故复盘与上线验收

> 到这里，机制已经能解释"为什么"；生产还要把它变成"什么时候报警、如何止血、如何签字"。这段是横切闭环，不新增第 10 层，也不改变 C 的主线。

### 1. 先看趋势，再看报错

| 指标群 | 关键指标 | 它回答的问题 |
|---|---|---|
| 流量与命中 | `instantaneous_ops_per_sec`、`keyspace_hits/misses`、客户端 p99 | 请求是否正在从快路径滑向回源/排队 |
| 内存与淘汰 | `used_memory/maxmemory`、`mem_fragmentation_ratio`、`evicted_keys` | 是正常淘汰、内存泄漏，还是即将拒写 |
| 阻塞与后台任务 | `blocked_clients`、`SLOWLOG`、`latest_fork_usec`、`aof_delayed_fsync` | 主线程、fork、磁盘是否正在放大尾延迟 |
| 复制与高可用 | 主从 offset 差、`master_link_status`、Sentinel/Cluster 状态 | 切换窗口与数据新鲜度是否超预算 |
| 结构专属 | Stream 的 `XLEN/XPENDING`、HLL 误差抽样、tracking 表水位 | 队列积压、近似口径、客户端失效广播是否健康 |

阈值不是跨环境常数。先建立基线，再按业务 SLO 设置报警；">80%"、">0" 等只能作为待实测的示例，不能替代压测与演练。

### 2. 一次缓存雪崩的排障顺序

下面是**示意事故形态**，数值不作真实线上承诺：

```text
现象：DB 回源 QPS 上升、Redis 命中率断崖、接口 p99/5xx 上升
  ① 先看命中率曲线：确认回源增量来自缓存层
  ② 看 used_memory 与 evicted_keys：evicted_keys=0 且内存正常 → 暂不按淘汰处理
  ③ 看失效/TTL 分布：大量 key 同一窗口到期 → 锁定雪崩
  ④ 对照 DB 慢查询 key 集：确认是否为同一批业务数据

止血：
  - 对热点 key 临时延长业务可接受的 TTL；
  - 分批预热/加本地缓存；
  - 开启互斥重建，限制回源并发；
  - 对不存在 key 做空值占位或入口限流。

根治：
  - 写入端统一 `baseTTL + random(jitter)`；
  - DB 变更删除缓存并配置失败补偿；
  - 命中率、回源 QPS、evicted_keys、p99 建趋势报警；
  - 发布/重启前做热点预热与灰度，按批次冷启动。
```

**排障纪律：**前三步先读指标，不在根因未定位时同时改 maxmemory、重启 Redis、扩 DB；否则事故结束后无法知道哪项措施真正有效。

### 3. 上线前架构评审四问

1. **业务真需要 Redis 吗？**是缓存、计数、排序、消息、锁，还是 DB 已经足够？
2. **一致性档位是什么？**能忍短暂过期才进缓存；强一致写入由 DB/共识存储裁决。
3. **容量与性能到顶了吗？**编码、热 key、大 key、fork、跨槽操作和真实 p99 是否都压测过？
4. **故障怎么兜？**缓存可重建吗？淘汰能接受吗？主从切换/清缓存/打满内存/断链是否演练过？

评审输出不应只是"同意使用 Redis"，而应是可验证的验收项：QPS 上限、p99 SLO、回源上限、RPO/RTO、淘汰预算、恢复步骤与责任人。

### 4. 可直接贴进项目的最小清单

```text
上线前：
[ ] 数据一致性档位已标注；缓存不作唯一真相
[ ] TTL 含抖动；穿透/雪崩/击穿分别有对策
[ ] DB 更新后的删除有重试/CDC/延迟双删补偿
[ ] 大 key 已扫描，线上没有 KEYS/大 HGETALL/大同步 DEL
[ ] 热 key 有本地缓存、读扩散或拆分方案；Cluster 不被当作热点解法
[ ] maxmemory、淘汰策略、持久化/副本策略与数据可重建性匹配
[ ] 命令、编码、序列化、跨槽边界已核验
[ ] 监控面板与趋势报警已上线

上线后/演练：
[ ] 清缓存/重启后的预热与回源限流
[ ] kill 主、断链、fork/恢复、打满内存、慢客户端
[ ] Stream PEL 积压与 HLL 误差抽样
[ ] 复盘记录现象→证据→止血→根治→验收结果
```

## 🧪 合书自测

### 一页主线时序图（C = `SET sku:1001:stock 42` 的一生）

```text
 t0  应用线程调用 SET
 t1  客户端库序列化 RESP3，write()（★超时≠失败：应答丢失 ≠ 未执行）
 t2  epoll 门铃响 → 主线程读包/解析（6.0+ 前半段可由 io-threads 代劳）
 t3  lookupCommand → call() 前置检查（服务器状态 / maxmemory 淘汰）
 t4  expireIfNeeded（同 key 旧值若已过期 → 先删）
 t5  ★线性化点★ dbAdd/dbOverwrite 写全局 dict（encoding 自适应）
 t6  dirty++ → propagate：aof_buf + 各 replica 输出缓冲 + backlog
 t7  "+OK" 进输出缓冲 → 可写时回包 ──┐
      ─── 以下与 t7 的回包并行，不影响其已成立的时序 ───
 t8  事件循环尾部 flush AOF（write→page cache）；everysec：bio 线程 fsync
 t9  从库异步收到 C → 各自主线程重放 → REPLCONF ACK offset
 t10 满足 save 规则 → fork → 子进程按 fork 点冻结视图写 RDB
     （C 若发生在 fork 后：不入此镜，但在 AOF / 下一镜里）
 t11 主死：sentinel 投票 → offset 最大的从升主 → 客户端重连
     （竞态窗口：t7 已确认而 t9 未完成的写，可能丢失）
 t12 重启：按 manifest → RDB/混合段 + AOF 增量回放 → 字典重建
     （恢复时长以你的恢复演练实测为准）
```

### 自测题 → 必须答出的不变量

| # | 自测题 | 必须答出的不变量 |
|---|---|---|
| 1 | 为什么不加锁，`INCR` 也是对的？ | 任意时刻只有一个命令在执行；线性化点 = call() 内改 dict 的那一行 |
| 2 | 客户端超时了，这条写到底成没成？ | 超时 ≠ 失败；重试写命令需要幂等设计，否则可能双写 |
| 3 | 主库上能读到"已过期 5 秒"的 key 吗？ | 主库上任何读写先过 expireIfNeeded——不能；但它仍占着内存（惰性）。从库是另一套（见题 21） |
| 4 | BGSAVE 期间的新写去哪了？ | RDB = fork 点冻结视图；新写只在 AOF / 下一次快照里 |
| 5 | 为什么 `KEYS *` 能在线上闯大祸？ | 事件循环内的任何 O(N)，都是全体连接的延迟 |
| 6 | 主库回了 +OK 就宕机，数据一定在吗？ | 复制异步：存在竞态窗口；WAIT/WAITAOF 只能压缩它 |
| 7 | fork 会让内存翻倍吗？ | COW：共享物理页，写时复制；成本 = 页表复制 + 快照期写放大（THP 会恶化） |
| 8 | everysec 是不是"最多丢严格的 1 秒"？ | 是目标值不是承诺；磁盘 stall 时 write 会被拖延（看 aof_delayed_fsync） |
| 9 | 集群里 `MSET a 1 b 2` 为什么报 CROSSSLOT？ | 多 key 原子边界 = 单槽；要共槽用 {hashtag} |
| 10 | 为什么 `SET k v` 的内存占用，同样的数据换台实例可能不同？ | type 只是语义；encoding 由阈值与版本决定（listpack/ht/intset…） |
| 11 | `EXEC` 中途一条命令失败，已执行的会回滚吗？ | 不会。Redis 事务保证隔离与"语法错误整组拒执"，不保证回滚 |
| 12 | 单机内存 256 G 了，下一步一定是上 Cluster 吗？ | 不一定：先算账（fork 耗时、迁移成本、热 key）；分片是搬家能力不是荣誉 |
| 13 | 节点 A 私聊说"B 死了"，集群凭什么不认？ | PFAIL 只是本地怀疑；FAIL 需多数 master 在 node-timeout×2 🔒 窗口内附议 + 广播 |
| 14 | Stream 凭什么敢说"至少一次"？ | PEL 小票箱：XACK 才是交付点；不认领的票可被 XPENDING/XAUTOCLAIM 过户重投 + 消费端幂等 |
| 15 | 为什么 HLL 不能"今天 UV − 昨天 UV = 净增"？ | 估计误差方向不可知，估计值之差无数学意义；近似结构只有并集没有减法 |
| 16 | 持锁者 GC 停顿 35s（TTL 30s），他人获锁开工；旧持锁者醒来继续写——锁的哪一环"错了"？ | 哪一环都没错：lease 与业务耗时是两个互不知情的时钟；互斥终裁权必须移交资源侧（fencing token/版本号/唯一约束），官方 DLW 页原话背书 |
| 17 | `lua-time-limit`（7.0+ 正名 `busy-reply-threshold` 🔒）到点会自动杀掉脚本吗？ | 不会。只开启"回 BUSY + 允许 SCRIPT KILL"的门；未执行写才可杀，已执行写只剩 SHUTDOWN NOSAVE |
| 18 | Pipeline 里批量发的两条 `INCR`，中间会被别的客户端命令插队吗？ | **会**。Pipeline 只省 RTT，不打包原子性：每条命令各有自己的 Level 2 线性化点，中途允许他客插入；要"不可插队"用 MULTI/EXEC（本[坑「打包混用」](#pit-batching)总表） |
| 19 | "灾备机房挂了异步从库，我们就有了跨机房多活"——错在哪？ | 多端可写+自动解冲突是 Enterprise 的 CRDT/CRDB 专属能力；OSS 官方对照口径原话：cannot accept writes in multiple regions at once。异步从库 = 热备+就近读，写入口仍全局唯一（卡 9） |
| 20 | 跨机房从库断链 40 分钟归来，为什么大概率触发全量重同步？backlog 该按什么算？ | 增量窗口 = backlog 🔒 默认 1mb，跨城断链期间早被写流量刷穿 → offset 出窗 → PSYNC 退化为全量；按"峰值写速率 × 可忍断链时长"重算（教学推导，实测为准） |
| 21 | 主库已把 key 过期删掉，从库上还能读到它吗？ | 可能。从库不主动删、等主库 DEL：正常链路按"逻辑过期"（从库自己的时钟 🔒）回 nil 但内存不释放；主从时钟偏差 / 断链（replica-serve-stale-data 🔒 默认 yes）时，已过期/已删的 key 在从库上仍可读（[坑「从库读过期」](#pit-replica-expire)） |
| 22 | 穿透、雪崩、击穿为什么不能共用一把锁？ | 根因不同：不存在的 key、齐整 TTL、单热点瞬间；分别用空值/布隆、TTL 抖动、互斥重建 |
| 23 | 为什么上 Cluster 仍可能被一个热点 key 打挂？ | 槽位只决定归属，不会把同一 key 的 QPS 自动分散；要本地缓存、读扩散或拆 key |
| 24 | 锁的 Lua 释放返回 0，为什么不能重试 DEL？ | 返回 0 说明 token 不匹配，锁可能已易主；重试会误删别人的锁，应走幂等/补偿 |
| 25 | Vector Set 为什么不能直接写进核心链路？ | beta、发行版构建能力可能不同，HNSW/量化有召回与内存代价；先做实际构建核验与 PoC 验收 |

<a id="sec-pitfalls"></a>
## ⚠️ 坑与细节（15 个）

每个坑五段：错误代码/操作 → 错因 → 便利店里的后果 → 线上现象 → 修正。

坑号按**认知依赖序**排列：后坑只依赖已讲过的 Level；与既有坑成镜像对的紧挨排列（[坑「读写分离」](#pit-replica-read)与[坑「从库读过期」](#pit-replica-expire)即一对）。**编号只是位置，不是身份**：正文交叉引用一律写 markdown 链接 `[坑「……」](#pit-…)`——**显示文本 = 坑标题的关键词/可读简称，锚点 id = 固定句柄**：重排、改名、合并都不再需要改引用，死链可机械检测（V1.8/V1.9 的两次全文级联重排是序数引用的代价，V1.11 起引用与标题解耦）。**与结构成对交付的教训（如 Stream/HLL 的纪律）直接写进所属 Level 的支线，不在坑清单重复开号**——坑清单只收跨层事故与排障速查。

<a id="pit-keys"></a>
### 坑 1：`KEYS` 盘库
- **错误**：`KEYS order:2024*`（线上百万级 keyspace）
- **错因**：全表 O(N) 扫描在单线程事件循环内执行（Level 2 公理）
- **便利店**：店长撇下收银，逐格清点全店商品，门口队伍排到街尾
- **线上现象**：全体连接延迟飙升/超时；从库心跳超时，连锁误判
- **修正**：`SCAN cursor MATCH … COUNT n` 分批；运维查询走从库；必要时离线导出 RDB 分析

<a id="pit-del-bigkey"></a>
### 坑 2：`DEL` 大 key
- **错误**：`DEL huge:list`（几百万元素）
- **错因**：同步释放整块结构的对象与内存，事件循环停摆
- **便利店**：店长亲手把一整排货架拖去废品站，全店等着
- **线上现象**：秒级毛刺，监控上一根孤零零的尖峰
- **修正**：`UNLINK`（异步惰性释放）；`lazyfree-lazy-user-del yes` 🔒；大对象治理（见[坑「胖 value」](#pit-fat-value)）

<a id="pit-setnx"></a>
### 坑 3：`SETNX` + `EXPIRE` 两条命令
- **错误**：`SETNX lock 1` 然后 `EXPIRE lock 30` —— 进程在两条之间崩了
- **错因**：非原子；锁永久存在 → 死锁
- **便利店**：寄存柜钥匙发出去了，"使用期限"纸条还没写，发钥匙的人猝死了
- **线上现象**：业务永远卡在某把锁上，重启才能发现
- **修正**：`SET lock token NX PX 30000` 原子一把梭；解锁用 Lua 比对 token 再删；并认知分布式锁的边界（需要 fencing；RedLock 存在公开争议，勿当银弹；完整选型与 fencing 论证见决策卡 6）

<a id="pit-maxmemory"></a>
### 坑 4：不配 `maxmemory` / 乱配 policy
- **错误**：默认跑长跑实例；或持久数据配了 `volatile-ttl` 而大多数 key 根本没 TTL
- **错因**：内存涨到物理极限 → 被内核 OOM-kill；或撞 noeviction 后写全部失败；volatile 系策略下"无 TTL 的 key 不可淘汰"(`≈` noeviction 的假象)
- **便利店**：仓库只进不出，最终爆仓，新货卸不下
- **线上现象**：实例突然消失（dmesg 里的 OOM）；写接口大面积报错
- **修正**：决策卡 2——maxmemory ≈ 物理内存 70–80%（教学参考，实测校准）+ 按业务选 policy + `evicted_keys` 入监控

<a id="pit-fsync-always"></a>
### 坑 5：`appendfsync always` 拍脑袋
- **错误**："金融级"自我感动，未压测直接 `appendfsync always`
- **错因**：每次写都等 fsync，写延迟挂到磁盘（Level 5 的墙）
- **便利店**：每卖一件商品，都要求会计当场盖章锁进保险柜
- **线上现象**：p99 写延迟数量级恶化（以你的实测为准）；`aof_delayed_fsync` 涨
- **修正**：everysec 起步；对少数强语义接口用 WAITAOF 🔒（7.2+）；修正"everysec = 严格 1 秒"的认知（勘误表 #3）

<a id="pit-thp"></a>
### 坑 6：BGSAVE 期间 THP 开着
- **错误**：云主机/容器镜像默认 THP=always，定时 bgsave 照跑
- **错因**：COW 粒度从 4K 变 2M，快照期写放大数倍；fork 本身随页表变大也变慢
- **便利店**：拍照时规定"动一件商品、整面墙重拍"
- **线上现象**：`latest_fork_usec` 高；BGSAVE 期间 RSS 飙升、p99 毛刺
- **修正**：关闭 THP（never）或 madvise；bgsave 错峰；把 RDB 挪到从库做（注意从库同样受 COW 影响）；同族前置检查：`vm.overcommit_memory=1`（=0 时内存吃紧 fork 直接失败，见 Level 5）

<a id="pit-nopersist"></a>
### 坑 7：把 Redis 当唯一存储，又全关持久化
- **错误**：`appendonly no` + `save ""`，数据却不可重建
- **错因**：进程重启 = 数据归零
- **便利店**：不拍照不记账，赌这条街永不停电
- **线上现象**：一次 OOM-kill 之后，业务数据人间蒸发
- **修正**：凡不可重建的数据：AOF everysec 起步 + 至少一个副本 + **定期恢复演练**（没恢复过的备份不存在）

<a id="pit-lua"></a>
### 坑 8：Lua 大脚本堵循环
- **错误**：一个脚本里循环几十万次做批处理
- **错因**：脚本与命令互斥执行（脚本内默认原子）→ 事件循环停摆；`SCRIPT KILL` 只能杀掉"还没执行过写"的脚本 🔒，已写过的只能 `SHUTDOWN NOSAVE`（以你版本语义为准）
- **便利店**：一位顾客掏出三年购物清单，要求一次性算完账
- **线上现象**：`BUSY … script` 报错刷屏；全体连接超时；sentinel 误判
- **修正**：拆小步、分批执行；`lua-time-limit` 🔒（默认 5000ms）只是"开始响应 KILL"的时间，不是超时自杀；上线评审与演练三板斧见决策卡 7

<a id="pit-batching"></a>
### 坑 9：混用 Pipeline / MULTI / Lua 三种"打包"
- **错误 A（拿 Pipeline 当原子）**：以为批量发的两条命令（`INCR c` + `DECR stock`）中间不会被别的客户端插队
- **错误 B（拿 MULTI 当条件分支）**：想写"if 上一条返回 X 就跳过下一条"——QUEUED 阶段拿不到任何执行结果，分支根本写不出来
- **错误 C（拿 MULTI 当回滚事务）**：依赖"EXEC 出错自动回滚"设计资金/库存操作（入队期语法错误 → 整组拒执；执行期某条失败 → **其余照跑**，官方设计如此）
- **错因**：三种打包解决的是三件不同的事，能力边界不互通——

  | 维度 | Pipeline | MULTI/EXEC | Lua/Function |
  |---|---|---|---|
  | 解决什么 | 省 RTT（N 次往返 → 1 次收发） | 排队 + 执行屏障：批内不被其他客户端插队 | 不可插队 + 能看中间结果做分支 |
  | 原子性 | **没有**：每条命令仍独立走 Level 2 六步、**各有自己的线性化点**，中途允许他客命令插入 | EXEC 起连续执行完，中途无人插队（同一台收银机连续结账） | 同 MULTI，且脚本内可读 A 再决定写 B |
  | 能否条件分支 | 不能，纯批量发送 | 不能：QUEUED 阶段互相看不见执行结果 | 能——相对 MULTI 的最大增量 |
  | 网络行为 | 客户端攒批一次 write、一次读完所有回包 | 客户端逐条发（收 QUEUED），EXEC 触发批量执行 | 一次 EVAL / FCALL 请求 |
  | Cluster 约束 | 理论不要求同槽；实践按槽分批，否则退化成多次单发 | **同槽**，跨槽直接 CROSSSLOT（[坑「跨槽」](#pit-cross-slot)同源） | 同槽（[坑「跨槽」](#pit-cross-slot)同源） |

- **便利店**：Pipeline 是一个人一口气报十样货——收银照样一件件办，队伍里照样有人能在两件之间插一句"加个茶叶蛋"；MULTI 是点套餐——后厨按成单一气呵成出餐，但你下单时看不到上一道的成色、临时改不了下一道；Lua 是你把整本菜谱交给店长——他边尝边做，中途不接待别人。
- **线上现象**：A → 计数与扣减之间被插入，超卖/负库存（这是线上最常见的真实事故形态）；B → 分支永远走不到，或把判断挪回应用侧、给 TOCTOU 留出一个网络往返的窗口；C → 半完成状态，对账对不上
- **修正**：纯省 RTT → Pipeline（集群下跨槽按槽分批）；要"不可插队" → MULTI（接受无分支）；要"看中间结果定分支" → Lua/FUNCTION（决策卡 7）；要"没人动过才提交" → WATCH + MULTI（决策卡 6）；要"失败回滚"的 ACID 语义 → 回关系库（坦白领见勘误表 #4）

<a id="pit-replica-read"></a>
### 坑 10：读写分离读从库
- **错误**：写主读从扛读压，读"我刚写的配置"
- **错因**：异步复制，从库天然落后一个窗口（监控 `master_repl_offset` 与从库偏移差）
- **便利店**：总店改了价目表，分店的小票复印件还在路上
- **线上现象**："刚保存的就丢了！！！"工单
- **修正**：写后读走主库（或 WAIT 保底）；可容忍延迟的接口才读从；客户端做好粘性路由；本坑的镜像见[坑「从库读过期」](#pit-replica-expire)（从库读得到"已过期"的数据）——两条都是"从库不是主库的强一致镜像"的不同侧面

<a id="pit-replica-expire"></a>
### 坑 11：读从库读到"已过期"的数据（从库不删过期 key）
- **错误**：读流量走从库 + key 带 TTL；主库侧已过期多时，从库流量仍返回旧值；主从断链期间从库把主库已删/已淘汰的 key 当活着的卖
- **错因**：从库**从不主动删除**过期 key（Level 4 的惰性班/抽查班只在主库跑）——读路径只判"逻辑过期"（判据 = 从库**自己的墙钟**，🔒 5.0~7.2 源码一致），回 nil 但不删、不传播；物理删除只发生在收到主库传播的 DEL 那一刻。于是两个窗口：① **主从时钟偏差**（官方原话：replicates expires with an accuracy that is not ideal）——从库钟慢时，主库已过期的 key 在从库仍按活着的返回；② **断链**——DEL 传不过来，主库侧已删/已淘汰的 key 在从库继续可读（replica-serve-stale-data 🔒 默认 yes），且过期未删的 key 一直占着从库内存（从库默认不淘汰：replica-ignore-maxmemory 🔒 默认 yes）
- **便利店**：总店撕掉临期标签，分店不自己扔货——总店的"扔货通知"（DEL）没送到之前，分店照样把过期商品卖给顾客
- **线上现象**："TTL 已过仍被读走"的 key 全部集中在从库；断链时段从库读到主库已删的值；从库 used_memory 高于按主库口径的预期（过期未删积压）
- **修正**：与[坑「读写分离」](#pit-replica-read)是一对镜像（它：读不到刚写的；本坑：读得到已过期的）——① 走从库的带 TTL key，业务语义必须容忍"过期后仍短暂可读"（窗口 = 时钟偏差 + DEL 传播/断链时长；接受不了就业务侧校验时间戳或读主库）；② 断链期间从库默认照常回旧值，不可容忍就显式 `replica-serve-stale-data no`（代价：断链时从库读直接报 MASTERDOWN）；③ 从库内存水位按"主库口径 + 过期未删积压"双看，别只盯主库；④ failover 升主后，新主自那一刻起独立开始过期处理（官方 replication 页原话；清理节奏版本相关 🔒，以你版本为准）

<a id="pit-cross-slot"></a>
### 坑 12：集群里照单机写法打多 key（跨槽）
- **错误**：切 Cluster 后照旧 `MSET a 1 b 2`、Lua 跨 key
- **错因**：多 key 原子边界 = 单个槽 → `CROSSSLOT`
- **便利店**：一张团购券想跨两个门店核销，系统不认
- **线上现象**：切量当天接口批量报错回滚
- **修正**：schema 评审阶段用 `{hashtag}` 共槽重设计；pipeline 按槽分组；无法共槽的：放弃原子，改幂等 + 补偿

<a id="pit-fat-value"></a>
### 坑 13：胖 value 全量搬运 + 失效广播风暴
- **错误**：单 value 几 MB 还 `MGET` 全量拉；客户端缓存开 BCAST 全量订阅推送
- **错因**：大块字节搬运堵 IO（io-threads 也救不了"又胖又频"）；tracking 广播面失控打爆客户端
- **便利店**：一位顾客要求把整面墙的货搬上收银台；广播喇叭对每个顾客播报全店每一次价格变动
- **线上现象**：网卡打满、p99 毛刺、`client-output-buffer-limit` 触发踢连接
- **修正**：拆对象/按需取字段/压缩（权衡 CPU）；MGET 分批；客户端缓存（RESP3）用默认/opt-in 模式控制广播面 🔒

<a id="pit-node-timeout"></a>
### 坑 14：`cluster-node-timeout` 手痒调小
- **错误**：嫌 15s 换主太慢，`CONFIG SET cluster-node-timeout 5000`（甚至更低）
- **错因**：PFAIL→FAIL 的窗口与选举延迟都锚在这个参数上；调小 = 调低"错杀阈值"，网络抖动被误判为死缓
- **便利店**：把"多数街坊签名才能贴讣告"改成"一个人喊一嗓子就封店"——风吹草动就换店长
- **线上现象**：抖动期 cross-AZ 连锁误判，无谓 failover 连环触发；客户端 -MOVED 风暴，可用性反而更差
- **修正**：调参前先给"误判一次 failover 的代价"定价（Level 8 师徒对话）；多数生产环境默认 15s 🔒 是甜点

<a id="pit-dr-dualwrite"></a>
### 坑 15：把"跨机房从库"当"双活容灾"
- **错误**：DR 评审材料写"Redis 已跨机房双活：主机房集群+灾备机房集群，异步复制打通，两机房同时承接读写"
- **错因**：把复制管道的**存在**当成写一致性语义的**存在**。OSS 无 CRDT：复制单向、从库默认只读 🔒（replica-read-only yes），两端同时可写没有任何冲突裁决机制——"多端可写+自动解冲突"是 Enterprise 的 Active-Active（CRDT/CRDB）专属，不是配置能拼出来的
- **便利店**：小票只许从总店顺风吹向分店；分店擅自开收银台记自己的账，月底两本账永远合不上——而且**没有一个机制宣判哪张票是真的**（居委会只管选店长，管不了跨街对账）
- **线上现象**：平时岁月静好（两边业务 key 集重叠少，冲突没炸）；一次同 key 双写、或一次切换后旧入口忘关 → 两地库存/余额分叉，对账 job 天天报差异，没人敢签字以谁为准
- **修正**：卡 9——写入口全局唯一（DNS/VIP 一刀切+旧主 fencing），异地 = 热备+就近读；真双写需求走 Enterprise CRDB 或单元化（写按用户锚定单机房，冲突消灭在路由层）；评审措辞从"双活"改"单写入口+异地热备"，一词之差是事故定级之差

<a id="sec-decisions"></a>
## 🏆 生产决策卡（机制 → 能签字的决定）

### 卡 1：热点数据要不要上缓存（Cache-Aside）

**场景与判断**：读远多于写、热点集中、可容忍秒级内短暂不一致 → 上；要求强一致或写多读少 → 不上。

| 机制（出处） | 决策 |
|---|---|
| 介质账（L1） | 只缓存热点数据；全量真相留在 DB，缓存永不作唯一存储 |
| 惰性过期（L4） | 每个缓存 key 必带 TTL，并加随机抖动防同时失效（雪崩） |
| 命令原子（L2） | 互斥重建成 single-flight：`SET lock NX PX`，防击穿 |
| AP 复制（L6） | 缓存丢失可重建 → 纯缓存实例不追持久化（卡 3 对照） |

**落地代码**（伪码，Java/Lettuce 同构）：

```text
读：v = GET k
    未命中 → SET lock_k token NX PX 3000
        抢到 → v = db.query(k); SET k v PX (300000 + rand(60000)); 解锁（Lua 比对 token）
        没抢到 → 短睡重读 / 回源限流（防狗桩）
写：先写 DB → DEL k（失败进重试队列/死信）   ← 失效，而不是"更新缓存"
    或：订阅 binlog（CDC）驱动失效             ← 更稳，链路更长
```

**不能做的错误决策**：① 把缓存当主库（无 TTL 全量常驻）；② 双写"同时更新 DB 与缓存"（并发交错必脏——失效优于更新）；③ 裸用"先删缓存再写库"（读并发回填旧值，要么延迟双删要么 CDC）。

**验收指标**（可监控的具体名字）：`keyspace_hits/(keyspace_hits+keyspace_misses)` ≥ 0.95（热点接口）；回源 QPS < DB 容量的 60%；接口 p99 低于基线 SLO；演练：主动掐掉 Redis 30 分钟，DB 不崩（限流降级预案生效）。

### 卡 2：容量与淘汰策略评审

**场景与判断**：任何实例上线前必过的评审；缓存与持久语义数据分开部署。

| 机制（出处） | 决策 |
|---|---|
| 内存是钱（L1/L4） | maxmemory ≈ 物理内存 70–80%（教学参考，实测校准），预留 fork 与缓冲 |
| 抽样淘汰（L4） | 纯缓存：allkeys-lru（热点稳态可 lfu）；有持久语义：noeviction——宁可写失败报警，不可偷偷丢 |
| 碎片（L3） | jemalloc 碎片率入巡检，超出区间追查 encoding 分布 |

**落地配置**：

```text
maxmemory 48gb              # 64G 物理机的教学示例
maxmemory-policy allkeys-lru
maxmemory-samples 10        # 默认 5 🔒（已实机核对）；调大更准、更费 CPU，按实测定
```

**不能做的错误决策**：① 不配 maxmemory；② 缓存与队列/持久数据同实例共享一个 policy；③ volatile-* 而多数 key 无 TTL（= noeviction 假象）；④ evicted_keys 长期猛涨无告警。

**验收指标**：`used_memory` 稳定低于 maxmemory；`mem_fragmentation_ratio` ∈ [1.0, 1.5]（教学区间）；`used_memory_rss`/物理内存 < 85%；OOM-kill 次数 = 0；告警项：`evicted_keys` 速率、`rejected_connections`。

### 卡 3：持久化选型评审（先写 RPO/RTO）

**场景与判断**：评审第一行先写两个数字：**最多丢几秒（RPO）、最多停几分钟（RTO）**，再往下谈配置。

| 机制（出处） | 决策 |
|---|---|
| fsync 的墙（L5） | RPO ≈ 1s 可接受 → appendonly yes + everysec |
| fork/COW（L5） | 要快速恢复 → aof-use-rdb-preamble yes 🔒；大实例 RDB 挪到从库做 |
| 纯缓存 | RPO 无所谓 → 允许全关（且接受重启冷启动回源压测） |

**落地配置**：

```text
appendonly yes
appendfsync everysec
aof-use-rdb-preamble yes
save "900 1"                # 兜底快照，阈值按变更频率定
dir /data/redis             # 独立大盘，磁盘 stall 入监控
sysctl -w vm.overcommit_memory=1   # fork 前置条件（Level 5）：=0 时内存吃紧 fork 直接失败
```

**不能做的错误决策**：① 未压测直接 `appendfsync always`；② 主库高峰时段 bgsave；③ 从不做恢复演练（没恢复过的备份不存在）；④ 把 everysec 当"严格最多丢 1s"（勘误表 #3）；⑤ 只查 THP 不查 `vm.overcommit_memory`（fork 前置条件成对核查，见 Level 5）。

**验收指标**：`aof_delayed_fsync` 基线 = 0；`latest_fork_usec` < 你压测划定的阈值；`rdb_last_bgsave_status:ok`；**恢复演练实测 RTO** ≤ SLO（写进评审记录）；磁盘 await/util 常态监控；日志 grep `Can't save in background` = 0（fork 失败数，overcommit 前置条件核查）。

### 卡 4：高可用（Sentinel）上线评审

**场景与判断**：数据有持久语义，或停机损失 > 值班成本 → 必配；纯缓存且可秒级重建 → 可缓配。

| 机制（出处） | 决策 |
|---|---|
| 竞态窗口（L6） | min-replicas-to-write 1 + min-replicas-max-lag N(秒) 收窄脑裂写 |
| 投票（L6） | sentinel ≥ 3 且跨机房；quorum=2；down-after-milliseconds 按网络实况定 |
| 客户端路由 | 用支持 sentinel 发现与拓扑刷新的客户端（Lettuce/Jedis），压测重连风暴 |

**落地配置**：

```text
sentinel monitor mymaster <ip> 6379 2
sentinel down-after-milliseconds mymaster 10000
sentinel failover-timeout mymaster 60000
# redis.conf（主）：
min-replicas-to-write 1
min-replicas-max-lag 10
```

**不能做的错误决策**：① sentinel 只起 1–2 个（多数派不成立）；② VIP 漂移当唯一方案且不处理旧主复活（双主写分叉，需 fencing）；③ 把 WAIT 配成全局默认（它是接口级旋钮）；④ 主从摆同一台物理机/同一机架（"分布式了个寂寞"）。

**验收指标**：每季度 failover 演练：断主 → 客户端恢复写 p95 ≤ 60s（教学 SLO，自定后签）；演练期间"客户端收到 OK 但最终丢失"的写条数**实测入档**；告警项：`master_link_down_since_seconds`、sentinel tilt 事件 = 0。

### 卡 5：要不要上 Cluster / 扩容演练

**场景与判断**：数据规划 > 单机内存控制线（示例：单实例 ≤25 GB 🔒 经验教学线，以你 fork/迁移压测为准），或写 QPS 预期超单机容量，或需多机分布 → 上；否则单机 + 哨兵继续扛（简单是资产）。

| 机制（出处） | 决策 |
|---|---|
| slot = 搬家单位（L7） | 容量规划按槽均摊；扩容 = 迁移计划而非开关 |
| MOVED/ASK（L7） | 客户端版本必须会处理重定向与拓扑刷新 |
| 槽内多 key 边界（L7） | schema 评审：需多 key 原子的一律 {hashtag} 共槽 |
| 热点不归拓扑管（L7） | 热 key 单独立项：本地缓存 / 读扩散 / 拆 key |

**落地动作**：

```text
创建：redis-cli --cluster create …（≥3 主 3 从，跨物理机/机架）
演练：--cluster reshard 灰度 10% 槽位 → 观测 → 分阶段推全量，随时可回滚
```

**不能做的错误决策**：① 生产直接全量 reshard 无灰度无回滚；② 应用未做 CROSSSLOT 改造就切量；③ 全节点挤一个可用区；④ 集群规模失控（官方建议千节点以内，gossip 成本随规模涨——以官方文档为准）；⑤ 跟风上 Cluster（单机+哨兵明明够）。

**验收指标**：迁移期 p99 毛刺 < 自定阈值；`CROSSSLOT`/`-ASK` 错误率 ≈ 0；MOVED 每秒次数无风暴（客户端路由表是热的）；迁移速率 slots/min、keys/s 实测入档；隔离演练：单主断网后窗口内写损失在预算内。

### 卡 6：分布式锁选型（效率锁 / 正确性锁 / RedLock 之争）

**场景与判断**：先审用途，再审实现——
- **效率锁**（防重复工作，重复了只是浪费、不会出错：热点缓存重建、定时任务防重跑）→ 单实例 `SET NX PX` 足矣，别上 RedLock 白交多数派写的税；
- **正确性锁**（两个"持锁者"并发写会坏数据：账务状态机、库存扣减）→ 任何基于超时的锁都只能当**加速层**，互斥的最终裁决必须移交资源侧（fencing token / DB 版本号 / 唯一约束）；
- 全链路要求"确认即互斥"且不愿自建 fencing → 换 etcd/ZooKeeper（原生单调递增 revision/zxid），或干脆用 DB 约束实现互斥——**最好的分布式锁常常是不用锁**。

| 机制（出处） | 决策 |
|---|---|
| 命令原子（L2） | 上锁单命令 `SET k token NX PX ttl`；解锁 Lua 比对 token（[坑「SETNX」](#pit-setnx)已立此规） |
| 主从异步（L6） | 锁写在主、主死未同步 → 新主"无锁" → 二次持有：效率场景接受此窗口，正确性场景靠 fencing 兜底——窗口可收窄不可消除 |
| 选举/多数派交集（L8） | RedLock 的本质是把 quorum 交集借到锁上：N=5 独立实例，拿到 N/2+1（≥3）才算持锁；有效余量 `MIN_VALIDITY = TTL − 获锁耗时 − 时钟漂移修正` 🔒（官方 DLW 页推导式）——获锁越快，"多数派并存"窗口越大 |
| 超时锁的本质边界（本卡时序） | lease 剩余时间 ≠ 业务剩余工作量 → fencing token：资源侧只认最新票据 |

**RedLock 延迟分析（2016 年公开辩论的完整时序——为什么"每个环节都对"照样击穿互斥）：**

```text
 t0  C1 获锁（TTL 30s，票据 33），向资源 R 写
 t1  C1 进程 GC stop-the-world（或网络分区/调度抖动），"死亡" 35s
     ——没有任何告警；对 C1 而言世界只是快进了一帧
 t2  锁到期自然释放（这是特性不是 bug）；C2 获锁（票据 34），写 R
 t3  C1 苏醒，记忆里仍"我持锁"，继续写 R（携带票据 33）
     ★ 互斥被击穿，而锁服务的每一步都符合规范
 病灶：锁只能回答"锁本身是否还在有效期"，
       回答不了"你对资源的写入还是不是最新的合法写入"——
       两个事实隔着进程边界，互不知情。
 处方（fencing）：资源 R 记录 max_seen=34；
       票据 33 的旧写入到达 → 拒绝。
       互斥终裁权从"锁服务"移交"被保护的资源"。

辩论交代（原文出处，均可查）：
  Kleppmann《How to do distributed locking》（2016-02）：
    以上述 GC/时钟跳变时序论证无 fencing 的超时锁不保证正确性，
    并提出 fencing token 方案（单调票据：ZK zxid / 自增计数器）。
  antirez《Is Redlock safe?》：认为在时钟与延迟假设可控时可接受。
  官方《Distributed Locks with Redis》页把这场辩论沉淀为两条工程建议
  （Disclaimer about consistency，原文照录）：
   ① "You should implement fencing tokens."
      ——且明言"applies to any distributed locking system"
   ② "Redis is not using monotonic clock for TTL expiration"
      ——墙钟跳变可让锁被多进程同时持有；NTP 与管理纪律只能缓解
  结论不是"谁赢"：而是暴露边界——锁 ≠ 互斥。
```

**落地代码**：

```text
效率锁（够用即止）：
  SET lock:hot:sku1001 tok NX PX 3000        # 重建互斥，配卡 1 的 single-flight
  -- 解锁 Lua（比对 token 原子删）见坑「SETNX」

续约看门狗（谨慎使用）：
  Redisson lockWatchdogTimeout 默认 30000ms 🔒
  （Redisson Config.java 源码核实）；续约节奏约为其 1/3 🔒（以所用版本源码为准）
  ⚠️ 看门狗和业务跑在同一进程：STW 把它和业务一起冻住，
     救不了 t1 那 35 秒——它解决"任务略超 TTL"，不解决"正确性"

正确性写入（fencing，资源侧闭环）：
  ① 票据源：INCR fence:order:42 → 34（或 DB 行版本号 / ZK zxid / etcd revision）
  ② 写 R 时携带票据；R 端维护 max_seen
  ③ 写入条件：票据 > max_seen 才接受并更新 max_seen
     ——C1 的 33 在 C2 的 34 之后到达：拒绝。双写窗口在资源侧收敛为零
```

> 📌 票据来源是单独的架构决策：RedLock 的 N 实例各自 INCR 拿不出全局单调票据（这正是辩论中被点名的软肋之一 🔒，以原文为准）；票据源要么用 DB 序列/共识存储，要么单点全局 INCR 加高可用——评审时单独签字。

**不能做的错误决策**：
① 单实例锁守正确性数据却不上 fencing（等于赌 t1 永不发生）；
② 看门狗无限续命长任务——锁语义被杀死、任务失控被掩盖、"进程死了"的检测被无限推迟（必须"干完才算数"的业务要的是任务队列+幂等，不是锁）；
③ RedLock 五实例摆进同一机房/同一故障域（多数派形同虚设，多数派写的税白交）；
④ 锁包大事务：锁内塞 IO 与慢计算，持有时长尾拖垮所有竞争方（锁内只做"读状态 + 改状态"）；
⑤ 重试不设随机退避（官方 DLW 页明言：失败应随机延迟重试，消解羊群同时抢锁的 split brain 竞争）。

**生产实践惯例（行业通行做法，非单一厂商口径，无内部数据）**：
- 锁 SDK 化：禁止业务裸写 `SET NX`；统一库内置 token、看门狗、获锁耗时直方图、fencing 协助；策略改动走配置不走代码；
- 正确性场景双保险常态化：Redis 锁只做并发削减，DB 唯一索引/乐观锁版本号做终裁——两条防线相互独立；
- 给"锁获取等待时长"单设 SLO 并看长尾：长尾突变往往比失败率更早暴露"有人在锁里干慢活"。

**附：WATCH——Redis 自带的轻量 fencing（数据全在 Redis 界内时的首选）**

当"资源"就是 Redis 自己的 key（不涉及下游 DB/文件系统），不必引入外部 fencing 源，`WATCH + MULTI` 就是原生乐观锁——一句话记忆：**fencing 是让别人认账，WATCH 是让 Redis 自己拒收旧账**。

```text
① WATCH stock:sku:1001           ← 盯柜：EXEC 前这 key 被任何人碰过（含自己）
② cur = GET stock:sku:1001       ← 读出旧值（在 WATCH 的监视期内）
③ MULTI
④   DECR stock:sku:1001          ← 基于 cur 计算的写入（此间仍有他客可插队进队列,
                                    但不影响判定：任何第三方改动已让 WATCH 失效）
⑤ EXEC                           ← ★若 ②③ 之间有人碰过 key 或被连接断开：
                                    整组事务拒绝执行，返回 nil
                                    → 客户端回到 ① 重试（乐观锁重试循环）
   CAS 语义 = "确认无人动过"才提交，正好补齐 MULTI 无分支的短板：
   分支判断（cur>0 才扣）放在客户端 ②④ 之间完成
```

| 对照 | fencing token（卡 6 主线） | WATCH + MULTI |
|---|---|---|
| 谁裁决 | 下游资源（DB/存储）查 max_seen | Redis 自己在 EXEC 时比对 WATCH 指纹 |
| 票据在哪 | 业务侧维护版本号/计数器 | Redis 服务端维护（对应用透明） 🔒 |
| 适用边界 | 跨出 Redis 的写（外部资源终裁） | 读写都落在 Redis 界内 |
| 失败形态 | 需求>写被拒，记录告警 | EXEC 返回 nil，客户端重试 |
| 心智定位 | 正确性锁的最终防线 | 轻量 CAS：够用就别上外部 fencing 基建 |

> 🔒 **前沿提示（超出 7.2.x/8.0 基线，标注待查）**：官方 latest 文档显示 **Redis 8.4** 起字符串支持原子 CAS：`SET key val IFEQ old` / `IFNE` / `DELEX`（SET 命令页 `since: 8.4.0` 已核 2026-08-02），官称比 WATCH 循环"更简单更快"。本文基线内仍以 `WATCH+MULTI` 为标准答案；你若部署 ≥8.4，请自行以 `SET key val IFEQ old` 替代度重测后采用。

**验收指标（可监控/可演练）**：SDK 埋点 `lock_acquire_seconds` P99 低于自定阈值、`lock_wait_timeout_total` 增速平稳；资源侧 `fencing_rejected_total` 平时 = 0，**演练时必须 >0 才证明 fencing 活着**；季度演练：构造持锁者休眠 > TTL，观测旧票据写入被拒、审计日志无并发写；Redis 侧以 `INFO commandstats` 中 set/eval 调用占比复核锁流量水位。

#### 生产落地回检：把错误用法挡在 API 面

专题材料中的真实落地形态可以压缩成两个受控入口，而不是让业务到处拼 Redis 命令：

```text
tryLock(key, lease) → true / false     # 非阻塞，失败是否重试由业务决定
unlock(key)                           # 只能在 finally/模板方法中调用

内部等价语义：
  SET key token NX EX/PX lease
  → token 与调用上下文绑定
  → Lua/EVALSHA：get(key)==token 才 DEL
  → EVALSHA 遇 NOSCRIPT：自动 SCRIPT LOAD / EVAL 回退
```

- 锁 key 用 `模块::动作::业务粒度ID` 命名，先审粒度再审算法；全局锁过粗，跨实体业务用单实体锁又过细。
- 脱敏案例里短 TTL 常落在秒级（如 1–10 秒只是案例，不是默认配置）；长任务不能靠无限延长 TTL 伪造正确性。
- `unlock` 返回 0 表示锁已过期/易主或本次没有持有，**不重试删除**；业务回到幂等检查、补偿或下一个调度周期。
- 框架在 `finally` 无条件调用释放是安全的前提：未持有者的 token 不匹配，Lua 应无副作用；真正执行临界区前仍必须做业务状态幂等判断。

这条 API 约束把 `SETNX + EXPIRE`、裸 `DEL`、GET+DEL、忘记 finally 等错误从代码入口处挡住，正好把 Level 2 的命令原子性、Level 6 的复制窗口和卡 6 的资源侧终裁串成一条生产链。

### 卡 7：Lua / EVALSHA / FUNCTION 上线评审

**场景与判断**："多条命令组成的最小原子动作"，逻辑稳定、循环上界可书面声明 → 脚本化；脚本需要复用、走查、版本化治理 → **FUNCTION（7.0+ 🧬）**；存量老版本或一次性逻辑 → EVALSHA + NOSCRIPT 自动回退。

| 机制（出处） | 决策 |
|---|---|
| 事件循环互斥（L2） | 脚本 = 循环内的长事务：最坏路径耗时先压测，再谈上线 |
| `busy-reply-threshold` 🔒 默认 5000ms（7.0 起正名，`lua-time-limit` 为别名——两版本 config.c 核实） | 它**不是超时熔断**：到点只是开始回 BUSY、并开始接受 SCRIPT KILL——脚本继续跑 |
| SCRIPT KILL 边界（官方命令页） | 未执行过写才可杀；已执行写 → 拒绝（UNKILLABLE），唯一手段 `SHUTDOWN NOSAVE`——牺牲实例 |
| EVALSHA 缓存易失（官方 functions-intro 原话） | 脚本缓存可在 SCRIPT FLUSH / 重启 / **failover 切换**后消失 → 回退链必须预埋 |
| Functions 一等公民（官方 functions-intro 原话） | 库随 AOF 持久化、复制到从库，"as durable as the data itself"；库级不可变、整体 LOAD REPLACE |

**落地配置 / 代码**：

```text
redis.conf / CONFIG SET：
  busy-reply-threshold 5000     # 🔒 默认 5000(ms)；7.0 起正名（旧名 lua-time-limit 仍可用，是别名）

首选：注册函数（7.0+）
  #!lua name=inventory                       ← 库名即治理单元（版本/回滚/稽核的颗粒）
  redis.register_function('deduct', function(keys, args)
    local cur = tonumber(redis.call('GET', keys[1]) or '-1')
    if cur < tonumber(args[1]) then return 0 end
    return redis.call('DECRBY', keys[1], args[1])
  end)
  发布：FUNCTION LOAD REPLACE "#!lua name=inventory …"（整体替换，不留半新半旧）
  调用：FCALL deduct 1 sku:1001
  只读且容忍复制延迟 → FCALL_RO 走从库 🔒（官页 Available since 7.0.0 已核）

兼容：EVALSHA 兜底（老版本/一次性逻辑）
  sha = SCRIPT LOAD body；EVALSHA sha …
  捕获 NOSCRIPT → 自动回退 EVAL 全量发一次 → 重新 SCRIPT LOAD 续缓存
```

**脚本体检清单（CI 门禁必过，缺一即打回）**：
- 循环上界写死头部注释（`-- MAX_LOOP=100`），压测按上界造数（演练 ①）；
- 禁非确定性调用：TIME / RANDOMKEY / 依赖外部时钟——脚本在副本按原样重放 🔒，副作用须自行论证确定性；
- KEYS/ARGV 显式入参；禁脚本内扫 keyspace；集群下入参必须同槽（[坑「跨槽」](#pit-cross-slot)）；
- 禁长 JSON 解析、大字符串拼装等重 CPU 活——脚本内 CPU 就是全店延迟（L2 公理）；
- 变更只允许 `FUNCTION LOAD REPLACE` 走 CI 发布；控制台手改 = 流程事故（演练 ③）。

**故障演练三板斧（每季度按序执行，留档才可进下一项）**：

```text
① 最坏路径压测：
   造数把循环灌到声明上界 → redis-benchmark/自研压测直打 → 记录墙钟 P99
   判据：P99 显著低于 busy-reply-threshold 🔒（教学建议低一个数量级，
   具体阈值自定后签字）。反向操作【先调大阈值再放行】明令禁止——
   那是把保险丝换成铜丝。

② "写后卡死"演练（隔离实例！）：
   构造脚本：先 SET 一笔，再进入刻意死循环
   a) SCRIPT KILL → 预期收到 UNKILLABLE 类报错（已执行写不可杀）
      ——团队必须亲眼看到，不许背答案
   b) SHUTDOWN NOSAVE 收尾，记录"实例牺牲→拉起→数据核对"全程墙钟
   通过标准：oncall 不看文档走完 a→b 全流程 < 5 分钟（教学 SLO，自定）

③ 流程演练：
   抽查一次"绕过仓库、手改库直接 LOAD 上生产"——CI 门禁必须拦下并留痕。
   拦截失败即流程事故，等级等同未走查变更上线。
```

**不能做的错误决策**：
① 把 `lua-time-limit` / `busy-reply-threshold` 当超时保险丝（它一个脚本也不杀）；
② 循环次数随数据量膨胀且无上限声明（O(N) 撞 Level 2 公理：循环内慢 = 全店排队）；
③ EVALSHA 不做 NOSCRIPT 回退（failover 后缓存蒸发，接口批量报错——官方明说缓存可随时丢失）；
④ 为图"原子"把多步业务逻辑全塞进脚本（原子范围按最小必要裁剪；能用单命令就不用脚本）；
⑤ 把脚本当配置管理：绕过 review 手改上线（这是治理漏洞不是技术漏洞，恰是事故高发点）。

**生产实践惯例（行业通行做法，非单一厂商口径，无内部数据）**：
- 库与业务同仓：library 文件挂版本号，生产 `FUNCTION LOAD` 只能由 CI 执行；`FUNCTION LIST` 与仓库清单定期 diff 稽核；
- 影子实例预演：新库先 FCALL 冒烟影子实例再上生产灰度；回滚 = `LOAD REPLACE` 旧库（库级不可变天然支持整体回退）；
- 度量常态化：`INFO commandstats` 的 `cmdstat_fcall*` / `cmdstat_evalsha`（calls、usec、usec_per_call）入看板；`blocked_clients` 尖峰、`LATENCY EVENTS`（事件名以你版本输出为准 🔒）入告警。

**验收指标**：`cmdstat_fcall*/cmdstat_evalsha` 的 `usec_per_call` 无趋势性恶化；P99 经客户端埋点入 SLO；`blocked_clients` 非零即告警可追因；季度稽核：生产 `FUNCTION LIST` 与应用仓库 diff = 0；演练 ② 的墙钟与数据核对结果入复盘档案。

### 卡 8：Cluster 生产配置与上线评审

**C 的一生（本卡段）——N 个 redis.conf 写得互相认识之前，C 会撞上什么**（协议层的 C 在 L7/L8 讲完：分槽、MOVED/ASK、gossip 多数票换主；本卡是运维层的同一件事——配置没配对时，同一个 C 的另一种命运）：

```text
 t0  C = SET sku:1001:stock 42；客户端查本地路由表（L7）→ 槽 s 归 node X
 t1  C 发到 X 的 6379；X 自查：槽归我？
     ——若 cluster-enabled 没开（🔒 默认 no）：槽的概念根本不存在，
        C 按单机落库——集群里每个节点都以为自己是独苗
 t2  C 落库，X 要把这次变更捎给全街（propagate 给副本 + gossip 带配置）；
     防火墙只放行 6379、漏了 16379（总线 = 数据端口 + 10000 🔒）→
     邻居收不到 X 的任何消息，X 也听不见邻居
 t3  邻居叫 X 叫不应 → 各自小本本记 PFAIL（L8）；多数附议永远凑不齐，
     FAIL 确诊长不出来：X 活着像死着，真死了也无人宣判
 t4  X 真死：槽无主 → require-full-coverage yes（🔒 默认）→ 全集群拒写；
     改 no？→ C 的写从"明确拒绝"变成"沉默丢写"——比拒绝更难发现
 —— 另一幕：故障已平、拓扑已换 ——
 t5  客户端旧路由仍指 X → -MOVED 指路 → 按 announce 三件套没配的地址
     重发 → 指进黑洞，重试风暴
 t6  手痒调小 cluster-node-timeout（坑「node-timeout」）：t3 的误诊门槛
     变低，一次网络抖动就换主 → 客户端被 MOVED 风暴拖着跑

 ★ 本卡每个参数，都是上面某一幕里 C 的命运开关：
    先看懂 C 死在哪一幕，再谈配什么值——清单见下。
```

**场景与判断**：卡 5 已拍板"要上 Cluster"之后才轮到本卡——落成什么样的集群：每个参数什么证据、防火墙怎么开、默认值哪些按住不许动。一句话：**单机是把一个 redis.conf 写对，集群是把 N 个 redis.conf 写得互相认识**。

| 机制（出处） | 决策 |
|---|---|
| 双泳道端口（L8：总线 = 数据端口 + 10000 🔒） | 防火墙/安全组 **6379 与 16379 双向成对放行**；只开 6379 → gossip 断路，节点互记 PFAIL 到死 |
| 两阶段确诊 × 15s 🔒（L8，[坑「node-timeout」](#pit-node-timeout)） | `cluster-node-timeout` 内网保持默认 15000；**客户端超时必须显著小于它**（教学建议 ≤ 1/5，自定后签）——否则故障期客户端先黑屏 |
| nodes.conf = 身份证+投票记忆（L8：lastVoteEpoch/configEpoch 落盘 🔒） | 官方 redis.conf 原话 "not intended to be edited by hand"：**永不手改；镜像/备份绝不可带它铺新节点** |
| 数据新鲜度窗口 = validity-factor × node-timeout 🔒 | 数据太旧的副本会**主动放弃** failover 资格；手痒调小 timeout 会连带缩窄这扇窗 |
| require-full-coverage 🔒 默认 yes | 名字反直觉：yes = 任一槽失去覆盖 → 整集群逐步拒写；改 no 换"残阵服务"只限纯缓存业务且评审签字 |
| allow-reads-when-down 🔒 默认 no | down 态默认连**读**都拒——别等故障演练才发现"读怎么也挂了" |
| announce 三件套（官方 redis.conf "CLUSTER DOCKER/NAT support" 节原话：地址被 NAT 或端口转发时自动探测失灵） | 容器/云主机/跨网段必配；不配则 gossip 公告的是别人够不着的内网地址，MOVED 把客户端指进黑洞 |

**落地配置**（7.2.x/8.0 通用；🔒 默认值逐行取证官方 redis.conf 7.2 分支）：

```text
# ── 开关与身份 ─────────────────────────────
cluster-enabled yes                   # 🔒 默认 no——最常见的"以为开了"事故
cluster-config-file nodes-6379.conf   # 节点自动生成/维护，永不手改；同机多实例文件名必须错开
# ── 时序（内网别手痒，见坑「node-timeout」）───────────────
cluster-node-timeout 15000            # 🔒 默认 15000ms
cluster-port 0                        # 🔒 默认 0 = 数据端口 + 10000（6379 → 16379）
# ── 副本行为 🔒 ─────────────────────────────
cluster-replica-validity-factor 10    # 数据太旧的副本放弃 failover（默认 10）
cluster-migration-barrier 1           # 副本保留线，防止被匀去别的 master（默认 1）
cluster-allow-replica-migration yes   # 孤儿 master 自动补副本（默认 yes）
# ── 降级行为（名字都反直觉，逐字读）───────────
cluster-require-full-coverage yes     # 🔒 默认 yes；改 no = 允许残阵服务，先读上表再签字
cluster-allow-reads-when-down no      # 🔒 默认 no
# cluster-preferred-endpoint-type ip   # 🔒 默认 ip（7.2 redis.conf 在案）；客户端靠 DNS/证书 SNI 才考虑 hostname
# ── 容器 / NAT / 云主机必配 ─────────────────
cluster-announce-ip       <对外可达地址>
cluster-announce-port     <对外数据端口>
cluster-announce-bus-port <对外总线端口>
# ── 每台自己的单机功课（Cluster 不替你做）─────
maxmemory <物理内存 × 70–80% 教学线，再预扣 COW/缓冲余量>
maxmemory-policy <按卡 2 评审；全集群口径必须一致>
appendonly yes / appendfsync everysec  # 主侧；RDB/AOF 组合按卡 3 评审
repl-backlog-size <按槽内写速率 × 可忍断链时长>   # 🔒 默认 1mb（卡 9 跨城要重算）

# 建库（任一节节点火；官方注释口径：推荐至少三个 shard）：
redis-cli --cluster create h1:6379 h2:6379 h3:6379 h4:6379 h5:6379 h6:6379 --cluster-replicas 1
redis-cli --cluster check h1:6379
# 停线标准：16384 槽全覆盖；同组主从不落在同一台物理机
```

**不能做的错误决策**：
① 只放行 6379 忘开 16379（双泳道不通：集群永远拼不起来，互相 PFAIL）；
② 手改 nodes.conf、或用带着旧 nodes.conf 的镜像批量铺节点（身份证与投票记忆全重复，gossip 被污染）；
③ 容器/跨网段裸用自动探测、不配 announce 三件套（地址学歪，路由表集体指黑洞）；
④ 不读语义先改 `cluster-require-full-coverage no`（把"槽无主即全停"降级成"部分 key 沉默丢写"）；
⑤ 把 node-timeout 拍到 1–2s（[坑「node-timeout」](#pit-node-timeout)：一次误判 failover 的链式代价 ≫ 晚判几秒）；
⑥ 三主挤两台物理机、主从同机架（"分布式了个寂寞"；官方注释口径：推荐至少三个 shard）；
⑦ 各节点 maxmemory/policy 不一致（同一个集群两种命运：一边 evict 一边 OOM）。

**生产实践惯例（行业通行做法，非单一厂商口径，无内部数据）**：
- 3 主 3 从是入场券，主从错机架/AZ，副本数全集群拉齐，不留裸奔 master；
- 建库第一件事 `CONFIG REWRITE` 防配置漂移；nodes.conf 不纳入数据备份（备份的是数据，不是拓扑身份）；
- 客户端三件套统一评审：超时预算、重试预算、拓扑刷新策略——MOVED 风暴 = 刷新过猛，是客户端病不是集群病。

**验收指标**：`INFO cluster` 常态入看板——`cluster_state:ok`、`cluster_slots_assigned=16384`、`cluster_slots_ok=16384`；`cluster_known_nodes` 与申报拓扑 diff=0；上线 `--cluster check` 输出归档；failover 演练单主断电恢复写 p95 墙钟（教学 SLO，自定后签）；MOVED/ASK 重定向频次建基线，偏离即告警。

### 卡 9：跨机房容灾——OSS 的现实方案是"异步跨机房从库+人工/半自动切换"

**C 的一生（本卡段）——切换那一刻，C 去哪了**（承接 Level 6 埋的"竞态窗口"钩子）：
```text
 t0  客户端执行 C = SET sku:1001:stock 42；主库 +OK 已回客户端（L6 t7）
 t1  C 异步流向异地从库——可能已到（offset 差 = 0），也可能没到（差 > 0）
 t2  主机房全灭，人工/半自动切到灾备侧：t1 没到的那批 C = 本次 RPO 实测值
 t3  旧入口没 fencing：旧区复活后继续收 C' → 双主分叉，同一把锁两个主人

 本卡全部配置与五步 runbook，都在回答这三行里 C 的三种命运：
 丢在 t2、分叉在 t3——以及怎么把两者压进预算。
```

**场景与判断**：动笔配置之前，先把一条线画死——**"多机房同时可写、冲突自动解"的 Active-Active（CRDT/CRDB）是 Redis Enterprise / Redis Cloud 的专属能力，开源版（本文双基线 7.2.x/8.0）没有**。官方 Active-Active 页写明：该能力"based on CRDT technology"、实现于 Redis Software（旧称 CRDB），需 Enterprise 或 Cloud 订阅；官方对照口径的两句原话（审阅者取证，本文复核 redis.io 官方页面结论一致）："**Out of the box, open-source Redis cannot accept writes in multiple regions at once.**"想在 OSS 里自己拼双写？同一口径的第二句：implement custom replication or application-level conflict handling —— "**but it's complex and often brittle**"。

所以本卡之后写下的**每一条配置，语义上限都是"单写入口+异地热备"，不是双活**。凡是评审材料里出现"Redis 跨机房双活/多活"字样的，先回到本段第一句（[坑「跨机房双活」](#pit-dr-dualwrite)就是这个词的事故形态）。分流：

- **读就近+灾备**（RPO 接受秒级~分钟级实测窗口）→ OSS 异步跨机房从库+人工/半自动切换（**本卡正餐**）；
- **同城多机房**（内网 RTT 级）→ 单 Cluster / Sentinel 跨 AZ、自动 failover——那叫高可用，不叫跨城容灾；
- **真要双写双活** → 三条都明码标价的路：Enterprise CRDB（付钱买 CRDT）；**单元化**（写流量按租户/用户锚定单一机房，把冲突域消灭在路由层，OSS 下的行业现实出路）；应用层自研冲突处理（官方口径：complex and often brittle，本基线不背书）。

| 机制（出处） | 决策 |
|---|---|
| 数据面异步（L6） | 跨城 = 把 Level 6 的丢失窗口按 WAN 放大：**RPO 按切换时点 offset 差实测，永远不许写 0** |
| 控制面投票（L6/L8） | 跨机房故障**不交给全自动**："真全灭"与"只断网"分不清时，自动切换 = 自动双主；动作进 runbook，人签字 |
| PSYNC backlog 🔒 默认 1mb（L6） | 跨城按 **峰值写速率 × 可忍断链时长** 重算；1mb 同城够用，跨城断链窗口内早被刷穿 → 归来必全量 |
| 副本输出缓冲 🔒 默认 256mb/64mb/60s（redis.conf 7.2 L2066 生效行） | 跨城慢从顶到硬限 → 断连 → 全量重同步风暴；相关内存指标先立看板再上线 |
| cluster-replica-no-failover 🔒 默认 no | 官方 redis.conf 注释原话："especially in the case of multiple data center operations, where we want one side to never be promoted"——单 Cluster 横跨 DC 时，指定一侧副本**永不自动升主**，官方预留的手动阀 |
| WAIT / min-replicas（L6） | 别拿 WAIT 等异地副本：写延迟直接挂 WAN RTT（教学量级：同国跨城往返通常数十 ms 级，以实测为准），Level 1 的墙白翻；min-replicas-* 同理，别把异地从算进写门槛（lag 天然大，要么误伤写、要么给你假安心） |
| replica-read-only 🔒 默认 yes（redis.conf 7.2 L583 生效行） | 异地从的禁写第一道闸——别为"临时调试"在灾备侧关掉 |

**落地配置**：

```text
# 灾备机房实例（整套实例独立部署，只做从库）
replicaof <主机房主库地址> 6379
replica-read-only yes             # 🔒 默认 yes：异地禁写第一道闸
masterauth <复制专用账号>          # 最小权限；复制账号与客户端账号分离，灾备侧 ACL 禁写
# 跨机房 = 出信任边界：TLS（6.0+ 支持复制链路加密 🔒）或专线/stunnel，二选一，没有第三选

# 主机房侧
repl-backlog-size <峰值写速率 × 可忍断链时长，实测校准>   # 🔒 默认 1mb，同城够用跨城不够
# 盯死副本输出缓冲 🔒 默认 256mb/64mb/60s：顶到硬限 = 断连 = 跨城全量重同步
```

**切换 runbook（人工/半自动，五步，顺序即因果）**：

```text
① 判死：主机房是"真全灭"还是"与灾备之间断了网"？
    ——分不清时一律按分区处理：不切。切错的罪名是双主分叉
② 升主：灾备侧 REPLICAOF NO ONE（Cluster 架构走 CLUSTER FAILOVER 人工链路）
③ 对账：切换时点 offset 差 = 本次 RPO 实测值 → 入档，触发补数程序
④ 写入口迁移：DNS/VIP/配置中心一刀切；旧入口同刻 fencing
    （旧主实例级只读 / 网络隔离 / ACL 断写——三重保险至少两重）
⑤ 旧区复活：先降从追平 → 数据核对通过 → 才谈回切；
    任何时刻仍流向旧入口的写 = 双写窗口 = 事故定级
```

**不能做的错误决策**：
① 把"配了跨机房异步从库"写成"双活/多活"（本卡第一条线；[坑「跨机房双活」](#pit-dr-dualwrite)）；
② 应用侧两机房双写"先顶着"（无冲突语义必然分叉；官方口径：complex and often brittle）；
③ 单 Cluster 硬拉数千公里（node-timeout 🔒 15s 与多数派数学都按内网假设设计，跨城抖动先把集群自己 fail 死；同城多 AZ ≠ 跨城）；
④ 哨兵摆"主用机房 2+灾备机房 1"（主机房整灭时，灾备那 1 个凑不够 quorum 判不了死；quorum 必须摆在"死后要作主"的那一侧）；
⑤ 切换剧本没有 fencing（旧主复活/分区恢复后被旧客户端继续写 → 分叉）；
⑥ RPO 拍 0 或拍"1 秒内"（必须实测 offset 差入档）。

**生产实践惯例（行业通行做法，非单一厂商口径，无内部数据）**：
- 同城双 AZ 走自动 failover（Sentinel/Cluster），跨城只做数据热备+剧本切换；
- 灾备侧常挂"真只读流量"（报表/导出先跑在异地从库上）：切换那一刻它不是一台冷机器，backlog 与缓冲的水位也早被实战校准；
- 单元化是"OSS 想要双写"的行业标配口径：写按用户锚定单机房，跨机房只流只读副本与异步账务——冲突消灭在路由层，而不是数据库层。

**验收指标**：常态 `master_link_status`、`master_last_io_seconds_ago`、主从 offset 差（字节数与折算秒数）入看板告警；季度跨机房演练：**RTO 墙钟+RPO（offset 差）实测入档**，且演练必须实证"旧入口写不进"（fencing 有效性，不是文档声明）；回切后全量重同步时长+数据核对 diff 入档，diff ≠ 0 逐条签收；复制账号权限审计例外 = 0。

### 卡 10：客户端缓存（RESP3 tracking）上线评审

**C 的一生（本卡段）——C 落库之后，谁还在用旧值**：
```text
 t0  某客户端 GET sku:1001:stock → 服务端记入 Invalidation Table（"可能缓存"）
 t1  你执行 C = SET sku:1001:stock 42 → 服务端向"可能缓存"的客户端推 INVALIDATE
 t2  收到失效的客户端逐出本地副本，下次 GET 回源取新值
 ★ C 的每次落库都是一颗"失效广播"的种子：
    逐 key 模式只播给读过的连接（广播面 = 读过的连接数）
    BCAST 模式播给订阅前缀的全体（广播面 = 前缀覆盖的写面）
 本卡评审的"广播面"，就是 C 的写成本放大成的失效流量。
```

**场景与判断**：同一批热点 key 被大量进程重复读、网络往返是主要成本（读多写少、热点集中、能容忍推送链路抖动时的短暂陈旧）→ 考虑。评审先答三问：① 失效推送断了一秒，本地缓存能容忍多旧的脏数据？（官方语义：任一连接断开 → 客户端必须**清空全部本地缓存**，之后重新积累——做不到这条的客户端实现直接出局）② 写流量多大？失效消息跟着每次**修改/过期/淘汰**产生（官方 reference 原话），写多读少的 key 上缓存 = 把写放大成全网推送；③ 客户端库是否原生支持（官方文档列明 redis-py 5.1+ / Jedis 5.2+ / node-redis 5.1+，其余以所用客户端为准 🔒）。这是 6.0 引入的 🧬 协议能力（RESP3 tracking，版本与证据边界表已有登记），本文基线 7.2/8.x 可放心评审。

| 机制（出处） | 决策 |
|---|---|
| 只推"失效"，不推新值（官方 reference） | 收到 INVALIDATE → 逐出本地副本，下次读回源重取；它替代的是"本地 TTL 轮询/手动失效"，不是缓存本身 |
| 默认逐 key 模式（官方 reference） | 服务端全局 Invalidation Table 记"哪个连接可能缓存了哪些 key"，key 变化只推给相关连接：精确、无广播风暴；代价 = 服务端内存随 **key 数 × 客户端数** 涨（官方原话 proportional to both） |
| BCAST 模式（官方 reference） | 按 PREFIX 订阅广播：服务端零逐 key 账本，但前缀下**任意** key 的修改/过期/淘汰推给**所有**订阅者；不写 PREFIX = 空前缀 = 全库广播；前缀不得互相重叠 🔒；服务端 CPU 随前缀数量线性涨（官方原话） |
| tracking-table-max-keys 🔒 默认 1000000（官方 redis.conf 7.2 在案） | 逐 key 模式表满后：服务端**假装 key 被改**、向客户端发假失效来腾位 → 本地缓存被集体清空 = 回源尖峰；百万级 key × 千级客户端规模按这个数规划 |
| 失效触发面（官方 reference 原话） | key 被**修改、因 TTL 过期、因 maxmemory 淘汰**都触发失效——计数器这类连续变动的 key 是天然反面教材（官方原话：don't cache keys that change continuously） |
| REDIRECT / RESP2（官方 reference） | RESP2 客户端用双连接：SUBSCRIBE `__redis__:invalidate` 🔒 官方通道；消息**只发给 REDIRECT 指定的那条连接**（不是 pub/sub 广播）🔒；FLUSHALL/FLUSHDB → null 消息 = 全清 |
| NOLOOP / OPTIN / OPTOUT（官方 reference） | NOLOOP：自己写的 key 不给自己推（写后自更新场景）；OPTIN + `CLIENT CACHING yes` 精确圈定缓存集（省服务端内存与无效失效）；OPTOUT + `CLIENT UNTRACKING` 反向圈定 |
| REDIRECT 竞态（官方 reference） | 双连接模式下失效消息可能**先于** GET 回包到达 → 官方解法：发送时先放"caching-in-progress"占位，失效先到则删占位，旧值后到不再回填；单连接 RESP3 无此竞态 |
| Cluster / 多节点（官方博客与客户端实现口径 🔒） | tracking 状态按连接存在各节点、失效消息由"执行修改/过期/淘汰的节点"产生——客户端要对实际读到的每个节点处理失效；读从库的失效同样来自写发生节点；评审时按所用客户端库的 Cluster/Sentinel 支持逐条核对 |

**落地配置 / 伪码**：

```text
# 服务端：6.0+ 默认支持，唯一要评审的配置：
tracking-table-max-keys 1000000   # 🔒 默认 100 万；超限 = 假失效风暴（见上表）

# 客户端 A（RESP3 单连接，无竞态）：
HELLO 3
CLIENT TRACKING on
GET goods:hot:1        # ← 此后该 key 被改/过期/淘汰 → 服务端推 INVALIDATE goods:hot:1

# 客户端 B（RESP2 + REDIRECT 双连接）：
#   连接①：CLIENT ID → 42；SUBSCRIBE __redis__:invalidate
#   连接②：CLIENT TRACKING on REDIRECT 42
#   收到 [invalidate, [k1,k2…]] → 逐条逐出；收到 null → 全表清空

# BCAST（广播面必须显式收窄）：
CLIENT TRACKING on BCAST PREFIX goods: PREFIX config:
#   ⚠️ 裸 BCAST 不写 PREFIX = 全库广播；前缀粒度 = 广播面上限
```

**不能做的错误决策**：
① 裸 `BCAST` 不配 PREFIX——全库任何写/过期/淘汰推给所有订阅者，写链路一变热就是全网失效风暴；
② 前缀粒度太宽（`user:*` 级）或把写多读少的 key（计数器、活跃位）圈进 BCAST 前缀；
③ 逐 key 模式在百万级 key × 千级客户端规模上不看 `tracking-table-max-keys`——表满 = 假失效风暴，回源尖峰比不用缓存还难看；
④ 把"收到失效"当强一致——推送会断、会延迟，官方语义要求断连即清空本地缓存，做不到的客户端实现是事故预定；
⑤ 双连接 REDIRECT 不做占位符防竞态（失效先到、旧值后到 → 脏值被回填）；
⑥ Cluster 只对单节点开 tracking 就当全集群生效（tracking 是每连接每节点的状态，失效消息由产生修改的节点发出——按客户端库实现逐节点核对 🔒）。

**生产实践惯例（行业通行做法，非单一厂商口径，无内部数据）**：
- 只在"requested often, change at a reasonable rate"（官方原话）的 key 集上启用；计数器类（change continuously）明确排除；
- 本地缓存永远叠加一个最大 TTL 兜底（官方 hints 原话：即使 key 没有 TTL 也要设）——防推送断链；
- 客户端库升级与"断连清缓存"行为一起验收（官方支持列表 redis-py 5.1+ / Jedis 5.2+ / node-redis 5.1+，以你所用版本为准 🔒）。

**验收指标**：`INFO stats` 的 `tracking_total_keys` / `tracking_total_items` / `tracking_total_prefixes`（官方 INFO 命令页在案）入看板，表满前趋势预警；本地命中率与回源 QPS 降幅实测入档；演练①：批量改/过期被缓存 key 集 → 观测失效消息速率 + 回源尖峰 p99 毛刺 < 自定阈值；演练②：掐断失效连接 → 客户端必须清空本地缓存（观测回源流量回升）。

## 🌍 跨语言 / 跨运行时视角——证明这道题是同构的

| 运行时/系统 | 它的"门铃" | 事件/命令执行模型 | 与本文的对应 |
|---|---|---|---|
| Redis（C） | epoll/kqueue（ae 封装） | 单线程主循环串行执行，线性化点免费 | L2 本体 |
| Lettuce（Java/Netty） | Netty NIO event loop | 连接复用 + pipeline；用户回调不许堵 loop | L2 Transfer-1 |
| go-redis（Go） | 每连接 goroutine + netpoll | 同步写法，IO 多路复用藏在 runtime | 同构 epoll，抽象更高 |
| Node.js + ioredis | libuv 单线程 loop | 对端也是单线程：两个店长打电话，谁也别让对方等 | L2 镜像 |
| memcached | 多线程 + slab（早期全局锁） | 同一道 C10K 题的另一解：线程 + 分片锁换并行 | L2 的对照组 |
| KeyDB / Dragonfly | SO_REUSEPORT / 每核 shared-nothing 切片 | 放弃"全局一条线性化序列"，用跨核协议换回多核 | 卡 5 判据里的变量 |

**换任何语言后仍然成立的六条判断力**：

1. 线性化点只在"串行执行处"免费；凡声称"无锁且强一致"，先找出它把串行点藏在了哪。
2. **IO 并行 + 状态串行**是通用最优分工（字节搬运并行，状态修改串行）。
3. 昂贵且非紧急的工作，一律"惰性 + 抽样 + 时间预算"（过期、回收、搬迁同此心法）。
4. 想要"某一瞬间的世界"，用 COW/快照冻结，别让全世界停工。
5. 持久化的最优平衡点是"**顺序追加日志 + 周期刷盘**"；凡说无日志还不丢数据的，一定在别处付了更贵的钱。
6. 分片单元必须远小于节点数，且自带搬家族谱（重定向/通知）；否则扩容一定变风暴。
