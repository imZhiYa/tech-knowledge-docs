# DDD 全局地图：从业务混乱到可演进模型

> 这不是一篇 DDD 名词清单。
>
> 本文只追踪一个主线：**推荐请求 R——用户打开首页后，系统为他生成一组个性化商品推荐**。
>
> R 从一个产品需求开始，先遇到业务规则混乱，再进入 DDD 的完整地图：
>
> ```text
> 业务问题
>   -> 领域模型
>   -> 战略设计
>   -> 战术设计
>   -> 代码架构
>   -> 运行时协作
>   -> 生产验证
> ```
>
> 本文只负责建立全局认知。统一语言、限界上下文、聚合和 Outbox 的细节，分别在后续文章中展开。

```text
用户提交推荐申请 R
        |
        v
+-------------------+
| 画像窗口          | 用户允许使用什么特征
+-------------------+
        |
        v
+-------------------+
| 商品窗口          | 哪些商品可以被推荐
+-------------------+
        |
        v
+-------------------+
| 策略窗口          | 哪个策略版本已经生效
+-------------------+
        |
        v
+-------------------+
| 决策窗口          | 召回、排序、过滤、兜底
+-------------------+
        |
        v
+-------------------+
| 反馈窗口          | 曝光、点击、转化事实
+-------------------+
```

## Mapping Table

| 比喻元素 | 技术概念 | 唯一职责 |
| --- | --- | --- |
| 所有窗口覆盖的业务 | Domain | 需要解决的完整问题空间 |
| 某一类专业窗口 | Subdomain | 一项相对完整的业务能力 |
| 窗口的有效范围 | Bounded Context | 一套模型和语言真正成立的边界 |
| 窗口内部的说法 | Ubiquitous Language | 业务和代码对词义达成一致 |
| 窗口内的业务档案 | Domain Model | 表达状态、行为和业务规则 |
| 档案的负责人 | Aggregate Root | 控制一组必须保持一致的状态 |
| 窗口间的交接信息 | Context Mapping | 规定上下文如何协作和翻译 |
| 办结通知 | Domain Event | 表达已经发生的业务事实 |
| 后台档案柜 | Repository | 为模型提供保存和加载能力 |

比喻只用于建立全局直觉，不替代 DDD 术语，也不把窗口直接等同于微服务。

# 正文：六个 Level 建立 DDD 全局地图

<a id="level-1"></a>

## Level 1：为什么业务复杂度会失控

一句话认知墙：**推荐系统代码变多，不一定是业务复杂；真正危险的是规则变多后没有明确负责人。**

### 前置知识关卡

- [ ] 知道 Controller、Service、DAO 是技术组织方式
- [ ] 知道推荐系统包含用户、商品、策略、模型和反馈
- [ ] 能区分“调用步骤”和“业务判断”

### Why：旧方案为什么会死

**徒弟：**

> 千人千面不就是查用户、查商品、调模型吗？我们先写一个 `RecommendationService`，业务复杂了再重构。

**老陈：**

> 这个方案确实能完成第一版功能。但它把几种不同的责任压到了一起：
>
> ```text
> 用户是否允许个性化
> 商品是否处于可推荐状态
> 哪个推荐策略当前生效
> 模型如何排序
> 结果是否需要过滤和兜底
> 曝光如何记录
> ```
>
> 这些规则一开始都能写成几行 `if`。问题是，半年后每个 `if` 都有不同的业务负责人，代码却只有一个 Service 负责人。

旧方案通常经历这样的变化：

```text
一个接口
  -> 一个 Service
  -> 一个巨大 Service
  -> 多个 Service 互相调用
  -> 共享 User/Item/Strategy 模型
  -> 谁都能改状态，没人说得清规则归属
```

| 方案 | 它解决什么 | 它留下什么问题 |
| --- | --- | --- |
| Controller + Service + DAO | 快速交付接口 | 业务规则和技术编排混在一起 |
| 全局 User/Item 模型 | 减少重复定义 | 不同业务含义互相污染 |
| 拆成多个微服务 | 物理隔离和独立发布 | 边界不清时变成分布式大泥球 |
| 规则全部配置化 | 运营修改更快 | 规则语义隐藏，版本和排障困难 |

### What：技术复杂和业务复杂不是一回事

```text
技术复杂度：网络、线程、缓存、数据库、模型服务、消息传输

业务复杂度：
  谁可以推荐？
  什么商品可以推荐？
  哪个策略生效？
  哪些结果必须过滤？
  失败时应该返回什么？
```

DDD 首先处理第二类问题。它不替代 Redis、MQ、向量数据库或模型服务，而是明确这些技术能力应该服务于哪条业务规则。

最值得先建模的不是“所有对象”，而是变化频繁且需要业务判断的地方：

```text
策略发布
实验分流
合规过滤
候选资格
推荐兜底
曝光归因
```

### How：先从业务判断入手

```text
① 找出一次请求中的业务动作
② 找出动作之前必须满足的条件
③ 找出动作完成后产生的业务事实
④ 给每个判断标记规则拥有者
⑤ 再决定哪些地方需要模型和代码保护
```

**徒弟：**

> 所以 DDD 就是把 Service 里的代码搬到 Entity 里吗？

**老陈：**

> 不是。那只是把代码换了位置。DDD 真正想解决的是：这条规则应该由谁负责，变化时应该影响哪里，哪些状态不能被随便修改。

### Transfer：这类问题还能在哪里出现

1. 支付系统的“支付成功”和“账单生成”不是同一个动作。
2. 审批系统的“提交申请”和“审批通过”不是同一个状态。
3. 物流系统的“库存存在”和“库存可以被某个订单预占”不是同一个判断。

本层留下的新账：**既然 DDD 不是搬代码，那它到底用什么东西表达业务？**下一层进入“领域模型”。

### Level Ending

```text
口诀：业务复杂不怕，怕的是规则无人负责。
```

## Level 2：DDD 的核心是领域模型

一句话认知墙：**领域模型不是数据库表，也不是类的集合，而是团队对业务如何运转的一套可执行理解。**

### 前置知识关卡

- [ ] 能说出业务复杂度和技术复杂度的区别
- [ ] 知道一个业务词可能在不同场景有不同含义
- [ ] 理解模型必须服务于业务判断

### Why：为什么不能只看数据库

**徒弟：**

> 数据库里已经有 `user`、`item`、`strategy` 表了，把表映射成 Java 类，不就是领域模型吗？

**老陈：**

> 表映射解决的是“数据怎么存”。领域模型还要回答“业务为什么允许这样改”。
>
> 例如，策略表里有一行 `PUBLISHED`，这只是一个值。真正的业务问题是：
>
> ```text
> 谁能发布策略？
> 发布前要检查什么？
> 已发布策略能否直接覆盖？
> 同一场景能否同时有两个生效版本？
> ```
>
> 如果这些规则仍然散落在 Controller、SQL 和运营脚本里，表虽然存在，模型并没有形成。

### What：领域模型包含什么

领域模型可以先用四句话理解：

```text
它描述什么业务对象或业务事实？
它处于什么状态？
它允许发生什么变化？
它禁止发生什么变化？
```

DDD 的概念地图可以先看成两层：

```text
战略设计：先决定模型在哪里有效
  ├── Domain：整个业务问题
  ├── Subdomain：业务能力
  ├── Bounded Context：模型边界
  ├── Ubiquitous Language：边界内的共同语言
  └── Context Map：边界之间的协作关系

战术设计：再决定边界内部如何写模型
  ├── Entity：有身份的对象
  ├── Value Object：由属性定义的值
  ├── Aggregate：一致性边界
  ├── Domain Service：不属于单个对象的业务规则
  ├── Repository：聚合的保存和加载入口
  └── Domain Event：已经发生的业务事实
```

战略设计先回答“窗口怎么分”，战术设计再回答“窗口内部的档案怎么管”。

### How：用一个业务判断检查模型是否存在

拿“策略发布”检查：

```text
业务事实：策略处于草稿状态
业务动作：运营申请发布
业务判断：规则完整、版本有效、目标场景明确
状态变化：草稿 -> 已发布
禁止变化：未通过校验的策略直接生效
```

如果这些内容可以被产品、测试和代码用同一套话描述，模型就开始形成；如果只能说“某个字段改成某个值”，那仍然只是数据操作。

**徒弟：**

> 领域模型是不是越完整越好？把用户、商品、策略、实验都放进去，理解起来不是更完整吗？

**老陈：**

> 这叫把所有资料放在一个档案里，不叫模型完整。模型的价值是保护一组相关规则。把不相关的对象装在一起，会让任何修改都变成全局修改。

### Transfer：领域模型的判断方式

1. 看到一个表，先问它保护什么业务规则，不要先生成 Entity。
2. 看到一个 Service，先问它协调流程还是拥有规则。
3. 看到一个事件，先问它表达什么已发生的事实。
4. 看到一个接口，先问它是业务用例还是技术适配入口。

本层留下的新账：**模型有了，但模型在哪些范围内有效？**如果商品、策略和用户画像都能修改同一个模型，模型仍然会重新膨胀。下一层建立 DDD 的战略和战术全局地图。

### Level Ending

```text
口诀：模型不是表的影子，是规则的载体。
```

## Level 3：战略设计和战术设计的全局地图

一句话认知墙：**战略设计负责划边界，战术设计负责保护边界内的规则。**

### 前置知识关卡

- [ ] 能解释领域模型和数据库表的区别
- [ ] 能说出战略设计和战术设计分别回答什么问题
- [ ] 知道 DDD 不强制微服务

### Why：为什么必须先战略后战术

**徒弟：**

> 我先把 `Order`、`User`、`Product`、`Strategy` 这些类写出来，边写边看它们怎么协作，应该也能做出模型吧？

**老陈：**

> 可以写出一套类，但你还没有决定这些类的语义边界。类一旦被多个模块共享，后面每个模块都会把自己的规则加进去。先做战略设计，是为了回答“哪些规则不应该共用”。

### What：一张 DDD 全局图

```text
业务问题空间
        |
        v
+-------------------------------+
| Strategic Design              |
|                               |
| Domain                         |
|   -> Subdomain                 |
|   -> Bounded Context           |
|   -> Ubiquitous Language       |
|   -> Context Map               |
+-------------------------------+
        |
        v
+-------------------------------+
| Tactical Design               |
|                               |
| Entity / Value Object         |
| Aggregate / Domain Service    |
| Repository / Domain Event     |
+-------------------------------+
        |
        v
+-------------------------------+
| Application Architecture      |
|                               |
| Interface -> Application      |
| Domain <- Infrastructure       |
+-------------------------------+
        |
        v
+-------------------------------+
| Runtime & Production          |
|                               |
| Transaction / Cache / MQ      |
| Timeout / Retry / Metrics     |
+-------------------------------+
```

每一层都在还上一层的账：

```text
业务很乱 -> 需要领域模型
模型含义冲突 -> 需要上下文边界
边界内部规则散落 -> 需要战术模型
模型被技术污染 -> 需要分层和依赖倒置
跨边界动作不可靠 -> 需要事件、Outbox、幂等和补偿
```

### How：用三张图开始 DDD

不要从类图开始，先画三张图：

#### 图一：业务流程图

```text
用户打开首页
  -> 获取允许使用的特征
  -> 选择策略
  -> 召回候选
  -> 排序
  -> 过滤
  -> 兜底
  -> 返回
  -> 记录曝光
```

#### 图二：责任边界图

```text
画像：允许使用什么特征
商品：商品是否可推荐
策略：哪个策略版本生效
决策：本次请求如何组合结果
反馈：发生了什么曝光和点击
```

战略设计的子域分类预览：

```text
核心子域候选：推荐策略与在线决策
支撑子域：用户画像、商品目录、实验管理、反馈分析
通用子域：身份认证、审计、基础消息能力
```

这里的分类只是千人千面示例的设计假设。反馈分析虽然不决定当前推荐顺序，但它支撑曝光、点击和转化归因，是推荐闭环的重要支撑能力；具体公司仍需用业务差异化和错误成本重新判断。

#### 图三：代码依赖图

```text
接口层 -> 应用层 -> 领域层
                    ^
                    |
             基础设施适配器
```

图一决定业务要做什么，图二决定谁负责，图三决定代码如何阻止错误依赖。

### Transfer：这张地图还能迁移到哪里

1. 交易系统可以从下单、支付、库存、履约、售后开始画图。
2. 教育系统可以从选课、教学、作业、成绩、结课开始画图。
3. 风控系统可以从申请、评分、决策、复核、处置开始画图。

本层留下的新账：**全局地图知道每个概念放在哪里，但真实业务的第一条边界还没有被画出来。**下一篇文章从一句真实需求开始，演练统一语言和限界上下文如何被发现；边界内部的状态保护再留给后续战术设计文章。

### Level Ending

```text
口诀：先定模型边界，再定对象形状。
```

<a id="level-4"></a>

## Level 4：模型如何进入代码架构

一句话认知墙：**分层不是为了好看，而是为了让稳定的业务规则不被易变的技术细节拖走。**

### 前置知识关卡

- [ ] 能画出战略设计和战术设计的关系
- [ ] 知道一个接口可能包含业务入口和技术适配两种含义
- [ ] 理解依赖方向会决定修改影响范围

### Why：技术框架为什么会污染业务模型

**徒弟：**

> 用 `@Entity`、`@Service`、`@Transactional` 直接标在领域类上不是更快吗？Spring 都替我们处理了。

**老陈：**

> 这些注解确实能降低开发成本，但它们也把领域模型和具体框架绑定起来。真正的问题不是“能不能使用注解”，而是领域规则是否只能在框架启动后才能被验证。

当领域类同时承担这些职责时，边界就开始混乱：

```text
保护业务状态
映射数据库表
接收 HTTP 参数
调用 Redis
调用模型服务
发布 MQ 消息
```

### What：四层各自保护什么

```text
接口层 Interface
  负责：HTTP/RPC/消息如何进入系统

应用层 Application
  负责：一次业务用例按什么顺序执行

领域层 Domain
  负责：业务规则、状态变化和不变量

基础设施层 Infrastructure
  负责：数据库、缓存、模型服务、MQ 等技术实现
```

依赖方向可以这样理解：

```text
HTTP Controller
      |
      v
Application Handler
      |
      v
Domain Policy / Model
      ^
      |
Infrastructure Adapter
```

基础设施可以实现领域层需要的接口，但领域层不应该反过来知道 Redis 客户端或模型 SDK 的细节。这是一种工程组织方式，不是 DDD 的唯一代码模板。

### How：从业务用例落到目录

以在线决策上下文为例：

```text
decision-context/
├── domain/
│   ├── RecommendationPolicy.java
│   ├── RecommendationContext.java
│   └── CandidateFilter.java
├── application/
│   └── GetRecommendationsHandler.java
├── adapter/in/
│   └── RecommendationController.java
└── adapter/out/
    ├── RedisFeatureProvider.java
    ├── ModelRanker.java
    └── ExposurePublisher.java
```

一次请求的责任分配：

```text
Controller：把 HTTP 请求转换为用例输入
Handler：编排读取特征、选择策略、召回、排序和过滤
Policy：判断哪些结果允许返回
RedisFeatureProvider：负责具体特征读取
ModelRanker：负责具体模型调用
ExposurePublisher：负责具体事件发布
```

**徒弟：**

> 这样代码文件比原来多很多，DDD 是不是用复杂度换复杂度？

**老陈：**

> 是的，DDD 不会免费消除复杂度。它牺牲前期建模和文件数量，换取业务规则的可追踪性和变化的局部化。简单业务不应该付这笔成本；复杂核心域才值得付。

### Transfer：分层的通用判断

1. 框架换掉时，业务规则是否还能测试？
2. 数据库换掉时，领域模型是否需要重写？
3. 模型服务超时时，降级规则是否仍由业务层控制？
4. 接口协议变化时，核心业务是否不必跟着变化？

本层留下的新账：**代码职责已经分开，但一次请求还要穿过缓存、模型服务和事件系统。**下一层把领域模型放回真实运行时，说明业务边界如何面对延迟、失败和最终一致性。

### Level Ending

```text
口诀：稳定规则向内，易变技术向外。
```

<a id="level-5"></a>

## Level 5：一次请求如何穿过运行时

一句话认知墙：**DDD 不是脱离运行时的类图，真正的设计要回答请求怎么进来、哪里等待、哪里失败、哪里异步。**

### 前置知识关卡

- [ ] 能说出四层架构各自负责什么
- [ ] 知道推荐请求会依赖缓存、特征和模型服务
- [ ] 理解同步等待和异步事实传播是两种不同语义

### Why：业务边界为什么必须连接运行时

**徒弟：**

> 领域模型只要规则正确，性能和故障交给平台团队处理就行了吧？

**老陈：**

> 不行。模型服务超时会占住请求线程，缓存失效会放大回源，事件积压会让曝光统计落后。运行时故障最终会表现成业务错误，所以领域设计必须标出哪些地方可以等待、哪些地方必须降级、哪些事实可以稍后处理。

### What：R 的完整运行路径

```text
① HTTP/RPC 进入 RecommendationController
② Application Handler 创建推荐用例上下文
③ FeatureProvider 读取允许使用的特征
④ StrategySelector 取得已发布策略和实验分组
⑤ CandidateRecallPort 召回候选
⑥ RankerPort 调用模型排序
⑦ Domain Policy 执行可推荐性、去重和多样性规则
⑧ 模型超时或候选不足时执行 Fallback
⑨ 返回 RecommendationResult
⑩ 异步发布 RecommendationExposed 事实
```

把这条链分成三类：

```text
业务规则：允许使用什么、什么结果可以返回、如何兜底
技术能力：缓存读取、候选召回、模型排序、消息发布
运行约束：超时预算、线程池、连接池、事件延迟和重试
```

### How：为每个等待点设置业务边界

```text
特征读取失败：使用安全的默认画像，还是直接拒绝？
策略读取失败：使用上一个已发布版本，还是返回兜底？
模型超时：等待多久？超过预算后返回什么？
曝光发布失败：是否影响用户响应？是否进入补偿？
```

**徒弟：**

> 曝光事件失败了，用户已经拿到推荐结果，为什么不直接忽略？

**老陈：**

> 如果曝光只用于低价值分析，可以允许延迟；如果曝光关系到实验分流、广告计费或推荐效果评估，就不能把它当普通日志。DDD 要求你先说清楚这个事实的业务价值，再决定同步、异步和补偿方式。

### Transfer：领域设计与已有基础设施知识的连接

1. 事件的投递语义可以回链到 MQ 的重复、顺序和幂等知识。
2. 应用服务的事务边界可以回链到 Spring 事务与代理知识。
3. 特征缓存的失效和回源可以回链到 Redis 的缓存治理知识。
4. 推荐结果的查询视图可以回链到 Elasticsearch 或其他读模型知识。

本层留下的新账：**知道运行时会失败，但还没有判断哪些业务真的值得使用 DDD。**下一层收束适用边界，并给出后续系列的阅读路线。

### Level Ending

```text
口诀：模型要懂规则，运行时要懂失败。
```

<a id="level-6"></a>

## Level 6：DDD 的适用边界与学习路线

一句话认知墙：**DDD 不是所有系统的默认答案，而是复杂业务的边界和规则治理方法。**

### 前置知识关卡

- [ ] 能画出 DDD 从战略到运行时的全局地图
- [ ] 能说明 DDD 和算法、缓存、MQ 的分工
- [ ] 能说出一个不适合重型 DDD 的场景

### Why：为什么不能全量使用 DDD

**徒弟：**

> 既然 DDD 能治理复杂度，那我们把用户、商品、特征、日志和报表全部建成领域模型，系统就更规范了。

**老陈：**

> 规范不是对象越多越好。离线特征 ETL 关心的是数据管道，模型训练关心的是样本和实验，报表查询关心的是读模型。把它们全部塞进领域层，只会让业务模型承担不属于它的成本。

DDD 最适合这些位置：

```text
规则复杂且经常变化
多个角色对词义理解不同
状态迁移有明确业务约束
跨团队修改容易互相影响
错误结果会产生真实业务损失
```

DDD 不必重度使用在这些位置：

```text
简单 CRUD
纯报表查询
纯模型训练
纯数据清洗
没有业务规则的缓存读路径
```

### What：一套可以落地的方法

```text
1. 选一条完整业务切片，不设计整个世界
2. 走一遍流程，记录动作、判断和事实
3. 把业务词义写清楚，并记录“它不是什么”
4. 按业务能力划分责任和限界上下文
5. 找出必须保持一致的规则
6. 只为真正需要保护的规则设计领域对象
7. 用应用服务编排一次业务用例
8. 用契约、事件、Outbox、幂等和补偿连接边界
9. 用需求变化、故障注入和指标验证设计
```

把这九步压缩成三个问题：

```text
谁拥有这条规则？
哪些事情必须一起成功或失败？
哪些事情可以晚一点完成？
```

### How：本系列的阅读路线

```text
ddd-00：全局地图
  先知道 DDD 为什么存在、各概念如何连接

ddd-01：统一语言与业务边界
  从一句推荐需求发现业务能力和上下文

ddd-02：上下文映射与协作
  解决上下文之间的契约、翻译和依赖关系

ddd-03：实体、值对象与聚合
  解决边界内部如何保护业务规则

ddd-04：一次推荐请求如何落到代码
  解决 Application、Domain、Infrastructure 如何分工

ddd-05：事件、Outbox 与最终一致性
  解决跨边界动作的可靠传播、幂等和补偿

ddd-06：生产决策与选择性 DDD
  解决何时使用、何时简化、何时拆服务
```

### Transfer：DDD 真正可迁移的思想

1. 先确定规则拥有者，再决定代码放在哪里。
2. 先确定一致性范围，再决定事务和聚合边界。
3. 先确定变化方向，再决定模块和服务边界。
4. 先确定事实和失败语义，再决定同步调用还是事件。

本篇全局地图到此闭合。下一篇不再重新解释 DDD，而是从产品的一句话需求 Q 开始，具体演练统一语言和限界上下文如何被发现。

### Level Ending

```text
口诀：DDD 不是全量套用，而是选择性保护复杂规则。
```

# ⚠️ 坑与细节

<a id="pitfalls"></a>

## 坑 1：把 DDD 当成框架

错误理解：引入某个 Java 依赖，项目就变成 DDD。

原因：把设计方法和技术工具混为一谈。

比喻后果：窗口换了新系统，但工作人员仍然不知道业务责任。

线上现象：类名很“领域化”，规则仍然散落在 Controller、SQL 和脚本中。

修正：先建立业务语言和边界，再选择代码和框架。

---

## 坑 2：把 DDD 当成面向对象编程升级版

错误理解：只要类有行为、没有 getter/setter，就是 DDD。

原因：战术模式被误认为 DDD 全部内容。

比喻后果：每个窗口都有漂亮档案，但窗口之间的责任仍然混乱。

线上现象：对象结构很复杂，需求修改范围依然无法预测。

修正：先做战略设计，再决定哪些对象需要行为和状态保护。

---

## 坑 3：把所有复杂度都交给领域层

错误理解：缓存、模型、MQ、ETL 都应该放进领域模型。

原因：没有区分业务规则和技术能力。

比喻后果：业务窗口开始维护后台设备，真正的业务判断无人负责。

线上现象：换模型、换缓存或调整消息产品都要修改核心业务代码。

修正：领域层保护业务规则，基础设施通过端口提供技术能力。

---

## 坑 4：没有核心子域也强行使用 DDD

错误理解：所有模块都必须拥有 Entity、Aggregate 和 Repository。

原因：把一致的架构模板优先于实际业务复杂度。

比喻后果：简单业务也必须经过复杂窗口，办理成本超过业务价值。

线上现象：代码量增加，业务规则没有增加，维护人员反而更多。

修正：简单查询使用读模型和简单 Service；把 DDD 资源集中到核心规则。

---

## 坑 5：把聚合当成大对象容器

错误理解：把相关业务对象全部装进一个 Aggregate，模型就完整了。

原因：没有先定义一致性边界。

比喻后果：一个窗口档案变成全城总档案，任何小修改都要锁住全部资料。

线上现象：事务变大、加载链变长、并发冲突增加。

修正：聚合只保护必须一起成立的不变量，详细规则留到 ddd-03 展开。

---

## 坑 6：把领域事件当成普通日志

错误理解：打印一条日志或发送一条消息就叫领域事件。

原因：没有区分“已经发生的业务事实”和“调试信息”。

比喻后果：窗口把内部工作记录当成正式办结通知，其他窗口无法判断是否应该行动。

线上现象：事件名称含糊，消费者重复执行或无法补偿。

修正：事件必须表达清晰的业务事实，并定义发布、重复和失败语义。

---

## 坑 7：逻辑边界和部署边界一起设计

错误理解：画了上下文就立即拆成多个服务。

原因：没有先验证责任和协作契约。

比喻后果：窗口还没有形成稳定流程，就先搬到不同办公楼。

线上现象：网络重试、部署和数据一致性问题超过业务问题本身。

修正：先模块化单体，边界经过变化和故障验证后再拆服务。

# 📚 概念勘误表

<a id="errata"></a>

| 错误说法 | 准确说法 |
| --- | --- |
| DDD 是一个 Java 框架 | DDD 是一种以业务模型和边界为中心的设计方法 |
| DDD 主要是为了代码复用 | DDD 主要是为了表达业务规则并控制变化范围 |
| 领域模型就是数据库表映射 | 数据库表描述存储，领域模型描述业务状态、行为和约束 |
| 战略设计和战术设计是两套互不相关的理论 | 战略设计先划边界，战术设计再保护边界内规则 |
| 限界上下文就是微服务 | 限界上下文是模型有效边界，可以先是模块 |
| DDD 适合所有代码 | DDD 应集中用于规则复杂且变化频繁的核心业务 |
| 领域层必须包含模型推理和缓存访问 | 领域层保护业务规则，算法和缓存通过端口接入 |
| 领域事件就是日志或 MQ 消息 | 领域事件表达已经发生的业务事实，MQ 是一种传输实现 |

其中两点我以前也讲得过于绝对：

```text
我以前容易把 DDD 和微服务绑定在一起；准确说法是先验证逻辑边界，再选择部署边界。
我以前容易把“领域模型”讲成一组有行为的类；准确说法是模型首先要表达业务规则和不变量。
```

# 🏆 生产决策卡

<a id="decisions"></a>

## Decision Card 1：是否值得引入 DDD

### 场景

业务规则持续变化，多个团队对同一概念理解不同，修改一次功能会影响多个模块。

### 判断

先做小范围业务走查。如果主要问题是语义冲突、规则散落和责任不清，采用选择性 DDD；如果只是简单 CRUD，保持简单设计。

### Mechanism -> Decision

| 机制 | 工程决策 |
| --- | --- |
| 业务词义冲突 | 建立上下文内统一语言 |
| 规则变化影响面大 | 划分业务边界 |
| 规则少、查询为主 | 使用读模型和简单 Service |

### Code

```java
public interface RecommendationPolicy {
    RecommendationResult apply(RecommendationContext context);
}
```

只有当 `RecommendationPolicy` 表达稳定的业务判断时，这个接口才有领域价值。

### 禁止决策

```text
因为项目使用 Spring，所以所有模块都必须按 DDD 目录重写。
```

### 验收指标

```text
需求变更涉及的模块数量
领域规则测试场景数
跨模块直接依赖数量
recommendation_request_latency_p99
规则相关 error rate
```

---

## Decision Card 2：DDD 应该覆盖哪一段链路

### 场景

团队准备把特征计算、模型推理、缓存、事件、报表全部塞进领域层。

### 判断

DDD 保护业务规则；算法、数据管道和高吞吐读路径使用适合自身问题的技术模型。

### Mechanism -> Decision

| 机制 | 工程决策 |
| --- | --- |
| 策略发布和业务过滤 | 领域模型 |
| 特征计算和模型训练 | 特征/算法平台 |
| 在线特征读取 | 缓存或特征存储 |
| 曝光传播 | 领域事实 + 消息传输 |
| 报表查询 | 读模型或分析系统 |

### Code

```java
public interface RankerPort {
    RankedCandidates rank(RankingInput input);
}
```

### 禁止决策

```text
让领域对象直接创建 Redis 客户端、HTTP 客户端或模型 SDK。
```

### 验收指标


## Decision Card 3：先模块化还是先拆微服务

### 场景

已经画出多个上下文，团队想立即把每个上下文独立部署。

### 判断

如果边界、契约和一致性还没有经过真实变化和故障验证，先使用模块化单体。

### Mechanism -> Decision

| 机制 | 工程决策 |
| --- | --- |
| 边界未验证 | 先用模块和依赖规则隔离 |
| 团队、发布、容量明显不同 | 再评估独立部署 |
| 跨边界一致性未设计 | 不要先引入分布式事务 |

### Code

```text
profile-context
  -> FeatureSnapshotContract
decision-context
  -> RecommendationResultContract
```

### 禁止决策

```text
上下文数量直接等于微服务数量。
```

### 验收指标

```text
模块间编译依赖数量
跨模块内部类访问次数
请求 p99 latency
跨服务 error rate
部署回滚时间
```
