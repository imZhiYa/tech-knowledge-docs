# DDD 生产决策：选择性使用、核心子域判断与系列收口

> 这不是一篇“DDD 优点总结”。
>
> 本文只追踪一个主线：**评审 F——一次真实的架构评审：推荐系统要不要全面 DDD 化，哪些模块该建模，哪些该保持简单，单体要不要拆。**
>
> 前面五篇已经把 DDD 的机制打穿。最后一篇回答的是最贵的问题：
>
> ```text
> 哪些业务值得付 DDD 的成本
>   -> 不付成本时用什么替代
>   -> 核心子域如何判断
>   -> 模块化单体何时拆微服务
>   -> 系列因果链如何收口
> ```
>
> 本文的目标不是让你把 DDD 用到所有地方，而是让你在架构评审里能说清：**这里为什么用、那里为什么不用。**

# 🏷️ 关键词与主线进度

关键词：

```text
选择性 DDD | Transaction Script | CRUD | 规则引擎 | 读模型
核心子域 | 支撑子域 | 通用子域 | 判断矩阵
模块化单体 | 微服务拆分 | 演进路径 | 系列总结 | 千人千面
```

主线进度：

```text
① 一次“全面 DDD 化”的架构评审
② 不做 DDD 时用什么替代
③ 核心子域判断矩阵
④ DDD 的渐进引入路径
⑤ 模块化单体何时拆微服务
⑥ 全系列因果链与决策卡收口
```

# ⚠️ 版本与证据边界

| 类型 | 本文承诺 |
| --- | --- |
| Specification | DDD 不规定“必须拆微服务”，也不规定“所有核心域都必须充血建模” |
| Implementation | 判断矩阵是决策工具，不是算法；权重和阈值需要结合具体公司目标 |
| Version | 无新增框架行为；回链各篇版本基线 |
| Need Benchmark | 本文没有性能数字；拆分决策依赖容量、延迟和团队实测数据 |
| Design Assumption | 千人千面推荐系统是本系列统一示例，实际判断必须回到自己的业务 |

本文最重要的纪律：

```text
DDD 是方法，不是信仰。
判断是否使用 DDD 的标准是：规则密度、变化速度、错误成本和协作复杂度。
不是“代码像不像 DDD”。
```

# 正文：六个 Level 打穿生产决策

<a id="level-1"></a>

## Level 1：不做 DDD 时用什么

一句话认知墙：**DDD 的替代方案不是“乱写”，而是各有适用场景的结构化写法。**

### 前置知识关卡

- [ ] 知道 DDD 的成本是建模、沟通和代码组织
- [ ] 能区分业务规则密度高和低
- [ ] 理解同一系统内可以混合多种写法

### Why：全面 DDD 化为什么是错误决策

**徒弟：**

> 既然 DDD 能治理复杂业务，那整个推荐系统都按 DDD 重写，规范统一，不是最省心吗？

**老陈：**

> 统一的是目录，不是业务。特征 ETL 的复杂度在数据管道，模型训练在实验和样本，报表在查询形态，后台配置可能只是几张表。给它们全部建聚合、事件和仓储，就是让简单模块承担复杂成本。

DDD 的成本清单：

```text
统一语言会议和文档
聚合边界讨论
仓储和适配器代码
架构测试维护
事件治理
团队学习曲线
```

规则很少的模块付这笔成本，换不回任何规则保护。

### What：五种替代方案

| 方案 | 适用业务 | 优点 | 代价 |
| --- | --- | --- | --- |
| 简单 CRUD | 后台配置、字典、基础资料 | 开发快、易理解 | 无规则保护，状态可被任意改 |
| Transaction Script | 流程明确、规则少 | 编排直观、适合小团队 | 规则增长后变成上帝 Service |
| 模块化 Service | 中等复杂度、无复杂不变量 | 有边界但成本低于 DDD | 边界靠约定，易漂移 |
| 规则引擎 | 规则高度配置化、运营驱动 | 运营可自助调整 | 语义隐藏、调试和版本治理难 |
| 读模型/查询服务 | 报表、搜索、在线查询 | 查询形态最优 | 不能保护写规则 |

推荐系统的现实组合：

```text
策略发布 -> 选择性 DDD（核心）
商品可售规则 -> 商品上下文领域规则
特征 ETL -> 数据管道，不用 DDD
模型训练 -> 算法平台，不用 DDD
曝光报表 -> 读模型/分析系统
后台字典 -> 简单 CRUD
```

### How：三问决定用哪种

```text
第一问：这条链路上有多少业务判断？
  几乎没有 -> CRUD / Transaction Script
  很多且变化频繁 -> 继续问

第二问：这些判断是否必须一起保持一致？
  是 -> 领域模型/聚合
  否 -> 模块化 Service 或规则引擎

第三问：规则是否需要运营频繁调整？
  是 -> 规则引擎候选
  否 -> 领域模型候选
```

**徒弟：**

> Transaction Script 不是被 DDD 淘汰的旧写法吗？

**老陈：**

> 它被淘汰的场景是“规则多到失去控制”。规则少的流程里，它仍然是最直接的选择。写法没有绝对优劣，只有和业务复杂度是否匹配。

### Transfer：替代方案的迁移

1. 电商后台的类目管理用 CRUD，交易规则用领域模型。
2. 审批流程简单时用 Transaction Script，复杂风控用领域模型或规则引擎。
3. 报表永远优先读模型，而不是复制一套聚合。

本层留下的新账：**知道哪些不用 DDD，但哪些模块是真正值得投入的核心，还没有判断标准。**下一层进入核心子域判断矩阵。

### Level Ending

```text
口诀：简单业务用简单写法，复杂规则才值得建模。
```

## Level 2：核心子域判断矩阵

一句话认知墙：**核心子域不是“技术最复杂”或“领导最重视”的模块，而是业务差异化最强、规则变化最快、错误代价最高的部分。**

### 前置知识关卡

- [ ] 能区分核心/支撑/通用子域
- [ ] 知道技术复杂度不等于业务重要性
- [ ] 理解判断依据必须来自业务而非技术热度

### Why：核心子域判断错误会损失什么

**徒弟：**

> 我们用了向量检索和大模型，算法当然就是核心子域，资源都投给模型团队。

**老陈：**

> 模型可能是技术热点，但如果竞品模型三天就能追平，而你们的策略规则、实验体系和合规过滤才是护城河，那模型就不是核心。判断错了，DDD 资源会投错地方。

### What：判断矩阵

每个候选模块按六个维度打分，分值和权重由业务目标决定：

| 维度 | 要问的问题 | 高分信号 | 低分信号 |
| --- | --- | --- | --- |
| 业务差异化 | 它能不能形成独特竞争力？ | 竞品难复制、客户愿意付费 | 行业通用能力 |
| 规则密度 | 有多少业务判断和不变量？ | 状态迁移复杂、约束多 | 基本是数据搬运 |
| 变化频率 | 需求多久变一次？ | 每周都在演进 | 半年不动 |
| 错误成本 | 出错损失多大？ | 资金、合规、用户体验损失大 | 可重算、可补偿 |
| 协作复杂度 | 多少团队共享语义？ | 多团队、多角色争论词义 | 单团队自洽 |
| 一致性要求 | 哪些状态必须一起正确？ | 强不变量多 | 全部可最终一致 |

示例（千人千面场景，分值仅示意）：

| 模块 | 差异化 | 规则密度 | 变化频率 | 错误成本 | 协作复杂度 | 一致性 | 合计 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 推荐策略 | 高 | 高 | 高 | 中 | 高 | 高 | 高 |
| 实验管理 | 中 | 高 | 高 | 高 | 中 | 中 | 高 |
| 用户画像 | 中 | 中 | 中 | 中 | 高 | 低 | 中 |
| 商品目录 | 低 | 中 | 低 | 中 | 中 | 高 | 中 |
| 身份认证 | 低 | 低 | 低 | 高 | 低 | 低 | 低 |

按结果分配 DDD 投入：

```text
高分模块 -> 领域模型、聚合、事件治理
中分模块 -> 模块化边界 + 必要规则保护
低分模块 -> CRUD、采购、第三方服务
```

落到代码上的差别一目了然：

```java
// 高分模块：策略发布走领域模型，规则由聚合保护
public final class RecommendationStrategy {
    public void publish() {
        // 校验规则、变更状态、保护不变量
    }
}
```

```java
// 低分模块：字典管理保持简单 CRUD，没有复杂状态迁移
@RestController
public class DictionaryController {
    @PostMapping("/dicts")
    DictDto create(@RequestBody DictDto dto) {
        return DictDto.from(dictRepository.save(dto.toEntity()));
    }
}
```

同一个系统里两种写法并存是正常状态，不是架构不统一。判断标准始终是规则密度和错误成本，而不是目录长得一样。

### How：使用判断矩阵

```text
① 列出候选模块
② 每个维度打分并记录一句业务依据
③ 汇总并排序
④ 与产品、运营和业务负责人核对
⑤ 把结果写进决策记录，而不是口头结论
```

**徒弟：**

> 六个维度分数怎么定？会不会各打各的？

**老陈：**

> 分数本身就是讨论工具，不是真理。关键是每个分数后面必须有一句业务事实：哪次事故、哪个需求、哪个客户反馈。没有事实支撑的分数，评审时直接删掉。

### Transfer：判断矩阵的迁移

1. 电商的核心可能是供应链和价格策略，不是商品展示。
2. 金融的核心可能是风控和合规规则，不是账户 CRUD。
3. 物流的核心可能是调度和履约承诺，不是运单记录。

本层留下的新账：**知道核心在哪，但 DDD 不能一夜重建。**如何在不停止业务的前提下渐进引入？下一层给出路径。

### Level Ending

```text
口诀：核心子域看业务护城河，不看技术热度。
```

<a id="level-3"></a>

## Level 3：DDD 的渐进引入路径

一句话认知墙：**DDD 是增量改造，不是推倒重来。**

### 前置知识关卡

- [ ] 能用手判断矩阵找出核心模块
- [ ] 知道既有系统仍然在线上服务
- [ ] 理解“大爆炸重构”的风险

### Why：全面重构为什么几乎必败

**徒弟：**

> 既然核心是策略模块，直接立项三个月把它全部重写成 DDD，一次到位。

**老陈：**

> 三个月里业务还会继续变化。等你重构完，需求已经变了三轮；而且重写期间新旧两套系统并存，最后还要冒险切换。DDD 应该从新需求和新边界切入，让旧代码自然收缩。

### What：四条渐进路径

| 路径 | 做法 | 适用 |
| --- | --- | --- |
| 新需求新写 | 新功能按领域模型实现 | 正在开发的新模块 |
| 绞杀式改造 | 新入口逐步替代旧实现 | 需要迁移的存量服务 |
| 提取核心规则 | 先提取散落的规则到领域服务 | 规则混乱但结构可救 |
| 边界先行 | 先划包和依赖，再逐块重写内部 | 模块化单体 |

推荐从“策略发布”切入：

```text
第一步：把发布规则从 Controller/SQL 提取到 RecommendationStrategy
第二步：建 StrategyRepository 和本地事务边界
第三步：接入 Outbox 和集成事件
第四步：架构测试守护领域层纯度
第五步：把改造经验复制到实验和商品规则
```

绞杀式改造的代码形态：旧入口继续服务存量调用，新入口按领域模型实现，逐步切换流量：

```java
// 旧入口：仍然在线，直接改数据库
@RestController
@RequestMapping("/legacy/strategies")
public class LegacyStrategyController {
    @PostMapping("/{id}/publish")
    void publish(@PathVariable String id) {
        strategyDao.updateStatus(id, "PUBLISHED");
    }
}
```

```java
// 新入口：按领域模型实现，规则由聚合保护
@RestController
@RequestMapping("/api/strategies")
public class StrategyController {
    @PostMapping("/{id}/publish")
    void publish(@PathVariable UUID id) {
        publishStrategyHandler.handle(
                new PublishStrategyCommand(new StrategyId(id))
        );
    }
}
```

切换纪律：

```text
新入口上线 -> 小流量验证 -> 对比新旧结果 -> 存量调用逐步迁移 -> 旧入口下线
迁移期间两条路径必须可对比，不能新老并存却无法判断谁对谁错
```

### How：每次改造都要有停止条件

```text
业务价值：这次改造解决哪个真实问题？
风险边界：改造失败如何回退？
验收标准：哪些测试和指标证明成功？
停止信号：哪些情况说明该停下来？
```

**徒弟：**

> 改造到一半发现业务又变了，怎么办？

**老陈：**

> 先停，先交付，再继续。DDD 改造不是一次性项目，而是随着需求持续进行的过程。每步只改与当前需求相关的部分。

### Transfer：渐进改造的迁移

1. 支付系统先改造退款规则，再逐步处理支付授权。
2. 老单体先拆模块边界，再逐步独立部署。
3. 规则引擎先接管新规则，再迁移存量规则。

本层留下的新账：**模块边界稳定后，部署边界要不要跟着变？**下一层判断模块化单体何时拆微服务。

### Level Ending

```text
口诀：从新需求切入，让旧代码自然老去。
```

<a id="level-4"></a>

## Level 4：模块化单体何时拆微服务

一句话认知墙：**微服务是部署形态，不是 DDD 的完成标准。**

### 前置知识关卡

- [ ] 知道限界上下文不等于微服务
- [ ] 理解拆分引入分布式事务、网络和运维成本
- [ ] 能说出模块化单体的边界验证价值

### Why：过早拆分把什么账提前了

**徒弟：**

> 上下文已经画好了，直接每个上下文一个服务，团队也能并行开发。

**老陈：**

> 拆分会把四笔账提前：
>
> ```text
> 分布式事务和最终一致性
> 网络超时、重试和故障隔离
> 独立部署和运维
> 跨服务调试和可观测性
> ```
>
> 如果边界还没有经过真实变化验证，你会同时支付“边界调整成本”和“分布式成本”。

### What：拆分判断条件

| 条件 | 问法 | 满足才加分 |
| --- | --- | --- |
| 发布节奏 | 模块是否经常独立发布？ | 发布冲突频繁 |
| 团队边界 | 是否由不同团队拥有？ | 团队和模块一一对应 |
| 容量隔离 | 是否负载特征完全不同？ | 需要独立扩缩容 |
| 故障隔离 | 故障是否必须互不影响？ | 相互依赖低 |
| 数据边界 | 是否能彻底分开数据？ | 无共享表、无共享事务 |
| 边界稳定 | 上下文是否经过验证？ | 多次需求变化边界未漂移 |

### How：拆与不拆的决策路径

```text
第一问：模块间的同步调用是否已经很少？
  否 -> 不拆，先内部解耦

第二问：是否仍有跨模块共享事务？
  是 -> 不拆，先转成事件和最终一致

第三问：数据表是否仍然互相直读？
  是 -> 不拆，先建立契约和所有权

第四问：边界是否经过至少几轮需求变化验证？
  否 -> 不拆，继续模块化单体验证

全通过 -> 按发布节奏优先拆第一个模块，验证拆分收益
```

### 不拆的信号

```text
同步调用过多
共享数据库事务
边界还在频繁变化
团队没有独立运维能力
拆分后收益无法量化
```

**徒弟：**

> 什么算“拆分收益可以量化”？

**老陈：**

> 独立发布频率提升、故障影响面缩小、扩容成本下降、团队交付速度提高。如果拆完只有“看起来更分布式”，没有指标改善，那就是为了拆而拆。
>
> 量化对比要在拆分前建好口径，拆后回填实测值：

| 指标 | 拆分前（实测） | 拆分后（实测） | 判断 |
| --- | --- | --- | --- |
| 独立发布频率 | 待采集 | 待采集 | 提升才是收益 |
| 故障影响面 | 待采集 | 待采集 | 缩小才是收益 |
| 推荐请求 p99 | 待采集 | 待采集 | 不许因为拆而变差 |
| 跨服务 error rate | 待采集 | 待采集 | 新增网络失败要低于收益 |
| 交付周期 | 待采集 | 待采集 | 缩短才是收益 |

这张表的纪律：数字必须来自拆分前后的真实观测，不允许预填拍脑袋的延迟和频率。任何“预期”数字都要标注为假设，拆完用实测推翻或确认。

### Transfer：拆分决策的迁移

1. 先拆发布节奏最痛、耦合最低的模块。
2. 拆分后回看错误率、延迟和交付周期。
3. 未验证边界永不物理拆分。

本层留下的新账：**拆分或保持之后，DDD 边界还需要持续治理。**下一层看如何防止模型漂移和边界回退。

### Level Ending

```text
口诀：先验证边界，再拆分进程。
```

<a id="level-5"></a>

## Level 5：DDD 落地后的治理与演进

一句话认知墙：**DDD 不是一次性建模，而是持续维护边界和规则的过程。**

### 前置知识关卡

- [ ] 知道架构测试如何守护依赖方向
- [ ] 理解事件治理和模型评审的作用
- [ ] 能识别边界漂移的信号

### Why：边界为什么还会漂移

**徒弟：**

> 领域模型建好了，边界也清楚了，代码写对就完事了吧？

**老陈：**

> 边界会被三件事侵蚀：新同事不理解旧边界、紧急需求走捷径、共享模型被顺手复用。没有持续治理，半年后上下文又变回大泥球。

### What：治理手段清单

| 手段 | 防什么 | 成本 |
| --- | --- | --- |
| 架构测试 | 依赖方向违规 | 测试维护 |
| 统一语言表 | 词义重新漂移 | 文档维护 |
| 模型评审 | 聚合变大、规则泄漏 | 评审时间 |
| 事件契约治理 | 字段随意演进 | 契约版本管理 |
| 边界变更记录 | 决策被遗忘 | 决策文档 |
| 指标看板 | 延迟、积压、错误率异常 | 监控建设 |

### How：漂移信号

```text
一个聚合开始被到处加载
领域层出现新的技术依赖
跨上下文直读表再次出现
同一业务词出现两种解释
一个变化要改三个以上模块
```

出现两个以上信号，就应该触发一次边界评审。

**徒弟：**

> 治理多久做一次？

**老陈：**

> 机制持续运行，评审按变化触发：新上下文接入时、聚合边界调整时、团队交接时、生产事故复盘时。周期不是目的，变化才是触发器。

### Transfer：治理的迁移

1. 支付系统按支付方式变更触发风控边界评审。
2. 交易系统按新营销玩法触发订单边界评审。
3. 所有系统按生产事故复盘检查边界是否失效。

本层留下的新账：**无。选择性 DDD 的决策闭环到此完整。**最后一层把全系列因果链和决策卡压缩成可执行框架。

### Level Ending

```text
口诀：边界不是建出来的，是护出来的。
```

# ⚠️ 坑与细节

<a id="pitfalls"></a>

## 坑 1：把 DDD 当技术先进指标

错误理解：用 DDD 的项目一定比 CRUD 项目好。

原因：把方法和业务复杂度匹配关系搞反了。

比喻后果：自助办理机也能处理的事，非要开专业窗口审核。

线上现象：简单模块代码量翻倍，交付变慢，规则没有增加。

修正：按规则密度和错误成本选择写法。

---

## 坑 2：核心子域由技术热度决定

错误理解：用了最热技术的就是核心子域。

原因：把技术复杂度和业务竞争力混为一谈。

比喻后果：按设备昂贵程度分窗口，而不是按业务价值。

线上现象：算法团队承担全部业务规则，产品和运营无法自助调整策略。

修正：用六维矩阵打分，每个分数配业务事实。

---

## 坑 3：全面重构一次到位

错误理解：立项三个月把所有模块重写成 DDD。

原因：忽略业务持续变化和新旧系统并存风险。

比喻后果：把还在营业的大厅推倒重建，客户没地方办事。

线上现象：重构期间需求追不上，切换风险集中爆发。

修正：渐进改造，从新需求切入，旧代码自然收缩。

---

## 坑 4：上下文数量等于微服务数量

错误理解：画了几个上下文就拆几个服务。

原因：把逻辑边界和部署边界混为一谈。

比喻后果：窗口责任还没稳定，就搬到不同办公楼。

线上现象：分布式事务、网络抖动和运维成本先于业务价值出现。

修正：模块化单体验证边界，再按拆分条件逐个评估。

---

## 坑 5：拆分后不再验证收益

错误理解：拆完就结束，不管指标有没有变好。

原因：把拆分当目标而不是手段。

比喻后果：搬迁完成，办事效率没变，房租贵了。

线上现象：服务多了，延迟涨了，交付没快。

修正：拆分前后对比发布频率、故障面、扩容和交付周期。

---

## 坑 6：边界建好就不再治理

错误理解：模型评审一次通过就一劳永逸。

原因：忽略新同事、紧急需求和共享复用的侵蚀。

比喻后果：新员工不知道窗口分工，开始跨窗口直接拿档案。

线上现象：半年后聚合被到处加载，上下文直读表复发。

修正：架构测试持续运行，变化触发评审，漂移信号告警。

---

## 坑 7：用“领域”命名包装旧代码

错误理解：把 Service 改名 DomainService 就是 DDD。

原因：只有名称变化，没有规则归属和边界。

比喻后果：窗口换了牌子，办理方式照旧混乱。

线上现象：目录像 DDD，规则仍在 Controller 和 SQL 里散落。

修正：先划规则拥有者，再谈目录和命名。

---

## 坑 8：决策只停留在口头

错误理解：评审会上说“这个模块用 DDD”，会后就忘。

原因：没有决策记录和验收标准。

比喻后果：换个人重新评审，结论又变一次。

线上现象：同一模块在不同季度被反复讨论要不要建模。

修正：决策写进 `decisions/ddd.md`，记录依据、代价和验收。

# 📚 概念勘误表

<a id="errata"></a>

| 错误说法 | 准确说法 |
| --- | --- |
| 不用 DDD 就是技术落后 | 写法要和规则密度匹配，简单业务用简单结构 |
| 核心子域就是最复杂的模块 | 核心子域由业务差异化和规则价值决定 |
| DDD 必须一次性全面落地 | 渐进引入，从新需求和新边界切入 |
| 上下文划分完就该拆微服务 | 部署边界需要发布、团队、容量、故障和边界条件 |
| 拆完微服务 DDD 就完成 | 治理才是长期工作，边界会持续漂移 |
| 规则引擎一定比领域模型先进 | 规则引擎适合高配置化场景，代价是语义和调试成本 |
| 充血模型永远优于贫血模型 | 读模型、查询和算法数据保持简单更合适 |
| 决策会议开完就是决策完成 | 决策需要记录、验收标准和回顾触发点 |

其中两点我以前也讲得过于绝对：

```text
我以前容易把“核心子域”讲成“技术最复杂”；准确说法是业务差异化、规则密度和错误成本决定投入。
我以前容易把“微服务”讲成 DDD 的终点；准确说法是部署形态服务于已验证的边界，不是完成标准。
```

# 🏆 生产决策卡

<a id="decisions"></a>

## Decision Card 1：这个模块用不用 DDD

### 场景

团队准备为推荐系统所有模块统一采用 DDD。

### 判断

先按规则密度、错误成本和变化频率筛选。策略、实验等核心模块用领域模型；ETL、报表、字典保持简单结构。

### Mechanism -> Decision

| 机制 | 工程决策 |
| --- | --- |
| 规则少、流程直 | CRUD / Transaction Script |
| 规则多、变化频繁 | 选择性 DDD |
| 运营高度配置化 | 规则引擎候选 |
| 只读查询 | 读模型/查询服务 |

### Code

```text
策略发布 -> RecommendationStrategy 聚合
曝光报表 -> PublishedView + 分析系统
特征 ETL -> 数据管道
```

### 禁止决策

```text
因为系统叫推荐系统，所以所有代码必须 DDD 化。
```

### 验收指标

```text
需求变更涉及模块数
领域规则测试场景数
交付周期
跨模块依赖数
Error rate
```

## Decision Card 2：核心子域判断

### 场景

团队需要决定建模资源投给哪个模块。

### 判断

用六维矩阵打分：业务差异化、规则密度、变化频率、错误成本、协作复杂度、一致性要求；每个分数配业务事实。

### Mechanism -> Decision

| 机制 | 工程决策 |
| --- | --- |
| 高分 | 领域模型 + 事件治理 |
| 中分 | 模块边界 + 必要规则 |
| 低分 | CRUD / 采购 / 第三方 |

### Code

```text
评分表 + 一句事实依据 + 决策记录
```

### 禁止决策

```text
按技术热度或领导偏好决定核心子域。
```

### 验收指标

```text
核心模块需求响应时间
规则事故数
建模资源投入占比
核心域测试覆盖
```

---

## Decision Card 3：渐进改造路径

### 场景

存量推荐系统需要引入 DDD。

### 判断

从新需求切入，先提取规则到领域对象，逐步建立仓储、事件和架构测试；每步有验收和停止条件。

### Mechanism -> Decision

| 机制 | 工程决策 |
| --- | --- |
| 新需求 | 按领域模型实现 |
| 存量改造 | 绞杀式替换 |
| 规则散落 | 先提取领域服务 |
| 边界不清 | 先模块化再重写内部 |

### Code

```text
第一步：RecommendationStrategy + publish()
第二步：StrategyRepository + 事务
第三步：Outbox + 集成事件
第四步：ArchUnit 守护
```

### 禁止决策

```text
三个月大爆炸重构，新旧系统并存硬切。
```

### 验收指标

```text
每步验收通过率
改造回滚次数
线上事故数
旧代码占比下降趋势
```

---

## Decision Card 4：模块化单体拆不拆

### 场景

六个上下文已经模块化运行，团队考虑拆分微服务。

### 判断

只有发布节奏、团队边界、容量隔离、故障隔离、数据边界和边界稳定六项都满足时才拆；先拆耦合最低、收益最可量化的模块。

### Mechanism -> Decision

| 机制 | 工程决策 |
| --- | --- |
| 同步调用多/共享事务/共享表 | 不拆 |
| 边界未验证 | 不拆 |
| 六条件满足 | 逐个拆并验证收益 |
| 拆分后无指标改善 | 回看决策 |

### Code

```text
拆分前：模块依赖图 + 跨模块调用统计
拆分后：发布频率、故障面、p99 对比
```

### 禁止决策

```text
上下文数量 = 微服务数量，拆完不验证收益。
```

### 验收指标

```text
独立发布频率
故障影响面
推荐请求 p99 latency
跨服务 error rate
交付周期
```

---

## Decision Card 5：边界持续治理

### 场景

DDD 落地一年后，检查边界是否漂移。

### 判断

架构测试持续运行，统一语言表和事件契约持续维护，变化触发评审，漂移信号触发告警。

### Mechanism -> Decision

| 机制 | 工程决策 |
| --- | --- |
| 依赖方向 | ArchUnit / Module |
| 词义漂移 | 统一语言表维护 |
| 聚合变大 | 模型评审 |
| 事件契约变化 | 版本治理 |
| 漂移信号 | 触发边界评审 |

### Code

```text
漂移信号：
聚合被到处加载
领域层出现新技术依赖
跨上下文直读表复发
一个变化改三个模块
```

### 禁止决策

```text
一次建模，终身不管。
```

### 验收指标

```text
架构测试失败数
跨模块依赖数
事件契约版本数
边界评审触发次数
生产事故复盘数
```
