# DDD 战略设计深度解析：从一句推荐需求到清晰的业务边界

> 这不是一篇 DDD 名词总结。
>
> 本文只追踪一个主线：**需求 Q——“给用户推荐首页商品”**。
>
> Q 从产品的一句话需求开始，沿途经过：
>
> ```text
> 需求表达
>   -> 业务语言
>   -> 业务能力
>   -> 限界上下文
>   -> 模块边界
>   -> 生产验证
> ```
>
> 本文只打穿 DDD 的战略设计：统一语言、子域、限界上下文和责任边界。
> Entity、Value Object、Aggregate 只在本文地图中预告，具体规则保护留到 `ddd-03`，不在这里提前堆概念。
>
> 本文承接 `ddd-00-为什么需要领域边界.md` 的全局地图，从真实需求开始进入战略设计。

# 🏷️ 关键词与主线进度

关键词：

```text
领域驱动设计 | 统一语言 | 子域 | 限界上下文 | 业务责任 | 模块边界 | 千人千面
```

主线进度：

```text
① 一个推荐服务为什么会失控
② 把一句需求拆成业务动作和业务判断
③ 让团队对词义达成局部一致
④ 按业务责任划分子域和限界上下文
⑤ 把边界落成代码模块
⑥ 用变更和故障验证边界是否有效
```

# 正文：六个 Level 打穿统一语言与业务边界

## Level 1：一句需求为什么不能直接变成一个 Service

一句话认知墙：**“给用户推荐首页商品”看起来只有一个动作，为什么最后会变成一个谁都不敢改的 `RecommendationService`？**

### 前置知识关卡

- [ ] 知道一个 HTTP 请求通常会进入 Controller、Service 和数据访问层
- [ ] 知道推荐系统通常包含用户、商品、策略、模型和曝光等概念
- [ ] 能区分“请求流程”和“业务规则”

### Why：简单写法为什么会留下账

**徒弟：**

> 需求不就是“给用户推荐商品”吗？我写一个 `RecommendationService`，里面依次查用户、查商品、调模型、返回结果，先跑起来再说。

**老陈：**

> 这个方案确实能让第一条链路跑起来。但它把四类不同的问题塞进了一个方法：
>
> ```text
> 用户允许使用什么信息
> 商品现在能不能推荐
> 当前策略应该选哪个版本
> 结果如何排序、过滤和兜底
> ```
>
> 一开始这些代码都在一个方法里，所以你感觉不到边界。等产品提出“用户关闭个性化后不能使用行为特征”，运营提出“策略要支持灰度发布”，算法提出“模型换成多路召回”，这个 Service 就开始同时承担隐私、商品、配置、实验和算法的规则。

最初的直觉方案并不是完全错误，它解决了“先把请求跑通”。问题在于，它没有回答“规则应该归谁负责”。

| 方案 | 解决什么 | 留下什么问题 |
| --- | --- | --- |
| 一个 `RecommendationService` | 快速串起推荐流程 | 流程、规则、技术调用全部混在一起 |
| 全局 `User`、`Item`、`Strategy` | 减少初期类数量 | 同一个词在不同业务里含义冲突 |
| 按 Controller/Service/DAO 分层 | 统一技术结构 | 看不出谁拥有商品、策略和画像规则 |
| 每个团队各写一套术语 | 局部开发速度快 | 联调时不断翻译，错误在运行期暴露 |

### What：一句需求里藏着什么

先不创建任何 Java 类，只把需求 Q 拆开：

```text
原始需求：给用户推荐首页商品

参与者：用户、产品、运营、算法、合规
场景：首页、登录状态、设备、时间、地域
输入：userId、场景、请求上下文、授权状态
业务判断：是否允许个性化、商品是否可推荐、策略是否生效
算法动作：召回候选、排序、打分
业务动作：过滤、去重、多样性、兜底
业务事实：推荐结果已经展示、用户点击了某个商品
```

可以把它分成三类：

```text
动作：系统要做什么
判断：系统在什么条件下允许做
事实：系统已经做完什么
```

这一步还不是 DDD 的完整设计，但它阻止我们过早地把所有逻辑塞进一个 Service。

### How：从需求句子开始走查

```text
① 记录原始需求 Q
② 标出所有动词：推荐、过滤、排序、记录
③ 标出所有判断：允许、可用、生效、兜底
④ 标出所有事实：展示、点击、转化
⑤ 把每个判断问一遍：谁拥有它？
```

最反直觉的一步是第 ③ 步。很多团队只记录“要调用什么接口”，不记录“为什么允许调用”。但真正变化最快的往往是判断：商品是否可推荐、用户是否允许个性化、策略何时生效。

**徒弟：**

> 这些判断先写在 Service 里也没问题吧？以后复杂了再拆。

**老陈：**

> 可以作为短期代码，但你要留下一个账：如果没有在需求阶段记录“这个判断属于谁”，以后拆分时只能从一团 `if/else` 里反推业务。DDD 的第一步不是创建聚合，而是让规则的来源可追踪。

### Transfer：这套拆法还能用于哪里

1. 支付需求可以拆成“扣款动作、风控判断、支付事实”。
2. 审批需求可以拆成“提交动作、审批规则、审批结果”。
3. 物流需求可以拆成“分配动作、配送资格、签收事实”。

本层留下的新账：**需求里的词还没有统一含义。**“用户”“商品”“策略”“曝光”在不同参与者口中可能不是一回事。下一层要解决：团队如何在一个业务边界内说同一种话？

### Level Ending

```text
口诀：先找规则归属，再写业务流程。
```

## Level 2：统一语言不是全局词典

一句话认知墙：**DDD 要求统一语言，但为什么不是让全公司所有地方都只能使用同一个模型？**

### 前置知识关卡

- [ ] 能说出上一层的三类信息：动作、判断、事实
- [ ] 知道推荐系统至少有用户、商品、策略和反馈等参与者
- [ ] 理解同一个中文词在不同业务中可能指不同东西

### Why：沟通损耗为什么会变成代码错误

**徒弟：**

> 产品、算法和开发都说“用户偏好”，那就统一叫 `UserPreference`，所有模块共用它，沟通不就简单了吗？

**老陈：**

> 先承认它解决了一个问题：大家有了一个共同的称呼。但还留下了更危险的问题——大家可能只是使用了同一个名字，并没有表达同一个含义。

在推荐系统里，“偏好”至少可能有三种意思：

```text
用户主动勾选的兴趣类别
根据点击行为推算出的兴趣分数
本次推荐请求临时计算出的排序特征
```

如果它们都叫 `UserPreference`，代码看起来统一，业务语义却被隐藏了。

### What：统一语言到底统一什么

统一语言的准确含义是：

> 在一个明确的业务边界内，业务人员、产品、测试和代码，对同一个词使用同一个含义。

它不是一份覆盖全公司的万能词典。

先建立一张“词义账本”：

| 词 | 画像上下文中的含义 | 商品上下文中的含义 | 在线推荐上下文中的含义 | 需要避免的误用 |
| --- | --- | --- | --- | --- |
| 用户 | 身份、授权、行为归属 | 可能只是购买关系 | 本次请求的推荐主体 | 不直接共享完整 `User` |
| 偏好 | 用户主动表达的兴趣 | 商品被用户关注的关系 | 本次排序使用的偏好特征 | 不把推算特征当成用户声明 |
| 商品 | 商品身份和状态 | 可售、上架、分类信息 | 可进入候选集的推荐对象 | 不把商品数据库实体直接传入推荐 |
| 策略 | 业务配置和发布版本 | 可能不是本上下文概念 | 当前请求要执行的策略 | 不把模型文件当成策略 |
| 曝光 | 推荐结果被展示的事实 | 商品可能被展示但不一定是推荐曝光 | 推荐链路的效果事件 | 不把返回结果直接当成曝光 |

统一语言至少要记录四件事：

```text
这个词在当前上下文中是什么意思
它不是什么意思
谁负责维护它
哪个业务动作会改变它
```

### How：用例子而不是定义开会

不要开一个只讨论名词的会议。拿真实场景逐句走查：

```text
场景：用户主动选择“运动”标签，系统随后点击了三个运动商品。
```

逐个追问：

```text
“运动”是用户声明，还是系统推算？
三个点击是画像输入，还是推荐结果反馈？
推荐时使用的分数是否等于用户偏好？
用户取消标签后，历史点击还算不算？
```

把争论记录成三列：

```text
原词 -> 当前上下文的准确词 -> 仍然没有决定的问题
```

例如：

```text
用户偏好 -> ExplicitPreference（用户主动选择）
用户画像 -> InferredInterest（系统推算）
推荐特征 -> RankingFeature（本次模型输入）
```

这些英文名不是为了显得专业，而是为了让代码不要继续使用一个模糊的 `Preference`。

**徒弟：**

> 统一语言的最终目标不是“代码即文档”吗？那有了代码是不是就不用维护词义表了？

**老陈：**

> 代码可以表达稳定的业务模型，但代码不会自动记录所有讨论、排除项和上下文关系。更准确的说法是：**代码应该使用统一语言，但代码不能替代业务决策记录。**

### Transfer：统一语言的迁移方法

1. 先用业务例子拆词，再给类和字段命名。
2. 每个词记录“它不是什么”，防止概念重新膨胀。
3. 词义变化要能追踪到负责人和测试用例。
4. 不同上下文允许有不同词义，但翻译必须显式存在。

本层留下的新账：**词义已经变清楚，但不同业务能力仍然混在一起。**“用户授权”“商品可售”“策略发布”“在线排序”不能由同一个窗口负责。下一层要回答：如何从业务能力划出限界上下文？

### Level Ending

```text
口诀：统一的是边界内含义，不是全世界模型。
```

## Level 3：从业务能力发现限界上下文

一句话认知墙：**限界上下文不是“拆一个微服务”，而是“划出一块模型在哪些范围内有效”。**

### 前置知识关卡

- [ ] 能区分用户声明、系统推算和模型输入
- [ ] 能说出推荐需求中的至少三类业务判断
- [ ] 知道一个业务系统可以先保持单体部署

### Why：一个全局模型为什么扛不住所有场景

**徒弟：**

> `User`、`Item`、`Strategy` 都是整个推荐平台的核心对象，统一放到 `common-domain` 里，所有模块复用，应该是最省事的方案。

**老陈：**

> 它确实能减少重复定义，但它把“共享类型”变成了“共享解释”。一旦画像模块给 `User` 增加行为特征，商品模块、实验模块和在线推荐模块都被迫理解这个字段；一旦商品模块修改商品状态，推荐模块又要跟着修改自己的判断。
>
> 你省掉的是几行类型定义，换来的是每个模块都要知道其他模块的语义。

全局模型的核心问题不是代码重复，而是**变化无法局部化**。

### What：三个层次不要混在一起

```text
领域 Domain
  整个业务问题空间：个性化推荐

子域 Subdomain
  一项相对完整的业务能力：用户画像、商品目录、推荐决策

限界上下文 Bounded Context
  一套模型和语言真正有效的边界：画像上下文、商品上下文、策略上下文
```

针对本示例，可以先提出一个设计假设：

```text
推荐领域
├── 核心子域：推荐策略与在线决策（待结合公司竞争力确认）
├── 支撑子域：用户画像、商品目录、实验管理、反馈分析
└── 通用子域：身份认证、审计、基础消息能力
```

这不是行业统一答案。对于一家算法公司，模型训练可能是核心子域；对于一家零售公司，商品和交易规则可能更核心。核心子域必须由业务竞争力和变化风险决定，不能由类名决定。

### How：按业务能力而不是按技术组件划分

用四个问题检查一项能力：

```text
它要解决哪一个业务问题？
它拥有哪些必须自己负责的规则？
它的词义是否和旁边模块不同？
它变化时是否希望尽量不影响其他能力？
```

得到一张初步上下文表：

| 上下文 | 它负责什么 | 它不负责什么 | 典型词义 |
| --- | --- | --- | --- |
| 用户画像 | 用户特征、行为归纳、授权状态 | 不决定最终推荐顺序 | `ExplicitPreference`、`InferredInterest` |
| 商品目录 | 商品状态、分类、可售性 | 不决定用户个性化策略 | `CatalogItem`、`Available` |
| 推荐策略 | 策略配置、版本、发布状态 | 不负责模型训练 | `StrategyVersion`、`Published` |
| 实验管理 | 分组、流量规则、实验生命周期 | 不负责商品可售性 | `Experiment`、`Treatment` |
| 在线决策 | 召回、排序、过滤、兜底 | 不拥有用户完整档案 | `RecommendationCandidate`、`Fallback` |
| 反馈分析 | 曝光、点击、转化归因 | 不决定当前请求的排序 | `RecommendationExposure` |

注意这个判断：

```text
同一个现实用户
  ≠ 所有上下文共享一个 User 类

同一个现实商品
  ≠ 所有上下文共享一个 Item 类
```

上下文使用同一个外部身份标识，并不意味着内部模型必须相同。

### Transfer：子域与上下文的迁移方法

1. 支付系统可以把“支付授权”“账单”“退款”分开看待。
2. 教育系统可以把“课程目录”“选课”“教学过程”“成绩”分开建模。
3. 物流系统可以把“运单”“仓储库存”“配送路线”“签收”分开建模。

本层留下的新账：**上下文边界画出来了，但边界之间迟早要交换信息。**下一篇会继续回答：一个上下文如何把自己的模型交给另一个上下文，而不把内部对象直接暴露出去？

### Level Ending

```text
口诀：边界按责任划，不按部署形式划。
```

<a id="level-4"></a>

## Level 4：用责任和变更验证边界

一句话认知墙：**画出几个框不等于完成建模，真正的边界要经得住规则变化。**

### 前置知识关卡

- [ ] 能说出 Domain、Subdomain、Bounded Context 的区别
- [ ] 能为用户画像、商品目录和在线决策各写一句责任描述
- [ ] 知道上下文可以先存在同一个进程里

### Why：看起来合理的边界也可能是假的

**徒弟：**

> 我们已经按 `user`、`item`、`strategy` 建了三个模块，边界应该清楚了吧？

**老陈：**

> 不一定。你只是按名词分了三个文件夹，还没有证明它们各自拥有规则。只要 `strategy` 模块还要直接修改 `User` 的内部字段，`item` 模块还要调用 `RecommendationService` 判断自己能不能推荐，这些边界就只是目录，不是业务边界。

边界需要通过三个测试：

```text
语言测试：同一个词在边界内是否只有一个含义？
责任测试：这条规则是否只有一个主要拥有者？
变化测试：某条需求变化时，修改范围是否主要停留在一个边界？
```

### What：边界的最小定义

一个可用的限界上下文至少要能说清楚四句话：

```text
我们负责什么业务结果？
我们拥有哪几条规则和状态？
别人可以向我们请求什么？
别人不能直接修改什么？
```

例如在线决策上下文：

```text
负责：为一次请求生成符合业务规则的推荐结果
拥有：候选过滤、推荐场景、兜底规则的执行状态
提供：GetRecommendations 用例和推荐结果契约
不允许：外部直接修改内部候选列表或排序中间状态
```

“拥有”不是说数据一定存在哪张表，而是说**谁对这个业务含义负责**。

### How：用变更场景做边界测试

拿真实变化逐条演练：

#### 场景一：用户关闭个性化

```text
变化首先影响：授权/画像上下文
在线决策需要接收：允许使用的特征范围
不应该发生：推荐模块直接读取用户隐私表的内部字段
```

#### 场景二：商品下架后不能推荐

```text
变化首先影响：商品上下文
在线决策需要接收：商品可推荐状态
不应该发生：推荐模块复制一套商品上架规则
```

#### 场景三：策略支持灰度发布

```text
变化首先影响：策略/实验上下文
在线决策需要接收：已经确定的策略版本和实验分组
不应该发生：在线请求临时修改策略配置
```

如果一个变化需要同时修改画像、商品、策略和在线决策四个内部模型，先不要急着说“业务本来就复杂”，要检查是否存在共享万能模型或责任泄漏。

**徒弟：**

> 那是不是边界越多越好？每个规则建一个上下文，修改范围就最小了。

**老陈：**

> 边界不是越多越好。边界越多，翻译、契约、部署和排障成本越高。真正的目标是：让强相关的规则留在一起，让不相关的变化不要互相拖着走。

### Transfer：边界验证的迁移方法

1. 代码评审时问“这条规则谁拥有”，不要只问“这段代码放哪个包”。
2. 需求评审时模拟一个规则变化，观察影响范围。
3. 事故复盘时检查是否出现跨上下文直接读表或改状态。
4. 团队拆分时先验证业务责任，再决定是否拆服务。

本层留下的新账：**边界通过了业务测试，但如果代码仍然共享内部类，边界会被依赖关系重新打穿。**下一层把战略边界落成模块和接口。

### Level Ending

```text
口诀：边界不是画出来的，是用变化测出来的。
```

<a id="level-5"></a>

## Level 5：把边界落成代码模块

一句话认知墙：**真正的业务边界，必须能阻止错误依赖进入代码。**

### 前置知识关卡

- [ ] 能用三句话描述一个限界上下文的责任
- [ ] 能用一个需求变化测试边界是否合理
- [ ] 知道模块化单体和微服务是两种不同维度的选择

### Why：只分包为什么不够

**徒弟：**

> 我把类分别放进 `profile`、`catalog`、`recommendation` 包里，就完成模块化了吧？

**老陈：**

> 如果 `recommendation` 仍然直接 import `profile.internal.UserEntity`，或者 `catalog` 允许任何模块修改 `ItemStatus`，那只是把耦合从一个目录搬到三个目录。边界真正生效，需要限制“谁可以看见谁、谁可以调用谁、谁可以修改谁”。

### What：一个上下文内部和外部分别暴露什么

建议从模块化单体开始：

```text
recommendation-system/
├── profile-context/
├── catalog-context/
├── strategy-context/
├── experiment-context/
├── decision-context/
└── feedback-context/
```

每个上下文内部再分责任：

```text
profile-context/
├── domain/          # 画像规则和本地模型
├── application/     # 画像用例
├── adapter/in/      # 接收外部请求或事件
└── adapter/out/     # 对外提供契约、访问存储
```

上下文之间只暴露稳定入口：

```text
ProfileContext -> FeatureSnapshotContract
CatalogContext -> RecommendableItemContract
StrategyContext -> PublishedStrategyContract
ExperimentContext -> AssignmentContract
```

不要暴露：

```text
JPA Entity
内部聚合对象
内部数据库表结构
内部缓存 Key
内部算法中间结果
```

### How：先做模块化，再决定是否拆服务

```text
① 为每个上下文建立独立 package 或 module
② 领域代码不直接依赖 Spring、JPA、Redis、MQ
③ 对外只提供 Use Case、Query 或 Contract
④ 禁止跨模块读取内部 Repository 和数据库表
⑤ 用编译依赖和架构测试检查边界
⑥ 经过真实需求和故障验证后，再评估独立部署
```

一个很小的契约示例：

```java
public record FeatureSnapshot(
        String userId,
        boolean personalizationAllowed,
        Set<String> inferredInterests
) {
}
```

这段代码的重点不在 `record`，而在它表达了一个边界决定：

```text
在线决策只拿到“允许使用的推荐特征快照”，
而不是直接拿到画像上下文内部的 User 对象。
```

**徒弟：**

> 既然未来可能拆成微服务，现在直接按微服务建多个项目不是更省事吗？

**老陈：**

> 物理拆分会立即引入网络、部署、监控、重试和数据一致性问题。如果业务边界还没被真实变化验证，你会把“边界不清”放大成“分布式边界不清”。先做模块化单体，是用更低的成本验证领域边界，不是拒绝微服务。

### Transfer：代码边界的迁移方法

1. Java 用 module/package 和依赖规则限制可见性。
2. Go 用 package 和 interface 表达拥有关系。
3. Rust 用 crate、module 和 trait 表达边界。
4. 微服务只是把已经验证的模块边界搬到进程边界。

本层留下的新账：**代码边界已经有了，但上下文之间的契约会变化，数据会延迟，事件会失败。**下一篇进入上下文映射，回答如何协作而不互相污染。

### Level Ending

```text
口诀：先隔离模型，再考虑拆进程。
```

<a id="level-6"></a>

## Level 6：生产验证与下一篇新账

一句话认知墙：**DDD 不是设计图上的“看起来合理”，而是能否让变化和故障停在正确边界内。**

### 前置知识关卡

- [ ] 能从一句需求拆出动作、判断和事实
- [ ] 能建立上下文责任表
- [ ] 能说明为什么模块化单体是第一阶段选择

### Why：边界正确为什么还不够

**徒弟：**

> 词义统一了、上下文也画了、代码包也分了，这篇文章是不是就结束了？

**老陈：**

> 还差最后一个问题：边界是否真的减少了生产风险？如果模型服务一超时，在线决策仍然拖垮请求线程；如果商品状态更新不能及时到达推荐模块，边界虽然漂亮，结果仍然错误。战略设计必须进入验证，而不是停在图上。

### What：验证边界的四类证据

```text
语言证据：同一上下文的产品、测试和代码是否使用同一含义
依赖证据：模块是否可以不访问其他上下文内部类和表
变化证据：需求变化是否主要落在规则拥有者所在上下文
运行证据：延迟、失败、过期和事件积压是否有可观测结果
```

### How：用一个变化和一个故障验收

#### 变化验收：增加“用户主动屏蔽品类”规则

```text
预期变化：画像/授权上下文增加屏蔽信息
预期协作：在线决策收到新的契约字段或策略事实
禁止结果：商品模型、模型推理代码、反馈归因同时修改内部实现
```

#### 故障验收：排序模型超时

```text
预期结果：在线决策在预算内停止等待并使用兜底结果
预期指标：ranker latency、fallback ratio、request p99
禁止结果：模型超时占满在线请求线程，导致整个推荐接口雪崩
```

#### 架构验收：检查领域代码依赖

```text
预期结果：领域模块不依赖 Spring、JPA、Redis、MQ
预期方式：编译依赖检查 + 领域单元测试
禁止结果：领域规则只有启动 Spring 容器后才能测试
```

### Transfer：战略设计的最终判断

1. 如果一个边界不能说明自己拥有的规则，它还不是有效边界。
2. 如果一条变化总是跨越所有模块，它可能存在共享模型或责任泄漏。
3. 如果一个模块只有数据搬运，没有业务判断，不必强行套完整 DDD。
4. 如果在线链路追求低延迟，应使用读模型、缓存和算法服务，不要用聚合加载替代数据访问设计。

本层不再留下战略设计的新账。下一篇进入 **上下文映射与协作**：当画像、商品、策略和在线决策必须交换信息时，如何定义契约、翻译模型并处理边界变化。

### Level Ending

```text
口诀：能限制变化，能解释故障，边界才算成立。
```

# ⚠️ 坑与细节

<a id="pitfalls"></a>

## 坑 1：把统一语言理解成全局词典

错误理解：全公司所有模块必须使用同一个 `User` 和 `Product`。

原因：忽略了同一个现实对象在不同业务中的含义不同。

比喻后果：所有窗口都被迫使用同一份内部档案，任何窗口修改字段，其他窗口都被牵连。

线上现象：画像字段增加导致推荐、商品和实验模块同时回归。

修正：统一上下文内的词义；跨上下文使用契约和翻译。

---

## 坑 2：把限界上下文等同于微服务

错误理解：画出三个上下文，就必须部署三个服务。

原因：把逻辑边界和物理部署混成一件事。

比喻后果：窗口责任还没确认，就先把每个窗口搬到不同办公楼，交接成本提前爆发。

线上现象：服务数量增加了，但调用、重试、数据一致性和排障成本先上升。

修正：先用模块化单体验证边界，再根据团队和发布需求决定是否拆服务。

---

## 坑 3：按数据库表划上下文

错误理解：一张表就是一个上下文。

原因：数据库结构是存储方案，不一定等于业务责任。

比喻后果：窗口按档案柜分工，而不是按办理事项分工；同一业务规则被拆散。

线上现象：一个业务动作需要跨多个 DAO 拼接，规则无法找到唯一负责人。

修正：先按业务能力和规则拥有者划边界，再决定数据如何存储。

---

## 坑 4：把算法模型当成全部领域

错误理解：推荐系统的核心是模型，所以模型代码就是 DDD 的领域层。

原因：把算法能力和业务决策混为一谈。

比喻后果：办理窗口开始维护后台机器的内部计算过程，业务规则反而没有负责人。

线上现象：模型替换需要修改大量业务代码，合规过滤和兜底规则埋在推理脚本中。

修正：模型通过端口提供排序能力，领域层负责可推荐性、策略、过滤和兜底规则。

---

## 坑 5：包名变化被当成边界完成

错误理解：把类移动到 `profile` 和 `recommendation` 目录就完成解耦。

原因：没有限制跨模块依赖和内部模型暴露。

比喻后果：窗口门牌换了，但工作人员仍然可以直接拿走其他窗口的内部档案。

线上现象：任意模块直接访问其他模块的 Entity、Repository 和表。

修正：只暴露用例和契约，禁止依赖内部对象和持久化细节。

---

## 坑 6：核心子域由技术热度决定

错误理解：用了向量检索或大模型，算法就一定是核心子域。

原因：把技术复杂度误认为业务竞争力。

比喻后果：窗口按设备昂贵程度分配，而不是按业务价值分配。

线上现象：算法团队负责了所有业务规则，产品和运营无法独立调整策略。

修正：核心子域由业务差异化、规则风险和变化频率共同判断。

---

## 坑 7：边界越多越高级

错误理解：上下文划得越细，耦合就越低。

原因：忽略了契约、翻译、监控和运维成本。

比喻后果：一份简单申请要盖十几个窗口的章，办理流程反而变慢。

线上现象：一次请求跨越大量模块，延迟和故障点增加，业务规则仍然没有清晰归属。

修正：让强相关规则留在一起，让不相关变化隔离开；不追求边界数量。

---

## 坑 8：代码即文档

错误理解：类名统一后就不需要业务词义和决策记录。

原因：代码能表达稳定结构，但不能完整表达讨论过程、排除项和上下文关系。

比喻后果：窗口只保留档案，不保留办理规则，换人后又开始各自解释。

线上现象：同一个字段被不同团队重新解释，接口没有改但业务结果变了。

修正：代码使用统一语言，同时保留词义表、责任表和重要决策。

# 📚 概念勘误表

<a id="errata"></a>

| 错误说法 | 准确说法 |
| --- | --- |
| 统一语言就是全公司使用同一套模型 | 统一语言保证一个限界上下文内部的词义一致 |
| 限界上下文就是微服务 | 限界上下文是模型边界，可以先存在模块化单体中 |
| 同一个现实用户必须对应一个全局 `User` 类 | 不同上下文可以使用不同用户模型，只共享必要身份标识 |
| 核心子域就是技术最复杂的模块 | 核心子域由业务竞争力和规则风险决定，技术复杂不等于业务核心 |
| 统一语言建立后代码就可以替代文档 | 代码表达稳定模型，词义、范围和决策仍需记录 |
| 每个上下文都必须有 ACL | ACL 是一种保护本地模型的方式，具体映射取决于上下游关系 |
| 包结构调整就完成了模块解耦 | 还要限制依赖、隐藏内部模型并验证变更影响范围 |
| 推荐算法模型应该全部放在领域层 | 领域层保护业务规则，模型推理通常通过端口接入 |

其中两点我以前也容易讲得过于绝对：

```text
我以前容易把“限界上下文”直接讲成微服务，准确说法是逻辑边界先于部署边界。
我以前容易把“统一语言”讲成全系统统一词典，准确说法是上下文内统一、上下文间显式翻译。
```

# 🏆 生产决策卡

<a id="decisions"></a>

## Decision Card 1：这个问题是否值得使用 DDD

### 场景

推荐策略、实验、合规规则和兜底逻辑持续变化，多个团队都在修改推荐链路。

### 判断

如果主要痛点是规则冲突、责任不清和变化影响面大，DDD 值得投入；如果只是简单查询，不要为了术语引入复杂模型。

### Mechanism -> Decision

| 机制 | 工程决策 |
| --- | --- |
| 规则频繁变化 | 建立统一语言和规则拥有者 |
| 多种业务含义冲突 | 划分限界上下文 |
| 查询为主、规则很少 | 使用读模型和简单 Service |

### Code

```java
public interface RecommendationPolicy {
    RecommendationResult apply(RecommendationContext context);
}
```

这个接口只有在存在稳定业务策略时才有意义；如果只是把几个 DAO 调用包起来，它不是领域模型。

### 禁止决策

```text
因为项目叫推荐系统，所以所有代码都必须使用 DDD 模式。
```

### 验收指标

```text
需求变更涉及的模块数量
领域规则单元测试覆盖的业务场景数
跨模块直接依赖数量
推荐请求 p99 latency
线上规则相关 error rate
```

## Decision Card 2：这个对象是领域模型还是读数据

### 场景

团队准备为 `UserFeature`、`RecommendationRequest`、`CandidateItem` 创建大量 Entity 和 Repository。

### 判断

先问它是否拥有身份、状态变化和必须保护的不变量。如果只是给一次查询使用的数据，不要强行设计成聚合。

### Mechanism -> Decision

| 机制 | 工程决策 |
| --- | --- |
| 有身份和状态迁移 | 考虑实体 |
| 属性组成完整含义 | 考虑值对象 |
| 必须一起保持规则 | 考虑聚合边界 |
| 只服务在线查询 | 优先读模型或 DTO |
| 算法中间结果 | 放在算法/基础设施数据路径 |

### Code

```java
public record RecommendationRequest(
        String userId,
        String scene,
        boolean personalizationAllowed
) {
}
```

这个请求是一次查询输入，不因为使用 `record` 就自动成为领域实体。

### 禁止决策

```text
凡是业务名词都创建 Entity，凡是数据都通过 Repository 加载。
```

### 验收指标

```text
在线请求数据库访问次数
feature_provider_latency
recommendation_request_latency_p99
CPU
Memory
```

## Decision Card 3：模块化单体还是微服务

### 场景

团队已经识别出画像、商品、策略和决策上下文，准备立即拆成多个服务。

### 判断

如果边界尚未经过需求变化、故障和团队协作验证，先使用模块化单体。

### Mechanism -> Decision

| 机制 | 工程决策 |
| --- | --- |
| 逻辑责任已经清楚 | 先分模块和依赖 |
| 发布节奏、团队和容量不同 | 再评估独立服务 |
| 跨上下文一致性尚未设计 | 不要先拆进程 |
| 在线链路延迟敏感 | 减少不必要的同步网络调用 |

### Code

```text
decision-context
  -> FeatureSnapshotContract
  -> PublishedStrategyContract
  -> RecommendableItemContract
```

模块先通过契约协作，未来是否改成网络调用是部署决策，不改变业务责任。

### 禁止决策

```text
上下文数量 = 微服务数量。
```

### 验收指标

```text
模块间编译依赖数量
跨模块直接访问内部类的次数
请求 p99 latency
跨服务 error rate
部署回滚时间
```

## Decision Card 4：算法链路和领域链路如何分工

### 场景

模型、召回、特征和业务过滤都被写进一个推荐领域 Service。

### 判断

业务规则进入领域模型；模型推理和特征访问通过端口接入；在线链路使用缓存和读模型降低等待。

### Mechanism -> Decision

| 机制 | 工程决策 |
| --- | --- |
| 商品是否可推荐 | 领域/商品规则 |
| 用户是否允许个性化 | 授权与推荐策略规则 |
| 候选如何召回 | CandidateRecallPort |
| 候选如何打分 | RankerPort |
| 特征如何读取 | FeatureProviderPort |
| 模型超时如何处理 | 应用编排和降级策略 |

### Code

```java
public interface RankerPort {
    RankedCandidates rank(RankingInput input);
}

public interface CandidateRecallPort {
    CandidateSet recall(RecommendationContext context);
}
```

### 禁止决策

```text
让领域对象直接创建 Redis 客户端、HTTP 客户端或模型 SDK。
```

### 验收指标

```text
candidate_recall_latency
ranker_latency
fallback_ratio
feature_provider_latency
CPU
Memory
Error rate
```

# 🌍 跨语言视角

<a id="cross-language"></a>

## Java 如何表达

```text
package/module 划分上下文
interface/port 隔离外部能力
record 表达稳定的数据契约
测试和依赖规则保护边界
```

## Go 如何表达

```text
package 划分上下文
interface 表达调用能力
struct 表达本地模型和契约
internal package 隐藏上下文内部实现
```

## Rust 如何表达

```text
crate/module 划分上下文
trait 表达端口
struct/enum 表达状态和契约
pub 可见性控制边界
```

## 跨语言仍成立的判断力

```text
同一个业务词不一定对应同一个类型。
拥有规则的模块才应该拥有状态修改权。
逻辑边界先于进程边界。
跨边界依赖应该是显式契约，而不是内部对象引用。
```

语言只能改变表达方式，不能替你决定业务边界。
