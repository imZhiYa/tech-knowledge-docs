# 02｜限界上下文与边界划分：决定哪些模型不能混用

## 本篇目标

从业务能力、语言差异、规则所有权和变化原因划分上下文。不要根据数据库表数量、团队人数或微服务数量机械切分。

## 1. 一个词在不同团队里可能不是同一个概念

“客户”可能指：

- 销售团队：需要跟进的潜在购买者。
- 客服团队：已经购买并需要服务的用户。
- 风控团队：需要评估风险的主体。

它们可能共享一个 customerId，但生命周期、字段、规则和责任不同。共享 ID 不代表共享一个领域模型。

## 2. 用四个维度判断边界

| 维度 | 要问的问题 | 边界信号 |
|---|---|---|
| 业务能力 | 这个模块对业务提供什么结果？ | 输入输出目标不同 |
| 语言语义 | 同一个词是否有不同含义？ | 状态、字段含义冲突 |
| 规则所有权 | 谁负责定义和改变规则？ | 规则由不同角色/团队维护 |
| 变化原因 | 什么需求会导致它变化？ | 变化节奏和风险不同 |

不要只因为两个模块的表结构不同就拆上下文；也不要因为它们使用同一张表就认为它们属于一个上下文。

## 3. 线索案例的候选上下文

下面是**案例假设**，需要根据真实组织和业务确认：

~~~text
线索管理上下文
  - 线索创建、分配、跟进、完结
  - 拥有线索生命周期规则

客户管理上下文
  - 客户主数据、客户归属和客户关系
  - 拥有客户身份与主数据规则

客户预警上下文
  - 预警规则、触发、处理和关闭
  - 拥有预警生命周期

销售任务上下文
  - 任务创建、执行、超时和完成
  - 拥有任务生命周期

报表分析上下文
  - 汇总、统计、分析和历史查询
  - 以读模型为主，不反向决定线索核心状态
~~~

## 4. 上下文不是微服务

三个概念不要混淆：

- 限界上下文：模型语义和规则适用的边界。
- 模块：代码和团队协作的组织边界。
- 微服务：独立部署、运行和治理的服务边界。

一个限界上下文可以先作为单体中的独立模块；一个微服务也可能因为历史原因包含多个模型边界。先明确模型边界，再评估部署边界。

## 5. 判断是否应该拆分的实用问题

如果两个业务区域满足以下多项，考虑拆开模型：

- 对同一个名词有不同定义。
- 状态机和生命周期不同。
- 规则由不同角色负责。
- 变更经常互相影响。
- 需要不同的数据保留、权限或一致性策略。

如果只是代码包不同、表不同，但语义和规则仍一致，拆分可能只增加调用和维护成本。

## 6. 上下文映射：明确关系和责任

| 关系 | 含义 | 什么时候考虑 |
|---|---|---|
| Customer-Supplier | 上下游存在供需关系 | 上游愿意提供稳定能力和契约 |
| Conformist | 下游接受上游模型 | 上游模型质量足够且改造成本低 |
| ACL | 下游翻译外部语义，保护本地模型 | 外部模型不应渗入本地领域 |
| Open Host Service | 上游提供标准化访问能力 | 多个消费者需要稳定接口 |
| Published Language | 双方约定共享契约 | 需要跨团队交换业务事实 |

不要为了背八种上下文映射关系而把每一种都放进系统。关系名称是分析工具，不是架构验收清单。

## 7. 输出上下文契约

每个上下文至少写清：

~~~text
上下文名称：
负责的业务能力：
拥有的核心规则：
核心模型：
对外提供的命令/查询/事件：
依赖哪些外部上下文：
外部模型如何进入本地：
数据所有权：
失败和一致性要求：
负责人/变更流程：
~~~

例如线索上下文拥有 Lead 状态，不允许客户预警上下文直接更新 lead.status。预警可以发布预警已触发的事实，线索上下文根据自己的规则决定是否改变线索状态。

## 本篇交付物

- 上下文清单和职责描述。
- 上下文关系图。
- 每个上下文的模型所有权。
- 对外契约草案。
- 尚未确定的边界争议。

**口诀：共享标识不等于共享模型，代码部署边界不等于领域边界。**
