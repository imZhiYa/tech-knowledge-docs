# 03｜实体、值对象与聚合根：让业务对象各司其职

## 本篇目标

前两篇已经梳理了业务职责和上下文边界。本篇进入领域模型内部，回答三个问题：

- 哪些业务对象具有独立身份和生命周期？
- 哪些数据其实是一个有含义、有约束的业务概念？
- 哪些对象和规则必须在同一个一致性边界内被保护？

实体、值对象和聚合根不是为了让代码看起来更“面向对象”，而是为了让业务身份、业务概念、业务行为和规则有明确归属。

## 1. 从业务问题进入，而不是先背术语

回到线索管理案例：

- 线索有独立 ID，负责人和状态会变化，但它仍然是同一条线索。
- 联系方式、金额、地址等数据可能具有独立的业务含义和校验约束。
- 线索分配时，负责人、分配时间和状态必须满足一致的业务规则。
- 跟进记录虽然关联线索，但未必需要和线索核心状态在同一个事务中修改。

这分别引出实体、值对象和聚合设计，但不能把每个字段、每张表都机械地变成一个领域对象。

## 2. 实体：明确业务身份和生命周期

实体解决的问题是：**属性变化之后，业务上仍然被认为是同一个对象。**

Lead 有独立身份；负责人、状态和更新时间可以变化，但仍是同一条线索。

~~~java
public record LeadId(UUID value) {
    public LeadId {
        Objects.requireNonNull(value);
    }
}
~~~

实体相等性主要由身份决定，而不是所有字段都相等。数据库自增主键可以是持久化实现，但领域身份不应被无意绑定到某个数据库方案。

判断一个候选对象是否是实体，可以问：

1. 业务是否需要持续识别它？
2. 它是否有独立生命周期？
3. 属性变化后，业务是否仍认为它是原来的那个对象？
4. 其他业务行为是否需要引用它的身份？

如果一个“负责人”只是指向用户上下文的 ID，而用户的身份、权限和生命周期由其他上下文管理，那么在线索模型里通常只需要引用 SalesRepId，不必复制一个完整 User 实体。

## 3. 值对象：让值带着业务含义和约束

值对象解决的问题是：**把一组有业务含义的数据及其约束表达为一个整体，而不是让调用方到处处理没有语义的原始字段。**

例如：

~~~java
public record ContactInfo(
    String name,
    String phone,
    String address
) {
    public ContactInfo {
        Objects.requireNonNull(name);
        Objects.requireNonNull(phone);
        Objects.requireNonNull(address);
        if (phone.isBlank()) {
            throw new IllegalArgumentException("phone must not be blank");
        }
    }
}
~~~

值对象适合表达没有独立身份、由值定义相等性的概念，通常设计为不可变对象。它不是“字段多就封装”的工具，也不是为了减少 DTO 字段数量。

判断是否值得建值对象：

- 这组数据是否代表一个稳定的业务概念？
- 是否有共同的校验规则或不变性？
- 是否在多个地方被重复解释或组合？
- 给它一个类型后，能否减少非法状态或误用？

如果只是简单展示字段，拆成值对象反而可能增加不必要的抽象。

## 4. 聚合与聚合根：保护业务规则和一致性边界

聚合解决的问题是：**哪些对象必须作为一个整体维护业务不变量？**

聚合根是聚合对外的唯一业务访问入口。外部对象通过聚合根执行会影响聚合内部状态的操作，不能绕过它随意修改内部对象。

线索分配案例假设：

- 只有待分配线索可以首次分配。
- 分配成功后必须有负责人。
- 负责人、分配时间和状态必须符合业务规则。
- 已完结线索不能被普通分配命令重新分配。

候选模型：

~~~text
Lead（聚合根 / Entity）
  - LeadId
  - LeadStatus
  - SalesRepId
  - AssignedAt
  - version
  - assignTo()
  - complete()
~~~

聚合根不是“最大的实体”，也不是把所有关联对象装进一个对象图。它负责保护聚合边界内必须成立的不变量。

## 5. 用代码让规则有唯一归属

下面是 JDK 21 的简化示例，只展示领域行为，不包含框架和持久化细节：

~~~java
public enum LeadStatus {
    NEW,
    PENDING_ASSIGNMENT,
    FOLLOWING,
    COMPLETED
}

public final class Lead {
    private final LeadId id;
    private LeadStatus status;
    private SalesRepId ownerId;
    private Instant assignedAt;

    public Lead(LeadId id, LeadStatus status) {
        this.id = Objects.requireNonNull(id);
        this.status = Objects.requireNonNull(status);
    }

    public void assignTo(SalesRepId target, Instant now) {
        Objects.requireNonNull(target);
        Objects.requireNonNull(now);

        if (status != LeadStatus.PENDING_ASSIGNMENT) {
            throw new IllegalStateException(
                "Only pending leads can be assigned");
        }

        this.ownerId = target;
        this.assignedAt = now;
        this.status = LeadStatus.FOLLOWING;
    }

    public void complete() {
        if (status != LeadStatus.FOLLOWING) {
            throw new IllegalStateException(
                "Only following leads can be completed");
        }
        this.status = LeadStatus.COMPLETED;
    }

    public LeadId id() { return id; }
    public LeadStatus status() { return status; }
    public Optional<SalesRepId> ownerId() {
        return Optional.ofNullable(ownerId);
    }
}
~~~

这里最重要的不是 Lead 这个类，而是：分配规则不再散落在多个 Controller、Service 和 SQL 更新语句中，而是有一个明确的领域入口负责判断状态是否合法。

但聚合根也不是万能的。权限、跨聚合查询、远程系统可用性等问题，仍然需要应用层、领域策略或基础设施协作。

## 6. 为什么跟进记录不一定属于 Lead 聚合？

不要因为“跟进属于线索”就把所有跟进记录都放进 Lead 聚合。

判断问题：

1. 新增跟进时，是否必须同步修改 Lead 的核心状态？
2. 跟进记录是否可能无限增长？
3. 跟进记录是否有独立查询、权限和保留策略？
4. 是否需要一次加载所有跟进记录才能执行核心规则？
5. 跟进记录能否独立创建、归档或审计？

如果跟进记录数量无上限、独立查询且不需要和 Lead 状态在同一个事务内修改，可以将其作为独立模型，通过 LeadId 关联，而不是放进聚合集合。

聚合不是对象关系图，也不是数据库外键的镜像。它是业务不变量需要被同步保护时所采用的一致性边界。

## 7. 聚合边界如何影响并发和事务？

聚合越大，加载和保存成本越高，并发冲突面也可能越大；聚合太小，又可能把一个必须原子成立的不变量拆散。

判断顺序：

1. 写出不变量。
2. 标明每条不变量涉及哪些对象。
3. 标明必须同步成立还是允许最终一致。
4. 同步必须成立的规则优先留在同一个事务边界。
5. 不需要同步成立的关系考虑引用 ID、事件或查询投影。
6. 通过并发测试验证边界，而不是仅凭类图判断。

乐观锁是常见实现方式，不是聚合定义本身。数据库更新可以使用版本条件：

~~~sql
UPDATE lead
SET owner_id = ?, status = ?, assigned_at = ?, version = version + 1
WHERE id = ? AND version = ? AND status = 'PENDING_ASSIGNMENT';
~~~

影响行数为 1 表示本次更新成功；为 0 需要区分记录不存在、状态变化或版本冲突。不要把所有冲突都当成可自动重试的瞬时错误。

## 8. 三个概念如何协作，而不是机械地一一对应？

| 设计工具 | 核心职责 | 主要保护什么 |
|---|---|---|
| Entity | 表达有独立身份和生命周期的对象 | 业务身份、状态和行为归属 |
| Value Object | 表达有意义、可校验的值 | 业务概念、值约束和不可变性 |
| Aggregate | 将必须共同满足不变量的对象组织在一起 | 一致性边界 |
| Aggregate Root | 作为聚合唯一对外入口 | 规则保护和状态修改权限 |

聚合根本身也是实体；实体和值对象共同构成领域模型。它们不是三个互相独立、各自解决一种症状的工具。

更准确地说，领域对象帮助我们让业务身份、业务概念和业务规则有明确归属；而业务职责混杂还需要上下文边界，跨领域协作还需要契约和协作机制。

## 9. Domain Service 何时需要？

当规则属于领域，但不自然地归属于某个实体或值对象时，才考虑领域服务。例如两个聚合之间的领域计算或复杂策略。不要把所有 Service 都改名为 DomainService。
