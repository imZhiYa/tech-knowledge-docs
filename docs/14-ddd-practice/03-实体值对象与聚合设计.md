# 03｜实体、值对象与聚合设计：从业务不变量推导一致性边界

## 本篇目标

不从数据库表推导聚合，而是从“必须始终成立的业务规则”推导一致性边界。读完后应能解释为什么一个对象是实体、为什么一个值是值对象、为什么某些记录不应该塞进聚合。

## 1. 先定义不变量

不变量（Invariant）是一次业务操作前后都必须成立的约束，或在状态迁移时必须满足的规则。

线索分配案例假设：

- 只有待分配的线索可以首次分配。
- 分配成功后必须有负责人。
- 分配人与分配时间必须同时记录。
- 两个并发分配不能互相覆盖。
- 已完结线索不能被普通分配命令重新分配。

先确认这些规则是否真实存在，再讨论聚合。

## 2. 实体：身份在属性变化后仍然稳定

Lead 有独立身份；负责人、状态和更新时间可以变化，但仍是同一条线索。

~~~java
public record LeadId(UUID value) {
    public LeadId {
        Objects.requireNonNull(value);
    }
}
~~~

实体相等性由身份决定，而不是所有字段都相等。数据库自增主键可以是持久化实现，但领域身份不应被无意绑定到某个数据库方案。

## 3. 值对象：让值带着含义和约束

例如负责人标识：

~~~java
public record SalesRepId(UUID value) {
    public SalesRepId {
        Objects.requireNonNull(value);
    }
}
~~~

值对象适合表达没有独立身份、由值定义相等性的概念。不是每个字段都值得包装成类；只有当类型能明确语义、校验或不变性时，才值得增加抽象。

## 4. 聚合：围绕必须一起保护的不变量划边界

候选模型：

~~~text
Lead（聚合根）
  - LeadId
  - LeadStatus
  - SalesRepId（可空，取决于状态）
  - AssignedAt（可空，取决于状态）
  - version
  - assignTo()
  - complete()
~~~

跟进记录是否属于 Lead 聚合？不要凭“跟进属于线索”决定。

判断问题：

1. 新增跟进时，是否必须同步修改 Lead 的核心状态？
2. 跟进记录是否可能无限增长？
3. 跟进记录是否有独立查询、权限和保留策略？
4. 是否需要一次加载所有跟进记录才能执行核心规则？
5. 跟进记录能否独立创建、归档或审计？

如果跟进记录数量无上限、独立查询且不需要和 Lead 状态在同一个事务内修改，可以将其作为独立模型，通过 LeadId 关联，而不是放进聚合集合。

聚合不是对象关系图，也不是数据库外键的镜像。它是事务一致性边界。

## 5. 用代码表达领域行为

下面是 JDK 21 的简化示例。它展示状态保护，不包含框架和持久化代码：

~~~java
public enum LeadStatus {
    NEW,
    PENDING_ASSIGNMENT,
    FOLLOWING,
    COMPLETED
}

public final class Lead {
    private final LeadId id;
    private LeadStatus status;
    private SalesRepId ownerId;
    private Instant assignedAt;

    public Lead(LeadId id, LeadStatus status) {
        this.id = Objects.requireNonNull(id);
        this.status = Objects.requireNonNull(status);
    }

    public void assignTo(SalesRepId target, Instant now) {
        Objects.requireNonNull(target);
        Objects.requireNonNull(now);

        if (status != LeadStatus.PENDING_ASSIGNMENT) {
            throw new IllegalStateException(
                "Only pending leads can be assigned");
        }

        this.ownerId = target;
        this.assignedAt = now;
        this.status = LeadStatus.FOLLOWING;
    }

    public void complete() {
        if (status != LeadStatus.FOLLOWING) {
            throw new IllegalStateException(
                "Only following leads can be completed");
        }
        this.status = LeadStatus.COMPLETED;
    }

    public LeadId id() { return id; }
    public LeadStatus status() { return status; }
    public Optional<SalesRepId> ownerId() {
        return Optional.ofNullable(ownerId);
    }
}
~~~

注意：真实系统要定义 NEW 如何进入 PENDING_ASSIGNMENT、完结原因、权限和重新打开规则。示例没有替业务做这些决定。

## 6. 聚合大小与并发

聚合越大，加载和保存成本越高，并发冲突面也可能越大；聚合太小，又可能把一个必须原子成立的不变量拆散。

判断顺序：

1. 写出不变量。
2. 标明每条不变量涉及哪些对象。
3. 标明必须同步成立还是允许最终一致。
4. 同步必须成立的规则优先留在同一个事务边界。
5. 不需要同步成立的关系考虑引用 ID、事件或查询投影。
6. 通过并发测试验证边界，而不是仅凭类图判断。

乐观锁是常见实现方式，不是聚合定义本身。数据库更新可以使用版本条件：

~~~sql
UPDATE lead
SET owner_id = ?, status = ?, assigned_at = ?, version = version + 1
WHERE id = ? AND version = ? AND status = 'PENDING_ASSIGNMENT';
~~~

影响行数为 1 表示本次更新成功；为 0 需要区分记录不存在、状态变化或版本冲突。不要把所有冲突都当成可自动重试的瞬时错误。

## 7. Domain Service 何时需要？

当规则属于领域，但不自然地归属于某个实体或值对象时，才考虑领域服务。例如两个聚合之间的领域计算或复杂策略。不要把所有 Service 都改名为 DomainService。
