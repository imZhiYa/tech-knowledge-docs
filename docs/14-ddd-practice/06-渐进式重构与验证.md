# 06｜渐进式重构与验证：让 DDD 安全进入已有系统

## 本篇目标

DDD 重构不是另起炉灶。要在旧 API、旧表、旧数据和旧调用方仍然存在的情况下，逐步替换规则实现，并证明新旧行为一致。

## 1. 不要一次性重写整个模块

建议从一个高价值用例切入，例如线索分配：

~~~text
旧系统
  -> 多个入口各自实现分配规则
  -> 更新同一组字段
  -> 规则不一致

渐进改造
  -> 建立 AssignLead 用例
  -> 新入口走新用例
  -> 旧入口转调新用例
  -> 影子比对
  -> 灰度切流
  -> 移除旧实现
~~~

如果一开始就拆微服务、迁数据库、换消息系统、重写接口，出了问题很难定位原因。

## 2. 第一步：建立行为基线

收集：

- 现有 API 请求与响应样本。
- 状态迁移记录和异常行为。
- 数据库更新 SQL、触发器和定时任务。
- 调用方列表及调用频率。
- 关键业务指标和缺陷基线。

对历史行为有争议时，找业务负责人确认“当前实现”是否就是“期望规则”。不要把旧 Bug 固化成新领域规则。

## 3. 第二步：补特征测试和契约测试

特征测试（Characterization Test）记录旧系统当前可观察行为；契约测试验证调用方依赖的输入输出。对于已确认的 Bug，先与业务确认预期，再写正确行为测试，避免盲目复制旧行为。

## 4. 第三步：建立新用例但复用旧基础设施

第一阶段可以不改数据库表、不改 API、不拆服务，只把业务规则集中到新的应用用例和领域对象中。

这是降低风险的关键：先改变规则组织方式，再考虑存储和部署架构。

## 5. 第四步：影子比对与灰度

影子比对示意：

~~~text
线上请求
  |
  +--> 旧逻辑 -> 正式响应
  |
  +--> 新逻辑 -> 只计算、不写入
                  |
                  v
             比较结果与差异
~~~

影子执行必须避免产生重复副作用。新逻辑不能重复发消息、创建任务或写正式数据。比对字段要区分“业务结果差异”和“无关字段差异”。

灰度时明确：

- 灰度对象和比例。
- 观察窗口。
- 成功指标和失败阈值。
- 回滚开关和责任人。
- 数据兼容策略。

比例和阈值根据实际流量、风险和基线制定，不在教程里虚构固定数字。

## 6. 第五步：处理数据和并发兼容

如果旧代码和新代码会同时写同一张表，必须确保它们遵循相同的状态约束和版本控制。否则新模型再好，也会被旧入口绕过。

可选策略：

- 旧入口先统一委托给新用例。
- 使用条件更新和版本号防止覆盖。
- 对关键写入增加审计日志。
- 暂时禁止不受控的脚本直接更新核心状态。
- 对数据修复操作设置审批、幂等和回滚方案。

## 7. 测试金字塔

| 测试类型 | 验证什么 | 典型测试 |
|---|---|---|
| 领域单元测试 | 不变量和状态迁移 | 非待分配线索不能分配 |
| 应用服务测试 | 用例编排和事务边界 | 分配成功后保存并登记事件 |
| Repository 集成测试 | ORM、SQL、乐观锁 | 并发更新只能有一个成功 |
| 契约测试 | API 和事件契约兼容 | 旧调用方字段仍可解析 |
| 端到端测试 | 关键业务链路 | 分配后任务和通知按约定产生 |
| 回归/影子比对 | 新旧行为差异 | 新旧计算结果一致性 |

不要只靠 Mock 测试证明数据库并发正确。乐观锁、唯一约束和事务行为必须通过真实数据库集成测试验证。

## 8. 生产观察指标

至少观察：

- 非法状态迁移拒绝次数。
- 分配冲突和乐观锁冲突次数。
- 分配成功率与业务耗时。
- 事件发布延迟、重试次数和死信数量。
- 消费者重复事件数量。
- 新旧逻辑差异率。
- 回滚次数和线上回归缺陷。

指标必须对应业务目标；仅仅类数量增加、包结构更整齐，不代表 DDD 改造成功。

## 9. 退出标准

一个用例完成迁移，至少满足：

- 规则有明确负责人和测试覆盖。
- 所有已知写入口已收敛或受约束。
- 并发冲突行为符合业务预期。
- API 和事件契约兼容。
- 关键指标在观察窗口内达到事先约定的目标。
- 回滚路径验证过。
- 旧实现可以安全下线。

**口诀：先建立行为基线，再替换规则实现；先证明一致，再扩大迁移范围。**
