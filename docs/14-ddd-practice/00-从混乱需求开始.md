# 00｜从混乱需求开始：DDD 不是从类图开始

## 本篇目标

读完后，你应该能做三件事：

- 用业务语言描述一个值得建模的问题，而不是说“代码太乱所以要上 DDD”。
- 区分事实、假设、症状和根因。
- 在写任何领域类之前，形成一份可评审的问题陈述和改造边界。

## 1. 问题现场：线索模块为什么越来越难改？

案例设定：一个 CRM 系统管理销售线索。随着业务增长，线索模块出现以下现象：

| 现象 | 可能的根因 | 需要调查的证据 |
|---|---|---|
| 详情 API 返回大量空字段 | 一个 DTO 承载多个业务场景 | 字段使用方、接口调用方、字段非空率 |
| 修改状态的入口很多 | 规则散落或缺少统一命令入口 | Controller、Job、MQ Consumer、SQL 更新点 |
| 分配后偶尔还能被其他人修改 | 并发控制或状态约束不足 | 更新 SQL、版本字段、冲突日志 |
| 预警状态与线索状态互相影响 | 两种生命周期被混为一谈 | 状态定义、状态迁移、责任团队 |
| 新需求经常回归旧功能 | 模块边界和契约不清晰 | 变更影响范围、回归缺陷 |

注意：这些是**待验证的现象假设**。不能仅凭“字段很多”就认定必须使用 DDD。大量字段可能只是 API 设计问题；并发错误可能只需数据库条件更新；低复杂度 CRUD 不需要为了架构完整而创建聚合。

## 2. 先区分四种陈述

分析需求时，把陈述分成四类：

- **事实**：代码、日志、SQL、工单或业务人员可以验证的内容。
- **症状**：用户能感知的问题，例如重复分配、状态错误、接口返回空字段。
- **假设**：对根因的解释，需要继续验证。
- **决策**：基于证据选择的改造方案。

示例：

~~~text
症状：线索被分配后仍可被另一名销售接管。
假设：分配命令没有检查当前状态，或并发更新没有版本保护。
证据：检查所有写入口、SQL where 条件、并发日志。
决策：由统一分配用例校验状态，并用条件更新/乐观锁处理并发。
~~~

不要把假设写成结论。

## 3. DDD 的进入条件：业务规则是否值得被模型保护？

先问五个问题：

1. 同一对象是否存在多个合法状态，且状态迁移有业务前提？
2. 是否存在多个角色或入口执行同一业务动作？
3. 规则是否散落在多个服务、SQL、定时任务或消息消费者中？
4. 业务概念是否在不同模块中含义不一致？
5. 规则变化是否频繁影响多个模块，且错误成本较高？

如果答案大多是否，简单分层 CRUD、事务脚本或模块化 Service 可能更合适。如果答案大多是“是”，再考虑用领域模型保护核心规则。

这不是打分公式，而是触发进一步分析的检查表。

## 4. 写出问题陈述

用下面模板形成一页纸：

~~~text
业务目标：
谁需要完成什么业务结果？

当前流程：
现在由哪些角色、系统和入口完成？

主要症状：
发生了什么可观察的问题？

业务风险：
错误会造成什么损失或合规风险？

已知约束：
API 是否必须兼容？数据库能否改？是否允许停机？

待验证假设：
我们认为根因是什么？还缺什么证据？

本次范围：
明确要改什么、不改什么。

成功指标：
例如非法状态迁移次数、重复分配率、回归缺陷、
接口字段空值比例、需求变更影响文件数。
指标阈值由项目基线和业务目标确定，不预设虚构数字。
~~~

## 5. 划清本次改造边界

建议先选择一个高频且规则明确的用例，例如“分配线索”，不要第一期重写整个 CRM。

范围示例：

- 纳入：分配资格校验、分配人记录、状态变化、并发冲突处理。
- 暂不纳入：客户画像、报表宽表、历史数据清洗、所有预警规则。
- 兼容：现有 API 字段和调用方行为。
- 风险控制：保留旧流程回滚开关，先影子比对再灰度。

## 6. 最小交付物

本篇结束时，不应该提交一个 Lead 类，而应该提交：

- 一份问题陈述。
- 一张当前流程图。
- 一份事实/假设清单。
- 一个改造范围声明。
- 一组可度量的成功指标。

## 7. 设计决策记录（ADR）示例

~~~text
ADR-001：先重构线索分配用例，不整体重写线索模块

背景：
分配规则分散在多个入口，存在状态校验不一致风险。

决策：
建立统一的 AssignLead 用例，所有入口调用同一应用服务。
领域对象负责合法性判断，持久化层负责并发冲突检测。

备选：
A. 只抽取公共 Service 方法
B. 先建立领域模型和统一用例
C. 直接拆成独立微服务

选择 B：
当前复杂度主要来自规则分散和状态边界不清。
拆微服务会引入网络、部署和数据一致性成本，暂时没有证据支持。

后果：
需要补领域测试和迁移旧入口；短期代码量会上升。
~~~
