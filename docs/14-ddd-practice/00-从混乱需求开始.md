# 00｜从混乱、膨胀、无序开始：为什么业务系统需要治理复杂度

## 本篇目标

读完后，你应该能够：

- 识别业务系统中混乱、膨胀、无序的典型表现。
- 区分可观察症状、潜在根因、待验证假设和设计决策。
- 判断问题属于业务边界、领域模型、规则保护，还是普通技术实现问题。
- 在引入 DDD 之前，形成一份有证据、有范围、有成功指标的问题陈述。

## 1. 一个系统是怎样逐渐变复杂的？

早期系统可能只有线索创建、查询和简单更新。随着业务发展，逐渐增加分配、跟进、完结、客户预警、通知、报表等能力。

如果每次需求都只是在原有 Service 中增加方法、在 DTO 中增加字段、在 SQL 中增加条件，短期交付很快，长期却可能出现：

- 一个 Service 同时处理线索生命周期、客户预警和通知。
- 同一个业务规则在 Controller、定时任务、消息消费者中重复实现。
- 一个 DTO 为多个页面和业务场景服务，字段越来越多，很多字段对当前场景没有意义。
- 不同模块可以直接修改同一业务对象的状态。
- 修改一个业务规则，需要理解多个模块和多个入口。

这不是因为代码行数本身变多，而是因为业务职责、规则和变化原因没有得到清晰组织。

## 2. 三类症状：混乱、膨胀、无序

| 症状 | 典型表现 | 首要调查方向 |
|---|---|---|
| 混乱 | 一个类承担多个业务职责；同一概念在不同模块含义不一致；规则散落多处 | 职责归属、统一语言、模型边界 |
| 膨胀 | Service、DTO、条件分支持续增长；一个需求牵动多个模块；重复数据结构增加 | 业务概念是否缺少抽象；模型是否承载多个场景；依赖是否过多 |
| 无序 | 多个入口任意修改状态；状态迁移没有统一约束；跨模块直接操作内部数据 | 状态所有权、业务不变量、一致性边界、协作契约 |

这三个词描述的是复杂度的外在症状，不是 DDD 概念的机械映射。不能简单得出“混乱就加 Entity、膨胀就加 Value Object、无序就加 Aggregate Root”。同一个问题往往需要多个设计层次共同处理。

## 3. 症状背后可能是什么根因？

以线索管理为例：

| 可观察症状 | 可能根因 | 需要收集的证据 |
|---|---|---|
| LeadService 同时处理线索、预警和通知 | 业务职责混杂，模块边界不清 | 方法职责、调用关系、变更记录 |
| 多个入口都能修改线索状态 | 状态规则没有明确所有者，写入口没有收敛 | Controller、Job、MQ Consumer、SQL 更新点 |
| 详情 DTO 大量字段为空 | 一个数据模型承载多个查询场景，API 契约过宽 | 字段使用方、调用方、字段非空率 |
| 分配后仍可能被其他人覆盖 | 并发控制不足，或业务规则未在写入时校验 | SQL 条件、版本字段、并发日志 |
| 预警状态和线索状态互相影响 | 两种生命周期被错误地放进同一个模型或事务 | 状态定义、规则负责人、状态迁移记录 |
| 改一个需求经常引发其他模块回归 | 依赖方向和协作契约不清晰 | 变更影响范围、回归缺陷、跨模块访问 |

注意：表中的根因都是候选解释，不是看到症状后就能直接下的结论。比如 DTO 空字段可能只需拆分查询 DTO，不必引入 DDD；并发覆盖可能通过条件更新和乐观锁解决；简单 CRUD 不需要为了架构完整而创建聚合。

## 4. 先区分事实、症状、假设和决策

- **事实**：可以通过代码、日志、SQL、工单或业务人员确认的内容。
- **症状**：系统表现出来的问题，例如重复分配、状态错误、接口返回大量空字段。
- **假设**：对症状背后原因的解释，需要证据验证。
- **决策**：基于证据和约束选择的方案。

示例：

~~~text
症状：
线索被分配后，另一个请求仍然可以覆盖负责人。

假设：
分配逻辑没有检查当前状态，或并发更新缺少版本保护。

证据：
检查所有写入口、SQL WHERE 条件、版本字段和并发日志。

决策：
统一分配用例中的业务校验，并使用条件更新/乐观锁处理竞争。
~~~

不要把假设写成结论，也不要先决定用 DDD 再倒推问题。

## 5. DDD 能治理什么，不能替代什么？

DDD 的价值不是增加类和分层，而是让业务职责、规则和模型边界变得明确。

| 治理目标 | 可能使用的设计工具 | 它主要解决什么 |
|---|---|---|
| 不同业务职责混在一起 | 统一语言、限界上下文、模块边界 | 明确模型语义、规则所有权和变化边界 |
| 业务身份与状态行为不清 | 实体 | 表达具有独立身份和生命周期的对象 |
| 数据只是零散字段，缺少业务含义 | 值对象 | 把有意义的值及其约束表达成模型 |
| 多个对象必须共同满足业务规则 | 聚合、聚合根 | 保护不变量，控制一致性边界和修改入口 |
| 用例编排与领域规则混杂 | Application Service、Domain Service | 分离流程协调和领域决策 |
| 跨模块直接依赖内部模型 | 上下文契约、ACL、领域/集成事件 | 控制协作关系和语义转换 |

这张表是分析导航，不是一对一的工具清单。比如 Service 膨胀可能源于上下文边界错误，也可能源于用例编排和领域规则混杂；不能只靠把字段封装成 Value Object 解决。

DDD 也不能替代数据库约束、并发控制、权限校验、可观测性和团队协作机制。领域模型提出规则，基础设施仍要保证这些规则在真实并发和故障环境中成立。

## 6. 判断是否值得引入领域模型

先问：

1. 同一业务对象是否有多个状态，且状态迁移存在明确前置条件？
2. 是否有多个入口执行相同业务动作，导致规则重复或不一致？
3. 业务规则是否散落在 Service、SQL、定时任务或消息消费者中？
4. 不同业务区域是否对同一个名词有不同定义？
5. 规则变化是否频繁影响多个模块，且错误成本较高？
6. 是否需要明确哪些对象必须在同一事务内保持一致？

如果答案大多是否，简单分层 CRUD、事务脚本或模块化 Service 可能更经济。如果答案大多是“是”，再进一步分析领域边界和不变量。

这不是打分公式，而是触发进一步调查的检查表。

## 7. 写出一份问题陈述

~~~text
业务目标：
谁需要完成什么业务结果？

当前流程：
现在由哪些角色、系统和入口完成？

主要症状：
发生了什么可观察的问题？

业务风险：
错误会造成什么损失或业务影响？

事实与证据：
有哪些代码、日志、SQL、工单或业务确认？

待验证假设：
我们认为根因是什么？还缺什么证据？

已知约束：
API 是否必须兼容？数据库能否改？是否允许停机？

本次范围：
明确要改什么、不改什么。

成功指标：
例如非法状态迁移次数、重复分配率、回归缺陷、
接口字段空值比例、需求变更影响范围。
指标阈值由项目基线和业务目标确定，不预设虚构数字。
~~~

## 8. 从一个小用例开始，不要一次性重写系统

建议先选择一个高频且规则明确的用例，例如“分配线索”。

- 纳入：分配资格校验、负责人记录、状态变化、并发冲突处理。
- 暂不纳入：客户画像、报表宽表、历史数据清洗、所有预警规则。
- 兼容：现有 API 字段和调用方行为。
- 风险控制：保留旧流程回滚开关，先测试和影子比对，再逐步灰度。

## 9. 最小交付物

本篇结束时，不应该先提交一个 Lead 类，而应该提交：

- 一份问题陈述。
- 一张当前业务流程图。
- 一份事实、症状、假设和证据清单。
- 一份改造范围声明。
- 一组可度量的成功指标。
- 一份“为什么考虑或暂不考虑 DDD”的决策记录。

**口诀：先看见混乱，再找到根因；先证明问题存在，再决定使用什么设计。**
