# DDD 实战：从业务问题到可演进代码

> 本系列不是 DDD 名词词典，而是一套可重复执行的业务分析与设计方法。读者将跟随一个线索管理系统的重构，从混乱需求出发，逐步得到业务规则、上下文边界、领域模型、代码结构、协作协议、迁移方案和验证证据。

## 学完应该能独立完成什么

给你一个陌生的复杂业务需求，你应该能够：

1. 把模糊需求拆成角色、命令、状态、规则、异常和业务结果。
2. 区分业务复杂度与技术复杂度，判断是否值得引入 DDD。
3. 根据业务能力和模型语义划分限界上下文，而不是按数据库表或微服务数量划分。
4. 从业务不变量推导实体、值对象、聚合根和事务边界。
5. 把用例编排、领域规则、持久化和外部系统适配放到合适的位置。
6. 根据上下文关系决定直接调用、ACL、领域/集成事件或最终一致性。
7. 通过测试、影子比对、灰度和指标证明重构没有破坏业务。

## 本系列的案例边界

主案例是一个**示例线索管理系统**，用于演示方法，不声称复刻任何公司的真实业务。已知问题设定：

- 线索详情对象包含大量与不同业务场景相关的字段，接口返回大量空值。
- 线索存在创建、分配、跟进、完结等生命周期。
- 客户预警有独立的触发原因、处理状态和生命周期。
- 多个入口可能修改线索状态，规则散落在 Controller、Service、SQL 和定时任务。
- 需要保留现有 API 和数据，不能一次性停机重写。

遇到业务事实不充分的地方，文章会标注“案例假设”，并说明需要向产品、运营或业务专家确认什么。不要把示例假设误当成通用业务事实。

## 统一教学结构

每篇文章必须完成同一闭环：

1. **问题现场**：业务发生了什么，谁遇到什么困难？
2. **证据收集**：哪些是事实，哪些只是猜测？
3. **推导过程**：从规则和约束推导设计，不先套术语。
4. **设计结果**：图、表、模型和 Java 代码。
5. **替代方案**：至少给出一种更简单或不同的方案。
6. **代价与边界**：新设计增加了什么成本，什么情况下不适用？
7. **验证方法**：如何用测试、指标或生产行为证明它有效？
8. **面试表达**：如何用 1-2 分钟讲清楚决策和取舍？

## 先记住这条主线

~~~text
业务问题
  -> 事实与规则
  -> 业务能力与边界
  -> 模型与不变量
  -> 用例与代码
  -> 跨边界协作
  -> 渐进迁移
  -> 生产验证
~~~

**不要从 Entity、Repository 或微服务开始。先理解业务，再决定是否需要这些设计。**

## 版本与证据纪律

- Java 示例使用 JDK 21；示例代码用于说明设计，不代表可直接复制进生产。
- Spring、ORM、消息中间件的具体行为不作为 DDD 概念的一部分；使用时必须注明版本并验证。
- DDD 没有强制的包名、类名或微服务拆分规范。
- 案例中未给定的规则会明确标注为假设。
- 性能、收益和改造效果必须用项目指标测量，不编造数字。
