# DDD 实战：以业务复杂度治理为主线

> 本系列不从 DDD 术语开始，而从一个业务系统逐渐变得混乱、膨胀、无序的过程开始。我们先识别复杂度从哪里来，再分析业务职责和规则，最后选择合适的领域建模工具。目标不是“把项目改成 DDD”，而是让业务规则有归属、模型有边界、变化可控制。

## 核心问题：系统为什么会失控？

随着业务增长，系统可能出现三类症状：

| 症状 | 常见表现 | 需要追问的根因 |
|---|---|---|
| 混乱 | 一个 Service 处理多个业务；同一规则在多个入口重复实现；一个名词在不同模块含义不同 | 业务职责是否混杂？模型语义是否冲突？规则归谁所有？ |
| 膨胀 | Service、DTO、条件分支和字段不断增加；修改一个需求牵动多个模块 | 是否缺少业务概念抽象？是否把不同场景塞进同一个模型？是否存在不必要的依赖？ |
| 无序 | 任意入口都能修改状态；规则执行顺序不明确；跨模块直接改表 | 谁拥有状态？哪些规则必须一起成立？谁有权改变业务对象？跨边界如何协作？ |

这三个词是观察复杂业务的入口，不是三个可以机械映射到 DDD 术语的分类。一个症状可能有多种根因，也可能需要多个层次共同治理。字段多不一定要值对象，Service 大不一定要聚合，出现并发问题也不意味着一定要引入完整 DDD。

## DDD 在这里扮演什么角色？

DDD 提供一套从业务理解到模型设计的方法，帮助我们：

- 通过**统一语言和限界上下文**明确业务职责、模型语义和规则所有权。
- 通过**实体和值对象**表达业务身份、生命周期和有意义的业务概念。
- 通过**聚合与聚合根**保护必须一致成立的业务不变量，明确状态修改入口和一致性边界。
- 通过**领域服务、应用服务和 Repository**组织领域行为、用例编排和持久化职责。
- 通过**上下文契约、ACL、领域事件和集成事件**管理跨边界协作。
- 通过**测试、渐进迁移和生产指标**验证设计是否真的降低了复杂度。

一句话：业务职责决定代码组织；领域边界保护业务规则；跨领域协作通过明确契约完成。

## 每个设计概念都必须回答三个问题

1. **它解决了什么实际问题？** 不能只给定义，要指出具体的业务症状和根因。
2. **不用它会付出什么代价？** 同时考虑更简单的替代方案。
3. **用了它又引入什么复杂度？** 说明维护、性能、协作、事务和学习成本。

## 案例边界与证据纪律

主案例是一个**示例线索管理系统**，用于演示分析方法，不声称复刻任何公司的真实业务。案例包含线索创建、分配、跟进、完结，以及具有独立生命周期的客户预警；详情对象存在多场景字段混杂、多个入口修改状态等待验证问题。

- 所有未被明确提供的业务规则均标注为“案例假设”，不能把假设写成事实。
- Java 示例使用 JDK 21；示例代码用于说明设计，不代表可直接复制进生产。
- DDD 没有强制的包名、类名、四层结构或微服务拆分规范。
- 不把限界上下文等同于微服务，不把聚合等同于数据库表关系。
- 性能收益、缺陷下降和重构效果必须通过项目指标验证，不编造数字。
- 简单 CRUD、报表查询和低复杂度模块可以采用更轻量的设计。
