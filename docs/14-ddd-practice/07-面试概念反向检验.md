# 07｜面试概念反向检验：用设计推导回答，而不是背术语

## 本篇目标

把前面的方法转成面试表达。回答时采用：结论 → 问题背景 → 设计推导 → 取舍 → 验证。不要把案例假设说成自己真实做过的项目经历。

## 1. DDD 是什么？解决什么问题？

**建议回答：**

DDD 不是一套固定分层或代码模板，而是一种围绕业务领域建立模型、语言和边界的设计方法。它更适合业务规则复杂、状态流转多、多个角色协作、模型语义容易冲突的系统。

我会先从业务流程和规则入手，识别哪些规则需要一致性保护，再划分上下文，最后决定是否需要聚合、领域服务、ACL 和事件。简单 CRUD 或报表查询不一定需要完整 DDD。

**追问：DDD 一定要拆微服务吗？**

不需要。限界上下文是模型边界，微服务是部署边界。可以先在模块化单体中建立上下文，只有独立部署、团队自治、容量或故障隔离等需求足够明确时，再评估服务拆分。

## 2. 如何识别聚合根？

**建议回答：**

我不会从数据库表关系或对象引用数量出发，而是先列业务不变量。哪些规则必须在一次业务操作中同步成立，哪些对象共同参与这些规则，就可能属于同一个聚合边界。聚合根是外部修改这个一致性边界的唯一入口。

例如线索分配，如果分配后负责人、分配时间和状态必须一致更新，它们由 Lead 聚合控制。跟进记录如果数量无限、独立查询且不需要和 Lead 状态同事务更新，就可能独立存储，通过 LeadId 关联。

**追问：聚合是不是越小越好？**

不是。聚合太大，会增加加载、锁竞争和并发冲突；聚合太小，会把必须同步成立的不变量拆到多个事务中。目标是最小化但完整地保护业务不变量。

## 3. Entity 和 Value Object 区别？

**建议回答：**

Entity 通过身份识别，同一个实体属性变化后仍是同一个对象；Value Object 没有独立身份，由属性值定义相等性，通常不可变。判断依据是业务语义，不是字段数量或是否有数据库主键。

## 4. Domain Service 和 Application Service 区别？

**建议回答：**

Application Service 表达用例，负责加载对象、协调依赖、控制事务和返回结果；Domain Service 表达领域规则，但该规则不自然归属于某个实体或值对象。不能因为一个类叫 Service 就判断它属于哪一层，要看它承担什么职责。

## 5. Repository 和 DAO 区别？

**建议回答：**

Repository 通常围绕聚合根提供集合式的加载和保存抽象，目的是保护领域模型的持久化边界；DAO 更偏向数据访问操作，可以面向表、SQL 或查询。两者在具体工程里可能有重叠，但不应只通过改名来宣称使用了 DDD。

## 6. ACL 和 Mapper 区别？

**建议回答：**

Mapper 主要解决结构转换，例如字段名、类型和嵌套对象；ACL 的目标是保护本地模型，当外部概念、状态和规则与本地语义不一致时，需要进行明确翻译。ACL 可能使用 Mapper，但不是所有 Mapper 都是 ACL。

## 7. 领域事件和集成事件区别？

**建议回答：**

领域事件表达某个上下文内部已经发生的领域事实；集成事件是对外发布的稳定契约。两者不必一一对应。跨上下文发布时要考虑契约版本、幂等、顺序和失败恢复。

## 8. 为什么需要 Outbox？

**建议回答：**

如果先提交数据库再发 MQ，可能出现 DB 成功但消息失败；先发 MQ 再提交 DB，又可能出现消息已发但事务回滚。Outbox 把业务变更和待发布事件写入同一个本地事务，再由发布器异步发送。它仍可能重复发布，所以消费者需要幂等；它解决的是本地事务与消息发布之间的可靠衔接，不是端到端 exactly-once。

## 9. 如何判断是否值得使用 DDD？

**建议回答：**

我会看业务规则复杂度、状态迁移数量、规则变化频率、多个入口是否共享规则、错误成本和团队协作边界。如果主要是简单数据录入和查询，事务脚本或普通分层更经济；如果核心业务规则频繁变化且散落多个模块，领域模型才有明确收益。

## 10. 如何把 DDD 引入旧系统？

**建议回答：**

我不会一次性重写。先选一个高价值用例，收集现有行为和调用方，补特征测试，再把新规则集中到应用用例和领域模型中。旧入口逐步委托新用例，做影子比对、灰度和回滚。只有当模块边界和数据所有权清楚后，才考虑独立部署。

## 11. 面试表达的完整模板

~~~text
结论：
我选择了什么设计。

背景：
当时的业务问题和约束是什么。

推导：
我依据哪些规则、不变量和边界得出这个方案。

取舍：
为什么不选其他方案，增加了什么成本。

验证：
通过哪些测试、指标或生产结果证明设计有效。
~~~

## 12. 不要这样回答

| 空泛回答 | 更好的回答方向 |
|---|---|
| 聚合就是一组对象 | 说明它保护哪些不变量和事务边界 |
| ACL 就是防止外部污染 | 说明具体语义差异和翻译规则 |
| DDD 就是四层架构 | 说明业务规则、用例编排和技术实现的依赖 |
| 事件可以解耦 | 说明事实归属、可靠发布、幂等和顺序 |
| Repository 就是 DAO | 说明聚合加载保存与查询模型的差异 |
| DDD 能提高可维护性 | 说明变更影响面、回归缺陷和规则集中程度如何验证 |

## 最后自测：不看文档，完成一次设计

给你一个需求：线索被分配后，系统需要创建跟进任务并通知销售。请独立回答：

1. 哪个上下文拥有线索状态？
2. 哪个上下文拥有任务生命周期？
3. 任务创建失败是否允许线索分配成功？
4. 如果允许异步，如何保证事件不丢？
5. 消费者重复收到事件怎么办？
6. 如何避免两个并发分配互相覆盖？
7. 如何测试和灰度上线？

如果这些问题能从业务约束推导出设计，而不是只说“用 DDD、MQ、Outbox”，才算真正理解。

**口诀：面试不是报出模式名称，而是证明你能从约束推导设计。**
