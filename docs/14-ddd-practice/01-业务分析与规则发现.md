# 01｜业务分析与规则发现：把混杂的职责还原成业务秩序

## 本篇目标

上一章识别了混乱、膨胀、无序的症状。本篇继续向下追问：业务到底由哪些角色、动作、状态和规则构成？哪些规则属于线索，哪些属于预警，哪些只是通知或查询？

没有这一步，后续的上下文和领域对象设计都只是在猜业务。

## 1. 从症状反推需要调查的业务问题

| 上一章的症状 | 本篇要回答的问题 |
|---|---|
| 一个 Service 处理多种业务 | 这些方法分别对应什么业务结果？由谁负责？ |
| 同一规则散落多个入口 | 业务规则是什么？哪些入口执行同一命令？ |
| 状态可以被任意修改 | 对象有哪些合法状态？谁能触发状态迁移？ |
| DTO 包含多个场景字段 | 不同场景真正需要什么信息？哪些概念被混在一起？ |
| 预警和线索互相影响 | 两者的生命周期、触发条件和规则负责人是否不同？ |

不要从类名、表名或现有包结构推导业务职责。先从真实业务流程和业务人员使用的语言开始。

## 2. 先问业务问题，不要先画类图

对业务专家逐项确认：

- 谁可以创建线索？重复线索如何处理？
- 谁可以分配？是否允许重新分配？
- 什么条件下可以开始跟进？
- 什么叫完结？谁能完结？能否重新打开？
- 跟进记录是否允许修改或删除？
- 客户预警由什么事实触发？预警是否会改变线索状态？
- 多人同时操作时，业务希望谁成功、谁收到冲突？
- 通知失败是否影响线索分配成功？

每个问题都要记录答案、来源、确认人和未决状态。业务人员说“正常情况下不会发生”不等于系统可以不处理异常。

## 3. 用业务流程还原一次分配

案例假设：只有待分配线索可以被分配；分配成功后状态变为待跟进；只有有权限的主管或规则引擎可以执行分配。

~~~text
分配请求
   |
   v
确认线索存在
   |
   v
确认操作者有分配权限
   |
   v
确认线索当前状态 = 待分配
   |
   v
确认目标销售有效
   |
   v
记录负责人和分配时间
   |
   v
状态变为待跟进
   |
   v
提交事务并返回结果
~~~

异常分支也要画出来：

- 线索不存在：返回 NotFound。
- 操作者无权限：返回 Forbidden。
- 线索状态已变化：返回 Conflict，而不是覆盖新状态。
- 目标销售无效：返回业务校验失败。
- 数据库版本冲突：重新读取并向调用方报告冲突，不能无条件重试覆盖。

## 4. 区分命令、查询和事件

| 类型 | 含义 | 示例 |
|---|---|---|
| Command | 请求系统执行动作，可能失败 | AssignLead、CompleteLead |
| Query | 读取数据，不改变业务状态 | GetLeadDetail |
| Domain Event | 领域内已经发生的事实 | LeadAssigned |
| Integration Event | 对外发布的业务事实契约 | LeadAssignmentCompleted |

命令用动词表达，事件用过去式表达。AssignLead 是意图，LeadAssigned 是成功后发生的事实。不能在命令刚进入系统时就发布“已分配”事件。

## 5. 建立状态机和规则清单

案例假设状态：

~~~text
NEW（新建）
  -> PENDING_ASSIGNMENT（待分配）
  -> FOLLOWING（跟进中）
  -> COMPLETED（已完结）
~~~

可能还存在 RECYCLED（已回收）等状态，但必须由真实业务确认。不要为了让图完整而添加没有业务依据的状态。

| 当前状态 | 命令 | 前置条件 | 下一状态 |
|---|---|---|---|
| NEW | SubmitLead | 必填信息完整 | PENDING_ASSIGNMENT |
| PENDING_ASSIGNMENT | AssignLead | 有权限、销售有效 | FOLLOWING |
| FOLLOWING | AddFollowUp | 当前负责人或授权角色 | FOLLOWING |
| FOLLOWING | CompleteLead | 完结原因符合规则 | COMPLETED |
| COMPLETED | ReopenLead | 有明确授权和原因 | 需业务确认 |

最后一行故意标为待确认。不要自行推断完结后一定可以重新打开。

规则不要只写“校验状态”，要写清输入、条件和结果：

~~~text
规则 R-ASSIGN-01：
Given 线索状态为 PENDING_ASSIGNMENT
And 操作者具有分配权限
And 目标销售账号有效
When 执行 AssignLead
Then 负责人更新为目标销售
And 状态变为 FOLLOWING
And 产生 LeadAssigned 领域事实

规则 R-ASSIGN-02：
Given 线索状态不是 PENDING_ASSIGNMENT
When 执行 AssignLead
Then 不修改负责人和状态
And 返回明确的状态冲突

规则 R-ASSIGN-03：
Given 两个请求基于同一个线索版本并发分配
When 两个请求同时提交
Then 至多一个请求成功
And 失败请求不得覆盖成功请求的结果
~~~

## 6. 识别业务职责，而不是按方法数量拆 Service

把现有能力按业务结果归类。下面是案例假设，不是固定拆分模板：

| 候选职责 | 业务行为 | 需要确认的规则所有者 |
|---|---|---|
| 线索管理 | 创建、分配、跟进、完结 | 线索业务负责人 |
| 客户预警 | 触发、处理、关闭 | 预警规则负责人 |
| 通知 | 选择渠道、发送、重试、记录结果 | 通知平台/业务团队 |
| 报表分析 | 汇总、统计、历史查询 | 数据分析负责人 |

注意：通知和报表不一定是核心领域模型；是否独立成上下文要看业务能力、语义和规则所有权。把 Service 拆成多个类不等于职责已经划清。

## 7. 事件风暴：发现流程、规则和边界争议

不依赖特定工具，白板上按时间从左到右排列：

- 橙色：领域事件（已经发生）。
- 蓝色：命令（希望发生）。
- 黄色：角色/策略（谁触发）。
- 粉色：疑问/规则冲突。

示例：

~~~text
销售主管
  -> AssignLead
  -> LeadAssigned
  -> 生成待跟进任务（是否属于同一上下文，待讨论）
  -> 通知销售（通知能力，不一定属于线索领域）
~~~

事件风暴不是把所有事件都做成 MQ 消息，而是帮助团队发现业务流程、规则和边界。

## 8. 从规则中找名词与动词

名词是候选概念，不是自动生成实体：

| 候选词 | 需要追问 | 可能结果 |
|---|---|---|
| 线索 | 是否有独立身份和生命周期？ | Entity / Aggregate |
| 负责人 | 是否有独立生命周期？ | UserId 值对象或用户上下文引用 |
| 跟进记录 | 是否允许修改？是否无限增长？ | 独立记录/子域模型 |
| 预警 | 是否有独立触发和处理流程？ | 可能是独立上下文 |
| 分配规则 | 是否有状态和身份？ | Policy / Domain Service |

动词是候选命令：创建、分配、跟进、完结、回收、重开。每个动词都要明确前置条件和副作用。

## 本篇交付物

- 一张业务流程图。
- 一张状态迁移表。
- 一份规则清单（每条有唯一编号）。
- 一份命令/查询/事件清单。
- 一份业务职责与规则所有者清单。
- 一份未决业务问题清单。

**口诀：先把职责和规则说清楚，再决定由哪个领域对象承担。**
