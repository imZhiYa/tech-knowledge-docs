## Level 1：Topic 的四重身份——完整抽象架构图

一句话认知墙：Topic 是队列吗？是目录吗？为什么 Kafka 和 RocketMQ 的 Topic 下挂的东西不一样？

### 前置知识关卡

- [ ] 知道 Topic 是归类标签，不是真实存储（mq-00 L2）
- [ ] 知道队列模型与日志模型的分野（mq-01）

### Why——一个名字，四种职责

**徒弟**：mq-00 说 Topic 是归类标签，mq-01 说真实存储是 Queue/Partition——那 Topic 在系统里到底算什么？

**老陈**：Topic 是 MQ 里被低估的概念，因为它一个名字扛了四种职责：

| 身份 | 含义 | 使用它的角色 |
| ---- | ---- | ---- |
| 命名空间 | 消息的归类标识（"ORDER_EVENT"） | 人（设计/运维/排查） |
| 路由单位 | 生产者的投递目标 | Producer |
| 订阅单位 | 消费者订阅的粒度 | Consumer Group |
| 资源边界 | 下面挂的 Queue/Partition 是并行度与存储边界 | Broker |

**四种身份绑定在一个名字上，是 MQ 设计的精妙处，也是事故温床**——改名动全家、分区数动全局、订阅关系藏在消费组里。

### What——Topic 的完整抽象架构图

```text
                     Topic（四合一：命名 / 路由 / 订阅 / 资源边界）
                                  │
        ┌─────────────┬───────────┼───────────────┬─────────────┐
        ▼             ▼           ▼               ▼             ▼
    Queue0/P0    Queue1/P1    Queue2/P2      Queue3/P3     （物理单元）
        │             │           │               │
        └──────┬──────┴─────┬─────┘               │
               ▼            ▼                     ▼
        Consumer Group A   Consumer Group B   Consumer Group C
        （库存组）          （通知组）           （审计组）
        组内分摊            组内分摊             组内分摊
        A1 A2 竞争          B1 独享              C1 独享
               │
               ▼
        组间广播：E 的三个组各拿一份（各自位点独立，mq-01 L3）
```

三家落地差异（同一个抽象，三种物理映射）：

```text
Kafka：    Topic → N 个 Partition（分区即日志文件；可增不可减，mq-06 详述）
RocketMQ： Topic → N 个 Queue（逻辑队列，真实存储是 CommitLog，可扩缩）
RabbitMQ： Topic Exchange 是路由规则（不是存储），
           存储单元是它绑定到的 Queue——"Topic"与"Queue"是两样东西
```

> 📌 最容易被误解的一点：**RabbitMQ 的"topic"只是路由规则，不是存储**。AMQP 世界里 `topic` 是一种 exchange 类型（按通配符匹配 routing key），真正的存储单元永远是 queue。所以"RabbitMQ 的 Topic"和"Kafka 的 Topic"不是一回事——前者是分拣规则，后者是分拣中心本身。这个混淆是 RabbitMQ → Kafka 迁移事故的常见源头。

### How——E 从 Topic 到消费者的分派推演

```text
① E 发送时指定 Topic = ORDER_EVENT（路由身份）
② E 按 Key 落到该 Topic 下的某个 Queue/Partition（资源边界）
③ 库存组订阅 Topic = ORDER_EVENT（订阅身份）
④ Broker 把 Topic 下的队列按分配策略分给组内消费者
⑤ 通知组同样订阅 → 各自独立位点 → 组间广播
⑥ 排查时按 Topic 检索消息（命名空间身份）
```

**徒弟**：④ 里"分配策略"是什么？队列和消费者不是固定的绑定关系吗？

**老陈**：不是——**消费者集合是动态的**（上线、下线、宕机、扩缩容），队列与消费者的绑定关系必须随动。这个"随动"就是分配策略（Kafka 的 Range/RoundRobin/Sticky/CooperativeSticky）与再平衡（rebalance）——mq-06 的完整战场。本文 L5 先把"静态"的两种模式（集群/广播）讲清楚，动态部分留给下一篇。

### Transfer——这个思想还能迁移到哪里

1. **一物多身份是抽象的成本**：一个名字扛多种职责（Topic、微服务的 service 名、DB 的库名）都面临"改名/变更的爆炸半径"问题。
2. **逻辑名与物理单元的映射是分布式的通用难题**：K8s 的 Service → Pod、Dubbo 的 service → 实例，同构。
3. **路由规则与存储单元分离**（RabbitMQ 的 topic exchange）是"分拣逻辑可独立演进"的典范。

本层留下的新账：订阅关系建立了，消息怎么到消费者手里？是消费者来取，还是 Broker 送上门？→ 逼出 Level 2。

### Level Ending

```
🔴 口诀：Topic 四合一：命名、路由、订阅、边界。
```

## Level 2：推拉之争——上门自取还是送货上门

一句话认知墙：推模式体验好、拉模式可靠——为什么 Kafka 和 RocketMQ 都选择了拉？

### 前置知识关卡

- [ ] 能画出 Topic 四重身份与物理映射（答不出回 Level 1）
- [ ] 知道"暂存"语义（mq-00 L2）

### Why——推拉的本质区别：谁掌握节奏

**老陈**：推与拉的本质区别就一条——**消息流动的节奏由谁控制**：

```text
推模式（Push）：
  Broker 有消息就投递给消费者
  节奏在 Broker → 消费者处理慢时被淹没 → 必须靠流控（prefetch）保命

拉模式（Pull）：
  消费者主动来取，取多少自己定
  节奏在消费者 → 天然流控，但消息不及时 → 必须靠长轮询补时效
```

| 维度 | 推（RabbitMQ basic.consume） | 拉（Kafka fetch / RocketMQ pull） |
| ---- | ---- | ---- |
| 流控 | Broker 端背压（prefetch count） | 天然流控（消费者按能力取） |
| 延迟 | 低（消息即到即推） | 略高（等下一轮拉取，长轮询弥补） |
| Broker 复杂度 | 高（要管理每个消费者的投递状态） | 低（只管响应 fetch） |
| 批量能力 | 弱（逐条推） | 强（一次拉一批） |
| 消费者挂掉 | Broker 要感知并重新投递 | 无感（下次不来取而已） |

### What——长轮询：拉模式如何补上时效

> 📌 本节比其他小节长：长轮询的机制细节多（朴素轮询的死锁 → 两个旋钮 → 完整时序 → 实现证据 → 隐藏成本，五步递进）。它支撑了本文后面所有"消费者为什么慢/怎么调参"的讨论，值得完整读；节奏上可以把它当作"一个独立小 Level"来读。

#### 第一步：朴素轮询的死锁——间隔怎么选都是错的

```text
轮询间隔小（比如 10ms）：
  延迟低（消息最多等 10ms）→ 但大部分轮询是空转
  → 空 RPC 请求与 CPU 白白消耗（无消息时 99% 轮询空跑）

轮询间隔大（比如 1s）：
  空转少 → 但消息到达后最坏要等 1s 才被取走
  → 延迟被轮询周期绑架

死锁：延迟与空转互为反比——朴素轮询只能二选一，
     "轮询得勤快"和"消息来得及时"无法兼得。
     长轮询就是来打破这个死锁的。
```

#### 第二步：长轮询的两个旋钮——把"立即返回"改成"有货才回"

拉取请求不再是一个简单的"给我消息"，而是携带两个条件的"有货再叫我"（Kafka 的 fetch.min.bytes / fetch.max.wait.ms 是这两个条件的协议字段）：

```text
拉取请求携带两个条件：
  条件一（批量）：凑够 min.bytes 字节才值得返回
  条件二（时效）：最多等 max.wait.ms，到期必须回话

Broker 收到 fetch 请求后的三种放行路径：
  ① 可返回数据已达 min.bytes → 立即返回（批量满足）
  ② 挂起期间新消息写入，数据量满足 min.bytes → 提前放行
     （服务端消息追加会触发对挂起请求的完成检查）
  ③ 挂起满 max.wait.ms 仍不足 min.bytes → 按当前数据返回
     （哪怕 0 条，消费者立刻发起下一轮）

= 消息到达时请求还挂在 Broker 上 → 到达即被取走
= 最坏等待上限 = max.wait.ms → "推的时效"是可控上限，不是玄学
```

> 三种放行路径的本质：**挂起（hold）+ 事件通知（arrival）+ 超时兜底（timeout）**。这是长轮询的全部机制，Kafka 与 RocketMQ 的实现都是这个骨架。

#### 第三步：E 在长轮询下的完整时序（含挂起期）

```text
T0  消费者 poll() 发出 fetch 请求
    fetch(offset=501, minBytes, maxWaitMs)      ← 两个旋钮随请求发出
    │
T1  Broker 检查当前分区数据量 < minBytes → 挂起该请求
    （不返回，连接保持占用，等待三件事之一）
    │
T2  挂起期间 E 被写入分区（CommitLog 追加）
    → 追加动作触发挂起请求检查 ★事件通知
    │
T3  数据量满足 minBytes → 立即完成请求 → 响应携带 E 返回
    │
T4  消费者收到 → 处理 E → 提交位点 → 下一轮 poll

    ── 若 T2 迟迟不来 ──
    T3' 挂起满 maxWaitMs → 返回空响应
    T4' 消费者收到空结果 → 立即发起下一轮（不是睡满一个周期再问）
```

#### 实现证据（区分 Specification / Implementation）

```text
Kafka 3.5.x 实现：DelayedFetch 机制（服务端延迟操作）
  - fetch 请求挂起在延迟操作管理（delayed fetch purgatory）
  - 分区日志追加（append）后触发对挂起 fetch 的完成检查
  - 超时由请求携带的 maxWait 驱动
  → 骨架：挂起 + 追加通知 + 超时兜底

RocketMQ 4.x/5.x 实现：Broker 端 PullRequestHoldService
  - 拉取请求挂起，消息写入 CommitLog 后由到达通知完成
  - 挂起时长上限受 Broker 配置控制（longPollingEnable 开关
    控制长轮询是否启用，具体默认值以官网为准）
  → 骨架：同上

注意：这里的"挂起多久"是产品实现细节（Implementation），
"有货才回、超时兜底"是长轮询的机制本质（Specification 无此概念，
它纯粹是工程手段）——不要把某个版本的默认值当规范。
```

#### 长轮询的隐藏成本——不是免费的

```text
① 挂起的请求占住服务端资源：
   每个空闲消费线程都挂着一个 fetch 请求
   → 空闲消费者越多，挂起请求条目越多（内存与连接额度成本）
   吞吐大但消息稀的场景，这个成本最明显（Kafka 的 delayed fetch
   purgatory 正是因此被反复调优）

② 最坏延迟 = 挂起窗口上限：
   消息在窗口将尽时到达 → 也要等到窗口结束才被返回
   → 长轮询给的"推的时效"是上限可控，不是即刻送达

③ 空转没有消失，只是换了形态：
   朴素轮询空转在"RPC 频率"，长轮询空转在"挂起占位"
   → 两者成本结构不同（前者是网络与 CPU 空耗，
     后者是连接与内存占位），但都不是零成本
```

> 📌 最容易被误解的一点：**RocketMQ 的 PushConsumer 是"假推真拉"**。它的内部是一个长轮询循环：客户端不断向 Broker 发起拉取请求，Broker 有新消息就立即返回——看起来像"消息被推过来"，本质是"拉取请求被快速响应"。**Kafka 的消费循环、RocketMQ 的 Push，全是拉**。真推的代表是 RabbitMQ 这类 AMQP 实现（Broker 主动投递 + prefetch 流控）；Pulsar 也是 Broker 推送，但用 Flow permit 授权机制做流控（消费者按 receiver queue 下发许可，Broker 凭许可推送）。记住这个，很多消费端行为（比如 RocketMQ Push 消费延迟为何有微小间隔）就都说得通了——那个"微小间隔"就是长轮询挂起窗口与空转占位的开销。

### How——E 在推拉两种模式下的到达路径

```text
拉模式（Kafka/RocketMQ）：
① 消费者 poll：fetch(offset=501, max.bytes, max.wait)  ← 时长/字节为示意值
② 没有新消息 → Broker 挂起请求
③ 200ms 后 E 写入分区 → Broker 立即响应：给你 E（长轮询放行路径②）
④ 消费者处理 E → 提交位点 → 下一轮 poll

推模式（RabbitMQ）：
① 消费者 basic.consume 订阅队列（prefetch=10）
② E 入队 → Broker 直接推送给消费者通道
③ 消费者 ack → Broker 投递下一条（受 prefetch 流控）
④ 消费者处理慢 → 未 ack 数达到 prefetch → Broker 停止推送 ★背压点
```

**徒弟**：推模式延迟低，为什么 Kafka 还是选了拉？

**老陈**：因为 Kafka 的出生场景（日志管道）里，消费者是批处理系统，处理速度远慢于写入速度——**让消费者按自己的节奏批量取，比 Broker 逐条推送更高效**。推模式的"低延迟"优势在批处理消费者面前毫无意义，反而 Broker 要维护海量消费者的投递状态。**推拉没有绝对优劣，只有场景适配：逐条低延迟场景推占优，批量高吞吐场景拉占优**。至于 RabbitMQ 的推为什么没被"淹没"问题拖垮——靠 prefetch 流控，这个参数在 L6 展开。

### Transfer——这个思想还能迁移到哪里

1. **节奏控制在谁手里，谁就掌握背压**：推拉之争 = 生产者驱动 vs 消费者驱动——HTTP 轮询 vs WebSocket 推送、事件驱动架构的同步/异步选择，同构。
2. **长轮询是"两全"的通用手法**：comet 技术、K8s watch、etcd watch 都是"挂起等待 + 有事件即返回"。
3. **假推真拉的实现透明性**：很多"推送"SDK 底层都是拉取——判断真实数据流要穿透 SDK 表象。

本层留下的新账：协议层的推拉讲完了。但"拉取"在客户端进程内部到底由谁执行？一个消费者进程里有几个线程在干活？"处理慢"在各自线程模型下会闯什么祸？→ 逼出 Level 3（消费者客户端内部：线程模型与拉取流水线）。

### Level Ending

```
🔴 口诀：推怕撑死，拉怕迟到，长轮询两全。
```

<a id="level-3"></a>

## Level 3：消费者客户端内部——线程模型与拉取流水线

一句话认知墙：poll() 背后是谁在干活？一个消费者进程里到底有几个线程？

### 前置知识关卡

- [ ] 能说出推拉的本质区别与长轮询三种放行路径（答不出回 Level 2）
- [ ] 知道"假推真拉"（Level 2 📌）
- [ ] 知道分区内有序与位点推进的机制（mq-01 L3/L4）

### Why——协议层之下还有实现层

**徒弟**：推拉和长轮询讲完了——"拉取"不就是发个 fetch 请求吗？还有什么可讲的？

**老陈**：L2 讲的是**协议层**（消费者和 Broker 之间怎么说话）；本层讲**实现层**（消费者进程内部谁在干活）。两个问题是不同的：协议回答了"消息怎么到客户端"，实现层回答"客户端进程里哪个线程执行拉取、哪个线程执行处理、处理慢了对线程模型意味着什么"。**三家的线程模型完全不同，这是消费端调优与事故定位的知识基础**——"处理慢"在 Kafka 里是"poll 间隔变长"，在 RocketMQ 里是"消费线程池占满"，在 RabbitMQ 里是"未 ack 堆积"，机制完全不同，排查路径完全不同。

### What——Kafka：单线程 poll 驱动一切

```text
KafkaConsumer 线程模型（非线程安全）：
  用户线程（业务代码所在）：
    单线程循环 poll()
    → poll() 内部完成网络 IO（fetch 请求发送、响应接收、位点提交）
    → 返回一批 Records → 业务处理
    → 再 poll() …… 串行循环

  后台线程：
    心跳线程（heartbeat）：独立于 poll 循环，定期发心跳
    → 防会话超时（mq-06 的"活着吗"尺子）
    → 但心跳线程只发心跳，不执行任何业务

关键约束：处理与拉取串行
  处理时长直接变成 poll 间隔
  → 处理太慢 → poll 间隔超过 max.poll.interval（"干活吗"尺子）
  → 被踢出组 → rebalance（mq-06 风暴源头之一）
  ★"处理慢"在 Kafka 线程模型里 = 被踢风险
```

**徒弟**：处理慢就得异步化？那异步处理怎么提交位点？

**老陈**：异步化 = 多线程扩展，三种模式各付各的账：

```text
模式一：单消费者 + 工作线程池（pull 线程分发任务，自己继续 poll）
  代价：位点提交要自己管——工作线程完成一个提交一个
  陷阱：并行处理完成顺序 ≠ 分区顺序
  → 后完成的先提交 → 先完成的提交被覆盖 → 重复消费（mq-04 重复来源③ 的变体）
  ★异步化的账：处理序与位点序的错乱

模式二：多消费者实例（partition 级并行）
  代价：并行度上限 = 分区数（mq-06 L4）
  → 这是"正规军"：每个消费者串行处理自己的分区

模式三：业务内多线程 + 分区内串行保证
  代价：业务实现复杂（按 Key 分片串行，mq-04 L4 已讲）
```

### What——RocketMQ：拉取-处理流水线（假推真拉的内部结构）

```text
RocketMQ PushConsumer 内部三组线程（拉与处理解耦）：

① PullMessageService（拉取线程，1 个）
   为每个队列维护一个拉取请求（pullRequest）
   长轮询拉取 → 返回的消息放入该队列的 ProcessQueue
   → 队列空时挂起（长轮询，L2 已讲）

② ProcessQueue（预取缓冲，每队列一个）
   拉取与消费之间的"蓄水池"
   → 消费慢时蓄水；水位超限（consumeConcurrentlyMaxSpan）
   → 暂停该队列的拉取 ★背压闭环
   （拉取速度被消费速度反向压制，不会无限预取）

③ ConsumeMessageService（消费线程池）
   线程池（consumeThreadMin/Max）从 ProcessQueue 取消息
   → 执行消费回调 → 成功更新位点 / 失败重试（mq-07）

对比 Kafka：
  Kafka = poll 单线程"拉取-处理串行"
  RocketMQ = 拉取线程与消费线程池"流水线并行"
  ★两种哲学：Kafka 用"串行"换位点顺序简单；
    RocketMQ 用"流水线"换吞吐，代价是 ProcessQueue
    水位与重复窗口的管理（mq-04 的重复来源在这里）
```

> 📌 最容易被误解的一点：**RocketMQ 的"消费线程池"不是越多越好**。线程池解决"单条处理逻辑里的等待"（如 IO 等待），但**并行度不等于线程数**：并发消费模式下，同一队列的消息会被拆成多个消费任务交给线程池并行处理（单队列在途上限受 consumeConcurrentlyMaxSpan 控制），所以"并行度 = 队列数"只对顺序消费成立（一条队列同一时刻只允许一个消费请求）；线程池 100 但队列只有 4 时，并发消费仍有排队空间，顺序消费则大量空转——**线程池大小要与队列数、消费模式、单条处理时长匹配**（mq-04 的 Key 级串行约束）。

### What——RabbitMQ 与 Pulsar 一句话对比

```text
RabbitMQ：每个 channel 一个消费回调线程（Java 客户端早期实现；4.x 起共享 ConsumerWorkService 线程池，具体以所用客户端版本为准）
  Broker 推消息 → 回调线程执行
  处理慢 → 未 ack 堆积 → prefetch 满 → Broker 停止投递（L2 背压点）
  ★回调线程阻塞（同步调下游）= 整个 channel 停滞

Pulsar：receiver queue（预取队列）+ 消息处理线程
  消费者按 receiver queue 大小预取
  处理慢 → 队列蓄满 → 停止预取（与 RocketMQ ProcessQueue 同思想）
```

### How——线程模型导致的四个事故

```text
事故一（Kafka 串行的代价）：
  消费回调里同步调下游慢接口（500ms/条）
  → poll 间隔飙升 → 超 max.poll.interval → 被踢 → rebalance 风暴
  ★处理慢直接换算成被踢风险（mq-06 三环事故链的起点）

事故二（Kafka 异步化的代价）：
  拉取线程分发任务给工作线程池
  → 工作线程完成顺序乱 → 位点提交乱序 → 重复消费
  ★异步化的账：并发处理与位点顺序冲突（mq-04 幂等兜底）

事故三（RocketMQ 池满的代价）：
  消费线程池全部阻塞在下游慢调用
  → ProcessQueue 蓄水超限 → 暂停拉取
  → pullRequest 堆积 → 内存压力与消费停滞
  ★线程池与下游能力必须匹配，否则池满即停滞

事故四（RabbitMQ 回调阻塞的代价）：
  回调线程同步调下游 → channel 停滞
  → 未 ack 堆积 → prefetch 满 → Broker 背压
  ★一个慢回调堵死一个 channel 的全部消息
```

**徒弟**：四个事故看起来都是"处理慢"的不同死法？

**老陈**：对——**线程模型的差异决定了"处理慢"的死亡形态**：Kafka 是被踢（协调层惩罚）、RocketMQ 是池满停滞（流水线堵死）、RabbitMQ 是 channel 背压（投递停止）。**排查"消费慢"事故，第一步就是确认线程模型，再按各自的死亡形态找原因**——用 Kafka 的排查思路查 RocketMQ 的池满问题，会绕一大圈。

### Transfer——这个思想还能迁移到哪里

1. **先问"谁的线程在干活"**：DB 驱动（连接池线程）、HTTP 客户端（事件循环）、消息客户端（poll/回调/池）——任何并发客户端都先画线程分工图。
2. **拉取-处理流水线 + 水位背压**：ProcessQueue/ProcessQueue 水位反压思想 = 生产者-消费者模式的水位控制，异步处理管道通用手法。
3. **串行换简单，并行换吞吐**：Kafka 串行（位点序简单）vs RocketMQ 流水线（吞吐高、管理复杂）——并发结构的第一性权衡。

本层留下的新账：单个消费者的内部结构讲完了。但 E 有多个下游（库存/通知/审计），每个下游还可能要横向扩容——一群消费者怎么组织起来共享一份 E？→ 逼出 Level 4（消费组统一模型）。

### Level Ending

```
🔴 口诀：拉取一个线程，处理一套池子，慢是事故源头。
```

## Level 4：消费组统一模型——组内分摊与组间广播

一句话认知墙：消费组（Consumer Group）到底是什么？为什么说它是 MQ 消费模型的灵魂？

### 前置知识关卡

- [ ] 能说出推拉各自的死穴与长轮询原理（答不出回 Level 2）
- [ ] 知道"消费组之间广播、组内分摊"（mq-00 L2）

### Why——为什么需要"组"这个抽象

**徒弟**：一个服务订阅一个 Topic，多个实例挂上去消费——这不就够了吗？"组"是什么多余概念？

**老陈**：够不够，看两个经典场景。**场景一（扩容）**：库存服务部署 3 个实例，希望 E 被 3 个实例**分摊**处理（每条 E 只被扣一次库存）——这需要"它们是一个整体"的概念，否则 3 个实例各扣一遍。**场景二（多下游）**：库存、通知、审计都要 E，希望**每家各拿一份**——这又需要"它们是不同整体"的概念。**"组"就是这两个"整体"的边界**：组内是分摊关系，组间是广播关系。

### What——八个字的完整消费拓扑

```text
                        Topic: ORDER_EVENT
                                 │
        ┌────────────────────────┼────────────────────┐
        ▼                        ▼                    ▼
   消费组 A（库存）          消费组 B（通知）      消费组 C（审计）
   ┌─────┬─────┐            ┌──────────┐          ┌──────────┐
   │ A1  │ A2  │            │ B1       │          │ C1       │
   └─────┴─────┘            └──────────┘          └──────────┘
   组内分摊：               组内分摊：              组内分摊：
   A1 管 Q0/Q1              B1 管全部队列           C1 管全部队列
   A2 管 Q2/Q3             （单实例）              （单实例）

   组间广播：E 的每一条，A/B/C 各拿一份（各自独立位点）
```

> 📌 最容易被误解的一点：**"组间广播"不是消息被复制三份**——Kafka/RocketMQ 里消息存一份，三个组各自维护独立位点（mq-01 L3 已讲）。广播的代价是"每个组都要全量消费一遍"，收益是"下游互不干扰"。**下游 A 消费慢，不会拖累下游 B**——这是消费组隔离性的核心价值。

### How——E 在消费组模型下的完整旅程

```text
① E 写入 Q1（Key 路由）
② 分配表：Q1 当前绑定给组 A 的消费者 A1
③ A1 拉取 E → 扣库存 → 提交组 A 的位点（Q1 → 502）
④ 组 B 的位点独立：B1 拉取 E → 发通知 → 提交组 B 的位点
⑤ 组 A 扩容：A3 上线 → 重新分配 → A3 接管 Q2/Q3 中的一部分（mq-06 展开）
⑥ 组 C（审计）落后 100 条 → 独立追赶，不影响 A/B
```

**徒弟**：那 RabbitMQ 怎么实现"消费组"？它没有这个概念啊。

**老陈**：问得好——RabbitMQ 用**结构换概念**：组内分摊 = 多个消费者绑定同一个队列（竞争消费）；组间广播 = exchange 把消息拷进多个队列，每组一个队列。**"消费组"是抽象的，产品要么内置它（Kafka/RocketMQ），要么用路由结构拼出它（RabbitMQ）**。拼出来的代价是 mq-01 讲过的存储放大（N 下游 N 份拷贝），而且"组的动态性"（加消费者）在 RabbitMQ 里天然无需 rebalance——竞争者多一个少一个，队列照发。这也是为什么 RabbitMQ 没有"再平衡事故"这个概念。

### Transfer——这个思想还能迁移到哪里

1. **分摊与广播是所有发布-订阅系统的两轴**：K8s 的 Service（分摊）与事件通知（广播）、负载均衡（分摊）与多播（广播）——先定位轴，再设计方案。
2. **组是隔离性的单元**：消费组的位点隔离 = 故障隔离——慢消费者不拖累快消费者。
3. **抽象要么内置要么拼装**：没有消费组的 RabbitMQ 用路由拼——评估产品时问"这个抽象是内置还是拼装"，拼装的代价往往在别处。

本层留下的新账：组是抽象，落地有两种形态——集群模式（组内分摊到底）和广播模式（组内全员全量）。这两种形态的位点存哪、队列怎么分、行为差多少？→ 逼出 Level 5。

### Level Ending

```
🔴 口诀：组内分摊，组间广播，位点隔离。
```

<a id="level-5"></a>

## Level 5：集群模式 vs 广播模式——细致架构对比

一句话认知墙：RocketMQ 的"集群模式"和"广播模式"到底差在哪？Kafka 的消费组又是哪种？

### 前置知识关卡

- [ ] 能用"组内分摊/组间广播"解释消费拓扑（答不出回 Level 4）
- [ ] 知道位点 = 消费进度书签（mq-01/mq-03）

### Why——同一组消费，两种组织方式

**老陈**：消费组内部还有两种组织方式，RocketMQ 把它们显式做成了两个模式，Kafka 只有一种（等价于集群模式），RabbitMQ 用结构表达：

| 模式 | 组内语义 | 位点存储 | 典型场景 |
| ---- | ---- | ---- | ---- |
| 集群模式（Clustering） | 队列在组内**分摊**：一个队列同一时刻只被一个消费者消费 | Broker 端（云端共享） | 扣库存：一条 E 只处理一次，水平扩容 |
| 广播模式（Broadcasting） | 每个消费者**全量**消费所有队列 | 消费者本地（各自记录） | 配置下发、缓存刷新：每个实例都要全量 |

### What——两种模式的细致架构

```text
集群模式（Kafka 消费组 / RocketMQ Clustering）：
  Topic(4 队列) ──→ 组内 2 消费者
  Q0 Q1 → 消费者 A1
  Q2 Q3 → 消费者 A2
  位点：Broker 端（Kafka 存 __consumer_offsets / RocketMQ 存 Broker）
  特征：
    ✓ 水平扩容（消费者 ≤ 队列数）
    ✓ 进度云端共享，重启续读
    ✗ 消费者数超过队列数 → 多余消费者空转

广播模式（RocketMQ Broadcasting）：
  Topic(4 队列) ──→ 每个消费者全量消费 4 个队列
  消费者 A1：Q0~Q3 全读（位点存 A1 本地文件）
  消费者 A2：Q0~Q3 全读（位点存 A2 本地文件）
  特征：
    ✓ 每个实例拿到全量消息
    ✓ 位点本地：消费者升级/换机 → 本地位点丢失 → 需从头消费或指定起点
    ✗ 无法组内扩容（加实例 = 再全量读一遍）
```

> 📌 最容易被误解的一点：**广播模式的位点在本地，是它的最大软肋**。RocketMQ 广播模式的消费进度保存在消费者进程的本地文件里——容器化时代这个设计很危险：实例重建、镜像更新，本地文件随容器一起消失，位点回到起点，**要么从头重读（重复轰炸下游），要么从最新开始（丢历史）**。用广播模式前，必须想清楚"消费者重启后从哪续读"。

### How——E 在两种模式下的三条命运

```text
命运一：集群模式 + 3 实例库存组
  E 进 Q1 → 分配表指向 A2 → A2 处理 → 位点存云端
  其他实例不碰这条 E → 恰好处理一次（配幂等）

命运二：广播模式 + 2 实例缓存刷新组（支线：非 E 因果链）
  同一份配置变更消息，实例 1、实例 2 各读一遍 → 各自刷新本地缓存
  位点各存本地 → 互不影响

命运三：集群模式 + 消费者数 > 队列数（误用）
  4 个消费者，4 个队列 → 刚好
  第 5 个消费者上线 → 分配不到队列 → 空转
  "加机器没用"的经典原因（神话⑦ 的机制根源，mq-06 展开）
```

**徒弟**：Kafka 怎么没有广播模式？配置下发场景在 Kafka 里怎么做？

**老陈**：Kafka 的答案是为每个下游建**独立消费组**——配置下发就建一个"config-refresh"组，组内单实例就是广播效果。**广播模式是"每个消费者都是独立组"的快捷方式**，RocketMQ 把它做成显式开关，Kafka 让你用组结构自己表达。本质都是 mq-01 的"各自位点"思想。

### Transfer——这个思想还能迁移到哪里

1. **位点存哪 = 状态归谁**：云端位点（可恢复、可共享）与本地位点（自包含、易丢失）的权衡，是分布式状态的通用选择题。
2. **模式开关 vs 结构表达**：同一个能力，RocketMQ 用参数（mode），Kafka 用结构（独立组）——评估设计时问"这个能力是开关给的还是结构给的"，结构的通常更正交。
3. **空转即信号**：消费者数 > 分区数 → 多余实例空转——任何"资源上限"型系统都有这个信号，要监控"活跃/闲置比"。

本层留下的新账：两种模式的静态架构清楚了。但消费者集合是动态的——实例上下线、心跳超时、扩容缩容，队列与消费者的绑定关系要重新分配。**重新分配的那一刻，消费会发生什么？** → 逼出 mq-06（再平衡与扩容）。

### Level Ending

```
🔴 口诀：集群位点存云端，广播位点留本机。
```

<a id="level-6"></a>

## Level 6：生产决策与参数配置

一句话认知墙：推拉、集群/广播、消费组——这些选项到了架构评审桌上怎么选？

### 前置知识关卡

- [ ] 能对比集群/广播的位点存储与扩容行为（答不出回 Level 5）
- [ ] 知道"假推真拉"（Level 2）

### Why——消费模型的决策是连锁反应

**老陈**：消费模型的选择不是单个开关，而是一串连锁：**订阅形态（组）→ 组内组织（集群/广播）→ 取件方式（推拉）→ 参数落地**。前三步定了，第四步的参数才有意义。

### What——决策清单

```text
决策一：要不要消费组？
  多下游各拿一份 → 消费组（组间广播）
  单下游单实例 → 可以不建组（Kafka 用 subscribe() 必须组；用 assign()
  手动指定分区可无 group.id——代价是丢自动重平衡与位点托管）

决策二：集群模式还是广播模式？
  需要水平扩容、进度共享 → 集群模式（绝大多数业务）
  每个实例都要全量 → 广播模式（配置下发/缓存刷新，注意本地位点软肋）

决策三：推还是拉？
  逐条低延迟、消费快 → 推（RabbitMQ 类）
  批量高吞吐、消费慢、要背压 → 拉（Kafka/RocketMQ）

决策四：新组从哪开始消费？
  Kafka：auto.offset.reset（earliest/latest）
  RocketMQ：ConsumeFromWhere（CONSUME_FROM_LAST_OFFSET / FIRST_OFFSET / TIMESTAMP）
  新组上线配 earliest → 从历史全量消费（可能重复轰炸下游）
  配 latest → 只吃新消息（历史数据缺口）
```

> 📌 最容易被误解的一点：**"从头消费"不是免费的补数手段**。新组配 earliest 会从保留期最早的消息开始全量重放——如果下游没有幂等，这就是一场重复轰炸。**补数场景的正确姿势：先问"下游幂等吗"，再决定 earliest 还是 latest**。

### How——E 的消费组从零上线的完整配置

```text
① 库存组全新上线，Topic 已有 3 天历史消息
② 决策：库存组只需实时扣减，历史订单无需补处理 → ConsumeFromWhere = LAST_OFFSET
③ 组内 3 实例 + 4 队列 → 集群模式
④ 拉模式：fetch 批量 = 业务单批处理能力（避免单批过大超时）
⑤ 上线验证：lag 曲线、重复率、处理延迟
⑥ 若配错成 FIRST_OFFSET → 3 天历史全量重放 → 重复扣减告警（幂等表救场）
```

**徒弟**：等等，如果扣库存历史真的需要补数呢（比如停机窗口期间的消息）？

**老陈**：停机窗口补数不是"新组从 earliest 消费"能解决的——保留期内最早的位点往往远超停机窗口。正解是按**时间戳指定位点**（Kafka 的 offsetsForTimes / RocketMQ 的 CONSUME_FROM_TIMESTAMP）从窗口起点开始消费。**补数是精确制导，不是全量扫射**。

### 📋 关键参数配置与注意事项

> 默认值随版本变化，以官方文档为准（写作基线 Kafka 3.5.x / RocketMQ 5.x / RabbitMQ 3.13.x），本文只讲参数控制的机制与配错的事故。

| 参数 | 控制的机制（指向本文 Level） | 配错的线上事故 |
| ---- | ---- | ---- |
| fetch.max.wait.ms（Kafka 长轮询窗口） | 空轮询挂起时长：延迟 vs 空转（L2） | 配太小 → 频繁空轮询 CPU 空转；配太大 → 单条消息端到端延迟上升 |
| fetch.min.bytes（Kafka 最小返回量） | 攒批阈值：延迟 vs 吞吐（L2） | 配太大 → 消息量小时迟迟不返回，延迟被拉长 |
| max.poll.records（Kafka 单次拉取条数） | 单批粒度：处理时长与提交粒度（L2/L3） | 配太大 → 单批处理超过 max.poll.interval（mq-06 详述）→ 被踢出组触发 rebalance |
| auto.offset.reset（Kafka 新组起点） | 新组/位点失效时的消费起点（L6） | 配 earliest → 新组上线全量重放历史，下游无幂等则重复轰炸 |
| ConsumeFromWhere（RocketMQ 新组起点） | 同上（L6） | FIRST_OFFSET 误用 → 全量重放；LAST_OFFSET 误用 → 停机窗口数据缺口 |
| pullBatchSize（RocketMQ 拉取批量） | 拉模式批量度（L2） | 配太大 → 单批处理超时、重复概率上升；配太小 → 拉取频率高、吞吐不足 |
| messageModel（RocketMQ 集群/广播） | 组内组织模式（L5） | 广播模式配到需要分摊的业务 → 每条消息被所有实例重复处理 |
| prefetch（RabbitMQ 未 ack 上限） | 推模式流控（L2） | 配太大 → 消费者被消息淹没、单实例积压；配太小 → 吞吐上不去（逐条 ack） |

<a id="pitfalls"></a>

# ⚠️ 坑与细节

## 坑 1：把 RabbitMQ 的 topic exchange 当成 Kafka 的 Topic

错误理解：都叫 topic，是同一个东西。

原因：RabbitMQ 的 topic 是路由规则（通配符匹配），Kafka 的 Topic 是存储与订阅的容器。

比喻后果：把"分拣规则"当成"分拣中心"，迁移时按名对号入座。

线上现象：RabbitMQ → Kafka 迁移时按 topic 名 1:1 建 Kafka Topic，路由逻辑丢失。

修正：迁移前先画消息流图，按"消息流 + 订阅关系"重建，不按名字搬。

## 坑 2：以为 RocketMQ PushConsumer 是真推

错误理解：Push 模式 = Broker 主动推送，消费端无控制权。

原因：不知道"假推真拉"——长轮询拉取的封装。

比喻后果：以为驿站送货上门，实际是收件人不断跑驿站。

线上现象：按"推"的直觉排查消费延迟（怪 Broker 不推），实际是拉取参数配错。

修正：理解长轮询机制，调 fetch 相关参数而非幻想 Broker 推送。

## 坑 3：广播模式用于需要分摊的业务

错误理解：广播模式更"保险"，每个实例都处理一遍不会漏。

原因：混淆"全量可见"与"恰好一次"——广播模式每条消息被每个实例处理。

比喻后果：同一份快递给每个收件人都签收一次，都付款一次。

线上现象：扣库存服务配广播模式，3 实例扣 3 次库存。

修正：分摊业务必须集群模式；广播模式只用于"每实例都要全量"的场景。

## 坑 4：广播模式 + 容器化，位点随容器消失

错误理解：消费进度当然存在 Broker 上，重启自动续读。

原因：广播模式位点在本地文件，容器重建即丢失。

比喻后果：签收簿放在收件人家里，搬家就没了。

线上现象：实例发布后从头重读历史消息，下游被重复轰炸。

修正：广播模式场景设计"重启从哪续读"方案；或改用独立消费组替代广播模式。

## 坑 5：新消费组上线配 earliest 全量重放

错误理解：从头消费 = 完整补数，稳妥。

原因：earliest 从保留期最早开始，远超补数窗口，且下游未必幂等。

比喻后果：为了补三天账，把三个月账本全翻出来重算。

线上现象：新组上线，下游被打爆、重复处理风暴。

修正：实时链路用 latest；补数用时间戳指定位点 + 下游幂等前置检查。

## 坑 6：prefetch 配太大，消费者被淹没

错误理解：prefetch 大 = 吞吐高。

原因：推模式下 prefetch 是"未 ack 上限"——Broker 一次性投递大量消息，处理慢的消费者被堆死。

比喻后果：驿站不限量送货，收件人门口堆成山。

线上现象：单消费者堆积大量未 ack 消息，重启后全部重新投递，重复风暴。

修正：prefetch = 单实例处理能力 × 单条处理时间，实测定值。

## 坑 7：消费者数超过队列数还期望提速

错误理解：多开实例总能更快（神话⑦ 的消费侧机制）。

原因：队列数是并发上限，多余消费者分配不到队列，空转。

比喻后果：取件口只有 4 个，来了 8 个取件员。

线上现象：扩容无效、CPU 空转，lag 不降。

修正：先算队列数（峰值并发度），再定实例数；监控"活跃消费者/总消费者"比。

## 坑 8：长轮询参数把延迟拉爆

错误理解：fetch.max.wait.ms 调大能提高吞吐。

原因：长轮询窗口是"空转的等待上限"——单条消息到来时可能等满窗口才被响应（取决于实现与批量参数联动）。

比喻后果：取件员蹲在驿站门口发呆，有件也不马上拿。

线上现象：消息量低峰时端到端延迟异常升高，排查发现是批量参数与等待窗口配大。

修正：低延迟场景调小等待窗口与最小批量；批量与延迟按业务权衡实测。

# 📚 版本勘误表

| 错误说法 | 准确说法 |
| ---- | ---- |
| "RocketMQ PushConsumer 是 Broker 推送" | 假推真拉：长轮询拉取的封装；真推只有 RabbitMQ 类 AMQP 实现 |
| "RabbitMQ 的 topic 和 Kafka 的 Topic 是一回事" | RabbitMQ 的 topic 是 exchange 路由规则，存储单元是 queue |
| "广播模式更保险，每条消息都有人处理" | 广播模式每条消息被**每个**实例处理；需要分摊的业务用它是资损 |
| "消费进度都存 Broker，重启自动续读" | 广播模式位点在本地文件；集群模式才存 Broker 端 |
| "推模式比拉模式先进" | 推拉无优劣：推适合逐条低延迟，拉适合批量高吞吐与背压 |
| "新组上线从 earliest 消费是稳妥补数" | earliest 是保留期全量重放；补数用时间戳指定位点 |
| "prefetch 调大 = 吞吐提高" | prefetch 是未 ack 上限；调大只会淹没慢消费者 |
| "消费组就是一批消费者而已" | 消费组是分摊/广播的边界：组内分摊、组间广播、位点隔离 |
| 坦白：我以前也讲错过"PushConsumer 是推模式" | 穿透 SDK 才看到长轮询循环；"推送"是接口语义，不是数据流语义 |
| 坦白：我以前也讲错过"Kafka 也能配广播模式" | Kafka 用独立消费组表达广播语义，没有显式开关——能力相同，表达方式不同 |

# 🏆 生产决策卡

## Decision Card 1：库存组消费模型配置

### 场景

库存组 3 实例扣库存，需要水平扩容、进度共享、恰好一次。

### 判断

集群模式 + 拉式消费 + 新组从 latest 起 + 幂等拦截。

### Mechanism → Decision

| 机制 | 工程决策 |
| -- | ---- |
| 组内组织 | 集群模式（分摊 + 云端位点） |
| 取件方式 | 拉（批量 + 长轮询，背压可控） |
| 消费起点 | latest（实时链路，历史不补） |
| 重复防护 | 幂等键 orderId+eventType（mq-04） |
| 线程模型 | 单 poll 串行处理（保位点序）；处理慢优先提队列数，异步化必须自管位点提交顺序 |

### 禁止决策

- 广播模式用于扣库存（每实例全量处理 = 资损）
- 新组 earliest 全量重放（下游重复轰炸）

### 验收指标

- 3 实例分摊验证：单条 E 仅被一个实例处理
- 重启演练：位点续读，无重复处理
- lag 曲线与处理延迟 p99 达标

---

## Decision Card 2：配置下发广播场景（支线）

### 场景

配置中心变更消息要推给所有应用实例刷新本地缓存（**支线：非 E 因果链**）。

### 判断

RocketMQ 广播模式可用，但容器化下建议**每个实例独立消费组**替代（位点云端化），或设计"重启后重新全量拉配置"兜底。

### Mechanism → Decision

| 机制 | 工程决策 |
| -- | ---- |
| 全量可见 | 广播模式 / 独立消费组 |
| 位点丢失兜底 | 重启后拉全量配置（配置数据量小，可接受） |
| 实例动态 | 新增实例从最新配置开始 + 首次全量拉取 |

### 禁止决策

- 广播模式 + 依赖本地位点做增量同步（容器重建位点必丢）

### 验收指标

- 配置下发到达率 100%（实例上报核对）
- 实例重启后配置最终一致（兜底拉全量验证）

---

## Decision Card 3：推拉选型评审

### 场景

新业务消息链：消费端是快逻辑（毫秒级处理）、消息量中低、延迟敏感。

### 判断

逐条低延迟 + 消费快 → 推模式占优（RabbitMQ 类）；若公司 MQ 平台只有 Kafka/RocketMQ，拉模式 + 小批量参数 + 短长轮询窗口可满足，不必为此引入新产品。

### Mechanism → Decision

| 机制 | 工程决策 |
| -- | ---- |
| 延迟敏感 | 缩短长轮询窗口、降低最小批量 |
| 批量度 | 小批量（与处理能力匹配） |
| 产品选择 | 复用现役产品 > 为推拉差异引入新品 |

### 禁止决策

- 为"推模式低延迟"引入第二个 MQ 产品线（运维成本远超收益）

### 验收指标

- 端到端 p99 ≤ 500ms（与推模式理论值对比实测）
- 消费端 CPU 空转率（空轮询比例）低于阈值

<a id="cross-language"></a>

# 🌍 跨语言视角

## 同一个问题：消费循环

| 语言 | 拉模式形态 | 推模式形态 |
| -- | ---- | ---- |
| Java | KafkaConsumer poll 循环（单线程） | RabbitMQ Consumer 回调 + prefetch |
| Go | kafka-go Reader / sarama ConsumerGroup（goroutine per partition） | amqp 库消费 channel |
| Rust | rdkafka StreamConsumer（poll 循环） | lapin 消费流（异步 Stream） |
| Python | confluent-kafka poll | pika 回调（Basic.Consume） |

## 跨语言仍成立的判断力

1. **消费循环与协程模型同构**：Java 单线程 poll 循环、Go goroutine per partition、Rust async Stream——都是"拉取-处理-提交"状态机的不同语法。
2. **背压是跨语言主题**：推模式靠 prefetch，拉模式靠批量与处理速度——与语言无关的流控思想。
