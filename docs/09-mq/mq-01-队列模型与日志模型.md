# 🏪 MQ 队列模型 vs 日志模型深度解析：从"消费即删"到"可回溯"的分野

> 这不是一篇 MQ 概念对比清单。
>
> 本文只追踪一个主线：**Message E 进入分拣中心**。
>
> E 是 `PaymentSucceeded` 事件——上一篇文章它从寄件柜台出发，本篇它走到分拣中心，发现面前有两条完全不同的分拣流水线：一条按"包裹"处理（队列模型），一条按"账本"处理（日志模型）。
>
> E 走哪条线，决定它之后的所有命运——能不能回溯、能不能重放、消费组怎么扩容。

---

# 写在最前面：一个被忽视的根源问题

大多数 MQ 选型讨论直接比较吞吐和延迟，但有一个更底层的问题被跳过：

**消息被消费之后，它在 Broker 里还存不存在？**

- 队列模型（RabbitMQ、RocketMQ 的**消费语义侧**）：**消费即删**——消息被"领走"后就被移除（RocketMQ 是"日志存储 + 队列语义"混合体：存储层消息不删，消费语义按队列模型表达，详见 Level 5）。
- 日志模型（Kafka、Pulsar）：**消费不删**——消息是 append-only 账本上的一条记录，消费者只是移动自己的"读到哪了"指针。

这个问题的答案，决定了顺序语义、重复消费形态、回溯能力、扩容方式——**本文所有内容都是这一个答案的展开**。

关键词：

```
队列模型 | 日志模型 | append-only | offset | 消费即删 | 保留策略 | RocketMQ 混合体 | 广播 vs 分摊
```

主线进度：

```
①为什么模型是根源 → ②队列模型：按件处理 → ③日志模型：按账本处理 → ④同一批业务问题的两套答案 → ⑤RocketMQ 混合体与模型选型 → ⑥队列 vs 日志
```

# 正文：五个 Level 打穿"队列 vs 日志"

<a id="level-1"></a>

## Level 1：为什么"消费之后还在不在"是根源问题

一句话认知墙：都是收发消息，为什么"消费之后消息还在不在"这个问题能分化出两套完全不同的系统行为？

### 前置知识关卡

- [ ] 能画出中转站最小模型（Producer/Broker/Consumer + Topic）
- [ ] 知道"暂存"与"转发"的区别（mq-00 Level 2）

### Why——一个答案分化的世界

**徒弟**：消息被消费后删不删，不就是个存储回收策略吗？跟"先进先出的队列"有什么关系？

**老陈**：这正是多数人卡住的地方。消息删不删，表面是存储问题，本质是**系统对"消费"这件事的定义不同**：

- 队列模型认为：消费 = **领取**。包裹被领走，货架上自然就没了。
- 日志模型认为：消费 = **阅读**。账本上的记录永远在，你只是翻到了第 N 行。

这个定义差，会向下传导出三个行为差异：

| 行为 | 队列模型（领取） | 日志模型（阅读） |
| ---- | ---- | ---- |
| 重复消费从哪来 | 重新投递（消息重新入队） | 位点回拨（重新读同一段账本） |
| 历史消息能否回溯 | 不能（已删） | 能（账本还在，保留期内） |
| 多个消费者看同一条消息 | 靠复制多份（fanout 出多队列） | 靠各自独立的位点 |

先记住这三个差异，Level 2 和 Level 3 会分别拆开两套模型，Level 4 会把它们放到业务问题面前对质。

### What——分拣中心的两条流水线

```text
            E 进入分拣中心
                 │
        ┌────────┴────────┐
        ▼                 ▼
   包裹流水线          账本流水线
  （队列模型）        （日志模型）
  按件分拣、          只增不删、
  取走即删            按行查阅
        │                 │
   RabbitMQ           Kafka / Pulsar
   RocketMQ(语义侧)
```

> 📌 最容易被误解的一点：**"队列模型"不等于"先进先出队列数据结构"**。队列模型指的是"消息生命周期 = 入队 → 被领取 → 消失"的管理方式；它内部完全可以用其他数据结构实现。同理，日志模型说的是"消息生命周期 = 追加 → 留存到保留期 → 按位点读取"。**模型说的是生命周期，不是数据结构。**

### How——E 在两套模型下的第一天

```text
队列模型：
① E 入队（Queue: ORDER_EVENT）
② InventoryService 领取 E → 扣库存 → ack
③ E 从队列中消失 —— 通知服务再也拿不到这份 E

日志模型：
① E 追加到账本（Partition: ORDER_EVENT-0, offset=1001）
② InventoryService 读到 offset=1001 → 位点推进到 1002
③ E 还在账本上 —— 通知服务组读自己的位点，同样能读到 offset=1001
```

**徒弟**：那队列模型里，通知服务怎么也能收到 E？E 不是被库存服务领走了吗？

**老陈**：好问题。队列模型的答案是**复制多份**——同一份 E 拷贝进两个队列，两个消费者各领各的（RabbitMQ 用 exchange 做这个分发）。日志模型的答案是**各读各的**——账本只有一份，两个消费组各自推进位点。这就是"广播"在两种模型下的两种实现，Level 2/3 分别展开。

### Transfer——这个思想还能迁移到哪里

1. **生命周期定义决定系统行为**：任何存储系统的第一问题都是"数据何时消失"——缓存 TTL、binlog 保留、日志轮转，都是在回答同一个问题。
2. **"复制多份" vs "共享一份 + 各自指针"**：Git 的分支（共享历史 + 各自 HEAD）是后者；文件拷贝是前者。设计广播类需求时先想清楚选哪种。
3. **领取 vs 阅读**：工单系统里"任务被认领"（领取）与"通知被查看"（阅读）是两套状态机——信息系统的日常决策里到处是这个区分。

本层留下的新账：两套模型的具体结构是什么样？队列模型怎么实现"复制多份"，日志模型怎么管理"各自位点"？→ 逼出 Level 2 和 Level 3。

### Level Ending

```
🔴 口诀：领取即销是队列，阅读留账是日志。
```

## Level 2：队列模型——按件处理的分拣线

一句话认知墙：RabbitMQ 为什么需要 exchange 和 queue 两个东西？queue 不就是队列吗？

### 前置知识关卡

- [ ] 能说出消费即删 vs 消费不删的三个行为差异（答不出回 Level 1）
- [ ] 知道 RabbitMQ 是 AMQP 0-9-1 的实现

### Why——为什么"队列"不够，还要"交换机"

**徒弟**：队列模型不就是"消息进队列、消费者出队列"吗？为什么 RabbitMQ 还多出一个 exchange？

**老陈**：因为你上一步问过的问题——"通知服务怎么也能拿到 E"。如果消息只能进一个队列、被一个消费者领走，那广播怎么实现？总不能要求生产者把 E 发给 100 个队列发 100 遍。**exchange 的职责就是把"发一次"变成"路由到 N 个队列"**——生产者只面对 exchange，exchange 按规则把消息拷进一个或多个队列。队列负责"存与领"，exchange 负责"分与拷"。

| 朴素方案 | 解决什么 | 留下什么问题 |
| ---- | ---- | ---- |
| 单队列单消费者 | 极简 | 无广播、无负载分担 |
| 生产者直发多队列 | 广播 | 生产者耦合所有消费者，新增消费者改生产者 |
| exchange 路由 + 多队列 | 广播与解耦 | 多一个路由层，队列本身仍是"领走即删" |

### What——AMQP 0-9-1 的路由结构

```text
        Producer
           │ publish(exchange, routingKey)
           ▼
     ┌──────────┐
     │ Exchange │（分拣台：按规则拷消息）
     └────┬─────┘
          │ binding（分拣规则）
   ┌──────┼──────┐
   ▼      ▼      ▼
Queue1  Queue2  Queue3    （包裹货架：领走即删）
   │      │      │
   ▼      ▼      ▼
ConsumerA ConsumerB ConsumerC
```

三种典型 exchange（分拣规则）：

```text
fanout：无条件拷贝到所有绑定的队列      → 广播（E 的通知场景）
direct：按 routingKey 精确匹配          → 点对点路由
topic：按通配符匹配（order.*.paid）     → 按规则分发
```

> 📌 最容易被误解的一点：**"一个队列一条队"是错的**。一个队列可以被多个消费者同时领取（RabbitMQ 默认轮询分发，即竞争消费），这时的队列承担了"负载分担"的角色；而"广播"必须靠 exchange 复制出多份，进多个队列。**队列内竞争、队列间广播**——这八个字是队列模型的全部消费语义。

### How——E 在队列模型下的旅程（9 步）

```text
① OrderService 声明 exchange = ORDER_EVENT_EX（类型 fanout）
② 声明两个队列：INVENTORY_Q、NOTIFY_Q
③ 建立 binding：exchange → 两个队列（广播规则）
④ publish：E 进入 exchange ★路由点
⑤ exchange 按 fanout 把 E 拷贝两份：进 INVENTORY_Q、NOTIFY_Q
⑥ InventoryService 从 INVENTORY_Q 领取 E（basic.get/consume）
⑦ 扣库存成功 → ack ★消息移除点
⑧ NotificationService 从 NOTIFY_Q 领取 E → 发通知 → ack
⑨ 两个队列各剩一条"领取后删除"的记录，E 在 Broker 内彻底消失
```

两个 ★ 是队列模型的两个关键边界：

- **④ 路由点**：E 在这一刻被"拷几份"决定下来——fanout 拷 N 份，direct 拷 0~1 份。**拷错即丢**：routingKey 不匹配任何 binding 时，消息静默消失（除非配置回退）。
- **⑦ 消息移除点**：ack 是队列模型的生命终点。**ack 之前消费者挂了，消息重新可见**（重新投递给别的消费者）——这是队列模型"不丢"的核心机制，也是"重复消费"的第一来源。

**徒弟**：等等，⑦ 和 ⑧ 之间——如果库存服务 ack 了，通知服务还没消费，E 在通知队列里还存着，对吧？那"E 彻底消失"是在 ⑧ 之后？

**老陈**：对。注意 ⑤ 的"拷两份"——E 在两个队列里是**两份独立副本**，各自有独立生命周期。库存队列那份 ack 就没了，通知队列那份还躺着。这就是队列模型广播的代价：**每多一个消费方，就多一份完整存储**。三个下游 = 三份 E 躺在三个队列里。日志模型没有这个代价，Level 3 见分晓。

### Transfer——这个思想还能迁移到哪里

1. **路由与存储分离**：exchange（怎么分）与 queue（怎么存）分离——与"业务规则引擎 + 任务队列"同构，规则变更不动存储。
2. **竞争消费 = 负载均衡**：一个队列多消费者轮询，就是最朴素的"任务分配给空闲 worker"。
3. **ack 前不可见**：消息在"处理中"状态的可见性管理——与 DB 悲观锁"行锁后不可见"同构。

本层留下的新账：队列模型广播靠"拷贝多份"，三份下游就是三倍存储。有没有一种模型，一份存储就能让所有人各读各的？→ 逼出 Level 3。

### Level Ending

```
🔴 口诀：队列内竞争分担，队列间拷贝广播。
```

## Level 3：日志模型——按账本处理的分拣线

一句话认知墙：Kafka 的 partition 为什么既是存储单元又是并发单元？"消费"为什么只是移动一个数字（offset）？

### 前置知识关卡

- [ ] 能说出队列模型"队列内竞争、队列间广播"八字（答不出回 Level 2）
- [ ] 知道 append-only 的含义

### Why——为什么 Kafka 把消息当"账本"而不是"包裹"

**老陈**：Level 2 留了一笔账：队列模型广播靠拷贝，N 个下游 N 份存储。Kafka 出生在 LinkedIn 的日志管道场景——同一个业务数据流，要喂给十几个下游系统（实时监控、离线分析、搜索索引、推荐模型……）。如果照队列模型做，一份日志要拷十几份，存储和写入都放大十几倍。于是它换了一个视角：**别拷消息，拷"指针"**。消息只写一份，每个下游自己记录"读到第几行"。

| 朴素方案 | 解决什么 | 留下什么问题 |
| ---- | ---- | ---- |
| 队列模型广播（拷 N 份） | 多下游 | N 倍存储与写入放大 |
| 日志模型（一份 + N 个 offset） | 多下游零拷贝 | 消息无法"领取即删"，保留期成为新问题 |

### What——append-only 账本结构

```text
Topic: ORDER_EVENT
   │
   ├── Partition 0（账本0）  ← 一块 append-only 磁盘日志
   │     offset 1000: msg A
   │     offset 1001: E     ★ E 被追加在这里
   │     offset 1002: msg C
   │
   ├── Partition 1（账本1）
   │     offset 500: msg D
   │
   └── Partition 2（账本2）

Consumer Group A（库存组）：group offset = {P0: 1002, P1: 501, P2: ...}
Consumer Group B（通知组）：group offset = {P0: 1001, ...}   ← 落后一格，还没读到 E
Consumer Group C（审计组）：group offset = {P0: 999, ...}    ← 落后很多，回头补读
```

> 📌 最容易被误解的一点：**"消费"在日志模型里只是移动一个数字**。Broker 不知道也不关心你"处理"了消息没有——它只知道你的位点动没动。所以日志模型的"消费成功"**天然没有业务含义**：位点推进了，业务可能根本没做（消费了没处理）；位点没推进，业务可能已经做了（处理了没提交位点）。这是神话③的根源，mq-03 展开。

### How——E 在日志模型下的旅程（8 步）

```text
① OrderService 对 E 取 Key = O_ID
② hash(Key) % 3 = 0 → E 追加到 Partition 0，offset = 1001 ★写入点
③ 副本同步（mq-08 展开，本文不表）
④ 库存组消费者 C1 从 P0 拉取（fetch offset=1001）
⑤ C1 扣库存成功 → 提交 group offset P0 → 1002 ★位点推进点
⑥ 通知组消费者 C2 从 P0 拉取（它自己的位点是 1001）
⑦ C2 发通知成功 → 提交自己组的位点
⑧ 审计组落后 100 条，从它自己的位点慢慢补读——E 在账本上原封不动
```

两个 ★ 对比队列模型：

- **② 写入点**：E 只有一个物理副本（加上 replica 也只有一份逻辑账本）。写入成本不随下游数量放大。
- **⑤ 位点推进点**：提交位点与"业务处理成功"是**两个独立事件**——先处理再提交（at-least-once），或先提交再处理（at-most-once），全凭客户端代码顺序。这个自由度是日志模型的强大之处，也是事故高发区。

**徒弟**：⑧ 里审计组能补读三天前的消息，是因为 E 还在账本上。那账本无限长怎么办？磁盘会爆吧？

**老陈**：对，这是日志模型的必答题——**保留策略（retention）**。按时间（保留 7 天）或按大小（保留 1TB）删旧段。账本不是永生的，只是"比消费即删活得久"。保留期是日志模型的核心运维参数：太短，迟到消费者读不到（神话⑪）；太长，磁盘成本失控。这个参数的深层含义在 mq-02 讲存储时展开。

### Transfer——这个思想还能迁移到哪里

1. **一份数据，多个视角**：数据库的 redo log 被多个从库各自追平——日志模型是分布式复制的通用形态。
2. **位点即状态**：把"进度"抽象成可回拨的数字，等于获得了"时间旅行"能力——重放、回补、修复全靠它。
3. **零拷贝广播**：不复制数据、只复制指针，是"读放大"问题的最优解——CDN、缓存失效、数据订阅都在用。

本层留下的新账：两套模型都看清了。但同一批业务问题——顺序、重复、回溯、扩容——两套模型给出的答案完全不同。E 到底该听谁的？→ 逼出 Level 4。

### Level Ending

```
🔴 口诀：账本只增不删，各人各持签收单。
```

<a id="level-4"></a>

## Level 4：同一批业务问题的两套答案

一句话认知墙：顺序、重复、回溯、扩容——这四个业务问题，队列模型和日志模型给出的答案为什么完全不同？

### 前置知识关卡

- [ ] 能画出队列模型（exchange → queue → ack）结构（答不出回 Level 2）
- [ ] 能画出日志模型（partition → offset → 消费组位点）结构（答不出回 Level 3）

### Why——模型差异如何传导成业务行为差异

**老陈**：模型不是学术分类，它直接决定你在生产上怎么解决四个高频问题。E 的扣库存场景逐个过一遍：

| 业务问题 | 队列模型（RabbitMQ） | 日志模型（Kafka） |
| ---- | ---- | ---- |
| **顺序**：同一订单的事件不乱序 | 队列天然 FIFO——同一队列内有序 | 分区内有序——同一 Key 进同一分区则有序（mq-04 展开） |
| **重复**：消息可能被处理两次 | 重投：ack 超时后消息重新可见 | 重读：位点回拨后重新拉取 |
| **回溯**：重放历史事件 | **做不到**（已删），靠死信/重试队列补救 | 天然支持：位点回拨到任意历史位置 |
| **扩容**：消费者加机器 | 队列内竞争——同一队列天然多消费者 | 分区数是上限——消费者数 ≤ 分区数 |

四个问题里最反直觉的是**扩容**：RabbitMQ 一个队列可以挂任意多个消费者轮询（扩消费者容易）；Kafka 消费者数量不能超过分区数（想加消费者，先加分区）。看起来队列模型更灵活，但代价在别处——队列模型的"容易扩"是单队列内的竞争，没有分区级并行度。

### What——两套模型的能力对比图

```text
                   队列模型              日志模型
消息生命周期：   入队 → 领取 → 消失      追加 → 常驻 → 过期删除
顺序保证：       队列内有序（简单）       分区内有序（靠 Key 路由）
重复来源：       重新投递                位点回拨
回溯能力：       无                      强（保留期内任意回拨）
广播实现：       exchange 拷贝多份        消费组各自位点
存储放大：       N 下游 = N 份存储        1 份存储
消费并发上限：   无硬上限（队列内竞争）     = 分区数
```

> 📌 最容易被误解的一点：**"日志模型更先进"是错的**。日志模型的回溯与吞吐优势，是用"消费进度与业务处理解耦"换来的——它不管消费者死活，你慢了它就积压。队列模型的重投机制天然关心"这条消息到底处理成功没有"。**一个关心单条消息的结局，一个关心整体数据的流动**——先进与否取决于 E 要哪种。

### How——E 的扣库存场景在两套模型下的实战推演

```text
场景：扣库存失败 3 次，需要人工介入排查

队列模型：
① 消费者领取 E → 扣库存失败 → nack（拒绝）
② E 重新入队 → 换消费者再试 → 还是失败
③ 重试 N 次后 → E 进死信队列（DLQ）
   （RabbitMQ 无原生重试计数：需 DLX + 消息 TTL + 应用侧计数实现；
    RocketMQ 内置重试队列与重试次数，mq-07 展开）
④ 运维从 DLQ 捞出 E 排查 → 修复后重新发布
   —— "单条消息的结局"被全程追踪

日志模型：
① 消费者读 offset=501 的 E → 扣库存失败
② 不提交位点（或提交但记录错误）→ 消息不会"消失"
③ 人工排查：直接把位点回拨到 501 重新消费
④ 或从账本上按 orderId 检索出 E 的完整上下文
   —— "账本上的记录"可反复查阅，但"处理结局"要自己记账
```

**徒弟**：那哪种更适合扣库存？

**老陈**：单看这个场景，队列模型的重试+死信更"顺手"——处理结局被系统关心。但注意 RabbitMQ 单队列吞吐有限，大促时订单事件是海量的。RocketMQ 的出现正是因为有人想**两个都要**：日志模型的高吞吐存储 + 队列模型的重试/死信语义。它就是 Level 5 的主角。

### Transfer——这个思想还能迁移到哪里

1. **"结局导向" vs "流动导向"**：工单系统（结局导向）与数据管道（流动导向）是两类系统设计，MCP/工作流引擎选型同样适用。
2. **回溯 = 时间旅行能力**：任何系统设计时问一句"半年后我要重放今天的数据吗"——要，就选可回溯的存储形态。
3. **并发上限设计**：分区数/队列数就是"并行度"，任何分布式系统都有这样一个"预先决定的并行上限"。

本层留下的新账：四个问题的答案已经分化。但 RocketMQ 号称两个都要——它是怎么把"日志存储"和"队列语义"缝在一起的？→ 逼出 Level 5。

### Level Ending

```
🔴 口诀：队列追结局，日志追流动。
```

<a id="level-5"></a>

## Level 5：RocketMQ 混合体与模型选型

一句话认知墙：RocketMQ 到底算队列模型还是日志模型？为什么它能把 Kafka 的吞吐和 RabbitMQ 的投递语义缝在一起？

### 前置知识关卡

- [ ] 能对比四维度（顺序/重复/回溯/扩容）的两套答案（答不出回 Level 4）
- [ ] 知道 RocketMQ 有事务消息/延迟消息（mq-00 Level 3）

### Why——为什么要做混合体

**老陈**：回顾前四层：队列模型赢在"关心单条消息结局"，输在吞吐与广播存储放大；日志模型赢在吞吐与回溯，输在"处理结局无人关心"。淘宝的交易场景是**两者都要**：大促海量吞吐（日志模型的强项）+ 订单消息的重试/死信/事务语义（队列模型的强项）。RocketMQ 的答案是：**存储层学日志，消费层学队列**。

| 方案 | 解决什么 | 留下什么问题 |
| ---- | ---- | ---- |
| 纯队列（RabbitMQ） | 结局追踪 | 吞吐受限、无回溯 |
| 纯日志（Kafka） | 吞吐回溯 | 结局追踪靠业务层自建 |
| 混合体（RocketMQ） | 两者兼顾 | 结构复杂，一致性边界多 |

### What——RocketMQ 的双层结构

```text
         存储层（学日志模型）              消费层（学队列模型）
   ┌──────────────────────────┐    ┌──────────────────────────┐
   │ CommitLog（全局一本账）      │    │ ConsumeQueue（每队列一索引）  │
   │ 所有 Topic 所有队列的消息     │    │ queue0: [offset, size, tag] │
   │ 顺序追加到一个文件序列        │    │ queue1: [offset, size, tag] │
   │ —— 写入路径只有一条          │    │ —— 读路径按队列定位          │
   └──────────────────────────┘    └──────────────────────────┘
                   │                              │
       写入：顺序追加，与 Kafka 同构     消费：按队列位点推进，可重试可死信
```

> 📌 最容易被误解的一点：**RocketMQ 的"队列"不是真实存储**。消息真实存放在 CommitLog（一份全局顺序账本），ConsumeQueue 只是每个队列的索引文件（每条 20 字节，指向 CommitLog 位置）。所以 RocketMQ 的"队列"是**逻辑队列**——它给消费者"我在队列里按位点消费"的错觉，底层却是日志式存储。这是理解 RocketMQ 一切机制（顺序、重试、延迟、事务）的钥匙，mq-02 会钻进这两层结构的源码级细节。

### How——E 在混合体里的旅程（7 步）

```text
① OrderService send E → Broker 受理
② E 顺序追加到 CommitLog ★唯一写入路径
③ 构建索引：ConsumeQueue 的 ORDER_EVENT-Q1 追加一条 {commitLogOffset, size}
④ 库存组从 Q1 按位点消费（索引指向 CommitLog 真实数据）
⑤ 扣库存失败 → E 进重试队列（RETRY 队列也是 ConsumeQueue 的一种）
⑥ 重试 N 次仍失败 → 进死信队列 DLQ
⑦ 运维从 DLQ 捞出 E → 修复 → 重新投递（新消息，走 ②）
```

注意第 ⑤⑥ 步——**重试与死信不是"换个指针"**：消费失败的消息由 Consumer 重新发回（sendMessageBack），作为**新消息**写入 RETRY/DLQ 主题，**再次追加到 CommitLog**（重试一次 = 多存一份，具体机制 mq-07 展开）。混合体的核心思想要精确表述：**正常消费的位点推进不动消息本体，但重试/死信/延迟会以新消息身份重新落账**——"语义"是位点与视图，"存储"该多存的还是会多存。

**徒弟**：那 RocketMQ 的广播模式怎么实现？也是靠"拷贝多份"吗？

**老陈**：不是——RocketMQ 集群模式（Clustering）是队列内分摊（一个队列被消费组内一个消费者消费）；广播模式（Broadcasting）是**每个消费者全量消费所有队列，各自记录位点**。广播模式没有"拷贝"，它靠的是每个消费者独立位点——这其实是日志模型的思想。看到没，RocketMQ 把两种模型的语义都装进了同一个存储：**分摊用队列语义，广播用日志语义**。

### Transfer——这个思想还能迁移到哪里

1. **存储一份，语义多份**：一份数据 + 多种视图（索引/物化视图/流式视图）——数据库的物化视图、列式存储的投影都是同构思想。
2. **写入路径与读取路径分离**：CommitLog（写）与 ConsumeQueue（读）分离——LSM 树的写优化、WAL 都是"先顺序写，再异步建索引"。
3. **逻辑与物理分离**：给上层"队列"的抽象，底层用"日志"实现——接口不变、实现可换，这是中间件设计的通用手法。

本层留下的新账：模型之争尘埃落定——但 E 现在要上货架了。账本怎么写到磁盘？顺序写为什么快？page cache 在里面扮演什么角色？→ 逼出 mq-02（存储引擎）。

### Level Ending

```
🔴 口诀：存储学日志，语义学队列，一份数据多种视图。
```

<a id="pitfalls"></a>

# ⚠️ 坑与细节

## 坑 1：把"队列模型"当成"FIFO 数据结构"

错误理解：队列模型 = 先进先出的队列数据结构。

原因：混淆"生命周期管理方式"与"底层数据结构"。

比喻后果：以为队列模型内部一定是个 FIFO 链表，看不懂 RabbitMQ 的优先级队列、惰性队列等变体（注：经典队列自 3.12 起统一为接近 lazy 的行为——消息体落盘、索引在内存，显式 lazy 模式已弃用，mq-02 展开）。

线上现象：用数据结构知识去推断 Broker 行为，得出错误结论（如"队列模型一定快"）。

修正：模型说的是生命周期（入队→领取→消失），数据结构是实现细节。

## 坑 2：以为 Kafka 消息消费后会被删

错误理解：消费完消息，Broker 里就没了。

原因：把队列模型的直觉带进日志模型。

比喻后果：以为账本会随阅读自动撕页。

线上现象：发现"已消费"的消息还占磁盘，误以为是 bug，手动删数据出事故。

修正：Kafka 的消息只由保留策略（时间/大小）删除，与消费进度无关。

## 坑 3：以为 RabbitMQ 加消费者就能无限扩容

错误理解：队列模型消费者无上限 = 吞吐无限扩展。

原因：看不到单队列的吞吐瓶颈——所有消费者竞争同一个队列的存储与投递。

比喻后果：一个货架再大，取货口只有一个，排队的是取货口不是货架。

线上现象：消费者加到 N 个，吞吐不再上升，反而因锁竞争下降。

修正：队列模型的扩展是"多队列 + 多消费者组合"，不是单队列无限加消费者。

## 坑 4：Kafka 消费者数超过分区数还期待性能提升

错误理解：多开几个消费者线程就能消费更快。

原因：不知道分区数是消费并发上限——多余消费者只能空转。

比喻后果：账本只有 3 本，来 10 个记账员，7 个没账可记。

线上现象：CPU 空转，lag 不降，被质疑"为什么加机器没用"。

修正：先加分区（有代价，见坑 5），再扩消费者；或按 Key 并行度预估分区数。

## 坑 5：以为分区可以随便加

错误理解：分区不够了，加就是了。

原因：不知道分区数是**预先决定的并行度**，中途增加会改变 Key 路由（hash(key) % N 变了），破坏有序性。

比喻后果：账本重新编号，原来"同一批货"的记录被拆到两本账里。

线上现象：加分区后同订单事件乱序，消费端幂等逻辑被打爆。

修正：分区数在主题创建时按峰值并行度设计（神话⑤、⑥的预警，mq-06/mq-04 展开）。

## 坑 6：把"消费成功"当成位点提交

错误理解：日志模型里提交位点 = 业务处理完成。

原因：把队列模型的 ack 语义套到日志模型上（神话③）。

比喻后果：签收单签了，货没验。

线上现象：处理逻辑抛异常但位点照常提交，消息静默丢失，对账才暴露。

修正：先处理成功后提交位点（at-least-once 语义），配合幂等兜底重复。

## 坑 7：以为 RocketMQ 的队列是真实存储单元

错误理解：RocketMQ 的 queue 和 RabbitMQ 的 queue 一样是消息存放的地方。

原因：只看消费 API 表象，不看 CommitLog + ConsumeQueue 双层结构。

比喻后果：以为每个货架独立堆货，实际是一本大账 + 各货架一张索引卡。

线上现象：按"队列 = 存储"的直觉去调存储参数（如单个队列的容量），全无效。

修正：真实数据在 CommitLog；队列是消费视图。

## 坑 8：在 RabbitMQ 上实现"回溯消费"

错误理解：RabbitMQ 也能做消息回放——消息重新投递就行。

原因：不知道队列模型的消息已删，重投 = 重新发送，不是回放。

比喻后果：包裹已经销毁，想"重新看一遍"只能让寄件人重寄。

线上现象：审计/修复场景想重放历史消息，发现根本无法实现，架构返工。

修正：需要回溯的形态（审计、回补、修复）选日志模型；队列模型用 DLQ 补救。

# 📚 版本勘误表

| 错误说法 | 准确说法 |
| ---- | ---- |
| "Kafka 消费后消息就删了" | 只由保留策略（retention）按时间/大小删除，与消费进度无关 |
| "RabbitMQ 的 queue 就是普通队列数据结构" | queue 是生命周期模型（领取即删），实现可以是内存/磁盘/惰性存储 |
| "RocketMQ 是 Java 版 Kafka" | 存储层同源（顺序日志），消费层不同——RocketMQ 有队列语义（重试/死信/事务） |
| "队列模型过时了，日志模型更先进" | 队列模型关心单条消息结局，日志模型关心数据流动——按形态选，无先进落后 |
| "Kafka 分区随便加" | 分区数是预先决定的并行度；增加分区改变 Key 路由，破坏有序性 |
| "RocketMQ 广播模式靠拷贝消息" | 靠每个消费者全量消费 + 独立位点（日志模型思想），无拷贝 |
| "Kafka 2.8 → 3.5 改了存储模型" | KRaft 改变的是元数据管理（ZK → Raft），分区日志的存储语义不变——语义变化 vs 代码组织变化必须分开讲 |
| 坦白：我以前也讲错过"消费完 Kafka 消息会删" | 早期我也被队列直觉带偏；日志模型的消息删除权只在保留策略手里 |
| 坦白：我以前也讲错过"RocketMQ 就是优化版 Kafka" | 存储同源让我误判为"改进版"；它的价值在消费层语义，不在存储层性能 |
| 坦白：我以前也讲错过"重试队列是索引复制，消息本体不动" | 重试/死信/延迟消息会以新消息身份再次写入 CommitLog——重试一次多存一份；索引是视图，重写是实体 |

# 🏆 生产决策卡

## Decision Card 1：订单事件选模型

### 场景

E（PaymentSucceeded）需要：海量吞吐（大促）、失败重试、死信追踪、可容忍重复。

### 判断

业务件 + 结局追踪 + 海量吞吐 → **RocketMQ**（混合体：日志存储 + 队列语义）。

### Mechanism → Decision

| 机制 | 工程决策 |
| -- | ---- |
| 海量顺序写 | CommitLog 统一顺序写 |
| 失败重试/死信 | 重试队列 + DLQ（消费层语义） |
| 下游多消费方 | 消费组（分摊）或广播模式（全量） |

### 禁止决策

- 用 RabbitMQ 扛大促主链路（单队列吞吐受限）
- 用 Kafka 但不上对账与 DLQ 自建体系（结局追踪真空）

### 验收指标

- 端到端 p99 ≤ 2s（消费完成）
- 重试成功率 / DLQ 积压水位监控
- 对账差异 ≤ 1/百万

---

## Decision Card 2：审计回溯选模型

### 场景

三个月前的订单事件要能按需回放排查（**支线：审计场景，与 E 的主链不同因果**）。

### 判断

可回溯 + 保留期 → **Kafka/Pulsar**（日志模型），保留策略按审计窗口配置。

### Mechanism → Decision

| 机制 | 工程决策 |
| -- | ---- |
| 位点回拨 | 审计消费组回拨到目标 offset 重放 |
| 保留策略 | retention = 审计窗口 × 1.5 |
| 磁盘成本 | 按消息量预算，冷数据可上分层存储（Pulsar） |

### 禁止决策

- 在 RabbitMQ 上实现回溯（消息已删，架构返工）

### 验收指标

- 回溯成功演练：任意历史位点重放成功
- 磁盘水位：保留期内告警线以下

---

## Decision Card 3：模型选型四问

### 场景

新系统要引入 MQ，产品还没定。

### 判断

用四个问题先定模型，再定产品：

```text
① 要回溯历史消息吗？     要 → 日志模型；不要 → 继续
② 单条消息的结局要追踪吗（重试/死信）？ 要 → 队列语义（RocketMQ）
③ 下游消费方很多吗（>5）？ 是 → 日志模型零拷贝广播占优
④ 吞吐目标多大？        百万级 → Kafka；十万级 → RocketMQ；万级 → RabbitMQ
```

### 禁止决策

- 先选产品再套场景（模型与场景不匹配，机制层硬补）

### 验收指标

- 模型四问文档化，评审会可复现决策过程

# 🌍 跨语言视角

## 同一个问题：队列与日志的分野

| 语言 | 队列模型实现 | 日志模型实现 |
| -- | ---- | ---- |
| Java | RabbitMQ/JMS 客户端 | Kafka 客户端（org.apache.kafka.clients） |
| Go | AMQP 库（streadway/amqp） | sarama / segmentio/kafka-go |
| Rust | lapin（AMQP） | rdkafka 绑定 / 自研（如 fluvio 生态） |
| Python | pika / Celery | kafka-python / confluent-kafka |

## 跨语言仍成立的判断力

1. **模型是协议的事，不是语言的事**：AMQP 0-9-1 的 ack 语义在 Java/Go/Rust 客户端完全一致——模型定义在协议层，语言只是搬运。
2. **"领取"与"阅读"两种状态机**：任何语言的异步消息代码都在处理同一个问题——消息拿走后，进度记录在哪（队列：Broker 记；日志：消费者记）。
