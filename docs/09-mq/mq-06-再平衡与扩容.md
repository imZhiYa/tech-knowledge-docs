# 写在最前面：两个神话，一个死结

mq-05 的结尾留下动态性之账（消费者集合变化 → 绑定重排），再加上 mq-01/mq-05 埋下的两个神话：

1. **神话⑤**：分区越多吞吐越高——真相是分区是并行度上限，分区数按峰值并行度设计，多分区有多分区成本。

本文要打穿一个死结：**消费者集合的动态性（rebalance）与消费者组的生产安全（不重复、不停摆）之间的冲突**。这是消费端事故浓度最高的地方。

# 正文：五个 Level 打穿"网点改组时 E 会怎样"

<a id="level-1"></a>

## Level 1：动态性为什么不可避免

一句话认知墙：队列与消费者的绑定关系为什么不能定死？

### 前置知识关卡

- [ ] 知道消费组"组内分摊、组间广播"（mq-05 L4）
- [ ] 知道消费者数 ≤ 队列数才都有活干（mq-01 L4 / mq-05 L5）

### Why——静态绑定的三个死因

**徒弟**：既然分配这么麻烦，干脆创建队列时把队列绑死给具体消费者不就行了？

**老陈**：绑死有三个死因，任何一个都足以让系统不能用：

| 死因 | 场景 | 后果 |
| ---- | ---- | ---- |
| ① 消费者会死 | 实例宕机/进程崩溃/网络分区 | 绑定的队列无人消费，业务停滞 |
| ② 消费者会动 | 发布、扩缩容、重启 | 新实例无队列可接，旧实例独吞 |
| ③ 处理会不均 | 热点 Key 倾斜、实例性能差异 | 固定绑定无法负载再均衡 |

**动态性是分布式系统的必然属性，不是设计缺陷**：只要消费者集合会变，绑定关系就必须能重排。"重排"这个动作，就叫 **rebalance（再平衡）**。

**徒弟**：那 RabbitMQ 为什么不需要 rebalance？它的队列绑定不是动态的吗？

**老陈**：RabbitMQ 的竞争消费里，队列和消费者本来就没有"一一绑定"关系——消息按轮询派发给任意消费者，消费者增减自然适配，**根本没有"分配表"需要重排**。这印证了 mq-05 的判断：RabbitMQ 用"无绑定"的结构绕开了 rebalance，而 Kafka/RocketMQ 用"队列-消费者绑定"换来了确定性的分摊与位点管理，代价就是必须处理 rebalance。注意：RabbitMQ 的竞争消费天然具备**分摊**（轮询派发 = 消息被多个消费者分担），它缺的是"确定性粘性绑定 + 组内位点托管"——**没有 rebalance 概念的代价，是绑定与位点的确定性；有 rebalance 的代价，是必须管理重排**——这是产品设计的 Trade-off，不是优劣。

### What——动态性制造的三类事件

```text
消费者集合变化的三类触发：
  ① 主动变化：上线（扩容/发布）、下线（缩容/优雅退出）
  ② 被动变化：宕机、心跳超时被踢（会话过期）
  ③ 结构变化：订阅变更、分区数变更、broker 故障

每一次变化，都要求"队列 ↔ 消费者"的映射重新计算。
```

### How——E 在动态世界里的第一课

```text
T0  库存组 3 实例：A1(队列0/1) A2(队列2/3) A3(队列4/5)
T1  A2 机器宕机 → 心跳消失
T2  协调器判定 A2 失效 → 触发重排（rebalance）
T3  重排结果：A1(队列0/1) A3(队列2/3/4/5)  ← 队列 2/3 换主人
T4  队列 2/3 的新主人 A3 从上次位点续读
T5  若 A2 已处理未提交的部分 → A3 再次读到 → ★重复窗口（mq-04 重复来源④）
```

**徒弟**：T5 的重复窗口，mq-04 已经用幂等挡住了——那 rebalance 还有什么可怕的？

**老陈**：重复只是事故链的第一环。重排瞬间的**停摆窗口**、踢人判断的**误杀**、连环重排的 **storm**——事故链在后三环，Level 3 展开。先记住：**rebalance 是"必要的机制"，也是"事故的窗口"**——机制必须存在，窗口必须可控。

### Transfer——这个思想还能迁移到哪里

1. **动态成员管理是分布式系统的通用问题**：K8s 的 Endpoint/EndpointSlice 更新、Raft 的成员变更、微服务的服务发现——都是"成员集合变化时如何安全重排"。
2. **无绑定绕开重排，绑定换取语义**：RabbitMQ 无绑定 vs Kafka 有绑定——设计问题时先问"我要分摊语义吗"，答案决定复杂度。
3. **必要机制 ≠ 免费午餐**：每个必要机制都有事故窗口，生产上要的是"窗口可控"，不是"机制不存在"。

本层留下的新账：重排机制到底怎么运作？谁来决定新映射？Kafka 和 RocketMQ 的"拍板者"为什么不一样？→ 逼出 Level 2。

### Level Ending

```
🔴 口诀：静态绑定必死，动态重排是常态。
```

## Level 2：再平衡机制全解——协调器与分配器

一句话认知墙：rebalance 是谁在拍板？拍板依据是什么？

### 前置知识关卡

- [ ] 能说出动态性不可避免的三个死因（答不出回 Level 1）
- [ ] 知道 Kafka 消费组由 GroupCoordinator 管理（本文 L4 展开）

### Why——两种拍板哲学

**老陈**：谁来决定"哪个消费者消费哪个队列"，两大流派：

```text
集中式拍板（Kafka）：
  组协调器 GroupCoordinator 集中管理成员关系
  消费者加入/心跳 → 协调器记录 → 分配 → 下发
  拍板权在 Broker：协调器选一个消费者当"组长"
  组长执行分配策略，结果分发全组

分布式拍板（RocketMQ）：
  没有集中协调器，每个消费者自己算
  客户端定时扫描：从 Broker 拉当前组的所有消费者列表
  每个消费者用同一套分配算法独立计算映射
  拍板权在客户端：算法一致，各自算出相同结果
```

| 维度 | Kafka（集中式） | RocketMQ（分布式自算） |
| ---- | ---- | ---- |
| 协调者 | Broker 端 GroupCoordinator | 无，客户端自协调 |
| 成员感知 | 心跳上报 | 拉取消费者列表 |
| 一致性 | 协调器保证全组一致 | 依赖算法一致 + 列表一致 |
| 分配粒度 | 分区（partition） | 队列（queue） |

> 📌 最容易被误解的一点：**"组长"不是权威，只是执行者**。Kafka 的 rebalance 里，组长消费者执行分配策略算出的结果，要回传给协调器统一下发——**权威是协调器，组长只是算数的人**。RocketMQ 更彻底：没有权威，人人自算，算法与列表一致则结果一致（分布式系统的"无中心共识"靠确定性算法实现）。

### What——Kafka 两阶段与分配策略

```text
Kafka rebalance 两阶段（join / sync）：

  阶段一 join（加入）：
    消费者 → 协调器：JoinGroup（报上自己是谁）
    协调器：选出组长（组内第一个/最新成员），
            返回当前成员列表给组长

  阶段二 sync（同步）：
    组长：执行分配策略 → 算出新映射（partition → consumer）
    组长 → 协调器：SyncGroup（交上分配结果）
    协调器 → 全组：下发各自的分配结果

  完成：每个消费者知道自己该消费哪些分区，开始拉取

分配策略四选（Kafka 默认策略由服务端/客户端配置决定）：
  Range        按 topic 分段均分（客户端默认配置，社区建议换 cooperative-sticky；重排时分区移动多）
  RoundRobin   轮询分配（移动次之）
  Sticky       最小移动（尽量不动已有分配）
  CooperativeSticky  渐进式（2.4+，只撤销要移动的分区，
                  不停止全组消费，配合 KIP-429）
```

### What——分配算例：4 分区 × 3 消费者，谁拿多少一算便知

策略名背得再熟，不如算一遍。设 topic 4 个分区（P0~P3），组内 3 个消费者（C0~C2）：

```text
Range（按 topic 分段均分，客户端默认配置）：
  4 ÷ 3 = 1 余 1 → 排前面的消费者多拿 1 个
  C0 → P0, P1      C1 → P2      C2 → P3

RoundRobin（跨 topic 全局轮询）：
  P0→C0  P1→C1  P2→C2  P3→C0
  C0 → P0, P3      C1 → P1      C2 → P2

Sticky（均匀优先，其次尽量保留已有分配）：
  首次分配与 RoundRobin 同构，差异在 rebalance 时刻
```

静态结果三个策略长得差不多——4 个分区分给 3 个人，**必然有人拿 2 个**（除不尽的余数必须落地）。真正的分水岭在 rebalance 时刻的移动量。

**徒弟**：Range 让 C0 多吃一倍，这不合理吧？

**老陈**：先承认直觉的合理性——但"不均"是算术必然：4 ÷ 3 除不尽，总有人多拿。Range 的选择是"排前面的多吃"，RoundRobin 是"大家轮着多吃"，单 topic 下没差别。**真正的设计问题在成员变化那一刻**：谁要被移动几个分区，决定了停摆面和重复窗口。看 C3 加入：

| 策略 | C3 加入后的分配 | 移动分区数 | 停摆面 |
| ---- | ---- | ---- | ---- |
| Range（eager） | 全组重算，每人 1 个 | 4（每个人都让出/接管） | 全组 revoke→assign，全部停摆 |
| Sticky | 从 C0={P0,P3} 出发，只让 C0 让出 1 个 | 1 | 只有 C0 的一个分区 |
| CooperativeSticky（2.4+，KIP-429） | 第一轮只 revoke 需移动的分区，C3 先拿空分区 | 1 | 增量进行，无全组停摆 |

同一个事件：Range 让全组 4 个消费者都动一遍（每个人停摆 + 重分），Sticky 只动 1 个分区；CooperativeSticky 再把"最小变动"做成分轮协议——先撤销再接管。**这就是生产上把默认 range 换掉的全部理由**（坑 8 提醒：它也不是银弹）。

### What——RocketMQ 的自算分配

```text
RocketMQ rebalance 循环（客户端 RebalanceImpl）：
  ① 定时扫描：从 Broker 获取当前组的消费者列表
  ② 获取 topic 的队列列表
  ③ 用分配算法（AllocateMessageQueueStrategy，默认平均分配）
     独立计算：本消费者该消费哪些队列
  ④ 对"新分配给自己的队列"从位点续读
     （位点在 Broker 端，mq-05 L5 已讲）

  特点：
    - 无全组停摆概念：每个消费者自己切换自己的队列
    - 但切换瞬间同样有"上一消费者已处理未提交"的重复窗口
    - 算法必须全组一致，否则两个消费者算到同一个队列
      → 队列被两个消费者同时消费 → 重复（分配冲突）
```

### How——E 经历一次完整的 Kafka rebalance

```text
T0  消费者 A2 心跳消失（宕机/网络分区）
T1  协调器在会话超时后判定 A2 失效
T2  join 阶段：A1、A3 重新加入（A2 缺席）
T3  协调器选 A1 为组长，返回成员列表 [A1, A3]
T4  A1 执行分配策略：队列(0/1)→A1，队列(2/3/4/5)→A3
T5  sync 阶段：协调器把结果下发 A1、A3
T6  A3 接管队列 2/3 → 从位点续读 → 潜在重复窗口（mq-04 幂等兜底）
T7  全组恢复消费

事故观察点：
  - T2→T7 期间组内消费暂停（eager 模式全组撤销再分配）
  - A2 未提交位点的消息会被 A3 重读（重复窗口）
  - 若 A2 只是 GC 停顿而非真死 → 回到组 → 又触发一次 rebalance
```

**徒弟**：A2 只是 GC 停顿几秒就被踢出组，代价是不是太大了？

**老陈**：这正是 Kafka 把"踢人"拆成两把尺子的原因——**会话超时（session.timeout）管"活着吗"，轮询超时（max.poll.interval）管"干活吗"**。GC 停顿导致心跳延迟 → 会话判定生死；处理太慢导致 poll 间隔过长 → 判定失职。两把尺子都能踢人，踢人即 rebalance，rebalance 即事故窗口——所以 Level 3 讲怎么让窗口可控。

### How——RocketMQ 算例与代价形态

同样算一遍：topic 8 个队列（Q0~Q7），组内 3 个消费者（C0~C2）：

```text
AllocateMessageQueueAveragely（默认平均分配）：
  8 ÷ 3 = 2 余 2 → 排前面的消费者多拿 1 个
  C0 → Q0,Q1,Q2    C1 → Q3,Q4,Q5    C2 → Q6,Q7
```

与 Kafka Range 同构——"商 + 余数给前面"，两大阵营的"平均分配系"用的是同一个算术。另一条路是**一致性哈希**（AllocateMessageQueueConsistentHash，默认 20 个虚拟节点）：消费者与队列都哈希到环上，队列归属顺时针遇到的第一个消费者。价值与 Sticky 同源——**消费者增减只影响环上邻近的队列**；代价是负载不均（虚拟节点只是缓解不是消除），所以生产默认仍是平均分配。

再算一次动态：C1 掉线，Q3~Q5 谁来接？

```text
T0   C1 宕机 → Q3~Q5 停摆
T1   ≤20s 后（下一次 RebalanceService 扫描，客户端默认周期 20s）
     C0/C2 发现组内成员少了 C1 → 重算 → 接管 Q3~Q5
T2   换手瞬间：C1 可能有未提交消息 → 新消费者从位点续读 → 重复窗口
```

**徒弟**：Kafka 掉线立刻感知，RocketMQ 要等 20 秒？这是缺陷吧？

**老陈**：先承认直觉——20s 空窗对延迟敏感业务确实是事故面。但要看到它是"无协调器"架构的必然代价：没有集中协调器盯着心跳，感知只能靠轮询，轮询间隔就是感知延迟的下界。Kafka 用协调器换来"立刻感知"，代价是 eager 协议的全组停摆；RocketMQ 用轮询换来"无全组停摆"，代价是 20s 空窗。**两种代价形态，没有免费午餐**——架构评审该问的是：你的业务怕停摆，还是怕空窗？

5.x 给出第三条路：**PopConsumer（POP 协议，5.0 引入）**——把消费分发从客户端收回 broker，broker 端按需 pop 派发。rebalance、20s 感知延迟、分配冲突全部消失，代价是放弃"队列-消费者绑定"的确定性：顺序语义与位点管理不再绑定物理队列（弱于 push 模式的粘性）。这与 Kafka 的新消费组协议（KIP-848 方向）是同一个演进——**重平衡的复杂性正在从客户端往 broker 集中**：客户端自算的代价（感知延迟、算法一致性、rebalance storm）在规模化后比集中协调更贵。

两种拍板哲学的机制与代价摊开对比：

| 维度 | Kafka | RocketMQ |
| ---- | ---- | ---- |
| 协调权威 | Broker 端 GroupCoordinator（集中） | 无权威，客户端自算 |
| 触发时机 | 事件驱动（成员变化即刻 rebalance） | 定时扫描（客户端默认 20s 周期） |
| 分配传播 | 组长算 → 协调器广播 | 各自算（确定性算法保证结果一致） |
| 换手互斥 | 协议保证分区唯一归属 | 确定性分配 + Broker 队列锁（实现细节） |
| 默认分配策略 | range（客户端默认配置） | AllocateMessageQueueAveragely |
| 停摆形态 | eager 全组停摆；cooperative（2.4+）缩到单分区 | 无全组停摆，代价是 ≤20s 感知空窗 |
| 并行度上限 | 分区数 | 队列数 |
| 一致性要求 | 无（分配只由协调器算） | 全组策略必须一致，否则双消费（坑 7） |

### Transfer——这个思想还能迁移到哪里

1. **集中拍板 vs 自算共识**：ZooKeeper 的集中协调 vs 确定性算法自算（一致性哈希也是"人人自算同一结果"）——选型时问"谁负责一致性"。
2. **两阶段协议是分布式协调的通用骨架**：join/sync 与两阶段提交（2PC）、Raft 的领导选举+日志复制同构。
3. **组长只是执行者**：权威与执行分离的治理模式（架构评审、权限模型同理）。

本层留下的新账：机制清楚了，事故窗口也看到了。窗口里到底会发生什么级别的破坏？→ 逼出 Level 3。

### Level Ending

```
🔴 口诀：协调器拍板，分配器分活。
```

## Level 3：再平衡事故链——停摆、重复与风暴

一句话认知墙：一次 rebalance 会闯什么祸？为什么"偶然一次 rebalance"会变成"连环事故"？

### 前置知识关卡

- [ ] 能画出 Kafka join/sync 两阶段（答不出回 Level 2）
- [ ] 知道重复窗口的产生原理（Level 1 / mq-04 L1）

### Why——rebalance 的三环事故链

**老陈**：一次 rebalance 本身是"有序切换"，但生产事故里 rebalance 从不是单次事件，而是三环相扣：

```text
第一环：停摆窗口（eager 全组暂停）
  传统 eager 语义：join 前全组撤销所有分区
  （非渐进式分配策略下的行为；CooperativeSticky 只撤销要移动的分区）
  → 从"第一个成员 join"到"全组 sync 完成"，
    组内所有消费停止 ★全体停摆
  停摆时长 ∝ 成员数 × 网络往返 + 分配计算

第二环：重复消费（位点未提交部分）
  被接管队列的新主人从位点续读
  → 旧主人"已处理未提交"的部分被重读 ★重复窗口
  → 没有幂等（mq-04）→ 业务重复

第三环：rebalance storm（连环重排）
  一个成员反复被踢（GC 停顿/慢处理）→ 反复触发 rebalance
  → 全组反复停摆、反复重复 ★风暴
  → 下游被重复轰炸，消费进度全面回退，集群进入抖动状态
```

> 📌 最容易被误解的一点：**rebalance storm 的起点往往不是 Broker 故障，而是消费端抖动**。一个消费者 GC 停顿 30 秒 → 被踢 → rebalance → 它回来 → 又触发 rebalance → 全组被它拖进循环。**慢消费者不是"自己慢"，而是"拖着全组慢"**——这是 rebalance 与普通慢消费的本质区别。

### What——三个事故的放大因素

```text
放大因素一：成员数
  全组停摆窗口随成员数线性增长
  → 组越大，一次 rebalance 的代价越大

放大因素二：分配策略
  Range 分配重排时分区移动最多 → 每次 rebalance 移动大量分区
  Sticky/CooperativeSticky 最小移动 → 窗口与重复面更小

放大因素三：踢人误判
  GC 停顿 / 慢处理 / 网络抖动 → 误判死亡 → 无谓 rebalance
  → 误判率越高，风暴概率越高
```

### How——E 的连环事故推演

```text
T0  库存组 3 实例，A2 处理慢（下游 DB 抖动）
T1  A2 单批处理超过 max.poll.interval → 协调器判定失职
T2  rebalance #1：全组撤销 → 重排 → 恢复（停摆 3s）
T3  A2 回来 → join → rebalance #2（停摆 3s）
T4  A2 又慢 → rebalance #3（停摆 3s）★storm 开始
T5  全组：消费进度反复回退、下游重复轰炸、
    lag 暴涨、告警风暴
T6  运维介入：摘除 A2 → 组恢复稳定
     （但 T0~T5 期间的重复需要幂等与对账兜底）
```

**徒弟**：CooperativeSticky 不是渐进式吗？它能挡住风暴吗？

**老陈**：CooperativeSticky（2.4+）把"全组撤销再分配"改成"只撤销要移动的分区"——**停摆窗口从'全组'缩小到'被移动的少量分区'**，风暴的破坏半径小了一个量级。但它不解决风暴的根源（踢人误判），只减轻后果。**治本在两头：一头是消费端健壮性（GC、处理时长、下游稳定性），一头是会话/轮询超时的合理设置**——这正是 L5 参数小节的地盘。

### Transfer——这个思想还能迁移到哪里

1. **必要机制的事故链分析**：任何必要机制（故障转移、扩缩容、发布）都要追问三环：窗口、重复、放大。
2. **抖动传染**：慢节点拖全组（队头阻塞、rebalance storm、热点）——"个别慢"放大成"全局抖"是分布式系统的常见事故模式。
3. **渐进式变更**：CooperativeSticky 的"只动必要的"思想 = 蓝绿发布、滚动更新的通用原则。

本层留下的新账：停摆和风暴的终极防线是"少触发 rebalance"——但触发变少之后，真正的问题来了：**触发一次 rebalance 时，组能扩到多大？加消费者真的能提高吞吐吗？** → 逼出 Level 4（扩容真相）。

### Level Ending

```
🔴 口诀：重排有窗口，风暴是连环。
```

## Level 4：扩容真相——分区数 = 并行度上限

一句话认知墙：堆积了就加 Consumer——为什么这个直觉在 MQ 世界里是错的？

### 前置知识关卡

- [ ] 能说出 rebalance 三环事故链（答不出回 Level 3）
- [ ] 知道消费者数 ≤ 队列数（mq-01 L4 / mq-05 L5）

### Why——神话⑦ 的破解：加消费者为什么没用

**老陈**：把消费组想象成一个柜台系统：**柜台数（分区数）决定同时处理多少件，柜员数（消费者数）超过柜台数就有人闲着**。堆积不是"人手不够"，是"柜台不够"：

```text
队列数 = 4，消费者数 = 4 → 恰好：每个消费者一个队列
队列数 = 4，消费者数 = 8 → 多余 4 个消费者分配不到队列 → 空转
堆积发生时：
  加消费者（6 个）→ 还是只有 4 个在干活 → lag 不降 ★神话⑦
  加分区（8 个）→ 并行度翻倍 → 但 Key 路由 hash(key)%8 变化
    → 历史消息与新高程消息可能不同分区 → 顺序破坏（mq-04 坑 5）
```

> 📌 最容易被误解的一点：**"加消费者没用"不等于"消费者数永远等于队列数"**。消费者数可以少于队列数（每个消费者扛多个队列），**消费者数 < 分区数时，加消费者同时提升并行度与可用性**（瓶颈在消费端时，这是扩吞吐的正路）；消费者数 = 分区数之后，加消费者才只买高可用（多一个备份不丢活，但并行度不变）。**两个目标、两种手段，边界在"并行度是否打满"**——别混。

### What——神话⑤ 的破解：分区越多吞吐越高吗

```text
分区数与吞吐的关系（机制层面）：
  并行度 = 分区数（一个分区同一时刻一个消费者）
  单分区吞吐 = 单消费者处理能力
  总吞吐上限 ≈ 分区数 × 单分区吞吐（理想情况）

但多分区有真实成本：
  ① 文件与句柄：每个分区一组日志段文件（.log/.index/.timeindex）与索引，
     文件数量 ≈ 分区数 × 副本数 × 段数，句柄与内存随分区数增长
  ② 元数据：分区列表、Leader 元数据、协调器状态随分区数膨胀
  ③ 复制放大：副本复制是每分区独立进行的
  ④ 分配与协调：rebalance 的分配计算与协调开销随分区数增长
  ⑤ 端到端延迟：分区多时批量不够大，小批量往返增多

结论：
  分区数 = 并行度上限，也是成本函数
"越多越好"是假话；"按峰值并行度设计，多一个分区多一份成本"
才是真相（成本清单见本文 L4）
```

### How——E 的扩容全推演

```text
场景：大促，库存组 lag 暴涨到 50 万
错误做法：
  ① 加 20 个消费者实例 → 只有 4 个（=队列数）在干活
  ② 其余空转 → lag 不降 → 再加实例 → 事故扩大
  （还伴随 rebalance 风暴，因为每加一个实例都触发一次重排）

正确做法：
  ① 先查队列数：4 → 并行度上限 = 4
  ② 确认瓶颈：单消费者处理能力（下游 DB）有没有余量？
     - 有 → 加队列（但要处理 Key 路由与顺序问题，mq-04 坑 5）
     - 没有 → 加队列也没用，瓶颈在下游 → 拆下游 / 限流 / 降级
  ③ 若瓶颈是热点 Key（mq-04 L4）→ 加队列没用，单 Key 仍串行
     → 需要 Key 拆分或业务改造
  ④ 用幂等兜住扩容期间的重复（mq-04）
```

**徒弟**：等等，为什么说"加队列要处理 Key 路由问题"？Kafka 不是支持动态加分区吗？

**老陈**：Kafka 支持动态增加分区数，但**不能减少**，且增加后 `hash(key) % N` 的 N 变了——同一个订单的新消息可能落到新分区，与历史消息不在同一分区，顺序链断裂（mq-04 L3 的坑一）。**生产上分区数基本是"创建时按峰值并行度定死"的**，动态加分区是"救命手段"不是"常规手段"。RocketMQ 同理：队列数调整会影响位点映射与重试队列，改动前必须评估顺序与消费进度的影响。

### Transfer——这个思想还能迁移到哪里

1. **并行度与容量的分离**：加消费者解决可用性，加分区解决并行度——数据库连接池、线程池、网关实例数都是同一个"资源上限在哪"的问题。
2. **成本是设计的第一约束**：分区不是免费的（文件、元数据、复制）——"越多的并行度"必须用"越多的成本"兑换。
3. **扩容先找瓶颈在哪一层**：消费者数、分区数、下游 DB、热点 Key——四层都可能，先定位再动刀。

本层留下的新账：并行度被分区数锁死，加分区又有顺序与成本问题——**那么消息形态本身能不能提供更多能力？半消息、延迟消息、死信这些"特殊消息形态"是怎么在底层机制上长出来的？** → 逼出 mq-07（事务/延迟/死信）。

### Level Ending

```
🔴 口诀：并行度看分区，加人不如加区。
```

## Level 5：生产决策与参数配置

一句话认知墙：rebalance 与扩容的决策，到了架构评审桌上怎么做？

### 前置知识关卡

- [ ] 能区分"加消费者=可用性、加分区=并行度"（答不出回 Level 4）
- [ ] 知道风暴的根源是踢人误判（Level 3）

### Why——决策的轴心是"少触发 + 触发可控"

**老陈**：rebalance 的决策只有一条主线：**能少触发就少触发，触发了要让窗口小、重复面小**。所有参数都围绕这条主线。

### What——决策清单

```text
决策一：实例数怎么定？
  实例数 ≤ 分区数（并行度上限）
  实例数 > 1（高可用冗余，一个挂掉不丢活）
  → 实例数 = min(峰值并行度所需, 分区数)，留 1~2 个冗余

决策二：分区数怎么定？
  按峰值并行度 + 单分区处理能力推算
  + 未来 1~2 年增长预留
  + 记住：创建后只增不减，改动破坏 Key 路由

决策三：分配策略选哪个？
  CooperativeSticky（Kafka 2.4+）优先：渐进式、窗口最小
  场景有特殊均衡需求时评估 Range/RoundRobin/Sticky

决策四：踢人尺子怎么配？
  会话超时：判"活着吗"——要给 GC 停顿/网络抖动留余量
  轮询超时：判"干活吗"——要大于单批最坏处理时长
  两把尺子都太紧 → 误杀 → storm
```

### How——E 的大促扩容决策推演

```text
① 现状：4 队列，4 实例，单实例处理 500 msg/s，峰值需 3000 msg/s
② 决策：分区数 = 3000 / 500 = 6 → 创建 8（预留余量）
③ 实例数 = 8（与分区数持平，含冗余）
④ 分配策略 = CooperativeSticky
⑤ 会话/轮询超时按最坏处理时长 + 20% 余量配置
⑥ 大促预案：lag 告警 → 先查瓶颈层（分区/下游/热点）再动刀
⑦ 兜底：幂等表（mq-04）防扩容期间重复；对账（mq-03）核对效果
```

**徒弟**：实例数为什么是 8 而不是 4？多出的 4 个不是空转吗？

**老陈**：4 个实例的组，挂一个就只剩 3 个消费者扛 8 个队列——lag 瞬间翻倍。8 个实例（=分区数）的组，挂一个还有 7 个在扛，lag 影响小得多。**实例数贴着分区数配置，是"用空转余量换故障韧性"**——空转成本低（空闲线程开销小），停摆成本高（lag 暴涨 + 告警 + 人工介入）。

### 📋 关键参数配置与注意事项

> 默认值随版本变化，以官方文档为准（写作基线 Kafka 3.5.x / RocketMQ 5.x），本文只讲参数控制的机制与配错的事故。

| 参数 | 控制的机制（指向本文 Level） | 配错的线上事故 |
| ---- | ---- | ---- |
| session.timeout.ms（Kafka 会话超时） | 判"消费者还活着吗"：心跳间隔上限（L1/L3） | 配太紧 → GC/网络抖动即误杀 → 反复 rebalance → storm |
| heartbeat.interval.ms（Kafka 心跳间隔） | 心跳上报频率，与会话超时联动（L2） | 配太密 → 心跳请求浪费；配太疏 → 误杀窗口放大 |
| max.poll.interval.ms（Kafka 轮询超时） | 判"消费者还在干活吗"：poll 间隔上限（L3） | 单批处理慢 → 被误踢 → storm；配太大 → 死消费者占用分区不释放 |
| partition.assignment.strategy（Kafka 分配策略） | 分配算法：移动面大小与停摆窗口（L2/L3） | 用 Range → 每次重排移动大量分区 → 窗口与重复面大 |
| group.instance.id（Kafka static membership） | 固定成员身份：重启不触发 rebalance（L3） | 未配置 → 每次发布/重启触发 rebalance → 大组频繁停摆 |
| AllocateMessageQueueStrategy（RocketMQ 分配算法） | 客户端自算分配（L2） | 组内配置不一致 → 分配冲突 → 队列被双消费者消费 → 重复 |
| RocketMQ rebalance 扫描间隔 | 客户端自协调的触发频率（L2） | 间隔太短 → 频繁重算；太长 → 消费者下线后队列交接慢 |
| num.partitions（Kafka 创建时分区数） | 并行度上限（L4） | 建小了 → 堆积极限，只能救命式加分区（破坏 Key 路由）；建大了 → 文件/元数据/复制成本白付 |
| RocketMQ 读写队列数（创建时） | 同上（L4） | 同上；调整影响位点映射与顺序 |
| 消费线程数（Kafka/RocketMQ 客户端） | 单消费者内并发度（L4） | 每分区/队列串行模型下配大于分区数 → 线程空转；配过小 → 单消费者吞吐不足（RocketMQ 并发消费模式单队列可拆多线程，属另一层并发，mq-05 L3） |


## Self Check

| 问题 | 必须回答的不变量 |
| ---- | ---- |
| 动态性三死因？ | 消费者会死 / 会动 / 处理不均 |
| Kafka 两阶段？ | join（选组长）→ sync（组长分配、协调器下发） |
| RocketMQ 怎么协调？ | 客户端自算：算法一致 + 列表一致 → 结果一致 |
| 三环事故链？ | 停摆窗口 → 重复消费 → rebalance storm |
| 加消费者 vs 加分区？ | 加消费者=可用性，加分区=并行度 |
| 分区数怎么定？ | 峰值并行度 + 增长预留；创建后只增不减 |

<a id="pitfalls"></a>

# ⚠️ 坑与细节

## 坑 1：把 rebalance 当"正常功能"忽略

错误理解：rebalance 是标准机制，不会出事。

原因：机制正常，但事故窗口真实存在——停摆、重复、风暴三环。

比喻后果：交接流程没问题，但每次交接都要停业 3 秒、重复签收一批件。

线上现象：发布触发 rebalance → 消费停顿 → 下游超时 → 慢消费者被踢 → 风暴。

修正：rebalance 作为变更事件管理：发布时优雅下线、评估窗口、监控重复率。

## 坑 2：会话超时配太紧，GC 停顿即误杀

错误理解：超时短 = 快速发现死消费者，恢复快。

原因：GC 停顿/网络抖动与真死难以区分，短超时放大误杀率。

比喻后果：员工上厕所 10 秒就按离职处理，全店重排。

线上现象：大促期间 GC 频繁 → 消费者连环被踢 → 全组风暴。

修正：会话超时按"最坏停顿 + 余量"配置；用 static membership 减少重排。

## 坑 3：堆积就加消费者（神话⑦）

错误理解：消费者多了，处理的件就多了。

原因：并行度上限是分区数，不是消费者数。

比喻后果：柜台 4 个，雇 20 个柜员，16 个闲站。

线上现象：lag 不降，实例空转，还触发 rebalance 风暴。

修正：先查分区数与瓶颈层，再决定加分区还是优化下游。

## 坑 4：分区数拍脑袋定小

错误理解：先建小的，不够再加。

原因：Kafka 分区只增不减；加分区破坏 Key 路由（mq-04 坑 5）。

比喻后果：柜台 2 个开业，大促爆单后加柜台，老客户排队顺序全乱。

线上现象：大促 lag 爆表，加分区后顺序消息乱序事故。

修正：按峰值并行度 + 增长预留设计分区数；Kafka 分区可增不可减（增的是"空分区"，存量消息不会自动迁移过去，消费并行度立即提升、历史数据仍留在旧分区；要重分布历史数据或更换 Key 路由，需重建主题）——扩吞吐必须加分区（本篇 L4）。

## 坑 5：分区数拍脑袋定大

错误理解：分区多 = 吞吐高，多建没坏处（神话⑤）。

原因：每分区有文件、元数据、复制、协调成本；批量变小延迟上升。

比喻后果：柜台开了 200 个，多数空着，房租水电照付。

线上现象：小消息场景分区过多 → 端到端延迟升高、文件句柄紧张。

修正：分区数 = 峰值并行度需求，不是越大越好；成本清单见本文 L4。

## 坑 6：踢人两把尺子只用一把

错误理解：配好 session.timeout 就完了。

原因：会话超时管"活着"，轮询超时管"干活"——两个维度缺一不可。

比喻后果：只查考勤不查产出，坐班摸鱼的人占着工位不放。

线上现象：消费者活着但不 poll（阻塞在业务逻辑）→ 分区被死占。

修正：session.timeout（活着）+ max.poll.interval（干活）双尺子配置。

## 坑 7：组内分配策略配置不一致（RocketMQ）

错误理解：分配算法是客户端自己的事，各配各的。

原因：RocketMQ 无协调器，全组算法必须一致，否则结果冲突。

比喻后果：两个店长用不同分货规则，同一件货分给两个柜员。

线上现象：队列被两个消费者同时消费 → 重复处理 → 资损。

修正：分配策略随配置中心统一下发，全组强一致。

## 坑 8：CooperativeSticky 是银弹

错误理解：用了渐进式 rebalance 就没有事故了。

原因：Cooperative 缩小停摆窗口与重复面，不解决踢人误判的根源。

比喻后果：交接改成"只换要换的货架"，但员工频繁离职照样乱。

线上现象：用了 2.4+ 仍遇到 storm——根源是消费端抖动，不是分配策略。

修正：渐进式策略 + 消费端健壮性 + 超时余量三管齐下。

# 📚 版本勘误表

| 错误说法 | 准确说法 |
| ---- | ---- |
| "堆积就加消费者" | 并行度上限是分区数；加消费者解决可用性冗余，加分区解决并行度 |
| "分区越多吞吐越高" | 分区是并行度上限也是成本函数；按峰值并行度设计 |
| "组长说了算" | 组长只是执行分配策略的执行者，权威是协调器 |
| "RabbitMQ 也有 rebalance" | RabbitMQ 竞争消费无队列绑定，没有 rebalance 概念（无确定性粘性绑定/组内位点托管，但有轮询分摊） |
| "rebalance 是正常功能，不用管" | 机制正常，但三环事故链（停摆/重复/风暴）必须管理 |
| "CooperativeSticky 解决风暴" | 缩小停摆窗口与重复面，不解决踢人误判根源 |
| "分区数可以随便加" | Kafka 只增不减；加分区破坏 hash(key)%N 的 Key 路由（顺序断裂） |
| "慢消费者只是自己慢" | 慢消费者触发 rebalance 拖着全组慢（抖动传染） |
| 坦白：我以前也讲错过"加消费者就能解决堆积" | 只有 4 个柜台，20 个柜员也白搭——先查分区数再动刀 |
| 坦白：我以前也讲错过"rebalance 瞬间没有损失" | eager 模式全组停摆 + 未提交位点重复，两笔账都要付 |

<a id="decisions"></a>

# 🏆 生产决策卡

## Decision Card 1：库存组扩容预案

### 场景

大促前库存组 4 队列 4 实例，预估峰值 3000 msg/s，单实例 500 msg/s。

### 判断

分区数按峰值并行度定 8（预留余量）；实例数 8（=分区数，含故障冗余）；CooperativeSticky；双超时按最坏处理时长 + 余量。

### Mechanism → Decision

| 机制 | 工程决策 |
| -- | ---- |
| 并行度上限 | 分区数 = 峰值/单实例能力 + 预留 |
| 故障韧性 | 实例数贴分区数（空转余量换韧性） |
| 停摆窗口 | CooperativeSticky 渐进式 |
| 重复兜底 | 幂等表（mq-04）+ 对账（mq-03） |

### 禁止决策

- lag 出现后临时加消费者（无用 + 风暴）
- 大促中改分区数（Key 路由断裂 + 顺序事故）

### 验收指标

- 峰值期 lag 曲线平稳，无告警
- 单实例宕机演练：lag 影响 ≤ 阈值，无风暴
- 发布演练：优雅下线，无全组停摆

---

## Decision Card 2：rebalance 风暴处置

### 场景

某组反复风暴，消费进度回退，下游重复轰炸。

### 判断

按三环排查：①谁是反复被踢的成员（GC/慢处理/网络）②分配策略与超时配置是否合理 ③static membership 是否可用；先摘除抖动实例止血，再修配置。

### Mechanism → Decision

| 机制 | 工程决策 |
| -- | ---- |
| 定位抖源 | 监控被踢成员的心跳/GC/处理时长 |
| 止血 | 摘除抖动实例（或增大超时余量） |
| 治本 | 消费端健壮性（GC 调优/处理时长拆分） |
| 减少触发 | static membership（group.instance.id） |

### 禁止决策

- 无脑增大超时（死消费者占分区不释放）
- 风暴期间加分区/加消费者（火上浇油）

### 验收指标

- 24h 内 rebalance 次数归零或阈值内
- 下游重复率 = 幂等兜底后业务效果恰好一次

---

## Decision Card 3：新建主题分区数评审

### 场景

新主题 ORDER_EVENT 创建前，团队对分区数有分歧。

### 判断

四步法：峰值消息速率 ÷ 单分区消费能力 → 并行度需求 → 增长预留（1~2 年）→ 与顺序需求交叉验证（Key 路由不因分区变化断裂的假设前提是创建后不变）。

### Mechanism → Decision

| 机制 | 工程决策 |
| -- | ---- |
| 并行度 | 峰值速率 / 单分区能力 |
| 预留 | ×1.5~2 增长系数（按业务增速预估） |
| 顺序 | 创建后不变更（Key 路由依赖 N） |
| 成本 | 分区成本在本文 L4 复核（文件/元数据/复制） |

### 禁止决策

- "先建 4 个，不行再加"（只增不减 + 路由断裂）
- "建 200 个反正不亏"（成本真实存在）

### 验收指标

- 上线 1 年 lag 峰值 ≤ 预留容量
- 无 Key 路由变更事故记录

<a id="cross-language"></a>

# 🌍 跨语言视角

## 同一个问题：消费组成员管理

| 语言 | 客户端形态 | 与 rebalance 的关系 |
| -- | ---- | ---- |
| Java | KafkaConsumer poll 循环 | 协调器驱动，poll 内触发 join/sync |
| Go | sarama 组消费 / franz-go | 同样实现 join/sync；消费者回调需快速返回避免误杀 |
| Rust | rdkafka StreamConsumer | 协调器驱动；poll 循环与业务并行 |
| Python | confluent-kafka 回调 | 回调模型下"处理慢"更隐蔽——回调阻塞即轮询超时 |

## 跨语言仍成立的判断力

1. **处理慢 = 被踢风险**：任何语言的消费循环，业务处理时长都会换算成 poll 间隔——慢处理在回调模型（Python）与轮询模型（Java/Go）里都是同一颗雷。
2. **两阶段协议与语言无关**：join/sync 的协调语义由 Broker 实现，客户端语言只是语法不同。
