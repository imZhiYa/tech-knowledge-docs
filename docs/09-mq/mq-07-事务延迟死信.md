# ⏳ MQ 事务消息、延迟消息与死信深度解析：从"事务消息解决分布式事务"的神话到异常件中心的三条流水线

> 这不是一篇半消息 API 讲解。
>
> 本文只追踪一个主线：**Message E 进异常件中心**。
>
> E 在正常流程里被签收了。但 MQ 世界里有一批"特殊件"：E 的兄弟——半消息（事务悬而未决）、延迟件（定时才该派送）、坏件（永远处理失败）。它们都进了异常件中心。本篇追踪这三类特殊件的完整命运：它们为什么存在、靠什么机制运转、在什么条件下失效。
>
> 看 E 如何穿透：双写之缝 → 半消息 → 四条事务路径的真相 → 延迟消息的真相 → 死信的真相 → 生产决策

# 写在最前面：两个神话，一条主线

mq-06 的结尾留下一笔账：并行度被分区数锁死之后，**消息形态本身还能提供什么能力**。本篇回答它，同时破解两个神话：

1. **神话⑧**：DLQ 是可靠性终点——真相是 DLQ 是故障的开始，它后面还有归因、修复、重放、幂等、过期五步。
2. **神话⑨**：事务消息解决分布式事务——真相是半消息只覆盖"本地事务 + 发消息"这一种协调模型，Kafka 事务是另一个模型，两者都不是通用分布式事务。

本文的全部内容，是讲清异常件中心的三条流水线：**事务（悬案流水线）、延迟（定时流水线）、死信（坏件流水线）**——它们各解决什么问题、各留下什么账。

## Level 1：双写之缝——为什么要"原子"

一句话认知墙：先发消息还是先提交事务？为什么两个顺序都是错？

### 前置知识关卡

- [ ] 知道"双写一致"陷阱（mq-00 L4 埋的引子）
- [ ] 知道 at-least-once 与对账（mq-03）

### Why——两个顺序，两个缝

**徒弟**：订单支付成功了，我要更新订单状态（本地事务），还要发 PaymentSucceeded 事件 E。先做哪个不都行吗？

**老陈**：都行——也都错。把两个顺序的失败路径都走一遍：

```text
方案 A：先发 E，再提交本地事务
  发 E 成功 → 本地事务回滚（库存不足/校验失败）
  → E 已经飞出去了 → 下游扣库存对着"不存在的支付"执行
  ★缝一：消息说了，事务没做

方案 B：先提交本地事务，再发 E
  事务提交成功 → 发 E 失败（Broker 挂了/网络断了/超时）
  → 状态变了但没人知道 → 下游永远等不到 E
  ★缝二：事务做了，消息没说

重试方案 B 能救吗？
  发 E 失败重试 → 重试成功 → 看起来好了
  但进程在"事务已提交、消息未发"之间崩溃 → 重启后重试逻辑在哪？
  → 消息最终没发，账永远悬着
```

> 📌 最容易被误解的一点：**"重试发送"解决不了缝二**。事务提交与消息发送之间的崩溃窗口，重试逻辑本身没有持久化的记忆——进程重启，重试就没了。**真正的解法是把"发 E"和"本地事务"绑成一个原子动作**，让失败恢复依赖系统的持久化状态，而不是进程内存里的重试计划。

### What——原子动作的三个候选

```text
候选一：本地消息表（业务库 + 消息表同事务）
  订单状态 和 待发消息 写在同一个数据库事务里
  定时任务扫描消息表 → 补发未发送的消息
  → 原子性由"同一个数据库事务"保证

候选二：RocketMQ 半消息（两阶段）
  先发一条"半消息"（消费者不可见）→ 执行本地事务
  → 提交则半消息转正（可见），回滚则删除
  → 原子性由"Broker 持币待决 + 回查"保证

候选三：Kafka 事务（跨分区原子写入）
  事务内写业务 Kafka 主题 + 事务标记
  消费者 read_committed 只读已提交
  → 原子性由"Kafka 事务日志"保证（但只管 Kafka 内部）
```

**这三个候选的原子性来源完全不同，覆盖的边界完全不同**——这正是神话⑨ 的入口，Level 3 摆上台面。

### Transfer——这个思想还能迁移到哪里

1. **"两个系统之间的缝"是所有分布式一致性问题的共同形状**：写 DB + 发消息、写缓存 + 写 DB、更新订单 + 扣库存——缝的位置不同，解法家族相同（本地消息表/事务/对账）。
2. **崩溃窗口的分析方法**：先提交后发送 / 先发送后提交——每个顺序都画崩溃点，两个缝就都露出来了。
3. **持久化记忆 vs 内存重试**：恢复逻辑必须依赖持久化状态，不能依赖进程内存。

本层留下的新账：原子动作的三个候选里，半消息最"像一个通用解法"——它到底怎么运作？崩溃之后靠什么兜底？→ 逼出 Level 2。

### Level Ending

```
🔴 口诀：双写必有缝，原子才能关。
```

## Level 2：半消息机制——悬案流水线

一句话认知墙：半消息是怎么做到"消费者看不见，又不会丢"的？

### 前置知识关卡

- [ ] 能画出双写之缝的两个方向（答不出回 Level 1）
- [ ] 知道消息落盘与副本（mq-02/mq-03 的存储与可靠性基础）

### Why——"持币待决"的三个要求

**老陈**：半消息的本质是"Broker 替我们持币待决"——它要满足三个要求：

```text
要求一：消费者不可见（不能对着未定事务的 E 干活）
  → 半消息不进入业务 Topic，存到独立的位置

要求二：不能丢（持币期间 Broker 崩溃，币就没了）
  → 半消息必须落盘，并依赖副本（mq-08 展开）

要求三：悬案必须能结（Producer 在提交前崩溃）
  → Broker 必须主动回查：这单到底成没成
```

**三个要求对应三个机制：隔离存储、持久化、回查**。前两个是存储问题（mq-02/mq-08），回查是半消息的灵魂。

### What——半消息两阶段 + 回查的完整机制

```text
阶段一：prepare（落"悬案"）
  Producer → Broker：发送半消息（带事务标识）
  Broker：写入半消息存储（业务消费者不可见）
  Broker → Producer：半消息已收（此时还没执行本地事务）

阶段二：本地事务
  Producer：执行本地业务事务（更新订单状态）
  结果二选一：
    commit   → Producer 通知 Broker：半消息转正（写入业务 Topic）
    rollback → Producer 通知 Broker：删除半消息

崩溃兜底：回查（check back）
  场景：Producer 在阶段二崩溃，commit/rollback 永远没到
  Broker：定期检查悬案半消息（超过事务超时未决）
         → 向 Producer 发起事务状态回查请求
  Producer：回调 checkLocalTransaction → 查本地事务结果
         → 返回 commit / rollback / unknow（再查）
```

### How——E 的完整半消息旅程

```text
T0  支付成功 → 事务协调器发起
T1  发半消息：E(half) 带事务 ID → Broker 存储（不可见）★悬案
T2  执行本地事务：更新订单状态（DB 事务提交）
T3  发 commit → Broker 把 E 从半消息区转入业务 Topic ★转正
T4  下游开始消费 E（此时事务已定）
T5  崩溃推演：
     - T2 前崩溃 → 半消息永远悬着 → Broker 回查
       → checkLocalTransaction：本地事务没提交 → rollback → 删除
     - T2 后崩溃 → Broker 回查
       → checkLocalTransaction：本地事务已提交 → commit → 转正
     - T3 消息丢失 → 同上，回查兜底
```

**徒弟**：回查的"checkLocalTransaction"怎么知道本地事务提交没有？它查什么？

**老陈**：它查的是**业务自己提供的状态查询逻辑**——比如查订单表的状态字段（PAID / FAILED）。**回查不是魔法，它把"事务状态"这个事实留在了业务库里，Broker 只是定期来问**。这也揭示了半消息的本质：**它没有消除"事务状态存在业务库"的事实，只是把"决定消息去留"的时机从发送时推迟到回查时**。事务结果的内存版可能丢了，但业务库里的状态不会丢——这才是半消息可靠性的根基。

### Transfer——这个思想还能迁移到哪里

1. **持币待决 = 延迟决策**：把"立即决定"推迟到"证据充分时决定"，配合定期复查（回查）——分布式事务的通用模式。
2. **隔离可见性**：未决数据对消费者不可见（半消息区、Kafka 的未提交事务消息同理）——发布系统的灰度发布同构。
3. **回查 = 对账的主动版**：mq-03 的对账是"被动核对"，回查是"主动询问"——同一思想的两种姿态。

本层留下的新账：半消息把"本地事务 + 发消息"缝上了。但它是"分布式事务"吗？Kafka 的事务又是干什么的？本地消息表为什么也活着？→ 逼出 Level 3（四路径对比，神话⑨ 主战场）。

### Level Ending

```
🔴 口诀：半消息先落账，提交才可见，悬案靠回查。
```

## Level 3：四条事务路径的真相（神话⑨）

一句话认知墙：事务消息到底解决什么、不解决什么？

### 前置知识关卡

- [ ] 能画出半消息两阶段 + 回查（答不出回 Level 2）
- [ ] 知道 Kafka 事务与半消息是不同机制（Level 2 预告）

### Why——神话⑨ 的破解：每个"事务"各管一亩三分地

**老陈**：把方案摆上台面，问同一个问题：**它把哪两个系统原子地绑在一起？** 答案分成两个维度：**原子绑定**（前三个）与**补偿编排**（Saga）——后者根本不追求原子，这是两条完全不同的路径：

```text
维度一：原子绑定（把两方绑成一个原子动作）

RocketMQ 半消息：
  绑定的双方 = 业务本地事务（DB）+ 发消息（MQ）
  原子性来源 = 半消息持币待决 + 回查
  覆盖的模型 = "本地 DB 事务 + 一条消息"的协调模型
  不覆盖     = 两个外部系统之间的事务（A 库 + B 库）
              = 多个 MQ 主题之间的原子写入（那是 Kafka 事务的地盘）

Kafka 事务（transactional producer，KIP-98）：
  绑定的双方 = Kafka 内部多个分区/主题的写入
  原子性来源 = 事务协调器（__transaction_state）+ commit/abort 标记
              + read_committed 隔离；序列号属幂等生产者机制（mq-03），
              不构成跨分区原子性
  覆盖的模型 = 跨分区/跨主题原子可见性
  不覆盖     = 业务本地事务（Kafka 不碰你的 DB）
              = 外部系统（Kafka 事务管不到 Redis/MySQL）

本地消息表（Outbox）：
  绑定的双方 = 业务本地事务（DB）+ 消息表（同一 DB 事务）
  原子性来源 = 同一个数据库事务
  覆盖的模型 = 单库场景的朴素方案
  不覆盖     = 无"业务库 + 消息表同库"条件时的场景

维度二：补偿编排（不追求原子，追求可恢复）

Saga：
  绑定的双方 = 多个外部系统之间（订单 + 库存 + 支付……）
  一致性来源 = 无原子——每个系统各自提交本地事务，
             失败时执行补偿动作（cancel/undo）回滚已完成的步骤
  覆盖的模型 = 跨系统长流程（原子性不存在的场景，
             这是唯一可选的路径）
  不覆盖     = "本地 DB + 一条消息"的原子缝
              （Saga 里每条消息的发送仍要自己解决双写，
              通常配 Outbox/半消息）
```

> 📌 最容易被误解的一点：**Saga 不是消息机制的替代品，是它的上游**。Saga 编排一个跨系统流程（Choreography 事件驱动 / Orchestration 集中协调），流程中的每一步都要发消息、都要解决双写——**Saga 里的每个"发消息"环节，依然要靠半消息或 Outbox 关缝**。把 Saga 和半消息放在同一排对比（"哪个更好"）是错位问题：**半消息管"一步内的原子缝"，Saga 管"多步之间的失败补偿"，两者是嵌套关系不是竞争关系**。

### What——四路径适用场景矩阵

| 路径 | 场景 | 代价 | 局限 |
| ---- | ---- | ---- | ---- |
| RocketMQ 半消息 | 业务事务 + 发消息（订单状态 + 事件 E） | 半消息存储、回查逻辑、回查时延 | 只覆盖单 DB + 单 MQ 协调模型 |
| Kafka 事务 | 多分区/多主题原子写入（ETL 管道） | 事务日志存储、read_committed 隔离 | 不碰外部系统；生态内事务 |
| 本地消息表（Outbox） | 单库 + 消息表同库 | 业务库侵入（消息表）、定时任务 | 跨库不行；多 Broker 不行 |
| Saga | 跨系统长流程（订单/库存/支付编排） | 补偿逻辑、流程状态机、对账 | 无原子性；补偿可能失败需人工兜底 |

**徒弟**：RabbitMQ 呢？它有没有事务消息？

**老陈**：RabbitMQ 的 AMQP 事务（txSelect/txCommit）只覆盖"本次连接内的消息收发"，连"业务 DB + 发消息"都绑不上——生产中没人用它解决双写一致。RabbitMQ 给的可靠发送工具是 **publisher confirms**（异步确认，配合回调重发），它解决的是"确认送达"，不是"事务原子性"（mq-03 已讲）。**没有半消息的产品，双写一致就靠本地消息表或对账补偿**——这就是为什么很多公司自研"发件箱（outbox）"模式。

### How——同一个双写场景，三个方案各自的成败边界

```text
场景：订单支付成功 → 更新订单表 + 发 E

方案一（半消息）：
  成功路径：prepare → 本地事务 → commit → E 可见
  崩溃点：T2 前后 → 回查兜底（Level 2 推演过）
  边界：消息本体存 Broker 半消息存储（RMQ_SYS_TRANS_HALF_TOPIC），
  不在业务库；回查的前提是"业务库的事务结果可查询"（订单状态字段可见）

方案二（本地消息表）：
  成功路径：订单表 + 消息表 同事务 → 定时任务发 E → 删消息表记录
  崩溃点：事务提交后定时任务没跑 → 重启后继续扫 → 兜底
  边界：需要业务库可用、消息表与订单表同库

方案三（Kafka 事务）：
  成功路径：事务内写订单主题 + 支付主题 → commit → 消费者只见已提交
  崩溃点：事务中止 → 已写分区回滚不可见
  边界：业务状态必须也写成 Kafka 消息（把"业务库"换成"消息流"）
       —— 这是流式架构的玩法，不是订单系统的玩法
```

### Transfer——这个思想还能迁移到哪里

1. **先问"原子地绑定了哪两方"**：评估任何"分布式事务"方案，先画出它原子覆盖的边界——边界外都是"可恢复的最终一致"。
2. **发件箱（outbox）模式**：本地消息表思想的产品化——很多现代框架（如 Debezium）把它做成"业务表 + 发件箱表 + CDC"的组合。
3. **"事务"是系统内部语义，跨系统只有恢复性**：架构评审时，听到"跨系统事务"直接降级为"对账 + 补偿"。

本层留下的新账：事务类特殊消息讲完了。异常件中心的第二条流水线是**定时件**——延迟消息。它凭什么"到点才送"？精度能到多少？→ 逼出 Level 4。

### Level Ending

```
🔴 口诀：事务消息不万能，先画原子边界。
```

## Level 4：延迟消息的真相——定时流水线

一句话认知墙：延迟消息是"精确定时器"吗？为什么不是？

### 前置知识关卡

- [ ] 知道半消息的原子边界（答不出回 Level 3）
- [ ] 知道存储引擎的批量与顺序写思想（mq-02）

### Why——延迟消息的两个约束

**老陈**：延迟消息要回答两个问题：**"多久之后投递"怎么表达？"到点"怎么被检测？** 而工程实现里，两个答案都是"粗略的"：

```text
约束一：延迟时间的表达是"级别"，不是"时刻"
  RocketMQ：固定延迟级别（官方定义的一组档位，
            如 1s/5s/10s/30s/1m/2m/……/2h，共 18 级，以官网为准）
  → 想要 7 秒？没有这个档，只能选 5s 或 10s
  → 想要 2026-08-16 09:00 投递？固定级别表达不了

约束二："到点"的检测是"定时扫描"，不是"精准闹钟"
  Broker：按延迟级别把消息写入对应调度主题
        → 定时扫描线程周期性检查到期消息
        → 到期的写入真实业务 Topic
  → 精度 = 扫描间隔 + 级别粒度，不是秒级定时器
```

### What——RocketMQ 延迟消息的完整机制

```text
Producer：消息设置延迟级别 N
    ↓
Broker：写入 SCHEDULE_TOPIC_N 调度主题（按级别分区）
    ↓
定时扫描线程（ScheduleMessageService）周期性扫描各调度主题
    ↓ 到期（当前时间 ≥ 可投递时间）
把消息写入真实业务 Topic ★转正
    ↓
消费者正常消费（此时才可见）

> 📌 存储注脚：**"转正"是一条新消息的完整写入**——调度主题→业务主题是两份存储，重试（%RETRY%→%DLQ%）同理。重试/延迟/死信都以新消息身份重新落盘（重试一次多存一份），这是 mq-01/mq-02 说的"索引是视图、重写是实体"的落点。
```

> 📌 最容易被误解的一点：**延迟消息的"延迟"是"存储上的延迟"**——消息先躺在调度主题里，到点才转入业务主题。它不是"Broker 记住未来某个时刻"的定时器，而是"分批扫描 + 到期转正"的粗粒度机制。**RocketMQ 任何标称"秒级"的延迟消息，实际投递精度都要按"级别粒度 + 扫描周期"重新评估**（Pulsar 按消息时间戳投递、精度更高，见下表）——这决定了"支付超时关单"这类业务能用它（容忍分钟级误差），"秒杀倒计时"不能用它。

### What——四家对比

| 产品 | 延迟能力 | 机制 | 精度边界 |
| ---- | ---- | ---- | ---- |
| RocketMQ | 固定延迟级别 | 调度主题 + 定时扫描 | 级别粒度 + 扫描周期 |
| Kafka | 无内置 | 自己实现（时间戳 + 消费端等待/分层时间轮） | 自研决定的精度 |
| RabbitMQ | delayed message exchange 插件 | 插件内部存储 + 定时投递 | 非 AMQP 标准，行为以插件文档为准 |
| Pulsar | 延迟投递 | 消息带 deliverAt 时间戳，broker 按游标延迟投递 | 精度高于扫描式（按消息时间戳） |

**徒弟**：为什么 RocketMQ 不做成"每一条消息一个精确时间戳"？技术上不难吧？

**老陈**：技术不难，成本要权衡。**"按消息精确定时"的最直白实现（每条消息一个独立定时器）确实是巨大的内存与调度开销**——但工程上有更省的路线：层级时间轮以近似 O(1) 的摊还成本维护海量定时器（Kafka 服务端 Purgatory 就是这类结构；Pulsar 的 delayed tracker 则是按投递时间戳排序的优先队列 + delayed index 索引恢复，实现不同、目标相同）。RocketMQ 选"固定级别 + 定时扫描"更多是**历史设计取舍**（把定时成本摊到固定调度主题，扫描一次唤醒一批）：核心权衡依然是"时间粒度换调度成本"，但"成本要命"不是必然结论——**同一需求可以有多种定时结构实现，成本取决于实现而非需求本身**。Pulsar 的按时间戳投递也是基于游标的有序扫描，不是每条消息一个闹钟。

### Transfer——这个思想还能迁移到哪里

1. **批量唤醒 vs 逐条定时**：延迟队列、定时任务调度（Quartz 的批量扫描）、Redis 的过期键惰性删除——都是"扫描式"而非"闹钟式"。
2. **粒度是成本的语言**：业务需求先问"容忍多大误差"，再选机制（分钟级误差 → 固定级别；秒级 → 专用定时器/时间轮）。
3. **调度与业务分离**：延迟消息的调度主题（SCHEDULE_TOPIC）是"调度基础设施"与"业务消息"分离的典范。

本层留下的新账：定时件到点转正，正常消费。但**如果一件消息反复消费失败、重试耗尽，它去哪？**——异常件中心的第三条流水线：坏件流水线（死信）。→ 逼出 Level 5。

### Level Ending

```
🔴 口诀：延迟看级别，精度看扫描。
```

## Level 5：死信的真相——坏件流水线（神话⑧）

一句话认知墙：DLQ 是"可靠性终点"吗？为什么说它是"故障的开始"？

### 前置知识关卡

- [ ] 知道重试的限度与毒消息（mq-04 L2）
- [ ] 知道积压拖磁盘（mq-02 积压与 CommitLog 回收）

### Why——神话⑧ 的破解：DLQ 是起点不是终点

**老陈**：把重试耗尽的消息丢进 DLQ，看起来"系统干净了"——但 DLQ 里的消息不会自己处理自己：

```text
DLQ 三个被高估的假设：
  ① "进了 DLQ 就安全了" —— DLQ 里消息在积压，照样拖磁盘（mq-02）
  ② "DLQ 是可靠性的最后一道防线" —— 防线后没有人处理 = 空防线
  ③ "DLQ 只存不查" —— 不归因、不修复，DLQ 只是"遗忘的仓库"

真相：
  DLQ 是"故障的显式化"——把隐性故障（静默丢失）变成
  显性故障（看得见的积压），让治理有机会发生。
  "进 DLQ"不是终点，"处理 DLQ"才是。
```

> 📌 最容易被误解的一点：**没有 DLQ 的世界不是"没有故障"，是"故障被静默"**。消费失败 → 位点不动 → 消息永远卡在重试 → 或者被跳过 → 数据静默丢失。DLQ 的价值不是"存储"，是**"把隐性故障变成显性清单"**——它是可观测性的工具。神话⑧ 的破解就在这：**DLQ 不增加"处理成功率"层面的可靠性（它不修消息），但它提供"故障消息持久保存、防静默丢弃"——这是消息不丢层面的可靠性**；DLQ 让故障可以被看见、被治理，真正闭环靠治理流程。

### What——死信治理五步

```text
第一步：归因（为什么失败）
  消息格式损坏？业务逻辑缺陷？下游依赖故障？
  → DLQ 消息要带失败原因（重试日志/异常堆栈）

第二步：修复（修谁）
  数据问题 → 修消息（补字段/改格式）
  代码问题 → 修消费逻辑，重新部署

第三步：重放（怎么回到业务流）
  按位点/时间/消息 ID 选择重放范围
  → 重放后消息再次进入消费流程
  → 重放是"变更操作"，必须受控：
     权限（谁能重放）——重放 = 对下游重复投递，
     默认只开放给治理责任人，禁止任意开发者随手重放
     审批（为什么重放）——重放范围与理由留痕
     影响面评估（重放给谁）——重放会再次轰炸下游，
     下游服务能扛住重放流量吗（限流/降级预案）
     演练（重放前先试）——先小范围重放验证，再全量

第四步：幂等（重放不重效果）
  重放必然可能重复（mq-04）→ 幂等表兜底
  → 没有幂等就重放 = 把故障放大

第五步：过期（别让 DLQ 长成毒瘤）
  DLQ 也要有保留期与清理策略
  → 不清理的 DLQ 占磁盘、拖慢检索（mq-02 积压教训）
  → 保留期还决定"重放窗口"：超过保留期的坏件
    想重放也无从放起——重放能力受保留期约束
```

### What——四家 DLQ 机制对比

| 产品 | DLQ 机制 | 重试默认 | 备注 |
| ---- | ---- | ---- | ---- |
| RocketMQ | 内置：%RETRY%组 重试队列 → %DLQ%组 死信队列 | 重试上限后进 DLQ（默认值以官网为准） | 重试间隔按延迟级别递增 |
| Kafka | 无内置 | 消费失败不提交位点 → 原地重试 | 业界自建 DLQ topic + 重放工具 |
| RabbitMQ | DLX（dead letter exchange） | 消息被拒（nack）/过期/队列满 → 转发 DLX | 需要显式配置绑定 |
| Pulsar | dead letter topic | 消费失败达阈值 → 进 DLQ topic | 需配置策略 |

**徒弟**：Kafka 没有内置 DLQ，那 Kafka 场景的坏件怎么处理？

**老陈**：自建三件套：**DLQ 主题（存坏件 + 失败原因）+ 重放工具（按位点/时间重放）+ 幂等保障（mq-04）**。Kafka 的哲学是"基础能力少而精，上层能力自己搭"——DLQ 不是它的基础能力，是上层治理。这也解释了为什么 Kafka 场景的团队往往要自研消费治理平台。**"内置 DLQ"（RocketMQ）与"自建 DLQ"（Kafka）的差别，是产品哲学（开箱即用 vs 可组合积木）在可靠性治理上的投影**。

### Transfer——这个思想还能迁移到哪里

1. **显式化故障是治理的第一步**：DLQ、告警、错误队列——先让故障可见，才能治理（可观测性第一性原理）。
2. **治理流程五步法可迁移**：归因 → 修复 → 重放 → 幂等 → 过期——ETL 管道、批处理失败重跑、Webhook 重试都适用。
3. **"终点思维"是运维大忌**：任何"兜底"组件（备份、DLQ、降级开关）都不是终点，都要设计"处理它的人与流程"。

本层留下的新账：三条流水线都讲完了。它们有一个共同的根基——**半消息不能丢、延迟消息不能丢、DLQ 消息不能丢，都依赖 Broker 的持久化与副本**。特殊消息形态的可靠性，最终押在存储与复制上。→ 逼出 mq-08（副本与高可用）。

### Level Ending

```
🔴 口诀：死信非终点，治理五步走。
```

## Level 6：生产决策与参数配置

一句话认知墙：事务、延迟、死信三个方案，到了评审桌上怎么决策、配什么参数？

### 前置知识关卡

- [ ] 能说出四路径原子边界（含 Saga 补偿编排）（答不出回 Level 3）
- [ ] 能说出死信治理五步（Level 5）

### Why——决策的轴心是"边界"与"账"

**老陈**：三个方案的决策各有一条轴：

```text
事务消息：先画原子边界（绑定了哪两方），边界外全是对账
延迟消息：先问精度需求（容忍多大误差），再选机制
死信：先答治理问题（谁处理 DLQ、处理流程是什么），再谈配置
```

### What——决策清单

```text
事务决策三问：
① 要原子绑定的是"业务 DB + 发消息"吗？ → 半消息/本地消息表
② 业务状态在"消息流"里吗（流式架构）？ → Kafka 事务
③ 两个外部系统要原子？ → 不存在，直接降级对账+补偿

延迟决策三问：
① 精度需求？ → 分钟级可用固定级别；秒级需自研定时器
② 消息量？ → 大批量延迟消息，扫描式成本摊薄；少量可用专用服务
③ 投递表达？ → 固定档位够用吗？要精确时刻必须换机制

死信决策三问：
① 谁处理 DLQ？ → 无人值守的 DLQ 不要建（= 遗忘仓库）
② 重试上限多少？ → 按失败可恢复性定（网络抖动可长重试，
   业务逻辑缺陷重试无用，短重试快速进 DLQ）
③ 重放流程？ → 归因/修复/重放/幂等/过期五步闭环了吗
```

### How——E 的兄弟们的完整治理推演

```text
场景一：订单支付双写（E 的诞生）
  决策：半消息（本地事务 + 发消息的协调模型）
  配置：事务超时 + 回查间隔（默认值以官网为准）
  验收：故障注入（kill producer）→ 回查正确转正/回滚

场景二：支付超时关单（延迟消息）
  决策：固定延迟级别（关单容忍分钟级误差）
  配置：延迟级别 = 支付超时窗口对应档位
  验收：定时投递精度 = 级别粒度 + 扫描周期（实测确认）

场景三：坏件（DLQ）
  决策：重试上限（快速失败进 DLQ）+ 治理五步闭环
  配置：重试次数、重试间隔递增
  验收：DLQ 消息 24h 内归因完成率、重放成功率、幂等保障
```

**徒弟**：重试上限怎么定？网上说 16 次，能照抄吗？

**老陈**：不能照抄，要按失败的可恢复性推：**网络抖动/下游瞬时故障 → 值得多次重试（递增加间隔）；业务逻辑缺陷（格式错、状态错）→ 重试 1~3 次就该进 DLQ**——因为重试只是反复支付同样的失败成本。重试上限的决策依据是"失败的可恢复性"，不是默认值。**重试参数的哲学：每一次重试都在花"延迟+重复风险"买"恢复概率"，可恢复性低的失败，越早进 DLQ 越省。**

### 📋 关键参数配置与注意事项

> 默认值随版本变化，以官方文档为准（写作基线 RocketMQ 5.x / Kafka 3.5.x / RabbitMQ 3.13.x），本文只讲参数控制的机制与配错的事故。

| 参数 | 控制的机制（指向本文 Level） | 配错的线上事故 |
| ---- | ---- | ---- |
| 事务超时 / 回查间隔（RocketMQ） | 悬案半消息何时触发回查（L2） | 超时太短 → 正常慢事务被回查干扰；太长 → 悬案期拉长、半消息积压 |
| 事务状态回查回调（RocketMQ checkLocalTransaction） | 崩溃后事务结果确认（L2） | 回调查错表/查错状态 → 已提交事务被回滚，消息丢失 |
| 延迟级别（RocketMQ messageDelayLevel） | 延迟档位定义（L4） | 档位定义被改 → 既有消息延迟语义错乱（改前必须评估存量消息） |
| 重试次数（RocketMQ 消费重试 / Kafka 无内置） | 失败重试上限（L5） | 无上限 → 毒消息无限重试占队列（mq-04 神话④ 反噬）；太小 → 可恢复失败过早进 DLQ |
| 重试间隔递增（RocketMQ 按延迟级别） | 重试节奏（L5） | 递增过慢 → 重试周期过长拖延迟；过快 → 下游被打爆 |
| transaction.timeout.ms（Kafka 事务超时） | 事务最大时长（L3） | 超时过短 → 长事务被强制中止，业务数据丢失 |
| isolation.level（Kafka read_committed） | 消费者是否只见已提交事务（L3） | 配 read_uncommitted → 读到未提交事务消息（脏读），消费已回滚的数据 |
| DLX 绑定（RabbitMQ dead letter exchange） | 坏件转发目的地（L5） | 未绑定/绑定错 → 死信丢失或进错队列 |

```text
   ↓
T6 死信治理：归因 → 修复 → 重放 → 幂等 → 过期
```

## Self Check

| 问题 | 必须回答的不变量 |
| ---- | ---- |
| 双写之缝？ | 消息说了事务没做 / 事务做了消息没说 |
| 半消息三要求？ | 不可见 / 不丢 / 悬案能结（回查） |
| 回查查什么？ | 业务库的事务状态（checkLocalTransaction） |
| 四路径原子边界？ | 半消息=DB+MQ；Kafka 事务=MQ 内部；Outbox=同库；Saga=跨系统补偿（无原子） |
| 延迟消息精度？ | 级别粒度 + 扫描周期，不是秒级定时器 |
| 死信治理五步？ | 归因 / 修复 / 重放 / 幂等 / 过期 |
| DLQ 的本质价值？ | 把隐性故障变成显性清单（可观测性工具） |

<a id="pitfalls"></a>

# ⚠️ 坑与细节

## 坑 1：用重试解决双写之缝

错误理解：发送失败重试几次就补上了。

原因：事务已提交、消息未发之间的崩溃窗口，内存里的重试计划随进程消失。

比喻后果：单据落账了，通知信没寄出，寄信计划记在记账员脑子里——记账员下班就忘了。

线上现象：进程重启后消息永远缺失，下游等不到事件，对账才暴露。

修正：本地消息表 / 半消息 / 对账补偿——恢复依赖持久化状态。

## 坑 2：回查回调查错状态

错误理解：checkLocalTransaction 随便查个字段就行。

原因：回查必须返回"事务最终状态"——查错状态 = 已提交被回滚。

比喻后果：回访问"这单成了吗"，调查员看错表格说"没成"，好单被撤。

线上现象：订单已支付，消息被回滚，下游永远不知道支付成功。

修正：回查逻辑与业务事务状态严格对应（查权威状态字段），灰度验证崩溃场景。

## 坑 3：把 Kafka 事务当分布式事务（神话⑨ 的余毒）

错误理解：Kafka 事务 = 跨系统分布式事务。

原因：Kafka 事务只覆盖 Kafka 内部跨分区/跨主题原子性，不碰业务 DB。

比喻后果：以为买了"全城配送险"，其实只保自家仓库内的货。

线上现象：用 Kafka 事务实现"DB + 消息"原子性，发现事务管不到 DB，业务照旧双写。

修正：先画原子边界；业务 DB + 消息必须用半消息/本地消息表/对账。

## 坑 4：用延迟消息做秒级定时

错误理解：延迟消息 = 定时器，随便用。

原因：固定级别 + 定时扫描，精度是分钟级。

比喻后果：闹钟只有整点档，想 9:03 起床只能 9:00 或 10:00。

线上现象：秒杀倒计时用延迟消息，投递误差数秒，业务错乱。

修正：按精度需求选机制：分钟级用固定级别，秒级自研定时器/时间轮。

## 坑 5：改延迟级别档位定义

错误理解：档位是我配的，想改就改。

原因：存量延迟消息按旧档位表映射，改表后语义错乱。

比喻后果：闹钟刻度全改了，已定的闹钟全部错乱。

线上现象：改档位后，既有延迟消息全部乱时投递。

修正：档位定义创建时定死；必须改时评估存量消息迁移方案。

## 坑 6：重试无上限（神话④ 的重演）

错误理解：多试几次总归能成功。

原因：业务逻辑缺陷的消息重试一万次也失败，还占队列、压下游。

比喻后果：地址写错的件反复派送，每次都占用派送员。

线上现象：毒消息无限重试，队列堆积、下游被打爆。

修正：按失败可恢复性定上限：可恢复（网络）多试，不可恢复（逻辑）早进 DLQ。

## 坑 7：建了 DLQ 没人管（神话⑧ 的重演）

错误理解：DLQ 建好就安全了。

原因：DLQ 只是显式化故障；没有治理流程 = 遗忘仓库。

比喻后果：坏件仓库建好了，没有分拣员，坏件烂在仓库。

线上现象：DLQ 积压数月无人问，磁盘告警才发现（mq-02 教训）。

修正：DLQ 与治理流程配套：归因/修复/重放/幂等/过期，告警 + 责任人。

## 坑 8：重放不配幂等

错误理解：重放是重发一次，不会出错。

原因：重放必然可能重复（mq-04：重放 = 重复来源）。

比喻后果：坏件重投，投两次，收货人签两次。

线上现象：DLQ 重放后业务重复（重复扣款/重复发券）。

修正：重放前必须确认幂等兜底（幂等表），重放演练先行。

## 坑 9：半消息积压不监控

错误理解：半消息量小，不用管。

原因：事务挂起（producer 崩溃/回查失败）→ 半消息滞留，且不可见。

比喻后果：悬案件堆在仓库角落，没人盘点。

线上现象：大量半消息滞留，业务消息"消失"，排查半天。

修正：监控半消息积压量与悬案时长，超时告警 + 人工介入。

# 📚 版本勘误表

| 错误说法 | 准确说法 |
| ---- | ---- |
| "事务消息解决分布式事务" | 半消息只覆盖"本地事务 + 发消息"协调模型；跨系统原子性工程上不存在，只有可恢复的最终一致 |
| "Kafka 事务 = 分布式事务" | Kafka 事务只覆盖 Kafka 内部跨分区原子性，不碰业务 DB 与外部系统 |
| "DLQ 是可靠性终点" | DLQ 不增加可靠性，只把隐性故障变成显性清单；治理五步才是闭环 |
| "延迟消息 = 精确定时器" | 固定级别 + 定时扫描，精度 = 级别粒度 + 扫描周期 |
| "重试次数照抄默认值" | 重试上限按失败可恢复性定；逻辑缺陷重试无用，早进 DLQ |
| "RabbitMQ 事务解决双写" | AMQP 事务只覆盖连接内消息收发；publisher confirms 是确认不是事务 |
| "DLQ 消息会自动被处理" | DLQ 里的消息不会自己处理自己，无人治理 = 遗忘仓库 |
| "延迟档位随便改" | 存量消息按旧档位映射，改档位 = 存量语义错乱 |
| 坦白：我以前也讲错过"重试几次就能补上双写缝" | 崩溃窗口的重试计划在进程内存里，重启即失忆——必须靠持久化状态 |
| 坦白：我以前也讲错过"DLQ 建了就是可靠" | DLQ 只是故障的告示牌，治理流程才是处理故障的人 |

<a id="decisions"></a>

# 🏆 生产决策卡

## Decision Card 1：订单支付双写（半消息）

### 场景

订单支付成功后必须"更新订单表 + 发 E"原子生效，Producer 可能随时崩溃。

### 判断

RocketMQ 半消息（协调模型 = 业务 DB + 发消息）；回查逻辑严格对应订单状态字段；故障注入演练崩溃场景。

### Mechanism → Decision

| 机制 | 工程决策 |
| -- | ---- |
| 原子性 | 半消息持币待决 + 回查 |
| 回查状态 | 查订单表权威状态字段（PAID/FAILED） |
| 超时配置 | 事务超时 > 最坏业务事务时长 + 余量 |
| 兜底 | 对账（mq-03）双保险 |

### 禁止决策

- 用"发送重试"替代原子动作（崩溃窗口内存失忆）
- 回查逻辑查非权威字段（已提交被回滚）

### 验收指标

- 故障注入：kill producer（T2 前后）→ 回查转正/回滚正确率 100%
- 半消息积压 = 0（悬案时长告警阈值内）

---

## Decision Card 2：支付超时关单（延迟消息）

### 场景

订单 30 分钟未支付自动关单，容忍分钟级误差。

### 判断

RocketMQ 固定延迟级别（档位覆盖 30 分钟场景）；投递精度实测确认。

### Mechanism → Decision

| 机制 | 工程决策 |
| -- | ---- |
| 延迟表达 | 固定级别档位（30m 级） |
| 精度确认 | 实测投递时延 = 级别粒度 + 扫描周期 |
| 改档治理 | 档位定义创建时定死，禁止运行期改动 |

### 禁止决策

- 秒级业务用固定级别延迟消息
- 运行期改档位定义（存量消息语义错乱）

### 验收指标

- 关单投递时延 p99 ≤ 业务容忍上限
- 超时关单率与人工核对差异 ≤ 阈值

---

## Decision Card 3：DLQ 治理体系

### 场景

消费失败消息需要完整治理闭环，避免 DLQ 变遗忘仓库。

### 判断

重试上限按可恢复性定（网络类多试、逻辑类早进）；DLQ 五步治理流程 + 告警 + 责任人；重放必须配幂等。

### Mechanism → Decision

| 机制 | 工程决策 |
| -- | ---- |
| 重试上限 | 按失败可恢复性分类定（逻辑缺陷 1~3 次） |
| 归因 | DLQ 消息带失败原因（异常堆栈/业务上下文） |
| 重放 | 按位点/时间精确重放 + 幂等表兜底 + 重放权限（责任人专属/审批留痕/影响面评估/先小范围演练） |
| 过期 | DLQ 保留期 + 清理策略（防磁盘绑架，mq-02）；保留期即重放窗口上限 |
| 告警 | DLQ 积压 > 阈值 → 告警 + 责任人 |

### 禁止决策

- 无治理流程的 DLQ（遗忘仓库）
- 无幂等保障的重放（重复轰炸）
- 重放权限开放给任意开发者（重放 = 对下游的重复投递，是变更操作不是自助工具）

### 验收指标

- DLQ 消息 24h 归因完成率 ≥ 阈值
- 重放成功率与业务效果核对（对账）
- DLQ 积压告警响应时长达标

# 🌍 跨语言视角

## 同一个问题：事务与死信

| 语言 | 半消息/事务客户端 | DLQ 处理 |
| -- | ---- | ---- |
| Java | RocketMQ 事务监听器（executeLocalTransaction / checkLocalTransaction） | 消费端 catch + 重放工具 |
| Go | rocketmq-client-go 事务消息 / franz-go 事务 | 自建 DLQ 消费者 |
| Rust | rocketmq-rust / rdkafka 事务 API | 自建 DLQ 消费者 |
| Python | rocketmq-client-python / confluent-kafka 事务 | 回调内 catch + 人工重放 |

## 跨语言仍成立的判断力

1. **回查逻辑是业务逻辑**：checkLocalTransaction 查什么状态，是业务库的语义问题，与语言无关。
2. **"先画原子边界"**：任何语言的任何"事务消息"方案，先问它原子绑定了哪两方。
