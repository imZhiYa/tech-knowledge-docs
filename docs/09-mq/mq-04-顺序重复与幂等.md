# 🔁 MQ 顺序重复与幂等深度解析：从"重试一定更可靠"的神话到"恰好一次"的工程落地

> 这不是一篇幂等方案大全。
>
> 本文只追踪一个主线：**Message E 被重发**。
>
> E 是 `PaymentSucceeded` 事件。mq-03 已经证明：at-least-once 世界里，E 被投递两次是常态，不是事故。本篇追踪 E 第二次到达收件网点时的命运——签收登记（幂等）能不能拦住它，顺序又能保到什么程度。
>
> 看 E 如何穿透：重复来源 → 幂等拦截 → 顺序边界 → 保序代价 → 生产决策

---

# 写在最前面：两个神话，一条防线

mq-03 的结尾留下两笔账：

1. **神话④**：重试一定提高可靠性——真相是重试制造重复、放大堆积、压垮下游。
2. **神话⑥**：顺序消息就是全局顺序——真相是"有序"必须先定义范围，全局有序是假象。

本文的全部内容就是回答这两个问题，并给出唯一可靠的防线：**幂等**。它不是一个库、一个注解，而是"业务键 + 唯一约束 + 拦截前置"的组合设计。

# 🏭 全文唯一比喻：重发件与签收登记

```text
现实世界（货运）                      技术世界（MQ）

重发件（同一包裹第二次上门）        ←→ 重复消息（生产重试/重投/位点回拨）
签收登记（查登记簿，签过就不签）    ←→ 幂等拦截（幂等表/唯一约束）
运单号（每个包裹唯一）              ←→ 幂等键（业务键/消息 ID）
同一条路线按序派送                  ←→ 分区/队列内有序
```

| 比喻元素 | 技术概念 | 唯一职责 |
| ---- | ---- | ---- |
| 重发件 | 重复消息 | 被第二次投递的 E |
| 签收登记簿 | 幂等表/唯一约束 | 记录"这条已处理过" |
| 运单号 | 幂等键 | 识别"同一条消息" |
| 路线派送顺序 | 分区/队列内有序 | 同一业务单元的局部顺序 |

# 正文：五个 Level 打穿"重发件如何被拦住"

<a id="level-1"></a>

## Level 1：重复从哪来——全链路重复来源清单

一句话认知墙：Broker 不是有确认机制吗？为什么消息还会被投递两次？

### 前置知识关卡

- [ ] 能说出 at-least-once 的代价（重复与幂等成本，mq-03 Level 1）
- [ ] 知道"确认丢失"与"发送失败"的区别（mq-03 Level 2）

### Why——确认机制挡不住重复

**徒弟**：mq-03 里说 ack 超时会导致重试，这不就是唯一重复来源吗？配好 acks 不就完了？

**老陈**：超时重发只是四个重复来源之一。把 E 从寄件柜台到收件网点的全程画出来，每一段都有它自己的重复开关：

| 来源 | 机理 | 典型场景 |
| ---- | ---- | ---- |
| ① 生产端重发 | send 超时但 Broker 实际已收，重发产生第二条 | acks 确认丢失（mq-03 L2 推演过） |
| ② Broker 重投 | 消费失败/ack 超时，消息重新投递 | RabbitMQ nack+requeue、RocketMQ 重试队列 |
| ③ 位点回拨 | 消费组位点被人为/故障回退，重新读旧消息 | Kafka 修复回拨、故障恢复 |
| ④ rebalance | 消费者改组，已处理未提交的消息被新消费者再读 | mq-06 主战场，本文只预告 |

**这四个来源没有一个是"配置错误"——它们是分布式系统在失败边界上的正常行为**。所以结论很硬：**重复不是 bug，是常态**；防线不在"杜绝重复"，在"重复时业务效果不翻倍"。

### What——重复的两类性质

```text
性质一：同一条消息投递两次（来源①②③④）
  → 消息内容完全相同（orderId 相同）
  → 幂等键可拦

性质二：两条不同消息表达同一业务事实（生产端业务逻辑重发）
  → 消息内容可能不同（时间戳变了），业务语义相同
  → 必须用业务键（orderId）而非消息 ID 拦截
```

> 📌 最容易被误解的一点：**用消息 ID 做幂等键，拦不住"业务重发"**。支付回调系统重发一次回调，生成了两条不同消息 ID 但同一个 orderId 的 E——如果消费端按消息 ID 去重，库存会扣两次。**幂等键必须取业务语义键，消息 ID 只作辅助**。

### How——E 的第二次上门（完整推演）

```text
① 库存组消费者 C1 处理 E（orderId=O_001）：扣库存成功
② 提交位点前 C1 心跳超时（GC 停顿）→ 被踢出消费组
③ 队列重新分配 → C2 接手 → 从上次提交的位点继续读
④ C2 再次读到 E（orderId=O_001）★重复上门
⑤ C2 查签收登记簿：
   - 无幂等拦截 → 库存扣第二次 → 资损
   - 有幂等拦截 → 发现 O_001 已登记 → 跳过 → 提交位点
```

at-least-once 默认下，第 ④ 步不可消灭（它来自 rebalance 的正常机制），第 ⑤ 步是唯一能拦截它的地方。**防线必须放在业务层，因为只有业务层知道"orderId=O_001 的库存扣减"这件事是否已经发生**。

**徒弟**：那为什么不把位点提交做成"扣库存 + 提交位点"的原子操作？

**老陈**：跨系统原子性做不到（mq-03 L4 已经讲过）。退一步的设计是：**先处理、后提交**（at-least-once），重复交给幂等拦截。你牺牲了"恰好一次投递"，换来"恰好一次效果"——后者才是业务要的东西。

### Transfer——这个思想还能迁移到哪里

1. **重复来源清单法**：任何跨系统交互（支付回调、Webhook、消息推送）先画全链路，标出每一段的"重发开关"。
2. **效果幂等 > 投递幂等**：验收标准是"业务效果发生一次"，不是"消息到达一次"。
3. **防线放在语义层**：只有业务层知道"这件事做过没有"，框架层只能提供工具（唯一约束、分布式锁）。

本层留下的新账：重复是常态，那么"拦截"怎么设计才不会被高并发打穿？幂等表、唯一约束、状态机各有什么取舍？→ 逼出 Level 2。

### Level Ending

```
🔴 口诀：重复是常态，防线在业务。
```

## Level 2：幂等设计——神话④ 的破解

一句话认知墙：幂等就是"加个唯一索引"吗？为什么有人加了唯一索引还是资损？

### 前置知识关卡

- [ ] 能列出四个重复来源（答不出回 Level 1）
- [ ] 知道幂等键必须取业务语义键（Level 1）

### Why——神话④：重试一定提高可靠性吗

**徒弟**：mq-03 里说消费失败要重试，重试不是提高可靠性的标准手段吗？

**老陈**：重试提高的是"送达概率"，不是"业务可靠性"。不加限制的重试有三个反噬：

| 反噬 | 机理 | 线上现象 |
| ---- | ---- | ---- |
| 制造重复 | 每次重试都可能产生重复效果 | 库存扣两次、券发两张 |
| 放大堆积 | 毒消息被反复消费失败，占满重试队列 | 队列越堆越高，正常消息被拖死 |
| 压垮下游 | 重试风暴打向下游服务 | 下游被打挂，全链路雪崩 |

**重试是"有限度的、配幂等的、有上限的"**——这三个定语缺一个，重试就从防线变成事故源。这才是神话④的完整破解。

### What——三种幂等方案的取舍

```text
方案 A：幂等表（独立去重表）
  处理前：INSERT INTO idempotency(unique_key, status) VALUES(?, 'PROCESSING')
    → 插入成功 = 首次处理；插入冲突 = 重复，查状态跳过
  处理后：UPDATE status='DONE'
  优点：支持"处理中/已完成"状态机，可扩展
  代价：多一张表的写入，需要状态清理（TTL）

方案 B：业务表唯一约束（借力打力）
  业务表本身有唯一键：stock_deduct(order_id, ...) UNIQUE
  重复扣减 → 唯一约束冲突 → 捕获 DuplicateKey → 视为已处理
  优点：零额外存储，天然原子
  代价：只能表达"做过没做过"，不能表达"处理中"；冲突只说明记录已存在，不代表上次处理成功（上次可能已提交记录、外部副作用失败且未清理）

方案 C：状态机幂等（业务状态流转）
  订单表加状态字段：PENDING → PAID → INVENTORY_DEDUCTED
  扣库存 = UPDATE orders SET status='INVENTORY_DEDUCTED' WHERE id=? AND status='PAID'
  影响行数 = 0 → 已处理过/状态不对 → 跳过
  优点：状态本身是业务资产，可审计
  代价：状态设计要预留失败回退路径
```

> 📌 最容易被误解的一点：**方案 B 的"冲突"不等于"成功"**。唯一约束冲突只说明"这条记录已存在"——但上次的处理可能失败且未清理（记录已提交、外部副作用失败却没回滚），这是冲突残留的真实成因；回滚删除本身会清掉记录，不会留残留。所以生产上更稳的姿势是**方案 A + 方案 B 组合**：幂等表管"处理中"，唯一约束管"已完成"，两者互相兜底。

### How——E 的幂等拦截完整时序（7 步）

```text
① C2 收到 E（orderId=O_001）
② 幂等拦截：SELECT status FROM idempotency WHERE unique_key='O_001'
   - 无记录 → 插入 PROCESSING（成功 = 抢到处理权）
   - 有记录 → 查状态：
       PROCESSING → 前一个处理者还在处理，本次跳过（或延迟重试）
       DONE → 重复消息，直接提交位点跳过 ★拦截点
③ 业务事务：扣库存 + 写业务表（唯一约束兜底）★业务原子点
④ 更新幂等表 status=DONE
⑤ 提交位点
⑥ 崩溃推演：
   - ③ 成功 ④ 前崩溃 → 下次重复 → 查到 PROCESSING + 业务表已有记录
     → 按业务表补偿状态 → 更新 DONE
   - ② 前崩溃 → 下次重新插入，正常处理
```

**徒弟**：第 ② 步的"查 + 插入"在高并发下不是原子的吧？两个消费者同时查不到、同时插入怎么办？

**老陈**：对，这正是幂等的核心并发问题——**拦截本身必须是原子的**。答案是把"查"干掉，只留"插"：`INSERT ... ON DUPLICATE KEY` 或先插入唯一键，插入成功者获得处理权，冲突者按状态走。**原子性由数据库唯一约束保证，不由应用代码保证**。这也是为什么方案 B 的唯一约束是所有幂等设计的最后底座。

### Transfer——这个思想还能迁移到哪里

1. **拦截前置 + 原子抢占**：先抢"处理权"再做事，是分布式任务去重的通用姿势（定时任务锁、消息去重、请求去重同构）。
2. **"冲突 ≠ 成功"的语义区分**：任何借力唯一约束的方案都要区分"已成功"与"已处理过但失败"。
3. **状态机是幂等的最高形态**：把操作编码成状态流转（UPDATE ... WHERE status=X），幂等变成状态机的自然属性。

本层留下的新账：重复被拦住了。但 E 还有第二个问题——**顺序**。同一个订单的"支付成功"和"退款成功"如果乱序到达，幂等也救不了业务逻辑。顺序到底能保到什么程度？→ 逼出 Level 3。

### Level Ending

```
🔴 口诀：业务键做运单号，唯一约束是底座。
```

## Level 3：顺序的真相——神话⑥ 的破解

一句话认知墙："顺序消息"听起来是 MQ 的基础能力，为什么说"全局顺序"是假的、买不到的？

### 前置知识关卡

- [ ] 能设计幂等拦截的原子抢占（答不出回 Level 2）
- [ ] 知道 Key 路由（mq-00 Level 4）与分区内有序（mq-01 Level 4）

### Why——顺序为什么必须是"范围"的

**徒弟**：文档里说 Kafka 分区内有序、RocketMQ 队列内有序，那我把消息都发到一个分区，不就是全局有序吗？

**老陈**：技术上成立，工程上自杀。一个分区 = 一个消费并发单元（mq-01 L4 讲过"消费者数 ≤ 分区数"）。全局有序意味着**全业务只有一条消费流水线**，吞吐天花板就是单线程处理速度。所以真正的问题是：**你的业务需要多大的顺序范围？** 先定义范围，再谈顺序：

| 顺序范围 | 含义 | 实现 |
| ---- | ---- | ---- |
| 全局有序 | 所有消息全序 | 单分区——吞吐自杀，几乎没人真需要 |
| 分区/队列有序 | 同分区内有序 | 默认能力，免费 |
| Key 有序 | 同一业务键的消息有序 | Key 路由进同一分区（mq-00 L4 的路由） |
| 会话有序 | 同一会话/订单内有序 | Key = orderId / sessionId |

**神话⑥的破解点就在这：顺序消息 ≠ 全局顺序。生产上绝大多数"要顺序"实际是 Key 有序——同一订单的事件不乱序，不同订单之间随便乱。**

### What——Key 路由保序的完整机制

```text
Kafka/RocketMQ 的 Key 有序原理：

   Producer（Key = O_001）          分区/队列
        │
   hash(O_001) % N = 1   ────────→  Queue 1 / Partition 1
                                       │  append 顺序追加
        │                              │
   hash(O_001) % N = 1   ────────→  [支付成功][扣库存完成]（顺序写入）
                                       │  append 顺序追加
        │                              │
   hash(O_001) % N = 1   ────────→  [退款成功]（追加在后）

   同一 Key → 同一分区 → 追加序 = 业务序
   不同 Key → 可能不同分区 → 全局无序（但业务上不需要）
```

> 📌 最容易被误解的一点：**"有序"只是"写入有序"，消费端并发一开，处理就可能乱序**。分区内消息是顺序投递的，但如果消费端开 20 个线程并行处理，线程调度顺序 ≠ 分区顺序——"顺序投递"被"并行处理"破坏。**真正要保序，消费端必须串行处理（Level 4 展开）**。

### How——E 的乱序事故与 Key 路由的修复

```text
错误设计（乱序事故）：
① 订单 O_001 的"支付成功 E1"进入分区 1
② O_001 的"退款成功 E2"进入分区 3（Key 路由缺失/错误）
③ 消费端并发处理：E2 先完成，E1 后完成
④ 库存状态机：先"退款回补库存"，后"扣减库存"——账全乱

正确设计（Key 路由）：
① E1、E2 的 Key 都取 O_001 → 同进分区 1
② 分区 1 内 E1 在前、E2 在后（追加序 = 业务序）
③ 消费端对分区 1 串行处理 → 状态机按序推进
④ 乱序被"路由 + 串行"两道闸门挡住
```

**徒弟**：Key 取 orderId 就万事大吉了吗？

**老陈**：还有两个暗坑。**坑一**：分区数变更（mq-06 详述）——`hash(key) % N` 的 N 变了，同一个 Key 的历史消息和新消息落到不同分区，序就断了。**坑二**：Key 设计错误——比如取 userId，同一用户的两个订单事件会互相排队，造成无关阻塞。**Key 的粒度必须等于"顺序要求的业务单元"**，大了小了都有害。

### Transfer——这个思想还能迁移到哪里

1. **顺序是业务单元的函数**：先问"谁和谁之间必须有序"，再选路由键——分库分表的分片键选择完全同构。
2. **写入序 ≠ 处理序**：任何"保序"设计都要过两道闸：路由保证写入序，串行保证处理序。
3. **范围定义是架构的第一语言**：全局/局部、强一致/最终一致——先定义范围，再谈方案。

本层留下的新账：顺序要保，就得串行；串行了，消费就快不起来——保序和扩容之间有个死结。这个死结怎么解？→ 逼出 Level 4。

### Level Ending

```
🔴 口诀：有序看范围，Key 定生死。
```

<a id="level-4"></a>

## Level 4：保序的代价——串行与扩容的死结

一句话认知墙：顺序消息的消费端为什么快不起来？串行处理到底堵住了什么？

### 前置知识关卡

- [ ] 能解释 Key 路由保序 + 两个暗坑（答不出回 Level 3）
- [ ] 知道消费者数 ≤ 分区数（mq-01 Level 4）

### Why——串行是保序的必然代价

**老陈**：保序的完整链条是"Key 路由 + 分区内有序 + 消费端串行"。前两个免费，第三个收费——而且收的是吞吐的税：

```text
并行消费（不保序）：
  Queue 1 ──┬── 线程 1 处理消息 A
            ├── 线程 2 处理消息 B     ← 处理顺序 = 线程调度顺序 ≠ 写入顺序
            └── 线程 3 处理消息 C

串行消费（保序）：
  Queue 1 ──────→ 线程 1 逐条处理 A → B → C
                                     ↑
                 B 失败重试期间，C 被阻塞（SUSPEND_CURRENT_QUEUE_A_MOMENT）
```

| 消费方式 | 顺序 | 吞吐 | 失败处理 |
| ---- | ---- | ---- | ---- |
| 并发消费 | 无保证 | 高（线程池并行） | 单条失败不影响其他 |
| 顺序消费 | 队列内保证 | 低（串行） | 一条失败阻塞整条队列，直到重试成功或进 DLQ |

**RocketMQ 的顺序消费（ConsumeMessageOrderlyService）是最典型的串行实现**：单队列单线程逐条处理，失败时挂起当前队列（SUSPEND_CURRENT_QUEUE_A_MOMENT）——**一条毒消息可以让整个队列停摆**，这就是保序的真实账单。

### What——保序与扩容的死结图

```text
要保序 → 必须串行 → 单队列吞吐 = 单线程吞吐
要扩容 → 多消费者 → 需要多队列/多分区
多队列 + Key 路由 → 同一 Key 的消息还在同一队列（可以保序）
但：
  队列数受限于分区数 → 并行度有天花板（mq-01 L4）
  分区数不能随便加 → Key 路由会变，序会断（Level 3 坑一）
  单 Key 热点 → 所有消息挤进一个队列，其他队列空闲（热点问题）

死结：
  吞吐 ← 并行度 ← 分区数 ← 可增不可减（改动代价大）
  顺序 ← Key 路由 ← 依赖分区数不变
  → 分区数既是吞吐的解药，又是顺序的毒药
```

> 📌 最容易被误解的一点：**"顺序消息"是"业务约束"，不是"性能优化"**。它不会让系统更快，只会更慢。选它只有一个理由：业务正确性需要它。凡是不需要顺序的业务链路上顺序消息，等于花钱买慢。

### How——E 的顺序消费全流程与阻塞事故

```text
① 订单事件队列 Q1：E1(支付) E2(扣减完成) E3(退款)
② 顺序消费线程逐条处理：
   E1 → 支付成功，更新状态机 ✓
   E2 → 扣减完成，更新状态机 ✓
   E3 → 退款，调用退款服务 ✗ 失败（下游抖动）
③ ConsumeMessageOrderlyService：挂起 Q1，重试 E3
④ 重试 3 次仍失败 → E3 继续占着队列头
⑤ Q1 后续消息（其他订单的事件）全部排队等待 ★阻塞
⑥ 直到 E3 重试成功 / 达上限进 DLQ，Q1 才恢复
```

**徒弟**：这太危险了——一条失败消息拖死一个队列，有没有办法让"同 Key 串行、异 Key 并行"？

**老陈**：这正是工业界的答案：**用 Key 做并行度分片，而不是用队列做分片**。常见做法：消费端按 Key 哈希分发给 N 个"业务串行单元"（每个 Key 一个串行处理器，类似 actor 模型），Key 之间并行、Key 之内串行。RocketMQ 的顺序消费严格版做不到这一点（它锁的是整个队列），所以生产上经常是**队列内并发拉取 + 应用层按 Key 串行**的组合。**保序的粒度从"队列"细化到"Key"，吞吐就从"单线程"变成"N 个 Key 并行"**——这就是保序死结的最优解。

### Transfer——这个思想还能迁移到哪里

1. **Key 级串行 + Key 间并行**：actor 模型、协程按用户分片、数据库行锁——"同单元串行、异单元并行"是并发设计的通用准则。
2. **失败隔离与失败阻塞的权衡**：保序系统的失败处理必然更重——支付清算、订单状态机都是"顺序优先"的场景。
3. **粒度即性能**：锁的粒度、串行的粒度、分片的粒度——粒度设计就是性能设计。

本层留下的新账：保序死结的根子在"消费端怎么组织"——推还是拉？一个队列/分区到底给谁消费？多个消费者怎么分配队列？→ 逼出 mq-05（消费模型：推拉与集群广播）。

### Level Ending

```
🔴 口诀：保序要串行，粒度定吞吐。
```

## Level 5：生产决策与参数配置

一句话认知墙：顺序、幂等两个设计到了架构评审桌上，怎么决策、配什么参数、配错会出什么事故？

### 前置知识关卡

- [ ] 能画出保序死结图（答不出回 Level 4）
- [ ] 能设计幂等三方案（Level 2）

### Why——顺序与幂等是打包决策

**老陈**：这两个设计在生产上从来不是分开做的——**保序场景通常伴随重复风险（串行重试 = 重复投递），重复的消息必须幂等（否则保序毫无意义）**。需要澄清：重复与保序**正交**——重复源于 at-least-once 投递 + 重试，不源于保序本身（at-most-once 或事务投递下保序可以无重复）；但主流工程默认 at-least-once（mq-03），所以"要保序就必然要面对重复"在工程上成立。它们是一对：顺序定义"怎么不乱"，幂等保证"重了也没事"。

### What——决策清单

```text
顺序决策三问：
① 谁和谁之间必须有序？      → 定义 Key 粒度（订单/会话/用户）
② 乱序的后果是什么？        → 业务状态机能校验吗？能容忍吗？
③ 保序的吞吐够吗？          → 峰值单 Key QPS 是否超过单线程处理能力

幂等决策三问：
① 幂等键取什么业务字段？    → orderId / 请求号 / 业务唯一键
② 拦截放在事务内还是事务外？ → 事务内（推荐）：处理 + 登记同事务
③ "处理中"状态要不要？      → 长任务要（防并发抢），短事务可不要
```

> 📌 最容易被误解的一点：**幂等键设计错的一个隐蔽症状是"丢失"而不是"重复"**。比如把幂等键设计得太粗（取 userId），两个不同订单的事件被误判为重复，第二条被吞——**幂等键过粗 = 静默丢业务**，比重复更隐蔽。但这只覆盖"键过粗"这一类；键过细（如消息 ID，本篇坑 1）或查+插被打穿（本篇坑 3）的症状恰恰是"重复"。**设计幂等键要同时防两类错误：过粗吞业务、过细放重复。**粒度必须严格等于业务单元。

### How——E 的完整配置推演

```text
E（订单事件）的配置决策：
① 顺序范围：同一订单内有序 → Key = orderId ✓
② 幂等键：orderId + eventType（同一订单的支付/退款是不同事件）
   —— 只用 orderId 会把退款事件误判为支付重复！
③ 拦截位置：扣库存事务内（处理 + 登记原子）
④ 消费模式：并发消费 + 应用层按 orderId 串行分片
   —— 订单之间并行，订单之内串行
⑤ 保序验证：乱序演练（人为倒灌乱序事件，状态机应拒绝非法流转）
```

**徒弟**：为什么幂等键要加 eventType？订单 O_001 的支付和退款不都该各处理一次吗？

**老陈**：对——正因如此，幂等键必须区分事件类型。`O_001+PAID` 和 `O_001+REFUNDED` 是两个不同的幂等键，各自去重。如果只用 `O_001`，退款事件会被误判为"支付已处理"而吞掉。**幂等键 = 业务单元 + 事件语义**，两者缺一不可。

### 📋 关键参数配置与注意事项

> 默认值随版本变化，以官方文档为准（写作基线 Kafka 3.5.x / RocketMQ 5.x / RabbitMQ 3.13.x），本文只讲参数控制的机制与配错的事故。

| 参数 | 控制的机制（指向本文 Level） | 配错的线上事故 |
| ---- | ---- | ---- |
| max.in.flight.requests.per.connection（Kafka） | 在途请求数：重试时是否乱序（L3） | 非幂等生产 + 在途 > 1 + 重试 → 消息乱序；开启幂等生产后 in.flight ≤ 5 有序列号保序，语义不同 |
| enable.idempotence（Kafka） | 生产端序号去重（mq-03 L2） | 3.0 起默认开启（KIP-679）；旧版本/显式关闭 + 重试 → 生产重复（mq-03 已破） |
| compression.type（Kafka 生产端） | 批量压缩：带宽 vs CPU（L4 吞吐链） | 高压缩比类型（如 zstd 高配）在弱 CPU 机器上拖慢生产端，吞吐反降 |
| RocketMQ 顺序消费模式（orderly vs concurrent） | 队列串行 vs 并发（L4） | 误用 orderly → 一条失败消息阻塞整队列；需要 Key 级并行时仍用 concurrent + 应用层分片 |
| MessageQueueSelector（RocketMQ） | Key 路由选队列（L3） | 未实现/选错 Key → 同订单事件进不同队列 → 乱序 |
| consumeThreadMin/Max（RocketMQ） | 消费线程池（L4 并发度） | 线程数开大 ≠ 吞吐上升（瓶颈在下游 DB）；过大线程池加剧下游压力 |
| max.poll.records（Kafka） | 单次拉取条数（L4 批量度） | 配太大 → 单批处理超时、位点提交粒度变粗；配太小 → 拉取频繁、延迟升高 |

<a id="pitfalls"></a>

# ⚠️ 坑与细节

## 坑 1：用消息 ID 做幂等键

错误理解：消息 ID 全局唯一，天然适合去重。

原因：消息 ID 只标识"传输批次"，不标识"业务事实"——业务重发产生新 ID。

比喻后果：同一份合同换了快递单号重寄，收件人照签两份。

线上现象：支付回调重发导致重复扣库存，幂等表毫无作用。

修正：幂等键 = 业务单元 + 事件语义；消息 ID 只做辅助日志。

## 坑 2：幂等键过粗，重复变丢失

错误理解：键越粗越"安全"（防重复更彻底）。

原因：键覆盖范围超过业务单元，不同业务被误判为重复。

比喻后果：登记簿按"小区"登记，同一小区第二个包裹被拒收。

线上现象：同一用户的两个订单事件，第二个被吞，静默丢业务。

修正：键粒度严格等于业务单元；上线前用双订单场景测试。

## 坑 3："查 + 插"幂等被打穿

错误理解：先查幂等表，没有记录就处理——两步就够了。

原因：两步之间无原子性，并发下两个消费者都"查到没有"。

比喻后果：两个收货员同时翻登记簿，都以为没签过。

线上现象：大促并发下重复扣减，事后翻日志才发现竞态。

修正：原子插入抢占（唯一约束/ON DUPLICATE KEY），插入成功者处理。

## 坑 4：只保写入序，不保处理序

错误理解：分区内有序 = 消费端按序处理。

原因：写入序是 Broker 的，处理序是消费端线程调度的——并发消费下必乱。

比喻后果：快递按顺序送到驿站，取件人蜂拥而上，先后不分。

线上现象：顺序消息配了并发消费，退款先于支付被处理，状态机报错。

修正：保序必须串行处理，或应用层按 Key 串行分片。

## 坑 5：分区数变更破坏 Key 有序

错误理解：分区不够了，加几个就行（mq-01 坑 5 的续集）。

原因：hash(key) % N 的 N 变化，历史消息与新消息路由不同。

比喻后果：货架重排，同一客户的货分到两个货架，先来后到全乱。

线上现象：加分区后同订单事件乱序，幂等表查无此单，状态机拒绝流转。

修正：分区数创建时按峰值并行度定死；必须变更时只能重建主题重分布存量（mq-06 坑 4 展开）。

## 坑 6：顺序消费被毒消息阻塞

错误理解：失败重试是自动的，业务无感。

原因：串行队列里，一条消息失败挂起整个队列（SUSPEND_CURRENT_QUEUE_A_MOMENT）。

比喻后果：一件派不出的件堵在传送带出口，全线停工。

线上现象：一个订单的事件反复重试失败，同队列几百个订单全部延迟。

修正：重试上限 + DLQ + 告警；毒消息人工介入（mq-07 展开）。

## 坑 7：压缩参数一刀切

错误理解：压缩越大越好，省带宽。

原因：压缩吃 CPU——弱 CPU 机器上高压缩比反噬生产端吞吐。

比喻后果：打包太紧，打包员累瘫，出货反而变慢。

线上现象：生产端 CPU 打满，消息延迟飙升，排查发现是压缩级别调太高。

修正：按"带宽瓶颈还是 CPU 瓶颈"选压缩类型与级别；实测为准。

## 坑 8：幂等表不清理

错误理解：幂等表是保险，多存点无所谓。

原因：幂等表随业务量线性增长，PROCESSING 状态残留会成为僵尸记录。

比喻后果：登记簿堆满历史页，翻查越来越慢，还混着没撕掉的半页。

线上现象：幂等表膨胀拖慢查询，残留 PROCESSING 让后续消息全部等待。

修正：DONE 记录按业务窗口 TTL 清理；PROCESSING 超时告警 + 补偿。

<a id="errata"></a>

# 📚 版本勘误表

| 错误说法 | 准确说法 |
| ---- | ---- |
| "重试一定提高可靠性" | 重试提高送达概率；不配幂等与上限，重试制造重复、放大堆积、压垮下游 |
| "顺序消息就是全局顺序" | 顺序必须定义范围；全局有序 = 单分区 = 吞吐自杀，生产绝大多数要的是 Key 有序 |
| "分区内有序，消费端就有序" | 写入序是 Broker 的；并发消费下处理序无保证，保序必须串行处理 |
| "消息 ID 就是天然的幂等键" | 消息 ID 标识传输，不标识业务事实；幂等键必须取业务单元 + 事件语义 |
| "唯一约束冲突 = 已处理成功" | 冲突只说明记录已存在，可能是失败残留；需配合状态区分 |
| "查一下没记录就可以处理" | 查+插无原子性，并发下被打穿；必须原子插入抢占 |
| "幂等键越粗越安全" | 键过粗导致不同业务误判重复，重复变成静默丢失 |
| "顺序消息是性能优化" | 是业务约束；它让系统更慢，只为正确性买单 |
| 坦白：我以前也讲错过"用消息 ID 去重就够了" | 消息 ID 拦不住业务重发；幂等键的语义必须落到业务单元 |
| 坦白：我以前也讲错过"Kafka 分区内有序所以消费端天然有序" | 我漏掉了"处理序"这一半；写入序与处理序是两道独立的闸门 |

<a id="decisions"></a>

# 🏆 生产决策卡

## Decision Card 1：订单事件链的顺序与幂等设计

### 场景

订单 O 的支付/退款事件必须有序、扣库存必须恰好一次，峰值单 Key QPS 低（每订单事件稀疏）。

### 判断

Key = orderId 路由保序 + 消费端按 orderId 串行分片 + 幂等键 = orderId + eventType + 唯一约束兜底。

### Mechanism → Decision

| 机制 | 工程决策 |
| -- | ---- |
| Key 路由 | orderId 哈希进同一队列（写入序） |
| 处理序 | 应用层按 orderId 分片串行（Key 间并行） |
| 幂等 | 幂等表（PROCESSING/DONE）+ 业务表唯一约束双底座 |
| 重复来源 ④（rebalance） | 拦截前置，重复直接跳过 |

### 禁止决策

- 为"保序"把全部消息发进单分区（吞吐自杀）
- 只加唯一索引不处理"冲突≠成功"（失败残留误判）

### 验收指标

- 乱序演练：人为倒灌乱序事件，状态机拒绝非法流转率 100%
- 重放演练：同一批消息重放两次，业务效果恰好一次
- 幂等表 PROCESSING 残留 = 0（告警阈值）

---

## Decision Card 2：日志管道不需要顺序（支线）

### 场景

埋点流水 L 入仓分析（**支线：与 E 不同因果链**），允许延迟与乱序。

### 判断

不设 Key、并发消费、无幂等表——按时间窗口去重即可（分析场景容忍）。

### Mechanism → Decision

| 机制 | 工程决策 |
| -- | ---- |
| 顺序 | 不需要，按事件时间排序在数仓侧做 |
| 重复 | 数仓按 (deviceId, eventId, ts) 窗口去重 |

### 禁止决策

- 给日志管道上顺序消费（花钱买慢，毫无收益）
- 用订单事件的幂等标准要求日志管道（过度设计）

### 验收指标

- 端到端延迟 ≤ 分钟级
- 数仓去重后事件量与上游埋点量偏差 ≤ 1‰

---

## Decision Card 3：幂等键粒度评审

### 场景

新事件接入，团队提议幂等键用 userId（"简单省事"）。

### 判断

userId 粒度粗于业务单元 → 同一用户的并发订单事件互相误杀 → **拒绝**，改 orderId + eventType。

### Mechanism → Decision

| 机制 | 工程决策 |
| -- | ---- |
| 业务单元 | 订单（不是用户） |
| 事件语义 | eventType 区分支付/退款 |
| 原子性 | 唯一约束兜底 |

### 禁止决策

- 幂等键过粗（吞业务）或过细（拦不住重复）

### 验收指标

- 双订单并发测试：两个订单事件互不干扰
- 同事件重放：第二次被拦截，第一次生效

# 🌍 跨语言视角

## 同一个问题：幂等与顺序

| 语言 | 幂等落地 | 串行处理 |
| -- | ---- | ---- |
| Java | 唯一约束 + Spring 事务；Redisson 分布式锁 | 队列串行线程池 / 按 Key 分片 executor |
| Go | 唯一约束 + 事务；singleflight 防重 | goroutine 按 Key 哈希分片（chan per key） |
| Rust | 唯一约束 + 事务；dashmap 抢占 | actor/tokio 任务按 Key 分片 |
| Python | 唯一约束 + 事务；Redis SETNX 抢占 | asyncio 按 Key 串行队列 |

## 跨语言仍成立的判断力

1. **幂等的底座是数据库唯一约束，不是语言特性**：任何语言的幂等设计最终都落到"原子插入抢占"。
2. **Key 级串行 + Key 间并行**：Go 的 chan per key、Rust 的 actor、Java 的分片 executor——同构的并发模式。
