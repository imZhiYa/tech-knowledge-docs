# 🏭 全文唯一比喻：运输车队

```text
现实世界（运输车队）                技术世界（副本与高可用）

同一批货多辆车运输               ←→ 分区多副本（replication）
队长车（负责接单记账）           ←→ Leader（读写服务）

两辆车都以为自己是队长           ←→ 脑裂（split brain）
只要求快、不要求稳的车队         ←→ 异步复制（丢数据窗口）
```

| ---- | ---- | ---- |

| 抄账进度 | HW/LEO | 复制水位 |

| 双重队长 | 脑裂 | 一致性破坏 |

## Level 1：为什么需要副本——一车必翻

一句话认知墙：单台机器 + 及时 fsync，为什么还不够？

### 前置知识关卡

- [ ] 知道单机 fsync 的丢失窗口（mq-02 L1）
- [ ] 知道"副本冗余优先于单机 fsync"的 Kafka 哲学（mq-02 L4 埋的引子）

### Why——单机的三个死因

**徒弟**：mq-02 说 fsync 到磁盘数据就安全了——那加个 UPS 不断电，单机够安全吧？

**老陈**：fsync 防的是"进程崩溃、机器断电"，防不了"机器本身没了"：

| 死因 | 场景 | fsync 能救吗 |
| ---- | ---- | ---- |
| ① 整机故障 | 硬盘物理损坏、机器烧毁、机房事故 | 不能——数据在坏掉的盘上 |
| ② 维护窗口 | 系统升级、硬件更换、机房迁移 | 不能——业务要中断 |
| ③ 故障恢复耗时 | 机器坏了到数据恢复的时间 | 不能——恢复期业务停滞 |

**单机的"安全"是"数据躺在盘上"的安全，不是"数据随时可读"的安全**。副本首要解决的是第一类问题——**整机故障**（数据在另一台机器上还有一份，这台没了，那台顶上；fsync 救不了盘坏，副本能救）；同时副本让第三类问题（故障恢复耗时）从"停机恢复"变成"秒级切换"；对第二类（维护窗口），副本提供滚动维护能力。这就是"副本冗余优先于单机 fsync"（mq-02 的判断）：一台机器断电，page cache 里的数据丢了，但副本还在。

> 📌 最容易被误解的一点：**副本不是"备份"**。备份（backup）是"定期拷贝，恢复时可能丢最近数据"；副本（replica）是"实时同步，随时可切换"。mq-02 说 Kafka 默认不配 fsync 参数、靠多副本兜底——**副本的定位是"切换即用"，不是"出事再恢复"**。备份救"数据"，副本救"可用性"，两者都要，但不是一回事。

### What——副本的本质：多份拷贝 + 一致性协调

```text
副本的本质是两个问题的组合：
  问题一：拷贝（谁有 E 的完整日志？）
    → 同一分区的日志，多台机器各存一份
  问题二：协调（多份拷贝之间怎么保持一致？）
    → 谁负责读写？（Leader）
    → 谁跟着同步？（Follower）
    → 哪些算"跟上"？（ISR）
    → 读到哪算"安全"？（HW）

没有协调的多份拷贝 = 各写各的账 = 灾难
所以副本机制的全部内容，就是"协调"两个字。
```

### How——E 在单机 vs 副本世界的对比

```text
单机世界：
  E 写入 → fsync → 返回成功 → 机器宕机 → E 在盘上但读不了
  → 恢复时间 = 修机器时间 → 业务停滞数小时

副本世界（3 副本）：
  E 写入 → Leader 写入本地日志（page cache）→ 同步给 2 个 Follower → 返回成功
  → Leader 宕机 → ISR 中选新 Leader → 业务几乎无感继续
  → 丢数据窗口 = 同步策略决定的窗口（Level 3 展开）
```

**徒弟**：为什么是"同步给 2 个 Follower"才返回？同步 1 个行不行？

**老陈**：这就是 mq-03 讲过的 acks=all + min.insync.replicas 组合——**确认阈值决定丢数据窗口**。同步 2 个返回：Leader 挂了一个还剩 2 份，不丢；同步 0 个返回（异步）：Leader 挂的那一瞬间，最后一批 E 只有 Leader 有，全丢。**"几份确认"是可靠性与你主动选择的窗口之间的刻度盘**——mq-03 讲的是 ack 语义，本篇讲的是背后 ISR/HW 的完整机制。

### Transfer——这个思想还能迁移到哪里

1. **冗余的目的是可用性不是存储**：副本、多活、灾备——判断标准是"切换多快、丢多少"。
2. **多份拷贝的代价是协调复杂度**：任何"复制"（DB 主从、缓存副本、DNS 多区域）都引入一致性协调问题。
3. **确认阈值 = 可靠性刻度盘**：多少份确认才返回，是"性能 vs 丢失窗口"的显式选择。

本层留下的新账：多份拷贝必须有协调——协调的第一问是"谁负责读写、谁跟着同步"？副本之间到底怎么保持同步？→ 逼出 Level 2。

### Level Ending

```
🔴 口诀：一车必翻，多车才稳，确认阈值定窗口。
```

## Level 2：复制机制——队长写账，队员抄账

一句话认知墙：Leader 和 Follower 是怎么保持同步的？"同步"的判据是什么？

### 前置知识关卡

- [ ] 知道副本是"协调"问题（答不出回 Level 1）
- [ ] 知道 ISR 与 min.insync.replicas（mq-03 L3 已初讲）

### Why——为什么不能"人人都是队长"

**徒弟**：为什么不搞"多 Leader 同时写"，谁写都一样？

**老陈**：多 Leader 同时写 = 多台机器同时改同一本账 = 冲突与不一致（两辆车都记账，账单对不上）。**单 Leader 是"账本一致性"的最简解**：写只有一个人，顺序自然唯一；其他人只抄。这是"队长写账、队员抄账"的全部理由——**Leader 制把"并发写的一致性"问题转化为"单点顺序写 + 复制"问题**。

### What——Kafka 的 ISR / HW / LEO 完整机制

```text
三把尺子：

LEO（log end offset）：每台车自己抄到的位置（自己的账本末端）
HW（high watermark）：所有不掉队队员都抄到的位置（安全水位）
ISR（in-sync replicas）：不掉队的队员名单

推进机制：
  ① Leader 收到 E → 追加日志 → LEO(Leader) + 1
  ② Follower 从 Leader 拉取（replica fetcher，长轮询机制与
     消费者一致，mq-05 L2 已讲）→ 追加 → LEO(Follower) + 1
  ③ Leader 观察：所有 ISR 成员的 LEO 都 ≥ 某位置 → HW 推进
  ④ 消费者只能读到 HW 以下 ★安全水位
  ⑤ Follower 落后超过阈值（replica.lag.time.max.ms）
     → 从 ISR 剔除（掉队）
  ⑥ 追上后 → 重新加入 ISR（归队）
```

> 📌 最容易被误解的一点：**HW 不是"Leader 写到的位置"，是"所有 ISR 成员都写到的位置"**。消费者读 HW 以下，是因为"这些消息即使 Leader 立刻挂了，Follower 也有"——**HW 是"可承诺不丢"的水位线**。这就是为什么 acks=all 的"all"不是"所有副本"，而是"所有 ISR 成员"（mq-03 的机制根源，这里落地）。

### How——E 在复制机制下的完整旅程

```text
T0  分区 3 副本：Leader=L1，Follower=F1/F2，ISR=[L1,F1,F2]
T1  生产者 acks=all 发送 E → L1 追加 → LEO(L1)=100
T2  F1 拉取复制 → LEO(F1)=100；F2 稍慢 → LEO(F2)=98
T3  HW 只能推进到 98（F2 还没到）→ 消费者可读 ≤ 98
T4  F2 追到 100 → HW=100 → 消费者可读 99/100
T5  F2 持续掉队（GC/网络）超过阈值 → 从 ISR 剔除
T6  ISR=[L1,F1] → HW 继续推进（不再等 F2）★掉队者不再拖慢全队
T7  F2 恢复追上 → 重新加入 ISR
```

**徒弟**：T5 把 F2 剔除，是不是 F2 的数据就废了？

**老陈**：不是——**剔除只影响"它还算不算同步副本"，不影响它继续复制**。F2 还是 Follower，还是从 Leader 拉数据，只是：①不参与 HW 推进（不再拖慢写入确认）②不能当选 Leader（不在 ISR 里，min.insync.replicas 的确认也不包括它）。**ISR 收缩是"降级为后备"，不是"开除"**——这个机制让慢副本不再拖慢快副本，是"木桶效应"的解药。

### Transfer——这个思想还能迁移到哪里

1. **单 Leader + 复制 + 水位**：MySQL 主从（relay log + 同步水位）、Redis 主从、DNS 主区——同一个骨架。
2. **木桶效应的解药是"降级"**：ISR 剔除 = 把拖后腿的从"必须等待"降级为"可选等待"——分布式系统常见的容错手法。
3. **可承诺水位**：HW 思想 = 发布系统的"已确认可承诺"边界。

本层留下的新账：同步机制清楚了。但"队长"本身会死——**Leader 挂了，谁来当新队长？选举瞬间丢不丢账？两个队长的脑裂怎么防？** → 逼出 Level 3。

### Level Ending

```
🔴 口诀：队长写账，队员抄账，HW 是安全线。
```

## Level 3：Leader 切换与脑裂——车队的政变

一句话认知墙：Leader 挂了之后，丢失窗口、选举规则、脑裂防护三件事怎么解？

### 前置知识关卡

- [ ] 能画出 ISR/HW/LEO 推进（答不出回 Level 2）
- [ ] 知道 mq-03 L3 的"切换丢最后一批"推演

### Why——切换的三种命运

**老陈**：Leader 挂了，新 Leader 从哪选，决定 E 的三条命运：

```text
命运一：从 ISR 里选（默认，安全）
  新 Leader 有全部"已确认不丢"的消息（≥ HW）
  → acks=all 确认过的 E 一条不丢 ★不丢

命运二：ISR 空了 + 允许 unclean 选举（默认禁止，危险）
  允许非 ISR 副本当选 → 它缺最后一批消息
  → 已确认的 E 可能丢失 + 旧 Leader 回归时数据截断 ★丢数据

命运三：ISR 空了 + 禁止 unclean 选举（默认行为）
  拒绝选举 → 分区不可用（leader 缺失）
  → 不丢，但牺牲可用性：宁可停，不可错 ★停摆
```

> 📌 最容易被误解的一点：**"高可用"与"不丢数据"在极端场景下是互斥的**。ISR 全挂（比如机房级故障），要么选一个缺数据的副本当 Leader（恢复服务但丢数据），要么拒绝选举（不丢数据但服务停摆）。**unclean leader election 这个开关，就是"丢数据换可用性"的显式选择**——默认关，是"宁可停摆不可丢账"的默认立场。

### What——两个防护机制：leader epoch 与 controller epoch

```text
防护一：leader epoch（防数据截断事故，KIP-101）
  事故场景：旧 Leader 回来，带着多写的几笔账（当年它挂之前
            Follower 没抄到的部分）→ 如果它继续当 Leader
            → 那几笔账和 ISR 的账对不上
  leader epoch 机制：
    每个 Leader 任期带一个递增的 epoch 编号
    新 Leader 上任时告知 Follower 自己的 epoch
    Follower 发现 Leader 的 epoch 变化 → 按新 Leader 的
    水位截断自己多余的账 ★截断是"对账本"，不是"丢账"
    （截掉的是"旧 Leader 独有、从未被确认"的部分）

防护二：controller epoch（防僵尸 controller 发指令）
  事故场景：旧 controller 因网络分区失联，新 controller 已选出
            → 旧 controller 恢复后若还能发指令，两个 controller
            同时指挥集群 ★控制面脑裂
  controller epoch 机制：
    集群元数据由一个 controller 管理（KRaft 时代是
    QuorumController，基于 Raft）
    每个 controller 任期带递增的 epoch
    旧 controller 的请求携带旧 epoch → 被新 controller 拒绝
    → 僵尸 controller 的指令作废

分工：leader epoch（KIP-101）防"旧 Leader 回归掌权/截断事故"，
     controller epoch 防"僵尸 controller 发指令"——两个 epoch
     管两个不同的"旧王"
```

### How——E 经历的完整切换事故链

```text
场景：Leader L1 所在机器网络分区（没死，但失联）

T0  分区 3 副本，ISR=[L1,F1,F2]，L1 失联
T1  元数据控制器判定 L1 失效 → 从 ISR 选新 Leader（如 F1）
T2  F1 上任，epoch=3（L1 时代是 2）
T3  生产者写 E 到 F1 → F2 复制 → 正常服务 ★切换完成
T4  L1 恢复，带着 epoch=2 的旧账试图回归
T5  leader epoch 校验（KIP-101）：L1 的 epoch 过旧，
    无法重新当选 Leader（旧 epoch 请求被拒）→ 不能行使写入权
T6  L1 降为 Follower → 收到 F1 的 epoch=3 → 截断多余账 → 归队
T7  终局：E 一条不丢（如果都在 HW 内），无脑裂，账本一致

另一结局（unclean 开启 + ISR 全挂）：
  新 Leader 缺最后一批 E → 已确认的 E 丢失
  → 下游幂等 + 对账（mq-03/mq-04）兜底
```

**徒弟**：T6 的"截断多余账"——那几笔账不是丢了吗？

**老陈**：要分清"确认过的账"和"没确认的账"。在默认语义下（unclean 关闭、新 Leader 必须来自 ISR），**HW 以下（确认过）的账，当前 ISR 成员上都有，截不掉**；被截的是"旧 Leader 独有、未同步给任何 ISR 成员、从未被确认"的部分——这部分在 acks=all 语义下**从未承诺过不丢**。所以截断不是事故，是"把从未承诺的数据清理掉"的收尾。**丢掉"从未承诺不丢"的数据，不算丢数据**——这是理解所有副本系统的关键判据。⚠️ 但这个保证以 **unclean leader election 关闭**为前提：开启 unclean 时，缺数据的非 ISR 副本可以当选，旧 Leader 回归后的截断可能删掉"曾 acks=all 确认且在 HW 内"的数据（本层事故链"另一结局"正是这个场景）——所以"截断不删确认数据"与"unclean 开启会丢已确认数据"是同一机制的两面。

### Transfer——这个思想还能迁移到哪里

1. **任期与 epoch 防脑裂**：Raft 的 term、ZooKeeper 的 zxid、数据库的 LSN——"递增编号识别旧王"是分布式协调的通用语言。
2. **可用性与一致性的显式开关**：unclean election 式的选择在数据库（slave 提升）、缓存（旧副本接管）里反复出现。
3. **"从未承诺的账"不算丢**：SLA 的语言——承诺边界（HW/ack）决定了"丢数据"的合法定义。

本层留下的新账：Kafka 的 ISR + epoch 讲透了。四家产品各用什么哲学解决同一问题？→ 逼出 Level 4。

### Level Ending

```
🔴 口诀：切换看 ISR，脑裂靠 epoch。
```

## Level 4：四家对照——同一个问题的四个答案

一句话认知墙：Kafka、RocketMQ、RabbitMQ、Pulsar 的副本哲学差在哪？

### 前置知识关卡

- [ ] 能说出三种切换命运（答不出回 Level 3）
- [ ] 知道"确认阈值 = 可靠性刻度盘"（Level 1）

### Why——同一问题的四个答案

**老陈**：所有副本系统回答同一个问题：**"一份账要在几台机器确认，才敢说没丢？"** 四个产品给了四个不同的答案，对应四种不同的取舍：

| 产品 | 复制哲学 | 确认语义 | 切换 | 丢数据窗口 |
| ---- | ---- | ---- | ---- | ---- |
| Kafka | ISR（可收缩的同步集合） | acks=all 等全部 ISR | ISR 内选举 + epoch | 承诺内不丢；unclean 开关可放弃 |
| RocketMQ | 主从复制（同步/异步两档） | 同步复制等 slave 写入本地日志（page cache 层，fsync 由各节点刷盘配置定） | 4.5+ DLedger(Raft) / 5.x controller | 同步=承诺内不丢；异步=最后一批 |
| RabbitMQ | quorum queue（Raft 多数派） | 多数派确认 | Raft 选举 | 确认消息不丢 |
| Pulsar | BookKeeper ledger（write/ack quorum 可配置，通常设多数派） | write/ack quorum 数量确认 | broker 无状态，bookie 独立 | 承诺内不丢——前提是持有条目的 bookie 有足够数量存活 |

### What——四个答案的机制差异

```text
Kafka：ISR 哲学——"跟得上的才算数"
  同步集合可收缩 → 慢副本不拖慢确认
  代价：ISR 收缩到 < min.insync.replicas → 拒绝写入（mq-03）
        （保一致性，牺牲可用性）

RocketMQ：主从哲学——"一主一从（或一主多从）"
  同步复制（SYNC_MASTER）：master 等 slave 写入本地日志（mmap CommitLog，
  page cache 层）的 ACK 才返回；fsync 由各节点刷盘配置（flushDiskType）
  决定——承诺的是"副本冗余"，不是"每副本 fsync"
  异步复制（ASYNC_MASTER）：master 返回后再复制 → 快但切换丢末批
  切换：DLedger（4.5+ Raft 组）或 controller（5.x）
  代价：同步复制延迟高；异步复制有窗口（mq-03 的丢数据窗口来源）

RabbitMQ：Raft 哲学——"多数派说了算"
  quorum queue（3.8+）：每条消息多数派确认 → 确认即不丢
  替换了镜像队列（异步 gm 组播，提升可能丢未同步消息）
  代价：吞吐受多数派确认限制；强一致换性能

Pulsar：BookKeeper 哲学——"账本独立于 Broker"
  存算分离：Broker 无状态，数据在 BookKeeper ledger
  ledger 写入需满足 write quorum + ack quorum
  代价：组件多、运维重；换来的是任意 Broker 故障数据不丢
```

> 📌 最容易被误解的一点：**"同步复制"与"异步复制"是 RocketMQ 的档位，"ISR"是 Kafka 的机制——它们不是同一个东西**。RocketMQ 的同步复制是"固定等 slave"（一主多从确认），Kafka 的 acks=all 是"等当前 ISR 成员"（可收缩集合）。**RocketMQ 更像"固定船队的确认"，Kafka 更像"当前不掉队名单的确认"**——前者的确认对象固定，后者的确认对象动态。这个区别决定了两者遇到慢副本时的不同表现。

### How——同一场故障，四家的命运

```text
故障：3 副本机器，1 台宕机

Kafka（3 副本，ISR 收缩）：
  剩 2 台在 ISR → 继续服务 → 丢数据窗口 = 0（承诺内）
  若 ISR 缩到 0（全挂）→ 不可用（默认）或 unclean 选举（可选）

RocketMQ（1 主 1 从，异步复制）：
  主挂 → 从提升 → 最后一批"主已收未复制"的消息丢失 ★窗口
  同步复制：主挂 → 从有全部已确认消息 → 不丢

RabbitMQ（quorum queue，3 节点）：
  1 节点挂 → 多数派（2/3）继续 → 已确认消息不丢

Pulsar（write=2 ack=1，3 bookie）：
  1 bookie 挂 → 剩余 2 bookie 继续 → 已确认 ledger 数据不丢
  （条目只写在被选入 write quorum 的 2 台上；若这 2 台全挂，
  数据即丢——容错预算 = write quorum - ack quorum = 2-1 = 1，
  与 ensemble 总台数无关：W=2/A=1 对 5 台时仍只容忍 1 台故障）
  → 各产品确认阈值不同，丢数据窗口不同 ★对照的意义
```

**徒弟**：Kafka 的 ISR 收缩和 Pulsar 的 quorum 有什么区别？看起来都是"部分副本确认"。

**老陈**：ISR 是"动态名单 + 全部确认"，quorum 是"固定集合（write/ack quorum 可配置）+ 指定数量确认"。区别在容错形态：ISR 收缩允许"慢副本被降级"，quorum 则通过"集合轮换（bookie 故障时 ensemble 变更）"维持条目持有的指定副本数——注意 BookKeeper 的 quorum 数量**可以小于多数派**（如 write=2 对 5 台），此时容错预算也随之下降，多数派只是常规推荐配置而非机制要求。**另一个关键区别在架构：Kafka 的副本是"分区独立管理"（每分区一个 Leader），Pulsar 的 ledger 是"存储层独立管理"（broker 无状态）**——Pulsar 的切换是"换个 broker 挂上同一个 ledger"，数据从不跟着 broker 走。这就是"存算分离"在副本层面的意义（mq-00 的定位，mq-09 有架构代价呼应）。

### Transfer——这个思想还能迁移到哪里

1. **确认哲学决定一切**：动态集合（ISR）/固定多数（Raft）/固定主从（同步复制）——数据库复制、配置中心、服务发现的选型都问"确认对象是什么"。
2. **存算分离改变故障语义**：数据与计算分离（Pulsar/BookKeeper）后，故障从"数据迁移"变成"计算挂接"——云原生架构的通用方向。
3. **承诺边界定义 SLA**：每个产品的"确认"边界不同，SLA 的"不丢"必须按产品边界书写。

本层留下的新账：四家的取舍背后是同一个轴——**同步复制牺牲吞吐、异步复制有丢数据窗口**。这个轴在选型时怎么权衡？→ 逼出 mq-09（生产决策与选型）。

### Level Ending

```
🔴 口诀：同步慢而稳，异步快而险，哲学定命运。
```

## Level 5：生产决策与参数配置

一句话认知墙：副本因子、ISR 阈值、选举开关——三个参数怎么配，才敢上线？

### 前置知识关卡

- [ ] 能对比四家复制哲学（答不出回 Level 4）
- [ ] 知道"unclean 开关 = 丢数据换可用性"（Level 3）

### Why——决策的轴心是"确认哲学与业务代价"

**老陈**：副本参数配置的轴心只有一条：**"已确认"的语义必须覆盖业务"不可丢"的承诺**。业务说"支付成功消息不能丢"，那"支付成功消息"的确认必须落在"承诺不丢"的副本水位上——三个参数都是这个轴上的刻度。

### What——决策清单

```text
决策一：副本因子（几份拷贝）
  = 可容忍同时挂几台机器（3 副本容忍 1 台）
  = 与集群规模、机器预算挂钩
  规则：副本因子 > 可容忍故障数 + 1

决策二：确认阈值（Kafka min.insync.replicas / acks=all）
  = 承诺不丢的最小同步副本数
  规则：min.insync.replicas ≥ 2（至少有一个冗余确认）
  ISR 缩到阈值以下 → 拒绝写入（保护"确认语义"不被稀释）

决策三：选举开关（unclean leader election）
  = 极端场景要"服务"还是要"不丢"
  规则：默认关闭（宁可停摆不可丢账）
  开启条件：业务可容忍丢末批数据（对账可补），换可用性

决策四：ISR 滞后阈值（replica.lag.time.max.ms）
  = 判定"掉队"的尺度：太紧 → 抖动即剔除（确认集合缩水）
  太松 → 慢副本长期占着 ISR 拖慢确认
  规则：按复制链路最坏延迟 + 余量配置
```

### How——E 的生产配置推演

```text
场景：订单事件 E 的 Topic，业务承诺"支付成功消息不丢"

① 副本因子 = 3（容忍 1 台机器故障）
② acks=all + min.insync.replicas=2（承诺不丢 ≥ 2 份）
③ unclean leader election = false（默认，不丢优先）
④ ISR 滞后阈值按复制链路实测 + 余量
⑤ 故障演练（kill broker）验证切换窗口：
   - 单台挂 → 无丢失、无停摆（ISR 还有 2）
   - 两台挂 → ISR < 2 → 拒绝写入（保护语义）→ 告警
⑥ 对账兜底（mq-03）：端到端核对消息量与业务效果
```

**徒弟**：min.insync.replicas=2 的话，两台挂掉系统就拒绝写入了——这算不算可用性事故？

**老陈**：算——但这是"设计过的失败"：**拒绝写入比"确认了却丢数据"安全**。写入被拒，生产者看到错误、重试、告警、人工介入——一切都在明处；"确认了却丢"是静默的，下游按成功继续执行，账对不上才发现。**min.insync.replicas 的哲学：宁可把失败显式化，不可把丢失静默化**（与 DLQ 的"显式化故障"思想同源，mq-07）。

### 📋 关键参数配置与注意事项

> 默认值随版本变化，以官方文档为准（写作基线 Kafka 3.5.x / RocketMQ 5.x / RabbitMQ 3.13.x），本文只讲参数控制的机制与配错的事故。

| 参数 | 控制的机制（指向本文 Level） | 配错的线上事故 |
| ---- | ---- | ---- |
| replication.factor（Kafka 副本因子） | 拷贝份数：容错上限（L1） | 配 1 → 无冗余，单机故障即丢；配太多 → 复制放大、磁盘与带宽成本高 |
| min.insync.replicas（Kafka 最小同步副本） | 确认语义的下限（L2/L5） | 配 1 → acks=all 也可能只剩 1 份确认（ISR 收缩后）→ 切换即丢 |
| acks=all（生产者） | 等全部 ISR 确认（L2） | acks=1 → 只等 Leader，Leader 挂丢最后一批（mq-03 已破） |
| unclean.leader.election.enable（Kafka 选举开关） | 丢数据换可用性（L3/L5） | 开启 → 机房级故障时选缺数据副本 → 已确认消息丢失 |
| replica.lag.time.max.ms（Kafka ISR 滞后阈值） | 掉队判定尺度（L2/L5） | 太紧 → 复制抖动即剔除 → ISR 缩水 → 写入被拒或确认面缩小 |
| brokerRole（RocketMQ SYNC/ASYNC_MASTER） | 同步/异步复制档位（L4） | ASYNC_MASTER → 主挂丢最后一批已确认消息；SYNC_MASTER → 延迟与吞吐代价 |
| DLedger/controller 配置（RocketMQ 选举） | 自动故障切换（L4） | 未配置 → 主挂后无自动切换，业务停滞 |
| quorum queue 多数派（RabbitMQ） | 确认语义（L4） | 节点数配偶 → 多数派=一半+1，故障容忍反而降低（3→1, 2→0） |

<a id="pitfalls"></a>

# ⚠️ 坑与细节

## 坑 1：副本因子配 1

错误理解：反正有 fsync，一份就够。

原因：fsync 防进程崩溃与断电，防不了机器没了。

比喻后果：货只装一辆车，车烧了货就没了。

线上现象：机器硬盘损坏 → 数据全无，只能靠备份恢复（丢失最近数据）。

修正：副本因子 ≥ 2（容忍 1 台故障），集群规模决定上限。

## 坑 2：min.insync.replicas 配 1，acks=all 形同虚设

错误理解：配了 acks=all 就安全了。

原因：acks=all 是"等全部 ISR"，ISR 收缩到 1 时"全部"就是 1。

比喻后果：名单只剩 1 辆车，说"全员确认"等于只确认 1 辆。

线上现象：ISR 收缩后切换，已确认消息丢失（确认面被稀释）。

修正：min.insync.replicas ≥ 2，确认面下限与业务承诺绑定。

## 坑 3：误开 unclean leader election

错误理解：选举嘛，有副本能选就选，恢复快。

原因：非 ISR 副本缺已确认数据，当选即丢。

比喻后果：缺货的车当队长，按它的缺货账本发单。

线上现象：机房级故障后恢复服务，但已确认支付消息丢失，对账爆雷。

修正：默认关闭；开启必须业务明确承诺"可容忍末批丢失 + 对账可补"。

## 坑 4：把 HW 当 Leader 的写位置

错误理解：HW = Leader 写到哪消费者就能读到哪。

原因：HW 是"所有 ISR 都到"的水位，通常落后于 Leader。

比喻后果：队长账本比抄账本多几页，只让看抄到的部分。

线上现象：消费者读不到刚确认的消息，误判为延迟问题乱调参。

修正：理解 HW 语义——读不到的是"尚未被全部 ISR 确认"的部分，是特性不是故障。

## 坑 5：ISR 滞后阈值配太紧

错误理解：阈值紧 = 及时剔除慢副本，确认快。

原因：复制链路抖动（GC/网络/负载）即被误判掉队。

比喻后果：队员打了个喷嚏就除名，名单缩水，确认变慢。

线上现象：复制抖动期 ISR 频繁收缩扩张，写入确认抖动，甚至触发拒绝写入。

修正：按复制链路最坏延迟 + 余量配置；观察收缩频率调参。

## 坑 6：RocketMQ 异步复制当同步用

错误理解：主从都配了就安全。

原因：ASYNC_MASTER 是主返回后再复制，主挂丢末批。

比喻后果：队长先回话"收到"再让队员抄——队长出车祸，最后几单没抄。

线上现象：主挂后末批已确认消息丢失，对账暴露。

修正：不可丢链路必须 SYNC_MASTER（或 DLedger/controller 模式），接受延迟代价。

## 坑 7：RabbitMQ 节点数配偶

错误理解：节点越多越安全。

原因：Raft 多数派 = n/2+1；2 节点多数派是 2（全要），故障容忍为 0。

比喻后果：2 辆车，1 辆坏了就凑不够多数，账本停摆。

线上现象：2 节点 quorum queue 集群，任一节点挂即无法确认。

修正：quorum queue 集群 ≥ 3 节点（容忍 1 台）。

## 坑 8：把"截断"当"丢数据"

错误理解：旧 Leader 回归截断账本 = 数据丢失事故。

原因：截断的是"从未同步、从未确认"的部分（epoch 语义下）。

比喻后果：把"对账本时划掉的无效记录"当成"烧了账本"。

线上现象：误判截断为事故，紧急处理反而造成真事故。

修正：以 HW/确认语义判断——承诺内的不丢，承诺外的截断是收尾。

<a id="errata"></a>

# 📚 版本勘误表

| 错误说法 | 准确说法 |
| ---- | ---- |
| "副本就是备份" | 副本是实时同步、切换即用；备份是定期拷贝、恢复丢窗口 |
| "acks=all = 所有副本确认" | 是"所有 ISR 成员"确认，ISR 可收缩 |
| "HW 是 Leader 写到的位置" | HW 是所有 ISR 都到过的水位（可承诺不丢） |
| "ISR 剔除 = 开除副本" | 是降级为后备：不拖慢确认、不参与选举，继续复制 |
| "unclean 选举只是恢复快" | 是"丢已确认数据换可用性"的显式开关 |
| "旧 Leader 回归截断 = 丢数据" | 截断的是从未同步从未确认的部分，承诺内不丢 |
| "同步复制和 ISR 是一回事" | RocketMQ 固定主从确认 vs Kafka 动态 ISR 确认，确认对象不同 |
| "节点越多越安全（RabbitMQ）" | Raft 多数派语义下 2 节点容忍 0 故障，3 节点才容忍 1 |
| 坦白：我以前也讲错过"配了 acks=all 就不丢" | ISR 收缩到 1 时"all"就是 1——min.insync.replicas 才是下限 |
| 坦白：我以前也讲错过"Kafka 2.8 到 3.5 只是版本升级" | ZK→KRaft 是元数据管理语义变化（controller 从 ZK 协调到 Raft 自管理），不是代码搬家 |

# 🏆 生产决策卡

## Decision Card 1：订单事件 Topic 副本配置

### 场景

E 承载"支付成功"业务承诺，不可丢；集群 3 台机器。

### 判断

副本因子 3 + acks=all + min.insync.replicas=2 + unclean 关闭；故障演练验证切换窗口；对账兜底。

### Mechanism → Decision

| 机制 | 工程决策 |
| -- | ---- |
| 容错上限 | 副本因子 3（容忍 1 台） |
| 确认面下限 | min.insync.replicas=2 |
| 极端选择 | unclean 关闭（不丢优先） |
| 兜底 | 对账核对（mq-03） |

### 禁止决策

- min.insync.replicas=1（确认面可缩水到单份）
- 无演练直接上线（切换窗口未验证）

### 验收指标

- kill 单台 broker：0 丢失、0 停摆（ISR 还有 2）
- kill 两台：拒绝写入告警（显式失败），恢复后数据无丢失
- 对账 24h 零差异

---

## Decision Card 2：RocketMQ 主从复制选型

### 场景

业务消息链，主从部署，要求切换不丢末批。

### 判断

SYNC_MASTER（同步复制）+ 自动故障切换（5.x controller / DLedger）；接受同步复制延迟代价；延迟敏感业务与不可丢业务分 Topic 配置。

### Mechanism → Decision

| 机制 | 工程决策 |
| -- | ---- |
| 复制档位 | SYNC_MASTER（不可丢链路） |
| 自动切换 | controller/DLedger（避免人工介入） |
| 延迟取舍 | 不可丢链路付延迟代价；可丢链路用 ASYNC_MASTER |

### 禁止决策

- 不可丢链路用 ASYNC_MASTER（末批丢失）
- 主挂后人工切换（切换窗口不可控）

### 验收指标

- 主挂演练：0 丢失、切换时间 ≤ 阈值
- 同步复制延迟 vs 异步基线（实测对比，mq/experiments）

---

## Decision Card 3：复制哲学选型评审（本篇支线小结）

### 场景

新业务集群选型，纠结四家复制哲学。

### 判断

按业务承诺分类：强不可丢 + 大吞吐 → Kafka（ISR + min.insync）；交易业务消息 → RocketMQ（同步复制/DLedger）；企业路由 → RabbitMQ（quorum queue 多数派）；云原生多租户 → Pulsar（BookKeeper）。不做跨产品复制哲学混用。

### Mechanism → Decision

| 机制 | 工程决策 |
| -- | ---- |
| 确认哲学 | 与业务"不可丢承诺"对齐 |
| 故障形态 | 按可容忍故障数设计副本 |
| 切换语义 | 演练验证切换窗口与丢数据边界 |

### 禁止决策

- 按"听说吞吐高"选型，不验证确认语义
- 混合部署后跨产品复制（语义不一致）

### 验收指标

- 每产品故障演练通过（切换窗口/丢数据边界实测）
- SLA 的"不丢"按产品确认边界书写

<a id="cross-language"></a>

# 🌍 跨语言视角

## 同一个问题：副本一致性

| 语言 | 复制机制 |
| -- | ---- |
| Java | Kafka/RocketMQ 生态（客户端视角：acks、幂等生产者） |
| Go | franz-go / sarama（acks 配置、事务） |
| Rust | rdkafka（生产者确认与重试语义） |
| Python | confluent-kafka（同一客户端语义） |

## 跨语言仍成立的判断力

1. **副本是 Broker 层问题**：客户端语言只接触"确认语义"的接口（acks、等待、重试），机制在 Broker 内部。
2. **确认语义是跨语言的契约**：acks=all + min.insync.replicas 在任何语言客户端都是同一份承诺。
