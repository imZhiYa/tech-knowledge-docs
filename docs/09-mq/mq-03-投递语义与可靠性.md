# 🧾 MQ 投递语义与可靠性深度解析：从"绝不丢消息"的幻觉到三道防线的工程真相

> 这不是一篇可靠性配置清单。
>
> 本文只追踪一个主线：**Message E 的签收单**。
>
> E 从寄件柜台出发，要过三道关卡才能算"安全送达"：Producer 确认、Broker 落定、Consumer 签收。每一关的签收单都有不同的"真假"——本文追踪的正是这张签收单从产生到作废的全过程。
>
> 看 E 如何穿透：发送 API → 确认级别 → 刷盘/副本 → ack → 对账补偿 → 生产决策

# 写在最前面：三道防线，三个神话

"MQ 保证消息不丢"是分布系统里流传最广、害人最深的一句话。真相是：

1. **Producer 返回成功 ≠ 消息不丢**（神话①）——成功是"某个级别"的成功，级别由配置决定。
2. **Exactly-once 不是开关**（神话②）——Broker 层根本做不到，能买到的是"幂等生产 + 事务协调"。
3. **消费成功 ≠ ack**（神话③）——ack 是进度提交，业务副作用是否成功是另一层。

本文把 E 的可靠性拆成**三道防线**：生产确认 → 落定冗余 → 消费提交，外加一道**兜底防线**（对账补偿）。四道防线各自解决一部分问题，各自留下新的账。

# 正文：六个 Level 打穿"签收单的真假"

<a id="level-1"></a>

## Level 1：投递语义三分类——神话② 的破解

一句话认知墙：文档里的 at-most-once / at-least-once / exactly-once 到底是什么意思？为什么说 exactly-once 是个"买不到"的东西？

### 前置知识关卡

- [ ] 知道 E 落定的四级安全（mq-02 Level 1）
- [ ] 知道 ack 超时重投/位点回拨会产生重复（mq-01）

### Why——为什么要给"送达"下定义

**徒弟**：消息不就是"发出去 → 收到"吗？成功、失败、重试，还能有几种花样？

**老陈**：因为**失败是无声的**。网络超时后，消息可能已经到达、也可能没到达——你不知道。于是"送达"必须按"可容忍什么"来分级：

| 语义 | 承诺 | 代价 | 典型实现 |
| ---- | ---- | ---- | ---- |
| at-most-once | 最多一次，可能丢 | 无重试 | acks=0 / oneway（自动提交的归属见下：既可能丢也可能重，取决于提交与处理谁先） |
| at-least-once | 至少一次，可能重复 | 重试 + 幂等 | acks=1/all + 重投 / 手动提交 |
| exactly-once | 恰好一次 | **做不到**（见下） | 幂等生产 + 事务/幂等消费组合 |

### What——为什么 Broker 层不存在 exactly-once

```text
exactly-once 需要的三个"原子动作"：

① 生产者：发送 E + 得知结果，恰好一次
   问题：超时后重发，Broker 可能收到两次（幂等生产者可解——同一条 E 去重）

② Broker：E 只存一份
   问题：Leader 切换时，新 Leader 可能没有最后一批消息（mq-08 展开）——
   于是消费者可能"读不到某条 E"，也可能"读到两条不同副本的同一位置"

③ 消费者：处理 E + 提交位点，恰好一次
   问题：处理与提交是两个独立动作，跨两个系统（业务 DB 与 Broker），
   没有分布式事务能原子覆盖两者——崩溃点落在任何一边都会产生重复或丢失
```

> 📌 最容易被误解的一点：**exactly-once 是"效果一次"，不是"投递一次"**。业界说的 exactly-once（Kafka 的幂等生产、Streams 的 EOS）指的是：配合幂等处理后，**业务效果**恰好发生一次——消息本身可能被投递两次，但第二次被去重了。神话②的破解点就在这：**没有开关，只有组合拳**（幂等生产 + 事务协调 + 幂等消费），而且事务边界只覆盖 Broker 到 Broker，覆盖不到你的业务 DB。

### How——三种语义在 E 的扣库存场景下的真实后果

```text
① at-most-once：E 发送后不重试
   → 丢一条 E = 订单已支付但库存没扣 → 资损
   → 适用场景：监控指标、日志采样（丢了无所谓）

② at-least-once：E 发送超时 → 重发 → 两条 E 都到
   → 库存扣两次 = 重复扣减 → 需要幂等
   → 适用场景：绝大多数业务链路（重复可控，丢失不可控）

③ 幂等生产 + at-least-once 消费 + 幂等：
   → 重发被 Broker 去重（同一条 E 只存一份）
   → 重复投递被业务幂等去重（扣库存按 orderId 幂等）
   → 业务效果恰好一次 —— 这才是工程上能买到的"exactly-once"
```

**徒弟**：那②里"两条 E"为什么不能由 Broker 去重？Broker 按消息 ID 去重不就行了？

**老陈**：这就是幂等生产干的事（Level 2 展开）。但注意：Broker 去重只能在"生产者重复发送"这一个环节生效。**消费者重复处理**（比如扣库存成功但 ack 超时，消息重投）发生在 Broker 下游，Broker 无从判断——去重只能由业务自己做（幂等键）。所以"恰好一次"从头到尾都不是一个组件能承诺的，是整条链路的组合拳。

### Transfer——这个思想还能迁移到哪里

1. **失败语义必须显式分级**：任何跨系统交互都要先声明"容忍丢还是容忍重"——RPC 重试、支付回调、Webhook 全部适用。
2. **幂等是分布式系统的默认要求**：网络不可靠决定了"至少一次"是唯一可行的投递承诺，幂等不是可选项。
3. **效果语义 > 传递语义**：评价系统不要问"投递了几次"，要问"业务效果发生了几次"。

本层留下的新账：at-least-once 是唯一可行承诺，重试是必然动作。那 send 返回成功到底意味着什么？不同配置下"成功"的含义天差地别。→ 逼出 Level 2。

### Level Ending

```
🔴 口诀：至多丢、至少重，恰好一次靠组合拳。
```

## Level 2：Producer 确认——神话① 的破解

一句话认知墙：`send` 返回成功，消息就一定在 Broker 手里了吗？

### 前置知识关卡

- [ ] 能说出投递语义三分类与取舍（答不出回 Level 1）
- [ ] 知道 Producer 本地缓冲的存在（mq-00 Level 4）

### Why——"成功"是分级别的

**徒弟**：send 返回成功，不就是 Broker 收到了吗？这有什么好讨论的？

**老陈**：问三个问题：① 消息到 Broker 内存算成功，还是到磁盘算成功？② 到 Leader 磁盘算成功，还是副本也到才算成功？③ send 返回成功，和消息还在本地缓冲里没发出去，冲突吗？——**"成功"的定义有至少四个级别，每个产品用不同参数控制**：

| 级别 | Kafka 参数 | RocketMQ | 丢数据窗口 |
| ---- | ---- | ---- | ---- |
| 发出去就行 | acks=0 | oneway 发送 | 网络丢、Broker 拒收，全丢 |
| Leader 写入本地日志（page cache，无 fsync） | acks=1 | SEND_OK（默认异步刷盘 ASYNC_FLUSH） | 断电丢（未 fsync 部分）；Leader 崩溃时 ISR 中其他副本可能有，acks=1 不保证 |
| 本地 fsync（真正落盘） | 无 acks 对应（由 Broker 刷盘配置 log.flush.* 控制） | SEND_OK（同步刷盘 SYNC_FLUSH，fsync 后才返回） | 单机断电、进程崩溃都不丢（已 fsync 部分） |
| 副本同步 | acks=all | 同步/异步复制（SYNC_MASTER / ASYNC_MASTER） | 取决于副本策略与确认水位（Level 3） |

### What——Producer 确认的完整模型

```text
         Producer（寄件人）
              │ send(E)
              ▼
      ┌──────────────┐
      │ 本地批量缓冲   │ ← E 可能在这里停留（攒批）
      └──────┬───────┘
              │ 批量发出
              ▼
      ┌──────────────┐
      │ Broker 受理   │ ← acks=0：到此为止，立即返回（不保证任何事）
      │  → 本地日志    │ ← acks=1：Leader 写入本地日志（page cache，无 fsync）后返回
      │  → 副本同步    │ ← acks=all：ISR 全部确认后返回
      └──────────────┘
              │
              ▼
      Producer 收到确认（或超时 → 重试）
```

> 📌 最容易被误解的一点：**异步发送的"成功回调"不是"已到 Broker"的证明**。RocketMQ 的异步发送回调触发时消息已进入发送通道，而 `SEND_OK` 的含义由 Broker 刷盘配置决定：**SYNC_FLUSH 下已刷盘、ASYNC_FLUSH 下只入内存**——要看 `SendStatus`：`SEND_OK`（成功，含义随刷盘配置）/ `FLUSH_DISK_TIMEOUT`（等刷盘确认超时）/ `FLUSH_SLAVE_TIMEOUT`（等副本确认超时）。**返回成功的形态里藏着丢失窗口**，这是神话① 的完整破解。

### How——E 的一次失败重发全流程

```text
① OrderService send(E)，acks=all，超时 3s
② E 进入批量缓冲 → 发出 → Broker 落盘 → 副本同步
③ 副本确认丢失（网络抖动）→ 3s 超时 → Producer 判定失败
④ 重试：E 再次发送 → 这次成功
⑤ 结果：Broker 里躺着两条 E（第一次其实成功了，只是确认丢了）
   —— 这就是 at-least-once 的重复来源：不是系统坏了，是确认机制的正常行为
```

**徒弟**：那 Kafka 的幂等生产者（enable.idempotence）就是干这个的？

**老陈**：对。幂等生产者给每条消息分配 `{producerId, sequenceNumber}`，Broker 记录每个 producerId 已收到的最大序号——序号重复的消息直接丢弃。④ 的重发与①是同一条 E（同序号），Broker 去重。但注意两个边界：① 去重窗口有限（Broker 内存只保留每分区最近的序号段；Kafka 2.5 起 KIP-360 改进：日志因 retention/deleteRecords 截断时不再丢弃 producer 状态，状态保留到过期——解决 UnknownProducerId 恢复问题；幂等生产自 3.0 起默认开启，KIP-679，语义以官方文档为准）；② 它只解决"生产重复"，不解决"消费重复"——消费重复还在下游等着（Level 4）。

### Transfer——这个思想还能迁移到哪里

1. **确认级别 = SLA 的语言**：任何"发出去"的接口都要声明"收到意味着什么"——支付回调、短信网关、文件上传同构。
2. **幂等键的端到端设计**：生产端去重键（序号）+ 消费端业务键（orderId）是两段幂等的标准组合。
3. **超时重试的真相**：分布式系统里"失败"往往不是真失败，而是"确认没回来"——重试机制必须按这个前提设计。

本层留下的新账：Producer 侧清楚了。但 acks=all 就万事大吉了吗？ISR 收缩时，副本确认的"all"可能名存实亡。→ 逼出 Level 3。

### Level Ending

```
🔴 口诀：确认级别自己选，成功形态藏窗口。
```

## Level 3：Broker 落定与副本——ack 级别背后的机理

一句话认知墙：acks=all 明明要求所有副本确认，为什么生产上还是发生过"确认了却丢了"？

### 前置知识关卡

- [ ] 能按级别说出 send 成功的含义（答不出回 Level 2）
- [ ] 知道 ISR 概念（mq-00 提过，本文正式展开）

### Why——"all"是动态的

**老陈**：acks=all 的真实语义是"**当前 ISR 集合内的所有副本**都确认"。ISR（In-Sync Replicas）是"跟得上 Leader 的副本"名单——它是**动态收缩**的。副本挂掉或落后，会被踢出 ISR；此时如果只有 Leader 自己还在 ISR 里，acks=all 就退化成 acks=1 的效果。**"all"随 ISR 缩水而缩水**，这就是"确认了却丢了"的头号机理。

### What——ISR 与 min.insync.replicas 的组合

```text
Kafka 副本模型（Topic: ORDER_EVENT, replication factor = 3）：

  Partition 1:  Leader(B1)  ← 写入入口
                Follower(B2) ← ISR 成员，同步复制
                Follower(B3) ← 落后被踢出 ISR

acks=all + min.insync.replicas=2 的含义：

① 写入时，Leader 写入本地日志（page cache）+ **ISR 内全部副本**确认 → 才算成功
  （本例 rf=3，初始 ISR={B1,B2,B3} → 要 3 个都确认；min.insync=2 不是"确认 2 个"，
  是"ISR 规模低于 2 就拒写"的水位线）
② B3 挂了 → ISR = {B1, B2} → 确认要求降为 2 个（仍等于"全部 ISR 成员"）；ISR 规模(2) ≥ min=2 → 正常写
③ B2 也挂了 → ISR = {B1} → ISR 数(1) < min(2)
   → Broker 拒绝写入！Producer 收到 NotEnoughReplicas
   —— 宁可拒绝服务，也不降低安全水位
④ 若 min.insync.replicas=1 → ③ 不拒绝 → 但确认退化为"只有 Leader"
   —— B1 随后宕机 → 最后一批"已确认"消息可能丢失（mq-08 详述切换细节）
```

> 📌 最容易被误解的一点：**副本同步 ≠ 同步刷盘**。acks=all 确认的是"副本把消息写进了自己的 page cache 并返回"，不是"每个副本都 fsync 了"（Kafka 默认语义）。所以 acks=all 防的是"单机进程/磁盘故障"（数据在别的机器上有副本），**防不住"所有副本机器同时断电"**（page cache 全蒸发）。要防后者，得在各副本上强制 fsync——Kafka 默认不这么做，因为副本冗余已经把概率压到足够低。**可靠性的本质是概率管理，不是开关**。

### How——E 在三种 acks 下的落定推演

```text
配置 A：acks=0
  send 即返回 → 网络丢、Broker 拒收 → E 无声消失 → 仅适合指标/日志

配置 B：acks=1
  Leader 写入本地日志确认 → Leader 挂（磁盘坏）→ E 丢失
  → 适合"偶尔丢可容忍 + 吞吐优先"

配置 C：acks=all + min.insync.replicas=2 + rf=3
  ISR 内全部副本确认（ISR 满时 = 3 个确认；B3 挂后缩为 2 个时 = 2 个）→ 任一单机故障不丢 E
  → 交易链路标准配置

配置 D：C + 同步刷盘（RocketMQ SYNC_FLUSH 类比）
  ISR 内副本全部 fsync 确认 → 断电也不丢（窗口内）
  → 代价最高，吞吐下降明显，按业务定夺
```

**徒弟**：那 RocketMQ 这边怎么对应？

**老陈**：RocketMQ 的模型是"刷盘 × 复制"两个维度正交：刷盘分同步（SYNC_FLUSH）/异步（ASYNC_FLUSH），复制分同步/异步。同步刷盘+同步复制 ≈ 最强；异步刷盘+异步复制 ≈ 吞吐优先。**Kafka 用 acks 一个参数表达了类似光谱，RocketMQ 拆成了两个维度**——本质都是"确认级别"这个思想的两种落地。

### Transfer——这个思想还能迁移到哪里

1. **"全部"必须定义集合**：分布式里的 all/majority 永远要问"谁的集合"——数据库 quorum、Raft 的多数派同构。
2. **动态水位线**：min.insync.replicas 是"安全水位线"——宁可拒绝服务不降级安全的模式，在 DB 半同步复制（半同步超时降级）里有反面教训。
3. **可用性与一致性的显式旋钮**：把 CAP 的选择做成参数，让业务自己调——这是 MQ 比 DB 更诚实的做法。

本层留下的新账：Broker 侧守住了一关。但 E 到了消费者手里——ack 到底该什么时候发？先处理还是先提交，这步棋怎么走？→ 逼出 Level 4。

### Level Ending

```
🔴 口诀：all 是动态集合，副本同步不是刷盘。
```

<a id="level-4"></a>

## Level 4：Consumer 提交——神话③ 的破解

一句话认知墙：消费者把消息处理完，提交 offset——这不就是"消费成功"吗？还能出什么岔子？

### 前置知识关卡

- [ ] 能解释 acks=all 与 ISR 收缩的相互作用（答不出回 Level 3）
- [ ] 知道位点提交与消息删除无关（mq-01/mq-02）

### Why——ack 是"进度"，不是"结果"

**老陈**：神话③的完整表述是"消费成功就是 ack"。真相：**ack/位点提交只表达一件事——"这条消息我不再要了"，不表达"这条消息我处理成功了"**。两个动作（业务处理、提交位点）之间必然有个先后，崩溃点落在哪个先后之间，就产生哪种损失：

| 提交时机 | 崩溃点 | 后果 | 语义 |
| ---- | ---- | ---- | ---- |
| 先处理 → 后提交 | 处理成功、提交前崩溃 | 消息重投 → **重复处理** | at-least-once |
| 先提交 → 后处理 | 提交成功、处理前崩溃 | 消息跳过 → **丢失处理** | at-most-once |

### What——三种提交模式与自动提交的陷阱

```text
模式一：自动提交（Kafka enable.auto.commit=true，默认开启）
  消费者 poll 一批 → poll() 内按 auto.commit.interval.ms 触发异步提交
  （提交由 poll 调用链驱动，无独立提交线程；KIP-62 的后台线程只发心跳）
  陷阱：提交与处理无顺序保证——既可能"丢"也可能"重"：
  · 拉取了但业务没处理 → 位点已提交 → 崩溃后这批消息被跳过 = 丢失
  · 处理成功但还没到提交点 → 崩溃 → 重启重投 = 重复（资损场景同样致命）

模式二：手动提交（同步/异步）
  业务处理成功 → commitSync/commitAsync
  陷阱：异步提交的乱序覆盖、同步提交的吞吐代价

模式三：事务式消费-生产（read-process-write）
  消费 E + 生产新消息 + 事务内提交位点 → 三者原子（Kafka 事务）
  边界：Kafka 事务只覆盖 Kafka 内部（消费/生产/位点提交原子），
  业务 DB 写不进事务——DB 那侧仍要靠幂等/本地消息表兜底（mq-07 展开）
```

> 📌 最容易被误解的一点：**"消费失败就不提交位点，重试就行"——重试是有限度的**。Kafka 默认不重试（消费失败由业务自己决定何时再读，位点不动即可）；RocketMQ 有内置重试队列（消费返回失败自动进重试队列，**并发消费模式**默认最多 16 次之后进 DLQ；顺序消费模式是无限重试——默认值以官网为准）；RabbitMQ 靠 nack+requeue。**三种产品的"重试"实现完全不同，但"重试上限之后去哪"这个问题三家都必须回答**——答案都是死信（mq-07 展开）。

### How——E 的扣库存提交位点的完整时序

```text
正确姿势（at-least-once + 幂等）：

① 拉取 E（offset=501）
② 按 orderId 查幂等表：未处理过 → 继续；已处理 → 直接提交位点跳过
③ 业务事务：扣库存 + 写幂等记录（同 DB 事务）★业务原子点
④ 提交位点：offset → 502 ★进度原子点
⑤ 崩溃推演：
   - ③ 成功后 ④ 前崩溃 → 重投 → ② 幂等拦截 → 不重复扣减
   - ② 前崩溃 → 重投 → 正常处理
   结论：业务效果恰好一次

错误姿势（自动提交）：
① poll 拿到 E（自动提交已在后台推进位点）
② 业务处理慢/失败 → 重试无从谈起（位点已走）
③ 消息静默丢失 → 对账才发现
```

**徒弟**：为什么③和④不能合成一个原子动作？比如本地消息表方案？

**老陈**：问到了事务消息的门口。③和④跨两个系统（业务 DB、Broker），没有现成的分布式事务能原子覆盖——这就是为什么有 RocketMQ 半消息、Kafka 事务、本地消息表三种补偿方案。它们的本质都是**把"跨系统原子性"降级成"可恢复的最终一致"**。mq-07 会把这三种方案摆上台面对比，本文先记住结论：**没有原子性，只有可恢复性**。

### Transfer——这个思想还能迁移到哪里

1. **进度与结果分离**：任何"处理队列"都要区分"读过"与"做完"——文件处理、爬虫抓取、批处理作业同构。
2. **幂等拦截前置**：把幂等检查放在业务处理之前，是 at-least-once 世界的标准姿势。
3. **可恢复性 > 原子性**：跨系统没有银弹，设计目标从"不犯错"转向"犯错可修"。

本层留下的新账：四道关卡的每一道都留了缝——有没有一道防线能兜住所有缝？有：对账补偿。→ 逼出 Level 5。

### Level Ending

```
🔴 口诀：先处理再签收，先签收会丢件。
```

<a id="level-5"></a>

## Level 5：对账补偿——最后一道防线

一句话认知墙：如果每道关卡都有缝，为什么生产上交易链路还敢用 MQ？

### 前置知识关卡

- [ ] 能画出"先处理后提交/先提交后处理"的损失矩阵（答不出回 Level 4）
- [ ] 知道幂等拦截前置的姿势（Level 4）

### Why——为什么四道防线还不够

**老陈**：因为所有机制防的都是"已知故障模式"，而生产事故大多是"组合拳"——Producer 确认级别配错了、ISR 收缩没告警、消费幂等键设计有漏洞，三个小缝叠出一个大洞。**机制防患，对账兜底**——对账回答的问题不是"会不会丢"，而是"丢了能不能发现、能不能补"。

### What——对账闭环的最小设计

```text
        消息状态表（业务 DB 内）                 定时对账任务
   ┌──────────────────────────┐      ┌──────────────────────────┐
   │ orderId | eventStatus     │ ←→  │ ① 扫描超时未完成的订单事件  │
   │ O_001   | PUBLISHED       │      │ ② 与 Broker 位点/消息比对   │
   │ O_002   | CONSUMED        │      │ ③ 与业务结果比对（库存）    │
   │ O_003   | PENDING(超时)   │      │ ④ 差异 → 告警 + 补偿任务    │
   └──────────────────────────┘      └──────────────────────────┘
```

三段对账（覆盖三道防线）：

```text
① 生产对账：本地事务写消息状态表 PENDING → 发送 E → 更新 PUBLISHED
   定时扫描 PENDING 超时记录 → 重发或告警（本地消息表方案）

② 位点对账：消费端记录"已处理的最后位点"与 Broker 位点比对
   lag 异常（堆积或跳号）→ 告警

③ 结果对账：订单状态与库存结果核对（订单已支付但库存未扣 = 差异）
   差异单 → 人工/自动补偿（补扣库存或退款）
```

> 📌 最容易被误解的一点：**对账不是"事后擦屁股"，是可靠性的组成部件**。银行对账系统不是银行系统的附属品，它就是支付系统本身的一部分。上 MQ 不做对账，等于开着没有仪表盘的车——不是不会出事，是出了事你不知道。

### How——一次真实的丢消息被对账救回的全过程

```text
① 大促深夜，Producer acks 级别被误改为 1（灰度配置错误）
② Leader 磁盘故障，窗口内 12 条 E 丢失——"已确认"消息无声蒸发
③ 消费端无感（没收到的消息不会报错）
④ 凌晨 3 点，结果对账任务扫描：
   "订单状态=已支付 且 库存未扣 且 无消费记录" → 12 条差异
⑤ 告警 → 值班确认 → 从订单 DB 重建 12 条 E → 重新投递
⑥ 复盘：配置变更未走审批；acks 级别纳入巡检
   结论：机制失守，对账兜底——资损被控制在窗口内
```

**徒弟**：这 12 条 E 是怎么"重建"的？订单 DB 里本来就有完整信息吗？

**老陈**：对——这就是**事件溯源思维**的落地：业务事实的源头是 DB（订单表），E 只是事实的投影。投影丢了，可以从源头重建。前提是①订单状态机完整（每个状态变更都有记录）；②重建脚本经过演练。**DB 是事实源，MQ 是传输带**——分清这个主次，可靠性设计就豁然开朗。

### Transfer——这个思想还能迁移到哪里

1. **事实源与投影**：任何消息都是 DB 状态的投影——丢了投影可以重建，丢了事实源无法挽回；架构上先保住事实源。
2. **对账即监控**：三段对账覆盖生产/传输/消费，是比任何单点监控都强的可观测性设计。
3. **补偿任务化**：差异单 → 补偿任务 → 幂等执行，是可恢复性工程的通用闭环。

本层留下的新账：可靠性是买来的——每个级别都有价签。什么业务买什么级别，怎么验收？→ 逼出 Level 6。

### Level Ending

```
🔴 口诀：机制防患，对账兜底，事实源可重建。
```

<a id="level-6"></a>

## Level 6：可靠性生产决策——成本曲线与验收

一句话认知墙：可靠性配置是不是越强越好？"零丢失"到底要花多少钱？

### 前置知识关卡

- [ ] 能画出三段对账闭环（答不出回 Level 5）
- [ ] 知道可靠性是概率管理（Level 3）

### Why——可靠性是成本曲线

**老陈**：每一档可靠性都有价签——更高的确认级别、更勤的刷盘、更多的副本，每一项都吃吞吐、吃延迟、吃机器。**买"零丢失"的每一分钱，都花在越来越小的概率上**：

| 可靠性配置 | 防住什么 | 付出的代价 |
| ---- | ---- | ---- |
| acks=0 + 自动提交 | 什么都不防 | 吞吐最大 |
| acks=1 + 手动提交 | 网络丢、Broker 拒收 | 吞吐小幅下降 |
| acks=all + 手动提交 + 幂等 | 单机故障 | 延迟上升、成本 ×3（3 副本） |
| 同步刷盘 + 同步复制 | 单机断电 | 吞吐显著下降 |
| + 对账补偿 + 演练 | 组合故障、未知故障 | 研发与运营成本 |

**先给业务分级，再选配置**——交易主链路买最贵的，通知类买最便宜的。**"一刀切全上最强"是花最贵的钱买最慢的系统**。

### What——可靠性验收清单

```text
① 故障演练（不演练的可靠性都是纸面可靠性）：
   - kill Leader → 观察切换窗口与数据完整性
   - 断电重启（模拟）→ 观察 page cache 丢失窗口
   - 消费者处理中途崩溃 → 观察重复与幂等拦截
② 指标监控：
   - 生产确认失败率、重试次数
   - lag 水位与 DLQ 积压
   - 对账差异数/百万
③ 回放能力：从 DB 重建消息的脚本 + 定期演练
```

### How——E 的可靠性配置决策全过程

```text
① 业务分级：E 是交易主链路 → 最高档
② 配置选择：acks=all + min.insync.replicas=2 + rf=3
   + 幂等生产 + 手动提交 + 消费幂等表 + 三段对账
③ 验收演练：
   - 演练 1：kill Leader → 无消息缺口，切换窗口内延迟上升可接受
   - 演练 2：消费者崩溃重放 → 幂等拦截生效，库存不重复扣
   - 演练 3：人为制造 12 条丢失 → 对账发现 → 重建投递成功
④ 上线条件：三项演练全部通过 + 对账差异数连续 7 天为 0
```

**徒弟**：演练 3 里"人为制造丢失"具体怎么造？

**老陈**：直接往测试环境的订单表插 12 条"已支付"状态、但不发消息——对账任务必须在 N 分钟内发现这 12 条差异。**验收的本质不是"看配置对不对"，是"证明兜底真的兜得住"**。配置可以背，兜底能力只能练。

### Transfer——这个思想还能迁移到哪里

1. **可靠性分级定价**：SLA 分级是架构的通用语言——存储、网络、计算都要按业务分级配置。
2. **演练是验收的一部分**：混沌工程（Chaos Engineering）不是大厂专属，kill 进程是每家都能做的第一步。
3. **纸面可靠性 vs 演练可靠性**：评审时只认演练记录，不认配置截图。

本层留下的新账：可靠性闭环了。但 at-least-once 世界里的重复与乱序是常态——E 被投递两次时，扣库存怎么做到"恰好一次"？顺序到底能保到什么程度？→ 逼出 mq-04（顺序、重复与幂等）。

### Level Ending

```
🔴 口诀：可靠性按级买，兜底靠演练验。
```

<a id="pitfalls"></a>

# ⚠️ 坑与细节

## 坑 1：认为 acks=all 就是"零丢失"

错误理解：所有副本确认 = 消息绝对安全。

原因：忽略了 ISR 收缩与 page cache 断电窗口——all 是动态集合，确认的是副本写入 page cache。

比喻后果：签收单盖了章，但货还堆在运输车（page cache）里，车翻了货没了。

线上现象：Leader 宕机后部分"已确认"消息消失，对账发现缺口。

修正：理解 acks=all 的真实覆盖范围（mq-08 详述切换细节）；交易链路加对账。

## 坑 2：开启自动提交追求"简单"

错误理解：enable.auto.commit 省事，官方默认值肯定安全。

原因：不知道自动提交在 poll 时提交的是"已拉取位点"，与"已处理"无关。

比喻后果：快递员把包裹从车上拿下来就算"签收"。

线上现象：消费者 OOM 重启，中间一段消息静默跳过，业务无感知。

修正：业务链路一律手动提交；自动提交只用于指标类消费。

## 坑 3：消费失败不提交位点 + 无限重试

错误理解：失败了就重试，总有一次成功。

原因：不知道重试是有限度的（RocketMQ 默认 16 次进 DLQ），无限重试会卡死队列并放大积压（神话④）。

比喻后果：一个派不出的件堵在传送带出口，后面全部堆积。

线上现象：一条毒消息（poison message）让整个队列消费停滞。

修正：设置重试上限 + DLQ + 告警；毒消息人工介入。

## 坑 4：生产端重试导致重复，消费端无幂等

错误理解：消息重复概率低，业务表加个唯一索引麻烦。

原因：低估 at-least-once 的必然性——任何超时重试、重投、位点回拨都会产生重复。

比喻后果：快递重发，收货人签了两份货款。

线上现象：库存重复扣减、优惠券重复发放——资损。

修正：幂等键设计（业务键 + 唯一约束），幂等拦截前置。

## 坑 5：把"Broker 可靠"当成"链路可靠"

错误理解：MQ 配置全拉满，业务侧就不用管了（神话⑫ 的可靠性侧面）。

原因：MQ 只覆盖传输环节，业务效果（处理成功与否）在 MQ 视野之外。

比喻后果：运输公司 100% 准点，收货人把货摔了——不能怪运输公司。

线上现象：消息全部送达，业务处理失败，无人知晓。

修正：对账覆盖业务结果，不只看消息送达率。

## 坑 6：对账任务只告警不补偿

错误理解：对账发现差异，发个告警就算完成使命。

原因：把对账当监控用，丢了"补偿"这一半闭环。

比喻后果：盘点发现缺货，贴个条子就下班。

线上现象：差异单堆积，人工处理不过来，对账沦为摆设。

修正：差异 → 自动补偿任务（幂等）→ 人工兜底，双层闭环。

## 坑 7：可靠性配置一刀切

错误理解：所有 Topic 都 acks=all + 3 副本 + 同步刷盘。

原因：不看业务分级，用最贵的配置买最慢的系统。

比喻后果：寄明信片也要用武装押运。

线上现象：通知类低价值消息拖累整体吞吐，磁盘成本翻倍。

修正：业务分级定价（Level 6 的配置表），按需选档。

## 坑 8：验收看配置不看演练

错误理解：配置截图 + 官方文档 = 可靠性证明。

原因：纸面可靠性无法验证"组合故障"下的真实行为。

比喻后果：消防演练从来没做过，火警响了没人会用灭火器。

线上现象：故障发生才发现 acks 配置没生效、切换流程没人会走。

修正：演练三件套（kill Leader / 崩溃重放 / 制造丢失）纳入上线门槛。

<a id="errata"></a>

# 📚 版本勘误表

| 错误说法 | 准确说法 |
| ---- | ---- |
| "MQ 保证消息不丢" | 不丢 = 确认级别 × 刷盘/副本 × 消费提交 × 对账的综合结果 |
| "acks=all 就是零丢失" | 只防单机故障；ISR 收缩与 page cache 断电窗口仍然存在 |
| "exactly-once 是配置开关" | 是组合拳：幂等生产 + 事务协调 + 幂等消费，效果恰好一次 |
| "消费成功就是 ack" | ack 是进度提交；处理成功是另一层，两者之间有崩溃窗口 |
| "重试一定提高可靠性" | 重试制造重复、放大积压；必须配合幂等与上限 |
| "自动提交是官方默认所以安全" | 默认是吞吐优先；自动提交在 poll 时提交，与处理无关 |
| "副本同步就是刷盘" | 副本确认的是 page cache 写入，不是 fsync |
| "对账是事后补救" | 对账是可靠性的组成部件，与机制同等地位 |
| 坦白：我以前也讲错过"acks=all 就绝对不丢" | 早期忽略了 ISR 收缩；"all"是动态集合，水位线要 min.insync.replicas 撑着 |
| 坦白：我以前也讲错过"MQ 事务消息就是 exactly-once" | 事务消息解决的是生产端原子性，消费端幂等仍需业务自建 |
| 坦白：我以前也讲错过"RocketMQ 的 SEND_OK 只代表已受理入内存" | SEND_OK 的含义由 Broker 刷盘配置决定：SYNC_FLUSH 下已刷盘、ASYNC_FLUSH 下才只是入内存 |

<a id="decisions"></a>

# 🏆 生产决策卡

## Decision Card 1：交易主链路的可靠性配置

### 场景

E 是支付成功事件，资损敏感，预算允许吞吐下降。

### 判断

acks=all + min.insync.replicas=2 + rf=3 + 幂等生产 + 手动提交 + 消费幂等 + 三段对账。

### Mechanism → Decision

| 机制 | 工程决策 |
| -- | ---- |
| 单机故障 | acks=all（ISR 集合确认） |
| ISR 收缩退化 | min.insync.replicas=2（宁可拒写不降级） |
| 生产重复 | enable.idempotence（序号去重） |
| 消费重复 | orderId 唯一约束 + 幂等表 |
| 未知故障 | 三段对账 + 补偿任务 |

### 禁止决策

- acks=1 上交易主链路并宣称不丢
- 开启自动提交处理资损敏感消息

### 验收指标

- kill Leader 演练：无消息缺口，切换窗口 p99 ≤ 2s
- 崩溃重放演练：幂等拦截 100%，库存零重复扣减
- 对账差异数连续 7 天 = 0

---

## Decision Card 2：通知类消息的可靠性配置

### 场景

支付成功通知短信/推送（低价值、可容忍少量丢失、不可容忍延迟）。

### 判断

acks=1 + 手动提交（简化版：处理成功提交）+ 结果对账即可；不配幂等表，用消息 ID 去重即可。

### Mechanism → Decision

| 机制 | 工程决策 |
| -- | ---- |
| 吞吐优先 | acks=1 |
| 少量重复 | 通知网关侧按消息 ID 去重 |
| 丢失容忍 | 结果对账低频扫描 |

### 禁止决策

- 为通知类消息配 3 副本同步刷盘（成本错配）
- 完全不对账（丢失无感知会积成口碑事故）

### 验收指标

- 端到端 p99 ≤ 500ms
- 月对账差异 ≤ 1‰（可解释）

---

## Decision Card 3：消费提交模式的选择

### 场景

新消费组上线，团队争论用自动提交还是手动提交。

### 判断

按消息价值决策：业务消息 → 手动提交 + 幂等；指标/日志 → 自动提交可接受。

### Mechanism → Decision

| 机制 | 工程决策 |
| -- | ---- |
| 业务消息 | 先处理后提交（at-least-once）+ 幂等拦截 |
| 指标消息 | 自动提交（容忍丢失） |
| 批量处理 | 批量成功后提交整批位点 |

### 禁止决策

- 业务消息用自动提交
- 手动提交但无幂等（重复同样资损）

### 验收指标

- 崩溃重放演练：无业务重复效果
- lag 曲线正常，无位点跳号

<a id="cross-language"></a>

# 🌍 跨语言视角

## 同一个问题：确认与提交

| 语言 | 对应机制 |
| -- | ---- |
| Java | Kafka 客户端 acks 配置、KafkaConsumer.commitSync；RocketMQ SendCallback / Consumer 返回 CONSUME_SUCCESS |
| Go | sarama（config.Producer.RequiredAcks）、kafka-go（CommitMessages） |
| Rust | rdkafka（Acks 枚举、Consumer::commit） |
| Python | confluent-kafka（enable.auto.commit=False + consumer.commit） |

## 跨语言仍成立的判断力

1. **投递语义是协议与配置的事，不是语言的事**：acks 级别、提交时机在任何语言客户端语义一致——换语言不换可靠性模型。
2. **先处理后提交是跨语言的纪律**：无论 Java 回调还是 Go channel，崩溃窗口都在"处理与提交之间"，幂等拦截都是同一姿势。
