# 🏭 全文唯一比喻：货架与账本

```text
现实世界（仓库）                      技术世界（MQ 存储）

货架（包裹上架，取走即移出）        ←→ 队列存储（RabbitMQ queue）
账本（流水逐行记录，永不改行）       ←→ 日志存储（Kafka / RocketMQ）
索引卡（按货品名指向账本页码）       ←→ 稀疏索引 / ConsumeQueue
入库台账顺序写（不插页不改页）       ←→ 顺序写 + append-only
仓库总账 + 各柜台索引               ←→ CommitLog + ConsumeQueue
```

| 比喻元素 | 技术概念 | 唯一职责 |
| ---- | ---- | ---- |
| 账本 | Log / CommitLog | 只增不删的顺序记录 |
| 索引卡 | Index / ConsumeQueue | 从业务键定位到账本位置 |
| 入库顺序 | append-only 顺序写 | 最大化磁盘吞吐 |
| 台账保留期 | Retention / TTL | 决定历史数据何时销毁 |

# 正文：六个 Level 打穿"一次落盘"

<a id="level-1"></a>

## Level 1：为什么必须落盘——内存中转站的死亡场景

一句话认知墙：内存比磁盘快几个数量级，MQ 把消息放内存不就行了，为什么非要落盘？

### 前置知识关卡

- [ ] 知道 E 的"落定"是对外可见时刻（mq-00 Level 2）
- [ ] 知道队列模型与日志模型的存储差异（mq-01）

### Why——内存中转站的三个死亡场景

**徒弟**：Redis 就是内存存储，单机十万 QPS 也不丢性能。MQ 的消息也放内存，刷盘交给异步线程慢慢做，不行吗？

**老陈**：Redis 敢用内存，是因为它的数据**可以重新生成**（缓存回源、锁有过期时间）。E 不行——E 是业务事实的载体，扣库存的依据，丢了就是事故。内存中转站有三个死亡场景：

| 死亡场景 | 机理 | 后果 |
| ---- | ---- | ---- |
| 进程重启 | 内存态全部蒸发 | 窗口内所有消息静默消失 |
| 机器断电 | 连异步刷盘线程都来不及执行 | 已"确认"的消息丢失 |
| OOM / 堆溢出 | Broker 内存被打满 → 长 GC / 崩溃 / 网络背压阻塞 | 已"确认"的消息可能永远到不了 Broker，或服务不可用 |

所以落盘不是"要不要"的问题，是**消息在哪一刻算安全**的问题。内存可以当缓冲，但"安全"的定义必须建立在磁盘上。

### What——落盘与安全的分级

```text
E 的落定分级（从弱到强）：

级别 0：写入生产者本地缓冲          ← 进程挂即丢（mq-00 Level 4）
级别 1：到达 Broker 内存            ← Broker 挂即丢
级别 2：写入 OS page cache         ← 断电即丢
级别 3：fsync 到磁盘              ← 只有磁盘上才真正安全
级别 4：副本也落盘                 ← 单机故障也不丢（mq-08）
```

> 📌 最容易被误解的一点：**"写文件"≠"写磁盘"**。`write()` 系统调用返回时，数据通常还在内核的 page cache 里，并没有到磁盘——真正到磁盘的是 `fsync` 之后。这个"page cache 与磁盘之间"的窗口，是 MQ 丢失数据的头号高发区，也是本文后面每一层都在处理的核心矛盾。

### How——E 落盘的完整时序（6 步）

```text
① Producer 发送 E → Broker 网络线程接收（字节在网卡缓冲）
② E 写入 Broker 内存（堆内对象）
③ Broker 调用 write() → E 进入 OS page cache ★第一落点
④ 异步/同步刷盘线程调 fsync() → E 落到磁盘 ★安全点
⑤ 更新索引（E 可以被消费定位）
⑥ 副本同步（mq-08 展开，本文不表）
```

两个 ★ 之间（③→④）就是丢失窗口：**fsync 之前，机器断电，E 随 page cache 一起消失**。而 fsync 的开销正是"为什么不能每条都同步刷盘"的原因——下一层先回答"磁盘到底慢在哪"，才能理解这个取舍。

**徒弟**：那我把 fsync 频率调最高，每条都刷，不就不丢了？

**老陈**：那吞吐会断崖式下跌——fsync 要等磁盘机械动作（HDD 的旋转+寻道），每条等一次，QPS 就变成磁盘 IOPS。**不丢与吞吐是同一根跷跷板的两端**，中间的砝码是"批量"。这正是本文 Level 6 的决策战场。

### Transfer——这个思想还能迁移到哪里

1. **安全分级思维**：任何持久化系统都要定义"数据在哪一刻算安全"——DB 的 WAL、Redis 的 AOF 都是同一个分级表。
2. **缓冲与安全分离**：内存是缓冲，磁盘是安全——把"快"和"稳"拆成两层，各司其职。
3. **批量是性能与安全的通用砝码**：攒批写入（DB 批量 commit、日志批量 flush）是分布式系统永恒的调节旋钮。

本层留下的新账：落盘是必须的，但"磁盘慢"的直觉会让人不敢落盘——磁盘真的慢吗？顺序写和随机写是一回事吗？→ 逼出 Level 2。

### Level Ending

```
🔴 口诀：内存是缓冲，磁盘才是安全。
```

## Level 2：顺序写为什么快——磁盘的真相

一句话认知墙：教科书说磁盘比内存慢几个数量级，为什么 MQ 敢说"顺序写磁盘接近内存写"？

### 前置知识关卡

- [ ] 能说出 E 落定的四个级别（答不出回 Level 1）
- [ ] 知道 write() 与 fsync() 的区别

### Why——"磁盘慢"错在哪

**老陈**：磁盘慢的直觉来自**随机写**——数据库的 B+ 树更新是这里改一点、那里改一点，每次都要先寻道、再旋转、再写。HDD 的机械寻道是毫秒级，这期间磁盘什么都干不了。但 MQ 的写入模式完全相反：**顺序追加**。写头不需要跳来跳去，磁道顺序扫过，速度就完全不同量级。

| 写入模式 | 瓶颈 | 量级（HDD 时代经典结论） |
| ---- | ---- | ---- |
| 随机写（B+ 树页更新） | 寻道 + 旋转延迟 | 百次/秒级 IOPS |
| 顺序写（append log） | 带宽 | 接近内存写（业界经典测量结论，见下注，待本机实测复核） |

> 版本说明：依据 ACM Queue 2009（Adam Jacobs, "The Pathologies of Big Data"）的经典测量结论——**顺序磁盘访问快于随机内存访问**（原文方向是"顺序读盘 > 随机读内存"，"顺序写接近内存写"是据此流传的通俗表述）。HDD 时代结论；SSD 时代随机写能力大幅上升，但"顺序写 ≥ 随机写、append-only 免寻址"的方向不变。具体比值待 mq/experiments 实测。

### What——MQ 存储的两条铁律

```text
铁律一：只追加，不修改
  账本逐行往下写，已写的行永不回头改——没有"寻址写"，就没有寻道

铁律二：写入路径唯一
  Kafka：一个分区只有 Leader 写（副本由 Leader 顺序复制）
  RocketMQ：所有 Topic 所有队列共用一条 CommitLog 写入路径
```

> 📌 最容易被误解的一点：**顺序写不解决"读"的问题**。顺序写的账本，要找"第 10086 行"还是得靠索引。写得快，读得慢——这就是 Level 4/5 里 Kafka 和 RocketMQ 各自建索引的原因。**写入结构解决吞吐，索引结构解决定位**，两者分开设计。

### How——E 写入的磁盘动作拆解

```text
Kafka 视角（E 追加到 Partition 1 的当前 segment）：

① E 到达 Leader 的写入队列
② 拿到当前活跃 segment 的写入位置（文件尾）
③ write() 追加字节到文件尾 ★顺序写，无寻道
④ 更新内存中的 offset 索引（不立刻写盘）
⑤ 副本拉取同一位置的数据（顺序复制）
⑥ fsync 时机由配置/OS 决定（Level 6 展开）

对比：若 E 的写入是随机写（比如按 orderId 哈希落位）
① 定位写入块 → 寻道（HDD 毫秒级）
② 磁头等待扇区旋转到位
③ 写入 → 重复上述动作
结论：顺序写是 MQ 吞吐的物理根基，没有它，百万级吞吐无从谈起
```

**徒弟**：那为什么数据库不也用 append-only 存储？

**老陈**：好问题——数据库当然用。MySQL 的 binlog、redo log、LSM 树的 WAL 全是 append-only。但数据库还要回答"随机读"（按主键查任意一行），所以它必须再建 B+ 树索引，索引的维护又引入随机写。**MQ 把"随机读"的难题推迟给了消费者**——稳态消费是按位点顺序读的，基本没有随机读需求（重启续读、位点回拨、seek 补数是文件内随机寻址，是例外不是常态），所以它可以纯 append。这是"场景简单 → 结构简单 → 性能极致"的典型例子。

### Transfer——这个思想还能迁移到哪里

1. **append-only 是日志类系统的通用底座**：LSM 树（RocksDB）、redo log、binlog、事件溯源——先顺序写，再异步整理。
2. **把难题推迟给读侧**：写时简单、读时复杂——bitcask、日志文件系统都是这个哲学。
3. **结构简单是性能的护城河**：不要为了"通用"给写入路径加分支，每一条分支都是吞吐的税。

本层留下的新账：顺序写解决了写吞吐，但消费端要读——数据从磁盘到网卡，中间要经过几次拷贝？为什么 Kafka 消费能那么快？→ 逼出 Level 3。

### Level Ending

```
🔴 口诀：只追加不修改，顺序写免寻道。
```

## Level 3：page cache 与零拷贝——OS 层的助攻

一句话认知墙：消息写到磁盘，又要从磁盘读出来发给消费者，这一来一回的拷贝开销藏在哪？

### 前置知识关卡

- [ ] 能解释顺序写与随机写的机理差异（答不出回 Level 2）
- [ ] 知道 write() 与 fsync() 的区别（Level 1）

### Why——为什么 Kafka 消费几乎不做磁盘读

**老陈**：先看传统数据流的四次拷贝：

```text
传统路径（无 page cache 意识）：
磁盘 → 内核缓冲区 → 用户态应用缓冲 → 内核 socket 缓冲 → 网卡
        ↑ 拷贝1（DMA）  ↑ 拷贝2（CPU）    ↑ 拷贝3（CPU）  ↑ 拷贝4（DMA）
```

其中拷贝 2、3 是 **CPU 亲自参与**的用户态/内核态拷贝——数据根本没被"处理"，只是路过应用层，却要付出两次 CPU 拷贝和两次上下文切换。而 page cache 的存在改变了这个局面：**消息写在 page cache 里，就同时完成了"落盘预备"和"读取缓冲"两件事**——Kafka 消费时，如果消息还在 page cache，直接从内核缓存读，磁盘都不碰。

### What——page cache 与 sendfile 零拷贝

```text
Kafka 消费路径（page cache 命中 + sendfile）：

磁盘 → page cache ──sendfile──→ 网卡
        ↑ DMA 拷贝           ↑ DMA 拷贝

没有用户态参与！CPU 只负责调度，数据由 DMA 搬运两次。
```

| 机制 | 干什么 | 省掉了什么 |
| ---- | ---- | ---- |
| page cache | 内核托管最近读写的文件页 | 热数据绕过磁盘 |
| mmap | 把文件映射到用户态地址空间 | 用户态/内核态之间的显式拷贝（映射式访问） |
| sendfile | 内核直接把文件数据送到 socket | 用户态中转的拷贝 + 上下文切换 |

> 📌 最容易被误解的一点：**page cache 不是 MQ 自己的缓存，是 OS 的**。这意味着两个后果：① MQ 进程重启，page cache 还在（数据在 OS 手里，不在进程堆里）——所以 Kafka 依赖 page cache 的设计，进程重启不丢"已写但未 fsync"的数据，但**机器断电会丢**；② page cache 的大小与淘汰由 OS 决定，MQ 只能"影响"不能"控制"——这就是为什么 Kafka 的官方调优建议"别乱改 fsync，交给 OS"。

### How——E 的消费读取路径拆解

```text
① 消费者 fetch（offset = 501，顺序读 P1 的 segment 文件）
② 内核查 page cache：
   - 命中：直接从内核缓存读 → 跳过磁盘
   - 未命中：磁盘读入 page cache（顺序预读，一次读多页）
③ sendfile 把数据从 page cache 直送网卡
④ 消费者收到 E，处理，提交位点
```

**徒弟**：RocketMQ 也是这么干的吗？

**老陈**：RocketMQ 的写入路径用了 mmap（CommitLog 默认 mmap 映射），读路径（消费）同样受益于 page cache（4.x/5.x 行为一致）；另外 RocketMQ 提供堆外内存池（transientStorePool，4.2 起引入，5.x 沿用）方案，写入先到堆外内存，减少 page cache 刷盘的抖动。**零拷贝思想两边都有，落地姿势不同**——这正是 Level 5 要展开的。

### Transfer——这个思想还能迁移到哪里

1. **数据只搬运不处理，就永远别让它进用户态**：Nginx 静态文件、文件下载服务都在用 sendfile——IO 密集场景的通用优化。
2. **缓存的所有权问题**：缓存属于 OS 还是属于应用，决定了"进程重启后数据还在不在"——这是 JVM 堆缓存与 page cache 的本质区别。
3. **影响而不控制**：面对 OS 管理的资源（page cache、线程调度），架构设计要"顺势"而非"硬抢"。

本层留下的新账：通用机制讲完了。落到具体产品——Kafka 和 RocketMQ 各自怎么组织账本与索引，为什么一个按分区建账本、一个搞全局一本账？→ 逼出 Level 4。

### Level Ending

```
🔴 口诀：写在页缓存，发出零拷贝。
```

<a id="level-4"></a>

## Level 4：Kafka 存储结构——分区账本

一句话认知墙：一个 Kafka 分区到底长什么样？"分区"在磁盘上是什么、怎么按 offset 定位一条消息？

### 前置知识关卡

- [ ] 能解释 page cache 与 sendfile 的协作（答不出回 Level 3）
- [ ] 知道 Kafka 分区是 append-only 日志（mq-01 Level 3）

### Why——为什么要切成 segment

**徒弟**：一个分区就是一个文件，从 offset 0 写到天荒地老，不就行了吗？

**老陈**：不行。单文件无限增长带来两个真问题：① 删除过期数据只能整文件删——你要删"7 天前的消息"，单文件只能从头截断，代价巨大（文件越大、越频繁地整段清理，代价越高）；② 查找慢——offset 定位只能从头扫。**切成固定大小的 segment 文件**后：删除 = 删整个 segment 文件（干净利落）；定位 = 先按 offset 找到 segment，再在段内二分。**分段是日志管理的通用手法**——数据库的 binlog 轮转、日志系统的日志滚动，全部同构。

### What——分区在磁盘上的完整结构

```text
Topic: ORDER_EVENT / Partition 1 的目录：

├── 00000000000000000500.log        ← 段1（文件名=起始 offset）
│     offset 500: msg D
│     offset 501: E
│     ...
├── 00000000000000000500.index      ← 段1的偏移索引（稀疏）
├── 00000000000000000500.timeindex  ← 段1的时间索引（稀疏）
├── 00000000000000100000.log        ← 段2（正在写的活跃段）
│     offset 100000: msg X
│     ...
├── 00000000000000100000.index
└── 00000000000000100000.timeindex

默认 segment 大小：log.segment.bytes = 1GB（Kafka 官方默认值）
```

**稀疏索引**（关键设计）：index 文件不记录每条消息，而是每写满 `index.interval.bytes`（默认 4KB）记一条 `{相对offset, 物理位置}`。索引文件因此很小，可以全部进内存。

```text
稀疏索引的定位过程（要找 offset = 50123 的 E）：

① 文件名二分：50123 在段 500 和 100000 之间 → 打开 00000000000000000500.log
   （文件名 = 起始 offset，20 位补零）
② 段内 index 二分：找到 ≤ 50123 的最近索引项（如 offset=50120, pos=20480）
③ 从 pos=20480 顺序扫：比对每条消息的 offset，扫到 50123 → 命中
   —— 最多扫 index.interval.bytes 大小（默认 4KB），代价可控
```

> 📌 最容易被误解的一点：**"消费速度"与"offset 提交"是两回事，而"消息删除"只认保留策略**。消费者把位点提交到 100 万，不代表 100 万之前的消息被删——删不删由 `log.retention.hours`（默认 168h）和 `log.retention.bytes` 决定。**位点是读者的书签，保留策略是书架的规则**，两者互不认识。

### How——E 写入 Kafka 分区的完整落账（7 步）

```text
① E 由 Key 路由到 P1（mq-00 Level 4）
② Leader 写入活跃 segment 文件尾（顺序写）
③ 更新内存 offset 索引（攒到 4KB 边界再落 index 文件）
④ 写入内存 timeindex（按时间检索用）
⑤ follower 副本拉取复制（mq-08 展开）
⑥ fsync 时机：默认交给 OS（log.flush.interval.* 默认关闭——Kafka 官方建议依赖 page cache + 副本冗余）
⑦ 保留线程按 retention 检查段文件，过期整段删除
```

**徒弟**：等等，⑥ 说 Kafka 默认不主动 fsync？那不是"级别 2"的安全吗，断电就丢？

**老陈**：对，Kafka 的可靠性哲学是**副本冗余优先于单机 fsync**——一台机器断电，page cache 里的数据丢了，但副本还在（只要副本机器没同时断电）。所以 Kafka 默认不配 fsync 参数，靠多副本兜底。而 RocketMQ 在这件事上走了另一条路——它提供显式的同步刷盘选项。**单机持久化（fsync）与集群冗余（副本）是可靠性的两条腿**，mq-03 和 mq-08 会分别讲清它们各自的丢失窗口。

### Transfer——这个思想还能迁移到哪里

1. **分段 + 稀疏索引 + 整段删除**：LSM 树的 SSTable、日志系统的滚动文件——"按段管理、按段回收"是持久化日志的标准姿势。
2. **文件名编码元数据**：segment 文件名 = 起始 offset——把定位信息编码进文件名，省一次查找。
3. **稀疏索引 = 空间换时间**：不全量索引，只记录锚点，查询时"锚点定位 + 小范围顺序扫"——B+ 树页内查找同构。

本层留下的新账：Kafka 是"每个分区一本账本"。RocketMQ 却把所有消息写进一本全局总账——为什么？它怎么解决"一本账本怎么定位各队列消息"的问题？→ 逼出 Level 5。

### Level Ending

```
🔴 口诀：分段管理账本，稀疏索引定位。
```

<a id="level-5"></a>

## Level 5：RocketMQ 存储结构——一本总账

一句话认知墙：Kafka 每个分区一个账本，RocketMQ 为什么反其道而行，把所有 Topic 所有队列写进同一个 CommitLog？

### 前置知识关卡

- [ ] 能画出 Kafka 的 LogSegment + 稀疏索引结构（答不出回 Level 4）
- [ ] 知道 RocketMQ 是"日志存储 + 队列语义"混合体（mq-01 Level 5）

### Why——为什么写一条全局总账

**老陈**：先看 Kafka 的账本结构在 RocketMQ 场景下的痛点：RocketMQ 要支撑大量 **小 Topic**（一个业务一个 Topic，电商平台几千个 Topic 很正常）。Kafka 的"每分区一个账本"意味着——**几千个 Topic × 每个分区一个活跃文件 = 成千上万个文件同时被写**。HDD 时代，这等于成千上万个写入点随机分布在不同磁道区域，顺序写退化成随机写，吞吐崩盘。所以 RocketMQ 的选择是：**所有消息写一个 CommitLog**，全局只有一条写入路径，永远顺序。

| 方案 | 解决什么 | 留下什么问题 |
| ---- | ---- | ---- |
| 每分区一账本（Kafka） | 分区独立管理、删除方便 | 小 Topic 多时写放大、文件数爆炸 |
| 全局一本账（RocketMQ） | 写入路径唯一、顺序写纯粹 | 读取要绕道索引、删除要按页回收 |

### What——双层结构的完整图纸

```text
RocketMQ Broker 存储结构：

写入路径（唯一）：
  所有 Topic 所有队列的消息 → CommitLog（顺序追加，MappedFile 管理）
  ├── 00000000000000000000  (1GB，mmap 映射)
  ├── 00000000001073741824  (1GB)
  └── ...（每个文件默认 1GB，写满滚动）

读取路径（按队列）：
  Topic=ORDER_EVENT, Queue=1 → ConsumeQueue
  ├── 每条 20 字节：{commitLogOffset(8B), size(4B), tagHashCode(8B)}
  ├── 一个 ConsumeQueue 文件 = 30 万条 × 20B = 5.72MB
  └── 位点 = 该队列消费到第几条索引

IndexFile（可选）：按 Key 反查消息（orderId → commitLogOffset）
```

> 📌 最容易被误解的一点：**ConsumeQueue 不是消息副本，是"指向总账的索引"**。消费者在队列里消费到第 N 条，实际动作是：读 ConsumeQueue 第 N 条索引 → 拿到 commitLogOffset → 去 CommitLog 读真实消息。**正常消费的位点推进确实不动消息本体**；但重试/死信/延迟消息会以新消息身份**再次写入 CommitLog**（重试一次多存一份，mq-07 展开）——索引是"视图"，重写是"实体"，两者别混。

### How——E 在 RocketMQ 的落账旅程（8 步）

```text
① E send 到 Broker → 网络层接收
② CommitLog 当前 MappedFile 追加 E 的消息体 + 属性 ★唯一写点
③ 更新内存索引：E 属于 ORDER_EVENT-Q1
④ 后台线程（ReputMessageService）把索引追加到 ConsumeQueue ★异步建索引
⑤ 可选：IndexFile 按 orderId 登记（支持按 Key 查消息）
⑥ 刷盘：同步刷盘（GroupCommitService）/ 异步刷盘（FlushRealTimeService）
⑦ 库存组从 Q1 按位点消费：读索引 → 定位 CommitLog → 读消息
⑧ 位点推进：Q1 的消费位点前移（消息本体仍在 CommitLog，直到过期）
```

第 ④ 步最反直觉：**索引是异步构建的**——E 已经进了 CommitLog，但 ConsumeQueue 可能还没跟上，此刻消费者"看不到"这条消息。这个窗口极短（毫秒级），但它决定了 RocketMQ 的消费可见性模型：**先落账，后建索引，再可见**。

**徒弟**：那 CommitLog 的过期删除怎么办？总账里混着所有 Topic 的消息，总不能删一段把别的 Topic 也删了。

**老陈**：这就是全局账本的代价——**不能像 Kafka 那样整段删文件**。RocketMQ 的做法是：ConsumeQueue 的消费位点推进到哪，CommitLog 就允许删除到哪（所有队列位点的最小值之前的部分可以回收），删除粒度为**整个文件**（1GB MappedFile 写满后，等所有队列消费位点越过再整文件删除）。所以 RocketMQ 要求生产上**不能有长期不消费的积压队列**——它拖着 CommitLog 不能回收，磁盘被少数滞后队列绑架（神话⑦的存储侧根源，mq-06 破解、mq-09 运维版）。

### Transfer——这个思想还能迁移到哪里

1. **写入路径唯一化**：把所有写合并成一条流——与"单写多读"架构、日志合并思想同构，代价是读路径变复杂。
2. **异步建索引**：先落数据、后建索引——与数据库"延迟索引维护"、搜索引擎"准实时索引"同构：数据安全优先，查询时效其次。
3. **索引与位点即语义**：正常消费、顺序消息的位点回退靠索引与位点视图实现，消息本体不动——**用视图的变更代替数据的搬移**；但重试/死信/延迟消息会以新消息身份重写 CommitLog，存储代价是真实的（mq-07 展开）。

本层留下的新账：存储结构清楚了。但存进去了，什么时候删？保留期/TTL 到底影响什么？为什么说它是"业务参数"而不是"运维参数"？→ 逼出 Level 6。

### Level Ending

```
🔴 口诀：一本总账顺序写，队列索引指账行。
```

<a id="level-6"></a>

## Level 6：保留策略与生产决策——神话⑪ 的破解

一句话认知墙：保留期不就是"磁盘能存多少天"的运维参数吗？为什么说它决定业务能力？

### 前置知识关卡

- [ ] 能对比 Kafka 与 RocketMQ 的存储结构取舍（答不出回 Level 4/5）
- [ ] 知道位点与保留策略互不相关（Level 4）

### Why——神话⑪ 为什么错

**徒弟**：TTL/保留期不就是"消息存多久自动清理"吗？磁盘够大就多存几天，不够就少存几天，纯运维问题。

**老陈**：错在把"存储参数"当成了"业务参数"的答案。保留期真正决定的是四件事：

| 保留期影响 | 机理 | 出问题时的现象 |
| ---- | ---- | ---- |
| 迟到消费者 | 消费 lag 超过保留期，位点之后的消息已被删 | 消费者重启后报 offset 越界，被迫从头或跳过 |
| 回放/修复 | 历史消息被删，无法回拨位点重放 | 事故复盘想重放数据，账本已被清空 |
| 审计/合规 | 需要追溯 N 个月前的消息 | 合规要求 180 天，保留期只有 7 天 |
| 成本边界 | 保留越长，磁盘/对象存储成本越高 | 磁盘告警后被迫手动清理，引发次生事故 |

**"迟到消费者"是生产第一高发事故**：消费者服务挂了 8 天没消费，恢复时发现位点之前的消息已经过了 7 天保留期被删——offset 失效。RabbitMQ 有"队列空闲不丢"的优势（队列模型消息等消费者），Kafka/RocketMQ 则是**消息不等人**。

### What——保留策略的三条生产铁律

```text
铁律一：保留期 > 最大可容忍消费停滞时长
  lag 报警阈值 × 故障恢复时间窗口 < retention

铁律二：保留期由"业务最慢场景"决定，不是"磁盘大小"决定
  先问：最慢的消费方多久能追完？审计要回溯多久？→ 倒推 retention

铁律三：删除要可观测
  段删除/文件回收要有指标（磁盘水位、删除速率），
  发现"消费者还没到，段先删了"必须提前告警
```

> 📌 最容易被误解的一点：**"消息堆积不占内存"是幻觉，堆积的尽头是磁盘**。Kafka 堆积只占磁盘（好）；RabbitMQ 经典队列自 3.12 起统一为接近 lazy 的行为（消息体落盘、索引在内存），堆积吃磁盘、索引仍吃内存（官方时间线：CQv2 自 3.10 引入、3.12 显著改进；3.13 默认仍是 CQv1——官方文档原文 "Version 1 is the default"；4.0 移除 v1 支持后仅剩 CQv2）；RocketMQ 积压卡住 CommitLog 回收，绑架全 Broker 磁盘。**积压的账，最终都在存储层还**。
>
> 实测佐证（EX-05，FAST 档，RabbitMQ 3.13）：灌入 30,000 条后，CQv1 进程内存 0.1MB、消息体 bytes 29.3MB 可通过 rabbitmqctl 观测（消息体挂消息存储）；CQv2 进程内存 1.7MB、bytes 不暴露（Raft 日志式，由 RA 管理，rabbitmqctl 对 quorum 队列的 message_bytes 为空列），且消息可见性有秒级延迟。形态差异真实可感。

### How——一个迟到的审计消费者引发的完整事故链

```text
① 审计服务（支线：与 E 不同因果链）部署故障，停摆 10 天
② 第 11 天恢复：位点还停在 10 天前
③ retention = 7 天 → 位点之后的账本段已整段删除
④ 审计消费者拉取 → Broker 返回 OFFSET_OUT_OF_RANGE
⑤ 恢复方案二选一：
   a. 从最早可用位点继续 → 丢 3 天审计数据
   b. 从上游系统重导 3 天数据 → 人工成本巨大
⑥ 复盘结论：retention 应从"审计最长停机窗口"倒推（≥15 天）
```

**徒弟**：那直接把 retention 设成一年，一劳永逸？

**老陈**：磁盘成本先跳出来反对——Kafka 一年热数据是 TB 级甚至 PB 级成本。正解是**分层**：热数据（近 7 天，Kafka 原样）→ 冷数据（对象存储归档，Pulsar 分层存储原生支持 / Kafka 用 S3 连接器）。"留多久"不是选择题，是一道**成本 × 业务需求 × 恢复能力**的三元方程。

### Transfer——这个思想还能迁移到哪里

1. **保留期 = 容错预算**：日志保留、快照保留、备份保留——所有"存多久"的参数本质都是"允许系统出多久故障"。
2. **消息不等人 vs 人等消息**：日志模型的保留期倒推，与"缓存 TTL 倒推业务可容忍脏读时长"同构。
3. **分层存储**：热/温/冷三级，是所有大数据体系的成本模型（Redis 热数据 / DB / 对象存储同构）。

本层留下的新账：存储讲完了，E 安全地躺在账本上。但"躺在 page cache"和"躺在磁盘"之间、单机落盘和多副本之间，都有丢失窗口——**E 到底在哪一刻算"不丢"？** → 逼出 mq-03（投递语义与可靠性）。

### Level Ending

```
🔴 口诀：保留期是业务参数，倒推自最慢场景。
```

<a id="pitfalls"></a>

# ⚠️ 坑与细节

## 坑 1：以为 write() 返回就是落盘

错误理解：写入文件成功 = 数据在磁盘上。

原因：不知道 page cache——write() 只到内核缓存，fsync 才到磁盘。

比喻后果：记了账本（写进 OS 的草稿纸），没誊到正式账上。

线上现象：断电后"已确认"的消息丢失，对账发现缺口。

修正：理解四级安全；关键链路配置刷盘策略，并做断电演练验证。

## 坑 2：以为 Kafka 消费快是因为内存多

错误理解：Broker 大内存 → 消息全在内存 → 消费快。

原因：不知道消费快的主因是 page cache + 零拷贝，堆内存大反而拖累 GC。

比喻后果：把书全摊在桌上（堆内存），不如让图书管理员（内核）快速调阅。

线上现象：盲目给 Broker 加堆，GC 停顿反而更严重。

修正：Kafka 官方建议"小堆 + 余量交给 OS page cache"（方向以官方文档为准）；"5-8GB 封顶"是社区/Confluent 流传说法，官方文档未检索到该数值（待验证）。

## 坑 3：以为分区数越多写入越快（单盘视角）

错误理解：分区多 = 并行写多 = 吞吐高。

原因：**单台 Broker、同一物理盘**上，分区越多，顺序写被更多写入点切碎；副本同步、segment 文件数同步膨胀（神话⑤ 的存储侧证据）。

比喻后果：账本太多，每本都写一点，入库员（磁盘）疲于奔命。

线上现象：单机分区数从 6 扩到 60，吞吐不升反降，延迟抖动加剧。

修正：**单盘写入点是吞吐关键**——分区数要按"消费并行度"设计；跨多 Broker/多盘的分布式集群上加分区才是横向扩展吞吐的官方手段（每个分区落在不同磁盘上，写入点随之增多，mq-06 展开）。

## 坑 4：在 RocketMQ 上放任一个队列长期积压

错误理解：堆积只是"没消费"，磁盘够就没事。

原因：不知道 CommitLog 回收受"所有队列最小位点"约束——一个积压队列拖着整本账不能删。

比喻后果：一个人没结账，全仓库的旧台账都不能销毁。

线上现象：磁盘告警，排查发现是三个月前的冷队列卡住回收。

修正：积压队列监控告警 + 到期清理策略（mq-09 展开）。

## 坑 5：保留期小于消费者故障窗口

错误理解：磁盘小，retention 设 3 天；消费者故障修 5 天。

原因：把保留期当磁盘参数，不当容错预算（神话⑪）。

比喻后果：台账只保留 3 天，财务休假 5 天回来，前两天的账没了。

线上现象：消费者恢复后 OFFSET_OUT_OF_RANGE，数据缺口无法修复。

修正：retention = 最慢消费者恢复窗口 × 2；恢复演练验证。

## 坑 6：以为 mmap 让 RocketMQ 数据全在内存

错误理解：mmap 映射 = 数据加载进内存，读取零开销。

原因：mmap 只是建立映射，实际页访问仍走 page cache 机制，冷页照样读磁盘。

比喻后果：以为索引卡 = 书本身。

线上现象：夸大 mmap 收益，冷数据场景消费性能不符合预期。

修正：mmap 省的是拷贝与系统调用，不是磁盘 IO 本身。

## 坑 7：给 Kafka 频繁调 fsync 参数保"不丢"

错误理解：fsync 越勤越安全，调大 `log.flush.interval.messages` 就稳了。

原因：不了解 Kafka 可靠性哲学——副本冗余优先于单机 fsync；频繁 fsync 直接冲击吞吐。

比喻后果：为了怕丢账，每记一笔就锁一次保险柜。

线上现象：吞吐腰斩，而单机 fsync 仍挡不住整机故障（副本才是答案）。

修正：Kafka 默认交给 OS 刷盘；可靠性靠副本与 ack 级别（mq-03/mq-08）。

## 坑 8：RabbitMQ 持久化消息以为"立即写盘"

错误理解：delivery mode=2（持久化）就是每条消息同步写盘。

原因：RabbitMQ 持久消息进 msg_store，实际有内存缓冲与批量落盘，不是每条 fsync。

比喻后果：以为入了保险柜，其实还在前台抽屉。

线上现象：断电丢窗口内消息，误以为"持久化"= "零丢失"。

修正：持久化 ≠ 同步刷盘；强需求要加镜像/仲裁队列与 confirm（publisher confirm 机制见 mq-03 版本表，仲裁队列见 mq-08）。

<a id="errata"></a>

# 📚 版本勘误表

| 错误说法 | 准确说法 |
| ---- | ---- |
| "写文件成功就是落盘了" | write() 到 page cache，fsync 才到磁盘——中间是断电丢失窗口 |
| "Kafka 消费快靠大堆内存" | 靠 page cache + 零拷贝；堆内存建议"小堆 + 余量交给 page cache"（"5-8GB 封顶"为社区流传说法，官方文档未检索到，待验证） |
| "分区越多吞吐越高" | 分区多会切碎顺序写、膨胀文件数；分区数按消费并行度设计 |
| "mmap 让数据全进内存" | mmap 建立映射，页访问仍走 page cache，冷页照样读盘 |
| "RocketMQ 队列就是存储单元" | 真实数据在 CommitLog，ConsumeQueue 是 20 字节/条的索引 |
| "保留期是磁盘参数" | 是容错预算与业务能力参数：迟到窗口/回放/审计/成本 |
| "Kafka 默认 fsync 所以不安全" | 可靠性哲学是副本冗余优先；单机 fsync 挡不住整机故障 |
| "RabbitMQ 持久化 = 同步写盘" | 持久消息进 msg_store 有批量落盘，非每条 fsync |
| 坦白：我以前也讲错过"Kafka 快是因为全内存" | 早期我把 Kafka 和 Redis 类比；它的快在顺序写 + 零拷贝，内存只是 page cache 的副产品 |
| 坦白：我以前也讲错过"ConsumeQueue 是消息的副本" | 它是索引不是副本——20 字节指向 CommitLog；消息本体永远只有一份 |
| 坦白：我以前也讲错过"重试/延迟消息只是索引复制，不产生新存储" | 重试/死信/延迟会以新消息身份重写 CommitLog；正常消费的位点推进才不动消息本体 |
| 坦白：我以前也讲错过"RabbitMQ 队列堆积先吃内存" | 经典队列自 3.12 起统一接近 lazy 行为：消息体落盘、索引在内存；堆积吃磁盘为主，索引仍吃内存（官方时间线：CQv2 自 3.10 引入、3.12 改进；3.13 默认仍为 CQv1；4.0 移除 v1 后仅剩 CQv2）。实测回填（EX-05）：30,000 条，v1 进程内存 0.1MB、bytes 29.3MB 可见；v2 进程内存 1.7MB、bytes 由 RA 管理不可观测 |

<a id="decisions"></a>

# 🏆 生产决策卡

## Decision Card 1：订单事件的刷盘策略

### 场景

E 是交易链路事件，对账要求"确认过 = 可找回"，预算允许吞吐下降 30%。

### 判断

RocketMQ 同步刷盘（SYNC_FLUSH）+ 异步复制起步；若要"确认即单机可恢复"，同步刷盘是单机安全的最小配置。

### Mechanism → Decision

| 机制 | 工程决策 |
| -- | ---- |
| 级别 2→3 窗口（page cache 到磁盘） | 同步刷盘关闭窗口 |
| 吞吐代价 | 实测后评估（验收指标） |
| 副本冗余 | 与刷盘互为备份（mq-08） |

### 禁止决策

- 交易主链路用"纯内存 + 不刷盘"并宣称不丢
- 每条消息单独 fsync（破坏批量，吞吐崩溃）

### 验收指标

- 断电演练：同步刷盘配置下，恢复后无消息缺口
- 吞吐对比：刷盘开启前后实测 TPS 差异 ≤ 预期
- 刷盘延迟 p99 监控

---

## Decision Card 2：保留期的设定

### 场景

订单事件要支持"消费者最长 3 天故障恢复窗口 + 审计回溯 30 天"。

### 判断

retention = 30 天（审计需求主导，覆盖 3 天故障窗口）；磁盘预算按 30 天消息量 + 1.5 冗余计算。

### Mechanism → Decision

| 机制 | 工程决策 |
| -- | ---- |
| 迟到消费者窗口 | retention ≥ 故障恢复窗口 × 3 |
| 审计回溯 | retention ≥ 30 天 |
| 成本 | 冷数据归档对象存储（按需） |

### 禁止决策

- 按"磁盘大小"倒推 retention（先问业务再算磁盘）
- retention 卡在消费者恢复窗口以内

### 验收指标

- 故障演练：消费者停 3 天后恢复，无 OFFSET_OUT_OF_RANGE
- 磁盘水位监控：保留期内不触发告警

---

## Decision Card 3：Topic/队列数的存储侧评估

### 场景

业务拆微服务，计划建 2000 个 Topic，每个 4 分区。

### 判断

Kafka：8000 个活跃写入文件 × 多副本，单 Broker 文件数与管理开销需评估，建议收敛 Topic；RocketMQ：全局 CommitLog 不受 Topic 数影响，但 ConsumeQueue 文件数同比例增长。

### Mechanism → Decision

| 机制 | 工程决策 |
| -- | ---- |
| Kafka 文件数爆炸 | 合并小 Topic / 用大分区代替多 Topic |
| RocketMQ 一本账 | Topic 数宽容度高，但监控 ConsumeQueue 总量 |

### 禁止决策

- 无评估直接铺 2000 小 Topic（HDD 时代写入点爆炸，SSD 时代文件句柄压力）

### 验收指标

- 单 Broker 打开文件句柄数 < 上限的 50%
- 写入延迟 p99 无 Topic 数敏感

<a id="cross-language"></a>

# 🌍 跨语言视角

## 同一个问题：持久化与零拷贝

| 语言 | 对应机制 |
| -- | ---- |
| Java | FileChannel.transferTo（sendfile）、MappedByteBuffer（mmap）、DirectByteBuffer（堆外） |
| Go | syscall.Sendfile、os.File 的 ReadFrom（内部走 sendfile）、mmap（golang.org/x/exp/mmap 或 syscall.Mmap） |
| Rust | std::os::unix::fs 与 libc、io_uring 生态（tokio-uring / monoio）、memmap2 |
| Python | os.sendfile、mmap 模块 |

## 跨语言仍成立的判断力

1. **零拷贝是 OS 能力，不是语言能力**：sendfile/mmap 是系统调用——Java 的 `transferTo`、Go 的 `ReadFrom`、Rust 的 libc 调用，本质都是同一个内核机制。
2. **"写文件 ≠ 写磁盘"在每种语言都成立**：文件 IO 默认经过 page cache；语言只决定 API 形态，不改变安全语义。
