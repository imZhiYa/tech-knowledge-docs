# 写在最前面：三个场景，一个诊断框架

1. **病例一**：`@Transactional` 里 insert 订单 + kafkaTemplate.send，线上"数据库有订单，Kafka 没有消息"——**确认语义错位**：把"方法返回"当成了"消息已持久化"（神话① 的实战版）。
2. **病例二**：Producer = 200000 msg/s、Consumer = 50000 msg/s、Partition = 12、Lag = 1000 万——**容量规划缺失 + 无背压**：把"能发出去"当成了"能消化"（神话⑦ 的实战版）。
3. **病例三**：订单状态事件（CREATED → PAID → SHIPPED → COMPLETED / CANCELLED）线上偶发 PAID 先于 CREATED、同一消息消费两次、订单卡在 PAID、Lag 持续增长——**顺序边界认知缺失 + 补偿机制缺位**：把"物理序"当成了"业务序"。

本篇同时给出全系列的闭环方法论：**故障 = 机制的某个窗口被击中**——任何事故都能翻译成"哪个机制、哪个窗口"，翻译成功，救治路径就自动浮现；再进一步，**把窗口全部列出来，就是一份完整的系统设计**。

## Level 1：病例一——DB 有订单，Kafka 没有消息

一句话认知墙：@Transactional 为什么保不住一条 Kafka 消息？

### 前置知识关卡

- [ ] 知道"双写一致"陷阱（mq-00 L4 埋的引子）
- [ ] 知道本地消息表 / 半消息 / 事务消息的边界（mq-07 L3 四条路径）
- [ ] 知道"ack 不表达业务成功"（mq-03 L4，神话③）

### 病历

```java
@Transactional
public void createOrder(Order order) {
    orderMapper.insert(order);
    kafkaTemplate.send("order-topic", order);
}
```

线上现象：**数据库存在订单，但 Kafka 中没有消息**。

### Why——为什么这个写法会漏消息

**徒弟**：方法标了 @Transactional，insert 成功、send 也执行了——事务提交后，两边不都应该成功吗？

**老陈**：先破一个前提：**@Transactional 只管理数据库事务**（默认配置下，只有一个 DataSourceTransactionManager 在管）。它管不到 Kafka。再破第二个前提：**kafkaTemplate.send 是异步的**——它把消息丢进客户端的发送缓冲（RecordAccumulator）就立刻返回，真正的网络发送由后台线程执行（Kafka 客户端 API 语义）。所以"方法返回"这个时间点，消息可能还没离开进程。

把两个前提合起来，漏消息的窗口就出来了：

```text
方法执行：
  T1  orderMapper.insert(order)   → 进入 DB 事务
  T2  kafkaTemplate.send(...)     → 消息进入发送缓冲，方法立即返回
  T3  方法返回 → @Transactional 提交 → DB 落库 ★用户看到"订单存在"

消息的命运（T2 之后完全不受 T3 控制）：
  a. 缓冲里的消息还没发出去，应用崩溃/被 kill → 消息丢失 ★最常见
  b. 后台线程发送失败（Broker 不可用、超时、序列化错误）
     → 异常进异步回调；代码里没有回调处理 → 失败静默 ★次常见
  c. 发送成功、Broker 已确认 → 一切正常（幸运路径）
```

> 📌 最容易被误解的一点：**send() 返回 ≠ 消息已持久化**。send 返回的是"已入缓冲"的凭证（Future），不是"Broker 已确认"的凭证。把"方法返回"当成"消息已发"，等于把"把信丢进邮筒"当成"对方已收到"——这是神话①（Producer 返回成功 ≠ 消息不会丢）的实战变体，区别只是这次"返回成功"换成了 send 返回。

### What——双写一致问题的完整结构

**老陈**：先把这个病例放到 mq-00 L4 就埋下的框架里看——**"写数据库 + 发消息"是两个系统之间的双写，而两个系统之间不存在原子事务**（mq-03 L4 的结论）。所以任何"同一个事务里搞定两边"的直觉都是幻觉，问题必然被压缩成：

```text
要么先 DB 后 MQ（DB 成功、MQ 可能失败 → 消息少 ★本病例）
要么先 MQ 后 DB（MQ 成功、DB 可能失败 → 消息多）
两个方向都不可能做到"两个都成功才整体成功"，只能选一个方向 + 兜底。
```

本病例是"DB 在前"方向：DB 已经提交，消息没了。**反向病例同样常见**（先发消息、后写 DB，DB 回滚但消息已发出——消费端收到"不存在的订单"）。架构评审的第一问永远是：**你的场景，消息多和消息少，哪个更不可接受？**

### How——四个方案与 Trade-off

**徒弟**：那我把 send 改成同步等待，失败就抛异常回滚 DB，不就行了吗？

**老陈**：这是方案 A，先承认它有效，再看边界：

```text
方案 A：同步等待 + 失败回滚
  kafkaTemplate.send(...).get(timeout)   // 等 Broker 确认才返回
  失败 → 抛异常 → @Transactional 回滚 → DB 无订单、Kafka 无消息 → 两边一致
  ★关闭了"消息少"窗口
  代价 1：send 阻塞期间持有 DB 事务与连接（长事务风险）
  代价 2：引入"消息多"窗口——Broker 已 ack、DB 回滚 → 消息有、订单无
         （ack 之后、commit 之前的崩溃，和 ack 后回滚，都是消息多）
  代价 3：吞吐下降（等 ack 串行化）
  适用：消息多可接受（消费端有幂等，mq-04）、延迟敏感度低、单条量小

方案 B：本地消息表（Outbox）——推荐
  订单 + outbox 表 同 DB 事务插入 → 定时任务扫 outbox → 发 Kafka
  → 成功后删 outbox 记录（mq-07 L1 候选一的机制落地）
  ★DB 事务内的操作全部原子：要么都有，要么都无
  消息少的窗口只剩"outbox 已删但消息其实没到"——用对账兜底
  代价：多一张表 + 定时任务 + 秒级延迟；消息表与订单表同库（mq-07 的边界）
  适用：交易链路、消息少和消息多都不可接受

方案 C：事务提交后发送（AFTER_COMMIT 事件）+ 失败重试与告警
  @TransactionalEventListener(phase = AFTER_COMMIT) 里 send
  失败 → 重试队列/告警 → 人工或自动补偿
  代价：提交后、发送前进程崩溃 → 消息仍丢（窗口缩小但没关闭）
  适用：对延迟敏感、可接受小概率消息少 + 有补偿流程

方案 D：对账补偿（兜底，不单独用）
  定期对账：DB 订单 vs Kafka 消息，缺失补发（mq-03 L5 / mq-09 L2）
  代价：时效差（分钟级）；对账本身要幂等
  适用：任何方案的最后一道网
```

**老陈**：生产推荐组合是 **B + D**（B 关窗口、D 兜底），**A** 是"改一行代码"的缓解（把异步改成同步等待），**C** 是"最小改动 + 补偿流程"。**禁止决策：什么都不做，只靠 @Transactional 的幻觉**。

> 📌 最容易被误解的一点：**"消息多"和"消息少"不是同一个问题的两面，是两种事故**。消息少要"补发"，消息多要"幂等"（mq-04）——补发与幂等的工具完全不同。选方案时先回答：我的场景哪边更疼？

### Transfer——这个思想还能迁移到哪里

1. **任何"DB + 外部系统"双写**：DB + Redis、DB + ES、DB + 第三方 API——同一个问题，同一套方案（本地消息表 / 事务后动作 / 对账）。
2. **"API 返回 = 业务成功"的确认语义错位**：HTTP 200 不代表业务已生效（异步处理）、RPC 成功不代表落库——确认语义要追问到"哪个环节的确认"（mq-03 的确认级别框架）。
3. **两个系统之间没有原子事务**：这是分布式系统的地基性结论，Saga/Outbox/对账都是它的衍生（mq-07 四条路径的总纲）。

本层留下的新账：病例一解决的是"消息有没有"——但消息有之后，**消息太多、消费不完**，就是下一个病例：**Lag 1000 万**。

### Level Ending

```
🔴 口诀：send 返回 ≠ 已持久化；DB 提交 ≠ 消息已发；双写无原子，窗口必有一边。
```

## Level 2：病例二——堆积事故的两个实例

一句话认知墙：为什么单纯加 Consumer 可能没用？积压了先动哪只手？

### 前置知识关卡

- [ ] 知道"并行度 = 分区数"（mq-06 L4）
- [ ] 知道消费者客户端线程模型与"处理慢"的形态（mq-05 L3）
- [ ] 知道单盘写入点与分区成本（mq-02 坑 3）

### 病历——同一机制的两个数字实例

```text
实例 A（存量深水区）：生产者 200000 msg/s、消费者 50000 msg/s、12 分区、Lag 1000 万
实例 B（常态积压）：  生产者 200000 msg/s、消费者 100000 msg/s、持续 30 分钟
```

两个实例是同一套机制的不同数字形态：**生产速率 > 消费速率，积压必然发生**。先把给定数据换算成机制语言（以下为**推算**，假设路由均匀、消费者数 ≥ 分区数；真实值取决于 Key 分布与瓶颈位置，待实测）：

```text
实例 A：每分区生产 ≈ 200000/12 ≈ 16667 msg/s；每分区消费 ≈ 50000/12 ≈ 4167 msg/s
       缺口 ≈ 150000 msg/s（Lag 每秒 +15 万，每天 ≈ +130 亿）
实例 B：缺口 = 200000 - 100000 = 100000 msg/s
       backlog = 100000 × 30 min × 60 s = 1.8 亿条（推算）
       按单条 1KB 估算（推算）：约 180GB 存储水位（待实测）
```

### Why——为什么单纯加 Consumer 可能没用

**徒弟**：Lag 涨就加消费者，加到能吃完为止——不对吗？

**老陈**：加消费者前先回答一个问题：**消费者数 vs 分区数**（mq-06 L4 的机制）：

```text
情况一：消费者数 < 分区数（比如 12 分区只有 4 个消费者）
  → 加消费者有效：每个消费者都还有分区可领（并行度没打满）

情况二：消费者数 = 分区数
  → 加消费者没用：每分区/队列串行处理模型下并行度 = 分区数，
    第 N+1 个消费者没有分区可领，纯空转（RocketMQ 并发消费模式
    可在单消费者内再拆线程，属另一层并发，mq-05 L3）
  → 此时消费速率就是所有分区的总产出——瓶颈在哪决定了它
    能不能更高：是单分区上限？是处理逻辑？是下游？还是被踢循环？

情况三：消费者数 = 分区数但消费速率仍上不去
  → 加消费者必然没用；问题在"单分区为什么只能出这么多"
  → 这才是要查的病根（Consumer 慢在哪，见下）
```

**另一个关键前提：消费速率是"结果"，不是"上限"**。它是当前瓶颈压制下的产出——瓶颈在下游（DB/第三方）时，加多少消费者都提不动；瓶颈在客户端（处理逻辑/批量太小）时，优化单条路径才有用。**先定位瓶颈，再谈扩容**（mq-09 L2 的瓶颈四层定位法）。

### What——止血三路径

**老陈**：急诊的第一原则：先救命，再确诊。三条路径，按生效速度排序：

```text
路径一：降生产（最快生效）
  Producer 限流/拒绝新请求/削峰 → 止住 Lag 增速
  ★积压仍在增长时，第一动作永远是压生产，不是扩消费
  —— 消费扩不动是常见情况（下游瓶颈），生产是唯一能立刻控制的水龙头

路径二：提消费（治本方向）
  ① 消费者数补到分区数（如果没满）
  ② 批量消费（见下）
  ③ 优化单条处理路径（定位 Consumer 慢在哪，见下）
  ④ 扩容分区（注意边界！见下）

路径三：降级（保核心）
  低优先级消息丢弃 / 延迟处理 / 熔断下游依赖
  → 用"丢不重要的"换"保核心的"，把消费能力聚焦到关键链路
```

### What——实例 A 的存量清算：加分区救不了存量 Lag

```text
Kafka 加分区是"加空分区"（mq-06 坑 4 修正）：
  新分区只接新消息；存量 Lag（1000 万条）仍在旧 12 个分区上
  → 加分区后：新消息的并行度上去了，旧 Lag 还是只能靠旧分区慢慢消化
  → 清空 1000 万 Lag 的公式只有一个：
     清空时间 ≈ Lag /（消费速率 - 生产速率）   （消费速率 > 生产速率才可清）
  → 正确的组合拳：先降生产（路径一）→ 旧分区吃满（提消费）→ 再加分区扩容
```

恢复时间**推算**示例（真实值取决于瓶颈，待实测）：

```text
若消费能力提到 250000 msg/s（下游能扛）：
  清空 ≈ 1000 万 /（250000 - 200000）= 200 秒
若消费能力只有 100000 msg/s（瓶颈压住）：
  100000 < 200000 → Lag 继续增长，永远清不完 → 必须降生产
```

### What——实例 B 的决策规则：什么时候限流生产、什么时候降级业务

**徒弟**：实例 B 的 1.8 亿 backlog——什么情况下限流生产者，什么情况下干脆降级？

**老陈**：这是急诊的"分诊决策"。规则如下：

```text
什么时候限流生产者（把生产压到 ≤ 消费速率）：
  ① backlog 超过安全水位（如 30 分钟消费量），且扩消费后仍追不上 → 限流
  ② 积压开始威胁存储与延迟（mq-02：RocketMQ 积压卡住 CommitLog 回收；Kafka 段回收由 retention 驱动、积压威胁的是磁盘水位与延迟；延迟超业务 SLA）
  ③ 消费端已被下游压垮 → 限流生产 = 保护下游的最后闸门

什么时候降级业务（不是限流，是砍链路）：
  ① 下游（库存/支付/履约）过载或不可用 → 熔断下游依赖，消费端只做轻处理
  ② 延迟超过业务容忍（如支付事件 > 2 分钟）→ 低优先级事件（如履约）丢弃/延迟，
     消费能力聚焦核心事件（CREATED/PAID）
  ③ 30 分钟持续 = 常态而非峰值 → 容量必须扩到消费 ≥ 生产，降级只是过渡

分诊顺序：先查"是峰值还是常态"→ 常态必须扩容量；
  峰值积压 → 压生产 → 提消费 → 清存量 → 降级保核心。
```

### How——Consumer 慢到底可能慢在哪里

**老陈**：实例 A 每分区 4167 msg/s → 单条处理预算 ≈ 240 微秒/条（推算：1/4167 秒）。超过预算就是 Lag。慢的位置按概率排查（映射 mq-05 L3 的线程模型）：

```text
① 处理逻辑本身（最常见）：每条消息做 DB 写 / 外部 RPC / 锁等待
   → 单条处理慢 = 每分区吞吐直接下降（Kafka 单 poll 线程串行）
② 批量太小（高频踩坑）：max.poll.records 默认 500
   → 消息稀疏或处理慢时，poll 往返开销占比高（空轮询 + 网络往返）
   → 拉大批量 + 批量写 DB / 批量 RPC，吞吐可差数倍（待实测）
③ poll 循环里做了重活：在循环体内同步调用慢服务
   → 阻塞拉取 → 轮询间隔拉长（Kafka 客户端语义）
④ 下游瓶颈：DB 连接池耗尽、第三方 API 限流、下游接口变慢
   → 消费端等下游，每分区吞吐被下游钉死（最常见病根之一）
⑤ 被踢出重平衡循环：处理时长超过 max.poll.interval.ms（默认 5 分钟）
   → 分区被收回 → rebalance（mq-06）→ 重复消费 + 更慢 → 恶性循环 ★危险
⑥ 客户端资源：GC、CPU 打满、网络带宽、反序列化成本
⑦ 单分区有序约束：Key 级串行（mq-04）——同一 Key 只能串行，热点 Key 拖慢整分区
```

> 📌 最容易被误解的一点：**Lag 大 ≠ 消费端慢**。Lag 是"生产-消费"的差值——生产端突发暴涨（大促/定时任务）一样让 Lag 冲高，消费端可能完全健康。查 Lag 的第一问：**生产速率最近变了没有？**（mq-09 L1 的相关与因果——lag 先涨，根因可能在生产端）。

### What——如何批量消费

```text
客户端侧：max.poll.records 调大（如 500 → 5000）
  每次 poll 拉更多 → 网络往返与 poll 开销摊薄

处理侧：批处理模式
  攒 N 条 / 攒 T 毫秒 → 批量 DB insert / 批量 RPC / 批量计算
  Spring Kafka：@KafkaListener 批量监听（BatchListener）同类机制

权衡（批量的代价）：
  ① 失败重试粒度变粗：批里一条失败，整批重试（mq-03 重试语义）
     → 配死信 + 拆批策略（毒消息隔离，mq-07 L5）
  ② 单批处理时长变长 → 逼近 max.poll.interval.ms → 被踢风险
     → 调大批量的同时必须同步调大 max.poll.interval.ms（坑 4）
  ③ 内存占用：批量拉取 + 处理中队列占内存（mq-05 L3 的背压水位）
```

### What——如何建立背压和降级机制

**徒弟**：批量拉大之后，下游还是扛不住怎么办？

**老陈**：背压的本质是"消费速率向生产速率传导压力"——MQ 的架构决定了**生产端感知不到消费端**（mq-00 的异步解耦就是为此）。所以背压要自己建：

```text
消费端背压（保护下游）：
  ① 信号量/令牌桶限流：消费线程池入口限流，超限排队或等待
     → 保护 DB/第三方不被击穿（比"放任 + 事后扩容"可控）
  ② Kafka pause/resume：暂停分区拉取，给下游喘息
     ★陷阱：pause 只是停拉取、不停止 poll——若处理/恢复逻辑阻塞了 poll 循环、
     间隔超过 max.poll.interval.ms → 被踢出组（mq-06 风暴）；持续 poll 的 pause 本身不触发被踢
     → 恢复逻辑要保证 poll 持续心跳，或配合调大 max.poll.interval.ms

生产端背压（Kafka 无原生背压协议）：
  客户端缓冲上限（RecordAccumulator 满 → send 阻塞至 max.block.ms）
  → 缓冲满 = 生产端被迫降速（这是 Kafka 唯一的"自动背压"）
  降级开关：低优先级消息丢弃 / 转延迟主题（mq-07 延迟机制）/ 本地暂存

降级的分级设计（先定好，事故时才有剧本）：
  S1 限流生产（保护 Broker 与消费）
  S2 低优消息丢弃/延迟（核心链路保活）
  S3 消费端熔断下游 + 降级到简化处理路径（mq-09 的开关与回滚）
  S4 告警升级 + 值班预案（lag 分级阈值，mq-09 监控分层）
```

### Transfer——这个思想还能迁移到哪里

1. **任何"生产-消费"速率不匹配系统**：日志管道（采集 > 消费）、ETL、数据同步——"降生产/提消费/降级"三路径通用。
2. **并行度 = 分区数**：数据库分片、队列分片、连接池分片——"扩容先问并行度是否打满"是通用第一问。
3. **存量与增量分离**：加分区只救增量、清存量靠旧分区——磁盘扩容、缓存预热、灰度发布都是"存量/增量"两套策略。

本层留下的新账：消息"有没有"解决了（L1）、"堵不堵"解决了（L2）——但消息到了之后，**顺序和重复**是下一道坎：PAID 先于 CREATED、同一消息消费两次。 → 逼出 Level 3。

### Level Ending

```
🔴 口诀：先压生产再扩消费；并行度问分区；加分区救不了存量 Lag；批量越大越要防被踢。
```

<a id="level-3"></a>

## Level 3：订单链路——顺序与重复（乱序四视角 / 幂等四方案）

一句话认知墙：把"物理序"当成"业务序"，事故只是时间问题。

### 前置知识关卡

- [ ] 知道"顺序必须定义范围"（mq-04 L3，神话⑥：顺序消息 ≠ 全局顺序）
- [ ] 知道 at-least-once 与重复来源（mq-03 L1/L4）
- [ ] 知道 rebalance 事故链与并行度 = 分区数（mq-06）

### 病历——订单链路事故面

```text
订单状态事件：ORDER_CREATED → ORDER_PAID → ORDER_SHIPPED → ORDER_COMPLETED
              （任一状态可转 ORDER_CANCELLED）
线上偶发：
  ① ORDER_PAID 先于 ORDER_CREATED 被消费   ★乱序
  ② 同一消息被消费两次                    ★重复
  ③ 某些订单卡在 ORDER_PAID              ★顺序缺口（第 5 题的"重点"）
  ④ MQ Lag 持续增长                      ★容量（L2 已解）
要求：同 orderId 按业务顺序；不同 orderId 并行；峰值生产 20 万/s；消费正常 10 万/s
```

### Why——为什么消息会乱序：四个视角

**徒弟**：我明明按顺序发的，为什么 PAID 会先到？

**老陈**：先接受一个事实：**"按顺序发"和"按顺序消费"之间隔着四层，每一层都可能打乱序**：

```text
视角一：Producer（发送层）
  ① 重试乱序：at-least-once 的代价（mq-03）——消息 1 失败重发期间消息 2 已发出
     → 落盘序 = 1,2（重发后）或 2,1 交错
     Kafka 幂等生产者（KIP-98）开启后重试保序；未开启且
     max.in.flight.requests.per.connection > 1 时同分区可乱序
     RocketMQ 异步发送 + 失败重发同理
  ② 多线程发送：生产者多线程并发 send，完成序 ≠ 业务序

视角二：Partition / Queue（路由层）
  ① 跨分区 = 无顺序保证（Kafka 只有分区内有序，mq-01/mq-04）
     → 同一 orderId 若落在不同分区，必然乱序 ★本题 PAID 先到的最高概率根因
  ② 队列/分区数变更（扩容）：hash 路由变化 → 同 orderId 后续消息换分区
     → 顺序断裂（mq-06 坑 4 原因）——扩容与顺序是冲突的

视角三：Consumer（处理层）
  ① 并发消费（RocketMQ ConsumeMessageConcurrentlyService / Kafka 多线程处理）
     无顺序保证
  ② 路由正确（同分区）时，单分区单线程按序处理——同订单的 CREATED 与
     PAID 必在同一分区同一消费者，此时乱序只剩一条路径：③ 的处理线程池并发
     （多消费者并行处理不同分区不会造成同订单乱序）
  ③ 处理线程池并发（mq-05 L3）：单分区消息拆给多线程 → 处理完成序 ≠ 消费序

视角四：Rebalance（归属层）
  ① 分区归属切换：处理中的消息随分区移交 → 新消费者从旧位点重读
     → 同一消息可能被两个消费者并发处理 → 完成序乱
  ② 滚动发布（本题场景：发布新版本触发 rebalance）→ 上述窗口放大（mq-06）
  ③ max.poll.interval.ms 超时被踢 → 强制 rebalance 循环
```

**根因排序**：PAID 先于 CREATED 最高概率是"**路由层：两条消息落到不同分区 + 消费端并行**"，其次是"**处理层：并发线程完成序乱**"。Producer 重试和 Rebalance 是放大器。

### What——同订单有序 + 不同订单并行：三种方案比较

```text
要求拆解：有序范围 = 单 orderId（Key 级）；并行范围 = 跨 orderId（分区级）
         —— 这就是"顺序边界"（mq-04）：把顺序锁死在 Key 内，并行放行到分区
```

| 维度 | Kafka partition key=orderId | RocketMQ queue + sharding key | 单消费者串行 |
| ---- | ---- | ---- | ---- |
| 有序机制 | 同 key 同分区，分区内有序（机制保证） | 同 key 同队列 + MessageListenerOrderly 队列内串行（Implementation） | 全部串行（天然有序） |
| 并行度 | = 分区数 | = 队列数 | = 1 |
| 吞吐 | 高（分区多） | 高（队列多） | 单消费者上限，本题 20 万/s 不可行 |
| 扩容影响 | **加分区破坏 key 路由 → 同 key 换分区 → 乱序** | 队列数变更同样破坏路由 | 无路由问题 |
| 故障影响 | 单分区不可用 → 该分区订单全部卡住（unclean 关闭时） | 单队列积压拖累该队列订单 | **单点：一个消费者挂 = 全部停摆** |
| 热点问题 | 热点 orderId（海量事件）串行拖慢整分区 | 同左 | 全部订单互相拖累 |

**架构师结论**：
- 本题选 **Kafka key=orderId 或 RocketMQ sharding key**（按现有技术栈），**排除单消费者串行**（20 万/s 峰值下吞吐不够）
- **分区/队列数必须在容量规划时定死**（mq-06 坑 4）：按峰值需求 × 增长系数预留，不接受运行期扩容换乱序；要扩只能重建主题 + 双跑（mq-09 变更治理）
- 热点 orderId 是顺序的代价：单 Key 串行（mq-04）——设计时评估"单订单事件密度 × 单条处理时长"是否超过单分区预算

### What——同一消息为什么会重复消费

**徒弟**：我已经提交位点了，为什么还会消费两次？

**老陈**：因为"处理成功"和"提交位点"之间有一个**必然存在的先后窗口**（mq-03 L4 提交窗口）：

```text
主窗口（必然）：
  consume → 业务处理成功 → commit/ACK 前进程宕机 → 位点未推进
  → 重启/rebalance 后从旧位点重投 → 该消息被消费第二次 ★重复
  （镜像窗口：拉取成功 → 自动提交已推进 → 业务处理前宕机 → 消息丢失）

其他来源（按概率）：
  ① Rebalance 移交：处理中未提交的分区被移交，新消费者重读（mq-06）
     ★本题滚动发布场景的主来源
  ② 生产者重试：Broker 已写入但 ack 丢失 → 生产者重发 → Broker 落两条
     （KIP-98 幂等生产者可消除这一层）
  ③ max.poll.interval.ms 超时被踢：处理太久 → 分区移交 → 重投
  ④ 消费端乱序提交：并行处理 + 先完成先提交/后完成覆盖（mq-05 L3）
  ⑤ 位点回拨/重放（运维动作，mq-07 重放权限）
```

**结论**：at-least-once 语义下，"处理成功但未提交"必然导致重复——这不是 bug，是机制（mq-03）。**重复无法靠 MQ 消除，只能靠消费端幂等**。

### What——幂等设计：四个方案与最终正确性依赖谁

**徒弟**：Redis SETNX 不行吗？快啊。

**老陈**：快是快，但**快不能当"正确"用**。四方案对比：

| 方案 | 原子性来源 | 速度 | 最终正确性依赖 | 风险 |
| ---- | ---- | ---- | ---- | ---- |
| Redis SETNX | Redis 单线程 | 快 | **不能依赖**：Redis 非持久化/主从切换/内存淘汰都会丢键 | 重复可能漏网 |
| DB 唯一索引（幂等表） | DB 事务 | 中 | **可依赖**：同库事务原子 | 表膨胀需清理策略 |
| 状态机校验 | 业务事务 | 中 | **可依赖**：非法流转拒绝（PAID→PAID 拒绝） | 需完整定义状态转移表 |
| 消费记录表（与业务同事务） | DB 事务 | 中 | **可依赖**：处理 + 登记同事务原子 | 表膨胀；与业务同库耦合 |

**最终正确性依赖谁（架构师判据）**：

```text
生产者幂等（KIP-98）   → 消除"Broker 落两条"       （MQ 层）
消费端幂等（DB 同事务） → 消除"处理两次"            （业务 + DB 层）
状态机                → 消除"乱序落地"（挡非法转移） （业务层）
对账                  → 兜底一切漏网                （运营层）
→ Redis 只能是性能层（前置过滤），不能是正确性层
→ 正确性必须落在 DB 事务上
```

**本题推荐组合**：**状态机 + 唯一索引（消费记录表）同事务**——状态机管"序"，唯一索引管"重"，同一 DB 事务落地。幂等键粒度 = 业务单元（mq-04）：orderId + 事件类型，不是消息 ID（消息 ID 只在"重建消息的重放"时才会变，Kafka 原生重投同一条消息 ID 不变——所以消息 ID 从来不是可靠的幂等键）。

### Transfer——这个思想还能迁移到哪里

1. **"物理序 ≠ 业务序"**：任何事件驱动系统（订单、支付、物流）都要先定义顺序边界——顺序范围的声明比顺序实现更重要。
2. **幂等键粒度 = 业务单元**：消息 ID、请求 ID、业务键——选错粒度，要么吞业务（过粗）要么放重复（过细）（mq-04 坑）。
3. **扩容与顺序的冲突**：任何"哈希路由 + 有序消费"的组合（分库分表按用户 ID、缓存分片）——扩容都破坏路由连续性，重建是唯一出路。

本层留下的新账：乱序和重复能"防"了——但**已经乱了的消息怎么办**？PAID 先到了，CREATED 还没到，系统不能干等。 → 逼出 Level 4。

### Level Ending

```
🔴 口诀：顺序范围 = Key 级；并行范围 = 分区级；重复靠幂等，正确性靠 DB 事务。
```

<a id="level-4"></a>

## Level 4：订单链路——顺序缺口补偿与 Rebalance 保障

一句话认知墙：乱序是常态，补偿是设计；不防无限等待的补偿机制，是第二个事故源。

### 前置知识关卡

- [ ] 知道延迟消息与死信机制（mq-07 L4/L5）
- [ ] 知道 rebalance 事故链与优雅离开（mq-06 L3）
- [ ] 知道状态机与幂等（L3 本层）

### 病历——PAID 已经先到，CREATED 尚未到

```text
现象：消费端收到 ORDER_PAID，但 ORDER_CREATED 还没到（或还没处理完）
要求：设计 本地缓存等待 / 延迟重试 / 状态机校验 / 消息重投 / 死信队列
      并说明如何避免无限等待
```

### Why——顺序缺口不是"消息丢了"，是"它还没到"

**老陈**：先定性：这是**顺序缺口**——不是消息丢失，是它还没到、在路上、或被别的路径延迟（跨分区并发、重试、积压都会造成，L3 已拆）。**乱序可以等（秒级），丢了必须补（对账），等一辈子也等不来**——这个判断决定了方案的选择。

### What——"等、拒、扔"三件套

```text
方案一：本地缓存等待（等）
  收到 PAID → 查 CREATED 未到 → 缓存 PAID，限时等待
  代价：内存占用、等待超时后仍需后续处理
  适用：乱序窗口小（毫秒~秒级）、PAID 通常紧随 CREATED

方案二：延迟重试（等，但放到 MQ 里等）★推荐
  PAID 处理失败（前置状态缺失）→ 回投延迟主题（mq-07 延迟机制）
  → 秒级/分钟级后重投 → 届时 CREATED 大概率已到
  ★不占用内存，重试状态可观测（重试次数可查）
  代价：延迟送达、重试次数要设上限

方案三：状态机校验（拒）★第一道闸
  处理入口先校验前置状态：CREATED 不存在 → 拒绝 + 回投（方案二）
  状态机是"第一道闸"：非法流转进不来，合法流转按序执行
  代价：状态机要完整定义（PAID 前置 = CREATED，SHIPPED 前置 = PAID…）

方案四：消息重投（人工/自动）
  超过重试上限仍前置缺失 → 触发"重投 CREATED"（对账补发，mq-03 L5）
  —— 此时要查根因：CREATED 为什么一直没到？被丢弃？进 DLQ？生产端没发？

方案五：DLQ 兜底（扔）
  重试次数到上限 → 进 DLQ + 告警（mq-07 L5 治理）
  → 人工/对账介入，绝不在业务队列里无限打转
```

### What——如何避免无限等待（防活锁纪律）

```text
① 每个"等"必须有上限：缓存等待 ≤ 5s；延迟重试 ≤ 3 次（指数退避 1s/10s/60s）
② 每次回投都带剩余重试次数，次数耗尽 → DLQ（防活锁：消息永远在队列里转圈）
③ 订单卡死检测：状态机加"卡点告警"——某订单超过 N 分钟未推进 → 告警
   ★本题"某些订单卡在 PAID"就是缺了这个检测
④ 对账闭环：定期对账，发现状态缺失 → 自动补发/人工介入
⑤ 判"乱序还是丢了"：乱序可以等（秒级）；丢了必须补（对账）——别用等待
   治疗"丢消息"
```

### What——Rebalance 时如何不丢消息、不乱序

**徒弟**：发布新版本触发 Rebalance，我怎么保证不丢、不乱序？

**老陈**：先分清三个机制各自能保证什么（mq-06）：

```text
Consumer Group：组内分区所有权唯一（同一分区同时只属一个消费者）
Partition ownership：rebalance 重新分配所有权 → 处理中消息随所有权移交
Offset：位点推进 = "我不再要这条了"（mq-03）——处理完才提交 = 不丢；
       但处理完未提交就移交 = 必然重投 = 重复
→ "不丢"由 at-least-once + 提交纪律保证
→ "不重复"做不到（机制层面）——靠幂等兜底
→ "不乱序"必须由业务层状态机保证（MQ 不提供跨 rebalance 的顺序）
```

**工程纪律组合拳（不丢不乱序）**：

```text
① 提交纪律：业务成功 → 再提交位点；绝不自动提交（mq-03 自动提交两面性）
② 优雅停机（发布新版本场景）：
   应用的停机纪律 = 先停拉取（停止 poll 循环）→ 等待处理中消息完成 → 提交位点 → 再 consumer.close() 离组
   （注意：consumer.close() 本身不排空、也不替你提交位点——排空与提交是应用/容器要做的纪律）
   ★被 kill -9 / 超时踢出 = 强制 rebalance = 处理中消息重投（重复的来源）
   滚动发布应：先停拉取、排空、再下线实例（每实例优雅离组）
③ 处理中消息跟踪：onPartitionsRevoked 时提交已完成的、记录未完成的
   （RocketMQ 顺序消费的 ProcessQueue 锁机制内建；Kafka 需自己处理）
④ Cooperative Rebalance（KIP-429，Kafka 2.4+，Implementation）：
   增量重平衡——先撤销部分分区（消费完再交）→ 再分配，
   避免 stop-the-world 全量风暴（RocketMQ 5.x 逐步演进，按版本确认——待验证）
⑤ 幂等兜底：无论 rebalance 多么优雅，"处理完未提交"窗口永远存在
   → 消费端幂等（L3）是最后防线，rebalance 优化只能缩小窗口不能关闭窗口
```

**架构师结论**：rebalance 下"不丢"可以做到（提交纪律），"不重复"做不到（at-least-once 机制），"不乱序"要靠业务层状态机挡非法流转——**MQ 的 rebalance 保证不了顺序，保证顺序的是你的状态机**。

### Transfer——这个思想还能迁移到哪里

1. **"等/拒/扔"是顺序补偿的通用三件套**：数据库双写乱序（binlog 追平）、缓存与库不一致（延迟重试）——同一个模式。
2. **防无限等待 = 状态机 + 超时 + 死信**：任何"重试补偿"机制都必须自带终止条件，否则活锁（mq-07 的治理思想）。
3. **优雅停机 = 把"强制"变成"可控"**：滚动发布、集群缩容、任务调度——"先停入口、排空、再退出"是通用纪律。

本层留下的新账：所有机制都讲完了——**严格顺序 + at-least-once + 高吞吐，怎么一次设计对？** → 逼出 Level 5。

### Level Ending

```
🔴 口诀：乱序可以等，丢了必须补；等要有上限，扔要进 DLQ；rebalance 保证不了顺序，状态机能。
```

## Level 5：订单链路——最终设计（保证归属表）

一句话认知墙：设计评审的第一问不是"用什么 MQ"，而是"每个保证由谁提供"。

### 前置知识关卡

- [ ] 完成 L1~L4 全部机制（确认/堆积/顺序/幂等/补偿/Rebalance）

### 病历——要求

```text
严格顺序（同 orderId）+ at-least-once + 高吞吐（峰值 20 万/s）
要求：画出完整架构，明确哪些保证由 MQ 提供、哪些由业务提供、哪些由数据库提供
```

### What——完整架构图

```text
┌─────────────────────────────────────────────────────────┐
│ Producer（订单服务）                                       │
│   ① 幂等生产者（KIP-98）——重试保序 + Broker 层去重          │
│   ② key = orderId（Kafka）/ sharding key = orderId        │
│   ③ 峰值 20 万/s 容量规划：分区数 = 峰值 / 单分区实测 × 系数   │
│      （分区数创建时定死，不接受运行期扩容换乱序）              │
└──────────────┬──────────────────────────────────────────┘
               ▼
┌─────────────────────────────────────────────────────────┐
│ MQ（Kafka 或 RocketMQ）                                   │
│   同 orderId → 同分区/同队列（路由定死）                     │
│   分区内/队列内有序（MQ 机制保证）                           │
│   at-least-once 重投（MQ 机制保证）                        │
│   Cooperative Rebalance + 优雅停机（缩小重复窗口）           │
└──────────────┬──────────────────────────────────────────┘
               ▼
┌─────────────────────────────────────────────────────────┐
│ Consumer（库存/支付/履约，消费者数 = 分区数）                │
│   ① 每分区单线程处理（顺序消费模式，Key 级串行）              │
│   ② 处理成功 → 同事务写"消费记录表 + 状态机推进"→ 再提交位点   │
│   ③ 状态机校验前置：PAID 无 CREATED → 延迟重试（上限 3 次）   │
│   ④ 重试耗尽 → DLQ + 告警 + 卡点检测（N 分钟未推进即告警）     │
│   ⑤ 对账：缺失状态自动补发                                  │
└──────────────┬──────────────────────────────────────────┘
               ▼
┌─────────────────────────────────────────────────────────┐
│ DB（业务库）                                              │
│   ① 唯一索引（orderId + 事件类型）——幂等                    │
│   ② 状态机表——顺序正确性                                   │
│   ③ 消费记录表（与业务同事务）——最终正确性                  │
└─────────────────────────────────────────────────────────┘
```

### What——保证归属表（架构评审必答）

| 保证 | 谁提供 | 机制 |
| ---- | ---- | ---- |
| 同订单有序 | **MQ** | 分区/队列内有序（key 路由 + 顺序消费） |
| 跨订单并行 | **MQ + 容量规划** | 分区数 = 并行度；分区数定死不扩容 |
| at-least-once | **MQ** | 位点/ack 语义 + 重投 |
| 生产者不重复落盘 | **MQ** | 幂等生产者（KIP-98） |
| 消费不重复处理 | **业务 + DB** | 唯一索引 / 消费记录表（同事务） |
| 乱序不落地 | **业务 + DB** | 状态机校验（挡非法转移） |
| 顺序缺口补偿 | **业务 + MQ** | 延迟重试 + DLQ + 对账 |
| 最终正确性 | **DB** | 事务原子性（唯一约束 + 状态机同事务） |

**判读规则（老陈）**：表格里"MQ 提供"的列越短越好——MQ 只保证"分区内有序 + at-least-once + 幂等生产"这三件事；其余全部下沉到业务与 DB。**任何想让 MQ 多保证一点的设计（全局顺序、跨分区事务、exactly-once 开关），都是在问一个 mq-04/mq-07 已经否决过的问题**。

### What——Trade-off 与风险（架构评审收尾）

```text
① "严格顺序"的真实代价：热点 orderId 串行拖慢整分区（单 Key 热点，mq-04）
   → 吞吐靠"订单间并行"补齐
   → 先确认单分区吞吐能扛峰值单订单流量（待实测），扛不住要重新评估
     （分拆事件流 or 接受热点订单延迟）
② 运行期扩容 = 换乱序：分区数创建时定死；要扩只能重建主题 + 双跑（mq-09）
③ 高吞吐与严格顺序的平衡点：
   顺序范围 = 单订单（Key 级），并行范围 = 跨订单（分区级）
   → 这个边界就是本设计的全部答案
④ 兜底双保险：状态机挡乱序、幂等挡重复、对账挡漏网——三层缺一层，
   事故就从缺的那层进来
```

### Transfer——这个思想还能迁移到哪里

1. **保证归属表是通用评审工具**：任何分布式设计（缓存一致性、分布式事务、多活）都该回答"每个保证由谁提供"——答不出归属的保证，就是不存在的保证。
2. **"MQ 提供的越少越好"**：中间件只做它机制内的事（mq-00 的模型分野），把"业务语义"外包给中间件 = 选型时就把事故买下来了。
3. **兜底三层设计**：机制层（MQ）→ 正确性层（DB）→ 运营层（对账）——任何系统都该有三层。

本层留下的新账：三个场景全部复盘完了——**它们的共同病根是什么？怎么把诊断变成可迁移的方法论？** → 逼出 Level 6。

### Level Ending

```
🔴 口诀：MQ 只保证三件事；正确性归 DB；顺序范围是 Key；兜底三层缺一不可。
```

## Level 6：病例复盘——共同病根与故障诊断方法论

一句话认知墙：任意故障 = 机制的某个窗口被击中。

### 前置知识关卡

- [ ] 能说出系列全部机制：确认级别（mq-03）、存储窗口（mq-02）、重平衡（mq-06）、事务路径（mq-07）、副本承诺（mq-08）、顺序边界（mq-04）

### Why——三个场景的共同病根

**老陈**：三个场景的根，是同一个字：**"以为"**。

```text
病例一：以为 @Transactional 管到了 Kafka；以为 send 返回 = 已持久化
  → 病根：确认语义错位（把 API 返回当成业务成功，神话① 的实战版）

病例二：以为加消费者就有用；以为加分区能清 Lag；以为消费速率是上限
  → 病根：容量规划缺失 + 无背压（把"能发出去"当成"能消化"，神话⑦ 的实战版）

病例三：以为按顺序发就按顺序消费；以为提交位点就不会重复；
        以为 PAID 先到是"消息丢了"
  → 病根：顺序边界认知缺失 + 补偿机制缺位（把"物理序"当成"业务序"，
        把"乱序"当成"丢失"）

共性：把"机制的某一层"当成了"机制的终点"
  —— 确认的终点是 Broker 持久化（不是 send 返回）
  —— 消费的终点是业务完成（不是拉取成功）
  —— 顺序的终点是业务序（不是发送序）
  —— 系列的每篇都在拆这种"以为"：mq-02 拆"内存快"、mq-03 拆"ack=成功"、
     mq-06 拆"加机器有用"、mq-07 拆"事务消息万能"
```

### What——故障诊断模板：机制 + 窗口

**老陈**：把故障翻译成"机制 + 窗口"，救治路径自动浮现。翻译表（本系列机制 × 事故现象）：

```text
现象                        → 机制            → 窗口                → 救治
DB 有单、Kafka 无消息        → 发送确认(mq-03) → 入缓冲→发送→确认间    → Outbox/对账（L1）
Lag 持续增长                → 消费并行度(mq-06)→ 消费速率 < 生产速率  → 降生产/提消费（L2）
消费突然变慢                → 线程模型(mq-05) → 单 poll 串行/批量太小 → 批量/优化处理（L2）
消费者反复加入退出           → 重平衡(mq-06)   → 处理超时被踢          → 调大超时/减批量
PAID 先于 CREATED           → 顺序边界(mq-04) → 跨分区/并发完成序     → 状态机+延迟重试（L4）
消息重复                    → 重试/位点(mq-03) → 提交与处理无顺序保证  → 幂等（L3）
订单卡在 PAID               → 补偿(mq-07)     → 重试耗尽无兜底        → DLQ+卡点告警（L4）
断电丢已确认消息             → 存储(mq-02)     → page cache → fsync   → 刷盘配置（mq-02）
切换丢末批                  → 副本(mq-08)     → HW/ack 承诺边界       → 同步复制档位
```

**诊断顺序（急诊流程）**：

```text
第一步 止血：控制恶化（压生产 / 停写 / 降级）——不追求最优解
第二步 定位：把现象翻译成"机制 + 窗口"（上表）
第三步 根治：在窗口边界上做方案（窗口关不掉 = 补兜底）
第四步 演练：故障注入验证（mq-09 变更治理的演练纪律）
```

### How——方法论迁移到其他系统

**徒弟**：这套流程能不能用到别的中间件？

**老陈**：翻译表里的"机制"换成任何系统都成立：

```text
Redis：现象"缓存有、DB 无"→ 机制=双写 → 窗口=写序 → 救治=binlog 订阅/对账
数据库：现象"主从不一致"→ 机制=复制 → 窗口=半同步 ack → 救治=半同步/校验和
微服务：现象"订单有、通知没发"→ 机制=消息投递 → 窗口=发送确认 → 救治=Outbox
订单链路：现象"PAID 先到"→ 机制=顺序边界 → 窗口=跨分区 → 救治=状态机+补偿
```

**通用配方**：任何系统先回答三个问题——① 机制是什么（哪一层在保证什么）？② 窗口在哪里（保证的边界）？③ 窗口被击中后，哪边多、哪边少（不可接受的损失方向）？**答得出这三个问题，故障就不是黑盒；把全部窗口列出来，就是一份完整的设计**（L5 的保证归属表就是这么来的）。

### Transfer——这个思想还能迁移到哪里

1. **事故复盘 = 窗口归因**：复盘会上不要问"谁的锅"，要问"哪个机制的哪个窗口被击中了"——归因到机制，修复才可复用（mq-07 的归因思想）。
2. **架构评审 = 窗口审计**：评审任何设计，先问"你的机制是什么、窗口在哪里、窗口被击中怎么办"——答不出窗口的设计，就是没设计完。
3. **演练 = 窗口注入**：故障演练的本质是"人为击中每个窗口"，验证每个窗口都有救治路径（mq-08 切换演练、mq-09 变更演练）。
4. **设计与诊断是同一张表**：L5 的保证归属表（正常视角）与 L6 的窗口翻译表（故障视角）是一枚硬币的两面——设计时把窗口列全，事故时才有答案。

### Level Ending

```
🔴 口诀：故障 = 机制 × 窗口；止血在前，定位在中，根治在后，演练闭环。
```

<a id="pitfalls"></a>

# ⚠️ 坑与细节

## 坑 1：把 send() 返回值当成功凭证

错误理解：send 不抛异常 = 消息发出去了。

机制：send 是异步入缓冲（Kafka 客户端 API 语义），失败在异步回调里。

线上现象：DB 有单、Kafka 无消息，且日志无任何异常。

修正：要么同步等待 + 失败处理（方案 A），要么 Outbox（方案 B）；send 必须有失败回调与告警（方案 C 的底线）。

## 坑 2：加消费者不加分区

错误理解：消费者数越多消费越快。

机制：并行度 = 分区数（mq-06 L4）。

线上现象：消费者从 4 加到 20，消费速率纹丝不动。

修正：先数分区，消费者补到分区数为止；要更多并行度 → 扩容分区（增量）+ 旧分区吃满（存量）。

## 坑 3：加分区想清存量 Lag

错误理解：分区多了，1.8 亿 backlog 消化得快。

机制：加分区 = 加空分区，存量消息不迁移（mq-06 坑 4）。

线上现象：加了分区，Lag 只降了几个百分点（存量还在旧分区）。

修正：清存量靠"降生产 + 旧分区吃满"；加分区只缓解新消息的并行度。

## 坑 4：调大批量忘记调 max.poll.interval.ms

错误理解：max.poll.records 拉大就是纯赚。

机制：单批处理时长变长 → 超过 max.poll.interval.ms（默认 5 分钟）→ 被踢出组（mq-06 风暴）。

线上现象：批量后消费更慢了（频繁 rebalance + 重复消费）。

修正：批量参数与轮询超时参数同步调整；批处理时长留 30% 以上余量。

## 坑 5：只用集群层告警发现堆积

错误理解：Broker 磁盘红了才是事故。

机制：Lag 是先行指标，磁盘是滞后指标（mq-09 L1 监控分层）。

线上现象：Lag 涨了 3 小时，磁盘满了才告警。

修正：业务层 lag 告警分级阈值（mq-09 L2），故障注入验证"lag 先于磁盘告警"。

## 坑 6：运行期扩容分区想要"顺序与并行兼得"

错误理解：订单量涨了，加几个分区再让订单重新 hash 就行。

机制：加分区改变 key 路由 → 同 orderId 后续消息换分区 → 顺序断裂（mq-06 坑 4 原因）。

线上现象：扩容后同一订单 PAID/SHIPPED 乱序，状态机告警刷屏。

修正：分区数创建时按峰值定死 + 增长系数预留；要扩只能重建主题 + 双跑（mq-09 变更治理）。

## 坑 7：没有状态机的"顺序消息"

错误理解：路由对了、消费串行了，顺序就有保证了。

机制：乱序窗口（重试/并发/rebalance）不可能关死——**顺序保证的最后一道闸是状态机挡非法流转**。

线上现象：PAID 先到后业务直接处理，扣款成功但订单还没创建。

修正：状态机校验前置（L4 方案三）+ 延迟重试 + DLQ，缺一不可。

## 病例一：双写一致（Level 1）

```text
T0  @Transactional 方法执行：insert + send（入缓冲）
T1  方法返回 → DB 提交成功 → 订单可见
T2  缓冲消息后台发送（或失败静默 / 或应用崩溃）
T3  线上现象：DB 有单、Kafka 无消息 ★窗口被击中
T4  救治：Outbox（关窗口）+ 对账（兜底）
```

## 病例二：堆积事故（Level 2）

```text
T0  生产 20 万/s、消费 5 万/s、12 分区 → 缺口 15 万/s（推算）
T1  止血：压生产（限流/削峰）→ Lag 增速归零
T2  定位：消费者数 vs 分区数 → 批量 → 单条路径 → 下游瓶颈
T3  提消费：批量 + 优化 + （必要时）扩容分区（救增量）
T4  清存量：旧分区吃满（Lag ≈ 1000 万 / 富余消费速率）
T5  根治：容量规划（分区数 = 峰值消费需求 / 单分区吞吐）+ 背压机制
T6  演练：故障注入验证 Lag 告警 → 预案执行 → 指标回归
```

## 病例三：订单链路（Level 3~5）

```text
T0  事件流：key=orderId 路由 → 同订单同分区（有序基础）
T1  乱序窗口被击中：PAID 先于 CREATED（跨分区/并发/rebalance）
T2  状态机拦截非法流转 → 回投延迟重试（1s/10s/60s，上限 3 次）
T3  重试耗尽 → DLQ + 告警 + 卡点检测（N 分钟未推进即告警）
T4  对账补发缺失状态（CREATED 一直没到 → 查根因）
T5  滚动发布：优雅停机（停拉取→排空→提交→离组）+ Cooperative
T6  最终设计：保证归属表（MQ 三件事 / 业务幂等与状态机 / DB 最终正确性）
```

<a id="errata"></a>

# 📚 版本勘误表

| 坦白 | 事实 |
| ---- | ---- |
| "send 返回 = 消息已发" | send 异步入缓冲，返回的是 Future（Kafka 客户端 API 语义）；确认以 Broker ack 为准 |
| "@Transactional 管到 Kafka" | 默认只管理单一 DataSourceTransactionManager（Spring 语义）；要管 Kafka 需显式配置事务管理器（Kafka 事务，mq-07），且管不到业务 DB |
| "加消费者一定提速" | 并行度 = 分区数；消费者 > 分区数即空转（mq-06 机制） |
| "加分区能清 Lag" | 加分区 = 加空分区，存量不迁移（mq-06 坑 4 修正） |
| "消费速率是上限" | 消费速率是瓶颈压制下的结果，不是上限；上限由瓶颈位置决定（待实测） |
| "批量越大越好" | 批大 → 处理时长长 → max.poll.interval.ms 被踢风险；批量与超时参数联动（Implementation，默认值以所用版本官网为准） |
| "Redis SETNX 就是幂等" | Redis 是性能层（前置过滤），非持久化/主从切换/淘汰都会丢键；最终正确性必须落在 DB 事务 |
| "重试保证不乱序" | Kafka 幂等生产者（KIP-98）开启后重试保序；未开启时同分区可乱序（Implementation，按版本） |
| "rebalance 保证不重复" | at-least-once 机制下"处理完未提交"窗口永远存在；Cooperative（KIP-429，2.4+）只缩小窗口，幂等才是兜底 |
| "按顺序发就按顺序消费" | 顺序边界 = Key 级；跨分区/并发/rebalance 都会打乱"发送序"与"业务序" |

# 🏆 生产决策卡

## Decision Card 1：双写一致性方案选型

### 场景

交易链路：`@Transactional` 里写 DB + 发消息，要求消息少与消息多都不可接受。

### 判断

Outbox 本地消息表（B）+ 对账（D）组合；同步等待（A）仅作单条低频缓解；AFTER_COMMIT（C）仅限可接受小概率消息少。

### Mechanism → Decision

| 机制 | 工程决策 |
| -- | ---- |
| DB 事务原子性 | 订单 + outbox 同库同事务（mq-07 L1 候选一） |
| 发送确认 | 定时任务发 Kafka，成功后删 outbox；失败重试 + 告警 |
| 兜底 | 对账补发（mq-03 L5），幂等消费（mq-04） |
| 反向窗口 | 消息多（ack 后回滚）→ 消费端幂等兜底 |

### 禁止决策

- 裸 `@Transactional + send` 上线（两个窗口都开着）
- 先发消息后写 DB 且无对账（消息多无兜底）

### 验收指标

- 故障注入：kill 发送进程 → 对账发现缺失 → 补发恢复，零静默丢失
- DB 回滚演练：消费端幂等拦截重复消息（mq-04）
- 对账 24h 零差异（mq-03）

## Decision Card 2：堆积事故响应预案

### 场景

生产 20 万/s、消费 5 万/s、12 分区、Lag 1000 万（或生产 20 万/s、消费 10 万/s、30 分钟积压 1.8 亿）。

### 判断

止血（压生产）→ 定位（消费者数 vs 分区数 → 批量 → 单条路径 → 下游）→ 提消费（批量 + 优化）→ 清存量（旧分区吃满）→ 根治（容量规划 + 背压）。

### Mechanism → Decision

| 机制 | 工程决策 |
| -- | ---- |
| 并行度 = 分区数 | 消费者数 ≤ 分区数（每分区/队列串行模型）；要更高并行度先加分区（增量） |
| 加分区不迁存量 | 清 Lag 靠"降生产 + 旧分区吃满" |
| 线程模型 | 批量消费（max.poll.records ↑）+ 批量写下游（mq-05 L3） |
| 重平衡 | 批量与 max.poll.interval.ms 联动（坑 4） |
| 背压 | 消费端限流 + pause/resume + 降级分级（S1~S4） |

### 禁止决策

- 不压生产先扩消费（Lag 增速压不住，扩容白做）
- 加消费者超过分区数（纯空转）
- 批量调大不调轮询超时（被踢风暴）
- 无降级剧本（事故时临场发明）

### 验收指标

- 演练：Lag 注入 → 预案执行 → Lag 清空时间与推算一致（±30%，待实测校准）
- 指标回归：恢复后 24h 延迟/错误率回到基线
- 预案文档化：S1~S4 分级动作与责任人（mq-09 变更治理纪律）

---

## Decision Card 3：订单链路最终设计评审

### 场景

要求严格顺序（同 orderId）+ at-least-once + 高吞吐（峰值 20 万/s）的订单事件链路。

### 判断

Kafka key=orderId（或 RocketMQ sharding key）+ 分区数创建时定死 + 消费端"状态机 + 唯一索引同事务" + 延迟重试/DLQ/对账兜底 + 优雅停机与 Cooperative。

### Mechanism → Decision

| 机制 | 工程决策 |
| -- | ---- |
| 同订单有序 | key 路由 + 分区内有序（MQ）；分区数定死不扩容 |
| 幂等 | 唯一索引/消费记录表同事务（DB）；幂等生产者（KIP-98） |
| 乱序不落地 | 状态机校验前置（业务）；延迟重试 + DLQ + 对账（补偿） |
| Rebalance | 提交纪律 + 优雅停机 + Cooperative（KIP-429） |
| 正确性归属 | MQ 只保证三件事；最终正确性归 DB 事务 |

### 禁止决策

- 运行期扩容分区（换乱序）
- 用 Redis 当幂等正确性层
- 无状态机的"顺序消息"（乱序窗口关不死）
- 无卡点检测（订单卡死不告警）

### 验收指标

- 故障注入：乱序注入（PAID 先到）→ 状态机拦截 → 延迟重试恢复，零非法流转
- 重复注入（kill 消费进程）→ 幂等拦截，零重复处理
- Rebalance 演练：滚动发布 → 无重复、无乱序（状态机零告警）
- 对账 24h 零差异（mq-03）

# 🌍 跨语言视角

## 同一个问题：生产故障诊断与顺序链路

| 语言 | 双写一致性形态 | 堆积排查形态 | 顺序链路形态 |
| -- | ---- | ---- | ---- |
| Java | Spring @Transactional + KafkaTemplate（病例一） | Kafka 客户端指标 + 线程 dump | Spring Kafka 顺序消费/批量监听 |
| Go | 手动事务 + sarama（同步发送/回调） | 消费组 lag exporter | 单分区 goroutine 串行 + 状态机 |
| Rust | rdkafka 同步发送 + 本地表 | 统计回调 + 外部监控 | 分区级 actor 模型串行 |
| Python | confluent-kafka（异步回调必接） | 消费组监控 + 批处理脚本 | 单线程按分区消费 + 状态机 |

## 跨语言仍成立的判断力

1. **确认语义是协议问题不是语言问题**：任何语言的 Kafka 客户端，send 都是异步语义——回调/同步等待是必须的选择题，不是可选项。
2. **并行度 = 分区数（每分区串行处理模型下）**：与语言无关的机制，任何语言栈的消费者数都不能超过分区数；并发消费模式（RocketMQ）的单消费者内并发是另一层变量（mq-05 L3）。
3. **批量与超时的联动**：任何语言的消费循环都受 poll 间隔约束——批量调大必须同步调大轮询超时。
4. **顺序边界与状态机**：Key 级串行 + 状态机挡非法流转，与语言无关——业务序是业务自己的事，MQ/语言都不管。

## 唯一主线与唯一比喻
