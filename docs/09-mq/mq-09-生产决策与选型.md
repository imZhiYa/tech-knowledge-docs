## Level 1：监控分层——神话⑫ 的破解

一句话认知墙：为什么集群指标全绿，业务还是死了？

### 前置知识关卡

- [ ] 知道"DLQ 把隐性故障变成显性清单"（mq-07 L5）
- [ ] 知道积压拖磁盘（mq-02 积压教训）

### Why——两层指标，两种死亡

**徒弟**：监控大屏上 Broker 的 CPU、磁盘、内存都正常，副本也同步——系统应该是健康的吧？

**老陈**：大屏绿了，业务可能已经死了。把指标分成两层，各看各的死亡：

```text
集群层指标（大屏）：Broker 存活、CPU、内存、磁盘、副本同步
  回答：中转站的车站设施还开着吗？
  死亡形态：机器故障、资源耗尽、副本脱节

业务层指标（后台）：生产速率、消费速率、lag、端到端延迟、
  DLQ 积压、重试次数、生产错误率
  回答：货真的在流动吗？
  死亡形态：消息滞留、消费停滞、延迟飙升、坏件堆积

神话⑫ 的破解点：
  集群层全绿 ≠ 业务层健康
  —— 最常见的"绿屏惨案"：
    * 消费组被风暴拖死（mq-06），Broker 一切正常
    * 毒消息占住队列（mq-04/mq-07），Broker 一切正常
    * 下游 DB 挂掉，消费端全部阻塞，Broker 一切正常
  → 集群健康管"设施"，业务指标管"流动"
  → 只有业务层指标能发现"设施正常但货不流动"
```

> 📌 最容易被误解的一点：**告警体系最容易犯的错是"只接集群层指标"**。因为集群指标 API 现成、接入快；而 lag、延迟、DLQ 需要消费端配合上报。但**集群层告警多是"事后告警"**（进程挂了、分区不可用才响；少数事前项是磁盘水位、连接数这类资源阈值），业务层告警才是"事前告警"（货开始堆积就响；注：lag 本质仍是"已堆积"的反应性信号，它比磁盘早响只因为它更接近源头——是先兆，不是根因，见 L2 相关与因果）。**事故发现得越早，越接近业务层**——监控分层的核心就是"把告警边界下沉到业务层"。

### What——监控分层全景图

```text
第一层：集群层（基础设施）
  Broker 存活 / CPU / 内存 / 磁盘 / 副本同步 / 网络
  作用：设施故障的及时感知（mq-08 的切换演练也依赖这层）

第二层：消息层（流转）
  生产速率（TPS）/ 消费速率 / lag / 端到端延迟
  作用：货流是否通畅（lag 是这层的主角）

第三层：业务层（效果）
  DLQ 积压 / 重试次数 / 生产错误率 / 对账差异
  作用：业务正确性（mq-03 对账、mq-07 死信治理）

三层的关系：
  集群层是底座（设施），消息层是血管（流动），
  业务层是器官（效果）——每层都有自己的死亡形态，
  只盯一层等于只救一种死法。
```

### How——E 的"绿屏惨案"推演

```text
T0  监控大屏：集群层全绿（CPU 正常、磁盘正常、副本同步）
T1  实际：消费组被风暴拖死（mq-06 事故链）
T2  消息堆积：lag 从 1000 涨到 50 万
T3  下游依赖超时 → 消费失败 → 重试 → 毒消息占队列
T4  磁盘被积压拖满（mq-02：积压拖住 CommitLog 回收）
T5  集群层终于告警（磁盘）——但事故已发生 3 小时
T6  复盘：若 T2 的 lag 告警存在（业务层），事故边界在 10 分钟内
```

**徒弟**：为什么 lag 告警能提前这么多？

**老陈**：因为 lag 是"货在堆积"的直接信号——**消费速率跟不上生产速率的第一毫秒就开始涨**；而磁盘是"堆积的结果"的最终信号——要等堆到满才响。但要分清**相关与因果**：监控里"业务层指标在前、集群层指标在后"只是时间上的相关（lag 涨 → 堆 → 磁盘涨），不代表根因在业务层——lag 涨的因可能在消费端（处理慢，mq-05/mq-06）、在生产端（突发流量）、在存储层（积压拖住 CommitLog 回收，mq-02）。**指标回答"哪里先响"，根因要靠下钻链路去查**：盯"先行指标"能提前止损，但止损动作必须来自因果分析，不能只凭相关性。

### Transfer——这个思想还能迁移到哪里

1. **指标分层是通用方法论**：数据库（连接池/慢查询/锁等待 vs 磁盘/CPU）、网关（错误率/延迟 vs 负载）——"基础设施层 vs 业务效果层"永远分两层看。
2. **事前告警 vs 事后告警**：因指标（前置）永远比果指标（后置）早响——告警设计的第一原则。
3. **设施健康 ≠ 业务健康**：任何系统评审都要问"业务效果指标是什么"，答不上来 = 没有可观测性。

本层留下的新账：lag 是最重要的业务层指标——但看到 lag 暴涨之后怎么办？堆积的瓶颈到底在哪一层？→ 逼出 Level 2。

### Level Ending

```
🔴 口诀：集群绿了，业务可能死了。
```

## Level 2：堆积治理——lag 分层定位法

一句话认知墙：lag 暴涨，先加机器还是先查什么？

### 前置知识关卡

- [ ] 知道"加消费者=可用性、加分区=并行度"（mq-06 L4）
- [ ] 知道积压与磁盘互相绑架（mq-02）

### Why——lag 涨了先别动刀

**徒弟**：lag 告警响了，赶紧加消费者？

**老陈**：先定位，再动刀——**lag 上涨只有一个数学原因：消费速率 < 生产速率**。但"消费速率为什么慢"有四个候选层，加错层等于白干：

```text
瓶颈四层（mq-06 L4 的扩容真相在这里落地）：

第一层：并行度层（分区/队列数）
  分区数 = 并行度上限 → 消费者再多也空转
  验证：消费者数 ≥ 分区数？分区数够峰值吗？

第二层：单消费者处理层（业务执行成本）
  单条处理时间 = 消费速率的分子
  验证：单批处理时长、线程池、批量参数

第三层：下游层（DB/外部依赖）
  消费端把压力传给下游 → 下游是最终瓶颈
  验证：下游 QPS/连接池/慢查询

第四层：热点层（Key 倾斜）
  单 Key 串行（mq-04 L4）→ 热点 Key 拖住整个队列
  验证：队列消费速率不均衡（某个队列 lag 独大）
```

### What——治理手段矩阵

| 瓶颈层 | 治理手段 | 代价 |
| ---- | ---- | ---- |
| 并行度层 | 加分区（破坏 Key 路由，mq-04 坑 5） | 顺序风险 |
| 单消费者层 | 调批量/线程池/优化处理逻辑 | 有限（受分区数约束） |
| 下游层 | 下游扩容 / 限流 / 降级 / 缓存 | 跨团队协调 |
| 热点层 | Key 拆分 / 业务改造 / 分桶 | 业务侵入 |
| 生产侧 | 生产端限流（削峰填谷的另一半） | 生产者背压 |

**徒弟**：还有一个场景——生产侧暴涨呢？大促流量 10 倍，消费怎么扛？

**老陈**：这就要区分"生产暴涨"与"消费变慢"两种堆积：**生产暴涨 → 削峰是主战场**（mq-00 的削峰填谷语义在这里兑现：消费端按能力消费，堆积是预期的缓冲）；**消费变慢 → 治理是主战场**（定位瓶颈四层）。**但任何堆积都有上限**：堆积超过磁盘承载或业务容忍窗口（mq-02：积压拖住 CommitLog 回收），就必须降级——砍非关键消息（通知类降级、审计类丢弃）、保核心链路（订单类优先）。

### How——E 的堆积治理全流程

```text
T0  lag 告警：库存组 lag 50 万，持续 30 分钟
T1  定位第一步：生产速率 vs 消费速率
    - 生产速率平稳 → 消费变慢（不是生产暴涨）
T2  定位第二步：瓶颈四层
    - 消费者数 = 分区数（并行度不是瓶颈）
    - 单消费者处理时长正常（不是执行成本）
    - 下游 DB 慢查询飙升 ★瓶颈在下游
T3  治理：下游扩容 + 慢查询优化（不是加消费者！）
T4  兜底：幂等表（mq-04）防治理期间的重复
T5  复盘：堆积期间磁盘压力与恢复策略（mq-02 整文件粒度回收）
```

**徒弟**：如果瓶颈在热点层呢？加分区也没用对吧？

**老陈**：对——热点 Key 的单队列串行（mq-04 L4），加分区改变不了"同一个 Key 的所有消息仍在一个队列"（扩容后 Key 会换到新队列，但依然只有一个队列，同一队列内依然串行）。**热点层治理只能靠业务层：Key 拆分（按维度拆）、分桶（打散到多个 Key）、或接受延迟**。这也再次说明：**堆积治理的第一原则是"先定位层，再选手段"——四层各有一把锁，用错钥匙打不开门**。

### Transfer——这个思想还能迁移到哪里

1. **分层定位法通用**：数据库慢查询（索引/执行计划/锁/硬件）、网络延迟（客户端/链路/服务端）——先定位层再动刀。
2. **削峰与治理的区分**：生产暴涨用缓冲，消费变慢用治理——两类问题两类手段，混用必错。
3. **降级优先级的通用原则**：保核心、砍非核心——容灾演练、限流降级的通用顺序。

本层留下的新账：堆积治得了。但堆积过程中暴露了另一个事故源——**消息格式本身**：消费端升级发布、消息字段变更，为什么是堆积与崩溃的高发点？→ 逼出 Level 3。

### Level Ending

```
🔴 口诀：积压先分层，瓶颈再动刀。
```

## Level 3：Schema 演进——神话⑩ 的破解

一句话认知墙：消息格式不就是个 JSON 吗？改个字段怎么就会出事故？

### 前置知识关卡

- [ ] 知道消费端与生产端是不同发布节奏（mq-05/mq-06 的发布触发 rebalance）
- [ ] 知道消息是跨服务契约（mq-00 的解耦语义）

### Why——神话⑩ 的破解：格式变更的爆炸半径

**老陈**：消息是**跨服务的契约**——一个 Topic 的生产端和消费端是不同团队、不同发布节奏。格式变更不是"改个字段"，是"单方面修改多人共享的合同"：

```text
发布顺序事故（最常见的死法）：
  生产端先发布：开始发新格式消息（加了字段/改了类型）
  消费端还没升级：按旧格式反序列化 → 崩溃/丢字段
  → 一次发布，全量消费者排队崩溃 ★Schema 事故

为什么"消费端先升级"也不行：
  消费端按新格式解析 → 生产端还在发旧格式
  → 新字段解析为空 → 业务逻辑拿到 null → 静默错乱

结论：单向升级必然踩缝——"两边同时升级"又做不到
      → 必须靠"格式本身的兼容性"消除顺序依赖
```

> 📌 最容易被误解的一点：**"两边同时升级"不是解决方案**。生产端 3 个实例 + 消费端 5 个实例，滚动发布期间新旧版本共存是常态（还有 rebalance 打断，mq-06）——**"同时"在分布式发布里不存在，最可靠的做法是格式兼容性设计**：让旧代码读新消息不出错、新代码读旧消息不出错；做不到格式兼容时，只能走双 topic 双跑/版本路由这类显式迁移（见本层发布纪律）。

### What——兼容性矩阵与发布纪律

```text
兼容性矩阵（四个象限）：

新增字段（只加不改）      → 向后兼容 + 向前兼容 ✓
  旧消费者读新消息：忽略未知字段（宽松反序列化）
  新消费者读旧消息：字段缺失（用默认值兜底）

删除字段                  → 新消费者读旧消息：多余字段可忽略 ✓
                         → 旧消费者读新消息：字段没了 ✗ 不兼容

改字段类型/语义            → 双向都不兼容 ✗✗（必须双写双读过渡）

发布纪律：
  纪律一：只加不改（additive change）——唯一无痛路径
  纪律二：版本字段（schema version 随消息携带）——解析按版本分派
  纪律三：双写双读（新旧格式同时发、同时读）——破坏性变更的过渡
  纪律四：灰度（先升级小流量消费端，验证后全量）
```

### How——E 的 Schema 演进事故与正确姿势

```text
错误姿势（事故）：
  ① 生产端发布 v2（字段 status 从 string 改成 int）
  ② 消费端仍是 v1 解析 → 类型转换异常 → 消费崩溃
  ③ 消费崩溃 → 位点不提交 → 重试 → DLQ（mq-07）
  ④ 部分消息进 DLQ → 部分堆积 → 全链路受损

正确姿势（兼容演进）：
  ① 需求：status 需要数值语义
  ② 方案 A（无痛）：新增字段 status_code（int），保留 status
  ③ 方案 B（破坏性变更）：版本字段 + 双写双读 + 灰度
  ④ 消费端验证：旧消费端读新消息零异常（宽松解析 + 默认值）
  ⑤ 全量升级完成后再清理旧字段（延迟清理）
```

**徒弟**：双写双读的成本好高，能跳过吗？

**老陈**：能——只要破坏性变更永远不做。但业务演进必然遇到"字段语义改变"（比如 status 从字符串变成枚举码）。**双写双读是"破坏性变更的入场券"**：它把一次原子破坏拆成两步渐进（先并行、后切换、再清理）——成本高，但这是"必须改语义"时的唯一安全路径。**选"无痛路径"（加字段）还是买"入场券"（双写双读），取决于语义要不要变**——决策框架比成本更重要。

### Transfer——这个思想还能迁移到哪里

1. **契约的兼容性设计**：API 版本演进（加参数不加参数位置）、数据库 schema 迁移（加列 vs 改列）、配置中心格式——同一矩阵。
2. **发布顺序依赖是架构债**：凡是"必须先 A 后 B"的发布要求，都是事故点——设计目标是把顺序依赖消除。
3. **版本字段 + 宽松解析**：AVRO/Protobuf/JSON 的演进策略（Schema Registry 的兼容策略）是同一思想的落地工具。

本层留下的新账：格式稳了、治理齐了——但这一切都建立在"选对了产品"的前提上。四大 MQ 怎么选？选错了能迁吗？→ 逼出 Level 4。

### Level Ending

```
🔴 口诀：只加不改，版本先行，破坏变更双写过渡。
```

## Level 4：四大选型——模型定生死

一句话认知墙：Kafka、RocketMQ、RabbitMQ、Pulsar——选型看什么？

### 前置知识关卡

- [ ] 知道四大 MQ 开篇对比（mq-00）
- [ ] 知道"模型决定能力"（mq-01 队列 vs 日志）

### Why——选型的第一性：模型，不是功能列表

**老陈**：选型最容易踩的坑是"按功能列表比"——这个有事务消息、那个有延迟消息，比完就选。**功能可以补（插件、自研、生态），模型补不了**。mq-01 的两大模型分野是选型的第一性：

```text
日志模型（Kafka / Pulsar）：消费可回溯、吞吐高、水平扩展
  → 天然适合：数据管道、事件溯源、海量流式
队列模型（RabbitMQ）：路由灵活、低延迟、消费即删
  → 天然适合：企业集成、复杂路由、请求式消息
折中模型（RocketMQ）：队列 + 日志思想混合（CommitLog 存储 +
  队列视图）→ 业务消息语义（事务/延迟/重试）最完整
  → 天然适合：交易链路、订单削峰
```

### What——四大 MQ 选型矩阵

| 维度 | Kafka 3.5.x | RocketMQ 5.x | RabbitMQ 3.13.x | Pulsar 3.x |
| ---- | ---- | ---- | ---- | ---- |
| 模型 | 日志 | 队列+日志混合 | 队列 | 日志（存算分离） |
| 吞吐 | 极高 | 高 | 中 | 高 |
| 延迟 | 中高（批量/长轮询） | 中 | 低 | 中 |
| 顺序 | 分区内 | 队列内 | 单队列 | 分区内 |
| 事务消息 | 无（Kafka 事务≠业务事务，mq-07） | 半消息 ✓ | 无 | 2.7 技术预览引入、2.8 社区宣布可用（口径同 mq-00） |
| 延迟消息 | 无内置 | 固定级别 ✓ | 插件 | 延迟投递 ✓ |
| DLQ | 自建 | 内置 ✓ | DLX | 内置 |
| 路由能力 | 弱（topic 扁平） | 中 | 强（exchange 灵活） | 弱 |
| 生态 | 极强（Streams/Connect） | 中 | 强（插件丰富） | 中（偏小） |
| 运维复杂度 | 中（KRaft 简化） | 中 | 低 | 高（组件多） |
| 云原生 | 中 | 中 | 中 | 极强（多租户/分层存储） |

> 📌 最容易被误解的一点：**"Kafka 吞吐最高"是场景化的，不是绝对的**。Kafka 的高吞吐依赖批量与日志模型（mq-01/mq-02）——小消息、低延迟、复杂路由场景，Kafka 的优势反而变成劣势（批量摊不薄开销、吞吐与低延迟难兼得——linger.ms=0 时延迟可低但批量优势就没了、路由要自己拼）。**选型矩阵的每一格都要与业务场景对齐，不要用"别人的 benchmark"代替"自己的场景分析"**。

### How——E 的中转站选型推演

```text
场景：电商订单链路（订单事件、削峰、事务语义、多下游）

需求清单（按因果链推导，不按功能对比）：
  ① 业务消息（订单事件 E）→ 需要事务消息？双写一致（mq-07）
  ② 削峰填谷 → 高吞吐 + 堆积容忍
  ③ 多下游广播 → 消费组语义（mq-05）
  ④ 重试/DLQ → 内置或自建（mq-07）
  ⑤ 顺序 → 分区/队列内有序（mq-04）

推导：
  交易业务 + 事务语义 + 内置重试/DLQ → RocketMQ（折中模型）
  若订单事件全走流式（数仓/事件溯源）→ Kafka
  若企业集成/复杂路由 → RabbitMQ
  若云原生多租户 → Pulsar

迁移风险（选错后的代价）：
  模型差异：队列 vs 日志（消费语义、位点、可回溯性）——无法迁移
  语义差异：事务消息、延迟级别、DLQ 语义（mq-07）——无法迁移
  消费模型：推拉、rebalance、广播（mq-05/mq-06）——客户端重写
  运维体系：监控、治理、Schema（本篇 L1~L3）——重建
  → 迁移不是"换客户端"，是"换模型（无法迁移）+ 换语义（无法迁移）
    + 换客户端（重写）+ 换运维（重建）"——四层代价，缺一不可 ★四换
```

**徒弟**：Pulsar 看起来什么都有（事务演进、延迟投递、分层存储），为什么不是默认选择？

**老陈**：因为"什么都有的代价是组件多"——**BookKeeper + broker + 协调器三套体系（mq-08 已讲存算分离的架构代价）**，运维复杂度显著高于其他三家。**选型的本质是"用运维成本换能力"的权衡**：云原生多租户需求（多团队隔离、无限扩展、分层存储）值得付这个成本；单业务线用不上这些能力，就是白付。**"能力上限"与"运维成本"永远成对出现——选型评审必问的不是"它有什么"，而是"它的代价我付得起吗"**。

### Transfer——这个思想还能迁移到哪里

1. **模型 > 功能**：数据库选型（关系 vs 文档 vs 图）、缓存选型——先问模型匹配，再比功能。
2. **四换成本模型**：迁移评估（换模型+换语义+换客户端+换运维）适用于任何中间件迁移。
3. **能力与成本的配对**：架构评审的通用提问——"它的代价我付得起吗"。

本层留下的新账：选型定了。但生产系统的另一半是"变更"——参数调整、版本升级、配置治理。变更怎么管理才不酿成事故？→ 逼出 Level 5（变更治理 + 参数对照，收官）。

### Level Ending

```
🔴 口诀：模型定生死，代价定选型。
```

<a id="level-5"></a>

## Level 5：变更治理与参数对照

一句话认知墙：参数表有了，但"改参数"本身怎么治理？

### 前置知识关卡

- [ ] 能说出四大选型矩阵（答不出回 Level 4）
- [ ] 知道参数"控制机制 + 配错事故"的写法（mq-02~mq-08 各参数小节）

### Why——变更才是事故的第一来源

**老陈**：全系列前九篇讲完，所有的参数都是"配错就出事故"——但**参数本身不会自己变，是人改的**。生产事故统计里，"变更"是头号来源：改配置、升版本、调参数——一次无治理的变更 = 一次随机事故。**变更治理是生产体系的最后一环：把"改"变成"受控的改"**。

### What——参数变更治理五步

```text
第一步：评审（为什么要改）
  改的参数控制什么机制？（对应本系列哪篇哪个 Level）
  预期收益是什么？风险是什么？
  → 答不上"控制什么机制" = 还没资格改（参数手册式乱改的根源）
  → 变更不止参数：消息重放、位点回拨（mq-03/mq-07 的回放能力）
    也是变更操作——重放 = 对下游重复投递，必须走同一套
    评审/审批/影响面评估流程（mq-07 重放权限）

第二步：灰度（先小范围）
  低峰期 / 小流量 / 单实例验证
  → 观察指标：目标指标变化 + 副作用指标（错误率/延迟）

第三步：回滚预案（改坏了怎么办）
  参数可回滚吗？（配置回滚 vs 数据回滚）
  → 不可回滚的变更（如分区数，mq-06）必须演练到位

第四步：验收（改对了没有）
  目标指标 vs 基线对比
  → 无验收的变更 = 白改（可能改了没生效或改错）

第五步：记录（改了什么）
  变更记录 + 关联事故复盘
  → 没有记录 = 下次事故无法归因（mq-07 归因思想的运维版）
```

### What——三家参数对照速查（机制对照）

> 默认值随版本变化，以官方文档为准；本文按机制对照，不做数值罗列。

| 机制（对应 Level） | Kafka | RocketMQ | RabbitMQ |
| ---- | ---- | ---- | ---- |
| 生产确认（mq-03） | acks=0/1/all + enable.idempotence | 同步/异步刷盘 + 复制档位 | publisher confirms |
| 存储与保留（mq-02） | retention.ms/bytes + segment | 保留时长 + 整文件回收（mq-02） | 队列 TTL/消息 TTL（经典队列 3.12 起默认惰性落盘，mq-02） |
| 顺序与幂等（mq-04） | max.in.flight + idempotence | 顺序消费模式 + 幂等由业务做 | 单队列 FIFO + 业务幂等 |
| 消费模型（mq-05） | fetch 批量 + 长轮询 + 位点 | Push 长轮询 + 集群/广播 | prefetch + 推式 |
| 再平衡（mq-06） | 会话/轮询超时 + 分配策略 | 分配算法 + 扫描间隔 | 无（竞争消费） |
| 重试/死信（mq-07） | 自建（不提交位点） | 重试队列 + DLQ | nack/requeue + DLX |
| 副本（mq-08） | 副本因子 + min.insync + ISR | 主从 + DLedger/controller | quorum queue 多数派 |

**徒弟**：对照表里 Kafka 那列怎么很多"自建"？

**老陈**：这是产品哲学的差异（mq-07 已点过）：**Kafka 提供"少而精的基础能力 + 强生态"，重试/DLQ/Schema 这类治理能力交给上层自建；RocketMQ 提供"开箱即用的业务语义"**。对照速查的意义不是"哪家功能全"，而是**"机制边界在哪、我要补什么"**——Kafka 团队要自建 DLQ 治理（mq-07 三件套），RocketMQ 团队要自建 Schema 治理（本篇 L3）。**每个产品都有"另一半"要自己补，选型时把这半的工程量算进去**。

### How——E 的变更治理全流程（收官推演）

```text
场景：调整库存组的 max.poll.records（mq-05 参数）

① 评审：该参数控制单批拉取粒度 → 影响处理时长与轮询超时
   （对应 mq-05 L3/L6、mq-06 L3 的踢人风险）
   预期：降低单批处理时长，减少被踢概率
② 灰度：先调 1 个实例 → 观察处理时长/被踢次数/错误率
③ 回滚预案：参数可配置回滚（无数据风险）
④ 验收：处理时长 p99 下降 ✓、被踢次数归零 ✓、错误率无变化 ✓
⑤ 记录：变更单归档，关联 mq-06 事故复盘

收官闭环：这个参数从"机制"到"事故"到"治理"的全链路
  = mq-05（机制）→ mq-06（事故）→ 本篇（治理）
  = 全系列因果链在最后一个变更上合龙。
```

<a id="pitfalls"></a>

# ⚠️ 坑与细节

## 坑 1：只接集群层告警

错误理解：集群健康监控接好就安全了。

原因：集群指标是"果"，业务指标是"因"——果告警只能收尸。

比喻后果：只盯着车站大屏，货堆在月台没人知道。

线上现象：消费组风暴 3 小时后磁盘才告警（mq-06 事故链）。

修正：告警边界下沉到业务层（lag/DLQ/延迟），因指标先行。

## 坑 2：堆积就加消费者（神话⑦ 的运维版）

错误理解：lag 涨了加机器总没错。

原因：瓶颈四层未必在并行度层（mq-06 L4）。

比喻后果：瓶颈在司机（下游），却不停雇柜台员。

线上现象：加 20 实例 lag 不降，还触发 rebalance 风暴。

修正：先定位瓶颈层（并行度/单消费者/下游/热点），再选手段。

## 坑 3：生产端先发布新格式（神话⑩ 的经典死法）

错误理解：格式改好了，发出去就行。

原因：消费端旧解析器读新格式 → 崩溃/丢字段（发布顺序事故）。

比喻后果：新单据发出去了，收件人还按旧格式填表。

线上现象：一次发布，全量消费者排队崩溃，消息进 DLQ。

修正：只加不改 + 版本字段 + 消费端灰度先行。

## 坑 4：删字段省事

错误理解：没用的字段删掉，干净。

原因：删除字段 = 旧消费者读新消息缺字段（不兼容）。

比喻后果：单据上划掉一栏，老收件人看不懂了。

线上现象：消费端升级滞后，缺字段解析崩溃。

修正：删除 = 破坏性变更，必须双写双读过渡 + 延迟清理。

## 坑 5：按功能列表选型

错误理解：谁功能多选谁。

原因：功能可补，模型补不了（mq-01 两大模型分野）。

比喻后果：看谁家货车多就选谁，没看路况（场景）。

线上现象：选错模型，迁移成本=换模型+换语义+换客户端+换运维（四换）。

修正：先模型匹配，再功能对比，最后算运维代价。

## 坑 6：无视产品"另一半"

错误理解：选了产品，能力就是产品的。

原因：每个产品都有要自己补的治理（Kafka 自建 DLQ，RocketMQ 自建 Schema）。

比喻后果：买了车，以为加油站也是车自带的。

线上现象：Kafka 场景没有 DLQ 治理，坏件静默丢失（mq-07 教训）。

修正：选型时把"自建部分"的工程量计入总成本。

## 坑 7：参数随手改（无评审）

错误理解：配置改一下，很简单。

原因：每个参数控制一个机制（本系列前九篇），配错即事故。

比喻后果：调度规则随手改，全站排班错乱。

线上现象：改 max.poll.records 过大 → 单批超时 → 被踢 → 风暴。

修正：变更五步（评审/灰度/回滚/验收/记录），答不上机制不配改。

## 坑 8：迁移当"换客户端"

错误理解：换 MQ 就是换 SDK，改改代码就行。

原因：模型、语义、客户端、运维四套体系都要换（mq-01 讲模型分野，mq-04~mq-08 讲语义与客户端）。

比喻后果：换了车队，发现路、调度、单据全要换。

线上现象：迁移后消费语义错乱、位点丢失、事务语义缺失。

修正：迁移前做"四换"评估 + 双跑验证 + 对账核对。

| T0 | 监控层 | 三层指标采集 | 业务层先行 | 只接集群层 |
| T1 | 告警 | lag/DLQ/延迟触发 | 因指标先行 | 告警疲劳 |
| T2 | 治理 | 瓶颈四层定位 | 分层定位 | 加错层 |

<a id="errata"></a>

# 📚 版本勘误表

| 错误说法 | 准确说法 |
| ---- | ---- |
| "Broker 集群健康 = 业务可靠" | 集群层管设施、业务层管流动；设施正常 ≠ 货在流动 |
| "堆积就加消费者" | 瓶颈四层定位后选手段，加消费者只在并行度瓶颈时有用 |
| "两边同时升级就行" | 滚动发布没有"同时"；唯一可靠的是格式兼容性设计 |
| "删字段没风险" | 删除 = 破坏性变更（旧消费者缺字段），需双写双读过渡 |
| "Kafka 吞吐最高所以最合适" | 高吞吐依赖批量与日志模型，低延迟/路由场景反而劣势 |
| "功能多 = 选它" | 模型 > 功能；能力与运维代价成对出现 |
| "换 MQ 就是换客户端" | 换模型 + 换语义 + 换客户端 + 换运维（四换） |
| "参数想改就改" | 参数控制机制，配错即事故；变更五步治理 |
| 坦白：我以前也讲错过"集群监控全绿就没问题" | 最危险的事故全发生在集群层全绿时（风暴/毒消息/下游挂） |
| 坦白：我以前也讲错过"选型就是比功能" | 模型匹配是第一性，功能列表是第二性，运维代价是最后一性 |

<a id="decisions"></a>

# 🏆 生产决策卡

## Decision Card 1：MQ 监控体系设计

### 场景

新 MQ 平台上线，设计监控告警体系。

### 判断

三层指标：集群层（设施）+ 消息层（流转）+ 业务层（效果）；业务层告警先行；每层各自死亡形态对应告警。

### Mechanism → Decision

| 机制 | 工程决策 |
| -- | ---- |
| 集群层 | Broker 存活/资源/副本同步（mq-08 演练配套） |
| 消息层 | 生产/消费速率、lag、端到端延迟 |
| 业务层 | DLQ 积压、重试、生产错误率、对账差异（mq-03/mq-07） |

### 禁止决策

- 只接集群层（果指标告警 = 收尸）
- 告警无分级（全量告警 = 告警疲劳 = 无人响应）

### 验收指标

- 故障注入演练：lag 告警先于磁盘告警（因先于果）
- 告警响应时长达标，误报率低于阈值

---

## Decision Card 2：订单链路选型评审（收官）

### 场景

电商订单事件链路选型，多下游、事务语义、削峰需求。

### 判断

RocketMQ（交易业务 + 事务/延迟/DLQ 语义最完整）；若事件全走流式数仓 → Kafka；云原生多租户 → Pulsar；复杂路由企业集成 → RabbitMQ。

### Mechanism → Decision

| 机制 | 工程决策 |
| -- | ---- |
| 模型匹配 | 业务消息语义（mq-00/mq-01 模型分野） |
| 事务语义 | 半消息（mq-07） |
| 消费模型 | 集群/广播 + 长轮询（mq-05） |
| 自建部分 | Schema 治理（本篇 L3） |

### 禁止决策

- 按"听说吞吐高"选型（场景不对齐）
- 迁移未做"四换"评估（模型/语义/客户端/运维）

### 验收指标

- 故障演练：消费组风暴、毒消息、主从切换三类演练通过
- 对账 24h 零差异（mq-03）
- 运维成本核算（自建部分工程量）纳入立项评审

---

## Decision Card 3：参数变更治理流程落地

### 场景

团队经常改消费端参数，要求变更可追溯、可回滚。

### 判断

变更五步（评审/灰度/回滚/验收/记录）+ 参数机制对照表（本系列各篇参数小节）+ 不可回滚变更（分区数）专项演练。

### Mechanism → Decision

| 机制 | 工程决策 |
| -- | ---- |
| 评审 | 答"控制什么机制"（对应文章与 Level） |
| 灰度 | 低峰/小流量/单实例 |
| 回滚 | 配置回滚优先；数据型变更专项预案 |
| 验收 | 目标指标 vs 基线 |
| 记录 | 变更单 + 事故归因（mq-07 归因思想） |

### 禁止决策

- 无评审直接改（参数 = 机制开关）
- 不可回滚变更（分区数）无演练

### 验收指标

- 变更后 24h 指标回归基线
- 变更记录完整率 100%（事故可归因）

<a id="cross-language"></a>

# 🌍 跨语言视角

## 同一个问题：生产治理

| 语言 | 监控与治理形态 |
| -- | ---- |
| Java | Kafka/RocketMQ 原生指标（lag/速率）+ 管理 API |
| Go | prometheus 客户端 + 消费组监控 exporter |
| Rust | rdkafka 统计回调 + 外部监控 |
| Python | confluent-kafka 统计 + 运维脚本 |

## 跨语言仍成立的判断力

1. **监控是指标问题不是语言问题**：lag/延迟/速率在任何语言栈都有等价指标，治理框架通用。
2. **Schema 兼容是契约问题**：Protobuf/AVRO/JSON 的演进策略与语言无关（宽松解析 + 版本字段）。
