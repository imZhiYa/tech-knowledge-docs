# 📐 高性能网络编程原理：从 I/O、BIO、NIO、AIO 到 Reactor 的状态所有权

> 这不是 BIO、NIO、`epoll`、Netty 的知识点清单。
>
> 全文只跟踪一个支付查询请求 **R**：它从客户端发出，经过内核、解码、业务、写回，必要时等待业务确认，最后在正常完成、超时或停机中收口。我们只追问：**R 停住时谁替它等待；等待被转交后，谁仍拥有 R 的状态？**
>
> **全文唯一比喻**是一座港口集装箱中转站。它不是技术结论后的装饰，而是每次推导前的提问工具：泊位状态牌亮了，货真的完整了吗？货轮失联了，泊位谁来回收？货过了出港闸门，对方真的签收了吗？

**🏷️ 关键词**：I/O · BIO · NIO · AIO · 多路复用 · `select` / `poll` / `epoll` · `kqueue` · Reactor · readiness · completion · 背压 · TCP 流控 · 半开连接 · ack · drain

**🧵 主线进度条**：

```text
【① 已合】R 在哪里等待
→ 【② 已合】BIO：线程为什么会陪等
→ 【③ 已合】NIO：不陪等为何会空转
→ 【④ 已合】多路复用 / AIO：内核能交付什么

→ 【⑦ 已合】模型选择与生产收口
→ 【⑧-Redis / Reactor / Dubbo / Netty 专题】
```

## 🗺️ 先看全图：这些名词不是同一层的替代品

先有全局认知，再进入细节。I/O、BIO、NIO、AIO、Reactor 并不在同一维度回答问题：

```text
                           R 的一次网络生命周期

I/O：        字节如何跨越应用与内核边界？
              │
BIO：        调用者等待；顺序代码换来线程陪等
              │
NIO：        调用者不等待；但“该检查谁”仍未解决
              │
多路复用：    内核集中报告 readiness，解决“谁值得尝试”
              │
AIO：        以 completion 交付操作结果，改变通知语义
              │
Reactor：    无论 readiness 还是 completion，应用仍须拥有 R 的状态
              │
生产治理：    背压、ack、drain 为状态规定上限、终点和死亡方式
```

| 锚点 | 这一段只解决一个问题 | 后一段为何被逼出来 |
|---|---|---|
| [I/O：R 在哪里等](#io) | 字节、帧、发送、业务确认与存活分别是什么等待？ | 先辨认等待，才谈由谁承担 |
| [BIO：谁在陪等](#bio) | 为什么一个连接一个线程会被沉默连接拖垮？ | 不让线程等后，还要找到有活的连接 |
| [NIO / 多路复用：谁找活](#nio) | 非阻塞为何空转；就绪究竟交付什么？ | 内核只给资格，不能理解 R |
| [AIO：completion 改变什么](#aio) | 完成通知能否替应用保存协议和业务状态？ | 不能，状态 owner 仍不可逃避 |
| [Reactor：谁拥有状态](#reactor) | 谁能串行改连接、帧、写队列、deadline、ack？ | 拥有状态后，必须为它设上限与终点 |
| [生产收口：状态如何死亡](#production) | 慢客户端、半开、ack、drain 怎样不变成全局事故？ | 最终翻译成模型选择与验收指标 |

> 📌 **全篇中心论点**：高性能不是让等待消失，而是不断转移“谁承担等待”；每转移一次，应用就必须更明确地接管“等待之后仍然存在的状态”。

| 项目 | 本文边界 | 不能据此断言 |
|---|---|---|
| Java 基线 | OpenJDK 21 LTS；与 JDK 8 对比 `Selector` 的公开核心语义 | 不能把某个 JDK 私有类、字段或 provider 当作规范 |
| OS 基线 | Linux 常见 `epoll` 用于解释 readiness；macOS / BSD 常见 `kqueue`；Windows 路径不同 | `Selector` 不承诺底层一定是 `epoll` |
| AIO 范围 | `AsynchronousSocketChannel` 用于辨析 completion 语义；不展开 provider 调优 | 不能由 Java completion API 反推某 OS 有相同原生语义 |
| TLS / socket buffer | TLS、`SO_SNDBUF` / `SO_RCVBUF`、自动调优、代理均会影响实际曲线 | 不给出脱离环境的吞吐、连接数或延迟数字 |
| 教学简化 | R 被描述成一个请求；真实 TCP 是无消息边界的字节流 | 不可把一次 `read()` 或一次 `write()` 等同完整业务收发 |
| 证据原则 | API、JDK 源码、man page、内核文档为事实入口；链接在文末 | 内核参数、容器限制、网卡、TLS 和负载必须现场实测 |

> 📌 JDK 8 到 JDK 21，`Selector` 的公开核心语义——注册 channel、选择就绪状态、取得 selected-key set——没有被重定义。实现组织可变；虚拟线程改变阻塞等待的承载成本，不会消除慢客户端、无界队列、下游配额和背压。

```text
外海货轮 ──> [入港闸门] ──> [泊位状态牌] ──> [调度台] ──> [作业区] ──> [出港闸门] ──TCP 响应──> 客户端
   R 的字节       accept              selector           reactor        handler          write
                         ↑                    │                               │
                         └──── 有货/可通行 ───┴── 不是“货已处理完” ──────────┘
                                                                                           │
              （可选：客户端收到并按协议处理响应后；时点、超时和是否存在由协议决定）
                                                                                           └- - - - - > [回执单] ──> R: ACKED
```

| 比喻元素 | 技术概念 | 它只负责的一件事 |
|---|---|---|
| 外海货轮 | 对端 TCP 连接与字节 | 把字节送入本机协议栈 |
| 入港闸门 | listen socket / `accept()` | 接纳完成握手、等待应用接收的连接 |
| 泊位状态牌 | readiness / selected key | 报告“现在值得尝试 I/O” |
| 调度台 | `Selector` + event loop | 集中等待并领取就绪事件 |
| 作业区 | decoder、handler、业务执行器 | 将字节恢复为 R 并生成结果 |
| 出港闸门 | 发送缓冲与写事件 | 暂存可发送字节；满时向上游反压 |
| 回执单 | 应用 ack / correlation id 确认 | 表示对端按协议确认；不是 TCP ACK，也不是 `write()` 返回 |

<a id="io"></a>
# 第一幕：I/O——R 在哪里等？

徒弟看到超时，常说：“网络慢。”

老陈先问：“R 是等货轮靠泊、等出港闸门腾位、等作业区、等回执单，还是一艘失联货轮仍占着泊位？”

这不是修辞。五种等待都可叫慢，但资源归属不同：

| R 等待的对象 | 港口问题 | 典型技术边界 |
|---|---|---|
| 入站字节 | 货轮尚未靠泊 / 货未卸完 | 接收路径、TCP 重传、TLS 解密、增量 decoder |
| 出站空间 | 出港闸门暂时满 | 部分写、outbound queue、`OP_WRITE`、慢客户端 |
| CPU / 下游资源 | 作业区排队 | event-loop lag、业务队列、DB / RPC 并发与 deadline |
| 业务 ack | 回执单尚未回来 | correlation id、ack timeout、幂等与结果查询 |
| 存活判定 | 货轮失联仍占泊位 | keepalive、应用心跳、idle timeout、半开清理 |

## 字节到 R：I/O 的第一个事实

```text
客户端字节 ──TCP──> 内核接收路径 ── read ──> 用户 ByteBuffer ── decode ──> R
业务结果   ── encode ──> 用户 ByteBuffer ── write ──> 内核发送路径 ──TCP──> 客户端
```

TCP 只给有序字节流。泊位状态牌亮起，不表示 R 完整；`read()` 得到字节，也不表示一条业务消息完成。应用必须维护 framing：长度字段、分隔符、自描述编码均可，但必须能跨多次读取累计状态。

TLS 不会给消息边界：

```text
TCP 字节流 <──> TLS record 字节流 <──> 应用帧 <──> R
```

TLS record 可以装半个应用帧，也可装多个帧；一帧也能跨 record。`SSLEngine.unwrap()` 后仍需 decoder。这里先留下一个洞：既然内核连 R 是否完整都不知道，谁能保存 R 的半包、超时与关联状态？第三、四幕回答它。

## 发送路径也会制造尾延迟

短请求不意味着延迟只由 handler 决定。Nagle 会在存在未确认数据时倾向合并小段；接收端可能 delayed ACK；应用多次小 `write()`、TLS record 与代理缓冲也会改变时序。

港口不会每拿到一张小回执就独立放一艘船出港。`TCP_NODELAY` 关闭 Nagle，可能降低某些小报文交互延迟，也可能增加 segment 和包处理成本。不存在跨平台固定的“40 ms Nagle 延迟”；必须以抓包、TCP 指标和端到端 P99/P999 判断。

> 🔴 **不变量**：先问 R 等谁，才知道该保护哪种资源。

<a id="bio"></a>
# 第二幕：BIO——线程为什么会陪等？

一连接一线程并不愚蠢。它把流程写成顺序代码：读到 R、处理、写回。问题在于同一位工作人员同时承担了所有等待：

```text
C 无字节：worker 阻塞在 read
R 等 DB：worker 停在同一调用链
客户端慢：worker 阻塞在 write
对端失联：worker 不知道该等到何时
```

BIO 的账不是“阻塞”二字，而是**用可调度执行单元一对一地陪沉默连接**。连接多数时间不运货时，线程的栈、调度、上下文切换与真正的业务 CPU 发生竞争。固定线程池只限制 worker 数；若前面允许无限连接、后面允许无界任务队列，风险只是换了位置。

## 入港闸门先于线程池拥堵

`listen(backlog)` 不是应用可处理并发数。以 Linux 为例，建连有半连接（SYN）路径，也有已完成握手、等待应用 `accept()` 的队列；上限还受内核参数、syncookies、版本、容器约束和 accept 速度影响。

所以“worker 还没满”并不表示入口健康。应一起看：accept 速率、连接建立失败、`TcpExtListenOverflows` / `TcpExtListenDrops`（目标系统核验字段）、应用连接准入与拒绝率。

```text
listen(backlog) 参数
≠ net.core.somaxconn 对 backlog 的内核上限
≠ 应用 in-flight 上限
≠ 业务拒绝率
```

## 最安静的连接，可能已经死亡

货轮不送货、也不发离港通知，可能空闲，也可能失联。对端崩溃、断网或 NAT 状态丢失时，本地未必马上收到 FIN/RST；阻塞 `read()` 可以长期等待。

TCP keepalive、应用心跳、idle timeout 分别有不同语义。keepalive 的默认节奏不应直接当成业务 SLA；应用心跳更贴近协议，却必须定义超时、关闭与重试。它们不是吞吐优化，而是回收“失联仍占泊位”的状态。

BIO 因而留下下一笔账：不让线程陪每个泊位，谁来告诉应用哪些泊位值得看？

> 🔴 **不变量**：阻塞不必然错；让昂贵线程无界陪等才错。

<a id="nio"></a>
# 第三幕：NIO 与多路复用——内核找活，但不能理解 R

把 channel 改为 non-blocking，`read()` 没有字节就返回。线程不再睡在 C 上，但徒弟很容易写出新灾难：

```text
for every C in connections:
    n = C.read(buffer)
    if n > 0: decode
    if n == 0: continue
```

这不是没有等待，而是让 CPU 替应用轮询所有泊位。`read()==0` 不等于 EOF；`-1` 才是流结束信号。扫描连接集合还会带来并发访问、遍历和空转账。

多路复用把“关注谁、何时等待、谁现在值得尝试”交给内核与 selector provider：

```text
C1 ─┐ register(interestOps) ┌──────────┐ selected keys ┌────────────┐
C2 ─┼──────────────────────>│ Selector │──────────────>│ event loop │
C3 ─┘                        └──────────┘               └────────────┘

interest：应用希望关心什么
ready：本轮观察到什么可以尝试
```

`select` / `poll` / `epoll` 解决的都是关注集合遍历账：`select`、`poll` 每轮仍要提交和检查较大的关注集合；Linux `epoll` 将关注关系持久注册，更适合大量连接、少量活跃的画像。不要把它神化为“永远 O(1)”：返回事件数、内核维护、唤醒、缓存和 handler 时长仍有成本。

macOS / BSD 的 `kqueue` 也在回答同一问题：登记关注，再从事件队列取变化；常以 `EVFILT_READ` / `EVFILT_WRITE` 表达读写关注。API 与实现不同，架构问题相同。

## 就绪不是完成：多路复用的边界

```text
READ-ready  ≠ 完整 R
WRITE-ready ≠ 全部响应可写完
本地 write ≠ 客户端收到
客户端收到 ≠ 客户端按协议确认
```

内核避免的是应用扫描全部连接，**没有替应用处理返回事件**。每个 `epoll_wait` 事件或 selected key 仍要逐项消费；LT 下条件持续成立时同一 fd 可反复就绪。领到 C 后，应用还要处理部分读、EOF、错误、帧边界和处理预算。

Java `Selector.select()` 返回 `int`，即本轮 ready-operation 新增或更新的 key 数；key 集合通过 `selectedKeys()` 取得并消费。返回 0 不代表 selected-key set 一定为空。跨线程提交注册/写意图时，应投递给 C 所属 loop，并以 `wakeup()` 让等待中的 owner 返回；`wakeup()` 不是直接写网络的魔法。

## LT / ET：通知方式改变消费义务

Linux `epoll` 的 LT 下，只要条件持续满足，后续等待通常仍有机会报告；ET 下，状态从不满足到满足时才通知。ET 收到 read 通知后通常要读到 `EAGAIN` / `EWOULDBLOCK`，否则已有字节可能没有新边沿提醒。

标准 Java `Selector` 不提供可移植的 `EPOLLET` 开关。使用 native transport 或框架特定 ET 能力时，必须用压测和故障注入证明读空、预算和重新调度正确；不要把“减少通知”当成无条件性能结论。

多路复用把等待从线程转交给内核，却留下最关键的空洞：**内核给资格，谁保存资格之后 R 的状态？**

> 🔴 **不变量**：内核报资格，应用保状态。

<a id="aio"></a>
## AIO：completion 改变通知语义，不会接管业务状态

Java 还提供 `AsynchronousSocketChannel` / `AsynchronousServerSocketChannel`。其 read/write 可通过 `CompletionHandler` 或 `Future` 交付操作完成；这是 completion 风格，而不是 `Selector` 的 ready key 风格。

不同 provider / OS 的实现路径不同：Windows 常可借助 IOCP；OpenJDK Linux 实现可用 `epoll` 驱动内部 provider 来兑现 completion 回调。公开 API 的 completion 语义，不等于所有 OS 有相同原生原语。

更重要的是，completion 没有替应用回答：

```text
完成读到的一段字节是否已组成完整 R？
超时后的 buffer / channel 还能否安全继续？
哪个业务结果属于哪个 R？
谁等待业务 ack？
谁在取消、关闭、drain 时回收状态？
```

所以 BIO、NIO、AIO 不是“性能等级”。它们改变等待的写法或通知语义，但都不能代替应用拥有协议和业务状态。

<a id="reactor"></a>
# 第四幕：Reactor——不是线程模型，而是状态所有权制度

Reactor 并非一个固定线程数的类图。它从第三幕的空洞中被逼出：R 的半包、解码、业务交接、未写完 buffer、timeout、ack 都不属于内核；若多个线程随意修改它们，顺序也不再可推理。

一条 C 的可变状态至少包括：

```text
累计字节与 decoder 进度
R 是否完整、是否已投递、对应 deadline
业务结果是否回来
outbound queue 的剩余 buffer
OP_WRITE 是否被关注
WAITING_ACK 的 correlation state
closing / draining / cancelled 状态
```

因此 Reactor 的第一条规则不是“单线程更快”，而是：

> **每份连接 I/O 状态，在同一时刻有清晰的串行 owner。**

```text
READ-ready
  → C 所属 event loop 读取、累计、解码
  → 完整 R 穿过有界业务边界
  → 业务完成后只提交 task 回原 event loop
  → 原 loop 修改 outbound queue 与 interestOps
  → WRITE-ready 时继续写剩余字节
```

业务线程直接改 key、buffer 或 interestOps，看似少一次排队，实则破坏 owner：它会与 loop 竞争关闭、取消、写队列和兴趣集。跨 owner 只能消息传递，才能让异常、重试、超时与关闭有唯一解释。

## R 的终态不是一个笼统 DONE

```text
READING_FRAME → DISPATCHED → RESPONSE_QUEUED → WRITING → LOCAL_WRITE_DONE
                                                           ├─ 无业务 ack：COMPLETED_BY_CONTRACT
                                                           └─ 有业务 ack：WAITING_ACK → ACKED | ACK_TIMEOUT / FAILED
```

`LOCAL_WRITE_DONE` 至多表示应用已将响应交给本地发送路径。它不是 TCP ACK，不是客户端读取，也不是业务确认。若协议没有业务 ack，必须显式说明何时按契约完成；若有 ack，则 correlation state、deadline、超时后的可查询结果与幂等都属于 R 的状态机。

> 🔴 **不变量**：事件归 owner，跨 owner 只传意图。

<a id="production"></a>
# 第五幕：背压、ack、drain——状态如何增长，又如何死亡

Reactor 让状态有主，不代表状态有界。真正的生产故障往往发生在业务很快、客户端很慢时：业务不断生成响应，出港闸门却写不出去。

```text
业务响应 → 每连接有界 outbound queue → non-blocking write → 内核发送路径 → 客户端
                         │
                         ├─ 低水位：可恢复读取
                         ├─ 高水位：暂停读取 / 限流 / 降级 / 协议化拒绝
                         └─ 超时或超预算：关闭或转异步交付
```

一次 non-blocking `write()` 可部分写、可返回 0。必须保留 ByteBuffer 剩余区间；只在有残留数据时订阅 `OP_WRITE`，清空后取消它。常驻 `OP_WRITE` 在健康 socket 上可能持续就绪，让 loop 空转。

## 暂停 `OP_READ` 是压力反馈，不是业务拒绝

应用移除 `OP_READ` 或暂不 drain：数据仍可进入接收路径；应用不取走，接收缓冲逐步占用；TCP receive window 可能收窄；对端发送最终受到流控。

这是港口不再从泊位卸货向货轮传递压力的路径，但不是完整过载协议：已在途字节、自动调优、代理、TLS、对端队列都会改变时机，TCP 也不会替你告知“业务请求已拒绝”。应用仍须定义水位、拒绝、deadline 和重试。

## drain：停机才审计你是否真的拥有状态

```text
RUNNING
  ↓
DRAINING：关闭入港闸门（停止 accept），明确新 R 的拒绝边界
  ├─ 半包 R：不误进入业务
  ├─ 已投递 R：完成到 deadline 或取消
  ├─ outbound queue：尝试 flush 到 deadline
  ├─ WAITING_ACK：记录超时、保留查询状态或按协议失败
  ↓
CLOSED：取消 key、关闭 C、释放 buffer 与任务引用
```

港口关闸不等于已离港的船被对方签收。已执行但未送达响应的 R 可能被客户端重试；因此 request / correlation id、幂等键、可查询结果不是支付系统的装饰，而是网络不确定性下状态所有权的最后一段。

> 🔴 **不变量**：背压限制状态增长；drain 定义状态死亡。

<a id="decisions"></a>
# 模型选择与生产决策：复杂度必须由等待画像证明

## 决策卡 1：大量长连接、多数空闲

| 场景判断 | 决策 |
|---|---|
| 连接多、活跃比例低；I/O 等待是主要成本；协议/推送要求连接状态 | 选择 selector / 成熟 Reactor 框架；event loop 只做短、可预测 I/O 工作 |
| 机制映射 | 多路复用避免用户态扫描全部 C；owner 保证连接状态可推理 |
| 不能做 | 在 event loop 执行 DB/RPC；无限连接、无限帧、无限业务队列 |
| 验收 | `event_loop_lag`、`selected_key_backlog`、`active_connections`、`open_fds`、P99、帧解码错误 |

## 决策卡 2：网络层之后有慢 DB / RPC

| 场景判断 | 决策 |
|---|---|
| R 的业务执行不可预测、依赖下游 | I/O loop 与有界业务边界隔离；结果投回连接 owner |
| 机制映射 | loop 共享于很多 C；长业务会把局部下游慢放大为整组连接尾延迟 |
| 不能做 | 默认无界 executor；业务线程直接改 C 的 key / buffer |
| 验收 | `business_queue_depth`、`business_queue_wait_seconds`、`executor_rejected_total`、`downstream_timeout_total`、`event_loop_lag` |

## 决策卡 3：大响应、推送、慢消费者

| 场景判断 | 决策 |
|---|---|
| 响应产生速度可能高于客户端消费速度 | 配置每连接 / 每 loop / 全局 outbound 字节预算、水位线、超时和服务分级 |
| 机制映射 | 部分写与 `OP_WRITE` 维护残留数据；高水位将压力向读取、准入和业务传播 |
| 选做边界 | `SO_SNDBUF` / `SO_RCVBUF`、`FileChannel.transferTo` / `sendfile` 仅在目标 OS、TLS、容器限制与压测下评估；不替代 framing、背压或 ack |
| 不能做 | 扩 JVM 堆或无界队列来掩盖慢客户端；把本地写出宣称为对端消费 |
| 验收 | `outbound_queue_bytes`、`write_zero_total`、高水位命中、慢客户端关闭、GC、直接内存、响应 P99 |

## 决策卡 4：短连接、低并发或虚拟线程阻塞模型

| 场景判断 | 决策 |
|---|---|
| 连接/等待比例低，瓶颈主要在 DB/RPC；团队优先顺序代码 | 可采用受控 BIO 或 JDK 21 virtual-thread-per-task；仍需下游和连接边界 |
| 机制映射 | 虚拟线程降低许多阻塞式等待的承载成本，不改变 TCP、内存、下游并发与慢客户端事实 |
| 不能做 | 因为“不上 Reactor”就取消 timeout、半开清理、响应大小、FD、下游 bulkhead |
| 验收 | `requests_inflight`、`request_latency_p99`、`request_timeout_total`、`downstream_pool_wait`、`open_fds`、半开超时 |

<a id="self-test"></a>
## 🧪 合书自测：从 T0 到 T8 跟 R 走一遍

```text
T0 建连准入 → T1 字节抵达 → T2 READ-ready → T3 累积解码
→ T4 有界投递业务 → T5 下游执行 → T6 部分写 → T7 WRITE-ready
→ T8 LOCAL_WRITE_DONE → （可选）WAITING_ACK → ACKED / timeout / failed
```

| 自测题 | 必须答出的不变量 |
|---|---|
| 为什么 `select()` 返回不能代表 R 已可执行业务？ | 就绪只是 I/O 尝试资格；帧完整性由应用 decoder 判断 |
| `Selector.select()` 返回什么，key 从哪里取得？ | 返回本轮 ready 状态新增/更新的 key 数；通过 `selectedKeys()` 取得并消费集合 |
| TLS record 完整能否代表完整应用帧？ | 不能。TLS record 与 framing 无一一对应，解密后仍须累计 decoder |
| 为什么不能常驻 `OP_WRITE`？ | 可写常态成立会令 loop 空转；仅有残留数据时订阅 |
| `epoll_wait` 返回后，内核是否已处理事件？ | 否。应用仍须逐项消费并处理半包、EOF、错误与预算；LT 可重复就绪 |
| 小报文尖峰是否必是固定 40 ms Nagle 问题？ | 否。Nagle、delayed ACK、写拆分、TLS、代理均可能参与，须抓包实测 |
| backlog 调大是否等于连接不会失败？ | 否。SYN/accept 路径、内核参数、accept 速率、准入策略必须一起看 |
| 暂停 `OP_READ` 是否就是拒绝业务请求？ | 否。它可能经 receive window 反馈字节压力；业务拒绝仍由协议定义 |
| 本地 `write()` 后能否标业务 DONE？ | 至多是 LOCAL_WRITE_DONE；若协议有 ack，仍要等待 ACKED 或 timeout / failed |
| drain 时半包、已执行未送达、WAITING_ACK 是否同一类状态？ | 否。必须分别定义是否执行业务、是否取消、是否保留结果、如何支持幂等重试 |

<a id="pitfalls"></a>
## ⚠️ 坑与细节：先看错误代码，再看它吞掉了哪个状态

### 1. 把一次 read 当作一个 R

```java
int n = ch.read(buf);
handle(decode(buf));
```

- **错因**：TCP 没有应用消息边界；`n > 0` 不等于一帧完整。
- **港口后果**：半箱货被当成完整订单送进作业区。
- **线上现象**：偶发反序列化失败、字段错位、协议失步。
- **修正**：ConnectionState 保留累计 buffer；仅 decoder 产出完整帧后才投递 R。

### 2. 将 `read() == 0` 当作连接死亡

```java
if (ch.read(buf) <= 0) {
    ch.close();
}
```

- **错因**：non-blocking `read()` 的 0 表示此刻未读到字节（还需结合 buffer 状态），不是 EOF；`-1` 才是流结束。
- **港口后果**：泊位暂时没货就永久封港。
- **线上现象**：分片发送或低峰时随机断连。
- **修正**：0 保持状态、等待下一次 READ-ready；EOF / 异常进入幂等关闭契约。

### 3. 常驻 `OP_WRITE`

```java
key.interestOps(key.interestOps() | SelectionKey.OP_WRITE);
```

- **错因**：健康 socket 常常可写；长期订阅会让 selector 持续返回。
- **港口后果**：调度台不停报告空着的出港闸门。
- **线上现象**：空闲连接下 event loop CPU 异常高。
- **修正**：只在 outbound 有残留时添加 `OP_WRITE`；队列清空立即移除。

### 4. 假设一次 write 写完

```java
ch.write(response);
response.release();
```

- **错因**：non-blocking write 可部分写或返回 0。
- **港口后果**：半箱货过闸后，余货被销毁。
- **线上现象**：大响应、慢客户端下响应截断。
- **修正**：保存 ByteBuffer position，直到 `hasRemaining()` 为 false 才释放。

### 5. 在 event loop 中同步调用慢下游

```java
void onMessage(Request r) {
    Result result = jdbcCall(r);
    write(result);
}
```

- **错因**：一个 event loop 服务很多 C；慢 DB/RPC 占住整个调度台。
- **港口后果**：调度员离岗填长表，所有泊位无人调度。
- **线上现象**：一个慢依赖抬高同 loop 所有连接的 P99。
- **修正**：跨入有界业务边界，带 deadline；结果以 task 回到原 loop。

### 6. 用默认无界队列承接业务

```java
ExecutorService pool = Executors.newFixedThreadPool(32);
pool.submit(() -> service.handle(r));
```

- **错因**：固定线程数不等于任务内存有界；默认队列可持续堆积。
- **港口后果**：作业区不够时，把集装箱无限堆在港内。
- **线上现象**：堆增长、GC 抖动、最终 OOM。
- **修正**：显式有界队列、拒绝/降级、deadline 与队列驻留时间指标。

### 7. 业务线程直接修改连接兴趣集

```java
worker.execute(() ->
    key.interestOps(key.interestOps() | SelectionKey.OP_WRITE));
```

- **错因**：破坏 C 的 owner；worker 与 event loop 并发修改 key、buffer、关闭状态。
- **港口后果**：多个作业员绕过调度台修改同一泊位牌。
- **线上现象**：偶发漏写、`CancelledKeyException`、竞态断连。
- **修正**：worker 只提交“追加响应”的意图；所属 loop 串行改队列与兴趣集。

### 8. 用 backlog 代替应用准入

```java
server.bind(address, 65535); // 以为连接不会被拒绝
```

- **错因**：`listen(backlog)`、`somaxconn`、SYN / accept 路径、应用 in-flight 是不同边界。
- **港口后果**：把入港闸门容量误当作作业区容量。
- **线上现象**：connect timeout / connection failure 难归因。
- **修正**：分别观测建连、accept、活跃连接、in-flight、业务拒绝与 `TcpExtListen*` 指标。

### 9. 将 TCP keepalive 当作业务 SLA

```java
channel.setOption(StandardSocketOptions.SO_KEEPALIVE, true);
// 因而不再设计心跳或 idle timeout
```

- **错因**：keepalive 的探测周期与业务超时语义不同，且依赖系统配置。
- **港口后果**：失联货轮仍长期占着泊位。
- **线上现象**：幽灵连接、FD 占用、请求永远等不到对端。
- **修正**：按协议设置心跳 / idle timeout，并定义超时后的关闭和重试语义。

### 10. outbound 满了就加堆

```java
conn.outboundQueue.add(response); // 无字节预算
```

- **错因**：把慢消费者的责任转移到服务端内存。
- **港口后果**：港区无限扩张，而出港闸门仍然没变宽。
- **线上现象**：尾延迟恶化、直接内存/堆耗尽、全局抖动。
- **修正**：连接、loop、进程三级预算；水位、限流、降级、关闭或异步交付。

### 11. 把本地 write 当业务成功

```java
ch.write(response);
markRequestDone(requestId);
```

- **错因**：本地写入发送路径不等于 TCP 对端收到，更不等于业务 ack。
- **港口后果**：船刚离港就把货单盖成“已签收”。
- **线上现象**：重试导致重复执行，审计无法解释结果。
- **修正**：区分 `LOCAL_WRITE_DONE` 与 `ACKED`；有 ack 时保留 correlation state、deadline 与幂等策略。

### 12. 收到停机信号就直接 close

```java
server.close();
connections.forEach(Channel::close);
```

- **错因**：半包、已投递、未写完、WAITING_ACK 的 R 被混成同一种关闭。
- **港口后果**：关闸时货单和未签收结果一起消失。
- **线上现象**：重复扣款、结果不明、客户端无谓重试。
- **修正**：drain deadline 下分别处理半包、业务中、outbound、ack；保留结果查询与幂等契约。

<a id="errata"></a>
## 📚 版本勘误表

| ❌ 常见说法 | ✅ 更准确的说法 |
|---|---|
| NIO 一定比 BIO 快。 | NIO 改善大量 I/O 等待的组织；收益取决于连接画像、业务耗时、TLS、OS 与压测。 |
| `select()` 返回说明收到一个完整请求。 | 它更新就绪状态；完整帧由 decoder 判断。 |
| `OP_WRITE` 表示对端收到。 | 它只涉及本地写入条件。 |
| 一次 `write()` 一定写完整。 | 可能部分写或 0；剩余字节必须保存。 |
| `epoll` 返回后内核已处理事件。 | 内核交付就绪事件；应用仍逐项处理。 |
| Nagle 会造成固定 40 ms 延迟。 | 时长与 OS、ACK、写模式、代理、TLS 有关，必须实测。 |
| 调大 backlog 就不会连接失败。 | backlog 只是建连路径一环；accept、内核参数、准入共同决定。 |
| `Selector` 在 Linux 永远等于 `epoll`。 | 公开 API 不承诺 provider；私有实现仅用于对应版本诊断。 |
| Java 只有 `SocketChannel + Selector`。 | Java 还有 NIO.2 AIO completion API；provider 不可从 API 反推。 |
| 虚拟线程让背压过时。 | 它改变等待承载成本；慢客户端、内存、下游配额仍需边界。 |
| `write()` 完成即业务 DONE。 | 至多 LOCAL_WRITE_DONE；有业务 ack 时还要 WAITING_ACK → ACKED / timeout。 |
| `close()` 就完成停机收尾。 | 半包、已投递、未送达、待 ack 的 R 需不同 drain 契约。 |

<a id="cross-runtime"></a>
## 🌍 跨语言 / 跨运行时视角

| 生态 | 常见承载物 | 同构问题 | 不应误读为 |
|---|---|---|---|
| Java | `Selector`、Netty EventLoop、NIO.2 AIO、virtual threads | readiness / completion 不同；framing、owner、背压相同 | “Java 只有 Selector”或“Netty 自动解决业务阻塞” |
| Go | runtime netpoll + goroutine | goroutine 降低等待成本；仍有下游、队列和慢消费者边界 | “goroutine 很轻，所以可以无上限” |
| Rust | mio / Tokio | readiness、task poll、buffer 生命周期、背压 | “async 没有显式状态机和取消路径” |
| Node.js | libuv、stream | event loop 不能被同步长任务卡住；`drain` 对应写恢复 | “回调 / Promise 就没有阻塞和背压问题” |
| .NET | IOCP、`async/await` | completion 通知不等于业务完成；仍需状态、取消与限流 | “完成端口表示对端业务已完成” |

跨语言后仍成立的判断力：

```text
字节边界不是消息边界。
通知资格不是完成确认。
等待必须有承担者，状态必须有 owner。
队列不是免费缓冲，写路径是容量系统的一半。
框架名不是架构决策，指标和故障注入才是证据。
```
