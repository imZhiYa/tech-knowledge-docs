# 🧯 生产演练与验证：从“代码正确”到“生产可用”

> 这不是一篇监控面板教程。
>
> 本文只追踪一个主线：**下单请求 B 的故障演练**——B 已经从 00 的谱系、01 的 AT、02 的 TCC/Saga 代码层走到这里，它要回答的是最后一个问题：**代码正确了，凭什么相信生产环境里真的扛得住？**
>
> `distributed-tx-00` 已经把生产收口压缩成一句话：**先重构边界，再选谱系，最后用演练和指标让它可观测。** 本文把“演练和指标”拆成可执行的动作：
>
> ```text
> 为什么必须演练（代码正确 ≠ 生产可用）
>   -> 故障注入：协调者 kill / 参与者宕机 / 网络分区
>   -> 乱序与重复注入：Confirm/Cancel 重放、迟到 Try
>   -> 可观测指标：in-doubt / 成功率 / 补偿积压 / 对账差异
>   -> 恢复预案：人工裁决 / 重试上限 / 对账兜底
>   -> 上线门槛：用演练和 SLO 验收，而不是架构评审
> ```

# 🏷️ 关键词与主线进度

关键词：

```text
故障演练 | 故障注入 | 协调者 kill | 参与者宕机 | 网络分区
Confirm/Cancel 重复注入 | 迟到 Try | in-doubt | XA RECOVER
全局事务成功率 | 补偿执行率 | 补偿积压 | 对账差异数 | SLO
恢复预案 | 人工裁决 | 重试上限 | 死信 | 上线门槛
```

主线进度：

```text
① B 从“代码正确”到“生产可用”的最后一公里
② 为什么必须用故障演练代替“我觉得没问题”
③ 第一组演练：协调者/参与者/网络——协议级故障
④ 第二组演练：重复与乱序——幂等/悬挂路径
⑤ 指标与告警：故障时能不能快速归因
⑥ 恢复预案与上线门槛：如何验收“生产可用”
```

```text

```

# 正文：五个 Level 打穿生产演练与验证

## Level 1：为什么必须演练——代码正确不等于生产可用

一句话认知墙：**代码正确是“正常路径正确”，生产可用是“故障路径可恢复、可归因、可兜底”。**

### 前置知识关卡

- [ ] 知道 2PC 的 in-doubt 悬挂（dtx-00 L2）
- [ ] 知道 TCC 的空回滚/悬挂/幂等代码防御（dtx-02 L2/L3）
- [ ] 知道 Saga 超时 = 结果未知（dtx-02 L4）
- [ ] 知道 AT 的 undo_log/全局锁/脏写检测（dtx-01）

### Why：为什么“测试过了”还不够

**徒弟：**

> dtx-02 的冻结表、控制表、编排器都写了，单测也过了，还不能上线吗？

**老陈：**

> 单测验证的是“正常路径下代码符合预期”，生产要面对的是“故障路径下系统还能不能恢复”。两者差三层：
>
> ```text
> 差距一：正常路径没有故障，生产路径有协调者崩溃、消息重复、网络分区
> 差距二：代码正确看“结果对不对”，生产可用看“故障时能不能快速归因”
> 差距三：单测能重放确定性输入，故障路径依赖时序、并发、恢复顺序，只能靠演练
> ```

### What：生产可用的三个可验收标准

```text
可恢复：任何故障发生后，系统能回到一致状态或进入明确的人工兜底
可归因：故障发生时，指标/日志能告诉我们“卡在哪、欠什么、谁在等”
可兜底：自动路径失败后，有重试上限、死信、对账、人工处置闭环
```

> 📌 最容易被误解的一点：演练不是证明“系统不会出故障”，而是证明“出了故障之后，你能在规定时间内恢复并解释差异”。

### How：从代码正确到生产可用的验证闭环

```text
代码正确（表结构/幂等/状态机）
   -> 故障注入（协调者 kill / 参与者宕机 / 网络分区 / 重复与乱序）
   -> 观察行为（阻塞？补偿？待确认？对账差异？）
   -> 恢复验证（人工裁决 / 重试 / 清理 / 对账归零）
   -> 指标沉淀（in-doubt、补偿积压、对账差异）
   -> 上线门槛（恢复时长 / 成功率 / 差异数）
```

**徒弟：**

> 那直接上混沌工程，到处杀进程不就行了？

**老陈：**

> 不行。没有恢复预案和指标的乱杀，只是制造事故，不是演练。**演练的输入是故障注入，输出必须是“恢复路径是否有效、指标是否可归因、对账是否收敛”。**

### Transfer：演练思想的迁移

1. 缓存穿透、消息积压、索引同步延迟，同样需要“故障注入 + 恢复验证 + 对账”。
2. “没出事”不等于“安全”，只等于“还没踩到故障路径”。
3. 生产可信度 = 演练路径 × 可观测性，不依赖任何框架的“保证”。

本层留下的新账：**具体演练哪些故障？**下一层从协议级故障开始。

### Level Ending

```text
口诀：代码正确看正常，生产可用看恢复。
```

## Level 2：协议级故障演练——协调者 / 参与者 / 网络分区

一句话认知墙：**协议级演练回答三个问题：协调者没了怎么办？参与者挂了谁在等？网络断了选哪边？**

### 前置知识关卡

- [ ] 知道 2PC prepare 后的 in-doubt 语义（dtx-00 L2）
- [ ] 知道 Seata TC 的全局事务状态存储（dtx-01 L4）
- [ ] 知道 CAP 分区时 C/A 选边（dtx-00 L5）

### Why：为什么先练协议级故障

**徒弟：**

> 重复和幂等不是更常见吗？为什么要先练协调者 kill？

**老陈：**

> 因为协议级故障决定的是“系统还能不能继续跑”：
>
> ```text
> 2PC 系：协调者 prepare 后崩溃 -> 参与者持锁等待 -> 业务冻结
> 异步补偿系：协调者/编排器崩溃 -> 补偿链条可能断 -> 数据部分生效
> 网络分区：同步系阻塞，异步系积压 -> 恢复后必须靠对账收敛
> ```
>
> 这些故障不演练，线上第一次遇到就是事故。

### What：三组协议级演练设计

```text
演练一：协调者 kill（对应 EX-01；人工裁决流程配合 EX-05）
  场景：2PC 已 PREPARE，协调者在 COMMIT 前崩溃
  注入：kill -9 协调者进程
  观察：XA RECOVER 是否列出 in-doubt；参与者锁持有时长
  验证：恢复协调者日志或人工裁决后，三库最终一致

演练二：参与者 prepare 后宕机（对应 EX-02；恢复语义配合 EX-05）
  场景：参与者 A 收到 prepare 后宕机，未返回 Ready
  注入：kill -9 参与者 A
  观察：协调者是否有超时 abort；其余参与者锁持有时长
  验证：A 恢复后，全局事务最终一致或被明确回滚
  恢复语义：A 恢复时同样处于“不知道裁决”的参与者侧 in-doubt，
           必须靠 XA RECOVER / 询问协调者收口，不能自作主张提交或回滚

演练三：网络分区（对应 EX-03）
  场景：订单库与协调者/其他参与者断连
  注入：防火墙 / tc 模拟分区
  观察：2PC 链路阻塞/超时；Saga/消息链路积压；恢复后对账差异归零
  验证：分区期间业务行为符合预期选边，恢复后无静默不一致
```

### How：一次协调者 kill 的完整观察路径

```text
① 制造全局事务，停在 prepare 后
② kill 协调者
③ 观察业务：请求超时/阻塞
④ 查 XA RECOVER：in-doubt 事务数
⑤ 恢复协调者（或人工裁决）
⑥ 验证三库最终状态
⑦ 记录：in-doubt 数、锁持有时长、恢复耗时、最终一致性
```

**徒弟：**

> 协调者 kill 后，能不能直接“选一个新协调者”？

**老陈：**

> 对 2PC 不能随便选。新协调者不知道旧协调者是否已经把 COMMIT 发给部分参与者，所以唯一安全路径是恢复旧协调者日志或按日志/对账人工裁决。**Seata TC 这类有持久化状态存储的实现，恢复路径是 TC 高可用 + 状态重建；XA 裸用则经常要靠 XA RECOVER 人工收口。**

### Transfer：协议级演练的迁移

1. 任何“先锁定、后裁决”的协议，都要练“裁决者消失”。
2. 网络分区不是“网络团队的事”，是分布式事务选型后的必然验收项。
3. 恢复路径必须写进演练剧本，不能现场发明。

本层留下的新账：**协议级故障之后，还要练“同一件事被重复执行”。**下一层进入幂等与乱序。

### Level Ending

```text
口诀：协调者没了看恢复，网络断了看选边。
```

## Level 3：重复与乱序演练——幂等、空回滚、悬挂

一句话认知墙：**分布式事务的日常故障不是“机器全挂”，而是同一件事重复到达、顺序颠倒；演练要把这些路径全部打一遍。**

### 前置知识关卡

- [ ] 知道 Confirm/Cancel 必须以状态机 CAS 为门（dtx-02 L2）
- [ ] 知道空回滚 = Cancel 先到、Try 未执行（dtx-00/dtx-02）
- [ ] 知道正确防御下迟到 Try 会被控制表拦截（dtx-02 L3）
- [ ] 知道 Saga 超时必须先确认结果再补偿（dtx-02 L4）

### Why：为什么重复与乱序比崩溃更值得练

**徒弟：**

> 协调者 kill 是黑天鹅，重复请求是日常吧？

**老陈：**

> 对。网络重试、超时重发、协调者恢复都会让 Confirm/Cancel 重复到达；消息延迟会让 Cancel 先到、Try 后到。这些不是低概率，而是**必然会在某个时刻发生**。代码里写了幂等不算数，注入重复执行后结果仍然一致才算数。

### What：四组重复与乱序演练

```text
演练四：Confirm 重复注入（对应 EX-06）
  注入：同一 freezeId 顺序/并发执行 N 次 Confirm
  验证：只生效一次；重复 Confirm 被状态机 CAS 挡在副作用之前

演练五：Cancel 重复注入（对应 EX-06）
  注入：同一 freezeId 顺序/并发执行 N 次 Cancel
  验证：只释放一次 frozen；重复 Cancel 幂等返回

演练六：空回滚 + 迟到 Try（对应 EX-04/EX-06）
  注入：先 Cancel，后 Try
  验证：Cancel 写 SUSPENDED；迟到 Try 被控制表拦截；无 FROZEN 残留

演练七：Saga 超时结果未知（对应 EX-08）
  注入：扣款步骤超时，不返回成功/失败
  验证：编排器先查询确认，不直接补偿；无法确认时进入 UNKNOWN/人工
```

### How：一次 Confirm 重复注入的验证过程

```text
① 正常完成一次 Try，得到 freezeId
② 对同一 freezeId 连续调用 Confirm 3 次
③ 检查库存：total/frozen 只变化一次
④ 检查冻结表：状态为 CONFIRMED，终态不可逆
⑤ 检查控制表：状态为 COMMITTED
⑥ 记录：重复执行结果偏差数 = 0
```

**徒弟：**

> 如果注入后发现 Confirm 重复执行了两次扣减呢？

**老陈：**

> 说明状态机 CAS 门放错了位置——副作用跑到门前面了。这正是 dtx-02 强调的“状态机 CAS 是所有副作用的总闸门”。**演练的价值就是把这个 bug 从线上提前拽到实验环境。**

### Transfer：重复与乱序演练的迁移

1. 所有“至少一次”投递的消费端，都要练重复幂等（回链 mq-03/ddd-05）。
2. “先到”和“后到”不是代码 bug，是分布式时序的常态。
3. 正确性不是靠“消息不会重复”保证，是靠“重复了也没事”保证。

本层留下的新账：**故障和重复都练了，线上怎么知道正在发生？**下一层看指标。

### Level Ending

```text
口诀：重复打三遍，结果只能变一次。
```

<a id="level-4"></a>

## Level 4：可观测指标——故障时能不能快速归因

一句话认知墙：**指标不是越多越好，而是每个故障场景都要有一个“一看到就知道卡在哪”的指标。**

### 前置知识关卡

- [ ] 知道 in-doubt / 补偿积压 / 对账差异的含义
- [ ] 知道指标必须配合告警阈值和恢复动作
- [ ] 知道没有实测的阈值要保持“待实测”

### Why：为什么“有监控”不等于“可观测”

**徒弟：**

> 我们已经有监控大屏了，各种成功率都有，还不够吗？

**老陈：**

> 大屏上的成功率只能告诉你“出事了”，不能告诉你“卡在哪个环节”。可观测性要能回答：
>
> ```text
> 是协调者挂了？（in-doubt 数上升 / 锁持有时长上升）
> 是补偿没执行？（补偿积压上升 / 补偿执行率下降）
> 是重复请求导致？（幂等冲突数 / 终态重放次数）
> 是数据对不上？（对账差异数上升）
> ```

### What：指标与故障场景的映射

```text
协议级故障：
  xa_in_doubt_count              -> in-doubt 事务数
  prepared_lock_hold_ms          -> prepare 锁持有时长（待实测）
  global_tx_success_rate         -> 全局事务成功率

补偿/编排故障：
  compensation_execution_rate    -> 补偿执行率
  compensation_pending_count     -> 补偿积压
  saga_success_rate              -> Saga 成功率
  saga_unknown_count             -> 结果未知事务数

幂等/乱序：
  confirm_retry_count            -> Confirm 重试次数
  cancel_retry_count             -> Cancel 重试次数
  suspended_intercept_count      -> SUSPENDED 拦截迟到 Try 次数

TCC 悬挂：
  frozen_pending_count           -> 未闭环 FROZEN 记录数
  hanging_detect_latency         -> 悬挂发现延迟（待实测）
  cleanup_error_count            -> 清理失败数

最终兜底：
  reconcile_diff_count           -> 对账差异数
  reconcile_diff_age             -> 对账差异存在时长（必须 < 一致时间窗口 SLO）
  reconcile_compensation_rate    -> 差异补偿执行率
```

### How：指标怎么变成告警和动作

```text
xa_in_doubt_count > 0            -> 告警：进入人工/协调者恢复预案
compensation_pending_count 持续上升 -> 告警：补偿积压，查失败原因
reconcile_diff_count > 0         -> 告警：对账差异，禁止静默
reconcile_diff_age 超 SLO         -> 告警：最终一致超窗，进入人工/补偿
frozen_pending_count 超阈值       -> 告警：悬挂扫描，按阈值/二次校验处理
saga_unknown_count > 0           -> 告警：结果未知事务，需要查询确认或人工
```

**徒弟：**

> 指标一直为 0，是不是就安全了？

**老陈：**

> 一直为 0 往往说明你根本没演练过故障路径。**指标的价值是故障时能快速归因，不是证明没出过事。** 把“in-doubt 恢复时长”“补偿成功率”“对账差异数”作为上线门槛，比任何架构评审都有说服力。

### Transfer：指标思想的迁移

1. 每个故障场景都要回答：哪个指标会先动？看到它后做什么？
2. 指标要能驱动动作，不能只是“看起来很忙”。
3. 阈值必须来自演练和业务 SLO，不能拍脑袋（待实测）。

本层留下的新账：**指标有了，恢复路径和上线门槛呢？**下一层收口。

### Level Ending

```text
口诀：指标不只看有没有，要看能不能归因。
```

<a id="level-5"></a>

## Level 5：恢复预案与上线门槛

一句话认知墙：**生产可用的验收标准不是“没有故障”，而是“故障发生后能在 SLO 内恢复，且对账差异可解释”。**

### 前置知识关卡

- [ ] 知道 2PC in-doubt 的人工裁决路径（dtx-00 L2）
- [ ] 知道补偿失败的重试上限与死信（dtx-02 L4）
- [ ] 知道对账是总验收（dtx-02 L6）

### Why：为什么恢复预案要提前写

**徒弟：**

> 故障真的发生时再想办法不行吗？

**老陈：**

> 分布式事务的故障窗口很短，但影响很大：锁持有越久业务越堵，补偿积压越久数据越脏。**恢复预案要提前写，是因为现场没有时间重新理解协议语义。**

### What：三类恢复预案

```text
2PC/XA：
  in-doubt 恢复：XA RECOVER 列出 -> 按协调者日志/对账人工裁决
  禁止：无依据地随便 commit/rollback

Seata/AT：
  TC 故障：依赖 TC 高可用 + 持久化状态恢复
  TC 存储模式（file/db/redis）决定 TC 可用性和全局锁表性能上限；演练时按实际模式验证
  undo_log 残留：清理任务 + 残留监控
  回滚失败：重试上限 -> 待确认 -> 人工/对账

TCC/Saga：
  悬挂：扫描 + 二次校验 + 分阶段处置
  补偿失败：有限重试 -> 死信 -> 对账
  Saga UNKNOWN：先查询确认，禁止直接补偿
```

### How：上线门槛清单

```text
① 故障演练全部跑通，并记录恢复时长
② 关键指标已接入告警：in-doubt、补偿积压、对账差异
③ 人工处置路径有负责人和 SLO
④ 对账任务已上线，差异数可观测
⑤ 恢复演练不是“演示一次”，而是有周期性的常态化演练
```

**徒弟：**

> 演练跑通了，但没跑出问题，能上线吗？

**老陈：**

> 能，但要满足一个前提：**演练的结论是“我们看到了故障行为，并验证了恢复路径有效”，而不是“没出问题所以安全”。** 如果演练设计本身没有覆盖故障路径，那通过也没有意义。

### Transfer：收口思想的迁移

1. 缓存、消息、搜索索引的同步问题，同样用“演练 × 指标 × 对账”收口。
2. 上线门槛必须包含恢复时长和差异数，不能只包含功能测试。
3. 生产可信度 = 演练路径 × 可观测性 × 恢复预案。

本层收口：从 00 的谱系，到 01 的 AT，到 02 的 TCC/Saga 代码，再到本文的演练与指标，B 的完整闭环已经成立：**先重构边界，再选最便宜的格子，最后用演练和指标让它可观测。**

### Level Ending

```text
口诀：演练出恢复，指标能归因，对账是总闸。
```

# ⚠️ 坑与细节

<a id="pitfalls"></a>

## 坑 1：把“测试通过”当“生产可用”

错误理解：单测/联调过了就能上线。

原因：测试验证正常路径，生产还要面对协调者崩溃、重复请求、网络分区。

比喻后果：演练没做过，总柜台一停电全楼抓瞎。

线上现象：in-doubt 堆积、补偿断链、对账差异无人处理。

修正：故障演练 + 恢复预案 + 指标告警一起验收。

---

## 坑 2：协调者 kill 后随便选新协调者

错误理解：换一个协调者继续提交/回滚就行。

原因：新协调者不知道旧协调者是否已通知部分参与者 COMMIT。

比喻后果：新柜台不知道旧柜台盖到第几个章，乱作决定。

线上现象：部分库已提交、部分库被回滚，数据不一致。

修正：恢复旧协调者日志，或基于 XA RECOVER/对账人工裁决。

---

## 坑 3：网络分区演练只测“通不通”

错误理解：断网后能 ping 通就算恢复。

原因：分布式事务要验证的是恢复后的数据一致性，不是网络连通性。

比喻后果：电话修通了，但登记本已经对不上。

线上现象：网络恢复后差异仍存在，静默不一致。

修正：分区恢复后跑对账，差异必须归零或有解释。

---

## 坑 4：重复注入只测“不报错”

错误理解：Confirm/Cancel 重复执行没抛异常就说明幂等。

原因：幂等要求结果一致，不报错但双扣也是失败。

比喻后果：重复盖章没被拒绝，但材料盖了两遍。

线上现象：库存/余额被重复扣减。

修正：断言最终库存/余额与单次执行一致，而不是只看错误率。

---

## 坑 5：Saga 超时直接补偿

错误理解：扣款超时 = 失败，直接退款。

原因：超时可能只是响应丢失，扣款实际成功；退款会造成资损。

比喻后果：顾客可能已扣款，柜台却当成没扣。

线上现象：扣款成功 + 退款。

修正：先查询确认，再决定推进或补偿；无法确认进 UNKNOWN。

---

## 坑 6：指标堆一屏但没有动作

错误理解：监控大屏指标越多越安全。

原因：指标必须能回答“卡在哪、下一步做什么”。

比喻后果：总控室全是灯，但没人知道哪盏灯对应哪个预案。

线上现象：故障发生时看板全红，处置靠猜。

修正：每个关键指标绑定告警阈值和恢复动作。

---

## 坑 7：演练通过一次就再也不练

错误理解：上次演练没问题，以后也没问题。

原因：版本升级、拓扑变化、参数调整都可能改变故障路径。

比喻后果：去年演练过停电，今年设备早换了。

线上现象：新版本上线后老预案失效。

修正：演练常态化，关键变更后重跑。

---

## 坑 8：以为最终一致 = 随便多久

错误理解：用了 Saga/消息方案，晚点对上就行，不需要设窗口。

原因：最终一致必须有业务容忍度边界和观测手段；没有时间窗口，差异会长期存在且无人告警。

比喻后果：各部门说“最后会对上”，但没人定义多久对、怎么查。

线上现象：对账差异长期存在，补偿积压无人发现。

修正：为每条异步链路定义一致时间窗口 SLO，用补偿积压、对账差异、悬挂发现延迟来验收。

```text
我以前容易把“监控指标”讲成“成功率”；准确说法是成功率只能报警，
in-doubt、补偿积压、对账差异这些指标才能定位环节。
```

# 🏆 生产决策卡

<a id="decisions"></a>

## Decision Card 1：协调者 kill 演练

### 场景

2PC/Seata 全局事务上线前，需要验证协调者故障。

### 判断

必须制造 prepare 后的 kill，验证 in-doubt 可见、恢复路径有效、最终一致。

### Mechanism -> Decision

| 机制 | 工程决策 |
| --- | --- |
| 2PC 裸 XA | XA RECOVER 列出 in-doubt，恢复协调者日志或人工裁决 |
| Seata TC | TC 高可用 + 持久化状态恢复，演练 TC 切换 |
| 指标 | xa_in_doubt_count、prepared_lock_hold_ms（待实测） |

### 禁止决策

```text
不演练协调者故障直接上线；kill 后无预案现场发明。
```

### 验收指标

```text
in-doubt 恢复时长
锁持有时长（待实测）
恢复后三库一致性
```

---

## Decision Card 2：网络分区演练

### 场景

需要验证分区期间与恢复后的行为。

### 判断

同步系应阻塞/超时，异步系应积压/补偿；恢复后对账差异归零。

### Mechanism -> Decision

| 机制 | 工程决策 |
| --- | --- |
| 2PC/AT | 观察阻塞/超时行为，设置超时与恢复预案 |
| Saga/消息 | 观察积压/补偿，恢复后跑对账 |
| 指标 | reconcile_diff_count、消息积压 |

### 禁止决策

```text
分区恢复后不跑对账就宣布“已恢复”。
```

### 验收指标

```text
分区期间业务成功率
恢复后对账差异数
端到端恢复时间
```

---

## Decision Card 3：重复与乱序注入

### 场景

TCC/Saga 上线前需要验证幂等、空回滚、悬挂拦截。

### 判断

Confirm/Cancel 重复执行结果只能变化一次；迟到 Try 必须被 SUSPENDED 拦截。

### Mechanism -> Decision

| 机制 | 工程决策 |
| --- | --- |
| Confirm/Cancel 重复 | 状态机 CAS 门在副作用前 |
| 迟到 Try | 控制表 SUSPENDED 拦截 |
| Saga 超时 | 查询确认，禁止直接补偿 |

### 禁止决策

```text
只测“不报错”，不验证最终库存/余额一致。
```

### 验收指标

```text
重复执行结果偏差数 = 0
SUSPENDED 拦截次数
UNKNOWN 事务数
```

---

## Decision Card 4：上线门槛

### 场景

所有机制和演练都完成后，决定是否放量上线。

### 判断

故障可恢复、指标可归因、对账差异可解释。

### Mechanism -> Decision

| 机制 | 工程决策 |
| --- | --- |
| 故障演练 | 全部通过并记录恢复时长 |
| 指标告警 | in-doubt、补偿积压、对账差异已接入 |
| 对账 | 差异数为 0 或有解释 |

### 禁止决策

```text
拿“没出过事”当上线依据。
```

### 验收指标

```text
恢复时长符合 SLO
补偿执行率
对账差异数
```
