# 🏭 全文唯一比喻：冻结登记 + 倒着撤销

顾客办理业务时，办理处先做"预审登记"（冻结登记表）：登记了才允许后续动作；如果业务失败，按登记单"倒着撤销"。

## ASCII Diagram

```text
B 的预留与补偿之旅
        |
        v
+------------------------------+
| 预审登记（Try）              |
| 冻结表：登记冻结记录           |  -> 预留语义落地
+------------------------------+
        |
        | 全部登记成功
        v
+------------------------------+
| 确认办理（Confirm）           |  -> 冻结转正式
| 或 倒着撤销（Cancel/补偿）     |  -> 解冻 / 反向操作
+------------------------------+
        |
        v
+------------------------------+
| 悬挂扫描（清理任务）           |
| 登记了没人销 -> 告警/清理      |  -> 三难题收尾
+------------------------------+
```

## Mapping Table

| 比喻元素 | 技术概念 | 唯一职责 |
| --- | --- | --- |
| 预审登记 | Try + 冻结表 | 预留语义落地 |
| 冻结登记表 | 冻结表（freezeId 主键）+ 事务控制表（globalTxId+branchId） | 账本 + 幂等/防悬挂依据 |
| 确认办理 | Confirm | 冻结转正式 |
| 倒着撤销 | Cancel / Saga 补偿 | 反向操作 |

## Level 1：从机制到代码——落地为什么难

一句话认知墙：**机制层讲的是"为什么"，代码层必须回答"幂等键放哪、状态机怎么画、防御代码怎么写"——三个鸿沟不跨过去，机制正确就是纸上谈兵。**

### 前置知识关卡

- [ ] 知道 TCC 三难题（dtx-00 L3）
- [ ] 知道 Saga 补偿对偶（dtx-00 L4）
- [ ] 知道冻结/预留的业务语义

### Why：为什么"机制懂了"不等于"能写代码"

**徒弟：**

> dtx-00 把三难题都讲清楚了，空回滚、悬挂、幂等。机制都懂了，写代码不就是照着做吗？

**老陈：**

> 机制层回答的是"为什么存在这三个问题"，代码层要回答的是三个具体决策：
>
> ```text
> 鸿沟一：幂等键放哪？
>   机制层说"要幂等"，代码层必须选：freezeId 管预留记录去重（全局唯一 ID，落库靠唯一约束），
>   globalTxId+branchId 管防悬挂/空回滚（事务控制表唯一键，见 Level 2）
> 鸿沟二：状态机怎么画？
>   机制层说"Try/Confirm/Cancel"，代码层必须画：FROZEN -> CONFIRMED/CANCELLED，
>   还要处理"Cancel 先到"（空回滚）和"Try 迟到"（悬挂）
> 鸿沟三：防御代码怎么写？
>   机制层说"要防空回滚/悬挂"，代码层必须写：Cancel 无记录写 SUSPENDED 标记、Try 控制表插入冲突按状态区分幂等/拒绝、记录状态终态判定
> ```
>
> 机制讲的是"问题的形状"，代码讲的是"问题的答案"。本文从冻结表开始——它是 TCC 的账本，也是所有防御的基础。

### What：落地层的三个固定决策

```text
决策一：预留必须落表（冻结表），不能靠内存判断
决策二：幂等必须靠唯一约束，不能靠"先查再写"
决策三：状态机必须显式建模，不能靠 try-catch 代替
```

> 📌 最容易被误解的一点：TCC 的"预留"不是内存变量，是数据库里的一条冻结记录。没有这条记录，空回滚/悬挂/幂等三个问题都没有落脚点。

### How：从机制到代码的映射路径

```text
机制问题       -> 代码答案
空回滚         -> Cancel 查控制表：无记录 = Try 未执行或还在路上 ->
                 写入 SUSPENDED 标记再返回成功（拦截迟到 Try 的唯一依据）
悬挂           -> Try 第一步向控制表 insert（唯一键 globalTxId+branchId）：
                 插入冲突按状态区分：TRIED/COMMITTED 幂等成功，
                 ROLLBACKED/SUSPENDED 拒绝执行
幂等           -> 控制表唯一约束 + 状态机终态判定（freezeId 只管预留记录去重）
```

**徒弟：**

> 为什么幂等不能靠"先查再写"？并发下先查后写不就漏了吗？

**老陈：**

> 对。两个并发请求同时"查到无记录"，然后同时插入——都通过了。**唯一约束是数据库级别的最后防线，先查再写是应用级别的侥幸。**代码层的第一课就是：凡是幂等，必须落唯一约束。

### Transfer：机制到代码的迁移

1. 任何"防御性正确"的机制，代码层都要回答：状态落哪张表、幂等靠什么约束、防御怎么写。
2. "先查再写"的不安全是所有并发系统的通用教训（回链 ddd-05 幂等结论）。
3. 机制正确是必要条件，代码正确是把必要变充分的最后一段；两者之间的鸿沟就是本文的内容。

本层留下的新账：**冻结表长什么样？**下一层落 TCC 的账本。

### Level Ending

```text
口诀：机制讲形状，代码讲答案。
```

## Level 2：TCC 落地——冻结表 + 幂等 + 空回滚

一句话认知墙：**冻结表是 TCC 的账本：Try 记一笔冻结，Confirm 转正式，Cancel 解冻；账本的唯一约束与状态机，同时解决幂等和空回滚。**

### 前置知识关卡

- [ ] 知道 TCC 三难题的定义（dtx-00 L3 锁定版）
- [ ] 知道唯一约束与并发写的关系
- [ ] 知道状态机（FROZEN/CONFIRMED/CANCELLED）的终态

### Why：为什么必须有冻结表

**徒弟：**

> 库存扣减直接 UPDATE 不行吗？为什么非要先"冻结"再"确认"？

**老陈：**

> 直接 UPDATE 的问题：如果后面环节失败，你需要"撤销扣减"——但扣减已经生效，撤销动作本身没有幂等锚点。
>
> 冻结表解决的是**预留语义 + 撤销锚点**：
>
> ```text
> Try    : frozen +N（总量不变、可用量减少；写冻结记录）
> Confirm: total -N、frozen -N（正式扣减 + 释放冻结，冻结记录转终态）
> Cancel : frozen -N（释放冻结，冻结记录转终态）
> ```
>
> 有了冻结表，撤销永远有对象（freezeId 指向的记录），幂等永远有依据（唯一约束），空回滚与防悬挂永远有判断（事务控制表：Cancel 无记录时写 SUSPENDED 标记，Try 插入冲突时按状态区分幂等返回/拒绝）。

### What：冻结表 + 事务控制表的最小结构

```text
冻结表（freeze_id 主键，教学级结构，非框架内建）：
  freeze_id       : 全局唯一，来源：业务 ID + 随机/雪花
  xid             : 全局事务 ID
  resource_type   : 资源类型（库存/余额）
  resource_id     : 资源 ID（SKU/账户）
  freeze_amount   : 冻结数量/金额
  status          : FROZEN -> CONFIRMED / CANCELLED（终态）
  create_time / update_time

stock 表（教学级结构，供 Try/Confirm/Cancel 引用）：
  resource_id   : 主键
  total         : 总量
  frozen        : 已冻结量
  （可用量 = total - frozen）

事务控制表（tcc_fence 表，唯一键 global_tx_id+branch_id，防悬挂的核心）：
  global_tx_id    : 全局事务 ID（与 branch_id 联合唯一）
  branch_id       : 分支 ID
  status          : 含 SUSPENDED（拦截迟到的 Try）
```

状态机：

```text
FROZEN --Confirm--> CONFIRMED（终态）
FROZEN --Cancel-->  CANCELLED（终态）

控制表状态线：
  TRIED --Confirm--> COMMITTED（终态）
  TRIED --Cancel-->  ROLLBACKED（终态）
  （空回滚：无 TRIED 记录时 Cancel 插入 SUSPENDED，拦截迟到 Try）
```

> 📌 两张表必须在**同一业务库、同一本地事务**里：先插控制表、再插冻结表/更新库存，任一步失败都要一起回滚；否则“控制表防悬挂”和“冻结表原子性”都不成立。

### How：Try/Confirm/Cancel 的代码骨架

```text
Try（预留）：
① 使用发起方（B 所在服务）预先生成的 freezeId（ID 值先于 Try 存在，但冻结记录在 Try 成功后才落库）+ globalTxId+branchId
② 先向事务控制表 INSERT（唯一键 globalTxId+branchId，状态 TRIED）
   插入冲突时按状态区分：
   - 已存在 TRIED / COMMITTED -> Try 已执行过，幂等返回成功
   - 已存在 ROLLBACKED / SUSPENDED -> 已被 Cancel 处理过，拒绝执行 Try
③ 插入成功 -> 用条件 UPDATE 原子校验并冻结可用量：
   UPDATE stock SET frozen = frozen + ?
   WHERE resource_id = ? AND (total - frozen) >= ?;
   影响行数 = 0 -> 可用量不足，预留失败回滚（含控制表插入）
④ INSERT INTO freeze 表（freeze_id 唯一约束）
⑤ 全部成功则提交本地事务；任一步失败则回滚（不预留）

Confirm（确认）——幂等门在最前：
① UPDATE freeze SET status = CONFIRMED WHERE freeze_id = ? AND status = FROZEN
   影响行数 = 0 -> 已终态（重复 Confirm），直接成功返回，不执行任何扣减
② UPDATE stock SET total = total - ?, frozen = frozen - ? WHERE resource_id = ?
   （正式扣减 + 释放冻结，同一行一次更新）
③ UPDATE tcc_fence SET status = COMMITTED WHERE ... AND status = TRIED
④ 失败不允许返回业务失败，只能重试 Confirm

Cancel（取消）——同样先过门：
① 控制表处置：
   有 TRIED -> UPDATE 为 ROLLBACKED；
   无记录 -> INSERT SUSPENDED；
   INSERT 撞已有 SUSPENDED（重复空回滚）-> 幂等成功返回
② UPDATE freeze SET status = CANCELLED WHERE freeze_id = ? AND status = FROZEN
   影响行数 = 0 -> 已终态或不存在（空回滚）-> 直接成功返回
③ 仅当 ② 影响行数 = 1：UPDATE stock SET frozen = frozen - ? WHERE resource_id = ?
   （释放冻结；空回滚路径不执行——Try 从未冻结过）
```

**状态机 CAS 是所有副作用的总闸门，副作用必须在门后**——这正是本文第一课“幂等 = 唯一约束 + 状态机终态判定”的代码化：Confirm/Cancel 先做状态 CAS，影响行数为 0 就幂等返回，不再执行任何库存副作用。

补一条协议纪律：**Try 全部成功后，全局事务只能走向 Confirm；Confirm/Cancel 都不允许返回业务失败，只能重试，直到成功或进入人工/对账。** 这样才不会出现“Try 成功后又 Cancel”的协议错误。

**徒弟：**

> Cancel 影响行数为 0 就"直接成功返回"，这安全吗？

**老陈：**

> 安全，这正是空回滚防御：**Cancel 先到、Try 还没执行时，查控制表无记录，Cancel 必须写入 SUSPENDED 标记再安全返回而不是报错。**报错会让协调者认为取消失败，进入重试死循环；不写标记，迟到的 Try 照样执行，悬挂照旧发生。幂等安全返回 + 留痕是 TCC 的礼貌——空回滚、防悬挂、幂等是同一个防御的三面。

### Transfer：账本思想的迁移

1. "预留 + 确认/取消"是业务级语义的通用建模（订票占座、预授权、库存锁定）。
2. 幂等锚点必须与业务动作绑定：预留记录去重用 freezeId，防悬挂/空回滚用控制表键（globalTxId+branchId），不能是独立随机数。
3. 状态机终态判定 + 唯一约束，是幂等防御的标准组合。

本层留下的新账：**记录可能永远停在 FROZEN——Try 已成功但二阶段 Confirm/Cancel 没来，或防御未覆盖路径留下残留。**下一层看悬挂检测与清理。

### Level Ending

```text
口诀：账本落表，幂等靠约束，空回滚要礼貌。
```

<a id="level-3"></a>

## Level 3：TCC 悬挂检测与清理

一句话认知墙：**悬挂是“二阶段结果丢失”或“防御未覆盖路径”的兜底场景；检测靠超时扫描，清理必须防误伤正常事务。**

### 前置知识关卡

- [ ] 知道悬挂的定义（Try 已生效、但 Confirm/Cancel 未闭环）
- [ ] 知道"正常长事务"与"悬挂"的区别
- [ ] 知道超时阈值与业务 SLO 的关系

### Why：悬挂从哪里来

**徒弟：**

> 只要 Try 和 Cancel 都幂等了，悬挂还有啥问题？

**老陈：**

> 问题不在重复执行，在**预留记录永远留在 FROZEN**：
>
> ```text
> 场景一（真正需要扫描的悬挂）：
> Try 成功并提交 -> 协调者崩溃 / 二阶段消息丢失
> -> Confirm/Cancel 都没来 -> FROZEN 永远无人推进
>
> 场景二（防御未覆盖的路径）：
> 历史脏数据、绕过控制表的写入、防御代码漏写标记
> -> 迟到的 Try 仍可能插入 FROZEN
> ```
>
> 在 Level 2 的正确防御下，“Cancel 先到、Try 迟到再插入 FROZEN”的路径会被控制表拦截。所以扫描任务不是给“正确防御下的必然路径”收尾，而是给 **二阶段结果丢失 + 防御未覆盖** 做第二道保险。

### What：悬挂扫描任务的设计

```text
扫描目标：FROZEN 且超过阈值未闭环的记录
两个变量：
  扫描周期：多久扫一次（成本 vs 发现延迟）
  超时阈值：超过多久算悬挂（必须 > 正常 Try->Confirm/Cancel 最长路径）

误报风险：正常长事务（人工审批、慢业务）被误判为悬挂 -> 误清理
防误伤：
  阈值由业务 SLO 决定（正常路径最长时间 + 安全余量）
  扫描只告警/标记，不自动清理（或分阶段：先告警后人工确认）
  清理前二次校验：全局事务状态（协调者已结束才可清理）

规模问题：FROZEN 记录量大时，`WHERE status='FROZEN' AND create_time < ?` 这种大范围扫描本身就是新性能风险。生产上可考虑：
  按 create_time 分桶/分区索引；
  或把“悬挂候选”单独落一张轻量扫描表，扫描任务只读小表；
  避免扫描任务在热点冻结表上造成新的锁冲突和 IO 放大。
```

**徒弟：**

> 那阈值设大一点不就没误报了？

**老陈：**

> 阈值越大，悬挂发现越晚，无效预留占用越久。**这是发现延迟与误报率的权衡，没有最优值，只有业务 SLO 决定的可接受区间。**（阈值档位待实测，见 experiments EX-04）

### Transfer：扫描思想的迁移

1. 任何"可能永远不闭环"的异步状态都要配扫描 + 告警 + 清理三件套。
2. 清理类任务的核心风险是误伤，阈值设计必须回答"正常路径最长时间"。
3. 分阶段处置（先告警后清理）是高风险清理的通用模式。

本层留下的新账：**TCC 的账本落地完了。Saga 呢？——编排器状态机和补偿表。**下一层看 Saga 落地。

### Level Ending

```text
口诀：悬挂兜底有，扫描要防误伤。
```

<a id="level-4"></a>

## Level 4：Saga 编排器——状态机 + 补偿表

一句话认知墙：**Saga 落地的核心不是"写补偿方法"，是编排器：一个持久化的状态机 + 一张补偿对偶表 + sagaId 幂等。**

### 前置知识关卡

- [ ] 知道 Saga 定义（dtx-00 L4）
- [ ] 知道编排与协同的区别（回链 ddd-02 事件协作）
- [ ] 知道补偿与正向动作的对偶性

### Why：为什么需要编排器

**徒弟：**

> Saga 不就是"失败就调补偿方法"吗？try-catch 反向调用不就行了？

**老陈：**

> try-catch 的问题是：**进程重启后，补偿逻辑就丢了。**Saga 可能跑几个小时，中途任何一步失败，补偿链条必须能接上——这需要持久化。
>
> 编排器就是"持久化 + 状态机 + 补偿表"三件套：
>
> ```text
> 持久化：每步执行结果落库，重启后可继续
> 状态机：明确每一步的状态（PENDING/DONE/FAILED/COMPENSATING/COMPENSATED）
> 补偿表：正向动作 T 与补偿动作 C 的映射，保证对偶
> ```

### What：编排器状态机与补偿表

```text
状态机：
  PENDING -> DONE（逐步推进）
  DONE -> 下一步 PENDING
  任一步 FAILED -> COMPENSATING（倒序执行补偿）
  COMPENSATING -> COMPENSATED（终态）

补偿表（本文聚焦扣库存 + 扣款；完整 00 主线可加 T0 下单 <-> C0 取消订单）：
  T1 扣库存   <-> C1 加回库存
  T2 扣款     <-> C2 退款
  对偶性检查：T 与 C 的净效果 = 零
```

**徒弟：**

> 补偿方法怎么保证对偶？代码写得不好怎么办？

**老陈：**

> 靠两件事：**评审 + 测试**。
>
> ```text
> 评审：每个 T/C 对要过"净效果为零"的账
> 测试：补偿路径演练（EX-06 重复注入验证幂等 + EX-04 悬挂路径配合）
> 幂等：sagaId 贯穿所有步骤，重复执行补偿不产生二次效果
> ```
>
> 补偿对偶是业务语义，框架管不了，只能靠组织纪律。

### How：一次失败补偿的时序

```text
① Saga 开始，sagaId 生成，状态 PENDING
② T1 扣库存 -> DONE
③ T2 扣款 -> FAILED
④ 状态 -> COMPENSATING，倒序执行 C2（退款）、C1（加回库存）
⑤ 全部补偿成功 -> COMPENSATED（终态）
⑥ 任一补偿失败 -> 重试；超过上限 -> 死信 + 对账（回链 ddd-05）
```

**超时怎么办：结果未知不能直接补偿。** 如果 T2 扣款超时，编排器并不知道扣款到底成功没有；此时直接走补偿（退款）可能造成“扣款成功 + 退款”的双花。正确顺序是先幂等重试/查询确认（幂等键精确到 `(sagaId, step)`）：

```text
查询确认成功 -> 继续推进或标记 DONE
查询确认失败 -> 才进入补偿
一直无法确认 -> 置为 UNKNOWN，交人工/对账，禁止自动补偿
```

### Transfer：状态机的迁移

1. 任何长流程（审批流、订单流、支付流）都是状态机 + 持久化 + 补偿的变体。
2. "失败处理必须持久化"是长流程系统与 try-catch 的本质区别。
3. 补偿对偶的评审与测试，是业务正确性的最后防线。

本层留下的新账：**Saga 每步都提交了，中间状态对下游可见——超卖、重复怎么防？**下一层看语义锁。

### Level Ending

```text
口诀：状态机持久化，补偿靠对偶。
```

<a id="level-5"></a>

## Level 5：Saga 隔离性与语义锁

一句话认知墙：**Saga 天然无隔离——中间状态可见且可回滚；缓解手段是语义锁 + 幂等键 + 读隔离规则，但永远做不到事务级隔离。**

### 前置知识关卡

- [ ] 知道 Saga 每步独立提交
- [ ] 知道"无隔离"的后果（超卖、重复）
- [ ] 知道预留语义在 Saga 里怎么补

### Why：为什么 Saga 必须处理隔离问题

**徒弟：**

> Saga 不是有补偿吗？补偿兜底不就完了？

**老陈：**

> 补偿兜的是"最终一致"，兜不了"中间可见的脏结果"：
>
> ```text
> T1 扣库存提交后，另一个请求读到库存已减、但订单还没创建（中间态）
> -> 数据在业务上"看起来"是错的（订单不存在却有扣减记录）
> 若 T2 失败回滚补偿，中间态又消失——下游读到的数据前后矛盾
> ```
>
> 更危险的是**中间态被业务利用**：读到"已扣款"就发货，结果补偿把扣款撤销了——钱退了货发了。

### What：语义锁与读隔离规则

```text
语义锁（业务级预留）：
  Saga 中"敏感资源"步骤改用预留语义：
  T1 扣库存 -> 改为"冻结库存"（冻结表，回链 L2）
  C1 加回库存 -> 改为"解冻"（天然对偶）
  -> 中间态是"已冻结"而不是"已扣减"，语义上可解释

幂等键：
  sagaId 贯穿所有步骤，下游消费方按 sagaId 幂等（回链 ddd-05）

读隔离规则：
  下游读取必须过滤"未闭环 Saga 的中间态"（如订单状态未终态不算数）
```

> 📌 术语消歧：本文的“语义锁”指用冻结/预留把中间态变成“可解释”；Seata Saga 官方语境里的 semantic lock 常指业务表上的“处理中”状态字段，防的是同一记录上正向重试与补偿的并发冲突。两者相关但不同，不要混成一个概念。

**徒弟：**

> 语义锁能做成和事务隔离一样吗？

**老陈：**

> 不能。语义锁只是把"不可解释的中间态"变成"可解释的中间态"（冻结比扣减安全），**它减少的是业务危害，不是数据可见性**。Saga 的隔离性天花板就是"语义可解释 + 幂等 + 读规则"，想要完整事务级隔离需要换 XA 这类强同步方案，或对 TCC/AT 做显式读隔离设计；TCC/AT 也只是比 Saga 更可控，并不是天然完整事务隔离。

### Transfer：隔离缓解的迁移

1. "无隔离不是放任不管"——业务语义层可以自造隔离（语义锁、状态机可见性过滤）。
2. 中间态的可解释性（冻结 vs 扣减）是业务设计问题，不是框架问题。
3. 隔离性要求是选型的第一变量：Saga 满足不了事务级隔离。

本层留下的新账：**TCC 和 Saga 都落地完了，B 的场景到底选哪个？**下一层收口。

### Level Ending

```text
口诀：Saga 无隔离，语义锁缓解。
```

## Level 6：TCC vs Saga 落地选型

一句话认知墙：**选型不是二选一，是看业务形态：需要预留语义用 TCC，长流程可逆动作用 Saga，混合场景可以混用。**

### 前置知识关卡

- [ ] 能说出 TCC 与 Saga 的核心区别（预留 vs 补偿）
- [ ] 能说出 TCC 的成本（三方法 + 冻结建模 + 悬挂扫描）
- [ ] 能说出 Saga 的成本（编排器 + 补偿对偶 + 隔离缓解）

### Why：为什么不能"统一用 TCC"

**徒弟：**

> TCC 有预留语义，比 Saga 安全，统一用 TCC 不就行了？

**老陈：**

> TCC 的代价全在"预留建模"：
>
> ```text
> 每个资源都要拆三方法 + 冻结表 + 悬挂扫描
> 纯查询/日志/外部通知类动作没有"预留语义"，强行 TCC 是自找麻烦
> Saga 的补偿对偶对这类动作更自然（占座 -> 释放座位、加积分 -> 扣回积分；不可逆动作如邮件只能做反向通知，不是撤销）
> ```
>
> 反过来，长流程（跨小时/跨天）TCC 的预留资源长期占用，Saga 的逐步提交更适合。**TCC 适合"短事务 + 强预留"，Saga 适合"长流程 + 可逆动作"。**

### What：选型矩阵

| 业务形态 | 首选 | 原因 |
| --- | --- | --- |
| 短事务、资源需要预留（库存/余额） | TCC | 冻结语义天然匹配 |
| 长流程、动作可逆（订单状态流转） | Saga | 逐步提交不长期占用 |
| 混合（短预留 + 长流程） | TCC + Saga 混用 | 按步骤选择 |
| 只改状态 + 发消息 | Outbox/半消息（回链 ddd-05） | 不需要补偿框架 |
| 能合并事务边界 | 边界重构优先（dtx-00 L6） | 最省 |

### How：收口验证清单

```text
① 冻结表/补偿表结构评审（幂等键、状态机、对偶性）
② 悬挂扫描阈值与误报演练（EX-04）
③ 补偿与幂等路径演练（EX-06 重复注入：验证补偿与幂等）
④ 指标就位：补偿执行率、悬挂发现延迟、saga 成功率、对账差异数
```

**徒弟：**

> 上线前最该盯哪个指标？

**老陈：**

> **对账差异数。**它是对补偿、幂等、悬挂、隔离缓解全部机制的总验收——所有机制都失效时，它是最后一张网（回链 ddd-05）。

### Transfer：选型的迁移

1. 方案选型先看业务形态（预留？长流程？可逆？），再看框架能力。
2. "统一方案"是组织方便，不是技术最优——混用是常态。
3. 对账是分布式事务方案的总验收，指标设计必须包含它。

本篇完成 TCC/Saga 落地闭环：机制 → 代码 → 扫描 → 编排 → 隔离 → 选型。下一篇进入生产演练，把"代码正确"验证成"生产可用"。

### Level Ending

```text
口诀：短事务看预留，长流程看补偿。
```

# ⚠️ 坑与细节

<a id="pitfalls"></a>

## 坑 1：幂等靠"先查再写"

错误理解：查一下记录在不在，不在就插入，安全。

原因：并发下两个请求同时查到"无记录"再同时插入，都通过。

比喻后果：两个窗口同时登记同一份预审单，都成功。

线上现象：冻结记录重复、补偿执行两次。

修正：幂等必须落唯一约束（freeze_id 主键），先查再写只是提示。

---

## 坑 2：空回滚返回异常

错误理解：Cancel 找不到记录，说明流程错了，报错让协调者知道。

原因：Try 迟到时 Cancel 必然先到，报错触发重试死循环。

比喻后果：顾客还没登记就要撤销，预审员拒绝办理还反复确认。

线上现象：补偿任务无限重试。

修正：查控制表无记录 -> 写入 SUSPENDED 标记 -> 直接成功返回（幂等安全返回 + 留痕拦截迟到 Try）。

---

## 坑 3：悬挂扫描直接自动清理

错误理解：扫描到超时记录，直接删掉/清理。

原因：误伤正常长事务（人工审批、慢业务），且可能清理了仍在执行的事务。

比喻后果：预审员看登记久未销，直接把预审单撕了——顾客还在办理中。

线上现象：正常业务被中断。

修正：阈值 > 正常路径最长时长；先告警后清理；清理前二次校验全局事务状态。

---

## 坑 4：编排器 = try-catch 反向调用

错误理解：Saga 失败就在 catch 里调补偿方法。

原因：进程重启后补偿链条丢失，长流程无法接续。

比喻后果：预审员下班了，顾客的撤销单没人接。

线上现象：失败后数据不齐，重启后补偿丢失。

修正：编排器持久化 + 状态机 + 补偿表。

---

## 坑 5：补偿方法与正向方法写一样

错误理解：T 和 C 都改同一张表，逻辑差不多。

原因：补偿要求净效果为零，与正向动作对偶，写错就是二次扣减/加错。

比喻后果：撤销时把"加回库存"写成了"再扣一次"。

线上现象：数据越补越乱。

修正：T/C 对偶性评审 + 补偿路径测试。

---

## 坑 6：Saga 无隔离 = 不用管

错误理解：Saga 靠补偿兜底，中间态无妨。

原因：中间态被下游利用（读到已扣款就发货），补偿撤销后钱退货发。

比喻后果：顾客看到材料"已办结"，实际还在撤销流程中。

线上现象：业务按中间态行动，补偿后矛盾。

修正：语义锁 + 幂等键 + 读隔离规则。

---

## 坑 7：补偿失败无限重试

错误理解：补偿失败就一直重试到成功。

原因：永久性失败（数据被删、约束冲突）永远重试不成功，占资源、掩盖问题。

比喻后果：撤销单一直挂着，没人上报。

线上现象：补偿任务堆积，告警失灵。

修正：重试上限 -> 死信 -> 对账（回链 ddd-05）。

---

## 坑 8：TCC 和 Saga 二选一

错误理解：整个系统统一用一种方案。

原因：业务形态不同（短预留 vs 长流程），统一方案是组织方便不是技术最优。

比喻后果：所有业务都走同一套登记流程，不适合的也硬走。

线上现象：不适合的场景成本高、效果差。

修正：按业务形态混合选型（TCC 短预留 + Saga 长流程）。

| T0 | 发起方（B 所在服务） | 生成 freezeId/sagaId，开启全局事务 | ID 全局唯一 | ID 冲突 |
| T1 | 参与者 | Try：条件 UPDATE 校验可用量 + 冻结表 INSERT | 唯一约束 + 原子校验 | 并发超卖 |
| T2 | 参与者 | Confirm：扣减 + 终态 + 控制表 COMMITTED | 状态机单向 + CAS 门在前 | Confirm 失败只能重试 |
| T3 | 参与者 | Cancel：解冻/空回滚 + 控制表留痕 | 空回滚安全返回 | 悬挂残留 |
| T4 | 协调者 | 迟到 Try 按控制表状态处置 | 终态判定 | 悬挂/空回滚 |
| T5 | 扫描任务 | 悬挂检测（二阶段未闭环） | 阈值 > 正常路径 | 误报误伤 |
| T6 | 编排器 | Saga 先确认结果再补偿 | 对偶 + 幂等 | 补偿失败 |
| T7 | 对账 | 总验收 | 差异数 = 0 或可解释 | 静默不一致 |

# 📚 概念勘误表

<a id="errata"></a>

| 错误说法 | 准确说法 |
| --- | --- |
| 幂等靠查重表就行 | 必须唯一约束，查重只是提示 |
| 空回滚要报错 | Cancel 查控制表无记录，写 SUSPENDED 标记后直接成功返回 |
| Try 冲突一律拒绝 | 按控制表状态区分：TRIED/COMMITTED 幂等成功，ROLLBACKED/SUSPENDED 拒绝 |
| Confirm 失败转 Cancel | Try 成功后 Confirm 只能重试，不能转 Cancel |
| 悬挂扫描可以直接清理 | 先告警后清理，防误伤 |
| 悬挂只有“迟到 Try”一个来源 | 经典悬挂指迟到 Try（dtx-00 定义），防御目标是拦截；扫描兜底的残留来自二阶段结果丢失与防御未覆盖，两类常被混称为悬挂 |
| 编排器 = try-catch 反向调用 | 持久化状态机 + 补偿表 |
| 补偿方法和正向方法一样 | 必须对偶（净效果为零） |
| Saga 无隔离不用管 | 语义锁 + 幂等 + 读隔离规则 |
| 补偿失败无限重试 | 上限 -> 死信 -> 对账 |
| TCC 和 Saga 二选一 | 按业务形态混合选型 |

其中两点我以前也讲得过于绝对：

```text
我以前容易把"悬挂扫描"讲成"定时清理任务"；准确说法是扫描只是发现，
清理必须防误伤（阈值 + 二次校验 + 分阶段处置）。
我以前容易把"Saga 无隔离"讲成"不用管"；准确说法是必须做语义锁 + 幂等 + 读隔离规则，
只是永远达不到事务级隔离。
```

# 🏆 生产决策卡

<a id="decisions"></a>

## Decision Card 1：冻结表设计

### 场景

TCC 链路需要预留语义（库存/余额）。

### 判断

预留必须落表；幂等靠 freezeId 唯一约束；防悬挂/空回滚靠事务控制表（globalTxId+branchId 唯一键）。

### Mechanism -> Decision

| 机制 | 工程决策 |
| --- | --- |
| 预留语义 | 冻结表（freezeId 主键） |
| 幂等 | 唯一约束 + 状态机终态判定 |
| 防悬挂/空回滚 | 事务控制表（globalTxId+branchId 唯一键 + SUSPENDED 状态） |
| 撤销锚点 | freezeId 指向冻结记录 |

### 禁止决策

```text
用内存变量做预留；幂等靠先查再写。
```

### 验收指标

```text
冻结记录重复数 = 0
空回滚路径成功率
悬挂残留数
```

---

## Decision Card 2：悬挂扫描阈值

### 场景

TCC 上线后需要悬挂检测。

### 判断

阈值必须 > 正常 Try->Confirm/Cancel 最长路径，发现延迟与误报率权衡。

### Mechanism -> Decision

| 机制 | 工程决策 |
| --- | --- |
| 扫描周期 | 成本 vs 发现延迟（待实测档位） |
| 超时阈值 | 业务 SLO 决定（正常路径 + 安全余量） |
| 误伤防护 | 先告警后清理 + 二次校验 |

### 禁止决策

```text
阈值拍脑袋；扫描直接自动清理。
```

### 验收指标

```text
悬挂发现延迟
误报率
清理成功率
```

---

## Decision Card 3：Saga 编排器

### 场景

长流程业务需要逐步提交 + 补偿。

### 判断

编排器必须持久化，补偿表必须对偶，sagaId 贯穿全链。

### Mechanism -> Decision

| 机制 | 工程决策 |
| --- | --- |
| 状态机 | 持久化，重启可接续 |
| 补偿对偶 | 评审 + 测试 |
| 幂等 | sagaId 贯穿所有步骤 |

### 禁止决策

```text
try-catch 反向调用代替编排器；补偿方法不评审。
```

### 验收指标

```text
saga 成功率
补偿执行率
对账差异数
```

---

## Decision Card 4：Saga 隔离缓解

### 场景

Saga 链路过中间态可见，下游可能利用中间态。

### 判断

语义锁 + 幂等键 + 读隔离规则，降低业务危害，不追求事务级隔离。

### Mechanism -> Decision

| 机制 | 工程决策 |
| --- | --- |
| 敏感资源 | 语义锁（冻结语义） |
| 下游消费 | sagaId 幂等 |
| 读取方 | 过滤未闭环中间态 |

### 禁止决策

```text
把 Saga 当 XA 用（宣称事务级隔离）。
```

### 验收指标

```text
中间态被利用次数（业务探测）
超卖/重复数
对账差异数
```
