> 这不是一篇 Seata 使用教程。
>
> 本文只追踪一个主线：**下单请求 B 走 AT 通道**——B 不想写三个业务方法（TCC），也不想锁三库等裁决（XA），它想知道：Seata AT 是怎么做到"业务无侵入"又能回滚的？

顾客办理业务时，办事员把每次办理自动誊写一份"办前/办后底稿"进登记本；全局复核员负责看有没有别的窗口在同一份材料上动手脚。

```text
| ③ 按底稿还原 / 失败待人工     |  -> 回放 / 待确认
+------------------------------+
```

| 比喻元素 | 技术概念 | 唯一职责 |
| --- | --- | --- |
| 办前/办后底稿 | undo_log（before/after image） | 记录"怎么还原" |
| 自动誊写 | 一阶段写入 undo_log | 与业务 SQL 同本地事务 |
| 本地提交不锁材料 | 一阶段本地提交 | 资源释放，不等全局裁决 |

# 正文：五个 Level 打穿 Seata AT

<a id="level-1"></a>

## Level 1：AT 为什么存在——两种侵入之间的第三条路

一句话认知墙：**XA 侵入的是系统（锁与阻塞），TCC 侵入的是业务（三个方法），AT 想两头都不碰——靠镜像回放。**

### 前置知识关卡

- [ ] 知道 2PC/XA 的 prepare 为什么阻塞（distributed-tx-00 L2）
- [ ] 知道 TCC 三难题与业务侵入（distributed-tx-00 L3）
- [ ] 知道"数据级回滚"与"业务级补偿"的区别

### Why：XA 和 TCC 的侵入各在哪里

**徒弟：**

> dtx-00 说 AT 站在 2PC 和 TCC 之间。2PC 业务无侵入，TCC 业务侵入大但灵活——那 AT 是把两者的优点拼起来了吗？

**老陈：**

> 先看清楚两者的侵入对象：
>
> ```text
> XA 侵入的是"运行方式"：prepare 后所有参与者持锁等裁决，
>   业务代码不用改，但系统被锁、被阻塞、可能悬挂
> TCC 侵入的是"业务代码"：每个资源动作拆成 Try/Confirm/Cancel，
>   业务不锁了，但每个业务都要做冻结语义建模
> ```
>
> AT 想两头都不碰：业务代码不拆（像 XA），也不像 TCC 那样靠业务预留；它只短暂持有数据库行锁，提交后释放，靠镜像回放。它靠的是一笔"自动誊写的底稿"——**每个分支在本地事务里把"改之前是什么、改之后是什么"记下来，提交后释放数据库行锁；如果全局要回滚，按底稿还原**。这就是镜像回放（backward recovery）思想的工程化。
>
> 注意：**释放的是数据库行锁，全局锁（见 Level 3）仍由 TC 持有到全局事务结束**——这正是 dtx-00 谱系图"阻塞风险中"的来源（写热点下后到事务仍会等待）。

| 方案 | 解决什么 | 留下什么问题 |
| --- | --- | --- |
| XA | 业务无侵入 | 系统级阻塞、协调者崩溃悬挂 |
| TCC | 不持锁、可预留 | 业务三方法 + 冻结建模 |
| AT | 业务无侵入 + 不长期持行锁 | undo_log 写放大、全局锁等待、读可见中间态 |

**关键区分：AT 的"回滚"是数据级镜像还原，TCC 的"Cancel"是业务级解冻/撤销。** 前者不关心业务语义，后者必须懂业务语义。这就是为什么 AT 做不到 TCC 的预留能力（比如"锁定库存"在 AT 里只是数据行，没有冻结语义）。

### What：AT 的结构性前提

```text
前提一：每个分支库必须支持本地事务（undo_log 与业务 SQL 同事务写入）
前提二：回滚语义是"还原数据"而不是"执行业务反向动作"
前提三：所有分支提交在全局协调（TC）管理下进行
```

> 📌 最容易被误解的一点：AT 不是"自动执行的 TCC"。TCC 的 Cancel 是业务方法，AT 的回放是数据镜像。业务冻结语义（预留）是 TCC 独有的，AT 给不了。

### How：B 走 AT 的宏观路径

```text
① TM 开启全局事务（拿到全局事务 ID）
② 各 RM 分支执行本地 SQL + 写 undo_log（同一本地事务）
③ 向 TC 注册分支、申请该行全局锁，再本地提交
④ 全局提交：异步批量删 undo_log（提交路径轻）；全局回滚：按 undo_log 反向回放（回滚路径重）
```

**徒弟：**

> 本地事务提交了，别的请求读到的就是新值了——那中间状态谁管？

**老陈：**

> 这正是 AT 和 XA 的本质区别：AT 的一阶段提交意味着**中间状态可见**（谱系图"读可见/写被锁"）。它不追求"全局同一时刻一致"，而是"能回滚 + 挡住并发写冲突"。怎么挡？下一层看镜像，再下一层看全局锁。

### Transfer：镜像思想的迁移

1. 任何"提交后还能撤销"的需求，都可用镜像回放（备份、快照、闪回）。
2. "业务无侵入"的代价必然落在别处（写放大/锁/中间态）——不存在免费午餐。
3. 数据级回滚与业务级补偿的边界，是所有恢复系统设计的第一个问题。

本层留下的新账：**"按底稿还原"——底稿怎么记、记在哪、什么时候记？**下一层看 undo_log 镜像。

### Level Ending

```text
口诀：XA 锁系统，TCC 改业务，AT 靠底稿。
```

## Level 2：一阶段本地提交 + undo_log 镜像

一句话认知墙：**AT 的一阶段是"本地事务提交 + 镜像入库"二合一；回滚的能力不在数据库事务里，而在镜像里。**

### 前置知识关卡

- [ ] 知道本地事务的原子性边界
- [ ] 知道数据库 redo/undo 日志与应用层镜像日志的区别（数据库日志按实现可能记录动作或旧值）

### Why：为什么不能直接靠数据库回滚

**徒弟：**

> 分支库自己就有事务，回滚时让分支库 rollback 不就行了？为什么还要 undo_log？

**老陈：**

> 因为**全局回滚发生时，分支事务早就提交了**。分支库的 rollback 只能回滚"还没提交的事务"，救不了"已经提交的"。
>
> ```text
> 一阶段：分支 SQL 已提交（数据已变）
> 二阶段：全局说"回滚" -> 数据库无法撤回已提交事务
> 所以：必须在提交前把"还原所需的信息"记下来 -> undo_log
> ```

undo_log 记的不是动作，是**状态**：改之前长什么样（before image）、改之后长什么样（after image）。回滚 = 把数据还原成 before image。

### What：undo_log 的最小结构

```text
undo_log 记录（结构细节以 Seata 实际版本为准，待核证）：
  branchId / xid      : 分支与全局事务归属
  rollbackInfo        : before/after 镜像（序列化后的行数据）
  status              : 待回滚 / 已回滚
  与业务 SQL 同事务写入 : 一阶段提交时镜像必须已经落库
```

一阶段的提交形态：

```text
本地事务 = [ 业务 SQL（改数据） + undo_log 写入（记镜像） ] 一起提交
```

> 📌 最容易被误解的一点：undo_log 不是数据库的 redo/undo 日志。它是**应用层为"将来可能的全局回滚"自备的还原信息**，存在业务库里的一张业务表里。

### How：一阶段与二阶段的完整时序

```text
一阶段（每个分支）：
① 执行业务 SQL
② 生成 before/after 镜像，写入 undo_log（与业务 SQL 同一本地事务）
③ 向 TC 注册分支，申请该行全局锁（必须在本地提交【前】拿到）
④ 本地事务提交（数据可见，数据库行锁释放；全局锁仍由 TC 持有）
⑤ 向 TC 上报分支状态

二阶段（全局）：
⑥ 全局提交 -> 异步批量删除 undo_log（提交路径轻）
⑦ 全局回滚 -> 读 undo_log，按镜像反向执行 UPDATE/DELETE/INSERT 还原
   （执行前先校验当前数据 = after image，防止脏写覆盖）
```

**为什么必须先拿全局锁再提交？** 若先提交再拿锁，中间存在一个危险窗口：T2 可能先拿到全局锁并改了同一行；随后 T1 回滚时做 after image 校验必然失败，T2 的正常写入会被误判成脏写，回滚链路瘫痪。先拿锁再提交，才能保证“从修改到全局事务结束”期间其他全局事务进不来，after image 校验在全局事务之间才恒成立。

另外，等全局锁期间，当前分支仍持着本地数据库行锁在等；锁等待超时会触发本地回滚重试。这也是 AT“阻塞风险中”的另一半来源。

**徒弟：**

> 回滚时按镜像反向还原，那如果数据在提交后被别的请求改了，还原不就覆盖别人了吗？

**老陈：**

> 问到了关键点。还原前必须校验"当前数据是否还是我提交后的样子"（与 after image 比对）。不是了，说明数据被别人改过——这就是下一层的脏写检测。

### Transfer：镜像的迁移

1. 数据库闪回、备份恢复的核心都是镜像回放。
2. "提交后需要可撤销"的分布式动作都可以套用"状态镜像 + 反向还原"。
3. 任何"记日志"方案都要回答：记的是动作还是状态？决定能否还原。

本层留下的新账：**一阶段已提交，两个全局事务可能同时改同一行数据。**下一层看全局锁与脏写检测怎么挡。

### Level Ending

```text
口诀：提交即释放，回滚靠镜像。
```

## Level 3：全局锁与脏写检测

一句话认知墙：**全局锁挡的是"全局事务之间的写冲突"；挡不住绕过它的写入——那部分靠镜像比对兜底，兜不住就放弃回滚。**

### 前置知识关卡

- [ ] 知道一阶段提交后数据可见
- [ ] 知道"锁"解决的是写写冲突
- [ ] 知道脏写与脏读的区别（写覆盖才算脏写）

### Why：为什么本地事务提交后还需要锁

**徒弟：**

> 一阶段都本地提交了，数据都生效了，再加锁不是回到 2PC 的阻塞老路了吗？

**老陈：**

> 这个锁和 2PC 的行锁不是一回事：
>
> ```text
> 2PC：prepare 后锁行，锁到全局裁决为止——锁的持有者是自己，时长不可控
> AT 全局锁：写前申请，冲突的另一方（另一个全局事务）等待——锁归属于该全局事务、
>   由 TC 统一维护到全局事务结束；释放的是数据库行锁，不是全局锁
> ```
>
> 需要它的原因很直接：两个全局事务 T1、T2 同时改同一行。T1 一阶段提交后 T2 又改了。T1 全局回滚时按镜像还原，会把 T2 的写入也还原掉——数据丢失。全局锁就是让 T2 在 T1 全局结束前**等**，避免这种覆盖。这个"等"就是 dtx-00 谱系图"阻塞风险中"的由来。

### What：全局锁与脏写检测的分工

```text
全局锁：全局事务之间（T1 与 T2）
   -> 同一行数据的写冲突，由 TC 协调等待
   -> 全局锁是 TC 侧 lock 表里的逻辑锁，key = 资源 + 表名 + 主键值，不是数据库行锁
   -> 代价：写热点下，后到事务等待全局事务结束，这就是"阻塞风险中"的来源
   -> 注意：这个等待是有界重试（lockRetryInterval / lockRetryTimes），
      超过阈值后分支本地事务失败回滚，不是无限阻塞；
      这是 AT 的“中”和 2PC 的“高”最本质的区别

脏写检测：回滚时校验
   -> 当前数据 == after image ? 可以还原 : 数据被外部改过（脏写）
   -> 脏写来源：绕过全局锁的写入
      （本地事务直连、运维改数、非 Seata 客户端写入）
   -> 脏写发生：放弃回滚，标记异常，交人工/对账
```

AT 的读隔离（面试高频）：

```text
默认 = 读未提交：一阶段本地提交后，普通 SELECT 能看到中间态
需要读已提交：
   - SELECT ... FOR UPDATE：查询前先向 TC 申请该行全局锁，
     等相关全局事务定案后才能读到，读到的必然是最终值
   - @GlobalLock：不开全局事务的本地读也可声明拿全局锁（防脏读/脏写）
代价：读也排队全局锁 -> 写热点下读也会阻塞，这是拿读已提交的价格
```

**徒弟：**

> 全局锁都挡了全局事务，怎么还会有脏写？

**老陈：**

> 全局锁管不到"不走全局通道"的写：SQL 客户端直连数据库改数、别的服务不带 Seata 上下文写同一行、运维临时修数据。这些写入对全局锁免疫，只能在回滚时靠镜像比对发现。**全局锁是防君子（全局事务），镜像比对是防小人（非全局写），小人也可能防不住——那时只能放弃回滚。**（回滚失败的处置见下一层）

### How：一次写冲突的完整时序

```text
① T1 开启全局事务，写行 X，申请全局锁，本地提交
② T2 开启全局事务，写行 X，申请全局锁 -> 等待 T1 全局结束
③ T1 全局提交 -> 释放全局锁，异步删 undo_log
④ T2 获得全局锁，继续执行
⑤ 若 T1 全局回滚 -> 校验镜像 -> 还原 -> 释放锁 -> T2 继续
```

### Transfer：锁与校验的迁移

1. "锁"与"校验"是两件事：锁减少冲突概率，校验兜底冲突后果。
2. 分布式锁之外永远要准备"冲突检测"（乐观锁/版本号/镜像比对）。
3. "防君子不防小人"是几乎所有分布式一致性机制的边界。

本层留下的新账：**脏写发生时回滚被放弃——放弃之后怎么办？**下一层看回滚失败与恢复。

### Level Ending

```text
口诀：全局锁防君子，镜像比对防小人。
```

<a id="level-4"></a>

## Level 4：回滚失败与恢复

一句话认知墙：**自动回滚不是"保证回滚成功"，而是"尽量回滚 + 失败有归属 + 兜底能对齐"。**

### 前置知识关卡

- [ ] 知道脏写检测会在什么情况下放弃回滚
- [ ] 知道对账是最终兜底（ddd-05）
- [ ] 知道 2PC 的 in-doubt 状态（prepare 后未裁决，dtx-00 L2）

> 📌 术语区分：本文"待确认"= 已裁决回滚但执行失败的状态；dtx-00 2PC 的 in-doubt = prepare 后协调者未裁决。两者都是"挂起等待处置"，但一个是"回滚没执行完"，一个是"还没决定提交还是回滚"。

### Why：为什么必须假设回滚会失败

**徒弟：**

> AT 叫"自动回滚"，自动两个字听起来就是保证成功。回滚失败的场景多吗？

**老陈：**

> 不多，但必须预案，因为失败的后果是数据不一致：
>
> ```text
> 脏写放弃回滚：分支数据已被外部改过，镜像失效
> 回滚 SQL 执行失败：网络、约束冲突、数据被删
> 协调者故障或状态存储不可达：TC 恢复前全局事务无法推进，分支等待恢复/重试
>   （“状态丢失”只在 TC 持久化存储本身损坏的极端情况下才成立）
> ```
>
> 这些路径概率低，但每一条都意味着"业务已经部分生效"。没有预案，就是静默不一致。

### What：回滚失败后的状态与兜底

```text
状态：分支回滚失败 -> 全局事务进入异常/待确认路径
   -> 人工介入（看数据、核对失败原因，选择继续重试回滚、手工补偿或标记处置）
   -> 或定时重试（失败原因消除后重试回滚）
   -> 最终兜底：对账（源库 vs 目标库差异 -> 补偿任务，回链 ddd-05）
```

回滚失败的处置纪律：

```text
回滚失败必须可见：状态暴露 + 指标 + 告警，不能静默
重试必须有上限：上限后交人工/死信，不能无限重试（回链 ddd-05 L5）
对账是最后一道网：差异数持续为 0 或有解释
```

**徒弟：**

> 那"自动回滚"到底自动在哪？

**老陈：**

> 自动在"正常路径"：镜像生成、回放执行、日志清理都是自动的。**异常路径从来都是人工+对账兜底**——所有分布式事务方案都逃不掉这条尾巴，AT 也不例外。宣称"全自动回滚"是把异常路径的账藏起来了。

### Transfer：失败处理的迁移

1. 任何"自动恢复"机制都要显式回答：恢复失败时状态可见吗？谁兜底？
2. 重试上限 + 死信 + 对账三件套，是所有异步系统的通用兜底（回链 mq-03/ddd-05）。
3. "自动"承诺的边界必须写进 SLO，而不是留在宣传语里。

本层留下的新账：**机制都懂了，但 AT 的成本到底多大——写放大、锁等待、中间态，什么业务付得起？**下一层进入生产决策。

### Level Ending

```text
口诀：自动只在正常路，异常永远要兜底。
```

<a id="level-5"></a>

## Level 5：生产决策——什么时候该用 AT

一句话认知墙：**AT 的适用边界由"写热点、一致性要求、侵入预算"三个变量决定，不是技术栈决定。**

### 前置知识关卡

- [ ] 能说出 AT 的三个成本（undo_log 写放大、全局锁等待、中间态可见）
- [ ] 能区分数据级回滚与业务级预留
- [ ] 知道强一致场景为什么选 XA

### Why：为什么不能"用了 Seata 就完事"

**徒弟：**

> 我们就是 Spring 栈，加个 Seata 注解不就行了吗？

**老陈：**

> 先对着三个变量过一遍：
>
> ```text
> 写热点：同一行被高频改 -> 全局锁等待放大（有界重试，超时后分支失败回滚），吞吐受损（待实测量级）
> 一致性：业务能否接受中间态读可见
>   -> 完全不能接受：XA（AT 默认读未提交；若只是部分读需要最终值，
>      可用 FOR UPDATE / @GlobalLock 换读已提交，但读也吃全局锁）
>   -> 能接受较短预留窗口：TCC
>   -> 能接受较长中间态：AT/Saga/消息
> 预留语义：业务需要冻结/锁定 -> AT 给不了 -> TCC
> ```
>
> 三个变量全过，才轮到"技术栈是否支持"。AT 是"一致性中等 + 写热点低 + 无预留语义"场景的格子，不是万能注解。

### What：AT 适用性矩阵

| 场景特征 | AT 是否适用 | 原因 |
| --- | --- | --- |
| 写热点低、可接受最终一致窗口 | ✅ 适用 | 全局锁竞争小，中间态可容忍 |
| 写热点高 | ⚠️ 慎用 | 全局锁等待放大（待实测） |
| 必须强一致、拒绝中间态 | ❌ 不适用 | AT 默认读未提交；逐条读可用 FOR UPDATE/@GlobalLock 换读已提交，但读也吃全局锁，严格强一致仍选 XA |
| 需要冻结/预留语义 | ❌ 不适用 | 用 TCC |
| 只需"改状态 + 发消息" | ❌ 不必用 | 用 Outbox/半消息（回链 ddd-05） |
| 能合并事务边界 | ❌ 不必用 | 边界重构优先（回链 00 L6） |

### How：上线前的验证清单

```text
① 压测确认 undo_log 写放大与全局锁等待的量级（待实测，experiments EX-07 回填）
② 故障演练：全局事务中杀 TC、杀分支、网络分区（回链 00 L6 场景）
③ 回滚失败路径演练：制造脏写，确认待确认/对账流程生效
④ 指标就位：global_tx_success_rate、undo_log 写入量、锁冲突率
```

**徒弟：**

> 如果演练发现回滚失败路径没人盯，能上线吗？

**老陈：**

> 不能。回滚失败静默 = 数据不一致无人知晓。**回滚失败可见性是对账和人工介入的前提**，没有它就等于没做兜底。

### Transfer：决策的迁移

1. 任何框架选型都先列"代价变量"，再谈功能列表。
2. "自动"能力的边界 = 正常路径自动 + 异常路径预案，缺一不可。
3. 中间态容忍度是一致性选型的第一问，比技术栈重要。

本篇完成 AT 机制闭环：存在理由 → 镜像回放 → 全局锁/脏写 → 失败兜底 → 适用边界。下一篇进入 TCC/Saga 的落地细节，把"机制正确"变成"代码正确"。

### Level Ending

```text
口诀：写热点低、可容忍，才配得上 AT。
```

# ⚠️ 坑与细节

<a id="pitfalls"></a>

## 坑 1：把 AT 当成"自动 TCC"

错误理解：AT 是把 TCC 的三个方法自动化了。

原因：AT 是数据级镜像回放，TCC 是业务级预留补偿；冻结语义 AT 给不了。

比喻后果：自动誊写底稿的办事员，不会"冻结"材料，只会"记录原样"。

线上现象：需要预留的场景（库存锁定）在 AT 下表现为普通行更新，无预留语义。

修正：区分"还原数据"与"撤销业务"，预留语义场景选 TCC。

---

## 坑 2：以为 AT 无侵入 = 零成本

错误理解：业务代码不用改，所以没有代价。

原因：代价转移到了 undo_log 写放大、全局锁等待、中间态可见（待实测）。

比喻后果：誊写底稿不占业务员时间？每笔业务都要多写一份、多一道检查。

线上现象：写入吞吐下降、锁冲突增加（需实测确认量级）。

修正：把 AT 当"有成本的自动回滚"，上线前压测确认代价。

---

## 坑 3：以为一阶段提交后没有中间状态

错误理解：全局事务内所有分支要么全成要么全不成，读不到中间值。

原因：一阶段本地提交后数据已可见，中间态存在（谱系图"读可见/写被锁"）。

比喻后果：B 的订单已生效，但库存扣减还没做——别的顾客已经看到了订单。

线上现象：读到"已下单未扣库存"的中间状态。

修正：业务需容忍中间态；若只是部分读需要最终值，可用 FOR UPDATE/@GlobalLock 换取读已提交，但要接受读也排全局锁；完全拒绝中间态则选 XA。

---

## 坑 4：以为全局锁挡住所有并发写

错误理解：有了全局锁，脏写不存在。

原因：全局锁只挡全局事务之间的写；直连/运维/非 Seata 客户端写绕过它。

比喻后果：复核员只管窗口之间，管不了外面的人直接涂改材料。

线上现象：回滚时镜像校验失败，事务进入待确认。

修正：镜像比对兜底 + 对账 + 运维写库规范。

---

## 坑 5：以为"自动回滚"保证回滚成功

错误理解：AT 二阶段回滚一定会成功。

原因：脏写、回滚 SQL 失败、协调者故障都会让回滚失败。

比喻后果：按底稿还原时发现材料已面目全非，还原不了。

线上现象：数据部分生效、差异靠对账发现。

修正：回滚失败可见 + 重试上限 + 对账兜底。

---

## 坑 6：以为 undo_log 是数据库的 redo/undo 日志

错误理解：Seata 用的 undo_log 就是 InnoDB 的 undo log。

原因：它是应用层为全局回滚自备的镜像表，存在业务库里。

比喻后果：把办事员的誊写底稿当成档案馆的原始登记。

线上现象：排查问题时在错误位置找回滚信息。

修正：undo_log 是业务表，与数据库内部日志是两回事。

---

## 坑 7：以为 Seata 全局事务 = 分布式数据库强一致

错误理解：Seata 保证所有分支同一时刻一致。

原因：AT 是最终一致 + 可回滚，不是同一时刻的强一致。

比喻后果：全局复核员保证"最后能对齐"，不保证"此刻全一致"。

线上现象：中间态被下游读到，业务误判。

修正：按一致性契约选型（强一致用 XA）。

---

## 坑 8：以为 AT 场景不需要幂等

错误理解：事务框架保证不重复，消费方不用幂等。

原因：重试、超时重发、协调者恢复都可能重复执行（回链 ddd-05 幂等结论）。

比喻后果：底稿被誊写两遍，还原执行两次。

线上现象：重复提交/重复回滚。

修正：关键业务动作仍然幂等设计。


## Decision Card 3：回滚失败预案

### 场景

AT 上线后脏写或回滚失败，需要兜底流程。

### 判断

失败可见性 > 自动重试；重试有上限；对账是最后一道网。

### Mechanism -> Decision

| 机制 | 工程决策 |
| --- | --- |
| 回滚失败 | 状态暴露 + 指标 + 告警 |
| 暂时性失败 | 有限重试 |
| 永久失败 | 人工介入 + 对账 |
| 运维直连写库 | 规范 + 校验兜底 |

### 禁止决策

```text
回滚失败静默吞掉，依赖"概率低不会发生"。
```

### 验收指标

```text
回滚失败数（暴露可见）
待确认事务数
对账差异数
处置时效（SLO）
```

# 🌍 跨语言视角

<a id="cross-language"></a>

## Java

```text
Seata AT：TC/TM/RM + undo_log 镜像回放（Implementation 1.x/2.x）
```

## Go


## Rust

```text
无成熟 AT 框架（待核证），

```

## 跨语言仍成立的判断力

```text
已提交事务无法靠数据库回滚，必须自备还原信息（镜像）
"锁"减少冲突概率，"校验"兜底冲突后果——语言无关
回滚失败必须可见，人工+对账是通用兜底
"自动"承诺的边界 = 正常路径自动 + 异常路径预案
```
