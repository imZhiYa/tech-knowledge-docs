# 🧾 分布式事务深度解析：从 2PC 的阻塞死因到最终一致的方案谱系

> 这不是一篇"分布式事务方案对比"清单。
>
> 本文只追踪一个主线：**一次下单请求 B —— 下单、扣库存、扣款，一笔业务动作要同时写三个服务、三个库。**
>
> B 从进入订单服务开始，一路逼出五代方案的生死：
>
> ```text
> 本地事务
>   -> 2PC / XA（同步阻塞，prepare 后悬挂）
>   -> TCC（预留-确认-取消）
>   -> Saga（正转 + 补偿）
>   -> 消息方案（Outbox / 半消息，复用 DB+MQ 原子性）
>   -> 方案谱系与选型收口
> ```
>
> 本文的目标不是让你记住每个方案的 API，而是说清楚：**每一个方案解决了上一代的哪个死因，又留下了什么新的账，最终把"到底怎么选、怎么验证"变成可执行的工程决策。**

# 🏷️ 关键词与主线进度

关键词：

```text
本地事务 | 资源管理器 | 两阶段提交 | XA | 3PC | 阻塞 | 悬挂
TCC | Try-Confirm-Cancel | Saga | 补偿 | 幂等 | Outbox | 半消息
Seata | 全局锁 | undo_log | CAP | 最终一致性 | 对账
```

主线进度：

```text
① B 进入订单服务：本地事务为何跨不过进程边界
② 第一代尝试：2PC/XA 如何制造出"prepare 后的悬挂"
③ 出路一：TCC 把数据库锁换成业务预留
④ 出路二：Saga 正转加补偿；消息方案复用 DB+MQ 原子性
⑤ 没有银弹：方案谱系与选型矩阵
⑥ 生产收口：如何让分布式事务不出现在系统里
```

| 类型 | 本文承诺 |
| --- | --- |
| Specification | 2PC、3PC、Saga 是协议/论文级理论（Sagas，Garcia-Molina & Salem 1987）；X/Open XA 是接口规范；CAP 是分布式系统理论语境，不绑定具体产品 |

| Design Assumption | 主线业务为"下单+扣库存+扣款"三库三服务；单库单服务的本地事务不在本文讨论范围 |

必须区分的五层语义：

```text
本地事务：作用域是单个资源管理器（一个连接、一个库）
分布式事务：一次业务动作跨多个资源管理器的提交决策
协议/规范：2PC、3PC、XA（与实现无关的抽象）
实现：MySQL XA、Seata、RocketMQ 事务消息（具体行为随版本）
业务设计：边界重构、异步化、幂等——让分布式事务不出现
```

# 正文：六个 Level 打穿分布式事务

<a id="level-1"></a>

## Level 1：本地事务为什么跨不过服务边界

一句话认知墙：**`@Transactional` 的作用域只有一个资源管理器——一个连接、一个库；进程边界之外，它管不到任何东西。**

### 前置知识关卡

- [ ] 知道本地事务的 ACID 语义
- [ ] 知道一次 RPC 调用跨进程、跨连接
- [ ] 知道 mq-07 的双写之缝（DB 与 MQ 没有原子性）

### Why：本地事务的边界在哪

**徒弟：**

> 我把下单、扣库存、扣款整个流程包进一个 `@Transactional` 方法里，调库存服务、调支付服务，不都在"一个事务"里吗？失败了全回滚不就行了？

**老陈：**

> 你包住的是一个本地事务，它只管理一个数据库连接（单数据源的默认事务管理器）。扣库存发生在另一个进程、另一个库、另一条连接上——那个库有自己的事务，它感知不到你的事务上下文。你这边 `rollback`，那边的扣减早就提交了，谁也回不了谁。
>
> 更麻烦的是，就算把事务上下文强行传过去，也只会撞上另一个问题：**两个资源管理器之间没有共享的提交决策**。它们在不可靠的网络上各说各话，永远无法用消息交换达成"我们一起提交、要么一起回滚"的确定性共识——这是分布式系统里著名的"两军问题"（更准确地说，是原子提交/协调问题在不可靠通信下的同源困难），也是后续所有方案存在的根本原因。
>
> 两个不可能性需要分清：**两军问题**说的是不可靠信道上共识不可能；这里讨论的是崩溃容错下**非阻塞原子提交不可能**——2PC 能保证原子性，但代价是选择了阻塞。两个命题同源（都是"不可靠通信下的分布式决策"），但不是同一个结论。

| 方案 | 解决什么 | 留下什么问题 |
| --- | --- | --- |
| 本地事务 | 单库原子性、一致性、隔离性、持久性 | 跨库跨服务时没有任何保证 |
| 双写（先写 A 再写 B） | 无——只是两次独立提交，没有一致性保证 | 中间状态：A 成 B 败，或 A 败 B 成 |
| 消息补偿 | 异步对齐 | 延迟、重复、幂等成本（回链 mq-07） |

### What：分布式事务问题的精确形状

问题不是"代码写错了"，而是两个结构性事实：

```text
事实一：每个库只有自己的本地事务，跨库没有共享 undo/redo
事实二：两个进程在不可靠网络上无法达成确定性共识
```

所以"分布式事务"这个名词本身就是一个工程妥协的产物：**你不可能获得"本地事务那样"无条件、不阻塞的强保证，只能在各种妥协方案里选一个。**（2PC 确实能换来强一致，但代价是阻塞与活性丧失——这正是下一层要展开的死因。）

> 📌 最容易被误解的一点："分布式事务"不是一种东西，而是一族方案。2PC、TCC、Saga、消息方案解决的是同一个问题的不同侧面，代价各不相同。

### How：一次 B 在没有方案时的真实结局

```text
① 订单服务本地事务提交：订单已生成（commit）
② 库存服务本地事务提交：库存已扣（commit）
③ 支付服务调用失败 / 扣款超时
④ 订单、库存无法回滚——只能补偿，但此时还没有补偿方案
```

三个库各自 `commit`，没有任何机制能"撤回"①②。这就是 Level 2 要解决的问题：**需要一个全局的提交协议。**

**徒弟：**

> 那给三个库套一个"更大的事务"不行吗？

**老陈：**

> 这个直觉很接近了，这就是 2PC 的思路。但它引入了一个新问题——协调者。让我们去 Level 2 看它怎么死。

### Transfer：边界思想迁移

1. 缓存与 DB 的写入、DB 与搜索引擎的索引同步，本质都是双写问题。
2. 任何"先写 A 再写 B"的代码路径，都隐含中间失败窗口。
3. "事务"这个词只在本地方案里可靠，跨系统时它只是一个营销词。

本层留下的新账：**跨资源原子性需要全局协调。**下一层看第一代方案 2PC/XA 如何协调，以及它为什么死于阻塞。

### Level Ending

```text
口诀：事务边界只到连接，跨库提交无共识。
```

## Level 2：2PC / XA —— 两阶段为何会悬挂

一句话认知墙：**2PC 用"prepare + 两轮 RTT"换来了强一致，代价是 prepare 之后任何一环崩溃，整个业务原地冻结。**

### 前置知识关卡

- [ ] 知道协调者/参与者角色
- [ ] 知道 prepare 是"锁定资源并记录日志"
- [ ] 知道 XA 是规范、2PC 是实现该协调模型的主流协议

### Why：为什么必须有两个阶段

**徒弟：**

> 让三个库各自提交，先提交的等后面的一起提交，不就行了吗？

**老陈：**

> 一阶段做不到"全有或全无"：各参与者独立提交，第一个提交后系统已经暴露了部分状态，第二个失败时无法撤回第一个——除非第一个"还没真正提交"。这就是 prepare 的由来：**每个参与者先做"预提交"（锁资源、写日志、报告准备就绪），等协调者收集到所有人的"就绪"后才广播真正的 commit。** 这样要么全部正式提交，要么全部回滚。

协议结构：

```text
协调者（总柜台牵头人）
    |
    |--- Prepare(所有参与者)
    |       参与者：锁资源 + 写日志 + 回复 Ready / Abort
    |
    |--- 全部 Ready ?
    |       Yes -> Commit(广播)
    |       No  -> Rollback(广播)
    |
    |--- 参与者：正式提交 / 回滚，释放锁
```

### What：2PC 的核心对象与不变量

```text
不变量一：prepare 后参与者持锁，等待最终裁决
不变量二：参与者回复 Ready 之后、收到最终裁决之前，
   无论协调者是否存活、网络是否分区，都不能自行裁决
不变量三：XA RECOVER 能列出 in-doubt（已 prepare 未裁决）事务
```

XA 是规范（X/Open XA），2PC 是实现它的主流协议；MySQL InnoDB 通过 SQL 暴露该能力（Implementation）：

```sql
XA START 'b-1';           -- 订单库
UPDATE orders SET status='PAID' WHERE id=1001;
XA END 'b-1';
XA PREPARE 'b-1';         -- 锁资源，进入 prepared

XA COMMIT 'b-1';          -- 最终裁决
-- 或 XA ROLLBACK 'b-1';
XA RECOVER;               -- 列出 in-doubt 事务（协调者崩溃时排查入口）
```

### How：B 在 2PC 下的时序与死点

```text
① 协调者向订单/库存/支付三库发送 prepare
② 三库各自锁资源、写日志、回复 Ready
③ 协调者广播 commit
④ 三库正式提交，释放锁
```

**死点就在这里：**

```text
② 与 ③ 之间：协调者崩溃
   -> 三库都已锁资源，无人知道该提交还是回滚
   -> 只能等协调者恢复（XA RECOVER 里躺着 in-doubt）
   -> 资源一直被锁，业务被冻结
阻塞不止来自崩溃：协调者活着但与参与者网络分区，同样冻结
   -> 参与者收不到裁决，也联系不上协调者，按不变量二仍不能自行裁决
   -> 冻结的根源是"等待最终裁决"这件事本身，而不是"谁坏了"
```

**徒弟：**

> 协调者崩了，重新选举一个不就行了？

**老陈：**

> 新协调者不知道旧协调者是否已经把 commit 发给过部分参与者，因此无法在保证一致性的前提下自行裁决提交或回滚；唯一安全路径是恢复旧协调者的日志或等待其恢复——这就是"阻塞"。3PC 引入超时和 pre-commit 阶段降低阻塞概率，但网络分区下会出现"部分提交"，**连一致性都保不住了**。这不是实现 bug，是协议层面的结构性问题（待验证：3PC 部分提交的具体失败窗口在教材结论范围内，真实实现极少，生产主流仍以 2PC/XA 为准）。

| 方案 | 解决什么 | 留下什么问题 |
| --- | --- | --- |
| 2PC/XA | 跨库强一致 | 阻塞、协调者单点、锁持有时间长 |
| 3PC | 降低阻塞概率 | 分区下可能部分提交，一致性丧失 |

性能代价是结构性的：两轮 RTT、每个参与者锁住资源直到全局裁决（锁持有时长与吞吐、延迟的数字影响待实测）。

### Transfer：2PC 思想的迁移

1. 任何"先询问、后执行"的分布式协议都有投票窗口风险。
2. 数据库两阶段提交 = 分布式系统里"先锁定再裁决"的通用原型。
3. "等待不可能恢复的裁决"这个问题，出现在所有分布式协调场景（如共识算法里的旧 leader 问题）。

本层留下的新账：**同步等待 + 阻塞是结构性死因。**必须放弃"所有参与者同一时刻达成共识"的幻想，允许"部分完成、事后修正"。下一层看 TCC 如何用业务预留替代数据库锁。

### Level Ending

```text
口诀：prepare 之后一崩，全局冻结没商量。
```

<a id="level-3"></a>

## Level 3：TCC —— 把数据库锁换成业务预留

一句话认知墙：**TCC 把"锁数据库行"换成"锁业务资源"（冻结额度、锁定库存），让每个参与者有明确的 Try/Confirm/Cancel 三态动作，悬挂窗口缩小但没消失。**

### 前置知识关卡

- [ ] 知道 2PC 的 prepare 阶段为什么要锁资源
- [ ] 知道"冻结"和"扣减"是两个动作
- [ ] 知道网络重试会让任何一次调用重复到达

### Why：为什么不能照抄 2PC 的锁

**徒弟：**

> TCC 不就是把 prepare 改名叫 Try、commit 改名叫 Confirm 吗？那和 2PC 有什么区别？

**老陈：**

> 区别在锁的对象。2PC 的 prepare 锁的是数据库行，锁多久取决于协调者多久能恢复；TCC 的 Try 锁的是**业务语义**——扣款 Try 是"冻结 100 元"，不是"锁住余额行"。冻结记录和真正的扣减是两件事，Cancel 是明确的业务反向操作，能把冻结记录解冻，不需要像 2PC 那样一直持有数据库行锁等协调者恢复。但如果协调者崩溃导致 Cancel 根本没发出来，Try 的预留记录仍可能悬挂，需要超时/对账兜底。这就是为什么 TCC 在协调者崩溃时不会把整条链路冻结，但仍要防悬挂。
>
> 但代价是：**业务必须自己实现三个方法，并且要处理三个新的魔鬼。**

### What：TCC 三动作与三难题

三个动作：

```text
Try     ：预留资源（冻结 100 元、锁定库存 5 件），写入预留记录
Confirm ：正式生效（真正扣走 100 元、扣掉 5 件），清理预留记录
Cancel  ：取消（解冻 100 元、释放 5 件），清理预留记录
```

三个结构性难题（顺序可能颠倒、重试可能重复）：

```text
空回滚：Cancel 先到，但 Try 从未执行（Try 消息丢失）
   -> Cancel 查控制表无记录，写一条"已回滚"标记再返回成功（不能报错）
   -> 这条标记是拦截迟到 Try 的唯一依据
悬挂：Try 消息延迟到达；协调者已判定失败并先执行了 Cancel，Cancel 已完成
   -> 迟到的 Try 后到，若没有控制表标记，又会写入预留记录
   -> 预留记录无人清理，资源被永久挂起
   -> 拦截手段：Try 第一步先向事务控制表 insert（唯一键 globalTxId+branchId），
      插入冲突 = 该事务已被处理过（Cancel 已留痕或 Try 已执行）-> 拒绝执行
幂等：Confirm/Cancel 因网络重试可能执行多次
   -> 以控制表记录（globalTxId+branchId）为幂等键，重复执行结果一致
```

预留记录表（冻结表）+ 事务控制表示意：

```java
class FrozenAccount {
    Long freezeId;      // 业务预留记录 ID（Confirm/Cancel 重试时用它幂等）
    String accountId;
    BigDecimal amount;  // 冻结金额
    int status;         // FROZEN / CONFIRMED / CANCELLED
    String globalTxId;  // 归属的全局事务
}

class TccControlRow {           // 事务控制表（Seata 的 tcc_fence_log 即此物）
    String globalTxId;          // 唯一键（与 branchId 联合）
    String branchId;            // 唯一键
    int status;                 // 含 SUSPENDED：拦截迟到的 Try
}
```

注意：这里要区分“ID 值”和“落库记录”：**freezeId 的值可以由发起方在调用 Try 前预先生成，但对应的冻结记录（DB 行）只在 Try 执行后存在；空回滚场景下这条记录根本不存在**。所以防悬挂的键是 `globalTxId+branchId`，不是 freezeId。前者拦"这个事务是否已被处理过"，后者只做"预留记录的去重"。

### How：B 在 TCC 下的完整时序

```text
① 协调者生成 globalTxId+branchId；Try 第一步：向控制表 insert（唯一键）
② 插入冲突 -> 已被处理过（Cancel 已留痕或 Try 已执行）-> 拒绝/幂等返回
③ 插入成功 -> 写冻结记录（freezeId）-> Try 冻结余额 100（支付库）、锁定库存 5（库存库）
④ 全部 Try 成功 -> 协调者广播 Confirm（真正扣减+扣库存）
⑤ 任一 Try 失败 -> 协调者广播 Cancel（解冻+释放）
⑥ Confirm/Cancel 均按控制表记录幂等，可安全重试
```

**徒弟：**

> Cancel 和 Try 同时到怎么办？谁会先执行？

**老陈：**

> 顺序无法保证，所以两个方向都要靠"写"而不是"查"来防御：
>
> ```text
> Try 第一步：向事务控制表 insert（唯一键 globalTxId+branchId）。
>   插入冲突 = 已被处理过（Cancel 已留痕或 Try 已执行）-> 拒绝。
> Cancel 第一步：查控制表。无记录 = Try 未执行或还在路上（无法区分）->
>   写入一条"已回滚"标记记录，再返回成功。这条标记是拦截迟到 Try 的唯一依据。
> ```
>
> 纯"查"是防不住的：空回滚场景 Try 根本没执行过、没有任何记录——Cancel 查完没记录就返回，迟到的 Try 再来查也查不到任何标记，照样执行，悬挂照旧发生。这两条是 TCC 落地最容易漏的边界——漏一条，线上就出现"资源挂起"或"解冻失败"（悬挂的具体检测手段：以全局事务 ID 扫描冻结记录，超时未终态即告警，待实测确认超时阈值）。

业务侵入是 TCC 的硬成本：**每一个被协调的资源动作都要拆成三个方法 + 预留表 + 幂等键。** 有些资源天生不好冻结（例如"发送短信"），TCC 就不适用。

| 方案 | 解决什么 | 留下什么问题 |
| --- | --- | --- |
| 2PC/XA | 跨库强一致 | 阻塞、单点、锁持有 |
| TCC | 协调者崩溃不冻结链路 | 三难题、业务侵入大、冻结语义难建模 |

### Transfer：TCC 思想的迁移

1. 库存锁定、座位预留、余额冻结：业务里本来就存在的"预留"概念，正好映射 TCC。
2. 抢购场景的"锁定名额"与"确认购买"天然是 Try/Confirm。
3. 任何"先占位、后兑现"的业务模式都可以用 TCC 思路建模。

本层留下的新账：**冻结语义难建模的资源（如不可逆动作）不能用 TCC；且每多一个参与者，三难题就多一份。**下一层看更轻的 Saga 顺序补偿，以及复用既有 DB+MQ 原子性的消息方案。

### Level Ending

```text
口诀：预留换锁，三难题防，侵入为代价。
```

## Level 4：Saga 与消息方案 —— 异步修正的两条路

一句话认知墙：**Saga 用"正转序列 + 逆序补偿"换取不阻塞，代价是没有隔离性、补偿要严格对偶；消息方案则把"DB+MQ"的原子性复用到极致，但只覆盖"一个本地事务 + 一次投递"这一种原子性。**

### 前置知识关卡

- [ ] 知道"补偿"和"数据库回滚"是两回事（回链 ddd-05）
- [ ] 知道 at-least-once 投递与幂等消费（回链 mq-03/ddd-05）
- [ ] 知道 Outbox 和半消息的机制（回链 ddd-05 / mq-07）

### Why：为什么还要第三条路

**徒弟：**

> TCC 已经能把资源预留做得不错了，Saga 不就是没有预留、直接执行，失败倒着撤销吗？这不是更不严谨？

**老陈：**

> 恰恰相反，Saga 换来的东西是 TCC 给不了的：**参与者不需要实现预留语义，只需要业务上可逆。** 下单→扣库存→扣款，正向执行；扣款失败，倒着补偿"释放库存→取消订单"。对业务方来说，正向和补偿都是正常业务方法，比 Try/Confirm/Cancel 三方法轻得多。但代价是**没有隔离性**：正向步骤之间，其他事务可能看到中间状态。

### What：Saga 的两种形态与约束

```text
编排（Orchestration）：中央协调器（状态机）依次指挥正向步骤、逆序触发补偿
协同（Choreography）：各服务监听事件自行执行下一步（回链 ddd-02 事件协作）
```

Saga 的约束：

```text
补偿与正向严格对偶：T2 的补偿 C2 必须恰好撤销 T2 的效果
补偿必须幂等：网络重试下补偿可能执行多次
不可逆动作不能补偿：发短信、发邮件、外呼——只能前置预留或接受风险
无隔离性：需要语义锁 / 幂等键缓解并发读中间态
```

Saga 编排器示意（**同步伪代码示意**：真实编排是持久化状态机，见 dtx-02 Level 4）：

```java
class OrderSaga {
    // 正向：下单 -> 扣库存 -> 扣款
    // 失败点：扣款失败
    // 补偿：C2 释放库存 -> C1 取消订单
    void run(OrderCmd cmd) {
        try {
            orderService.create(cmd);        // T1
            inventoryService.deduct(cmd);    // T2
            paymentService.charge(cmd);      // T3
        } catch (ChargeFailed e) {
            inventoryService.release(cmd);   // C2 幂等
            orderService.cancel(cmd);        // C1 幂等
            throw new SagaRolledBack(cmd.id());
        }
    }
}
```

### What：消息方案 —— 复用 DB+MQ 的原子性

Saga 还有一条姊妹路：**当分布式事务的形态恰好是"一个库 + 一个 MQ"时，根本不需要全局协调**——把"待发事件"写进本地事务（Outbox，国内常说"本地消息表"），或用半消息两阶段 + 回查（RocketMQ），这两种机制各自复用了"状态变更"一侧既有的事务原子性。机制细节回链 `ddd-05`（Outbox）与 `mq-07`（半消息与双写之缝），本文只讲边界：

```text
适用：状态变更 + 发消息（DB+MQ 双写，单条原子性）
边界一：单条事务消息只保证"一个本地事务 + 一次投递"的原子性；
   多个 Outbox 串联（订单库+Outbox -> 事件 -> 库存库+Outbox -> ...）
   等价于协同 Saga——只能正向推进，没有补偿回滚
边界二：只保证"事件被投递"，消费方业务结果仍要靠幂等与对账（回链 ddd-05）
边界三：事务消息不是通用分布式事务（回链 mq-07 神话⑨）
本质边界是"无补偿语义"：消息被消费后，事件链里没有反向撤销的通道
```

中文面试语境常被单列的一格：**最大努力通知**（best-effort notification）——不做原子性，靠定时重试 + 对账最终把事件送达，是最便宜的一种"异步对齐"，代价是延迟与重复不可控。

**徒弟：**

> 那 Saga 和消息方案哪个更好？

**老陈：**

> 它们解决的不是同一个问题：Saga 解决"多个服务都要执行业务动作"；消息方案解决"一个服务改状态 + 一个 MQ 投递事件"的原子性。把 B 拆开看——下单改订单库 + 通知积分系统，这是消息方案；下单 + 扣库存 + 扣款三个库都要改，这才是 Saga 的领域。方案之间的边界，就是业务动作的边界。

| 方案 | 解决什么 | 留下什么问题 |
| --- | --- | --- |
| Saga | 多服务顺序执行 + 可逆补偿 | 无隔离性、补偿对偶成本、不可逆动作无解 |
| 消息方案 | 单条 DB+MQ 双写原子性 | 无补偿语义；事件链串联等价协同 Saga，消费侧幂等成本 |
| TCC | 预留型多资源协调 | 侵入大、冻结难建模 |
| 2PC/XA | 跨库强一致 | 阻塞、单点 |

### Transfer：Saga 思想的迁移

1. 长流程业务（下单→出库→配送→签收）天然是 Saga 序列。
2. "正向执行 + 逆序补偿"也可用于单个应用内的多步骤操作。
3. 事件驱动架构里的"补偿命令"模式，是 Saga 在消息世界的投影。

本层留下的新账：**每个方案都各自为政，边界靠经验判断。**下一层把全部方案放进一张谱系图，回答"什么场景选什么"。

### Level Ending

```text
口诀：Saga 倒着退，消息只对 MQ，各有边界。
```

## Level 5：方案谱系与选型矩阵

一句话认知墙：**所有分布式事务方案躺在同一条轴上——越靠左一致性越强、越阻塞，越靠右越可用、越异步；选型是选"业务能接受的一致性契约"，不是选"最流行的框架"。**

### 前置知识关卡

- [ ] 能说出 2PC/TCC/Saga/消息方案各自的死因
- [ ] 知道 CAP 语境下"分区时在 C 与 A 之间选边"
- [ ] 知道 Seata 有 AT/TCC/Saga/XA 四种模式（Implementation）

### Why：为什么没有银弹

**徒弟：**

> 网上都说大厂用 Saga，我们也用 Saga 不行吗？

**老陈：**

> 大厂的"Saga"通常同时依赖幂等、对账、事件溯源才能兜底，不是框架替你扛。**一致性契约决定方案，不是方案决定业务。** 你的业务能容忍"扣款成功但库存扣减延迟 10 秒"吗（举例示意，非基准数字）？如果能，Saga/消息方案可用；如果不能，你只能在阻塞（2PC/XA）或业务预留（TCC）里选。这条轴上的每一格，都对应不同的成本。

### What：一张谱系图

```text
一致性强度       ←————————————————→         可用性强度
方案           2PC/XA      Seata AT     TCC         Saga        Outbox/半消息
形态          (同步阻塞)  (回滚日志)  (业务预留)  (正转+补偿)  (DB+MQ 复用原子性)
阻塞风险       高          中          低          无阻塞      无阻塞
业务侵入       无          自动        三方法拆解   正/补偿成对  幂等消费
中间状态       无          读可见/写被锁 短窗口      长窗口      长窗口
协调者         必须        必须        必须        可选/编排    无
```

谱系不是排行榜，是**成本阶梯**：往右走，一致性变弱、侵入变轻、可用性变好。

阻塞风险分级的依据：

```text
高：2PC/XA，prepare 后持数据库行锁，协调者崩溃即悬挂
中：Seata AT，一阶段本地提交，但全局锁/锁等待仍可能阻塞写入
低：TCC，业务预留可被 Cancel 主动释放，但悬挂窗口仍存在（见 Level 3 三难题）
无：Saga 与消息方案，没有跨库锁，以最终一致为代价
```

"中间状态"行的依据：

```text
2PC/XA：prepare 未提交前所有参与者都未生效，无中间状态
Seata AT：一阶段已本地提交，其他事务"读"可见中间态，全局锁只挡"写"不挡"读"
TCC：Try 冻结可见，Confirm 前是"已预留未生效"的短窗口
Saga / 消息：正向步骤逐步生效，中间状态持续整个流程窗口
```

### How：Seata AT 的定位（Implementation）

Seata 的 AT 模式站在 2PC 与 TCC 之间：一阶段在本地事务里提交业务 SQL 并写 undo_log（回滚日志），二阶段全局提交直接删日志、全局回滚则按日志反向回放。它把"回滚逻辑"自动化了，业务侧接近无侵入（Implementation 细节：全局锁与脏写检测、undo_log 的写放大成本，均以 Seata 1.x/2.x 实际版本为准，性能影响待实测）。

Seata 三角色（架构级，类名/实现以实际版本为准）：

```text
TC（Transaction Coordinator）：独立协调器，管理全局事务状态与全局锁
TM（Transaction Manager）：发起方，开启/提交/回滚全局事务
RM（Resource Manager）：分支注册 + 本地事务执行 + undo_log 写入
```

选型矩阵：

| 场景特征 | 推荐 | 原因 |
| --- | --- | --- |
| 跨库强一致、量小、可容忍锁持有 | 2PC/XA | 数据库原生，语义最强 |
| 侵入低、已有 Spring 技术栈、一致性中等 | Seata AT | 自动回滚日志，业务不改 |
| 资源天然可预留（余额/库存/座位） | TCC | 冻结语义与业务一致 |
| 长流程、补偿可逆、允许中间状态 | Saga | 最灵活 |
| 状态变更 + 发消息 | Outbox / 半消息 | 复用既有原子性，无协调者 |

**徒弟：**

> CAP 说"只能三选二"，所以分布式事务本质是无解？

**老陈：**

> 精确的说法是：CAP 不是"任何时候都只能三选二"——没有分区时 C 和 A 可以兼得，只有网络分区时才需要在 C 与 A 之间选边：2PC 系选"一致"（代价是阻塞时的不可用），异步补偿系选"可用"（代价是最终一致）。"三选二"是常见简化说法，不是 CAP 的核心。实践中几乎所有系统都会遭遇分区，所以选边是常态，不是例外。

### Transfer：谱系思想的迁移

1. 缓存一致性方案（旁路/双删/延迟双删）也可以画在"强同步→最终一致"轴上。
2. 所有"选型"问题本质是"先定义你接受的一致性契约，再找成本最低的实现"。
3. 框架是落点，不是起点；先画轴，再选格子。

本层留下的新账：**选型之后是生产验证。**下一层回答：上线前怎么演练、上线后盯什么指标，以及最关键的——如何让 B 根本不需要分布式事务。

### Level Ending

```text
口诀：先定一致契约，再找最便宜格子。
```

## Level 6：生产收口 —— 如何少用分布式事务

一句话认知墙：**最高级的分布式事务用法，是让它不出现在系统里；当它必须出现时，用谱系选型 + 演练 + 指标让它可控。**

### 前置知识关卡

- [ ] 能画出完整谱系
- [ ] 知道对账、幂等、重试是异步方案的兜底
- [ ] 知道故障演练是验证分布式行为的唯一手段

### Why：为什么先想"不做"

**徒弟：**

> 我们业务就是要跨三个库，是不是直接上 Seata 就完了？

**老陈：**

> 先问三个问题：这三个状态**必须**同时可见吗？能不能合并进一个服务、一个库？能不能把"扣库存"变成异步事件，让业务容忍最终一致？分布式事务的每一项能力都有成本——锁、日志、补偿、对账、演练。**能用边界设计消灭的问题，不要用协议解决。**

### What：三道减负手段

```text
边界重构：把需要原子性的状态放进同一库/同一服务（聚合、单写服务）
异步化：RPC 改事件（回链 ddd-05 的事件链路）
幂等 + 重试 + 对账：让任何一次失败都可安全重放（回链 mq-03 投递语义）
```

### How：上线与验证

故障演练（必须真实执行）：

```text
场景一：全局事务执行中杀掉协调者 -> 观察 in-doubt 数与恢复流程
场景二：参与者 A 收到 prepare 后宕机 -> 观察锁持有时长与恢复
场景三：网络分区（模拟库不可达）-> 观察阻塞/补偿行为
场景四：重复发送 Confirm/Cancel -> 观察幂等结果
场景五：对账任务 -> 观察差异数与补偿执行率
```

指标（可监控的具体项）：

```text
xa_in_doubt_count（in-doubt 事务数，协调者恢复预算）
global_tx_success_rate（全局事务成功率）
compensation_execution_rate（补偿执行率）
compensation_pending_count（补偿积压）
reconcile_diff_count（对账差异数）
prepared_lock_hold_ms（prepare 锁持有时长，待实测）
```

⚠️ XA 还有一个比“锁持有时长”更早触发的生产坑：**XA 事务从 PREPARE 到最终 COMMIT/ROLLBACK 必须独占一条数据库连接，不能还给连接池**。并发量稍高时连接池可能先于行锁被耗尽。选 XA 前必须给 XA 链路预留独立连接池/限制并发，并把连接占用时长纳入压测。

**徒弟：**

> 如果这些指标一直为 0，是不是就安全了？

**老陈：**

> 一直为 0 恰恰说明你没有演练过故障路径。指标的价值在于**故障时能快速归因**，而不是证明"没出过事"。把"in-doubt 恢复时长"、"补偿成功率"作为上线门槛，比任何架构评审都有说服力。

### Transfer：收口思想迁移

1. 缓存一致性、搜索索引同步、跨域事件：先想"能不能不跨"，再想"跨了怎么补偿"。
2. "用协议兜底"永远是最后手段，边界设计是第一手段。
3. 生产可信度 = 演练路径 × 可观测性，不依赖任何框架的"保证"。

本层收口：从 B 进入订单服务开始，到"协调者崩溃时的悬挂"，到"三难题、补偿对偶、消息边界"，到"谱系选型与验证"，因果链已闭环：**分布式事务的完整问题是"多资源提交决策"，它的完整答案是"先重构边界，再按一致性契约选最便宜的格子，最后用演练和指标让它可观测"。**

### Level Ending

```text
口诀：先改边界，再选谱系，最后演练。
```

# ⚠️ 坑与细节

<a id="pitfalls"></a>

## 坑 1：把 `@Transactional` 当跨库解决方案

错误理解：一个大方法包住所有远程调用就原子了。

原因：本地事务作用域只有单个连接；远程调用另一端是独立事务。

比喻后果：受理处以为一张总单据管了三个部门，其实仓储部、财务部各自记各自的账。

线上现象：扣款失败但订单、库存已提交，数据对不上。

修正：认清边界，按谱系选方案。

---

## 坑 2：相信 2PC 就是"分布式事务的标准答案"

错误理解：面试背完 2PC 就等于掌握了分布式事务。

原因：2PC 是代价最重的一格（阻塞、单点），不是默认选择。

比喻后果：总柜台把所有部门锁在预审状态，牵头人一离职全部冻结。

线上现象：in-doubt 事务堆积，资源被锁。

修正：先问一致性契约，2PC 只是谱系左端一格。

---

## 坑 3：把 XA 规范和 2PC 协议混为一谈

错误理解：XA 就是两阶段提交。

原因：XA 是接口规范（X/Open），2PC 是实现该协调模型的主流协议；"版本行为"要按具体实现查。

比喻后果：把"办事规则"和"某个办事员的习惯"当成一回事。

线上现象：跨实现排查 in-doubt 时找错位置。

修正：规范与实现分层标注（本文 Level 2 的边界表）。

---

## 坑 4：以为 3PC 彻底解决了阻塞

错误理解：3PC 不阻塞，所以比 2PC 好。

原因：3PC 只是降低概率，网络分区下会出现部分提交。

比喻后果：三个部门各自"超时自动盖章"，结果章盖了一半。

线上现象：极端情况下数据部分提交（生产实现极少，主流仍是 2PC/XA，待验证）。

修正：3PC 是理论改进，不是工程银弹。

---

## 坑 5：以为 TCC 就是"写三个方法"

错误理解：把业务方法拆成 Try/Confirm/Cancel 就完事。

原因：三难题（空回滚、悬挂、幂等）才是 TCC 的主体工程。

比喻后果：财务部 Cancel 到了却不知道这笔款"没冻结过"，直接报错；或冻结记录没人清理。

线上现象：资源挂起、解冻失败、幂等冲突。

修正：预留表 + 幂等键 + 空回滚/悬挂双向防御（防御靠"写"控制表，见 Level 3 How）。

补充一条蚂蚁 TCC 实践里的经典追问：**Confirm/Cancel 不允许返回业务失败，只能重试**——Try 全部成功后事务必须提交，不能改走 Cancel；Cancel 一旦触发也必须执行到底。业务校验失败要发生在 Try 阶段，而不是把"不能提交"甩给 Confirm。

---

## 坑 6：以为 Saga 就是"倒着调用一遍"

错误理解：补偿方法把正向方法换个方向调用。

原因：补偿要与正向严格对偶且幂等；不可逆动作（短信、外呼）根本不能补偿。

比喻后果：部门把"撤销"做成"重新办理一遍"，越撤越乱。

线上现象：补偿重复执行、补偿与正向效果叠加。

修正：补偿对偶表 + 幂等 + 不可逆动作前置预留。

---

## 坑 7：以为事务消息 = 通用分布式事务

错误理解：用了 RocketMQ 事务消息就解决了跨库问题。

原因：半消息只保证"一个本地事务 + 一次投递"的原子性，事件链串联时等价协同 Saga，没有补偿回滚；消费方业务结果仍要幂等（回链 mq-07 神话⑨）。

比喻后果：部门登记本只能解决"本部门登记+通知专员"，跨部门协调它管不了。

线上现象：多资源管理器场景下事件乱序、结果不一致。

修正：消息方案只用于 DB+MQ 场景。

---

## 坑 8：以为"最终一致"就是"随便多久"

错误理解：异步方案 + 最终一致 = 不用设时间窗口。

原因：最终一致必须有业务容忍度边界和观测手段（回链 ddd-05 L6）。

比喻后果：三个部门说"最后会对上"，但没人定义多久对、怎么查。

线上现象：差异长期存在，无人告警。

修正：对账窗口 + 差异指标 + 补偿任务。

---

## 坑 9：以为 AT 模式"零成本"

错误理解：Seata AT 无侵入所以无成本。

原因：undo_log 写放大、全局锁、脏写检测都有代价（Implementation，性能影响待实测）。

比喻后果：自动誊写副本的办事员省了人工复核，但每笔业务都要多誊写一份回滚底稿、多接受一道检查。

线上现象：写入吞吐下降、锁冲突增加（需实测确认量级）。

修正：把 AT 当"有成本的自动回滚"，不是"零成本"。

---

## 坑 10：以为选型 = 选框架

错误理解：选个流行框架，分布式事务就解决了。

原因：一致性契约、业务形态、运维能力决定方案；框架只是落点。

比喻后果：别的银行用总柜台制很好，不代表你的网点适合总柜台制。

线上现象：框架引入后业务代码被迫改造、故障演练缺失。

修正：先画谱系选格子，再选框架，最后演练验证。

# 📚 概念勘误表

<a id="errata"></a>

| 错误说法 | 准确说法 |
| --- | --- |
| 分布式事务是一个方案 | 是一族方案：2PC/TCC/Saga/消息，各付各的代价 |
| `@Transactional` 能跨库 | 它只管理一个连接，跨库没有共享提交决策 |
| 2PC 保证强一致 | 协调者崩溃时会悬挂，一致性以阻塞为代价 |
| XA 就是两阶段提交 | XA 是接口规范，2PC 是实现该模型的主流协议 |
| 3PC 解决阻塞 | 只降低概率，分区下会部分提交 |
| TCC = 三个方法 | 三难题（空回滚/悬挂/幂等）才是主体 |
| Saga = 反向操作 | 补偿要严格对偶、幂等，不可逆动作无法补偿 |
| 事务消息解决分布式事务 | 单条消息只保证"一个本地事务+一次投递"；事件链串联等价协同 Saga，无补偿语义（回链 mq-07） |
| 最终一致 = 无限延迟 | 必须有时间窗口、指标、对账 |
| AT 模式零成本 | undo_log/全局锁/脏写检测都有代价，待实测 |
| 选框架 = 选方案 | 先定一致性契约，再选谱系格子，框架只是落点 |
| "悬挂"只有一种 | 两个机制共用一个词：Level 2 in-doubt 悬挂 = prepare 后未裁决、等协调者；Level 3 TCC 悬挂 = Try 迟到、Cancel 已完成、预留记录无人清理。前者是协议阻塞，后者是消息乱序，解法完全不同 |

其中两点我以前也讲得过于绝对：

```text
我以前容易把 2PC 讲成"强一致的唯一实现"；准确说法是它是一致性最强、阻塞最重的一格，且协调者崩溃时照样悬挂。
我以前容易把 Seata AT 讲成"无侵入自动补偿"；准确说法是它自动做回滚日志回放，但 undo_log 写放大与全局锁检测是真实成本。
```

# 🏆 生产决策卡

<a id="decisions"></a>

## Decision Card 1：跨库强一致，用不用 MySQL XA

### 场景

跨库转账、账务系统，量级低、可容忍锁持有，业务拒绝"最终一致"。

### 判断

量小 + 强一致 + 可接受阻塞窗口 → XA；否则一律往下走。

### Mechanism -> Decision

| 机制 | 工程决策 |
| --- | --- |
| 必须强一致、量小 | XA（XA RECOVER 管 in-doubt） |
| XA 连接占用 | 预留独立连接池/限制并发，连接占用时长纳入压测 |
| 可接受最终一致 | TCC/Saga/消息 |
| 量级高 | 边界重构，尽量不做分布式事务 |

### Code

```text
XA START/PREPARE/COMMIT 三库
XA RECOVER 排查 in-doubt
协调者恢复预案：人工或工具解析事务日志
```

### 禁止决策

```text
对高吞吐链路用 XA，然后宣称"强一致零成本"。
```

### 验收指标

```text
xa_in_doubt_count
prepared_lock_hold_ms（待实测）
global_tx_success_rate
错误率、恢复演练时长
```

---

## Decision Card 2：侵入低、一致性中等，用 Seata AT

### 场景

Spring 技术栈、业务不想拆三方法、一致性要求高于消息方案。

### 判断

先确认 undo_log 与全局锁的成本可接受（待实测），再选 AT。

### Mechanism -> Decision

| 机制 | 工程决策 |
| --- | --- |
| 一阶段本地提交 + undo_log | 全局回滚自动回放 |
| 全局锁/脏写检测 | 高并发写热点慎用 AT |
| 业务有预留语义 | 换 TCC |

### Code

```text
@GlobalTransactional 开启全局事务
分支注册/undo_log 由 RM 自动处理
回滚失败 -> 人工介入 + 对账
```

### 禁止决策

```text
不评估 undo_log 写放大与锁冲突，直接全链路 AT。
```

### 验收指标

```text
global_tx_success_rate
undo_log 写入量占比（待实测）
锁冲突/重试率
p99 延迟
```

---

## Decision Card 3：资源天然可预留，用 TCC

### 场景

余额冻结、库存锁定、座位预留——业务本身就有"预留"概念。

### 判断

有冻结语义 → TCC；三难题必须逐项防御。

### Mechanism -> Decision

| 机制 | 工程决策 |
| --- | --- |
| Try 冻结 + 预留表 | 幂等键 = freezeId |
| Cancel 先于 Try | 空回滚防御 |
| Try 后无 Cancel | 悬挂检测任务 |
| Confirm/Cancel 重试 | 幂等 |

### Code

```text
Try: 写冻结记录（FROZEN）
Confirm: 真正扣减 + 状态改 CONFIRMED
Cancel: 解冻 + 状态改 CANCELLED
超时扫描 FROZEN 悬挂记录
```

### 禁止决策

```text
只写三方法，不做空回滚/悬挂/幂等防御。
```

### 验收指标

```text
frozen_pending_count
cancel_before_try_count（空回滚触发数）
confirm_retry_count / cancel_retry_count
p99 延迟
```

---

## Decision Card 4：长流程可逆，用 Saga

### 场景

下单→出库→扣款→发货；正向长链路，补偿可对偶建模。

### 判断

中间状态可容忍 + 补偿可逆 → Saga；不可逆步骤前置处理。

### Mechanism -> Decision

| 机制 | 工程决策 |
| --- | --- |
| 编排器状态机 | 明确每步正/补偿映射 |
| 补偿失败 | 补偿积压 + 对账 |
| 不可逆动作 | 前置预留或接受风险 |
| 并发读中间态 | 语义锁/幂等键 |

### Code

```text
T1 下单 -> T2 扣库存 -> T3 扣款
T3 失败 -> C2 释放库存 -> C1 取消订单
所有补偿按 sagaId 幂等
```

### 禁止决策

```text
对不可逆动作（短信、外呼）做"补偿"，或补偿不幂等。
```

### 验收指标

```text
saga_success_rate
compensation_execution_rate
compensation_pending_count
reconcile_diff_count
```

---

## Decision Card 5：状态变更 + 发消息，用 Outbox/半消息

### 场景

订单状态变更后要通知积分、库存、搜索等下游。

### 判断

动作形态是"改状态 + 发消息"（单条 DB+MQ 原子性）→ Outbox/半消息（回链 ddd-05 / mq-07）。

### Mechanism -> Decision

| 机制 | 工程决策 |
| --- | --- |
| 状态与事件同事务 | Outbox 表 + 轮询发布 |
| 半消息 | RocketMQ 两阶段 + 回查 |
| 消费重复 | 事件 ID/业务键幂等 |
| 投递失败 | 对账补偿 |

### Code

```text
@Transactional:
  save(order);
  outbox.append(OrderCreatedEvent.from(order));
```

### 禁止决策

```text
用事务消息宣称"解决了跨服务分布式事务"。
```

### 验收指标

```text
outbox_pending
publish_error_rate
duplicate_event_count
event_consume_lag
reconcile_diff_count
```
