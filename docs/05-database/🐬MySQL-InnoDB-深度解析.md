## 🎯 InnoDB 解决的核心问题

在进入具体机制之前，先回答一个元问题：**InnoDB 到底在解决什么问题？**

**一句话：** 在不可靠的、慢速的、容量有限的介质（磁盘）上，构建一个可靠的、快速的、支持高并发的数据管理系统。

所有机制都是为了对抗三个根本约束：

| 约束 | 本质 | InnoDB 的对抗手段 |
|---|---|---|
| **不可靠** | 磁盘会断电，写入可能撕裂，并发可能冲突 | WAL、Doublewrite、2PC、锁、MVCC |
| **慢** | 内存 100ns vs 磁盘 100μs，随机写比顺序写慢 2~1000 倍 | Buffer Pool、B+ Tree、Change Buffer、Group Commit |
| **有限** | 内存容量远小于数据集，单个页只能存有限行 | B+ Tree 扇出最大化、改良 LRU、前缀索引 |

这些机制最终交付的是**六个层次的保证**（有递进关系）：

```
不坏（Doublewrite 防撕裂页）
  → 不丢（Redo Log WAL 保持久性）
    → 不出错（锁 + MVCC 保并发正确性）
      → 可恢复（Redo 重放 + Undo 回滚）
        → 可追溯（Binlog 行级记录 / 主从同步）
          → 可溯源（MVCC 版本链 / Binlog 时间点恢复）
```

这就是 InnoDB 的**核心使命**：让数据在不可靠的介质上，既跑得快，又保证不坏、不丢、不出错，还能恢复、追溯、溯源。

接下来 9 个 Level 的每一层，都是在解决这六个"不"中的某一个或某几个。

### 从"表名"到"磁道"的六级映射链

读者最常困惑的问题是："B+ 树、.ibd 文件、InnoDB 到底怎么串起来的？" 下面这张表给出从逻辑名称到物理扇区的完整映射：

| 层级 | 你看到的（逻辑） | InnoDB 内部编号 | 操作系统看到的 | 物理硬件位置 |
|---|---|---|---|---|
| **① 表名** | `users` | 数据字典查 → `space_id = 42` | 无（MySQL 自己记的） | 无 |
| **② 表空间** | `Tablespace` | `space_id = 42` 对应文件 | `/var/lib/mysql/mydb/users.ibd` | 磁盘上的一个文件 Inode |
| **③ 段（Segment）** | 聚簇索引 / 二级索引 | `SEG_ID`（段编号） | 无（InnoDB 内部维护） | 无（纯逻辑分组） |
| **④ 区（Extent）** | 1MB 的连续空间 | `Extent No. 56` | 文件偏移量 `56 × 1MB` 开始 | 磁盘上的连续 1MB 空间 |
| **⑤ 页（Page）** | 16KB 的数据块 | `page_no = 2048` | 文件偏移量 = `2048 × 16384` | **磁盘上具体的 16KB 扇区集合** |
| **⑥ 行（Row）** | `id=1, name='赵四'` | 在页内的偏移量（如 `1536` 字节处） | 无（文件系统不管行） | 磁盘上某 16KB 块内的具体字节位置 |

> 📌 **核心公式**：
>
> `磁盘物理位置 = .ibd 文件起始 + (page_no × 16384) + 页内偏移量`
>
> 这就是 InnoDB 能找到任何一行数据的**唯一物理依据**。Level 1 讲 Page、Level 2 讲 Buffer Pool、Level 3 讲 B+ 树——这三层的核心任务就是**确定 page_no 和页内偏移量**。

#### 常见误区预警

> ❌ **误区 1**："InnoDB 的 16KB 页就是存 16KB 数据"
> ✅ **真相**：页内有 File Header（38B）、Page Header（56B）、Page Directory（每 slot 2B）、File Trailer（8B）等元数据，真正能存用户数据约 16180 字节。

> ❌ **误区 2**："DELETE 一行后，磁盘文件会变小"
> ✅ **真相**：InnoDB 的 .ibd 文件不会因为 DELETE 而缩小，空间只是标记为"可复用"。这也是为什么需要 `OPTIMIZE TABLE` 的原因。

> ❌ **误区 3**："SSD 这么快，随机读和顺序读没区别"
> ✅ **真相**：SSD 的顺序写仍比随机写快 2~5 倍（因为避免了写放大和垃圾回收开销），这个差异在写入密集型场景下至关重要。

### Why——为什么不能"一条记录一个文件"

**徒弟**：我想把每一行记录存成一个文件，这样增删改最直观——`/data/table1/row_001.dat`。

**老陈**：好，假设你有一张订单表 1 亿行。

| 朴素方案 | 它本来想解决什么 | 它留下的致命账 |
|---|---|---|
| 一行一文件 | 增删改直观 | 1 亿个 inode，文件系统直接爆炸；读 100 行 = 100 次随机 I/O；无法利用空间局部性 |
| 退一步：一个文件存全部行，按写入顺序追加 | 减少文件数 | 范围查询需要全文件扫描；删除产生空洞无法回收 |
| 再退一步：固定大小的"页"，每页存多行 | 对齐 I/O 单元 | ✅ 方向对了，但页内部怎么管理？页之间怎么快速定位？→ 这就是 Level 1 要解决的 |

> 📌 **最容易错的点**：很多人以为 InnoDB 的 16KB 页是"正好存 16KB 数据"。实际上页内有 **~38 字节的 File Header + ~56 字节的 Page Header + Page Directory + File Trailer**，真正能存数据的空间约 **16KB - 约 200 字节 ≈ 16180 字节左右**（具体取决于页类型和 slot 数量）。

### What——InnoDB Page 的内部结构

```
┌────────────────────────────────────────────────────┐
│  File Header (38 bytes)                            │  ← 前驱/后继页指针、LSN、页类型
├────────────────────────────────────────────────────┤
│  Page Header (56 bytes)                            │  ← 记录数、首个/末个记录偏移、
│                                                    │     Free Space 指针、页方向等
├────────────────────────────────────────────────────┤
│  Infimum Record (伪记录)                            │  ← 页内最小值的哨兵
├────────────────────────────────────────────────────┤
│                                                    │
│  User Records (真实数据行，按主键顺序排列)            │  ← 你的数据在这里
│                                                    │
├────────────────────────────────────────────────────┤
│  Supremum Record (伪记录)                           │  ← 页内最大值的哨兵
├────────────────────────────────────────────────────┤
│  Free Space (空闲空间)                              │  ← 新行插入时从这里分配
├────────────────────────────────────────────────────┤
│  Page Directory (槽目录)                            │  ← 二分查找的"目录"，
│     slot[0] slot[1] ... slot[N]                    │     每个 slot 指向一条记录
├────────────────────────────────────────────────────┤
│  File Trailer (8 bytes)                            │  ← checksum + 尾部 LSN
│                                                    │     用于校验页的完整性
└────────────────────────────────────────────────────┘
              ← 共 16KB (innodb_page_size 默认值) →
```

**关键数字**（InnoDB 默认 `innodb_page_size = 16KB`）：

| 结构 | 大小 | 作用 |
|---|---|---|
| File Header | 38 bytes | `FIL_PAGE_PREV`(4B) / `FIL_PAGE_NEXT`(4B) / `FIL_PAGE_LSN`(8B) / `FIL_PAGE_TYPE`(2B) 等 |
| Page Header | 56 bytes | `PAGE_N_RECS`(2B) 当前记录数、`PAGE_FREE`(2B) 空闲链表头 等 |
| Infimum + Supremum | 各 ~13 bytes | 哨兵记录，保证链表/二分查找不需要判空 |
| Page Directory | 2 bytes/slot | 每个 slot 是一个 2 字节的偏移量，指向一条"组首记录"（每组 4~8 条记录） |
| File Trailer | 8 bytes | 4B checksum + 4B 尾部 LSN，确保页写入的原子性 |

### What（续）——一行记录在磁盘上到底长什么样

**徒弟**：Level 1 讲了 Page 里有 File Header、Page Header、User Records 这些区域，但 User Records 里面每一行记录本身的物理格式是什么样的？

**老陈**：这个问题问到了 InnoDB 存储的最后一层细节。InnoDB 5.7.9+ 默认使用 **DYNAMIC 行格式**（5.7.9 之前默认 Compact），一行记录在磁盘上的布局是这样的：

```text
┌─────────────────────────────────────────────────────────────┐
│  一行记录的物理布局（DYNAMIC 行格式）                          │
│                                                             │
│  ┌──────────┬──────────────┬─────────────┬──────────────┐  │
│  │ 记录头    │  NULL 值列表  │ 变长字段长度 │   列数据      │  │
│  │ (5 字节)  │  (N bit)     │  列表       │ (用户数据 +   │  │
│  │          │              │ (每字段1-2B) │  隐藏列)      │  │
│  └──────────┴──────────────┴─────────────┴──────────────┘  │
│                                                             │
│  物理布局从左到右（低地址→高地址）：                            │
│  记录头 → NULL 值列表 → 变长字段长度列表 → 列数据              │
│  （其中变长字段长度列表和 NULL 值列表在构造记录时反向填充）      │
└─────────────────────────────────────────────────────────────┘
```

| 部分 | 大小 | 内容 |
|---|---|---|
| **记录头（Record Header）** | 固定 5 字节 | 删除标记（deleted flag）、组内记录数（n_owned）、堆号（heap_no）、记录类型（record_type）、指向下一条记录的偏移指针（next_record） |
| **NULL 值列表** | `ceil(允许 NULL 的列数 / 8)` 字节 | 每个允许 NULL 的列占 1 bit，标记该列本行是否为 NULL |
| **变长字段长度列表** | 每个 VARCHAR/TEXT 字段 1-2 字节 | 记录每个变长字段实际占用了多少字节（InnoDB 从右到左存储列数据，所以变长字段长度也是从右到左记录） |
| **隐藏列** | 0-19 字节 | `DB_TRX_ID`（6B，最近修改的事务 ID）+ `DB_ROLL_PTR`（7B，回滚指针）+ `DB_ROW_ID`（6B，仅当表无主键时） |
| **用户数据列** | 各列实际长度之和 | 按表定义的列顺序存储，CHAR/VARCHAR 存实际内容，INT/DATE 等定长列存固定字节 |

**关键细节**：

1. **NULL 不占数据空间**：如果某列本行是 NULL，该列在"用户数据列"区域完全不占用字节，只在 NULL 值列表的 bitmap 里标一位。这就是为什么 NULL 列在存储层面几乎是零开销的。

2. **隐藏列的代价**：每行数据额外增加 6+7=13 字节（`DB_TRX_ID` + `DB_ROLL_PTR`），如果有隐式主键则再加 6 字节。这些隐藏列对用户不可见，但确实占用了存储空间和 Buffer Pool 的缓存空间。

3. **行溢出**：如果一行数据太大（比如包含 VARCHAR(1000) 且实际存了 1000 字节），导致整个页放不下几行，InnoDB 会把变长字段的值放到**溢出页**（Overflow Page），在行内只存一个 20 字节的指针。这是 InnoDB 处理大字段的标准手段，和 Level 3 讲的前缀索引（只取前 N 字节建索引）是互补的优化策略。

**🏛️ 图书馆比喻**：

```text
把 Page 里的 User Records 区域想象成一排书架上的书。

每本书（一行记录）的内部结构：
  ┌─────────────────────────────────────────┐
  │  封面（记录头：5字节）                    │  ← 写着"这本书属于哪个系列、下一本在哪"
  │  目录索引（NULL 值列表）                  │  ← 标记哪些章节是空的
  │  章节长度表（变长字段长度列表）            │  ← 每个变长章节实际有多少页
  │  正文内容（隐藏列 + 用户数据列）          │  ← 真正的内容
  └─────────────────────────────────────────┘

如果正文内容太多（大字段），书会太厚：
  → InnoDB 把最后几章拆到另一本书里（溢出页）
  → 原来的书里留一个纸条："这几章在第 XX 号书架上"（20字节指针）
```

**这一节和后续内容的关系**：

| 后续内容 | 依赖本节什么知识 |
|---|---|
| Level 3 索引与 NULL | NULL 值列表的 bitmap 结构、NULL 不占数据空间 |
| Level 6 MVCC | `DB_TRX_ID` 和 `DB_ROLL_PTR` 是版本链的基础 |
| Level 7 Undo Log | `DB_ROLL_PTR` 指向 Undo Log 中的旧版本 |

> 📌 **最容易错的点**：很多人以为"一行记录 = 各列数据拼接"，但实际上每行还有 5 字节记录头 + NULL bitmap + 变长字段长度列表 + 13 字节隐藏列。对于小行（比如只有 id + status 两列），这些元数据可能占总行长度的 30%+。这就是为什么"行越短，单页能放的行数越多，B+ 树扇出越大，查询越快"——不仅是数据本身短，元数据的占比也相对更小。

### What（续）——Extent 与空间管理

```
┌──── Extent (1MB = 64 pages × 16KB) ────┐
│  P0  P1  P2  P3 ... P62  P63           │
│  每个 P 是一个 16KB 的 Page             │
└────────────────────────────────────────┘

Tablespace
  └─ Segment (段：一个索引 = 一个段)
       ├─ Extent 0 (叶子节点页)
       ├─ Extent 1 (叶子节点页)
       ├─ Extent 2 (非叶子节点页)
       └─ ...
```

| 概念 | 含义 | 📌 关键 |
|---|---|---|
| **Page** | 16KB，最小 I/O 单元 | 读一行也要读整页到 Buffer Pool |
| **Extent** | 64 pages = 1MB，连续空间分配单元 | 大表按 Extent 分配，小表先用"碎片页"（32 个单独页），满 32 页后切 Extent 分配 |
| **Segment** | 一个索引（或一个 LOB）= 一个段 | 段内包含叶子段和非叶子段 |
| **Tablespace** | `.ibd` 文件 | 独立表空间 = 一表一文件（`innodb_file_per_table=ON`，5.6+ 默认） |

**把这四个概念串成一条寻址链**：

```text
Tablespace (users.ibd)
  └─ Segment（一个索引 = 一个段，聚簇索引段 / 二级索引段）
       └─ Extent（1MB = 64 个连续 Page）
            └─ Page（16KB，最小 I/O 单元，page_no 是它在 .ibd 文件中的逻辑编号）

寻址公式：磁盘物理偏移 = .ibd 文件起始 + (page_no × 16384)
```

> 📌 上面这张图把 Level 1 的四个核心概念（Page / Extent / Segment / Tablespace）连成了**一条从逻辑到物理的寻址链**。至于"表名"怎么映射到 `space_id`、`page_no` 最终怎么落到磁盘扇区，完整的六级映射链见 [🏗️ 全文架构速览](#arch-overview)。

### How——读者 U 第一次找到它的"书"

```text
① U 要修改 user_id = 1001 的记录
② InnoDB 通过 B+ 树（Level 3 详述）定位到目标 Page 的页号 = 42
③ 操作系统从 .ibd 文件的 offset = 42 × 16384 = 688128 处读取 16KB
④ 这 16KB 被加载到 Buffer Pool（Level 2 详述）
⑤ 在 Page 内部，通过 Page Directory 做二分查找
   → slot 定位到"组"，组内顺序扫描找到 user_id = 1001 的记录
⑥ 找到目标记录的偏移量，开始修改
```

> 📌 **Page Directory 的二分查找**：每个 slot 指向一个"组"的首条记录，每组 4~8 条记录。先在 slot 数组上二分（O(log(N/4~8))），再在组内顺序扫描（≤8 次比较）。这是 InnoDB 页内定位的核心。

**徒弟**：为什么组内不全用二分？

**老陈**：每组最多 8 条记录，顺序扫描的常数极小（CPU 缓存友好），而维护有序 slot 的开销不值得。这是经典的**分块查找（Block Search）**思想。

### Transfer——可迁移的工程方法论

1. **对齐 I/O 单元**：几乎所有存储引擎（PostgreSQL 的 8KB page、RocksDB 的 block）都遵循"最小 I/O 单元 = 页/块"的设计。当你设计自己的持久化方案时，第一步就是确定页大小。
2. **哨兵值消除边界判断**：Infimum/Supremum 的设计在跳表、B+ 树、有序链表中反复出现——用空间换掉 `if (ptr == NULL)` 的判断。
3. **分块查找**：在大数组上建稀疏索引，先粗定位再精确定位——这是 B+ 树思想在页内的递归应用。

**本层留下的新账**：每次操作都要从磁盘读 16KB 到内存——如果每条 UPDATE 都触发一次磁盘 I/O，TPS 只能到几百（HDD）或几万（SSD）。**必须有一个内存缓存层** → 逼出 Level 2。

> 🔴 **口诀**：页是 I/O 最小单元，16KB 不止存数据。

## Level 2：Buffer Pool——磁盘数据如何"定位、加载、查找"三步进入内存

### 👶 前置知识关卡
- [ ] Level 1 的不变量：InnoDB 操作的最小 I/O 单元是 16KB Page？
- [ ] SSD 随机读延迟 ~100μs，内存访问延迟 ~100ns，差距约 1000 倍？
- [ ] 经典的 LRU（Least Recently Used）缓存淘汰算法？

### Why——直接读磁盘死在哪

**徒弟**：那就每次操作都从磁盘读页，改完写回去，简单粗暴。

**老陈**：好，来算一笔账。假设你的系统每秒处理 10000 次 UPDATE，每次 UPDATE 涉及：

| 操作 | 磁盘 I/O 次数（无缓存） | 有 Buffer Pool 命中时 |
|---|---|---|
| 读目标数据页 | 1 次随机读 | 0（已在内存） |
| 读 B+ 树非叶子页 | 2~3 次随机读 | 0~1（热点页常驻） |
| 写回数据页 | 1 次随机写 | 0（脏页异步刷盘） |
| **合计** | **4~5 次 I/O / 语句** | **0~1 次 I/O / 语句** |

无缓存：10000 × 4 = 40000 IOPS（SSD 随机写通常 5~10 万 IOPS，但延迟叠加后 TPS 远低于理论值）
有缓存（命中率 99%）：10000 × 0.05 = 500 IOPS

> 📌 **教学参考量级**：SSD 随机读延迟约 50~200μs，4 次叠加 ≈ 200~800μs 纯 I/O 时间。加上 CPU 处理，无缓存时单语句 ~1ms，TPS 上限约 1000。有缓存时单语句 ~10~50μs CPU 时间，TPS 可达数万。`[须实测]`

| 朴素方案 | 它本来想解决什么 | 它留下的致命账 |
|---|---|---|
| 直接读磁盘 | 简单正确 | I/O 瓶颈，TPS 差 2~3 个数量级 |
| 加一个 LRU 缓存 | 减少 I/O | 标准 LRU 会被全表扫描"污染"——一次 `SELECT * FROM big_table` 把所有热点页踢出去 |

### What——Buffer Pool 是整条因果链的中枢

**Buffer Pool 不是一个孤立的缓存组件，它是 InnoDB 所有数据操作的必经之路。** 磁盘上的数据要到达应用程序手中，必须经过三个紧密衔接的步骤——**定位、加载、查找**——而 Buffer Pool 贯穿了全部三步：

```
┌─────────────────────────────────────────────────────────────────────────┐
│                  Buffer Pool 因果主线：定位 → 加载 → 查找                │
│                                                                         │
│  ┌──────────┐     ┌──────────┐     ┌──────────┐     ┌──────────────┐   │
│  │ ① 定位    │     │ ② 加载    │     │ ③ 查找    │     │ ④ 返回给上层  │   │
│  │           │────→│           │────→│           │────→│              │   │
│  │ "我需要   │     │ "从磁盘   │     │ "在这个   │     │ 记录指针     │   │
│  │ page 42" │     │ 搬到内存" │     │ 页里找    │     │ 交给锁/MVCC  │   │
│  │           │     │           │     │ id=1001" │     │              │   │
│  │ 谁告诉我  │     │ 怎么管理  │     │ 页内怎么  │     │              │   │
│  │ 页号？    │     │ 缓存空间？│     │ 快速定位？│     │              │   │
│  │ → B+ 树   │     │ → 改良LRU │     │ → Page Dir│     │              │   │
│  │ (Level 3) │     │ (本节核心)│     │ (Level 1) │     │              │   │
│  └──────────┘     └──────────┘     └──────────┘     └──────────────┘   │
│        ↑                ↑                ↑                              │
│   B+ 树告诉 BP      BP 自己决定       Page Directory                  │
│   "该加载哪页"     "怎么放进去、      负责页内精确定位                  │
│                     怎么淘汰旧页"                                       │
└─────────────────────────────────────────────────────────────────────────┘
```

> 📌 **核心洞察**：Buffer Pool 是被动的——它不知道"该加载哪一页"。它只知道"给我一个 page_no，我还你一个内存地址"。告诉它 page_no 的，是 B+ 树（Level 3）。而在页内精确定位目标记录的，是 Page Directory（Level 1 已讲）。**Buffer Pool 的核心职责是中间那一步——"加载"：把磁盘页高效地搬进内存，并决定哪些页留下、哪些页被淘汰。**

### What（续）——步骤 ① 定位：Buffer Pool 的 Hash Table

当上层（B+ 树遍历过程中）请求 `page_no = 42` 时，Buffer Pool 首先查自己的内部 **Hash Table**：

```text
① 计算 hash(page_no=42) → 得到 hash 桶位置
② 在桶内查找：
   ├── 命中 → 返回 buffer_page 的内存地址（0 次磁盘 I/O）
   │         同时将该页移到 LRU 的 MRU 端（或 Old 区头部）
   └── 未命中 → 进入步骤 ② 加载
```

这个 Hash Table 是 `page_no → buffer_page 内存地址` 的映射，查找复杂度 O(1)。

> 📌 **Buffer Pool 的 Hash Table 和 Adaptive Hash Index 是两个东西**。前者是 BP 内部用于"页号 → 缓存页"的映射；后者是在 B+ 树之上为高频等值查询建立的额外索引（详见 Level 3）。

### What（续）——步骤 ② 加载：改良 LRU 的 New/Old 分区

当 Hash Table 未命中时，Buffer Pool 需要从磁盘加载目标页。但**加载到哪里？如果 Buffer Pool 已满，淘汰谁？**

InnoDB **不能**用标准 LRU，因为两类操作会摧毁缓存质量：

1. **全表扫描**：一次扫百万行，加载的页只用一次，却把热点页全部踢出
2. **预读（read-ahead）**：预测性加载的页可能根本不会被访问

```
标准 LRU（问题版）：
┌─────────────────────────────────────────────────┐
│  MRU ←── [新加载页插入头部] ──→ LRU（尾部淘汰）  │
│  全表扫描一来，热点页全被挤到尾部被淘汰           │
└─────────────────────────────────────────────────┘

InnoDB 改良 LRU：
┌───────────────────────────────────────────────────────────────┐
│                        Buffer Pool                            │
│  ┌─────────────────────┐  ┌──────────────────────────────┐   │
│  │   New Sublist        │  │       Old Sublist            │   │
│  │   (~63% 默认)        │  │       (~37% 默认)            │   │
│  │   "年轻代"           │  │       "年老代"               │   │
│  │                      │  │                              │   │
│  │  只有从 Old 区       │  │  ← 新加载的页先放这里        │   │
│  │  "毕业"的页          │  │    存活超过 old_blocks_time   │   │
│  │  才能进这里          │  │    (默认 1000ms) 且被再次    │   │
│  │                      │  │     访问才能"毕业"到 New 区  │   │
│  └─────────────────────┘  └──────────────────────────────┘   │
│  MRU                                              LRU        │
└───────────────────────────────────────────────────────────────┘
```

| 参数 | 默认值 | 作用 |
|---|---|---|
| `innodb_buffer_pool_size` | 128MB | Buffer Pool 总大小（生产环境通常设为物理内存的 50~75%） |
| `innodb_old_blocks_pct` | 37 | **Old 区**占 Buffer Pool 的比例（%）。37 表示 Old 区占 37%，New 区占 63% |
| `innodb_old_blocks_time` | 1000 | 页加载到 Old 区后，必须存活超过此时间（ms）且被再次访问，才能"毕业"到 New 区 |

> 📌 最容易错的点：innodb_old_blocks_pct = 37 的意思是 Old 区占 37%，New 区占 63%，不是 Old 区占 63%。参数名 old_blocks_pct 直接说明它控制的是 Old 区比例，但很多人凭直觉以为"数字大 = 常用区（New 区）大"，就把 37 记成 New 区。记住：37% = Old 区，63% = New 区。


**徒弟**：为什么新加载的页不直接放 New 区？

**老陈**：用图书馆来想。阅览室桌面（Buffer Pool）空间有限。如果每次有人请求一本书，不管他是精读还是随手翻一下，都直接放到桌面最显眼的位置（New 区），那么当一个"巡视员"（全表扫描）进来把所有书架上的书都翻一遍时，桌面上原本放着的热门书籍就全被挤掉了。Old 区就是一个试用期/隔离区——新书先放在桌角，但有个反直觉的点：如果 1 秒内（innodb_old_blocks_time=1000ms）有人反复翻它，InnoDB 反而不会把它移走，因为"短时间连续翻看"正是巡视员（全表扫描）那种一次性读的特征；只有当它在桌角待满 1 秒之后，再有人来翻它，才证明它是真正的高频书，才会被移到桌面正中央（New 区）。

### What（续）——步骤 ③ 查找：Page Directory 页内精确定位

页加载到 Buffer Pool 后，上层需要在页内找到目标记录。这一步在 Level 1 已讲过（Page Directory 二分查找 + 组内顺序扫描），此处不再重复。**关键点是：这一步完全是纯内存操作，代价与磁盘 I/O 不在一个量级。**

### What（续）——Buffer Pool 的三种链表

Buffer Pool 内部维护三个关键链表，各自独立演进：

| 链表 | 说明 | 包含什么 |
|---|---|---|
| **Free List** | 空闲页链表 | 从未使用过的干净页 |
| **LRU List** | 已使用页链表（含 New + Old 区） | 所有缓存了磁盘页内容的 buffer page |
| **Flush List** | 脏页链表 | 被修改过但还没刷回磁盘的页（按首次修改时间排序） |

```
                    ┌──────────┐
  Free List:        │ FP1 → FP2 → FP3 → ... │  ← 空闲页池
                    └──────────┘

                    ┌──────────────────────────────────┐
  LRU List:         │ [New 区] ←→ [Old 区]             │  ← 已缓存的页
                    │  H ← P_a ← P_b ← P_c ← ... ← T  │
                    └──────────────────────────────────┘

                    ┌──────────────────────────────────┐
  Flush List:       │ D1(first_mod_time=T1) →          │  ← 脏页按修改时间排序
                    │ D2(T2) → D3(T3) → ...            │     checkpoint 从这里推进
                    └──────────────────────────────────┘
```

### How——读者 U 通过 Buffer Pool 完成"定位→加载→查找"

```text
① B+ 树遍历过程中，得知需要 page_no = 42
② 查 Buffer Pool 的 Hash Table（定位）
   ├── 命中 → 直接返回内存中的页（0 次 I/O）
   └── 未命中 ↓
③ 从 Free List 取一个空闲页（加载准备）
   ├── Free List 有空页 → 取一个
   └── Free List 为空 → 从 LRU List 尾部淘汰一个页
       ├── 淘汰的是干净页 → 直接回收
       └── 淘汰的是脏页 → 先刷盘再回收（触发 I/O）
④ 从磁盘读 page_no = 42 的 16KB 到该 buffer page（加载执行）
⑤ 将该 buffer page 插入 LRU List 的 Old 区头部
⑥ 在 Page Directory 中二分查找 id = 1001（查找）
   → slot 定位到"组"，组内顺序扫描找到记录
⑦ 如果 1000ms 内该页被再次访问 → "毕业"到 New 区
⑧ 返回记录的内存指针给上层（加锁/MVCC/修改）
```

**线性化点**：步骤 ⑥ 完成时，U 持有了目标记录在内存中的精确地址。此后的所有操作（加锁、修改、写 Undo/Redo）都在内存中完成，不再触发磁盘 I/O。

### What（续）——🏛️ 用图书馆深度理解：主键为什么必须自增

**这是 Buffer Pool 因果链延伸出的第一个重要推论。**

**徒弟**：主键用 UUID 不行吗？反正 B+ 树能处理任意顺序的键。

**老陈**：B+ 树**功能上**能处理任意键，但**物理上**会付出巨大代价。让我们从图书馆的视角来看：

```
场景 A：自增主键（AUTO_INCREMENT）

  图书馆每天收到的新书，编号都比上一本大。
  新书永远放到最后一个书架的末尾。
  
  书架 1: [1] [2] [3] ... [72]  ← 满了，利用率 100%
  书架 2: [73] [74] ... [144]   ← 满了，利用率 100%
  书架 3: [145] [146] ...       ← 正在填充中
  
  阅览室桌面（Buffer Pool）上放的每一本书架都是满满的。
  每次从磁盘加载一个 16KB 页到 Buffer Pool，这个页里几乎 100% 是有效数据。
  
  ✅ Buffer Pool 利用率极高
  ✅ 范围查询时，相邻记录在物理上也相邻 → 顺序 I/O
  ✅ 不需要页分裂


场景 B：UUID 主键（随机无序）

  图书馆每天收到的新书，编号完全随机。
  新书可能需要塞到中间某个已经满了的书架上。
  
  书架 1: [a3f2] [b1c8] ... [f5d9]  ← 满了
  现在来了一本编号 "c4e7" 的书，应该插在书架 1 中间。
  书架 1 已经满了 → 必须"页分裂"：
  
  书架 1a: [a3f2] ... [c000]  ← 只用了 50%
  书架 1b: [c001] ... [f5d9]  ← 只用了 50%
  
  ❌ 两个书架各浪费了一半空间
  ❌ 阅览室桌面（Buffer Pool）上放的书有一半是空的
  ❌ 范围查询时，逻辑相邻的记录物理上分散 → 随机 I/O
  ❌ 频繁的页分裂产生大量额外磁盘写入
```

**硬核数字推导——页分裂的代价**：

| 指标 | 自增主键 | UUID 主键 |
|---|---|---|
| **页利用率** | ~90~100%（新页追加写入，写满才开新页） | ~50~70%（随机插入触发分裂，分裂后各 ~50%） |
| **Buffer Pool 有效数据密度** | 每个 16KB 缓存页包含 ~16KB 有效数据 | 每个 16KB 缓存页可能只包含 ~8KB 有效数据 |
| **写入 I/O 放大** | 1x（只写目标页 + 新页） | 2~3x（页分裂需要：读旧页 + 写两个新页 + 更新父节点） |
| **范围查询性能** | 顺序扫描（叶子链表物理连续） | 随机跳跃（分裂后物理不连续） |

> 📌 **教学参考量级**：UUID 主键相比自增主键，写入吞吐通常下降 3~10 倍（取决于数据量和并发度），Buffer Pool 的有效利用率下降约 30~50%。`[须实测]`

**徒弟**：那如果我非要用 UUID 做主键呢？

**老陈**：8.0 可以考虑 `UUID_TO_BIN(uuid, 1)` 把 UUID 的时间戳部分提到前面，让 UUID 变成"大致有序"，大幅减少页分裂。但最优解仍然是自增 BIGINT。

### What（续）——🏛️ 用图书馆深度理解：DELETE 为什么不容易造成 Buffer Pool "空洞"

**这是 Buffer Pool 因果链延伸出的第二个重要推论。**

**徒弟**：我 DELETE 了大量数据，Buffer Pool 里缓存的页岂不是变"空"了？就像书架上抽走一半的书，桌面放着半空的书架，不是浪费吗？

**老陈**：这个问题非常好，但答案是——**DELETE 在 Buffer Pool 层面几乎不造成"空洞"问题**。原因要从 InnoDB 的空间管理粒度说起：

```
关键区分：DELETE 影响的是"页内空间"，而不是"页级缓存"

┌─────────────────────────────────────────────────────────────────┐
│  Buffer Pool（阅览室桌面）                                       │
│                                                                 │
│  ┌─────────────────┐  ┌─────────────────┐  ┌────────────────┐  │
│  │ Page 42         │  │ Page 43         │  │ Page 44        │  │
│  │                 │  │                 │  │                │  │
│  │ [行1] ✅ 存在   │  │ [行100] ✅ 存在 │  │ [行200] ✅     │  │
│  │ [行2] ❌ 已删除 │  │ [行101] ✅ 存在 │  │ [行201] ✅     │  │
│  │ [行3] ✅ 存在   │  │ [行102] ❌ 已删 │  │ [行202] ❌     │  │
│  │ [行4] ✅ 存在   │  │ [行103] ✅ 存在 │  │ [行203] ✅     │  │
│  │                 │  │                 │  │                │  │
│  │ Free: 20%       │  │ Free: 15%       │  │ Free: 25%      │  │
│  └─────────────────┘  └─────────────────┘  └────────────────┘  │
│                                                                 │
│  页本身仍在 Buffer Pool 中！页内的 Free Space 可以被后续 INSERT 复用 │
└─────────────────────────────────────────────────────────────────┘
```

**三层解释**：

| 层级 | DELETE 的影响 | 为什么不是问题 |
|---|---|---|
| **行级**（页内） | 被删行标记为"已删除"，空间加入页内 Free Space 链表 | ✅ 下一条 INSERT 如果落到同一页，直接复用 Free Space，无需额外 I/O |
| **页级**（Buffer Pool） | 页内有些行被删了，但**页本身仍在 Buffer Pool 中** | ✅ Buffer Pool 缓存的是"页"不是"行"。页只要还在被访问，就不会被淘汰。页内的空洞由页自己管理 |
| **文件级**（.ibd） | 页内的 Free Space 增大，但 .ibd 文件大小不变 | ⚠️ 这是唯一真正"浪费"的层面——空间不归还 OS（详见坑 6），但和 Buffer Pool 无关 |

**图书馆比喻**：

```
你从阅览室桌面上的某本书架（Page 42）里抽走了 3 本书（DELETE 3 行）。
书架还在桌面上（页还在 Buffer Pool 中）。
书架上多了 3 个空位（页内 Free Space 增大）。

明天有人要放 3 本新书进来（INSERT 3 行）：
  ├── 如果新书的主键恰好应该放在这个书架上 → 直接塞进空位，0 额外开销
  └── 如果新书的主键应该放在别的书架上 → 空位暂时留着，等未来有人用到

关键：书架（页）本身没有被"浪费"。
它仍然在桌面上（Buffer Pool 中），随时可以被访问。
只是它内部的利用率从 100% 降到了 75%。
```

> 📌 **DELETE 真正的问题不在 Buffer Pool，而在磁盘空间**：.ibd 文件不会缩小（坑 6），且如果大量删除导致很多页只有 1~2 行数据，B+ 树的叶子页数量不变但有效数据密度降低，范围扫描时需要读更多页。**但这一切都不是 Buffer Pool 的问题——Buffer Pool 只关心"页是否在内存中"，不关心"页内有多少行"。**

#### 🏛️ 深度案例：删除一半数据后，INSERT 依然飞快，但 BETWEEN 查询崩了

**场景**：一张订单表有 1000 万行，主键是自增 ID（1~1000 万）。现在执行 `DELETE FROM orders WHERE id % 2 = 0`，删除所有偶数 ID，剩下 500 万行。

**后续 INSERT 性能：几乎不受影响** ✅

```text
自增 ID 写入的因果链：
  ① 新 INSERT 的 ID = 10000001（自增，永远追加到最后一个叶子页）
  ② 最后一个叶子页的位置与删除操作无关
  ③ 即使中间的叶子页被删空了，也不影响追加写入
  ④ 写入性能 ≈ 删除前（依然是 O(1) 的追加操作）
```

**后续 BETWEEN 查询性能：急剧下降** ❌

```text
删除前的叶子页状态（每页 72 行，连续密集）：
  Page 1: [id=1, 2, 3, ..., 72]      ← 72 行有效数据
  Page 2: [id=73, 74, 75, ..., 144]  ← 72 行有效数据
  Page 3: [id=145, 146, ..., 216]    ← 72 行有效数据
  ...

删除后的叶子页状态（每页只剩 ~36 行，大量空洞）：
  Page 1: [id=1, 3, 5, ..., 71]      ← 36 行有效数据，50% 空洞
  Page 2: [id=73, 75, 77, ..., 143]  ← 36 行有效数据，50% 空洞
  Page 3: [id=145, 147, ..., 215]    ← 36 行有效数据，50% 空洞
  ...

查询 SELECT * FROM orders WHERE id BETWEEN 1 AND 10000：
  删除前：10000 行 ÷ 72 行/页 = 139 页 → 读 139 页
  删除后：5000 行 ÷ 36 行/页 = 139 页 → 还是读 139 页
                                                  ↑
                                          但有效数据只剩一半！

更糟的是大范围查询：
  SELECT * FROM orders WHERE id BETWEEN 1 AND 1000000（该区间覆盖原表前 100 万行）：
  删除前：100万行 ÷ 72 行/页 ≈ 13889 页
  删除后：50万行 ÷ 36 行/页 ≈ 13889 页（页数没变，但有效数据减半）
  
  如果这些页不在 Buffer Pool 中 → 磁盘 I/O 次数与删除前相同
  但返回的有效数据量减半 → 单位 I/O 的数据吞吐量腰斩
```

**根本原因**：InnoDB 的 B+ 树叶子页**不会因为删除而自动合并**。即使一个叶子页只剩 1 行数据，它仍然占据 B+ 树中的一个位置，范围查询时仍然需要被扫描。

| 操作 | 删除前（1000 万行） | 删除一半后（500 万行） | 影响 |
|---|---|---|---|
| `INSERT`（自增 ID） | 追加到最后一页 | 追加到最后一页 | **无影响** |
| `SELECT ... WHERE id = X` | 3 层 B+ 树定位 | 3 层 B+ 树定位 | **无影响** |
| `SELECT ... WHERE id BETWEEN A AND B` | N 页密集扫描 | N 页稀疏扫描 | **性能下降 ~50%** |
| `COUNT(*)` | 扫描全表 | 扫描全表（页数不变） | **性能不变，但结果减半** |
| `.ibd` 文件大小 | 约 2.2GB | 约 2.2GB（不缩小） | **空间浪费** |

> 📌 **解决方案**：如果删除了大量数据且需要恢复范围查询性能，可以执行 `OPTIMIZE TABLE` 或 `ALTER TABLE ... ENGINE=InnoDB` 重建表。重建后 B+ 树会重新组织，叶子页重新填满，.ibd 文件也会缩小。但重建大表需要停机或大量 I/O，需谨慎评估。

**徒弟**：那什么情况下 Buffer Pool 真的会有"空洞"？

**老陈**：**全表扫描**才是真正的 Buffer Pool "空洞制造者"。一次 `SELECT COUNT(*) FROM big_table` 会加载几十万页到 Old 区，这些页只被访问一次就不再使用，却占用了 Buffer Pool 的空间。这正是改良 LRU 的 New/Old 分区要解决的问题——让这些"一次性页"在 Old 区自然淘汰，不污染 New 区的热点页。

### What（5.7 vs 8.0）——Buffer Pool 的变化

| 特性 | MySQL 5.7 | MySQL 8.0 |
|---|---|---|
| **Buffer Pool 多实例** | `innodb_buffer_pool_instances`（最多 64 个，减少 mutex 竞争） | 同上，但 8.0 内部 mutex 粒度更细 |
| **在线扩缩** | 支持 `SET GLOBAL innodb_buffer_pool_size`，但过程可能阻塞 | 改进：后台线程处理更平滑 |
| **Buffer Pool dump/load** | `innodb_buffer_pool_dump_at_shutdown` + `load_at_startup`（冷启动预热） | 同上，8.0 默认开启 |

> 📌 5.7 → 8.0 在 Buffer Pool 层面**没有语义变化**，主要是代码组织和锁粒度优化。

### Transfer——可迁移的工程方法论

1. **定位→加载→查找三步分离**：任何缓存系统都面临这三步。Redis Cluster 也是：先通过 hash slot **定位**到哪个节点，再**加载**（网络请求）数据，最后在节点内**查找**具体 key。三步的解耦使得每层可以独立优化。
2. **分代缓存**：任何可能被"一次性批量操作"污染的缓存系统，都应该考虑 New/Old 分区（Java 的 Caffeine 用 Window TinyLFU 解决了类似问题）。
3. **三链表分离**：Free / LRU / Flush 分离使得淘汰策略和刷盘策略可以独立演进——这是"关注点分离"的经典实践。
4. **主键有序性 = 缓存效率**：自增主键不仅影响磁盘写入（页分裂），还间接影响 Buffer Pool 的有效利用率。这个"写入模式影响缓存效率"的洞察，在 LSM-Tree 的 Compaction 策略、CPU cache 的预取机制中反复出现。

**本层留下的新账**：Buffer Pool 解决了"加载"问题——给定一个 page_no，它能高效地把页从磁盘搬进内存。但**谁来告诉 Buffer Pool 该加载哪个 page_no？** 如果只有 `WHERE id = 1001`，怎么知道 id=1001 在哪个页上？→ 需要一个索引结构来做"主键值 → page_no"的映射 → 逼出 Level 3（B+ 树）。

> 🔴 **口诀**：定位加载查找三步走，改良 LRU 分新老，自增主键页不裂，DELETE 空洞页内消。

## Level 3：B+ 树索引——告诉 Buffer Pool "该加载哪一页"

---


### 👶 前置知识关卡
- [ ] Level 1：一个 Page 16KB，页内通过 Page Directory 二分查找？
- [ ] Level 2：Buffer Pool 是被动的——它需要别人告诉它 page_no，然后负责加载和缓存？
- [ ] 你知道 B 树和 B+ 树的区别吗？（B 树非叶子也存数据，B+ 树非叶子只存键和指针）

### Why——哈希表、二叉树、B 树分别死在哪

**徒弟**：为什么不直接用一个 Hash Map 做 `primary_key → (page_no, offset)` 的映射？

**老陈**：Hash Map 等值查询 O(1)，看似完美。但 InnoDB 需要的不只是等值查询：

| 朴素方案 | 它本来想解决什么 | 它留下的致命账 |
|---|---|---|
| Hash Map | O(1) 等值查询 | ❌ 不支持范围查询（`WHERE id BETWEEN 100 AND 200`）、不支持排序（`ORDER BY`）、不支持前缀匹配（`LIKE 'abc%'`） |
| 平衡二叉树（AVL/红黑树） | 有序 + O(log N) | ❌ 树高 = log₂(N)。1 亿行 → 树高 ~27，**每层一个节点在磁盘上物理分散** → 27 次随机 I/O → 27 × 10ms = 270ms |
| B 树（多路化） | 降低树高 | ❌ 非叶子节点也存完整数据行 → 16KB 页只能放 ~16 个分支（假设行 1KB）→ 树高 6~7 层 → 仍然 60~70ms |
| **B+ 树** | 非叶子只存键+指针，最大化扇出 | ✅ 3 层即可索引 2000 万+行；叶子双向链表支持范围扫描 |

> 📌 关于二叉树在磁盘上的灾难性表现，与 Level 1 讨论的"最小 I/O 单元是页而非字节"一脉相承。**红黑树/AVL 树的每个节点在内存中通过指针分散存放**（参见《🌳 树形数据结构》Level 5 的"指针追逐"分析），搬到磁盘上意味着每个节点可能位于不同的物理扇区，每下降一层就是一次完整的磁盘随机寻道。

### What——B+ 树的两把手术刀（对齐《🌳 树形数据结构》Level 6）

B+ 树对 B 树做了两把精确的外科手术：

**手术一：非叶子节点彻底"净化"——只放路标，不放数据**

```text
B 树（中间节点混合存放 Key + Data）：
  16KB 页 ÷ (8B key + 1KB data) ≈ 15 个分支 → 扇出率 ~15

B+ 树（中间节点只存 Key + 页指针）：
  16KB 可用空间(~16000B) ÷ (8B key + 6B pointer) = 16000B ÷ 14B ≈ 1142 个分支 → 扇出率 ~1142
 （下文"硬核数字推导"沿用同一基准：全文按页内可用空间约 16000 字节计算，不再用 16384 的理论满值，这样不同小节的数字可以互相对得上）


扇出率提升：1142 / 15 ≈ 76 倍！
```

**手术二：叶子节点双向链表串联——范围查询一气呵成**

```
                    [Root Page]                    ← 常驻 Buffer Pool
                   /     |     \
            [Non-Leaf] [Non-Leaf] [Non-Leaf]       ← ~1170 个分支/页
            / | \      / | \      / | \
         [NL][NL][NL] [NL][NL][NL] [NL][NL][NL]   ← ~1170 个分支/页
          |   |   |    |   |   |    |   |   |
         [L]⇄[L]⇄[L]⇄[L]⇄[L]⇄[L]⇄[L]⇄[L]⇄[L]     ← 叶子双向链表
              ↑ 真实数据行只存在这里
```

### 📐 硬核数字推导——为什么 3 层 B+ 树能装下 2000 万数据

```
假设条件：
  - 主键类型：BIGINT（8 字节）
  - 页指针：6 字节
  - 非叶子节点每条记录：8 + 6 = 14 字节
  - 叶子节点每行数据：~200 字节（含 overhead ~20B = 220B）
  - 页大小：16KB = 16384 字节（可用空间约 16000 字节）

非叶子节点扇出率：
  F = 16000 / 14 ≈ 1142 路分支

叶子节点容量：
  C = 16000 / 220 ≈ 72 行/页

3 层 B+ 树总容量：
  F × F × C = 1142 × 1142 × 72 ≈ 93,900,000 行 ≈ 9400 万行

如果行更小（100B/行）：
  C = 16000 / 120 ≈ 133 行/页
  F × F × C = 1142 × 1142 × 133 ≈ 1.73 亿行
```

> 📌 **关键结论**：3 层 B+ 树通常能容纳 **数千万到近亿行**（取决于行大小）。Root 页几乎永远常驻 Buffer Pool，第二层热点页也大概率命中。**这意味着对一个千万级数据表执行主键点查，底层真正触发的物理磁盘 I/O 通常只有 1 次**（读叶子页），查询耗时约 100~200μs（SSD）。`[须实测]`

### What（续）——B+ 树如何告诉 Buffer Pool "该加载哪一页"

**这就是 B+ 树与 Buffer Pool 的协作接口。** 以 `WHERE id = 1001` 为例：

```text
① 从 Root Page 开始（Root 页常驻 Buffer Pool，page_no 已知）
② Root Page 在 Buffer Pool 中，通过 Page Directory 二分查找
   → 1001 落在子指针 P₁ 的范围内（P₁ = page_no: 105）
③ 向 Buffer Pool 请求 page_no = 105
   ├── BP Hash Table 命中 → 直接返回内存地址（0 I/O）
   └── BP Hash Table 未命中 → BP 从磁盘加载 page 105（1 I/O）
④ 在 page 105 内继续二分 → 定位到子指针 P₂ = page_no: 2048
⑤ 向 Buffer Pool 请求 page_no = 2048
   ├── 命中 → 0 I/O
   └── 未命中 → 1 I/O
⑥ page 2048 是叶子页，通过 Page Directory 找到 id = 1001 的记录
⑦ 返回记录在 Buffer Pool 中的内存指针
```

**B+ 树的角色 = "定位器"**：它不直接读磁盘，而是通过逐层向下遍历，一步步告诉 Buffer Pool "我需要 page_no X"。Buffer Pool 负责实际的磁盘 I/O 和缓存管理。

> 📌 **这个解耦设计极其优雅**：B+ 树完全不需要知道 Buffer Pool 的内部实现（LRU 策略、Hash Table 等），它只需要知道"给我一个 page_no，你能返回这个页的内存地址"。这使得 B+ 树和 Buffer Pool 可以独立演进。

### What（续）——聚簇索引 vs 二级索引

```
聚簇索引 (Clustered Index)：
  B+ 树叶子节点存储 = 完整的数据行
  键 = 主键
  一张表只能有一个聚簇索引（数据只有一份物理排列）

二级索引 (Secondary Index)：
  B+ 树叶子节点存储 = 索引列值 + 主键值
  键 = 索引列
  
  回表 (Bookmark Lookup)：
  二级索引找到主键 → 再去聚簇索引查完整行
  
  ┌──────────────┐       ┌──────────────┐
  │ 二级索引      │       │ 聚簇索引      │
  │ (name → id)  │       │ (id → row)   │
  │              │       │              │
  │ "Alice" → 5  │──┐    │  5 → [完整行] │
  │ "Bob"   → 12 │  │    │ 12 → [完整行] │
  │ "Carol" → 5  │──┘    │              │
  └──────────────┘       └──────────────┘
       ↑ 回表：拿着主键 5 去聚簇索引再查一次
       ↑ 这意味着需要再次经过"定位→加载→查找"三步！
```

| 特性 | 聚簇索引 | 二级索引 |
|---|---|---|
| 叶子存什么 | 完整数据行 | 索引列值 + 主键 |
| 每表数量 | 1 个（就是表本身） | 可以有多个 |
| 范围查询 | 主键范围查询极快（叶子链表顺序扫描） | 索引列范围查询需要逐行回表 |
| 如果没有显式 PK | InnoDB 选第一个 UNIQUE NOT NULL 列；都没有则生成 6 字节 Row ID | — |
| **Buffer Pool 影响** | 聚簇索引页包含完整行，单页行数少 | 二级索引页只含索引列+PK，单页行数多，更"缓存友好" |

### What（续）——索引选择性（Selectivity）：该不该建索引的第一道判断题

**徒弟**：前面讲了 B+ 树的结构和容量，但我怎么判断"这一列到底该不该建索引"？

**老陈**：在建索引之前，必须先回答一个更基本的问题：**这列的值有多"独特"？** 这就是索引选择性（也叫区分度）。

```text
索引选择性 = COUNT(DISTINCT col) / COUNT(*)

值域：0.0 ~ 1.0
  → 越接近 1.0：每个值几乎唯一（如身份证号），建索引收益最大
  → 越接近 0.0：大量行共享同一个值（如性别只有男/女），建索引收益极小
```

**为什么选择性决定索引是否有效？** 从因果链推导：

```text
假设 users 表 100 万行，gender 列只有 "M" 和 "F" 两个值（各 ~50 万行）：

  SELECT * FROM users WHERE gender = 'M';

  即使 gender 上有 B+ 树索引：
  ① 索引定位到 gender = 'M' 的所有记录 → 50 万条
  ② 每条记录都需要回表取完整行 → 50 万次随机 I/O
  ③ 优化器一算：50 万行 × 回表代价 ≈ 直接全表扫描的代价
  ④ 结论：放弃索引，直接全表扫描（type=ALL）
```

| 选择性范围 | 示例列 | 索引收益 | 建议 |
|---|---|---|---|
| > 0.9 | 主键、身份证号、邮箱 | ✅ 极高 | 必建索引 |
| 0.1 ~ 0.9 | 用户名、城市、状态码（状态较多的场景） | ✅ 中等~高 | 视查询模式决定 |
| < 0.01 | 性别（M/F）、布尔值、is_deleted | ❌ 极低 | 通常不建单列索引 |

**实操诊断**：`SHOW INDEX FROM table` 中的 `Cardinality` 字段就是 InnoDB 维护的选择性统计值（唯一值的估算数量）。对比 `Cardinality` 和表的总行数，就能快速判断一个索引的"质量"：

```sql
SHOW INDEX FROM users;
-- Cardinality 列：
--   PRIMARY   → 1000000（= 总行数，完美）
--   idx_email → 998000（≈ 总行数，极好）
--   idx_gender → 2（只有 2 个不同值，几乎无用）
```

> 📌 **与 B+ 树扇出率的因果链**：选择性低的列 → 每个值对应大量行 → 索引叶子节点指向大量回表操作 → 相当于"索引帮了倒忙"。这和 Level 1 讲的"页内扇出率"是同一个思想在不同层面的映射——**索引的价值在于"用尽可能少的 I/O 排除尽可能多的无关数据"**，选择性低的列恰恰做不到这一点。

### What（续）——前缀索引（Prefix Index）：大字段索引的标准手段

**徒弟**：如果一列是 `VARCHAR(255)` 的 email 字段，我需要经常按 email 查询，但整个 255 字符建索引太浪费空间了——怎么办？

**老陈**：这正是前缀索引要解决的问题。**只取列值的前 N 个字符建索引**，牺牲微小的区分度，换取大幅的空间节省和 B+ 树扇出率提升。

```sql
-- ❌ 对整个 VARCHAR(255) 建索引：每条例如 "alice@example.com................" 全存
INDEX idx_email (email)
-- 索引记录大小：~255 bytes/条 → 单页能放的索引记录少 → B+ 树扇出小 → 树更高

-- ✅ 只取前 10 个字符建索引
INDEX idx_email_prefix (email(10))
-- 索引记录大小：~10 bytes/条 → 单页能放的索引记录多 → B+ 树扇出大 → 树更矮
```

**如何确定前缀长度 N？** 计算不同前缀长度下的选择性，找到"够用就好"的临界点：

```sql
-- 逐步增加前缀长度，观察选择性变化
SELECT COUNT(DISTINCT LEFT(email, 4))  / COUNT(*) AS sel_4,
       COUNT(DISTINCT LEFT(email, 8))  / COUNT(*) AS sel_8,
       COUNT(DISTINCT LEFT(email, 12)) / COUNT(*) AS sel_12,
       COUNT(DISTINCT LEFT(email, 16)) / COUNT(*) AS sel_16,
       COUNT(DISTINCT email)            / COUNT(*) AS sel_full
FROM users;

-- 典型结果：
-- sel_4 = 0.02, sel_8 = 0.65, sel_12 = 0.95, sel_16 = 0.99, sel_full = 1.0
-- → 选 N=12 已经足够（0.95 vs 1.0，差距极小）
```

| 方案 | 索引记录大小 | 叶子页扇出 | 选择性 | 空间占用 |
|---|---|---|---|---|
| 全列索引 `email` | ~255B | ~60 条/页 | 1.0 | 最大 |
| 前缀索引 `email(12)` | ~12B | ~1200 条/页 | 0.95 | 约 1/20 |

> 📌 **与 Level 1 的因果链**：索引列越短 → 每条索引记录越小 → 单个 16KB 页能放的索引记录越多（扇出越大）→ B+ 树层数越低 → 查询时需要加载的页数越少。前缀索引本质上是在用"微小的区分度损失"换"B+ 树整体效率的提升"。

**前缀索引的限制**：
- ❌ 不能用于 `ORDER BY`（前缀相同但后缀不同的记录，排序结果不正确）
- ❌ 不能用于覆盖索引（前缀不包含完整值，无法直接从索引返回结果）
- ✅ 可以用于 `WHERE` 的等值和前缀匹配查询

### What（续）——最左前缀原则：联合索引设计的第一准则

**徒弟**：前面讲了联合索引，坑 15 也说了范围查询会导致后面的列失效。但我需要一个明确的、可以指导设计的"原则"。

**老陈**：这条原则值得在正文里正面定义，而不是只在坑里反面出现：

```text
最左前缀原则（Leftmost Prefix Rule）：

  联合索引 (a, b, c) 在 B+ 树中的物理排列是：
    先按 a 排序 → a 相同时按 b 排序 → a 和 b 都相同时按 c 排序

  因此，联合索引能用于"定位"（缩小搜索范围）的条件是：
    查询必须从最左列开始，且不能跳过中间的列。

  等价说法：联合索引 (a, b, c) 可以当作以下三组索引使用：
    (a)          ← 只用第一列
    (a, b)       ← 用前两列
    (a, b, c)    ← 用全部三列

  但不能当作：
    (b)          ← 跳过了 a
    (c)          ← 跳过了 a 和 b
    (b, c)       ← 跳过了 a
```

**因果推导**（和 B+ 树的物理结构直接对应）：

```text
联合索引 (a, b, c) 的 B+ 树叶子节点：

  a=1, b=1, c=1  ←┐
  a=1, b=1, c=3  ←┤ a=1, b=1 内部，c 有序 → c 可用于定位 ✅
  a=1, b=1, c=5  ←┘
  a=1, b=3, c=2  ←┐
  a=1, b=3, c=7  ←┤ a=1 内部，b 有序 → b 可用于定位 ✅
  a=1, b=3, c=9  ←┘    但 b=3 内部，c 无序（b=1 和 b=3 的 c 值混在一起）
  a=2, b=2, c=1  ←┐
  a=2, b=2, c=4  ←┤ a=2 内部...
  a=2, b=5, c=3  ←┘

  结论：
  ✅ WHERE a = 1                → 利用 a 有序，二分查找定位
  ✅ WHERE a = 1 AND b = 3      → 先 a 定位，再 b 定位
  ✅ WHERE a = 1 AND b = 3 AND c = 7 → 三列全部用于定位
  ✅ WHERE a = 1 AND b > 3      → a 定位后，b 做范围扫描
  ❌ WHERE b = 3                → a 的值不确定，b 在全局无序，无法二分查找
  ❌ WHERE a = 1 AND c = 7      → a 定位后，b 不确定，c 在 b 的维度上无序
```

**联合索引列顺序的设计准则**：

```text
准则 1：等值查询列放前面，范围查询列放后面
  查询：WHERE a = 1 AND c = 5 AND b > 10
  最优索引：(a, c, b)  → a 和 c 等值定位，b 范围扫描
  而不是：(a, b, c)  → a 等值，b 范围后 c 失效

准则 2：选择性高的列放前面（在同等条件下）
  如果 a 有 1000 个不同值，b 有 10 个不同值
  → (a, b) 优于 (b, a)
  → 因为先按 a 筛选，能更快缩小范围

准则 3：考虑排序需求
  查询：WHERE a = 1 ORDER BY b
  → 索引 (a, b) 可以直接利用索引的有序性，避免 filesort
```

### What（续）——索引合并（Index Merge）：优化器的隐藏机制

**徒弟**：如果一张表上只有两个单列索引 `idx_a(a)` 和 `idx_b(b)`，查询是 `WHERE a = 1 OR b = 2`，是不是索引完全失效了？

**老陈**：不一定。InnoDB 的优化器有一个很多人不知道的机制叫 **Index Merge（索引合并）**——它可以**同时使用两个单列索引**，分别扫描后合并结果。

```text
表上有两个单列索引：idx_a(a), idx_b(b)

查询：SELECT * FROM t WHERE a = 1 OR b = 2

优化器的选择：
  方案 A：全表扫描（没有联合索引时的默认假设）
  方案 B：Index Merge ——
    ① 用 idx_a 扫描 a = 1 → 得到行集合 {r1, r3, r7}
    ② 用 idx_b 扫描 b = 2 → 得到行集合 {r2, r3, r9}
    ③ 对两个结果集做 Union → {r1, r2, r3, r7, r9}
    ④ 回表取完整行

  EXPLAIN 的 Extra 列会显示：Using union(idx_a, idx_b)
```

**Index Merge 的三种变体**：

| 变体 | 触发条件 | Extra 显示 | 合并方式 |
|---|---|---|---|
| **Union** | `WHERE a = 1 OR b = 2` | `Using union(idx_a, idx_b)` | 两个结果集取并集 |
| **Intersection** | `WHERE a = 1 AND b = 2` | `Using intersect(idx_a, idx_b)` | 两个结果集取交集 |
| **Sort-Union** | Union 的变体，先排序再合并 | `Using sort_union(idx_a, idx_b)` | 排序后合并（用于减少随机 I/O） |

> 📌 **重要提醒**：Index Merge 通常**不如一个设计良好的联合索引高效**——它需要做多次索引扫描 + 结果集合并（内存操作），而一个联合索引只需一次 B+ 树遍历。所以 Index Merge 是优化器在"没有联合索引"时的**兜底策略**，不是你应该依赖的常规手段。如果你看到 EXPLAIN 里频繁出现 Index Merge，说明该考虑建联合索引了。

**这个机制和坑 15 的关系**：坑 15 说"违反最左前缀原则导致索引失效"——但 Index Merge 告诉我们，**"索引失效"不是绝对的**。优化器会尽力利用现有的单列索引，只是效果通常不如联合索引。**正确的设计思路是"主动建好联合索引"，而不是"指望优化器帮你合并单列索引"。**

### What（续）——InnoDB 索引类型全景图

**徒弟**：前面讲了聚簇索引、二级索引、前缀索引、联合索引，还有坑 10 提到的 FULLTEXT……我需要一个完整的全景图。

**老陈**：把 InnoDB 支持的所有索引类型整理成一张表。注意区分**结构类型**（B+ 树/倒排/R-Tree）和**逻辑类型**（主键/唯一/普通等）——它们不是同一个维度的分类：

| **普通二级索引** | B+ 树 | 叶子存索引列 + 主键值，查询需回表 | ✅ Level 3 正文详述 |
| **唯一索引（UNIQUE）** | B+ 树 | 在普通二级索引基础上增加唯一性约束。**关键区别**：唯一索引不能用 Change Buffer 延迟合并（详见后文 Level 7），因为每次写入必须立即检查唯一性 | ⚠️ Level 7 Change Buffer 展开，坑 8 涉及加锁差异 |
| **联合索引** | B+ 树 | 多列组合索引，遵循最左前缀原则 | ✅ 本节正文刚讲 |
| **前缀索引** | B+ 树 | 取列值前 N 个字符建索引，节省空间 | ✅ 本节正文刚讲 |
| **降序索引** | B+ 树 | 8.0 新增，支持真正的降序存储（5.7 的 DESC 被忽略） | ✅ Level 3 的 5.7 vs 8.0 表格 |
| **表达式索引** | B+ 树 | 8.0 新增，对表达式建索引（如 `LOWER(name)`） | ✅ Level 3 的 5.7 vs 8.0 表格 |
| **全文索引 FULLTEXT** | **倒排索引** | 与 B+ 树完全不同的结构。将文本拆成词元（token），每个词元指向包含它的行。用于 `MATCH ... AGAINST` 语法 | ⚠️ 坑 10 提了一句"用 FULLTEXT"，未展开 |
| **空间索引 SPATIAL** | **R-Tree** | 用于 GIS 数据（经纬度、几何图形）。InnoDB 从 5.7 开始支持 SPATIAL 索引 | ❌ 长尾场景，本文不展开 |

> 📌 **FULLTEXT 的底层结构值得注意**：它和 B+ 树完全不同——B+ 树是"从键找页"的有序结构，而倒排索引是"从词找行"的映射结构。这就是为什么 `LIKE '%keyword%'` 无法走 B+ 树索引（坑 10），但 FULLTEXT 可以——因为 FULLTEXT 根本不靠字符的有序性做查找，它靠的是"词元→行号"的倒排映射。

**🏛️ 图书馆比喻**：

```text
B+ 树索引 = 图书馆的"按编号排序的目录柜"
  → 你知道要找的编号（或编号范围），顺着柜子的顺序快速定位

全文索引（倒排索引）= 图书馆的"关键词索引卡片"
  → 每张卡片写了一个关键词，后面列着所有包含这个关键词的书号
  → "MySQL" → [书号5, 书号23, 书号107, ...]
  → 你不需要知道书号的顺序，只需要找到关键词对应的卡片

空间索引（R-Tree）= 图书馆的"楼层平面图"
  → 按空间区域划分，"A区第3排到第5排" 对应一批书
  → 用于"找距离某个位置最近的书"这类空间查询
```



### What（续）——Adaptive Hash Index（自适应哈希索引）

InnoDB 在 B+ 树之上还维护了一个**自适应哈希索引**（AHI）：

- 当 InnoDB 发现某些索引值被**高频等值查询**（如 `WHERE id = 5`），会自动为这些值建立 Hash 映射
- 命中 AHI 时，**直接跳过 B+ 树遍历**，一步到位拿到 Buffer Pool 中的页地址 + 记录偏移
- AHI 由 InnoDB 自动维护，用户无法手动指定哪些列进入 AHI
- 参数 `innodb_adaptive_hash_index = ON/OFF`

> 📌 AHI 在高并发等值查询场景下可提升 10~30% 性能（教学量级），但在范围查询为主的场景下可能引入额外的维护开销。某些高并发写入场景下关闭 AHI 反而更好。`[须实测]`

### What（5.7 vs 8.0）——索引层面的变化

| 特性 | MySQL 5.7 | MySQL 8.0 | 变化类型 |
|---|---|---|---|
| **降序索引** | 不支持（`DESC` 被忽略，实际升序存储 + 反向扫描） | ✅ 支持真正的降序索引 | **语义变化** |
| **不可见索引** | 不支持 | ✅ `ALTER TABLE ... ALTER INDEX idx INVISIBLE` | 新能力 |
| **表达式索引** | 不支持 | ✅ `CREATE INDEX idx ON t ((LOWER(name)))` | 新能力 |
| **直方图** | 不支持 | ✅ `ANALYZE TABLE ... UPDATE HISTOGRAM` | 新能力 |

> 📌 降序索引是 **语义变化**（5.7 的 `DESC` 被静默忽略，8.0 真正生效——如果你的 SQL 写了 `DESC` 但实际行为变了，这是真正的行为差异）。不可见索引和表达式索引是 **新能力**，不影响已有行为。

### What（续）——🏛️ 图书馆视角：页分裂如何从 B+ 树波及 Buffer Pool

**这个分析把 Level 2 和 Level 3 串成了一条完整的因果链。**

```
UUID 主键的灾难链：

① UUID 随机插入 → B+ 树中间位置的叶子页被命中
② 该页已满 → 触发页分裂（Page Split）：
   - 申请新页
   - 搬移 ~50% 的记录到新页
   - 更新父节点的指针
③ 分裂后的两个页各只有 ~50% 的数据
④ 这两个页如果都在 Buffer Pool 中 → Buffer Pool 的有效数据密度降低 50%
⑤ 更糟的是：分裂产生的新页需要写入磁盘（随机写 I/O）
⑥ 父节点页也需要更新（可能触发级联分裂）
⑦ 分裂还打乱了叶子页的物理连续性 → 范围查询从顺序 I/O 退化为随机 I/O
⑧ 随机 I/O 意味着更多页需要加载到 Buffer Pool → 加剧缓存竞争

自增主键的幸福链：

① 自增插入 → 永远命中最后一个叶子页
② 该页满了 → 开辟全新页，追加到末尾（无分裂）
③ 新页 100% 利用率
④ Buffer Pool 中每个缓存页都是满满的
⑤ 叶子页物理连续 → 范围查询 = 顺序 I/O → 预读命中率高
⑥ 预读加载的页大概率会被用到 → 进入 New 区 → 缓存质量高
```

> 📌 **这就是为什么"主键自增"不仅仅是一个"写入优化"——它通过 B+ 树的页结构，间接影响了 Buffer Pool 的缓存效率、磁盘 I/O 模式、以及范围查询的性能。因果链从主键类型 → 页分裂 → Buffer Pool 利用率 → 全局性能。**

### How——读者 U 通过 B+ 树 + Buffer Pool 定位目标行（完整版）

```text
① U: UPDATE users SET name = 'NewName' WHERE id = 1001
② 从 Root Page（常驻 Buffer Pool，无需 I/O）开始
③ Root Page 内二分查找：1001 落在子指针 P_child 的范围内
④ 向 Buffer Pool 请求 P_child 对应的页
   ├── BP Hash 命中 → 内存直接返回（0 I/O）
   └── BP Hash 未命中 → 触发"加载"流程（1 I/O）
⑤ 在 P_child 页内继续二分 → 定位到下一级子指针
⑥ 重复 ④⑤ 直到到达叶子页（总计 1~3 次 BP 请求）
⑦ 在叶子页内通过 Page Directory 二分 → 组内顺序扫描
⑧ 找到 id = 1001 的记录，获取其在 Buffer Pool 中的内存地址
⑨ 开始修改（进入 Level 4~6 的事务/锁/MVCC 流程）
```

**徒弟**：如果 `WHERE` 条件没有索引怎么办？

**老陈**：**全表扫描**。InnoDB 从聚簇索引的第一个叶子页开始，沿叶子节点的双向链表逐页加载到 Buffer Pool，逐行检查 WHERE 条件。1 亿行的表 = 加载约 140 万个叶子页。即使每个页都在 Buffer Pool 中，CPU 逐行比较的开销也是巨大的。更糟的是，这 140 万页会涌入 Buffer Pool 的 Old 区，把真正的热点页挤出去——**这就是为什么慢查询优化第一条就是"检查是否走了索引"**。

#### 起点：NULL 在记录里怎么存（比 Page 结构更细一级）

Level 1 讲了 Page 内部结构，也讲了**一行记录在磁盘上的完整物理格式**（记录头 → NULL 值列表 → 变长字段长度列表 → 隐藏列 → 用户数据列）。这里聚焦和 NULL 直接相关的那一块：每条记录的 **NULL 值列表（NULL Flag List）**——一个 bitmap，每个"允许为 NULL"的列占一位，标记该列本行是否为空。

```text
单条记录的物理布局（简化）：

┌──────────────────────────────────────────────────────────────┐
│  变长字段长度列表  │  NULL Flag List  │  记录头  │  各列数据   │
│  (每个 VARCHAR   │  (每个允许NULL   │ (trx_id │  (按列定义   │
│   占 1~2 字节)    │   的列占 1 bit)  │  roll_ptr │   顺序存储)  │
│                   │                  │  列数据…) │             │
└──────────────────────────────────────────────────────────────┘

关键推论：
  如果某列本行是 NULL → 这一列完全不占用该行的数据存储空间
  → 只在 NULL Flag List 的 bitmap 里标一位（1 bit）
  → NULL 不是"存了一个空字符串"，而是"这个位置的数据字节根本不存在"
```

这解释了为什么 NULL 值在索引里能被正常处理——它在 B+ 树里作为一个"确定的、可排序的标记"存在，而不是一段无意义的数据。

#### 哪些索引允许 NULL

| 索引类型 | 是否允许 NULL | 关键点 |
|---|---|---|
| 主键索引（聚簇索引） | ❌ 不允许 | 定义主键时隐式加 `NOT NULL`，即使建表没显式写 |
| 唯一索引（UNIQUE） | ✅ 允许，且**可以有多个 NULL** | 见下方"陷阱 1" |
| 普通二级索引 | ✅ 允许，无限制 | — |
| 联合索引 | ✅ 任意列都可以是 NULL | 见下方"排序与查询行为" |
| 前缀索引 | ✅ 允许 NULL | 不存在"截取前缀"的问题 |

#### 排序规则：NULL 在索引里排在哪

MySQL 里 NULL 在索引排序（ASC）中被当作**比任何值都小**处理。联合索引 `(a, b, c)` 里，如果 b 有 NULL，B+ 树内的顺序是：

```text
先按 a 排序
a 相同时，b=NULL 的记录排在最前面（比 b=1、b=2... 都靠前）
a、b 都相同时，再按 c 排序

具体示例——索引 (a, b, c) 的叶子节点排列：
  a=1, b=NULL, c=3    ← b=NULL 排最前
  a=1, b=NULL, c=7
  a=1, b=1,   c=2     ← b 有具体值，排在 NULL 后面
  a=1, b=1,   c=5
  a=1, b=3,   c=1
  a=1, b=3,   c=9
  a=2, b=NULL, c=4
  a=2, b=2,   c=6
```

**🏛️ 图书馆比喻**：目录检索柜里，如果某本书的"出版年份"字段是 NULL，它会被放到该分类下所有有出版年份的书的前面——NULL 不是一个"缺失"，而是一个"确定的、排在最前的位置"。

#### 查询行为：`IS NULL` 是等值条件，`IS NOT NULL` 是范围条件

**这是最容易被直觉误导、也是这条因果链里最关键的一环**，直接关联坑 15（最左前缀原则）：

```sql
-- 索引: (a, b, c)

-- ① IS NULL —— 等值条件，b、c 都能正常走索引
SELECT * FROM t WHERE a = 1 AND b IS NULL AND c = 5;
-- EXPLAIN 的 key_len 显示 a、b、c 三列全部用到 ✅
-- 原因：NULL 在索引里是一个具体的、可定位的排序位置，不是一个区间

-- ② IS NOT NULL —— 范围条件，c 会失效，和坑 15 是同一类问题
SELECT * FROM t WHERE a = 1 AND b IS NOT NULL AND c = 5;
-- 相当于 "排除 b=NULL 那一段，取剩余所有"
-- 性质等同于 WHERE a=1 AND b>10 AND c=5
-- c 无法继续利用索引有序性 ❌
```

**因果推导**：

```text
IS NULL：
  → 在 B+ 树中，NULL 是 b 列的一个确定值（排在最前）
  → WHERE b IS NULL 等价于 WHERE b = "NULL标记"
  → 等值条件，后面的 c 列仍然有序 → c 可用于索引定位 ✅

IS NOT NULL：
  → 排除 b=NULL 那一段，取 b 列从最小非 NULL 值到最大值的全部
  → 这是一个范围条件（类似 b >= 最小值）
  → 和坑 15 的 b > 10 完全同类——范围条件后面的列无法用于定位 ❌
```

> 📌 **版本勘误**："索引列有 NULL 就没法用索引"是一个流传很广的错误说法。InnoDB 的 B+ 树正常收录 NULL 值，`WHERE col IS NULL` 完全可以走索引（`EXPLAIN` 的 `type` 通常是 `ref`），不会退化成全表扫描。真正会导致索引失效的是 `IS NOT NULL` 出现在联合索引的中间列（范围条件的通病），以及下面两个陷阱。

#### 陷阱 1：联合唯一索引里，NULL 不受唯一性约束限制

```sql
UNIQUE KEY uk_email (email)

INSERT INTO t VALUES (1, NULL);  -- ✅ 成功
INSERT INTO t VALUES (2, NULL);  -- ✅ 也成功！不报 Duplicate entry

-- 联合唯一索引同理
UNIQUE KEY uk_a_b (a, b)

INSERT INTO t VALUES (1, NULL);  -- ✅
INSERT INTO t VALUES (1, NULL);  -- ✅ 依然成功
```

**根因**：唯一性判断依赖"两个值是否相等"，而 SQL 的三值逻辑里 `NULL = NULL` 的结果是 `NULL`（既非 true 也非 false），不满足"相等"，所以不会被判定为冲突。这是 SQL 标准行为，不是 InnoDB 特有的，PostgreSQL、SQL Server 一致。

**生产事故点**：业务经常误以为"加了唯一索引就绝对不会重复"，但只要参与索引的某列允许 NULL、且值恰好是 NULL，重复行照样能插入成功。**修正方式**：该列改 `NOT NULL` + 业务默认值（空字符串/0），或应用层兜底校验。

#### 陷阱 2：`NOT IN` 里混入 NULL，整个查询静默返回空结果集

```sql
SELECT * FROM t WHERE id NOT IN (1, 2, NULL);
-- 只要 IN 列表里出现一个 NULL，NOT IN 永远返回空结果集！

-- 展开等价于：
-- id <> 1 AND id <> 2 AND id <> NULL
-- 而 id <> NULL 的结果永远是 NULL（非 true），整个 AND 链条永远不成立
```

**这个坑经常伪装成"索引问题"**：典型场景是 `NOT IN` 的列表来自子查询，子查询字段本身允许 NULL 又没过滤，业务发现查不出预期数据，第一反应是去查 `EXPLAIN`、查索引是否生效，但真正的病根和索引无关，是数据里的 NULL 值污染了 `IN` 列表。**排查时一定要先确认 `NOT IN` 子查询结果集里有没有 NULL**，而不是先怀疑索引。

#### 这一节的因果链总结

```text
记录里 NULL 不占数据空间（存储层）
    → 索引里 NULL 是一个确定的排序位置、且排最前（索引结构层）
        → IS NULL 能正常用索引，IS NOT NULL 是范围条件会让后续列失效（查询优化层）
            → 唯一索引不能拦住多个 NULL，NOT IN 遇 NULL 会整体失效（业务陷阱层）

四层环环相扣，任何一层理解错了，都会导致线上一个
"看起来跟索引有关、实际另有病根"的诡异问题。
```

### Transfer——可迁移的工程方法论

1. **扇出最大化**：B+ 树的核心思想——非叶子节点不存数据，只存键和指针，最大化每层的扇出，降低树高。这在 Elasticsearch（倒排索引的 segment 层级）、文件系统（ext4 的 extent tree）中反复出现。
2. **索引与缓存的解耦接口**：B+ 树通过 `page_no` 与 Buffer Pool 交互，两者互不知晓对方的内部实现。这种"通过抽象接口解耦"的设计是大型系统的基石——微服务的 API 契约、操作系统的系统调用都是同一思想。
3. **主键有序性 = 全链路效率**：自增主键的好处不是局部的——它从 B+ 树（无页分裂）→ Buffer Pool（高利用率）→ 磁盘 I/O（顺序写）→ 范围查询（物理连续），形成正向飞轮。反过来，UUID 主键在每个环节都制造摩擦。
4. **自适应索引**：运行时根据访问模式自动优化（AHI）——JIT 编译、数据库的自动统计信息收集都是这个思想。

**本层留下的新账**：B+ 树解决了"告诉 Buffer Pool 该加载哪一页"的问题，配合 Buffer Pool 实现了毫秒级定位。但**如果两个 UPDATE 同时修改同一行怎么办？** 没有并发控制机制，两个事务可能读到同一个旧值，各自修改后写回，后写的覆盖先写的——**丢失更新**。→ 逼出 Level 4。

> 🔴 **口诀**：三层 B+ 管亿行，净化中间挂叶链；选择性高才值得建，左前缀定联合索引；NULL 不占数据位，IS NULL 走索引 IS NOT 退范围；自增不裂缓存满，UUID 分裂全链路瘫。

## Level 4：事务与 ACID——并发读写为什么需要"规矩"

### 👶 前置知识关卡
- [ ] Level 3：通过 B+ 树可以在 O(log N) 内定位到目标行？
- [ ] 你知道"丢失更新"和"脏读"分别是什么场景下发生的？
- [ ] 你理解"原子性"和"持久性"是两个不同维度的保证吗？

### Why——裸并发死在哪

**徒弟**：既然 B+ 树能快速定位行，那直接让多个事务并发读写不就行了？数据库自己保证写入正确就好。

**老陈**：来看四个经典的并发灾难：

| 并发灾难 | 场景 | 后果 |
|---|---|---|
| **丢失更新（Lost Update）** | T1 读余额 100 → T2 读余额 100 → T1 写 120（+20）→ T2 写 130（+30） | 最终 130，正确应是 150。T1 的 +20 被覆盖 |
| **脏读（Dirty Read）** | T1 写 price=50（未提交）→ T2 读到 50 → T1 回滚 | T2 读到了一个"从未真正存在"的值 |
| **不可重复读（Non-Repeatable Read）** | T1 读 price=100 → T2 改 price=200 并提交 → T1 再读 price=200 | 同一事务内两次读同一行，结果不同 |
| **幻读（Phantom Read）** | T1 读 `WHERE age > 20` 得到 3 行 → T2 插入 age=25 的行并提交 → T1 再读得到 4 行 | 同一事务内两次范围查询，行数不同 |

| 朴素方案 | 它本来想解决什么 | 它留下的致命账 |
|---|---|---|
| 不做并发控制 | 最大吞吐 | 四种灾难全部出现 |
| 串行执行所有事务 | 完全正确 | 吞吐降到单线程水平，不可接受 |
| **隔离级别** | 让用户在正确性和性能之间选择 | ✅ 但不同级别需要不同的实现机制（锁 / MVCC）→ Level 5、6 |

### What——ACID 与四个隔离级别

**ACID 四维保证**：

| 属性 | 含义 | InnoDB 靠什么实现 |
|---|---|---|
| **A**tomicity（原子性） | 事务要么全做，要么全不做 | Undo Log（回滚到事务开始前状态） |
| **C**onsistency（一致性） | 事务执行前后数据库处于合法状态 | A + I + D + 应用层约束共同保证 |
| **I**solation（隔离性） | 并发事务互不干扰 | 锁 + MVCC |
| **D**urability（持久性） | 提交后数据不丢失 | Redo Log（WAL） |

**四个隔离级别矩阵**：

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | InnoDB 实现方式 |
|---|---|---|---|---|
| `READ UNCOMMITTED` | ✗ 可能 | ✗ 可能 | ✗ 可能 | 无锁，无 MVCC（直接读最新版本） |
| `READ COMMITTED` | ✅ 防止 | ✗ 可能 | ✗ 可能 | MVCC：每次 SELECT 生成新 Read View |
| `REPEATABLE READ`（默认） | ✅ 防止 | ✅ 防止 | ✅ InnoDB 用 Next-Key Lock 大部分防止 | MVCC：事务首次 SELECT 生成 Read View 并复用 |
| `SERIALIZABLE` | ✅ 防止 | ✅ 防止 | ✅ 防止 | 所有 SELECT 自动加 `LOCK IN SHARE MODE` |

> 📌 **最容易错的点**：InnoDB 的 RR 级别通过 **Next-Key Lock（锁）+ MVCC（快照读）** 组合，在大多数场景下防止幻读。但仍有边界场景会出现幻读（详见 Level 5 和 Level 6 的坑）。**不要说"InnoDB RR 完全解决了幻读"**。

### What（续）——事务的生命周期

```
                    START TRANSACTION
                          │
                    ┌─────▼─────┐
                    │   Active   │ ← 事务正在执行 SQL
                    └─────┬─────┘
                    ┌─────┴─────┐
                    │           │
              ┌─────▼─────┐ ┌──▼──────────┐
              │ Partially  │ │  Failed     │
              │ Committed  │ │ (出错/死锁) │
              └─────┬─────┘ └──┬──────────┘
                    │           │
              ┌─────▼─────┐ ┌──▼──────────┐
              │  Committed │ │  Aborted  │
              │ (已提交)   │ │ (已回滚)    │
              └───────────┘ └─────────────┘
```

### How——读者 U 开启事务

```text
① U 所属事务 T 执行 BEGIN / START TRANSACTION
② InnoDB 为 T 分配 trx_id（事务 ID，单调递增的 8 字节整数）
③ T 进入 Active 状态
④ T 的后续 SQL 将在 Level 5（加锁）和 Level 6（MVCC 快照读）的框架下执行
⑤ T 执行 COMMIT 时：
   ⑤a 写入 Redo Log（prepare → commit，详见 Level 7）
   ⑤b 释放所有锁
   ⑤c 状态变为 Committed
⑥ T 执行 ROLLBACK 时：
   ⑥a 通过 Undo Log 逆向操作，恢复到事务开始前
   ⑥b 释放所有锁
   ⑥c 状态变为 Aborted
```

**徒弟**：`trx_id` 是全局唯一的吗？会不会溢出？

**老陈**：`trx_id` 是 8 字节无符号整数（`uint64`），最大值 2^64 - 1 ≈ 1.8 × 10^19。即使每秒 100 万个事务，也需要约 **58 万年**才能用完。不是你需要担心的问题。

> 📌 **InnoDB 的 trx_id 分配**：自 MySQL 5.6.4 起，`START TRANSACTION READ ONLY` 声明的只读事务不分配 trx_id（不获取 trx->mutex），5.7 和 8.0 均延续此行为。这是一个常被忽略的优化——如果你的应用有大量只读查询，显式声明 `READ ONLY` 可以减少内部结构的压力。

### Transfer——可迁移的工程方法论

1. **隔离级别 = 正确性与吞吐的 trade-off**：这个思想适用于所有并发系统——Kafka 的 `isolation.level`、Redis 的事务（MULTI/EXEC）都面临类似选择。
2. **ACID 不是铁板一块**：四个属性由不同机制实现（Undo/Redo/Lock/MVCC），理解每个属性的实现机制才能在出问题时精准定位。
3. **事务 ID 的设计**：单调递增、足够大、不需要回收——这是分布式系统中"逻辑时钟"思想的变体。

**本层留下的新账**：隔离级别定义了"应该防止什么"，但**具体怎么防止？** 两个事务写同一行时用什么机制互斥？→ 逼出 Level 5（锁机制）。

> 🔴 **口诀**：四级隔离防三灾，实现靠锁加快照。

## Level 5：锁机制——从表锁到间隙锁的进化链

### 👶 前置知识关卡
- [ ] Level 4：RR 隔离级别需要防止脏读、不可重复读和幻读？
- [ ] Level 3：B+ 树叶子节点通过双向链表串联？
- [ ] 你理解"锁的粒度"对并发度的影响吗？

### Why——表级锁和简单行锁死在哪

**徒弟**：给每行加一把锁，谁要改就先拿锁，不就行了？

**老陈**：先看锁粒度的进化链：

| 朴素方案 | 它本来想解决什么 | 它留下的致命账 |
|---|---|---|
| 表级锁（锁整张表） | 实现简单 | 任何写操作阻塞全表所有读写，并发度 = 1 |
| 行级锁（只锁目标行） | 最大化并发 | ❌ **幻读**：T1 `SELECT * WHERE id > 5 FOR UPDATE` 锁了 id=6,7,8 的行，T2 插入 id=9 不冲突 → 幻读 |
| 行锁 + 间隙锁 | 防止幻读 | ✅ 但实现复杂度高，死锁概率增加 |

### What——InnoDB 的三种行级锁

InnoDB 的行级锁实际上有**三种形态**：

```
假设 B+ 树叶子节点中存在索引值：... 5, 8, 12, 15, 20 ...

Record Lock（记录锁）：
  只锁一行记录
  例：WHERE id = 8 → 只锁 id=8 这一行
  ┌───┐
  │ 8 │ ← 🔒 locked
  └───┘

Gap Lock（间隙锁）：
  锁两个索引值之间的"间隙"，不锁记录本身
  例：锁 (5, 8) 这个间隙 → 阻止其他事务在此间隙内插入新行
  ┌───┐     ┌───┐
  │ 5 │ gap │ 8 │
  └───┘(5,8)└───┘
           ← 🔒 gap locked

Next-Key Lock（临键锁 = Record Lock + Gap Lock）：
  对索引中的每条记录 R，Next-Key Lock = R 本身的 Record Lock + R 之前间隙的 Gap Lock
  加锁范围 = 左开右闭区间 (prev_key, R.key]

  例：索引值存在 [5, 8, 12, 15, 20]
  对 id=8 加 Next-Key Lock → 锁住 (5, 8]：
    → 包括 id=8 这条记录本身（Record Lock）
    → 包括 (5, 8) 的间隙，阻止插入 id=6,7（Gap Lock）
    → 但不锁 id=5
  ┌───┐     ┌───┐
  │ 5 │ gap │ 8 │ ← 🔒 record + gap locked
  └───┘(5,8]└───┘
```

> 📌 **InnoDB RR 隔离级别下，`SELECT ... FOR UPDATE` / `UPDATE` / `DELETE` 默认使用 Next-Key Lock**。这是防止幻读的核心机制。

### What（续）——锁的加锁规则（RR 隔离级别）

这是 InnoDB 最复杂也最重要的部分。加锁规则可以总结为：

```
RR 隔离级别下的加锁规则：

1. 加锁的基本单位是 Next-Key Lock (左开右闭)
2. 访问到的索引记录会退化为 Record Lock（如果查询条件是等值且唯一）
3. 索引上的等值查询，如果记录不存在，Next-Key Lock 退化为 Gap Lock
4. 没有索引时，全表扫描 → 所有行加 Record Lock + 所有间隙加 Gap Lock ≈ 锁表
```

**具体场景分析**：

| SQL | 索引情况 | 实际加锁范围 |
|---|---|---|
| `SELECT * FROM t WHERE id = 5 FOR UPDATE` | id 是 PK | Record Lock on id=5（唯一索引等值，退化为记录锁） |
| `SELECT * FROM t WHERE id = 5 FOR UPDATE` | id=5 不存在 | Gap Lock on (prev_id, next_id)（记录不存在，退化为间隙锁） |
| `SELECT * FROM t WHERE age = 25 FOR UPDATE` | age 是普通索引 | Next-Key Lock on age=25 + Gap Lock on (25, next_age)（非唯一索引，需要锁间隙防幻读） |
| `SELECT * FROM t WHERE age BETWEEN 20 AND 30 FOR UPDATE` | age 是普通索引 | 多个 Next-Key Lock 覆盖 [20, 30] 范围 |
| `UPDATE t SET name='x' WHERE name = 'Alice'` | name 无索引 | **全表所有行和间隙加锁** ≈ 表锁！ |

> 📌 **最容易错的点**：`WHERE` 条件列没有索引时，InnoDB 需要全表扫描，**对扫描到的每一行都加锁**。这不是"退化成表锁"的比喻——它是真的逐行加锁，效果等同于表锁，但 `information_schema.INNODB_LOCKS` 里看到的是行锁记录。**一定要确保 WHERE 条件走索引！**

### What（续）——意向锁（Intention Lock）

意向锁是表级锁，用于**协调表锁和行锁的冲突检测**：

| 锁类型 | 含义 |
|---|---|
| IS（Intention Shared） | 事务打算给某些行加 S 锁（共享锁/读锁） |
| IX（Intention Exclusive） | 事务打算给某些行加 X 锁（排他锁/写锁） |

```
加行锁前，先加意向锁：
  T 要对某行加 X 锁
  → 先对表加 IX 锁（如果还没有）
  → 再对行加 X 锁

冲突矩阵：
       IS    IX    S     X
IS     ✅    ✅    ✅    ❌
IX     ✅    ✅    ❌    ❌
S      ✅    ❌    ✅    ❌
X      ❌    ❌    ❌    ❌

意义：如果 T1 要给整张表加 S 锁（如 LOCK TABLE），只需要检查表上有没有 IX 锁，
     而不需要遍历所有行检查行锁。O(1) 检测。
```

### What（续）——死锁检测与处理

InnoDB 的死锁处理有两种策略：

| 策略 | 参数 | 行为 |
|---|---|---|
| **等待超时** | `innodb_lock_wait_timeout`（默认 50s） | 等锁超过此时间则报错 `Lock wait timeout exceeded` |
| **死锁检测** | `innodb_deadlock_detect = ON`（默认） | 维护等待图（wait-for graph），检测到环时回滚持有最少行锁的事务 |

> 📌 **高并发下的死锁检测开销**：当并发线程数 > 100 时，死锁检测的等待图遍历可能成为瓶颈（复杂度与锁数量、事务数量相关 `[教学量级]`）。MySQL 5.7.15+ 可以通过 `innodb_deadlock_detect = OFF` 关闭死锁检测，仅依赖超时。但这是极端场景下的 trade-off，大多数业务不应关闭。

### What（5.7 vs 8.0）——锁机制的变化

| 特性 | MySQL 5.7 | MySQL 8.0 |
|---|---|---|
| **锁信息查看** | `information_schema.INNODB_LOCKS` / `INNODB_LOCK_WAITS` | ❌ 已移除；改用 `performance_schema.data_locks` / `data_lock_waits` |
| **SKIP LOCKED** | 不支持 | ✅ `SELECT ... FOR UPDATE SKIP LOCKED`（跳过被锁的行） |
| **NOWAIT** | 不支持 | ✅ `SELECT ... FOR UPDATE NOWAIT`（立即报错而非等待） |
| **`innodb_locks_unsafe_for_binlog`** | 存在（允许 RC 下减少 gap lock） | ❌ 已移除（8.0 统一行为） |

> 📌 `SKIP LOCKED` 和 `NOWAIT` 是 8.0 的**语义新增能力**，对消息队列类场景（多消费者抢任务）极有价值。5.7 只能用 `GET_LOCK()` 应用层锁模拟。

### How——读者 U 加锁的完整过程

```text
① U: UPDATE users SET name = 'NewName' WHERE id = 1001
② 对表加 IX 意向锁
③ 通过 B+ 树定位到 id = 1001 的记录
④ 对 id = 1001 加 X（排他）锁
   ├── 因为 id 是主键（唯一索引），等值查询
   └── Next-Key Lock 退化为 Record Lock（只锁这一行）
⑤ 修改 name 字段（此时其他事务如果要修改 id=1001 会被阻塞）
⑥ 如果 id 上有二级索引且被修改，还需要对二级索引记录加锁
⑦ COMMIT 时释放所有锁
```

**徒弟**：如果 `WHERE id > 1000` 呢？

**老陈**：

```text
① U: DELETE FROM users WHERE id > 1000
② 对表加 IX 锁
③ 从 B+ 树定位到 id > 1000 的第一条记录（比如 id = 1001）
④ 对 id = 1001 加 Next-Key Lock (prev_id, 1001]
⑤ 沿叶子链表向后扫描，对每条满足条件的记录加 Next-Key Lock
⑥ 直到遇到不满足条件的记录（比如 id = 2000），对 (last_match, 2000] 加 Gap Lock
⑦ 所有 id ∈ (1000, +∞) 的行和间隙都被锁住了 → 防止幻读
```

### What（续）——MDL（Metadata Lock）：Server 层的"隐形锁队列"

**这是 InnoDB 行锁之外、MySQL Server 层的另一套锁机制，却是生产环境最高频的"诡异阻塞"故障源。**

**徒弟**：InnoDB 的行锁已经够复杂了，还有别的锁？

**老陈**：有。MDL 不在 InnoDB 层，而在 **MySQL Server 层**。它保护的不是数据行，而是**表的元数据结构**（表定义、列定义等）。任何对表的访问——哪怕是 `SELECT`——都需要先获取 MDL。

```text
MDL 的两种模式：
  MDL_SHARED（读锁）：普通 SELECT / INSERT / UPDATE / DELETE 持有
  MDL_EXCLUSIVE（写锁）：ALTER TABLE / DROP TABLE / TRUNCATE TABLE 等 DDL 持有

冲突规则：
  MDL_SHARED 与 MDL_SHARED → 兼容（多个查询可以并发读同一张表）
  MDL_SHARED 与 MDL_EXCLUSIVE → 不兼容（DDL 需要独占）
  MDL_EXCLUSIVE 与 MDL_EXCLUSIVE → 不兼容
```

**致命特性：MDL 的 FIFO 队列会引发"雪崩式阻塞"**

```text
时间线：

T0  T1 开启一个长事务：BEGIN; SELECT * FROM orders WHERE id = 1;
    → T1 持有 orders 表的 MDL_SHARED（读锁）
    → T1 忘了 COMMIT，一直保持连接

T1  DBA 执行 ALTER TABLE orders ADD INDEX idx_status (status);
    → 需要 MDL_EXCLUSIVE（写锁）
    → 发现 T1 持有 MDL_SHARED → DDL 进入等待队列

T2  新来的普通查询：SELECT * FROM orders WHERE id = 2;
    → 需要 MDL_SHARED（读锁）
    → 按常理，读锁和读锁兼容，应该能直接执行
    → 但是！MySQL 的 MDL 队列是 FIFO（先进先出）
    → T2 发现队列前面有一个等待 MDL_EXCLUSIVE 的 DDL
    → T2 被排在 DDL 后面，等待 DDL 先完成
    → 而 DDL 在等 T1 释放锁

结果：T1（忘了 commit 的长事务）→ 阻塞 DDL → DDL 阻塞所有后续查询
      SHOW PROCESSLIST 出现大量 "Waiting for table metadata lock"
      但 InnoDB 行锁指标（Innodb_row_lock_waits）完全正常！
      因为问题根本不在 InnoDB 层，而在 Server 层的 MDL 队列。
```

**排查方法**：

```sql
-- MySQL 8.0：查看 MDL 持有和等待情况
SELECT * FROM performance_schema.metadata_locks
WHERE OBJECT_SCHEMA = 'your_db' AND OBJECT_NAME = 'orders';

-- 找到持有 MDL 的线程 ID 后，查看对应的连接
SELECT * FROM information_schema.processlist WHERE ID = <thread_id>;

-- 确认是长事务后，KILL 掉
KILL <connection_id>;
```

> 📌 **生产环境必做**：① 监控长事务（`innodb_trx` 中运行超过 60s 的事务）；② DDL 操作选择低峰期执行；③ 设置 `lock_wait_timeout`（默认 31536000 秒 = 1 年，生产环境建议调低到 10~60 秒）防止 DDL 无限等待。

### What（续）——行锁的物理本质：锁的是"索引记录"，不是"数据行"

**这是 Level 5 最重要的一条底层真相，也是坑 1（无索引锁全表）的根本原因。**

**徒弟**：前面一直在说"行锁"，但 InnoDB 到底是怎么在物理层面"锁住一行"的？

**老陈**：**InnoDB 的行锁，锁的是 B+ 树索引上的记录（Index Record），不是数据行本身。** 没有索引，就没有"索引记录"可以加锁，只能退化为全表扫描加锁。

```text
聚簇索引（Clustered Index）上加锁：

  ┌─────────────────────────────────────────────┐
  │  B+ 树叶子节点 = 完整数据行                   │
  │  每行数据本身就是一个"聚簇索引记录"            │
  │  加锁时：锁直接标记在聚簇索引的叶子记录上      │
  └─────────────────────────────────────────────┘

二级索引（Secondary Index）上加锁：

  ┌─────────────────────────────────────────────┐
  │  B+ 树叶子节点 = (索引列值, 主键值)           │
  │  加锁时：                                      │
  │    ① 先在二级索引的 B+ 树叶子记录上加锁         │
  │    ② 再通过主键值，去聚簇索引上对对应行加锁      │
  │  （两棵 B+ 树上的记录都要锁）                   │
  └─────────────────────────────────────────────┘

没有索引时（全表扫描加锁）：

  ┌─────────────────────────────────────────────┐
  │  WHERE 条件列没有索引                          │
  │  → InnoDB 无法通过索引记录加锁                 │
  │  → 只能扫描聚簇索引上的每一条记录               │
  │  → 对聚簇索引上的每一行都加 Next-Key Lock       │
  │  → 效果等同于表锁                              │
  │  → 但在 information_schema 里看到的是行锁记录   │
  └─────────────────────────────────────────────┘
```

**为什么这很重要？**

| 推论 | 说明 |
|---|---|
| **行锁必须有索引才能生效** | 没有索引 → 没有索引记录可锁 → 退化为逐行加锁 ≈ 表锁 |
| **死锁分析要看索引** | 死锁检测的等待图是基于索引记录锁构建的，不是基于数据行 |
| **不同索引上的锁互不干扰** | 在二级索引 `idx_a` 上加锁和在二级索引 `idx_b` 上加锁，操作的是不同 B+ 树上的不同记录 |

> 📌 **和 Level 3 的闭环**：这条真相把 Level 3 的 B+ 树索引和 Level 5 的锁机制彻底串起来了——**B+ 树不仅是查询加速器，还是锁的承载结构**。没有 B+ 树索引，锁就无处可"挂"，只能退化为全表扫描逐行加锁。

### What（续）——`REPLACE INTO` vs `INSERT ... ON DUPLICATE KEY UPDATE` 的锁行为差异

**徒弟**：这两个语法都能实现"有则更新，无则插入"，锁行为有区别吗？

**老陈**：区别很大。大厂生产环境中，**绝大多数场景应该用 `INSERT ... ON DUPLICATE KEY UPDATE`，而不是 `REPLACE INTO`**。

```text
场景：表上有唯一索引 uk，尝试插入一个会冲突的值

INSERT INTO t VALUES (1, 'a') ON DUPLICATE KEY UPDATE name = 'a':
  ┌─────────────────────────────────────────────────┐
  │  冲突时：                                         │
  │  ① 对冲突行加 X 锁（Record Lock）                │
  │  ② 就地 UPDATE 该行的 name 列                    │
  │  ③ 释放锁                                        │
  │                                                   │
  │  锁范围 = 冲突行本身                              │
  └─────────────────────────────────────────────────┘

REPLACE INTO t VALUES (1, 'a'):
  ┌─────────────────────────────────────────────────┐
  │  冲突时：                                         │
  │  ① 对冲突行加 X 锁（Record Lock）                │
  │  ② DELETE 该冲突行                               │
  │  ③ INSERT 新行（全新主键值）                       │
  │  ④ RR 下 DELETE 还会触发 Gap Lock                 │
  │                                                   │
  │  锁范围 = 冲突行 + 间隙（Gap Lock）               │
  └─────────────────────────────────────────────────┘
```

| 对比维度 | `INSERT ... ON DUPLICATE KEY UPDATE` | `REPLACE INTO` |
|---|---|---|
| 冲突时操作 | 就地 UPDATE | DELETE + INSERT |
| 锁范围 | 仅冲突行 | 冲突行 + 间隙（RR 下有 Gap Lock） |
| 死锁风险 | 低 | **高**（DELETE 触发 Gap Lock 扩大锁范围） |
| 自增 ID | 不变（UPDATE 不消耗新 ID） | **消耗新 ID**（DELETE 旧行 + INSERT 新行） |
| 触发器 | 触发 `ON UPDATE` | 触发 `ON DELETE` + `ON INSERT` |

> 📌 **大厂最佳实践**：使用 `INSERT ... ON DUPLICATE KEY UPDATE` 代替 `REPLACE INTO`，除非确实需要"删除+重建"语义（比如需要重置所有列的值）。`REPLACE INTO` 的 DELETE + INSERT 语义在 RR 下会触发 Gap Lock，显著增加死锁概率。

### Transfer——可迁移的工程方法论

1. **锁粒度进化链**：表锁 → 行锁 → 间隙锁，每一步都是在"并发度"和"正确性"之间找平衡。分布式锁（Redis Redlock / ZooKeeper）也面临类似的粒度选择。
2. **意向锁 = 层次化锁协议的信号量**：在多级资源（表→页→行）上，上层用"意向"信号避免遍历下层——这在文件系统的目录锁、Java 的 `StampedLock` 中也有体现。
3. **死锁检测的 trade-off**：检测本身有开销。高并发下可以选择"超时不检测"——这是正确性与吞吐的经典权衡。

**本层留下的新账**：锁机制让写操作互斥，保证了正确性。但**所有读操作也要加锁吗？** 如果 `SELECT` 也要加 S 锁，那读和写互斥，并发度大打折扣。**能不能让读不加锁？** → 逼出 Level 6（MVCC）。

> 🔴 **口诀**：临键锁防幻读，无索引就锁全表；MDL 队列 FIFO，长事务卡死全表。

<a id="level-6"></a>
## Level 6：MVCC——读写不再互斥的魔法

### 👶 前置知识关卡
- [ ] Level 5：Next-Key Lock 在 RR 级别下防止幻读？
- [ ] Level 4：RC 和 RR 隔离级别的区别？
- [ ] 你知道"快照读"（普通 SELECT）和"当前读"（SELECT FOR UPDATE）的区别吗？

### Why——锁模式读写互斥死在哪

**徒弟**：Level 5 解决了写写冲突。那读写冲突呢？读操作加 S 锁，写操作加 X 锁，S 和 X 互斥，所以读和写互相阻塞。

**老陈**：对，在纯锁模型下：

| 场景 | 纯锁模型 | 后果 |
|---|---|---|
| T1 在读大量数据（S 锁）| T2 想 UPDATE 同一行（X 锁） | T2 必须等 T1 读完 |
| T2 在 UPDATE（X 锁）| T1 想 SELECT 同一行（S 锁） | T1 必须等 T2 提交 |
| OLAP 报表扫描百万行 | 在线交易被阻塞 | **读写互斥 = OLTP 和 OLAP 无法共存** |

| 朴素方案 | 它本来想解决什么 | 它留下的致命账 |
|---|---|---|
| 读加 S 锁、写加 X 锁 | 保证一致性读 | 读写互斥，OLAP 查询阻塞 OLTP 事务 |
| 读不加锁，直接读最新值 | 最大化并发 | 脏读（读到未提交的数据） |
| **MVCC**：读不加锁，读"快照版本" | 读写不互斥 + 不脏读 | ✅ 但需要额外的版本存储空间和 GC 机制 |

### What——MVCC 的核心数据结构

MVCC 依赖两个核心数据结构：**隐藏列**和**版本链**。

**隐藏列**（每行记录自带）：

| 隐藏列 | 大小 | 含义 |
|---|---|---|
| `DB_TRX_ID` | 6 bytes | 最近一次修改该行的事务 ID |
| `DB_ROLL_PTR` | 7 bytes | 回滚指针，指向 Undo Log 中该行的上一个版本 |
| `DB_ROW_ID` | 6 bytes | 隐式自增行 ID（仅当表没有主键且无 UNIQUE NOT NULL 列时生成） |

**版本链**（通过 `DB_ROLL_PTR` 串联）：

```
当前行（最新版本）
┌───────────────────────────────┐
│ id=5, name='Carol', age=30    │
│ DB_TRX_ID = 100               │  ← 事务 100 修改了这行
│ DB_ROLL_PTR ──────────────┐   │
└───────────────────────────┼───┘
                            │
                            ▼
Undo Log 中的旧版本
┌───────────────────────────────┐
│ id=5, name='Bob', age=28      │
│ DB_TRX_ID = 80                │  ← 事务 80 修改了这行
│ DB_ROLL_PTR ──────────────┐   │
└───────────────────────────┼───┘
                            │
                            ▼
┌───────────────────────────────┐
│ id=5, name='Alice', age=25    │
│ DB_TRX_ID = 50                │  ← 事务 50 最初创建了这行
│ DB_ROLL_PTR = NULL            │
└───────────────────────────────┘
```

### What（续）——Read View（快照读的灵魂）

**Read View** 是 MVCC 的核心判断逻辑。它在某个时刻"拍一张快照"，记录当前活跃事务的状态。

Read View 包含三个关键字段：

| 字段 | 含义 |
|---|---|
| `m_ids` | 生成 Read View 时，所有**活跃（未提交）事务**的 ID 列表。**注意：`m_ids` 不包含 `creator_trx_id`（创建者自身的事务 ID 不在列表中）** |
| `min_trx_id` | `m_ids` 中的最小值 |
| `max_trx_id` | 生成 Read View 时，InnoDB **即将分配**的下一个事务 ID（= 最大 trx_id + 1） |
| `creator_trx_id` | 创建这个 Read View 的事务 ID |

**可见性判断算法**：

对于版本链中某行的 `DB_TRX_ID = X`，判断该版本是否对当前 Read View 可见：

```text
if X == creator_trx_id:
    可见（自己修改的，当然能看到）

elif X < min_trx_id:
    可见（在 Read View 创建前就已经提交的事务）

elif X >= max_trx_id:
    不可见（在 Read View 创建后才开始的事务）

elif X in m_ids:
    不可见（Read View 创建时该事务还未提交）

else:
    可见（Read View 创建时该事务已提交）
```

### What（续）——RC 与 RR 的根本区别

**RC（Read Committed）**：**每次** SELECT 都生成一个新的 Read View。

**RR（Repeatable Read）**：事务中**第一次** SELECT 生成 Read View，后续所有 SELECT **复用**同一个 Read View。

```
RC 场景：
  T1 BEGIN
  T1 SELECT age FROM users WHERE id = 5 → 生成 ReadView_1，看到 age=25
  T2 BEGIN; UPDATE users SET age=30 WHERE id=5; COMMIT;
  T1 SELECT age FROM users WHERE id=5 → 生成 ReadView_2，看到 age=30 ← 不可重复读！

RR 场景：
  T1 BEGIN
  T1 SELECT age FROM users WHERE id = 5 → 生成 ReadView_1，看到 age=25
  T2 BEGIN; UPDATE users SET age=30 WHERE id=5; COMMIT;
  T1 SELECT age FROM users WHERE id=5 → 复用 ReadView_1，看到 age=25 ← 可重复读 ✅
```

### How——读者 U 执行快照读

```text
① U 所属事务 T（trx_id = 100）执行 SELECT * FROM users WHERE id = 5
② 判断是否需要生成 Read View：
   ├── RC 隔离级别：每次都生成新 Read View
   └── RR 隔离级别：仅首次 SELECT 生成，后续复用
③ 生成 Read View：
   m_ids = [90, 95, 100]     ← 当前活跃事务
   min_trx_id = 90
   max_trx_id = 101           ← 下一个将分配的 trx_id
   creator_trx_id = 100
④ 从 B+ 树定位到 id = 5 的记录，读取 DB_TRX_ID
⑤ 用可见性算法判断：
   ├── DB_TRX_ID = 100 → 等于 creator_trx_id → 可见 ✅
   └── 如果不可见 → 沿 DB_ROLL_PTR 找上一个版本，重复判断
⑥ 返回可见的版本数据
```

**徒弟**：MVCC 只解决普通 SELECT 的读，那 `SELECT ... FOR UPDATE` 呢？

**老陈**：`SELECT ... FOR UPDATE` 是**当前读（current read）**，不走 MVCC。它直接读最新版本并加 X 锁。同样，`UPDATE` / `DELETE` 也是当前读。只有**普通 SELECT（快照读）** 走 MVCC。

| 操作 | 读类型 | 是否走 MVCC |
|---|---|---|
| `SELECT ...`（无 LOCK） | 快照读 | ✅ |
| `SELECT ... LOCK IN SHARE MODE` | 当前读 | ❌，加 S 锁 |
| `SELECT ... FOR UPDATE` | 当前读 | ❌，加 X 锁 |
| `INSERT / UPDATE / DELETE` | 当前读 | ❌，加 X 锁 |

### What（续）——Purge 线程与版本链 GC

Undo Log 中的旧版本不能永远保留。**Purge 线程**负责清理不再被任何 Read View 需要的旧版本：

```text
① Purge 线程定期运行
② 检查当前所有活跃事务的 Read View
③ 找到所有 Read View 中最小的 min_trx_id
④ 版本链中 DB_TRX_ID < min_trx_id 且没有更早活跃事务依赖的版本 → 可以清理
⑤ 释放 Undo Log 空间
```

> 📌 **长事务的危害**：如果一个事务长时间不提交（比如一个忘了 COMMIT 的交互式 session），它的 Read View 会阻止 Purge 线程清理旧版本，导致 Undo Log 膨胀、版本链变长、查询变慢。**生产环境务必监控长事务**（`SELECT * FROM information_schema.innodb_trx` 查看运行超过 N 秒的事务）。

### What（5.7 vs 8.0）——MVCC 的变化

| 特性 | MySQL 5.7 | MySQL 8.0 |
|---|---|---|
| **只读事务优化** | 5.6.4+ 已支持 `START TRANSACTION READ ONLY` 不分配 trx_id（5.7 延续） | 同上，但 8.0 内部 trx 管理进一步细化 |
| **原子 DDL** | DDL 不是原子的（`RENAME TABLE` 中途 crash 可能留下不一致状态） | ✅ Data Dictionary 支持原子 DDL |
| **Undo Log 存储** | Undo Log 在系统表空间或独立 undo tablespace | ✅ 8.0 默认 undo log 存放在独立 tablespace，支持在线 truncate |

> 📌 原子 DDL 是 8.0 的**语义变化**（8.0 引入 Data Dictionary，DDL 操作变为原子性）。Undo Log 独立表空间是代码组织改进。只读事务优化自 5.6.4 起已存在，不构成 5.7 vs 8.0 差异。

### Transfer——可迁移的工程方法论

1. **Copy-on-Write + 引用计数**：MVCC 本质上是 CoW 思想——写时创建新版本，读时选择合适版本。PostgreSQL 的 MVCC、文件系统快照（ZFS/Btrfs）、Git 的 commit 历史都是同一思想。
2. **Read View = 逻辑时钟快照**：用"某一时刻的活跃事务集合"定义"一致性视角"——这对应分布式系统中的 snapshot isolation，Google Spanner 的 TrueTime 也是在做类似的事。
3. **GC 与活跃读的反向依赖**：任何 MVCC 系统都必须解决"旧版本什么时候能删"——PostgreSQL 的 VACUUM、Oracle 的 UNDO retention 都是同一问题的不同解法。

**本层留下的新账**：MVCC 解决了读写互斥，但所有修改最终需要**持久化到磁盘**。如果修改只在内存中，crash 后数据丢失。Redo Log 如何保证 crash-safe？Undo Log 如何支持回滚？Binlog 如何支持复制？→ 逼出 Level 7。

> 🔴 **口诀**：快照读看 Read View，RR 复用 RC 新建。

## Level 7：Redo / Undo / Binlog——日志三剑客

### 👶 前置知识关卡
- [ ] Level 6：MVCC 的版本链存储在 Undo Log 中？
- [ ] Level 4：ACID 中 A（原子性）靠 Undo Log，D（持久性）靠 Redo Log？
- [ ] 你知道 WAL（Write-Ahead Logging）原则吗？

### Why——没有日志系统死在哪

**徒弟**：数据已经在 Buffer Pool 里改好了，后台异步刷回磁盘不就行了？

**老陈**：如果只靠刷盘：

| 朴素方案 | 它本来想解决什么 | 它留下的致命账 |
|---|---|---|
| 每次 commit 直接刷脏页到磁盘 | 持久化 | 随机写（脏页可能分散在 .ibd 文件各处），16KB × N 页，I/O 放大严重 |
| 只靠后台异步刷盘 | 减少 I/O | crash 时脏页未刷盘 → 数据丢失（违反 Durability） |
| 事务执行一半 crash | — | 部分修改已刷盘、部分未刷盘 → 数据不一致（违反 Atomicity） |
| **Redo Log（WAL）** | 顺序写 + crash recovery | ✅ 但只解决引擎层持久性，不解决主从一致性 |
| **Undo Log** | 回滚 + MVCC 版本链 | ✅ |
| **Binlog** | 主从复制 + 时间点恢复 | ✅ 但需要与 Redo Log 协调 → 两阶段提交 |

### What——Redo Log

**Redo Log 是 InnoDB 引擎层**的物理日志，记录"在某个数据页的某个偏移量处，将某段字节从 A 改为 B"。

```
Redo Log 文件结构（环形写入）：

  ib_logfile0         ib_logfile1
┌──────────────┐  ┌──────────────┐
│              │  │              │
│  [已写区域]  │  │  [已写区域]  │
│              │  │              │
│  ← checkpoint│  │              │
│  ← write pos │  │              │
│              │  │              │
│  [可覆写区]  │  │  [可覆写区]  │
│              │  │              │
└──────────────┘  └──────────────┘

  write pos → 当前写入位置（顺时针推进）
  checkpoint → 已刷盘脏页的边界（顺时针推进）
  write pos 和 checkpoint 之间 = 已记录但未确认刷盘的 redo
  checkpoint 和 write pos 之间 = 可覆写的空间
```

| 参数 | 默认值 | 含义 |
|---|---|---|
| `innodb_log_file_size` | 48MB (5.7) / 自动 (8.0.30+) | 每个 redo log 文件大小 |
| `innodb_log_files_in_group` | 2 | redo log 文件个数 |
| `innodb_log_buffer_size` | 16MB | redo log 在内存中的缓冲区 |
| `innodb_flush_log_at_trx_commit` | 1 | **最关键的参数**，见下文 |

**`innodb_flush_log_at_trx_commit` 三档**：

| 值 | 行为 | 安全性 | 性能 |
|---|---|---|---|
| **1**（默认） | 每次 commit 都 `fsync` 到磁盘 | ✅ crash 不丢数据 | 最慢（每次 commit 一次 fsync） |
| **2** | 每次 commit 写到 OS page cache，每秒 fsync | 操作系统 crash 可能丢 ~1s 数据 | 较快 |
| **0** | 每秒写 + fsync | mysqld crash 可能丢 ~1s 数据 | 最快 |

> 📌 **生产环境除非有明确理由，否则保持 `innodb_flush_log_at_trx_commit = 1`**。这是 Durability 的硬保证。

### What（续）——Redo Log 的 WAL 原则

```text
WAL (Write-Ahead Logging) 原则：
  修改数据前，先把修改操作写入 Redo Log
  且 Redo Log 的持久化 必须先于 数据页的持久化

流程：
  ① 在 Buffer Pool 中修改页（产生脏页）
  ② 将修改操作写入 Redo Log Buffer（内存）
  ③ COMMIT 时，将 Redo Log Buffer 刷到磁盘（fsync）
  ④ 脏页的刷盘由后台线程异步进行（可以在 commit 之后很久）

  崩溃恢复：
  ⑤ mysqld 启动时读取 Redo Log
  ⑥ 将 Redo Log 中记录的修改"重放"到数据页
  ⑦ 数据恢复到 crash 前的一致状态
```

**为什么 WAL 能大幅提升写性能？**
- 脏页刷盘 = **随机 I/O**（页分散在 .ibd 文件各处）
- Redo Log 写入 = **顺序 I/O**（追加写入）
- SSD 顺序写 vs 随机写性能差距约 2~5 倍；HDD 差距约 **100~1000 倍**（教学量级）`[须实测]`

### What（续）——Group Commit：把多次 fsync 合并为一次

**徒弟**：`innodb_flush_log_at_trx_commit = 1` 意味着每次 commit 都要 fsync 一次 Redo Log。如果每秒有 10000 次 commit，岂不是要 10000 次 fsync？SSD 的 fsync 延迟约 100μs，10000 次 fsync 需要 1 秒——TPS 不是被 fsync 限制到 10000 以下吗？

**老陈**：实际上不会这么差。InnoDB 有一个关键优化叫 **Group Commit（组提交）**：

```text
Group Commit 机制：

  多个事务同时 COMMIT 时，InnoDB 将它们的 Redo Log 刷盘合并为一次 fsync。

  ① 事务们排队等待 commit（进入 log writer 的等待队列）
  ② 第一个到达的事务成为 "leader"
  ③ leader 收集等待队列中所有事务的 redo log
  ④ 一次 fsync 写入所有收集到的 redo log
  ⑤ 依次唤醒所有事务，返回 OK

  效果：
  10000 个并发事务 → 可能被合并为几十次 fsync（而不是 10000 次）
  → 高并发下 TPS 远超 "1/fsync_latency" 的理论上限
```

| 并发度 | 无 Group Commit | 有 Group Commit |
|---|---|---|
| 1 事务/秒 | 1 次 fsync/秒 | 1 次 fsync/秒（无合并） |
| 1000 事务/秒 | 1000 次 fsync/秒 → 需要 SSD 支持 | 合并为 ~50-100 次 fsync/秒 → 轻松应对 |
| 10000 事务/秒 | 10000 次 fsync/秒 → 可能阻塞 | 合并为 ~200-500 次 fsync/秒 → 性能优秀 |

> 📌 **这就是为什么"双 1 配置"（`innodb_flush_log_at_trx_commit = 1` + `sync_binlog = 1`）在高并发下仍有不错性能的核心原因之一**：Group Commit 把多次 fsync 的系统调用开销摊薄了。在低并发场景下（每秒只有几个事务），Group Commit 无法合并，每次 commit 仍然需要独立 fsync——这时候"双 1 配置"的性能开销会更明显。`[须实测]`

### What（续）——Doublewrite Buffer：防止"部分页写入"损坏数据

**Redo Log 解决的是"逻辑上写到哪了"的问题，但还有一个更底层的物理问题它解决不了。**

**徒弟**：Redo Log 已经保证 crash 后能恢复了，还需要什么？

**老陈**：考虑一个更隐蔽的崩溃场景——**部分页写入（Partial Page Write）**：

```text
InnoDB 的页大小 = 16KB
操作系统的原子写入单元 = 4KB（通常是 OS page size）

当 InnoDB 将一个 16KB 的脏页刷盘时，OS 实际上分 4 次写入（每次 4KB）。
如果在写入第 2 个 4KB 时发生了 crash：

  ┌──────────────────────────────────────────┐
  │  16KB Page in .ibd file                  │
  │                                          │
  │  [4KB #1] ✅ 新数据（已写入）             │
  │  [4KB #2] 💥 写入中断（部分新、部分旧）    │
  │  [4KB #3] ❌ 旧数据（未写入）             │
  │  [4KB #4] ❌ 旧数据（未写入）             │
  │                                          │
  │  结果：这个页变成了一个"半新半旧"的怪物     │
  │  → checksum 校验失败                     │
  │  → Redo Log 无法修复（因为 Redo 记录的是   │
  │    "在页内某偏移量改了什么字节"，           │
  │    但页本身的物理结构已经损坏了）           │
  └──────────────────────────────────────────┘

  这种损坏叫做 "torn page"（撕裂页），是 Redo Log 无法修复的。
```

**Doublewrite Buffer 的解决方案**：

```text
在将脏页写入 .ibd 文件之前，先完整地写入一个"双写缓冲区"：

  ① 脏页（16KB）→ 顺序写入 Doublewrite Buffer（磁盘上的连续区域）
     → 这是顺序写，即使 crash 也能保证 16KB 完整写入
  ② 脏页（16KB）→ 写入 .ibd 文件的目标位置（随机写）
     → 如果此时 crash 导致 torn page：
  ③ 崩溃恢复时：
     → 先检查 .ibd 中页的 checksum
     → 如果校验失败 → 从 Doublewrite Buffer 中读取完整副本
     → 用完整副本覆盖损坏的页
     → 然后再应用 Redo Log
```

| 机制 | 解决什么问题 | 协作关系 |
|---|---|---|
| **Doublewrite Buffer** | 物理页的完整性（防止 torn page） | 先保证"页本身是完整的" |
| **Redo Log** | 逻辑修改的持久性（crash 后知道改了什么） | 然后在完整的页上应用修改 |

> 📌 **Doublewrite Buffer 的开销**：每个脏页写两次（一次到 Doublewrite，一次到 .ibd），写放大约 2x。但由于 Doublewrite 是顺序写，实际开销远小于 2x 随机写。参数 `innodb_doublewrite = ON/OFF`（默认 ON，**生产环境不要关闭**）。8.0 改进了 Doublewrite 实现，减少了锁竞争。

### What（续）——Change Buffer：二级索引的写入合并优化

**徒弟**：Level 3 讲了聚簇索引和二级索引。修改二级索引也需要 B+ 树操作，如果二级索引的页不在 Buffer Pool 中，每次都要从磁盘读进来改一下再写回去？

**老陈**：这正是 **Change Buffer**（也叫 Insert Buffer）要解决的问题。

```text
问题场景：
  UPDATE users SET status = 'inactive' WHERE id = 1001;
  → 聚簇索引：定位到 id=1001 的页（大概率在 Buffer Pool 中）
  → 二级索引 idx_status：需要修改 status 列对应的 B+ 树
     → 但 idx_status 的目标页可能不在 Buffer Pool 中
     → 每次都从磁盘读入、修改、写回 → 大量随机 I/O

Change Buffer 的解决方案：
  ① 如果二级索引的目标页不在 Buffer Pool 中：
     → 不立即从磁盘读入
     → 将修改操作记录到 Change Buffer 中（Change Buffer 在 Buffer Pool 内）
  ② 后续某个时刻（后台线程或下次访问该页时）：
     → 将目标页从磁盘读入 Buffer Pool
     → 将 Change Buffer 中积累的修改一次性合并（merge）到该页
     → 多次随机写被合并为一次随机读 + 一次顺序写

适用条件：
  ✅ 二级索引（非聚簇索引）
  ✅ 非唯一索引（唯一索引需要立即检查唯一性，不能延迟）
  ✅ 目标页不在 Buffer Pool 中
```

| 参数 | 默认值 | 含义 |
|---|---|---|
| `innodb_change_buffering` | `all` | 缓冲哪些操作：`all` / `inserts` / `deletes` / `changes` / `purges` / `none` |
| `innodb_change_buffer_max_size` | `25` | Change Buffer 最大占 Buffer Pool 的比例（%） |

> 📌 **Change Buffer 是 InnoDB 内部实现细节**，合并时机、淘汰策略等随版本可能变化。用户通常不需要调参，除非有极端的写入模式。

### What（续）——Undo Log

Undo Log 是**逻辑日志**，记录与修改操作相反的"逆操作"：

| 原始操作 | Undo Log 记录 |
|---|---|
| `INSERT INTO t VALUES (1, 'a')` | "DELETE WHERE id = 1" |
| `DELETE FROM t WHERE id = 5` | "INSERT INTO t VALUES (5, ...)" |
| `UPDATE t SET name = 'b' WHERE id = 3` | "UPDATE t SET name = 'old_name' WHERE id = 3" |

**Undo Log 的两个作用**：

1. **事务回滚**：ROLLBACK 时，按 Undo Log 逆序执行逆操作
2. **MVCC 版本链**：旧版本数据存储在 Undo Log 中，通过 `DB_ROLL_PTR` 串联

**Undo Log 的类型**：

| 类型 | 何时可清理 |
|---|---|
| **Insert Undo Log** | 事务提交后即可清理（INSERT 不会产生其他事务需要看到的旧版本——因为插入前这行不存在） |
| **Update/Delete Undo Log** | 需要等到所有可能引用该版本的 Read View 都不再活跃时才能清理（Purge 线程负责） |

### What（续）——Binlog

Binlog 是 **MySQL Server 层**的逻辑日志（与存储引擎无关），记录所有修改数据的 SQL 或行变更。

**三种格式**：

| 格式 | 记录内容 | 优点 | 缺点 |
|---|---|---|---|
| **STATEMENT** | 原始 SQL 语句 | 日志量小 | 某些函数（`NOW()`, `UUID()`）导致主从不一致 |
| **ROW** | 行级变更（before/after image） | 精确、一致性最好 | 日志量大（批量 UPDATE 每行都记录） |
| **MIXED** | 自动选择 STATEMENT 或 ROW | 折中 | 仍有可能不一致 |

> 📌 **生产环境推荐 `binlog_format = ROW`**。5.7.7+ 默认 ROW。

### What（续）——两阶段提交（Redo Log + Binlog 协调）

**为什么需要两阶段提交？** 因为 Redo Log（InnoDB 层）和 Binlog（Server 层）是两个独立的日志系统。如果不协调，crash 可能导致：

```
场景 1：先写 Redo Log，再写 Binlog
  → Redo Log 写完，Binlog 写之前 crash
  → 恢复后主库有这条数据，但从库重放 Binlog 缺少这条 → 主从不一致

场景 2：先写 Binlog，再写 Redo Log
  → Binlog 写完，Redo Log 写之前 crash
  → 恢复后主库没有这条数据（Redo Log 缺失），但从库重放了 → 主从不一致
```

**两阶段提交的流程**：

```text
阶段 1（Prepare）：
  ① InnoDB 将事务的所有修改写入 Redo Log 并持久化
  ② 在 InnoDB 内部将事务标记为 TRX_STATE_PREPARED
     → 此时事务已"半持久化"：crash 后可以从 Redo Log 恢复
     → 注意：不是"写一个 prepare 标记位"，而是事务的内部状态机切换到 PREPARED 状态

阶段 2（Commit）：
  ③ MySQL Server 将 Binlog 写入磁盘并 fsync
  ④ Binlog 写入成功后，InnoDB 将事务标记为 TRX_STATE_COMMITTED
  ⑤ 释放锁、返回客户端 OK

崩溃恢复时：
  ├── Redo Log 中事务状态为 COMMITTED → 提交（前滚）
  ├── Redo Log 中事务状态为 PREPARED + Binlog 完整 → 提交
  │   → 关键：PREPARED + Binlog 完整 = 事务可以被提交
  │     因为 Binlog 一旦写入，从库/备份就依赖它了
  └── Redo Log 中事务状态为 PREPARED + Binlog 不完整 → 回滚事务
```

```
时间线：
  T ──────────────────────────────────────────────→

  InnoDB:  [redo write] [redo prepare] ────── [redo commit]
  Server:                    [binlog write + fsync]
                              ↑
                          线性化点：binlog fsync 成功后，事务才算"可提交"
```

### What（续）——两阶段提交 vs Semi-Sync 复制：两个不同层次的"一致性"

**两阶段提交解决的是单机 crash-safe，但还有一个问题它解决不了：主库宕机时，从库有没有收到数据？**

| 机制 | 解决什么问题 | 保证的层次 |
|---|---|---|
| **两阶段提交**（Redo + Binlog 协调） | 单机 crash 后，InnoDB 数据与 Binlog 一致 | 单机内部一致性 |
| **Semi-Sync 复制**（`rpl_semi_sync_master_enabled`） | 主库 commit 返回时，至少一个从库已收到 Binlog | 主从之间的一致性 |

```text
异步复制（默认）的数据丢失窗口：

  主库 commit → 返回客户端 OK → Binlog 异步发送给从库
                                    ↑
                              如果此时主库宕机，
                              从库还没收到 Binlog
                              → 主从切换后数据丢失

Semi-Sync 复制的改进：

  主库 commit → 等待至少一个从库确认收到 Binlog → 返回客户端 OK
               ↑
          多了这一步等待，消除了数据丢失窗口
          代价：commit 延迟增加（多一次网络 RTT，通常 ~0.5~2ms）
```

> 📌 **生产环境建议**：金融/支付类系统开启 semi-sync（`rpl_semi_sync_master_enabled = ON`）；日志类系统可以保持异步复制以换取更低延迟。semi-sync 在超时后会降级为异步复制（`rpl_semi_sync_master_timeout`），这是一个 safety valve。

### How——读者 U 的日志写入全流程

```text
① U: UPDATE users SET name = 'NewName' WHERE id = 1001
② 在 Buffer Pool 中修改数据页（产生脏页）
③ 将修改的逆操作写入 Undo Log（用于回滚 + MVCC）
④ 将修改操作写入 Redo Log Buffer
⑤ COMMIT：
   ⑤a Redo Log Buffer → Redo Log 文件（prepare 状态）
   ⑤b Binlog Buffer → Binlog 文件 + fsync
   ⑤c Redo Log 标记 commit
⑥ 后台线程异步将脏页刷回磁盘（可能在几秒甚至几分钟后）
⑦ Purge 线程在合适时机清理不再需要的 Undo Log 版本
```

### What（5.7 vs 8.0）——日志体系的变化

| 特性 | MySQL 5.7 | MySQL 8.0 |
|---|---|---|
| **Redo Log 大小** | 需手动设置 `innodb_log_file_size`，修改需停机 | ✅ 8.0.30+ 支持 `innodb_redo_log_capacity`，动态调整 |
| **Binlog 压缩** | 不支持 | ✅ 8.0.20+ 支持 `binlog_transaction_compression`（ZSTD 压缩） |
| **Binlog 过期** | `expire_logs_days` | `binlog_expire_logs_seconds`（秒级精度） |
| **GTID** | 可选开启 | 推荐开启，8.0 默认行为更稳定 |

> 📌 Redo Log 动态调整是 8.0.30 的**重要运维改进**——5.7 修改 redo log 大小需要停机。

### Transfer——可迁移的工程方法论

1. **WAL 是通用模式**：Kafka 的 segment log、PostgreSQL 的 WAL、RocksDB 的 WAL 都是同一思想——先顺序写日志，再异步持久化数据。
2. **两阶段提交**：任何需要协调两个独立持久化系统的场景（数据库 + 消息队列、本地事务 + 远程调用）都需要类似机制——XA 事务、Saga 模式都是这个问题的不同解法。
3. **顺序写替代随机写**：LSM-Tree（RocksDB、Cassandra）将这个思想推向极致——所有写操作都是顺序追加。

**本层留下的新账**：所有组件都已就位。现在让我们把 Level 1~7 串起来，看一条 UPDATE 从客户端发出到 commit 返回的**完整旅程**。→ 逼出 Level 8。

> 🔴 **口诀**：WAL 先写日志，两阶段提交保一致。

## Level 8：全链路穿透——一条 UPDATE 的完整旅程

### 👶 前置知识关卡
- [ ] Level 1~7 的所有核心概念？
- [ ] 你能说出 Buffer Pool / B+ Tree / Lock / MVCC / Redo Log 各自解决什么问题？

### Why——为什么需要全链路视角

**徒弟**：前面 7 层我都理解了，但面对线上问题，怎么把这些知识串起来？

**老陈**：理解单个组件只是第一步。线上排障、性能调优、架构评审，都需要你脑中有一条**完整的时间线**，能在任何一步停下来分析。

### What——一条 UPDATE 的 12 步全链路

```text
U: UPDATE users SET name = 'NewName' WHERE id = 1001

═══════════════ MySQL Server 层 ═══════════════

① 连接器验证权限
   └─ 客户端通过 TCP 连接发送 SQL → Server 验证用户权限

② 解析器（Parser）生成解析树
   └─ 词法分析 → 语法分析 → 生成抽象语法树（AST）

③ 预处理器（Preprocessor）
   └─ 检查表/列是否存在、展开 SELECT *、权限再验证

④ 优化器（Optimizer）生成执行计划
   └─ 选择使用哪个索引、JOIN 顺序、是否使用覆盖索引等
   └─ 📌 可通过 EXPLAIN 查看执行计划

═══════════════ InnoDB 存储引擎层 ═══════════════

⑤ 开启/加入事务
   └─ 分配 trx_id、初始化事务上下文

⑥ B+ 树定位目标页 [Level 3]
   └─ Root → Non-Leaf → Leaf，找到 id = 1001 所在的页
   └─ 如果页不在 Buffer Pool 中 [Level 2]：
      └─ 从磁盘读入 Buffer Pool（Old 区）

⑦ 加锁 [Level 5]
   └─ 对表加 IX 锁
   └─ 对 id = 1001 加 X Record Lock（唯一索引等值）
   └─ 如果被其他事务持锁 → 进入锁等待队列

⑧ 读取当前行（当前读）
   └─ 读取最新已提交版本（非快照读，不走 MVCC）

⑨ 写 Undo Log [Level 7]
   └─ 记录逆操作："UPDATE users SET name = 'OldName' WHERE id = 1001"
   └─ 在版本链中创建新版本节点 [Level 6]

⑩ 修改 Buffer Pool 中的数据页
   └─ 将 name 字段从 'OldName' 改为 'NewName'
   └─ 页变为脏页，加入 Flush List

⑪ 写 Redo Log [Level 7]
   └─ 将物理修改写入 Redo Log Buffer
   └─ Redo Log Buffer → Redo Log 文件（prepare 状态）

═══════════════ 提交流程 ═══════════════

⑫ 两阶段提交 [Level 7]
   └─ ⑫a Redo Log prepare
   └─ ⑫b Binlog write + fsync
   └─ ⑫c Redo Log commit
   └─ 释放所有锁
   └─ 返回客户端 OK
```

```
完整时间线图：

  Client          Server          InnoDB           Disk
    │               │               │               │
    │─── SQL ──────→│               │               │
    │               │── parse ─────→│               │
    │               │── optimize ──→│               │
    │               │               │               │
    │               │               │─ B+tree ─────→│ (if page not in BP)
    │               │               │← page data ──│
    │               │               │               │
    │               │               │─ lock(X) ────→│ (lock subsystem)
    │               │               │─ undo write ─→│ (undo log)
    │               │               │─ modify BP ──→│ (in memory)
    │               │               │─ redo write ─→│ (redo log, prepare)
    │               │               │─ binlog ─────→│ (binlog + fsync)
    │               │               │─ redo commit ─→│ (redo log, commit)
    │               │               │─ unlock ─────→│
    │               │               │               │
    │←── OK ────────│←──────────────│               │
    │               │               │               │
    │               │               │  [后台异步]    │
    │               │               │─ flush dirty ─→│ (.ibd file)
    │               │               │─ purge undo ──→│ (cleanup)
```

### What（续）——崩溃恢复（Crash Recovery）

```text
mysqld 重启后的恢复流程：

① 读取 Redo Log，找到最后一个 checkpoint
② 从 checkpoint 开始重放（replay）Redo Log 中的修改
   → 恢复数据页到 crash 前的状态
③ 扫描 Redo Log 中的事务状态：
   ├── prepare + binlog 完整 → 提交事务（前滚）
   ├── commit → 已完成，跳过
   └── prepare + binlog 不完整 → 回滚事务（通过 Undo Log 回滚）
④ 数据恢复到 crash 前的一致状态
⑤ 开始接受新的连接
```

### What（续）——生产环境中的关键监控指标

| 指标 | 来源 | 含义 | 阈值参考 |
|---|---|---|---|
| `Innodb_buffer_pool_read_requests` | `SHOW STATUS` | 逻辑读（从 BP 读取） | — |
| `Innodb_buffer_pool_reads` | `SHOW STATUS` | 物理读（从磁盘读取） | — |
| **Buffer Pool 命中率** | 1 - (物理读/逻辑读) | 越高越好 | > 99% 为健康 |
| `Innodb_row_lock_waits` | `SHOW STATUS` | 行锁等待次数 | 持续增长需关注 |
| `Innodb_row_lock_time_avg` | `SHOW STATUS` | 平均行锁等待时间（ms） | < 50ms 为健康 |
| `Innodb_log_waits` | `SHOW STATUS` | Redo Log Buffer 不够导致的等待 | 应为 0 |
| 长事务 | `information_schema.innodb_trx` | 运行超过 N 秒的事务 | > 60s 需告警 |
| 主从延迟 | `SHOW SLAVE STATUS` | `Seconds_Behind_Master` | < 1s 为健康 |

> 📌 以上阈值为教学参考，不同业务场景差异巨大。`[须实测]`

### Transfer——可迁移的工程方法论

1. **全链路追踪思维**：不仅适用于数据库，任何复杂系统（分布式微服务、浏览器渲染管线、编译器）排障时都需要一条完整的时间线。
2. **同步路径 vs 异步路径分离**：commit 返回前的同步路径（锁 + redo + binlog）和 commit 后的异步路径（刷脏页 + purge）分离——这是高性能系统的通用模式。
3. **崩溃恢复的幂等性**：Redo Log 重放是幂等的——同样的日志重放多次结果不变。这是所有 WAL 系统的核心性质。

## Level 9：一线大厂 SQL 调优实战

### 👶 前置知识关卡
- [ ] Level 3：B+ 树扇出、聚簇索引 vs 二级索引、回表？
- [ ] Level 5：Next-Key Lock、加锁规则？
- [ ] 你会看 `EXPLAIN` 的 `type` 列，但知道 `rows` 和 `filtered` 怎么配合估算真实扫描代价吗？

### Why——为什么"建了索引"不等于"调优做完了"

**徒弟**：该建的索引都建了，`EXPLAIN` 里 `type` 也不是 `ALL` 了，还要调什么？

**老陈**：索引解决的是"能不能走捷径"，调优解决的是"走的捷径是不是最优路径、代价是否可控"。三个常见误区：

| 误区 | 真相 |
|---|---|
| "type 不是 ALL 就没问题" | `type=index`（全索引扫描）比 `range` 慢得多，扫的是整棵索引树而非区间 |
| "有索引就一定会用" | 优化器基于代价模型（cost model）选执行计划，索引选择性差、统计信息过期都会导致弃用索引 |
| "EXPLAIN 里 rows 小就是快" | `rows` 是估算值，`filtered` 才是"过滤后剩余比例"，两者相乘才是真实扫描代价的近似值 |

### 9.1 EXPLAIN 深度解读——大厂面试和线上排障的共同基础

```sql
EXPLAIN SELECT * FROM orders WHERE user_id = 1001 AND status = 'paid' ORDER BY created_at DESC LIMIT 10;
```

| 字段 | 含义 | 大厂关注点 |
|---|---|---|
| `type` | 访问类型 | 优先级：`system > const > eq_ref > ref > range > index > ALL`。生产 SQL 底线是 `range` 以上，`index` 和 `ALL` 都要警惕 |
| `key` | 实际使用的索引 | 和你预期的索引不一致时，是排查第一步 |
| `key_len` | 使用的索引字节数 | 判断联合索引用到了几列——比预期短说明后面的列没生效（见坑 15） |
| `rows` | 预计扫描行数 | 优化器估算值，依赖统计信息（`ANALYZE TABLE` 更新） |
| `filtered` | 该步骤过滤后剩余行占比（%） | `rows × filtered / 100` ≈ 真实需要处理的行数，这是被低估最严重的字段 |
| `Extra` | 额外信息 | `Using filesort` / `Using temporary` / `Using index`（覆盖索引）/ `Using index condition`（ICP）是四个高频信号 |

**徒弟**：`Using where` 和 `Using index condition` 有什么区别？

**老陈**：这是索引下推（ICP, Index Condition Pushdown, 5.6+ 默认开启）的核心问题。

```text
索引：(status, amount)
SQL:  WHERE status = 'paid' AND amount > 100

没有 ICP（老行为）：
  ① 用 status = 'paid' 定位到索引记录
  ② 回表取出完整行
  ③ 在 Server 层判断 amount > 100
  → 即使 amount 不满足，也要先回表

有 ICP：
  ① 用 status = 'paid' 定位到索引记录
  ② 【在存储引擎层就地判断 amount > 100】（amount 虽然在索引里，
     但因为是范围条件无法用于定位起始点，ICP 能让 InnoDB 在遍历
     索引项时就地过滤，不满足的直接跳过、不触发回表）
  ③ 只有通过的才回表取完整行

→ 省了大量随机 I/O
→ EXPLAIN 里 Extra = Using index condition 就是命中了这个优化
```

> 📌 **ICP 的适用条件**：只对**索引里包含、但不是等值查询前缀**的列有效。ICP 能减少回表次数，但不能替代索引定位——这就是为什么坑 15（联合索引范围查询导致后面的列失效）中，即使有 ICP，c 列仍然无法用于索引定位。

### 9.2 JOIN 优化——大厂高频考点

**徒弟**：JOIN 两张表，数据库内部是怎么跑的？

**老陈**：先看三种算法的代价差异：

| 算法 | 原理 | 代价 |
|---|---|---|
| **NLJ**（Nested Loop Join） | 驱动表逐行，每行去被驱动表按索引查 | 有索引时代价可控：`驱动表行数 × 索引查找代价` |
| **BNL**（Block Nested Loop Join） | 被驱动表没有可用索引时，把驱动表整块放入 `join_buffer`，被驱动表全表扫一次做批量比较 | `驱动表行数 × 被驱动表行数`（退化情况），5.7 无索引 JOIN 的默认兜底方案 |
| **Hash Join**（8.0.18+） | 对小表建哈希表，大表探测 | 等值 JOIN 无索引时通常远快于 BNL，8.0 优化器在无索引等值 JOIN 时会自动选用 |

> 📌 **最容易踩的坑**：5.7 环境下如果 JOIN 的关联字段没有索引，会退化成 BNL，`Extra` 里出现 `Using join buffer (Block Nested Loop)`，这是全表 × 全表的笛卡尔比较，大表 JOIN 时是灾难性的。8.0.18+ 会自动尝试 Hash Join 顶替 BNL，但**最优解永远是关联字段建索引**，让 JOIN 走 NLJ。

**驱动表选择**：

**老陈**：优化器一般会选**过滤后结果集更小的表作为驱动表**，但复杂 SQL 有时候会选错。判断方法：`EXPLAIN` 结果里第一行就是驱动表，如果发现驱动表选反了（应该小表驱动大表，却反过来了），可以用 `STRAIGHT_JOIN` 强制指定 JOIN 顺序——但这是最后手段，先检查索引和统计信息是否正常。

### 9.3 批量操作优化——大厂写入吞吐的常规手段

**徒弟**：INSERT 1 万行数据，循环单条插入和批量插入差多少？

**老陈**：差一个数量级以上。原因是每条 INSERT 都要走一次网络往返（RTT）+ 一次（或多次，取决于 `sync_binlog` / `flush_log_at_trx_commit`）fsync。

```sql
-- ❌ 循环单条插入：1 万次网络往返 + 1 万次事务提交开销
for i in range(10000):
    INSERT INTO t VALUES (...);

-- ✅ 多值 INSERT：1 次网络往返，1 次事务提交
INSERT INTO t VALUES (...), (...), (...), ... ;  -- 建议每批 500~1000 行

-- ✅ 显式事务包裹批量提交：减少 fsync 次数
BEGIN;
INSERT INTO t VALUES (...);
INSERT INTO t VALUES (...);
-- ... 500~1000 条
COMMIT;
```

| 参数 | 作用 |
|---|---|
| `bulk_insert_buffer_size` | MyISAM 专用，InnoDB 不受此参数影响 |
| `max_allowed_packet` | 多值 INSERT 的单包大小上限，批量太大会报 `Packet too large` |
| `innodb_autoinc_lock_mode` | 批量 INSERT 在自增锁上的行为（见坑 3），mode=2 并发最好但主从复制需要 ROW 格式 |

> 📌 **大厂经验值**：单批 500~1000 行是常见折中——太小达不到批量收益，太大会导致单个事务过长、Undo Log 膨胀、锁持有时间变长，反而影响并发写入的其他事务。

### 9.4 大表无锁变更——大厂 DDL 治理的标配

**徒弟**：线上一张亿级大表要加个字段，直接 `ALTER TABLE ADD COLUMN` 会怎样？

**老陈**：8.0 的 Online DDL 对"加字段"这类操作（如果不涉及重建聚簇索引）支持在线执行，不完全锁表，但仍然会短暂持有 MDL 写锁（申请阶段和提交阶段各有一次），如果这两个时间点恰好有长事务占着 MDL 读锁，DDL 会排队等，期间新来的读写请求全部排在 DDL 后面（参见坑 14 的 MDL 雪崩）。

大厂对亿级大表变更的标准做法是用**在线 DDL 工具**（gh-ost / pt-online-schema-change），原理都是同一套思路：

```text
① 创建一张和原表结构相同（加上新变更）的影子表 _t_new
② 在影子表上应用 DDL（比如加字段）——因为是空表，这一步瞬间完成
③ 通过触发器（pt-osc）或 binlog 订阅（gh-ost）持续把原表的增量变更同步到影子表
④ 分批把原表存量数据拷贝到影子表（带限速，避免打满 I/O 和主从延迟）
⑤ 存量数据追平后，做一次原子 RENAME 切换表名
   → RENAME 是元数据操作，代价极小，锁表时间在毫秒级
```

| 工具 | 增量同步方式 | 特点 |
|---|---|---|
| **pt-online-schema-change** | 触发器（INSERT/UPDATE/DELETE 触发器同步变更） | 成熟稳定，对主库有一定触发器开销 |
| **gh-ost** | 订阅 binlog（伪装成从库） | 不用触发器，对主库侵入更小，支持暂停/限速，大厂更主流 |

**Online DDL 原生能力速查表**：

> 一线大厂的 DDL 治理原则：**能用原生 Online DDL 就用（轻量），需要重建表的才用 gh-ost**。
> 
> ⚠️ **重要区分**：`ALGORITHM=INPLACE`（允许并发 DML，仅在开始/结束时短暂持 MDL 写锁）vs `ALGORITHM=COPY`（完全锁表，不允许并发写入）。"需要重建表"的操作（如加主键、OPTIMIZE）在 5.6+ 默认走 INPLACE，**重建过程中仍然允许并发 DML**，只有在操作开始和结束时各需要短暂持有一次 MDL 写锁（参见坑 14 的 MDL 雪崩）。

| DDL 操作 | 5.7 是否 Online | 8.0 是否 Online | 是否需要 gh-ost |
|---|---|---|---|
| `ADD COLUMN`（非自增列） | ✅ `ALGORITHM=INPLACE` | ✅ `ALGORITHM=INSTANT`（8.0.12+，秒级完成） | ❌ 一般不需要 |
| `ADD COLUMN`（自增列） | ❌ 需要重建表 | ❌ 仍需重建 | ✅ 推荐 |
| `DROP COLUMN` | ✅ `ALGORITHM=INPLACE` | ✅ `ALGORITHM=INSTANT`（8.0.29+） | ❌ |
| `RENAME COLUMN` | ✅ | ✅（更高效） | ❌ |
| `ADD INDEX` / `DROP INDEX` | ✅ `ALGORITHM=INPLACE` | ✅ | ❌ |
| `ADD PRIMARY KEY` | ✅ `ALGORITHM=INPLACE`（允许并发 DML） | ✅ | ❌ 一般不需要 |
| `OPTIMIZE TABLE` | ✅ `ALGORITHM=INPLACE`（允许并发 DML） | ✅ | ❌ 一般不需要 |
| `MODIFY COLUMN`（扩大 VARCHAR） | ✅（满足条件时） | ✅ | ❌ |
| `MODIFY COLUMN`（改数据类型） | ⚠️ 部分类型转换需 `ALGORITHM=COPY`（完全锁表） | ⚠️ 同左，视具体类型而定 | ⚠️ 视情况，小表可直接 ALTER，大表用 gh-ost |

> 📌 **INSTANT DDL（8.0.12+ / 8.0.29+）**：`ALGORITHM=INSTANT` 分为两个阶段引入——8.0.12 仅支持**在表末尾追加列**；8.0.29 扩展到**DROP COLUMN、任意位置 ADD COLUMN、列重排**等更多操作（靠的是更通用的行版本化机制）。这是 8.0 相比 5.7 的重大改进，很多原本需要 gh-ost 的场景现在可以直接用原生 DDL。

> 📌 **核心判断逻辑**：
> 1. 如果 DDL 走 `ALGORITHM=COPY`（如某些数据类型转换），重建过程中**完全锁表**，大表必须用 gh-ost/pt-osc。
> 2. 如果 DDL 走 `ALGORITHM=INPLACE`（如加索引、加主键、OPTIMIZE），重建过程中**允许并发 DML**，仅在开始/结束时短暂持 MDL 写锁。大多数场景可直接用原生 DDL，除非表非常大且对 MDL 锁等待敏感。
> 3. 如果 DDL 走 `ALGORITHM=INSTANT`（8.0.12+），纯元数据操作，秒级完成，无需 gh-ost。
> 
> 可以在执行前加 `LOCK=NONE` 验证是否支持 Online：`ALTER TABLE t ADD INDEX idx(col), LOCK=NONE;`

> 📌 这两个工具解决的核心问题就是把"一次性大 DDL 锁表"转化成"持续小增量同步 + 一次原子 RENAME"，本质上是把大事务拆成无数小事务，和坑 7（大事务导致主从延迟）是同一个治理思路的应用。

### 9.5 SQL 审核与慢查询治理体系——组织层面的"调优"

**徒弟**：前面讲的都是单条 SQL 怎么优化，大厂怎么保证成百上千个开发写的 SQL 都不出问题？

**老陈**：靠的不是"每个人都精通调优"，而是**流程和工具兜底**：

```text
上线前：SQL 审核（SQL Review）
  ├─ 强制走索引扫描，禁止全表扫描的 DML 上线（通过 EXPLAIN 自动检测 type=ALL）
  ├─ 禁止无 WHERE 条件的 UPDATE/DELETE
  ├─ 禁止 SELECT *（存在版本兼容和覆盖索引失效风险）
  ├─ 大表 DDL 强制走 gh-ost/pt-osc，不允许直接 ALTER
  └─ 常见工具：字节的 Bytebase、阿里的 SQLAdvisor/DMS、美团的 SQLAdvisor 等 SQL 审核平台

上线中：变更审批 + 影响面评估
  ├─ 预估执行时间、锁表时间、影响行数
  └─ 大表变更走灰度/低峰期窗口

上线后：慢查询自动化治理
  ├─ 慢查询日志（slow_query_log）+ pt-query-digest 定期聚合分析（TOP N 慢 SQL、按指纹归类）
  ├─ 慢查询自动告警 + 自动生成 EXPLAIN 报告推送给 SQL 责任人
  └─ 大表定期健康巡检（碎片率、索引使用率、僵尸索引识别）
```

**僵尸索引（从未被使用的索引）识别**是很多人忽略的一环——索引不是只有"缺索引"的问题，还有"建了但没人用，白白拖慢写入"的问题：

```sql
-- 8.0：通过 performance_schema 查从未被使用的索引
SELECT object_schema, object_name, index_name
FROM performance_schema.table_io_waits_summary_by_index_usage
WHERE index_name IS NOT NULL AND count_star = 0
  AND object_schema NOT IN ('mysql', 'performance_schema', 'sys');
```

发现僵尸索引后，大厂标准流程是先用 8.0 的 `INVISIBLE` 索引观察一段时间（确认没有隐藏依赖，比如某些低频报表任务），确认无风险后再物理删除。

> 🔴 **口诀**：EXPLAIN 看 filtered，JOIN 建索引走 NLJ；批量提交减 fsync，大表变更 gh-ost；审核治理靠流程，僵尸索引定期清。

<a id="pitfalls"></a>
## ⚠️ 坑与细节（18 个）

### 坑 1：`WHERE` 无索引导致锁全表

```sql
-- ❌ 错误代码
UPDATE orders SET status = 'shipped' WHERE customer_name = 'Alice';
-- customer_name 没有索引
```

| 项目 | 内容 |
|---|---|
| **错因** | InnoDB 全表扫描，对每一行加 Next-Key Lock |
| **比喻里的后果** | 读者 U 找不到目标书，把整个图书馆每本书都贴了便签，其他人什么都不能动 |
| **线上现象** | 其他事务的 INSERT/UPDATE 全部阻塞；`SHOW ENGINE INNODB STATUS` 看到大量行锁；`Innodb_row_lock_waits` 飙升 |
| **修正** | 给 `customer_name` 加索引；或改为先查出 id 再按 id 更新 |

### 坑 2：RR 下仍然可能出现幻读（特定边界场景）

```sql
-- T1:
BEGIN;
SELECT * FROM t WHERE id > 5 LIMIT 3 FOR UPDATE;  -- 返回 3 行，只对这 3 行加 Next-Key Lock

-- T2:
BEGIN;
INSERT INTO t VALUES (10, ...);  -- ✅ 可以插入成功！因为 T1 的锁只覆盖了扫描到的 3 行
COMMIT;

-- T1:
SELECT * FROM t WHERE id > 5 LIMIT 3 FOR UPDATE;  -- 返回 4 行！幻读！
-- 原因：LIMIT 提前终止扫描，(last_matched_id, +∞) 的间隙未锁定
```

| 项目 | 内容 |
|---|---|
| **错因** | LIMIT 提前终止范围扫描，InnoDB 只对实际扫描到的记录加 Next-Key Lock，尾部间隙未锁定。其他事务可以在未锁定的间隙中插入新行，导致后续查询看到新行（幻读） |
| **比喻里的后果** | 便签系统只贴在扫描到的书上，没扫描到的书的间隙没贴便签，别人可以从缝隙里塞新书进来 |
| **线上现象** | 同事务内两次 `SELECT ... FOR UPDATE` 返回行数不同；常见于带 LIMIT 的分页查询 |
| **修正** | ① 避免在事务中使用 LIMIT + FOR UPDATE 的组合；② 如需绝对防幻读，使用 `SERIALIZABLE` 隔离级别；③ 理解"RR 用 Next-Key Lock **大部分**防幻读"的边界条件——LIMIT、快照读与当前读混用、二级索引定位错位等场景仍可能出现幻读 |

> 📌 **注意**：普通的范围查询（不带 LIMIT）如 `WHERE id > 5 FOR UPDATE` 会锁定整个 (5, +∞) 的间隙，不会出现幻读。只有 LIMIT 提前终止扫描时，尾部间隙才未锁定。

### 坑 3：自增主键的 `AUTO_INCREMENT` 锁

```sql
-- ❌ 高并发 INSERT 时
INSERT INTO orders (user_id, amount) VALUES (1, 99.9);
-- innodb_autoinc_lock_mode = 0（传统模式）时，每次 INSERT 都要拿表级 AUTO-INC 锁
```

| 项目 | 内容 |
|---|---|
| **错因** | 传统模式下 AUTO_INCREMENT 是表级锁，串行化所有 INSERT |
| **比喻里的后果** | 每次给新书编号都要排队等前台唯一的编号机 |
| **线上现象** | 高并发 INSERT 时 TPS 远低于预期，`SHOW STATUS` 看到 `Innodb_autoinc_lock_waits` |
| **修正** | `innodb_autoinc_lock_mode = 1`（连续模式，5.7 默认）或 `= 2`（交叉模式，8.0 默认）。`批量 INSERT` 在 mode=1 下仍会短暂持有表级锁。**注意**：8.0 默认值已从 1 改为 2，因为 8.0 的 binlog_format 默认 ROW，交叉模式在行级复制下是安全的 |

### 坑 4：`COUNT(*)` 为什么慢

```sql
-- ❌ 以为 COUNT(*) 很快
SELECT COUNT(*) FROM orders;
-- InnoDB 没有维护全局行数计数器（因为 MVCC 下不同事务看到的行数不同）
-- 需要扫描一个完整索引
```

| 项目 | 内容 |
|---|---|
| **错因** | InnoDB 的 MVCC 导致不同事务在同一时刻可能看到不同行数，无法维护一个全局准确的 COUNT |
| **比喻里的后果** | 图书馆的影子副本系统让每个读者看到的藏书数量不同，所以没有一个"总藏书数"的牌子 |
| **线上现象** | 亿级表的 `COUNT(*)` 耗时数秒甚至数十秒 |
| **修正** | 如果不需要精确值，用 `EXPLAIN` 的 `rows` 估算；维护一个计数表；或用 `COUNT(*)` 走最小的二级索引（InnoDB 优化器会自动选择最小的索引） |

### 坑 5：`innodb_flush_log_at_trx_commit = 0` 的隐性丢数据

```sql
-- 配置
SET GLOBAL innodb_flush_log_at_trx_commit = 0;  -- 追求性能

-- 如果 mysqld 进程 crash（如 OOM Killer）
-- 最近 ~1 秒的已提交事务可能丢失
```

| 项目 | 内容 |
|---|---|
| **错因** | `= 0` 模式下，Redo Log 每秒才 fsync 一次。crash 时 Redo Log Buffer 中未 fsync 的内容丢失 |
| **比喻里的后果** | 前台变更流水账每秒才往保险柜里存一次，中间 crash 了，这一秒的变更记录全丢 |
| **线上现象** | 主从数据不一致（主库丢了事务但从库可能没有）；主库恢复后某些"已提交"的数据消失 |
| **修正** | 金融/支付类系统**必须** `= 1`；只有日志类/可容忍少量丢失的场景才考虑 `= 0` 或 `= 2` |

### 坑 6：`DELETE` 后磁盘空间不释放

```sql
-- ❌ 以为 DELETE 后 .ibd 文件会变小
DELETE FROM logs WHERE created_at < '2024-01-01';
-- .ibd 文件大小不变！空间标记为可复用但不归还操作系统
```

| 项目 | 内容 |
|---|---|
| **错因** | InnoDB 删除行后，页内空间标记为 Free Space，Extent 不归还给 OS |
| **比喻里的后果** | 从书架上取走了书，但书架还在，图书馆建筑面积不变 |
| **线上现象** | `du -sh *.ibd` 文件大小不减少 |
| **修正** | `OPTIMIZE TABLE` 或 `ALTER TABLE ... ENGINE=InnoDB`（重建表，释放空间，但会锁表/消耗大量 I/O）；或定期 `TRUNCATE` 历史分区 |

### 坑 7：大事务导致主从延迟

```sql
-- ❌ 一个事务更新了 100 万行
BEGIN;
UPDATE products SET price = price * 1.1;  -- 全表更新
COMMIT;
-- 这个事务的 Binlog 在主库执行完后，从库才开始重放
-- 从库单线程重放（5.7 默认）→ 主从延迟可能达到分钟级
```

| 项目 | 内容 |
|---|---|
| **错因** | 大事务在从库的重放时间 ≈ 主库执行时间；5.7 默认单线程复制 |
| **比喻里的后果** | 传抄记录中有一笔"修改 100 万本书"的超级大单，传抄员要抄很久 |
| **线上现象** | `Seconds_Behind_Master` 飙升；读从库的应用读到过期数据 |
| **修正** | 拆分大事务（每 1000 行一批）；8.0 开启并行复制（`slave_parallel_workers`）；使用 GTID 简化故障转移 |

### 坑 8：`SELECT ... FOR UPDATE` 在 RC 下不加 Gap Lock

```sql
-- RC 隔离级别下
BEGIN;
SELECT * FROM t WHERE id > 5 FOR UPDATE;
-- RC 下只加 Record Lock，不加 Gap Lock
-- 其他事务可以在 (5, next_id) 的间隙中插入新行
```

| 项目 | 内容 |
|---|---|
| **错因** | RC 级别下 InnoDB 不添加 Gap Lock（除了外键检查），因为 RC 不需要防幻读 |
| **比喻里的后果** | 便签只贴在已有的书上，书与书之间的空隙没有保护 |
| **线上现象** | 业务逻辑中"先查后插"的去重操作在 RC 下可能插入重复数据 |
| **修正** | 如果需要防幻读，使用 RR 或 SERIALIZABLE；或用 `UNIQUE` 约束兜底 |

### 坑 9：`ORDER BY` 导致的 filesort

```sql
-- ❌ 以为有索引就能排序
SELECT * FROM orders WHERE status = 'pending' ORDER BY created_at DESC;
-- 如果索引是 (status)，排序字段 created_at 不在索引中 → filesort
```

| 项目 | 内容 |
|---|---|
| **错因** | 索引只能按索引列的顺序返回数据，无法直接提供非索引列的排序 |
| **比喻里的后果** | 目录柜按状态分类，但每个分类内部的书不是按日期排的，需要人工重新排序 |
| **线上现象** | `EXPLAIN` 中出现 `Using filesort`，大表排序耗时显著 |
| **修正** | 创建联合索引 `(status, created_at)` 或 `(status, created_at DESC)`（8.0） |

### 坑 10：`LIKE '%keyword'` 不走索引

```sql
-- ❌
SELECT * FROM users WHERE name LIKE '%Alice%';
-- 左模糊匹配无法利用 B+ 树索引（B+ 树只能利用前缀匹配）
```

| 项目 | 内容 |
|---|---|
| **错因** | B+ 树基于前缀比较做二分查找，`%Alice%` 无法确定起始位置 |
| **比喻里的后果** | 目录柜按首字母排列，但你要找"名字中间包含 Alice"的书，只能逐本翻 |
| **线上现象** | 全表扫描，大表查询超时 |
| **修正** | 使用全文索引 `FULLTEXT`；或引入 Elasticsearch 等搜索引擎 |

### 坑 11：`innodb_buffer_pool_size` 设太大导致 OOM

```sql
-- ❌ 把 Buffer Pool 设成物理内存的 95%
SET GLOBAL innodb_buffer_pool_size = 60 * 1024 * 1024 * 1024;  -- 64GB 机器设了 60GB
```

| 项目 | 内容 |
|---|---|
| **错因** | MySQL 进程除了 Buffer Pool 还需要：连接内存、排序缓冲区、临时表、binlog cache、各线程栈等 |
| **比喻里的后果** | 阅览室桌面占了图书馆 95% 的面积，留给走廊、前台、消防通道的空间不够了 |
| **线上现象** | Linux OOM Killer 杀掉 mysqld 进程 |
| **修正** | `innodb_buffer_pool_size` 通常设为物理内存的 **50~75%**（专用数据库服务器）；预留足够给 OS 文件缓存和其他 MySQL 组件 |

### 坑 12：隐式类型转换导致索引失效

```sql
-- phone 列类型是 VARCHAR(20)，有索引
SELECT * FROM users WHERE phone = 13800138000;  -- 传了数字，不是字符串
-- MySQL 对 phone 列做隐式 CAST(phone AS SIGNED) → 索引失效
```

| 项目 | 内容 |
|---|---|
| **错因** | MySQL 对 VARCHAR 列进行隐式类型转换，等价于对列加函数 → 无法走索引 |
| **比喻里的后果** | 你要查 ISBN 编号，但传了一个数字而不是字符串，目录柜的检索方式变了，只能逐本比对 |
| **线上现象** | `EXPLAIN` 显示 `type: ALL`（全表扫描），预期走索引却没走 |
| **修正** | SQL 中使用正确的类型：`WHERE phone = '13800138000'`（加引号） |

### 坑 13：大量 DELETE 后，INSERT 飞快但 BETWEEN 查询崩了

> 📌 **详细内容**：参见 Level 2 的"🏛️ 深度案例：删除一半数据后，INSERT 依然飞快，但 BETWEEN 查询崩了"。核心原因是 InnoDB 的 B+ 树叶子页**不会因为 DELETE 而自动合并**，导致页内有效数据密度下降，范围查询性能恶化。

| 项目 | 内容 |
|---|---|
| **错因** | 删除大量数据后，叶子页数量不变，但每页有效数据密度下降。范围查询需要扫描的页数不变，但返回的有效数据量减半 → 单位 I/O 吞吐量腰斩 |
| **线上现象** | `EXPLAIN` 显示的扫描行数与删除前相近；范围查询耗时显著增加；Buffer Pool 命中率可能下降 |
| **修正** | `OPTIMIZE TABLE` 或 `ALTER TABLE ... ENGINE=InnoDB` 重建表（注意：重建大表需要停机或大量 I/O） |

### 坑 14：`Waiting for table metadata lock`——长事务引发的 MDL 雪崩

```sql
-- T1：一个忘了 COMMIT 的长事务（可能只是一个交互式 session 里的 SELECT）
BEGIN;
SELECT * FROM orders WHERE id = 1;
-- 忘了 COMMIT，连接一直保持

-- T2：DBA 执行 DDL
ALTER TABLE orders ADD INDEX idx_status (status);
-- 卡在 "Waiting for table metadata lock"

-- T3：新来的普通查询
SELECT * FROM orders WHERE id = 2;
-- 也卡在 "Waiting for table metadata lock"（被排队的 DDL 阻塞）
```

| 项目 | 内容 |
|---|---|
| **错因** | MDL（Metadata Lock）是 Server 层的锁，不在 InnoDB 层。普通 SELECT 持有 MDL_SHARED，DDL 需要 MDL_EXCLUSIVE。MDL 队列是 FIFO：DDL 排在长事务后面等，后续查询排在 DDL 后面等 → 雪崩式阻塞 |
| **比喻里的后果** | 图书馆要重新装修某个阅览室（DDL），但里面有个读者（长事务）一直没走。装修队排队等着，新来的读者也被排在装修队后面——整个阅览室被"冻结"了 |
| **线上现象** | `SHOW PROCESSLIST` 出现大量 `Waiting for table metadata lock`；但 `Innodb_row_lock_waits` 完全正常（因为问题不在 InnoDB 行锁层） |
| **修正** | ① 监控长事务（`SELECT * FROM information_schema.innodb_trx` 找运行 > 60s 的事务）；② 排查 MDL 持有者：`SELECT * FROM performance_schema.metadata_locks`（8.0）；③ KILL 长事务连接；④ DDL 选择低峰期；⑤ `lock_wait_timeout` 调低到 10~60s |

### 坑 15：联合索引遇到范围查询，后面的列失效

```sql
-- 索引：INDEX idx_abc (a, b, c)
SELECT * FROM t WHERE a = 1 AND b > 10 AND c = 5;
-- EXPLAIN 显示：type=range, key_len=8（只用了 a 和 b，c 没用上）
```

| 项目 | 内容 |
|---|---|
| **错因** | InnoDB 联合索引的物理排列是"a 有序，a 相同时 b 有序，a 和 b 都相同时 c 才有序"。一旦 b 是范围条件（`b > 10`），在 `a=1 AND b>10` 的结果集里，c 的值是无序的，无法用索引定位，只能逐行比对 |
| **比喻里的后果** | 图书馆的目录柜按"作者→出版年→书名"排序。你查"作者=张三 AND 出版年>2010 AND 书名=MySQL"，找到张三 2010 年后的所有书后，这些书的书名是无序的，只能逐本翻 |
| **线上现象** | `EXPLAIN` 的 `key_len` 比预期短；`Extra` 出现 `Using where`（表示需要额外过滤）；查询性能不如预期 |
| **修正** | ① 调整联合索引列顺序，把等值查询列放前面，范围查询列放最后：`INDEX (a, c, b)` 让 `a=1 AND c=5` 先用上索引，`b>10` 最后过滤；② 8.0 的 Index Condition Pushdown（ICP）能部分缓解（在存储引擎层过滤而非 Server 层），但**不能完全解决**——ICP 减少回表次数，但 c 仍然无法用于索引定位 |

### 坑 16：对索引列做函数运算导致索引失效

```sql
-- create_time 有索引
SELECT * FROM orders WHERE DATE(create_time) = '2024-01-01';
-- EXPLAIN 显示：type=ALL（全表扫描）
```

| 项目 | 内容 |
|---|---|
| **错因** | `DATE(create_time)` 对索引列加了函数，InnoDB 必须对每一行都执行 `DATE()` 计算后才能比较，无法利用 B+ 树的有序性做二分查找，退化为全表扫描 |
| **比喻里的后果** | 目录柜按"出版日期"排序，但你要查"出版日期的年份=2024"。管理员必须把每本书的出版日期都算一遍年份，才能判断是否匹配——目录柜的排序完全没用上 |
| **线上现象** | `EXPLAIN` 显示 `type=ALL`；大表查询超时；CPU 使用率飙升（大量函数计算） |
| **修正** | ① 改写 SQL，避免对索引列做函数运算：`WHERE create_time >= '2024-01-01' AND create_time < '2024-01-02'`；② 8.0 的表达式索引可以解决：`CREATE INDEX idx ON orders ((DATE(create_time)))`，但需要提前规划，且只对这个特定表达式有效 |

### 坑 17：`LIMIT offset, N` 深度分页性能雪崩

```sql
-- 翻到第 10 万页（每页 10 条）
SELECT * FROM orders ORDER BY id LIMIT 1000000, 10;
-- 耗时从第 1 页的 ~1ms 飙升到 ~2s
```

| 项目 | 内容 |
|---|---|
| **错因** | `LIMIT 1000000, 10` 不是"跳过 100 万行再取 10 行"，物理上是"扫描 1000010 行，丢弃前 100 万行，返回最后 10 行"。offset 越大，扫描行数越多，I/O 和 CPU 开销线性增长 |
| **比喻里的后果** | 你要找图书馆里第 100001~100010 本书。管理员必须从第 1 本开始数，数到第 100010 本，然后只给你最后 10 本——前 10 万本白数了 |
| **线上现象** | 翻页越往后越慢；`EXPLAIN` 显示 `rows` 值很大（= offset + N）；Buffer Pool 被大量"一次性页"污染 |
| **修正** | ① **游标分页**（推荐）：记住上一页最后一条记录的 id，用 `WHERE id > 上次最大id ORDER BY id LIMIT 10`，每次只扫描 10 行，性能恒定；② **子查询优化**：`SELECT * FROM orders WHERE id >= (SELECT id FROM orders ORDER BY id LIMIT 1000000, 1) LIMIT 10`，先用覆盖索引快速定位 id，再回表取完整行 |

### 坑 18：长事务 ROLLBACK 代价被严重低估

```sql
-- 一个跑了 30 分钟、修改了 100 万行的事务
-- DBA 决定 KILL 掉
KILL 12345;
-- 事务进入 ROLLBACK 状态，又卡了 40 分钟
```

| 项目 | 内容 |
|---|---|
| **错因** | ROLLBACK 不是"撤销事务标记"，而是沿着 Undo Log **逐条执行反向操作**（INSERT 变 DELETE，DELETE 变 INSERT，UPDATE 反向 UPDATE）。如果事务正向执行了 30 分钟、修改了 100 万行，回滚也需要执行 100 万次反向操作，耗时经常与正向执行同一量级，甚至更长（因为回滚时的 I/O 模式可能更差） |
| **比喻里的后果** | 图书馆管理员花了 30 分钟把 100 万本书从旧书架搬到新书架。现在要撤销，必须把这 100 万本书再搬回去——耗时不会比正向搬更短 |
| **线上现象** | `SHOW PROCESSLIST` 中 `State` 显示 `Rolling back`；`KILL` 后系统卡顿反而加剧（回滚占用大量 CPU/I/O）；`SHOW ENGINE INNODB STATUS` 的 `TRANSACTIONS` 段显示 `ROLLING BACK` 和预估剩余行数 |
| **修正** | ① **预防为主**：拆分大事务（每 1000~5000 行一批），避免单事务修改行数过多；② **不要急于 KILL**：先评估事务已修改行数（`SELECT * FROM information_schema.innodb_trx` 查看 `trx_rows_modified`），如果行数很大，让事务自然 COMMIT 可能比 ROLLBACK 更快；③ **监控回滚进度**：`SHOW ENGINE INNODB STATUS` 查看 `ROLLING BACK` 后的 `X rows` 预估剩余量 |

<a id="timeline-table"></a>
## 📊 竖切总表 T0–T8

一条 `UPDATE users SET name='X' WHERE id=1001` 的完整时间线：

| 阶段 | 位置 | 关键动作 | 不变量 | 典型坑 |
|---|---|---|---|---|
| **T0** | Client → Server | SQL 文本通过 TCP 到达 mysqld | SQL 文本完整、未篡改 | 网络超时 / 连接数打满 |
| **T1** | Server: Parser + Preprocessor | 词法分析 → 语法树 → 检查表/列存在 | 语法正确的 AST | 表名/列名拼写错误 |
| **T2** | Server: Optimizer | 选择索引、生成执行计划 | 最优执行计划（基于统计信息） | 统计信息过期导致选错索引 |
| **T3** | InnoDB: B+ Tree | Root → NonLeaf → Leaf，定位 page_no | 页在 BP 中可寻址 | 页不在 BP 中触发随机读 I/O |
| **T4** | InnoDB: Lock | IX(表) + X Record Lock(id=1001) | 排他锁获取成功或进入等待 | 无索引 → 全表加锁；死锁回滚 |
| **T5** | InnoDB: Current Read | 读取 id=1001 的最新已提交版本 | 读到的是已提交数据 | MVCC 版本链过长导致读取慢 |
| **T6** | InnoDB: Undo Log | 写逆操作 + 创建版本链节点 | 回滚所需信息已持久化 | Undo Log 空间不足（长事务） |
| **T7** | InnoDB: Buffer Pool | 修改页内数据，页变脏 | 内存中数据已更新、Flush List 已记录 | — |
| **T8** | InnoDB: Redo Log + Binlog | Redo prepare → Binlog fsync → Redo commit | 日志已持久化，crash 可恢复 | `flush_log_at_trx_commit ≠ 1` 丢数据 |
| **T9** | InnoDB: Commit 返回 | 释放锁、返回客户端 OK | 事务已提交、锁已释放 | — |
| **T10** | [异步] InnoDB: Checkpoint | 后台刷脏页到 .ibd | 脏页最终落盘 | 刷盘风暴导致 I/O 尖刺 |
| **T11** | [异步] InnoDB: Purge | 清理过期 Undo Log 版本 | 不再需要的版本已回收 | 长事务阻止 Purge |

<a id="errata"></a>
## 📚 版本勘误表

| # | ❌ 常见说法 | ✅ 更准确的说法 |
|---|---|---|
| 1 | "InnoDB RR 级别完全解决了幻读" | InnoDB RR 通过 Next-Key Lock **大部分场景**防幻读，但当前读仍有边界场景可出现幻读（如 Level 5 坑 2 所示） |
| 2 | "`innodb_old_blocks_pct = 37` 表示 New 区占 37%" | 实际是 **Old 区占 37%**，New 区占 63%。参数名 `old_blocks_pct` 直译就是"Old 区百分比"，但实际调参时容易凭直觉把数字记反 |
| 3 | "InnoDB 行锁锁的是行" | 行锁实际上是锁在**索引记录**上的，不是锁在数据行上。如果 WHERE 条件没有索引，InnoDB 需要全表扫描逐行加锁 |
| 4 | "DELETE 后空间会释放" | InnoDB DELETE 后空间标记为可复用，但**不归还操作系统**。需要 `OPTIMIZE TABLE` 重建表才能释放 |
| 5 | "COUNT(*) 在 InnoDB 中有缓存，很快" | InnoDB 不维护全局行数（MVCC 下不同事务看到的行数不同）。`COUNT(*)` 需要扫描一个完整索引。MyISAM 才有行数缓存 |
| 6 | "MySQL 8.0 默认隔离级别改成了 RC" | 8.0 **默认隔离级别仍然是 RR**。但 8.0 移除了 `innodb_locks_unsafe_for_binlog` 参数，且部分 ORM/框架默认用 RC |
| 7 | "Redo Log 记录的是 SQL 语句" | Redo Log 是**物理日志**，记录的是"页号 + 偏移量 + 修改后的字节"。Binlog（ROW 格式）记录的才是行级变更 |
| 8 | "我以前也讲错过：`SELECT ... FOR UPDATE` 在 RR 下一定加 Next-Key Lock" | 如果是**唯一索引等值查询**且记录存在，Next-Key Lock 会**退化为 Record Lock**（只锁记录不锁间隙）。不是所有 FOR UPDATE 都加完整的 Next-Key Lock |
| 9 | "我以前也讲错过：`innodb_buffer_pool_size` 越大越好" | Buffer Pool 过大会挤压 OS 文件缓存和其他 MySQL 组件内存。一般设为物理内存的 50~75%，并且需要观察 `Innodb_buffer_pool_pages_free` 确认是否真正需要更大 |
| 10 | "Binlog 是 InnoDB 的日志" | Binlog 是 **MySQL Server 层**的日志，与存储引擎无关。MyISAM、Memory 等引擎也会写 Binlog。Redo Log 才是 InnoDB 引擎层的 |

## 🏆 生产决策卡

### 决策卡 1：隔离级别选型

| 项目 | 内容 |
|---|---|
| **场景与判断** | 新业务项目选型 InnoDB 隔离级别 |
| **机制到决策映射** | RR → 默认、防幻读能力强、MVCC 复用 Read View；RC → 锁粒度小、gap lock 少、但需应用层防幻读 |

| 决策 | 落地 | 代码 / 配置 |
|---|---|---|
| 大多数 OLTP 业务 | 保持默认 RR | `SET GLOBAL tx_isolation = 'REPEATABLE-READ'`（5.7）/ `SET GLOBAL transaction_isolation = 'REPEATABLE-READ'`（8.0） |
| 高并发 + 简单读写比 | RC 减少 gap lock | `SET GLOBAL transaction_isolation = 'READ-COMMITTED'`；需确保 Binlog 格式为 ROW |
| 金融/强一致场景 | RR + 应用层乐观锁 | 使用 `version` 字段做 CAS 检查 |

| 不能做的错误决策 | 原因 |
|---|---|
| 在 STATEMENT Binlog 下使用 RC | RC 下 gap lock 减少，STATEMENT 复制可能不一致。5.7 会报错 |
| 使用 SERIALIZABLE | 所有 SELECT 加锁，并发度暴跌 |

| 验收指标 | 目标值 |
|---|---|
| `Innodb_row_lock_waits` | 增长趋势平稳，无尖刺 |
| `Innodb_row_lock_time_avg` | < 50ms |
| 业务层幻读投诉 | 0 |

### 决策卡 2：Buffer Pool 容量规划

| 项目 | 内容 |
|---|---|
| **场景与判断** | 新服务器上线或扩容时，确定 Buffer Pool 大小 |
| **机制到决策映射** | Buffer Pool 命中率 < 99% 说明容量不足或存在全表扫描 |

| 决策 | 落地 | 代码 / 配置 |
|---|---|---|
| 专用 DB 服务器 | 物理内存的 60~75% | `innodb_buffer_pool_size = 48G`（64GB 机器） |
| 混部服务器（DB + 应用） | 物理内存的 30~50% | 按实际可用内存计算 |
| 多实例 | `innodb_buffer_pool_instances = 8` | 减少 mutex 竞争（BP > 1GB 时建议开启） |

| 不能做的错误决策 | 原因 |
|---|---|
| 设为物理内存 90%+ | OS 文件缓存 + MySQL 其他组件内存不足 → OOM |
| 命中率低就无脑加大 | 先检查是否有全表扫描在污染缓存 |

| 验收指标 | 目标值 |
|---|---|
| Buffer Pool 命中率 | > 99.5% |
| `Innodb_buffer_pool_pages_free` | > 总页数的 5% |
| `Innodb_buffer_pool_read_requests` vs `Innodb_buffer_pool_reads` | 比值 > 200:1 |

### 决策卡 3：索引设计

| 项目 | 内容 |
|---|---|
| **场景与判断** | 表结构设计阶段 + 慢查询优化 |
| **机制到决策映射** | B+ 树 3 层 ≈ 亿级容量；聚簇索引决定数据物理排列；二级索引回表有代价；选择性是建索引的第一道门槛；最左前缀原则决定联合索引列顺序 |

| 决策 | 落地 | 代码 / 配置 |
|---|---|---|
| **判断是否建索引** | 先算选择性：`COUNT(DISTINCT col) / COUNT(*)`，< 0.01 的列通常不值得建单列索引 | `SHOW INDEX FROM t` 看 `Cardinality` 列 |
| 主键选择 | 自增 BIGINT（避免 UUID 导致页分裂） | `id BIGINT AUTO_INCREMENT PRIMARY KEY` |
| 联合索引列顺序 | 等值列放前面，范围列放最后；同等条件下选择性高的列靠前 | `INDEX idx (a, c, b)` 而非 `INDEX idx (a, b, c)` |
| 高频查询覆盖 | 创建联合索引，优先覆盖 WHERE + ORDER BY | `INDEX idx_status_created (status, created_at)` |
| 大字段索引 | 用前缀索引代替全列索引，取"够用就好"的前缀长度 | `INDEX idx_email (email(12))` |
| 避免回表 | 覆盖索引（Covering Index） | `INDEX idx_cover (status, created_at, user_id)`，查询只 SELECT 索引列 |
| 评估删除索引 | 8.0 用不可见索引先观察 | `ALTER TABLE t ALTER INDEX idx INVISIBLE` |

| 不能做的错误决策 | 原因 |
|---|---|
| 给每列都建索引 | 写入时每个索引都需要维护 B+ 树，INSERT/UPDATE 变慢 |
| 给低选择性列建单列索引 | 性别、boolean 等列区分度太低，优化器大概率放弃使用索引，白占空间 |
| 联合索引按表定义顺序而非查询顺序 | 应该按 WHERE 条件的使用频率和选择性排列，不是按表中列的先后顺序 |
| 用 UUID 做主键 | 随机插入导致 B+ 树频繁页分裂，写放大严重 |
| 在大表上 `DROP INDEX` 直接删 | 如果索引实际有用，删了导致慢查询。8.0 先用 `INVISIBLE` 观察 |

| 验收指标 | 目标值 |
|---|---|
| `EXPLAIN` 中 `type` | `ref` / `eq_ref` / `range`（非 `ALL`） |
| `EXPLAIN` 中 `Extra` | 无 `Using filesort`、无 `Using temporary` |
| `SHOW INDEX` 的 `Cardinality` | 常用索引的 Cardinality 应远大于 1 |
| 单表索引数量 | ≤ 6 个（经验值，以业务为准）`[须实测]` |

### 决策卡 4：日志与持久性配置

| 项目 | 内容 |
|---|---|
| **场景与判断** | 部署配置阶段，确定日志策略 |
| **机制到决策映射** | `flush_log_at_trx_commit` 决定数据安全与写性能的 trade-off；Binlog 格式决定主从一致性；`innodb_io_capacity` 决定脏页刷盘速率 |

| 决策 | 落地 | 代码 / 配置 |
|---|---|---|
| 金融/支付系统 | `flush=1` + `binlog_format=ROW` + `sync_binlog=1` | "双 1 配置"：最安全，每次 commit 两次 fsync |
| 一般业务系统 | `flush=1` + `binlog_format=ROW` + `sync_binlog=100`（配合 group commit） | 平衡安全与性能 |
| 日志/埋点系统 | `flush=2` + `binlog_format=ROW` | 允许极端情况丢少量数据 |
| SSD 环境 | `innodb_io_capacity = 2000~20000` | 默认 200 是为 HDD 设计的，SSD 必须调高 |
| HDD 环境 | `innodb_io_capacity = 200~500` | 保持默认或适当调高 |

| 不能做的错误决策 | 原因 |
|---|---|
| `flush=0` 用于金融系统 | crash 丢数据不可接受 |
| `binlog_format=STATEMENT` + RC 隔离级别 | 5.7 会报错；8.0 虽不报错但复制可能不一致 |
| 不设 Binlog 过期时间 | 磁盘逐渐被 Binlog 填满 → 数据库宕机 |
| SSD 环境保持 `innodb_io_capacity = 200` | 刷盘速率太低 → 脏页堆积 → 触发激进刷盘（furious flushing）→ 写入延迟突然飙升（竖切总表 T10 提到的"I/O 尖刺"的直接成因） |

| 验收指标 | 目标值 |
|---|---|
| `Innodb_log_waits` | 0（如果 > 0，考虑加大 `innodb_log_buffer_size`） |
| `Innodb_os_log_written` 增长率 | 稳定，无异常尖刺 |
| `Innodb_buffer_pool_pages_dirty` | 占 Buffer Pool 总页数 < 50%（过高说明刷盘跟不上） |
| 主从延迟 `Seconds_Behind_Master` | < 1s |
| Binlog 磁盘占用 | 有过期策略，不超过磁盘 30% |

> 📌 **`innodb_io_capacity` 与刷盘风暴的关系**：这个参数告诉 InnoDB "后台每秒可以尝试刷多少个脏页"。默认值 200 是为 7200RPM HDD 设计的。如果在 SSD 上保持默认值，InnoDB 的刷盘速率被人为限制在很低的水平，脏页会在 Buffer Pool 中不断堆积。当脏页比例达到 `innodb_max_dirty_pages_pct`（默认 90%）时，InnoDB 被迫进入"激进刷盘"模式，把所有 I/O 资源用于刷脏页，导致前台写入延迟突然飙升——这就是线上常见的"I/O 尖刺"现象。`innodb_io_capacity_max` 控制激进刷盘时的上限。

### 决策卡 5：慢查询排查 SOP

| 项目 | 内容 |
|---|---|
| **场景与判断** | 线上出现慢查询告警 |
| **机制到决策映射** | 全链路每一层都可能成为瓶颈：解析/优化/索引/锁/Buffer Pool/日志 |

| 步骤 | 命令 / 动作 | 检查什么 |
|---|---|---|
| 1. 识别慢查询 | `SHOW PROCESSLIST` / slow_query_log | 哪条 SQL 在执行、状态是什么 |
| 2. 分析执行计划 | `EXPLAIN SELECT ...` | `type` 是否 ALL、是否 `Using filesort` |

|---|---|

| 验收指标 | 目标值 |
|---|---|
| 慢查询数量（> 1s） | 趋势下降 |
| P99 查询延迟 | < 200ms（业务相关）`[须实测]` |
| 锁等待超时次数 | 0 |

## 🌍 跨语言/跨运行时视角

### 同构性问题映射

InnoDB 面临的核心问题不是 MySQL 独有的。以下是同构性问题在不同系统中的解法：

| InnoDB 问题 | PostgreSQL | Oracle | RocksDB / LevelDB | Redis |
|---|---|---|---|---|
| **页面存储** | 8KB heap page（与 InnoDB 的 16KB B+ tree page 结构不同） | 8KB block | SSTable（LSM-Tree 的不可变文件） | 内存 + RDB/AOF 持久化 |
| **Buffer 缓存** | Shared Buffers + OS Page Cache（依赖 OS 缓存更多） | Buffer Cache（SGA） | Block Cache（内存） | 纯内存 |
| **索引结构** | B-Tree + GiST + GIN + BRIN | B-Tree + Bitmap + IOT | LSM-Tree + Bloom Filter | Skip List / Hash Table |
| **MVCC** | ✅ 每行多版本存储在主表中（非 Undo Log），需 VACUUM 清理 | ✅ Undo Segments | 不支持（KV 存储，无事务隔离级别概念） | 不支持（单线程模型） |
| **锁机制** | 行锁（基于元组 header 的 xid），无间隙锁；但 SERIALIZABLE 级别下用 SIREAD 谓词锁防幻读 | 行锁 + TM/TX 锁，无间隙锁 | 无（单写线程） | 无（单线程） |
| **WAL** | WAL（pg_wal/） | Redo Log（online redo logs） | WAL（.log 文件） | AOF |
| **两阶段提交** | 无（只有一层 WAL） | 无（只有一层 Redo） | 无 | 无 |

### 跨语言后仍成立的 7 条判断力

无论用什么数据库/存储系统，以下判断力始终成立：

1. **I/O 单元对齐**：任何持久化存储都有"最小 I/O 单元"（page / block / segment）。理解它是分析性能的第一步。
2. **缓存必然存在**：从 CPU cache → Buffer Pool → OS page cache → SSD DRAM cache，每一层都在用"更快更小的存储"缓存"更慢更大的存储"的数据。缓存策略（LRU / LFU / ARC）的选择决定了系统在不同负载下的表现。
3. **索引是空间换时间**：所有索引都是"额外的数据结构 + 写入时维护开销"换"读取时更快定位"。没有免费的索引。
4. **并发控制只有两条路**：悲观（锁）或乐观（MVCC / CAS / Timestamp ordering）。选择取决于读写比例。
5. **WAL 是持久性的通用模式**：先顺序写日志，再异步持久化数据。任何需要 crash-safe 的系统都需要类似机制。
6. **两阶段提交是跨系统一致性的最小代价**：当两个独立的持久化系统需要协调时，必然需要某种形式的 2PC（或降级到最终一致性）。
7. **长事务是所有 MVCC 系统的敌人**：无论 InnoDB、PostgreSQL 还是 Oracle，长事务都会阻止 GC，导致版本堆积和性能退化。

### 从 InnoDB 到其他系统的迁移清单

当你学习一个新的存储系统时，用以下问题快速建立认知框架：

| 问题 | 在 InnoDB 中的答案 | 在新系统中找对应 |
|---|---|---|
| 最小 I/O 单元是什么？ | 16KB Page | → ? |
| 缓存策略是什么？ | 改良 LRU（New/Old 分区） | → ? |
| 索引结构是什么？ | B+ Tree（聚簇） | → ? |
| 并发控制用什么？ | Lock + MVCC | → ? |
| WAL 怎么实现？ | Redo Log 环形写入 | → ? |
| 崩溃恢复怎么做？ | Redo Log 重放 + Undo Log 回滚 | → ? |

**八条口诀（电梯版复述稿）**：

1. 📦 页是 I/O 最小单元，16KB 不止存数据

6. 📸 快照读看 Read View，RR 复用 RC 新建
