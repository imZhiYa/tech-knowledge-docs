# shard-02：中间件架构与一次 SQL 的生命 ⚙️

> 本文只追踪一个主线：**一条 SQL S 穿越中间件**。shard-01 的结尾留了一笔账：分片键选好了、算法定了、ID 有了，但业务代码里的 SQL 怎么执行？T 的主人以为中间件就是一个"把 SQL 发到多个库的连接池"——结果先后发现：不带分片键的 SQL 被悄悄广播到 8 片、`ORDER BY` 返回的结果顺序是乱的、`AVG` 算出来的平均值是错的。中间件不是连接池，它是**解析、路由、改写、执行、归并**五段引擎的串行，其中改写引擎是正确性边界——改写错，结果就错。
>
> 下一篇（shard-03）承接：SQL 穿过中间件之后，每笔跨片查询到底要付多少代价（广播放大、深翻页、跨片 JOIN）。

# 全文唯一比喻：读者查目录、取书、跨馆调书

延续本系列图书馆体系：T 是书，分片是馆，分片键是分类号。本文的 S 是**一张借书单**：

```text
读者提交借书单                    ←→ 应用提交 SQL
检索台读懂借书单                  ←→ 解析引擎：理解 SQL 语义
目录告诉书在哪个馆                ←→ 路由引擎：决定去哪几个分片
把借书单改写成"去 X 馆取书"       ←→ 改写引擎：逻辑表→物理表
各馆同时取书                      ←→ 执行引擎：并发执行到分片
服务台按清单顺序整理              ←→ 归并引擎：排序/聚合/分页
读者自己跑去找书                      ←→ JDBC 模式：检索台就在读者家里
图书馆设统一检索台                    ←→ Proxy 模式：独立服务台
```

| 图书馆 | 中间件 | 机制含义 |
| --- | --- | --- |
| 借书单 | SQL | 一次查询请求 |
| 检索台读懂借书单 | 解析引擎 | 语法树是后续所有引擎的输入 |
| 目录定位 | 路由引擎 | 决定单片/多片/广播 |
| 改写借书单 | 改写引擎 | 正确性边界：改写错=结果错 |
| 各馆取书 | 执行引擎 | 并发 + 连接策略 |
| 服务台整理 | 归并引擎 | 排序/聚合/分页恢复语义 |
| 读者自己跑 | JDBC 模式 | 应用内嵌，进程内路由 |
| 统一检索台 | Proxy 模式 | 独立服务，协议兼容 |

## Level 1：为什么需要中间件这一层——神话④"中间件=连接池"

一句话认知墙：**中间件不是连接池——它是路由、改写、归并三职责的串行，缺一个，SQL 的执行结果就是错的。**

### 前置知识关卡

- [ ] 知道分片键决定路由（shard-01 L1）
- [ ] 知道无路由键查询 = 广播全分片（shard-00 L4）
- [ ] 知道本地事务 = 单连接原子性（springboot-05 L6.4）

### Why：为什么"连接池"这个直觉是错的

**徒弟**：

> 分库分表之后，我把 4 个库、8 张物理表的地址配进中间件，中间件不就是个"大连接池"吗？SQL 进去，它按分片键挑一个库一张表发出去，完事。MyBatis 连的是中间件，中间件连的是 4 个库。

**老陈**：

> "挑一个库发出去"只是路由，而且是最简单的那种。真正的问题是：**分片之后，你的 SQL 在单库上成立的前提，在 8 个物理分片上不成立了**。一条单库 SQL 里有三个东西会失效，每一个都需要引擎来救：

```text
① 表名失效
   逻辑表 order 在物理上不存在，只存在 order_0 ~ order_7。
   没有改写引擎，SQL 发到任何库都是"表不存在"。

② 语义失效
   单库上 "ORDER BY id LIMIT 10" 就是全局前 10。
   8 片各执行一遍，每片都返回自己那片的前 10，
   8 个"局部前 10"合并后**不是**全局前 10（例子：全局前 10 可能
   全在 0 号片，但 1~7 号片也各交了 10 条凑数）。
   没有归并引擎，排序、分页、聚合结果全是错的。

③ 正确性失效
   "SELECT AVG(price) FROM order" 单库直接算。
   8 片各算一个 AVG，8 个 AVG 再求平均 ≠ 全局 AVG
   （各片行数不同，不能简单平均——机制推导，见 L4）。
   没有改写引擎，聚合结果也是错的。
```

> 所以中间件是三件事：**路由**（去哪）、**改写**（把 SQL 改成每片能执行的正确版本）、**归并**（把各片结果拼成单库语义的结果）。它像图书馆的检索台：读懂借书单、查目录定位、改写借书单、通知各馆、整理结果——**不是读者和书库之间的一个管道**。

### What：三个职责各自回答什么问题

```text
路由引擎   这条 SQL 要去哪几个分片？       → 单片 / 多片 / 广播
改写引擎   每片收到的 SQL 长什么样？       → 表名、聚合、排序、分页的局部化
归并引擎   各片结果怎么拼成全局语义？      → 遍历/排序/分组/聚合/分页归并
```

三者关系（机制）：**路由决定"去几片"，改写决定"每片执行什么"，归并决定"结果怎么拼"。改写必须知道路由结果（改给哪几片），归并必须知道改写结果（每片返回了什么）——所以是串行管道，不是并列组件。**

### How：三个职责怎么协作——用 T 的 SQL 走一遍

```text
SQL：SELECT user_id, amount FROM order WHERE order_id = 500 ORDER BY amount LIMIT 5

① 解析   读懂：从 order 表查 order_id=500 的记录，按 amount 排序取前 5
② 路由   分片键 order_id=500 → 500 % 8 = 4 → 命中 4 号片 → 单片路由
③ 改写   order → order_4；ORDER BY amount 本身在分片内执行
④ 执行   连接 4 号库执行
⑤ 归并   单分片结果无需归并，直接返回（遍历归并）

——这是最幸福的情况：带分片键、单分片、简单查询。

再来一条：
SQL：SELECT SUM(amount) FROM order WHERE created_at > '2026-01-01'

① 解析   读懂：聚合统计
② 路由   WHERE 没有分片键 → 广播 8 片
③ 改写   order → order_0..order_7，SQL 本身不变（SUM 各片可独立算）
④ 执行   8 片并发执行 SUM
⑤ 归并   聚合归并：8 个 SUM 相加 = 全局 SUM
```

> 注意第三条隐含结论：**SUM 可以各片先算再加，但 AVG 不能各片先算再平均**——这是改写引擎存在的理由之一（L4 展开）。

### Transfer：三职责是所有"分片存储"的通用骨架

1. Redis Cluster：客户端算 slot（路由）→ 单 key 直连（无改写，因为 Redis 无 SQL）→ 客户端聚合或命令合并（归并）。
2. Elasticsearch：shard 上的倒排索引（路由）→ 查询 DSL 下发（改写：filter/agg 下推到分片）→ 协调节点汇总（归并：fetch/agg 阶段，es-02 回链）。
3. 所有分布式存储的第一课：**路由决定"去哪"，改写决定"每片干什么"，归并决定"怎么拼"——越复杂的语义（SQL > 命令 > KV），改写与归并越重**。

本层留下的新账：**三职责串行成立，但每一步具体怎么干？解析怎么"读懂"SQL，路由怎么判断单片还是广播？** 下一层先看五段链路的完整形状。

### Level Ending

```text
口诀：路由去几片，改写改语义，归并拼结果；三缺一，结果错。
```

## Level 2：五段链路总览——一条 SQL 的完整旅程

一句话认知墙：**一条 SQL 从应用到数据库，中间件执行五段链路：解析 → 路由 → 改写 → 执行 → 归并，前四段都在"翻译"，只有最后一段在"拼装"。**

### 前置知识关卡

- [ ] 知道三职责（L1）
- [ ] 知道分片键 = 路由条件来源（shard-01 L1）

### Why：为什么链路是五段而不是两段

**徒弟**：

> 上一层的三个职责（路由/改写/归并）就够了，为什么还要拆出"解析"和"执行"两段？

**老陈**：

> 因为路由不能直接读 SQL 字符串——它需要结构化的语义信息。`WHERE order_id = 500` 是字符串，路由引擎要的是"这是个等值条件、键是 order_id、值是 500"。从字符串到结构化语义，中间必须有一道**解析**。而"执行"是独立的一段，是因为它有独立的策略问题：8 片是串行还是并发？连接是拿到就释放还是保持到归并完？这两段各有各的机制，拆开讲才讲得清。所以三职责是核心逻辑（**做什么**），五段链路是完整实现（**怎么干**）：解析为路由提供输入，执行是改写的落地——缺一环，链路就断。

### What：五段链路的输入输出

```text
应用 SQL（字符串）
   ↓
① 解析：SQL 字符串 → 抽象语法树 AST（结构化语义）
   ↓
② 路由：AST + 分片规则 → 路由结果（单片/多片/广播 + 每片条件）
   ↓
③ 改写：路由结果 + AST → 每分片可执行的 SQL（表名/聚合/排序/分页局部化）
   ↓
④ 执行：每片 SQL + 连接策略 → 每分片结果集
   ↓
⑤ 归并：多分片结果集 → 单库语义的结果集（排序/聚合/分页恢复）
   ↓
应用结果集
```

各段的"产出物"（机制，实现类名待核证）：

```text
① 解析 → AST：语法树节点（SELECT 语句、WHERE 条件、JOIN 树、聚合函数）
② 路由 → RouterResult：路由类型（单/多/广播）+ 命中的分片集合
③ 改写 → 每片一条 SQL：与分片对应的物理表名、局部化的聚合/排序/分页
④ 执行 → ResultSet 列表：每个分片的原始结果
⑤ 归并 → 最终 ResultSet：全局语义的结果（流式或内存）
```

### How：五段链路的全图——S 的完整旅程

```text
       应用
        │  SELECT user_id, amount FROM order WHERE order_id=500
        ▼
┌─────────────────── 中间件 ───────────────────┐
│ ① 解析  SQL 字符串 ──▶ AST                    │
│         （ANTLR 词法/语法分析，见 L3）         │
│ ② 路由  AST ──▶ 4 号片（单片）                │
│ ③ 改写  AST+路由 ──▶ SELECT ... FROM order_4  │
│ ④ 执行  order_4 SQL ──▶ 4 号库执行 ──▶ 结果集 │
│ ⑤ 归并  单片无需归并 ──▶ 直接返回             │
└──────────────────────────────────────────────┘
        │
        ▼
       应用拿到结果
```

再来一条广播的例子（S 的另一种命运）：

```text
       应用
        │  SELECT COUNT(*) FROM order WHERE created_at > '2026-01-01'
        ▼
┌─────────────────── 中间件 ───────────────────┐
│ ① 解析  AST：COUNT 聚合                       │
│ ② 路由  无分片键 → 广播 8 片                  │
│ ③ 改写  8 条 SQL：order → order_0..order_7    │
│ ④ 执行  8 片并发执行 COUNT(*)                 │
│ ⑤ 归并  聚合归并：8 个 COUNT 相加              │
└──────────────────────────────────────────────┘
```

### Transfer：五段链路 = "编译"的通用结构

1. 数据库自身的 SQL 执行：解析（parser）→ 优化（optimizer）→ 执行（executor）——中间件多了"改写"这一道，因为**同一份 SQL 要翻译成 N 份局部 SQL**。
2. 分布式查询引擎（Presto/Spark SQL）：解析 → 逻辑计划 → 物理计划 → 执行 → 结果汇总，同构。
3. 所有"把一段程序翻译到多台机器执行"的系统，中间都有一道**改写（rewrite）**：编译器也是把 AST 改写（lowering）成目标代码。**改写 = 语义保持的翻译**，是正确性防线。

本层留下的新账：**五段链路的骨架有了，但每一段的机制还是黑盒：解析怎么从字符串得到 AST？路由凭什么判断单片/广播？** 下一层进前两段：解析与路由。

### Level Ending

```text
口诀：解析出语义，路由定去向，改写改语义，执行分片跑，归并拼全局。
```

## Level 3：解析与路由——SQL 怎么变成"去哪几个分片"

一句话认知墙：**解析把 SQL 字符串变成结构化语义（AST），路由从 AST 里提取分片键条件，决定单片、多片还是广播——路由的决定只取决于"条件里有没有分片键、什么形状"。**

### 前置知识关卡

- [ ] 知道分片键等值 = 单片、范围 = 多片、无键 = 广播（shard-01 L1）
- [ ] 知道 IN 是等值集合（可拆成多片逐片等值）

### Why：为什么路由前必须先解析

**徒弟**：

> 路由不就是"看 WHERE 里有没有分片键吗"？我拿正则匹配 `user_id=(\d+)` 不就行了，要什么解析？

**老陈**：

> 正则有两个死穴。第一，**SQL 是嵌套结构**，WHERE 里可能有子查询、括号、OR 组合，正则处理不了树的逻辑；第二，**分片键可能藏在表达式里**——`WHERE order_id = user_id + 100`（order_id 是分片键，但条件右侧是列运算，执行前取不到 user_id 的值）。AST 能告诉你"order_id 在等式左侧、右侧是含列的表达运算"，从而判定"无法推导 → 广播"；正则只知道"有个 order_id 字符串"。路由的正确性依赖语义，语义依赖解析——这就是为什么必须有解析段。

### What：解析与路由各自的机制

```text
解析（机制，实现细节待核证）：
  词法分析：SQL 字符串 → Token 流（关键字/标识符/数字/运算符）
  语法分析：Token 流 → 抽象语法树 AST
  AST 是结构化语义：SELECT 节点、WHERE 树、聚合节点、JOIN 树
  解析器只懂语法，不懂分片——分片规则在路由阶段才进入

路由（机制）：
  输入：AST + 分片规则（分片键、分片算法、分片数）
  核心动作：从 WHERE 条件里提取"分片键条件的形状"：
    等值       order_id = 500           → 单片（算哈希/取模定位）
    IN         user_id IN (1,2,3)       → 多片（逐值定位后并集）
    范围       user_id BETWEEN 1 AND 9  → 多片（按算法计算命中区间）
    无分片键   created_at > ...         → 广播（全分片）
    表达式     order_id + 1 = 501         → 纯常量运算，部分实现可推导
                                          → 单片（推导能力因实现而异，待核证）
               order_id = user_id + 1     → 含其他列值，执行前未知
                                          → 广播（坑表）
  输出：RouterResult（路由类型 + 命中分片集合）
```

### How：路由的三条分支——S 的三种命运

```text
SELECT * FROM order WHERE order_id = 500
  └─ 等值 → 单片：order_id=500 → %8 → 4 号片
     ├─ 代价最小：单分片 IO，结果天然正确

SELECT * FROM order WHERE order_id IN (1, 100, 999)
  └─ IN → 多片：1→1 号片、100→4 号片、999→7 号片
     ├─ 3 片并发执行（若多个值路由到同片，由改写引擎合并执行，L4）

SELECT * FROM order WHERE amount > 100
  └─ 无分片键 → 广播：8 片全查
     ├─ 放大倍数 = 分片数（shard-03 展开代价）
     ├─ 归并引擎兜底排序/分页（L5）
     └─ 广播本身不错——错的是"以为没广播"
```

> 注意路由的一个边界：**WHERE 条件形状决定路由，但"每片执行什么"由改写决定**。路由只回答"去哪"，不回答"去了怎么干"。

### Transfer：解析/路由的模式可迁移

1. Redis Cluster：客户端算 CRC16 取模定位 slot（没有解析——KV 无 SQL 语义，路由直接可算）。
2. ES：查询 DSL 解析 → shard 路由（routing 值或广播）——DSL 结构化，天然可路由。
3. 编译器：AST 是无数下游（类型检查、优化、代码生成）的公共接口——**解析的价值不在于解析本身，而在于为下游提供结构化语义**，中间件同理。

本层留下的新账：**路由说了"去哪"，但每片执行的 SQL 还没定：表名还是 order 不是 order_3；`AVG(price)` 每片直接算还是改写；排序分页要不要补列？** 下一层看改写引擎——正确性边界。

### Level Ending

```text
口诀：解析出语义，路由看形状；等值单片，IN 多片，无键广播。
```

<a id="level-4"></a>

## Level 4：改写引擎——正确性边界

一句话认知墙：**改写引擎把"全局语义的 SQL"翻译成"每片能执行且结果可归并的 SQL"——表名改写、补列、AVG 改写是正确性改写（不这么做结果就错），去重是优化改写（不这么做重复执行）。**

### 前置知识关卡

- [ ] 知道路由结果（L3）
- [ ] 知道各片 AVG 不能简单平均（L1 的机制推导）
- [ ] 知道全局排序 ≠ 局部排序合并（L1）

### Why：为什么"改写只是换表名"是错的

**徒弟**：

> 改写不就是把 order 换成 order_3 吗？加个字符串替换的事。

**老陈**：

> 表名改写只是最浅的一层。改写的本质是**保持语义的翻译**：把"单库语义的 SQL"变成"每片执行、结果能归并的 SQL"。有三类改写不做，结果就错；还有一类不做，性能就浪费：

```text
① 聚合语义失效（正确性）
   SELECT AVG(price) FROM order   （全局平均）
   各片算 AVG 再平均 ≠ 全局 AVG（各片行数不同，机制推导）
   → 改写为：SELECT SUM(price), COUNT(price) ... 每片执行
   → 归并时 SUM/COUNT 后再相除（聚合归并，L5）

② 排序语义失效（正确性）
   SELECT user_id FROM order ORDER BY id LIMIT 10  （全局前 10）
   分片内要排 id，但 select 里没有 id（结果集缺排序键，归并无法排）
   → 补列：SELECT user_id, id FROM order_3 ... （补 id 进查询）
   → 归并按 id 排序后取前 10（排序归并，L5）

③ 重复执行（性能）
   SELECT * FROM order WHERE order_id IN (1, 9)
   1 % 8 = 1、9 % 8 = 1 → 两个值都路由到 1 号片
   不去重 = 对 1 号片执行两条相同 SQL → 重复执行浪费
    → 去重：多个值命中同一片时合并为一个 IN 条件一次下发
      （WHERE order_id IN (1, 9) 只下发一次，而不是对该片
      执行两条等值 SQL——优化改写）
   （注意：各片返回的行天然互斥，不存在"同一行重复返回"）
```

### What：改写引擎的四种核心改写

```text
① 表名改写（逻辑表 → 物理表）
   order → order_0 ~ order_7（路由命中的片才改写）
   广播路由 → 8 条 SQL，每条对应一个物理表

② 补列（为归并补充必要信息）
   场景：ORDER BY/GROUP BY 的列不在 SELECT 中
   改写：把排序/分组键补进 SELECT（结果集携带排序键才能归并）
   为什么必要：归并引擎要按排序键排，结果集里没有就排不了（机制推导）

③ 聚合改写（AVG → SUM + COUNT）
   AVG(x) → SUM(x), COUNT(x)
   为什么必要：全局 AVG = 全局 SUM / 全局 COUNT，
   而 8 个局部 AVG 的平均 ≠ 全局 AVG（各片行数不同，机制推导）
   注意：SUM/MAX/MIN/COUNT 各片可独立算、归并时直接合并，无需改写
   （MAX/MIN 归并取最大/最小，SUM/COUNT 归并直接相加——机制推导）

④ 去重改写（优化改写，非正确性改写）
   场景：IN 多值路由到同一物理片（如 order_id IN (1, 9)，1 和 9
     都 %8=1 → 同片命中两次）
   改写：同一分片命中的多次等值条件合并为一个 IN 条件一次下发
     （WHERE order_id IN (1, 9) 只下发一次，而不是对该片
      执行两条等值 SQL）
   为什么必要：避免对同一分片重复执行相同 SQL（执行效率，
     不影响结果正确性——各片返回的行天然互斥）
```

### How：三条 SQL 在改写引擎里的命运

```text
SQL A：SELECT user_id, amount FROM order WHERE order_id = 500 ORDER BY amount LIMIT 5
  改写结果（4 号片）：
  表名改写：order → order_4（amount 已在 SELECT 中，无需补列）
  → SELECT user_id, amount FROM order_4 WHERE order_id = 500 ORDER BY amount LIMIT 5
  （ORDER BY amount 在分片内执行，归并无需排序——单片无需归并）

SQL B：SELECT user_id FROM order ORDER BY id LIMIT 10
  改写结果（8 片，每片一条）：
  补列：id 不在 SELECT → 补进
  → SELECT user_id, id FROM order_0 ~ order_7 ORDER BY id LIMIT 10
  归并：排序归并（8 片各 10 条 → 按 id 排序取前 10）
  注意：这是"每片取 10 条再归并"——深翻页会放大取数倍数
  （LIMIT 100000,10 的真相在 shard-03）

SQL C：SELECT AVG(price) FROM order WHERE created_at > '2026-01-01'
  改写结果（8 片，每片一条）：
  聚合改写 + 表名改写
  → SELECT SUM(price), COUNT(price) FROM order_0 ~ order_7 WHERE created_at > '2026-01-01'
  归并：SUM/COUNT 分别相加 → 全局 AVG = SUM(全局)/COUNT(全局)
```

### Transfer：改写的模式可迁移

1. 编译器 lowering：AST 保持语义地翻译成目标代码——**改写 = 语义保持的翻译**。
2. 数据库查询下推（pushdown）：把过滤/聚合下推到存储层，本质也是"改写"。
3. 所有"一份请求翻译成 N 份局部请求"的系统（分布式缓存、分片 MQ），**改写都是正确性边界**——改写错 = 结果错，这是中间件最危险的地方（也最值得测试覆盖，见实验①）。

本层留下的新账：**SQL 被改写成每片能执行的版本了，接下来怎么跑：8 片串行还是并发？连接什么时候释放？各片结果回来了，怎么拼成全局正确的结果？** 下一层看执行与归并。

### Level Ending

```text
口诀：表名是皮，聚合/排序是骨，去重省执行；改写错一步，结果错千里。
```

<a id="level-5"></a>

## Level 5：执行与归并——结果怎么拼回来

一句话认知墙：**执行段解决"并发与连接策略"，归并段解决"把各片结果拼回单库语义"——归并有五类，连接策略在"内存换连接"与"连接换内存"之间取边，选错会内存爆炸或连接耗尽。**

### 前置知识关卡

- [ ] 知道改写结果（L4）
- [ ] 知道广播 = 8 片结果都要拼（L2/L3）

### Why：为什么执行与归并需要专门机制

**徒弟**：

> 改写完了，把 8 条 SQL 发给 4 个库（每库 2 张物理表），结果拼起来不就行了？

**老陈**：

> 两个问题。第一，**8 条 SQL 是串行还是并发？连接什么时候归还？** 如果 8 片串行执行，广播查询慢 8 倍；如果 8 片并发，连接数暴涨。连接策略就是在这两难之间选边。第二，**结果不是"拼起来"就完了**——各片的结果集是局部的，`ORDER BY` 需要全局排序、`GROUP BY` 需要跨片分组、`AVG` 需要 SUM/COUNT 归并、`LIMIT` 需要全局截取。拼装本身是五种不同的算法。

### What：执行与归并的机制

```text
执行引擎（机制，参数名以官方文档为准）：
  并发：路由命中的分片并发执行（多分片场景）
  连接策略（版本语义变化）：
    4.x：静态配置二选一——
      内存限制模式：所有分片结果先载入内存，连接立即归还
        ——结果集小用这个（内存代价，大结果集 OOM 风险）
    连接限制模式：连接保持到归并完成，流式归并
      （游标逐行拉取，内存仅持有当前游标行，避免 OOM）
      ——结果集大用这个（连接代价，长事务/连接耗尽风险）
    5.x：自动化执行引擎，由 maxConnectionSizePerQuery 每次查询
      动态决策连接复用（同一查询内不同分片可混合）——
      机制思想不变：小结果集多用内存（参数调大）、
      大结果集保流式（参数调小），取舍方向一致（机制推导）
  取舍：内存换连接，还是连接换内存

归并引擎（官方文档公开的五类）：
  遍历归并：无排序/聚合，多片结果直接串联
  排序归并：ORDER BY → 各片已排好，多路归并（每片游标向前）
  分组归并：GROUP BY → 跨片分组聚合（实现是排序后归并，待核证细节）
  聚合归并：SUM/COUNT/MAX/MIN/AVG → 各片聚合值合并
  分页归并：LIMIT → 排序归并 + 全局截取（深翻页代价 shard-03）
```

### How：连接策略 + 三类归并走查

```text
场景：广播查询 COUNT(*)（8 片）
（以 4.x 的静态两种模式讲机制；5.x 由 maxConnectionSizePerQuery
 动态决策，取舍思想不变）

内存限制模式：
  8 片并发执行 → 8 个 COUNT 结果载入内存 → 连接全部归还
  → 聚合归并：8 个 COUNT 相加
  代价：结果集大时内存峰值 = 各片结果集之和

连接限制模式：
  8 片执行 → 连接保持 → 流式归并（聚合归并只需要 8 个值，几乎无内存）
  → 聚合归并后归还连接
  代价：归并期间连接被占用，高并发下连接池可能耗尽

——小结果集（COUNT/SUM）两种模式都轻松；大结果集（全量扫描）
必须连接限制模式（流式），否则内存先爆（机制推导）
```

```text
场景：广播查询 ORDER BY id LIMIT 10（8 片）

执行：8 片并发，每片先做局部排序取前 10（改写已补 id 列）
归并：排序归并
  8 个游标（每片结果已按 id 排好）→ 多路归并取出全局最小的 10 个
  流式：取完 10 个即停，不需要载入全部（机制推导）
```

```text
场景：广播查询 GROUP BY user_id, SUM(amount)

改写：每片 SELECT user_id, SUM(amount) GROUP BY user_id（8 份）
归并：分组归并
  同一 user_id 可能散在 8 片 → 归并时要按 user_id 汇总 8 片的值
  实现：排序（按 user_id）后归并（跨片合并同组）——细节待核证
  代价：group by 的基数越大，归并内存/CPU 越大（机制推导）
```

### Transfer：执行/归并的模式可迁移

1. MapReduce：map（分片执行）→ shuffle（跨片分组）→ reduce（聚合归并）——分组归并就是 shuffle+reduce。
2. 流式处理（Kafka Streams）：partition 并行 + 聚合窗口，同构。
3. 所有"并行执行 + 结果汇总"的系统，都面临同样的两难：**结果先在内存攒齐（内存限制）还是流式边取边合（连接限制）**——大数据系统的 streaming vs batch 是同一枚硬币。

本层留下的新账：**链路全通了，但"中间件形态"还没定：它住在应用进程里（JDBC 层）还是独立服务（Proxy 层）？连接数怎么算？事务边界在哪个层？** 下一层是架构选型与生产决策。

### Level Ending

```text
口诀：执行定并发，归并拼语义；小结果内存，大结果流式。
```

<a id="level-6"></a>

## Level 6：架构选型与生产——JDBC 层 vs Proxy 层

一句话认知墙：**JDBC 层内嵌应用（无网络跳、本地事务、Java only），Proxy 层独立服务（协议兼容、集中管控、多一跳网络）——选型取决于语言栈、管控需求和事务边界。**

### 前置知识关卡

- [ ] 知道五段链路（L2）
- [ ] 知道本地事务 = 单连接原子性（springboot-05 L6.4）
- [ ] 知道跨片事务的账（shard-01 L4）

### Why：为什么中间件有"两层"形态

**徒弟**：

> 五段链路讲完了，那中间件装在哪？直接塞进应用里，还是单独部署一个服务？

**老陈**：

> 这是"切分点"的选择——把五段链路放在进程内的哪个位置。**放进应用进程**，就是 JDBC 层形态（每个应用实例内置一套解析/路由/改写/执行/归并）；**抽成独立服务**，就是 Proxy 层形态（所有应用连同一个"统一检索台"）。两个形态各有结构性代价，不是"一个是另一个的简化版"。

### What：两种形态的机制对比

```text
JDBC 层（应用内嵌）：
  接入：应用连 ShardingSphere-JDBC 数据源（替代普通数据源）
  链路：五段链路跑在应用进程内
  连接：应用直连 4 个分片库（中间件管连接池，同库 2 表共用连接）
  事务：本地事务 = 单连接原子性（springboot-05 L6.4）；
        跨片 = 分布式事务（distributed-tx 主题，planned）
  语言：Java 生态专属（JDBC 规范）

Proxy 层（独立服务）：
  接入：应用连 Proxy（MySQL 协议兼容，任何语言）
  链路：五段链路跑在 Proxy 进程内
  连接：Proxy 连分片库（应用只连 Proxy 一个端口）
  事务：应用和 Proxy 间也是网络事务；
        跨片 = 分布式事务（Proxy 可承接，机制同 distributed-tx）
  语言：语言无关（MySQL 协议）
```

### What：第三种形态与分片后的高可用

```text
Cluster 形态（治理模式）：
  机制：配置中心/注册中心托管规则与实例状态，规则变更动态生效
        （机制性描述，不承诺任何版本的治理细节）
  适用：Proxy 多实例场景的集中管控；JDBC 场景用得少

分片与副本是正交的两个维度——必须显式区分：
  分片 = 数据切分（本系列主线，解决容量/性能）
  副本 = 冗余（每个分片内仍是 MySQL 主从复制拓扑，复制语义不变，shard-00 L2）

分片后的高可用 = 分片复制拓扑 × 分片数量：
  N 个分片 × 每片（主 + 从）复制链路 = N 组独立的复制链路
  同分片内主从复制，跨分片无复制——一个分片的主挂了，只影响该分片

中间件自身的高可用：
  JDBC 层无状态：内嵌应用进程，随应用实例伸缩（无独立部署面）
  Proxy 层：可多实例部署，由治理中心协调（机制性描述）

数据迁移期间的新旧集群一致性：
  双写/校验/切流/回滚四件套（shard-04 L3/L4 的账）
```

关键区分：**分库分表不是高可用方案**——它解决容量与性能，副本冗余（每分片内的主从）才是高可用来源；两者正交，缺一不可。

### How：三个维度的取舍走查

```text
维度 1：语言栈
  Java 应用 → JDBC 层（原生接入，无额外网络跳）
  非 Java（Go/Python/Node）→ Proxy 层（MySQL 协议天然兼容）
  ——Proxy 的存在价值一半在协议兼容（跨语言视角展开）

维度 2：连接数与运维
  连接按库算，不按片算（同库 2 张物理表共用连接，基线见文首）
  JDBC 层：连接目标数 = 应用实例数 × 库数（每个实例对每个物理库维护一个连接池）
    100 个应用实例 × 4 库 = 400 个连接目标（池数量）
    实际连接数上限 = 目标数 × 数据源连接池大小（机制性公式：池上限按数据源配置评估）
    连接池在应用内，可观测性在应用侧
  Proxy 层：连接数 = 应用实例数 × 1（到 Proxy） + Proxy 实例数 × 库数
    数据库端只看到 Proxy 的连接（集中收敛）
    Proxy 是新的故障点（要独立部署/扩容/监控）

维度 3：事务边界
  两形态的"本地事务"都只覆盖单分片（机制推导）
  跨片事务无论哪层，都要分布式事务机制
  ——中间件形态不改变事务边界，只改变"账算在谁头上"
```

### 生产决策卡：中间件形态选型

| 场景 | 判断 | Code | 验收指标 | 风险 | 回链 |
| --- | --- | --- | --- | --- | --- |
| Java 生态、实例少、追求低延迟 | JDBC 层 | ShardingSphere-JDBC 数据源替代 | 无额外网络跳；本地事务可用 | 连接数随实例数线性涨；Java only | springboot-05 L6.4 |
| 多语言、集中管控、数据库连接收敛 | Proxy 层 | ShardingSphere-Proxy 独立部署 | 任意语言接入；连接收敛到 Proxy | 多一跳网络延迟；Proxy 单点/扩容 | shard-05（评估） |
| 实例数大（数百） | 计算连接预算 | 实例数 × 库数 × 每数据源连接池上限 vs 数据库 max_connections | 连接不超限 | 连接数爆炸（JDBC 层常见坑） | 坑表 |

### 参数机制（只讲机制与事故后果，参数名/默认值指向官网）

| 参数类别 | 机制 | 事故后果 |
| --- | --- | --- |
| JDBC 内核配置（模式/数据源/分片规则） | 模式（内存/集群）决定元数据与规则的分发与一致性；数据源池决定连接预算（按库，不按片）；规则（分片键/算法/绑定表/广播表）决定路由正确性 | 分片规则与历史设计不一致（改分片键/算法）→ 全量路由错位；连接预算（实例数 × 库数 × 每数据源连接池上限）超出数据库 max_connections → 连接等待/超时（机制推导，参数名待核证） |
| Proxy 实例参数 | Proxy 是独立服务：自身连接池、worker 线程、结果集缓存 | Proxy 连接池过小 → 请求排队放大延迟；结果集缓存过大 → Proxy 内存 OOM（机制推导，参数名待核证） |

### 生产坑与细节（本层速览，详见坑表）

```text
① 连接数爆炸：JDBC 层连接数 = 实例数 × 库数（按库不按片），实例扩容前先算账
② 广播查询悄悄发生：无分片键的 SQL 被广播，放大倍数 = 分片数
   （监控广播查询占比，shard-03 展开代价）
③ 归并内存：大结果集 + 内存限制模式 = OOM 风险（L5）
④ 深翻页：LIMIT 深偏移的取数倍数放大（shard-03 展开）
⑤ 本地事务边界：跨片写不是本地事务能兜的（distributed-tx 主题）
```

### Transfer：形态选型可迁移

1. Redis：客户端直连 vs Sentinel/Proxy（Predixy/Twemproxy）——同一个"内嵌 vs 独立服务"的二分。
2. MQ：客户端直连集群 vs 网关代理——同构。
3. 所有中间件的形态选型，本质是同一道题：**把链路放在进程内（省一跳、绑语言）还是独立服务（协议兼容、集中管控）**——两边各有一本账，选型不是比功能，是比账本。

本层留下的新账：**链路机制与形态选型都通了，但"每笔跨片查询到底多贵"还没算过账：广播放大多少倍、深翻页多取多少行、跨片 JOIN 能不能做、绑定表/广播表是什么？** 下一层（shard-03）给分布式查询算总账。

### Level Ending

```text
口诀：JDBC 内嵌省一跳，Proxy 独立通百语；连接数先算账，事务边界不靠层。
```

## 坑与细节

| 坑 | 后果 | 对策 |
| --- | --- | --- |
| 以为中间件是连接池，无路由键查询悄悄广播 | 放大倍数 = 分片数，DB 压力线性涨（shard-03 展开） | 监控广播查询占比，路由键必须出现在 WHERE |
| WHERE 中分片键等于列表达式（如 order_id = user_id + 1） | 列值执行前未知，中间件无法推导 → 降级为广播查询 | 分片键等值条件右侧用常量或参数（?），避免列表达式 |
| ORDER BY 的列不在 SELECT 中 | 归并无法排序，结果乱序 | 中间件补列（L4），但业务侧应显式带排序键 |
| AVG 直接在各片算再平均 | 结果错（各片行数不同） | 依赖改写引擎（L4），业务侧不手工拼 AVG |
| 大结果集 + 内存限制模式 | OOM | 大查询用连接限制模式（流式归并，L5） |
| JDBC 层实例数膨胀不控连接 | 数据库连接耗尽 | 连接预算 = 实例数 × 库数（同库多表共用连接），扩容前先算（L6） |
| 深翻页（LIMIT 100000,10） | 每片取 100010 行再归并丢弃，IO 放大 | 游标/键集分页（shard-03 展开） |
| 跨片事务用本地事务兜 | 数据不一致 | 分布式事务机制（distributed-tx 主题，planned） |
| 以为改写只是换表名 | 忽视聚合/排序改写的正确性与去重的执行合并 | 改写是正确性边界，测试覆盖改写日志（实验①） |
