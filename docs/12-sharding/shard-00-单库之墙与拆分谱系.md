# 🏛️ 单库之墙与拆分谱系：从"数据多了加机器"到"改变数据分布"

> 这不是一篇"分库分表概念科普"。
>
> 本文只追踪一个主线：**订单表 T 的一生**。T 出生在单库，业务一天天涨，T 先撞上数据量的墙，再撞上并发的墙；T 的主人尝试过升级机器、加缓存、加从库，全都没用；最后 T 被垂直拆分，拆完还在长大，又被水平拆成了 T_0..T_n。
>
> 本文回答的是拆分决策链的第一段：**墙长什么样、为什么优化单机治标、先拆什么后拆什么、什么时候根本不该拆**。
>
> 后续每篇只承接一个具体问题：分片键怎么选（shard-01）、SQL 怎么穿过中间件（shard-02）、跨片查询多贵（shard-03）、满了怎么扩（shard-04）、该不该用中间件/NewSQL（shard-05）。

# 🏷️ 关键词与主线进度

关键词：

```
容量墙 | 性能墙 | 垂直拆分 | 水平拆分 | 分库 vs 分表 | 分片键 | 读写分离 | 缓存 | 归档 | 决策顺序
```

主线进度：

```
① T 撞上容量墙 → ② T 撞上性能墙 → ③ 升级/缓存/从库治标 → ④ 垂直拆分 → ⑤ 水平拆分 → ⑥ 拆分谱系全景 → ⑦ 何时不该拆
```

系列基线：

> T 的拆分拓扑 = 分库分表 4 库 × 2 表（8 个物理分片：order_0~order_7，库 0~3 各持 2 片）。本系列"分片"指物理分片；连接按库算、路由按片算。（分库 vs 分表的代价差异见 L4；本系列后续 shard-01~05 默认按此基线展开）

## Level 1：单库为什么死——两堵不同的墙

一句话认知墙：**数据量增长和并发增长是两堵不同的墙，症状不同、瓶颈不同、对策不同。**

### 前置知识关卡

- [ ] 知道 InnoDB 是 B+ 树索引、数据页默认 16KB（MySQL 官方默认）
- [ ] 知道"连接"是数据库的硬资源（springboot-05 L1：连接池为什么存在）
- [ ] 知道事务 = 单连接原子性（springboot-05 L6）

### Why：把两堵墙混为一谈会误诊

**徒弟**：

> 数据库变慢了，不就是数据太多、机器不够吗？先加内存、加 CPU，不行就换 SSD，肯定能扛一阵。

**老陈**：

> "变慢"是症状，不是病名。你先回答一个问题：**是数据量涨了，还是并发涨了？** 这两个问题的物理瓶颈完全不一样，对策也完全不一样。混在一起，就是拿治感冒的药去治骨折。

### What：两堵墙各自的机制

**容量墙（数据量增长）**——瓶颈在"数据放不下、读不动"：

```text
B+ 树层级加深：数据页 16KB，主键索引每层能容纳的索引项有限
  层数 +1 → 随机点查多一次磁盘 IO（机制推导，与页大小、行宽有关）

页缓存命中率下降：buffer pool 大小固定，数据量超出后，热数据被冷数据挤出
  → 原本命中内存的查询开始落盘

备份/恢复窗口拉长：全量备份时间随数据量线性增长
  → 窗口内资源占用，业务高峰撞备份 = 事故

DDL 阻塞：大数据量表 ALTER 即使走 INPLACE/INSTANT（MySQL 8.0 官方算法），
  重构/拷贝类操作仍有资源与时间代价（具体行为以版本为准）
```

**性能墙（并发增长）**——瓶颈在"同时干活的人太多"：

```text
连接是硬资源：MySQL 8.0 默认 max_connections=151（官方默认值）
  → 连接耗尽 = 新请求直接失败，这是硬顶，不是"再等等就行"

锁竞争：同一行/间隙上的并发写互相排队；
  批量插入时 AUTO-INC 锁的持有时长与策略受 innodb_autoinc_lock_mode 控制
  （MySQL 8.0 默认为 2，采用轻量级互斥量，极大减少表级锁争用，
  但大批量 INSERT...SELECT 仍可能持有表级锁，具体行为以版本为准）
  → 并发上去了，吞吐不一定上去，延迟先上去

主库单点写：读写分离只缓解读压力，写仍集中在主库一个实例
  → 写的并发扩展性为零
```

| 维度 | 容量墙 | 性能墙 |
| ---- | ---- | ---- |
| 触发源 | 数据量增长 | 并发增长 |
| 典型症状 | 慢查询变多、磁盘涨、备份窗口长、DDL 慢 | 连接耗尽、锁等待、超时、CPU 飙高 |
| 物理瓶颈 | 索引层级、页缓存、磁盘 IO、备份 | 连接数、锁、主库单点 |
| 对策方向 | 改变数据分布（拆分/归档/分区） | 扩展执行能力（水平分库/NewSQL/读写分离辅助） |

### How：先诊断，再开方

```text
① 看监控：慢查询是集中在一张表（容量墙嫌疑），还是全局连接耗尽/锁等待（性能墙嫌疑）
② 看数据量：单表行数 × 行宽，估算索引层级（机制推导公式，不是经验数字）
③ 看 QPS 构成：读多写少 → 读写分离/缓存先上；写多 → 拆或 NewSQL
```

**徒弟**：

> 那两堵墙不能同时存在吗？

**老陈**：

> 能，而且大促前常见——数据量本来就大了，并发再一冲，两堵墙一起压。但诊断必须分开做：**先确认哪堵墙是主因**。因为它们的解药不同：容量墙的解药是让数据分布更广（归档、分区、水平拆分），性能墙的解药是让执行更并行（分片、读写分离）。开错药，拆了也白拆——比如把一张 10 万行的表拆成 8 份，除了把简单查询变复杂，什么都没解决。

### Transfer：墙的诊断法可迁移

1. Redis：内存涨（容量）vs 连接/命令阻塞（性能）——两堵墙，redis-01 事件循环讲的是性能墙。
2. MQ：存储涨（容量）vs 消费积压（性能）——mq-02 存储与 mq-06 扩容是两套账。
3. ES：索引体积涨（容量）vs 查询并发涨（性能）——es-06 容量边界。
4. 一切"系统变慢"的排查第一步都是分墙，而不是先加机器。

本层留下的新账：**墙确认了，那升级机器、加缓存、加从库不就能解决吗？** 下一层看为什么这些方案都治标。

### Level Ending

```text
口诀：容量看数据量，性能看并发量；先分墙，再开方。
```

## Level 2：为什么"更好的单机"治标不治本

一句话认知墙：**优化单机只能推迟两堵墙，不能拆除它们——因为这是数据分布的结构问题，不是参数问题。**

### 前置知识关卡

- [ ] 知道读写分离的主从延迟窗口（redis/mysql 复制语义）
- [ ] 知道缓存击穿/一致性（knowledge/redis 系列已有推导）
- [ ] 知道连接是硬资源（L1 已建立）

### Why：徒弟的三板斧各只解决一半

**徒弟**：

> 我常用的三板斧：加内存换 SSD（垂直扩容）、加从库读分离、Redis 缓存热点。这三招不够吗？

**老陈**：

> 每招都能解决一部分，但都留下一半。我们逐个过：

### What：三板斧各自的边界

**① 垂直扩容（更大更快的单机）**

```text
解决：性能墙的一部分（CPU/内存/磁盘 IO 更快）
留下：容量墙的备份窗口、DDL 阻塞问题依然在——机器再大，
  高增长业务下数据量迟早再次追上升级速度
物理上限：单机的内存总线、磁盘 IO、网络吞吐有上限；
  升级成本不是线性而是跳跃的（换档位贵）
```

**② 读写分离（从库扛读）**

```text
解决：读并发（性能墙的读方向）
留下：主库写仍是单点——写并发是性能墙最硬的部分；
  主从异步复制的延迟窗口（回链 redis-05：异步复制从库天然落后一个窗口；
  springboot-05：readOnly 是读写分离路由的标记）；
  主从延迟导致"读自己刚写的数据"读到旧值——业务语义问题
```

**③ 缓存（Redis 扛热点）**

```text
解决：读热点（性能墙的读方向，且只能打热点）
留下：写路径不变——写仍是单库；
  缓存一致性、击穿、雪崩、重建风暴（回链 knowledge/redis 系列）
  缓存是"读路径的减负"，不是"数据容量的扩容"
```

### How：三板斧的共同盲区

```text
三板斧全是"单机模型内的优化"：
  它们让同一个实例更快、读更分散，
  但没有改变"一份数据必须装在一个实例"这个前提。

数据量结构性增长 → 必须改变数据分布本身
  → 这是"把一份数据拆成多份"（拆分）与"让数据天然分布"
    （NewSQL）两条路的分岔口，先垂直后水平（L3/L4）
```

**徒弟**：

> 所以三板斧白用了？

**老陈**：

> 不是白用，是**顺序问题**。缓存、读写分离是低成本的第一个台阶，拆库是最后一个台阶。正确顺序是：先用尽单库模型内的优化，确认墙还在，才走拆分。跳级的人——表都没建好索引就分库——等于把简单问题复杂化（详见 L6 决策顺序）。

### Transfer：同样的"缓解 vs 结构解"模式

1. MQ 扩容：加消费者 ≠ 加分区（mq-06：并行度由分区数决定）——"加机器"是缓解，"改分区"才是结构解。
2. Redis 扩容：加内存 ≠ Cluster（redis-03：单机内存是容量墙，Cluster 是分布解）。
3. 负载均衡：加实例是缓解，改架构（异步化）是结构解。

本层留下的新账：**必须改变数据分布。那从哪一步开始拆？** 下一层看垂直拆分。

### Level Ending

```text
口诀：三板斧治标，分布治本；顺序先单机优化，后结构拆分。
```

## Level 3：垂直拆分——业务边界问题

一句话认知墙：**垂直拆分按业务模块拆库，解决的是"一个库装下所有业务"的耦合问题，不是数据量问题。**

### 前置知识关卡

- [ ] 知道跨库 JOIN 消失的后果（应用层聚合）
- [ ] 知道本地事务 = 单连接原子性，跨库失效（springboot-05 L6）
- [ ] 知道路由键 = 事务边界的思想（springboot-05 L6.4）

### Why：为什么先拆垂直

**徒弟**：

> 既然要改变数据分布，直接按行把订单表拆成 8 份不行吗？为什么还要先按业务拆库？

**老陈**：

> 因为订单、用户、商品、库存这几张表**业务上互相咬合**：查订单要带出用户信息，下单要扣库存。如果不先按业务边界拆开，直接按行分片，你会同时面对两个问题：跨片查询 + 跨业务域耦合，两个变量一起动，出了问题你都不知道是哪个引起的。**先拆业务，再拆数据**，每一步只引入一个新变量。

### What：垂直拆分解决什么、留下什么

**解决**：

```text
各库独立扩展（订单库扩容不影响用户库）
故障隔离（订单库抖动不拖垮用户库）
写并发分散（多库多写路径）
团队边界清晰（订单域/用户域各自拥有数据库）
```

**留下（拆分的第一次代价，这就是拆分的"账"）**：

```text
① 跨库 JOIN 消失
   JOIN 只能在应用层做：查两次 + 内存拼装
   → 出现 N+1 查询风险、冗余字段/宽表设计、查两次的一致性窗口
   （支线标注：OLAP 报表需要全量数据，跨库后报表要走独立数仓，
    是另一条因果链，不在本系列展开）

② 跨库事务失效
   本地事务 = 单连接原子性（springboot-05 L6）：
   两个库 = 两个连接 = 两套事务 = 没有统一协调者
   → 扣库存成功、改订单失败，无法回滚
   → 完整机制在 distributed-tx 主题闭环（planned，目录待建），
     本文只记这笔账：垂直拆分制造了跨库事务问题

③ 全局约束失效
   唯一索引、自增 ID 的全局唯一性开始出现缺口（预告 shard-03 L5）
```

### How：垂直拆分的执行顺序

```text
① 画业务边界：订单/用户/商品/库存各是一域（高内聚的写路径）
② 先拆"写路径"：每域自己的写事务留在域内
③ 再处理"读路径"：跨域读用冗余字段/应用聚合/宽表（回链 ddd 的
   读模型思想，但那是业务建模问题，此处是数据分布问题）
④ 验证门：每拆一库，跑通跨域查询链路，确认无漏网 JOIN
```

**徒弟**：

> 垂直拆分把墙切碎了，但订单表本身还在长大，这个怎么办？

**老陈**：

> 问对了。垂直拆分解决的是"一个库装下所有业务"的耦合墙；**单张核心表自己的数据量墙，垂直拆分拆不动**——订单表 2 亿行，不会因为用户库独立了就变小。这就是下一层：水平拆分。

### Transfer：垂直拆分 = 通用"先切边界"原则

1. DDD 限界上下文：先按业务边界划域，再谈内部建模（ddd-03）。
2. 微服务拆分：先按业务边界拆服务，再处理调用链（dubbo 系列）。
3. 模块化单体：先模块边界，后独立部署（ddd-06 决策）。

本层留下的新账：**业务边界拆完了，核心表的数据量墙还在。** 下一层看水平拆分。

### Level Ending

```text
口诀：先拆业务再拆数据；垂直拆耦合，水平拆容量。
```

<a id="level-4"></a>

## Level 4：水平拆分——数据量问题

一句话认知墙：**水平拆分按数据行分片，是唯一直接解决"单表数据量"的方案；分片键决定一切。**

### 前置知识关卡

- [ ] 知道分表 ≠ 分库（springboot-05 L6.4 已实测推导：同实例分表不破坏事务）
- [ ] 知道路由键 = 事务边界（springboot-05 L6.4）

### Why：分库和分表不是一回事

**徒弟**：

> 把订单表拆成 order_0、order_1……order_7 不就行了吗？这不就是分库分表？

**老陈**：

> 你已经踩中第一个坑了。**分表（同实例多张表）和分库（多实例）是两个不同的动作，代价完全不同**（回链 springboot-05 L6.4 的结论）：

### What：水平拆分的三种形态与代价差

| 形态 | 物理分布 | 事务 | 并发扩展 | 典型动机 |
| ---- | ---- | ---- | ---- | ---- |
| 水平分表（同实例） | order_0..7 在同一 MySQL | 仍走同一连接，本地事务有效 | 不扩展（同一实例） | 单表锁/IO 争用，数据量治理 |
| 水平分库（多实例） | order_0..7 在不同 MySQL | 跨实例 = 无统一协调者 | 扩展写并发 | 性能墙 |
| 分库分表（组合） | 库 × 表矩阵 | 单库内本地事务有效，跨库失效 | 双维度扩展 | 容量墙 + 性能墙同时存在 |

关键结论（承接 springboot-05）：**破坏事务的是分库，不是分表。**

### What：分片键为什么是四合一

水平拆分的核心问题是：**每一行数据凭什么决定自己落在哪个分片？** 答案是分片键（Sharding Key）——通常是一个业务字段（如 order_id / user_id），通过算法（MOD / HASH / RANGE，shard-01 展开）映射到分片。

分片键同时决定四件事（本文先立概念，shard-01 展开设计方法）：

```text
① 路由：这条 SQL 去哪几个分片（单分片还是全分片广播）
② 查询半径：WHERE 带分片键 = 只打一个分片；不带 = 广播全分片再归并
③ 事务边界：同一分片键的写 = 单分片本地事务；
   跨分片键的写 = 跨片事务（distributed-tx 主题）
④ 热点：分片键取值分布决定写是否均匀
```

### How：水平拆分制造了哪些新账

```text
① 跨片 JOIN / 跨片事务（最强约束：跨片 JOIN 直接在 SQL 层消失）
② 聚合查询归并（count/sum/order by/limit 要合并多个分片结果，shard-03）
③ 全局唯一约束失效（唯一索引只在本分片内唯一，shard-03 L5）
④ 分布式 ID（自增 ID 在分片下重复，shard-01）
⑤ 扩容 = 搬迁（分片数变化后路由变化，shard-04）
```

**徒弟**：

> 这么多代价，为什么还要水平拆分？

**老陈**：

> 因为它是**唯一直接解决"单表数据量"的方案**——归档能解决冷数据，分区表能解决单实例内管理，但"一张表装不下的数据量"只有拆成多份才能继续装。代价清单不是阻止你拆，是告诉你：**拆之前先确认墙真的存在（L1 诊断），拆之后每笔账都有对应的治理方案（shard-01~04）**。拆是负债，墙是债主，负债要付利息，但不借就是违约。

### Transfer：分片键四合一可迁移

1. Redis Cluster：slot = 分片键的哈希（redis-03），热点槽 = 热点分片。
2. Kafka：partition key = 分片键，决定顺序与局部性（mq-04）。
3. ES：routing = 分片键，决定文档落哪个分片（es 系列）。
4. 所有分布式存储的共同问题：**路由键决定局部性，局部性决定你能做什么、不能做什么**（redis-03 Transfer 已有同一结论：hashtag 与分库分表 sharding key 同为数据局部性的显式控制）。

本层留下的新账：**拆完了，业务代码里的 SQL 怎么知道去哪执行？难道手写路由？** 下一层看拆分谱系全景与两条技术路线。

### Level Ending

```text
口诀：分表不破事务，分库才破；分片键四合一，选错全盘错。
```

<a id="level-5"></a>

## Level 5：拆分谱系全景——先垂直后水平

一句话认知墙：**分库分表是一个谱系（垂直/水平 × 库/表），不是单一动作；顺序是因果：先垂直，后水平。**

### 前置知识关卡

- [ ] 理解 L3 垂直拆分与 L4 水平拆分各自的动机
- [ ] 知道 ShardingSphere 有 JDBC/Proxy 两种形态（概念级，shard-02 展开）
- [ ] 知道 NewSQL（TiDB/OB）概念：原生分布式存储 + 分布式事务

### Why：为什么说"分库分表 = 水平拆分"是神话①

**徒弟**：

> 面试里说"分库分表"，大家第一反应都是把一张表按行拆成多份。垂直拆分算分库分表吗？

**老陈**：

> 这就是本系列要破的第一个神话：**分库分表 ≠ 水平拆分**。它是一个 2×2 谱系。而且顺序有因果：跳过垂直直接水平，等于业务耦合未解就先付分片的代价——两个变量一起动，排障成本翻倍。**实际工程中垂直拆分常常被跳过，这是神话① 存在的土壤。**

### What：四象限全景

```text
                   拆 库（多实例）          拆 表（同实例多表）
垂直（按业务/字段）  垂直分库：订单/用户/商品  垂直分表：大字段拆出、
                   各自独立库              冷热字段分离
                   （业务边界，L3 已展开）    （字段级，使用场景少）

水平（按数据行）    水平分库：order_0..7      水平分表：order_0..7
                   在不同实例               在同一实例
                   （性能墙解）              （容量治理，不扩并发）
                   ←—— 分库分表组合：库 × 表矩阵，最常见
```

对应到比喻：

```text
垂直分库 = 按学科分馆（文学馆/科技馆）
水平分片 = 馆内按分类号分架（001~999）
分库分表组合 = 每个学科馆内都按分类号分架
```

### How：两条技术路线

拆完之后，"SQL 怎么知道去哪执行"有两条路线（本层只立路线图，细节在 shard-02/05）：

```text
路线 A：中间件分片
  ShardingSphere-JDBC（应用内，数据源代理）
  ShardingSphere-Proxy（独立代理，兼容 MySQL 协议）
  原理：解析 SQL → 路由 → 改写 → 执行 → 归并（shard-02 展开）
  特征：MySQL 不动，中间件在 SQL 层做文章

路线 B：NewSQL 原生分布式（TiDB / OceanBase）
  原理：存储层原生分片（Region），SQL 层透明；
       分布式事务原生支持（2PC/Percolator 等模型——TiDB 用优化版 2PC
       Percolator，OB 用 Paxos 强一致 + 分布式事务，
       与 distributed-tx 主题思想同构，实现细节各自文档为准）
  特征：无需中间件，但迁移 = 换存储引擎，运维栈变化
```

**徒弟**：

> NewSQL 不是把分库分表消灭了吗？

**老陈**：

> 这是神话⑦（shard-05 展开）。真相是：**NewSQL 内部就是"分片 + 分布式事务"，只是把它藏进了存储引擎**——你不再手写分片键，但 Region 分裂、热点、跨区事务这些问题一个不少，只是换了名字。消灭的是"手写中间件"，不是"分片机制"。理解本系列的机制，等于同时理解了 NewSQL 的地基。

### Transfer：谱系思维可迁移

1. 所有"拆"的决策都是 2×2 谱系：先问拆什么维度（业务/数据/字段），再问拆到什么物理粒度（实例/表）。
2. Kafka partition 扩容、Redis slot 重分、ES 分片再平衡——全是"先定切分维度，再定物理粒度"。

本层留下的新账：**谱系清楚了，那到底什么时候不该拆？** 下一层收口决策框架。

### Level Ending

```text
口诀：谱系四象限，先垂直后水平；中间件与 NewSQL 是同一机制的两张脸。
```

<a id="level-6"></a>

## Level 6：何时不该拆——决策框架

一句话认知墙：**拆是最后一步，不是第一步；不少系统根本不该拆，拆错比不拆更贵。**

### 前置知识关卡

- [ ] 理解 L1 两堵墙的诊断法
- [ ] 理解 L2 三板斧的边界
- [ ] 理解拆分代价清单（L3/L4）

### Why：为什么"遇到瓶颈就拆"是错的

**徒弟**：

> 那按您的意思，只要数据量涨了就该拆？还是说有个阈值，比如单表 500 万行就该拆？

**老陈**：

> 先说阈值：**任何"单表多少行该拆"的数字都是经验值，不是真理**。行数只是症状输入之一，真正要看的是 L1 的诊断：墙在不在、是哪堵。50 万行的热点行锁表也能拖垮全库，那是性能墙 + 索引问题，不是容量墙；2 亿行的冷数据表只要查询都走索引，不一定会死。**先问墙，再问数字。**

### What：决策顺序（从低负债到高负债）

```text
第 0 步：SQL 与表结构诊断（慢查询缺索引？大字段/冗余字段导致页分裂、
  容量墙提前到来？先修这个，成本最低）
第 1 步：归档冷数据（数据量治理的最低成本方案，冷热分离）
第 2 步：缓存（读热点，redis 系列知识）
第 3 步：读写分离（读并发，注意主从延迟语义）
第 4 步：垂直拆分（业务边界清晰时）
第 5 步：水平拆分（核心表容量墙确认时）
   ↑ 每一步都有验证门：墙消失了吗？没有才走下一步
```

### What：三类不该拆的信号

```text
① 墙不存在
   慢查询是缺索引/写错 SQL → 拆了也白拆，还把简单查询变复杂

② 跨片事务无法收敛
   业务写路径必须同时改多个分片键的数据，且无法用
   路由键收敛成单片事务 → 拆了之后每个写都是跨片事务
   （正确顺序：先回 distributed-tx 主题解决事务建模，再谈拆）

③ 团队没有迁移与治理能力
   分片是长期负债：SQL 改写、数据迁移、一致性校验、监控、
   回滚——没有这些能力，拆完的半年内会持续流血
```

### How：拆的不可逆性

```text
拆出去容易，拆回来难：
  数据迁回单库 = 全量搬迁 + 业务改造回退
  查询复杂度永久上升（每个 SQL 都要思考分片键）
  → 所以决策的门槛是"墙确认 + 负债可承受"，缺一不可
```

**徒弟**：

> 那 T 到底拆不拆？

**老陈**：

> 这就是本系列的完整主线：**先诊断墙（L1）→ 用尽单机优化（L2）→ 垂直拆边界（L3）→ 水平拆容量（L4）→ 每条 SQL 穿过中间件（shard-02）→ 每笔跨片查询付代价（shard-03）→ 满了搬迁（shard-04）→ 最后评估这条路 vs NewSQL vs 不拆（shard-05）**。00 篇给你的是决策的**顺序和门**，不是答案——答案在每一篇的机制里。

### Transfer：决策顺序可迁移

1. 微服务拆分：先模块边界验证，再拆部署（ddd-06 决策）。
2. 缓存引入：先确认读多写少，再上缓存（redis 系列）。
3. 任何"引入复杂度"的决策：**先确认问题存在，再评估负债，再动手**。

本层留下的新账：**决定拆了，第一件事是选分片键。分片键四合一（路由/查询半径/事务边界/热点），具体怎么选、选错什么后果？** 这就是 shard-01 的入口。

### Level Ending

```text
口诀：先诊断后开方，拆是最后一步；墙确认、债可扛，才动手。
```

| # | 坑 | 真相 | 级别 |
| - | - | - | - |

## 🏆 生产决策卡

## Decision Card 1：单库变慢，先做什么

### 场景

订单库最近慢查询变多、偶发超时，团队开始讨论分库分表。

### 判断

先分墙，再开方。按 L1 诊断：慢查询分布、连接数曲线、锁等待、数据量，确认是哪堵墙、哪张表，再决定是执行计划治理、归档、缓存、读写分离、垂直拆分还是水平拆分。分库分表是最后一步，不是第一步。

### Mechanism -> Decision

| 机制 | 工程决策 |
| ---- | ---- |
| 慢查询集中在单表，行数高 | 先查执行计划/索引 → 归档冷数据 → 再评估容量墙 |
| 连接耗尽/锁等待，写并发高 | 性能墙：评估拆分或 NewSQL，缓存/从库解不了写 |
| 读多写少，主从延迟可接受 | 读写分离（注意"读自己刚写的数据"语义） |
| 业务边界清晰，模块耦合高 | 垂直拆分先行 |
| 核心表仍在长大 | 水平拆分 + 分片键设计（shard-01） |

### Code

```text
诊断清单（伪代码，指标名按监控平台）：
  slow_query_by_table   // 慢查询按表分组
  connection_usage      // 连接使用率（与 max_connections 对照）
  lock_wait_count       // 锁等待
  data_size_by_table    // 单表数据量趋势
  qps_ratio             // 读/写比例
```

### 禁止决策

```text
不诊断直接拆库。
拿经验行数阈值当决策依据。
跳过单机优化（索引/归档/缓存/读写分离）直接拆。
```

### 验收指标

```text
slow_query_count（治理前后）
connection_usage
p99 latency
锁等待时长
（拆与不拆的对比数据见 knowledge/sharding/experiments）
```

## Decision Card 2：先垂直还是先水平

### 场景

团队确认要拆，争论先按业务拆库（垂直）还是先按行拆表（水平）。

### 判断

先垂直后水平。垂直拆的是业务耦合（跨库 JOIN/事务的账），水平拆的是单表容量；垂直拆完才能确认"剩下的墙是不是真的在单表上"。跳级 = 两个变量一起动。

### Mechanism -> Decision

| 机制 | 工程决策 |
| ---- | ---- |
| 多业务模块共用一库、跨域查询多 | 先垂直拆分 |
| 垂直拆分后单表仍在长大 | 再水平拆分 |
| 业务本来就单域、无跨域耦合 | 可直接评估水平拆分 |
| 跨片事务无法收敛 | 停止拆分，先回 distributed-tx 解决事务建模 |

### Code

```text
拆分顺序（伪代码）：
  step1: 识别业务域（订单/用户/商品/库存）
  step2: 逐域拆库，每步验证跨域查询链路
  step3: 监控核心表数据量，确认容量墙
  step4: 设计分片键（shard-01 方法论）后水平拆分
```

### 禁止决策

```text
业务耦合未解就直接按行分片。
垂直拆分与水平拆分同批上线。
```

### 验收指标

```text
跨域查询延迟（拆库前后）
核心表数据量趋势
跨片查询占比（拆分后应尽量低）
```

## 🌍 跨语言视角

<a id="cross-language"></a>

## Java

```text
ShardingSphere-JDBC 数据源代理：业务代码无感，SQL 层路由
数据源/连接池配置：库数 × 每库连接数 = 放大倍数（连接按库算，不按片算）
```

## Go

```text
无 ShardingSphere-JDBC 等价物（官方以 Java 为主）：
选择 ShardingSphere-Proxy（MySQL 协议兼容，语言无关）
或应用层自研路由（分片算法 + 多数据源，大厂主流选择）
或社区方案（ORM 生态的分表插件/钩子；能力、分库支持与维护状态
以各自仓库为准，多数仅覆盖表级分片）
```

## Rust

```text
同 Go：Proxy 或自研；
自研时注意：分片键解析必须在 SQL 执行前完成，禁止全分片广播兜底
```

## 跨语言仍成立的判断力

```text
拆是负债：任何语言下，迁移、校验、回滚成本都在。
```
