# 全文唯一比喻：跨馆借阅与馆际互借

延续本系列图书馆体系：分片是馆，分片键是分类号。本文讲**借书单（查询）在跨馆时怎么变贵**：

```text
读者不知道书在哪个馆                      ←→ 无路由键查询：广播所有分片
借第 100000 本之后的 10 本                 ←→ 深翻页：每馆先搬 100010 本
书在 A 馆、配套册在 B 馆                   ←→ 跨片 JOIN：关联数据不在同片
两本书约定放同一馆                        ←→ 绑定表：同分片键 JOIN 不跨片
每个馆都放一本工具字典                    ←→ 广播表：小表全分片复制
每馆图书编号只保证馆内唯一                ←→ 唯一索引 = 每片唯一，非全局唯一
```

| 图书馆 | 分布式查询 | 代价性质 |
| --- | --- | --- |
| 不知道书在哪个馆 | 广播查询 | 执行次数 × 分片数（线性） |
| 跨馆搬书凑页码 | 深翻页 | 取数 × 分片数 × 偏移（乘性） |
| 馆际互借 | 跨片 JOIN | 不可行，需改造 |
| 约定同馆 | 绑定表 | 同键 JOIN 退化为片内 JOIN |
| 每馆放字典 | 广播表 | 小表冗余 × 分片数 |
| 馆内编号 | 每片唯一 | 全局唯一性失效 |

## Level 1：为什么跨片查询要付代价——神话⑤"分片后 SQL 随便写"

一句话认知墙：**分片前 SQL 免费享受四种局部性红利（数据、索引、关联、唯一性），分片后每种红利都标了价——跨片查询的代价不是例外，是默认。**

### 前置知识关卡

- [ ] 知道无路由键查询 = 广播（shard-02 L3）
- [ ] 知道归并引擎（shard-02 L5）
- [ ] 知道分片键决定路由（shard-01 L1）

### Why：为什么"SQL 随便写"是神话⑤

**徒弟**：

> 分片只是把表拆成 8 份，SQL 不都一样吗？SELECT 还是 SELECT，JOIN 还是 JOIN，唯一索引还是唯一索引。中间件不是都处理了吗？

**老陈**：

> 中间件处理的是"翻译"，不是"魔法"。单库上一条 SQL 之所以便宜，是因为它享受四种**局部性红利**——分片之后，每种红利都要单独付账：

```text
单库 SQL 的四种局部性红利          分片后对应的账
① 数据局部性：数据在本地          无路由键查询 → 8 片全扫（广播，L2）
② 索引局部性：B+ 树在本地         深翻页 → 每片各取一截再拼（L3）
③ 关联局部性：JOIN 同库做         跨片 JOIN → 数据不在同片（L4）
④ 一致性局部性：唯一索引本地查     唯一约束 → 每片只管自己（L5）
```

> 记住一句话：**分片是把"数据库的局部性"换成了"路由的局部性"**——你得到了容量，但每条 SQL 都要重新确认它需要的局部性还在不在。

### What：四种代价的谱系

```text
代价谱系（从"贵"到"不可行"）：

① 广播查询：贵（线性）——执行 × 分片数
   代价 = 每片各跑一遍 + 结果归并
   还能用：监控住，低频可接受（shard-01 L4 的"接受广播"）

② 深翻页：更贵（乘性）——取数 × 分片数 × 偏移
   每片取 (offset+limit) 条，归并层持有 分片数 × (offset+limit) 条
   页码越大，账越贵（L3）

③ 跨片 JOIN：默认不可行（结构性）——关联数据不在同片
   默认配置下中间件不跨库 JOIN（5.x 的 SQL Federation 实验特性
   可执行部分跨片 JOIN，代价与成熟度待核证）
   工程上仍需绑定表/广播表/应用层改造（L4）

④ 全局唯一约束：失效（结构性）——唯一性检查在片内
   唯一索引 = 每片唯一，不是全局唯一（L5）
```

### How：用 T 的四条 SQL 感受代价谱系

```text
SQL 1：SELECT * FROM order WHERE order_id = 500      （带路由键，单片）
   → 付账：0 额外代价（数据、索引局部性都在）

SQL 2：SELECT * FROM order WHERE amount > 100        （无路由键，广播）
   → 付账：8 片各扫一遍 + 归并（数据局部性没了）

SQL 3：SELECT * FROM order ORDER BY id LIMIT 1000000, 10  （深翻页）
   → 付账：8 片各取 1000010 条 + 归并层持有 8000080 条（L3 展开）

SQL 4：SELECT * FROM order JOIN user ON order.user_id = user.id  （跨片 JOIN）
   → 付账：order 按 order_id 分片、user 按 user_id 分片，关联键不一致
   → 默认配置下中间件不跨库 JOIN（L4 展开）
```

### Transfer：局部性红利是通用框架

1. Redis Cluster：key 只在本地（数据局部性），跨 slot 的 MULTI 不可用（一致性局部性）——同一框架。
2. ES：跨 shard 的聚合 = 协调节点归并（广播的变体），routing 缺失 = 全分片扫。
3. 所有分布式存储的共同账单：**数据在不在本地、索引在不在本地、关联在不在本地、一致性在不在本地**——四问是通用的"查询代价清单"。

本层留下的新账：**四种代价的谱系有了，但每种代价的机制还没算清楚：广播到底放大多少倍？深翻页为什么那么贵？** 下一层从最常用的广播查询开始算账。

### Level Ending

```text
口诀：四种局部性，四种账；路由键在，账为零，路由键丢，账翻番。
```

## Level 2：广播查询——无路由键的线性放大

一句话认知墙：**无路由键查询 = 广播全分片再归并，执行次数与返回量都按分片数放大；广播写（UPDATE/DELETE）比广播读危险得多——它是写放大加部分失败风险。**

### 前置知识关卡

- [ ] 知道路由的三种结果（shard-02 L3）
- [ ] 知道归并引擎五类（shard-02 L5）

### Why：为什么"偶尔广播一次没事"是错的

**徒弟**：

> 广播查询就是慢一点嘛，8 倍而已，低频查询忍忍就过去了。

**老陈**：

> 广播的账不是"一次多慢"，而是**它是分片数的线性函数，且分片会越加越多**。今天 8 片忍忍，明年 32 片呢？更关键的是——广播不止有读，还有写。**无路由键的 UPDATE/DELETE 会广播到全部分片执行**：写放大 8 倍不说，如果执行到第 5 片失败，前 4 片已经改了，后 3 片没改——这是数据不一致，不是慢。

### What：广播的三种形态

```text
① 广播读（聚合类）：SELECT COUNT(*) FROM order WHERE amount > 100
   8 片各执行 COUNT → 归并相加
   放大：执行次数 × 8（IO/CPU 放大），返回量小

② 广播读（全量类）：SELECT * FROM order WHERE amount > 100
   8 片各全扫 → 归并持有 8 份结果集
   放大：执行 × 8 + 数据量 × 8 + 归并内存 × 8（内存放大）

③ 广播写：UPDATE order SET status = 1 WHERE amount > 100
   8 片各执行 UPDATE → 无法"归并"
   放大：写放大 × 8 + 部分失败风险（跨库部分没有原子性；
     同库 2 表能否合并在一个事务取决于中间件实现，待核证）
   ——这是事故级，不只是性能级（机制推导）
```

### How：广播的放大倍数推导

```text
放大倍数 = 分片数 N（机制推导）

读：执行次数从 1 变 N；扫描数据量从"命中行所在片"变"全部分片"
写：受影响行数从"命中行"变"N 份命中行"，且 N 次写没有原子性

例子（8 片，order 共 1000 万行，amount > 100 全局命中 100 万行）：
  带路由键单片：扫 1 片（125 万行），返回该片命中 12.5 万行
  广播查询：扫 8 片（1000 万行），返回 100 万行（每片 12.5 万的并集）
  ——执行的 IO 是 8 倍，返回量是"各片命中的并集"（行本身不重复）

例子（无路由键 UPDATE，命中 100 万行，8 片 = 4 库 × 2 表）：
  每片各改 12.5 万行，跨库部分无原子性
  第 4 片执行失败 → 前 3 片已改、后 4 片未改（机制推导）
  ——"部分成功"是广播写最危险的后果
```

> 注意一个容易误判的点：**广播读的返回行数不一定放大**（行本身不重复，只是每片都要扫）。放大的是"执行次数 × 每片扫描量"，不是"最终返回量"。但广播写的放大是实打实的写量 + 原子性风险。

### Transfer：广播模式可迁移

1. ES：无 routing 查询 = 所有 shard 都查（广播），协调节点汇总——同构。
2. Redis Cluster：MGET 跨 slot 的 key 要客户端分组逐批（广播的变体）。
3. 所有分布式存储的通用规律：**没有路由键 = 让系统替你做"不知道在哪"的代价**——要么接受线性放大，要么把键补上。

本层留下的新账：**广播是线性放大，账还算得清；但深翻页的账是乘性的——页码越大越离谱。** 下一层算深翻页的账。

### Level Ending

```text
口诀：无键必广播，读放大执行，写放大数据；广播写，先想清楚。
```

## Level 3：深翻页——取数倍数的乘性放大

一句话认知墙：**偏移分页在分片下的真相：每片取 (offset+limit) 条、归并层持有 N 份再丢弃——取数随 offset 线性增长再乘分片数；游标分页让每页代价恒定。**
> 实测回填：dev-lab/sharding-demo EX-04（ShardingSphere 5.4.1：offset=9000 每片下推 `LIMIT 0, 9020` 共 8 条物理 SQL（排序场景不做 UNION 合并）；keyset 每片 `LIMIT 20`；中位延迟 41ms vs 4ms，教学量级）

### 前置知识关卡

- [ ] 知道分页归并（shard-02 L5）
- [ ] 知道排序归并（shard-02 L5）

### Why：为什么"LIMIT 1000000, 10"在分片下是事故

**徒弟**：

> 分页不就是 LIMIT 吗？单库上 LIMIT 1000000, 10 有索引也就几十毫秒，分片后顶多慢 8 倍？

**老陈**：

> 慢 8 倍？你把账算反了。单库上 LIMIT 1000000, 10 虽然也要遍历并丢弃前 100 万条（单库深翻页也有开销，常用延迟关联优化），但**只需扫一份**；分片下呢？**每片都不知道全局的前 100 万条在自己这边占多少**，所以每片都得老老实实取 (1000000+10) 条交给归并层，8 片就是 8000080 条在归并层内存里排序——**这才是真相：8 倍扫描量 + 网络传输 + 归并层内存爆炸**。

### What：偏移分页 vs 游标分页的机制

```text
偏移分页（LIMIT offset, limit）——分片下的机制：
  改写：每片执行 LIMIT 0, offset+limit（把偏移抹平成"取前 offset+limit 条"，
    因为"每片的 offset"不等于全局 offset，片内偏移会取错）
  每片返回：(offset + limit) 条
  归并层持有：分片数 × (offset + limit) 条
  排序后丢弃前 offset 条，返回 limit 条
  总取数 = N × (offset + limit)   ← 随 offset 线性增长，再乘 N（机制推导）

游标分页（WHERE id > last_id ORDER BY id LIMIT limit）：
  每片执行：WHERE id > last_id LIMIT limit
  每片返回：limit 条（只取本片大于 last_id 的前 limit 条）
  归并层持有：分片数 × limit 条
  排序取前 limit 条 → 下一页的 last_id = 这 limit 条的最后一条
  总取数 = N × limit              ← 每页恒定，与页码无关（机制推导）
```

### How：两条 SQL 的取数对比

```text
场景：order 1000 万行，8 片，翻到第 10 万页（每页 10 条）

SQL A（偏移分页）：LIMIT 1000000, 10
  每片取 1000010 条 → 8 片 = 8000080 条进归并层
  排序 → 丢前 1000000 条 → 返回 10 条
  代价：800 万条数据的传输 + 归并层内存 + 排序
  ——返回 10 条，动了 800 万条（机制推导）

SQL B（游标分页）：WHERE id > last_id ORDER BY id LIMIT 10
  每片取 10 条（id > last_id 的局部前 10）→ 8 片 = 80 条进归并层
  排序取前 10 → 下一页 last_id = 第 10 条
  代价：80 条的传输 + 归并
  ——每页都是 80 条，第 1 页和第 10 万页一样贵（机制推导）
```

> 注意游标分页的前提：**排序键必须唯一且稳定**（id 主键天然满足）。如果按 amount 排序且 amount 有重复，last_id 无法唯一定位下一页的起点——这是游标分页的适用边界。

### 深翻页的三种解法

```text
① 游标分页（推荐）：WHERE id > last_id
   适用：顺序浏览（"下一页"场景），排序键唯一
   不适用：随机跳页（用户要直接跳到第 10000 页）

② 禁止深翻页：产品约束（只允许前 100 页 / 用"加载更多"替代页码）
   适用：C 端列表天然如此（用户不会翻 10 万页）

③ 接受代价：真的需要随机跳页 + 大数据集
   → 换存储也换检索语义：OLAP 引擎 / ES search_after（游标式）/
     物化快照——随机跳页在任何分布式系统都没有免费实现
     （ES 的 from+size 同样有 max_result_window 硬上限，见 Transfer）
```

### Transfer：分页机制可迁移

1. MySQL 单库其实也有深翻页问题（LIMIT 1000000 也要遍历丢弃前 100 万条），但只需扫一份；分片把"扫一份"变成"扫 N 份 + 网络传输 + 归并层内存"。
2. ES：from+size 深翻页同样爆炸，官方解法 search_after（= 游标）——同一机制。
3. MongoDB：skip 深翻页同理，官方推荐 range 查询（= 游标）——**"深偏移 = 全量重取"是所有索引系统的共同算术**。

本层留下的新账：**广播和深翻页是"慢"的问题，还有更硬的账：JOIN 在分片下直接不可行。** 下一层看关联的四种解法。

### Level Ending

```text
口诀：偏移翻页 = 每片全取再丢；游标翻页 = 每片只取一页；排序键要唯一。
```

## Level 4：跨片 JOIN——关联的四种解法

一句话认知墙：**JOIN 在单库是索引/哈希的本地运算，在分片下是"关联数据不在同片"的结构性问题——默认配置下中间件不跨库 JOIN（5.x SQL Federation 实验特性例外）；解法是让关联在同片发生（绑定表/广播表）或把关联移出 SQL（应用层/宽表）。**

### 前置知识关卡

- [ ] 知道分片键决定同片（shard-01 L1）
- [ ] 知道路由/归并（shard-02 L3/L5）

### Why：为什么"JOIN 照写"会撞墙

**徒弟**：

> JOIN 不是 SQL 的基本操作吗？order JOIN user 不是很正常？中间件不能把两边的数据都取回来在内存里 JOIN 吗？

**老陈**：

> "取回来在内存里 JOIN"——理论上可以，实际是灾难。order 按 order_id 分片、user 按 user_id 分片，两张表的关联键（user_id）和分片键不一致：**JOIN 需要的数据不在同一个分片里**。要 JOIN 就得把两边的数据全拉回中间件做内存 Hash Join——数据搬移量是两表命中行的全量级（网络传输 + 内存 Hash Join 的代价），比广播还贵。所以中间件的默认定位是：**不跨库 JOIN（官方不推荐；5.3.0 起 SQL Federation 实验特性可执行部分跨片 JOIN，代价与成熟度待核证）——工程上仍然把关联设计到同片内**。
>
> 注意基线的一个细节：4 库 × 2 表下，**同一库内两张物理表之间的 JOIN 本来就是 MySQL 的原生能力**——但"关联数据恰好落进同一库"不归分片键管，靠运气；绑定表才把"同片（进而同库）"变成保证。所以"不可行"说的是**跨库**，同库跨表 JOIN 可行但不可依赖。

### What：关联的四种解法谱系

```text
① 绑定表（官方概念）：
   两个表用相同分片键分片（order 和 order_item 都按 order_id）
   → 同 order_id 的数据必在同片 → JOIN 退化为每片内 JOIN
   → 8 个片内 JOIN 结果直接串联 = 全局 JOIN 结果（对等连接）
   适用：天然同键的父子表（订单/订单明细）
   代价：两表的分片键必须一致（设计时定死）

② 广播表（官方概念）：
   小表（配置表/字典表/地区表）全分片复制一份
   → 每片都有完整副本 → 任意键 JOIN 都在片内完成
   适用：小、低频更新、JOIN 频繁的表
   代价：写入要同步 N 份副本——跨片写无原子性（同 L2 广播写的账）；
   跨系统同步场景才涉及 Outbox（ddd-05）

③ 应用层关联：
   先按路由键查主表（单片）→ 收集外键集合
   → 按外键 IN 查询从表（多片）→ 内存里手工 JOIN
   适用：大表之间的关联（无法用绑定/广播表）
   代价：多一次查询 + 内存关联逻辑（代码复杂度）

④ 宽表/反范式：
   把 JOIN 要的字段直接冗余进主表（下单时写冗余列）
   适用：字段少、变化慢、查询高频
   代价：冗余一致性账（写放大 + 同步逻辑）
```

### How：绑定表为什么是"对等连接"

```text
场景：order JOIN order_item ON order.order_id = order_item.order_id

绑定表配置（官方概念）：order 与 order_item 都用 order_id 分片
  同一条 order_id = 500 的订单和明细，路由到同一个分片（机制推导：
  相同分片键 → 相同路由结果 → 同片）

执行（8 片）：
  每片：SELECT ... FROM order_3 JOIN order_item_3 ON ...
   （同序号物理表必同库，片内 JOIN = MySQL 原生同库 JOIN）
  归并：8 个片内 JOIN 结果串联 = 全局 JOIN（无跨片数据移动）
  ——放大倍数 = 1（关联没有额外代价，只有"本来就要扫的量"）

对比（非绑定表，order 按 order_id、user 按 user_id）：
  JOIN 数据分散 → 默认配置下不支持/无法执行
  （5.x SQL Federation 实验特性可执行部分跨片 JOIN，
   具体行为与代价待核证；同库跨表 JOIN 虽是 MySQL 原生能力，
   但关联数据是否同库不由分片键保证，靠运气）
```

> 绑定表的关键是**设计时对齐**：父子表的分片键必须在建模时就一致——这是 shard-01"路由键 = 事务边界"（springboot-05 L6.4 回链）在查询侧的镜像：**同片既是事务的边界，也是 JOIN 的边界**。

### Transfer：关联解法可迁移

1. ES：parent-child / nested 文档（同分片关联，= 绑定表思想）；宽字段（= 反范式）。
2. HBase：单行/单列族原子性，跨行事务要协处理器（= 应用层关联）。
3. 所有分布式存储的共同规律：**关联要么建模到同片（绑定/广播），要么移出存储（应用层/宽表）——"跨片 JOIN"在分布式存储里不存在免费版本**。

本层留下的新账：**广播贵、深翻页贵、JOIN 不可行——还有一笔更隐蔽的账：唯一约束在分片下静默失效，重复数据悄悄入库。** 下一层看全局唯一性。

### Level Ending

```text
口诀：JOIN 要同片，绑定表管父子，广播表管小字典，应用层管大表。
```

## Level 5：全局唯一约束——"唯一"在分片下失效

一句话认知墙：**唯一索引在分片下 = 每片唯一，不是全局唯一——唯一性检查是片内本地操作，跨片重复无法被数据库发现；全局唯一要靠分片键设计或外部协调。**

### 前置知识关卡

- [ ] 知道分布式 ID（shard-01 L5）
- [ ] 知道分片键 = 局部性（shard-01 L1）

### Why：为什么"唯一索引失效"是静默事故

**徒弟**：

> email 建了唯一索引，重复注册的 email 会直接报错吧？这有什么好担心的？

**老陈**：

> 在单库上会。但分片之后，email 的唯一性检查发生在**每个分片的 B+ 树里**——order_0 的邮箱唯一索引只管 order_0，它看不到 order_1 里的数据。两个用户用同一个 email 注册，user 表按 user_id 分片，他们散在不同的片——**每片都检查通过，全局却重复了**。数据库不会报错，重复数据静默入库，等你按 email 登录时才发现两个账号。这是最危险的一种失效：**不报错、不告警、只在业务侧暴露**。

### What：为什么唯一性在分片下失效

```text
唯一索引的机制（单库）：
  唯一性检查 = B+ 树插入时查重（本地索引，原子）

分片后的机制：
  唯一索引建在物理表上 → order_0 ~ order_7 各自维护自己的唯一索引
  检查范围 = 片内 → 跨片重复无法被发现（机制推导）

失效条件（机制推导）：
  ① 唯一键 ≠ 分片键 → 相同唯一键值的行可以散在不同片
  ② 唯一键 = 分片键 → 唯一键相同必同片 → 片内唯一 = 全局唯一（成立！）

——所以唯一性失效的本质：唯一键和分片键不是同一个键
```

### How：全局唯一的四种解法

```text
① 把唯一键变成分片键（最省，但受限）
   user 表按 email 分片 → email 唯一 = 片内唯一 = 全局唯一
   代价：email 可变（改邮箱 = 换片/重路由）、email 可能是热点
   适用：唯一键稳定、非热点的场景（如按手机号分片的用户表）

② 唯一键映射表（第二张表）
   email → user_id 的映射表，按 email 分片
   机制：映射表自身对 email 建立片内唯一索引
     （因为按 email 分片，片内唯一 = 全局唯一）
   注册时：先插映射表（靠唯一索引拦截并发重复，不能"先查后插"——
     两个相同 email 并发到达时先查都返回"不存在"，随后都插主表仍会重复）
     成功后再插用户表
   代价：多一张表 + 两表一致性（同事务或最终一致）
   本质：把"全局唯一约束"转成"以唯一键为分片键的表"（机制推导）

③ 外部协调器
   Redis SETNX / 分布式锁 / 独立数据库表
   注册时先抢占唯一键，成功才入库
   代价：外部依赖 + 锁的可用性/性能账
   适用：跨表跨系统的唯一键（如全局手机号池）

④ 全局 ID 兜底（主键唯一）
   主键唯一性用分布式 ID 保证（雪花/号段，shard-01 L5 回链）
   ——注意：这只解决"主键唯一"，不解决"业务字段唯一"（email）
   业务唯一键仍需 ①②③ 之一
```

### How：走查一遍"email 重复注册"的两种命运

```text
场景：user 表按 user_id 分片，email 建了唯一索引，8 片

命运 A（无额外设计）：
  用户甲 email=a@x.com → user_id=100 → 3 号片插入 → 片内查重通过
  用户乙 email=a@x.com → user_id=200 → 6 号片插入 → 片内查重通过
  → 两个账号入库，email 全局重复（机制推导：片内查重看不到其他片）

命运 B（唯一键映射表）：
  映射表按 email 分片 + 片内唯一索引：a@x.com → 2 号片
  用户乙注册：插映射表（2 号片，唯一索引拦截）→ email 已存在 → 冲突拒绝
  → 全局唯一成立（机制推导：映射表按 email 分片，
    email 相同的行必落同片，片内唯一 = 全局唯一；
    并发重复也由唯一索引拦截，不靠"先查后插"）
```

### Transfer：唯一性失效可迁移

1. Redis：SETNX 单实例才全局唯一，集群分片后要看 slot 路由（同 key 同 slot 才可靠）。
2. MQ：消息 ID 全局唯一靠生成器（雪花），不靠存储去重——去重要在消费侧幂等（mq-04 回链）。
3. 所有分布式系统的共同规律：**"全局唯一"要么靠"唯一键 = 分区键"让存储自己保证，要么靠"外部协调"让系统保证，要么靠"生成器"让生成保证——存储的本地唯一性在分片后自动降级为分区内唯一**。

本层留下的新账：**四种代价的机制都清楚了，但生产里怎么治理？每笔查询怎么判断自己付什么账、用什么手段？** 下一层把治理做成决策框架。

### Level Ending

```text
口诀：唯一键=分片键，存储自保证；否则映射表，或外部协调。
```

## Level 6：查询代价治理——生产决策

一句话认知墙：**分布式查询的代价不是"不可接受"，而是"必须显式管理"——每笔查询上线前用四问走查，选好治理手段，代价就可控。**

### 前置知识关卡

- [ ] 知道四种代价（L1~L5）
- [ ] 知道生产监控（shard-01 L6）

### Why：为什么治理要"显式"

**徒弟**：

> 代价我知道了，但生产里总不能每笔 SQL 都人工审查吧？

**老陈**：

> 不用每笔都审，但要给**查询分级**：带路由键的单片查询是"免费档"，不带路由键的是"付费档"，付费档必须有归属（哪个业务、什么频率、怎么治理）。四个问题问完，这笔查询属于哪个档、付什么账，就清楚了——**治理不是"禁止代价"，是"让每笔代价都有主人"**。

### What：四问走查表

```text
问题 1：有路由键吗？
  有 → 单片，免费档
  没有 → 广播档：频率多高？能不能加路由键/映射表？（L2）

问题 2：怎么分页？
  顺序浏览 → 游标分页（L3）
  随机跳页 → 约束页码 / 换存储 / 物化快照（L3）

问题 3：要 JOIN 吗？
  父子表 → 绑定表（同键分片，L4）
  小字典 → 广播表（L4）
  大表互关联 → 应用层关联 / 宽表（L4）

问题 4：有全局唯一约束吗？
  唯一键 = 分片键 → 存储保证（L5）
  否则 → 映射表 / 外部协调（L5）
  主键唯一 → 分布式 ID（shard-01 L5）
```

### 生产决策卡：跨片查询治理

| 场景 | 判断 | Code | 验收指标 | 风险 | 回链 |
| --- | --- | --- | --- | --- | --- |
| 低频无路由键读 | 接受广播，但登记 + 监控占比 | 查询白名单 + 广播率监控 | 广播占比有上限（如 <5%，阈值待实测） | 分片扩容后线性放大 | shard-01 L6 |
| 无路由键写 | 禁止上线（事故级） | 代码评审强制路由键检查 + 慢日志拦截无路由键 DML | 无路由键 UPDATE/DELETE = 0 | 部分失败不一致 | L2 |
| 列表分页 | 游标分页（顺序浏览） | WHERE id > last_id | 每页取数 = 分片数 × limit 恒定 | 随机跳页需求 | L3 |
| 父子表 JOIN | 绑定表（同键分片） | 建模时同分片键 | JOIN 放大 = 1 | 分片键设计时锁死 | L4 |
| 小字典 JOIN | 广播表（全分片复制） | 广播表配置 | 任意键 JOIN 片内完成 | 写放大 N 倍 + 跨片写无原子性 | L2 |
| 大表互关联 | 应用层关联 / 宽表 | 先主后从 IN 查询 | 无跨片 JOIN | 代码复杂度 | L4 |
| 业务字段唯一 | 唯一键映射表 / 外部协调 | email→user_id 映射表 | 重复注册拦截率 100% | 两表一致性 | L5 |
| 主键唯一 | 分布式 ID | 雪花/号段 | 全局不重复 | 时钟回拨/发号器单点 | shard-01 L5 |

### 参数机制（只讲机制与事故后果，参数名/默认值指向官网）

| 参数类别 | 机制 | 事故后果 |
| --- | --- | --- |
| 查询提示（Hint，显式指定强制路由/强制分片） | 绕过 SQL 条件推导，由业务显式指定这条 SQL 去哪个分片 | Hint 与 WHERE 实际条件不一致 → 路由到错片：查不到（静默丢结果）或改错片（数据错位）；Hint 是官方公开特性，参数形式待核证 |
| 分页参数（归并层取数/流式开关） | 控制分页归并的取数上限与流式归并行为 | 取数上限过大 → 归并内存爆炸；上限过小 → 深翻页结果被截断错乱（机制推导，参数名待核证） |

### 生产坑与细节（本层速览，详见坑表）

```text
① 广播写没有"归并"可兜底：部分失败 = 数据不一致（L2）
② 深翻页的放大是"取数"不是"返回"：10 条结果背后 800 万条搬运（L3）
③ 绑定表/广播表是设计期决策：分片后补 = 全量迁移（shard-04）
④ 唯一约束失效不报错：唯一性要有"检测手段"（巡检脚本/业务校验）
```

### Transfer：代价治理可迁移

1. 缓存：缓存键设计 = 路由键设计（先一致语义再命中率，redis 系列决策卡同构）。
2. MQ 分区：分区键 = 路由键，跨分区查询 = 广播（mq-04 回链）。
3. 所有分布式系统的共同治理观：**代价不可消灭，只能显式管理——把每笔操作的"账"写清楚（哪个业务、什么频率、付什么账、怎么降），系统才可演进**。

本层留下的新账：**查询的账算清了，但拆分还欠一笔更大的账：容量满了怎么办？取模扩容 = 大量搬迁，怎么迁才不丢数据、不闪断？** 下一层（shard-04）进入扩容迁移。

### Level Ending

```text
口诀：四问走查每一笔查询：路由键、分页、JOIN、唯一性；免费档单片，付费档有主。
```

## 坑与细节

| 坑 | 后果 | 对策 |
| --- | --- | --- |
| 无路由键 UPDATE/DELETE | 广播写：写放大 × 分片数 + 部分失败不一致 | 强制路由键检查，禁止无键写上线（L2） |
| 深翻页（LIMIT 深偏移） | 每片取 (offset+limit) 条再丢，10 万页动 800 万条 | 游标分页 / 产品约束页码 / 换存储（L3） |
| 普通表跨片 JOIN | 默认配置下中间件不支持（SQL Federation 实验特性除外），SQL 报错或无法执行 | 绑定表/广播表/应用层关联（L4） |
| 以为唯一索引全局唯一 | 跨片重复静默入库，业务侧才暴露 | 唯一键映射表 / 外部协调（L5） |
| 绑定表/广播表分片后补 | 改分片键 = 全量数据迁移 | 建模时定死同键分片（L4，shard-04） |
| 广播表更新 | N 份副本写入一致性账 | 低频更新才用广播表；同步走最终一致（ddd-05） |
| 应用层关联循环查 | N+1 查询放大 | 用 IN 批量收集外键一次查（L4） |
| 游标分页排序键不唯一 | 下一页起点错位，数据重复/丢失 | 排序键必须唯一稳定（id 主键，L3） |
| 查询提示（Hint）与 WHERE 条件不一致 | 强制路由到错片：查不到或改错片（静默） | Hint 只作兜底路由，上线前核对 Hint 与条件一致性（L6 参数机制） |
