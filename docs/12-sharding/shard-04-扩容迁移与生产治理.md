# 🚚 扩容迁移与生产治理：T 的搬迁与盘点

> 本文只追踪一个主线：**T 的搬迁与盘点**。shard-03 把跨片查询的账算清了，但 T 的容量墙还在——数据满了，得扩容。T 的主人以为"加两台机器，扩容就完成了"——结果发现：新机器上是空的，路由规则一改，一半订单的查询落空。分片之后，**扩容不是加机器，是给 T 搬家**；搬家不能停业，双写、校验、切流、回滚四件套缺一不可。分片前扩容是运维动作，分片后扩容是数据工程。

## Level 1：扩容 ≠ 加机器——神话⑥ 的破解

一句话认知墙：**加机器只是给路由增加了目标，数据不会自己搬家——扩容的真实成本是"路由重算之后，数据还在正确的位置上"。**

### 前置知识关卡

- [ ] 知道容量墙 vs 性能墙（shard-00 L1）
- [ ] 知道路由 = 分片键 + 算法的纯函数（shard-01 L1）
- [ ] 知道中间件把路由规则配在配置里（shard-02 L3）

### Why——为什么"加机器就行"是直觉陷阱

**徒弟**：

> 单库时代加从库、换 SSD 都立竿见影，为什么一分片，加机器就失灵了？

**老陈**：

> 因为单库时代"加机器"只做一件事：换更大的桶。分片之后，每一行数据都按路由规则贴在特定分片上——你加了新机器，但路由规则没有指向它。桶多了，书不会自己爬过去。

单库时代，加机器确实治标：加从库缓解读压力（shard-00 L2），升级硬件解容量。这套经验在分片后被带了过来：**T 满仓了 → 加两台机器 → 完了？**

不对。分片之后，每行数据的归属是路由算出来的：


order_id % 8 = 分片号（中间件配置里的规则，纯函数）


加一台新机器 = 中间件的路由目标多了，但**路由规则没有指向它**：新机器上是空的，旧数据还在旧分片里。更隐蔽的是：如果此时把分片数从 8 改成 16（否则新机器永远没有数据），路由规则一变，**一半的行按新规则算出的位置和实际存放位置对不上**——查询落空、写入错位，数据像"凭空消失"。

图书馆的比喻：扩建书架不叫扩容，**改索书号规则 + 把书搬到新位置才叫扩容**。加书架只是上半场，搬书才是下半场，而下半场的成本往往没人提前算。

### What——扩容的三个动机与三路选择

| 动机 | 症状 | 扩容对象 | 治不治得了 |
| --- | --- | --- | --- |
| 容量墙（数据量） | 单分片磁盘/索引层级涨 | 扩分片（库/表） | 治（但要搬数据） |
| 性能墙（写并发） | 单库写锁/连接耗尽 | 扩分片（分散写） | 治（但要搬数据） |
| 单点可用性 | 主库挂全挂 | 加副本（从库） | 不搬数据，但只缓解读、不解容量 |

扩容对象三路选择：

```
① 扩分片（MOD）：路由重算 → 大部分行搬家 → 本卷 L2 的账
② 加区间（RANGE）：新数据去新区 → 旧数据不搬 → 但旧区间继续扛热点（shard-01 L3 的账）
③ 加节点（一致性哈希）：只影响相邻节点 → 但分布不均 + 迁移不可控（redis-03 L2 已结的账）
```

### How——T 的仓库满仓，馆长的三个方案

T 的 8 片满了，馆长面前三个方案：

```
方案一（MOD 扩片）：8 片 → 16 片
  路由：order_id % 8 → order_id % 16
  代价：数据搬家（L2 算账）
  收益：容量 × 2，分布均匀（MOD 的旧账不犯的前提下）

方案二（RANGE 加区间）：加一个区间
  路由：区间规则加一行
  代价：零搬迁；但新数据全去新区，旧区间继续扛热点
    ——热点不均的账 shard-01 L3 结过：时间键/块状键的冷热
  收益：加区即扩容，且不惊动旧数据

方案三（一致性哈希加节点）：
  路由：环上加节点，只有相邻区间受影响
  代价：迁移不可控（redis-03 L2：无法精确指定搬哪些数据）
  收益：理论上迁移量最小，实操上没人敢在生产裸用
```

馆长的结论：**扩容的账，核心不在"加不加"，在"数据搬不搬、搬多少、怎么搬"**——本卷 L2 算第一笔，L3/L4 算第二笔。

### Transfer——这个思想还能迁移到哪里

1. **所有"扩容量"的系统都是"扩目标 + 搬数据"两件事**：Kafka 加分区要重平衡（mq-06）、ES 加索引要 reindex（es-05）、Redis 加节点要 reshard（redis-03）、MySQL 加分片要搬行（本卷）。加机器永远只是上半场。
2. **"目标变多了"和"数据到位了"是两回事**——凡是把"扩容"理解成"资源池变大"的，都会漏掉"数据重分布"这本账。

本层留下的新账：**MOD 扩片到底要搬多少？为什么 8→16 要搬一半、8→9 要搬九成？** 下一层算取模扩容的搬迁账——这次不引用结论，把公式从头推一遍。

### Level Ending

```text
口诀：加机器是上半场，搬数据是下半场；路由一变，数据不会自己跟过去。
```

## Level 2：取模扩容的搬迁账——为什么是 gcd

一句话认知墙：**MOD 从 N 片扩到 M 片，搬迁比例 = 1 − gcd(N,M)/max(N,M)——8→16 搬一半，8→9 搬近九成；这个公式不是背的，是从"不搬的数学条件"推出来的。**
> 实测回填：dev-lab/sharding-demo EX-06（SQL 实测 8→16：连续键子集 1 万行迁移 5000 行 = 0.5000，与公式一致；注意混入集中型键后比例会被数据分布稀释——先做分布审计再评估）

### 前置知识关卡

- [ ] 知道 MOD 路由：order_id % N（shard-01 L2）
- [ ] 知道映射表方案（shard-01 L4）
- [ ] 知道 RANGE 顺序键的冷热不均（shard-01 L3）

### Why——为什么行会"搬家"

**徒弟**：

> 8 片扩 16 片，order_id 是 8 的倍数那批行才要搬吧？毕竟 % 8 和 % 16 对它们不一样。

**老陈**：

> 恰恰反了——8 的倍数确实全搬，但搬的不止它们：% 8 = r 的行，在 % 16 下不是 r 就是 r+8，一半都得动。直觉"少数搬家"低估了一个数量级。

行不搬家，是**归属变了**。MOD 下行的位置 = order_id % 分片数。分片数从 8 变 16：

```
order_id = 9：  9 % 8 = 1 号片（旧）  9 % 16 = 9 号片（新）  → 搬
order_id = 8：  8 % 8 = 0 号片（旧）  8 % 16 = 8 号片（新）  → 搬
order_id = 0：  0 % 8 = 0 号片（旧）  0 % 16 = 0 号片（新）  → 不动
```

### What——公式的完整推导（为什么是 gcd）

shard-01 L2 给了结论，这里把"为什么"推完。先定义清楚问题：

```
行 key x 在旧规则下的位置：r = x mod N
搬与不搬的分界：新规则算出的片号 x mod M 是否等于旧片号 r
不搬 ⟺ x mod N = x mod M
```

把"不搬"翻译成同余条件：

```
设 d = gcd(N,M)，L = lcm(N,M) = N·M / d

x mod N = x mod M = r 等价于：
  x ≡ r (mod N) 且 x ≡ r (mod M)
⟺ x − r 同时被 N 和 M 整除
⟺ x ≡ r (mod L)，其中 r ∈ [0, min(N,M))
```

翻译成人话：**一个行不搬，当且仅当它在模 L（新旧分片数的最小公倍数）下，余数小于 min(N,M)**。模 L 的余数空间一共 L 个值，落在 [0, min(N,M)) 里的有 min(N,M) 个——键均匀分布时：

```
不搬比例 = min(N,M) / L = min(N,M) / (N·M/d) = d / max(N,M)
搬迁比例 = 1 − d / max(N,M) = 1 − gcd(N,M) / max(N,M)
```

代入几组（推导代入，不是实测）：

| 扩容 | d = gcd | L = lcm | 不搬 | 搬迁 | 直觉 |
| --- | --- | --- | --- | --- | --- |
| 8 → 16 | 8 | 16 | 8/16 | **1/2** | 幂翻倍也要搬一半，别以为不用搬 |
| 4 → 8 | 4 | 8 | 4/8 | **1/2** | 同上 |
| 8 → 12 | 4 | 24 | 8/24 | **2/3** | 非幂翻倍更惨 |
| 8 → 9 | 1 | 72 | 8/72 | **≈ 89%** | 互质 = 灾难 |
| 8 → 32 | 8 | 32 | 8/32 | **3/4** | 跨度大 = 更惨 |

规律：**gcd 越大搬得越少，互质几乎全搬；幂翻倍是"少搬"的特例，不是"不搬"**。

前提：**键在余数空间均匀分布**（连续递增键成立）。块状键会偏离——雪花 ID 低速率下余数恒 0、日期键的余数集中，实际搬迁行数可能严重偏离比例值（键取值形态的教训，shard-01 L3 已结）。

### How——三种方案的扩容走查

```
方案一（MOD 8 → 16）：
  搬哪些：x mod 16 ≠ x mod 8 的行（恰好一半，推导见上）
  搬法：逐片读旧数据 → 按新路由写入 16 片（L3 讲不闪断的搬法）
  代价：搬迁量 = 全量的一半；迁移期间新旧路由并存（L3）

方案二（RANGE 加区间）：
  搬哪些：零搬迁——新数据直接去新区
  代价：旧区间继续扛热点（shard-01 L3：顺序键的冷热不均）
    ——RANGE 的"扩容便宜"和"热点贵"是同一枚硬币的两面
  适用：时间维度的业务（日志/流水），接受最新区是热点

方案三（映射表扩容，shard-01 L4 的方案）：
  搬哪些：数据本身要搬，映射表每行也要重算归属/搬迁
  代价：等于"数据搬迁 + 映射表全量重写"两笔账
  ——映射表方案查询是两跳（先查表再路由），扩容也是最贵的两跳
```

### Transfer——这个思想还能迁移到哪里

1. **同余推理是"模空间扩容"的通解**——任何"取模定位"的系统（路由表、哈希取模的缓存分片），搬迁比例都能用"不搬 ⟺ 双模同余 ⟺ 模 lcm 的余数小于 min"推出来。记推导不记公式，任何 N、M 组合都能现场算。
2. **两级映射省掉的是"全量重哈希"，不是"搬数据"**：Redis Cluster 的 key→槽→节点两级映射，扩容时新增节点不需要重算 key 的槽号，但被迁移槽内的 key 数据仍要逐 key 搬迁（MIGRATE，redis-03 L5）——对比 MOD 的单级"数据→位置"直连：MOD 扩容连"哪些 key 不用搬"都要靠模空间重算。两级映射的收益是"重算范围可控"，不是"免搬"。

本层留下的新账：**搬一半的行，线上不能停机——怎么搬才不丢数据、不闪断？** 下一层讲双写迁移与影子表。

### Level Ending

```text
口诀：不搬当且仅当模 lcm 余数小；gcd 越大越省力，互质最惨九成搬。
```

## Level 3：双写迁移与影子表——不闪断的搬法

一句话认知墙：**搬迁的正确性不靠"停库搬完再开"，靠"双写 + 校验 + 切流 + 回滚"四件套——每一步都可验证、可回退。**（双写/影子表/位点衔接/校验/切流/回滚为业界通用迁移机制，本文描述机制，不承诺具体工具行为）

### 前置知识关卡

- [ ] 知道本地事务 = 单连接原子性（springboot-05 L6.4）
- [ ] 知道 CDC/消息回放的幂等与断点续传（mq-04）
- [ ] 知道槽位迁移的单 key 原子步骤（redis-03 L5）

### Why——为什么"停库搬完再开"是错解

**徒弟**：

> 停库搬完再开，简单、可控、没有中间态。双写那么复杂，还两套账，图什么？

**老陈**：

> 图"搬的时候新单写哪"有答案。停到凌晨两点，两点零一分的单丢哪去？更别提搬一半失败了只能重来。"搬"和"写"并存，是唯一让两者都不丢的答案——中间态不是复杂度，是安全区。

直觉方案：停写 → 全量搬 → 校验 → 开写。三个死穴：

```
① 停写窗口 = 业务不可用（SLA 直接违反；夜里停？凌晨也有单）
② 搬一半失败怎么办？（没有增量追平机制，只能重来，越搬越没底）
③ 搬完怎么证明没错？（"搬完了"和"搬对了"是两句话）
```

更细的死穴：**停库期间的新写入去哪了？** 任何"搬完再开"的方案都没回答这个问题——回答它的唯一方式，是让"搬"和"写"并存：这就是双写。

### What——双写的两种实现与位点衔接

```
① 双写：迁移期间，新写入同时落旧拓扑和新拓扑

   a. 应用层双写：业务代码里写两个库
      ——死穴：两个库 = 两个事务 = 无原子性（回链 distributed-tx）
         要么补偿要么对账，双写本身变成一个新的分布式问题
         （springboot-05 L6.4：本地事务 = 单连接原子性，跨库即失效）

   b. Binlog 订阅回放（CDC）：订阅旧库 Binlog → 回放到新库
      ——单源有序、不侵入应用；幂等/断点续传是工程题（mq-04）
         ——主流选择的原因：它把"双写"从应用问题变成管道问题
```

**位点衔接——"不重不漏"的成立条件：**

```
全量拷贝和 CDC 必须从同一个位点 P 出发：
  全量：从一致快照位点 P 起拷（拷的是 P 时刻的数据视图）
  CDC：从位点 P 起回放（P 之后的所有变更逐条补到新库）
起点晚了 → P 之后的变更有缺口（拷的旧视图没覆盖）
起点早了 → P 之前的变更重复回放（靠幂等兜底，mq-04）
```

影子表：全量复制一份数据到新拓扑，影子流量先打新拓扑验证——"先跑流量，不切流"：新路由规则是否正确、结果是否一致，先在影子流量里验证（ShardingSphere 影子库相关能力存在，具体机制待核证）。影子验证的是**机制正确性**，不是性能承诺——影子流量 ≠ 生产流量，吞吐/超时行为不同（机制性提醒）。

### How——T 的 8 → 16 搬迁时序（八步）

```
① 建新拓扑：16 个物理分片（空库/空表）
② 全量搬旧数据：逐片读 → 按 % 16 路由写入新片（并行 + 断点续传）
③ 增量追平：CDC 从位点 P 回放 Binlog 到新库
   ——② 和 ③ 同时跑：全量是"存量"，CDC 是"增量"，两者追平 = 迁移完成
④ 一致性校验：新旧逐行比对，零差异才算"搬对了"（L4 展开）
⑤ 读流量灰度：10% → 50% → 100%（L4 展开治理细节）
⑥ 写切换：低峰期，中间件规则从 % 8 切到 % 16（一次切，配回滚预案）
⑦ 观察窗口：切换后持续观察（唯一键冲突、丢失、延迟）
   ——期间旧拓扑仍靠反向 CDC 回灌维持写入，收尾才停
⑧ 收尾：确认稳定 → 停回灌 → 旧拓扑下线；异常 → 切回旧路由
```

时序图：

```text
时间轴（自上而下）：

旧拓扑(8 片)          CDC 管道            新拓扑(16 片)
────────────────────  ──────────────────  ────────────────────
持续写入 ──────────────┐
① 建新拓扑 ────────────┼──────────────────→ 16 个空分片
② 全量拷贝（位点 P 起）─┼──────────────────→ 存量数据写入
持续写入 ──────────────┼→ Binlog(P 起)
③ 增量回放 ────────────┼──────────────────→ 增量逐条补写
④ 追平 → 全量校验 ──────┼──────────────────→ 新旧逐行比对
⑤ 读灰度 10%→50%→100% ─┼──────────────────→ 读流量打新拓扑
⑥ 写切换（一次切）      ─┼─── 反向 CDC 回灌 ──→ 新写入全落新拓扑
⑦ 观察窗口             ←──── 旧拓扑仍收到写 ─┐
⑧ 停回灌 → 旧拓扑下线 ──────────────────────→ 新拓扑正式生产
```

关键机制：**旧拓扑一直写到收尾前（⑦ 观察窗口期间靠反向 CDC 回灌维持）**——所以回滚 = 切回旧路由，旧数据完整无缺（包括切换后新写入的那部分），不靠"新库数据可信"。

### Transfer——这个思想还能迁移到哪里

1. **迁移的正确性 = "新旧并存 + 渐进切换 + 可回退"**：与 redis-03 的槽迁移对比——Redis 用"单 key 原子步骤"（目标写 → 源删，任一时刻 key 在且仅在一端），MySQL 数据迁移用"全量 + 增量追平"（数据量级不同，原子粒度不同）。同一道题，两个量级的答案。
2. **与 mq-06 消费者重平衡同构**：迁移期"新旧两套并存、渐进收敛"是分布式系统变更的通律。

本层留下的新账：**四件套都做了，怎么证明"真的没差"？读流量灰度到多少才敢切写？** 下一层展开一致性校验与切流治理。

### Level Ending

```text
口诀：双写保不丢，位点定不重不漏；影子先验证，回灌保回滚。
```

## Level 4：一致性校验与切流治理——敢不敢上线的判据

一句话认知墙：**校验是迁移的"测试"，切流是迁移的"发布"——校验用漏斗式三档逼近"逐行一致"，切流用灰度/观察/回滚的纪律逼近"无损发布"。**（校验机制与切流步骤为通用工程实践，指标为机制性定义，不给死数字）

### 前置知识关卡

- [ ] 知道灰度发布的基本纪律（dubbo-08 生产治理）
- [ ] 知道广播查询是事故放大器（shard-03 L2）

### Why——为什么"行数一样"不等于一致

**徒弟**：

> 行数对得上，不就说明没丢数据吗？校验还分三档，是不是过度设计了？

**老陈**：

> 行数对得上只说明"没多没少"，不说明"没搬错"——同一行少个零、状态翻个转，行数一模一样。验收报告上的那句话必须是"逐行一致"，不是"大概齐"。三档不是过度设计，是把"大概齐"挡在门外。

行数一致只证明"数量对得上"，不证明"值对得上"：同一行新库少了 0.01 元、状态字段翻转过，行数一样。而且校验有漏网概率：抽样可能漏掉坏行，校验和（SUM/CRC）撞冲突的概率虽小但不是零。**"校验过"要说清楚是哪一档校验**——这是迁移验收里最容易糊弄的一环。

### What——漏斗式校验三档（算法机制）

```text
漏斗式：低成本先筛，高成本兜底——前两档便宜，用来把"明显不对"提前拦住；
全量逐行是最终依据，跑在最贵的那一格。

① 行数比对：新旧各片 COUNT 求和，两边总数相等
   机制：只证"数量"，筛掉大批搬漏/多搬
   漏洞：同一行值错，行数照样相等

② 校验和/SUM：按分片（或分桶）对关键列求和（或 CRC）
   机制：证"总量"——单桶内不同值恰好凑出同和的概率低但非零
   漏洞：撞冲突漏网（机制性提醒，不编概率数字）

③ 全量逐行：两边按主键排序 → 双游标单趟比对
   机制：两个游标各自从头走，主键小的那侧前进；
     相等则比对整行，不等即差异——单趟 O(M+N) 扫完
   分片并行：比对天然按分片隔离，每片独立比对互不影响
   依据：迁移验收的最终答案——不是抽样、不是校验和，是逐行
```

### What——切流四步的治理机制

```text
① 读灰度：10% → 50% → 100%，每档对照迁移前基线
   机制：比例由中间件路由规则控制（读流量按比例打新拓扑）
   每档观测窗口：报错率、慢查询、延迟三指标对照基线，异常即停

② 写切换：低峰一次切（中间件规则切换），不是"渐进写"
   机制：切换瞬间新写入全部落新拓扑；旧拓扑靠反向 CDC 回灌维持

③ 观察窗口：三组信号持续监视
   数据信号：唯一键冲突 = 双写期间有错位写入；对账差异 = 丢写
   性能信号：延迟涨、慢查询集中 = 新拓扑性能问题
   业务信号：业务侧对账/客诉 = 数据面没暴露的问题

④ 回滚：任何信号触发 → 切回旧路由
   （观察窗口内旧拓扑由反向 CDC 回灌维持写入，回滚无损）
```

### How——T 的验收指标（机制性定义，不给死数字）

| 验收项 | 机制性指标 | 通过判据 |
| --- | --- | --- |
| 全量校验 | 全量逐行零差异 | 不是抽样、不是校验和，是双游标逐行 |
| 读灰度 | 报错率/慢查询/延迟不升（对照基线） | 每档灰度都有观测窗口，异常即停 |
| 写切换 | 无唯一键冲突、无丢失、延迟不升 | 切换后观察窗口内持续满足 |
| 回滚预案 | 切回旧路由即可恢复 | 观察窗口内旧拓扑由反向 CDC 回灌维持写入（机制保证） |

### Transfer——这个思想还能迁移到哪里

1. **"所有迁移都是发布"**：迁移和发布共用同一套灰度/观察/回滚纪律——canary 发布、数据库迁移、中间件规则切换，本质都是"变更"，都要"可回退的渐进暴露"（dubbo-08 的"方向性 → 灰度 → 基线"同一条纪律）。
2. **校验的"漏斗"思想**：任何"验证一致性"的场景（数据迁移、对账、双写补偿）都要先定义"哪一档校验算数"——这是验收标准的第一句。

本层留下的新账：**迁移是一次事件，做完就完了。但生产里天天烧库的"无路由键查询"，为什么一到变更窗口就集中爆炸？** 下一层进入常态化的生产治理。

### Level Ending

```text
口诀：漏斗三档逼逐行，双游标单趟扫完；切流四步走灰度，回滚保平安。
```

## Level 5：无路由键查询治理

一句话认知墙：**扩容是一次事件，治理是常态——事故不是迁移带来的，是平时放任的广播/深翻页在变更窗口集中引爆。**（治理清单为工程实践，指标为机制性定义）

### 前置知识关卡

- [ ] 知道无路由键查询 = 广播（shard-03 L2）
- [ ] 知道"禁止无路由键写上线"的决策卡（shard-03 L6）
- [ ] 知道慢日志拦截作为兜底（shard-03 L6）

### Why——为什么变更窗口是事故高发期

**徒弟**：

> 迁移窗口出的事故，当然算迁移头上。这还有什么好说的？

**老陈**：

> 换个窗口，它照样炸。事故报告写"迁移导致"，根因是广播 SQL 一直在烧库——迁移只是把火烧旺了。今天不治理，明天发布也炸、后天大促也炸。

迁移窗口的配置切换（% 8 → % 16）会瞬间改变每条 SQL 的路由结果：**平时靠"路由键总是带上"才能压住的那批广播 SQL，在路由规则切换的瞬间，放大倍数、命中片数、连接分配全部重排**——存量问题（shard-03 的账：广播线性、翻页乘性、JOIN 不可行）不会因为迁移而消失，只会被变更窗口集中暴露。事故报告写"迁移导致故障"，根因其实是"存量广播 + 变更放大"。

窗口内至少三条机制在放大存量问题（机制推导）：

```
① 源库 IO 被占用：全量拷贝 + 双写占着源库 IO——平时能忍的广播/慢查询，
   在窗口内被推过临界点，慢变卡、卡变挂
② 新拓扑 buffer pool 全冷：切换瞬间命中率骤降，延迟尖峰——
   平时依赖页缓存"才不慢"的查询，冷缓存下原形毕露
③ 放大倍数翻倍：8 → 16 后，广播/深翻页的放大倍数直接翻倍（shard-03 的账）
   ——广播从 ×8 变 ×16，不是迁移的错，是存量 SQL 的账被重估
```

### What——治理五件套

```
① 慢日志拦截：无路由键的 DML 直接拦截（shard-03 L6 决策卡已立，落地为机制）
② 广播监控：监控广播查询的执行次数占比、耗时占比（相对基线，不给死阈值）
③ SQL 规范：WHERE 必须带分片键（评审门禁）
④ 路由预检：中间件层路由前检查（无路由键 → 告警或拒绝）
⑤ 发布门禁：上线 SQL 走评审，禁止无键写流入生产
```

### How——T 的治理走查

```
监控指标（机制性定义）：
  广播查询占比：执行次数占比、耗时占比，对照基线，异常即查
  单库 QPS 分布：路由是否均匀（扩片后 16 片是否都接到了流量）
  慢查询曲线：迁移前后对照（变更窗口的慢查询集中度）

告警机制：相对基线告警（不是死阈值）——广播占比翻倍、慢查询集中到单个分片，先查路由再查 SQL
```

### Transfer——这个思想还能迁移到哪里

1. **"变更窗口集中引爆存量问题"是运维通律**：es-05 reindex、mq-06 重平衡、Redis reshard——所有数据迁移都会在窗口内放大存量问题。治理不在迁移当天做，在平时的每一条 SQL。
2. **"事件治理 + 常态治理"二分**：一次性的迁移（事件）永远打不过常态的放任（状态）。生产系统的问题，大多数是"状态"不是"事件"。

本层留下的新账：**扩容的账全算清了——那什么时候根本不该拆？拆了之后遇到 NewSQL 是不是就该换？** 下一层（shard-05）做选型与边界评估。

### Level Ending

```text
口诀：迁移是一次事件，治理是日常状态；变更窗口不背锅，存量问题才是根。
```

## Level 6：四问走查与生产决策

一句话认知墙：**扩容决策四问——该不该扩（治墙优先）、扩什么（库/表/副本）、怎么迁（四件套）、敢不敢（验收指标）——四问过完才动工。**（决策框架为机制性结论，指标为机制性定义）

### 前置知识关卡

- [ ] 知道治标三板斧（shard-00 L2：垂直扩容/从库/缓存）与决策顺序（shard-00 L6：SQL 诊断→归档→缓存→读写分离→垂直→水平，拆分是最后一步）
- [ ] 知道扩副本不解容量墙（本卷 L1）

### Why——为什么先问"该不该扩"

**徒弟**：

> 满仓了就扩，早扩早安心，为什么要先问"该不该"？多一道门不是耽误事吗？

**老陈**：

> shard-00 结过的账：拆是最后一步。SQL 缺索引造成的慢，拆了也慢；归档能拖回"没满"的表，扩了白搬。先扩后治，是把治墙的钱花了两遍。

容量墙不等于"必须扩分片"：shard-00 L6 的决策顺序是先治墙——SQL 诊断（慢查询缺索引？先修这个，成本最低）、归档（历史数据挪走）、缓存（读放大压下来）、读写分离——这些都可能把"满了"拖回"没满"（shard-00 L2 的三板斧治标）。**扩容是最后一步，不是第一步**——和 shard-00 的结论同一条因果链：先诊断，再开方。

### What——四问走查表

| 问 | 判断 | 决策 |
| --- | --- | --- |
| ① 该不该扩 | 归档/缓存/冷热分离都做完了还满？ | 做完了才扩；没做完先治墙 |
| ② 扩什么 | 容量满 → 扩分片（库/表）；读压力 → 加副本；写并发 → 扩分片 | 副本不解容量墙（L1） |
| ③ 怎么迁 | MOD：四件套（双写 + 校验 + 切流 + 回滚；双写选 CDC、位点衔接是双写下的关键机制）；RANGE：加区零搬 | 应用层双写是最后选择（L3） |
| ④ 敢不敢 | 全量逐行零差异 + 灰度平滑 + 回滚预案就绪 | 任一不满足 = 不动工 |

### How——T 的扩容决策走查

```
场景：T 每片数据量逼近容量墙（归档/缓存已做）
① 该不该扩：归档做过、缓存做过 → 还满 → 扩
② 扩什么：容量墙 → 扩分片；8 → 16（幂翻倍，搬迁 1/2，L2 推导）
   ——对比：扩到 12 片搬迁 2/3 更贵，幂翻倍是 MOD 的"最不坏"路径
     （基因法场景的分片数 2 的幂约束，shard-01 L4）
③ 怎么迁：四件套八步（L3）；CDC 位点衔接 + 影子流量先验证 + 全量逐行校验（L4）
④ 敢不敢：逐行零差异、读灰度三档平滑、写切换后观察窗口无异常 → 收尾
```

### Transfer——这个思想还能迁移到哪里

1. **"四问走查"是任何容量类变更的通用框架**：加分区、加分片、换存储，先问"是不是真到墙"、再问"换哪个对象"、然后"怎么迁"、最后"凭什么敢"。
2. **"最不坏路径"思维**：MOD 扩容选幂翻倍不是因为不搬，而是因为"搬得最少"——没有免费午餐，只有成本排序。

本层留下的新账：**四问走查默认了"分库分表这条路是对的"。但真有业务该一开始就不拆、或者拆了之后该换 NewSQL 吗？** 下一层（shard-05）做选型与边界评估，给本系列收尾。

### Level Ending

```text
口诀：四问过完才动工——该不该、扩什么、怎么迁、敢不敢。
```

<a id="pitfalls"></a>

## 坑与细节（坑表）

| 坑 | 事故后果 | 防法 |
| --- | --- | --- |
| 加机器 = 扩容完成 | 新实例空库 + 路由不指向 → 流量打空、数据"凭空消失" | 扩容 = 扩目标 + 搬数据（L1） |
| 幂翻倍以为不用搬 | 8→16 实际搬一半（推导代入），窗口排期错 | 先推公式再排期（L2） |
| 互质扩容 | 8→9 搬 89%，等于重做一遍 | 分片数按 2 的幂规划（shard-01 L4） |
| 应用层双写当万能 | 两个事务无原子性 → 补偿/对账变成新工程 | 双写选 CDC（L3） |
| 全量与 CDC 位点不衔接 | 起点晚了有缺口、早了重复——数据不一致没被任何一步拦截 | 同一位点 P：全量从 P 起拷、CDC 从 P 起回放（L3） |
| 影子表流量 ≠ 生产流量 | 吞吐/超时行为不同，验证结论失真（机制性提醒） | 影子验证看机制正确性，不看性能承诺（L3） |
| "行数一样" = 一致 | 值不同照样漏 | 验收 = 双游标全量逐行零差异（L4） |
| 写切换当天切当天收尾 | 观察窗口为零，异常没时间暴露 | 观察窗口 + 反向 CDC 回灌维持旧拓扑（L4） |
| 存量广播不治理直接迁移 | 变更窗口集中引爆，事故报告甩锅给迁移 | 治理是常态（L5） |
| 映射表方案扩片 | 映射表全量重写 + 数据搬迁双账 | 立项时就评估扩容成本（L2） |
| 迁移工具并行度拉满 | 源库 IO 被打满，业务先于迁移挂掉（机制推导） | 并行度 = 源库负载预算（参数机制） |

## 生产决策卡

| 场景 | 判断 | Code | 验收指标 | 风险 | 回链 |
| --- | --- | --- | --- | --- | --- |
| T 满仓，归档/缓存已做 | 扩容分片（幂翻倍优先） | 中间件规则 8 → 16 | 逐行零差异；灰度平滑；可回滚 | 搬迁 1/2 + 窗口风险 | 本卷 L2 |

<a id="params"></a>

## 参数机制

只讲机制与事故后果，参数名/默认值指向官网（参数细节待 research 核证）。

| 参数类别 | 机制 | 事故后果 |
| --- | --- | --- |
| 迁移工具并行度/批次 | 并行度决定源库读取压力与迁移速度的交换 | 并行度拉满 → 源库 IO 被打满，业务先于迁移挂掉（机制推导）；批次过大 → 单批失败重放成本高 |
| 校验并发/批次 | 校验是"读全部 + 比全部"，并发是内存/IO 的交换 | 校验并发过大 → 校验期间业务延迟上升（机制推导） |
| 双写/影子窗口时长 | 窗口越长，验证越充分但故障面越大（双写期间两套拓扑都在写路径上） | 窗口过短 → 验证不足；过长 → 故障面长期双倍（机制推导） |
| 慢查询/广播监控阈值 | 阈值 = 相对基线的倍数，不是绝对数 | 绝对阈值在低峰误报、高峰漏报（机制推导） |

## 跨语言视角

| 语言/系统 | 对应实现 | 差异点 |
| --- | --- | --- |
| Redis Cluster | 槽迁移：单 key 原子步骤（目标写→源删） | 原子粒度 vs 全量+增量追平——同一道题两个量级的答案（redis-03 L5） |
| Kafka | 分区数只增不减 + 重平衡 | 数据不搬（日志追加语义），消费者重新分配（mq-06） |
| Elasticsearch | reindex：快照视角 + 增量补写 | 与 MySQL 同构：全量拷贝 + 增量追平 + 校验（es-05） |
| MongoDB | chunk 迁移 | 数据按 chunk 搬迁，同样是"新旧并存 + 渐进切流" |
| 一致性哈希 | 增删只影响相邻节点 | 迁移不可控是通病（redis-03 L2），槽位方案才解决"精确迁移" |
