# 🔀 Sharding 系列：从"数据多了加机器"到"改变数据分布"

**分库分表全链路：为什么存在（两堵墙）→ 分片键怎么选 → 中间件架构与一次 SQL 的生命 → 分布式查询的代价 → 扩容迁移与生产治理 → 选型与边界（何时不拆）。**

> 主线比喻：一座图书馆体系——一馆装不下（容量墙）、柜台排长队（性能墙）、按学科分馆（垂直拆分）、按分类号分架（水平拆分）、跨馆借书要馆际互借（跨片查询）、扩建搬家全馆重新上架（扩容迁移），六篇唯一比喻。业务主线：订单表 T 的一生，从出生单库到被拆成 T_0..T_n。

## 🧪 配套实验

可运行代码实验位于 [dev-lab/sharding-demo](https://github.com/imZhiYa/dev-lab)（EX-01~07 + SmokeApp，与每篇文章对应，CI 公审通过）：

- **EX-01 分片键分布**（shard-01 L3）：连续键取模 8 片均匀 vs 雪花低速率键集中 2 片（最大片 66.7%）
- **EX-02 路由与广播**（shard-02 L3）：带分片键 1 条物理 SQL 路由单片；无键广播 8 片（5.4.1 实测同库两片合并 UNION ALL 下推，共 4 条）
- **EX-03 改写引擎**（shard-02 L4/L5）：AVG→SUM+COUNT 下推；IN 同片合并 1 条、跨库拆分 2 条
- **EX-04 翻页代价**（shard-03 L3）：offset=9000 每片下推 LIMIT 0, 9020（线性放大）vs keyset 每片 LIMIT 20（恒定）
- **EX-05 跨片 JOIN**（shard-03 L4）：**5.4.1 实测无绑定 JOIN 不报错但静默丢数据**（期望 1000 行只回 260 行）
- **EX-06 扩容搬迁比例**（shard-04 L2）：SQL 实测 8→16 迁移 0.5000，与 gcd 公式一致
- **EX-07 连接预算**（shard-02 L6）：广播 8 片后仅 4 连接（连接按库算不按片算；上限 = 4 库 × 池大小 4 = 16）

## 🔑 核心主线

- **业务主线**：订单表 T 的一生——出生单库 → 撞容量墙/性能墙 → 单机优化全失效 → 垂直拆边界 → 水平拆容量 → 每条 SQL 穿过中间件 → 每笔跨片查询付代价 → 满了搬迁 → 选型评估（拆 vs NewSQL vs 不拆）。
- **唯一比喻**：一座图书馆体系——分馆=分片库、分类号=分片键、跨馆互借=跨片查询、扩建搬家=扩容迁移。
- **核心机制**：两堵墙（容量/性能）→ 垂直+水平拆分谱系 → 分片键四合一（路由/查询半径/事务边界/热点）→ 五阶段 SQL 生命周期（解析→路由→改写→执行→归并）→ 跨片查询三类代价（广播/翻页/JOIN）→ 搬迁比例 gcd 公式 → 双写+校验+切流+回滚四件套 → 四维选型矩阵。
- **版本纪律**：机制级结论（路由/改写/归并/搬迁公式）与实现级行为（ShardingSphere 5.4.1 实测）区分标注；实验全部基于 ShardingSphere-JDBC 5.4.1 + MySQL 8.0.36，跨版本行为差异需按版本复核。
