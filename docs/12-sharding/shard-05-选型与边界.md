# 🧭 路线评估与选型边界：T 的一生收官

> 本文只追踪一个主线：**T 的路线评估**。前五卷把分库分表的账全算清了——墙（shard-00）、键（shard-01）、SQL（shard-02）、代价（shard-03）、扩容（shard-04）。但"值不值得"这笔总账还没算。T 的主人想：拆都拆了，还能怎么办？可路由的每一道约束、跨片查询的每一笔放大、扩容的每一次搬迁，都是签过的借条。分库分表不是唯一出路——**先治墙、再拆分、后换装**：每一步都有边界，每一条路都要算账。本卷把前五卷的账汇成总账，给出路线评估的四维矩阵，给 T 的一生收官。

# 🏷️ 关键词与主线进度

关键词：

> 总账清算 | 治墙优先 | 替代方案边界 | NewSQL 选型 | 换装成本 | 四维矩阵 | 排除法选型 | 系列复盘

## Level 1：拆分的总账清算——五笔借条

一句话认知墙：**拆分不是免费的扩容——路由、改写、跨片、扩容、治理，前五卷各有一笔账；选型之前先清总账，收益是估算的，账是实签的。**

### 前置知识关卡

- [ ] 知道两堵墙与拆分谱系（shard-00 L1/L5）
- [ ] 知道分片键四维与算法家族（shard-01 L1/L2）
- [ ] 知道 SQL 五段链路与改写代价（shard-02 L2/L4）
- [ ] 知道跨片查询的放大与治理（shard-03 L2/L6）
- [ ] 知道扩容迁移与治理的账（shard-04 L2/L4）

### Why——为什么立项算收益，上线算成本，复盘算总账

**徒弟**：

> 都拆完半年了还算什么账？总账清不清，架构也不会变回去。

**老陈**：

> 总账不是为了变回去，是为了下一次选型。今天不清，下次扩容、下个新业务、下回技术评审，还是会拍脑袋选分库分表——因为没人记得它借了多少钱。

前五卷各算各的账，但决策需要一张总账：立项时只看见容量墙的收益（shard-00 L1），上线后才逐笔还债。**没有总账，选型就是重复上一次的拍脑袋**——这是路线评估存在的原因：先清算，再谈路线。

### What——五笔借条（每笔都标证据来源）

| 借条 | 账目 | 证据来源 |
| --- | --- | --- |
| ① 路由约束 | 每一行数据都贴死在分片键+算法上；键选错，分布/扩容/查询全错 | shard-01 L1/L3 |
| ② 改写复杂度 | SQL 五段链路里多了解析→路由→改写→归并四段；AVG 不能直接下推、同片 IN 要去重 | shard-02 L3/L4/L5 |
| ③ 跨片查询 | 广播线性放大、翻页乘性放大、JOIN 默认不可行、唯一约束降级为每片唯一 | shard-03 L2~L5 |
| ④ 扩容搬迁 | 加机器只是上半场；MOD 扩容要按 1 − gcd/max 搬数据，四件套（双写/校验/切流/回滚）才算搬完 | shard-04 L2/L3/L4 |
| ⑤ 治理成本 | 无路由键查询要监控/拦截/门禁；变更窗口集中引爆存量问题 | shard-03 L6、shard-04 L5 |

### How——T 的账目盘点

```
T 拆了半年，账目清点：
  ① 路由约束：order_id 曾以 % 8 钉死 8 片——扩容时搬一半（shard-04 L2 的账已付）
  ② 改写复杂度：AVG 订单额统计走了 SUM/COUNT 合并（shard-02 L5）
  ③ 跨片查询：后台对账 SQL 忘了带 user_id，全库广播（shard-03 L2 的账）
  ④ 扩容搬迁：8 → 16 的迁移四件套走完（shard-04 L3/L4 的账已付）
  ⑤ 治理成本：广播监控 + 无键写拦截门禁在跑（shard-04 L5）
```

### Transfer——这个思想还能迁移到哪里

1. **所有架构选型都该先算总账**：微服务化、缓存引入、消息队列——每一项都有"收益是估算的，代价是实签的"不对称。总账的作用不是否定选型，是让下一次选型有历史依据。
2. **"借条"思维**：架构决策的代价不会消失，只会推迟——今天没还的账，扩容/发版/大促时集中还。

本层留下的新账：**五笔借条摆在这，有没有"不拆"的路能把借条少签几张？** 下一层把治墙四招的边界划清楚。

### Level Ending

```text
口诀：收益是估算，账是实签的；选型先清总账，路线才有依据。
```

## Level 2：治墙优先——替代方案的边界

一句话认知墙：**shard-00 给了"拆是最后一步"的顺序，本层给"最后一步"之前每一步的边界与失效场景——顺序是流程，边界是判据。**

### 前置知识关卡

- [ ] 知道治标三板斧（shard-00 L2：垂直扩容/从库/缓存）
- [ ] 知道决策顺序（shard-00 L6：SQL 诊断→归档→缓存→读写分离→垂直→水平，拆分是最后一步）

### Why——为什么"满了就拆"是偷懒的决策

**徒弟**：

> 治墙四招 shard-00 讲过顺序了，这里又讲边界，不是重复吗？

**老陈**：

> shard-00 给了流程：先诊断再开方。但没给判据：归档治到什么程度算治好了？缓存什么时候不能上？读写分离的失效场景是什么？流程回答"先做什么"，边界回答"做到什么时候算完、什么时候换下一招"。没有边界的流程，每一步都走不彻底。

shard-00 L6 给了决策顺序，但"每一步的适用边界"没给全——顺序解决"先做什么"，边界解决"这一招治不治得了"。没有边界的顺序，会在某一招上无限拖：归档拖三年、缓存硬扛写多、读写分离被写后读打死——最后还是要拆，但晚了。

### What——四招的边界与失效场景（SQL 诊断是前置，不算招）

```
第 0 步：SQL 诊断（最便宜，永远先做——前置检查，不是四招之一）
   边界：慢查询缺索引、深翻页、大事务——这些是"代码病"，拆库治不了
   失效：诊断做完、索引加满，还是满 → 进入四招

① 归档/冷热分离（历史数据挪走）
   边界：冷热可分离（时间维度明确）、冷数据查询模式可迁移（走归档表/冷库）
   失效：冷数据被高频访问（归档后查询全打冷库）→ 热数据仍然大 → 进入②

② 缓存（读放大压下来）
   边界：读多写少、热点可枚举、一致性可接受（缓存与库的窗口差）
   失效：写多（缓存失效频繁）、一致性敏感（写后读必须准）、热点不可枚举 → 进入③

③ 读写分离（读压力再分一层）
   边界：读放大为主、主从延迟可接受（写后读可容忍窗口差）
   失效：延迟敏感业务（写后立即读、对账）→ 主从延迟被业务放大 → 进入④

④ 垂直拆分（模块级拆分，shard-00 L3）
   边界：模块边界清晰、跨模块事务少、联表可切断
   性质：与前三招不同——这是第一笔"拆分借条"：
     治了业务耦合墙，但签下了跨库 JOIN 消失、跨库事务失效的账
     （前三招是单机模型内的优化，④ 已是结构性改变）
   失效：跨模块事务多（拆了立刻撞分布式事务）、联表切不断 → 必须水平拆分（真到数据量墙了）
```

### How——T 的走查（假设 T 还没拆）

```
T 的单库满仓，走一遍边界：
  第 0 步 诊断：对账慢查询缺索引 → 加上，慢查询降下来
  ① 归档：2024 年前订单冷数据占比大且查询少 → 归档，热数据回到安全水位
  ② 缓存：商品详情读放大 → 缓存，读 QPS 压下来
  ③ 读写分离：订单列表读多写少 → 从库，读压力再分一层
  ④ 垂直拆分：用户/订单/支付模块耦合紧密、跨模块事务多 → 失效，切不断
  结论：到④才真到墙——此时拆，借条里没有"本可以治墙就解决的"那一部分
```

### Transfer——这个思想还能迁移到哪里

1. **"顺序 + 边界"是决策框架的完整形态**：任何分层决策（缓存穿透治理、限流降级、容量规划）都要同时有流程顺序和每步的失效判据——只有顺序会永远停留在第一步，只有边界会乱序。
2. **"失效场景先行"**：选型/治理方案的评估，先写它在什么场景下失效，再写它治什么——失效场景决定方案的边界，边界决定适用域。

本层留下的新账：**治墙四招都失效，真到墙了——两条路摆在面前：应用层分库分表，还是换 NewSQL？** 下一层把 NewSQL 的账算清楚（选型视角）。

### Level Ending

```text
口诀：顺序定流程，边界定判据；四招各有失效场，全失效才真到墙。
```

## Level 3：NewSQL 的账——选型视角

一句话认知墙：**NewSQL 把分片、重平衡、分布式事务做进存储内核——前四卷的应用层账被"内置化"了；但复杂度没有消失，只是从应用层搬进了存储层黑盒，代价换了个形式收。**

### 前置知识关卡

- [ ] 知道跨片事务在分库分表下无原子性（shard-00 L4 / shard-01 L4 / shard-02 L6 留账，完整机制 distributed-tx planned）
- [ ] 知道扩容搬迁的账（shard-04 L2）
- [ ] 知道路由 = 分片键 + 算法的纯函数（shard-01 L1）

### Why——为什么"NewSQL 全自动"会动摇分库分表

**徒弟**：

> 分片自动、事务全局、扩容自动搬——那我学 shard-01~04 干嘛？NewSQL 全包了。

**老陈**：

> 正因为全包了，你才更需要前四卷。判断 NewSQL 好不好的尺子，正是这四卷的账：它内置的分片要不要分片键？跨片查询有没有放大？扩容搬不搬数据？NewSQL 也躲不掉这些账，只是"谁付、什么时候付、能不能看见"变了。看不见的账，往往更贵。

NewSQL（TiDB 类）的卖点恰好精准命中了前四卷的每一笔账：分片键选择（shard-01）、跨片查询代价（shard-03）、扩容搬迁（shard-04）——这些账在 NewSQL 里被宣称"内置解决"。**如果连这四卷的账是什么都不知道，"内置解决"就只是营销词**——这是本层存在的意义：用前四卷的尺子量 NewSQL。

### What——NewSQL 解决什么（机制性描述，不承诺版本行为）

```
① 透明分片：路由不在应用层——SQL 不需要带分片键也能执行
   对照：shard-01 的"键必带"约束被内置化（机制性描述，具体行为待核证）

② 全局事务：跨片原子性内置
   对照：跨片事务无原子性的账（shard-00 L4 / shard-01 L4 / shard-02 L6 留账）被内置化

③ 自动重平衡：扩容时数据搬移由存储层自动完成
   对照：shard-04 的四件套（双写/校验/切流/回滚）被内置化
```

### What——代价换了个形式收（三笔）

```
① SQL 兼容边界：不是所有 SQL 方言/生态能力都完整支持
   机制性提醒：语法兼容 ≠ 行为兼容（锁、隔离级别、执行计划语义）
   ——评估方式：拿生产 SQL 全集做兼容性回归，而不是拿文档对照

② 运维模型：分布式存储的运维复杂度整体转移
   组件变多（协调层/存储层/调度层）、工具链重来（监控/备份/告警全换）

③ 性能不确定性：无分片键查询在 NewSQL 里也躲不开"扫多个存储节点"
   分片键的价值没有被消灭，只是从"应用层强制"变成"存储层建议"——
   键选得烂，NewSQL 一样慢（机制推导：数据分布决定访问分布，与谁执行无关）

   机制推导（穿透）：NewSQL 虽然不要求应用层传分片键，但数据依然按
   Region 类分片单位分布在多个节点上。查询条件没有命中主键/索引的前缀
   （相当于没有路由键）时，优化器依然生成全表扫描计划，下推到所有
   Region 并发扫——本质依然是广播，只是中间件不发 SQL 了，
   由存储层自己并行（机制性描述：具体执行计划细节以产品实测为准）
```

### What——NewSQL 不是银弹：内部也是分片 + 分布式事务

机制性事实：**NewSQL 内部同样是"分片存储 + 分布式事务"**——数据去哪个节点的路由决策、跨节点事务的协调成本，一个不少（机制性描述：与 shard-01 的路由思想同构、与两阶段/共识思想同构，distributed-tx planned）。

同构意味着前四卷的账没有消失，只是换了执行者：

```
分片键的均匀性 → 依然决定分布质量（shard-01 L1/L3 的账，执行者换成存储层）
跨片事务的协调成本 → 依然存在（distributed-tx planned 的账，执行者换成存储层）
扩容搬迁 → 依然要移动数据（shard-04 L2 的账，执行者换成存储层调度）
```

所以神话⑦"NewSQL 已杀死分库分表"只对了一半：**它杀死的是"应用层手工分片"，不是"分片"这件事本身**——分片、事务、搬迁的账一个没少，只是账本从应用层搬进了存储层。

### How——T 的对比走查

```
T 用前四卷的尺子量 NewSQL：
  ① 分片键：T 的 order_id 均匀连续——无论谁路由，分布好的键都不会更差（shard-01 L3 的结论照用）
  ② 跨片查询：后台对账的广播 SQL，在 NewSQL 里执行计划可能自动拆分发多节点
     ——但"扫全量"的账还在，只是从 SQL 广播变成执行计划跨节点（机制性提醒，待实测）
  ③ 扩容：8 → 16 的四件套变成存储层自动——但迁移窗口的 IO 占用、追平、校验
     一个都少不了，只是看不见（shard-04 的账照付，付款人换了）
  ④ 全局事务：T 若新增"跨片支付+订单"的强一致需求，NewSQL 内置事务是真实收益
      （分库分表下这是分布式事务账，distributed-tx planned）
```

### Transfer——这个思想还能迁移到哪里

1. **"内置化 ≠ 免费"是评估所有 PaaS/托管方案的第一原则**：托管 Kubernetes、云数据库、消息队列服务——复杂度从你的团队搬进厂商黑盒，账没消失，只是改成订阅费+看不见的风险。评估托管方案，要会用自建时的账本去问厂商。
2. **"用旧方案的账本量新方案"**：新技术评估的第一动作是列旧方案的账，再看新方案把每笔账变成了什么——账本比特性清单可靠。

本层留下的新账：**NewSQL 的账算清了——那什么时候该换？"拆了再换"和"直接换"哪个更贵？** 下一层把换装的成本账拆开。

### Level Ending

## Level 4：换装的时机与成本账——"拆了再换"最贵

一句话认知墙：**换数据库不是升级，是重写一遍 shard-04 的迁移 + 应用全栈替换；"拆了再换"等于先付分片的账、再付换装的账——两笔账全付，是最贵路径。**

### 前置知识关卡

- [ ] 知道扩容迁移四件套（shard-04 L3/L4）
- [ ] 知道发布/变更的灰度纪律（dubbo-08）

### Why——为什么"早晚要换，不如现在就换"是错觉

**徒弟**：

> 既然 NewSQL 是终点，现在分库分表、以后还要换，不如一步到位直接换。

**老陈**：

> "一步到位"少付的只是"未来换装的账"，多付的是"现在不该付的账"：团队还没把账本练熟、数据量级还没到、业务模式还在变。早换的人常发现：换完之后，本来会被治墙四招解决掉的账，现在也全签在 NewSQL 的黑盒里了。

"早晚要换"的推理里藏着一个跳跃：**把"未来可能换"当成"现在必须换"**。换装的成本三笔账是现在付，收益（内置分片/事务）可能永远用不到——如果治墙四招能把 T 拖回安全水位，或者业务模式根本稳定（分片键十年不变），换装的收益就是零。

### What——换装的三笔账

```
① 数据迁移：shard-04 的账重来一遍，而且更重
   双写/校验/切流/回滚一件不少（shard-04 四件套），位点衔接是双写下的关键机制
   外加：迁移目标从"同构 8→16"变成"异构换引擎"——类型/索引/字符集/默认值的差异面
   外加：异构防回环——双写期间同步数据必须打标，防止 A 写 B、B 同步回 A、A 又同步给 B 的循环回放

② 代码改造：应用全栈替换的改造面
   SQL 方言差异（语法兼容 ≠ 行为兼容，L3 已述）
   事务模型：本地事务语义 → 分布式事务语义（隔离级别/锁等待/死锁重试的差异面）

③ 运维模型重建：监控/备份/告警/工具链全换
   中间件运维 → 分布式存储运维：新组件、新故障模式、新值班手册
   团队学习曲线：前四卷的账本换了记账单位（机制性提醒，不编时间数字）
```

### What——该换 vs 忍住的判据（机制性判据，不编数字）

```
该换的信号：
  ① 事务需求天然跨片：业务上就是跨模块强一致，分片键救不了（L2 ④ 失效场景）
  ② 分片键找不到：任何键都有不可接受的分布/查询代价（shard-01 L1 四维全输）
  ③ 数据量级进入 NewSQL 甜区：规模不可预估、增长曲线陡——分片规划的账算不清
     （甜区为机制性描述，具体量级待实测）

忍住的信号：
  ① 现有架构可治：五笔借条（L1）都在付，但没有一笔压垮业务
  ② 迁移成本 > 收益：三笔账（迁移/改造/重建）加起来，比继续付借条更贵
  ③ 团队账本没练熟：还不会用 shard-01~04 的量 NewSQL——黑盒先不签
```

### How——T 的决策走查

```
T 评估"要不要换 NewSQL"：
  ① 事务天然跨片？——订单/支付跨模块事务在现状下靠业务补偿，无强一致需求 → 不满足
  ② 分片键找不到？——order_id 均匀连续（shard-01 L3 已验），键不愁 → 不满足
  ③ 量级进入甜区？——业务增长可预估，8 → 16 的扩容账已付清（shard-04）→ 不满足
  结论：三条"该换"信号全不满足 → 忍住，维持分库分表 + 治墙治理
```

### Transfer——这个思想还能迁移到哪里

1. **"该换 vs 忍住"是技术债决策的通式**：重构、换框架、换语言——"早晚要做"永远不是"现在做"的理由；判据永远是"该换的信号是否真实出现" + "忍住的成本是否可支付"。
2. **"两笔账全付"警示**：任何"先 A 后 B"的过渡方案，都要算"过渡期付出的账在 B 方案里是否作废"——作废的部分就是选 A 的沉没成本，立项时就要认。

本层留下的新账：**该换、该忍、该治，三路都列出来了——但判据散在各处，怎么把它们拼成一个可执行的选型框架？** 下一层给出四维矩阵。

### Level Ending

```text
口诀：早晚要换≠现在要换；换装三笔账，两笔全付最贵。
```

## Level 5：选型决策框架——四维矩阵

一句话认知墙：**选型不是比特性清单，是规模×模式×团队×演进四维的匹配——四维不是打分，是排除法：任一维亮红灯，方案出局。**

### 前置知识关卡

- [ ] 知道五笔借条（本卷 L1）
- [ ] 知道治墙四招的边界（本卷 L2）
- [ ] 知道换装三笔账（本卷 L4）

### Why——为什么特性清单会选错

**徒弟**：

> 我把分库分表和 NewSQL 的特性列个表，优点多的就选，不科学吗？

**老陈**：

> 特性清单的每一条都在回答"它能不能"，没一条回答"你现在需不需要"。分片键约束是"缺点"还是"纪律"？取决于你的团队有没有能力用它。同一个特性，在 A 业务是优点，在 B 业务是陷阱——清单不加权，选型等于抽签。

特性清单的两个死穴：**不回答"现在需不需要"**（NewSQL 的全局事务很强，但 T 没有跨片事务需求，这个优点=零价值）；**不回答"团队接不接得住"**（分布式存储运维比中间件运维复杂，团队能力跟不上，优点=隐患）。选型框架必须把"需求"和"能力"放进矩阵。

### What——四维矩阵

```
① 数据规模：量级 + 增速曲线
   量级可预估且增速平缓 → 分片规划可行（8→16→32 的账算得清）
   量级不可预估/增速陡 → 分片规划的账算不清，NewSQL 甜区（L4 判据③）

② 访问模式：读写比 / 热点 / 事务模式
   模式稳定、事务不跨片 → 分片键可选对（shard-01 L1/L4），分库分表可行
   事务天然跨片 → 分片键救不了（L4 判据①），NewSQL 真实收益

③ 团队能力：SQL/应用层能力 vs 存储运维能力
   团队强应用层、弱存储运维 → 分库分表（账在明处，团队看得懂）
   团队强存储运维、弱应用层改造 → NewSQL（账在黑盒，但有人值守）

④ 演进路径：上下游生态绑定与合规约束
   生态依赖重（工具链/上下游绑定某引擎）→ 选生态成熟的方案
   未来有强 HTAP（在线+分析）需求 → NewSQL 加分（机制性提醒，不展开）
```

### What——分库分表的实现选择（B 候选内部的次级决策）

选定 B（分库分表）之后，实现还有一笔次级账——三种实现机制同构，换了实现，shard-01~04 的账一笔不少：

```
原生分区（MySQL 单库内分区）：
  机制：单实例内分区，无网络一跳
  边界：单库的容量墙/写并发墙仍在——只解表级膨胀，不解库级墙（shard-00 L1 的墙没拆）

中间件（ShardingSphere，本系列贯穿方案）：
  机制：解析→路由→改写→执行→归并五段链路（shard-02），应用透明
  边界：五段链路的代价已付（shard-02/shard-03 的账）

其他中间件（MyCat 类）：
  机制：同类 Proxy 路由改写方案，机制同构（机制性描述，不承诺其版本行为）
  边界：账本同 ShardingSphere——选它看生态/活跃度/团队栈，不指望它免账
```

**没有实现能免掉哪笔账**——原生分区免不掉库级墙，MyCat 免不掉五段链路的代价，中间件免不掉跨片查询的放大。实现选择看生态与运维，不看"它能免账"。

### What——排除法决策卡

```
选型三候选：A=维持现状（治墙）、B=分库分表、C=NewSQL

排除法规则（任一维亮红灯，候选出局）：

  A 出局信号：治墙四招全失效（本卷 L2 四招走完仍到墙）
  B 出局信号：分片键找不到（shard-01 L1 四维全输）；事务天然跨片（L4 判据①）
  C 出局信号：团队无存储运维能力且补不上；迁移三笔账 > 收益（L4 忍住判据②）

  无人出局时的优先级：A > B > C（代价递增：治墙最便宜，换装最贵）
```

### How——T 的四维填表走查

```
T 的四维填写：
  ① 规模：量级可预估、增速平缓 → 不排除 B
  ② 模式：读多写少、事务不跨片、热点可控 → 不排除 B；A 是否出局看 L2 ④
  ③ 团队：SQL 能力强、无分布式存储运维经验 → C 亮红灯（无存储运维能力）
  ④ 演进：合规/生态无特殊锁定（无 HTAP 类强依赖）→ 任一方案可行
  结论：C 出局；A 与 B 二选一——L2 走查已到墙（治墙四招失效）→ 选 B
  （若 L2 走查发现治墙四招未穷尽 → 选 A，拆是最后一步，shard-00 L6）
```

### Transfer——这个思想还能迁移到哪里

1. **"排除法选型"是技术决策的通用纪律**：任何候选对比（框架/存储/中间件），先列"出局信号"再比较优点——优点清单会误导，出局信号不会。评审会上先问"什么情况下不能用它"，比问"它有什么优点"有效得多。
2. **"四维是能力×需求的匹配，不是打分"**：选型矩阵的每个维度都同时问两件事——业务需不需要、团队接不接得住。单问一边，选型必然失衡。

本层留下的新账：**四维框架也选完了——六篇文章的因果链，能不能串成一张图，让三个月后的人还能从头推导？** 下一层做全系列复盘。

### Level Ending

```text
口诀：四维两问——需不需要、接不接得住；任一维红灯，方案出局。
```

## 坑与细节（坑表）

| 坑 | 事故后果 | 防法 |
| --- | --- | --- |
| 立项只看收益不算总账 | 五笔借条（L1）逐笔到期，团队措手不及 | 立项时把五笔借条贴评审墙上 |
| 治墙四招没走完就拆 | 白拆——本可治墙解决的账签进分片 | 按 shard-00 L6 顺序 + 本卷 L2 边界走查 |
| 把 NewSQL 当免费午餐 | 黑盒账（兼容边界/运维/性能）到期时无人会查 | 用前四卷的账本逐笔问供应商（L3） |
| "早晚要换"当"现在要换" | 两笔账全付（L4）——分片的账+换装的账 | 该换信号出现才换；忍住判据常体检 |
| 特性清单选型 | 优点不加权，选了"很强但不需要"的方案 | 四维矩阵 + 排除法（L5） |
| 团队能力不设维度 | 方案先进，团队接不住——黑盒无人值守 | 四维里团队单独一维（L5） |
| 换装只算数据迁移 | 代码改造/运维重建两笔账漏算，工期失控 | 三笔账全列（L4） |
| 异构双写未做防回环 | 数据循环回放，导致数据膨胀或死循环 | 同步管道打标过滤，识别并丢弃反向同步的数据（L4 ①） |
| 总结式收官 | 三个月后断片，因果链推不出来 | 复盘复因果链（L6） |

<a id="params"></a>

## 评估参数

只讲评估机制与误用后果，具体阈值不编数字（待实测）。

| 评估参数 | 机制 | 误用后果 |
| --- | --- | --- |
| 数据量级/增速 | 量级+增速决定"分片规划可不可算"——增速陡则扩容账算不清（shard-04 L2 搬迁账随分片数变化） | 用现状量级做选型，忽略增速——选完三年内重新选型 |
| 读写比/事务模式 | 决定分片键选不选得对（shard-01 L1/L4）与跨片事务需求（L4 判据①） | 用当下模式代表未来——模式一变，键白选 |
| 团队能力评估 | 应用层 SQL 能力 vs 存储运维能力，决定账在明处还是黑盒 | 只评估"学不学得会"，不评估"故障时接不接得住" |
| 迁移成本三笔账 | 数据/代码/运维全算，缺一笔工期失控 | 只算数据迁移，代码改造与运维重建漏账 |

<a id="cross-language"></a>

## 跨语言视角

| 语言/系统 | 对应实现 | 差异点 |
| --- | --- | --- |
| Redis Cluster | 槽位自动分配，扩容迁移以槽为单位可控（redis-03 L5） | 键分布均匀性靠槽，不靠键本身——一致性哈希才不可控（redis-03 L2） |
| Kafka | 分区=分片，消费者重平衡 | 数据不搬（日志追加语义），分区的账比数据库轻（mq-06） |
| Elasticsearch | 自动分片 + 自动路由 | 无路由键查询天然全分片扫——广播账在 ES 是常态不是事故（es-02 L2） |
| TiDB 类 NewSQL | 分片/事务/重平衡内置 | 账从应用层搬进存储层黑盒（本卷 L3） |
| 单库 + 读写分离 | 治墙招数的常规形态 | 分片的账一笔不签，直到墙真的到 |
