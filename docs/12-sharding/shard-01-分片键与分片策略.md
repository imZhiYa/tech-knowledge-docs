## Level 1：分片键四合一——四个维度为什么互相打架

一句话认知墙：**分片键同时决定路由、查询半径、事务边界、热点，而这四个维度互相冲突，不可能同时最优。**

### 前置知识关卡

- [ ] 知道分片键四合一概念（shard-00 L4）
- [ ] 知道路由键 = 事务边界（springboot-05 L6.4）
- [ ] 知道无路由键查询 = 广播全分片（shard-00 L4）

### Why：为什么"选个字段就行"是神话②

**徒弟**：

> 分片键不就是选个字段吗？订单表就按 order_id 分，或者按 user_id 分，二选一，选完配置进中间件，完事。

**老陈**：

> 你已经把四个维度的冲突一起忽略了。我们用 T 的业务场景过一遍：下单要同时写订单、明细、库存，按 user_id 查"我的订单"，按 order_id 查"订单详情"。现在开始选：

### What：四个维度各自的要求

```text
① 路由
   每条 SQL 都要回答"去哪几个分片"。
   WHERE 带分片键 → 单分片；不带 → 广播全分片（代价 = 分片数倍放大）

② 查询半径
   高频查询按什么键进来，分片键就该对齐什么键：
   按 user_id 查"我的订单" → 分片键选 user_id，查询单分片
   按 order_id 查详情 → 分片键选 order_id，查询单分片

③ 事务边界
   一笔事务涉及的数据必须落在同一分片（本地事务才成立）：
   下单 = 订单 + 明细 → 必须按同一个键收敛到一片
   库存是共享资源，扣减跨片/跨域的账归 distributed-tx
   （承接 shard-00 L3 的库存独立域结论）

④ 热点
   分片键取值分布决定写是否均匀：
   连续键取模均匀；块状键（日期键、雪花低速率）同块集中（L3 ①）
```

### How：冲突在哪里

```text
选 order_id：事务收敛（订单+明细同片）；库存扣减跨片，账留给 distributed-tx
  但"按 user_id 查我的订单"变成广播查询（用户订单散在 8 片）

选 user_id：查询半径对齐（我的订单单片查）
  但一笔订单 = 订单+明细按 user_id 同片（可收敛）
  跨用户事务（如转账 A→B）散片

热点维度独立于前三个：
  连续键 + MOD：余数轮转，速率无关，分布均匀（L3 ①）
  块状键 + MOD：同块全打一片（日期键/雪花低速率，L3 ①/L5）
  顺序键 + RANGE：无论速率，新数据永远挤尾部（L2 ③）
```

**徒弟**：

> 那能不能两个都选？既有 order_id 又有 user_id 的分片？

**老陈**：

> 一个表只有一个主分片键。要覆盖第二个查询维度，靠的是**映射表/索引表**（user_id → order_id 的索引分片，L4 展开）或**反范式冗余**（把"我的订单"的摘要表按 user_id 单独分片）。这就是分布式查询的代价之一——**查询维度越多，要维护的映射越多**。先接受这个事实：**四维不可能同时最优，只能按业务排序做取舍**（L4 给方法论）。

### Transfer：四维冲突可迁移

1. Kafka：partition key 决定顺序与局部性，但"按另一个字段查"同样做不到（mq-04）。
2. Redis Cluster：slot 是固定哈希，key 设计决定局部性，热点 key 无法靠槽位解决（redis-03）。
3. ES：routing 决定文档落片，跨 routing 的查询 = 广播（es-02）。
4. 所有分布式存储的第一课：**选路由键 = 明确"什么被放弃了"**。

本层留下的新账：**方向定了（按业务排序取舍），但"分片算法"还没选——MOD 和 RANGE 对均匀性、扩容、热点的机制完全不同。** 下一层看算法家族。

### Level Ending

```text
口诀：四维打架是常态，取舍排序是正道；一个表只有一个主分片键。
```

## Level 2：算法家族——MOD / HASH / RANGE / 一致性哈希

一句话认知墙：**分片算法在"均匀性、迁移量、热点、扩容"四个指标上各有取舍，没有全能选手。**

### 前置知识关卡

- [ ] 知道四维冲突（L1）
- [ ] 知道 Redis Cluster 用 16384 slot 固定哈希（redis-03，对照用）

### Why：为什么不能只有一种算法

**徒弟**：

> 我见过的大多是"ID % 分片数"，这个不是挺好吗？又简单又均匀。

**老陈**：

> MOD 确实最常用，而且它的"均匀"是真的——但有两个前提：键的取值连续轮转（连续键余数逐条轮转，速率无关）、数据冷热均匀。两个前提破坏一个，MOD 就翻车（L3）。而且 MOD 有一个硬伤：**分片数一变，大部分行的归属都变**（迁移比例 = 1 − gcd(N,M)/max(N,M)，机制推导）。所以我们把四个算法摆开，先看清各自的机制，再谈选型。

### What：四算法机制对照

**① MOD（取模）**

```text
分片号 = sharding_value % N
均匀性：连续递增键余数轮转、速率无关（机制推导）；
  块状键（日期键/雪花低速率）同块集中（L3 ①）
扩容：分片数 N → M，取模结果整体重算
  迁移比例 = 1 − gcd(N,M)/max(N,M)
  （互质且分片数大时接近全量，如 8→9 约 89%）——机制推导
热点：连续键无集中问题；块状键集中（L3 ①）
适用：键连续递增、分片拓扑稳定、无扩容预期的场景
```

**② HASH（哈希取模）**

```text
分片号 = hash(sharding_value) % N
解决：字符串等非连续键的均匀化（hash 打散原始分布）
代价：与 MOD 同样的扩容硬伤（模数变 → 同样大量迁移，比例同 ①）
  "哈希一致性"的误区：hash(key) % N 不是一致性哈希，
  两者名字像、机制完全不同（避免与一致性哈希混为一谈）
适用：键是字符串/复合值、需要均匀化的场景
```

**③ RANGE（区间）**

```text
分片号 = 按取值区间映射（如 [0,1000) → 片0，[1000,2000) → 片1）
扩容：新增区间即可，存量不动（可增量扩展）——唯一可增量扩容的算法
均匀性：完全取决于数据分布（区间切得不均 = 片大小不均）
热点：顺序增长的新数据全部落入尾部区间（最尾部一片持续写入）
适用：可预测区间分布、天然按范围管理的场景（时间/地区/ID 段）
```

**④ 一致性哈希（Consistent Hashing）**

```text
机制：key 哈希后落在哈希环上，顺时针找到第一个节点（Karger 1997）
扩容：新增节点只影响环上相邻区间 → 迁移量 ≈ 1/N（机制推导）
  对比 MOD 的大量迁移（互质时接近全量），这是它存在的全部理由
代价①：节点少时分布不均（随机落点可能扎堆）→ 虚拟节点缓解
代价②：热点 key 无解（哈希打散后热点依然集中在一个节点）
适用：节点动态增删频繁的场景（缓存集群更常见）
支线标注：数据库分片实践中用得较少——分片拓扑需要稳定，
  增删分片是重迁移事件而不是日常操作；缓存场景（一致性哈希的
  主战场）是另一条因果链，此处仅作机制对照
```

### How：四指标横评

| 算法 | 均匀性 | 扩容迁移量 | 热点应对 | 典型场景 |
| ---- | ---- | ---- | ---- | ---- |
| MOD | 键连续时好 | 接近全量（互质时） | 差（块状键集中） | 稳定拓扑、连续键 |
| HASH 取模 | 好（打散原始分布） | 接近全量（互质时） | 差（热点无解） | 字符串/复合键 |
| RANGE | 取决于区间划分 | 增量（可扩展） | 差（尾部新数据集中） | 时间/地区/ID 段 |
| 一致性哈希 | 节点少时差（虚拟节点缓解） | ≈ 1/N | 差（热点无解） | 动态节点（缓存场景为主） |

**徒弟**：

> 表里看下来没有一个是完美的？

**老陈**：

> 对，这就是分片的本质：**你永远在四个指标里选三个**。数据库分片的工程现实是：MOD/HASH 换来均匀性、牺牲扩容；RANGE 换来增量扩容、牺牲均匀。一致性哈希在数据库分片里反而少见——因为"分片数不变"在数据库里是常态（扩容是重事件，不是日常操作）。**先定业务对"扩容频率"的预期，再选算法**（L6 决策卡）。

### Transfer：算法家族可迁移

1. Redis Cluster：16384 slot = 固定模数的哈希取模 + 显式 slot→节点映射，扩容只迁移 slot、不重算映射（redis-03）——对照 MOD 的"模数一变大量重算"看，slot 方案就是为扩容而生的。
2. 负载均衡的一致性哈希：网关/缓存路由同构（dubbo 负载均衡家族）。
3. 分区表：MySQL 原生 PARTITION BY RANGE/HASH 是单实例内的同族机制（shard-05 对照）。

本层留下的新账：**算法选定了，但"取模均匀 = 热点均匀"这个直觉还是错的——分布均匀为什么不等于访问均匀？** 下一层破神话③。

### Level Ending

```text
口诀：四个指标选三个；MOD 均匀怕扩容，RANGE 可扩怕不均。
```

## Level 3：热点与倾斜——为什么"取模均匀"不等于"热点均匀"

一句话认知墙：**连续键取模的均匀与速率无关（分布层）；但"分布均匀"管的是容量，管不了访问与写入的集中——块状键写集中、冷热不均、单点热点键，算法都救不了。**

### 前置知识关卡

- [ ] 知道 MOD 的机制与均匀前提（L2）
- [ ] 知道容量墙 vs 性能墙（shard-00 L1）
- [ ] 知道热点是分片键四维之一（shard-00 L4）

### Why：神话③的机制根源

**徒弟**：

> ID 取模 8，1 到 8 各落一片，9 到 16 又各落一片……这不是挺均匀的吗？为什么说热点不均匀？

**老陈**：

> 你这次直觉没错——**连续递增键取模，余数逐条轮转，任何速率下都均匀**，这正是它流行的原因。但取模的均匀有一个前提：键的取值是连续轮转的。键一旦按"块"变化，均匀就塌了（①）；而且"分布均匀"解决的是**容量**（每片数据量相近），访问/写入均匀解决的是**性能**（每片负载相近）。容量均匀了，负载未必均匀。三个机制，往下看。

### What：三类倾斜的机制

```text
① 块状键的瞬时写集中（键值按"块"变化）
   连续递增键（自增/号段）取模：余数逐条轮转，速率无关，均匀
   ——这是"取模均匀"成立的真实前提
   块状键：取值在一个"块"内不变、跨块跳变：
     a. 业务日期键（如 YYYYMMDD，或按天/小时分段）直接取模 →
        同一时间段的数据同余数 → 瞬时写全打一片
        （注意：毫秒级时间戳本质是连续键，取模是均匀的；
        工程中极少直接拿毫秒时间戳做分片键）
     b. 雪花 ID 低速率（每毫秒 ≤1 次写）→ 序列号归零 → 余数恒 0
        → 新数据全打一片，比自增更集中（L5 展开）
        → 实测回填：dev-lab/sharding-demo EX-01（ShardingSphere 5.4.1 + MySQL 8.0.36，
        每毫秒 1~2 单的雪花模拟键 1.5 万行 → 片 0/1 两片集中，最大片占比 66.7%；
        连续键 1 万行 8 片各 1250 均匀）
   → 取模的均匀性由"键的取值形态"决定，不由速率决定

② 冷热不均（RANGE/时间键的问题，MOD 不成立）
   老数据（几年前的订单）几乎不访问，新数据全热
   → RANGE：热数据本就集中尾部 → 冷热叠加，尾部热点加剧
   → MOD：新数据均匀散片，不存在"热数据集中"；MOD 的对应代价是
     时间范围查询（如查最近 7 天）要在每片过滤大量冷数据，
     热点行被冷数据稀释（buffer pool 命中率下降，机制推导）

③ 单点热点键（大客户/大商家）
   某个用户的订单量占全表很高比例 → 无论取模还是哈希，
   他的数据都在同一片 → 一片打满，其他片空闲
   → 这是哈希分片也救不了的（哈希打散的是键的分布，
     不是键的访问频率）
```

### How：热点分片的物理后果

```text
热点分片 = 性能墙在分片后的复活（回链 shard-00 L1 概念）：
  一片的连接/锁/IO 被打满 → 该片变慢
  → 跨片查询（如广播查"我的订单"）被最慢的一片拖累
  → 拆了 8 片，1 片扛大部分流量 = 拆了等于没拆

热点不是"配置问题"，是"数据形态问题"：
  中间件（ShardingSphere）负责路由，不负责重新分布热点
  ——热点要靠在数据形态上化解（L4 方案）
```

**徒弟**：

> 那热点分片怎么治？换 RANGE 行不行？

**老陈**：

> RANGE 更糟——顺序键 RANGE 是**永久性**的尾部热点（新数据永远落最后一个区间）。MOD 对连续键没有集中问题，只对块状键（日期键、雪花低速率）集中。真正的解法不在算法，在**分片键的取值设计**：让键本身不随时间成块（用连续键或业务键，避开日期直取模/雪花低速率直取模），或者对超热点做散列拆分（L4 展开）。记住：**算法的均匀是"分布均匀"，不是"访问均匀"，后者只能靠键的设计解决。**

### Transfer：热点问题可迁移

1. Redis 热点 key：任何哈希分片都解决不了热点 key 的访问集中（redis-03）。
2. Kafka 分区热点：热点 Key 倾斜、单 Key 串行拖慢整分区（mq-04、mq-06）。
3. ES：分片分配要服从均衡约束，热点分片同样只能靠 routing 设计缓解（es-02）。
4. 通用结论：**分布式存储只能均匀"分布"，不能均匀"热度"；热度是业务形态，要靠键设计和业务拆解**。

本层留下的新账：**四个维度、四种算法、三类倾斜都摆完了，那到底怎么选？** 下一层给方法论。

### Level Ending

```text
口诀：分布均匀管容量，访问均匀管性能；取模救不了大客户。
```

## Level 4：选键方法论——事务 > 查询 > 热点的权衡顺序

一句话认知墙：**选分片键没有标准答案，但有标准顺序：先收敛事务，再对齐查询，最后兜热点。**

### 前置知识关卡

- [ ] 知道四维冲突（L1）
- [ ] 知道三类倾斜（L3）
- [ ] 知道跨片事务的账（shard-00 L4，完整机制在 distributed-tx）

### Why：为什么"事务优先"不是教条

**徒弟**：

> 我听说"分片键要选事务收敛的键"，那不是所有表都选 order_id 就行？

**老陈**：

> 事务优先是对的，但它不是唯一标准——**它是第一标准**。原因很硬：跨片事务是拆分的代价里最贵的一种（要么分布式事务，要么业务改造），而查询广播只是"慢"，事务散片是"错"。**先保证不错，再追求不慢。** 但只有事务维度还不够，我们把顺序排出来：

### What：权衡顺序与方案谱系

```text
第一步：事务收敛（硬约束）
   一笔业务事务的所有写，必须落在同一分片
   → 分片键 = 该业务的聚合根键（订单域 = order_id）
   → 违反 = 每个写都是跨片事务（代价最高，先排除）

第二步：查询半径对齐（性能约束）
   高频查询按什么键进来？分片键对齐哪个，哪个就单片查
   → 只能对齐一个主键，其余查询维度用方案补：
     a. 映射表/索引表：user_id → order_id 单独分片的索引
        （本质是分布式环境下的 Index Table 模式 / CQRS 读模型）
     b. 反范式冗余：按 user_id 分片的"我的订单摘要"表
     c. 接受广播：低频查询可以广播（但要监控广播率）
     d. 分片基因法：把 user_id 的分片信息编码进 order_id 低位
        （免冗余免广播，但绑定 ID 生成与扩容约束，见 How）

第三步：热点兜底（数据形态约束）
   检查分片键取值形态与访问分布：
   → 块状键（日期直取模/雪花低速率）= 瞬时写集中（L3 ①）
   → 日期/时间键 + RANGE = 永久性尾部热点（L2 ③）
   → 超热点实体 = 散列拆分（大客户拆成 N 个子键）或接受单点热点
```

### How：经典案例——订单表选键

```text
候选：order_id vs user_id

选 order_id：
  事务收敛 ✓（订单+明细同片；库存扣减跨片归 distributed-tx）
  查询：order_id 详情单片 ✓；"我的订单"广播 ✗ → 映射表/摘要表补
  热点：order_id 连续递增（自增/号段）→ 取模均匀（L3 ①）；
   雪花低速率 → 块状集中（L5）

选 user_id：
  查询：我的订单单片 ✓
  事务：单用户下单收敛 ✓；跨用户事务（转账/拼单）散片 ✗
  热点：大客户单点热点 ✗（user_id 是天然的热点载体）

工程结论（常用形态）：
  订单主表按 order_id 分片（事务优先），
  配 user_id → order_id 映射表 / 按 user_id 分片的订单摘要表
  / 分片基因法（绑定 ID 生成与倍增扩容约束）
  ——查询维度的账，用冗余结构或 ID 生成约束还，不用事务的账还
```

**徒弟**：

> 映射表本身也是表，它怎么分片？

**老陈**：

> 映射表按它自己的查询键分片（user_id），一次查就定位。它的代价是：**写订单时多一次映射表的写**（与订单同事务或异步最终一致，后者回链 ddd-05 Outbox 知识）。多一个维度，多一套冗余，多一分一致性维护——这就是"查询维度"的定价。所以第二步才问：**这个查询维度的频率，值不值得付这笔钱？**

**徒弟**：

> 映射表要维护一套冗余，太重了。有没有办法让 order_id 自己带上 user_id 的路由信息？

**老陈**：

> 有，这就是**分片基因法**——把 user_id 的分片基因编码进 order_id 的低位，让"按 user_id 查"不用映射表、不用广播：

```text
做法（以分片数 = 8 = 2^3 为例，基因位 = 3）：

  1. 发号时让号段低 3 位恒为 0：
     号段按 2^3 步长发号（如 1000、1008、1016……）
  2. 生成 order_id：order_id = 原号 | (user_id 低 3 位)
     （user_id 的低 3 位 = 它的"分片基因"）
  3. 分片算法：order_id % 8 → 余数就是低 3 位
     = user_id 的低 3 位 → 订单落在 user_id 的基因片上

效果：双键单片路由，免映射表
  按 order_id 查详情：直接取模定位（order_id 本身就是分片键）
  按 user_id 查"我的订单"：直接算 user_id 低 3 位 → 单片查询
  → 同一个用户的所有订单收敛在同一片（基因相同）

代价（三条，缺一不可）：
  ① 分片数必须是 2 的幂（基因位 = log2(分片数)，非 2 的幂无法对齐）
  ② ID 生成器耦合分片逻辑（步长发号 + 基因 OR 进低位）
  ③ 扩容只能倍增（8 → 16：基因位 3 → 4，机制延续但历史数据
     仍要搬迁；8 → 12：基因错位，路由全部失效）

注意：直接替换低位会破坏原号唯一性——必须"步长发号让低位恒 0"
再 OR 基因，否则两个不同的原号可能 OR 出同一个 order_id（机制推导）
```

> 基因法把"查询维度的账"从"冗余表"换成"ID 生成器的账"：冗余表的钱花在存储与一致性维护，基因法的钱花在 ID 生成约束与扩容约束。选哪个，先问一件事——**你的 ID 体系允不允许绑定分片逻辑？**

### Transfer：权衡顺序可迁移

1. 微服务拆分：先事务边界（聚合边界），再调用链优化（ddd-03/04）。
2. 缓存键设计：先一致性语义，再命中率（redis 系列决策卡同构）。
3. 所有"切分"决策：**先保证不破坏正确性（事务/一致性），再优化性能，最后处理形态问题（热点）**。

本层留下的新账：**键选好了、算法定了，但"分片键的值"从哪来？自增 ID 在分片下会重复，谁给 T 一个全局唯一、还能路由的书号？** 下一层看分布式 ID。

### Level Ending

```text
口诀：先收敛事务，再对齐查询，最后兜热点；查询维度的账用冗余还。
```

<a id="level-5"></a>

## Level 5：分布式 ID 与路由可寻址性

一句话认知墙：**分片后自增 ID 失效；分布式 ID 不只要全局唯一，还能把分片信息编码进去，让 ID 本身可路由。**

### 前置知识关卡

- [ ] 知道自增 ID 单库语义（单库内唯一，shard-00 L3 已预告失效）
- [ ] 知道分片键的选择（L1~L4）
- [ ] 知道全局唯一约束在分片下的失效（shard-00 L4 账⑤）

### Why：自增 ID 为什么在分片下失效

**徒弟**：

> 自增 ID 在单库里不是好好的吗？拆了之后每片各增各的不就行了？

**老陈**：

> 每片各增各的，8 片就出现 8 个"ID=1001"——**唯一性是分片内的，不是全局的**。而订单号一旦重复，日志、对账、报表、对外引用全部错位。更要命的是：自增 ID 的取值是"时间有序的"——按它分片，均匀性依赖写入速率（L3 ①），且它本身只保证片内唯一。所以分片之后，ID 生成要从"数据库的自增"换成"独立的 ID 服务/算法"。

### What：两种主流机制

**① 雪花算法（Snowflake）**

```text
结构（Twitter 公开设计）：64 位 long
  1 bit 符号位 + 41 bit 毫秒时间戳 + 10 bit 机器 ID + 12 bit 序列号
  （各实现位分配有差异，以实现文档为准）

机制：
  时间戳 → 单调递增（趋势有序）
  机器 ID → 多实例不重复
  序列号 → 同一毫秒内最多 4096 个（机制推导）
  全部字段合起来 → 单机单毫秒内唯一，跨机器靠机器 ID 区分

特性与风险：
  无中心依赖：唯一性计算本地化（机器 ID 的分配常见实现仍需
  ZK/DB 一次性协调）→ 高吞吐（实测需压测）
  时钟回拨 → 同一毫秒内可能生成重复 ID → 需要回拨检测
  （等待/拒绝/号段备用，属工程实现差异，以各实现为准）
  分布误区：ID 直接取模时，余数只看序列号低位（N 为 2 的幂且
  ≤ 4096 时）；序列号每毫秒从 0 重新递增 → 每毫秒写入次数少于
  分片数时，余数只覆盖序列号的一部分、部分分片收不到新数据；
  每毫秒 ≤1 次写时余数恒 0，新数据全打一片，比自增 ID 的
  轮转更集中——机制推导
  → 雪花解决的是"唯一 + 趋势有序"，不解决"分布均匀"；
  分布靠业务键做分片键，或对 ID 哈希后再取模
```

**② 号段模式（批量取号）**

```text
机制：集中发号器（如数据库/服务）一次取一段号（如 [1000,2000)），
  应用本地内存发号，用完后再次取号
   → 集中取号 + 本地发号 → 数据库压力从"每次一条"降到"每次一段"

特性与风险：
  号段窗口 = 应用崩溃时未用完的号会浪费（机制推导）
  发号器有单点（可用多实例分段/双写缓解，属工程实现）
  连续递增 → 取模余数逐条轮转，任何速率下都均匀（机制推导），
  且连续性不受时钟回拨和实例重启影响（对比雪花的时钟依赖）
  → 与雪花不同：号段没有"序列号归零"的块状集中问题

与分片的关系（两者共同点）：
  ID 趋势有序 → 按 ID 取模的分布由键的取值形态决定：
    连续号（号段/自增）均匀；雪花低速率块状集中（L3 ①/L5 ①）
  → 工程上两种化解：a. 业务键做分片键（ID 只当唯一键）
    b. 分片信息编码进 ID（见下）
```

### How：ID 可路由——把分片信息编码进 ID

```text
需求：按 ID 查详情时，如何定位分片？
方案 a：WHERE id = ? 时，中间件对 ID 取模/哈希 → 广播？不，
  如果分片键就是 ID，直接计算即可定位（无需映射表）
方案 b：ID 内含分片信息（如雪花机器 ID 段映射分片号）：
  机器 ID = 分片号 × 每片实例数 + 实例序号
  → 从 ID 直接算出分片 → 免映射表、免计算路由（机制推导）
  代价：机器 ID 段被占死 → 分片扩容受限（每片实例数固定）
   → 这是"可路由性"与"扩展性"的权衡（L6 决策卡再收口）
```

**徒弟**：

> 那我把雪花机器 ID 直接当分片号，是不是最优雅？

**老陈**：

> 优雅是有定价的：机器 ID 段一旦编码了分片号，**分片数上限被锁死**（位数有限），后续扩容要么改位分配（全量重建 ID 语义），要么另想办法。可路由性换来的免映射，是用"拓扑弹性"买的。所以工程上先问：**这个表的高频查询是不是"按 ID 精确查"？** 是，才值得编码；否则 ID 只负责唯一，路由交给业务键。

### Transfer：ID 设计可迁移

1. Kafka 消息 ID / 事务 ID：全局唯一 + 可排序，但"可路由"要看分区键设计（mq-04）。
2. Redis 的 key 设计：把分片/槽位信息编码进 key 是常见技巧（redis-03）。
3. 跨系统 ID 语义：订单号、流水号在金融场景还要带机构/渠道位（业务编码），与雪花可叠加——ID 是"位分配的艺术"。

本层留下的新账：**键、算法、ID 都定了，但"怎么配置进中间件、配错了会出什么事故"还没讲——MOD 的取模基数配错、RANGE 的区间配错，后果完全不同。** 下一层收口到生产配置。

### Level Ending

```text
口诀：唯一是底线，可路由是溢价；编码分片信息 = 用拓扑弹性换免映射。
```

<a id="level-6"></a>

## Level 6：生产决策与参数

一句话认知墙：**算法参数不是填完就完事——配错基数/区间/节点数的后果各不相同，且大多要等流量上来才爆。**

### 前置知识关卡

- [ ] 知道四算法机制（L2）
- [ ] 知道三类倾斜（L3）
- [ ] 知道权衡顺序（L4）

### Why：为什么"配置完就完事"是最后一个误区

**徒弟**：

> 分片算法配置里填个数，不就行了吗？还要注意什么？

**老陈**：

> 分片算法配置的本质是"把业务假设固化进路由规则"。三个常见事故，全是因为**配置与实际数据形态不符**：分片数配置与数据分布不匹配、区间配置与业务量预估不符、节点数配置与容量规划脱节。我们一个个看机制。

### What：三类配置事故的机制

```text
事故①：MOD 分片数配错/随意改
   基数 N 变了 → 大量迁移（互质时接近全量，L2 机制）→ 生产扩容不是"加配置"，
   是"数据搬迁工程"（shard-04 完整展开）
   配错后果：存量行路由错位 → 查不到数据（最隐蔽的故障）

事故②：RANGE 区间预估错误
   区间切得宽窄不均 → 片大小不均（L2 机制）
   配错后果：某一片先满 → 容量墙提前到达 → 又要迁移
   （区间预估需要业务量数据支撑，不是拍脑袋）

事故③：一致性哈希节点数/虚拟节点数配置不当
   虚拟节点太少 → 分布不均（L2 机制）
   配错后果：负载倾斜 → 部分节点先打满
```

### How：生产决策框架

```text
选算法前必答三问：
  1. 业务预期扩容频率？常扩 → 考虑 RANGE/可扩展方案；稳定 → MOD/HASH
  2. 键的取值形态？连续数字 → MOD；字符串/复合 → HASH；
     天然按段管理 → RANGE
  3. 热点可接受度？大客户/大商家存在 → 业务键兜底 + 散列拆分预案

配置时必做三件事：
  1. 分片数 = 容量规划结果（×3~5 年余量，经验范围，按业务增长率修正），不是拍脑袋
  2. 区间表/基数表评审（业务量数据支撑，标注预估依据）
  3. 灰度验证：先在低流量分片核对路由结果（实验计划中的
     "路由改写"实验），再放全量

上线后必监控三指标（回链 dubbo-08 可观测三件套的指标视角）：
  1. 各分片数据量分布（物理均匀性）
  2. 各分片连接数/活跃查询（访问均匀性，L3 的账）
  3. 广播查询占比（路由效率，shard-03 展开）
```

**徒弟**：

> 分片数 ×3~5 年余量，是怕什么？

**老陈**：

> 怕的是"分片数定小 → 几年后单片容量又到墙 → 取模扩容大量搬迁"。MOD 的扩容成本是**接近全量搬迁（互质时）**（L2），所以分片数的决定要按最坏增长做余量——这也是为什么"分片键和分片数"在立项时就要定死，而不是上线后再调。RANGE 相对好办（加区间即可），所以**预期会频繁扩容的业务，一开始就选 RANGE 或预留区间**，不要先 MOD 后补。

### Transfer：生产配置可迁移

1. Kafka 分区数：定小难扩、定大浪费，同样要先算容量（mq-06）。
2. Redis Cluster 槽位规划：16384 slot 的迁移也是重事件（redis-03）。
3. ES 分片数：主分片数创建后不可变，扩容靠重索引（es-02）。
4. 通用结论：**路由参数的"初始值"决定"后续成本"，一切路由配置都要按容量规划反推，而不是随手填**。

本层留下的新账：**分片键定了、算法定了、参数定了，但 SQL 本身怎么穿过中间件？广播/归并/分布式 JOIN 的机制是什么，哪些 SQL 会变成事故？** 下一篇（shard-02）进入 SQL 链路。

<a id="pitfalls"></a>

## ⚠️ 坑与细节

| 坑 | 机制根源 | 避免方法 |
| ---- | ---- | ---- |
| 以为 hash(key) % N 是"一致性哈希" | 名字像、机制完全不同（L2） | 记住：取模是"全量重算"，一致性哈希是"环上相邻迁移" |
| 自增 ID 当分片键 | 片内唯一失效（L5）+ 扩容大量迁移（L2） | 换全局 ID 服务（雪花/号段），或业务键分片 |
| 雪花 ID 低速率直接取模当分片键 | 序列号每毫秒归零 → 余数恒 0 → 全打一片（L5） | 业务键做分片键，或对 ID 哈希后再取模 |
| 业务日期键（YYYYMMDD）直接取模当分片键 | 同一天数据同余数 → 全天打一片（L3 ①） | 换连续键/业务键，或哈希后再取模 |
| 大客户数据天然热点还选它当分片键 | 单点热点键（L3） | 散列拆分预案（L4）或接受并隔离 |
| 先 MOD 后预期扩容 | MOD 扩容大量迁移，互质时接近全量（L2/L6） | 一开始就按容量规划定死分片数，或选 RANGE |
| 用了基因法却按非 2 的幂扩容 | 基因低位映射失效，路由全部错位（L4） | 基因法必须约束扩容为倍增（2→4→8→16） |
| 映射表与主表不同事务写 | 一致性窗口（回链 ddd-05） | 明确一致性级别：同事务 or Outbox |
| 把机器 ID 编码分片号后想扩容 | 位数锁死（L5） | 编码前先确认"按 ID 查"是不是高频 |
| 配置算法时随手填基数/区间 | 参数=业务假设固化（L6） | 三问三件事（L6 决策框架） |

## 🏆 生产决策卡

## 决策卡 1：订单主表分片键

| 项 | 内容 |
| ---- | ---- |
| 场景 | 订单表，高频：下单（写订单+明细；库存扣减跨片）、按 ID 查详情、按 user 查我的订单 |
| 判断 | 事务收敛是硬约束 → 分片键 = order_id；查询维度用映射表/摘要表补，或评估是否适用基因法（需满足 2 的幂扩容）；ID 用雪花保证全局唯一 |
| Mechanism → Decision | 跨片事务最贵（错）> 广播查询（慢）> 冗余维护（钱） |
| Code | 分片键 order_id；摘要表按 user_id 分片；或基因法（分片数 2 的幂 + 步长发号 + 基因 OR 低位） |
| 禁止决策 | 禁止按 user_id 分片（跨用户事务散片）；禁止把片内自增当全局唯一来源（硬）；雪花低速率取模会集中（L5），分布靠业务键兜底 |
| 验收指标 | 订单+明细全部单片；库存扣减走跨片方案（distributed-tx）；广播查询占比有上限 |

## 决策卡 2：算法选择

| 项 | 内容 |
| ---- | ---- |
| 场景 | 新表分片，业务预期 3 年不扩容 vs 预期持续增长 |
| 判断 | 稳定 → MOD（连续键）/HASH（字符串键）；持续增长 → RANGE 或预留扩容方案 |
| Mechanism → Decision | MOD 扩容大量迁移（互质时接近全量，L2）→ 扩容预期决定算法 |
| Code | 稳定拓扑：MOD/HASH；可扩展：RANGE |
| 禁止决策 | 禁止"先 MOD 后补扩容"（大量搬迁）；禁止随手填基数 |
| 验收指标 | 各片数据量分布监控；区间/基数表有业务量依据 |

## 决策卡 3：ID 编码分片信息

| 项 | 内容 |
| ---- | ---- |
| 场景 | "按 ID 精确查"是最高频查询，想免映射表 |
| 判断 | 高频按 ID 查 → 编码（机器 ID 段映射分片号）；否则 ID 只保证唯一 |
| Mechanism → Decision | 可路由 = 免映射（L5）；代价 = 分片数上限锁死 |
| Code | 机器 ID = 分片号 × 每片实例数 + 实例序号 |
| 禁止决策 | 禁止不评估"按 ID 查频率"就编码；禁止编码后随意扩片 |
| 验收指标 | 按 ID 查询 100% 单片路由（免广播）；扩容预案明确 |
