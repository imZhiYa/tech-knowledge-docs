> ## 写在最前面的承诺
>

## 🏭 全文唯一比喻地图


```text
总部台账 = 门店营业状态表（在 N 个地点各存一份副本）
   │
   ├─ 电话点名（客户端心跳）── 门店自己定期报"我还开着"
   ├─ 巡逻队上门（服务端主动探活）── 总部派人确认"这店真开着吗"
   ├─ 抄送副本、各点稍后对齐（Distro 异步复制）── 写单处先记账，副本慢慢补
   ├─ 全员开会、半数点头才记下（ZAB / Raft 全序广播）── 每笔登记要过半确认
   └─ 电话线断了，各点照手上副本派单（consumer 本地缓存目录）── 断线不断单

各城区调度台（Consumer）只认自己手上那份副本
   └─ 总部某地副本坏了：调度台照样派单，但"新店开业/旧店关停"看不到
```


| 中央厨房元素 | Dubbo 技术对象 | 它负责的唯一一件事 |
|---|---|---|
| 总部台账副本 | 注册中心集群节点（Nacos/ZK） | 各自持有一份门店营业状态表，按同步规矩保持一致。 |
| 电话点名 | 客户端心跳续约（临时实例语义） | 门店自己声明"我还开着"，逾期总部有权摘除。 |
| 巡逻队上门 | 服务端主动探活（持久实例/健康检查语义） | 总部不信自称，主动确认门店真能接单。 |
| 抄送副本 | Distro 异步复制（Nacos 2.x 临时实例数据） | 写单节点先记账，其他节点稍后补齐（最终一致）。 |
| 全员会议 | ZAB / Raft 全序广播（ZK / Nacos CP 模式） | 每笔登记过半确认才生效，任何时刻读到同一顺序。 |
| 各城区手上的副本 | Consumer 本地缓存目录（RegistryDirectory 快照） | 订单 O 只读本地表；总部失联也不打断派单。 |
| 电话线断了 | 网络分区 / 注册中心故障 | 控制面与数据面分离：断线影响"目录更新"，不影响"已派订单"。 |


> 📌 比喻边界：**"电话点名"和"巡逻队上门"是两种不同的故障发现语义，不是同一件事的两种说法**。前者靠门店自觉，后者靠总部主动——它们决定了"门店死了多久才被发现"。本文 Level 4 会展开这笔账。

## Level 1：为什么台账不能只放一台机器——单点的死法


### 👶 前置知识关卡


- [ ] 目录登记什么、怎么送达、何时不可靠？（见 03 篇 L1–L4）
- [ ] 控制面与数据面的分离：注册中心不在订单 O 的调用路径上。

### Why——上一代方案死在哪


**徒弟**：03 篇说清楚了目录怎么用。那总部就把这本台账放一台机器上，维护成本最低，不行吗？

**老陈**：可以——直到那台机器坏掉或网络抖动。你看控制面发生了什么：


```text
单点台账故障 → 谁受影响？
  ├─ 正在跑的订单：不受影响（O 只读本地表，不进总部）   ← 数据面分离的功劳
  ├─ 新门店开业：登记不进去 → 永远接不到单            ← 扩容卡死
  ├─ 旧门店故障摘除：摘不掉 → 调度台继续派单            ← 故障放大
  └─ 变更通知：收不到 → 新地址永不生效                  ← 发布卡死
```

**单点的死法不是"服务不可用"（数据面还活着），而是"成员变化不可处理"**：不能扩容、不能摘除、不能发布。故障恢复时，全网的服务发现能力被一台机器绑架。


| 朴素方案 | 它本来想解决什么 | 它留下的致命账 |
|---|---|---|
| 单机台账 | 维护最简单 | 一台机器绑死扩容/摘除/发布；进程或网络一抖，成员变更全停。 |
| 主从冷备、坏了人工切换 | 降低宕机概率 | 切换要人、要时间，切换窗口内台账仍不可写；且从库没有选主能力。 |
| 每城区各存各的、不互通 | 彻底不要中心 | 全城没有统一视图：新店开了这家城区不知道，派单靠猜。 |

### What——新结构是什么


```text
单点：      一台总部 → 全体调度台
复制：      总部 N 台，各持一份副本
            ┌─ 同一时刻大家看到的是不是同一份表？   ← 一致性语义（Level 2/3）
            └─ 一台坏了，其余台能不能继续接受登记？  ← 可用性语义
```

关键不变量：**复制的目的不是防丢，而是让"成员变更"在部分节点故障时仍可处理。** 副本一旦多起来，一致性问题立刻产生——这就是 Level 2 的账。

### How——订单 O 的慢动作


```text
① 台账从 1 台扩到 N 台（多副本）
② 门店登记到达任一节点
③ 问题：这个节点怎么让其他节点知道？
      ├─ 立即通知等确认（强一致）→ 慢，但任何时刻读一致
      └─ 先记账后补发（最终一致）→ 快，但存在不一致窗口
④ 门店下线、摘除同样要走这套同步
```

**徒弟**：那就"立即通知等确认"呗，永远一致多好。

**老陈**：你还没付账。等确认意味着：每笔登记要等"足够多的其他节点"点头才能算数；如果点头的人凑不齐（分区），这单登记就永远写不进去——**可用性被一致性换走了**。到底怎么换、换多少，是 Level 2 的完整账。

### Transfer——迁移到其他设计问题


- 任何共享状态的复制（配置中心、分布式锁、消息队列元数据、DNS）都要回答同一问：**节点故障时，写操作是"拒绝"还是"先记账再说"**。
- "复制"不是免费的冗余，它用一致性复杂度换可用性；复杂度必须显式记账。
- 演练设计的第一课：**先杀控制面，看业务面是否还活着**——数据面/控制面分离是所有高可用架构的同一命题。


> 本层留下的新账：副本多了，**副本之间怎么保持一致**？每条登记"先记账后补发"还是"过半确认"，后果完全不同。
>
> 🔴 **口诀**：**单点台账不死在"不可用"，死在"不能变更"。**

## Level 2：副本之间怎么同步——CP 与 AP，先回答两个问题


### 👶 前置知识关卡


- [ ] 复制引出一致性问题（L1 已答）。
- [ ] 03 篇的"目录条目"是"活租约"——条目背后有生命周期（心跳、超时摘除）。

### Why——上一代方案死在哪


**徒弟**：那简单，多抄几份副本，每个节点存一样的不就行了。

**老陈**：抄的时候就有问题：门店 P1 今天上午 10:00 登记，10:00:01 你问节点 A 它知道，问节点 B 它还不知道——**副本之间天然存在不一致窗口**。这个窗口怎么处理，就是"一致性语义"。这不是实现细节，它决定你在故障时看到的行为。

一致性语义不是"选快的"或"选一致的"两个按钮，而是两个问题：

```text
Q1 写操作：一次登记要等几个人点头才算成功？
Q2 读操作：任何时刻，各节点读到的是不是同一份表？
```

| 回答 | 语义 | 付出的代价 |
|---|---|---|
| 过半点头 + 任何时刻读同一顺序 | **CP（强一致）**：写成功 = 已经超过半数的副本记下了，后续读一致。 | 分区时凑不齐过半 → 写被拒绝（牺牲可用性）。 |
| 记下即返回，副本慢慢补 | **AP（最终一致）**：写快，但读可能读到旧值。 | 不一致窗口内，不同调度台看到不同门店表。 |


### What——新结构是什么


**为什么服务发现场景天然倾向 AP？** 看这张表的数据特征：


| 特征 | 服务发现的数据 | 记账类数据（余额/库存） |
|---|---|---|
| 读多还是写多 | 读远多于写（注册/心跳 vs 海量订阅者查询） | 写为主 |
| 不一致的代价 | 地址短暂旧一点点：订单打到一个将下线的店，由 Cluster/重试兜底 | 读到旧余额 → 超卖/错账 |
| 强一致的必要性 | 低：地址本来就在动态变化，"最新"意义有限 | 高：一致性就是正确性 |

- 服务发现的数据**天生允许短暂陈旧**（03 篇 L3 已论证：本地表允许陈旧，目录抖动不打断订单）。
- 因此 AP 付出的"不一致窗口"代价在这里很便宜；而 CP 付出的"分区时拒绝写"代价在这里很贵（扩容/摘除卡死）。
- **但注意：这是针对"服务发现这张表"的结论**。同一个注册中心里如果还放着别的一致性敏感的账（如配置、锁），需要单独评估——标签不能一贴到底。

**ZK（CP，ZAB）与 Nacos 默认（AP，Distro）不是品牌差异，是两种写路径的差异：**

```text
CP 写路径（过半确认）：
门店登记 → 节点 A 发起 → 广播给过半节点 → 过半确认 → 记下并通知所有节点 → 返回成功

AP 写路径（先记账后补发）：
门店登记 → 节点 A 记下 → 返回成功 → 后台把变更复制给其他节点（最终一致）
```


**徒弟**：那 AP 明显更好啊，为什么还有人用 CP 的 ZK？

**老陈**：因为 ZK 不止服务发现这一张表。ZK 常被用来做分布式锁、选主、配置发布——这些数据的"不一致"就是事故本身（两个主同时干活）。**同一套一致性语义不可能同时最优地服务"地址表"和"锁"**。所以 Nacos 才做成双模：临时实例走 AP，需要强一致的数据（如非临时实例/配置在某些模式下）走 JRaft。选注册中心，先问你要在这上面存几类账。

### How——订单 O 的慢动作


```text
场景：台账变成 3 个副本（A、B、C），P1 在节点 A 上登记。

CP（ZAB）：
① P1 登记到达 A → A 广播提案 → B、C 各记一票
② A 收到过半确认（A 自己 + B 或 C）→ 提交 → 通知全节点
③ 任何调度台问任何节点，都看到 P1
④ 若 A、B 失联只剩 C：C 无法凑过半 → P1 登记失败（返回错误）

AP（Distro）：
① P1 登记到达 A → A 本地记下 → 立即返回成功
② 后台把 P1 变更复制给 B、C
③ 此刻问 B、C：可能还没看到 P1（不一致窗口）
④ 网络抖动只影响"复制进度"，不影响"登记是否成功"
```

### Transfer——迁移到其他设计问题


- **判断模板**：任何状态同步系统，先回答 Q1/Q2 两问，再决定语义；不要先选协议。
- 分布式锁、选主、双写迁移 → 通常需要 CP；服务发现、DNS、缓存失效广播 → 通常 AP 够用。
- 混存场景（一个中心既存地址又存锁）→ 拆表或用双模，别指望一个语义通吃。


> 本层留下的新账：CP/AP 是语义层，**具体由哪个协议实现、窗口到底多大**，要看协议深处的写路径——ZAB 怎么广播？Distro 怎么补发？JRaft 又是什么？
>
> 🔴 **口诀**：**先问读多写多、错一会儿多贵；再选抄送还是开会。**

## Level 3：同步规矩的深处——ZAB 全序广播 vs Distro 异步复制 vs JRaft


### 👶 前置知识关卡


- [ ] CP/AP 两个问题的语义（L2 已答）。
- [ ] 写路径：过半确认 vs 先记账后补发。

### Why——上一代方案死在哪


**徒弟**：协议就是"广播"和"补发"的区别吧？我背下"ZK 用 ZAB、Nacos 用 Distro"不就完了。

**老陈**：背名字没意义，要背的是**写路径和故障行为**。三种协议回答的是同一个问题——"一次写之后，其他节点什么时候、以什么顺序看到它"——但答案完全不同，故障时行为也不同。


| 协议 | 系统 | 一致性 | 写路径 | 故障行为 |
|---|---|---|---|---|
| ZAB | ZK 3.x（机制层） | 强一致（全序广播） | leader 提案 → 过半确认 → 提交 | 选主窗口内不可写 |
| Distro | Nacos 2.x 临时实例（机制层） | 最终一致（异步复制） | 写本地 → 返回 → 后台复制 | 节点失联只影响复制，不影响写 |
| JRaft | Nacos 2.x 非临时实例/CP 模式（机制层） | 强一致（Raft 系） | leader 日志复制 → 过半提交 | 选主窗口内不可写 |

### What——新结构是什么


**ZAB（ZooKeeper Atomic Broadcast）——机制层，按 ZK 3.x 文档/源码核验**

```text
正常期：
  所有写必须经 leader（顺序写入 → 给每条写分配全局单调递增的 zxid）
  leader 广播提案 → 过半 follower 确认 → leader 提交 → 各节点按 zxid 顺序应用

  结果：所有节点按同一个顺序应用写 → 任何时刻读到的顺序一致（全序）

选主期（leader 挂了 / 失去过半）：
  全体进入选举 → 选出新 leader → 恢复日志（epoch 递增，旧 leader 的残留提案作废）
  → 选举+恢复完成前，系统不提供写服务（窗口期）

  分区场景：多数派里有 leader → 继续写（少数派不可写，被"隔离"）
           没有多数派 → 全体不可写，等分区恢复
```

- 关键不变量：**写成功 = 已经过半确认 = 该写不可能被回滚**；代价是"凑不齐过半就拒绝写"。
- 全序广播的价值：不只"一致"，而是**顺序一致**——所有节点按同一顺序应用，任何读都等价于某个时点的一致快照。这对锁、选主是硬要求。

**Distro——机制层，按 Nacos 2.x 文档/源码核验**

```text
写路径：
  写请求到达任意节点 → 该节点本地落账 → 返回成功
  → 后台任务把本次变更同步（推送/校验）给其他节点 → 最终一致

无 leader、无全序：
  没有全局顺序，节点间可能短暂看到不同先后
  有反熵：定期/触发式核对差异（类似 gossip 的收敛思想，实现细节按版本核验）
```

- 关键不变量：**写成功 ≠ 其他节点已经知道**；不一致窗口 = 复制延迟。
- 收益：任何节点可写（无单点写路径）、写延迟低、分区不阻塞写。
- 代价：读可能旧；节点间账目短时不一致；**没有全局顺序**（无法可靠做锁/选主）。

**JRaft（Nacos CP 模式）——机制层，按 Nacos 2.x 文档/源码核验**

```text
写路径：
  写到达 leader → leader 追加日志 → 复制到多数节点 → 过半提交 → 返回成功

与 ZAB 的关系：
  同属"日志复制 + 过半提交 + 选主恢复"家族（共识算法）
  与 ZAB 的差异在恢复协议细节（epoch vs term、日志同步方式），语义效果同类
```

### How——订单 O 的慢动作（三种协议下，P1 的一次登记）

```text
ZAB（CP）：P1 登记 → leader 广播 → 过半确认 → 提交。期间 leader 挂了？等选主，
          选主窗口内登记失败/重试。P1 的登记一旦成功，全城立刻一致。

Distro（AP）：P1 登记 → 任一节点记账 → 成功。另一节点稍后补上；
            你问 B 节点可能还说"没有 P1"——直到复制到达。

JRaft（CP）：P1 登记 → leader 追加日志 → 过半确认 → 成功。窗口同 ZAB 系。
```

### Transfer——迁移到其他设计问题


- 三个协议是**三类写路径**的代表：`过半确认 + 全序`（ZAB/Raft 系）、`本地记账 + 异步补发`（Distro/gossip 系）。
- 判断模板：数据需要全局顺序（锁、选主、事件溯源）→ 全序系；数据只需要最终可见（地址、缓存、指标）→ 反熵系。
- 混合形态很常见：一个系统里"元数据强一致 + 业务数据最终一致"（如 Raft 管成员，gossip 管数据）——Nacos 双模就是这个思路的实例化。


> 本层留下的新账：协议再正确，**遇到分区/选举/节点故障时，调用方（调度台）看到的窗口到底是什么**？空壳、摘除、保护、缓存——这是 Level 4。
>
> 🔴 **口诀**：**过半确认换顺序，先记账补发换窗口；要顺序选开会，要快选抄送。**

## Level 4：故障窗口里调度台看到什么——session、心跳与本地缓存


### 👶 前置知识关卡


- [ ] 三种协议的写路径（L3 已答）。
- [ ] 03 篇 L4：目录条目是"活租约"，目录收敛是异步的、有残留。

### Why——上一代方案死在哪


**徒弟**：总部台账就算有 3 份副本，电话线全断了呢？调度台是不是就哑了？

**老陈**：恰恰相反——这正是 03 篇"控制面/数据面分离"的最后一层红利：**调度台手里的副本（本地缓存目录）不依赖总部**。但你要分清两件事：**"订单 O 还能派"（数据面）和"门店表还新"（控制面）**。断线时前者照常，后者冻结——新店开业、旧店关停都看不见。还有一层更微妙的账：**门店死没死，靠什么发现？**这就是心跳与探活的语义。

### What——新结构是什么


**两个故障发现语义（机制层，按具体版本文档核验）**

```text
电话点名（客户端心跳）：
  门店定期向总部报"我还开着"。总部在一段时间内没听到 → 认为门店失联 → 摘除。
  语义：门店自觉续约，续约断了才被发现。发现延迟 = 心跳周期 × 容错倍数。
  → ZK 临时节点（session 语义）与 Nacos 临时实例（心跳/长连接语义）都属此类。

巡逻队上门（服务端主动探活）：
  总部定期主动检查门店端口/健康。检查失败即摘除。
  语义：总部主动出击，门店死没死由总部探测决定。发现延迟 = 探活周期。
  → Nacos 持久实例（非临时实例）属此类（机制层）。
```

**关键点：这两者不是"实现差异"，是"发现责任在谁"的语义差异。**

- 临时实例（客户端心跳）：**客户端进程死了 → 心跳停 → 总部摘除**。适合大多数业务服务：进程死 = 服务死。
- 持久实例（服务端探活）：**客户端进程死了，节点还在**（需要显式注销/探活失败才摘）。适合"注册主体比进程长"的场景（如控制台登记的静态地址、长期资源）。
- 陷阱：**心跳语义下，进程活着但业务卡死（GC 长停顿、连接池耗尽）时，心跳仍可能正常**——"在心跳"不等于"能接单"。这就是 03 篇"注册 ≠ 接单"的底层原因之一。

**consumer 本地缓存目录（RegistryDirectory）——Dubbo 3.3.4 机制，E03 已观察**

```text
Consumer 启动 → 订阅 → 收到地址列表 → 维护本地候选集合（快照）
后续 O 只读本地候选集合，不访问注册中心（03 篇 L3 已论证）
总部失联 → 本地表不动 → 订单照常派给快照里的门店（可能打到已下线的店，由 Cluster 兜底）
```

**Nacos 保护阈值（protectThreshold）——机制层，按 Nacos 2.x 文档核验**

```text
当健康实例占比低于保护阈值（举例：0.8；默认值按你的版本核验）时，Nacos 返回"不健康但存在的实例"给订阅者
目的：防止大规模故障时地址列表瞬间清空 → 全部调度台失去候选 → 雪崩
代价：订阅者会拿到部分不健康地址 → 调用失败率上升，由上层容错消化
```

**E03 实测复用（2026-08-11 本机）：**

- provider 进程被停止后，Nacos 里接口级 service 名**残留为空壳**（0 实例，观察期持续存在）——"服务名的生命周期比实例长"（03 篇 L4 实测）。
- consumer 在无映射源时，日志报 `MetadataServiceNameMapping: Local cache mapping is empty`，随后 `No provider available`——**本地缓存不存在/为空时，调度台直接失去派单能力**（03 篇 L2 实测）。
- provider 启动时 Consumer/Provider 双方都会发起订阅并收到通知；订阅的接口无实例时，Dubbo 收到**空地址列表**并清空本地候选（03 篇 L3 实测）——**注意：这是注册中心主动推空，不是注册中心故障**。区分"目录主动变空"（业务上有意义）与"目录联系不上"（保留旧表），是排障第一课。

### How——订单 O 的慢动作（故障注入视角）

```text
场景 A：注册中心整体挂掉（控制面断线）
  ① 调度台本地表：不动（快照仍在）→ E04 实测：Nacos 死 ≥68s 派单全 OK
  ② 订单 O：照常从快照选店直连 → 业务不受影响
  ③ 但：新店登记不了、旧店摘不掉、变更通知收不到
  ④ 恢复后：活节点自动重连并全量对齐 → E04 补测：provider 在 Nacos 重启后 11.4s 自动重注册
     （E04 里 provider 已死所以无人重注册、服务残留 0 实例——"自愈"的前提是节点还活着）
  ⑤ E04 新发现：Nacos 重启恢复瞬间可能向订阅者推空地址列表 → 清空本地候选 → 短暂 FAIL
     （与 ① 不矛盾：推空是"目录主动变空"语义，与"目录联系不上保留旧表"是两种行为，排障要分清）
  （①② 由 E03 本地表观察 + E04 实测支撑；③④⑤ 见 experiment-004 记录）

场景 B：门店进程突然死亡（心跳语义）
  ① 门店心跳停止
  ② 总部在"心跳周期 × 容错倍数"后才摘除（机制层，具体阈值按版本核验）
  ③ 摘除前：调度台本地表仍含该店 → 订单打到死店 → 失败 → Cluster 兜底（05 篇的账）
  ③' 但 kill -9 瞬间**已在途**的订单（请求已发出、等待响应）兜不住：连接被切断 → 在途请求以 CANCELLED 取消（tri 异步完成）→ 异常晚于 failover 重试窗口冒出 → 直接 FAIL。
     E05-2 实测：kill -9 单个 provider（retries=2）三轮中一轮出现 1/300 FAIL，异常链
     `RpcException: ExecutionException: StatusRpcException: CANCELLED`，cost=5ms 且无重试流量；
     其余两轮 0 FAIL（kill 后新请求的连接不可用被 failover 捕获并重试成功）。
     语义：failover 只兜"发起时失败"，兜不住"在途被切断"——这就是"先停新单、再清在途"必须存在的第二个理由（第一个是防幂等破坏）。
  ④ 摘除后：变更通知 → 本地表移除

场景 C：大规模故障，健康实例占比跌破保护阈值
  ① 总部开始返回不健康实例 → 本地表"回填"了不健康地址
  ② 订单打到坏店概率上升 → 错误率上升但候选集不真空
  ③ 意图：用"部分失败"换"不雪崩"
```

**徒弟**：那我把心跳周期调短一点，发现死店不就能快一点？

**老陈**：心跳周期短 → 每个门店上报频率高 → 台账写入量线性上升（还记得 03 篇的写放大吗？心跳也是按条目计费的）。**发现速度是用写入量换的**。权衡点：业务能容忍订单打向死店的窗口 vs 台账的心跳压力。另外还有第三种思路：客户端主动上报关闭（优雅下线）——比被动发现快得多，这正是 03 篇"先停新单、再清在途"的意义。

### Transfer——迁移到其他设计问题


- **"发现责任在谁"是通用问题**：健康检查分"自报（心跳）"与"他查（探活）"两类，K8s liveness/readiness、负载均衡器健康检查、消息消费者心跳都是同一语义选择。
- 保护阈值 = **用错误率换候选集不真空**，与熔断（主动停止调用）互补但不同：保护在发现层兜底，熔断在调用层兜底。
- 排障口诀：**先问"谁在发现故障"，再问"故障发现多久后生效"**——别把"进程没死"当"服务健康"。


> 本层留下的新账：语义都清楚了，**那到底怎么选、怎么演练、怎么验收**？一张决策卡 + 一次混沌演练模板。
>
> 🔴 **口诀**：**点名靠自觉、探活靠主动；断线不断单，变新卡在总部。**

## Level 5：选型与演练——把一致性语义变成上线决策


### 👶 前置知识关卡


- [ ] CP/AP 语义（L2）、三种协议写路径（L3）、故障窗口（L4）。

### Why——上一代方案死在哪


**徒弟**：结论不就是"Nacos 默认 AP 适合服务发现"吗？选它完事。

**老陈**：那是广告语，不是决策。选型要回答的是**你的故障窗口预算**：你接受订单打向死店的窗口是 10 秒还是 1 分钟？你的心跳压力预算多少？你有没有能力做控制面故障演练？——**Nacos 的标签（AP）只决定"机制上允许不一致"，不决定"你的环境里不一致有多大"**。

### What——新结构是什么


**注册中心选型核对清单（不是评分表，是问题清单）：**


| 问题 | 为什么必须先答 | 答案如何影响选型 |
|---|---|---|
| 这张表上还存什么？ | 混存锁/配置 → 需要 CP 能力 | 只存地址 → AP 足够；混存 → 双模/拆表。 |
| 死店发现窗口预算？ | 决定心跳/探活语义与心跳压力 | 窗口紧 → 心跳密或客户端主动上报（优雅下线）。 |
| 分区时宁可"拒绝登记"还是"接受但不保证新"？ | 决定 CP/AP 取舍 | 扩容/发布不能停 → 倾向 AP；锁语义 → CP。 |
| 控制面故障时订单可不可以继续？ | 决定本地缓存策略 | 必须继续 → 缓存目录 + 快照年龄监控。 |
| 保护阈值开不开？ | 决定大规模故障行为 | 开 → 用部分错误率换不雪崩。 |
| 有没有能力演练？ | 决定你敢不敢上线 | 没有演练 → 先做故障注入再谈切换。 |

**选择矩阵（机制层语义，不是厂商评分）：**

| 场景特征 | 倾向 | 理由 |
|---|---|---|
| 纯服务发现、读多写少、可容忍短暂陈旧 | AP（Distro） | 分区不阻塞写；不一致窗口由调用层兜底。 |
| 锁 / 选主 / 配置发布，顺序就是正确性 | CP（ZAB/JRaft） | 全序广播保证顺序一致；代价是分区不可写。 |
| 需要两种语义共存 | 双模（Nacos 临时实例 AP + 非临时/CP 数据） | 一张表一个语义，不互相污染。 |
| 已有 ZK 存量、无新一致性需求 | 维持或评估迁移成本 | 迁移成本 > 收益时，先算账。 |

### How——订单 O 的慢动作（一次真实的切换决策）

```text
① 列出所有"要写进台账的数据类型"（地址？配置？锁？）→ 决定语义组合
② 为每种语义定故障窗口预算（死店发现窗口、分区写可用性）
③ 搭建最小集群 → 杀一个节点 → 观察：登记是否停？调度台是否仍派单？
④ 网络分区演练（停多数派/停少数派）→ 记录窗口
⑤ 保护阈值 + 心跳参数按预算调 → 压测台账写入压力
⑥ 结论：能过演练 → 上线；不能过 → 回到 ① 或换语义
```

**徒弟**：这套流程里哪个最容易做假？

**老陈**：最容易做假的是"只演练了注册中心集群健康"——节点都活着、健康检查全绿，但**订阅者的本地表从未更新、候选集早已陈旧**。演练必须从 Consumer 视角验收（03 篇坑 12）：订阅延迟、候选集、空地址次数。控制面绿 ≠ 调度台的表新。

### Transfer——迁移到其他设计问题


- 选型清单可迁移到**任何控制面组件**（配置中心、消息集群元数据、DNS 服务）：先列数据类、定窗口预算、再演练。
- "标签 → 决策"的捷径是故障演练的敌人：AP/CP 只是语义起点，窗口必须实测。
- 验收视角必须是**消费方**（订阅者/调用方），不是组件自身的健康指标。

## Level 6：迁移——gossip、全序、quorum，一套方法论


### 👶 前置知识关卡


- [ ] 三种协议（L3）、窗口（L4）、选型（L5）。

### Why——上一代方案死在哪


**徒弟**：我已经会背 ZAB/Distro/JRaft 了，是不是就懂分布式同步了？

**老陈**：会背三个名字不等于会设计。真正该带走的是**同步机制的三个家族**——每个家族解决一类问题，你可以把它们用到任何状态同步场景（注册中心、配置中心、DNS、缓存失效、日志复制）。

### What——新结构是什么


```text
同步机制家族（按"顺序与确认"的强弱排列）：

全序广播家族（ZAB / Raft / Multi-Paxos）
  特征：全局顺序 + 过半提交 + 选主
  解决：顺序即正确性的问题（锁、选主、事件日志、状态机复制）
  代价：凑不齐过半不可写；选主窗口
   系统：ZK、etcd、Nacos CP 模式、Consul KV（其服务注册数据走 gossip，见反熵家族）

异步复制家族（Distro / MySQL 主从 / 缓存失效广播）
  特征：写本地即返回 + 后台补发
  解决：读多写少、可容忍陈旧的数据（地址表、DNS 记录、缓存）
  代价：不一致窗口、无全局顺序
  系统：Nacos AP 模式、Cassandra（部分）、DNS

反熵家族（gossip / 定期对账）
  特征：周期/触发式交换摘要、弥合差异、最终收敛
  解决：大规模成员发现与对账（没有强中心时）
  代价：收敛时间不确定、无强一致
  系统：Cassandra、Consul（gossip 层）、Nacos（同步/核对机制）

共性结论：
  ① 三个家族不是互斥而是分层：一个系统可同时用全序管"元数据"，用反熵管"数据"
  ② 一致性语义是产品决策，不是协议属性：同一个系统（Nacos）可切 AP/CP
  ③ "窗口"是这三家共同的度量：不一致窗口 / 选主窗口 / 收敛窗口
```

### How——订单 O 的慢动作（把方法论迁移出去）

```text
场景：你在设计一个"分布式配置下发"系统。
① 配置数据分两类：版本元数据（需要顺序，谁先谁后）→ 全序家族
                   配置内容（最终可见即可）→ 异步/反熵家族
② 故障窗口预算：分区时配置写不写？→ 决定 CP/AP 取舍
③ 验收视角：订阅者是否拿到一致配置？→ 不从服务端健康看

—— 同一套三问，从注册中心搬到配置中心。
```

### Transfer——迁移到其他设计问题


- 看到任何"多副本 + 同步"设计，先归类：要顺序吗？要过半确认吗？窗口多大可接受？
- 三个家族是**复用词表**：你的系统里该用哪个家族，取决于数据语义，不取决于厂商。
- 跨系统经验：K8s 的 etcd（全序）+ kubelet 缓存（本地快照）、DNS 的 TTL（陈旧窗口）——**同步语义 + 本地缓存 + 陈旧边界**是分布式系统设计的万能三段论。


> 本篇闭环：**单点死法 → 复制引出 CP/AP → 协议实现窗口 → 窗口内靠本地缓存兜底 → 选型靠演练 → 方法论可迁移。** 下一篇进入订单 O 的下一站：调度台怎么在候选门店里选一家、选错之后怎么承担代价（Router、LoadBalance、Cluster）。
>
> 🔴 **口诀**：**要顺序，开会；要快，抄送；要收敛，对账。**

## 📚 版本勘误表


| ❌ 常见说法 | ✅ 更准确的说法 |
|---|---|
| Nacos 是 AP、ZK 是 CP，选型完事。 | 标签只是语义起点；先答两问、定义窗口预算、做演练（本文 L5 清单）。 |
| 注册中心挂了，服务就全挂了。 | 数据面靠 consumer 本地缓存目录继续工作；控制面冻结（变更不可见）。 |
| ZAB 就是 Raft 换了个名字。 | 同属共识/全序家族，但恢复协议与日志同步细节不同（机制层）；语义效果同类。 |
| 心跳越快，系统越可靠。 | 发现窗口用写入压力换；心跳只是"自报"语义，还有"他查"（探活）与主动上报（优雅下线）。 |
| 进程活着 = 服务健康。 | 心跳正常 ≠ 能接单（GC/连接池问题心跳照样发）；健康要分探活与业务层。 |
| 空地址列表 = 注册中心出故障了。 | 空列表可能是订阅语义的正常推送（目录主动变空）；与"控制面断连"是两种不同情况。 |
| AP 就是"不要一致性"。 | AP 是有界的不一致（最终一致 + 窗口可度量）；只是不强保证"任何时刻全一致"。 |
| 保护阈值会让系统变差。 | 阈值用部分错误率换候选集不真空，是防雪崩的发现层兜底；与熔断互补。 |

## 🏆 生产决策卡


### 决策卡 1：注册中心高可用部署与演练


**场景与判断**：集群决定注册中心多副本部署。


| 机制到决策映射 | 落地 |
|---|---|
| 单点死法 | 至少两节点起步；控制面故障 ≠ 数据面故障，演练分开做。 |
| Consumer 视角验收 | 演练观察订阅延迟、候选集大小、空地址次数，不只服务端健康。 |
| 故障注入 | 杀一个节点 → 观察登记可用性；停多数派 → 观察分区窗口；恢复 → 观察对账。 |

- **不能做的错误决策**：单点部署、或演练只查"节点都活着"。
- **验收指标**：节点故障时成员变更是否可用、Consumer 候选集与订阅延迟、恢复后对账耗时。


### 决策卡 2：语义选型（CP / AP / 双模）


**场景与判断**：决定注册中心写语义。


| 机制到决策映射 | 落地 |
|---|---|
| 数据类 | 列出所有要存的账：只有地址表 → AP 起步；含锁/选主 → CP 或拆表。 |
| 窗口预算 | 定义"死店发现窗口"与"分区时写可用性"的预算值。 |
| 心跳压力 | 按条目数与心跳频率估算台账写入量（写放大同样适用于心跳）。 |

- **不能做的错误决策**：用厂商标签替代窗口预算；混存不同一致性敏感度的数据且不拆表。
- **验收指标**：不一致窗口实测、分区演练行为、写入压力指标。


### 决策卡 3：故障发现语义（心跳 vs 探活 vs 主动上报）


**场景与判断**：决定"死店多久被发现"。


| 机制到决策映射 | 落地 |
|---|---|
| 自报（心跳） | 大多数进程型服务适用；注意"心跳 ≠ 健康"。 |
| 他查（探活） | 注册主体比进程长、或需要总部主动确认时用。 |
| 主动上报（优雅下线） | 计划发布必用：先停新单再清在途，比被动发现快一个数量级。**注意：被动发现（哪怕 failover 重试）也兜不住"在途被切断"——E05-2 实测在途请求 kill 瞬间 CANCELLED 直接 FAIL（1/300），failover 只兜"发起时失败"。另外优雅停机本身也要按版本实测（08 篇 E08：3.3.4 triple 的"送完在途"不可靠，PING ack 即断连）。** |

- **不能做的错误决策**：只靠被动发现做计划发布；把心跳周期调到伤害写入量。
- **验收指标**：死店发现耗时、优雅下线耗时、发现期调用错误率。


### 决策卡 4：保护阈值与雪崩防护


**场景与判断**：大规模故障时是否允许候选集"回填"不健康地址。


| 机制到决策映射 | 落地 |
|---|---|
| 阈值语义 | 健康占比跌破阈值 → 返回不健康实例，用部分错误率换候选不真空。 |
| 与熔断分工 | 保护在发现层兜底；熔断在调用层兜底（05 篇展开）。 |
| 预算 | 按"可承受的坏店占比"反推阈值，演练验证。 |

- **不能做的错误决策**：阈值不开也不演练；或开满导致常态大量打坏店。
- **验收指标**：故障期错误率、候选集大小、恢复期收敛耗时。

## 🌍 跨语言 / 跨运行时视角


| Dubbo 视角 | 跨语言同构对象 | 不变的问题 |
|---|---|---|
| ZAB（ZK） | etcd/Raft、Consul KV（Raft；注册数据走 gossip）、Paxos 系 | 顺序即正确性时，用全序广播 + 过半确认。 |
| Distro（Nacos AP） | Cassandra、DNS 复制、MySQL 主从 | 读多写少、可容忍陈旧时，先记账后补发。 |
| 临时节点/session | K8s Lease 对象、gRPC 健康检查、Eureka 心跳续约 | 客户端死亡如何被发现：自报 vs 他查。 |
| RegistryDirectory 缓存 | Envoy xDS 缓存、DNS 客户端缓存、K8s informer 缓存 | 控制面失联时数据面如何继续、陈旧边界在哪。 |
| 保护阈值 | K8s 驱逐、熔断保护、DNS 故障降级 | 用部分失败换整体可用，阈值如何定。 |
| 双模（AP+CP） | 成员元数据用 Raft + 数据用 gossip 的混合架构 | 一个系统多种数据语义，如何分层不污染。 |


### 跨语言后仍成立的 7 条判断力


1. **单点控制面不死在"不可用"，死在"不能变更"。**
2. **复制引出两问：写等几人点头、读是否一致——先答问，再选协议。**
3. **一致性语义是产品决策，不是协议属性（同一系统可切 AP/CP）。**
4. **三种协议 = 三个家族：全序 / 异步复制 / 反熵，按数据语义复用。**
5. **故障发现分自报与他查，发现窗口 = 周期 × 容错倍数，用写入量换。**
6. **控制面断线时数据面靠本地缓存继续，但"目录更新"冻结——分离监控。**
7. **验收视角是消费方：订阅延迟、候选集、空地址——不是组件自检报告。**
