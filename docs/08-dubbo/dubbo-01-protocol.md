|---|---|---|

## 🏭 全文唯一比喻地图

```text
订单 O（Invocation）
   │ 放进
   ▼
┌─ 配送信封（协议）───────────────────────────┐
│ ① 封口：消息边界（帧/长度头）               │
│ ② 单号：请求 ID / Stream ID（请求-响应配对）│
│ ③ 单据：方法名 + 参数（RPC 元数据）         │
│ ④ 签收章：status / grpc-status（成败语义）  │
│ ⑤ 装车：连接复用（一辆车装多单）            │
│ ⑥ 电话：连接建立/保活/超时（对方在不在）    │
└─────────────────────────────────────────────┘
   │ 信封有两种厂商：
   │ 私有专线（dubbo 协议，只有 Dubbo 读得懂）
   │ 开放高速（Triple/HTTP/2，gRPC 全兼容）
   ▼
骑手（Netty 连接）送往后厨
```

| 信封元素 | Dubbo 技术对象 | 它负责的唯一一件事 |
| ---- | ---- | ---- |
| 封口 | 帧/长度头（dubbo 16B 头；HTTP/2 9B 帧头） | 规定一条消息在哪结束 |
| 单号 | requestId（dubbo）/ Stream ID（HTTP/2） | 响应与请求配对，不串单 |
| 单据 | 接口全名+方法+参数（header/body） | 传递 RPC 元数据 |
| 签收章 | status 字段 / grpc-status + grpc-message | 表达调用成败与错误细节 |
| 装车 | 连接复用（串行 / 多路复用） | 一条连接运多单 |
| 电话 | 连接建立、保活、超时 | 对方在不在 |
| 信封厂商 | dubbo 协议（私有）/ Triple（开放标准） | 谁读得懂这封信（生态边界） |

> 📌 比喻边界：**信封不决定盒子里装什么**——信封管"边界/配对/状态"，盒子里装的序列化格式（Hessian2/protobuf）是另一个正交维度（02 篇）。换了信封，盒子里还是 Hessian2；想 gRPC 互通，盒子和信封要一起对齐。

## Level 1 为什么需要信封：网络传输的四件麻烦事

### 👶 前置知识关卡

* [ ] 知道 TCP 是"字节流"（没有消息边界）
* [ ] 知道 HTTP 请求-响应模型与 header/body 结构

### 1.1 徒弟的直觉

徒弟：

> 协议不就是"序列化完往 socket 里一写，对面读出来"吗？为什么 Dubbo 要搞出 dubbo 协议、Triple 两个信封？

老陈：

> 你把"往 socket 写字节"想得太简单了。**TCP 是一条字节流，没有边界**——你写两次，对面可能一次读完；你写一次，对面可能分三次读。更麻烦的是：
>
> - 对方怎么知道"一个请求到这儿就结束了"？（**消息边界**）
> - 请求和响应混在一条连接里，怎么配对？（**请求-响应关联**）
> - 怎么知道这次调用了哪个方法、带了什么附加信息？（**RPC 元数据**）
> - 连接断了怎么办、谁来通知？（**状态与失败语义**）
>
> 这些答案全由"信封"（协议）规定。**信封规定消息的格式、边界、配对方式、状态语义**——这是协议的全部职责。

### 1.2 协议的职责清单（每个协议必须回答的问题）

| 协议要回答的问题 | 比喻 | 对应机制 |
| ---- | ---- | ---- |
| 一个请求在哪结束 | 信封的封口 | 帧（Frame）：长度头 / 定界符 |
| 响应属于哪个请求 | 信封上的单号 | 请求 ID / Stream ID |
| 调用的方法和参数在哪 | 信封内的单据 | Header + Body（方法名、序列化数据） |
| 调用成败怎么表达 | 信封上的签收章 | 状态码（HTTP status / grpc-status / 协议错误码） |
| 一次可以运几个单 | 一辆车装几个信封 | 连接复用（串行 / 多路复用） |
| 对方在不在 | 电话通了没 | 连接建立、保活、超时 |

> **说人话**：你学任何 RPC 协议，就盯着这六问看。dubbo 协议和 Triple 的差异，本质是**对这六问的回答方式不同**——一个是私有的，一个是开放标准。

### Transfer——迁移到其他设计问题

- **任何传输层都要回答同一组问题**：TCP 的流式无边界、HTTP 的请求-响应、gRPC 的流式——都是在为六问选答案；协议 = 约定的答案集。
- **分层是职责边界不是性能手段**：协议层只解决传输语义，业务语义留给上层；把业务逻辑塞进协议层是设计腐化的开始。

> 本层留下的新账：六问有了，但**两套信封的答案完全不同**——私有的 dubbo 专线 vs 开放的 HTTP/2 高速，它俩各自的账在哪？
>
> 🔴 **口诀**：协议不是格式，是一整套问题的答案集；六问先背熟再谈协议。

## Level 2 dubbo 协议：省钱的专线铁路，但铁轨是私有的

### 👶 前置知识关卡

* [ ] 知道二进制协议与文本协议的差别
* [ ] 知道序列化（Hessian2）与传输协议是两层

### 2.1 2.7.x 时代的答案：专线铁路

**dubbo 协议（2.7 默认）的六问答案**：

```text
消息边界：私有二进制帧（header 16 字节 + body）
请求配对：请求 ID（requestId）
方法元数据：固定头里带 dubbo 版本/接口/方法/参数类型 + body 序列化数据
状态语义：Response 对象里的 status 字段（OK/ERROR/...）
连接复用：一条 TCP 长连接上请求串行发出，按 requestId 配对返回
协议协商：私有的 magic 头 0xdabb
```

**它为什么好**：帧头极简（16 字节固定头 + 可变扩展头），二进制紧凑，同语言内序列化直接——**在"Java 调 Java、直连、私有网络"的场景里，这是最省钱的专线铁路**。

### 2.2 E01 实测：直连场景 dubbo 协议确实更快

本机同 JVM 双协议直连压测（同序列化 Hessian2，方向性参考）：

```text
dubbo  p50=356~427us  qps=1923~2440
triple p50=825~1291us qps=687~1053
```

与官方 benchmark（research R7）方向一致：**直连场景 Triple 无优势**。为什么？因为 dubbo 协议的信封开销更小（16 字节私有帧头 vs HTTP/2 帧 + HPACK 头压缩 + 更重的协议栈）。

补充（E01 §2.1.1，信封 × 打包盒交叉压测）：**盒子（序列化）也影响性能**——本机自实现 Kryo 扩展后，`dubbo+kryo` 比 `dubbo+hessian2` 快约 25%、`triple+kryo` 快约 20%（方向性）。协议与序列化是两个独立旋钮，02 篇展开。

### 2.3 它死在哪儿：私有铁轨的三笔账

| 账 | 后果 | 谁买单 |
| ---- | ---- | ---- |
| **铁轨私有**：magic 头 0xdabb + 私有帧语义，只有 Dubbo 懂 | 网关、LB、网格（Istio）、跨语言客户端全部无法解析 | 云原生团队、多语言团队 |
| **不能流式**：请求-响应模型，一问一答 | 无法做流式传输（SSE/gRPC streaming 场景） | 数据同步、AI 推理流式场景 |
| **调试黑盒**：curl/wireshark 看不懂 | 排障只能靠框架日志 | 所有运维 |

> **祛魅**：dubbo 协议不是"性能不行"才被换的——**它性能很好，死在自己的私有性上**。3.x 换 Triple 不是性能手术，是"开放化"手术（Level 5 决策）。

### Transfer——迁移到其他设计问题

- **私有协议的通用死法**：生态读不懂 = 隐性成本（私有 RPC 协议、专有消息格式都一样）——评估任何私有方案先算"谁要读它、谁来维护客户端"。
- **替代决策先找真实死因**：不是"最慢的"被换，是"成本最高的"被换；先问旧方案死在哪个维度，再谈新方案。

> 本层留下的新账：私有的账清楚了，**开放的答案呢**？——Triple/HTTP/2 怎么回答六问？多路复用又解决了什么？
>
> 🔴 **口诀**：私有协议死于生态成本，不是性能；换方案先找旧方案的真实死因。

## Level 3 Triple：开放的 HTTP/2 高速公路

### 👶 前置知识关卡

* [ ] 知道 HTTP/1.1 的队头阻塞（一条连接一次只能一个请求）
* [ ] 知道 HTTP/2 的流（Stream）与多路复用

### 3.1 Triple 的六问答案

**Triple（3.x 主推）的六问答案**：

```text
消息边界：HTTP/2 帧（9 字节帧头，DATA 帧承载 body）
请求配对：Stream ID（多路复用，一条连接并发多流）
方法元数据：HTTP Path（/接口全名/方法名）+ Header（content-type 等）+ body
状态语义：HTTP/2 200 + trailers 里的 grpc-status / grpc-message（gRPC 语义）
连接复用：一条 HTTP/2 连接上多流并发（Stream 多路复用）
协议协商：HTTP/2 prior-knowledge / ALPN，或 HTTP/1.1 降级（端口统一服务器）
```

### 3.2 HTTP/2 三个关键机制（对照信封讲）

```text
① 流（Stream）：一条连接 = 一捆信封，每个信封一个编号（Stream ID）
   → 多路复用：小包裹慢，大包裹快，互不排队（应用层不再队头阻塞）
② 头部压缩（HPACK）：信封上的地址栏反复写同样内容 → 查字典压缩
   → 小请求头开销比 HTTP/1.1 文本头小得多
③ 二进制分帧：所有内容切成 9 字节头的帧
   → 协议栈更规整，但帧本身有开销（对极端小包不友好）
```

### 3.3 祛魅：队头阻塞的真相（两层）

徒弟：

> HTTP/2 解决了队头阻塞，那 Triple 是不是就没有队头阻塞了？

老陈：

> 只解决了一半，这是全行业最容易被忽悠的点：

```text
HTTP/1.1 的队头阻塞（应用层）：一条连接一次只能一个请求 → HTTP/2 多路复用解决 ✅
TCP 层的队头阻塞（传输层）：一个包丢了，整个 TCP 流都等重传 → HTTP/2 依然存在 ❌
```

> 所以：**多路复用解决的是"应用层排队"，TCP 层丢包重传仍会阻塞整个连接**（这是 HTTP/3/QUIC 想解决的下一层问题，QUIC 一个流一个传输通道）。Triple 也一样——别跟人说"HTTP/2 没队头阻塞"。

### 3.4 E00/E01 实测：端口统一服务器

E00 日志：`Start NettyPortUnificationServer bind /0.0.0.0:50051`——**端口统一服务器**（按首包协商协议）。E01 实测证实：

```text
HTTP/2 prior-knowledge 调用  → 成功（HTTP/2 200）
HTTP/1.1 调用                → 也成功！alt-svc: h2=":50052"（通告支持 h2）
```

> **说人话**：Triple 的服务端口像一个"多语种前台"——说 HTTP/2 也行、说 HTTP/1.1 也行，服务先听你说哪种语言再切换。这让 Triple 服务的调试门槛降到"curl 就能调"（3.5）。

### 3.5 开放信封实测：curl 直接调业务

E01 关键实验（原样引用）：

```text
$ curl --http2-prior-knowledge -X POST -H "content-type: application/json" \
    -d '{"name":"O","sequence":1}' \
    "http://192.xxx.x.xxx:50052/com.zhiya.dubbo.demo.api.GreetingService/greet"

HTTP/2 200
content-type: application/json

"Hello O (sequence=1)"
```

**一个 curl 就调通了业务**——不需要 Dubbo 客户端、不需要 .proto。这对三层人意义完全不同：

| 角色 | dubbo 协议时代 | Triple 时代 |
| ---- | ---- | ---- |
| 网关/运维 | 无法解析，只能放行或放弃 | 标准 HTTP，路由、限流、日志直接上 |
| 多语言团队 | 自己实现 Dubbo 协议客户端 | curl/gRPC 客户端直接调 |
| 排障 | 看框架日志猜 | curl + 浏览器 + 抓包工具直接看 |

### Transfer——迁移到其他设计问题

- **HTTP/2 三机制（流/HPACK/二进制分帧）是通用传输设计**：HTTP/3 继承流思想换 QUIC 传输、gRPC/Thrift 都选标准传输——学一次 HTTP/2，整个传输层半本书就通了。
- **"多路复用"要问解决哪层的排队**：任何复用方案（连接池、线程池、多路复用）先问它消除的是哪层的等待，另一层可能还在。
- **多语种前台（端口统一）是友好服务入口的设计**：ALPN、alt-svc 通告、协议降级都是同一思路——入口不挑食，能力往下兼容。

> 本层留下的新账：信封语义都通了，但**要跟 gRPC 生态互通**——"兼容"到底兼容到什么程度？协议层全对就能调通吗？
>
> 🔴 **口诀**：流解应用层、QUIC 解传输层；多路复用不是万能药。

## Level 4 gRPC 兼容语义实测：信封是 gRPC 的，盒子可以是别的

### 👶 前置知识关卡

* [ ] 知道 gRPC 的"状态码在 trailers 里"的设计（HTTP 200 + grpc-status）

### 4.1 gRPC over HTTP/2 的四个语义约定（Specification）

gRPC 在 HTTP/2 上定义的语义（Triple 完整实现）：

```text
① HTTP 状态码 200 不代表调用成功 → 真正的成败在 trailers 的 grpc-status
② content-type: application/grpc（+ 可选 +proto 后缀）
③ te: trailers（声明响应会带 trailers）
④ 错误细节在 grpc-message（人类可读）+ grpc-status（机器可读）
```

### 4.2 E01 实测：手搓 gRPC 帧调用 Triple

用 curl 构造标准 gRPC 帧（`0x00 压缩标志 + 4字节大端长度 + protobuf payload`）调用：

```text
HTTP/2 200
te: trailers
content-type: application/grpc
tri-exception-code: 3

grpc-status: 2
grpc-message: Internal Server Error
```

**协议层 100% gRPC**：HTTP/2 200 + application/grpc + trailers + grpc-status——任何标准 gRPC 客户端都能解析。

**业务失败（grpc-status: 2）的原因**：POJO 接口在 triple 下默认 Hessian2 序列化（Implementation 3.3.4），而纯 gRPC 客户端按 protobuf 解码 payload → 解码不匹配。

### 4.3 结论：信封与盒子是两个维度

```text
信封（协议）＝ 配送信封：Triple 就是 gRPC over HTTP/2，语义全兼容 ✅
盒子（序列化）＝ 打包盒：POJO 默认 Hessian2；要真·gRPC 互通 → 用 protobuf 盒子（02 篇）
```

> **祛魅**：别以为"Triple 兼容 gRPC" = "gRPC 客户端能直接调我现有的 Dubbo 接口"。**协议语义兼容 ≠ 序列化互通**。想让纯 gRPC 客户端（Go/Python）调通，接口得用 proto 定义 + protobuf 序列化（02 篇展开）。E01 的 grpc-status: 2 就是这条分界线的实测。

### Transfer——迁移到其他设计问题

- **兼容是分层的**：语义契约（信封）与编码契约（盒子）两层对齐才互通——验收任何"兼容"先列契约清单，逐层测试。
- **"手搓协议帧"是协议学习的最高效手段**：读规范 → 构造字节 → 看对端反应（E01 的 curl gRPC 帧就是模板）——用字节对话验证理解，不靠文档背诵。

> 本层留下的新账：机制与边界都清楚了，剩下的是**决策**——直连更慢为什么还迁？收益到底在哪个场景？
>
> 🔴 **口诀**：兼容要两层契约对齐；用字节对话验证协议理解。

## Level 5 决策：直连性能不占优，为什么还要迁

### 👶 前置知识关卡

* [ ] 知道"直连场景"与"经网关场景"的区别
* [ ] 知道灰度迁移（双协议并存）的思路

### 5.1 先承认事实：直连确实更慢

E01 + 官方 benchmark（research R7）双重证据：**直连、同语言、小 payload 场景，dubbo 协议更快**。任何告诉你是为了性能迁移 Triple 的，都是没看数据的。

### 5.2 那迁移的收益在哪：场景变了

| 场景 | dubbo 协议 | Triple | 决策 |
| ---- | ---- | ---- | ---- |
| 纯 Java 直连私有网络 | ✅ 最快 | 慢 2-3 倍（方向性） | 存量可不动 |
| 经网关 / LB / 云原生（Mesh） | ❌ 网关解析不了 | ✅ 标准 HTTP 全兼容 | **必须 Triple** |
| 多语言调用（Go/Python 客户端） | ❌ 私有协议 | ✅ gRPC 客户端直连 | **必须 Triple** |
| 流式场景（AI 流式输出、数据同步） | ❌ 一问一答 | ✅ 标准流（grpc streaming） | **必须 Triple** |
| 浏览器/移动端（南北向） | ❌ | HTTP 兼容（甚至 JSON 直调） | 视架构选 |

### 5.3 官方定调 + 本系列决策

**官方 benchmark（工行团队，research R7）**：直连 Triple 无优势；Triple 的优势在网关穿透、Stream、跨语言、云原生。

> **生产决策**：
> - 新服务：默认 Triple（面向未来的开放信封）；
> - 存量直连服务：不折腾（dubbo 协议性能没问题）；
> - 存量子系统要接网关/多语言：双协议并存灰度迁移（dubbo + tri 同时导出，03/08 篇讲多协议）；
> - 迁移顺序：**先迁网关必经之路的服务，再迁其余**（流量验证放最前面）。

### 5.4 迁移的隐藏成本（Trade-off）

```text
收益：开放、跨语言、网关直通、流式、云原生
代价：直连性能下降（方向性 2-3 倍）、HPACK/帧开销、调试面从"框架日志"变为"HTTP 工具"
      + 序列化需要对齐（POJO 默认 Hessian → 真 gRPC 互通要上 protobuf，02 篇）
验证：本机 E01 压测（方向性）+ 生产灰度对比（网关路径 latency/throughput/错误率）
```

### Transfer——迁移到其他设计问题

- **场景 × 收益 × 代价表是技术迁移的评估模板**：直连/网关/多语言/流式/南北向分列，先填表再开会（L5.2 就是完整示例）。
- **"先迁必经之路"是迁移的风险控制**：按流量路径排序，灰度放量验证先行——迁移顺序本身就是风险清单。
- **性能只是决策变量之一**："直连更慢也要迁"说明开放性/生态/演进路径也是变量；单变量决策必翻车。

> 本层留下的新账：信封的账还清了——**但信封里装的"盒子"还没讲**：序列化怎么选？为什么默认的不是最快的？02 篇接上。
>
> 🔴 **口诀**：迁移看场景不看病名；决策矩阵先列变量再谈性能。

## 🎯 生产决策卡

## 决策卡 1：新服务用什么协议

- **Decision**：Triple（`tri`）。
- **Reason**：开放信封——网关/多语言/流式/云原生全部可对接（Level 5）。
- **Alternative**：纯内网 Java 直连且无演进计划，可保留 dubbo 协议。
- **Trade-off**：直连性能方向性下降 2-3 倍（E01），换开放性与生态。
- **Validation**：E01 本机方向性压测 + 生产网关路径灰度对比。

## 决策卡 2：存量 dubbo 协议服务要不要迁

- **Decision**：网关必经之路的先迁（双协议并存灰度），其余不动。
- **Reason**：私有协议在网关/LB/Mesh 前是死路，但直连场景性能没毛病。
- **Trade-off**：迁移成本 vs 开放收益，按流量路径排序。
- **Validation**：双协议同时导出（demo01 的 Provider 就是原型），灰度观察。

## 决策卡 3：验收时怎么验证"信封"对不对

- **Decision**：curl 三连测（JSON 调用 / gRPC 帧调用 / HTTP/1.1 调用）。
- **Reason**：三连测分别验证"开放/兼容/协商"三层语义（E01 §2.2/§2.3）。
- **Trade-off**：curl 只能验证信封，业务互通还要验盒子（02 篇）。
- **Validation**：`--http2-prior-knowledge` + `content-type: application/grpc` + `--http1.1` 三条命令。

## 🌍 跨语言 / 跨运行时视角

| Dubbo 视角 | 跨语言同构对象 | 不变的问题 |
|---|---|---|
| 六问职责清单（边界/配对/元数据/状态/复用/协商） | gRPC、Thrift、HTTP/2、Redis RESP、MySQL 协议 | 任何协议都回答同一组问题，差异只在回答方式 |
| dubbo 私有帧（magic 0xDABB） | Thrift 私有协议、各类私有 RPC 协议 | 私有 = 生态锁定：性能收益 vs 互操作性 |
| Triple = gRPC over HTTP/2 | gRPC、HTTP/2、QUIC | 开放协议 = 生态接入成本最低 |
| 端口统一服务器（HTTP/1.1 + HTTP/2 协商） | ALPN 协商、gRPC-Web 降级 | 向下兼容的协议协商模式 |
| 协议兼容 ≠ 序列化互通 | gRPC 的 message 编码选择 | 语义契约与编码契约是两层，互通要两层对齐 |

### 跨语言后仍成立的 4 条判断力

1. **学任何协议先答六问**——边界、配对、元数据、状态、复用、协商；答完这六问，协议就学完了（E01 的 curl 三连测就是按六问设计的验收法）。
2. **"信封与盒子正交"是网络中间件的通用切分**——任何 RPC/消息系统（gRPC、Thrift、Kafka）都分"帧格式 + 序列化"两层，先分清这两层再谈性能。
3. **私有 vs 开放的取舍公式**——性能优势 × 私有化收益（生态锁定）vs 互操作性 × 生态接入成本；dubbo 协议死在私有，HTTP/2/QUIC 生在开放。
4. **兼容是分层的**——协议语义兼容 ≠ 序列化互通（E01 的 grpc-status: 2 就是一次真实翻车）；验收时两层契约都要测。
