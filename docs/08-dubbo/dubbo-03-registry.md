# 🧭 03｜注册中心：菜单为什么不能塞进目录

> **副标题：从订单 O 如何找到可接单的门店，到目录登记什么、怎么送达、何时不可靠，以及接口级到应用级注册的迁移决策。**

---

> ## 写在最前面的承诺
>
> 这不是 Nacos 与 ZooKeeper 的选型广告，也不是"注册、订阅、通知"三个词的流程图。
>
> 我们只追踪订单 O：它到了 Consumer 的调度台，准备寻找一家能接单的后厨。本文要证明三件事：地址为什么不能写死；为什么目录不能按"菜名"（接口）登记、菜单（契约）为什么不能跟着门店走；以及从接口级迁到应用级注册时，Consumer 调度台必须多知道什么——否则订单会送不出去。
>
> 全文唯一比喻仍是**一座外卖中央厨房**。注册中心是总部维护的门店目录；Consumer 本地地址快照是调度台手里的一份门店表。新增的关键一问：**目录里登记的是"门店"还是"菜品"？菜单放在目录里，还是放在门店的墙上？**


**🏷️ 关键词**：注册中心、服务发现、接口级注册、应用级注册、register-mode、写放大、元数据、MetadataService、revision 指纹、订阅通知、本地快照、地址陈旧、优雅下线、register-mode 迁移、providedBy、映射


**🧵 主线进度条**：①门店开业 → ②总部登记（登记什么？门牌还是菜单）→ ③调度台订阅目录 → ④本地表更新 → ⑤订单 O 查表 → 【03 注册中心专题：本篇展开注册域内部步骤——直送后厨 → 门店摘流 → 目录收敛】→ 下一步：台账多副本怎么同步（04 篇）

## 🏭 全文唯一比喻地图


```text
门店 P1 / P2                              Consumer 调度台
─────────────                              ───────────────
开业、预热、打烊                                  本地"可接单门店表"
      │                                                   ▲
      ▼                                                   │ 订阅通知
总部目录（注册中心 / 服务发现） ──────────────────────────┘
      │
      └──── 正常不承接订单 O 的同步转发 ────┐
                                            ▼
订单 O：调度台查本地表 ────────────────> 直接送 P1 / P2 后厨
```


| 中央厨房元素 | Dubbo 技术对象 | 它负责的唯一一件事 |
|---|---|---|
| 门店 | Provider 应用实例 | 声明"我在哪、我能提供什么"。 |
| 菜品 / 菜单 | 服务接口 / 契约（MetadataInfo） | "我能做什么"的完整定义。 |
| 门牌 | 应用级注册条目（实例 metadata） | 只有端点、协议、菜单版本指纹。 |
| 总部目录 | 注册中心 | 维护一份"哪些门店在营业"的动态目录。 |
| 菜单 + 门店映射 | 接口→应用的映射（mapping / providedBy） | 顾客要"宫保鸡丁"时，告诉他哪家店有。 |
| 调度台门店表 | Consumer 本地地址快照 | 订单 O 的候选门店集合。 |
| 打烊流程 | 摘流、注销、优雅下线 | 阻止新 O 进入，处理在途 O。 |


> 📌 目录不是配送中转站。**真正致命的问题往往是目录里存了什么**：按"菜品"登记时，一家店 50 道菜就占 50 行；按"门店"登记时，菜单留在店里，目录只挂门牌。

## Level 1：地址为什么会变——为什么需要注册中心


### 👶 前置知识关卡


- [ ] 一次 RPC 调用从 consumer 到 provider 沿途经过哪些站？（见 00 篇）
- [ ] 服务契约（接口）在哪里定义？它有多常变？（见 02 篇）

### Why——上一代方案死在哪


**徒弟**：库存服务先上两台机器，配置 `10.x.x.21:20880, 10.x.x.22:20880` 就够了。什么时候真需要注册中心？

**老陈**：当你扩容、发布、换机、容器漂移、灰度、故障摘除的时候——地址就不再是静态配置，而是一份高速变化的共享状态。让每个 Consumer 人工维护这份状态，一次运维变更就会被放大成全网配置事故。


| 朴素方案 | 它本来想解决什么 | 它留下的致命账 |
|---|---|---|
| IP:Port 写进 Consumer 配置 | 快速直连 | Provider 漂移、扩缩容、故障迁移都要改大量调用方。 |
| DNS 只做单一名字解析 | 隐藏 IP | 没有契约、标签、灰度与生命周期信息。 |
| 发布时全网同步替换地址 | 快速切流 | 无预热、无在途保护、无回滚证据。 |


### What——新结构是什么


```text
静态世界：
Consumer 配置 ────> P1 固定 IP


动态世界：
P1/P2/P3 生命周期变化
        ↓ 注册 / 变更 / 注销
      服务目录（总部登记）
        ↓ 订阅分发
  各 Consumer 的本地门店表
        ↓
  订单 O 直连候选门店
```


关键不变量：**目录是共享状态，但订单 O 不经过目录**——目录只影响"以后可选的实例集合"。


### How——订单 O 的慢动作


```text
① P1 完成初始化与预热
② P1 向目录登记"我在营业，地址是 X"
③ Consumer 订阅目录，本地表更新为 {P1, P2}
④ 订单 O 到来，调度台从本地表选一家店直连
⑤ P1 故障或准备下线，目录发布变更
⑥ Consumer 本地表移除 P1；后续 O 不再派给 P1
```


**徒弟**：我把 P1 从目录里删掉，就算优雅下线了吧？

**老陈**：删目录只是防止**未来**的订单继续发现它。已经拿到旧地址的 Consumer、已经在路上的订单、正在执行的扣库存，都需要单独处理——这个账我们留到 Level 4。

### Transfer——迁移到其他设计问题


- Kubernetes 的 Pod IP、消息消费者实例、数据库读副本都是"带生命周期的地址"。
- 任何"注册成功"都不应等于"可以接流量"：启动依赖、缓存预热、连接池尚未就绪。
- 地址变更必须有可观测性：注册成功率、订阅延迟、实例候选数、实例真实入站流量。


> 本层留下的新账：目录出现了，那**目录里到底登记什么**？登记的单位错一点，规模一大就爆。
>
> 🔴 **口诀**：**地址一旦会变，目录就不能靠人抄。**

## Level 2：目录登记什么——接口级 vs 应用级，写放大从哪来


### 👶 前置知识关卡


- [ ] 地址会变 → 需要注册中心（L1 已答）
- [ ] 清单：一家门店同时提供几道菜（接口）？

### Why——上一代方案死在哪


**徒弟**：服务发现不就是"接口对应一组 Provider URL"吗？接口多一点，目录里多几条记录而已。

**老陈**：问题就在"多几条记录"——它是**乘出来的**，不是加出来的。目录按"菜品"登记时，每家店每道菜都要一行：

```text
按菜品登记（接口级）：
  宫保鸡丁 → P1 店、P2 店
  水煮鱼   → P1 店、P2 店
  ...
  50 道菜 × 200 家店 = 10,000 行目录条目     ← 推算（不是实测）

按门店登记（应用级）：
  P1 店：门牌 + 菜单版本号
  P2 店：门牌 + 菜单版本号
  ...
  200 家店 = 200 行
```

接口级时代，**同一个门店的信息（地址、端口、序列化……十几个字段）在 N 个菜品条目里重复 N 遍**；新菜上线，每家店各加一行；门店扩缩容，每道菜各动一行。目录条目数 = 接口数 × 实例数——这就是**写放大**：写入、心跳、watch、通知全都按条目数计费，条目数却跟"真正的容量主体（实例）"脱钩。


| 朴素方案 | 它本来想解决什么 | 它留下的致命账 |
|---|---|---|
| 每接口维护完整实例集合 | Consumer 按接口直找 Provider | 同一实例的地址与元数据在 N 个接口维度重复。 |
| 每接口变更独立推送 | 简化局部订阅 | 一个实例上下线触发 N 条重复通知。 |
| Consumer 缓存接口级全量 URL | 免去每次查询 | 内存与通知事件随条目组合增长。 |


### What——新结构是什么


应用级注册把**登记单位从"菜品"换成"门店"**，并做了一件更根本的事：**把菜单（契约）从目录里搬走**。

实测（E03：同一 provider 导出 2 个接口、1 个实例，Dubbo 3.3.4 + Nacos 2.4.3）：

**interface 模式——目录按菜品登记，每行是完整菜单：**

```json
service: providers:org.example.dubbo.demo.api.GreetingService::
实例 metadata: { side, release, methods: "greet", interface: "org.example.dubbo.demo.api.GreetingService",
                 protocol, application, path, revision: "1.0.0", category, timestamp, ... }
→ 14 个字段 / 约 270 字节（实测）
```

**instance 模式——目录按门店登记，门牌上只有三样东西：**

```json
service: demo02-provider
实例 metadata: {
  "dubbo.endpoints": "[{\"port\":50052,\"protocol\":\"tri\"}]",
  "dubbo.metadata.revision": "b2dca2af4a7d5e92af090524c061b11a",
  "dubbo.metadata-service.url-params": "{...\"port\":\"20880\",\"protocol\":\"dubbo\"}"
}
→ 5 个字段（另加 meta-v、timestamp）/ 约 318 字节（all 模式实测，instance 轮未单独量体积）
```

三样东西各回答一个问题：

1. `endpoints`——**门牌**：这个进程在哪些端口用哪些协议听单。
2. `revision`——**菜单版本指纹**：这门店的菜单算了个哈希；菜谱一改，指纹就变。
3. `metadata-service.url-params`——**菜单在哪取**：完整菜单（接口方法签名、入参出参）不落目录，住在门店墙上（provider 进程里的一个内部服务，随机端口，实测为 20880），且**不登记进目录**——顾客来了直接按门牌去问。

> 📌 **反直觉点：应用级每条记录并不更小**（约 318B vs 270B，doorplate 里的 url-params 是转义 JSON 很占地方；318B 为 all 模式抓取的 instance 条目实测，纯 instance 轮未单独量体积）。收益不在"单条变瘦"，而在**条目数**：接口级是 接口数×实例数，应用级只随实例数走。目录的推送、心跳、watch 按条目计费，条目数降一个数量级，写放大才真正消失。


### How——订单 O 的慢动作（provider 侧登记流程）


```text
① 门店把 N 道菜整理成一份菜单（全部接口契约汇总成一份元数据）
② 给菜单算一个版本指纹（revision）
③ 在目录挂出"门牌"：endpoints + revision + 菜单取法   ← 只登记一次，与菜品数无关
④ 菜单本体留在店内（内部服务，同一进程，随机端口）
⑤ 菜谱改了 → 指纹变 → 目录里的门牌跟着更新，而非每道菜每条记录都动
```

（顾客侧如何取菜单，见 Level 3 的故事线；此处先记下这条路的存在。）


**徒弟**：那 application 模式下 Consumer 怎么知道哪家店有"宫保鸡丁"？目录里没有菜名了呀。

**老陈**：问得好——这就是 Level 5 的账：**菜名到门店的映射**。现在先记住：目录只说"哪些门店在营业"，"哪家店有这道菜"是另一份信息。有些地方（总部档案）有这张表，有些地方没有，没有时调度台就得自己点菜名（providedBy）。

### Transfer——迁移到其他设计问题


- **慢变 × 快变分离**是通用模式：菜单（契约）慢变、门牌（实例）快变——把慢变数据塞进快变通道，就是写放大。
- K8s：EndpointSlice 管实例，Service/ConfigMap 管契约，两者分离。
- DNS：域名（契约）慢变，A 记录（实例）快变，TTL 就是指纹的类似物。
- 判断模板：如果你的"服务变更"（加接口/改签名）会触发每条实例的注册与通知风暴，就是该做这层分离的信号。


> 本层留下的新账：目录登记好了，但**怎么送到每家调度台**？每次订单都现场问总部？
>
> 🔴 **口诀**：**目录只挂门牌，菜单留在店里；菜谱一改，不用全城抄菜单。**

## Level 3：目录怎么送达——订阅通知、本地快照与地址陈旧


### 👶 前置知识关卡


- [ ] 目录登记什么（接口级 vs 应用级、门牌 vs 菜单）？（L2 已答）
- [ ] 菜单留在了门店里，顾客怎么取？

### Why——上一代方案死在哪


**徒弟**：干脆每次订单 O 都去总部问一次最新目录，保证最新，也不怕本地表过期。

**老陈**：你把总部目录放进了每单配送的同步关键路径。目录的一次网络抖动变成每单的延迟；高峰请求量变成注册中心的读压力。更糟的是，目录"最新"也保证不了刚选中的门店下一毫秒不故障。


| 朴素方案 | 它本来想解决什么 | 它留下的致命账 |
|---|---|---|
| 每次 RPC 同步查目录 | 拿到最新地址 | 注册中心成为同步依赖与性能瓶颈。 |
| 本地地址永不更新 | 减轻目录压力 | 下线、扩容、灰度永不生效。 |
| 同步等全网目录一致 | 避免陈旧 | 变更传播被拉进调用热路径，可用性下降。 |


### What——新结构是什么


```text
控制面（异步）：
Provider ↔ 注册中心 ↔ Consumer 订阅器
            │
            ▼
      更新 Consumer 本地门店表

数据面（同步、每笔 O）：
Consumer 本地门店表 ──────────────> Provider 直连
```


关键不变量：**控制面异步影响候选集合，数据面直连完成业务；本地表允许短暂陈旧，换目录瞬时抖动不打断订单。**


### How——订单 O 的慢动作


```text
① Consumer 启动，订阅感兴趣的门店/菜品目录
② 总部推送变更 {P1, P2}；Consumer 原子替换本地表
③ O 到来：只读本地表选 P1/P2，不访问总部
④ 总部短暂失联：本地表仍是 {P1, P2}，订单照常发出（可能打到已下线的店）
⑤ 若 P2 已失效但变更未达：O 可能失败，由 Cluster/业务策略处理
```

本实验（E03）中真实观察到的这一过程：provider 启动时，Consumer/Provider 双方都会发起订阅并收到通知；当订阅的接口在目录中没有任何实例时，Dubbo 会收到一条**空地址列表**并据此清空本地候选——本地表确实会随目录变化被"清空"或"替换"。


**徒弟**：本地表会过期，那不就是不可靠吗？

**老陈**：可靠性不是"永远最新"的幻觉。真正的问题是：**陈旧窗口有多长**、**选中旧门店后多快失败**、**失败会不会造成不可接受的副作用**。这三个问题要量化，而不是一句"有缓存就稳了"。

### Transfer——迁移到其他设计问题


- CDN、DNS、浏览器缓存都在"新鲜度 vs 可用性/成本"之间取舍。
- 控制面故障与数据面故障分开告警与演练：注册中心断连 ≠ Provider 不可达。
- 本地表要定义边界：冷启动目录不可用怎么办、长期失联怎么办、陈旧数据最长容忍多久。


> 本层留下的新账：目录说 P1"在营业"——**它真的能接单吗？** 目录条目消失就代表门店关停吗？
>
> 🔴 **口诀**：**目录异步下发，订单直送后厨。**


<a id="level-6"></a>
## Level 4：目录何时不可靠——注册≠接单、残留与生命周期


### 👶 前置知识关卡


- [ ] 本地表过期/目录抖动时订单会怎样？（L3 已答）
- [ ] 目录里的条目是"活"的还是"写死的"？

### Why——上一代方案死在哪


**徒弟**：发布时让门店收到终止信号，注销目录条目，进程退出。下线这不就完成了吗？

**老陈**：目录条目只是"登记簿上的名字"。它背后还有三件事：**Consumer 还没收到变更**（旧表继续派单）、**在途订单还在处理**（强杀会制造超时与重试风暴）、**新店还没备货就挂了门牌**（冷启动错误率尖峰）。上线和下线都是多阶段状态机，不是一条 delete。


| 朴素方案 | 它本来想解决什么 | 它留下的致命账 |
|---|---|---|
| 先 kill 再注销 | 快速释放机器 | Consumer 旧快照仍派单；在途请求被中断。 |
| 端口监听即注册接单 | 缩短发布时间 | 缓存/连接池未就绪，冷启动错误率上升。 |
| 只看目录条目消失 | 判断摘流完成 | 不知道真实调用量是否归零。 |


### What——新结构是什么


```text
安全上线：
启动 → 依赖检查 → 预热 → 挂门牌(注册/Ready) → 小流量 → 正常接单

安全下线：
停止接新单(摘流) → 目录变更传播 → 等在途 O → 到期处置 → 关闭端口/进程
```


关键不变量：**目录条目 ≠ 接单资格**；**条目消失 ≠ 摘流完成**。摘流完成的证据是实例真实入站调用归零、在途请求被处置。


**关于残留——本实验的真实观察（E03）**：provider 进程被停止后，Nacos 里**接口级 service 名会残留为空壳**（实例数归零，但服务名还在目录列表里，观察期间持续存在）。目录条目是"暂时性租约"（心跳续租、超时摘除），但**服务名的生命周期比实例长**——这和"进程退出 = 目录干净"的直觉相反：目录的收敛是异步、有迟延的。


### How——订单 O 的慢动作


```text
① P2 准备下线：先被路由排除/标记不接新单（摘流）
② 目录变更传播；后续 O 的本地表不再含 P2
③ 已在 P2 执行的 O 继续完成，直到优雅关闭期限
④ 观察 P2：新入站 QPS → 0，活跃调用 → 0
⑤ 再关监听与进程；目录条目随后被摘除（可能残留空 service 名）
⑥ 若到期仍有 O：按业务规则记录、取消或转异步补偿；不能静默强杀
```

> 📌 ③ 的"在途 O 继续完成"是**机制期望**，不是所有协议实现都兑现：08 篇 E08 实测发现 3.3.4 triple 的优雅停机"送完在途"不可靠——PING ack 即断连，业务线程即使跑完，响应也送不出去。上线前按你的协议版本实测优雅关闭的真实行为，别把机制图当验收结论。


**徒弟**：能不能只靠健康检查失败，让总部自动摘掉 P2？

**老陈**：健康失败适合处理**故障**，计划发布需要可控顺序。故障摘除、计划摘流、业务降级是三种情形；不要把"故意下线"伪装成"突然故障"。另外，目录自身的一致性语义（CP/AP 之争）只决定"你此刻拿到怎样的目录"，**不决定订单业务状态的一致性**——那是接口幂等与事务的问题，别把两笔账混在一起。


### Transfer——迁移到其他设计问题


- K8s `preStop`、Readiness、负载均衡摘流、优雅关闭必须一起设计。
- 发布验收看**实例维度**而非应用平均：少量旧实例被误派单，平均 QPS 完全看不出。
- 非幂等在途操作不能被"强制取消"免费解决：需要状态查询与对账方案。


> 本层留下的新账：目录会说谎（残留、陈旧、分区）。那**旧的还能用吗？怎么迁过去？**
>
> 🔴 **口诀**：**先停新单，再清在途，最后才关门；门牌会旧，菜单会残。**

## Level 5：怎么选怎么迁——register-mode 三态与迁移决策


### 👶 前置知识关卡


- [ ] 目录登记什么（L2）、怎么送达（L3）、何时不可靠（L4）。

### Why——上一代方案死在哪


**徒弟**：Dubbo 3 应用级注册好，直接把 register-mode 切成 instance 就行了吧？

**老陈**：切换的不是一个开关，是**一批 Consumer 的发现方式**。接口级时代 Consumer 订阅的是菜名，拿到完整菜单；应用级时代它必须先把菜名翻译成门店名（映射），再去取菜单。**翻译表（映射）存在于哪里**，决定了你切过去之后订单能不能送出去——这是我们实验里真实踩到的坑（见下）。


| 朴素方案 | 它本来想解决什么 | 它留下的致命账 |
|---|---|---|
| 全量直接切 instance | 一步到位 | 无映射源时 Consumer 找不到门店，订单全挂。 |
| 永远保留 interface | 保兼容 | 写放大不消失，多一份维护成本。 |
| 不验证就切换 | 省事 | 映射、host、配置中心任一没对齐，线下故障。 |


### What——新结构是什么


**register-mode 三态语义（Dubbo 3.3.4）：**

```text
interface —— 目录按"菜品"登记：每接口一条 service，实例带完整菜单（14 字段实测）
instance  —— 目录按"门店"登记：一条 service，门牌只带 endpoints + revision + 取菜单方式（5 字段实测）
all       —— 两种都登记：接口级 + 应用级并存（迁移过渡态，3 条 service 实测）
```

**关键点：默认值不是 instance。** 实验实测：不设任何 register-mode 时，Nacos 里出现的是**接口级 + 应用级并存（= all 的行为）**——源码逻辑：`nacos://` 这类配置不属于"纯 service-discovery"协议时，默认走 all。所以"升级就默认应用级"是错觉，必须显式确认。

**顾客（Consumer）怎么知道哪家店有"宫保鸡丁"（接口→应用映射）：**

```text
有总部档案（配置中心/映射存储）：查档案 → 菜名 → 门店名
没有任何档案：
   └─ 接口级条目还在（all 模式）：可从旧条目的 application 信息桥接出门店名
        （桥接细节为行为推断：观察到 all 模式无 providedBy 可用、纯 instance 不行；
          具体消费路径未逐行验证，见证据入口）
   └─ 纯 instance 模式：无源可查 → consumer 必须自己点名（显式 providedBy=门店名）
```


### How——订单 O 的慢动作（E03 实测迁移故事）


```text
场景：provider 两个接口，consumer 无 providedBy、无配置中心。

① 模式 = interface：目录按菜名登记，各 1 实例，14 字段/约 270B
   → Consumer 订阅菜名直连，订单成功（实测）
② 模式 = instance：目录只剩"门店"一条，5 字段，接口级条目残留为 0 实例空壳
   → Consumer 拿菜名问"哪家店有"→ 没有档案、没有桥接 → 报"找不到映射源"→ No provider，订单全挂（实测）
③ Consumer 加一个参数点名：providedBy=demo02-provider
   → 直接订阅"门店"→ 取门牌 → 向店内取菜单 → 构造调用 → 订单成功（实测）
④ 模式 = all：接口级条目仍在 → 无 providedBy 也能桥接 → 订单成功（实测）
```


**第二个实测坑——注册地址会漂移**：本机同时存在 TUN 代理网卡（198.xx.x.x）和物理网卡（192.xxx.x.xxx）时，两次启动 provider 探测到的"本机地址"不稳定：一次注册 198.xx.x.x（TUN），consumer 回连时流量被代理劫持 → 误报 No provider；另一次注册 192.xxx.x.xxx（物理）则正常。修复：显式固定注册地址（环境变量 DUBBO_IP_TO_BIND / DUBBO_IP_TO_REGISTRY）。


**三态实测对比表（E03，2 接口 / 1 实例 / Nacos 2.4.3）：**


| 维度 | interface | instance | all |
|---|---|---|---|
| Nacos service 数 | 2（按菜品） | 1（按门店） | 3（两套并存） |
| 条目内容 | 完整菜单 14-15 字段 / 约 270-301B | 门牌 5 字段 / 约 318B | 双份 |
| Consumer 发现 | 订阅菜名直连 | 订阅门店 + 取菜单 | 两者，可桥接 |
| 无映射源 consumer | 可用（菜名即条目） | **必须 providedBy**（实测） | 可用（桥接） |


**迁移落地（决策见下）：**

```text
① 先开 all：双轨并存，验证应用级连通（Consumer 候选正常、无空目录报警）
② 逐个应用把 consumer 映射义务补齐：要么上配置中心/映射存储，要么显式 providedBy
③ 观察 N 天：无回归 → 切 instance
④ 保留回滚手段：register-mode 是配置项（本实验经启动参数传入，动态下发未验证，按你的配置中心能力核验），切换不需改代码
```


**徒弟**：切到 instance 之后，目录确实只剩 1 条了，但会不会以后出问题？

**老陈**：会有的新风险是"**取菜单的时延与可用性**"——每次发现新实例都可能要跨进程取一次菜单（具体缓存与刷新行为按配置核验，本实验未单独测时延，标"待测"）。这是用"每实例一次取菜单"换"目录条目数降一个数量级"，属于明确交换，不是免费午餐。

### Transfer——迁移到其他设计问题


- 任何发现/配置系统的迁移，先回答"**旧的依赖里，谁同时握着两张表**"——切换主表前，把副表的来源补上。
- 双轨运行（all）是迁移的通用安全网：新旧并存直到新轨被验证，再拆旧轨。
- "注册地址必须稳定可达"适用于所有多网卡、容器 IP 漂移、代理拦截环境。


> 本层留下的新账：目录已经能正确导航到门店，订单 O 到了候选门店集合门口。**后续进入 Router、LoadBalance 与 Cluster（05 篇）：为什么先判资格、再选目标、最后才定义失败代价。**
>
> 🔴 **口诀**：**菜名找门店，得有翻译表；切轨不备表，订单全挂掉。**

## 🏆 生产决策卡


### 决策卡 1：接口级 → 应用级迁移


**场景与判断**：集群准备上 Dubbo 3 应用级注册。


| 机制到决策映射 | 落地 |
|---|---|
| 应用名规范 | 先统一应用命名、实例身份与发布边界。 |
| 映射来源 | 配置中心/档案，或每个 consumer 显式 providedBy。 |
| 双轨过渡 | 先 all 后拆 interface，保留回滚。 |
| 双视角观测 | 服务候选集与应用实例目录同时看。 |

- **不能做的错误决策**：只升级版本、看到目录出现"应用实例"就宣布完成——不验证映射链路。
- **验收指标**：服务映射完整率、Consumer 空地址次数、候选实例数、迁移前后错误率与订阅延迟。


### 决策卡 2：多网卡 / 代理环境下的注册地址


**场景与判断**：本机/容器存在 TUN、代理虚拟网卡，provider 注册地址不稳定。


| 机制到决策映射 | 落地 |
|---|---|
| 地址探测 | 显式固定注册与绑定地址（DUBBO_IP_TO_BIND / DUBBO_IP_TO_REGISTRY）。 |
| 语义 | bind（进程监听）与 registry（对外宣告）可分离配置。 |
| 排查 | consumer"No provider"时先查注册条目的 IP 是否可达、是否被代理拦截。 |

- **不能做的错误决策**：用 127.0.0.1 期望绕过探测（实测会被当作无效地址重新探测）。
- **验收指标**：注册条目的 IP 与可达性、consumer 连接失败数。


### 决策卡 3：Consumer 冷启动与目录失联


**场景与判断**：新 Consumer 启动时目录暂不可达，或运行期目录长期失联。


| 机制到决策映射 | 落地 |
|---|---|
| 启动检查 | 区分"进程存活"与"目录已可用"。 |
| 流量入口 | 目录未就绪：延迟 Ready、明确降级或只开放不依赖 RPC 的功能。 |
| 快照策略 | 定义陈旧窗口与长期失联的失效策略。 |

- **不能做的错误决策**：无任何候选实例仍对外 Ready 并接交易流量。
- **验收指标**：启动到目录就绪耗时、空地址调用数、快照年龄、错误率。


### 决策卡 4：发布与优雅下线


**场景与判断**：Provider 滚动发布，写操作在途时不能粗暴中断。


| 机制到决策映射 | 落地 |
|---|---|
| 预热 / Ready | 依赖、缓存就绪后才进候选。 |
| 摘流 | 发布前阻止新 O 进入待下线实例。 |
| 在途处置 | 等待完成或明确策略，不静默强杀。 |

- **不能做的错误决策**：因容器终止倒计时存在就直接 kill -9。
- **验收指标**：实例入站 QPS、活跃调用、优雅关闭耗时、关闭期错误率。

## 🌍 跨语言 / 跨运行时视角


| Dubbo 视角 | 跨语言同构对象 | 不变的问题 |
|---|---|---|
| 接口级 vs 应用级注册 | Eureka（纯 app 维度）；ZK/Consul 按服务名分节点 | 登记单位在哪一层？容量主体是接口还是实例？ |
| 契约与实例分离 | gRPC proto / name resolver、OpenAPI 规范独立分发 | 契约慢变、实例快变，谁进发现通道？ |
| 门牌指纹（revision） | Docker image digest、config version、etcd revision | 如何用指纹判断要不要重新拉取？ |
| 订阅 + 本地快照 | DNS cache、Envoy xDS cache、客户端 endpoint cache | 控制面失联时继续用多久、陈旧如何处理？ |
| 双轨迁移（all） | K8s 蓝绿、双写迁移 | 新旧并存直到新轨验证，怎么拆旧轨？ |
| 残留空壳 | DNS 失效记录、K8s terminating | 目录收敛滞后，服务名生命周期比实例长。 |


### 跨语言后仍成立的 7 条判断力


1. **地址是带生命周期的动态数据，不是常量配置。**
2. **注册条目数 = 登记单位粒度 × 数量，登记单位错了就写放大。**
3. **契约（菜单）慢变、实例（门牌）快变，两者进不同的通道。**
4. **目录异步下发，数据面直连；本地快照允许短暂陈旧，但要有陈旧边界。**
5. **目录条目消失 ≠ 摘流完成，残留是常态，收敛要观测。**
6. **切换发现模型前，先补齐"旧名字→新名字"的翻译表。**
7. **注册中心只决定"拿到什么样的目录"，不决定业务一致性。**
