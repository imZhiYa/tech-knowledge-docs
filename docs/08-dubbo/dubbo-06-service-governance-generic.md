<a id="level-2"></a>
## Level 1：为什么规则必须"不发版就能改"——资格这张账

### 为什么存在

05 篇留下了一个结构：**候选列表是容错的原料；资格、选择、兜底，三个时点三种账**。选择与兜底两章讲完了，资格还悬着——当时只说了资格是"Router 在选之前先过滤"，但**资格规则本身从哪来、怎么变**，05 篇没有展开。这就是本文的第一层账。

**徒弟**：资格规则……不就是代码里写死的条件吗？比如"已打烊的店不进候选"，加一行判断不就完了。

**老陈**：那一行判断是**怎么变成线上行为的**？如果你改的是代码，那个循环是：

- 改 → 构建 → 发版 → 全量重启 → 回滚再发一次

这套流程在**静态资格**（比如"按套餐类型过滤"）下没问题；但资格里有一大类是**运营态规则**：

```text
"今晚 18:00 起 XX 店歇业 2 小时"（临时歇业）
"新店前三天只接 5 公里内订单"（新店保护）
"会员专享商品只对会员店开放"（会员资格）
"灰度：新结算逻辑只让 10% 老店参与"（灰度比例）
```

这些规则的共同点：**今天生效、明天可能就变、变了不能等发版流程**。发版周期按天算，运营规则按小时变——用发版承载运营规则，等于让外卖总部每次调价都要重装修厨房。旧方案死在这种时间粒度错配上。

所以治理（governance）的核心动机不是"配置化"这种口号，而是**把规则的变更周期从"发版周期"压缩到"下发周期"**。代价是：规则变成运行时的外部输入，于是凭空多出四段必须自己背的账：

```text
规则存储在哪里？        → 来源账（哪份权威数据）
规则怎么到达调用方？    → 传输账（谁通知、丢不丢）
规则什么时候变成行为？  → 生效账（热更的时机与原子性）
规则错了怎么退回去？    → 回滚账（撤回的路径）
```

**关键不变量**：规则生效必须**无感**——正在进行的调用不能因为规则变更而中断（热更），且新规则必须**原子切换**（要么全用旧规则，要么全用新规则，不存在中间态）。

**留下的新账**：规则是外部输入了，那么"规则放到哪、Dubbo 从哪把它接回来"？→ 下一层讲传输与生效。

## Level 2：规则下发与热更——从注册中心到 RouterChain 的最后一公里

### 接上一层的账

规则必须到达 **调用点**（consumer 侧 `RegistryDirectory`）才能变成资格行为。Dubbo 的选择是：**复用注册中心的订阅通道**——规则不是单独拉的一个配置，而是注册中心里一类特殊的"数据"（`category=routers` / `configurators`），和地址一样被订阅、被 notify。

```text
总部（Admin/控制台）
   │  写规则（如：tag 灰度的标签、条件的 JSON）
   ▼
注册中心（Nacos 2.4.3 实测环境）
   │  category=routers / configurators 的 dataId 持有规则
   ▼  notify（复用地址通知通道）
consumer 侧 RegistryDirectory
   │  toRouters() / addRouters()   ← 3.3.4 dubbo-registry-api 源码（05 篇证据）
   ▼
RouterChain 双链（05 篇走查过）→ 资格过滤在 select 之前执行
```

**生效账的关键**：`RegistryDirectory.notify()` 收到 routers 通知后，调用 `addRouters()` 把新 Router **追加进 RouterChain**；链是**不可变重建**（新链替换旧链）而不是原地修改——这就是热更新"原子切换"的实现方式（机制层，3.3.4 `RouterChain` 语义）。

### 条件路由与 tag 路由：两种资格的形态

```text
条件路由 condition-router：  "=> host = 192.xxx.x.xxx:50052"  基于 URL 条件的 if-then 过滤
标签路由 tag-router：       请求打 tag（如 dv=canary）→ 只路由到带同 tag 的实例
                            没有同 tag 实例 → 按 force=false 配置决定是否降级到全量
```

tag 路由因此是**灰度**的天然载体（能力地图里"10% 老店先上"的落地形态）。两种路由都在 RouterChain 里按序执行，资格过滤发生在 `AbstractClusterInvoker.select` 之前（05 篇的双链图）。

### mock 降级：资格的另一面

**徒弟**：资格过滤都是"不让进"。那"不让打这个店、但订单还得往前走"呢？

**老陈**：这是资格的另一面——**mock 降级**。规则不是真的打过去，而是调用方直接拿到一个写死的假结果。机制上它在 Cluster 外面套了一层 `MockClusterInvoker`（3.3.4 `dubbo-cluster/.../wrapper/`），

```text
MockClusterInvoker（mock=true / mock=force:return xxx / mock=fail:return xxx）
  ├─ 命中 mock 配置 → 直接返回假结果（force 不建连接、不打网络）
  └─ 未命中 → 透传，走真实调用的 Router/LoadBalance/Cluster 三层
```

> **E10 实测锚点（2026-08-12，`experiment-010-mock.md`）**：mock 是 **Cluster 层特性**，只在注册中心路径生效——`setUrl` 直连返回裸 TripleInvoker，mock 参数无人解析（实测抛 `RemotingException`）。值语义实测：`force:return null` 不碰 provider 直接返回；`fail:return null` 调用失败才降级（provider 在线时正常走真实调用）；`true` 需接口同名 `XxxMock` 类，没有则报 `mock error: Failed to create mock implementation class`；`force:throw X` 抛降级异常。排障"mock 不生效"先确认路径与值格式。

它与资格过滤是**同一张账的两个方向**：Router 决定"能不能选"，mock 决定"不选时给什么"。两者共同的输入都是**外部规则**，所以共享本文的"来源→传输→生效→回滚"四段账。

### 规则下发的失败模式（敢不敢上线的第一道考题）

1. **规则没到达**：下发链路断（注册中心抖动），调用方仍持旧规则——行为不变，但"临时歇业"不生效，顾客还是打到已歇业的店。
2. **规则下错了**：JSON 格式错 / 条件写反（`host =` 写成 `host !=`）。**生效账没有"预编译校验"义务**——条件路由是把规则编译成表达式再匹配。（E05-4 实测排障见 `experiment-005` §5：dataId 必须双冒号 `接口::.condition-router`、group=dubbo、namespace 独立；纯 API 模式的 config-center 装载链路：`DefaultGovernanceRuleRepositoryImpl.getRule()` 走模块级 `ModuleEnvironment.getDynamicConfiguration()`，而装载发生在应用级 `DefaultApplicationDeployer.java:308`——纯 API 链路委托未打通，规则静默返回 null 且无日志。**这条实测结论是"规则没到达"的实锤案例**：链路通、格式对、读为空、日志无。)
3. **规则生效了但验证不了**：没有"规则生效回执"，运维只能靠流量表现反推。

**回滚账**：规则本体存在注册中心，**删除规则 = 删掉这份数据**，RouterChain 在下一次 notify 时重建链、去掉该 Router（前提是链路没断）。所以回滚预案的第一条永远不是"发一个反规则"，而是**删除或覆盖源数据**——反规则要和原规则竞争生效顺序，是给自己留坑。

> **E05-4 遗留（待验证）**：条件路由在本机（3.3.4 + Nacos 纯 API）未跑通，机制结论保持"机制层"标注；E06 计划中尝试补齐（见本文结尾证据入口）。

**留下的新账**：规则这套"资格账"的前提是**调用方知道接口签名**（条件路由要按接口名匹配）。那么问题来了：**网关这种调用方，手里根本没有接口 jar**——资格、选择、兜底整条链在它面前都失效了。它怎么进场？→ 下一层：泛化调用。

## Level 3：泛化调用——没有接口 jar 的调用方（约占全文 1/3）

### 为什么存在：免契约调用的边界

**徒弟**：网关不是有上游接口的 jar 嘛？配一下不就完了。

**老陈**：网关面对的是一堆**不同团队、不同版本、频繁变接口**的服务。每接一个服务就引入一个 jar、构建一次、重发一次，网关就把自己变成了 05 篇里那种"每次改规则都要重装修厨房"的部署单元。**旧方案（强桩集成）死在集成成本上**。所以要一种"调用时不依赖 jar、只依赖运行时约定的通用描述"的方式——泛化调用（generic call）：

```text
强类型调用：consumer 持 jar → 编译期就知道类型 → 直接 invoke
泛化调用：consumer 不带 jar → 运行时用 Map/字符串 描述类型与参数 → $invoke

GenericService 契约签名（2.x/3.x 一致）：
    Object $invoke(String method, String[] parameterTypes, Object[] args)
    // parameterTypes: 如 {"com.zhiya.api.Param"}
    // args:           Map 结构，键 class 描述类型，value 承载值
```

**关键不变量**：泛化调用**不是另一种协议**——它描述的是一份"参数清单"，清单通过原有协议（tri 等）和原有序列化框架到达 provider，provider 侧把清单翻译回真实类型再执行真实方法。**资格/选择/兜底三层在泛化下依然存在**（消费端仍是 Router→LoadBalance→Cluster 链，只是参数形态变了），这正是网关能复用整个治理体系的原因。

> **E06 实测锚点（3.3.4，2026-08-12，`experiment-006`）**：本机 `GenericService` 泛化调用同样走 tri + Nacos 跑通——Map（`class` 键 + 字段）→ provider 侧 `GreetingRequest` POJO 翻译正确、返回正常，3/3 成功。方向性验证，未做高频/大对象压力（OOM 依赖 issue 锚点）。

### 代价模型：泛化调用为什么容易"涨内存"

泛化调用把"类型信息"从编译期挪到了运行时——**每次调用都要现构建类型元数据**。类型元数据的缓存、上下文持有、失败后的残留清理，就是四种内存机制的共同土壤。以下全部以 GitHub issue 锚点证锚，版本严格区分，不做本机复现（标"待验证"）：

**机制一：ThreadLocal 强引用链（2.x 为主，3.x 仍有残余）**

```text
调用线程（线程池核心线程，固定数量、长期存活）
  └─ ThreadLocal / InternalThreadLocal
       ├─ hessian2 ObjectInput（InputStream 链，持大响应缓冲）   ← #7770（2.7.11）
       └─ FutureContext.future（持 Result/Invocation 强引用）   ← #7271（母题）→ #7770
```

- 2.7.x 报告：`Hessian2ObjectInput` 的 `INPUT_TL` 未在 cleanup 中 remove——**源码 tag 核验（02 篇修复路径表）更精确：2.7.8 连 cleanup 方法都没有（#6847 首报版本）；2.7.11 起 cleanup 只 reset 不 remove（#7770 讨论给出修复 diff，但整条 2.7.x 线未落地）；3.3.4 已删除 INPUT_TL、每次 `new Hessian2Input(is)`**。加上 `FutureContext` 用 `InternalThreadLocal` 持 `AsyncRpcResult` 的 future——**ThreadLocal 的 key 是弱引用，value 是强引用**，只要线程存活、不清除，value 链就不会断（#7770 的堆转储截图锚点，2.7.11）。
- 3.0.11 报告：provider 侧 `AsyncRpcResult.whenCompleteWithContext()` 把 responseFuture 放进 `FutureContext`，大响应（20M）循环调用 150 次左右即 OOM（#10827，3.0.11）。
- 缓解开关：`future.sync.set`（`CommonConstants.SET_FUTURE_IN_SYNC_MODE`）控制同步模式下是否把 future 塞进上下文。**默认值有官方确认**：源码 `Boolean.parseBoolean(System.getProperty(SET_FUTURE_IN_SYNC_MODE, "true"))` 默认 **true**，官方称 2.7/3.0 没有关闭途径、此开关为防泄漏而引入（issue #14727，2024-09，官方回复给出源码与"2.7/3.0 无法关闭"的说明）；**3.4 计划把默认值改为 false**（breaking change，PR #14785，2024-10）。配套 `future.clear.once=true`（清一次即释放，见 #10827 讨论）。讨论中专家观点：`FutureContext` 无法自动判断用户何时不再使用，只能靠配置或用户 finally 清理。

**机制二：Map 对象风暴（泛化调用的特有土壤）**

- 泛化参数是**嵌套 Map 结构**（`class` 键 + 具体值），与强类型参数相比，每次调用都多出成批的 HashMap、LinkedHashMap 与 char[]。3.x 报告：持续泛化调用后堆转储出现**数百万级别的 HashMap 与 char[]** 无法释放（#11451，2023-02，3.x 仍存在）。这是机制一之外的**体量放大**：即使引用链都正确，对象总量也被泛化格式本身放大。

**机制三：失败路径的残留（泛化场景暴露更狠）**

- 泛化调用失败后，同一 URL 在配置内部列表被**重复保存多条**、内存持续增长（#7377，`AbstractInterfaceConfig` 的列表字段 + `ReferenceConfig` 的处理路径）；且 provider 异常时，泛化生成的 ReferenceConfig 调 destroy **并不能释放已建立的连接资源**（#3369）——`destroy()` 里 `ref == null` 直接 return 的早退路径（讨论中给出源码定位）让 invoker 漏销毁。强类型调用同样会踩，但泛化场景"人人都是运行时构造 ReferenceConfig"，踩中概率成倍放大。

**机制四：注册表残留（泛化暴露侧）**

- 泛化方式**暴露**的服务，注销后 `GenericService` 对象仍被 `ServiceRepository` 的 services/providers 注册表持有、GC 不掉（#11218，3.1.x 讨论中仍有报告；讨论提到 ReferenceConfig 与 GenericService 循环引用）。注意：这是 Provider 侧泛化（用 GenericService 暴露假接口），与消费侧泛化是同一张账的两面。

### 语义总结与 3.x 现状

```text
四种机制不是四类 bug，是一条因果链：
  类型信息运行时化（泛化）→ 对象体量放大（机制二）
  + ThreadLocal 缓存/上下文不清理（机制一：2.x 核心事故）
  + 失败路径不清理（机制三：runtime 建 ReferenceConfig 放大）
  + 注册表生命周期管理缺位（机制四：泛化暴露）
  2.x 核心事故是机制一；3.x issue 仍大量集中在机制二与机制三/四
```

**版本必须区分**：2.7.x 的 hessian2/FutureContext 泄漏与 3.3.4 的现状不是同一个东西——3.x 重构过序列化与上下文管理，**其中 INPUT_TL 的删除已由 02 篇源码实证**（3.3.4 `Hessian2ObjectInput` 每次 new 实例）；但 #11451（3.x）证明"泛化的体量放大"不是 2.x 专属，FutureContext 等其余上下文清理路径**未逐行确认，标"待验证"**。

### 工程落地：四个必须写进评审的条件

1. **ReferenceConfig 必须缓存复用**（`ReferenceConfigCache` 语义），禁止每次调用新建——机制三直接把它变成漏洞制造机。
2. **destroy 语义要专门测试**：provider 不可达时建出来的引用，能不能真正释放连接（#3369 的场景）。
3. **大对象响应 + 高频泛化**是 OOM 最短路：预警指标是堆对象增长与 GC 频率，而不是等 OOM 日志。
4. **泛化只放在"集成边界"**（网关、测试工具、跨团队适配），业务链路内部用强类型——这是 L4 决策卡的输入。

**留下的新账**：泛化调用解决了"没有 jar"，但引入了"内存账"。整套治理（规则热更 + 泛化）的**上线评审清单**就是下一层：什么时候用、怎么确认没出问题。

<a id="level-5"></a>
## Level 4：生产决策——规则怎么改才敢上线，泛化怎么用才不炸内存

### 决策卡 1：要不要上"规则热更"（而不是发版）

```text
Decision： 运营态、小时级变化、失败可容忍的资格规则 → 注册中心下发
Reason：   变更周期从发版周期压缩到通知周期；复用地址订阅通道，无新链路
Alternative：发版硬编码（周期错配）、独立配置中心+自研推送（新链路新故障面）
Trade-off：规则是外部输入 → 多出来源/传输/生效/回滚四段账；下错规则是局部事故，
           下错代码是全量事故——账本身是划算的
Validation：本层"可观测三仪表"（规则读数回执、重试率、对象增长）→ 见下文"可观测"
```

**五问检查**：规则在哪（来源账）→ 谁负责删（回滚账）→ 生效了如何证明（E05-4 的教训：链路通≠生效）→ 会影响哪些实例（传输账）→ 与发版规则冲突时谁赢（生效账的优先级语义，本文标"机制层，按版本核验"）。

### 决策卡 2：泛化调用选型

```text
Decision：      网关/多语言/测试工具（接口多变、集成边界）→ 泛化调用
Reason：        免 jar 集成，资格/选择/兜底三层仍可复用（机制语义）
Alternative：   强桩集成（维护成本爆炸）、HTTP API 网关（协议栈重新建设）、
                stub 动态生成（构建期依赖，接近强桩）
Trade-off：     对象体量放大 + 失败路径残留 + 线程上下文账（机制一~四）
Validation：    评审必查四项（ReferenceConfig 缓存、destroy 测试、大对象预警、
                只用于集成边界）+ E06 本机 demo 方向性验证
```

### 可观测：治理系统的三个仪表（衔接 05 篇的账）

```text
规则生效验证：下发后必须有"规则读数"回执（调用方当前 RouterChain 内容），
             不能只验证"注册中心里写着"——E05-4 实锤
重试率：      05 篇的指标，规则下错的一个显著表现就是重试率突然抬升
对象增长：    泛化链路的堆增长与 GC 频率（机制一二三的预警）
```

## 🕳️ 坑与细节

- **dataId 双冒号**：条件路由的 dataId 是 `接口全名::.condition-router`——接口名、双冒号、后缀，错一个都不生效（E05-4 实测排障记录，`experiment-005` §5）。
- **group 与 namespace**：本机环境 group=dubbo（`DEFAULT_GROUP`）、namespace 独立创建——与地址服务共用环境时最容易互相污染。
- **规则观测陷阱**："Nacos 里能看到规则" ≠ "consumer 已生效"——3.3.4 纯 API 链路实测：规则读取静默返回 null、无任何日志（`DefaultGovernanceRuleRepositoryImpl` 走模块级环境，装载在应用级 `DefaultApplicationDeployer.java:308`）。
- **`future.sync.set` 默认值**：官方确认默认 true（`SET_FUTURE_IN_SYNC_MODE` 源码 default "true"，#14727）；**3.4 将改为 false**（#14785，breaking change）——按你的版本核验，别拿"默认 false"写运维手册。
- **#7770 有争议**：官方一方认为 demo 是"小堆 + 大请求压力"而非泄漏，另一方指出 ThreadLocal value 强引用链（key 弱、value 强）的实证——本文立场：**"会不会在典型负载下 OOM"有争议，但"2.7.x cleanup 只 reset 不 remove"是源码 tag 核验的客观事实（02 篇）**，且"线程上下文必须清理"是双方共识。
- **ReferenceConfig 复用**：机制三的放大器就是"每次调用新建 ReferenceConfig"——缓存语义不是优化，是内存安全项。
- **2.x 与 3.x 别混讲**：#7770 是 2.7.11 的实证，#11451 是 3.x 的实证，机制不同源，版本必须带锚点。

## 🌐 跨语言 / 跨运行时视角

- **规则热更**的"来源→传输→生效→回滚"四段账不是 Dubbo 独有：K8s ConfigMap/探针、Nacos/Consul 的配置监听、Spring Cloud Config 的 refresh 语义，都是同一结构——**谁持有权威数据、谁负责通知、生效是不是原子、回滚走哪条路**。评审任何"配置即代码"方案都套这四问。
- **泛化调用**相当于强类型世界的 `Object`/反射、Python 的 duck typing、gRPC 的 any 字段——**"运行时描述类型"必然付出体量放大与清理成本**：gRPC-any 也有编解码放大、反射调用有 MethodHandle 缓存账。可以迁移的教训：**运行时类型描述应当只出现在系统边界**（网关/适配器），且必须配有生命周期治理，否则边界组件先死。
