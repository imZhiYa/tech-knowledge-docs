## Level 1：打烊——为什么优雅停机是"先拒新单再关店"

### 👶 前置知识关卡

- [ ] 03 篇：目录摘除 ≠ 接单停止；目录收敛是异步的，service 名可能残留空壳。
- [ ] 04 篇：故障窗口语义（Nacos 1.1s / ZK 13.1s 发现窗口，E04 实测）。

### 1.1 徒弟的直觉

徒弟：

> 下架不就是 `kill -9` 吗？进程没了，请求自然就断了。

老陈：

> 请求"断了"就是事故本身：**在途请求被硬掐**。调用方重试（failover）还好，非幂等写在途掐断 = 状态不明（05 篇的账：重试只对"换店能成"的故障有效）。优雅停机的全部意义，就是让"关门"这个动作**不制造新的故障**。

### 1.2 三步关店（机制层：官方文档口径 vs 3.3.4 实测）

**官方文档口径**（先拒新单 → 送完在途 → 再退出）：

```text
① 先拒新单：摘除服务/停止接收新请求
   └ 注意：注册中心摘除是异步收敛（03 篇残留账），所以还要：
       - 已有连接的消费者收到"不再接单"（连接关闭/优雅拒绝）
       - 新连接不再建立（端口侧停止 accept 或标记停止服务）
② 送完在途：等待已受理请求完成（有超时上限，否则永远关不了门）
③ 再退出：关端口、释放资源、退出进程
```

**3.3.4 实测修正**（E08 反编译 + SIGTERM 实测，`experiments/experiment-008`）：

```text
真实链路：SIGTERM → DubboShutdownHook → 连接层 close 事件
  → TripleServerConnectionHandler.close → GracefulShutdown 握手：
     ① 发 GOAWAY（extraStreamIds=MAX_VALUE）→ 拒新流 ✅ 与口径一致
     ② 发 PING + schedule 10s 超时
     ③ 收到 PING ack（netty 层自动秒回）→ 立即 second GOAWAY + close ❌ 不检查活跃流
  → 在途业务流被掐断 → consumer 收到 CANCELLED
```

**关键差异**：3.3.4 的"送完在途"用的是 **PING 当排空确认**，但 PING ack 语义是"连接活着"，不是"流已排空"——两个语义混用，导致在途请求被误杀。E08-2 实测：8s 在途业务，SIGTERM 时剩 ~4s，连接在业务完成前 ~2s 关闭，consumer 收到 `StatusRpcException: CANCELLED`；业务线程照常跑完（线程池不掐线程），但响应送不出去。

**结论**："送完在途"在 Dubbo triple 3.3.4 上**不可依赖**。10s 兜底的真实角色是 PING 超时（等不到 ack 时兜底），不是等待业务线程的上限。

顺序反过来的后果：

```text
先关端口 / 直接 kill
  → 在途请求被掐 → 调用方看到"连接被重置/超时"
  → 幂等写还好；非幂等写 = 状态不明（单子到底做没做）→ 人工对账
```

### 1.3 与注册中心语义的衔接（03/04 篇账）

- **目录摘除只是"通知不再接新单"的第一道**：Nacos 剔除窗口 1.1s、ZK 13.1s（E04 实测）——窗口期内消费者仍可能打过来，Provider 侧必须自己"拒新单"（不接收新请求、在途送完）；
- **优雅停机与探活分离**：进程活着 ≠ 能接单（04 篇坑 6）；停机信号要能被编排系统（K8s preStop/readiness，跨语言视角）感知。

> 本层留下的新账：门关好了，但**关门的动作做得对不对、开店后健不健康**——得靠"回访"：可观测三件套。下一层。

### Transfer——迁移到其他设计问题

- **"先拒新单再关店"适用于一切有状态的退出**：数据库实例下线（先停写再切读）、消息消费者停拉、K8s pod 终止（preStop → SIGTERM → SIGKILL）——退出顺序本身就是一致性协议。
- **停机是分布式协议的一部分**：它和注册/发现共享同一套"成员变更"语义（谁还在、谁退出），04 篇的窗口思维直接复用。

> 🔴 **口诀**：先拒新单、送完在途、再关灯；顺序反了就是"关门制造新故障"。

## Level 2：回访——可观测三件套：指标、日志、链路追踪

### 👶 前置知识关卡

- [ ] 00 篇：E00 TraceFilter 逐站打印模板；06 篇：治理体系的指标/规则。
- [ ] 05 篇：重试率、invoked 列表等指标清单（E05 采集基线）。

### 2.1 三件套各回答一个问题

```text
Metrics（指标）：整体健康吗？   —— 聚合视角：QPS、RT 分位、错误率、重试率、队列深度
Logs（日志）：  发生了什么？    —— 单点视角：每站的明细记录
Tracing（链路）：这单卡在哪？   —— 请求视角：一次调用的跨站路径与耗时
```

三个视角缺一不可：**只有指标**知道"有 30% 变慢"；**只有日志**知道"某站报了错"；**只有追踪**才知道"这一单到底走了哪条路、卡在哪个环节"。

### 2.2 逐站打印 = 把 00 篇六站图变成监控

E00 的 TraceFilter 就是现成模板（原样引用格式）：

```text
[PROVIDER TraceFilter] enter, thread=DubboServerHandler-198.xx.x.x:50051-thread-2, ...
[PROVIDER Business]   greet() executing, thread=...
[PROVIDER TraceFilter] exit, result=Hello O (sequence=1), ...
```

把这张"逐站打印"扩展成三件套的挂点（机制层建议，未实测验证监控组件集成）：

```text
六站 × 三件套（示例）
  收银台（Proxy 入站）   → Metrics: 调用量 / Logs: 参数摘要 / Tracing: 根 span
  验单台（Filter 链）    → Metrics: 各 Filter 耗时 / Tracing: span 边界
  门店表（候选集）       → Metrics: 候选集大小、空地址次数（03 篇）
  派单（Router/LB）      → Metrics: 选择分布、RouterSnapshot（05 篇）
  打包+信封+骑手         → Metrics: 连接数、帧大小（01/02 篇 T 表）
  后厨（线程池/队列）    → Metrics: 池活跃度、队列深度（07 篇 T38/T39）
```

### 2.3 traceId 透传：把"一次调用"串起来

- Filter 链是天然挂点：consumer 出站 Filter 生成 traceId → provider 入站 Filter 透传 → 业务线程（E00 线程名）继续携带 → 响应回传；
- 跨线程语义：业务在 `DubboServerHandler-` 线程执行，traceId 要随调用上下文（RpcContext 语义，00 篇 Invocation 会话域）传递，不能靠 ThreadLocal 想当然（07 篇 R9 的 ThreadLocal 泄漏史就是教训，06 篇泛化调用也吃过上下文账）。

> 说人话：**可观测性 = 把 00 篇的六站总图逐站装上"仪表 + 记录 + 追踪"**。每站至少一个指标（05 篇判断力 5）、一次日志、一个 span 边界——这是"敢上线"的前提，不是上线后的点缀。

> 本层留下的新账：观测的管道有了，但**上线前的"试营业"**怎么验收？方向性数据怎么用、怎么灰度？下一层。

### Transfer——迁移到其他设计问题

- **三件套分三是可观测性的通用框架**：任何系统（Web 服务、消息队列、大数据管道）都按"聚合/单点/请求"三个视角装仪表——先定视角再选工具。
- **"机制设计时就埋观测点"是工程纪律**：E00 的 TraceFilter 不是后补的；后补的可观测性必然漏关键站。

> 🔴 **口诀**：指标看整体、日志看单点、追踪看单请求；每站至少一个指标、一个 span。

## Level 3：试营业——验收与压测的方法论（方向性数据纪律）

### 👶 前置知识关卡

- [ ] 01/02 篇：E01 压测是"本机单机串行方向性参考，不可外推"。
- [ ] 05 篇：E05 kill 实例重试边界的实测结论与边界。

### 3.1 方向性数据纪律（本系列贯彻的验收方法）

```text
第一步：本机方向性验证（快、便宜）
   E01：本机 8 组压测 → "dubbo 直连更快 / kryo 快 ~25%" —— 只回答"方向"，不回答"数值"
第二步：生产灰度对比（真、可信）
   同协议换盒子 / 换协议：灰度流量上对比 latency / throughput / 错误率
第三步：基线校验（防漂移）
   监控项先有基线（E05 指标清单），变更后对照基线看差异，而不是看绝对值
```

教训来源（E01/E05）：

```text
E01：单机串行压测 → 上线后行为不同（坑 7，01 篇）
E05：kill 实例重试对比 → 重试"无差异"的实测结论 —— 不实测就会凭直觉配置
```

### 3.2 验收清单（把"敢不敢上线"变成动作）

```text
① 方向性数据齐了（协议/序列化/线程预算的方向结论）
② 灰度路径设计好（tag 路由 + 回滚预案，06 篇）
③ 三件套挂点验证（每站至少一个指标，L2）
④ 预算表评审过（最坏等待 ≤ 上游容忍度，07 篇）
⑤ 幂等/重试声明逐接口核对（05 篇）
⑥ 优雅停机演练过（L1：实测发现 triple 3.3.4 "送完在途"不可靠——在途会被 CANCELLED，所以**幂等/对账才是停机安全的底牌**）
```

> 说人话：**验收不是"压测过了就上线"，而是"方向性数据 + 灰度对比 + 基线校验"三连**——单机压测只告诉你方向，生产灰度才告诉你数值，基线校验防止你下次改坏。

> 本层留下的新账：验收方法有了，**选什么技术**呢？——全系列的决策卡该总装成一张表了。下一层。

### Transfer——迁移到其他设计问题

- **方向性数据纪律适用于一切技术选型**：benchmark 结论只回答"方向"，任何"更快/更稳"的数字都要在目标场景灰度复验。
- **验收 = 可评审的动作清单**：把"敢不敢上线"翻译成勾选项（灰度路径/回滚/观测/预算/演练），评审会就有了可反驳对象。

> 🔴 **口诀**：本机定方向、灰度定数值、基线防漂移；验收清单先于上线。

| 优雅停机/观测 | 先拒新单再关店；三件套逐站挂点（08 篇 L1/L2） | 停机语义与注册窗口联动 |

### 4.2 决策的优先级（先答哪一问）

```text
1. 生态边界：谁要读这封信（网关/多语言）→ 协议
2. 互通契约：盒子与信封两层对齐 → 序列化
3. 成员变更语义：候选集从哪来 → 注册中心
4. 失败语义：幂等性声明 → 容错与预算
5. 治理与观测：止损半径 + 三件套 → 治理面与可观测
```

> 说人话：**选型不是"每个点单独挑最好的"，而是从生态边界往外推**——先定协议与序列化（开放/互通），再定注册与容错（成员变更/失败语义），最后补治理与观测（止损/可见）。

### 4.3 评审时的三问（架构评审视角）

1. **每笔账还上了吗？**（02 篇 Hessian 账 / 03 篇 URL 账 / 05 篇重试账 / 07 篇预算账）
2. **每站可观测吗？**（00 篇六站 × 每站一个指标）
3. **最坏路径是什么？**（注册中心挂了 / 半死不活的店 / 在途掐断——04/05/08 各有一张窗口账）

> 本层留下的新账：新架构定完了，但**存量系统怎么走过去**？——2.7→3.x 迁移路线图收尾。下一层。

### Transfer——迁移到其他设计问题

- **"总装表"是架构评审的通用载体**：把各技术决策放进一张互相约束的表，评审会讨论"约束"而不是"单个技术好坏"。
- **从生态边界往外推是选型的第一优先级**：谁消费你的数据、谁调用你的服务，先于一切内部偏好。

> 🔴 **口诀**：先定生态边界（协议/序列化），再定成员变更（注册），后定失败语义（容错/预算）；每笔账还上、每站可观测、最坏路径有数。

## Level 5：迁移路线图——从 2.7 五笔账收尾

### 👶 前置知识关卡

- [ ] 00 篇 L1：2.7.x 的两笔大账（URL 爆炸 / 私有协议）。

### 5.1 三条迁移线（对应 00 篇的两笔账 + 序列化账）

```text
账① URL 爆炸（接口级发现）→ 应用级发现
   迁移要点（03 篇决策卡 1）：统一应用命名 → 映射来源（配置中心/providedBy）
   → 双轨过渡（register-mode=all）→ 先 all 后拆 interface，保留回滚

账② 私有协议穿透差 → Triple
   迁移要点（01 篇 L5）：先迁网关必经之路的服务 → 双协议并存灰度
   → 网关路径验证通过再迁其余

账③ 序列化升级 → 协商机制
   迁移要点（02 篇 L2）：prefer-serialization 服务端宣告 + 客户端协商 + 兜底
   → 两端依赖齐了才协商到 fastjson2，否则回退 hessian2
```

### 5.2 迁移纪律（贯穿 01/03 篇的原则）

```text
① 按流量路径排序：网关必经之路最先迁（01 篇）
② 双轨并存：新旧能力同时导出（协议双导出 / register-mode=all），保留回滚
③ 观测先行：迁移前先有基线（三件套），迁移中对比基线（L3）
④ 一次只动一条线：协议/发现/序列化三条线不要同一次发布全切
```

### 5.3 系列闭环

00 篇立下六站总图 → 01~07 逐站打深井（信封/盒子/门店表/台账/派单/规则/线程）→ 08 篇把每一站收成"上线动作"。回到 00 篇的问题："一次 RPC 调用到底发生了什么"——现在每一站都有源码/实测/决策三层答案。

> 说人话：**迁移 = 还 2.7 的账，但一次只还一笔**；每笔账都有"双轨 + 回滚 + 基线"三个护栏。

### Transfer——迁移到其他设计问题

- **"一次只动一条线"是大型迁移的第一纪律**：多变量同时变更时，出问题无法归因（对照 07 篇"单变量决策必翻车"）。
- **迁移 = 还账 + 护栏**：每条迁移线自带双轨/回滚/基线三个护栏，是任何技术栈升级（Java 版本、框架大版本、数据库）的通用模板。

> 🔴 **口诀**：先网关路径、双轨保留、基线先行、一次一条线。

| 7 | 指标没有基线就上线 | 观测无参照 | 变更无法对比 | 变差看不出差在哪 | 迁移前先采基线（E05 清单）。 |

## 🌍 跨语言 / 跨运行时视角

| Dubbo 视角 | 跨语言同构对象 | 不变的问题 |
|---|---|---|
| 优雅停机（先拒新单再关店） | K8s pod 终止（preStop → SIGTERM → SIGKILL）、数据库实例下线 | 退出顺序 = 一致性协议 |
| 目录摘除异步窗口 | K8s Endpoint 收敛、DNS TTL、负载均衡器摘流 | 摘除异步 → 数据面自己拒新单 |
| Metrics/Logs/Tracing | Prometheus、ELK、OpenTelemetry（OTel）标准 | 聚合/单点/请求三个视角 |
| traceId 透传 | W3C traceparent、Jaeger/Zipkin | 跨线程/跨进程上下文传递 |
| 方向性数据纪律 | 一切技术选型与容量评估 | 本机定方向、灰度定数值、基线防漂移 |
| 迁移路线图 | 蓝绿/金丝雀发布、数据库分库迁移 | 一次一条线 + 回滚 + 基线 |

### 跨语言后仍成立的 6 条判断力

1. **优雅停机是"先拒新单再关店"**——退出顺序本身就是一致性协议，K8s preStop 与 Dubbo 停机同构。
2. **目录摘除 ≠ 接单停止**——异步收敛有窗口，数据面必须自己拒新单。
3. **三件套各管一个视角**——指标看整体、日志看单点、追踪看单请求；缺一个就有一类问题看不见。
4. **本机定方向、灰度定数值、基线防漂移**——任何 benchmark 结论都要过这三关。
5. **选型从生态边界往外推**——先协议/序列化，再注册/容错，后治理/观测；单点最优是伪最优。
6. **迁移一次一条线**——多变量同时变更无法归因；每条线带双轨/回滚/基线。
