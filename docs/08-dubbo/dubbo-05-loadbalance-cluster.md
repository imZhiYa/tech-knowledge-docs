## 🏭 全文唯一比喻地图


```text
候选门店列表（注册中心给的营业表）
   │
   ├─ 资格审核（Router）── 今天营业吗？骑手覆盖吗？会员专享吗？灰度名单有我吗？
   │       └─ 过滤后的"可派单门店"集合
   ├─ 派单规则（LoadBalance）── 轮流 / 随机加权 / 闲者优先 / 老顾客固定熟店
   │       └─ 挑出"这一单派给谁"
   └─ 拒单与失联（Cluster）── 打过去拒单/占线怎么办
           ├─ 换一家再试（failover，默认）
           ├─ 立刻放弃（failfast）／ 吞掉（failsafe）
           ├─ 记小本本稍后补（failback）
           ├─ 同时问几家（forking）／ 全问一遍（broadcast）
           └─ 全挂了自动回话"今日已打烊"（mock 降级）
```


| 中央厨房元素 | Dubbo 技术对象 | 它负责的唯一一件事 |
|---|---|---|
| 候选门店列表 | RegistryDirectory 本地候选集 | 从注册中心快照 + 路由链过滤后，得到"这一单可派的门店"。 |
| 资格审核 | Router 链（条件/标签/状态路由） | 在"选谁"之前先回答"谁有资格"，把候选集缩小。 |
| 派单规则 | LoadBalance（random/roundrobin/leastactive/…） | 在合格集里按规则挑一个 Invoker。 |
| 新店磨合期 | 预热（warmup 降权） | 刚开业的门店权重按运行时长渐进恢复，避免被瞬间打满。 |
| 老顾客固定熟店 | sticky 粘性（默认关闭） | 同会话/同参数尽量复用上一次选中的门店。 |
| 拒单换一家 | failover（默认 cluster） | 失败后排除已试门店，最多试 N+1 家（retries 默认 2）。 |
| 记小本本稍后补 | failback | 失败任务异步重试，调用方先拿到成功返回。 |
| 全挂自动回话 | mock 降级 | 真实门店全不可用时，返回预置的"打烊"应答，保住调用链路。 |


> 📌 比喻边界：**Router 管"谁有资格"，LoadBalance 管"选谁"，Cluster 管"选错之后"**——三者是同一份候选集上三个不同时点、不同目标的决策，不是同一件事的三个叫法。混在一起，排障时就会在"为什么没打到我预期的店"上绕圈。

## Level 1：为什么不能永远选同一家——单门店的失败


### 👶 前置知识关卡


- [ ] 03 篇：注册中心给 consumer 的是"候选地址列表"，不是"唯一地址"。
- [ ] 04 篇：本地缓存目录在控制面失联时仍可派单；剔除/残留的窗口由注册中心语义决定。
- [ ] 04 篇：打到"已摘除/已死亡"的地址，由调用侧兜底——**这层兜底就是本文 Cluster 的账**。

### Why——上一代方案死在哪


**徒弟**：03、04 篇绕了这么大一圈，候选列表都有了。那订单 O 直接从列表里抓第一家，不行吗？

**老陈**：可以——假设列表永远只有一家，且这一家永远活着。现实是：一旦列表有了第二家，三个问题立刻出现——**凭什么选这家？**（L2）**谁没资格？**（L3）**选了之后挂了怎么办？**（L4）。

先看"只有一家"时的死法：

```text
永远选同一家（直连单地址）
   ├─ 发布/升级：店关了做改造 → 这一单没人接           ← 发布=停服
   ├─ 扩容：第二家店开了，调度台根本没机会知道怎么用   ← 扩容=改配置（甚至停机）
   └─ 故障：这家店爆单/宕机 → 订单 O 必失败            ← 故障=全挂
```

**单门店直连的死法不是"这家店不行"，而是"所有风险都绑在同一个地址上"**：发布、扩容、故障三个场景都没有逃生门。候选列表的价值恰恰在于——**每一单都有"换一家"的可能**。


| 朴素方案 | 它本来想解决什么 | 它留下的致命账 |
|---|---|---|
| 直连一个地址 | 最简单，零决策 | 发布停服、扩容停机、故障全挂。 |
| 客户端轮询列表（自己写循环） | 至少能换店 | 换店时机、失败判断、并发安全全部自己造轮子；每次加一家店改一次代码。 |
| 全部打一遍取成功 | 保证至少一个成功 | 同一订单被多家店同时处理（重复下单）；正常流量下也是 N 倍调用量。 |

### What——新结构是什么


```text
单门店：   订单 O → 唯一地址 → 结果
多门店：   订单 O → 候选集（N 家）
                    ├─ 资格过滤（Router）→ 可派集合（M 家，M ≤ N）
                    ├─ 规则选择（LoadBalance）→ 选中 1 家
                    └─ 失败兜底（Cluster）→ 重试/放弃/补偿
```

关键不变量：**三个决策时点互相不越权**——Router 不改"选谁"的规则，LoadBalance 不判"谁没资格"，Cluster 不决定"下一次选谁"（它只排除已试的）。

### How——订单 O 的慢动作


```text
① 候选集：注册中心快照给出 N 家（03/04 篇已闭环）
② 过滤：Router 链逐家问"这单你有资格接吗" → M 家
③ 选择：LoadBalance 从 M 家里按规则挑 1 家
④ 调用：发出请求
⑤ 失败：Cluster 决定下一步（重试/放弃/补偿/并发）
```

**徒弟**：那我把"规则"写在调用方里，每家店权重写死，不就行了吗？为什么 Dubbo 要搞三个层次？

**老陈**：因为三个问题变化的频率和目标完全不同——"谁有资格"跟着业务策略变（灰度、区域、会员），"选谁"跟着运行时状态变（预热、负载、响应速度），"失败怎么办"跟着成本预算变（幂等性、重试成本）。写死在一起，就是改一个需求动一次调用方代码。分层之后，每一层都能独立配置、独立动态下发——这就是 L2/L3/L4 各自的账。

### Transfer——迁移到其他设计问题


- 任何"从一个集合里挑一个执行者"的系统都在回答同一组问题：**资格（谁行）→ 选择（选谁）→ 兜底（不行了怎么办）**。DNS 轮询、K8s Service/Endpoint + 探针、消息队列的消费分配、数据库连接池选连接，都是同一结构。
- "换一家"能力是候选列表的隐含价值：**没有候选集，就没有容错的原料**——单地址时代的所有"高可用"都是假的。
- 分层决策的判据：**变化频率不同就分层，变化频率相同才合并**。


> 本层留下的新账：候选集有了，第一层决策来了——**从 N 家里"选谁"，规则怎么定？** 随机、轮流、按闲忙、按快慢、按请求特征，每种规则在换什么？
>
> 🔴 **口诀**：**候选列表是容错的原料；资格、选择、兜底，三个时点三种账。**


<a id="level-4"></a>
## Level 2：LoadBalance——在合格候选里按规则选一家


### 👶 前置知识关卡


- [ ] L1：候选集为什么存在；三个决策时点为什么要分层。
- [ ] 03 篇：接口级/应用级注册下，consumer 拿到的候选集形态不同（URL 列表 vs 实例 + 元数据）。

### Why——为什么不能"随便挑一个"


**徒弟**：既然每家店都能接单，那随机挑一家不就行了？还搞什么算法。

**老陈**：随机确实是最低成本的方案，也是默认方案——但"随机"的前提是**每家店能力相同**。现实里有两个不对称：**静态不对称**（机器规格不同 → 权重）和**动态不对称**（新店刚开业、老店快挂了 → 预热与活跃度）。没有权重，小餐馆和大酒楼平分订单，小餐馆先死；没有预热，新店开业第一秒就涌进全网流量，直接打垮。

**LoadBalance 的完整命题是：在合格集合里，按"能力不对称"分配流量，并让每个算法的不对称模型可配置。**

### What——核心机制与不变量


```text
LoadBalance.select(invokers, invocation) → 1 个 Invoker
     │
     ├─ 权重从哪来：静态 weight 参数 + 动态预热降权（getWeight）
     ├─ 各算法只看同一份权重，但"分布目标"不同
     └─ 不变量：单次选择是确定性的（给定输入，输出可复现）
```

Dubbo 3.3.4 `dubbo-cluster/.../loadbalance/` 的算法族（机制层，按 3.3.4 源码）：

| 算法 | 分布目标 | 它在换什么 |
|---|---|---|
| random（默认） | 按权重随机 | 实现最简；单次看"概率"，小流量窗口内不保证均匀。 |
| roundrobin | 按权重平滑轮询 | 保证"任意前缀窗口内配额公平"；实现是平滑加权轮询（当前权重 = 当前 + 静态权重，取最大者，减去总权重）。 |
| leastactive | 打向活跃请求数最少的店 | 用"在途请求数"做动态不对称建模；活跃数本身是运行时统计。 |
| shortestresponse | 打向成功响应时间最短的店 | 用"响应时间"做动态不对称建模；需要统计窗口与平滑。 |
| consistenthash | 同参数请求固定打向同一家 | 用"请求参数哈希"绑定门店；门店增减时只迁移部分键（虚拟节点环）。 |
| adaptive（3.3 新增） | 按运行时健康指标自适应 | 把 CPU/内存/响应时间等指标喂进选择模型；机制层按 3.3.4 源码与文档核验。 |

**预热（warmup）——机制层，按 3.3.4 源码核验**：`AbstractLoadBalance.getWeight` 里，实例运行时长（uptime）小于预热窗口（warmup）时，权重按 `uptime / (warmup / weight)` 比例降权——**新门店开业初期权重低，随运行时长线性恢复**。这解决"新店冷启动被流量打垮"：权重不是纯静态的，是"静态权重 × 预热进度"。

**平滑加权轮询（roundrobin）**——机制层，按 3.3.4 源码核验：不是"数到几打谁"，而是每轮给每家"当前权重 += 静态权重"，选当前权重最大者，再对选中者"当前权重 -= 总权重"。效果：**权重 4:1 的两家店，流量严格按 4:1 交错（A A A A B A A A A B…），没有"连打 4 次再歇 1 次"的抖动**。这是解决"普通加权轮询分布不匀"的经典平滑化——Nginx 平滑加权轮询同一思想。

**一致性哈希（consistenthash）**——机制层，按 3.3.4 源码核验：虚拟节点放 TreeMap 环，`hash.arguments` 指定参与哈希的请求参数（默认按方法第一个参数，需按版本核验）；**invokers 列表的 hashCode 变化时整体重建 selector**——所以"门店增减导致迁移多少键"取决于环上虚拟节点数（**3.3.4 源码默认 `HASH_NODES=160`**，源码实证），增减节点只影响环上一小段。

**leastactive**——机制层，按 3.3.4 源码核验：先找出活跃数最小的那组（可能多家并列），再在这组内按权重随机——**"闲者优先"是粗筛，组内仍是权重随机**。

### How——订单 O 的慢动作（选店规则怎么起作用）


```text
① 候选集（M 家）进来
② 每家算当前权重 = 静态 weight × 预热系数（uptime 相关）
③ 算法按自己的分布目标挑一家：
      random：按权重总和随机落点
      roundrobin：平滑加权（当前+=静态；取最大；选中者减总权重）
      leastactive：先筛活跃最少组，组内按权重随机
      consistenthash：按参数哈希走环，命中虚拟节点
④ 返回这一家 → 进入调用
```

**徒弟**：那 leastactive 最智能啊，怎么默认不是它？

**老陈**：leastactive 的"活跃数"是运行时统计——统计有窗口、有滞后：**请求极快时活跃数几乎恒为 0，等于随机；请求极慢时活跃数能反映排队，但统计窗口要精心调**。它的不对称模型比随机更复杂，但**复杂性本身是成本**：每个算法换的东西不一样，没有免费的午餐。随机是"无信息时的最简选择"，roundrobin 是"有配额需求的确定选择"，一致性哈希是"有状态依赖（会话/缓存）的选择"——选哪个，取决于你的流量有没有状态、重不重会话、门店差异大不大。

### Transfer——迁移到其他设计问题


- **加权与预热是通用思想**：K8s 滚动发布的新 Pod 有 readiness 缓冲、CDN 的新节点有预热、数据库连接池的新连接有 min-idle——"新成员按进度渐进接管流量"到处是同一笔账。
- **平滑加权轮询 = "配额公平"问题的标准解**：任何"多个参与方按比例分流量/分任务"的场景（DNS 加权、消息分片、限流配额），平滑化都能消除"吃一段饿一段"。
- **一致性哈希的迁移语义**：只影响环上一小段——这就是"缓存/会话亲和"系统选它的原因；反过来说，**无状态系统用它反而引入"选择不随机"的代价**（热点参数会把流量钉死在一家）。
- 选算法前先问：**我的请求有状态吗？我的门店差异是静态还是动态？我对分布均匀有硬性要求吗？** 三个答案决定算法族。


> 本层留下的新账：选店规则定了，但"选"发生在**整个候选集**上——**灰度流量、区域限流、会员专享这类"资格"问题还没解决**。在选之前，要不要先把没资格的门店筛掉？
>
> 🔴 **口诀**：**权重管"能力差"，预热管"新店冷启动"；算法没有免费午餐，每个都在换一个不对称模型。**


<a id="level-5"></a>
## Level 3：Router——为什么必须在选之前先过滤


### 👶 前置知识关卡


- [ ] L2：LoadBalance 作用在"合格集合"上——集合的定义权在 Router。
- [ ] 04 篇：注册中心通知变更时，consumer 更新本地候选集（RegistryDirectory 快照）。

### Why——为什么不能"先选后筛"


**徒弟**：我理解要搞灰度：让 10% 的订单去新版门店。但放 LoadBalance 后面做不行吗？先选一家，再检查它有没有资格，没资格就重选，不行吗？

**老陈**：能跑，但有两个致命账：

```text
先选后筛（错误的顺序）
   ├─ 资格是"集合级"概念，选择是"单点级"概念
   │     └─ "灰度期间新店只接 10% 流量"= 资格判定要影响集合的构成，不是单点概率
   ├─ 筛选失败重选 → 重选次数不可控
   │     └─ 10 家里 9 家没资格时，平均要选 10 次才命中 1 家 → 选择成本放大
   └─ 更关键：规则下发（动态调整灰度比例）时，选层无法感知
           └─ 规则跟着注册中心通知走，只有"过滤集合"这一条路能统一生效
```

**Router 存在的意义：把"谁有资格"变成候选集合的前置收缩**——LoadBalance 永远只看到"有资格的那 M 家"，选择层不需要知道资格规则的存在。资格规则变了，集合收缩就变，选择层无感。

### What——核心机制与不变量


**Router 链（3.3.4 `dubbo-cluster/.../router/`）**：一个请求会按顺序经过多个 Router，**每个 Router 对当前集合做一次收缩，输出交给下一个**：

```text
候选集(N) → Router1 → Router2 → ... → Routerk → 最终可派集合(M)
     资格判定是"链式收缩"，不是单点二值
```

| Router 类型（3.3.4 目录） | 资格模型 | 典型场景 |
|---|---|---|
| condition（条件路由） | 按接口/方法/参数 + 地址条件匹配（黑白名单、限流条件） | 区域隔离、环境隔离、方法级限流 |
| tag（标签路由） | 按标签匹配（tag 规则 + 请求携带 tag） | 灰度发布（打标服务 + 打标请求） |
| state（状态路由，3.3） | 按服务状态（ProviderAppStateRouter 等）动态调整 | 服务健康状态驱动的流量调整（机制层，按 3.3.4 核验） |
| script / mesh / file | 动态脚本 / mesh 规则 / 本地文件 | 高级自定义（机制层，本文不展开） |
| mock | mock 语义路由 | 降级/测试 |

**规则从哪来（动态下发）**：注册中心里 `router` 类配置 URL 随服务通知一起给到 consumer → `RegistryDirectory.toRouters(routerURLs) → addRouters` → RouterChain 追加 Router（3.3.4 `RegistryDirectory.java`）。**灰度比例、黑白名单的修改不用发版、不用重启 consumer——改配置下发即生效。**

**执行点（源码级，3.3.4）**：`AbstractDirectory.list()` → `RouterChain.getSingleChain()` → `SingleRouterChain.route()` 顺序执行链上 Router（3.3.4 的 `route()` 已 @Deprecated，内部即委托给 getSingleChain）。`RouterChain.setInvokers` 用 **main/backup 双链 + 读写锁**切换：先 `currentChain = backupChain` 让刷新期间的请求全部走 backup（保持旧视图），再持 main 链写锁刷新 `mainChain.setInvokers`，完成后原子切回 main——**保证"路由期间地址变更"不会让 consumer 看到半新半旧的候选集**（3.3.4 `RouterChain.java`）。

### How——订单 O 的慢动作（灰度怎么生效）


```text
① 运营下发规则："新版门店打 tag=canary，灰度 10% 请求"
   └─ 规则 URL 进注册中心 → consumer 订阅收到 → RegistryDirectory.addRouters
② 订单 O 到来（携带 tag=canary 的请求）
③ Router 链执行：
      condition/tag router 检查请求 tag vs 门店 tag
      → 命中灰度的请求：集合 = {新版门店}
      → 未命中：集合 = {老版门店}
④ 收缩后的集合交给 LoadBalance → 选中 1 家
⑤ 灰度比例调大（20%）：只改规则，consumer 无感，选择层无感
```

**徒弟**：那条件路由和标签路由什么区别？我该用哪个做灰度？

**老陈**：**条件路由是"按请求内容匹配地址"**（请求带什么参数 → 去哪些地址），**标签路由是"按标签匹配"**（请求 tag 与 provider tag 对齐才放行）——标签路由更适合灰度，因为灰度本身就是"打标"（provider 打 canary 标、流量打 canary 标、规则决定哪些标对上）；条件路由更适合隔离类需求（环境、区域、黑白名单）。另外注意：**灰度不只是路由**——新版门店如果挂了，灰度流量要能自动切回老版，这已经是 L4 Cluster 和熔断的账了。

### Transfer——迁移到其他设计问题


- **"过滤前置"是通用架构原则**：数据库查询的"下推"（过滤条件给存储层而不是客户端再筛）、网关的路由（按 host/路径先分流再进后端）、K8s 的 labelSelector——**先把集合缩小，再谈选择，是降复杂度的第一手段**。
- **规则与执行分离**：Router 不内嵌规则，规则从注册中心/配置中心下发——"策略可热更"是所有流量治理系统的共同形态（网关路由表、Envoy xDS 同构）。
- **链式收缩**：多个资格模型叠加时用链，每个 Router 只做一件事——可插拔、可单测、可观测（3.3 的 RouterSnapshot 就是为此设计的，机制层按 3.3.4 核验）。


> 本层留下的新账：资格筛完了，店也选出来了，**请求打过去——门店挂了、拒单了、超时了，怎么办？** 重试换一家？立刻放弃？稍后补偿？这些选择各自把什么代价留给系统？
>
> 🔴 **口诀**：**资格是集合级、选择是单点级；先筛后选，规则下发热更。**


<a id="level-6"></a>
## Level 4：Cluster——选中后失败，代价由谁承担


### 👶 前置知识关卡


- [ ] L1–L3：候选集 → 过滤 → 选择，三次决策后请求发出。
- [ ] 04 篇：注册中心剔除死店有窗口（Nacos ~1.1s / ZK ~13s）——**窗口内打向死店是常态，不是异常**。

### Why——为什么"重试三次"不是万能解


**徒弟**：终于到兜底了。简单——失败就换一家重试，重试 3 次总行了吧？

**老陈**：先给你看重试的完整账，再决定要不要"重试 3 次"：

```text
失败重试的代价（三本账）
   ├─ 账 1：重试风暴（雪崩）
   │     所有 consumer 同时超时 → 同时重试 → 全部流量瞬间打向"第 2 家"
   │     → 第 2 家也被打挂 → 重试第 3 家 → 全挂 = 全网雪崩
   │     （重试放大了故障：故障 1 台，重试把它扩散到 N 台）
   ├─ 账 2：幂等
   │     门店可能"处理了但响应丢了"——重试 = 同一订单被处理两遍
   │     下单/扣款/加库存类操作，重复执行 = 资损
   └─ 账 3：超时叠加
   │     单次超时 T，重试 R 次 → 调用方最坏等待 T × (R+1)
   │     → 上游的调度台等不起，自己的超时参数等于没设
```

**Cluster 的完整命题：用"可接受的其他代价"换取"这次调用有结果"**——每种 cluster 是在"重试的代价"与"失败的代价"之间选一个位置。默认值是什么、每个位置换什么，看机制。

### What——核心机制与不变量


**八种 Cluster（3.3.4 `dubbo-cluster/.../support/`，机制层按源码核验）**：

| Cluster | 失败后的行为 | 它换的代价 | 适用 |
|---|---|---|---|
| failover（默认） | 排除已试者，换一家重试，`retries` 次（默认 2） | 重试风暴/幂等/超时叠加 | 幂等读类调用、门店多且健康 |
| failfast | 立即抛异常，不重试 | 快速失败（无重试代价） | 非幂等写、一次不可重复的操作 |
| failsafe | 吞掉异常，返回空结果 | 静默丢失 | 日志、统计、旁路调用 |
| failback | 失败入队，后台异步重试 | 丢失时延，换来"调用方不感知" | 补偿任务、可延迟执行的作业 |
| forking | 并发调 `forks` 家，取第一个成功 | 放大 N 倍流量 | 极短平快的查询，容忍放大 |
| broadcast | 逐家调用全部，汇总结果 | 同步等最慢一家 | 批量通知、缓存刷新 |
| available | 直接调第一个可用者 | 无选择算法（不 failover） | 单活场景 |
| mergeable | 调多家合并结果 | 合并逻辑成本 | 聚合查询（机制层，本文不展开） |

**failover 重试循环（源码级，3.3.4 `FailoverClusterInvoker.doInvoke`）**：

```text
len = retries + 1                        // 默认 retries=2 → 最多打 3 家不同门店
for (i = 0; i < len; i++) {
    invoker = select(loadbalance, invokers, invoked)   // select 排除 invoked（已试过的）
    invoked.add(invoker)
    try { return invoke(invoker) }
    catch (非业务异常) { 记录；继续下一轮 }            // 业务异常（BizException）不重试
}
throw 最后一个异常（并记录初始错误）
```

三个机制细节（3.3.4）：
1. **重试是"排除已试者再选"**——不是打同一家 N 遍；`retries=2` 意味着**最多打到 3 家不同的店**。
2. **业务异常不重试**——门店正常返回了业务错误（比如"库存不足"），重试没有意义；只有"调用异常"（连不上、超时、解码失败）才值得换店。
3. **`AbstractClusterInvoker.select` 还有 sticky 粘性（默认关闭）与 availableCheck（默认开启）**：sticky 开启时优先复用上次选中的店（老顾客熟店）；availableCheck 开启时每次选择先确认店可用。

**mock 降级（3.3.4 `wrapper/MockClusterInvoker`）**：`mock` 参数存在时，cluster 外再包一层 mock 逻辑——**真实调用失败（或显式 mock 开关）时，返回预置的降级响应**（"门店全挂了，自动回话今日打烊"），调用方拿到的是"业务可接受的结果"而不是异常。这是"用假结果换链路存活"。

> **E10 实测边界（2026-08-12，`experiment-010-mock.md`）**：mock 是 **Cluster 层特性**——只在注册中心路径生效。`setUrl` 直连返回裸 TripleInvoker，`mock=force:return null` 写进 URL 也无人解析（实测抛 `RemotingException` 建连失败）。排查"mock 不生效"先确认调用走的是注册中心路径，不是直连。

### How——订单 O 的慢动作（选错之后）


```text
场景：订单 O 打到门店 A（failover 默认，retries=2）
  ① A 超时（注册中心还挂着它——04 篇的剔除窗口）
  ② doInvoke 捕获异常 → invoked={A} → select 从 {B,C,D} 里重选 → 打 B
  ③ B 也超时 → invoked={A,B} → select 从 {C,D} 重选 → 打 C
  ④ C 成功 → 返回
  总耗时 = 3 次调用的等待（若每次都超时 = 3 × 超时）
```

> **E05 实测边界（3.3.4）**：上面的"超时→重试"是**发起时失败**的语义。但 kill -9 一个实例的实测发现另一条路径——**连接层 invalidate 比重试更快**：
> 1. kill 后新请求：连接建立即失败 → `AbstractDirectory` 把死实例加入 invalidate 列表（日志 `has been added to invalidate list due to connectivity problem`）→ select 阶段直接排除 → 实测 300/300 全兜住（甚至 retries=0 也一样，见 E05-3）
> 2. **kill 瞬间的在途请求**（请求已发出、连接被切断）：tri 协议下以 CANCELLED 异步完成 future → `FailoverClusterInvoker` 拿到 `AsyncRpcResult` 后不 await 直接 return → 异常在上层 `get()` 才冒出 → **重试机会已失去** → 实测 3 轮中 1 轮出现 1 FAIL（`RpcException: ExecutionException: StatusRpcException: CANCELLED`）
>
> **语义**：failover 兜"发起时失败"，兜不住"在途被切断"——后者正是 K8s preStop / SIGTERM 优雅下线（先停新单、再清在途）必须存在的原因（04 篇场景 B ③' 的账）。

**徒弟**：那 failover 这么多坑，为什么还是默认？

**老陈**：因为"读多写少、门店多、剔除窗口存在"的系统里，**重试是性价比最高的失败兜底**——网络抖动、门店偶发拒绝这类瞬时故障占绝大多数，换一家就好了；而重试的三本账（风暴/幂等/叠加）可以通过**预算设计**约束住（L6）。它不是万能解，是"默认解"——真正的工程决策是：**哪些调用开重试、重试几次、什么异常才重试、超时怎么定**。

### Transfer——迁移到其他设计问题


- **重试三本账是通用模型**：数据库连接重试、消息发送重试、HTTP 重试、K8s 探针重试——任何"失败再试"都要回答风暴/幂等/叠加三问。**重试预算 = 超时 ×（重试次数 + 1）**，这条算式到处成立。
- **"排除已试者"是去重试风暴的关键细节**：重试打向"没试过的节点"（轮换），而不是"再打一次同一个节点"——数据库 failover、DNS 多 IP 重试同构。
- **业务异常不重试 = 区分"错误"与"业务拒绝"**：HTTP 里 5xx 可重试、4xx 不可重试，同一思想。
- **mock 降级 = 用假结果换链路存活**：网关兜底响应、前端静态降级页、消息消费的"跳过坏消息"，同构。


> 本层留下的新账：三层机制都清楚了，但**它们不是独立开关——一次调用要把它们串成一条完整决策栈**。Router、LoadBalance、Cluster 在源码里到底怎么按顺序执行？retries 与超时在调用链里怎么相互作用？
>
> 🔴 **口诀**：**重试不是免费午餐：风暴、幂等、超时叠加三本账；业务异常不重试，排除已试者再选。**


<a id="level-7"></a>
## Level 5：全链路走查——一次调用的完整决策栈


### 👶 前置知识关卡


- [ ] L2–L4 三个机制的各自语义。
- [ ] 03 篇：consumer 引用接口后拿到的是"代理 + 本地目录"。

### Why——为什么需要"走查"这一层


**徒弟**：三个机制单独都懂了。但看报错日志的时候，什么 MockClusterInvoker、FailoverClusterInvoker、AbstractClusterInvoker 一层套一层，根本分不清谁是谁。

**老陈**：这正是要走的账——**Dubbo 的调用链是"装饰器嵌套"，每一层解决一个 L1 到 L4 的问题**。走查一次调用，就能在报错栈里认出每一层是谁、干了什么、为什么在那里。

### What——决策栈的结构（3.3.4）

```text
ReferenceConfig 代理（接口代理）
   └─ MockClusterInvoker            ← 有 mock 配置才包这一层（L4 mock 降级）
        └─ 某 ClusterInvoker（默认 FailoverClusterInvoker）
             ├─ AbstractClusterInvoker.invoke()
             │    ├─ directory.list()          ← RegistryDirectory：候选集 + Router 链
             │    │    ├─ 本地候选集（注册中心快照，03/04 篇的账）
             │    │    └─ RouterChain.getSingleChain()  ← L3：资格过滤（条件/标签/状态）
             │    ├─ select(loadbalance, ...)  ← L2：sticky 检查 → 预热权重 → 算法选择
             │    └─ invokeWithContext(invoker, invocation)
             └─ FailoverClusterInvoker.doInvoke()
                  └─ for retries: select(排除已试) → invoke → 业务异常不重试
                       └─ 传输层（tri/dubbo 协议）→ provider 门店
```

**执行顺序（源码级，3.3.4）**：

```text
1. 接口代理收到调用（一次 RPC 的入口）
2. MockClusterInvoker：若 mock 参数存在且命中 mock 语义 → 直接降级，不往下走
3. AbstractClusterInvoker.invoke（模板方法）：
   a. directory.list()：从 RegistryDirectory 取候选集（本地快照 + 规则链收缩）
      - RegistryDirectory 实现 Directory.list → AbstractDirectory.list → RouterChain.getSingleChain
      - RouterChain 双链切换保证"地址变更 vs 路由执行"互不撕裂
   b. 候选集非空检查（04 篇"空地址列表清空候选"的 FAIL 就发生在这里）
    c. select(loadbalance, invocation, invokers, selected)：
       - sticky 开启且上次的店仍可用 → 直接返回上次的店
       - 否则 doSelect → LoadBalance.select（预热权重在此计算）
       - 若选中的店不可用且 availableCheck → reselect（重选）
       - 边界：单 URL 直连（setUrl 单地址）走 point-to-point 短路路径，不经过
         LoadBalance.select——E09-5 实测（experiment-009-spi.md）；排查"负载均衡不生效"
         先确认 invoker 数 ≥2 与调用路径（注册中心订阅 vs 直连）
   d. 把选中的 Invoker 传给子类 doInvoke
4. FailoverClusterInvoker.doInvoke（默认）：
   - len = retries + 1（默认 3 次机会）
   - 每轮 select 都会拿到"排除已试者"的列表 → 换一家
   - 业务异常（BizException）直接抛出不重试；调用异常记录后继续
5. invokeWithContext → 传输层（协议编码、连接池、超时控制）
```

### How——订单 O 的完整决策栈（一张图）

```text
订单 O 到达调度台
   │
   ├─ [MockClusterInvoker]  有 mock 吗？→ 有且命中：直接回"今日已打烊"（降级）    L4
   │
   ├─ [AbstractClusterInvoker.invoke]
   │     ├─ directory.list()
   │     │     ├─ RegistryDirectory 本地候选：{A,B,C,D,E}（注册中心快照）         03/04
   │     │     └─ RouterChain.getSingleChain：灰度规则 → {A,B,C}（资格过滤）        L3
   │     ├─ 空集合检查：空 → "No provider available"（04 篇的 FAIL 路径）
   │     └─ select(loadbalance)
   │           ├─ sticky？→ 否（默认）
   │           ├─ LoadBalance.select：预热权重后随机 → 选中 A                      L2
   │           └─ availableCheck：A 可用 → 确认
   │
   ├─ [FailoverClusterInvoker.doInvoke]
   │     ├─ 第 1 轮：调 A → 超时异常 → invoked={A}                                L4
   │     ├─ 第 2 轮：select(排除 A) → 随机中 B → 调 B → 成功 → 返回
   │     └─ 若 B 也失败 → 第 3 轮 → C → 全败 → 抛最后异常（记录初始错误）
   │
   └─ 调用方拿到：成功结果 / 业务异常 / 最终失败（含 invoked 列表可观测）
```

**两个必须看懂的相互作用**（源码级）：

1. **超时 × 重试叠加**：每一轮重试都走独立的超时控制。`failover + retries=2 + 超时 1s` 的最坏等待 = **3 秒**——这不是 bug，是预算设计的问题（L6）。
2. **失败发生在"选择前"还是"选择后"**：`directory.list()` 为空（候选被清空）→ 在 select 之前就抛"没有可用店"；`select` 后调用失败 → 走 doInvoke 的重试循环。**看日志先分清是"列表问题"还是"调用问题"**——04 篇的"空地址清候选"和"死店打不通"是两条完全不同的排障路径。

### Transfer——迁移到其他设计问题


- **装饰器嵌套 = 分层责任**：每层只解决一个时点的决策，靠嵌套顺序表达"先后"——这是 RPC 框架、网关、中间件的通用组织方式（过滤器链、interceptor 链同构）。
- **模板方法（invoke → doInvoke）**：公共逻辑（取候选、选择、空检查）收在父类，策略（重试怎么循环）留给子类——`AbstractClusterInvoker` + 八种 XxxClusterInvoker 是"模板方法 + 策略"的标准组合。
- **可观测性的入口**：invoked 列表（试过哪几家）、sticky 命中、router 快照（RouterSnapshot）——**排障先定位"卡在哪一层"：Mock？list？select？重试？**


> 本层留下的新账：决策栈全部打通了，**但参数怎么定？** retries 设 2 还是 0？超时设多少？哪些接口开重试？灰度用标签还是条件路由？——需要一套把"预算"算清楚的决策方法。
>
> 🔴 **口诀**：**调用栈=责任栈：mock 降级 → 候选过滤 → 加权选择 → 排除重试；看日志先分"列表问题"与"调用问题"。**


<a id="level-8"></a>
## Level 6：生产决策——把超时、重试、幂等算成预算


### 👶 前置知识关卡


- [ ] L5 决策栈；L4 重试三本账。
- [ ] 04 篇：剔除窗口决定"打向死店的概率"（Nacos ~1.1s / ZK ~13s）。

### Why——为什么"参数调最大"是最危险的决策


**徒弟**：那我全链路上 retries=5、超时 10s，总能覆盖所有故障了吧？

**老陈**：你刚刚把三个最危险的事同时做了：**重试风暴**（全链路同时重试的放大倍数）、**超时叠加**（调用方最坏等 60 秒）、**依赖链失效**（上游的容错预算被你的参数吃掉）。生产决策不是"调最大"，是**把每一份代价算成预算，再分配**。

### What——预算算式与决策清单


**1. 重试预算（每层成立）**

```text
调用方最坏等待 = 单次超时 ×（重试次数 + 1）
例：超时 1s、retries=2 → 最坏 3s；下游 5 家时全链路放大 = 3 × N
```

**决策顺序**：先定单次超时（业务容忍度）→ 再定 retries（幂等性决定上限）→ 最后验证"最坏等待"是否突破上游预算。

**2. 幂等决定重试资格**

| 调用性质 | 可重试？ | 理由 |
|---|---|---|
| 读（查询） | ✅ | 重复执行无副作用 |
| 幂等写（带幂等键/版本号） | ✅ | 重复执行结果一致 |
| 非幂等写（下单、扣款、无幂等键） | ❌（或 retries=0） | 重复执行 = 资损 |
| 业务异常（库存不足、余额不够） | ❌（框架已不重试） | 重试无意义，换店也一样 |

**3. 灰度的路由选型**：标签路由（provider/consumer 打标）适合"比例渐进"；条件路由（按参数/地址）适合"隔离与黑白名单"；两者可叠加（链式）。**灰度必须配套"切回预案"**：规则热更回滚（Router 规则下发可逆）而不是发版回滚。

**4. 可观测性指标清单（E05 已按此采集基线）**

```text
RT 分位数（P50/P95/P99）与超时计数
重试率 = 重试发生次数 / 总调用次数（>0 说明剔除窗口或慢店存在）
invoked 列表（一次失败最终试过哪几家——排障入口）
active 数（leastactive 的输入；连接池压力）
mock 降级触发次数（链路存活的代价指标）
```

**5. E05 实验计划（已执行，2026-08-12，结果见 `experiment-005-loadbalance-cluster.md`）**

```text
E05-1  3 实例 provider + consumer：Random vs RoundRobin 的派单分布观察
       → 实测：Random 104/101/95、RoundRobin 101/100/99，均 300 OK / 0 FAIL
E05-2  kill -9 一个实例：failover 重试日志（invoked 列表）+ 失败窗口
       → 实测（3 轮）：2 轮 300/0，1 轮 299/1——唯一 FAIL 是 kill 瞬间在途请求
         （CANCELLED 异步冒出，failover 兜不住；kill 后新请求全部被兜住）
E05-3  retries=0 vs 2 的行为对比（失败次数、耗时、日志）
       → 实测：kill 场景两者均 300/0——抗 kill 的是连接层 invalidate（<1s）+ Nacos 剔除
         （~1.1s），不是 retries；retries 价值在"发起时失败"场景
E05-4  条件路由下发：consumer 候选集收缩 → 派单过滤生效
       → 受阻（纯 API config-center 级联未打通，源码定位到 ModuleEnvironment 委托链，
         标"待验证"，文章相关断言保持"机制层"标注）
```

**徒弟**：那到底有没有一个"标准配置"？

**老陈**：没有——但有一张不变的决策顺序表：**先答幂等（能不能重试）→ 再答超时（单次等多久）→ 再答重试次数（预算内最多几次）→ 再答路由（资格怎么筛）→ 最后用 E05 这类实验验证"最坏等待与放大倍数"没有突破预算**。参数是算出来的，不是抄出来的。

### Transfer——迁移到其他设计问题


- **预算思维是通用工程方法**：超时/重试/并发/队列深度——所有"容错参数"都该写成"最坏情况算式"，而不是拍脑袋。**"最坏等待 = 超时 × (重试+1)"在任何重试系统里都是第一条算式**。
- **幂等是重试的前提**：HTTP 幂等键、消息去重、数据库唯一约束——**先保幂等，再谈重试**，这条顺序在所有系统成立。
- **可观测性先于优化**：重试率、invoked 列表、mock 触发率——没有这些指标，"故障演练"就是盲演。


> 本篇闭环：**单门店死法 → 候选集 → 资格过滤 → 加权选择 → 失败兜底 → 决策栈走查 → 预算设计**。Router、LoadBalance、Cluster 不是三个开关，是一条决策栈上的三个时点；参数不是抄来的，是预算算出来的。
>
> 🔴 **口诀**：**先幂等、再超时、后重试；资格前置、选择加权、兜底算账；最坏等待 = 超时 ×（重试 + 1）。**

## 📚 版本勘误表


| ❌ 常见说法 | ✅ 更准确的说法 |
|---|---|
| "轮询就是数数" | 平滑加权轮询：当前权重累加、取最大、减总权重——任意前缀窗口配额公平（3.3.4）。 |
| "随机=绝对公平" | 随机=概率公平；小窗口内不保证均匀；权重与预热让它"按能力"分配。 |
| "重试 3 次" | retries=2（默认）= 最多打 3 家**不同**门店（排除已试者）。 |
| "挂了就重试" | 只有调用异常重试；业务异常（BizException）不重试（3.3.4 语义）。 |
| "一致性哈希=缓存亲和" | 是"参数→门店"绑定；门店增减只迁移环上一段（虚拟节点），无状态服务用它反而不随机。 |
| "灰度=改权重" | 灰度是 Router 的资格问题（标签/条件路由 + 规则热更），不是 LoadBalance 权重问题。 |

|---|---|---|
| LoadBalance | random / roundrobin / leastactive / consistenthash | 有状态会话 → 一致性哈希；要求配额公平 → 轮询；动态差异大 → leastactive；默认 → random。 |

## 🌍 跨语言 / 跨运行时视角


| Dubbo 视角 | 跨语言同构对象 | 不变的问题 |
|---|---|---|
| LoadBalance（random/轮询/哈希） | Nginx upstream 策略、gRPC 负载均衡、数据库连接池选连接 | 按能力不对称分配流量，每个算法换一个模型。 |
| 预热（warmup） | K8s 滚动发布 readiness、CDN 新节点预热 | 新成员按进度渐进接管流量。 |
| Router 链 + 规则热更 | Envoy 路由（xDS 动态下发）、网关路由表 | 资格过滤前置、策略可热更、执行与规则分离。 |
| failover（排除已试重试） | DNS 多 IP 重试、消息投递换 broker、HTTP 重试 | 失败换节点、业务异常不重试、预算=超时×(n+1)。 |
| mock 降级 | 网关兜底响应、静态降级页、消息跳过坏消息 | 用假结果换链路存活。 |
| sticky / 一致性哈希 | 会话亲和（session affinity）、缓存 key 分片 | 状态绑定 vs 随机分散的取舍。 |


### 跨语言后仍成立的 6 条判断力


1. **候选列表是容错原料**——没有候选集就没有"换一家"，单地址没有真正的 HA。
2. **资格（集合级）≠ 选择（单点级）**——过滤必须前置，选择永远作用在过滤后的集合上。
3. **算法没有免费午餐**——每个负载均衡策略都在换一个不对称模型；预热与权重是"能力不对称"的标准解法。
4. **重试三本账：风暴、幂等、叠加**——先答幂等再谈重试；重试打向"没试过的节点"。
5. **调用栈 = 责任栈**——每层一个决策时点；排障先定位层，再看参数。
6. **容错参数是预算不是直觉**——"最坏等待 = 超时 ×（重试+1）"是第一算式，可观测性先于优化。
