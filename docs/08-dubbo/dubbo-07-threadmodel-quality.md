# 🧭 07｜骑手与后厨：线程模型与质量保障总账（Provider 稳定性深井）

> **副标题：从"订单送到端口后谁接单"，到 IO 线程与业务线程池的分离、队列与拒绝、超时重试幂等的预算算式、熔断隔离的止损机制，最后收成一张稳定性预算表。**

---

> ## 写在最前面的承诺
>
> 这不是线程池参数大全，也不是"超时设大一点"的背参数文。
>
> 我们仍然只追踪订单 O。00 篇 Level 5 把 O 送进了后厨（`DubboServerHandler-` 线程池）；05 篇算清了改派（failover 重试）的账。本文回答 O 到后厨之后的问题：**谁接单、谁干活、排队爆了怎么办、后厨太慢或挂了怎么办**——把"线程模型"与"质量保障总账（超时/重试/幂等/熔断）"合成一条因果链，最终输出一张稳定性预算表。
>
> 全文唯一比喻仍是**一座外卖中央厨房**。骑手（Netty EventLoop）= 只送信不炒菜；出餐口（Dispatcher）= 决定谁接单；灶台（业务线程池）= 执行 Filter + 业务；排队等位（队列）= 尖峰缓冲；打烊拒客（拒绝/隔离）= 保护不被打垮；顾客等太久（超时）= 预算结束就放弃；重做一遍（重试）= 换店再试（幂等前提）；差评止损（熔断）= 暂停打向坏店。
>
> 本文机制层结论标注源码版本（Dubbo 3.3.4）；E00 实测线程命名与业务线程执行，E07 已实测 triple 线程池默认参数、饱和拒绝行为、`dispatcher` 参数边界与 QoS。熔断仍未做专项实测，因此相关内容继续标注为"待验证"；不允许任何编造 benchmark。

## 🏭 全文唯一比喻地图

```text
骑手把订单 O 送到后厨门口（请求到达 Provider 端口）
   │
   ▼
出餐口（Dispatcher / transport executor）── 谁接单？把 O 交给灶台执行器
   │
   ▼
┌─ 后厨（Provider 侧执行资源）──────────────────────┐
│ 灶台（业务线程池 DubboServerHandler-*）：切菜→炒菜 │
│   ├─ 排队等位（线程池队列）：尖峰缓冲              │
│   ├─ 打烊拒客（拒绝策略/信号量）：保护不被打垮      │
│   └─ 灶台爆满 → 排队的单子越积越多（内存账）       │
└───────────────────────────────────────────────────┘
   │ 出餐慢/出不了餐，顾客侧的反应：
   ├─ 顾客等太久（超时）：预算结束就放弃
   ├─ 重做一遍（重试）：换一家店再试（幂等前提）
   └─ 差评止损（熔断/隔离）：暂停打向这家店
```

| 比喻元素 | Dubbo 技术对象 | 它负责的唯一一件事 |
| ---- | ---- | ---- |
| 骑手 | Netty EventLoop（IO 线程） | 收信/送信/连接复用，**不炒菜** |
| 出餐口 | Dispatcher（旧 Dubbo 协议）/ transport executor（triple） | 决定"谁接单"；triple 3.3.4 不读取 `dispatcher` 参数 |
| 灶台 | 业务线程池（E00 实测命名 `DubboServerHandler-<host>:<port>-thread-N`） | 执行 Filter 链 + 业务方法 |
| 排队等位 | 线程池队列（ThreadPoolExecutor 队列） | 瞬间尖峰的缓冲 |
| 打烊拒客 | 拒绝策略 / 信号量隔离（executes 等） | 过载时的自我保护 |
| 顾客等太久 | timeout（consumer 侧超时，官方文档默认 1000ms 口径） | 预算结束就放弃，把等待变有界 |
| 重做一遍 | failover retries（重试换未试过的店） | 换店再试；**幂等是前提**（05 篇） |
| 差评止损 | 熔断：closed/open/half-open 三态 | 暂停打向半死不活的店，半开试探恢复 |

> 📌 比喻边界：**骑手不是"一次请求一个线程"**——高并发恰恰依赖少量 EventLoop 复用连接；**队列不是容量扩容**——它是尖峰缓冲，队列无限就是内存账；旧 Dubbo 协议的 Dispatcher 选项不能直接套到 triple 3.3.4，`dispatcher=direct` 在 E07 中实测无效；**"快速失败"（failfast）不是熔断**——熔断要把"暂停打进坏店"做成状态机（半开试探），Dubbo 内核是否内置该状态机**待验证**（生产多用 Sentinel 等外部治理组件，06 篇治理体系）。

## Level 1：为什么必须两类线程——BIO 与单事件循环各自的死法

### 👶 前置知识关卡

- [ ] 00 篇 Level 5：请求由 IO 线程接收，业务在 `DubboServerHandler-` 线程池执行（E00 实测）。
- [ ] 01 篇：Netty 是连接复用的事件循环模型（骑手不是一次请求一个线程）。

### 1.1 徒弟的直觉

徒弟：

> 服务端不就是"来一个请求，开一个线程处理"吗？BIO 不是照样能跑？

老陈：

> 能跑，但账在规模上。**BIO：每连接一线程**——1 万个连接就是 1 万个线程：每线程默认栈 1MB（JVM 默认值，待核验平台）、上下文切换爆炸、CPU 全花在换台上。所以 NIO 事件循环来了：**少量线程处理海量连接**。

### 1.2 NIO 的天真用法是怎么死的

```text
方案 A（BIO）：每请求一线程
  ┌ 账①：线程数 = 连接数 → 1 万连接 = 1 万线程（栈内存 + 上下文切换）
  └ 账②：线程创建/销毁成本进请求路径 → 高并发下吞吐暴跌

方案 B（NIO 天真版）：事件循环里直接跑业务
  ┌ 账①：一个慢业务（睡 5 秒 / 阻塞 IO）卡住事件循环
  ├ 账②：该事件循环上的所有连接一起等 → 一个慢服务拖垮整条链路
  └ 账③：事件循环忙等不能做任何收发 → 表现为"连接建立成功但请求无人响应"
```

### 1.3 两类线程分离 = 唯一解

```text
IO 线程（EventLoop）：只管 收发字节 / 解析报文 / 编解码 —— 永不执行业务
   ↓ 解出的 Invocation 交给
业务线程池：执行 Filter 链 + 业务方法 —— 阻塞、慢、重都发生在这里
   ↓ 结果回写由 IO 线程完成
```

分离之后：**慢业务只占用业务线程池的一个线程，事件循环依然能收发其他连接**。这是 Netty、Tomcat、gRPC 通用的架构——不是性能优化，是"隔离脏活"的结构性设计。

> 本层留下的新账：两类线程分离了，但**分离的边界在哪**——分发模式、线程池形态、默认参数，得看 3.3.4 实机是什么样。E00 给了线程名，下一层走查。

### Transfer——迁移到其他设计问题

- **"收信与干活分离"是高并发服务器的通用架构**：Netty、Tomcat、gRPC、Node（事件循环 + worker）都在回答同一问题——谁收发、谁干活、谁阻塞。
- **BIO→NIO 的演进是"连接与线程解耦"**：数据库连接池、HTTP/2 多路复用、K8s 调度器都是同一思想的变体：**稀有的执行资源不能被空闲连接绑死**。

> 🔴 **口诀**：IO 线程收信、业务线程干活；慢业务只配占一个线程。

## Level 2：线程模型实机走查——E00 线程名与 3.3.4 分发语义

### 👶 前置知识关卡

- [ ] 01 篇：Netty EventLoop 与 Channel 的关系（一条连接绑定一个 EventLoop）。
- [ ] 00 篇 Level 5：Filter 与业务方法在同一线程执行（E00）。

### 2.1 E00 实测：两颗铁证

```text
[PROVIDER TraceFilter] enter, thread=DubboServerHandler-198.xx.x.x:50051-thread-2
[PROVIDER Business]   greet() executing, thread=DubboServerHandler-198.xx.x.x:50051-thread-2
[PROVIDER TraceFilter] exit, ... result=Hello O ...
```

两个事实（E00 原样引用的输出）：

1. **业务线程命名 `DubboServerHandler-<host>:<port>-thread-N`**——Provider 端业务跑在专用的业务线程池（3.3.4 命名规则，Implementation），不跑在 Netty 线程；
2. **Filter 链与业务方法在同一线程**——Filter 不是独立线程，它在业务线程上顺序执行。所以"Filter 里做耗时操作"＝直接占用业务线程。

### 2.2 Provider 线程模型全景图：从网络请求到业务返回

先把一次 Provider 请求画完整。图中的 Boss/Worker 只表示 Netty 传输层的职责分工，不代表所有协议都使用相同线程数量，也不在这里推导 `iothreads` 默认值。

```text
                    [Consumer 网络请求]
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│ Netty Server IO / EventLoop                                  │
│                                                             │
│ Boss role：accept；Worker role：read / write / HTTP2 解码      │
│ 只负责传输层工作，不执行 Provider 用户业务方法               │
└──────────────────────────────┬──────────────────────────────┘
                               │ 解码出请求
                               ▼
┌─────────────────────────────────────────────────────────────┐
│ Triple Server Transport Listener                             │
│                                                             │
│ 通过 ExecutorRepository 获取 Provider 执行器                  │
│ （3.3.4：AbstractServerTransportListener + SerializingExecutor）│
└──────────────────────────────┬──────────────────────────────┘
                               │
                               ▼
┌─────────────────────────────────────────────────────────────┐
│ Provider 业务线程池                                          │
│                                                             │
│ DubboServerHandler-<host>:<port>-thread-N                    │
│ limited：max=200，core=0，queues=0（SynchronousQueue）        │
│                                                             │
│ Filter 链 ──→ GreetingService.greet() / 用户业务代码          │
└──────────────────────────────┬──────────────────────────────┘
                               │ 返回 Result / RpcResult
                               ▼
┌─────────────────────────────────────────────────────────────┐
│ Triple / Netty transport response path                       │
│                                                             │
│ 结果处理、编码并写回 Consumer；具体回写线程不作全协议泛化      │
└──────────────────────────────┬──────────────────────────────┘
                               │
                               ▼
                    [Consumer 收到响应]
```

这张图表达的是"IO 与业务执行分离"的结构不变量：网络线程不能被慢 SQL、远程 HTTP 调用或用户代码占住；用户业务应在 Provider 执行器中运行。E00 实测的 `DubboServerHandler-...-thread-N` 与 E07 的 3.3.4 源码/线程池证据，把图中的业务线程池从概念变成了实现证据。

但不能把图中的"切一刀"简单归因给所有版本的 `Dispatcher`：在 triple 3.3.4 中，业务执行器由 transport listener 固定接入；旧 Dubbo 协议的 Dispatcher SPI 是另一条实现路径。

### 2.3 Dispatcher 的协议边界

在旧 Dubbo 协议的 Dispatcher 抽象中，常见语义可以这样理解（Specification / legacy implementation，不能直接套到 triple）：

```text
all        ：请求与响应都交给业务执行器
execution  ：请求交给业务执行器，响应走传输线程路径
message    ：消息级别参与业务执行器分发
direct     ：在当前 IO 线程执行，放弃业务线程隔离
```

这些选项体现的是"隔离程度 × 调度开销"的旋钮；`direct` 如果在某个协议实现中有效，确实会重新暴露 L1 中"慢业务卡住 IO 线程"的风险。

**但对 Apache Dubbo 3.3.4 triple：**

1. E07 已确认 `dispatcher=direct` 出现在导出 URL 中，但业务仍运行在 `DubboServerHandler` 线程；
2. 反编译 `AbstractServerTransportListener.getExecutor()` 可见其通过 `ExecutorRepository` 获取业务执行器；
3. 扫描 `dubbo-rpc-triple-3.3.4.jar` 与 `dubbo-remoting-http12-3.3.4.jar` 未发现读取 `dispatcher` 参数的路径。

因此，**`dispatcher=direct` 不是 triple 3.3.4 的有效调优开关**。排查 triple 线程模型时，先看实际 transport 和 executor，不要只看导出 URL 上是否出现了 `dispatcher`。

### 2.4 线程池形态：3.3.4 triple 实测参数

E07 通过源码锚点和运行时线程清单确认了当前基线：

```text
threadpool = limited
threads    = 200       // 最大线程数，不等于固定 core 数
corethreads= 0         // 按请求惰性创建
queues     = 0         // LimitedThreadPool 使用 SynchronousQueue，无缓冲排队
alive       = 60000ms  // 空闲线程回收时间
拒绝策略   = AbortPolicyWithReport
```

所以不能把 3.3.4 triple 的默认线程池写成"fixed 200 + 队列等待"。更准确的因果链是：业务线程最多扩到 200；`queues=0` 不提供缓冲；第 201 个同时到达且无法立即获得线程的任务进入拒绝路径。

### 2.5 Consumer 端：同步模式没有"响应线程"

E00 实测（00 篇 5.3）：同步模式下，调用线程就是发起调用的线程（E00 里是 `main`），响应由该线程取回——**线程 dump 里找不到"响应线程"是正常现象**。异步（回调/Future）才引入额外线程语义（08 篇展开异步调用模型）。

> 本层留下的新账：线程与分发定了，但**尖峰超过处理能力时**——队列怎么缓冲、缓冲不下怎么办？下一层：队列与拒绝。

### Transfer——迁移到其他设计问题

- **分发模式的"隔离 × 性能"旋钮到处存在**：Tomcat 的 `executor` vs 直接处理、gRPC 的 `executor` 参数、消息消费者线程模型——都是同一个旋钮的不同刻度。
- **线程命名是可观测性的第一件小事**：线程名里带 host/port/用途，故障时线程 dump 一眼定位（E00 线程名就是范例）。

> 🔴 **口诀**：业务线程名里藏着机房坐标；同步调用没有响应线程，调用线程就是它。

## Level 3：队列与拒绝——后厨压垮前的防线

### 👶 前置知识关卡

- [ ] L2：业务线程池的形态（3.3.4 triple 默认是 limited）。
- [ ] Java 基础：`ThreadPoolExecutor` 的 核心线程 → 队列 → 最大线程 → 拒绝策略 四段式。

### 3.1 线程池的"三段缓冲"（Java 语义，通用机制）

```text
任务到达
   → 核心线程未满？直接执行
   → 队列未满？排队等位（尖峰缓冲）
   → 最大线程未满？创建临时线程（若策略如此）
   → 都满了？拒绝策略兜底
```

Dubbo 的业务线程池也是标准 `ThreadPoolExecutor` 家族（E07 已确认 3.3.4 triple 使用 limited 线程池）——所以**队列的账就是 Java 线程池的账**。

### 3.2 队列的三笔账

| 账 | 后果 | 谁买单 |
| ---- | ---- | ---- |
| 队列无限（无界队列） | 任务堆积 = 内存账：请求等不到超时/内存先爆（任务对象本身占内存） | 内存与 GC |
| 队列很大（有界但大） | 尖峰缓冲有余，但等待时间被拉长 → 上游超时先于队列消化触发 | 调用方等待预算 |
| 队列很小 / 无队列 | 尖峰直接触发拒绝 → 拒绝风暴 | 调用方错误率 |

> 核心认知：**队列是"用等待换吞吐"的尖峰缓冲，不是容量扩容**。队列大小和超时预算必须联动：队列能等的时长 ≤ 上游愿意等的时长。3.3.4 triple 默认 `queues=0` 时甚至没有这段等待，超额任务直接进入拒绝路径。

### 3.3 拒绝策略：最后一道防线（Java 语义 + Dubbo 落地）

- Provider 拒绝时抛 `RejectedExecutionException`；对 Consumer 的最终异常语义取决于协议。E07 的 triple 3.3.4 实测是 `CANCELLED : Canceled by remote peer`，不能把 Provider 侧拒绝异常原样映射到 Consumer 侧；
- 信号量方案（限制同时执行数/排队数，先到先拒）＝ **"打烊拒客"**：宁可当场拒绝也不让请求在队列里腐烂（官方文档有 executes/accepts 类限制口径，3.3.4 默认待核验）。

### 3.4 E07 饱和实测：线程池满不等于请求排队

实验条件：Provider 业务方法固定耗时 3000ms，同时发起 250 个请求，使用 triple 3.3.4 默认线程池配置。

```text
Consumer：ok=200 fail=50 total=250 elapsedMs=3183

Provider：
Thread pool is EXHAUSTED!
Pool Size: 200 (active: 200, core: 200, max: 200)
java.util.concurrent.RejectedExecutionException

Consumer 失败语义：
StatusRpcException: CANCELLED : Canceled by remote peer, errorCode=500
```

这条证据把线程模型图和线上现象接起来：

```text
250 个请求到达
       ↓
200 个业务线程被 3000ms 业务占满
       ↓
queues=0 → SynchronousQueue 无缓冲排队
       ↓
超额任务进入 AbortPolicyWithReport
       ↓
Provider 记录 EXHAUSTED / RejectedExecutionException
       ↓
triple 将失败呈现为 Consumer 侧 CANCELLED
```

### 3.4.1 线上故障读图

| 现象 | 第一证据 | 初步判断 |
|---|---|---|
| Provider 日志出现 `Thread pool is EXHAUSTED` | `active=200`、`max=200`、`RejectedExecutionException` | 业务线程池饱和，先查慢业务、并发量和线程池配置 |
| Consumer 收到 triple `CANCELLED` | 同时间窗口 Provider 是否有 `EXHAUSTED` | 不能只按网络故障判断，可能是 Provider 拒绝执行 |
| Consumer 超时但 Provider 没有拒绝 | 线程池活跃度、队列深度、业务 RT | 重点查业务执行慢或排队等待；超时是上游预算耗尽，不等于线程池拒绝 |
| 业务线程长期接近上限 | `DubboServerHandler-*` 线程 dump 与业务栈 | 查阻塞 IO、慢 SQL、下游调用和 Filter 中的耗时逻辑 |

因此线上排查不能只看 Consumer 的异常类型，至少要把三个时间轴对齐：Consumer 超时/取消时间、Provider 线程池状态、业务方法进入/完成时间。

### 3.5 舱壁隔离：灶台分灶

同一 Provider 上多个服务的隔离方式（机制层，Dubbo 是否按接口分线程池待核验）：

```text
一个后厨（一台 Provider）可以分多个灶：
  ├─ 接口 A 的队列爆了 → 只影响 A 的灶台
  └─ 不该让 A 的尖峰把整家店的灶台都占满
```

这是**舱壁（Bulkhead）思想**：线程池/队列按服务或分组隔离，爆一个不影响全部（跨语言视角里与 Hystrix 线程池隔离、K8s pod 隔离同构）。

> 本层留下的新账：排队和拒客是后厨侧的防线；**顾客侧**呢？等多久放弃、放弃后怎么办？下一层：超时与重试总账。

### Transfer——迁移到其他设计问题

- **"用等待换吞吐"是过载工程的通用选择**：队列、背压（backpressure）、限流排队——都是把瞬时尖峰摊平；代价是延迟，所以必须与超时预算联动。
- **舱壁是隔离思想的通用形态**：线程池分灶 / 进程分 pod / 流量分泳道——隔离粒度 × 资源利用率的取舍处处相同。

> 🔴 **口诀**：队列是尖峰缓冲不是扩容；能等的时长 ≤ 上游愿意等的时长；爆不了就拒，别让任务烂在队里。

## Level 4：超时与重试总账——最坏等待 = 超时 ×（重试+1）

### 👶 前置知识关卡

- [ ] 05 篇：failover 重试排除已试店、retries 默认 2（3.3.4 源码实证）、业务异常不重试；
- [ ] 05 篇 E05：kill 实例后重试边界实测（在途请求 CANCELLED 兜不住）。

### 4.1 超时是预算，不是参数

官方文档口径：timeout 默认 1000ms（Specification/官方文档；3.3.4 常量未本机核验，标待实测）。但**默认值不解决设计问题**——超时的本质是"本次调用愿意等多久"的预算声明：

```text
预算链（谁定谁的预算）：
  上游业务容忍度 ──► Consumer timeout（一次等方法多久）
                        ├─► Provider 业务执行 + 队列等待 ≤ 这个预算
                        └─► 重试时：最坏等待 = timeout × (retries+1)
```

### 4.2 重试三本账（接 05 篇，E05 实测边界）

```text
账① 重试风暴：全网同时重试 → 流量放大 → 把下游彻底打垮
账② 幂等前提：非幂等写重试 = 重复扣款/重复下单
账③ 超时叠加：最坏等待 = timeout × (retries+1)（数学推导，05 篇已立）
边界（E05 实测）：kill 实例后，retries 对比无差异、在途请求 CANCELLED 兜不住——
  重试不是万能的，它只对"换一家店能成"的故障有效
```

### 4.3 什么异常值得重试（3.3.4 语义，05 篇实证）

```text
值得重试：调用类异常（连接失败、超时、网络错）→ 换店可能成功
绝不重试：业务异常（BizException，库存不足去 B 店也一样）→ 框架已不重试，别手动再包一层
```

> 说人话：**超时和重试是一张预算表的两行**——超时定义"等多久放弃"，重试定义"放弃后还打几次"，乘积就是调用方的最坏等待；这张表的第一行永远先写"幂等性"。

### 4.4 最坏等待的推导演示（计算规则，非实测）

```text
timeout = 500ms，retries = 2（默认，3.3.4 实证）
  → 一次调用最多打 3 家不同的店（排除已试者，05 篇）
  → 最坏等待 = 500 × 3 = 1.5s
上游容忍度只有 1s？→ timeout 必须降到 333ms 以下，或 retries 降到 1
这就是"预算算式"：先定容忍度，再反推参数，不允许拍脑袋
```

> 本层留下的新账：等太久可以放弃、换店可以再试，但**如果这家店"半死不活"**——每次试探都失败、重试只加重负担，怎么办？"差评止损"（熔断）就是干这个的。下一层。

### Transfer——迁移到其他设计问题

- **"最坏等待 = 超时 ×（重试+1）"是第一算式**：HTTP 重试、消息投递重试、数据库连接重试都受它约束；先定容忍度再反推参数。
- **"业务异常不重试"是错误分类学**：任何重试设计第一步都是给失败分类（调用类 vs 业务类），分类错了重试就放大伤害。

> 🔴 **口诀**：先幂等、再超时、后重试；最坏等待 = 超时 ×（重试+1）；业务异常不重试。

## Level 5：熔断与隔离——半开试探与舱壁

### 👶 前置知识关卡

- [ ] 06 篇：治理体系的边界（限流/降级/熔断在 Dubbo 里多为 Filter/外部组件形态）。
- [ ] L3：舱壁隔离（分灶）思想。

### 5.1 快速失败 ≠ 熔断（先祛魅）

```text
failfast（05 篇）：这次调用立刻失败 → "立刻放弃"是单次决策
熔断：一台店连续差评 → "暂停派单给这家店"是状态转变（多数派单都不再打它）
```

Dubbo 的 failfast/failsafe 是**单次调用的失败策略**；熔断是**一段时间窗口内的流量决策状态机**——两者不是一个层级的东西。

### 5.2 熔断三态（通用机制，Dubbo 内核是否内置待验证）

```text
closed（关闭）：正常派单，统计错误率
   └─ 错误率 > 阈值 / 连续失败达窗口 → open
open（打开）：暂停派单给这家店（快速失败返回）→ 睡一个冷却窗口
   └─ 冷却结束 → half-open
half-open（半开）：放少量试探请求
   ├─ 试探成功（达标）→ closed（恢复派单）
   └─ 试探失败 → 回 open（再冷却）
```

### 5.3 在 Dubbo 生态里的落位（诚实标注）

- **内核口径待验证**：3.3.4 是否内置"半开状态机"熔断器，本系列未核验——**不要假设开箱即用**；
- **生产常规路径**：熔断/限流/降级由治理组件承担（Sentinel 适配 Dubbo 是社区标准做法，机制层；06 篇治理体系已讲规则热更与降级）；Dubbo 侧把失败语义（failfast/failsafe）与重试边界（E05）做干净。
- **信号量隔离**（L3.3）与 **分灶线程池**（L3.5）是 Dubbo 侧可落地的隔离手段；熔断是跨调用者的流量决策，天然适合放在治理面而不是每个 Provider 内部。

> 说人话：**止损的完整链条 = Provider 侧隔离（队列/信号量/分灶）＋ Consumer 侧预算（超时/重试）＋ 治理面熔断（半开试探）**。三家各管一段，别指望一个开关管全部。

> 本层留下的新账：机制全部到齐——**线程怎么配、队列多大、超时多少、重试几次**，得收成一张能评审的预算表。下一层：决策。

### Transfer——迁移到其他设计问题

- **熔断三态是"止损 + 灰度恢复"的通用状态机**：数据库连接池的半开重连、CDN 节点摘除恢复、K8s 探针的连续成功判定——都是同一模型。
- **故障定位的第一问是"谁该止损"**：Provider 隔离自己做，Consumer 预算自己定，跨调用者止损归治理面——责任边界清晰，止损才有效。

> 🔴 **口诀**：快速失败是单次决策，熔断是状态转变；半开试探是恢复的唯一通道。

## Level 6：决策——把线程、队列、超时写成一张预算表

### 👶 前置知识关卡

- [ ] L4：最坏等待算式。
- [ ] 05 篇：重试风暴与幂等账。

### 6.1 从 Little's Law 出发（计算规则，非实测）

```text
并发需求 L = QPS × RT（Little's Law：系统内平均在途量 = 到达率 × 平均处理时间）
例：QPS=1000，p99 RT=100ms → 在途 ≈ 1000 × 0.1 = 100 个并发需求
   → 线程池太小（<100）：线程排满，队列入场，等待变长
   → 线程池太大：线程idle占资源，Little's Law 决定你多配也吃不下更多吞吐
结论：线程数是按"在途并发"配的，不是按"QPS"拍脑袋配的
```

### 6.2 稳定性预算表（决策模板）

| 预算项 | 由谁定 | 算式/依据 | 反推什么 |
| ---- | ---- | ---- | ---- |
| 幂等性 | 业务 | 写操作必须幂等或 failfast | 能否开重试的前置条件 |
| 上游容忍度 | 业务/上游 | 接口 SLA 允许的最长等待 | timeout |
| timeout | Consumer | 容忍度 ÷（retries+1）向上取整 | 反推 retries |
| retries | Consumer | 幂等上限内、容忍度允许 | 最坏等待上界 |
| 并发需求 L | 压测 | QPS × RT（Little's Law） | 线程数下界 |
| 线程数 | Provider | ≥ L，按 RT 分布留余量 | 队列需要吸收的尖峰 |
| 队列 | Provider | 尖峰幅度 × 允许排队时长 | 拒绝策略触发点 |
| 熔断/隔离 | 治理面 | 错误率阈值 + 冷却窗口 | 止损半径 |

### 6.3 上线评审清单（本文收口）

1. 每个开重试的接口写"幂等键或 failfast"的声明（05 篇账）；
2. 最坏等待 = timeout × (retries+1) ≤ 上游容忍度（数学核对）；
3. 线程数 ≥ 压测得到的在途并发 L，队列能等时长 ≤ 上游容忍度；
4. 监控线程池活跃度、队列深度、超时率、重试率（E00 TraceFilter 可作逐站打印模板）；
5. 熔断/限流方案写清楚由谁承担（治理组件 or Provider 侧隔离）。

> 说人话：**稳定性不是"调到最大"，是把每项资源写成预算**——每一项都有算式、有反推、有监控，评审时逐行过。

> 本层留下的新账：预算表能在线上开着，但**关门（优雅停机）与回访（可观测/验收）**还没讲——08 篇接上。

### Transfer——迁移到其他设计问题

- **预算表思维适用于一切资源型系统**：数据库连接池、线程池、HTTP 客户端连接数、缓存容量——都是"需求算式 → 资源下界 → 上界约束 → 监控项"四件套。
- **"参数是预算不是直觉"是工程纪律**：把每个旋钮翻译成算式与监控，评审就有了可反驳的对象；05 篇的重试预算与本文线程预算同一方法论。

> 🔴 **口诀**：线程数按在途并发配，队列按尖峰配，超时按容忍度配；预算表逐行评审再上线。

## 📝 合书自测

| 自测题 | 必须答出的不变量 |

| 为什么必须两类线程？ | BIO 线程数=连接数；NIO 天真版一个慢业务卡死事件循环上所有连接；分离之后慢业务只占一个业务线程。 |

| 同步模式有"响应线程"吗？ | 没有：调用线程就是等待线程（E00 里是 main）。 |
| 队列是干什么的？ | 尖峰缓冲不是容量扩容；队列无限 = 内存账；能等的时长 ≤ 上游容忍度。 |
| 最坏等待怎么算？ | timeout × (retries+1)；先定容忍度再反推参数。 |
| 什么异常值得重试？ | 只重试调用类异常；业务异常（BizException）不重试（3.3.4 语义）。 |
| 快速失败和熔断区别？ | failfast 是单次决策；熔断是状态机（closed/open/half-open），半开试探恢复；Dubbo 内核是否内置待验证。 |
| 线程数怎么定？ | Little's Law：并发需求 L = QPS × RT，线程数 ≥ L；不按 QPS 拍脑袋。 |
| triple 3.3.4 默认线程池是什么？ | `limited`，max=200、core=0、queues=0（`SynchronousQueue`）；超额请求走拒绝，不是默认排队。 |
| `dispatcher=direct` 能让 triple 业务跑到 IO 线程吗？ | 不能：E07 实测该参数在 triple 3.3.4 中无效，业务仍运行在 `DubboServerHandler-*`。 |

## 🎯 生产决策卡

| 决策 | 选项 | 选型判据 |
|---|---|---|
| 线程池形态 | fixed / cached / limited / eager | 3.3.4 triple 默认 `limited`；其他策略按负载和排队预算选择，不能把旧协议默认值套到 triple。 |
| 线程数 | 按在途并发 L = QPS × RT | 压测得到 L 后配 ≥ L，RT 分位留余量；不按 QPS 拍脑袋。 |
| 队列 | 有界，容量随容忍度 | 能等待时长 ≤ 上游容忍度；拒绝策略兜底（信号量优先于无限堆积）。 |
| Dispatcher | 先确认协议实现 | triple 3.3.4 不读取 `dispatcher`；不要用 `direct` 参数假设业务已离开业务线程池。 |
| 超时 | timeout 反推 | 容忍度 ÷ (retries+1)；逐层递减给预算，不做"全链路最大"。 |
| 重试 | retries / failfast | 幂等写可重试；非幂等写 failfast；业务异常一律不重试。 |
| 熔断 | 治理组件 + Provider 隔离 | 半开熔断器交给 Sentinel 等治理面（06 篇体系）；Dubbo 侧做好队列/信号量/分灶隔离。 |

## 🌍 跨语言 / 跨运行时视角

| Dubbo 视角 | 跨语言同构对象 | 不变的问题 |
|---|---|---|
| IO/业务线程分离 | Netty/Tomcat/gRPC executor、Node 事件循环 + worker | 谁收发、谁干活、谁阻塞 |
| ThreadPool 策略（fixed/cached/…） | Go goroutine 池、Python 线程池、侧车进程 | 并发资源如何供给 |
| 队列 + 拒绝 | 消息队列背压、TCP 流控、限流排队 | 过载时的缓冲与拒绝语义 |
| 超时预算 | HTTP 客户端超时链、数据库连接池超时、gRPC deadline | 最坏等待有界 |
| 重试三本账 | 消息投递重试、HTTP 重试、DNS 多 IP 重试 | 幂等前提 + 预算算式 |
| 熔断三态 | Hystrix、Sentinel、Envoy outlier detection | 止损 + 半开灰度恢复 |
| 舱壁隔离 | Hystrix 线程池隔离、K8s pod 资源隔离、泳道流量隔离 | 隔离粒度 × 资源利用率 |

### 跨语言后仍成立的 6 条判断力

1. **收信与干活必须分离**——任何高并发服务器把业务放进 IO 线程，都是埋雷。
2. **队列是缓冲不是扩容**——无界排队 = 内存账与等待账，背压/拒绝必须存在且可见。
3. **最坏等待 = 超时 ×（重试+1）是第一算式**——先定容忍度再反推参数。
4. **重试前先答幂等**——幂等写重试、非幂等 failfast、业务异常永不重试。
5. **快速失败不是熔断**——熔断是有半开试探的状态机；止损要分保半径（Provider 隔离 / Consumer 预算 / 治理面熔断）。
6. **参数是预算不是直觉**——每个旋钮都要能翻译成算式与监控，预算表可评审。

>
> **O 到后厨之后：IO 线程（骑手）只收信，业务线程池（灶台，`DubboServerHandler-` 实测）干活——慢业务只占一个线程；队列是尖峰缓冲不是扩容，能等的时长 ≤ 上游容忍度，满了就拒（3.3.4 triple 默认 `queues=0` 无缓冲直接拒绝，要缓冲需显式配 queues；生产可用信号量做先到先拒）；超时与重试是一张预算表的两行：先幂等、再超时、后重试，最坏等待 = timeout ×（retries+1），业务异常不重试（E05 边界）；快速失败不是熔断，熔断是 closed/open/half-open 状态机（Dubbo 内核是否内置待验证，生产走治理组件）；线程数按 Little's Law（L = QPS × RT）配，稳定性=把每项资源写成预算表。**
