# 正文:五个 Level 打穿调优

## Level 1:指标先于调优——凭什么说慢

<a id="level-1"></a>

### 认知墙

> **"先调优,再想指标"**

徒弟:"业务说搜索变慢了,我先把 refresh_interval 调大、把堆加一加,不行吗?"

老陈:"你先回答我三个问题:慢了多少?哪个接口慢?变慢之前正常是多少?三个问题一个都答不上来,你调的就是猜。"

### Why:没有指标,调优为什么是猜

业务报障说"变慢了"——但"慢"这个字没有单位:

- 是 p99 从 200ms 变 2s,还是偶尔超时 10s?
- 是搜索慢,还是写入慢,还是 429 导致的客户端重试让整体变慢?
- 基线是多少?没有基线,你怎么知道调完是变好还是变坏?

旧方案失败:直接改参数,然后"感觉好像快了"。因为没有基线,同一份压测对比缺失,改了两个变量却无法归因——这是所有调优翻车的起点。实验 002 的正确之处不在于数字,而在于**对照组设计**:同一台机器、同一份 bulk 文件、只改 refresh_interval 一个变量,才能得出"891ms → 364ms"的因果结论。

### What:三层指标体系——核心五类,缺一不可

```text
业务层(用户能感知的):
  latency 分位(p50/p95/p99,不看平均值:均值被长尾掩盖)
  throughput(每秒查询/写入)
  error rate(429/409/5xx,来自 _nodes/thread_pool 与日志)

集群层(集群在告警什么):
  cluster health(green/yellow/red;yellow = 副本缺失,02 篇)
  磁盘水位(watermark,官方默认值;满了会 read-only,神话 3 的收网)
  429 计数(write/search 线程池拒绝,实验 010)

节点层(哪台机器在扛):
  GC(停顿次数/时长;官方建议监控,本系列无 GC 实验,数字"待验证")
  CPU/IO(协调者 CPU vs 分片 CPU,merge 期间的 IO 抖动,实验 003)
  段数/merge 统计(段太多 = merge 压力,01 篇机制)
```

关键不变量:**先有基线,再有一个变量的变更,最后用同一指标复测**。一次只改一个变量,否则无法归因。

### 师徒对话

徒弟:"那我先看 dashboard 的总延迟就行了吧?"

老陈:"总延迟是果不是因。429 会让客户端重试,重试会叠加延迟——总延迟高,但病根在 write 线程池。所以顺序是:业务指标定位'哪个接口',线程池/queue 指标定位'哪一层',GC/磁盘指标定位'哪台机器'。三层对上,才敢动手。"

### 留下的新账

指标齐了,报表说"慢"。但慢在**谁**身上?——Level 2 回答瓶颈分层。

## Level 2:瓶颈分层——慢在谁身上

<a id="level-2"></a>

### 认知墙

> **"慢就是查询慢"**

徒弟:"业务说搜索慢,那肯定就是查询慢啊。"

老陈:"搜索慢,可能是分片在慢慢查询,也可能是协调者在慢慢归并,也可能是所有线程都堵在 write 线程池,连查询线程也被饿死。你连层都没分,谈什么优化。"

### Why:为什么必须分层

一次搜索请求在集群里经过的每一段都有独立的机制与瓶颈:

```text
客户端
  ↓
协调节点:REST 解析 → 转发各分片 → 归并排序(from+size 候选集,实验 008)
  ↓
分片节点:search 线程池 → Lucene 查询(倒排/过滤) → 返回 docID+分数
  ↓
协调节点:fetch 阶段按 docID 回源取 _source
```

- 写路径(实验 010 实测):write 线程池 threads=核数(容器 4 vCPU 实测 size=4)、queue_size 默认 10000;实验 010 用 yml 把 queue_size 定制为 16 以便快速触达饱和,小 bulk × 高并发时 **queue 钉 16**、rejected 累计 ~24k-26k/节点,整批返回 429 `es_rejected_execution_exception`(默认 10000 下同机制,只是更难打满);而大 bulk(1.5MB)场景 **协调者解析成为更早瓶颈**,queue 峰值只有 7、rejected=0。
- 查路径:search 线程池固定 size=7、queue_size=1000(实测);慢查询会占住搜索线程,queue 排队最终 429(机制同写路径,实验 010 follow-up 标注"待验证"的具体数字)。
- 深分页(实验 008):from+size 越深,每分片收集 from+size 候选、协调者归并——归并候选量级 ≈ **实际查询分片数** × (from+size)(机制推导);150k 小数据热缓存下延迟差异不明显(实测 ~15-50ms),生产大索引必须实测。
- IO 层:merge 在后台吃 IO(实验 003:墓碑与段合并),磁盘满触发 watermark 只读。

### What:分层诊断的顺序

```text
① 429 出现在哪个线程池?
   write 429 → 写入过载(实验 010)
   search 429 → 查询过载(慢查询占满搜索线程)
② queue 深度:排队是"来的多"还是"干得慢"?
   queue 一直有积压 = 干得慢(分片 CPU/IO)
   queue 不积压但延迟高 = 协调者归并/网络(fetch 放大)
③ GC:停顿期间所有线程都停 → 先看 GC 再谈其他(官方建议,数字待验证)
④ IO:merge 期间写吞吐骤降 → 磁盘 IO 是瓶颈(实验 003 机制)
```

关键不变量:**429 是"整层过载"信号,不是孤立参数问题**。实验 010 恢复观测:负载停止后 queue→0,写入查询恢复正常——队列是弹性的,过载是可逆的;生产看到 429 是集群整体压力信号,客户端要配合重试兜底(04 篇)。

### 师徒对话

徒弟:"那我看到 search 线程池 429,直接调大 queue_size 不就行了?"

老陈:"queue_size 是静态设置,动态 PUT 直接报错 not dynamically updateable;实验 010 还实测 `-Des.thread_pool.write.queue_size` 系统属性根本不生效,必须 elasticsearch.yml 改完重启。而且 queue 只是缓冲,不是引擎——它改变的是'拒绝的时机',不是'干得快慢'。真正的解是让每个请求变快(优化查询/写入)或让请求变少(限流/容量)。"

### 留下的新账

定位到写路径了:批量导入时写入吞吐上不去。怎么写提速?——Level 3 回答写入优化三旋钮。

## Level 3:写入优化——写怎么提速

<a id="level-3"></a>

### 认知墙

> **"refresh 关掉,写入飞快"**

徒弟:"把 refresh_interval 设成 -1,写入快了 2.4 倍,那一直这么配不就行了?"

老陈:"你只看到了吞吐,没看到你付出的代价:数据可见性没了。实验 001 实测:refresh_interval=-1 后写入成功,不手动 refresh 永远搜不到。吞吐和可搜索性是同一个旋钮的两端。"

### Why:写入路径的三大开销

从 01 篇的写路径机制推导:一次 bulk 在分片上要付三笔账:

```text
① refresh 账:每 refresh 一次,内存 buffer 转成新段
   → 段数涨 → merge 压力涨(段越多,未来 merge 越多,IO 账后置)
② translog 账:durability=REQUEST(默认实测)时,每次请求 fsync
   → 磁盘 fsync 是写路径的硬成本;async 时按 sync_interval(默认 5s 实测)批量刷
③ 复制账:每个副本都执行一次相同的写操作(02 篇:副本必须完成才算成功)
```

### 实验 002:三档 refresh 的实测

```text
refresh_interval=1s  | 20000 docs | bulk time: 891ms
refresh_interval=30s | 20000 docs | bulk time: 635ms
refresh_interval=-1  | 20000 docs | bulk time: 364ms   ← 约 2.4 倍
(实验 002,ES 8.15.3,单节点容器 4 vCPU,方向性结论,数字不可外推)
```

机制解释:refresh 越频繁,段生成越多、merge 压力越大;buffer 周期越短,批量效率越低。**但代价是可见性延迟的上界**——refresh_interval 就是"写入成功到可搜索"的上界(实验 001:可见性延迟 ≈ 0 ~ refresh_interval)。

### What:三旋钮与代价交换表

| 旋钮 | 转的方向 | 换来的 | 付出去 |
| ---- | ---- | ---- | ---- |
| refresh_interval 拉长/关闭 | 吞吐 ↑(实验 002:2.4 倍) | 批量导入更快 | 可见性延迟 ↑;忘记恢复 = 永远搜不到(实验 001) |
| translog durability → async | fsync 次数 ↓ | 写更快 | 崩溃丢数据窗口 ≈ sync_interval(官方语义;具体窗口"待验证",取决于崩溃时机) |
| bulk 分批/加大 | 摊薄协调者解析与网络往返 | 单条开销 ↓ | bulk 过大 → 协调者解析成为新瓶颈(实验 010:1.5MB 大 bulk,queue 峰值 7、rejected=0) |
| 副本数减少 | 复制账 ↓ | 写更快 | 可用性预算下降(02 篇:副本是容错预算) |

关键不变量:**每个旋钮都是代价交换,不是免费午餐**。导入场景(实验 002 的三组设计)是 refresh/translog 旋钮的典型适用:导入完必须恢复 refresh_interval 与 durability,否则在线可见性与崩溃安全都违约(05 篇治理链的"导入前调大、导入完恢复"决策卡同源)。

### 师徒对话

徒弟:"那 translog 直接 async 不就行了?反正丢一点数据无所谓。"

老陈:"无所谓三个字最贵。async 模式下丢数据窗口由 sync_interval 决定,窗口内已确认的写入在节点崩溃时可能消失——你确认给用户的'成功'不可靠了。日志类场景可以接受(丢了重新打),交易类场景不行。所以 translog 旋钮不是性能决策,是**恢复预算决策**:你能接受丢多久,就敢开多大。"

## Level 4:查询优化——查怎么提速

<a id="level-4"></a>

### 认知墙

> **"查询优化 = 加缓存/加机器"**

徒弟:"查询慢,给 filter 加个缓存,再不行加机器呗?"

老陈:"缓存能救的只有一种查询:可缓存的那一种。先搞清楚你的查询在付什么钱——评分?过滤?遍历 term 字典?逐文档求值?四种钱,四种解法。"

### Why:查询开销的四个来源

```text
① 评分账(query 上下文):BM25 逐文档算分,不可缓存
   filter 上下文(constant_score):不评分,_score=1.0,可缓存
   (实验 007:同一 filter 的 constant_score _score=1.0,query 上下文有真实分数)
② 过滤账:过滤也要遍历倒排,但结果可进缓存
   shard request cache:size=0 的完整分片响应可缓存(实验 008:连发 5 次 1 miss + 4 hits)
   node query cache:filter context 命中可缓存(官方;实验 008 未单独验证,标注待验证)
③ 遍历账:wildcard 中缀要遍历整个 term dictionary 展开成精确 term 再查倒排
   (实验 009 profile 实测:MultiTermQueryConstantScoreBlendedWrapper + 多个 TermQuery 叶子)
④ 求值账:script 逐文档执行,且只能访问 doc_values
   (实验 009:text 字段无 doc_values,doc['title'] 直接抛异常;params._source 在 script query 里是 null)
```

### 实验 009:两条红线的实测

```text
wildcard 中缀 *23456*(1M docs,23 hits):   稳定 10-11ms(冷启动 106ms)
wildcard 前缀 code-123*(1M docs,1047 hits):稳定 3-4ms(冷启动 20ms)
→ 中缀成本与命中数无关,由 term dictionary 规模决定;term 18 万→95 万,中缀 4-5→10-11ms
→ 规模效应:中缀随 term 字典线性增长(机制外推,千万级 term 未实测,标注待验证)

脚本 vs range(等价条件,热缓存):3-4ms vs 4-5ms,无显著差异;冷启动 101ms vs 50ms
→ 脚本的墙不在单次执行,在上下文:拿不到 _source、text 字段 doc[] 抛异常
→ 脚本 × 并发会放大成 search 线程池排队/429(实验 010 写线程池同源,待实测)
```

结论:**中缀 wildcard 和脚本是"逐 term/逐文档"的线性成本,和命中数无关,和规模线性相关**——这正是神话 10/11 在 04 篇被打破的机制,06 篇收网到"查询优化红线"。

### 实验 008:分页三方案的边界

```text
from+size:硬边界 from+size ≤ max_result_window(默认 10000),越界报错
  (实测 from=9991+size=10 → "Result window is too large ... [10000] but was [10001]")
scroll:每节点持有一个上下文(实测 3 分片 3 节点 open_contexts=[1,1,1]),用完必须 clear
search_after:需要稳定唯一排序;非唯一排序字段实测 50,000 个 a 只翻出 10 个,静默丢数据
  (无 PIT 时排序字段非唯一会跳过所有"等于游标值"的文档;生产稳定分页建议 PIT)
```

### 实验 007:聚合内存的边界

```text
terms 聚合:shard_size 默认 = size*1.5+10,每片本地 top-N 截断
  全局第一的 t5(600)每片排第 16,被 shard_size=14 截断 → 归并后整体消失
  调大 shard_size 找回(实测误差归零),代价是每片候选集变大
  → 协调节点内存与网络字节上升(官方文档);size=0 全量 + composite 分页才是精确路径
HLL++(cardinality):默认阈值 3000,100,000 唯一值实测 99319(-0.68%)
  → 阈值内"接近准确",不是精确保证;精度与内存交换
T-Digest(percentiles):聚类分布下实测 p99 偏 2.8 倍(555 vs 200)
  → 尾部百分位误差由数据分布与质心合并共同决定(实验 007)
```

### 师徒对话

徒弟:"那我所有查询都套 constant_score,分数都不要了,全走缓存不行吗?"

老陈:"可以,但你要先想清楚:你还需要相关度排序吗?电商搜索靠 BM25 排'最相关',日志查询靠 filter 缩范围——两种查询的机制需求根本不同。'能缓存'的前提是'不评分','不评分'的前提是业务不需要分数。先有业务语义,后有优化手段。"

### 留下的新账

单个查询优化到头了:过滤、分页、聚合都规范了,但节点堆还是告警、磁盘还是快满。怎么办?——Level 5 回答堆/GC 与容量规划。

## Level 5:堆/GC 与容量规划——调优的边界

<a id="level-5"></a>

### 认知墙

> **"调优万能"**

徒弟:"再不行把堆加到 64GB,加机器总没错吧?"

老陈:"堆不是越大越好:ES 官方指引是 Xms=Xmx,且不超过 compressed oops(指针压缩)阈值——超过阈值,对象指针从窄指针变 64 位指针,同样的数据吃更多堆(官方 advanced-configuration;阈值依平台,官方给的是验证方法:启动日志里的 `compressed ordinary object pointers [true]` / `_nodes/jvm`,不是固定数)。而且堆只是容量的一面,磁盘水位、分片数、段数,每个都是独立的天花板。"

### Why:为什么堆/容量是独立的天花板

调优到这一层,四个约束同时在场,互不替代:

```text
① 堆:JVM 对象都要占堆
   → compressed oops 阈值:官方建议 Xms=Xmx 且不超过阈值(官方 advanced-configuration)
     阈值依平台、无固定数;判定法:启动日志 `compressed ordinary object pointers [true]`
     或 `_nodes/jvm` 的 using_compressed_ordinary_object_pointers
   → index_buffer_size 默认 10% 堆(实测 8.15.3):堆小,写缓冲就小,refresh 更频繁
② breaker:堆的"刹车"
   → 官方默认:parent real-memory 95%、fielddata 40%、request 60%、in-flight 100%(官方 circuit-breaker 文档)
   → breaker 只跟踪部分内存,不是 OOM 的完整保护;调高 limit 不是默认容量方案
③ 磁盘:水位满了索引变 read-only(官方 watermark;删除数据不立即释放,神话 3,01 篇)
④ 分片数:每分片有固定开销 + merge 放大(神话 4,02/05 篇);分片不是越多越好
```

### 容量规划:从机制推导,不是拍脑袋

```text
写入吞吐 → 看 write 线程池(threads=核数)与 IO:核数定了,吞吐上限在机制上就存在
查询吞吐 → 看 search 线程池(实测 size=7)与协调者归并:候选集放大来自 from+size
磁盘     → 数据增长 × 保留期:不规划保留期,磁盘水位迟早打爆(05 篇 ILM 就是保留期治理)
分片     → 单分片吞吐 × 分片数 = 并行度,但每分片固定开销 + merge 放大是代价
```

关键不变量:**调优的边界 = 机制决定的成本下限**。实验 010 的 write queue 429 是"线程数=核数"的机制下限:参数调不掉核数;实验 009 的中缀 wildcard 是"遍历 term 字典"的机制下限:参数调不掉字典规模。到这一步,剩下的都是架构问题:分片策略、索引模板、数据保留、节点规模——这就是 07 篇的场景选型。

### 师徒对话

徒弟:"那什么时候算'调优到头了'?"

老陈:"三句话:参数已经回到官方默认,瓶颈指标仍然满;单查询的机制成本已经压到下限,延迟还是不达标;容量已经按增长曲线排过,磁盘水位仍然在涨。三个'仍然'出现,就不是参数问题,是设计问题——你要重新选型,而不是继续拧螺丝。调优的终点是承认边界,并把这笔账交给架构。"

06 篇的最后一个问题:**这些边界之外,不同的业务该怎么选?**——07 篇回答场景落地与选型终局。

<a id="pitfalls"></a>

# ⚠️ 坑与细节

## 坑 1

错误理解:"改参数前不用看基线。"

原因:没有基线,调优无法归因;一次改两个变量,出了事故不知道回滚哪个。

修正:先记录五类指标基线,一次一个变更,复测同一指标(实验 002 的对照组精神)。

## 坑 2

错误理解:"refresh_interval=-1 一直开着,写入最快。"

原因:实验 001 实测:-1 后不手动 refresh 永远搜不到;导入场景结束后忘记恢复 = 在线业务不可搜。

修正:导入/批量场景用 refresh 拉长 + 导入完恢复;在线场景用默认 1s(05 篇治理链同源)。

## 坑 3

错误理解:"429 了就把 queue_size 调大。"

原因:queue_size 静态设置,动态 PUT 报错;`-Des.` 系统属性实测不生效,必须 yml 重启(实验 010);queue 只是缓冲,不改吞吐。

修正:优化单请求成本/限流/扩容;429 是整体过载信号,客户端配合重试兜底(04 篇)。

## 坑 4

错误理解:"from 翻到 100 万页没事。"

原因:from+size ≤ max_result_window(默认 10000),越界直接报错(实验 008:10001 > 10000);归并候选量级 ≈ 分片数 × (from+size)(机制推导)。

修正:前端分页用 search_after + PIT;全量导出用 scroll 并 clear。

## 坑 5

错误理解:"search_after 用 tag 这种字段排序就行。"

原因:非唯一排序字段会跳过"等于游标值"的文档——实测 50,000 个 a 只翻出 10 个,静默丢数据(实验 008)。

修正:排序元组必须稳定唯一(如 docnum),生产建议 PIT 内的完整 sort 数组。

## 坑 6

错误理解:"调大 shard_size 是免费的。"

原因:shard_size 放大 = 每片候选集变大 = 协调节点内存与网络字节上升(官方文档;实验 007 找回 t5 的同时候选集 14→1000)。

修正:先确认是否需要精确 top-N;需要精确就用 size=0 + composite 分页。

## 坑 7

错误理解:"堆加到 32GB 以上更快。"

原因:超过 compressed oops 阈值后 JVM 指针压缩失效,对象指针变宽,同样的数据吃更多堆;官方建议 Xms=Xmx 且不超过阈值,但阈值依平台、无固定数,官方给的是验证方法(启动日志/nodes API,官方 advanced-configuration)。

修正:堆按"官方指引 + 本机日志验证阈值"设置;性能由指标验证,不是由堆大小验证。

## 坑 8

错误理解:"看到 429 是客户端的问题,服务端不用管。"

原因:429 是集群整体过载信号(实验 010:负载停止后 queue→0,恢复可逆);客户端重试只是兜底,不是解药。

修正:分层定位过载源,优化或扩容;客户端加幂等重试兜底(04 篇决策卡)。

<a id="decisions"></a>

# 🏆 生产决策卡

## Decision Card 6-1:写入优化(批量导入/日志类)

场景:批量导入 1 亿条,或日志持续写入。

判断:refresh/translog/bulk 三旋钮是恢复预算决策,不是性能决策。

Mechanism → Decision:

| 机制 | 工程决策 |
| ---- | ---- |
| refresh 决定可见性上界(实验 001) | 导入:refresh_interval 拉长/-1,导入完恢复;在线:保持默认 |
| translog fsync 是写路径硬成本(实验 002 机制) | 能接受崩溃丢窗口 → async;不能 → REQUEST |
| bulk 摊薄协调者开销(实验 010) | 分批导入(如 5000~10000 条/批,01 篇决策卡同源),过大反而协调者瓶颈 |
| 副本复制账(02 篇) | 导入期可临时副本归零,导入完恢复(容错预算) |

禁止:导入完忘记恢复 refresh/durability;用 queue_size 硬扛 429。

验收:导入吞吐与恢复后的可搜索性,双指标复测。

## Decision Card 6-2:查询优化

场景:搜索/过滤/分页/聚合出现延迟。

判断:先分"评分/过滤/遍历/求值"四种开销,再动手。

Mechanism → Decision:

| 机制 | 工程决策 |
| ---- | ---- |
| query 评分不可缓存,filter 可缓存(实验 007/008) | 不需要分数的查询用 constant_score/filter 上下文 |
| 中缀 wildcard 遍历 term 字典(实验 009) | 查询侧禁止中缀;数据侧用前缀/枚举词设计 |
| 脚本只能访问 doc_values(实验 009) | 需要脚本逻辑先想数据模型,别靠脚本补 |
| from+size 硬边界(实验 008) | 前端翻页 search_after + PIT;导出 scroll + clear |
| 聚合近似(实验 007) | 需要精确 top-N:size=0 + composite;接受近似:明确 SLO |

禁止:filter 需求用 query 上下文写;生产查询出现中缀 wildcard。

验收:p99 与 429 计数对比基线。

## Decision Card 6-3:容量规划与调优边界

场景:节点堆告警、磁盘水位上涨、吞吐到顶。

判断:参数调优到机制下限后,剩下的都是架构问题。

Mechanism → Decision:

| 机制 | 工程决策 |
| ---- | ---- |
| write 线程数 = 核数(实验 010 实测) | 吞吐上限在核数:加机器而不是调参数 |
| 磁盘水位与删除语义(神话 3,01 篇) | 保留期治理(ILM,05 篇)优先于扩容 |
| 分片固定开销 + merge 放大(神话 4) | 分片数按容量/节点规划,不是越多越好 |
| compressed oops 阈值(官方) | 堆按官方指引(验证阈值)设置;breaker 不是容量方案 |

禁止:用"调大 breaker""加堆"掩盖容量问题。

验收:瓶颈指标 × 3 个"仍然"出现 → 进入选型(07 篇)。

# 🌍 跨语言视角

## MySQL:慢日志与 EXPLAIN

MySQL 的调优入口是慢查询日志 + EXPLAIN(执行计划),ES 的入口是慢查询日志(官方 slowlog)+ profile API——**都是"先定位,再优化"**。方法论同构:先有基线(慢日志阈值),再有一个变量的变更。区别在机制:MySQL 调的是执行计划(索引选择),ES 不暴露可调的优化器/提示,调优对象是查询形态与缓存(机制成本),查询路径是确定的两阶段(03 篇)。

## ClickHouse:批量写入与 merge tree

ClickHouse 的写入优化同样围绕批量(batch)与后台合并(merge tree)——与 ES 的 bulk + merge 是同一类机制:追加写、后台整理、读放大 vs 写放大权衡。**方法论可迁移**:任何"追加写 + 后台合并"的存储,刷新频率/批次大小/合并策略都是同一组旋钮。但 ClickHouse 的"点查"与"行级更新"是弱项,选型账要在 07 篇结。

## Redis:缓存层

Redis 是"热数据缓存"的典型:filter 结果集、热词补全可以放 Redis,减轻 ES 查询压力。但缓存一致性(失效/穿透)是新的复杂度——**优化转移不等于优化消失**。

## 方法论沉淀

"指标先行 → 分层定位 → 旋钮交换 → 验证复测 → 承认边界"是通用调优循环,不依赖任何具体存储:先有单位,再动手。
