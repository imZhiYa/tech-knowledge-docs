<a id="level-1"></a>

## Level 1

一句话认知墙:**mapping 不是"表结构"而是"索引结构声明"——已存在字段的类型一旦创建,倒排/doc_values 已经按它建好,改类型通常只能 reindex;神话 9 锁死的是字段物理语义,不是整个 mapping 永远不能演进。**

### 前置知识关卡

* [ ] 00 篇:定义类型才能建索引的因果(dynamic mapping 的风险)
* [ ] 01 篇:倒排/FST/doc_values 由字段类型决定
* [ ] 04 篇:text 字段没有 doc_values(实验 009)

### Why

徒弟:

> MySQL 里 ALTER TABLE 改个字段类型不是常规操作吗?ES 的 mapping 凭什么改不了?

老陈:

> 因为 ES 的 mapping 直接参与**物理布局声明**——`keyword` 决定 FST+倒排+doc_values,`text` 决定分词+倒排(无 doc_values),`double` 决定列式编码。关系数据库的 DDL 也可能触发重写,不能简单归结为"只改元数据";关键差异是 ES 对已存在字段类型通常不提供原地变更,想换就 reindex 重建。
> 另外 dynamic mapping 比你想的更阴险:写入一个没声明过的字段,ES 按值**猜类型**——原生 JSON 数值可能映射为 `long`/`double`,`"2026-08-17"` 这类字符串可能通过默认 date detection 变成 date;数字字符串只有开启 `numeric_detection` 后才会按数值映射。猜错的字段从此定死,比显式声明更早锁死。

| 方案 | 解决什么 | 留下什么问题 |
| ---- | ---- | ---- |
| MySQL ALTER TABLE | 改元数据即生效 | ES 无此模型:类型即物理布局 |
| dynamic mapping 自动猜 | 免声明,开箱即用 | 猜错即锁死;隐式 schema 漂移 |
| 显式 mapping 先行 | 类型可控 | 要在写入前完成设计 |

### What

字段类型 → 物理布局(01 篇机制,查询视角):

```
keyword : FST(term dictionary)+ postings + doc_values  ← 可过滤/排序/聚合
text    : 分词 + postings;无 doc_values                 ← 全文检索
           排序/聚合报错(实验 009:script_exception)
long/double/date : doc_values(列式)                    ← 范围/数值/日期
nested  : 独立子文档(Level 5 接入)
```

不变量:**mapping 的字段类型选择,同时决定"能做什么查询"和"结构成本"。** 已存在字段的类型/分析语义通常定死,但 mapping 仍可新增字段、multi-fields 或 runtime fields;需要为历史文档补齐新索引结构时再 reindex——所以核心字段设计是写入前最便宜的修改机会。

> 📌 最容易被误解的一点:text 字段"不能排序"不是功能阉割,是**物理必然**——倒排存的是词项位置,不是完整原始值。要排序/聚合就在 mapping 里加 `keyword` 子字段(`title.keyword`),成本是额外一份索引结构。

### How

① 写入前:显式定义 mapping(或让 dynamic 猜)

② 写入时:按类型建倒排/doc_values,字段类型锁定

③ 想改已有字段类型:PUT mapping 直接报错(类型不可变);新增字段则可以直接更新 mapping

④ 正确路径:新索引新 mapping → 数据搬过去 → 切别名(Level 2)

实测锚点(实验 009,es-ha-lab,ES 8.15.3):

```
text 字段 doc[] 访问:
  script_exception:"Text fields are not optimised for operations that
   require per-document field data like aggregations and sorting"
  ← text 没有 doc_values 的运行时铁证(8.15.3)

text + keyword 子字段是常规解:
  {"title":{"type":"text","fields":{"keyword":{"type":"keyword"}}}}
  ← 搜索走 text,排序/聚合走 title.keyword(官方映射模式)
```

### Transfer

- "元数据可变 vs 物理布局不可变"是存储系统的分水岭:列式数据库改 schema 要重写、对象存储改 schema 要迁移,只有"元数据与数据分离"的系统才能在线 ALTER。
- "先设计后写入"是免锁死铁律:任何有 schema 的系统,写入前把字段形态想清楚,通常比事后迁移更可控。
- 本层留下的新账:**已经锁死了怎么办?有没有不停服的路?**——逼出 Level 2 的翻新重编。

### Level Ending

🔴 口诀:类型即布局,写入前想清楚。

<a id="level-2"></a>

## Level 2

一句话认知墙:**reindex 是把数据从旧索引搬到新索引的后台拷贝,alias 是入口指针;在增量对齐或短暂停写等条件满足时,两者配合才能实现零停机换 mapping:建新 → 搬数据 → 原子切指针 → 删旧。**

### 前置知识关卡

* [ ] Level 1:已有字段类型锁定,类型变更通常需 reindex
* [ ] 02 篇:写入走主分片,alias 只是路由入口

### Why

徒弟:

> 既然只能重建,那停服一晚,导出导入不就行了?

老陈:

> 停服 = 停机窗口,大索引 = 数小时。ES 给的标准答案是**不闭馆**:
> reindex 是**后台拷贝**——旧索引可以继续服务,但 reindex 会占用 source 的 scroll/search 与 destination 的 write 资源,且不会自动处理拷贝期间的新写入;
> alias 是**入口指针**——应用只认识别名,不认识具体索引;
> 切换是**一次原子动作**——`_aliases` 请求里的 remove+add 一起生效,不存在"中间态"。
> 实测:切换瞬间 50 个并发写全部成功,0 失败——写请求要么落在旧索引(切换前),要么落在新索引(切换后),永远有地方可写。
> 唯一的坑是:别名不是"想写就自动有"的——**写一个不存在的别名,ES 会默默创建一个同名索引**,把数据写进一个没有别名的"孤儿索引"里。

| 方案 | 解决什么 | 留下什么问题 |
| ---- | ---- | ---- |
| 停服导出导入 | 简单直接 | 停机窗口;数据量大=数小时不可用 |
| reindex + alias 切换 | 在增量对齐条件下零停机换 mapping | 切换前要规划好写入偏移(停写/双写/增量 reindex) |
| 直接写别名 | 应用无感知 | 别名不存在 = 自动建同名索引(实测坑) |

### What

三个对象的职责(机制,非 API):

```
旧索引 v1 :数据在跑,读照常(可能只读或双写)
reindex   :后台把 v1 数据拷到 v2(快照视角拷贝,不阻塞 v1)
alias     :应用唯一入口;is_write_index 声明"写请求落哪个索引"
原子切换  :单次 _aliases 调用里 remove+add 同时生效,无中间态
```

切换后的状态(实验 011 实测):

```
切换前:alias-test → v1(is_write_index=true)
切换后:alias-test → v2(is_write_index=true);v1 退出别名
v1 数据保留,可显式访问;不再接收写请求
```

不变量:**alias 只管"路由到哪",不管"数据在不在"**——reindex 没搬完就切,新索引会缺数据;所以切换时机 = 数据对齐完成时,而不是"reindex 启动时"。

> 📌 最容易被误解的一点:reindex 不是"同步迁移",它拷贝的是**启动时刻的快照视角**,拷贝期间新写入 v1 的增量不会自动出现在 v2——生产双写或切换后补一次增量 reindex 是常见做法(官方 reindex 文档不保证强一致)。

### How

① 建 v2:新 mapping,分片/副本按新规划

② 后台 reindex:v1 → v2(实测 100 docs / 175ms / 0 冲突;生产需按资源限流)

③ 数据对齐校验:两边 count 一致(或接受增量方案)

④ 原子切换:单请求 remove v1 + add v2(is_write_index)

⑤ 验证:写走 v2,读走 alias;v1 保留观察期后删除;所有写请求开启 `require_alias=true`

实测锚点(实验 011,es-ha-lab,ES 8.15.3,单分片):

```
写 100 docs 走 alias-test → 全部进 v1
reindex v1→v2:took=175ms,total=100,created=100,version_conflicts=0

切换期间 50 个并发写(switch-1..50,0.1s 间隔)全部成功:
  v1=117(100 原始 + 17 切换前)  v2=133(100 reindex + 33 切换后)
  50/50 成功 → 切换零丢写

切换后 _cat/aliases:alias-test → 仅 v2(is_write_index=true)
```

坑的实测(实验 011):

```
写不存在的别名:
  bulk 写入 "alias-test" → errors=false,但别名不存在 →
  ES 自动创建同名索引 alias-test
  之后再建真实别名 → invalid_alias_name_exception:
  "an index or data stream exists with the same name as the alias"
  ← 必须删掉自动建的索引再挂别名(实测踩坑);生产写请求应带 `require_alias=true`

is_write_index 是 body 字段:
  URL 参数 ?is_write_index=true → 实测 400
  "request contains unrecognized parameter"
```

### Transfer

- "后台拷贝 + 原子切指针"是零停机迁移的通用骨架:数据库 online DDL、Kubernetes 蓝绿发布、DNS 切流,全是同一模式——**数据面与路由面分离**。
- "指针先行"思想:任何应用都要通过"指针"(alias/域名/版本号)访问资源,而不是直接拼资源名——这是可迁移性的起点。
- 本层留下的新账:**索引能翻了,但数据一直涨,索引会无限大——谁来管生命周期?**——逼出 Level 3 的 ILM。

### Level Ending

🔴 口诀:搬数据切指针,别名在手零停机。

<a id="level-3"></a>

## Level 3

一句话认知墙:**ILM 把"索引生命周期"自动化:rollover 按条件(max_docs/size/age)轮换写索引,phase 按阶段迁移(hot→warm→cold→frozen);rollover 只换写入口,不动老数据。**

### 前置知识关卡

* [ ] Level 2:alias 的 is_write_index 语义
* [ ] 01 篇:段/merge/存储成本随索引增长

### Why

徒弟:

> 日志一年涨几 TB,一个索引无限写下去,不也能用吗?为什么要 ILM?

老陈:

> 三个死法等着你:
> **分片无限大**:一个分片写到几百 GB,merge 和恢复都变慢(01 篇的 merge 放大),查询扫的段更多;
> **索引无限多段**:老数据从来不合并,段数、文件句柄、堆上的段元数据一起涨;
> **没有冷热分层**:一年的日志和昨天的日志用同样的热存储,成本白白翻几倍。
> ILM 的答案是**把"人工定期建新索引、迁移老索引"变成规则**:rollover 让写索引按条件自动轮换(书满开新架),phase 让数据按年龄自动搬家(新书热、旧书入库房)。你只需要定规则,不负责执行。

| 方案 | 解决什么 | 留下什么问题 |
| ---- | ---- | ---- |
| 单索引无限写 | 最简单 | 分片无限大、段无限多、无冷热分层 |
| 人工定期建索引/迁移 | 可控 | 人肉运维,漏一次就是事故 |
| ILM 自动化 | 规则驱动 | 规则要先想清楚;poll 有延迟(默认 10min) |

### What

ILM 的两个机制(官方概念 + 实验):

```
rollover:写索引(经 alias 的 is_write_index)达到条件后,
          自动新建 000002 并接管写;老索引保持可读
          条件:max_docs / max_size / max_age(满足其一);
          max_docs 看索引文档数且不计 replicas,限制最大主分片要看 max_primary_shard_docs
phase:hot → warm → cold → frozen → delete
       不同 phase 有不同 action;例如 hot rollover/forcemerge,
       warm/cold allocate/migrate, frozen searchable_snapshot,delete delete
检查节奏:indices.lifecycle.poll_interval(默认 10min;实验调 1s)
```

不变量:**rollover 不搬数据**——老索引的文档原地不动,只是"写入口"轮换到新索引;查询仍然要覆盖整个 alias(多索引)。在 ILM 管理的 rollover alias 配置中,写索引由 `is_write_index` 保证只有一个。

> 📌 最容易被误解的一点:rollover 不是"自动分区"——它不改变老索引的物理布局(不分段、不合并、不搬迁),只是创建新索引接管写。真正的"搬家"(forcemerge/shrink 等)发生在 phase 动作里,而且同样不是立刻执行,受 poll_interval 节拍约束。

### How

① 定义 policy:hot 阶段配 rollover 条件(如 max_docs=5000)

② 建 000001,挂 alias(ilm-test)并声明 is_write_index + 绑定 policy

③ 写入持续走 alias → 落在当前写索引

④ poll 节拍检查条件 → 满足则自动建 000002 并轮换写索引

⑤ 后续 phase 按年龄对老索引执行迁移动作

实测锚点(实验 011,es-ha-lab,ES 8.15.3,poll_interval=1s 实验值):

```
policy:hot.rollover.max_docs=5000
写 6000 docs 走 ilm-test 别名:
  ilm-test-000001: 6000 docs(触发轮换,数据留在原索引)
  ilm-test-000002: 0 docs,is_write_index=true → 新写入接管
  _ilm/explain 000001: phase=hot, action=complete(轮换完成)
再写 after-roll:_index=ilm-test-000002(实测落位)
```

### Transfer

- "写入口轮换 + 老数据按年龄分层"是时序数据治理的通用模型:MySQL 分区表、Kafka 日志保留策略、ClickHouse TTL,全是"新数据热、老数据冷"的自动迁移。
- "规则驱动运维"的价值:把高频、重复、容易漏的执行变成策略配置,是运维规模化的前提。
- 本层留下的新账:**索引再规范,数据也可能丢——误删、故障、迁移事故,最后的兜底是什么?**——逼出 Level 4 的 snapshot。

### Level Ending

🔴 口诀:写满自动换架,年龄决定冷热。

<a id="level-4"></a>

## Level 4

一句话认知墙:**snapshot 是段级去重快照(不是 cp 数据目录):注册仓库需 path.repo 白名单,快照落盘到共享目录,恢复 = 从快照重建索引;实测删索引后 6000/6000 全量找回。**

### 前置知识关卡

* [ ] 01 篇:段是 Lucene 的最小存储单元,不可变
* [ ] 02 篇:副本解决可用性,不解决"误删/物理损坏"

### Why

徒弟:

> 数据不是有副本吗?3 节点上都有副本,还要备份干嘛?

老陈:

> 副本防的是"节点挂了",防不了三件事:
> **误删**:DELETE 索引是集群级动作,3 个副本一起没;
> **损坏蔓延**:写入路径的 bug 会同时写到所有副本,坏数据同构;
> **物理灾难**:机房级别的故障,副本和主分片在一起。
> 所以副本 ≠ 备份。snapshot 是**把索引的段和相关元数据推到独立存储**(共享目录/S3),独立于集群生命周期。仓库会复用未变化的段来减少传输,但 merge 会产生新段;实测 23 个文件 153KB、200ms 完成。
> 而恢复不是"把文件拷回去",是**从快照重建索引**:restore 后分片重新分配;快照不是 live translog 的复制,恢复边界应按快照中包含的段和元数据验证。

| 方案 | 解决什么 | 留下什么问题 |
| ---- | ---- | ---- |
| 副本 | 节点故障 | 不防误删/同构损坏/机房灾难 |
| 物理拷贝数据目录 | 直觉上的"备份" | 不是官方备份语义;段与 translog 状态不一致 |
| snapshot | 分片视图 + 独立存储 | 恢复视图落在快照 start/end 窗口;仓库复用未变化段 |

### What

snapshot 机制(官方 + 实验):

```
仓库(repository):fs 类型,location 指向共享目录
  前提:path.repo 白名单(elasticsearch.yml 配置,实测注册才成功)
快照:段级去重——已存在且未变化的段不重复传,merge 产生的新段仍需处理
恢复:从快照重建索引(分片重新分配),不是文件拷贝
约束:快照期间的写入可能不出现在对应分片的快照视图中
       → 快照包含各分片在 start/end 窗口内的视图,不保证全局同一时刻
```

不变量:**Lucene 段不可变让仓库可以复用未变化的段**——但 merge 会生成新段并淘汰旧段;旧段只要仍被其他快照引用就不能删除。快照之间逻辑独立,不是一条必须按顺序依赖的链。

> 📌 最容易被误解的一点:快照不是"实时备份",也不代表整个集群某个精确瞬间。它覆盖一个 start/end 窗口;所以实际 RPO 还要结合快照持续时间、写入确认语义与恢复验证,不能只看快照间隔。

### How

① yml 配 path.repo 白名单(3 节点共享目录 /snapshots)

② 注册仓库:PUT _snapshot/es-repo(type=fs, location=/snapshots)

③ 打快照:PUT _snapshot/es-repo/snap-011(indices, wait_for_completion)

④ 验证快照:SUCCESS、分片数、文件数、大小

⑤ 灾难恢复:删索引 → _restore(不带 wait_for_completion)→ 数据找回

实测锚点(实验 011,es-ha-lab,ES 8.15.3,3 节点共享 /snapshots):

```
注册仓库:path.repo 未配时注册会失败 → yml 加 path.repo:["/snapshots"] 重启后成功
  本实验 /es-snapshots(宿主机 bind mount),只验证仓库 API 与索引恢复,
  不证明跨主机/跨可用区灾备能力;快照请求还使用了 include_global_state=false
snap-011(alias-test-v2 + ilm-test-000001):
  state=SUCCESS, done=2/2 shards, 23 files, 153,233 B, took=200ms
DELETE ilm-test-000001(数据消失)
_restore(不带 wait_for_completion——该参数实测 400):
  ilm-test-000001 恢复:green,count=6000(6000/6000 全量找回)
```

坑的实测(实验 011):

```
_restore 的 wait_for_completion:
  POST /_snapshot/es-repo/snap-011/_restore?wait_for_completion=true
  → 实测 400 "Unknown parameter wait_for_completion"
  ← restore 是异步任务,轮询 _recovery 或直接查数据验证

restore 恢复的索引按快照保留原 mapping/索引元数据
  (本次只核对 count;rename 到不同索引名需 rename_pattern,官方文档,待验证)
```

### Transfer

- "独立于主存储、可去重、可验证恢复的快照"是所有数据库的备份共识:MySQL 物理备份、Kafka 备份镜像、对象存储版本化——备份的黄金标准是**独立故障域 + 增量/去重 + 可验证恢复**。
- "恢复演练是备份的一部分":从不演练的备份=没有备份(restore 的坑只有恢复时才暴露)。
- 本层留下的新账:**单索引的治理齐了,整个集群的骨架怎么搭?分片数、节点角色、字段形态怎么定?**——逼出 Level 5 的集群规划。

### Level Ending

🔴 口诀:副本不防误删,快照独立增量。

<a id="level-5"></a>

## Level 5

一句话认知墙:**神话 9 打穿 + 神话 4 补刀:集群治理 = 先定字段形态(mapping/nested),再定容量(分片/节点),再定生命周期(ILM/快照);分片不是越多越好,每个选择都要能回溯到机制。**

### 前置知识关卡

* [ ] Level 1-4 全部机制
* [ ] 02 篇:分片路由固定、副本语义、节点角色
* [ ] 04 篇:容量与 429 的边界

### Why

徒弟:

> 那规划是不是"分片越多越快、节点越大越好"?

老陈:

> 恰恰相反,这两条都是神话的变体:
> **分片越多越好(神话 4)**:分片 = 路由分区的单元,也是合并、恢复、聚合扇出的单元。分片太多,每个分片小、段碎、merge 放大、聚合扇出开销大;分片太少,单分片无限涨。**分片数是"容量和并行度"之间的折中,不是越多越好。**
> **节点越大越好**:单个大节点是单点——内存、GC、故障半径都放大;正确模型是"若干节点 + 角色分工":master-eligible 负责集群状态与选举,data 角色负责分片数据,但所有节点都能承担协调请求,不能把角色理解成互斥职责。
> 还有 **nested 字段**:数组对象想"按对象独立匹配",扁平化会跨对象误命中(00 篇);nested 用独立子文档解决,但查询/索引成本明显更高(官方明确;性能差异本环境未实测)。
> 所以治理的顺序是:**先定字段形态,再定容量,再定生命周期**——每一步都问"这个选择对应哪个机制"。

| 方案 | 解决什么 | 留下什么问题 |
| ---- | ---- | ---- |
| 分片拍脑袋 | 直觉"越多越快" | 神话 4:merge/扇出/恢复放大 |
| 单一大节点 | 管理简单 | 单点、GC、故障半径 |
| 角色分工 + 容量规划 | 可控 | 规划要回溯机制,不能拍脑袋 |
| 扁平化数组对象 | 简单 | 跨元素误命中(00 篇 object 数组坑) |
| nested 独立文档 | 对象级独立匹配 | 索引/查询成本更高(官方声明,性能待实测) |

### What

集群治理的三个决策域(机制 → 决策):

```
① 字段形态
   keyword/text/数值/date 由查询需求定(Level 1)
   text 加 keyword 子字段:排序/聚合(官方映射模式)
   nested:对象级独立匹配才用;索引/查询成本需按真实数据待实测

② 容量(分片/节点)
    分片数 ≈ 容量与并行度的折中;不存在脱离负载的通用 GB 硬线,必须结合磁盘/heap/查询/恢复压测
   副本数:读扩展 + 可用性(02 篇),不解决数据安全(Level 4)
   节点角色:master/data/ingest 分工;数据节点是存储主体

③ 生命周期(Level 2-4)
   alias + reindex:翻新路径;ILM:自动轮换;snapshot:兜底
```

不变量:**集群里没有免费的"越多"——分片多付 merge/扇出,副本多付存储,节点多付协调。** 每个"加"都要对应一个机制账。

> 📌 最容易被误解的一点:nested 不是"给数组加索引"那么简单——它是**每行数组元素变成独立子文档**,join 回父文档才能聚合;查询语义对了,但索引体积、查询延迟都涨。官方文档明确说明成本,本环境未做性能对比(待验证)。

### How

① 字段形态:按查询需求定类型;数组对象按匹配粒度选扁平化/nested

② 容量:按数据量、heap、磁盘、查询与恢复目标估算分片,副本按读放大量

③ 生命周期:alias 入口 + ILM 轮换 + 独立故障域 snapshot + 恢复演练共同决定 RPO/RTO

④ 治理验证:写读压测、恢复演练、rejected 监控(04 篇)

实测锚点(实验 011 + 系列机制):

```
实验 011 的完整治理链(单分片教学环境):
  建 v1 → 需求变更 → 建 v2 + reindex → 原子切换 → ILM 轮换 → snapshot 兜底
  ← 一条链把 Level 1-4 全部串起来

神话 4 补刀(02/03/04 篇机制引用):
  分片多 → 聚合截断面大(03 篇 terms 误差)、merge 放大(01 篇)、
  每分片查询/恢复开销(02 篇)、429 前的协调瓶颈(04 篇)
```

安全与升级(官方文档级,本环境未验证):

```
xpack.security:生产默认应启用(官方强烈建议;本实验环境为教学关闭)
滚动升级:逐节点升级,兼容窗口内新旧节点会共存并继续服务;具体版本跨越、功能开关与回滚路径需按官方升级矩阵验证
```

### Transfer

- "先结构、再容量、再生命周期"是任何存储系统的搭建顺序:数据库表设计 → 硬件规划 → 备份策略,三层各有各的机制账。
- "每个选择能回溯到机制"是治理的验收标准:答不出"这个配置对应哪个机制",就是拍脑袋。
- 本系列因果链推进:06 篇把"性能"做透(指标驱动压榨,边界在哪),07 篇回答"什么场景该用 ES、什么时候离开"。

### Level Ending

🔴 口诀:结构容量周期,三问定集群。

<a id="pitfalls"></a>
# ⚠️ 坑与细节

## 坑 1

错误理解:"mapping 想改就改,PUT 一下就行。"

原因:已有字段类型即物理布局,类型变更通常不可变(官方);text 无 doc_values(实验 009);新增字段仍可直接更新 mapping。

比喻后果:编目卡片的分类栏印错了,撕掉重写?不行,整本目录要重编。

线上现象:PUT mapping 报错;字段查询行为与预期不符。

修正:写入前显式 mapping;错误就 reindex + alias 切换(Level 2)。

## 坑 2

错误理解:"写不存在的别名也没事,ES 会自动处理。"

原因:会**自动创建同名索引**(实验 011 实测),数据进了一个没有别名的孤儿索引;之后再挂别名报 invalid_alias_name_exception。

比喻后果:读者把书还到"临时柜",柜子自动生成了,但没人知道它存在。

线上现象:count 对不上,发现多了一个"别名同名"的索引。

修正:写别名前确认别名已存在,并在写请求上设置 `require_alias=true`;误建索引先删再挂别名。

## 坑 3

错误理解:"reindex 完就可以切了。"

原因:reindex 拷贝的是启动时刻的快照视角,切换前的增量不在 v2;reindex 期间 v1 持续写入时,两边会不一致。

比喻后果:搬家车装完车就走,屋里后来放的东西没搬。

线上现象:切换后新索引少数据。

修正:切换前对齐数据(停写/双写/增量 reindex);官方 reindex 不保证强一致。

## 坑 4

错误理解:"rollover 会把老数据搬到新索引。"

原因:rollover 只轮换写索引,老数据原地不动(实验 011:000001 的 6000 docs 未动);"搬家"是 phase 动作的事。

比喻后果:新书架开了,旧书架的书原封不动。

线上现象:rollover 后老索引大小不变,以为没生效。

修正:理解 rollover=换写入口;冷热迁移看 phase 配置。

## 坑 5

错误理解:"ILM 配完立刻生效。"

原因:检查节奏受 poll_interval 约束,默认 10min(官方);实验 1s 是为演示调的值。

比喻后果:管理员说"满了就开新架",但巡检员一小时来一次。

线上现象:max_docs 超了,新索引迟迟不建。

修正:接受默认节拍;需要更快再调 poll_interval(注意全局影响)。

## 坑 6

错误理解:"快照 = 把数据目录 cp 一份。"

原因:快照是段级去重视图,不是目录拷贝;恢复 = 重建索引,不是文件还原;cp 数据目录会造成段/translog 不一致。

比喻后果:把档案室的柜子整个搬走,档案还是乱的。

线上现象:手工 cp 恢复后数据损坏/不一致。

修正:一律用 snapshot API + restore;恢复后验证 count。

## 坑 7

错误理解:"快照仓库注册完就能用。"

原因:fs 仓库需要 path.repo 白名单(实验 011 实测:未配置注册失败);目录至少要对参与仓库验证和快照的 master/data 节点可访问,生产还要放在独立故障域。

比喻后果:档案室登记了,但门卫不认识送档案的人。

线上现象:注册仓库报错/快照失败。

修正:yml 加 path.repo,重启;共享目录挂到所有节点。

## 坑 8

错误理解:"restore 可以同步等结果。"

原因:_restore 不支持 wait_for_completion(实验 011 实测 400),是异步任务。

比喻后果:按了"取档案"按钮,以为马上拿到,其实档案室在搬。

线上现象:restore 请求返回后立刻查索引,报 not found。

修正:轮询 _recovery 或直接重试查询;验证 count。

## 坑 9

错误理解:"有副本就不需要快照。"

原因:副本不防误删(集群级 DELETE 一起删)、不防同构损坏、不防机房灾难;快照应放在独立故障域,且恢复视图受 snapshot start/end 窗口约束。

比喻后果:每个分馆都有同一本书的抄本,但总馆一把火烧了,抄本也没了。

线上现象:误删索引后,副本一起消失,只能从快照恢复。

修正:副本保可用性,快照保可恢复;两者都要。

## 坑 10

错误理解:"nested 就是高级数组索引,随便用。"

原因:nested 每行数组元素变独立子文档(官方),索引体积与查询成本显著更高;只有"对象级独立匹配"需求才值得。

比喻后果:合著书给每位作者都单独登记一本,书架占用翻倍。

线上现象:nested 字段写入变慢、索引体积膨胀。

修正:能扁平化就扁平化(00 篇 object 数组坑);真要对象级匹配才用 nested;性能差异本环境未实测(待验证)。

<a id="decisions"></a>
# 🏆 生产决策卡

## Decision Card 1:mapping 先行设计

### 场景

新业务上线,数据要写入 ES,字段形态未定。

### 判断

核心字段类型是最昂贵的修改点(Level 1);先按查询需求定类型,再定子字段。

### Mechanism → Decision

| 机制 | 工程决策 |
| ---- | ---- |
| 类型即物理布局 | 写入前显式 mapping,关闭/约束 dynamic(按字段控制) |
| text 无 doc_values | 排序/聚合字段加 keyword 子字段 |
| 数组对象 | 先评估扁平化;对象级匹配才 nested(成本待实测) |

### Code

```json
{"mappings":{"properties":{
  "title":{"type":"text","fields":{"keyword":{"type":"keyword"}}},
  "price":{"type":"double"},
  "create_time":{"type":"date"},
  "status":{"type":"keyword"},
  "authors":{"type":"nested","properties":{"name":{"type":"keyword"}}}
}}}
```

### 禁止决策

不要放任 dynamic mapping 猜类型;不要给纯过滤字段加 text;不要默认给所有字段加 keyword 子字段(存储翻倍)。

### 验收指标

- 写入吞吐(docs/s)、索引体积/原始数据比
- 查询 p99、聚合 p99(子字段路径)、nested 查询对比(待实测)
- dynamic mapping 新增字段数(监控漂移)

## Decision Card 2:零停机翻新(reindex + alias)

### 场景

线上索引 mapping 错误或需求变更,不能停服。

### 判断

建新索引 → reindex → 原子切换 → 删旧;别名是应用唯一入口。

### Mechanism → Decision

| 机制 | 工程决策 |
| ---- | ---- |
| 后台拷贝 | reindex 期间旧索引照常;增量需对齐(停写/双写/增量 reindex) |
| 原子切换 | 单请求 remove+add;切换后写落 v2 |
| 别名不存在的坑 | 先建索引再挂别名;写请求带 `require_alias=true`;误建同名索引先删 |

### Code

```http
POST /_reindex?wait_for_completion=true
{"source":{"index":"alias-test-v1"},"dest":{"index":"alias-test-v2"}}

POST /_aliases
{"actions":[{"remove":{"index":"alias-test-v1","alias":"alias-test"}},
            {"add":{"index":"alias-test-v2","alias":"alias-test","is_write_index":true}}]}

POST /alias-test/_update/c1?require_alias=true
{"doc":{"v":2}}
```

### 禁止决策

不要在数据未对齐时切换;不要直接改 v1 的 mapping(报错);不要删旧索引不观察期。

### 验收指标

- 切换期间写入失败数(应=0)、切换耗时
- reindex 吞吐(docs/s)、version_conflicts 数
- 切换后 count 一致性核对、查询 p99

## Decision Card 3:生命周期(ILM + snapshot)

### 场景

日志/时序数据无限增长;数据可能被误删。

### 判断

ILM 管增长(rollover + phase),snapshot 管兜底;RPO 需结合快照窗口、写入语义与恢复演练定义,两者独立配置。

### Mechanism → Decision

| 机制 | 工程决策 |
| ---- | ---- |
| rollover 条件 | 按 max_docs/max_size/max_age 定轮换;写索引永远只有一个 |
| phase 迁移 | hot→warm→cold→frozen 按年龄;具体 action 需按数据层与成本验证 |
| poll_interval | 默认 10min;接受节拍或明确调小 |
| snapshot 频率 | 实际 RPO 还受快照持续时间、写入语义与恢复验证影响;仓库必须独立于集群故障域 |
| path.repo | fs 仓库必须白名单;恢复演练定期做 |

### Code

```json
{"policy":{"phases":{"hot":{"actions":{"rollover":{"max_docs":5000000}}},
                       "delete":{"min_age":"30d","actions":{"delete":{}}}}}}
```

### 禁止决策

不要把 ILM 当"自动分区"(不搬数据);不要只做一次快照不演练恢复;不要在生产把 poll_interval 调到秒级(全局开销)。

### 验收指标

- rollover 成功率/次数、写索引轮换延迟、phase 迁移耗时
- 快照大小/增量率、快照耗时、restore 演练时长与 count 核对
- 存储分层成本对比(hot vs cold)

## Decision Card 4:集群容量规划

### 场景

从 0 搭集群,或扩容。

### 判断

先字段形态,再容量,再生命周期;每个选择回溯机制(神话 4 打穿)。

### Mechanism → Decision

| 机制 | 工程决策 |
| ---- | ---- |
| 分片 = 容量/并行折中 | 不套用固定 GB 硬线,结合 heap/磁盘/查询/恢复压测;不要"越多越快" |
| 副本 | 读扩展 + 可用性(02 篇);备份交给 snapshot(Level 4) |
| 节点角色 | master/data/ingest 分工;数据节点是存储主体 |
| 429/协调瓶颈 | 容量压测看 rejected 趋势(04 篇);小 bulk 高并发测真实容量 |

### Code

```text
容量估算示例(教学参数,以官方文档与实测为准):
  数据量 1TB、单分片目标 ~50GB → 主分片 ~20 个(待实测校准)
  副本 1 → 总分片 ~40
  节点数按内存/磁盘/角色分工规划
```

### 禁止决策

不要拍脑袋定分片数;不要用超大单节点替代集群;不要把副本当备份。

### 验收指标

- 分片大小分布、merge 速率、恢复时长(RTO)
- 写入/查询 p99、rejected 趋势、节点 GC
- 磁盘水位、存储分层成本

<a id="cross-language"></a>
# 🌍 跨语言视角

同一个问题:"结构变了怎么迁移?数据涨了怎么治理?"

| 语言/系统 | 解法 | 与 ES 的对应 |
| ---- | ---- | ---- |
| MySQL | ALTER TABLE(元数据可变);pt-online-schema-change | ES 类型不可变 → reindex + alias;PT-OSC 同样"影子表 + 切表名" |
| PostgreSQL | CREATE INDEX CONCURRENTLY;分区表 | 后台索引构建 = reindex 快照视角;分区 = ILM 轮换 |
| Kafka | 日志保留策略(retention.ms/bytes) | ILM rollover + phase = 保留策略的自动版 |
| ClickHouse | TTL 移动/删除;分区生命周期 | 冷热分层同构(官方级结论) |
| 对象存储(S3) | 版本化 + 生命周期规则 | snapshot 仓库 + 快照保留 |
| 数据库备份 | 物理备份 + PITR | snapshot 段级去重;PITR 对应"备份窗口 + 日志连续性" |

底层判断力:

- **结构与数据分离才可在线变更**:alias/指针模式让"结构"可以独立于"数据"演进——所有系统都应给数据一个稳定的逻辑入口。
- **增长必须自动治理**:手动的定期迁移一定会漏;规则(ILM/保留策略/TTL)是规模化的前提。
- **备份三要素:独立 + 增量 + 可演练恢复**:少一个,备份就等于没有。
