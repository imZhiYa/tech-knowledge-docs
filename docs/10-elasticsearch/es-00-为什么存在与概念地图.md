# 写在最前面:这不是一篇名词清单

本文回答的不是"ES 有哪些概念",而是四个问题:

1. **为什么**数据要组织成 doc?index 为什么不是"数据库表"?(铁律 1 的伏笔)
2. **为什么**必须有 mapping?为什么字段类型一旦建立就很难改?(神话 9 的伏笔)
3. **为什么**索引要切分片、分片要副本?(02 篇高可用的大门)
4. **为什么** node 和 cluster 要分角色?("会写 REST API 不等于懂 ES"的起点)

概念在这里不是名词,是**因果链**:因为…所以引入…。每个概念回答"为什么存在",而不是"是什么"。

三条铁律(全系列):

1. **ES 不是"能存 JSON 的 MySQL"**——没有事务、弱一致、更新=删+写、聚合近似。
2. **green 不等于数据绝对安全**——green 只是分片分配状态。
3. **会写 REST API 不等于懂 ES**——API 是入口,机制是因果。

## Level 0:为什么需要一张概念地图

### Why——没有地图会怎样

**徒弟**:REST API 我能调通,索引能建、文档能查。node、shard、mapping 这些名词我也听说过,为什么还要一张概念地图?

**老陈**:你调通了 API,但你知道下面三个问题的答案吗?

- 写入成功了,为什么马上搜不到?(→ 01 篇:refresh 窗口)
- 节点挂了一个,为什么整个集群可能变红?(→ 02 篇:分片分配)
- 聚合统计的结果,为什么可能是错的?(→ 03 篇:近似聚合)

这三件事的因果,全部挂在概念上:doc 进了哪个分片、分片有没有副本、聚合在多少个分片上跑。**概念不是名词,是因果链的锚点。** 没有地图,你在机制篇里遇到的每个"为什么",都不知道该挂在哪个概念上。

## Level 1:概念全景图——Doc D 的全部货架

### 前置知识关卡

- [ ] 知道 REST 接口:PUT /index/_doc 是写入入口
- [ ] 知道"数据库的索引"和 ES 的 index 不是一回事

### Why——为什么需要全景图

**徒弟**:概念很多,一个个背下来不就行了吗?

**老陈**:背下来的是名词,画出来的才是结构。Redis 系列先画了十张货架的命令树,ES 也一样——全景图回答"Doc D 进了这扇门之后,会有哪些站点等着它"。先认识全部站点,再进每一站打穿。

### What——Doc D 的货架全景

```text
ES 概念地图
│
├── 纵向链(Doc D 的旅程)
│   ├── doc ──────── 检索与存储的基本单元(JSON)
│   ├── index ────── 文档的逻辑分组(独立 mapping/settings/生命周期)
│   ├── mapping ──── 字段类型与索引方式的 schema(字段类型建后难改,新字段可加)
│   ├── analyzer ─── 分词链:文本 → token 流(查询与写入都要过)
│   ├── shard ────── 索引的物理切分(Lucene 实例;主分片数创建后不可变)
│   ├── replica ──── 主分片的副本(可用性 + 读扩展)
│   ├── node ─────── 物理实例,承载分片(master/data/ingest/coordinating 角色)
│   └── cluster ──── 节点集合,协同管理索引与分片
│
├── 横向概念(治理与运维)
│   ├── alias ────── 索引替代名(零停机 reindex 的前提)
│   ├── template ─── 新索引自动套用 settings/mapping
│   ├── ILM ──────── 索引生命周期(hot/warm/cold/delete + rollover)
│   └── snapshot ─── 集群级备份与恢复
│
└── 机制货架(01~07 篇的主角,本篇只预告)
    ├── 倒排索引 / FST / doc_values / segment / translog / merge(01)
    ├── 路由 / quorum / 选举 / 脑裂 / 分片恢复(02)
    ├── BM25 / 两阶段查询 / 近似聚合 / 深分页(03)
    ├── 脚本 / wildcard / 乐观锁 / 线程池(04)
    ├── nested / ILM / security / 滚动升级(05)
    └── 写入 / 查询 / GC / 容量(06)
```

> 📌 **最容易被误解的一点**:index 不是数据库的"表"。一个 index 是**多个 Lucene 实例(shard)的逻辑集合**,它有独立的 settings、mapping、生命周期策略;而"数据库表"是关系模型的逻辑概念,两者不在同一抽象层。这是铁律 1("ES 不是能存 JSON 的 MySQL")的第一块地基。

### How——这张图怎么用

```text
① 新读者:按纵向链从上往下走,每个概念问"为什么存在"
② 查坑者:横向概念 + 机制货架,直达对应篇
③ 写业务:从 doc 出发,问"我的数据是什么结构 → 放哪个 index → mapping 怎么定"
```

### Transfer

1. 任何中间件入门,先画"数据旅程全景图"(Redis:命令→结构→编码;Kafka:消息→分区→副本),再看机制。
2. 概念图的价值在"锚点":遇到报错时能定位到概念(429→线程池→04 篇;red→分片→02 篇)。

### Level Ending

🔴 口诀:一图看全站,Doc 进门不迷路。

## Level 2:纵向链——Doc D 沿途的每一站

### 前置知识关卡

- [ ] 能画出 Level 1 的全景树
- [ ] 知道 REST:PUT /index/_doc/{id}

### Why——为什么概念要按链讲

**徒弟**:doc、index、mapping、shard 这些概念,拆开讲不是更清楚吗?

**老陈**:拆开讲,你会得到八个定义,然后发现全忘了。按链讲,每一个概念都是**上一个概念的问题逼出来的**:文档多了要分组,分组了要定 schema,schema 定了要切容量,切了要防丢失……因果链记住一条,八个概念全记住。

### What——Doc D 沿途八站

#### 站 1:doc——为什么数据组织成 JSON 文档

**原因**:业务数据是**嵌套、多类型**的(订单里有商品数组,商品里有标签数组)。关系模型要拆表、要 join;ES 面向"整份数据检索",把一条业务实体存成一份 JSON 文档,查询时整份返回,不需要 join。

**不变量**:一条 doc = 一组字段;字段有类型(text/keyword/numeric/geo 等);`_id` 唯一标识。

> 📌 **最容易被误解的一点**:doc 不是"一行记录"。doc 可以嵌套(对象、数组),这是 JSON 的语义;关系模型没有这个结构。这也是 later(03 篇)"object 数组扁平化"坑的根源——嵌套在 ES 里有自己的代价。

#### 站 2:index——为什么文档要分组进索引库

**原因**:千万条业务数据放一个"大篮子",mapping、生命周期、权限、备份全要打架。**因为要独立管理,所以引入 index**:一个 index 是一组相似文档的逻辑集合,有独立的 mapping、settings、ILM、alias。

**不变量**:一个 index 至少 1 个主分片(ES 8.15.3 实测默认 1);索引名是 REST 地址的一部分。

> 📌 **最容易被误解的一点**:index 是"逻辑集合",不是物理文件。物理文件在 shard 里。一个 index 含 N 个主分片 + M 个副本分片,分布在节点上——**"index"这个词在 REST 里还当动词用(PUT /index/_doc 里的 index 是"写入"动作),这是 ES 独有的双关,经常让人困惑**。

#### 站 3:mapping——为什么必须有 schema

**原因**:Lucene 建立索引时,每个字段必须知道"怎么索引":text 要分词(进倒排)、keyword 不分词(精确匹配)、numeric 要支持范围查询。**因为索引方式由类型决定,所以引入 mapping**:字段类型 → 索引结构的一一对应。

**可修改性边界(关键,别把两件事混为一谈)**:

| 想改什么 | 能不能改 |
| ---- | ---- |
| 已有字段的 type | 通常不能直接改(索引结构已建,改类型 = 已有索引失效) |
| 新增字段 | 可以(追加 mapping,不影响已有字段) |
| 部分 mapping/settings 参数 | 取决于具体参数,部分可动态调整 |
| 已有字段 type 变更 | 生产上一般"新索引 + reindex",不原地改 |

所以准确的说法是:**mapping 不是"创建后完全不能修改";受约束最强的是"已经建立索引的字段类型"**。类型变更通常意味着索引结构重来,这就是为什么 mapping 设计是生产的第一道闸门(05 篇专题),"mapping 可以随意改"是神话 9。

#### 站 4:analyzer——为什么写入和查询都要分词

**原因**:倒排索引的入口是"词"。**因为要按词检索,所以引入 analyzer**:把文本切成 token 流。

**Analyzer 的三段链**:

```text
char_filter(字符预处理:去 HTML、替换字符)
   ↓
tokenizer(切词:standard / ik / whitespace 等)
   ↓
token_filter(词条加工:小写、停用词、同义词、ngram)
```

**关键认知:index analyzer ≠ search analyzer 是允许的**。索引阶段可以用 ngram/edge_ngram(把"es"切成 e/es/es- 前缀),查询阶段用普通 analyzer——两侧 analyzer 不同,但只要**索引生成的 token 与查询生成的 token 满足业务预期的匹配关系**(如前缀匹配、子串匹配),就是合法设计。真正要保证的不是"两边一模一样",而是"token 匹配语义"。

**不变量**:同义词、大小写、停用词等任何一侧改变 token,都会改变匹配语义——这是 03 篇"搜不到/搜多了"事故的根源。normalizer 用于 keyword 字段的查询前归一化(如忽略大小写),原理相同。

#### 站 5:shard——为什么索引要切分片

**原因**:单机装不下、单机查不快。**因为要水平扩展与并行,所以引入 shard**:一个 index 切成 N 个主分片,每个分片是一个独立 Lucene 实例,分布在不同节点上,查询时并行扫所有分片再合并。

**关键不变量**:**主分片数创建后不可变**(路由公式 hash(routing) % N 定死)。要改分片数,常规做法是 reindex 到新索引;在满足 `number_of_routing_shards` 等前置条件时,ES 8.x 也提供 `_split`(增分片)/ `_shrink`(减分片)原地重建(05/06 篇)。"分片越多越好"是神话 4(02/05 篇打破)。

**路由的本质(不是简单 hash(_id))**:

```text
路由公式:hash(_routing) % 主分片数 → 目标主分片
默认情况:_routing 未指定时,由 _id 提供
启用 custom routing:显式指定 routing 值,它才是决定分片位置的关键输入
```

默认场景写 `hash(_id) % N` 只是简化;**路由参与方永远是 routing 值**。custom routing 是后续(02/06 篇)热点分片、数据倾斜、query fan-out 等话题的机制起点,在这里把 _id 写死会导致概念断裂。

#### 站 6:replica——为什么分片要有副本

**原因**:节点会挂,磁盘会坏。**因为主分片可能消失,所以引入 replica**:每个主分片有 N 个副本分片(副本与主分片不能在同一节点),主挂了副本顶上;读请求也能打副本(读扩展)。

**职责模型(不要简化为"副本=读扩展、快照=唯一安全"两端)**:

```text
写入确认(wait_for_active_shards / 副本确认)
   ↓
primary / replica 写入状态
   ↓
translog durability(fsync 策略)
   ↓
节点故障恢复
   ↓
snapshot / 异地灾备
```

**三个不混为一谈的对子**:

- **高可用 ≠ 数据绝对不丢**:副本、故障接管让集群"还能服务",但复制窗口内的未确认数据可能丢;
- **数据冗余 ≠ 灾难恢复**:副本在集群内,机房级故障时冗余同样失效;
- **本地恢复 ≠ 异地灾备**:translog/副本恢复救本地故障,跨机房靠 snapshot/CCR。

是否存在丢失窗口,要结合写入确认方式、translog durability、故障发生时机共同判断——没有一句话的结论(02 篇打穿,神话 5、6)。

#### 站 7:node——为什么分片要落在物理实例上

**原因**:分片是"逻辑单元",总得有机器跑。**因为要承载分片,所以引入 node**:一个 node 是一个 ES 实例(一个 JVM 进程),一个节点可承载多个分片(主+副本)。

**Node role 是"能力集合",不是"单一定位"**:

```text
master-eligible   参与 master 选举、集群决策
data_*(data/data_hot/data_warm/data_cold/data_frozen)   存储与查询数据
ingest             写入前预处理(管道)
coordinating       转发请求、合并结果(所有节点默认都承担)
ml / transform / remote_cluster_client 等专用角色(按需)
```

一个节点可同时拥有多个角色;生产上常通过 **dedicated master**(纯 master-eligible,不存数据)与专用 data 节点做资源隔离——这不是"控制平面/数据平面"的强制分层,而是运维选择。

**实测默认(ES 8.15.3,容器 4 vCPU)**:write 线程池 fixed size=4、queue=10000;search 线程池 size=7、queue=1000(均为 4 vCPU 下的默认值,宿主机 8 核)——节点级资源是"共享的",一个节点的写被拖垮,所有分片跟着遭殃(04 篇 429 的机制起点)。

#### 站 8:cluster——为什么节点要组成集群

**原因**:单节点挂了就是单点。**因为要协同与容错,所以引入 cluster**:节点通过 discovery 互认,选举出一个 master 负责集群决策(mapping 变更、分片分配),cluster state 广播到所有节点。

**关键不变量**:master 只做决策,数据在 data 节点。master 故障后,集群的行为取决于**重新选举是否成功**:

```text
旧 master 失效
   ↓
master-eligible 节点尝试重新选举
   ├── 选举成功(剩余节点仍能形成法定多数)
   │      ↓
   │    恢复 cluster state 管理,写入恢复
   └── 无法形成有效选举条件(法定多数不足)
          ↓
       集群管理状态无法推进,写入被拒(读可继续)
```

所以不能简单概括"master 没了 = 整个集群只读"——**能否恢复取决于选举条件(quorum)与集群状态**(02 篇打穿)。

### How——Doc D 的旅程时序

```text
① 业务提交 JSON:POST /orders/_doc {订单数据}
② ES 解析文档:按 mapping 确定每个字段的类型
③ text 字段过 analyzer:切词(写入侧)
④ 路由:hash(_routing) % 主分片数 → 确定落在哪个主分片(默认 _routing 由 _id 提供)
⑤ 主分片写入:translog + 内存 buffer(1s 后 refresh 可见)
⑥ 复制到副本分片:等待 in-sync copies 完成,失败副本移出 in-sync set 后才 ACK(02 篇打穿)
⑦ 查询时:所有分片并行执行,协调节点合并
```

> 📌 **最反直觉的一步**:第 ⑤ 步。写入成功 ≠ 立刻可搜——这是神话 1,01 篇用实验 001 打破(写入后 0 命中,1.2s 后 1 命中)。

### Transfer

1. "分层留账"法:每引入一个概念,问"它解决了什么、留下了什么账"——doc 留下 schema 问题→mapping;mapping 留下容量问题→shard;shard 留下单点问题→replica。
2. 这套"因为…所以…"可迁移到任何存储系统:Kafka 的分区/副本、MySQL 的分库分表,同一套因果。

### Level Ending

🔴 口诀:文档分组定 schema,切片备份上集群。

## Level 3:横向概念——治理与运维的货架

### 前置知识关卡

- [ ] 纵向链八站已通关
- [ ] 知道"改字段类型通常只能新索引 + reindex"这个代价

### Why——为什么需要治理概念

**徒弟**:索引建好了,文档也写了,为什么还要 alias、template、ILM、snapshot 这些?

**老陈**:纵向链解决"数据怎么进去",横向概念解决"数据怎么长期活着"。线上索引会增长、会写错、会老化、会被删——没有治理层,每次都要停机重建。横向概念是"让索引可演进"的四件工具。

### What——四个横向货架

#### alias:为什么需要索引别名

**原因**:业务要零停机重建索引(改 mapping、改分片数)。**因为要"切流量",所以引入 alias**:别名指向真实索引,重建新索引后把 alias 切过去,业务无感。reindex 是"翻新重编"(05 篇专题)。

#### template:为什么需要索引模板

**原因**:日志类场景每天建一个新索引(orders-2026-08-16),手写 settings/mapping 会漏。**因为要批量生成,所以引入 template**:新索引创建时自动套用模板(settings + mapping + alias)。ES 8.x 用 component template + index template 两级。

#### ILM:为什么需要生命周期管理

**原因**:数据有热度:刚写入的查询频繁,三个月前的几乎不查。**因为要降成本,所以引入 ILM**:hot(热)→ warm(温)→ cold(冷)→ delete,阶段间自动迁移,hot 阶段可 rollover 按大小/时间滚动新索引(05 篇专题,比喻:旧书入库房)。

#### snapshot:为什么需要备份

**原因**:磁盘坏了、机房没了,分片恢复救不了。**因为要灾备,所以引入 snapshot**:集群/索引级快照到远端仓库(S3/OSS/共享盘),可按索引恢复。"green = 不丢数据"是神话 6,快照才是最后防线(02 篇 + 05 篇)。

### How——一个日志索引的一生

```text
① template 定义 orders-* 的 mapping + settings
② 每天新索引 orders-2026-08-16 自动套模板
③ ILM:hot 阶段 7 天,rollover 按 50GB 滚动
④ 30 天后转 warm,90 天后转 cold,180 天后 delete
⑤ 每天 snapshot 到远端仓库(容灾)
```

### Transfer

1. "写入路径"与"治理路径"分离:任何系统都要区分"数据怎么进"和"数据怎么活"(MySQL 的归档、Kafka 的 retention 同一思想)。
2. 别名切流量的模式:数据库表切换、服务灰度,都是"间接层"思想。

### Level Ending

🔴 口诀:别名切流量,模板批量建,ILM 管生死,快照保命底。

<a id="pitfalls"></a>

# ⚠️ 坑与细节

## 坑 1

错误理解:index = 数据库表。

原因:名字都叫"索引",概念不同层。

比喻后果:把 ES 当 MySQL 设计,嵌套用 join、强一致读写,全踩铁律 1。

线上现象:频繁全量 reindex、"为什么查不到刚写入的"。

修正:index 是分片集合的逻辑分组;doc 是 JSON 嵌套实体,不是行。

## 坑 2

错误理解:写入成功 = 数据已经可搜、可聚合。

原因:refresh 是可见性门槛,translog 是可靠性门槛,两者不同步。

比喻后果:读者以为书已上架,实际还在登记本上。

线上现象:写后立刻查 0 命中(实验 001)。

修正:写后查询用 refresh=wait_for 或接受 1s 延迟。

## 坑 3

错误理解:副本 = 数据更安全。

原因:写成功等待所有 in-sync copies 完成;失败副本被移出 in-sync set 后请求才 ACK。真正丢失条件:in-sync set 收缩到唯一 copy(如主分片)+ 该 copy 数据损坏(02 篇打穿)。

比喻后果:备用书架再全,着火时正在递书的那一本也没了。

线上现象:主节点宕机后丢失最近几秒写入。

修正:安全靠 translog fsync + snapshot,不靠副本(02/05 篇)。

## 坑 4

错误理解:分片数越多,查询越快。

原因:每分片有固定开销,路由定死,副本不能与主分片同节点。

比喻后果:书架拆太碎,找一本书反而要问十个分馆。

线上现象:分片多、段多、查询变慢,集群状态碎片化。

修正:分片数按数据量与查询模式规划(05 篇决策卡 2)。

<a id="errata"></a>

# 📚 版本勘误表

| 错误说法 | 准确说法 |
| ---- | ---- |
| ES 的 index 就是数据库的表 | index 是多个 Lucene 分片的逻辑集合,语义与关系表不同层 |
| 主分片数随时可以调整 | 路由 hash(routing)%N 定死,创建后不可原地改;常规做法 reindex,满足条件时可用 _split/_shrink(语义,官方契约) |
| refresh 是"刷新索引文件" | refresh 让近期写入进入可搜索视图;flush 涉及 commit/checkpoint 与 translog 生命周期,不是简单的"内存落盘/文件落盘"二元关系(语义,01 篇打穿) |
| 副本越多数据越安全 | 副本是跨节点冗余/故障接管/读扩展,并非绝对安全;丢失窗口由写入确认、translog durability 与故障时机共同决定(语义,02 篇打穿) |
| 8.x 默认配置和 7.x 一样 | 8.x 默认 security 开启(语义变化);7.x 起默认单分片单副本(语义变化,7.0) |
| doc 是"一行记录" | doc 是 JSON 嵌套实体,支持对象与数组,与关系模型不同(语义) |
| mapping 随便改 | 字段类型建索引后不可变,改动需 reindex(语义,官方契约) |
| ES 是"能存 JSON 的数据库" | 无事务、弱一致、更新=删+写、聚合近似(铁律 1,03/07 篇打破) |

坦白:我自己也曾把"写入成功"当"已落盘",直到实验 001 看到 0 命中才真正理解 refresh 与 translog 的分工;也曾把 index 当表设计嵌套结构,直到 03 篇的扁平化坑。

# 🏆 生产决策卡

## Decision Card 0-1

### 场景

新系统接入 ES,第一个问题:数据怎么组织?

### 判断

先定"业务实体 ↔ doc 结构",再定 index 边界,最后定 mapping——顺序不能反。

### Mechanism → Decision

| 机制 | 工程决策 |
| ---- | ---- |
| doc 是 JSON 嵌套实体 | 一个业务实体一个 doc,避免过度拆分与过度嵌套 |
| index 有独立生命周期 | 按业务域/时间分 index,不用一个大 index 装所有 |
| mapping 建完难改 | 上线前定死字段类型,宁可先保守(多 keyword) |
| 主分片数不可变 | 提前按数据增长估算分片数(05 篇决策卡 2) |

### Code

```bash
# 最小可用模型:显式 mapping,禁止动态映射裸奔
PUT /orders
{
  "mappings": { "dynamic": "strict",
    "properties": {
      "order_no":  {"type": "keyword"},
      "user_id":   {"type": "keyword"},
      "amount":    {"type": "scaled_float", "scaling_factor": 100},
      "status":    {"type": "keyword"},
      "title":     {"type": "text", "analyzer": "ik_max_word"},
      "created_at":{"type": "date"}
    }
  }
}
```

### 禁止决策

- 不用显式 mapping、全动态映射上线(字段爆炸,total_fields.limit=1000 实测默认)
- 把一个 index 当"一张表"用,塞进所有类型的数据

### 验收指标

- 创建索引与写入首条文档:latency < 1s(本机)
- mapping 字段与业务字段一一对应,无动态映射额外字段
- 索引数量按业务域划分,无单索引吞所有数据

## Decision Card 0-2

### 场景

要不要把数据从 MySQL 迁到 ES?

### 判断

看需求:检索/分析 → ES;事务/强一致/精确统计 → 留在 MySQL。迁移不是"搬家",是"分工"。

### Mechanism → Decision

| 机制 | 工程决策 |
| ---- | ---- |
| ES 无事务、弱一致 | 写一致性要求高的数据留在 MySQL,ES 做检索副本 |
| 聚合近似 | 账务类精确统计不在 ES 做 |
| 更新=删+写 | 高频字段更新场景慎用 ES 存储 |
| 全文检索是 ES 主战场 | 搜索类需求优先 ES |

### Code

```bash
# 典型分工:MySQL 主存储 + ES 检索副本
# MySQL 写入 → 同步/异步 → ES(写入侧),查询走 ES
```

### 禁止决策

- 用 ES 当主库存订单、用 ES 出财务报表
- 强一致读(写后必须立刻读到)走 ES

### 验收指标

- 检索场景:p99 < 100ms(数据量内实测)
- 一致性场景:MySQL 为准,ES 延迟同步窗口可接受
- 无"ES 数据对不上"的线上事故

# 🌍 跨语言视角

同一类问题,别的系统怎么解决?

| 问题 | ES | Redis | MySQL | 底层思想是否一致 |
| ---- | ---- | ---- | ---- | ---- |
| 数据分组 | index(分片集合) | 无分组,靠命名空间 | 表/库 | 都是"逻辑分组 + 物理分布"两层,ES 明确分层 |
| 容量扩展 | 分片(hash 路由) | Cluster 槽位(16384) | 分库分表(路由键) | 一致:一致性哈希/槽位/取模,都是"固定路由不变量" |
| 高可用 | 主副分片 | 主从/哨兵/Cluster | 主从 + 半同步 | 一致:主写从读,复制异步,丢数据窗口是共同难题 |
| 备份 | snapshot | RDB/AOF | binlog/备份 | 一致:内存/复制不能当备份,必须落盘 |
| 统计 | 近似聚合 | 无 | COUNT 精确 | ES 用近似换性能,MySQL 用性能换精确——取舍方向相反 |

**跨语言仍成立的判断力**:

1. 路由不变量(主分片数/槽位数/表数)一旦定死,改动必须重建——所有分布式存储的共同约束。
2. "等 in-sync copies、失败副本先移出 set 再 ACK"的窗口客观存在(wait_for_active_shards 默认 1)——"高可用"与"不丢数据"是两个不同的问题。
3. 逻辑分组与物理分布必须分离思考——index/shards、topic/partitions、table/分表,同一套两层模型。
