
| ---- | ---- | ---- |

| 馆长 | master | 分片分配与集群决策 |
| 备用书架 | replica | 主书架塌了顶上 |

# 正文:六个 Level 打穿 ES 分布式高可用

<a id="level-1"></a>

## Level 1:单机的三个死法——为什么需要集群

### 前置知识关卡

- [ ] 知道 node 是 ES 实例、cluster 是节点集合(00 篇站 7/8)
- [ ] 知道主分片数创建后不可变(00 篇站 5,路由公式 hash(_routing) % N)
- [ ] 知道副本与主分片不在同一节点(00 篇站 6)

### Why——单机跑得好好的,为什么要集群

**徒弟**:我单节点 ES 也能建索引、能查,线上为什么要上集群?集群不就是"多买几台机器"吗?

**老陈**:单机有三个死法,任何一个都能要命。集群不是"加机器",是**解决这三个死法**:

| 单机死法 | 具体表现 | 生产后果 |
| ---- | ---- | ---- |
| 容量天花板 | 磁盘、内存、CPU 单机上界;索引增长速度超过预期 | 索引写不进、查询 OOM |
| 单点 | 机器断电/磁盘坏/进程挂,整个服务全没 | 业务直接不可用 |
| 运维窗口 | 升级、重启、扩磁盘都要停机 | 每次运维都是事故窗口 |

**为什么"多买几台机器"解决不了?** 如果只是把数据散在几台机器上、各管各的,查询时要扫所有机器、写入要决定去哪台、挂了还要人工切——这些恰恰是"分布式"最难的部分。集群的真正价值是:**把"多台机器"包装成一个逻辑整体,故障切换由系统自己做**。

### What——朴素方案为什么都死

**直觉方案 1:双机主备(备机冷等)**。备机浪费一半硬件,而且"主挂了备顶上"需要人工/脚本操作,切换时间以分钟计,切换本身还容易出二次事故。

**直觉方案 2:双机互备(两边都读写,互相同步)**。听起来更好,但分布式里最危险的问题出现了:**网络抖动时,两边都可能认为自己才是"主"**——这就是脑裂(Level 4 打穿)。互备方案在"一致性"上没有任何保证,数据可能两边各写一半。

**直觉方案 3:加个负载均衡,请求轮流发**。解决不了数据分布问题:查询还是要全量扫。

**三个死法 → 三个集群机制**(本文每层都在回应这张图):

```text
单机死法          集群机制                       本文落点
─────────        ──────────────                ──────────
容量天花板  ──►  分片打散:hash 路由把数据        Level 2
                 切到 N 个主分片,N 个节点
单点故障    ──►  副本接管:主挂了,副本秒级        Level 5
                 晋升,业务不中断
运维窗口    ──►  滚动运维:节点逐个下线重启,      Level 6
                 集群照常读写
```

**最终设计**:ES 的做法是**三层解耦**——

```text
路由层:  每个文档 hash(_routing) % N 决定主分片(写入落点确定)
分配层:  master 决定每个分片落在哪个节点(物理摆放)
复制层:  主分片写,副本分片补(故障接管 + 读扩展)
```

单机时代的"数据在哪"只有一个答案;集群时代,"数据在哪"变成三层决策,每一层一个机制。这是本文的主线。

### How——3 节点集群怎么建起来的

**8.x 的启动方式**(ES 8.15.3 本机实验):

```text
单节点教学: discovery.type=single-node(自举,不选举)
真实集群:   discovery.seed_hosts=节点列表(互相发现)
            cluster.initial_master_nodes=n1,n2,n3(首次 bootstrap 的投票者)
```

首次 bootstrap 时,initial_master_nodes 的节点组成**初始投票配置(VotingConfiguration)**——这是 quorum 的起点(Level 4 的关键)。

**本实验环境**(3 节点,各 512m 堆,VM 4GiB):

```text
n1 | n2 | n3
cluster.name=es-ha-lab,全部 master-eligible + data + ingest + coordinating
```

启动后(实测日志):n2 当选首个 master,`elected-as-master ([2] nodes joined in term 1)`,cluster state version 从 1 开始递增。

### Transfer

1. "把多台机器包装成一个逻辑整体"是所有分布式系统的第一课:数据库分库分表中间件、Kafka 集群、Redis Cluster,同一个问题。
2. "三层解耦"(路由/分配/复制)可迁移:先想"数据落点怎么定",再想"物理怎么摆",最后想"挂了怎么办"——顺序不能反。

### Level Ending

🔴 口诀:单机三死法,集群三层解。

**留下的账**:集群有了,文档进来,**具体落哪台机器?副本怎么跟?**——Level 2 打穿数据分布。

## Level 2:数据怎么分布——路由、分片分配与副本复制

### 前置知识关卡

- [ ] 知道 hash(_routing) % N 路由公式(00 篇站 5)
- [ ] 知道副本与主分片不在同一节点(00 篇站 6)
- [ ] 通过 Level 1

### Why——Doc D 该去哪台机器

**徒弟**:一个文档进来,怎么知道放哪台机器?随机放不行吗?

**老陈**:随机放是"均匀但无意义":查询不知道文档在哪,只能全扫。**因为要"写入确定落点 + 查询确定范围",所以引入路由**:文档 → 主分片 → 节点,两步映射:

```text
① 文档 → 主分片:hash(_routing) % 主分片数    (00 篇已打:默认 _routing 由 _id 提供)
② 主分片 → 节点:master 的分片分配器决定        (本 Level 主角)
```

第①步在 00 篇打穿过(为什么主分片数创建后不可变)。第②步才是集群的新问题:**分片是逻辑单元,放到哪台机器、副本放哪台,必须满足约束**。

### What——分片分配的三条约束

**因为分片必须"摆得合理",所以引入分配约束**(ES 8.x 分片分配器,官方契约 + 本机观察):

```text
① 容错约束:主分片与它的副本必须在不同节点
   (同一节点挂了,主副本一起没,副本白做)
② 资源约束:节点磁盘水位(cluster.routing.allocation.disk.watermark)
   低水位以上才接受新分片
③ 均衡目标:节点间资源负载尽量均衡(分配器持续再平衡;分片数量只是因素之一)
```

> **Implementation 边界**:ES 8.15 的 desired balance 还会考虑索引分布、磁盘占用和写入负载;上面的"分片数量均衡"只是教学入口,不能直接当成分配器的完整评分函数。

**实测现场**(实验 004,2 主 1 副本):

```text
ha-orders 0 p STARTED n1     ha-orders 0 r STARTED n3
ha-orders 1 p STARTED n2     ha-orders 1 r STARTED n3
```

主分片落在 n1/n2,副本都在 n3——约束①得到满足(主副本不同节点)。

### What——副本复制与写入确认

**因为主分片可能消失,所以副本要"跟上"主分片**。复制模型的真实语义(8.15.3 源码锚点,禁止理解成"主分片成功后副本异步补"):

```text
写入请求 → 协调节点
   → checkActiveShardCount()        # wait_for_active_shards 只在这里起作用(写入开始前)
   → 主分片写入 + translog fsync
   → 向 in-sync set 内所有副本转发本次 op
       ├── 副本成功响应 → 计数 -1
       └── 副本失败(失联/超时)→ 请求 master 将该副本移出 in-sync set
            → 等待 cluster state 变更完成 → 计数 -1
   → 所有计数归零 → 才返回"成功"
```

**关键概念:in-sync copies(in-sync set)**。这是比"活跃副本"更严格的概念(官方契约):**in-sync copies 是被保证处理过所有已确认 index/delete 操作的 shard copies**。写入 ACK 有两个前置:

```text
① 失败副本必须先被移出 in-sync set(master 更新 cluster state 确认完成)
   → "某副本没拿到本次写入" ≠ "已确认写入会丢"
   → 因为该副本在 ACK 前已经不再是 in-sync copy,未来没有资格晋升为主
② 所有仍在 in-sync set 内的副本都处理了本次 op
   → 已确认写入 = 被所有 in-sync copies 处理过
```

**ACK 决定树(本 Level 核心图)**:

```text
                 写入成功 ACK
                      │
          ┌───────────┴───────────┐
          ↓                       ↓
   replication invariant     translog durability
   哪些 copy 可以晋升         ACK 前是否持久化
          │                       │
   in-sync copies          REQUEST / ASYNC
```

两层共同决定"ACK 到底意味着什么":

- **复制层(in-sync copies)**:决定"哪些副本有资格晋升主分片"。被 ack 的写入,所有 in-sync copies 都处理过;失败副本在 ack 前已移出 in-sync set。
- **持久化层(translog durability)**:决定"ACK 前是否 fsync"——REQUEST 模式下,primary 和**每个已分配 replica** 的 translog 都 fsync/commit 后才报告成功(01 篇的单机"持久化点"在集群里是"primary + 副本"的完整链条)。

**关键参数 `wait_for_active_shards`(默认 1)**:决定**写入开始前**至少需要几个分片副本处于活跃状态;默认 1 = 主分片活跃即可开始写,**不保证**所有副本在线。实验 004"副本节点 n3 挂了,写入照常 `result: created`"的真相是:**该副本不可用,请求 master 移出 in-sync set 后放行**——不是"复制本来就是异步的"。

**代价与 Trade-off**:

```text
wait_for_active_shards=1   写入开始前只要主分片活跃即可;
                           写入中失败副本被移出 in-sync set 后 ack
                           → in-sync set 可能收缩到只剩 primary
wait_for_active_shards=all 写入开始前要求所有配置的副本活跃;
                            写入开始后副本仍可能失败;
                            失败副本移出 in-sync set 后请求仍可能 ACK
```

### How——一次写入的完整旅程(实验 004 前段)

**节点级写入路径**(索引 ha-orders,主 0 在 n1、主 1 在 n2、副本都在 n3;本例文档路由到主分片 1):

```text
  Client(bulk API)
       │
       ▼
  ┌────────────────┐
  │ 协调节点 n1     │   ① hash(_id) % 2 → 主分片 1(路由层)
  │                │   ② 查 cluster state → 主分片 1 在 n2(分配层)
  └───────┬────────┘
          │ 转发写入请求
          ▼
  ┌────────────────┐           ┌────────────────┐
  │ n2:主分片 1     │─────────►│ n3:副本 1       │
  │ ③ 写入+fsync   │  复制 op  │ ④ 写入+fsync   │
  │ (REQUEST)      │           │ (REQUEST)      │
  └───────┬────────┘           └───────┬────────┘
          │ ◄──────── 成功响应 ────────┘
          ▼
      计数归零 → ACK → 协调节点 → 客户端(created)
```

**实验 004 的完整旅程**(kill 副本节点 n3):

```text
① 建索引 ha-orders:2 主分片 1 副本
② 写 2000 条 bulk:errors: False
③ 确认分布:主 0 在 n1、主 1 在 n2,副本都在 n3
④ kill 副本节点 n3:
   → 3s 内集群 yellow(unassigned: 2)   ← 主分片不受影响
   → 写入照常(created)、查询照常(2001 条)
   → 真相:副本 n3 不可用,请求 master 移出 in-sync set 后才放行(不是"复制本来就异步")
⑤ 重启 n3:
   → ~12s 后 green,副本复用本地数据恢复
```

**核心认知**:副本故障是"黄色预警"——集群还能服务,但冗余度下降;此时再挂一个节点,才有真正的主分片丢失(实验 005 现场)。

### Transfer

1. "in-sync set 维护"是 ES 复制模型与 MySQL/Redis 主从(真异步补)的本质差别:ES 宁可等可用副本、把失败副本移出 in-sync set,也不容忍"主确认了、副本根本没收到"的常态;在"已 ACK + REQUEST + 单节点/单磁盘故障"模型下,典型丢失风险才是"in-sync set 收缩到唯一 copy + 数据损坏"。对比参照:Kafka 的 ISR(不可用副本降级出 ISR,与 in-sync set 同思路)、MySQL 半同步(等一个副本 ack)。
2. 路由+分配的两步解耦:写入路径(业务侧)只关心"文档到分片",运维侧才关心"分片到机器"——职责分离让扩容时业务无感(05 篇 alias 配合)。

### Level Ending

🔴 口诀:路由定分片,分配定节点,副本同步等,失败副本移出 set 后 ACK。

**留下的账**:副本节点挂了,系统**怎么知道**它挂了?——Level 3 打穿故障检测。

## Level 3:故障检测——谁能发现节点挂了

### 前置知识关卡

- [ ] 知道主写副本补的复制模型(Level 2)
- [ ] 知道 delayed timeout 这个词的存在(01 篇 Level 5 预告)

### Why——"挂了"为什么不能直接观测

**徒弟**:节点挂了,ping 不通就发现了,这有什么好讲的?

**老陈**:分布式里没有"ping 不通"这种直接观测。你看到的只有:**连接超时、TCP 断开、心跳无响应**——这些都是"症状",不是"判决"。真正的难题是:

```text
节点 A 不响应了,可能是因为:
  ① 真的挂了(进程死/机器断电)
  ② 网络抖动(丢包/延迟高,节点其实活着)
  ③ 它太忙(GC 停顿几十秒,来不及响应)

判"挂"早了 → 误杀健康节点(它回来时数据可能已经搬家)
判"挂"晚了 → 故障窗口变长(用户一直打到死节点上)
```

**因为误判有代价,所以"检测"与"决策"必须分离**:检测只负责"发现症状并上报",决策(是否重新分配、是否重选)由 master 基于更多信息做。

### What——8.x 的两级检测

> ⚠️ **时间免责声明**:以下 1s / 3s / 6s 均为本实验环境观测值(docker 断链/容器停),**不是 Elasticsearch 的协议级 SLA**。实际时间受 TCP 状态、transport 连接、GC、网络、任务调度与集群负载影响,生产以监控实测为准。

ES 8.x(transport 层 + 协调层)的检测分两个方向(本机日志证据):

> 这是本文的教学分层,不是所有检测器的完整清单。ES 协调层还涉及双向 fault detection、leader check、lag/health 检查与 pre-voting;具体间隔和触发条件以对应版本源码/监控实测为准。

```text
① 连接层检测(最快):
   transport 连接断开 → 立即感知
   实验 005 现场(14:05:00):
   "transport connection to [n1] closed by remote"
   "Cluster health status changed from [GREEN] to [YELLOW]
    (reason: {n1} disconnected)"
   ← 从 kill 到感知,1 秒内(docker stop 直接断 TCP)

② 协调层检测(选举相关):
   master 对 follower 的心跳检测、follower 对 master 的检测
   实验 006 现场:隔离 master 后 3s 内健康分区开始重选
```

**关键区分:检测速度 ≠ 决策速度**。检测 1 秒就完成了,但"要不要重分配副本"是另一回事——那是 delayed timeout 的 1 分钟(Level 5 打穿)。**"感知快"与"行动快"是两件事**,混在一起是生产事故的常见来源。

### How——实验 006 的检测现场

**检测方向图**(谁发现谁):

```text
实验 005:kill 数据节点 n1                       实验 006:隔离 master n2

  n1 ────────✗────────► n2(master)              n2 ────────✗────────► n1,n3
  (进程消失)    断链      │                      (被隔离)    断链      │
                          ▼                                                ▼
               YELLOW(n1 disconnected)                          master_not_discovered
               ← 检测:1s                               → 健康分区开始重选(3s 内)
                          │                                          │
                          ▼                                          ▼
               reroute in 59.8s                        n3 当选新 master(6s)
               ← 决策:1m(Level 5)
```

```text
22:12:01 docker network disconnect es-net es-n2(隔离 master)
T+3s:健康分区(n1)视角:node_disconnected_exception
      → master_not_discovered(正在重选,临时 503)
T+6s:新 master 选出(n3)
```

隔离节点(n2)自己的视角(日志):

```text
"master not discovered or elected yet, an election requires at least 2 nodes
 with ids from [n1, n2, n3], have only discovered non-quorum [{n2}...]"
```

检测与决策在这里分离得很干净:n2 检测到"我连不上别人了"(症状),但**决策权**在 quorum——它凑不够票,就只能干等(Level 4 展开)。

### Transfer

1. "症状 vs 判决"分离是分布式可观测性的核心:监控系统报警是症状,值班同学决定"是否重启/降级"是判决——把判决自动化才是分布式系统该做的事。
2. 心跳/超时判活是通用机制:Kubernetes 的 livenessProbe、ZooKeeper 的 session timeout,同一思想,不同参数。

### Level Ending

🔴 口诀:检测看连接,决策看 quorum。

**留下的账**:检测完了,谁有资格当新 master?两个分区会不会各选一个?——Level 4 打穿选举与 quorum。

<a id="level-4"></a>

## Level 4:选举与 quorum——谁能当 master、脑裂怎么防

### 前置知识关卡

- [ ] 知道 8.x 的初始投票配置(Level 1)
- [ ] 通过 Level 3(检测与决策分离)

### Why——master 挂了,谁来接管决策

**徒弟**:master 挂了,剩下的人里随便选一个当 master 不就行了?

**老陈**:"随便选"在分布式里是事故的开端。考虑这个场景:3 节点集群,网络一劈两半(1 个节点在左,2 个在右)。左边节点说"我是 master",右边也选出一个"我是 master"——**两个 master 同时存在,这就是脑裂**。它们会同时接受写入、同时改 cluster state,数据分裂,无法收敛。

**因为要"只允许一个 master",所以引入 quorum(法定人数)**:

```text
quorum = voting configuration 的多数派
3 节点投票配置 → quorum = 2
5 节点投票配置 → quorum = 3
```

> ⚠️ **不要记成"节点数 / 2 + 1"**。实际参与决策的是 **voting configuration**(投票配置),它由 master-eligible 节点组成,但不等于"集群中所有节点数"——data-only 节点、尚未完成配置变更的后续节点都可能在配置之外。本实验的 n1、n2、n3 都在当前投票配置内。

**核心机制**:不是"响应最快的人当 master",而是**只有能凑够 quorum 的分区才有资格参与选举**。但 quorum 只是必要条件,ES 还会检查 voting configuration 的交集以及候选者的 last accepted term/version,防止状态较旧的候选者成为 master。

```text
3 节点集群,网络分区 1+2:

        ┌─────────────── 网络分区 ───────────────┐
        │                                       │
  ┌────────────┐                    ┌───────────┐   ┌───────────┐
  │ n2(master) │    连接断开 ✗✗✗    │    n1     │◄─►│    n3     │
  │   被隔离   │◄──────────────────►│           │   │           │
  └────────────┘                    └───────────┘   └───────────┘
  分区 A:1 票 < quorum 2               分区 B:2 票 ≥ quorum 2
  → 不能选,瘫痪                        → 正常选主,继续服务
   (实测:non-quorum WARN 每 10s)        (实测:n3 当选,写入正常)

  只有拥有 quorum 的分区能继续形成新 master/提交 cluster state;
  少数分区不能形成独立 master → 脑裂被结构性排除
```

**但"分区 B 的 2 票"从哪来?为什么不会各自投自己、1:1 僵死?** 这个问题不能直接套标准 Raft 的 `RequestVote/voted_for` 术语。ES 8.15.3 使用的是 **Raft 风格、但自有实现**:候选节点广播 `StartJoinRequest`,其他节点返回 `Join` vote;每个 voting node 在一个 term 内只贡献一票。

```text
正常路径(教学示意;实验 006 只观测到 n3 最终当选,未记录请求到达顺序):
   n3 失联 n2 → 发起新 term 的 StartJoinRequest
   → n1 接受这个 term,返回 Join(votingNode=n1, candidate=n3)
   → VoteCollection 收到 n3 的本地票 + n1 的 Join vote
   → 2 票 ≥ quorum 2 → n3 当选
   (图中的"本地票"是 Join/VoteCollection 语义,不是 ES 中的 voted_for 字段)

两个候选同时发起呢(各自只收集到 1 票 < quorum 2)?
   本轮选举失败 → ElectionSchedulerFactory 随机调度下一次尝试
   → 线性 backoff + 随机延迟提高下一轮打破对称的概率
   → 1:1 不会直接变成 master,但收敛是 liveness 机制的概率性结果,不是绝对 SLA

ES 7.x+协调层的 pre-voting(当前基线为 8.15.3):
   PreVoteRequest 携带 currentTerm;响应还带 lastAcceptedTerm/version
   → 先用 ElectionStrategy 判断预投票 quorum 和状态新鲜度
   → 通过后才启动真实 Join election,减少无谓选举扰动
```

### What——选举的机制骨架

**VotingConfiguration(投票配置)**:有资格投票的 master-eligible 节点集合。首次由 `cluster.initial_master_nodes` 建立;后续随节点加入/离开自动演进(实测日志:`an election requires at least 2 nodes with ids from [n1, n2, n3]`)。

**票怎么产生(ES 8.15.3 实现;不是标准 Raft 的 API 流程)**。源码锚点:`StartJoinRequest.java`、`Join.java`、`CoordinationState.java`、`StatefulPreVoteCollector.java`、`ElectionSchedulerFactory.java`

```text
① PreVoteCollector:广播 PreVoteRequest,检查 quorum、leader 状态与 lastAcceptedTerm/version
② 真实选举:候选节点广播 StartJoinRequest(candidate,term)
③ 投票节点:接受更高 term 后返回 Join(votingNode,candidate,term,lastAcceptedTerm/version)
④ 候选节点:收集每个 voting node 的一个 Join vote
⑤ 当选条件:多数是必要条件,还要通过 ElectionStrategy 的配置交集与状态新鲜度检查
⑥ 失败重试:ElectionSchedulerFactory 以随机延迟 + backoff 重试,提高 liveness
```

**term(任期)与 cluster state version**:每次**真实的 StartJoin election** 才会使 term +1,pre-voting 不直接推进 term;只有**当前 term 的 master** 才能发布 cluster state。**旧 master 归来后不能凭旧身份继续当主**——它必须接受新 master 的更高版本 state(这是 fencing 的思想,防止"僵尸主"写旧数据)。

```text
选举状态机(机制示意;实验 006 只提供时间与最终 master 证据):

  term=1(n2 在位)                        term=2(n3 在位)
       │                                       ▲
       │ 22:12:01 隔离 n2                       │ 选举完成
       ├─ 健康分区检测失联(3s)                  │
        ├─ PreVote 通过 quorum/状态检查           │
        ├─ n3 发出 StartJoinRequest(term 2)       │
        ├─ n1 返回 Join → VoteCollection 达 quorum │
        └─ n3 发布 cluster state(version +1)─────┘
               ↑ 新 state 内容:分片分配照旧 + n2 标记失联

  n2 孤岛:无法形成 quorum,持续 WARN "non-quorum" → 不能发布新 state
  恢复连接:n2 收到更高 term/version 的 state
          → 自己已过期 → 接受新 state、交出 master 身份(fencing)
```

**只有 2 个 voting members 为什么没有高可用**(关键认知):

```text
2 节点投票配置 → quorum = 2
挂 1 个 → 只剩 1 票 < 2 → 无法继续选主/提交新的 cluster state
3 节点投票配置 → quorum = 2
挂 1 个 → 还剩 2 票 = 2 → 正常服务
```

**"多一台 voting member"在集群语义里不是"多一份备份",是"多一票容错"**。这是神话"两节点互备最稳"的反面——互备(Level 1 的死法 2)在只有两个 voting members 的场景下恰恰是脑裂温床,而 ES 的 quorum 让失去任一 voting member 后**无法继续选主或提交新的 cluster state**。

### How——实验 006 的选举现场

```text
场景:隔离当前 master n2(它是 3 节点投票配置的一员)

健康分区(n1 + n3):
T+3s:  感知 n2 失联(master_not_discovered,选举进行中)
T+6s:  n3 当选新 master
         ← 2 票 = quorum 2,合法选举

隔离分区(n2 独自):
持续 WARN(每 10s):
"an election requires at least 2 nodes ... have only discovered non-quorum [n2]"
         ← 1 票 < quorum 2,永远选不出主

写请求验证:
发给健康分区 → created ✓
发给隔离节点 n2 → 超时无响应 ✗(没有 master 可路由)

恢复连接:
T+3s: master=n3, nodes: 3, green
         ← n2 归队接受新 state,不争当 master

对照组(隔离非 master 节点 n1):
集群无感:master 不变、写入照常、green
```

**对照组的价值**:不是"节点失联"本身危险,而是**"master 角色 + 投票身份"失联才触发选举**。故障影响面由"角色 + 分片位置"决定,不是节点数量。

### Transfer

1. quorum 思想是所有共识系统的地基:Raft 的多数派、etcd 的 quorum、ZooKeeper 的法定人数——"少数服从多数"不是民主,是**防止出现两个权威**。
2. fencing(旧主退役)思想迁移:分布式锁的 lease、Kubernetes 的 leader election,都要回答"旧主归来怎么处理"。

### Level Ending

🔴 口诀:多数定主,防裂靠票。

**留下的账**:新 master 选出来了,**分片数据怎么补全?副本要等 1 分钟才重建,为什么?**——Level 5 打穿分片恢复。

## Level 5:分片恢复——副本晋升与 delayed timeout

### 前置知识关卡

- [ ] 知道检测与决策分离(Level 3)
- [ ] 知道 quorum 语义(Level 4)

### Why——节点挂了,数据怎么补

**徒弟**:节点挂了,副本顶上,然后呢?系统怎么把数据补回完整状态?

**老陈**:分片恢复分三条路径,每条的时间尺度完全不同:

```text
① 副本晋升(毫秒~秒级):主分片所在节点挂了 → 副本立刻转正
② 副本重建(分钟级):缺失的副本被重新分配到别的节点 → 全量复制数据
③ 节点回归(秒级):原节点回来 → 有本地数据的分片直接复用
```

```text
故障响应不是一条线,先分控制面与数据面:

Node failure
   ├─ 控制面故障(master-only / master role)
   │     → 选举新 master → cluster state 继续发布
   │     → 如果没有 shard copy 丢失,allocation health 可能仍为 GREEN
   │
   └─ 数据面故障(shard copy 所在节点)
         → GREEN ──检测──► YELLOW(副本或主分片未分配)
                              │
                    ┌─────────┴─────────┐
                    ▼                   ▼
               主分片丢失             只缺副本
                    │                   │
             in-sync replica       业务继续,等待补冗余
             晋升为 primary              │
             业务恢复                   │
                    └─────────┬─────────┘
                              ▼
                 delayed allocation 到期后
                    回归复用或重新重建
                              ▼
                            GREEN
```

**而"重建副本"之前还有一个隐藏的 1 分钟等待**——delayed timeout,这是本 Level 的主角。

### What——为什么副本不立即重建

**直觉方案:副本丢了立刻在别的节点重建**。问题:节点可能只是**抖动**(重启、GC、网络闪断),几分钟就回来。立即重建 → 数据全量复制一遍 → 节点回来 → 又可能搬回去 → **重建风暴**:IO 被打满,集群反复抖动。

**因为要给"短暂离开的节点"留回归机会,所以引入 delayed timeout**:

```text
index.unassigned.node_left.delayed_timeout = 1m(实测 59.8s/59.9s,ES 8.15.3)
适用场景:node-left 导致的 unassigned 副本分片,延迟 1 分钟才重新分配
→ 1 分钟内回来:复用本地数据,零复制
→ allocation grace period 到期:允许开始重新分配/重建
```

**作用边界(官方契约,别扩大化)**:

```text
✓ 延迟的是:丢失副本分片的重新分配(冗余恢复)
✗ 不影响:replica → primary 的晋升(业务恢复不等它)
✗ 不适用:完整集群重启
✓ 提前回来:可复用本地同步数据,无需重建
```

**这是"检测快、行动慢"的完整解释**:检测先报告"失联",allocation grace period 到期后才允许"补冗余"——两个时间尺度各管一件事,且 delayed 只延迟"补冗余",不延迟"业务恢复"。它不是故障检测器,也不证明节点一定已经永久故障。

### How——实验 005 的完整时间线(本机实测)

**kill 前后的分片分布**(索引 ha-orders,2 主 1 副本,主分片用 ◉、副本用 ○):

```text
kill 前(22:04:59)                  恢复稳定后(22:09:30)

  ┌──────────┐  ┌──────────┐  ┌──────────┐      ┌──────────┐  ┌──────────┐  ┌──────────┐
  │   n1     │  │ n2(master)│ │   n3     │      │   n1     │  │ n2(master)│ │   n3     │
  │  ◉ 主 0  │  │  ◉ 主 1  │ │  ○ 副本 0 │      │  ○ 副本 1 │  │  ◉ 主 1  │ │  ◉ 主 0  │

  └──────────┘  └──────────┘  └──────────┘      └──────────┘  └──────────┘  └──────────┘
```

### What——RPO 与 RTO:高可用的两个数字

```text
RPO(Recovery Point Objective):最多丢多少数据
RTO(Recovery Time Objective):多久恢复
```

**ES 的实际边界(机制推导,非官方 benchmark)**。先拆开两个时间尺度——**delayed allocation 不影响 replica → primary 晋升**(官方契约),所以"业务恢复"与"冗余恢复"是两件事:

```text
业务 RTO:故障检测 → master 决策 → primary promotion → 业务恢复
         (本实验:检测 ~1s,晋升 ~3s 轮询粒度;教学环境量级,生产必须实测)

冗余恢复时间:故障检测 → delayed timeout(1m)→ replica recovery → GREEN
         (分钟级,取决于数据量与 IO;业务早已恢复,这是"补冗余"的账)
```

**RPO 的正确推导(in-sync copies 机制)**。关键不是"副本有没有拿到",而是"**哪些 copy 仍然属于 in-sync set**"。以下先限定故障模型:**已 ACK 的写入、`durability=REQUEST`、单个 shard、单节点/单磁盘故障**;跨故障域、ASYNC、未 ACK 但已被读到的写入另行处理。

```text
① 写入 ACK 的前置(官方契约):
   - 失败副本在 ACK 前被移出 in-sync set(master 更新 cluster state 确认)
   - 仍在 in-sync set 内的副本都处理了本次 op
   → "某副本没收到本次写入" ≠ "已确认写入会从它恢复而丢失"
   → 该副本 ACK 前已失去晋升资格

② 在上述故障模型下的典型丢失场景:
   primary 成为唯一 in-sync copy(其余副本都被移出)
   + 该唯一 copy 发生数据级故障(磁盘损坏/数据目录丢失)
   → 无 in-sync 副本可晋升,只能靠 stale 副本/快照
   → 此时"primary 成为唯一 in-sync copy 之后"的已确认写入丢失
   (注意:primary 单纯宕机不在此列——数据还在,可 recovery;丢失发生在"数据物理损坏")
```

**结论:默认配置下 RPO ≠ 0,但丢失窗口不是"复制异步"**。在"已 ACK + REQUEST + 单节点/单磁盘故障"模型里,窗口的完整打开条件有两个且缺一不可:

```text
① in-sync set 收缩到只剩 primary(副本失联被移出,写入照常 ack)
② 该 primary 数据物理损坏(磁盘坏,recovery 也无数据可恢复)
```

"green = 不丢数据"仍是神话 6:green 只保证分片齐全。实验 006 的 7777 案例:发给失联节点的写入直接失败(没被确认)——那是失败写入,不是本模型的 ACK 丢失;但官方复制模型还提示另一类边界:隔离 primary 可能先让未 ACK 写入被并发读到,之后该写入被拒绝或丢弃。

**换故障模型,结论也要换**:

```text
ASYNC translog:
  最近一次 fsync/commit 之后的 ACK 写入可能在进程/硬件故障后丢失

同一宿主机/AZ/机房故障:
  所有 in-sync copies 可能同时消失 → 需要 snapshot/CCR/异地副本定义 RPO
  snapshot 的 RPO 受最后一次完成快照时间影响,CCR 的 RPO 受复制 lag 影响

隔离 primary:
  未 ACK 写入可能已被读到(dirty read),不能把"客户端没收到 ACK"等同于"业务从未看到"
```

**"RPO=0 需要什么"的正确回答**(决策,05/06 篇展开):

```text
没有配置能让 RPO 严格为 0(磁盘损坏/机房级故障永远存在)。
要"接近 0"必须全链路覆盖:
- in-sync copies:按预期故障数与故障域放置副本,让故障后仍尽量保留至少两个独立 in-sync copies;不能防住多副本/关联故障
- translog durability=REQUEST:primary + 副本都 fsync 后才 ACK
- wait_for_active_shards=all:写入开始前要求所有副本活跃
  (作用:降低"写入开始时副本缺失"的可用性窗口,不是"提交到所有副本才成功"的保证,
   它 ≠ RPO 0)
- 快照/异地灾备:物理损坏、误删、机房级故障的最后防线
```

**wait_for_active_shards=all 的真实代价**:副本在**写入开始前**不可用时,写入阻塞/失败;但开始后副本仍可能失败并被移出 in-sync set——它只能把风险前移为可用性代价,不能替代复制不变量或灾备。

### Transfer

1. "延迟补偿"思想:分布式里"立即补偿"常常是最差策略(抖动引发补偿风暴)。Kubernetes 的 pod 终止宽限期、AWS 的实例替换延迟,同一思想:给"短暂异常"留窗口。
2. "检测快、决策慢"的双时间尺度:网络超时重试(快)vs 故障转移判定(慢),是 SRE 调参的核心心智。

## Level 6:高可用全景——green 到底承诺了什么

### 前置知识关卡

- [ ] 通过 Level 1-5
- [ ] 知道 01 篇的 translog durability(REQUEST/ASYNC)

### Why——green 是一个"健康灯",不是"安全承诺"

**徒弟**:集群 green 了,数据就安全了吧?神话 5/6 不是说"副本越多越安全""green 就是高可用"吗?

**老陈**:green 是一盏**状态灯**,它只回答一个问题:"所有分片都分配到位了吗?"——仅此而已。它**不承诺**数据安全,因为数据安全由一组完全不同的机制决定。先把 green 的定义钉死(官方契约):

```text
green  = 所有主分片 + 所有副本分片都已分配
yellow = 所有主分片已分配,至少一个副本未分配
red    = 至少一个主分片未分配(该分片数据不可用)
```

**关键**:yellow 是"还能服务但有风险",red 是"部分数据真不可用了"。实验 005 的现场:n1 挂掉、副本晋升,3 秒轮询内全程 yellow(未观察到 red,窗口 <3s 或同批次晋升,需更细粒度验证)——这就是副本的意义。

> ⚠️ **green 只反映 allocation health**:它不等价于 RPO=0、灾备完成或业务绝对安全。green 与"数据安全"之间隔着 in-sync copies、translog durability、快照三层(下文三层模型)。

### What——"安全"由什么决定(三层模型)

```text
第 1 层:写入确认(replication invariant:in-sync copies)
         被 ack 的写入 = 所有 in-sync copies 都处理过
         失败副本在 ACK 前被移出 in-sync set
         → 丢失窗口在"in-sync set 收缩到唯一 copy + 数据损坏"组合里
第 2 层:持久化(translog durability)
         REQUEST:primary + 每个已分配 replica 的 translog 都 fsync 后才 ACK(官方契约)
         ASYNC:5s 间隔 → 崩溃可能丢 5s(01 篇 Level 5)
第 3 层:灾备(snapshot / 异地)
         集群内冗余救不了机房级故障
```

**三个对子(00 篇站 6 已立,这里收网)**:

```text
高可用 ≠ 数据绝对不丢   副本让集群"还能服务",丢失窗口在"唯一 in-sync copy + 数据损坏"
数据冗余 ≠ 灾难恢复     副本在集群内,机房挂了冗余一起没
本地恢复 ≠ 异地灾备     translog 恢复救本地,跨机房靠 snapshot/CCR
```

### What——神话 4/5/6 收网

| 神话 | 打破 | 依据 |
| ---- | ---- | ---- |
| 4:分片越多性能越好 | 路由固定后分片数不可变;每分片是独立 Lucene 实例,分片越多,每查询扇出越多、merge/GC 开销越大 | 00 篇站 5 + 05/06 篇展开 |
| 5:副本越多数据越安全 | 副本解决可用性(冗余/接管/读扩展),不自动解决故障域丢失;在独立节点/故障域前提下,单节点模型的丢失条件是 in-sync set 收缩到唯一 copy + 该 copy 数据损坏 | 官方契约(in-sync copies 语义)+ ES 8.15.3 源码锚点;实验 005:3 秒轮询内未见 red |
| 6:green = 高可用/不丢数据 | green 只承诺"分片齐全";数据安全看三层模型 | 本实验:delayed 59.8s 期间集群保持 yellow(副本未分配);到期重建完成才 green——green 不承诺"数据不丢" |

**副本数的真实逻辑**:副本是"可用性预算",不是"安全等级"。在**副本分布于独立节点/故障域、剩余节点有容量、控制面仍可形成 quorum**的前提下,1 副本可以承受 1 个节点故障,2 副本可以承受 2 个节点故障。若副本都在同一宿主机或 AZ,节点级容错不等于宿主机/AZ 级容错。每加一个副本,写入成本与存储成本同步涨——**副本数是"容错预算 × 成本"的权衡,不是越多越好**(决策卡 2)。

### How——把本系列实验串成一张故障响应总表

```text
节点故障 F 的一生(实验 004/005/006 汇总,按故障面分支):

数据面故障(实验 005:主分片 0 在 n1):
  T+1s    transport 断链检测 → YELLOW
  T+3s    in-sync replica 晋升 → 业务恢复(不等 delayed)
  T+60s   delayed allocation 到期 → 副本重建开始
  T+60s+  recovery 完成(数据量/IO 决定) → GREEN

控制面故障(实验 006:master n2 被隔离):
  T+3~6s  健康分区完成选举 → 新 master 继续发布 cluster state
          allocation health 是否变化,取决于是否同时丢失 shard copy

节点回归:~5~12s 复用本地数据,集群再平衡
数据面观测:故障期间写入落在活跃主分片且副本可服务,未观察到丢失;
           发给失联节点的请求可能等待或失败(实验 006 的 7777)
通用结论:默认配置下 RPO ≠ 0,具体丢失条件必须绑定故障模型,
           不能从一次容器实验推广到 host/AZ/机房故障
```

```text
故障响应全景(机制图):
Node failure
   ↓

 ┌─┴────────────────────┐

```

### What——高可用决策卡(本章落点)

| 决策 | 推荐 | 原因 |
| ---- | ---- | ---- |
| 副本数 | 按 RPO 与故障域计算;核心数据通常至少 1-2 | 只有副本分布在独立节点/host/AZ,且剩余节点有容量与 quorum 时,副本才转化为对应故障容错;成本线性涨 |
| master-eligible 节点数 | 3 或 5(奇数) | quorum = 投票配置多数派,奇数最大化容错(3 容忍 1,4 与 3 相同容错但多一台成本) |
| 集群规模 | 需要高可用的 master-eligible 集群:≥3 个 voting members | 只有 2 个 voting members 时,任意一个故障都无法继续 quorum;voting-only/dedicated master 可改变拓扑,但必须核对当前 voting configuration |
| 故障域 | 配置 shard allocation awareness/forced awareness;多节点同 host 时评估 `same_shard.host`;跨 host/AZ 放置 | 节点副本不能替代跨故障域灾备;当前 Colima 实验只验证容器/进程级故障 |
| wait_for_active_shards | 默认 1;核心数据 all | 1 = 高吞吐,in-sync set 可能收缩;all = 写入开始前要求全部副本活跃,写入中仍可能移出失败副本,可用性换前置保障 |
| delayed_timeout | 默认 1m;节点频繁抖动可调大 | 只延迟副本冗余恢复(node-left 场景),不影响 primary 晋升与业务恢复;调大也会延长 yellow |
| 角色与入口 | 生产分离 dedicated master/data,客户端使用多入口/LB | 降低数据面负载影响控制面;避免单一入口成为新的单点 |
| 灾备与恢复 | snapshot/CCR + 恢复演练;预留 recovery 带宽与磁盘容量 | 集群内副本救不了机房故障;恢复速度受 IO、网络、并发恢复和剩余容量约束 |

### Transfer

1. "健康灯 ≠ 安全承诺"是通用的:MySQL 的主从状态、Kafka 的 ISR、Redis 的 cluster status——所有分布式系统都有"状态指标"与"真实安全边界"的落差,读文档时先问"它承诺了什么,没承诺什么"。
2. 三层安全模型(确认/持久化/灾备)是任何存储系统的安全审计清单:先查写入确认方式,再查持久化策略,最后查跨机房手段——三层都覆盖才算有答案。

<a id="pitfalls"></a>

# ⚠️ 坑与细节

1. **"节点挂了集群就 red"是错的**:主分片有副本时,3 秒轮询未观察到 red(副本晋升很快,需更细粒度验证);red 的精确定义是至少一个 primary shard 当前未分配,不等于数据已经永久物理丢失。
2. **"副本越多数据越安全"是错的**:副本是可用性预算,防的是"in-sync set 收缩 + 数据损坏"组合;丢失窗口不来自"复制异步"(写入等 in-sync copies,失败副本先移出 set 再 ACK)。
3. **"master 没了集群只读不写"是错的**:能否继续提交集群状态和写入取决于 quorum;能选主就恢复,选不出时需要新 cluster state 的写操作会受阻,读行为还受 `cluster.no_master_block` 与已有 state 影响(实验 006)。
4. **"副本重建越快越好"是错的**:立即重建 = 节点抖动时重建风暴;delayed timeout 是防风暴的延迟。
5. **只有 2 个 voting members 的集群看起来有冗余,实际无法容忍任一 voting member 故障**:quorum=2,挂 1 个无法继续决策;不要把"两个数据节点"与"两个 voting members"混为一谈。
6. **发给失联节点的写请求不一定立即失败**:可能长时间等待、连接失败或返回超时;客户端/网关必须配置 timeout、幂等重试与请求落点故障处理(实验 006 的 7777)。
7. **故障检测快 ≠ 恢复快**:检测 1s、重建 1m+,时间尺度不同,别用"感知到了"推"恢复了"。

# 📚 版本勘误表

| 旧认知 | 正确表述 | 依据 |
| ---- | ---- | ---- |
| 2 节点互备最稳 | 只有 2 个 voting members 时 quorum=2,挂 1 个无法继续决策;互备不等于高可用 | 官方 voting configuration 文档 + 实验 006 |
| master 失联=集群只读 | 能否提交新 cluster state/写入取决于 quorum;无 master 时读行为还受已有 state 与 `cluster.no_master_block` 影响 | 实验 006 + 集群协调文档 |

<a id="decisions"></a>

# 🏆 生产决策卡

| # | 决策 | Decision | Reason | Trade-off | 验证 |
| -- | ---- | ---- | ---- | ---- | ---- |
| 1 | 集群规模 | ≥3 个 voting members;master-eligible 通常取 3 或 5 | quorum 容错最大化 | 成本 vs 容错 | 实验 006 + voting config 文档 |
| 2 | 副本数 | 按 RPO 与独立故障域计算,核心数据通常至少 1-2 | 可用性预算与恢复副本 | 存储/写入成本线性涨 | 实验 004/005 + 生产演练 |
| 3 | wait_for_active_shards | 默认 1;核心数据 all | 只决定写入开始前的最低活跃副本数,不决定写入中等待;真正决定"哪些副本有资格晋升"的是 in-sync copies | 写延迟/可用性(all 时前置副本不足会等待或失败) | 官方契约 + ES 8.15.3 源码锚点 |
| 4 | delayed_timeout | 默认 1m,抖动频繁调大 | 防重建风暴;只延迟冗余恢复 | yellow 持续时间更长 | 实验 005 |
| 5 | 故障预案 | 先查"故障面+角色+分片位置",再谈恢复 | 影响面由控制面/数据面/故障域共同决定 | 预案复杂度 | 实验 006 对照组 |
| 6 | 故障域 | allocation awareness/forced awareness + 跨 host/AZ;同 host 多节点时评估 `same_shard.host` | 节点副本不等于宿主机/AZ 灾备 | 部署与运维成本 | 生产演练 |
| 7 | 灾备/恢复 | snapshot/CCR + 恢复演练,预留 recovery 容量 | 集群内副本救不了机房故障 | 备份存储与恢复带宽 | 生产演练 |
| 8 | 角色与入口 | 生产分离 dedicated master/data,客户端使用多入口/LB | 降低数据面负载影响控制面;避免单一入口成为新的单点 | 节点与网络成本 | 生产架构评审 |

### How——生产故障排查入口

```text
先判断:控制面(master/voting)还是数据面(shard copy)?
   ├─ 控制面 → _cat/master + voting configuration + master 日志
   └─ 数据面 → _cluster/health + _cat/shards + allocation/explain
再判断:节点故障域、in-sync copy、恢复容量、snapshot 是否可用
```

```http
# 1. 集群与分片健康
GET /_cluster/health?level=shards
GET /_cat/shards/ha-orders?v
GET /_cat/nodes?v

# 2. 分片为什么没有分配
POST /_cluster/allocation/explain
{
  "index": "ha-orders",
  "shard": 0,
  "primary": false
}

# 3. 当前 master 与 voting configuration
GET /_cat/master?v
GET /_cluster/state?filter_path=metadata.cluster_coordination.last_committed_config

# 4. 恢复是否正在消耗容量/IO
GET /_cat/recovery/ha-orders?v
GET /_cluster/pending_tasks?v
```

这些 API 只能告诉你当前状态,不能替代 snapshot 恢复演练、跨 host/AZ 故障演练或客户端幂等重试验证。

<a id="cross-language"></a>

# 🌍 跨语言视角

| 系统 | 复制模型 | 确认语义 | 与 ES 的对照 |
| ---- | ---- | ---- | ---- |
| MySQL 主从 | 异步/半同步 | 异步与半同步的 ACK/持久化点不同 | 只能类比"确认强度",不能等同 `wait_for_active_shards` |
| Kafka | ISR 副本集 | `acks` 与 `min.insync.replicas` 共同决定确认边界 | ISR 与 in-sync set 可类比;`acks=all` 不等于 ES 的写入前 active-shard 检查 |
| Redis Cluster | 异步主从 | 无确认 | 主挂丢失窗口更大,靠持久化与哨兵 |
| ZooKeeper | 同步多数派 | 多数确认才提交 | 与 ES 的 quorum 同源(但 ES 的数据复制更宽松) |
| etcd/Raft | 同步多数派 | 多数确认才提交 | 严格多数派;ES 的选举用 quorum,数据复制不强一致 |
| **ES 8.15.3** | **in-sync set 维护** | **写入开始前 checkActiveShardCount;写入中等待 in-sync copies 完成,失败副本移出 in-sync set 后 ACK** | **与 MySQL/Redis 的"真异步补"不同:ES 常态是等 in-sync copies,失败副本先移出 set 再 ACK,丢失风险在"set 收缩 + 数据损坏"组合** |

**一个可迁移的方法论**:所有复制型系统都在这条线上取点——

```text
确认策略(写入前门槛 + in-sync ACK) × 副本数量 × 持久化策略
= 可用性 vs 吞吐 vs 成本的三角权衡
```

没有任何配置能让三者全赢;生产上先定"可接受丢失窗口",再反推参数。
