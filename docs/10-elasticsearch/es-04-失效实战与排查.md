<a id="level-1"></a>

## Level 1

一句话认知墙:**"单次快"是错觉——脚本查询的成本随被求值候选规模走,中缀通配的成本随 term 字典规模走;单请求毫秒级差异,乘上并发就是生产事故。**

### 前置知识关卡

* [ ] 01 篇:倒排 = term dictionary + postings,term dictionary 决定词项寻址成本
* [ ] 03 篇:查询走两阶段扇出,协调节点归并
* [ ] 03 篇:Profile 负责定位执行路径

### Why

徒弟:

> 一个 `doc['price'].value >= 50` 的脚本查询,单次 3 毫秒;一个 `*23456*` 通配,单次 10 毫秒。都"不快也不慢",有什么好怕的?

老陈:

> 你掉进了"单次延迟"的陷阱。机制上这是两笔不同的账:
> 脚本查询是**逐候选文档求值**——没有前置过滤时,候选集可能接近全量,成本随被求值的候选规模走,数据涨它就涨;
> 中缀通配是**遍历整个 term dictionary**——先枚举出所有匹配的精确词项再查倒排,成本随词项总数走,与命中多少无关。
> 单次 3ms vs 10ms 在生产里可能看不出差异;但并发规模上升后,前者把 CPU 烧在脚本求值上,后者把 CPU 烧在字典遍历上——烧法不同,墙的位置不同。而这两个墙,都不在"查询本身",在规模。

| 方案 | 解决什么 | 留下什么问题 |
| ---- | ---- | ---- |
| 前缀查询(prefix/wildcard 前缀) | 枚举字典前缀段,成本可控 | 只能命中前缀匹配 |
| 中缀通配(*x*) | 任意位置匹配的便利 | 遍历全部 term dictionary,成本随词项规模(实验 009) |
| 脚本查询 | 任意条件求值 | 逐候选文档执行,成本随被求值规模(实验 009) |

### What

成本模型(机制,非 API):

```
script query:  cost ≈ 被求值的候选文档数 × 单文档求值成本
               —— 与 term 数无关,与候选规模成正比

wildcard 中缀: cost ≈ term dictionary 规模(枚举展开)
               —— 与命中数无关,与词项总数成正比
               profile 实测:MultiTermQueryConstantScoreBlendedWrapper
               展开成多个 BooleanQuery/TermQuery 精确词项再查倒排
```

不变量:**这两类写法的成本都不在"查询逻辑本身",而在它触碰的数据规模。** 单机单请求时规模小,看起来无辜;生产环境数据量级一变,墙立刻出现。

> 📌 最容易被误解的一点:脚本查询"热缓存下不慢"(实验 009 实测 1M docs 下 3-4ms,与 range 相当)——所以"脚本=慢"是错的;"脚本的代价会随被求值候选规模放大"才是对的。判断脚本风险,先问"它会评估多少候选文档、跑多少并发"。

### How

① 脚本查询:协调节点把脚本下发给每个分片

② 每个分片对**候选集中的每个文档**执行脚本(逐文档求值)

③ 中缀通配:先**枚举 term dictionary** 中所有匹配的精确词项

④ 展开后的词项逐个查 postings,再合并候选集

⑤ 并发放大:每多一路请求,上面的成本就多一份

实测锚点(实验 009,es-ha-lab,ES 8.15.3):

```
perf2(1M docs,唯一 term ~949,984,单分片):
  range price>=50         : 稳定 ~5ms        ← 基线
  script doc['price']>=50 : 稳定 ~3-4ms      ← 热缓存下不慢于 range!
  冷启动:range=50ms / script=101ms(约 2 倍)  ← 冷启动才有可见差异

  prefix code-123*(1047 命中):稳定 ~3-4ms
  infix  *23456*(23 命中)   :稳定 ~10-11ms   ← 命中少 45 倍,反而慢 3 倍
  冷启动:prefix=20ms / infix=106ms(约 5.3 倍)

  term 规模 18 万 → 95 万(5.3 倍):
    infix  4-5ms → 10-11ms(约 2.4 倍)        ← 成本随词项规模走
    prefix 2ms   → 3-4ms(约 1.8 倍)

  profile:infix 展开 = MultiTermQueryConstantScoreBlendedWrapper ms=23
           + 多个 BooleanQuery/TermQuery 叶子(精确词项查询)
```

脚本的上下文边界(实验 009,同为 8.15.3):

```
text 字段没有 doc_values:
  doc['title'].value → script_exception("Text fields are not optimised
  for operations that require per-document field data...")
script query 里拿 _source:
  params._source.title → script_exception("cannot access method/field
  [title] from a null def reference")   ← params._source 为 null
```

### Transfer

- "单次快 × 高并发 = 墙"是通用失效模型:任何"常数级单次成本 × 线性规模"的组合,都要在需求阶段算总量,而不是测单次。
- 成本锚点判断法:写查询前先问"成本跟什么走"——跟被求值候选数走(脚本),跟字典规模走(中缀),跟文档数走(全表扫)。锚点不同,优化手段完全不同。
- 本层留下的新账:**查询侧的失控是"慢"——那写侧呢?并发写同一个文档,会不会"错"?**——逼出 Level 2 的并发冲突。

### Level Ending

🔴 口诀:单次快不算快,成本锚点看规模。

<a id="level-2"></a>

## Level 2

一句话认知墙:**ES 没有行锁,并发写靠服务端乐观锁(seq_no + primary_term)兜底;裸 GET→PUT 在并发下实测丢 98%,正确姿势是 if_seq_no + 重试或 update API 的 retry_on_conflict。**

### 前置知识关卡

* [ ] Level 1:请求成本随规模放大
* [ ] 01 篇:写入 = translog + refresh 窗口;更新 = 墓碑 + 新建
* [ ] 02 篇:主分片串行处理写请求(复制模型)

### Why

徒弟:

> 先查出来、改两个字段、再写回去,这不是最自然的更新方式吗?就算两个人同时改,后写的覆盖先写的,顶多丢一次嘛。

老陈:

> "顶多丢一次"在你这里是 98 次。ES 是**无锁并发**:主分片不持有行锁,两个并发 GET→PUT 都基于同一个旧版本,两个都算"成功"写回——后一个把前一个的改动整个覆盖掉。实测 8 线程并发 100 次裸更新,最终只剩 2 次生效。
> 为什么 ES 不做用户可见的行锁?因为分布式系统里的排他锁需要额外协调;ES 的选择是:**写入先执行,用版本条件检测冲突,再让客户端重试**。这就是乐观锁。这里不把具体吞吐差异写成通用数字。

| 方案 | 解决什么 | 留下什么问题 |
| ---- | ---- | ---- |
| 行锁(MySQL 式) | 写写互斥 | 跨节点协调成本,吞吐下降 |
| 无版本直接写 | 简单 | 并发下静默覆盖,丢更新(实测 98%) |
| 乐观锁(seq_no + primary_term) | 冲突可检测 | 冲突要重试;不重试=仍然丢 |

### What

乐观锁的两个版本号(数据结构,官方契约):

```
seq_no         :主分片上的操作序号(单调递增);文档响应中的 seq_no 是该文档最近一次操作的序号
primary_term   :写入发生在哪一届主分片任期内(主分片切换会变)

写请求可带 if_seq_no + if_primary_term:
  服务端比较:当前 (seq_no, primary_term) == 请求条件?
    → 相等:执行写入,版本前进
    → 不等:409 version_conflict_engine_exception,body 不参与比较
```

不变量:**冲突判定只看版本号,不看文档内容。** 谁先写成功,谁的版本号前进;后到的、基于旧版本的请求一定被 409 挡下——前提是你带了版本条件。

> 📌 最容易被误解的一点:409 不是"请求失败"的信号,而是"并发发生了"的信号——它是设计出来的正常事件。真正的错误是**不带版本条件**,那样连 409 都没有,直接静默覆盖。

### How

① 无版本更新:GET 拿到旧文档 → 修改 → PUT

② 并发下两个请求都基于同一旧版本 → 后写覆盖先写 → 静默丢失(无任何报错)

③ 正确姿势 A:GET 拿到 (seq_no, primary_term) → PUT 带 if_seq_no/if_primary_term → 409 则重读重试

④ 正确姿势 B:update API,脚本或 doc 增量更新,retry_on_conflict 自动重试

实测锚点(实验 010,es-ha-lab,ES 8.15.3,conflict-test 1 主分片 0 副本):

```
A 裸 GET→PUT,8 线程并发 N=100(约 3.1s):
   最终 _version=2 → 丢 98/100(98%)     ← 无版本控制的代价

B if_seq_no + 409 重试,N=30/200 次尝试(约 6.4s):
   final=30,lost=0                      ← 本次负载与重试预算下收敛

C update API retry_on_conflict=50,N=100(约 1.7s):
   final=100,lost=0                     ← 最快且零丢失

409 响应原文(过期 seq_no 重放):
  409 {"type":"version_conflict_engine_exception",
    "reason":"[c1]: version conflict, required seqNo [0],
              primary term [1]. current document has seqNo [1]"}
```

### Transfer

- "不锁、校验版本、冲突让客户端重试"是分布式写入的通用范式:数据库 MVCC、Kafka 幂等、对象存储的条件写,全是同一思想——把并发控制从"排他"换成"可检测"。
- 重试是给乐观锁配的零件:不带版本条件的重试=重复覆盖;带版本条件的重试=收敛。**重试的正确性由条件参数决定,不由重试次数决定。**
- 本层留下的新账:**就算写对了,并发再大一点,服务端自己先扛不住了——429 是怎么来的?**——逼出 Level 3。

### Level Ending

🔴 口诀:不锁只校验,409 重试收敛。

<a id="level-3"></a>

## Level 3

一句话认知墙:**429 是 ES 的"队列满即拒":write 线程数固定为核数,队列排满就抛 EsRejectedExecutionException;被拒请求不会被静默持久化,但 Bulk 仍需逐 item 检查——429 是过载信号,且它之前往往先有更早的瓶颈。**

### 前置知识关卡

* [ ] Level 2:写请求带版本条件,冲突 409
* [ ] 02 篇:写请求先到协调节点,再转发到主分片所在节点

### Why

徒弟:

> 服务端扛不住,不是应该让请求排队等一等吗?为什么要直接 429 拒绝我?

老陈:

> "无限排队"是另一种死法:请求带着内存、连接和超时,排队越长,雪崩越深——客户端等不住超时重试,重试又变成新请求,队列被"僵尸请求"灌满,真正的活请求永远进不来。
> 所以 ES 用**有界队列 + 拒绝**:**threads 固定(写池 = 核数),queue 有上限,满了直接拒**。顶层拒绝会把结果返回客户端,但 Bulk API 也可能已经逐 item 处理并出现部分成功;客户端必须按 item 结果决定重试,而不是把所有请求当成全成或全败。

| 方案 | 解决什么 | 留下什么问题 |
| ---- | ---- | ---- |
| 无限队列 | 请求都收下 | 内存被排队请求吃光,雪崩 |
| 有界队列 + 拒绝(ES) | 内存有界、拒绝可见 | 客户端要处理 429 重试 |
| 只拒绝最慢的请求 | 保住吞吐 | 实现复杂,语义不可预期 |

### What

线程池模型(官方契约 + 实测):

```
thread_pool.write:
  threads    = 处理器核数(固定;实测 4 vCPU → threads=4)
  queue_size = 上限(默认 10000;实验调为 16 以便复现)
  满 → 新任务抛 EsRejectedExecutionException → HTTP 429

429 响应原文(实验 010,压测中单发 bulk):
  {"error":{"root_cause":[{"type":"es_rejected_execution_exception",
    "reason":"rejected execution of TimedRunnable{original=...bulk...
      requests[2000], indices[flood-test]...}"}]},"status":429}
```

配置边界(实验 010 实测,8.15.3):

```
thread_pool.write.queue_size 是静态设置:
  PUT _cluster/settings → "not dynamically updateable"(实测报错)
-Des.thread_pool.write.queue_size=16(系统属性)→ 实测不生效,
  queue 冲到 100+ 仍不拒(仍是默认 10000)→ 必须写 elasticsearch.yml
```

不变量:**顶层 429 不应被当成静默成功,但 Bulk 的结果仍需逐 item 判断**——已进入分片的写入仍受 seq_no 乐观锁保护;客户端必须检查 `errors` 与 `items[*].status` 后只重试失败且幂等的 item。

> 📌 最容易被误解的一点:429 不是"ES 坏了",恰恰相反——它是 ES 在**保护自己**。真正危险的是 429 之前的阶段:请求已经进了协调节点、占了连接和解析 CPU,却还没到写队列。**429 是链条的末端信号,不是起点。**

### How

① 协调节点解析 bulk(大 bulk 时这一步本身就吃 CPU/内存)

② 按分片拆成子请求,转发到主分片所在节点的 write 线程池

③ 线程池:threads 在跑,queue 排队;queue 满 → 直接拒绝

④ 顶层拒绝返回 HTTP 429;若请求已进入 Bulk item 处理,则按 `errors` 与 `items[*].status` 处理部分成功

⑤ 负载下降后:queue 排空,active 归零,写入恢复

实测锚点(实验 010,es-ha-lab,ES 8.15.3,flood-test 3 主 0 副,queue_size=16):

```
压测前采样的 thread_pool 曲线(每 4s):
  queue=16/16/16(钉满),active=4/4/4
  rejected: 346 → 836 → 1309 → 1860 → 2446 → 2922(持续增长,不是波动)
压测中单发 bulk → HTTP 429 es_rejected_execution_exception(整批 2000 docs 被拒)
结束后 rejected 累计:n1=24060 / n2=25197 / n3=25765
停止负载后:queue→0,active→0;写入/查询立刻正常
   (某一主分片上的新文档 `_seq_no=2439948`;该值是分片局部操作序号,不能推导 3 分片索引的总成功次数)

前置瓶颈对比(默认 queue=10000,1.5MB 大 bulk):
  单节点 100 并发 → queue 峰值仅 7,rejected=0
  三节点各 250 并发 → queue 波动 5-12,始终打不满
  ← 协调节点解析大 bulk 成为更早瓶颈,写线程池根本没满
  改 2000-doc 小 bulk(~150KB)后 → queue 立刻钉满 16,429 出现
```

### Transfer

- "有界队列 + 拒绝 + 客户端退避"是任何排队系统的生存法则(Java 线程池拒绝策略、网络 TCP 背压、消息队列消费限流同构)。
- 429 的可观测性价值:rejected 计数是一个直接的过载信号,但不是完整容量指标——**要和 queue/active、p99、CPU、磁盘 IO 一起看**。
- 本层留下的新账:**机制都懂了,事故真的来了,现场该按什么顺序看?**——逼出 Level 4 的复盘方法论。

### Level Ending

🔴 口诀:队列有界满即拒,429 是过载信号。

<a id="level-4"></a>

## Level 4

一句话认知墙:**事故复盘不是猜,是按请求链路分层看证据:先看执行路径(profile),再看资源队列(thread_pool),再看拒绝计数(rejected),最后验证恢复——每一层都在回答"墙在哪一层"。**

### 前置知识关卡

* [ ] Level 1-3:三类失控机制(规模/冲突/拒绝)
* [ ] 03 篇:Profile 定位执行路径,open_contexts 监控上下文

### Why

徒弟:

> 出事故了,打开日志一看:一堆 429、一堆 409、一堆超时。先查哪个?

老陈:

> 先查"哪个是原因、哪个是结果"。这就是复盘的意义:429 和 409 都**不是原因,是结果**——它们背后分别是"哪类请求把队列打满"和"哪个业务逻辑在并发写同 ID"。反过来看:
> 409 通常需要回到**业务写模型与重试链路**(同 ID 并发写、版本条件或幂等设计);
> 429 是**容量问题**(负载超过节点处理能力),但要分清是协调解析瓶颈还是写队列瓶颈;
> 超时是**结果的结果**(请求被拒绝或排队太久,客户端等不住)。
> 按"先看哪层、再看哪层"的顺序可以快速缩小范围;按"日志里搜关键字"的顺序,很容易一直停留在结果层。

| 方案 | 解决什么 | 留下什么问题 |
| ---- | ---- | ---- |
| 全文搜报错关键字 | 找到所有报错 | 报错是结果,找不到根因 |
| 分层看证据 | 定位墙在哪一层 | 需要理解每一层的指标语义 |

### What

分层定位路径(方法论,不是 API 清单):

```
第 0 层 现象清单:报错类型、时间窗、受影响接口/索引
第 1 层 执行路径:Profile / took / 慢日志
        → 回答:请求慢在哪一步?哪类查询最贵?
第 2 层 资源队列:thread_pool(queue/active/rejected)
        → 回答:哪类任务在排队?有没有被拒绝?
第 3 层 全局状态:open_contexts(未释放的 scroll)、
        GC、heap、磁盘 IO
        → 回答:有没有"慢性资源泄漏"叠加?
第 4 层 恢复验证:负载降后 queue→0、写入正常
        → 回答:是瞬态过载还是机制性死锁?
```

不变量:**每层指标回答一个特定问题;先分"原因层"与"结果层",再逐层下钻。** 409/429 是结果层,它们之上的查询形态与并发模型才是原因层。

> 📌 最容易被误解的一点:监控面板上"429 数量"和"409 数量"同时上涨,很容易被当成两个故障——实际上常常是**一个故障的两面**:同一批请求,查询侧超时重试造成 409 并发写,写侧过载造成 429。

### How

① 拿到现象:429/409/超时的分布与时间窗

② 第 1 层:开 Profile 跑典型请求,看慢在哪一步(脚本求值?字典遍历?)

③ 第 2 层:`_nodes/stats?filter_path=nodes.*.thread_pool` 看 queue/active/rejected 的**趋势**(不是瞬时值)

④ 第 3 层:open_contexts 是否上涨(scroll 泄漏)、GC/堆是否异常

⑤ 第 4 层:压测/降载复现,验证修复后 rejected→0、queue 回落

实测锚点(实验 009/010,es-ha-lab,ES 8.15.3):

```
profile(infix 中缀,1M docs):
  MultiTermQueryConstantScoreBlendedWrapper code:*23456* ms=23
  + BooleanQuery/TermQuery 叶子 × N
  ← 一帧画面看清"字典遍历展开"的真相

thread_pool 采样(429 压测中):
  queue=16/16/16,active=4/4/4,rejected 持续增长
  ← 一眼看清"写队列钉满 + 持续拒绝"

open_contexts(实验 008,scroll):[1,1,1] → clear 后 [0,0,0]
  ← scroll 泄漏的定位入口
```

### Transfer

- "先分原因层与结果层,再逐层下钻"是通用的故障定位骨架:MySQL 慢查询+锁等待、Kafka 消费延迟+堆积、JVM GC+OOM,全是同一套"分层+趋势"打法。
- 指标看**趋势**不看瞬时:rejected 单次采样为 0 不代表安全(队列在 16 和 0 之间波动是正常水位)。
- 本层留下的新账:**能定位了,怎么在设计期就不让这类事故发生?**——逼出 Level 5 的预防与决策。

### Level Ending

🔴 口诀:先分层再看趋势,报错是结果不是根。

<a id="level-5"></a>

## Level 5

一句话认知墙:**神话 10/11 打穿:wildcard 中缀和脚本不是"不能用",而是"必须在成本锚点上使用";配合乐观锁与有界队列,所有直觉写法都能变成有边界的写法。**

### 前置知识关卡

* [ ] Level 1-4 全部机制
* [ ] 02 篇:green ≠ 绝对安全(铁律 2)

### Why

徒弟:

> 听下来感觉 ES 哪儿都是坑:脚本不能写、通配不能写、并发要小心、还要防 429。那干脆全用简单查询得了?

老陈:

> 那是最贵的"安全"。真相是:
> 神话 10(wildcard 模糊查询很快)的真相:**前缀通配的成本可控**(实验 009:1M docs 前缀 3-4ms),中缀的成本随 term 字典规模走——**知道锚点,就能用**;
> 神话 11(脚本查询没代价)的真相:**热缓存下脚本不慢于 range,但成本随被求值候选规模走**——**限定候选范围,就能用**;
> 并发写不丢更新的真相:**本次负载下带 if_seq_no 的重试/retry_on_conflict 收敛到 0 丢失**——**姿势对,才有可验证的收敛路径**;
> 429 的真相:**队列满即拒 + rejected 可监控**——**容量可见,就能用**。
> 每一层机制都给了一个"能用的边界",这就是这四张决策卡。

| 神话 | 真相 | 机制 |
| ---- | ---- | ---- |
| 10 wildcard 模糊查询很快 | 中缀遍历全部 term;前缀成本可控 | Level 1 实验 009 |
| 11 脚本查询没代价 | 热缓存不慢,成本随被求值候选规模 | Level 1 实验 009 |
| (补) 并发写是"后写覆盖" | 乐观锁 409,不带条件丢 98% | Level 2 实验 010 |
| (补) 429 是服务端故障 | 有界队列满即拒,恢复可验证 | Level 3 实验 010 |

完整因果链(电梯版):

```
直觉写法(脚本/中缀/裸更新)
    → 成本随规模放大(L1:逐文档/字典遍历)
    → 并发写丢更新(L2:无锁 + 乐观锁,98% 丢失实测)
    → 服务端过载拒绝(L3:队列满 429,rejected 实测 ~25k)
    → 分层复盘定位(L4:profile → thread_pool → rejected → 恢复)
    → 生产决策:成本锚点 + 乐观锁 + 容量监控
```

### What

决策卡速览(详见文末):

| 决策 | 推荐 | 关键机制 |
| ---- | ---- | ---- |
| 脚本查询 | 限定候选范围/缓存热数据;禁止对全量字段无界求值 | 成本随被求值候选规模(实验 009) |
| 模糊匹配 | 前缀优先;中缀限定词项规模小/低频场景 | 字典遍历成本(实验 009) |
| 并发更新 | if_seq_no + 重试 / update retry_on_conflict | 乐观锁收敛(实验 010) |
| 容量与 429 | 监控 rejected 趋势;小 bulk;客户端退避重试 | 有界队列满即拒(实验 010) |

> 📌 最容易被误解的一点:"避免 429"不是调大 queue_size——**那只是把拒绝点往后挪,把内存压力变相放大**;正确姿势是让负载形态匹配处理能力(bulk 大小、并发度、退避)。

### How(生产排查路径)

```
查询慢/CPU 高:
  → 开 profile 看成本锚点:脚本求值(随命中)还是字典遍历(随词项)
  → 脚本:加 filter 缩小候选范围;中缀:改前缀/ngram/专用字段
并发更新丢数据:
  → 检查调用链:是否 GET→PUT 无版本?→ 改 if_seq_no + 重试
  → 或改 update API(retry_on_conflict),用脚本/detected_noop 控制
429 频发:
  → 看 thread_pool rejected 趋势与 queue 水位(先分协调解析 vs 写队列)
  → 客户端:指数退避重试 + 幂等 id;服务端:小 bulk、限流
  → 恢复验证:负载降后 queue→0、写入正常、rejected 停止增长
```

### Transfer

- "机制给边界,边界定决策"是全系列的方法论:每一类"直觉写法"先问成本锚点,再问并发语义,再问容量边界——三个问题都答完,才敢上线。
- 本系列因果链推进:05 篇把"治理"落到工程——mapping 一旦建错怎么零停机翻新(alias+reindex)、数据增长怎么自动管理(ILM)、数据丢失怎么兜底(snapshot)。

### Level Ending

🔴 口诀:锚点、锁、容量,三问才敢上线。

<a id="pitfalls"></a>
# ⚠️ 坑与细节

## 坑 1

错误理解:"脚本查询很慢,所以脚本不能用。"

原因:热缓存下脚本与 range 无显著差异(实验 009:1M docs 3-4ms vs 4-5ms);真正的风险是成本随被求值候选规模放大、冷启动 2 倍、并发放大。

比喻后果:管理员说"借阅台别用了",结果读者全挤在门口更乱。

线上现象:脚本查询单次不慢,但 QPS 一高 CPU 就上去。

修正:判断"被求值候选多少 × 多少并发",先用 filter 缩小候选范围;监控 CPU 与脚本耗时。

## 坑 2

错误理解:"wildcard 慢是因为命中太多。"

原因:中缀 `*x*` 的成本由 term 字典规模决定(实验 009:23 命中 vs 1047 命中,中缀反而慢 3 倍);前缀才是"枚举字典前缀段"。

比喻后果:读者翻了一整本索引页,只为了找 23 本书。

线上现象:命中很少的中缀查询吃掉大量 CPU;term 涨,查询变慢。

修正:前缀优先;中缀限定在词项规模小/低频场景;必要时用 ngram 专用字段。

## 坑 3

错误理解:"409 是网络问题,重试一次就行。"

原因:409 是乐观锁冲突信号;不带 if_seq_no 的"重试"只是把旧版本再覆盖一次,丢更新依旧(实验 010:裸 GET→PUT 丢 98%)。

比喻后果:两个管理员各记各的,最后只保留一张纸条。

线上现象:更新偶发丢失、数据回退,日志里没有报错。

修正:重试必须把 if_seq_no/if_primary_term 放在 URL 查询参数(重读→重试);或用 URL 上的 retry_on_conflict 调用 update API。

## 坑 4

错误理解:"429 是服务端故障,报障重启。"

原因:429 = 队列满即拒(有界队列的生存机制),是过载信号不是故障;重启只清瞬时状态,负载形态不变还会再来。

比喻后果:管理员关门半小时,开门后队伍还是那么长。

线上现象:429 高峰周期性出现,与流量峰值对齐。

修正:看 rejected 趋势与负载形态(bulk 大小/并发),客户端退避重试,服务端限流。

## 坑 5

错误理解:"调大 queue_size 就能消 429。"

原因:queue_size 是**静态设置**(动态 PUT 实测报错),且调大只是把拒绝点后移,排队请求占内存、客户端超时,雪崩更深。

比喻后果:借阅台无限加凳子,读者全坐在大厅里等,大厅挤爆。

线上现象:429 少了,但节点内存/GC 异常,超时更多。

修正:压测确认负载形态与容量;小 bulk、合理并发、客户端退避才是正解。

## 坑 6

错误理解:"429 靠客户端无限重试一定能成功。"

原因:无限重试 = 拒绝的请求立刻变成新请求,雪上加霜;429 期间服务端没有变快。

比喻后果:被拒的读者立刻重新排队,队伍永远清不完。

线上现象:429 期间请求量不降反升,恢复时间被拉长。

修正:指数退避 + 随机抖动;重试上限;幂等 id 防重复消费。

## 坑 7

错误理解:"rejected 计数为 0,说明很安全。"

原因:rejected 是趋势指标,不是水位指标;负载形态不对时(如大 bulk 解析瓶颈在前),队列根本没机会满(实验 010:queue 峰值 7、rejected 0)。

比喻后果:管理员只数被拒的人数,没看大厅里排队的。

线上现象:没有任何 429,但延迟持续走高——瓶颈在解析层。

修正:同时看 queue 水位、active、解析层 CPU;用"小 bulk × 高并发"测出真实队列行为。

## 坑 8

错误理解:"写成功 = 已持久化 = 可以安全读。"

原因:写入成功 = translog 已 fsync(01 篇);可读性由 refresh 窗口决定;并发下"读旧版本再写"会踩丢更新。

比喻后果:读者抄了旧目录去找书,书已经搬走了。

线上现象:更新后立刻读,偶尔读到旧值;对账时数据"回退"。

修正:先 refresh 语义(01 篇),再版本语义(本文);对账用 search_after + 稳定快照。

## 坑 9

错误理解:"把 -Des.thread_pool.write.queue_size=16 加到 JVM 参数就能改队列。"

原因:8.15.3 本实验实测系统属性方式**不生效**(queue 冲到 100+ 仍不拒,仍是默认 10000);必须写 elasticsearch.yml,并用 `_cat/thread_pool` 验证。

比喻后果:管理员把新规定贴在了门上,但借阅台是按旧规定执行的。

线上现象:改了配置,行为没变。

修正:静态设置一律走 elasticsearch.yml;改完验证 `_cat/thread_pool` 的 queue_size 列。

## 坑 10

错误理解:"update API 的 retry_on_conflict 是万能并发解药。"

原因:retry_on_conflict 只解决"同文档冲突重试";跨文档/跨索引的事务性、条件不满足的语义错误,它管不了;且重试上限内仍可能失败。

比喻后果:管理员帮读者重试了 50 次,但两本书的借阅记录还是要一起改,改一半失败了。

线上现象:单文档更新收敛了,但"一起改"的业务还是出现部分成功。

修正:需要原子性就用幂等业务设计/外部协调;文档级只保证单文档的乐观锁收敛。

<a id="decisions"></a>
# 🏆 生产决策卡

## Decision Card 1:脚本查询

### 场景

业务要在查询里做"文档算得出来的条件"(数值比较、自定义逻辑),数据量百万级、QPS 高。

### 判断

脚本单次不慢(实验 009),但成本随被求值候选规模走;先问"会评估多少候选文档",再决定写法。

### Mechanism → Decision

| 机制 | 工程决策 |
| ---- | ---- |
| 逐候选文档求值 | 尽量用 filter 把候选范围压小,脚本只做最后一步 |
| 热缓存与冷启动差异 | 热数据可接受;冷启动 2 倍(101ms vs 50ms)要在监控里看见 |
| text 无 doc_values | 脚本只能访问 doc_values 字段;要文本逻辑就走 keyword 子字段 |
| params._source 为 null | 脚本里拿不到源文档;需要 _source 数据的逻辑走应用层 |

### Code

```json
{"query":{"bool":{"filter":[{"range":{"price":{"gte":50}}}],
  "must":[{"script":{"script":{"source":"doc['count'].value > doc['price'].value * 2"}}}]}}}
```

### 禁止决策

不要对全量字段无界求值(无 filter 的脚本 query);不要把 _source 解析逻辑写进脚本。

### 验收指标

- p99 latency(脚本查询)、CPU(脚本执行时间占比)
- QPS、脚本命中文档规模(分段采样)
- 冷启动耗时(p99 首请求)、profile script time

## Decision Card 2:模糊匹配

### 场景

用户输入片段要模糊匹配(商品名/日志关键字),需要中缀匹配。

### 判断

前缀成本可控(实验 009:1M docs 3-4ms),中缀成本随 term 规模;按场景分级选型。

### Mechanism → Decision

| 机制 | 工程决策 |
| ---- | ---- |
| 前缀枚举字典段 | 能用前缀的模糊一律前缀/prefix |
| 中缀遍历全字典 | 词项规模小或低频场景才用;term 上千万级必须实测 |
| 展开成精确词项 | 看 profile 确认展开量;展开量大 = 查询 CPU 高 |
| ngram 专用字段 | 高频中缀搜索用 ngram 分词字段(独立成本,需压测) |

### Code

```json
{"query":{"prefix":{"code.keyword":{"value":"code-123"}}}}
```

### 禁止决策

不要对用户输入的任意中缀直接上生产 wildcard(先评估 term 规模);不要把中缀查询放进高 QPS 主链路。

### 验收指标

- p99 latency、CPU、term 字典规模与展开量(profile children 数)
- QPS、字典增长时的延迟斜率(定时采样)

## Decision Card 3:并发更新

### 场景

高频更新同一批文档(计数、状态机、库存类),多实例并发写。

### 判断

无版本更新会静默覆盖(实验 010:丢 98%);必须用乐观锁 + 重试。

### Mechanism → Decision

| 机制 | 工程决策 |
| ---- | ---- |
| seq_no + primary_term | 重读后带 if_seq_no/if_primary_term 重试 |
| update retry_on_conflict | 单文档增量更新优先用它(实验 010:最快且 0 丢失) |
| 409 频次监控 | 409 率高 = 业务冲突率,要审视写模型而不是加机器 |

### Code

```http
POST /conflict-test/_update/c1?if_seq_no=0&if_primary_term=1
{"doc":{"v":2}}

POST /conflict-test/_update/c1?retry_on_conflict=50
{"script":{"source":"ctx._source.v += 1"}}
```

### 禁止决策

不要写"GET→改→PUT"裸循环;不要对非幂等业务无脑重试。

### 验收指标

- 409 率(每分钟)、重试成功率、最终一致核对(抽样对账)
- p99 latency(带冲突重试后的写延迟)、丢更新率(对账差异)

## Decision Card 4:容量与 429

### 场景

大流量写入,偶发 429,要判断是容量问题还是写法问题。

### 判断

429 = 队列满即拒;先分"解析瓶颈在前"还是"写队列真满",再决定优化方向。

### Mechanism → Decision

| 机制 | 工程决策 |
| ---- | ---- |
| 大 bulk 解析瓶颈在前 | 减小 bulk 大小,多节点分担协调负载(实验 010 对比) |
| 小 bulk + 高并发打满队列 | 这才是真实写容量;用压测找安全并发度 |
| rejected 趋势监控 | 429 率、rejected 计数、queue 水位三件套 |
| Bulk item 级结果 | 检查 `errors` 与 `items[*].status`,只重试失败且幂等的 item |
| 客户端退避 | 指数退避 + 抖动 + 幂等 id,禁止无限重试 |

### Code

```json
{"index":{"_index":"flood-test","_id":"f0","op_type":"create"}}
```

### 禁止决策

不要调大 queue_size 消 429;不要在 429 期间关闭重试上限;不要用大 bulk 追求单请求吞吐。

### 验收指标

- rejected 计数(趋势)、429 响应率、queue 水位、active 线程
- p99/p999 写延迟、吞吐(docs/s)、恢复时间(负载停止到 queue=0)
- 客户端重试次数分布、幂等冲突率(重复消费)

<a id="cross-language"></a>
# 🌍 跨语言视角

同一个问题:"并发写怎么防丢?过载怎么拒绝?"

| 语言/系统 | 解法 | 与 ES 的对应 |
| ---- | ---- | ---- |
| MySQL | UPDATE ... WHERE version=?;行锁/意向锁 | 乐观锁同源;ES 用 seq_no 免锁 |
| Java | AtomicLong CAS / ConcurrentHashMap 版本控制 | seq_no = 分布式 CAS 条件 |
| Go | sync/atomic CompareAndSwap;channel 有界缓冲 | 有界队列 + 拒绝 = channel buffer full 的处理策略 |
| Rust | AtomicU64 fetch_update 循环 | 409 → 重读重试 = fetch_update 的 retry 循环 |
| Kafka | 幂等 producer(sequence number) | 客户端幂等 id 与 409 重试同思路 |
| Redis | WATCH/MULTI 事务;INCR 原子操作 | 不做并发控制的方案 = 裸 GET→PUT 的教训 |

底层判断力:

- **并发控制三选一**:锁(排他)、版本校验(可检测)、原子操作(免比较);分布式系统默认选版本校验,因为协调成本最低。
- **重试必须带条件**:无条件重试是"重复错误",有条件重试才是"收敛算法"。
- **过载用有界队列拒绝,不用无限排队**:任何系统的请求队列都要有界,拒绝要可观测、可退避。
