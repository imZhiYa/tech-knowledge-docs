# 正文:五个 Level 打穿 ES 存储内核

<a id="level-1"></a>

## Level 1:为什么数据库全文检索会死——倒排索引思想

### Why——上一代方案死在哪

**徒弟**:MySQL 加个 B+ 树索引,LIKE 查询慢就加个索引,不是挺稳的吗?为什么非要倒排索引?

**老陈**:B+ 树索引救不了全文检索,因为**你要查的东西在索引里根本不存在**。看这张表:

| 朴素方案 | 它想解决什么 | 它留下的致命账 |
| ---- | ---- | ---- |
| LIKE '%关键字%' | 子串匹配 | **全表扫描**:每一行从头到尾扫一遍,索引完全用不上 |
| B+ 树前缀索引 | 前缀匹配 | 只救得了 '关键字%',救不了 '%关键字%'(中缀)与分词查询 |
| 数据库自带 FULLTEXT | 全文检索 | 与 ES 在分词、相关度、查询模型、分布式扩展上差异明显;具体中文检索能力取决于版本、parser 与配置,不能一概而论 |

**核心矛盾**:数据库的索引是"值 → 位置"的正排思想,查询时你必须**提供完整的前缀**才能走索引;而全文检索是"我只有几个词,不知道它们在哪些文档里"——这是一个**从词找文档**的问题,正排索引天生答不了。

**倒排的思想**:与其查询时扫描全部文档,不如**写入时就预分词**——每个词后面挂一串"哪些文档含这个词"。查询"关键词"变成:查表找到词 → 直接拿到文档列表。**把"查询时的扫描"变成"写入时的索引",这就是倒排。**

### What——倒排索引的核心结构

```text
正排(数据库):文档 → 字段值      (查询时:不知道值在哪,只能扫)
倒排(ES):    词 → 文档列表       (查询时:查词表即得文档)
```

```text
倒排索引(简化)

term dictionary          postings
─────────────           ─────────────
"elastic"   ──────────→  [doc3, doc7]
"search"    ──────────→  [doc1, doc3]
"引擎"      ──────────→  [doc2, doc7]
```

**不变量**:一个 term 对应一个有序文档 ID 列表(postings);term 有序存储(支持范围与前缀查找)。

> 📌 **最容易被误解的一点**:倒排索引只回答"哪些文档命中"。**评分(相关性)、排序、返回内容**都需要别的结构配合(doc_values、_source、BM25 参数)——这是 Level 2 的内容。倒排不是"整个搜索",只是"命中判定"这一环。

### How——一次查询怎么走

```text
① 用户输入 "elasticsearch 引擎"
② analyzer 分词:"elasticsearch" "引擎"
③ 查 term dictionary → 拿到两个 postings 列表
④ 归并交集 → 命中文档集
⑤ 评分(BM25)排序 → 取 _source 返回
```

> 📌 **最反直觉的一步**:第 ② 步。**查询也要分词**——两侧 analyzer 不必相同,但索引与查询生成的 **token 必须满足预期的匹配语义**,不同源就是"明明有数据却搜不到"(00 篇站 4 的 index analyzer ≠ search analyzer 案例)。

### Transfer

1. "把查询时的扫描变成写入时的索引"——预计算思想:空间换时间,所有缓存/物化视图/预聚合都是同一思想。
2. 正排 vs 倒排:值找位置 vs 词找文档。Redis 的 Sorted Set 是值找位置,搜索引擎是词找文档——选型先问"你的查询方向是什么"。

### Level Ending

🔴 口诀:查询转索引,词表定命中文档。

## Level 2:Doc D 落盘后的长相——倒排/FST/doc_values/_source

### 前置知识关卡

- [ ] 知道 term dictionary → postings 的查找路径(Level 1)
- [ ] 知道 doc 是一份 JSON(00 篇站 1)

### Why——为什么倒排不能只存"词→文档"

**徒弟**:倒排索引不是已经能回答"哪些文档命中"了吗?为什么还要 term dictionary、doc_values、_source 这么多东西?

**老陈**:因为"命中"只是第一问。真实查询还有三问:**这一问有多少个词?文档按什么排序?命中的内容长什么样?** 每个问题一个结构,倒排只是其中一个:

| 查询问题 | 谁来回答 | 结构 |
| ---- | ---- | ---- |
| 哪些文档命中"词 X"? | 倒排索引 | term dictionary + postings |
| 这些词长什么样、怎么存才省内存? | 词表压缩 | FST(前缀共享) |
| 按字段排序/聚合(如按价格排序)? | 正排 | doc_values(列式) |
| 命中的原始内容是什么? | 原始存储 | _source |

### What——四个结构各管什么

#### ① Terms Dictionary / Terms Index(FST)/ Postings 的分层

**不要把这层压扁成"FST = 整个 term dictionary"**。Lucene 的 term 查找是分层协同:

```text
Terms Dictionary    term → postings 的完整映射(按 block 组织,磁盘)
Terms Index         辅助定位 term/block 的紧凑索引(内存常驻,FST 是典型实现)
Postings            每个 term 的文档列表与频率信息
```

**因为千万级 term 无法整表常驻内存,所以引入 Terms Index**:用 FST 这类紧凑结构(共享公共前缀,如 "search"/"searches"/"searching" 共享 "search" 前缀)辅助定位 term 所在的 block,再进 Dictionary 取详情——FST 是"定位器",不是"全部词表"。

```text
普通字典: "search"  "searches"  "searching"  → 3 个完整词条
FST:      "search" 共享前缀,分支复用后缀    → 前缀共享,一条路径

   s ─ e ─ a ─ r ─ c ─ h ─ e ─ s ─ END      # searches
                    │
                    └─ END                   # search
                          └─ i ─ n ─ g ─ END # searching
```

**查询路径**:

```text
query term
   ↓
terms index(FST)→ 定位 term/block
   ↓
term block
   ↓
term
   ↓
postings
```

**代价**:FST 查询是"沿边行走",比哈希表多几次跳转,但换来内存数量级下降——"内存换时间"的反向取舍(FST 用时间换内存)。

#### ② postings(文档列表)

**postings 不是固定"三件套"**。它**可能**包含:

```text
docID(命中文档)
term frequency(词频,默认 index_options=freqs 时记录)
positions(位置,index_options=positions 时记录,短语查询依赖)
offsets(偏移,index_options=offsets 时记录,高亮依赖)
```

具体粒度由字段的 **index_options** 配置决定。三个连带认知:

- **为什么 phrase query 需要 positions?** 短语 = "词 + 相邻位置",没有位置信息无法判断词序与间距;
- **为什么 positions/offsets 增加存储成本?** 每个 term 每处出现都要存位置/偏移,是频率信息之外额外数据;
- **为什么关闭部分 index_options 会牺牲查询能力?** 关掉 positions,短语/近似查询直接不可用——这是"省存储 vs 保能力"的字段级取舍(05 篇 Mapping 决策卡)。

**因为要省空间,所以做增量编码**(doc id 排序后存差值),Lucene 9.x 具体压缩算法待源码验证。

#### ③ doc_values(正排列式)

**因为倒排不能按字段排序/聚合,所以引入 doc_values**:把字段值按"文档 ID → 值"的列式结构单独存一份(与倒排相反的方向)。

**职责边界(不要写成"范围过滤都走 doc_values")**:doc_values 主要解决"按文档读取字段值"的访问模式;数值/日期范围查询通常涉及 Lucene points/BKD 等其他结构,具体路径依字段类型与查询实现而定:

| 查询需求 | 主要相关结构 |
| ---- | ---- |
| 全文命中 | inverted index / postings |
| 排序 | doc_values |
| 聚合 | doc_values |
| 脚本访问字段值 | doc_values |
| 数值/日期范围 | points / BKD 等结构 |
| 原始 JSON 返回 | _source |

**代价**:一份字段两份存储(倒排 + 正排),**磁盘成本显著增加**(列式压缩存储,不同字段类型增量差异大,不存在统一的"翻倍"比例)——所以"不需要排序/聚合的字段"可以关掉 doc_values 省磁盘(05 篇 Mapping 决策卡)。

#### ④ _source(原始 JSON)

**因为命中后要返回原始内容,所以存 _source**(行式,完整 JSON)。可以关闭节省磁盘,但**关闭后 reindex、update 能力受损**(05 篇的账)。

**实测默认(ES 8.15.3)**:mapping.total_fields.limit=1000——字段上限,动态映射裸奔会撞墙(神话 12 的伴生坑)。

### How——一次查询穿四个结构

```text
① match 查询 "search engine"
② term dictionary(FST)找到 "search" 和 "engine" 两个 term
③ postings 拿到两个文档 ID 列表,归并 → 命中 doc3, doc7
④ 按 doc_values 里的 price 排序
⑤ 从 _source 取 doc3/doc7 的原始 JSON 返回
```

> 📌 **最反直觉的一步**:第 ③→④ 步。倒排给了"命中谁",doc_values 给了"怎么排",**_source 给了"长什么样"——三次不同的磁盘/内存访问**。这就是为什么"只查 id 不取字段"的查询比"取全部字段"快一个数量级。

### Transfer

1. "一个查询问题一个结构"的拆分思想:命中/排序/聚合/返回内容,分别设计存储——ES 不是一张大表,是四张分工的表。
2. 列式存储(doc_values)思想迁移:ClickHouse 的列存、OLAP 的 projection,同一思想(查询哪个字段,就读哪列)。

### Level Ending

🔴 口诀:倒排定命中,正排做排序,source 管返回。

## Level 3:Doc D 的写路径——translog/refresh/flush

### 前置知识关卡

- [ ] 知道 segment 是不可变单元(Level 2 预告)
- [ ] 知道"写入成功 ≠ 可搜"是神话 1(00 篇预告)

### Why——为什么写路径要绕这么大一圈

**徒弟**:写入不就是把文档存进文件吗?为什么还要 buffer、translog、refresh、flush 四层?

**老陈**:因为写入面对两个互相打架的要求:**不能慢** vs **不能丢**。把每个变更立即 fsync 到磁盘 → 慢(一次 fsync 是毫秒级);攒在内存里批量落 → 快,但断电全丢。ES 的写路径是这两者的拆解:

| 朴素方案 | 它想解决什么 | 它留下的致命账 |
| ---- | ---- | ---- |
| 每次写入直接写磁盘文件 | 持久化 | 吞吐崩溃(每个请求一次 fsync) |
| 攒内存,定期批量落盘 | 吞吐 | 断电丢失窗口大 |
| 不可变段(直接改段) | 更新方便 | Lucene 的段一旦生成不可改——必须另想办法 |

**最终设计**:内存 buffer(快)+ translog(不丢)+ 不可变 segment(可搜)+ 后台 fsync(稳)——四个结构各管一件事。

### What——写路径四件套

```text
Doc D 的写路径(ES 8.15.3)

① 请求到达 → 主分片
② 写 translog(可靠性,durability=REQUEST:每次请求 fsync 落盘;集群语境下 = primary + 已分配副本的 translog 都 fsync 后才 ACK,02 篇 Level 2/5)
③ 写内存 buffer(吞吐,index_buffer_size=堆的 10%)
④ refresh(默认 1s):近期写入进入新的可搜索视图
⑤ flush(提交):Lucene commit/checkpoint + translog 生命周期管理

持久化点:②(translog fsync)——断电不丢的保证
可见性点:④(refresh)——能搜到的保证
```

**关键认知:持久化点 ≠ 可见性点。**

- **持久化点**:translog fsync(durability=REQUEST,实测 8.15.3)。此刻起断电不丢。
- **可见性点**:refresh(默认 1s)。此刻起查询可见。
- 两个点之间(写入成功但未 refresh):数据在 translog 里,**不丢但搜不到**。

### How——实验 001 证据(神话 1 打破)

```text
① POST /exp3/_doc {"msg":"hello"} → 返回 success
② 立即查询 → hits.total = 0       ← 写入成功但不可搜!
③ 等 1.2s 再查 → hits.total = 1   ← refresh 生效,可见
④ 设 refresh_interval=-1,再写一条,等 2s → 仍不可见
⑤ 手动 POST /_refresh → 可见
```

实验 002(写路径矩阵,ES 8.15.3):

```
refresh_interval=1s  → 20000 条 bulk 891ms
refresh_interval=30s → 635ms
refresh_interval=-1  → 364ms(约 2.4 倍差距)
```

**结论**:refresh 越频繁写入越慢——refresh 让近期写入进入新的可搜索视图,段逐步产生/打开,段越多、merge 压力越大。关闭 refresh 换吞吐,代价是可见性延迟(神话 1 的完整版:写入成功 = translog 里安全了,但搜得到是另一回事)。

**注意**:refresh 与"每调用一次就固定创建一个 segment"不是绑定关系。refresh 的核心职责是让近期写入进入可搜索视图;segment 的产生/打开与后台 merge 是配套的渐进过程。

**flush 又是什么**:refresh 只解决"可搜索视图",flush 才涉及 Lucene commit/checkpoint 与 translog 生命周期管理(清空 translog、生成 commit point)。实测默认:translog 达到 **10gb**(8.15.3,旧文档 512mb 已过时),或 translog 年龄超过 `index.translog.flush_threshold_age`(8.15.3 实测默认 **1m**)触发 flush。**flush 不是需要高频手动触发的操作,但它会产生 IO 与资源成本——不能为了"更安全"而频繁手动 flush**。这也是 00 篇勘误表里"refresh 是刷新索引文件"的错误理解来源。

> 📌 **最反直觉的一步**:写入成功返回的是"translog 已 fsync",不是"已可搜"。**"成功"两个字掩盖了持久化点与可见性点的差距**——这就是神话 1 为什么是生产第一坑。

### Transfer

1. "快 vs 丢"的拆解:先落日志(顺序写,快),再落主存储(批量,慢)——这是数据库 WAL、Redis AOF 的同一设计,顺序写是 IO 最快的写。
2. "持久化点与可见性点分离"的通用思想:Kafka 的 ISR 与消费者可见性、MySQL 的 redo 与 MVCC 可见性,全是两点的拆解。

### Level Ending

🔴 口诀:translog 保不丢,refresh 定可见。

<a id="level-4"></a>

## Level 4:更新=删+写——墓碑与段合并

### 前置知识关卡

- [ ] 知道"segment 不可变"是 Level 2/3 的暗线
- [ ] 知道写路径四件套(Level 3)

### Why——为什么更新不是"改"

**徒弟**:PUT 同一个 _id 的文档,不就是"修改"它吗?有什么讲究?

**老陈**:Lucene 的 segment **一旦生成就不可变**——这是倒排索引的根本约束(改一个词,词表、postings、doc_values 全要动,不可变才能 mmap 共享、才能压缩、才能并发读)。既然不能改,**更新只能=标记删除旧版本 + 写新版本**:

| 直觉方案 | 它想解决什么 | 它留下的致命账 |
| ---- | ---- | ---- |
| 直接改 segment | 原地更新 | 不可变段是 Lucene 契约,改了等于重写整个段 |
| 全量重写索引 | 一致性 | 写入放大:改一条文档要动整个段 |
| **墓碑 + 新文档** | 不可变约束 | 旧版本占着磁盘,直到 merge 才清 |

**最终设计**:更新 = 旧文档打**墓碑**(tombstone,标记 deleted)+ 新文档正常写入。查询时墓碑文档被过滤,但**物理上还在段里**。

### What——墓碑与段合并

```text
更新 doc7:
  segment_A: [doc1✓, doc7✗(墓碑), doc9✓]   ← doc7 被标记,物理还在
  segment_B: [doc7✓(新版本), doc10✓]        ← 新版本写入新段

查询时:Lucene 过滤掉带墓碑的 doc7 → 只命中 segment_B 的 doc7

merge 时:segment_A + segment_B 合并 → 墓碑被物理清除,磁盘释放
```

**TieredMergePolicy(实测 ES 8.15.3,默认)**:segments_per_tier=10 是**选择合并候选、控制 segment 层级数量的参数之一**,不能理解成"严格攒够 10 个就执行一次合并"。真实因果链:

```text
segment 增长
   ↓
TieredMergePolicy 按层选择合并候选(segments_per_tier 参与决策)
   ↓
merge 产生 IO / CPU
   ↓
segment 数量下降
   ↓
查询开销下降
   ↓
磁盘空间回收 / 重新组织
```

merge 由 Lucene 自调度,写压力大时 merge 让位(写优先)。

**代价(关键)**:merge 是后台 **IO/CPU 大户**,与写入竞争资源;merge 期间查询延迟可能抖动(04/06 篇)。所以"删除不释放磁盘""更新越频繁磁盘涨得越快"都是墓碑的必然结果。

### How——实验 003 证据(神话 2/3 打破)

```text
ES 8.15.3,1 分片,30000 文档:

① 初始写入            docs=30000  store=3.1MB  段数=1
② 同 _id 覆盖更新 30000  docs=30000  store=3.1MB  段数=3   ← 更新产生新段+墓碑
③ delete_by_query 删 15000 docs=15000  store=3.1MB  段数=5   ← 文档少了,磁盘一点没少!
④ force merge(首次)  docs=15000  store=3.1MB  段内墓碑=60000  ← merge 是异步的,没做完
⑤ force merge(完成)  docs=15000  store=666KB  段内墓碑=0      ← 墓碑清除,磁盘释放
```

**结论**:

- 更新 30000 次,段数 1→3:旧版本全部是墓碑(更新 = 标记删除 + 新建)。
- 删除 15000 后 docs.count 减半,**store.size 一字节没少**:删除不立即释放磁盘(神话 3)。
- merge 完成后墓碑 60000 → 0,存储 3.1MB → 666KB:物理清除只有 merge 能完成(神话 2/3 的完整因果)。
- 中间态很有意思:force merge 返回了,墓碑还在——**merge 是异步的,需要时间和资源**,"等 merge"在生产上可能是几十分钟。

> 📌 **最反直觉的一步**:第 ② 步。更新 30000 次之后,**磁盘上实际躺着 60000 个旧版本**(30000 个墓碑 + 新版本),文档数没涨,磁盘在悄悄涨。删数据同理——**你删的不是数据,是"可见性"**。

### Transfer

1. "不可变 + 增量"的取舍:不可变换来并发读安全与压缩,代价是更新成本与空间——这是 Log-structured 一切系统(LSM、WAL、Kafka 日志)的共同哲学。
2. 墓碑与垃圾回收:Java GC 的标记-清除、RocksDB 的 tombstone、Kafka 的 compaction,全是"标记 → 后台物理清除"两段式。

### Level Ending

🔴 口诀:段不可变,更新留墓碑,merge 才释放。

<a id="level-5"></a>

## Level 5:崩溃恢复与存储可靠性——登记本与正式卡片

### 前置知识关卡

- [ ] 知道 translog 是"临时登记本"(Level 3)
- [ ] 知道墓碑机制(Level 4)

### Why——为什么需要崩溃恢复

**徒弟**:有 translog 了,节点崩溃后数据怎么回来?

**老陈**:translog 是"登记本",segment 是"正式卡片"。崩溃时刻可能的情况:**登记本记了、卡片还没誊完**(buffer 丢失)、**卡片誊了、登记本还没清**(正常)。恢复就是"用登记本把没誊完的部分补上":

| 朴素方案 | 它想解决什么 | 它留下的致命账 |
| ---- | ---- | ---- |
| 只靠 segment | 落盘数据 | buffer 里的数据断电全丢 |
| 只靠 translog | 断电不丢 | translog 无限增长,恢复要重放全部 |
| translog + commit point | 两者兼顾 | 恢复要正确衔接两个状态 |

### What——commit point 与重放

```text
崩溃恢复流程:

① 读最后一次 commit point(记录哪些段已落盘)
② 从 commit point 之后开始重放 translog(补回 buffer 里没来得及成段的写入)
③ 数据回到崩溃前一刻(只要 translog 是 fsync 过的)

为什么 translog 要清空?→ flush 时:段已落盘 + translog 清空 + 新 commit point
                  → translog 只保留"段还没覆盖"的增量,恢复快
```

**可靠性边界(关键)**:

- durability=REQUEST(实测默认):**每次请求 fsync**,崩溃最多丢"正在 fsync 的那一次请求"(窗口极小)。
- durability=ASYNC:sync_interval=5s(实测),崩溃最多丢 5 秒的写入——**换吞吐,丢窗口变大**。
- **这就是"green ≠ 数据绝对安全"的机制根**:green 只表示分片分配完整,translog 的 fsync 策略才决定丢数据窗口(神话 6,02 篇用副本+恢复继续讲)。

**实测默认(ES 8.15.3)**:translog.flush_threshold_size=**10gb**(触发 flush 的阈值)、gc_deletes=60s(墓碑的垃圾回收时间窗)。

### How——一次崩溃的完整恢复时序

```text
① 节点崩溃(写了一半:translog 有记录, buffer 有内容, segment 只有旧段)
② 节点重启 → 加载最后 commit point
③ 重放 commit point 之后的 translog
④ 内存 buffer 重建 + refresh → 数据恢复可见
⑤ 若 translog 也损坏(磁盘坏)→ 丢 commit point 之后的数据,从副本/快照补
```

> 📌 **最反直觉的一步**:第 ⑤ 步。translog 救的是"进程崩溃",救不了"磁盘损坏"——**单机再稳,也只是单机**。副本、快照才是跨机器、跨机房的那一层。这留下 02 篇的账:数据怎么分布到多台机器、节点挂了谁能顶上?

### Transfer

1. WAL 思想的三要素(日志先行、批量合并、崩溃重放)——MySQL redo log、Redis AOF、Kafka 全用同一套。
2. "恢复 = commit point + 日志重放"的通用模式:检查点(watermark)+ 增量日志,流处理系统(checkpoint + Kafka)同构。

### Level Ending

🔴 口诀:commit 加 translog,崩溃重放不丢账。

<a id="pitfalls"></a>

# ⚠️ 坑与细节

## 坑 1

错误理解:写入成功 = 已落盘 = 可搜。

原因:把持久化点当可见性点(Level 3 的核心)。

比喻后果:读者以为书已上架,其实只在登记本上。

线上现象:写后立刻查 0 命中(实验 001);聚合结果少数据。

修正:接受 1s refresh,或 `refresh=wait_for` 强制可见(代价:吞吐)。

## 坑 2

错误理解:更新文档很便宜,就是改一下。

原因:不知道更新 = 墓碑 + 新文档,不知道 merge 的账。

比喻后果:频繁改卡片,书架越来越乱,整理一次要很久。

线上现象:高频更新场景磁盘暴涨、merge 频繁、查询变慢(实验 003)。

修正:高频更新场景考虑"追加事件 + 读取时归并"或换存储(04/07 篇)。

## 坑 3

错误理解:删数据 = 释放磁盘。

原因:墓碑直到 merge 才物理清除(Level 4)。

比喻后果:把书从目录划掉,书还占着书架。

线上现象:delete_by_query 后磁盘不降,容量告警(实验 003)。

修正:force merge(注意异步与 IO 代价)或接受延迟释放。

## 坑 4

错误理解:translog 越大越好,反正能恢复。

原因:translog 是恢复的来源,但不是"越大越安全"。

比喻后果:登记本越厚,补抄越慢。

线上现象:translog 异常大(如长时间未 flush)时,恢复耗时长。

修正:flush_threshold_size 与 flush 周期保持默认,勿乱改。

## 坑 5

错误理解:refresh_interval 调大 = 白嫖吞吐。

原因:吞吐是真的(实验 002),但可见性延迟也真的大,且大量 buffer 堆积会挤占内存。

比喻后果:卡片攒一个月才誊,读者全在等。

线上现象:bulk 导入快,但实时查询/近实时业务查不到刚写的数据。

修正:导入场景临时调大 + 导入完恢复;在线场景保持默认。

# 📚 版本勘误表

| 错误说法 | 准确说法 |
| ---- | ---- |

# 🏆 生产决策卡

## Decision Card 1-1

### 场景

批量导入海量历史数据(日志回灌/迁移),导入慢。

### 判断

导入是"吞吐优先、可见性无所谓"的场景:临时调大 refresh_interval + 调小副本,导入完恢复。

### Mechanism → Decision

| 机制 | 工程决策 |
| ---- | ---- |
| refresh 越频繁写入越慢(实验 002) | 导入时 refresh_interval=30s 或 -1,完成后恢复 1s |
| 副本复制是额外写入 | 导入时副本=0,导入完调回 1 |
| translog durability 决定丢窗口 | 导入非关键数据可 ASYNC,关键数据保持 REQUEST |

### Code

```bash
# 导入前:调大 refresh 间隔、副本归零
PUT /orders/_settings
{"index": {"refresh_interval": "30s", "number_of_replicas": 0}}

# 导入后用 bulk 分批(如 5000~10000 条/批)

# 导入完:恢复
PUT /orders/_settings
{"index": {"refresh_interval": "1s", "number_of_replicas": 1}}
```

### 禁止决策

- 导入全程保持默认 1s refresh(吞吐浪费一半以上)
- 导入后忘记恢复 refresh_interval

### 验收指标

- 导入吞吐:同数据量下对比默认配置提升 ≥ 1.5 倍(本机实测方向:364ms vs 891ms)
- 导入完成后查询可见性恢复 1s 内
- 副本恢复后集群 green

## Decision Card 1-2

### 场景

频繁更新同一批文档(如库存、状态机流转),磁盘涨得飞快。

### 判断

先量化更新频率与数据量,再决定"ES 是否适合当这些数据的存储"。

### Mechanism → Decision

| 机制 | 工程决策 |
| ---- | ---- |
| 更新 = 墓碑 + 新建(实验 003) | 高频更新场景先算"墓碑放大倍数" |
| 墓碑只有 merge 清 | 高频更新 = merge 常驻 = IO 与查询抖动 |
| ES 弱一致、无事务 | 状态机强一致更新请留在数据库 |

### Code

```bash
# 若必须用 ES:减少更新粒度
# 坏:每次状态变化都更新整个 doc
# 好:状态变化作为事件追加(如 order-events 索引),doc 只存最新快照(低频刷新)
```

### 禁止决策

- 用 ES 存高频更新的业务状态,并期望"和数据库一样便宜"
- 高频更新时不开监控 merge/段数,等磁盘报警才看

### 验收指标

- 段数稳定(合并速率 ≥ 产生速率,实验 003 的墓碑数可控)
- 更新风暴下查询 p99 抖动 < 2 倍
- 磁盘增长 = 净新增数据量 + 可控墓碑,而非更新次数 × 文档大小

---

## Decision Card 1-3

### 场景

"删了数据但磁盘没降"告警。

### 判断

这是墓碑的正常现象(实验 003),不是故障;先看段内墓碑数,再决定是否 force merge。

### Mechanism → Decision

| 机制 | 工程决策 |
| ---- | ---- |
| 删除只标记墓碑(实验 003) | 磁盘释放延迟是正常现象 |
| merge 异步且耗 IO | 一次性大清理可用 force merge,但要避开高峰 |
| force merge 后段=1,查询最优 | 频繁 merge 的索引考虑 ILM 滚动(05 篇) |

### Code

```bash
# 查看墓碑:段内 docs.deleted
GET /_cat/segments/my-index?v&h=shard,segment,docs.count,docs.deleted,size
```

# 🌍 跨语言视角

同一个问题,别的系统怎么解决?

| 问题 | ES | MySQL | Kafka | Redis | 底层思想是否一致 |
| ---- | ---- | ---- | ---- | ---- | ---- |
| 崩溃恢复 | commit point + translog | redo log + checkpoint | 高水位 + 日志 | AOF + RDB | 一致:WAL 思想,日志先行 + 检查点 |
| 更新不可变 | 墓碑 + 新建 | 原地更新(B+树) | append-only | 原地覆盖 | 分叉:LSM/日志系用墓碑,原地系直接改 |
| 删除释放 | 等 merge | 立即释放 | compaction | 惰性/异步 | LSM 系一致:物理清除都是后台做 |
| 写放大 | refresh + merge | redo/undo | 副本复制 | AOF 重写 | 一致:为了吞吐,总有后台代价 |
| 可见性 | refresh 1s | 事务提交 | ISR | 命令即见 | 分叉:ES 近实时,DB 强一致,Kafka 由消费侧定 |

**跨语言仍成立的判断力**:

1. 顺序写日志(快)+ 检查点(稳)+ 后台清除(省)——这是所有可靠存储的三角,没有第四种。
2. 不可变 vs 原地改,是 Log-structured 与 B+树 的分水岭;墓碑/compaction/后台 GC 是 Log-structured 的必付代价。
3. "写入成功"在每套系统里都指不同的点(ES 指 translog,Redis 指内存,MySQL 指 commit 返回)——**先问"成功"指什么,再谈可靠性**。
