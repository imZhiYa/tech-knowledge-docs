<a id="level-1"></a>

## Level 1

一句话认知墙:**搜索快,是因为查询不用扫全表,而是沿"词 → 文档"的索引直达。**

### 前置知识关卡

* [ ] 01 篇:倒排索引由 term dictionary(FST)+ postings 组成
* [ ] 01 篇:写入路径 refresh 后文档才可搜(神话 1)
* [ ] 00 篇:analyzer 决定一个词如何被切分

### Why

徒弟:

> 搜索不就是"在数据库里找包含某词的记录"吗?MySQL 加个索引不就完了?

老陈:

> 它确实解决了"按主键/前缀精确找",但是留下了两个死账:
> 第一,`LIKE '%x%'` 中缀匹配无法用 B+ 树,只能全表扫;
> 第二,就算能扫,它也不知道"哪条记录更相关",只能按时间/主键排序。
> 所以你看到的所有全文检索系统,都绕不开同一个决定:**把"词 → 文档"的映射提前建好**,查询时 O(词项)直达,而不是 O(文档数)扫描。

| 方案 | 解决什么 | 留下什么问题 |
| ---- | ---- | ---- |
| MySQL B+ 树 | 等值/前缀/范围查询 | 中缀模糊全表扫描;无相关度排序 |
| MySQL LIKE 扫描 | 简单模糊 | 全表扫;无分词;无排序 |
| 倒排索引(ES) | 词项直达文档 + 频率统计 | 索引建造成本;更新=删+写(01 篇) |

### What

核心数据结构(01 篇已建,这里只看查询视角):

```
倒排索引
├── term dictionary(FST)   词 → postings 文件位置(内存驻留)
└── postings                词 → 文档 ID 列表 + 词频 + 位置
       ↓ 查询时
   term("beta") → [d1, d7, d88, ...]     ← 命中即出,不扫全表
```

不变量:**命中判定只依赖 term dictionary + postings,与文档总数无关**(只与词项数相关)。

> 📌 最容易被误解的一点:倒排是"为查询建的",不是"为存储建的"。所以 ES 里的每个字段是否建立倒排,由 mapping 决定(`"index": false` 的字段查询不到,但照样能存、能聚合)。

### How

① 用户发 `match` 查询 Q

② 协调节点解析:query 里的文本先过 analyzer(与写入时同一套),拆成词项

③ 每个词项查 term dictionary → postings

④ 多词项按布尔逻辑合并(AND/OR)后得到候选文档集

⑤ 候选集进入评分阶段(Level 2)

实测锚点(实验 007,page-test):`match text=beta gamma` 返回第一名的 `_score=1.845`——说明参与了评分,但单凭 `_score` 不能证明具体使用了 BM25;`constant_score` filter 返回 `_score=1.0`——说明不按相关度评分。

### Transfer

- 倒排思想迁移:任何"属性 → 实体"的高频反向查询(标签查商品、作者查书、IP 查用户)都值得预建反向映射。
- 从"查询时扫描"到"写入时建索引"的交换,是几乎所有检索/时序/搜索系统的共同形态:用写放大换读直达。
- 本层留下的新账:**倒排只告诉你"哪些书含这个词",不告诉你"哪本书最相关"**——逼出 Level 2 的评分机制。

### Level Ending

🔴 口诀:词到文档提前建,查询直达不扫描。

<a id="level-2"></a>

## Level 2

一句话认知墙:**相关度不是玄学,是 BM25 在词频、逆文档频率、文档长度上的一个显式公式;而"要不要算分"由 query/filter 上下文决定,filter 具备进入 node query cache 的资格,但不等于一定命中 request cache。**

### 前置知识关卡

* [ ] Level 1:倒排返回候选文档集
* [ ] 01 篇:doc_values 是列式存储(聚合/排序用,与倒排并列)

### Why

徒弟:

> 候选集都有了,按"出现次数多就排前面"不行吗?

老陈:

> 纯词频排序有两个死法:
> 一是"的、了、是"这种停用词在每个文档里都出现,词频最高,但毫无区分度;
> 二是长文档天然词频高——500 页的书提 50 次"Java"和 5 页的小册子提 5 次"Java",谁更相关?
> 所以需要**逆文档频率**(区分度)和**长度归一**(惩罚长文档)共同参与。BM25 就是这两个直觉的显式公式。

| 方案 | 解决什么 | 留下什么问题 |
| ---- | ---- | ---- |
| 布尔匹配(AND/OR) | 命中判定 | 无排序,同分 |
| 纯词频计数 | 简单排序 | 停用词干扰、长文档占便宜 |
| BM25(ES 5.0+ 默认) | 词频饱和 + IDF + 长度归一 | 参数 k1/b 是工程经验值,需按场景调 |

### What

BM25 评分(ES 官方默认 k1=1.2, b=0.75;公式语义,非 API):

```
score(query, doc) = Σ_term IDF ×
  (tf × (k1 + 1)) /
  (tf + k1 × (1 - b + b × docLen/avgDocLen)) × boost

tf:词频,但"饱和"——出现 10 次不是出现 1 次的 10 倍分数(见实验)
IDF:逆文档频率——越稀有的词区分度越高
docLen/avgDocLen:文档长度与平均长度之比,长文档被惩罚
```

默认 `query_then_fetch` 使用各分片本地 term statistics;如果跨分片相关度排序确实需要全局 term statistics,可验证 `dfs_query_then_fetch`,但它会增加一次协调往返和执行成本。

query 上下文 vs filter 上下文:

```
query 上下文(must / match / should):参与评分,通常不具备 node query cache 资格;`size=0` 的完整请求仍可能进入 shard request cache
filter 上下文(filter / constant_score):不评分,具备进入 node query cache 的资格,仍受 segment/访问频率等条件约束
```

> 📌 最容易被误解的一点:"filter 不算分所以是弱功能"——恰恰相反,filter 具备 node query cache 资格;但 shard request cache 是另一层,默认关注 `size=0` 的完整请求。生产上**过滤条件(状态、时间、租户)通常该放 filter**。

### How

① `match text="beta gamma"` → 两个词项,分别查 postings,合并出候选集

② 每个候选文档按 BM25 对两个词项分别算分再求和

③ `constant_score`/`filter`:跳过评分,直接按 bitset 过滤

④ `size=0` 且带 `request_cache=true` 的请求,可以缓存 shard-level 响应;它是否包含 filter 不决定这层缓存的定义

实测锚点(实验 007,tf-test 受控数据,ES 8.15.3):

```
同词"alpha"不同词频的文档(单分片):
  t1 (1×)   : _score=0.1169
  t2 (2×)   : _score=0.1310
  t5 (5×)   : _score=0.1412
  t10 (10×) : _score=0.1450
  t20 (20×) : _score=0.1469   ← 词频 1→20 倍,分数只涨 ~26%:词频饱和
  long1(1×,长文档):_score=0.0526  ← 同样 1 个词,长文档分数腰斩:长度归一

shard request cache(size=0 请求包含 filter,连发 5 次):1 miss + 4 hits(第 1 次填充,后 4 次命中)
node query cache:本实验未单独测量
```

BM25 参数 k1=1.2/b=0.75:官方文档/源码默认值;`_settings?include_defaults` 不暴露该默认参数,但可用 `_search?explain=true` 查看一次具体评分分解。本实验只验证评分趋势,未用 `explain` 完成 k1/b 的独立复核。

### Transfer

- 评分模型的"饱和 + 稀有度 + 长度归一"三件套,可以迁移到任何排序场景(推荐、召回重排)。
- "计算分层"思想:把**高频的过滤**(不需要算分)与**低频的评分**拆开,是缓存与 CPU 预算的通用切法。
- 本层留下的新账:**默认 query_then_fetch 用的是"这个分片看到的词频"——文档分散在多个分片后,全局 IDF 和分片 IDF 不一致;什么时候要用 `dfs_query_then_fetch` 换取更一致的相关度?**——逼出 Level 3 的两阶段查询。

### Level Ending

🔴 口诀:评分走 BM25,过滤走缓存。

<a id="level-3"></a>

## Level 3

一句话认知墙:**查询是"每分片本地算 top-N + 协调节点归并"的两阶段过程,归并窗口的大小就是 from+size,这是深分页问题的源头。**

### 前置知识关卡

* [ ] Level 2:评分公式与上下文
* [ ] 02 篇:数据按 hash(routing)%N 分布到分片,主副本同数据

### Why

徒弟:

> 数据在 3 个节点上,那把每个分片的结果都收回来再排序不就行了?

老陈:

> 可行,但"每个分片都收全量"在大索引上是灾难——数据得全搬到协调节点。
> 正确的做法是**两阶段**:每分片本地算好"我要的 top-N",只把这一小撮发给协调节点归并。
> 但这里埋着一个炸弹:**分片不知道全局排名**,为了不丢正确文档,它必须多收集一点——收集多少?`from+size`。你翻得越深,每个分片要交出来的候选就越多,协调节点的内存就越大。

| 方案 | 解决什么 | 留下什么问题 |
| ---- | ---- | ---- |
| 单机全量排序 | 简单正确 | 不可扩展 |
| 每分片全量传输 | 正确 | 网络/内存爆炸 |
| 两阶段(top-N 归并) | 少传、快 | 归并窗口 = from+size,深翻页放大(Level 5) |

### What

两阶段查询(ES 8.15.3,官方"query-then-fetch"流程):

```
             协调节点
              │
     ① query phase:扇出
    ┌────┬────┬────┐
   shard0 shard1 shard2       每分片:本地评分 → 取 top (from+size)
    └────┴────┴────┘
              │ ② 只回传:文档 ID + 分数 + 排序字段(不含 _source)
              ▼
   协调节点归并排序 → 取全局第 from..from+size 名
              │
     ③ fetch phase:按文档 ID 去各分片取 _source
              ▼
   返回最终结果
```

估算边界:**协调节点需要处理的候选量级 ≈ 实际参与查询的分片数 × (from+size)**;实际内存还受 `pre_filter_shard_size`、`batched_reduce_size`、排序方式和 collector 实现影响。这是容量估算模型,不是严格内存不变量。

> 📌 最容易被误解的一点:无 PIT 时,同分/同排序值的 tie-break 依赖 Lucene internal doc ID,不同 replica 之间可能不同;使用 PIT 时,ES 会自动加入 PIT 内唯一的 `_shard_doc`。所以跨请求分页要么使用 PIT,要么显式提供稳定唯一的业务排序字段。

### How

① 用户发 `_search` 到任意节点(该节点成为 coordinating)

② 计算目标分片(默认覆盖目标索引的逻辑分片;routing 或 `preference=_shards:...` 才能限制分片;普通 `preference` 主要选择节点/副本)

③ query phase 并行发往各分片所在节点

④ 各分片返回窗口数据,协调节点归并

⑤ fetch phase 回源取 _source,拼装返回

实测锚点(实验 008,page-test):

```
_cat/shards:page-test 的 3 个主分片分别在 n3 / n2 / n1
→ 一次查询真实扇出 3 个节点(不是单机行为)
scroll 打开后 _nodes/stats 显示 open_contexts = [1, 1, 1]
→ 每个节点都持有一个上下文,归并确实是分布式的
```

### Transfer

- "本地 top-N + 归并"是分布式算法的通用骨架:MapReduce 的 reduce 阶段、Spark 的 takeOrdered、分库分表的全局分页,全是同一思想。
- 归并窗口通常按"实际参与分片数 × 参数"放大,可作为"分布式排序/分页"的容量估算起点,但必须结合 `batched_reduce_size` 与真实 heap 实测。
- 本层留下的新账:**聚合也走同样的扇出,但聚合要的是"全量统计",不是 top-N——它怎么在只收集一小撮的情况下给出结果?**——逼出 Level 4 的近似聚合。

### Level Ending

🔴 口诀:本地取顶归并排,窗口大小定成败。

<a id="level-4"></a>

## Level 4

一句话认知墙:**聚合的"不准"不是 bug,是三种机制(截断、HLL++、T-Digest)用可控误差换规模;doc_count_error_upper_bound 是 ES 给你的误差账单。**

### 前置知识关卡

* [ ] Level 3:扇出 + 归并机制
* [ ] 01 篇:doc_values 列式存储,聚合读它不读倒排

### Why

徒弟:

> 统计嘛,每个分片把计数传回来,协调节点一加,不就精确了吗?

老陈:

> 计数能加,但聚合不是只有计数:
> "排名前 10 的品类"——每个分片只知道自己的 top-N,全局第一可能在每个分片都排不进前 N(实验 007 当场打脸);
> "全馆有多少种书"——精确去重要把所有唯一值都传上来,内存爆炸;
> "借阅时长的 p99"——精确百分位要全量有序数据,同样爆炸。
> 所以三个最贵的统计分别用三种近似换规模:**top-N 截断、HLL++ 概率计数、T-Digest 质心合并**。

| 方案 | 解决什么 | 留下什么问题 |
| ---- | ---- | ---- |
| 全量收集/外部精确统计 | 在定义的数值类型与快照内可作为真值 | 内存/网络爆炸,不可扩展 |
| top-N 截断(terms) | 排名统计 | 跨片高频词可能整体丢失(实测) |
| HLL++(cardinality) | 去重计数 | 本次单分片实验误差 -0.68%;不是通用误差保证 |
| T-Digest(percentiles) | 百分位 | 本次聚类数据的 p99 偏差较大;不是通用误差结论 |

### What

**聚合三大家族不是三套孤立 API,而是同一棵结果树上的三个职责**:

| 家族 | 负责什么 | 典型类型 | 分布式边界 |
| ---- | ---- | ---- | ---- |
| Bucket | 把命中文档分成一组组桶 | `terms`、`range`、`date_histogram`、`filters`、`composite` | terms Top N 可能被分片候选截断;composite 通过 `after_key` 分页 |
| Metric | 对当前桶计算数值 | `sum`、`avg`、`min`、`max`、`cardinality`、`percentiles` | 可合并指标与近似指标边界不同 |
| Pipeline | 读取已经生成的桶/指标再计算 | `derivative`、`cumulative_sum`、`bucket_script`、`avg_bucket`、`bucket_sort` | 发生在非 Pipeline 聚合之后,不能反过来参与分片候选选择 |

`size: 0` 只表示不返回 hits,不会跳过 query 过滤和聚合执行。一个聚合请求的逻辑执行骨架是 **MapReduce-style**,不是 Hadoop MapReduce 框架:

```text
query 过滤命中文档
       ↓
Map: 每个分片读取 doc_values,构造本地 Bucket/Metric 状态
       ↓
Reduce: 协调节点合并桶与可合并指标
       ↓
Pipeline: 对已经合并的桶/指标计算 derivative、比例、累计值
       ↓
返回聚合树
```

关键不变量:**Pipeline 只能消费已经存在的聚合输出;它不能让分片重新找回已经被 terms 的 `size/shard_size` 截断的桶。**因此先解决 Bucket 候选是否完整,再讨论 Pipeline 的二次计算。

三种近似机制:

```
① terms top-N 截断(实验 007 核心,默认按 `_count desc`)
   每分片本地取 top shard_size,默认 shard_size = size*1.5+10
   全局第一如果每片都进不了本地 top-shard_size → 整体消失
   在 `_count desc` 下,误差账单 = 每片最大被截断桶之和;
   `_count asc`/按子聚合排序时可能无法计算有界误差

② HLL++(cardinality)
   低基数可走 linear counting,高基数使用 HLL++ 状态;
   分片状态合并时按寄存器逐位取最大值,不是按位 OR
   状态内存受 precision 控制,不随唯一值数量线性增长
   precision_threshold 以内是"预期接近准确",不是契约级精确

③ T-Digest(percentiles)
   把分布压缩成"质心"(均值+权重),分片间合并质心
   compression 影响质心压缩;具体误差取决数据分布/规模,本次聚类数据的 p99 出现明显偏差
```

**哪些聚合可合并、哪些仍然近似**(重要边界):

| 聚合 | 精确性 | 原因 |
| ---- | ---- | ---- |
| value_count / sum / min / max | 逻辑上可合并 | 结果仍受字段类型与浮点表示影响;`value_count` 统计值数量 |
| avg | 逻辑上可合并 | sum/count 合并;浮点输入仍有数值误差 |
| terms(单分片) | 精确 | 无截断(实验 007:error=0) |
| terms(多分片,按 _count 降序) | 近似 | 截断,有误差上界 |
| composite | 可完整枚举 bucket | 外层分页不改变子聚合语义;跨请求一致性需 PIT/冻结数据 |
| cardinality | 近似 | HLL++ |
| percentiles | 近似 | T-Digest |

> 📌 最容易被误解的一点:`doc_count_error_upper_bound=0` 只在 terms 的可计算误差语义下有意义,不代表所有聚合都精确;`sum_other_doc_count=29100` 是本实验单值 term 字段中未返回桶的文档计数,多值字段下它可能重复计数同一文档。

### How

① terms 聚合:各分片读 doc_values,本地统计 top shard_size

② 协调节点合并候选集,取全局 top size

③ cardinality:各分片 HLL++ 状态合并,查表得估计值

④ percentiles:各分片 T-Digest 质心,合并后插值

实测锚点(实验 007,ES 8.15.3,agg-err 4 分片 vs agg-single 1 分片):

```
构造:每片 15 个热点词×500 + 共享词 t5×150(全局 600,全局第一)

agg-err(size=3,默认 shard_size=14):
  error_upper_bound=2000  sum_other=29100
  heavy-0-1 500 / heavy-0-10 500 / heavy-0-11 500
  ← t5(600)整体丢失:每片本地第 16 名,被 shard_size=14 截断

agg-single(同数据,1 分片):t5=600 第一,error=0  ← 真值

agg-err(size=3,shard_size=1000):t5=600 找回,error=0
  ← 放大 shard_size 的代价:每片候选更多,协调节点内存/网络更大

error_upper_bound=2000 = 每片最大被截断桶 500 × 4 片 ← 与官方公式一致

cardinality(100,000 唯一值,单分片):
  默认阈值:99,319(-0.68%);precision_threshold=40000:100,060(+0.06%)
  ← HLL++ 是数据结构级近似;本实验未验证多分片与单分片误差是否相同

percentiles(T-Digest,聚类分布,真值 p99=200):
  compression=100(默认):p99=555.33(偏 2.8 倍)
  compression=10          :p99=584.54,p50=18.06(全面偏离)
  compression=1000       :p99=633.17(本次数据中不降反升 ← 质心合并与分布相关)
```

**Pipeline 的执行边界**:

```json
{
  "size": 0,
  "aggs": {
    "sales_per_day": {
      "date_histogram": {
        "field": "create_time",
        "calendar_interval": "day"
      },
      "aggs": {
        "daily_sales": { "sum": { "field": "amount" } },
        "sales_derivative": {
          "derivative": { "buckets_path": "daily_sales" }
        }
      }
    },
    "avg_daily_sales": {
      "avg_bucket": { "buckets_path": "sales_per_day>daily_sales" }
    }
  }
}
```

- `derivative` 是 Parent Pipeline,在 `date_histogram` 的桶内读取相邻桶的 `daily_sales`。
- `avg_bucket` 是 Sibling Pipeline,在同级读取 `sales_per_day>daily_sales`。
- Pipeline 聚合不能用于 terms 的分片候选排序;`bucket_sort` 也只能排序父聚合已经返回的桶,不能把未进入父聚合 `size` 的桶找回来。
- `moving_avg` 已从 ES 8.15 移除,需要移动窗口时使用 `moving_fn` 并明确 `window`、`gap_policy` 和脚本。

### Transfer

- "误差上界显式化"是工程良心:ES 用 `doc_count_error_upper_bound` 把近似程度变成可读数字,任何做近似的系统都应该输出类似账单。
- 概率数据结构的迁移:HLL++ 的"固定内存边界 + 可合并"特性被用在流量统计、AB 实验去重等所有"不能存全量唯一值"的场景。
- 本层留下的新账:**近似聚合和深分页是同一个病根——"协调节点内存 vs 数据规模"**——Level 5 看翻页怎么被 from+size 放大。

### Level Ending

🔴 口诀:截断 HLL 质心,误差上界摆明。

<a id="level-5"></a>

## Level 5

一句话认知墙:**深分页的三种方案对应三种边界:from+size 受窗口与硬边界约束,scroll 持有搜索上下文,search_after 需要稳定的排序元组;生产选型就是在这些成本里选择可控的一种。**

### 前置知识关卡

* [ ] Level 3:归并窗口 = from+size
* [ ] Level 4:协调节点内存是聚合与分页的共同瓶颈

### Why

徒弟:

> 用户要看第 1000 页,`from=9990, size=10` 不就行了?

老陈:

> 三个死法等着你:
> **from+size**:每分片都要收集 from+size 个候选,协调节点处理量级约为实际查询分片数 × (from+size);到第 10000 页就是每分片 10 万候选——更糟的是 ES 直接给你设了硬边界 `max_result_window=10000`,越界报错,根本不让你翻;
> **scroll**:它规避了窗口,但每个分片都要在节点上挂一个"搜索上下文"快照;忘了清会让资源持续占用到 TTL,不是永久泄漏;
> **search_after**:它既不放大窗口也不挂 scroll 上下文,但需要稳定的全序排序;无 PIT 时通常要显式加入唯一字段,字段不唯一会静默丢数据。

| 方案 | 解决什么 | 留下什么问题 |
| ---- | ---- | ---- |
| from+size | 简单、可跳页 | 窗口随 from 放大;硬边界 10000 |
| scroll | 受控批处理/大结果集导出 | 上下文占节点堆和旧 segment,必须 clear;非实时快照 |
| search_after | 无窗口、无 scroll 上下文 | 需要稳定排序元组;不可跳页 |

### What

```
from+size    :协调节点候选量级 ≈ 实际查询分片数 × (from+size);默认上限 10000
search_after :把"上页最后一条的排序值"作为游标传回
              语义:按完整排序元组和各字段方向取游标之后的下一批 → 无窗口、天然分页
scroll       :查询时在每分片挂"搜索上下文"(open_contexts),存快照 ID
              scroll=1m 续期;用完必须 DELETE,超时后也会自动释放,但 TTL 内仍占资源
PIT(point in time):固定时间视图 + search_after;PIT 自动加入唯一的 _shard_doc tie-breaker
                    深分页优先用 PIT + search_after(8.x 官方推荐)
```

> 📌 最容易被误解的一点:search_after 不是"跳页神器",它**不能跳页**(没有"第 N 页"概念),只适合"上一页下一页";要随机跳页,数据量小就 from+size,数据量大请重新设计产品交互。

### How

① from+size:查询 → 每分片取 top(from+size) → 协调节点归并丢弃前 from 个

② scroll:首次 `_search?scroll=1m` 拿 _scroll_id → 后续 POST /_search/scroll 续期取下一页 → 用完 DELETE

③ search_after:把上一页最后一条的**完整 sort 数组**传回,下一请求使用同一 query/sort;PIT 场景还要传回最新 PIT ID

实测锚点(实验 008,page-test,15 万 docs,3 分片):

```
from+size 越界(from=9991,size=10 → 10001 > 10000):
  "Result window is too large, from + size must be less than or equal
   to: [10000] but was [10001]. See the scroll api for a more efficient
   way to request large data sets."  ← 错误文案提到 scroll;ES 8.15 文档对深分页更推荐 PIT + search_after

提窗到 100000 后 from=50000:0.240s / 0.050s / 0.052s
  (热缓存小数据,延迟差异不大;机制成本在窗口与堆,生产大索引必须实测)

scroll:open_contexts 1,1,1（3 分片 3 节点各挂一个）→ clear 后 [0,0,0]
  ← 上下文会保留旧 segment/文件句柄并可能增加堆压力,clear 是主动释放,TTL 是兜底

search_after(排序字段 docnum 唯一):5 页 0-49,无重复无缺失 ✓

search_after(排序字段 tag,a/b/c 三值,50,000 个 a):
  page1: a×10 / page2: b×10 / page3: c×10 / page4: 空
  ← 游标 ["a"] 跳过了剩余 49,990 个 a!静默丢失 99.98%
```

### Transfer

- 游标分页(search_after)是"无状态服务 + 有状态数据"的经典解法,和 MySQL 的 keyset pagination、Kafka 的 offset、Redis SCAN 同构;需要一致快照时配 PIT。
- "窗口/上下文/游标"三分法是所有列表接口的选型框架:窗口浅、上下文短、游标稳。
- 本层留下的新账:**聚合近似、深分页、评分归并都是"规模与精确/内存"的同一笔账**——Level 6 把它们收成一组生产决策。

### Level Ending

🔴 口诀:深翻爆内存,游标要唯一。

<a id="level-6"></a>

## Level 6

一句话认知墙:**神话 7/8 打穿:聚合的近似和深分页的爆炸都不是偶然,是分布式"本地 top-N 归并"模型的必然;生产决策就是把"要什么精度、要什么交互、要多大规模"讲清楚。**

### 前置知识关卡

* [ ] Level 1-5 全部机制
* [ ] 02 篇:green ≠ 数据安全(铁律 2)

### Why

徒弟:

> 所以"聚合一定精确"和"深分页随便翻"这两个神话,本质是同一个?

老陈:

> 是。**它们的病根都是:数据不在一个节点上,而协调节点只有有限内存。**
> 神话 7 的真相:要完整枚举 bucket,要么让数据小到能全量(单分片或 composite 分页),要么换一个为全量扫描设计的存储(OLAP);数值精度和跨请求一致性仍要单独验证;
> 神话 8 的真相:翻页越深,每分片候选集越大,协调节点堆越撑不住,所以 ES 用 max_result_window 直接把门焊死。
> 而神话 4("分片越多性能越好")在这里再补一刀:**分片越多,top-N 截断的误差面越大**(默认 `_count desc` 下每片都截断一次,误差上界是各片之和;其他排序不套用这条公式)。

| 神话 | 真相 | 机制 |
| ---- | ---- | ---- |
| 7 聚合结果一定精确 | 截断/HLL++/T-Digest 三种近似;`doc_count_error_upper_bound` 只在可计算排序下是误差账单 | Level 4 实验 007 |
| 8 from+size 深分页没事 | 窗口线性放大 + 硬边界 10000;三方案各有死法 | Level 5 实验 008 |
| 4 分片越多性能越好(补刀) | 分片多 → 截断面大、merge 放大(01 篇)、每分片开销 | 02/01 篇 + Level 4 |

完整因果链(电梯版):

```
倒排免扫描 → 但要排序 → BM25 评分 → 数据在分片上 → 两阶段归并
    → 归并窗口 = from+size → 深分页爆炸(神话 8)
    → 聚合只收 top-N → 三种近似(神话 7)
    → 生产决策:精度/交互/规模三问
```

### What

决策卡速览(详见文末):

| 决策 | 推荐 | 关键机制 |
| ---- | ---- | ---- |
| 过滤条件 | 通常进 filter 上下文 | node query cache 具备资格;shard request cache 另按 `size=0` 请求验证 |
| 聚合精度敏感 | composite 分页完整枚举 bucket / 小数据单分片验证 / 大数上 OLAP | top-N 截断与 HLL++/T-Digest 近似;子聚合和快照边界仍需验证 |
| 翻页交互 | search_after + PIT;导出用 scroll 并保证 clear | 窗口/上下文/游标三分法 |
| terms 调参 | 用 show_term_doc_count_error 监控误差上界 | 截断公式 + shard_size 代价 |

> 📌 最容易被误解的一点:ES 不是"所有统计的正确答案"。精确对账、精确去重、精确百分位,ES 从来都不是对的工具——这不是缺陷,是设计取舍,选型时必须按精度要求分流。

### How(生产排查路径)

```
聚合结果存疑:
  GET index/_search {aggs:{t:{terms:{field,size,show_term_doc_count_error:true}}}}
  → 按 `_count desc` 前提看 doc_count_error_upper_bound 与 sum_other_doc_count
  → 不可接受:composite 分页完整枚举 bucket(必要时配 PIT);或换 OLAP(ClickHouse)

翻页报错 "Result window is too large":
  → 先查 max_result_window(默认 10000)
  → 用户翻页:search_after + PIT(固定 query/sort,使用完整 sort 数组)
  → 数据导出:scroll(记得 clear,监控 open_contexts)

查询慢:
  → 先分 filter(可缓存)/ query(评分) 上下文,再谈分片与调参
  → 分开看 `_nodes/stats/indices/query_cache` 与 `_nodes/stats/indices/request_cache`
```

### 生产资源治理:字段、桶、熔断器、Profile

**1. 先确认聚合字段的存储路径**

| 字段形态 | 聚合/排序入口 | 主要风险 |
| ---- | ---- | ---- |
| `keyword`、numeric、date | 默认使用 `doc_values` | 仍有磁盘/Page Cache/CPU 成本,但不把整列默认加载为 text fielddata |
| `text` | 默认不能聚合/排序 | 强行开启 fielddata 会把分词值加载到 JVM heap,高基数时可能触发 breaker |
| `text` + `keyword` 子字段 | `title.keyword` 做精确分桶 | 需要在 mapping 设计阶段承担额外索引/存储成本 |

```json
{
  "title": {
    "type": "text",
    "fields": {
      "keyword": { "type": "keyword" }
    }
  }
}
```

`doc_values` 不是"零内存"保证,fielddata 也不是"一定立刻 OOM";正确的判断是看字段类型、基数、文档范围、heap、Page Cache 和 breaker 指标。生产上不要把开启 text fielddata 当成默认优化方案。

**2. 先算 bucket 上界,再决定嵌套与 collect mode**

```text
terms(category) × terms(status) × terms(region)
候选桶上界 ≈ |category| × |status| × |region|
```

嵌套层级会放大 bucket、子聚合和协调节点 reduce 成本,实际还受 `size`、`min_doc_count`、数据分布和 `search.max_buckets`(默认 65536)约束。`depth_first` 与 `breadth_first` 不是"低/高基数固定选项":是否值得使用 `breadth_first`,必须结合父桶排序、子聚合成本和真实 profile/heap 压测判断。

**3. 把熔断器当拒绝保护,不是容量方案**

ES 8.15 默认值(具体还要核对 `use_real_memory` 与集群设置):

| Breaker | 默认语义 |
| ---- | ---- |
| Parent | `use_real_memory=true` 时默认 JVM heap 的 95%;关闭 real-memory 时起始限制为 70% |
| Fielddata | JVM heap 的 40% |
| Request | JVM heap 的 60%,主要保护单请求结构,包括聚合中间结构 |
| In-flight requests | JVM heap 的 100%,受 parent breaker 约束 |

breaker 只跟踪部分内存,不是 OOM 的完整保证。看到 `CircuitBreakingException` 时优先缩小 query 范围、降低 bucket/page、改用 composite 或预聚合;调高 breaker 是经过容量验证后的最后手段,不能作为默认修复。

**4. 高基数全量遍历优先 composite,但不能宣称 O(1)**

`composite` 按 `size` 返回一页 bucket,通过 `after_key` 继续。它避免一次性把全部 bucket 返回,但单页仍受分片数、page size、子聚合和排序影响;官方文档明确要求上线前压测。

```json
{
  "size": 0,
  "aggs": {
    "by_category_day": {
      "composite": {
        "size": 500,
        "sources": [
          { "category": { "terms": { "field": "category.keyword" } } },
          { "day": { "date_histogram": { "field": "create_time", "calendar_interval": "day" } } }
        ]
      },
      "aggs": {
        "sales": { "sum": { "field": "amount" } }
      }
    }
  }
}
```

`after` 必须使用上一页返回的 `after_key`;composite 按 source 字典序分页,不是按 `doc_count` 排 Top N。需要跨页一致快照时,要配合稳定数据窗口/PIT，并单独验证子聚合语义。

**5. Profile 负责定位,不负责证明优化有效**

```json
GET /orders/_search
{
  "profile": true,
  "size": 0,
  "aggs": {
    "by_brand": {
      "terms": { "field": "brand.keyword", "size": 20 },
      "aggs": { "avg_price": { "avg": { "field": "price" } } }
    }
  }
}
```

重点看 `profile.aggregations` 中的耗时、分片差异和 collector 路径;Profile 本身有额外开销,不能把 Profile 请求的时间当成线上 p99。`global_ordinals`、`map` 等 execution hint 只能作为待验证假设,不要把某个基数阈值或 GC 百分比写成通用规律。

### Transfer

- "三个问题定方案"(精度/交互/规模)可以套用到任何"数据不在一个节点"的系统选型。
- 误差可观测是近似的底线:任何用近似换规模的系统,都必须输出误差边界,否则就是埋雷。
- 本系列因果链推进:04 篇把"直觉写法"放大到生产规模看失控(脚本/wildcard/并发),05 篇用 Mapping 与集群规划把机制约束落地。

<a id="pitfalls"></a>
# ⚠️ 坑与细节

## 坑 1

错误理解:"聚合结果一定精确,误差上界为 0 就安全。"

原因:error_upper_bound=0 只说明**返回的桶没被截断**(且要满足可计算误差的排序前提),不代表没有丢失的全局高频桶;本实验单值字段中的 `sum_other_doc_count` 才表示未返回桶的文档计数。

比喻后果:管理员说"统计没问题",其实 29100 本书的借阅记录没进报表。

线上现象:报表数字与数据库对不上,排查半天才发现是 terms 截断。

修正:仅在 `_count desc` 下看 `error_upper_bound`;同时看 `sum_other_doc_count`、`shard_size` 与 `size` 的关系(实验 007)。

## 坑 2

错误理解:"size 调大聚合就精确了。"

原因:size 只决定**最多返回多少桶**;分片候选截断由 **shard_size** 决定;实际创建的 bucket 总数受 `search.max_buckets=65536` 限制(实验:terms size=200000 报 too_many_buckets)。

比喻后果:管理员说"多打印 100 行",可分馆交上来的候选还是那么点。

线上现象:terms agg 大 size 查询 OOM 或 max_buckets 报错。

修正:需要完整枚举 bucket → composite 分页;需要排名精度 → 调 shard_size,并在可计算误差的排序下监控误差上界。

## 坑 3

错误理解:"from+size 是翻页,想翻哪页翻哪页。"

原因:每分片候选集量级约为 from+size,协调节点内存会随实际查询分片数放大;ES 用 max_result_window=10000 焊死(实验 008 报错原文)。

比喻后果:读者翻到第 5000 页,管理员要把每个分馆最厚的 5 万本书全搬到前台。

线上现象:"Result window is too large" 报错;from 大时协调节点 GC。

修正:稳定翻页用 search_after + PIT;受控批处理/导出可用 scroll 并主动 clear;报错文案官方都帮你写了。

## 坑 4

错误理解:"search_after 随便找个字段排序就行。"

原因:排序字段非唯一时,游标等于"跳过所有等于游标值的文档"——实测 50,000 个 a 只翻出 10 个(实验 008)。

比喻后果:按"借阅次数"翻页,同次数的书被整批跳过,读者永远看不到。

线上现象:分页结果总量远小于应返回量,且没有报错——静默丢数据,最危险。

修正:无 PIT 时排序 = 业务字段 + 稳定唯一业务字段;PIT 内使用响应返回的完整 sort 数组,其中包含隐式 `_shard_doc`。

## 坑 5

错误理解:"scroll 用完了不用管,反正有超时。"

原因:scroll 上下文按分片挂在节点上(实测 open_contexts=[1,1,1]);1m 是续期窗口,超时后会自动释放,但 TTL 内会保留旧 segment/文件句柄并可能增加堆压力。

比喻后果:管理员借了索引卡不还,卡片堆满前台。

线上现象:_nodes/stats 里 open_contexts 持续上涨,节点堆水位升高。

修正:finally 里 DELETE scroll;限制并发和 keep_alive,监控 open_contexts/segment/文件句柄;深分页优先 PIT + search_after。

## 坑 6

错误理解:"filter 不算分,是弱查询;match 才算真查询。"

原因:反了。filter 不评分 → 具备 node query cache 资格;本实验的 5 连发 4 命中是 `size=0` shard request cache,不是 node query cache 证明。过滤条件(状态/时间/租户)通常该放 filter。

比喻后果:读者每次都要管理员重新"评估"书,不能直接翻索引卡。

线上现象:同一过滤条件的查询反复全量执行,CPU 高、缓存命中率低。

修正:bool 里 must 只放评分词,过滤条件全放 filter。

<a id="decisions"></a>
# 🏆 生产决策卡

## Decision Card 1:聚合精度敏感(报表/对账)

### 场景

财务/运营报表要对账,聚合结果必须精确,数据量千万级。

### 判断

terms 多分片可能截断,HLL++/T-Digest 是近似——先问"误差可接受吗";如果要对账,还要定义数值类型、容差和一致快照。

### Mechanism → Decision

| 机制 | 工程决策 |
| ---- | ---- |
| top-N 截断/HLL++/T-Digest | 精确需求 → 不用这三类聚合做最终答案 |
| composite 分页 | 完整枚举 bucket;需要一致快照时配 PIT,子聚合仍按自身语义计算 |
| 单分片 terms | 小索引可临时单分片验证 terms 真值(实验 007) |
| 数据规模 | 大数精确统计 → 换 OLAP(ClickHouse/数仓) |

### Code

```json
{"size":0,"pit":{"id":"<latest-pit-id>","keep_alive":"1m"},"aggs":{"c":{"composite":{"size":2000,"sources":[{"uid":{"terms":{"field":"uid"}}}]}}}}
```

### 禁止决策

不要为了精确把 terms size 调到几万——max_buckets=65536 上限 + 协调节点 OOM 风险。

### 验收指标

- p99 latency(composite 全量导出)、协调节点堆(GC 时长)
- 误差验收:terms 按 `_count desc` 时记录 error upper bound;composite 验收 `after_key` 直到结束、bucket 不重复,并验证快照/子聚合语义
- CPU(不因大 size 聚合持续高)

## Decision Card 2:用户翻页/数据导出

### 场景

列表页上一页/下一页交互;或后台全量导出 100 万行。

### 判断

深分页交互 → PIT + search_after;受控批处理/导出 → scroll;能跳页的深翻页在数据量大时不存在。

### Mechanism → Decision

| 机制 | 工程决策 |
| ---- | ---- |
| from+size 窗口 | 按实际查询分片数 × (from+size)估算,交互翻页禁深 from+size |
| max_result_window=10000 | 越界即报错,当心用户深翻 |
| search_after 游标 | 无 PIT 时业务字段 + 稳定唯一字段;PIT 内使用完整 sort 数组 |
| scroll 上下文 | 受控批处理/导出可用,finally 必 clear,限制 TTL/并发 |
| PIT | 稳定视图 + search_after,自动加入 `_shard_doc` tie-breaker |

### Code

```json
{"size":10,"pit":{"id":"<latest-pit-id>","keep_alive":"1m"},"sort":[{"docnum":"asc"}],"query":{"match_all":{}},"search_after":[42,4294967298]}
```

> `42` 与 `4294967298` 必须替换成上一页最后一条 hit 返回的完整 `sort` 数组;第二个值只是 `_shard_doc` 的示例值。

### 禁止决策

不要"为了支持随机跳页"把 max_result_window 调到百万——这是把深分页内存炸弹手动拆掉保险。

### 验收指标

- scroll 场景的 open_contexts(主动 clear 后回落)、PIT close 成功率、max_result_window 报错数(监控告警)
- p99 latency、协调节点堆;导出任务内存峰值

## Decision Card 3:查询性能分层

### 场景

高 QPS 查询接口,大量过滤条件 + 少量评分词。

### 判断

过滤条件(状态/时间/租户)与评分词混在 must 里,会让过滤条件参与评分并失去 node query cache 的资格。

### Mechanism → Decision

| 机制 | 工程决策 |
| ---- | ---- |
| filter 上下文 | 过滤条件通常进 filter/constant_score,监控 node query cache 资格与命中 |
| shard request cache | 仅在适合的 `size=0` 重复请求上验证并监控 |
| BM25 评分 | 只有真正要排名的词进 query 上下文 |

### Code

```json
{"query":{"bool":{"must":[{"match":{"text":"beta gamma"}}],"filter":[{"term":{"tag":"a"}}]}}}
```

### 禁止决策

不要把普通 hits 查询放进 request cache 期待它自动命中;对重复的 `size=0` 聚合请求再评估 request cache。

### 验收指标

- indices.query_cache 与 indices.request_cache 命中/淘汰、p99 latency、CPU

## Decision Card 4:terms 聚合调参

### 场景

运营要看"Top 20 品类",误差要可控。

### 判断

先看现状误差,再决定 shard_size;不要盲调。

### Mechanism → Decision

| 机制 | 工程决策 |
| ---- | ---- |
| 截断公式 | show_term_doc_count_error 打开,记录上界 |
| shard_size 代价 | 需要更高精度 → 放大 shard_size(内存/网络换) |
| max_buckets | 实际创建的 bucket 总数受 65536 限制,全量用 composite |

### Code

```json
{"size":0,"aggs":{"t":{"terms":{"field":"term","size":20,"shard_size":500,"show_term_doc_count_error":true}}}}
```

### 禁止决策

不要同时对每个 terms 聚合都调大 shard_size——误差上界会降,但每查询内存线性涨。

### 验收指标

- error_upper_bound 随时间保持稳定、协调节点堆
- p99 latency、网络字节(_search 响应体大小)

## Decision Card 5:生产级聚合资源治理

### 场景

电商销售分析:按品类看 Top N,桶内要金额/去重用户/日趋势,同时面对高基数字段和多租户查询。

### 判断

先确认字段走 `doc_values`,再限制 query 范围和 bucket 数;Top N 接受误差就用 terms,需要完整遍历就用 composite;Pipeline 只负责对已生成结果加工。

### Mechanism → Decision

| 机制 | 工程决策 |
| ---- | ---- |
| `keyword`/numeric/date + `doc_values` | 聚合优先使用正确 mapping;不要默认开启 text fielddata |
| `terms` + `shard_size` | Top N 场景按 `_count desc` 监控 error upper bound,用压测决定 shard_size |
| `composite` + `after_key` | 高基数完整遍历;限制 page size,配合 PIT/稳定数据窗口验证一致性 |
| Pipeline | 对已完成的 Bucket/Metric 做 derivative、比例、累计;不能找回被父 terms 截断的桶 |
| Circuit breaker | 作为拒绝保护和告警信号;优先缩小范围/桶数,不要先调高阈值 |

### Code

```json
{
  "size": 0,
  "query": {
    "bool": {
      "filter": [
        { "range": { "create_time": { "gte": "now-30d" } } },
        { "term": { "status": "paid" } }
      ]
    }
  },
  "aggs": {
    "by_category": {
      "terms": {
        "field": "category.keyword",
        "size": 20,

        "show_term_doc_count_error": true
      },

        "distinct_users": {

            "field": "user_id.keyword",
            "precision_threshold": 1000
          }
        },

          "date_histogram": {
            "field": "create_time",
            "calendar_interval": "day"

```

`size`、`shard_size` 和 `precision_threshold` 是示例起点,不是性能承诺;上线前必须用真实数据分布和目标 p99 验证。

### 禁止决策

不要在 text 字段上开启 fielddata 解决 mapping 问题;不要用 `terms size` 代替 composite 遍历高基数 bucket;不要用 Pipeline 聚合掩盖父 Bucket 已经丢桶;不要把 breaker 阈值调高当成容量规划。

### 验收指标

- `took`/Profile aggregation time、p99 latency、QPS
- `search.max_buckets` 错误数、`doc_count_error_upper_bound`(仅适用的 terms 排序)
- JVM heap、fielddata/request breaker limit 与 tripped 次数、GC pause
- `indices.fielddata.memory_size_in_bytes`、聚合节点 CPU、磁盘/Page Cache、网络字节
- composite 页数、每页 bucket 数、`after_key` 完成率和重复/遗漏校验

# 🌍 跨语言视角

同一个问题:"数据分散,怎么排序/分页/统计?"

| 语言/系统 | 解法 | 与 ES 的对应 |
| ---- | ---- | ---- |
| Java(JDK) | Stream.sort 全量;外部归并排序 | 协调节点归并 = 归并排序的分布式版 |
| Go | sort.Slice 全量;分页常用 keyset(WHERE id > ?) | search_after 与 keyset pagination 同构 |
| Rust | iterators + 惰性求值;BTreeMap 有序 | 倒排的 term dictionary 即有序映射 |
| MySQL | LIMIT/OFFSET 深翻页慢;keyset 优化 | from+size 与 LIMIT/OFFSET 同病;search_after = keyset |
| Kafka | 分区 offset 顺序消费 | scroll 上下文 ≈ 消费位点(有状态游标) |
| MapReduce/Spark | 本地 top-N + reduce 归并 | 两阶段查询就是它的特化 |

底层判断力:

- **可加性决定可合并性**:sum/min/max/count/avg 在逻辑上可跨分片合并,但浮点输入仍有数值误差;不能无损合并的(top-N/去重/百分位)必须近似或全量收集。
- **游标 > 窗口**:任何"翻页/消费"场景,带唯一键的游标方案在规模上碾压窗口方案。
- **误差必须可观测**:近似系统的第一原则是让误差可见(ES 的 error_upper_bound),而不是假装精确。
