# 正文:五个 Level 打穿场景落地

## Level 1:场景分析框架——四问定调

<a id="level-1"></a>

### 认知墙

> **"所有业务都是搜索"**

徒弟:"日志要查、商品要查、运单也要查,那不都是搜索吗?全进 ES 呗。"

老陈:"你说的'查'是三种完全不同的机制需求:日志是'过滤+聚合',商品是'相关度排序',运单是'按单号精确点查'。它们对倒排、doc_values、translog、复制的依赖完全不同——不问清楚,选型就是掷骰子。"

### Why:为什么必须四问

神话 12 说"ES 就是能存 JSON 的 MySQL"——这个神话的死因不是"ES 不好",而是**把不同机制需求的场景装进同一个容器**。选型的本质不是比产品,是比"机制需求 × 机制供给"的匹配度:

```text
场景需求(四问)                    机制供给(01~06 篇)
├─ 读多写少?                   →  倒排 + filter 缓存(实验 007/008)
├─ 写多读少?                   →  追加写 + merge(01 篇)+ ILM(实验 011)
├─ 增长形态:时序?随机更新?      →  rollover 轮换 vs 更新=删+写(铁律 1)
├─ 一致性:最终一致可否?         →  近实时窗口(实验 001)+ 无事务(铁律 1)
└─ 查询形态:全文?精确?聚合?geo? →  倒排/term/doc_values/近似聚合(实验 007)
```

旧方案失败:看 demo 选型——"ES 搜索结果很炫"就选了 ES,"ClickHouse 快"就换了 ClickHouse。没有四问,选型依据是别人的 benchmark,而 benchmark 的场景永远不是你的场景(数字不可迁移,本系列禁止编造)。

### What:四问与机制需求的映射

| 问 | 答案形态 | 决定什么 |
| ---- | ---- | ---- |
| 读写比 | 读多写少 / 写多读少 / 均衡 | filter 缓存价值;refresh/translog 旋钮(实验 002) |
| 增长形态 | 时序追加 / 随机更新 / 有界 | ILM 轮换(实验 011);更新=删+写代价(铁律 1) |
| 一致性 | 最终一致可否 / 强一致必须 | 近实时窗口(实验 001);无事务(铁律 1) |
| 查询形态 | 全文相关 / 精确点查 / 聚合 / geo | 倒排 vs term vs doc_values vs geo(官方) |

关键不变量:**四问的输出必须是机制需求,不是产品名**。先写"我要什么机制",再写"哪个产品给得起"——顺序反了,选型就变成追星。

### 师徒对话

徒弟:"那 ES 到底适合什么?"

老陈:"适合'全文相关度 + 过滤 + 聚合'组合的场景,且写放大可以接受。我们先拿四问过三个场景——电商、日志、运单——你就能自己回答了。"

### 留下的新账

四问有了,第一个场景:电商搜索,读多写少。机制怎么组合?——Level 2 回答。

## Level 2:电商搜索——读多写少

<a id="level-2"></a>

### 认知墙

> **"电商搜索 = 数据库 LIKE 加速"**

徒弟:"商品搜索不就是'名字 LIKE 手机'吗?MySQL 加个索引不就行了?"

老陈:"LIKE 是子串匹配,不是分词检索。'苹果手机'和'手机苹果'是同一个商品吗?用户搜'水果手机'该不该出苹果?相关度排序、同义词、聚合导航,这些是倒排 + BM25 的领域——MySQL 全文的默认分词器不支持中文(可选 ngram)、相关度模型简单、无 BM25 可调参数(官方文档),LIKE 前导通配(`%xx`)更是全表扫描。"

### Why:为什么电商搜索适合 ES

电商搜索的四问画像:**读多写少**(用户浏览远多于下单)、**增长有界**(商品量级有限)、**最终一致可接受**(库存瞬时抖动可容忍)、**查询形态 = 全文相关 + 过滤 + 聚合导航**。这与 ES 机制供给的匹配度:

```text
需求                        机制
├─ 相关度排序              →  BM25(实验 007:词频饱和 + 长度归一,非线性)
├─ 类目过滤 + 价格过滤      →  filter 上下文(实验 007:_score=1.0,可缓存)
├─ 类目/品牌聚合导航        →  terms 聚合(实验 007:shard_size 截断边界)
├─ 翻页                    →  search_after + PIT(实验 008:非唯一排序丢数据)
└─ 库存/价格低频更新        →  更新=删+写,但低频 → 写放大可控(铁律 1)
```

关键机制:BM25 的"词频饱和"恰恰是电商要的——一个词出现 20 次和 100 次不该差 5 倍(实验 007:词频 1→20 倍,分数只涨 ~26%);长度归一让标题短的文档不吃亏(实验 007:同样 1 个词,长文档分数腰斩)。这是 LIKE 给不了的。

### 实验回链:三个必须守的边界

```text
① 聚合导航:terms 聚合有 shard_size 截断(实验 007:全局第一的 t5 被截断丢失)
   → 类目聚合默认可用,但"精确 top-N"要 size=0 + composite 分页(官方)
② 分页:from+size 默认最大 10000(实验 008:10001 直接报错)
   → 前端翻页必须 search_after + PIT,排序字段稳定唯一
③ 过滤与评分分开:不需要分数的条件(类目/价格)进 filter 上下文
   → 可缓存 + 不污染评分(实验 007/008:request cache 1 miss + 4 hits)
```

### 师徒对话

徒弟:"那库存扣减直接 update 商品文档,行不行?"

老陈:"低频可以——但你要知道每次 update 都是删+写(铁律 1):同一文档反复改,就是反复写放大。电商商品文档低频改没事;高频变动的字段(库存/价格)如果量级上来,就应该拆成独立的低频快照 + 高频事件流,或者直接交给交易系统,ES 只存搜索视图。"

电商是读多写少。反过来的场景呢?日志——写多读少。机制取舍会怎么反转?——Level 3 回答。

## Level 3:日志分析——写多读少

<a id="level-3"></a>

### 认知墙

> **"日志直接进 ES 就完事"**

徒弟:"日志不就是一直写一直查吗?ES 写入快,查询也快,完美。"

老陈:"你把这个场景想成了'读多写少'。日志的真实形态是:**写是持续的大流量,读是偶尔的过滤+聚合**。写入端吃的是 translog/refresh/merge(实验 002),读取端吃的是 filter 和聚合(实验 007)——两个旋钮的方向相反,你不可能两头都白拿。"

### Why:为什么日志场景要"反转"优化

日志分析的四问画像:**写多读少**(每秒百万条写入,查询按分钟级)、**时序追加**(不更新、不删除,只有保留期)、**最终一致可接受**(日志延迟可见性可容忍)、**查询形态 = 过滤 + 聚合**(按时间/服务名过滤,再聚合错误率/延迟分位)。

机制需求:

```text
写入端(实验 002):refresh 拉长/关闭 → 吞吐 891→364ms(约 2.4 倍)
  translog async → 崩溃丢窗口可接受(日志可重打,恢复预算决策,06 篇)
  bulk 分批 → 摊薄协调者开销(实验 010:大 bulk 协调者是更早瓶颈)

增长端(实验 011):ILM rollover 按 max_docs 轮换写索引,000002 接管写
  → 数据按时间切片,老索引进 warm/cold,保留期到点删索引
  → 磁盘水位是硬约束(神话 3:删除不立即释放,01 篇)

读取端(实验 007):近似聚合是默认姿势
  cardinality(去重 IP/用户):HLL++ 实测 100,000 唯一值 99319(-0.68%)
  percentiles(延迟分位):T-Digest 聚类分布 p99 实测偏 2.8 倍(555 vs 200)
  → 日志报表接受近似,精确值另算(或提高 precision_threshold/compression,代价内存)
```

### 关键机制:时序数据的"切片"是 Logs 的核心

日志不是"一个无限增长的索引",而是**按时间切片的一串索引**:rollover 轮换(实验 011:6000 docs 触发 000002 接管写)+ 每片独立生命周期(ILM phase hot→warm→cold→frozen,05 篇)。这带来三个机制红利:

```text
① 写索引永远只有一个 → 写入不被打散的写索引(05 篇决策卡)
② 老索引只读 → 不再产生新段,存量 merge 完成后收敛,磁盘成本趋稳
③ 删除按索引粒度 → 不依赖 merge 释放磁盘(神话 3 的解法)
```

### 师徒对话

徒弟:"那日志的精确统计怎么办?比如精确用户数。"

老陈:"先问业务:报表要的是'量级'还是'审计级精确'?量级 → HLL++ 够了;审计级 → 单独精确管道(如每天一次对账作业)。日志场景的默认姿势是'近似 + 定期精确对账',不是让查询永远精确——让每一条查询都精确,是把写多读少当成读多写少来设计。"

## Level 4:物流运单与地址匹配——高更新率

<a id="level-4"></a>

### 认知墙

> **"运单状态就是 update"**

徒弟:"运单状态一直变:已揽收、运输中、派送中、已签收——直接 update 运单文档不就行了?"

老陈:"你每 update 一次,ES 做的是删掉旧文档、写一个新文档(铁律 1:更新=删+写)。一个运单生命周期 10 次状态变更,就是 10 次删除 + 10 次写入,墓碑堆积、merge 吃 IO(实验 003)。高更新率 + 倒排索引,是机制上最不匹配的组合。"

### Why:为什么高更新率是 ES 的机制劣势

物流运单的四问画像:**更新频繁**(状态机多态)、**点查为主**(按运单号查)、**增长有界**(运单有生命周期)、**一致性要求高**(状态不能乱)。

机制冲突:

```text
ES 的强项:全文相关度 + 聚合。运单需要吗?几乎不需要。
ES 的弱项:更新=删+写(铁律 1)。运单的日常恰恰是更新。

写放大账(示例推算:假设输入,非实测):
  运单 1000 万单 × 每单 10 次状态变更 = 1 亿次"删+写"
  每次写入:translog fsync + 内存 buffer + refresh 成段 + 副本复制(02 篇)
  墓碑:旧版本标记删除,等 merge 才释放(实验 003)
  → 查询'当前状态'还要排除墓碑,段越多越慢
```

### 替代方案:事件化,而不是状态化

01 篇决策卡 1-2 已经给了答案:**状态变化作为事件追加,doc 只存最新快照(低频刷新)**:

```text
坏:每次状态变化都 update 整个运单文档(删+写 × 10)
好:运单状态作为事件追加(order-events 索引:append-only,无墓碑)
   查询当前状态:最近事件或低频快照
   → 写入形态从"随机更新"变成"时序追加",回到 ES 的机制舒适区
```

这是整个系列最重要的迁移: **"改数据模型,而不是改参数"**——06 篇说"调优边界外是架构问题",这里就是架构问题:不是把 update 调快,是消灭 update。

### 地址匹配:geo 是附加能力,不是理由

物流要"按坐标找网点""算距离"——这是 `geo_point`/`geo_shape`(官方字段类型):

```text
geo_point:经纬度点,支持 geo_distance / geo_bounding_box 查询
geo_shape:多边形,支持空间关系判断(官方文档)
→ 机制层:倒排之外的 BKD 树(官方文档),查询形态与全文完全不同
→ 本系列未做 geo 实验:性能、精度、数据量级下的表现一律"待验证"
→ 决策:地址匹配可以作为 ES 的附加能力,但"为了 geo 而选 ES"是单点选型,
   必须先用四问确认整体场景匹配(待验证部分生产压测)
```

### 师徒对话

徒弟:"那运单到底该不该用 ES?"

老陈:"四问回答你:点查为主 → 不需要倒排;高更新 → 机制劣势;强一致 → 无事务兜底。运单的核心存储应该留给事务型数据库(MySQL 系),ES 只做它擅长的:运单的搜索/聚合视图(按客户查历史、按区域聚合时效)——主存储与搜索视图分离,这是最常见也最正确的姿势。"

### 留下的新账

三个场景过完,结论是"有的场景该离开 ES"。最后一步:选型终局,把边界说清楚。——Level 5 回答。

## Level 5:选型终局——何时离开 ES

<a id="level-5"></a>

### 认知墙

> **"ES 能替代一切存储"**

徒弟:"那 MySQL、ClickHouse 这些,是不是迟早都被 ES 干掉?"

老陈:"反过来才是真相:ES 只在一个狭窄但重要的窗口里最强——全文相关 + 过滤 + 聚合。窗口外,MySQL 有事务和点查,ClickHouse 有列存聚合吞吐,它们各自占据机制不重叠的领域。神话 12 说的'ES 是能存 JSON 的 MySQL',恰恰是三种存储都做不到对方的事。"

### 选型对比:按机制,不按 benchmark

```text
MySQL(B+ 树 + 事务):
  强项:事务/行级点查/高更新率(机制:B+ 树页内更新 + undo + 事务日志)
  ES 没有的:ACID 事务、行锁、成熟的强一致(铁律 1)
  弱项:全文检索(默认分词器不支持中文、相关度模型简单,官方文档)

ClickHouse(列存 + merge tree):
  强项:宽表聚合、扫描吞吐(机制:列式压缩 + 向量化,官方文档)
  弱项:高频点查/行级更新(机制:列存不适配点查,更新=重写,官方文档)
  → 日志"宽表聚合"场景可替代 ES 的聚合部分,但全文相关/点查是短板
  → 所有性能对比数字"待验证",机制层面结论可推导,benchmark 禁止引用

OpenSearch(ES 7.10 分叉):
  机制:与 ES 同源,API 兼容分支(官方项目说明)
  差异:8.x 之后的功能演进分叉,版本级差异需逐个核对("待验证")
  → 选它的理由是合规/迁移成本,不是机制优势
```

### 何时离开 ES:三条判定

```text
① 需要事务/强一致,且写入不能接受最终一致 → 离开(MySQL 系)
② 高更新率且无法事件化 → 离开或改数据模型(Level 4)
③ 纯点查/宽表聚合,无全文需求 → 离开(MySQL 点查 / ClickHouse 聚合)
留下 ES 的理由只有一条:全文相关 + 过滤 + 聚合的组合需求,且写放大可控
```

### 神话 12 与铁律的收网

```text
神话 12"ES 就是能存 JSON 的 MySQL" → 打破:
  无事务(铁律 1)、弱一致(铁律 2)、更新=删+写(铁律 1)、聚合近似(铁律 1)
  → 它不是 MySQL,它是"搜索视图"专用存储

铁律 1:ES 不是"能存 JSON 的 MySQL"——本文把它落成选型判定
铁律 2:green ≠ 数据绝对安全——02 篇,备份在 05 篇
铁律 3:会写 REST API ≠ 懂 ES——00~07 篇的机制链就是它的注脚
```

### 师徒对话

徒弟:"所以 ES 到底赢在哪?"

老陈:"赢在它唯一擅长的窗口:全文相关 + 过滤 + 聚合,且写放大可控。这个窗口里它没有对手;窗口外它不是对手。选型不是站队,是让每种存储回到它机制最匹配的场景——这就是本文的收网:8 段机制旅程,落成一张决策卡。"

<a id="pitfalls"></a>

# ⚠️ 坑与细节

## 坑 1

错误理解:"所有查询都是搜索,全进 ES。"

原因:运单点查不需要倒排,日志聚合不需要相关度——机制需求不同(Level 1 四问)。

修正:先四问,再选型;ES 只进"全文相关 + 过滤 + 聚合"窗口。

## 坑 2

错误理解:"日志索引无限增长没关系。"

原因:磁盘水位是硬约束,删除不立即释放(神话 3,实验 003);不切片就等磁盘爆炸。

修正:ILM 按时间切片 + rollover 轮换 + 保留期删索引(实验 011)。

## 坑 3

错误理解:"运单状态直接 update 就行。"

原因:更新=删+写(铁律 1):高更新率 = 高写放大 + 墓碑堆积(实验 003)。

修正:事件化改造(决策卡 1-2),或主存储用事务型数据库,ES 只做搜索视图。

## 坑 4

错误理解:"为了 geo 选 ES。"

原因:geo 是附加能力(官方字段类型),性能"待验证";单点能力不能支撑整体选型。

修正:整体四问匹配才选;geo 需求先压测(生产验证,本系列未实测)。

## 坑 5

错误理解:"用 MySQL LIKE 做搜索。"

原因:LIKE 是子串匹配,前导通配(`%xx`)走全表扫描;MySQL 全文默认分词器不支持中文、相关度模型简单(官方文档)。

修正:全文需求 → ES/其他倒排引擎;MySQL 只做事务与点查。

## 坑 6

错误理解:"OpenSearch 就是 ES 换皮。"

原因:OpenSearch 是 ES 7.10 分叉的兼容分支(官方项目说明),8.x 之后的功能分叉,版本级差异需核对("待验证")。

修正:选它之前,把需要的 8.x 特性逐条对照分支版本。

## 坑 7

错误理解:"ClickHouse 比 ES 快,日志全迁。"

原因:快在哪、慢在哪必须分开:聚合吞吐 vs 点查 vs 全文相关,机制不同(列存 vs 倒排);benchmark 数字不可迁移。

修正:按查询形态分流:聚合走 ClickHouse,全文相关留 ES;数字"待验证"。

## 坑 8

错误理解:"选型看别人的 benchmark 就行。"

原因:benchmark 的场景不是你的场景;数字不可迁移(本系列禁止编造)。

修正:四问定机制需求 → 自己压测(生产负载 + 指标,06 篇)。

# 🏆 生产决策卡

## Decision Card 7-1:电商搜索

场景:商品搜索 + 类目/品牌/价格过滤 + 聚合导航。

判断:读多写少 + 全文相关 → ES 主存储(搜索视图)。

Mechanism → Decision:

| 机制 | 工程决策 |
| ---- | ---- |
| BM25 词频饱和/长度归一(实验 007) | 相关度排序依赖 BM25,不要自己写评分 |
| filter 上下文可缓存(实验 007/008) | 类目/价格进 filter,不污染评分 |
| terms 聚合 shard_size 截断(实验 007) | 聚合导航默认够用;精确 top-N 走 size=0 + composite |
| search_after 需唯一排序(实验 008) | 前端翻页 PIT + 稳定排序字段 |

禁止:LIKE 搜索;from+size 深翻页;高频 update 商品文档。

验收:p99 + 聚合误差上限(SLO)。

## Decision Card 7-2:日志分析

场景:日志/指标持续写入,按时间过滤 + 聚合报表。

判断:写多读少 + 时序追加 → ES(按时间切片)。

Mechanism → Decision:

| 机制 | 工程决策 |
| ---- | ---- |
| refresh/translog 旋钮(实验 002/001) | 写入端拉长 refresh、评估 async(恢复预算) |
| ILM rollover(实验 011) | 按时间切片,保留期删索引,磁盘水位可控 |
| HLL++/T-Digest 近似(实验 007) | 报表接受近似 + 定期精确对账;精确需求单独管道 |
| bulk 协调者瓶颈(实验 010) | 分批写入,避免超大 bulk |

禁止:让所有查询精确;不配 ILM 让索引无限涨。

验收:写入吞吐 + 磁盘水位趋势 + 报表误差上界。

## Decision Card 7-3:何时离开 ES(全系列收网)

场景:任意业务选型。

判断:四问输出机制需求 → 匹配度判定。

Mechanism → Decision:

| 机制 | 工程决策 |
| ---- | ---- |
| 全文相关 + 过滤 + 聚合(本系列) | 留在 ES:搜索视图存储 |
| 事务/强一致/高更新率(铁律 1) | 离开:MySQL 系(或事件化后留 ES 做视图) |
| 宽表聚合、无全文(官方机制) | ClickHouse(点查/更新弱,数字待验证) |
| 兼容分支(官方项目说明) | OpenSearch 只在迁移/合规理由下选,8.x 差异待核对 |

禁止:benchmark 选型;单点能力(geo)支撑整体选型。

验收:选型报告 = 四问 → 机制需求 → 匹配度 → 压测指标(06 篇方法论)。

<a id="cross-language"></a>

# 🌍 跨语言视角

## MySQL FULLTEXT 与倒排

InnoDB FULLTEXT 也是倒排,但默认分词器不支持中文(可选 ngram)、相关度模型简单、无 BM25 可调参数、无分布式(官方文档)。同样叫"全文",机制完备度差一个量级——选型对比必须落到"机制供给",不是"都叫搜索"。

## PostgreSQL GIN 与 Lucene

PG 的 GIN 索引能加速部分文本查询,但评分模型、分词生态、分布式聚合仍是 Lucene 的领地。机制边界:数据库的全文是"查询加速",ES 的全文是"检索产品"。

## ClickHouse 与 ES:同一类,不同层

两者都是"追加写 + 后台合并"家族(merge tree vs segment merge),旋钮同构(批量/刷新/合并策略,06 篇方法论可迁移)。差别在读取形态:列存聚合 vs 倒排检索——**同一个家族,不同的读取器官**。

## 方法论沉淀

"场景四问 → 机制需求 → 机制供给匹配 → 压测验证"是通用存储选型框架,不限于 ES:任何选型,先问场景的机制需求,再谈产品。
